## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **파일 업로드**(multipart/form-data)를 받는 엔드포인트를 만들고, JSON+base64와의 차이를 안다.
- 파일 입력에도 **계약을 세운다** — 크기 상한(413) · 내용 검증(415) · 형식 통일.
- W17 이미지 모델과 W18 텍스트 모델을 **각각 API 프로토타입으로 서빙**할 수 있다.
- MP3 필수 기능 목록에 오늘 프로토타입을 대조해 **다음 주 할 일**을 스스로 뽑을 수 있다.

## ② 왜 필요한가

이번 주 나흘 동안 서빙의 뼈대(로드·전처리 일치·로그·성능)를 MP2 모델로 익혔습니다.
그런데 MP2의 입력은 JSON에 담긴 숫자 18개였습니다. MP3의 입력은 다릅니다 — **사진 파일**이거나
**한국어 문장**입니다. 파일은 pydantic 모델에 들어가지 않고, 문장에는 스케일러 대신 토크나이저가
필요합니다. 지난 나흘의 뼈대에 이 마지막 부품을 끼우면 MP3의 전체 그림이 완성됩니다.

그래서 오늘은 리허설입니다: **다음 주 월요일(Day 101)에 시작하는 MP3를, 오늘 축소판으로
끝까지 한 번** 가 봅니다. 리허설에서 막히는 곳이 본공연에서 시간을 잡아먹을 곳입니다.

## ③ 개념 설명

### 파일은 JSON에 안 들어간다 — 두 가지 운반 방식

JSON은 텍스트 형식이라 이미지의 원시 바이트를 직접 담을 수 없습니다. 선택지는 둘:

| | **multipart/form-data** (오늘 사용) | JSON + base64 |
|---|---|---|
| 원리 | HTTP 표준 파일 첨부 형식 — 바이트 그대로 | 바이트를 텍스트로 인코딩해 JSON 필드에 |
| 크기 | 원본 그대로 | **+33%** (3바이트 → 4문자) |
| 도구 | /docs·curl·브라우저 폼이 바로 지원 | 클라이언트가 인코딩 코드를 짜야 함 |
| 어울리는 곳 | 단건 업로드 (MP3의 `/predict`) | 파일+메타데이터를 한 계약에 묶을 때, 배치 항목 속 이미지 |

FastAPI에서는 핸들러 매개변수를 `file: UploadFile`로 선언하면 끝입니다 — 단, multipart 파싱은
별도 패키지가 필요해서 `pip install python-multipart`를 안 하면 서버가 기동을 거부합니다 (⑤ 참고).

### 파일 입력에도 계약이 있다 — 3중 검사

pydantic이 못 지켜 주는 곳이므로 **핸들러 입구에서 직접** 세웁니다. 순서가 곧 방어선입니다:

| 검사 | 실패 응답 | 왜 |
|---|---|---|
| ① 크기 상한 | **413** Payload Too Large | 100MB 파일 하나가 서버 메모리를 삼키는 사고 방지 |
| ② 내용 검증 (PIL로 열어 본다) | **415** Unsupported Media Type | 확장자·Content-Type은 **클라이언트의 자기 신고**라 못 믿음 — `cat.jpg`라는 이름의 텍스트 파일은 열어 봐야 안다 |
| ③ 형식 통일 (`convert("RGB")`) | — | PNG의 알파 채널(4채널)·흑백(1채널)이 (3,224,224) 계약을 깨기 전에 |

422(계약 위반)의 파일판이 413·415라고 기억하면 됩니다 — [Day 092](day-092.md)의 "의도된 4xx"
원칙은 입력이 무엇이든 같습니다.

### 텍스트 입력 — 전처리 일치의 텍스트판

문장 입력은 pydantic으로 검증하되(빈 문장·길이 상한), 전처리는 **학습 때 쓴 바로 그 토크나이저**가
합니다. [Day 097](day-097.md)의 원칙 그대로입니다:

```
테이블: 학습 Pipeline 저장     → 서빙에서 로드         (Day 097)
이미지: 학습 transforms 정의   → 서빙이 같은 코드 임포트 (오늘)
텍스트: 학습 토크나이저 지정   → 서빙이 같은 이름 로드   (오늘)
```

한글이 깨진다면 십중팔구 인코딩입니다 — HTTP 계층에서는 JSON이 UTF-8로 오가므로
(클라이언트 라이브러리의 `json=` 옵션이 처리) 보통 문제가 없고, 사고는 **파일을 읽어 보낼 때**
(`open(..., encoding="utf-8")` 누락, [Day 005](../01-python-data/day-005.md)의 그 문제) 납니다.

## ④ 단계별 실습

### Step 1. 이미지 서빙 프로토타입 (1~2교시)

[Day 085](day-085.md)의 `predict.py`를 서버로 바꿉니다. `serve_antbee.py`:

```python
# serve_antbee.py — Day 100: W17 이미지 모델 서빙 프로토타입 (MP3 리허설)
import io
import time
from contextlib import asynccontextmanager

import torch
import torch.nn as nn
from fastapi import FastAPI, HTTPException, UploadFile
from PIL import Image, UnidentifiedImageError
from torchvision import models, transforms

MAX_BYTES = 5 * 1024 * 1024                      # 입력 계약: 5MB 상한
MODEL_VERSION = "antbee-resnet18-d085"           # Day 085 체크포인트

# 학습(Day 083)과 같은 전처리 — predict.py(Day 085)와 동일 코드 (전처리 일치!)
PREPROCESS = transforms.Compose([
    transforms.Resize(256), transforms.CenterCrop(224),
    transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225]),
])

state = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    ckpt = torch.load("../models/antbee_resnet18.pt", map_location="cpu")
    m = models.resnet18(weights=None)
    m.fc = nn.Linear(m.fc.in_features, len(ckpt["classes"]))
    m.load_state_dict(ckpt["state_dict"])
    m.eval()
    state["model"], state["classes"] = m, ckpt["classes"]
    yield
    state.clear()


app = FastAPI(title="개미/벌 분류 API", version="1.0.0", lifespan=lifespan)


@app.post("/predict")
def predict(file: UploadFile):
    raw = file.file.read(MAX_BYTES + 1)
    if len(raw) > MAX_BYTES:
        raise HTTPException(413, detail="파일이 5MB를 넘습니다")
    try:
        img = Image.open(io.BytesIO(raw)).convert("RGB")   # 내용으로 검증 (확장자가 아니라!)
    except UnidentifiedImageError:
        raise HTTPException(415, detail=f"이미지 파일이 아닙니다: {file.filename}")
    t0 = time.perf_counter()
    x = PREPROCESS(img).unsqueeze(0)
    with torch.no_grad():
        probs = torch.softmax(state["model"](x), dim=1)[0]
    top = int(probs.argmax())
    return {"label": state["classes"][top],
            "confidence": round(float(probs[top]), 4),
            "model_version": MODEL_VERSION,
            "duration_ms": round((time.perf_counter() - t0) * 1000, 1)}


@app.get("/model/info")
def model_info():
    return {"model_version": MODEL_VERSION, "classes": state["classes"],
            "input": "이미지 파일 (multipart/form-data · 5MB 이하)"}


@app.get("/health")
def health():
    return {"status": "ok", "model_loaded": "model" in state}
```

구조 전체가 이번 주의 복습입니다: lifespan 1회 로드([096](day-096.md)), 전처리 일치([097](day-097.md)),
model_version 족보([096](day-096.md)), 그리고 파일 계약 3중 검사(오늘). 핸들러가 `def`인 이유는
이제 말 안 해도 되죠([094](day-094.md)).

### Step 2. 이미지 API 검증 — 성공과 실패 모두 (3교시)

`uvicorn serve_antbee:app --port 8100`으로 띄우고, 검증 데이터의 진짜 사진으로 확인합니다:

```

  200 → {'model_version': 'antbee-resnet18-d085', 'classes': ['ants', 'bees'], 'input': '이미지 파일 (multipart/form-data · 5MB 이하)'}
$ POST /predict (개미 사진)
  200 → {'label': 'ants', 'confidence': 0.7214, 'model_version': 'antbee-resnet18-d085', 'duration_ms': 46.0}
$ POST /predict (벌 사진)
  200 → {'label': 'bees', 'confidence': 0.7694, 'model_version': 'antbee-resnet18-d085', 'duration_ms': 24.6}
$ POST /predict (텍스트 파일을 cat.jpg로 위장)
  415 → {'detail': '이미지 파일이 아닙니다: cat.jpg'}
```

읽을거리:

1. **위장 파일이 415로 잡혔습니다** — 확장자(cat.jpg)와 Content-Type(image/jpeg)은 완벽했지만

2. 첫 요청 46.0ms, 둘째 24.6ms — [Day 099](day-099.md)에서 배운 워밍업 효과가 응답에도 보입니다.
3. /docs를 열어 보세요 — UploadFile 매개변수가 **파일 선택 버튼**으로 렌더링됩니다.
   브라우저에서 사진을 골라 Try it out 할 수 있는, 시연 가능한 데모가 이미 완성입니다.

### Step 3. 텍스트 서빙 프로토타입 (4~5교시)

같은 뼈대에 부품만 바꿉니다. `serve_nsmc.py` (핵심 — 전체 구조는 Step 1과 동일):

```python
class TextIn(BaseModel):
    model_config = {"extra": "forbid"}
    text: str = Field(min_length=1, max_length=500)      # 빈 문장 금지 · 길이 상한


@app.post("/predict")
def predict(r: TextIn):
    t0 = time.perf_counter()
    enc = state["tok"](r.text, return_tensors="pt", truncation=True, max_length=128)
    with torch.no_grad():
        probs = torch.softmax(state["model"](**enc).logits, dim=1)[0]
    return {"sentiment": "긍정" if int(probs.argmax()) == 1 else "부정",
            "confidence": round(float(probs.max()), 4),
            "model_version": MODEL_VERSION,
            "duration_ms": round((time.perf_counter() - t0) * 1000, 1)}
```

[Day 089](day-089.md)에서 파인튜닝한 모델(`nsmc_bert.pt`)을 그날의 확인 문장으로 검증합니다:

```
$ POST /predict {"text": "이 영화 진짜 최고였다"}
  200 → {'sentiment': '긍정', 'confidence': 0.9719, 'model_version': 'nsmc-klue-bert-d089', 'duration_ms': 92.2}
$ POST /predict {"text": "돈 아깝다 두 번은 못 보겠다"}
  200 → {'sentiment': '부정', 'confidence': 0.8307, 'model_version': 'nsmc-klue-bert-d089', 'duration_ms': 37.9}
$ POST /predict {"text": "배우 연기는 좋았는데 스토리가 아쉽다"}
  200 → {'sentiment': '부정', 'confidence': 0.7781, 'model_version': 'nsmc-klue-bert-d089', 'duration_ms': 37.6}
$ POST /predict {"text": ""}
  422 → {'detail': [{'type': 'string_too_short', 'loc': ['body', 'text'], 'msg': 'String should have at least 1 character', ...}]}
```

**Day 089의 숫자와 대조해 보세요** — 그날 스크립트의 P(긍정)이 0.97 / 0.17 / 0.22였는데, 오늘
API가 0.9719 긍정 / 0.8307 부정(=긍정 0.17) / 0.7781 부정(=긍정 0.22)을 돌려줍니다.
**같은 토크나이저 + 같은 가중치 = 같은 답.** 전처리 일치가 지켜졌다는 것을 학습 시점의 기록이
증명해 주는 순간이고, MP3 보고서의 "서빙 정확성" 항목이 바로 이 대조표입니다.

지연도 관찰하세요: BERT 순전파가 ~38ms — ResNet(~25ms)과 같은 자릿수라 CPU 서빙이 충분히
성립합니다. 문장이 길어지면 토큰 수와 함께 늘어나는 것도 실험해 볼 만합니다.

### 오늘 새로 나오는 실수

**`pip install python-multipart`를 빼먹음**

**증상** — 서버 기동 시 `RuntimeError: Form data requires "python-multipart" to be installed.`
**원인** — multipart 파싱은 FastAPI 기본 설치에 포함되지 않은 별도 패키지입니다.
**해결** — 설치하면 끝. 에러 메시지가 시키는 그대로입니다 — 읽지 않고 코드부터 의심하는 것이 진짜 실수.

**확장자·Content-Type만 믿고 통과시킴**

**증상** — `cat.jpg`(내용은 텍스트)가 전처리까지 흘러들어 500 — 사용자에겐 "서버 잘못"으로 보임.
**원인** — 파일 이름과 Content-Type은 클라이언트가 마음대로 쓰는 자기 신고입니다.
**해결** — 오늘 코드처럼 **열어 봐서** 검증하고 415로 거절. "내용이 계약"입니다.

**크기 상한 없이 `read()`**

**증상** — 누군가 4GB 동영상을 업로드 — 서버 메모리가 요청 하나에 잠식.
**원인** — 파일 입력의 규모를 계약에 안 넣음.
**해결** — 상한+1만 읽고 넘으면 413. 상한값은 /model/info와 문서에 공개합니다.

**base64를 "그냥 편해서" 선택**

**증상** — 5MB 사진이 6.7MB JSON이 되고, 클라이언트마다 인코딩 코드가 복제됨.
**원인** — 두 방식의 비용 차이를 모른 채 익숙한 JSON을 고름.
**해결** — 단건 업로드는 multipart가 기본값. base64는 "파일+메타데이터 한 계약" 같은 구체적 이유가 있을 때.

**Q1.** 위장 파일(cat.jpg)이 415로 거절되기까지, 오늘 서버의 3중 검사 중 어디서 어떻게
잡혔는지 순서대로 설명하세요.

<details>
<summary>답 보기</summary>

① 크기 검사: 통과 (작은 파일). ② 내용 검증: `Image.open()`이 바이트를 해석하지 못해
`UnidentifiedImageError` → 핸들러가 415로 번역. ③ 형식 통일에는 도달하지 못함.
핵심은 ②가 파일 이름(cat.jpg)도 Content-Type(image/jpeg)도 보지 않는다는 것 — 그 둘은
클라이언트의 주장이고, 검증은 내용물로만 합니다.

</details>

**Q2.** Step 3에서 API의 응답 확률이 Day 089 학습 스크립트의 기록과 일치하는 것이 왜
"전처리 일치의 증명"인지, 불일치했다면 무엇부터 의심해야 하는지 쓰세요.

<details>
<summary>답 보기</summary>

추론 결과는 (가중치, 전처리)의 함수입니다. 가중치는 같은 파일을 로드했으므로, 확률까지 같다는
것은 토큰화(전처리)도 학습 때와 동일하다는 뜻입니다. 불일치했다면: ① 토크나이저 이름/버전이
다른가 (klue/bert-base가 맞나), ② truncation·max_length 설정이 학습과 다른가, ③ 가중치를
다른 체크포인트에서 로드했나 순서로 의심합니다 — [Day 097](day-097.md)의 화씨 사고와 같은
계열이며, 그래서 이 대조표가 MP3 보고서의 "서빙 정확성" 증빙이 됩니다.

</details>

**Q3.** MP3에서 배치 예측을 만든다면, 이미지 API와 텍스트 API 각각 입력 계약을 어떻게
설계하겠습니까? (운반 방식 포함)

<details>
<summary>답 보기</summary>

텍스트: JSON 배열이 자연스럽습니다 — `{"texts": ["...", "..."]}` (pydantic `list[str]`,
`max_length`로 배치 크기 상한). 이미지: multipart로 파일 여러 개(`list[UploadFile]`)를 받거나,
항목별 메타데이터가 필요하면 JSON+base64 배열로 — +33% 크기를 감수하는 대신 계약이 한 덩어리가
됩니다. 어느 쪽이든 [Day 099](day-099.md)의 교훈대로 배치 크기 상한을 계약에 명시해야 합니다
(지연·메모리·실패 반경의 거래이므로).

</details>

## 주간 퀴즈 18 — W20 (추론 API 설계)

<details>
<summary>1. 모델 로드가 요청 경로에 있으면 안 되는 이유와 공식적인 자리는?</summary>

로드는 수백 ms~수십 초짜리 작업이라 요청마다 하면 응답의 대부분이 낭비되고 동시 요청 수만큼 메모리 사본이 뜹니다. 공식 자리는 lifespan — 시작 시 1회, 실패는 기동 실패로 드러남.

</details>

<details>
<summary>2. 추론 API의 3종 기본 엔드포인트와 각각의 소비자는?</summary>

POST /predict(클라이언트) · GET /model/info(운영자·디버깅 — run_id·데이터 지문) · GET /health(로드밸런서·모니터링 — 모델 적재 여부 포함).

</details>

<details>
<summary>3. "학습 전처리 = 서빙 전처리"를 사람의 규칙이 아니라 구조로 보장하는 세 가지 방법은?</summary>

테이블: 전처리를 Pipeline에 봉인해 저장·로드. 이미지: 학습의 transforms 정의를 서빙이 같은 코드로 임포트. 텍스트: 학습 때의 토크나이저를 같은 이름/버전으로 로드.

</details>

<details>
<summary>4. 예측 로그의 필수 필드 4가지는?</summary>

입력 요약(개인정보 아님을 확인한 필드만) · 출력 · model_version · 타임스탬프. 버전이 없으면 모델 교체 후 사후 분석이 불가능해집니다.

</details>

<details>
<summary>5. 지연 보고에 평균 대신 p50/p95를 쓰는 이유는?</summary>

지연 분포는 오른쪽 꼬리가 길어 평균이 소수의 큰 값에 끌려갑니다. p50 = 절반의 체감, p95 = 20명 중 1명의 나쁜 경험 하한 — SLA의 표준 단위.

</details>

<details>
<summary>6. 포화점이란 무엇이고, 지나면 어떤 증상이 나타나나?</summary>

처리량이 더 늘지 않기 시작하는 동시성 지점. 그 이후 동시성을 늘리면 처리량은 천장(≈50 req/s였죠)에 붙고 요청은 대기열에서 기다려 p50·p95만 자랍니다.

</details>

<details>
<summary>7. 배치 추론의 이득은 어디서 오고, 무엇과 맞바꾸나?</summary>

건당 고정 오버헤드를 배치가 나눠 갖는 데서 옵니다(오버헤드 지배 모델일수록 극적 — MP2 파이프라인 1,000배 vs ResNet CPU 1.3배). 대가는 요청 지연·메모리·실패 반경.

</details>

<details>
<summary>8. 캐시를 붙이기 전 확인할 두 가지는?</summary>

예상 히트율(같은 입력이 실제로 반복되는가 — 아니면 메모리 낭비)과 무효화 계획(모델 교체 시 cache_clear() — 안 하면 옛 모델의 답을 서빙).

</details>

<details>
<summary>9. 워커를 늘려도 처리량이 안 느는 대표적 경우는?</summary>

추론이 이미 프로세스 안에서 스레드 병렬로 코어를 포화시킨 경우(우리 실측: 워커 2 = +0%). 워커는 프로세스를 복제하지 코어를 복제하지 않습니다 — 메모리만 배로.

</details>

<details>
<summary>10. 파일 입력의 3중 검사와 각각의 실패 상태 코드는?</summary>

크기 상한(413) → 내용 검증 — 열어 봐서(415) → 형식 통일(RGB 변환, 실패 아님). 확장자·Content-Type은 자기 신고라 검증 근거가 못 됩니다.

</details>
