## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **실험 루프**(가설 → 실행 → 기록 → 결론)를 리듬으로 만들고, 1실험 1변경 원칙을 지킬 수 있다.
- 전처리 파이프라인을 **모듈**(src/)로 완성해 직렬화·재사용이 가능하게 만든다.
- 모델 후보를 계열 대표로 구성하고 **CV로 판정**할 수 있다 (test는 여전히 금고).
- MLflow에 조건·결과·**결론**이 담긴 run을 6개 이상 쌓는다.

---

## ② 왜 필요한가

구현일의 가장 흔한 실패는 코드가 아니라 **리듬**에서 옵니다.

```
나쁜 화요일: "일단 이것저것 바꿔서 돌려 보자" × 30회
             → 저녁: run은 많은데 뭐가 뭘 개선했는지 아무도 모름
좋은 화요일: 가설 하나 → 변경 하나 → run 하나 → 결론 한 줄  × 10회
             → 저녁: "채택 2, 기각 8, 내일 할 것 명확"
```

우리는 이 리듬의 부품을 전부 갖고 있습니다 — 심판(TSS CV, [Day 061](day-061.md)),
기록계(MLflow, [Day 067](day-067.md)), 실행기(train.py, [Day 070](day-070.md)).
오늘은 그것들로 **연주**하는 날입니다. 그리고 평가 기준 "실험 기록 25점"은 run의 개수가
아니라 이 리듬의 흔적(기각 기록, 조건 복원 가능성)을 봅니다.

## ③ 개념 설명

### 실험 루프 — 1실험 1변경

```
가설: "예보 특성이 MAE를 0.3 이상 줄일 것이다"
  ↓ 변경은 하나만 (특성 추가)  ← 두 개를 바꾸면 원인을 알 수 없음 (Day 066의 소거법)
실행: python train.py --config exp07.json
  ↓
기록: MLflow run + 실험 대장에 결론 한 줄
  ↓
결론: 채택/기각 + 다음 가설
```

**가설에 예상 크기를 적는 것**이 요령입니다 ("좋아질 것" ✗ → "MAE -0.3 이상" ✓).
결과가 예상과 다를 때 배우는 것이 생기고, CV 표준편차보다 작은 개선을 채택하는
실수([Day 061](day-061.md))를 예방합니다.

### 후보군 구성 — 계열 대표 2종이면 충분

| 계열 | 대표 | 이 계열이 이기는 판 |
|---|---|---|
| 선형 | LinearRegression/로지스틱 (+규제) | 신호가 매끈하고 상관 특성에 분산 ([Day 059](day-059.md)) |
| 부스팅 | LightGBM (또는 HGB/XGB) | 문턱·상호작용·이질적 특성 |

W12에서 배웠듯 계열 안의 차이(XGB vs LGBM)는 계열 간 차이보다 작습니다. 후보를 늘리는 것보다
**두 대표를 특성 세트마다 재대결**시키는 것이 정보량이 큽니다 ([Day 064](day-064.md)에서 순위가
접전으로 바뀌는 걸 봤습니다).

### 판정 규칙 — 미리 정해 둔다

1. 심판은 기획서의 CV (시계열이면 TSS). **test는 Day 073 저녁까지 봉인.**
2. CV 평균 차이가 표준편차 안이면 **동률** → 더 단순한(가볍고 설명 쉬운) 쪽.
3. 판정 불능이면 보류하고 다음 가설로 — 하루에 결판 안 나는 비교에 매달리지 않기.

## ④ 단계별 실습

### Step 1. 파이프라인을 모듈로 (1~3교시)

train.py 안에 있던 함수들을 `src/` 로 옮깁니다 — 노트북·테스트·서빙이 **같은 코드를 import**
하게 만들고, [Day 068](day-068.md)의 lambda 함정(직렬화 불가)을 구조적으로 피합니다.

```
src/
├── features.py    make_features(df) — 모든 파생은 여기에만 존재
├── model.py       build_pipeline(feats) — ColumnTransformer + 모델
└── validate.py    validate_input(x, schema) — Day 068
```

**전처리 결정 사항을 기획서와 대조하며 확정합니다** (예시 프로젝트의 결정):

| 항목 | 결정 | 근거 |
|---|---|---|
| 결측 | median 대치 (Pipeline 안) | 열별 결측률 ≤2% ([Day 063](day-063.md)) |
| 범주(station) | 원-핫 + handle_unknown="ignore" | 신규 측정소 대비 |
| 스케일 | 표준화 (선형 후보용) · 트리 후보는 생략 | [Day 053](day-053.md)·[058](day-058.md) |
| 파생 | groupby 안에서 shift/rolling | 경계 오염 방지 ([Day 064](day-064.md) ⑤) |

### Step 2. 후보 2종 CV 대결 (4~5교시)

예시 프로젝트의 대결 결과입니다 (전 특성, TSS 5폴드 — test는 열지 않았습니다):

```
| 후보 | 폴드별 R² | 평균 ± 표준편차 |
|---|---|---|
| 선형 파이프라인 | 0.163, 0.339, 0.427, 0.392, 0.455 | 0.355 ± 0.125 |
| LGBM(완화 설정) | -0.347, 0.250, 0.380, 0.471, 0.261 | 0.203 ± 0.287 |
```

판정 연습을 해 봅시다.

1. **평균**: 선형 0.355 vs LGBM 0.203 — 선형 우세.
2. **폴드1을 보세요**: LGBM이 -0.347로 무너졌습니다. 폴드1의 train은 500여 행 —
   **데이터가 적을 때 부스팅이 먼저 무너진다**는 계열 성질이 CV 안에서 그대로 보입니다.
3. **분산**: LGBM ±0.287은 "기간에 따라 성능이 크게 출렁인다"는 운영 관점의 경고이기도 합니다.

결론: 주 후보 = 선형 파이프라인, LGBM은 특성이 바뀔 때마다 재도전권 유지.
(그리고 스포일러 없이 한마디 — 이 CV 판정은 Day 073 저녁 금고를 열었을 때 test와 같은
결론이었습니다. **심판을 믿을 수 있게 설계했다면, 심판을 믿으세요.**)

### Step 3. 실험 루프 가동 — run 6개 (6~7교시)

train.py 의 config를 바꿔 가며 (모델 2종) × (특성 세트 3종)을 돌립니다.
[Day 067](day-067.md)에서 한 그 매트릭스를 이번엔 **여러분의 문제**로.

```powershell
python train.py --config configs/exp01-linear-base.json
python train.py --config configs/exp02-lgbm-base.json
# … exp06까지
```

run 이름 규약을 정하세요 (`{모델}-{특성}-{v}`), 그리고 run마다 실험 대장에 결론 한 줄:

```markdown
| run | 가설 | 결과(CV) | 결론 |
|---|---|---|---|
| linear-base | 기준점 | 0.28 ± 0.11 | 기준 확정 |
| lgbm-base | 트리가 나을 것 | 0.15 ± 0.24 | 기각 — 폴드1 붕괴, 표본 부족 |
| linear-time | 시간 파생 +0.02 이상 | +0.003 | 기각 — 기존 정보의 재표현 (Day 064) |
```

### Step 4. 퇴근 체크 (8교시)

```powershell
git add src/ configs/ docs/experiments.md
git commit -m "MP2 Day2: 파이프라인 모듈화 + 후보 비교 (선형 채택, run 6)"
```

□ src/ 모듈화 완료 (노트북이 src를 import) □ MLflow run 6개+ (기각 포함)
□ 후보 판정 근거가 실험 대장에 □ test는 아직 0회 열람

## ⑤ 자주 하는 실수

### 한 실험에서 여러 개를 바꿈

**증상** — "특성도 넣고 모델도 바꾸고 대치도 mean으로" → 좋아졌는데 **무엇 덕분인지 모름**.
**원인** — 변인이 셋이면 결론이 여덟 갈래입니다.
**해결** — 1실험 1변경. 급하면 실험을 쪼개지, 변경을 합치지 않습니다.

### 판정이 안 나면 test를 열고 싶어짐

**증상** — "CV로는 비슷하니 test로 갈라 보자" (수요일에!).
**원인** — test를 심판으로 쓰는 순간 최종 평가가 오염됩니다 ([Day 052](day-052.md)의 원칙, [Day 062](day-062.md)의 저주).
**해결** — CV 동률의 판정 규칙(단순한 쪽)을 미리 정해 뒀으니 그대로. test는 073 저녁, 최종 모델 확정 후 1회.

### 실패한 run을 지움

**증상** — MLflow에 성공 run만 남김 — "깔끔해 보이려고".
**원인** — 기각 기록이 없으면 같은 아이디어가 재시도되고([Day 065](day-065.md) ⑤), 심사에서는 "10회 이상"의 진정성을 의심받습니다.
**해결** — 실패 run에 결론 태그를 달아 남기세요. 기각 이력이 많은 실험 대장이 오히려 신뢰의 증거입니다.

### 실험을 노트북에서 돌리고 CLI는 장식이 됨

**증상** — train.py는 첫날 이후 안 돌아가고, 진짜 실험은 노트북 셀에서.
**원인** — 노트북이 편하니까. 하지만 그 실험들은 config도 run 기록도 재현성도 없습니다.
**해결** — 탐색은 노트북, **점수를 주장할 실험은 반드시 train.py 경유** ([Day 070](day-070.md)). 노트북에서 발견하면 config로 옮겨 재실행해 공식 기록을 만듭니다.

### 폴드 하나의 이상값에 과잉 반응

**증상** — "LGBM 폴드1이 -0.35! 버그다!" 반나절 디버깅.
**원인** — TSS 폴드1은 train이 가장 작아 원래 험합니다. 구조를 알면 놀랄 일이 아닙니다.
**해결** — 폴드별 train 크기를 함께 출력하고, 이상값이 **구조적**(항상 폴드1)인지 **우연**(특정 후보만)인지 구분한 뒤 움직이세요.

**Q2.** Step 2의 CV 표에서 LGBM의 폴드1(-0.347)과 표준편차(±0.287)가 각각 말해 주는 것을 쓰세요.

<details>
<summary>답 보기</summary>
