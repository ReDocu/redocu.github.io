## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **구조화(JSON) 로그**가 왜 검색·집계 가능한 데이터인지 알고 구현할 수 있다.
- **미들웨어**로 모든 요청의 처리시간·요청 ID를 자동 기록할 수 있다.
- **예측 로그**(입력 요약 + 출력 + 모델 버전)를 남기고, 그 용도(모니터링의 원료)를 안다.
- 로그에 **개인정보를 남기지 않는** 원칙과 판단 기준을 안다.

---

## ② 왜 필요한가

서버가 돌기 시작하면 질문이 날아옵니다:

```
운영:   "어제 오후에 느렸다는 민원이 있어요. 실제로 느렸나요?"
데이터: "요즘 '나쁨' 예측 비율이 이상하게 높지 않아요?"
개발:   "이 이상한 예측, 요청이 뭐였는지 볼 수 있어요?"
```

로그 없는 서버는 세 질문 모두에 "모르겠는데요"로 답합니다. 로그는 서버의 **블랙박스
(비행기록장치)** 입니다 — 그리고 ML 서버의 로그는 한 가지가 더 특별합니다. 예측 로그는
단순 디버깅 자료가 아니라 **모니터링과 재학습의 원료**입니다: 입력 분포가 변하면(어제 화씨
사고!) 드리프트 경보의 근거가 되고, 쌓인 (입력, 예측) 쌍은 나중에 정답이 도착하면 재학습
데이터가 됩니다 (W27에서 이 로그를 실제로 소비합니다).

이번 주 체크포인트가 오늘의 합격선입니다 — **"로그로 어제 요청의 처리시간 분포를 답할 수
있는가."** print 몇 줄로는 안 되는 이유부터 봅니다.

---

## ③ 개념 설명

### print가 아니라 구조화 로그인 이유

```
print 스타일:   요청 왔음! 강남구 예측함 34.1 (0.005초)
JSON 로그:      {"ts": "...", "station": "강남구", "pm25_next_pred": 34.1, "duration_ms": 5.3}
```

| | print/자유 텍스트 | 구조화(JSON) |
|---|---|---|
| 읽기 | 사람 눈 | **pandas·검색엔진** — 한 줄 = 레코드 하나 |
| "p95 처리시간은?" | grep + 눈물 | `df.duration_ms.quantile(.95)` |
| 스키마 | 없음 (형식이 제멋대로) | 필드가 계약 |

대단원 02에서 배운 감각 그대로입니다 — **분석할 데이터는 구조부터.** 로그도 데이터입니다.
(운영 환경에선 이 JSON 줄들이 수집기(ELK 등 — 별도 과정)로 흘러가지만, 형식은 오늘 것 그대로입니다.)

### 미들웨어 — 모든 요청이 지나는 관문

```python
@app.middleware("http")
async def observe(request, call_next):
    t0 = time.perf_counter()
    response = await call_next(request)      # ← 실제 핸들러는 이 안에서
    duration = time.perf_counter() - t0      # 앞뒤로 감싸 시간을 잰다
    ...
```

핸들러마다 시간 측정 코드를 복붙하는 대신, **한 곳**에서 전 요청을 감쌉니다 —
[Day 012](../01-python-data/day-012.md)의 데코레이터(함수를 감싸 시간을 재던)와 같은 발상이
서버 규모로 커진 것입니다. 요청 ID를 발급해 응답 헤더에 실어 주면, 사용자 문의("이 요청이
이상했어요")와 로그를 한 줄로 잇는 추적 고리가 됩니다.

### 두 종류의 로그

| 로그 | 기록 주체 | 내용 | 용도 |
|---|---|---|---|
| **요청 로그** | 미들웨어 (전 경로 자동) | 경로·상태·처리시간·요청 ID | 성능·에러율 관측 |
| **예측 로그** | predict 핸들러 | 입력 요약 + 예측 + **모델 버전** | 드리프트 감시·재학습 재료·사후 분석 |

### 개인정보는 로그에 남기지 않는다

[Day 019](../01-python-data/day-019.md)·[044](../02-sql-pipeline/day-044.md)에서 배운 원칙의 서빙판입니다.
로그는 오래 보관되고, 여러 시스템으로 복제되며, 접근 통제가 DB보다 느슨하기 쉽습니다 —
**한번 로그에 찍힌 개인정보는 회수가 사실상 불가능**합니다.

| 원칙 | 실천 |
|---|---|
| 필요한 최소만 | 입력 전체 덤프 금지 — 모니터링에 필요한 요약 필드만 골라서 |
| 식별자는 가명으로 | 사용자 ID가 필요하면 해시([Day 044](../02-sql-pipeline/day-044.md)의 비식별화) |
| 자유 텍스트 주의 | 텍스트 모델 입력(문장)에는 이름·연락처가 섞여 올 수 있음 — 남길 거면 마스킹 |
| 지울 수 있게 | 보관 기간을 정하고 로테이션 (무한 로그는 무한 책임) |

우리 예보 API의 입력(농도·기상)은 개인정보가 아니라 전량 로깅이 가능하지만 — **그 판단을
했다는 것 자체를 기록**하는 것이 규율입니다 (오늘 코드의 주석).

## ④ 단계별 실습

### Step 1. 관측 가능한 서버 (1~3교시)

어제의 서버에 로거·미들웨어·예측 로그를 답니다. `serve_logged.py` (핵심 부분):

```python
# ── 구조화(JSON) 로거: 한 줄 = JSON 하나 = 나중에 pandas로 읽는 데이터 ──
logger = logging.getLogger("predict")
handler = logging.FileHandler("predictions.log", encoding="utf-8")
handler.setFormatter(logging.Formatter("%(message)s"))
logger.addHandler(handler)
logger.setLevel(logging.INFO)


@app.middleware("http")
async def observe(request: Request, call_next):
    """모든 요청의 처리시간을 재고, 요청 ID를 발급한다 (Day 012의 데코레이터와 같은 발상)."""
    request_id = str(uuid.uuid4())[:8]
    t0 = time.perf_counter()
    response = await call_next(request)                     # 실제 핸들러 실행
    duration_ms = (time.perf_counter() - t0) * 1000
    response.headers["X-Request-ID"] = request_id
    response.headers["X-Process-Time-Ms"] = f"{duration_ms:.1f}"
    if request.url.path != "/health":                       # 헬스체크는 로그에서 제외 (소음)
        logger.info(json.dumps({
            "ts": time.strftime("%Y-%m-%dT%H:%M:%S"),
            "request_id": request_id,
            "path": request.url.path,
            "status": response.status_code,
            "duration_ms": round(duration_ms, 1),
        }, ensure_ascii=False))
    return response


@app.post("/predict")
def predict(r: PredictIn, request: Request):
    x = pd.DataFrame([r.model_dump()])[state["schema"]["columns"]]
    pred = float(state["pipe"].predict(x)[0])
    result = {"pm25_next_pred": round(pred, 1), "grade": to_grade(pred),
              "model_version": state["schema"]["run_id"][:8]}
    # ── 예측 로그: 무엇이 들어와 무엇이 나갔나 (모니터링의 원료 — W27) ──
    logger.info(json.dumps({
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S"),
        "kind": "prediction",
        "station": r.station, "pm25_today": r.pm25,          # 입력 요약 (개인정보 아님을 확인!)
        **result,
    }, ensure_ascii=False))
    return result
```

### Step 2. 트래픽을 흘려 보고 로그 확인 (4교시)

서버를 띄우고 요청 30건(측정소·농도 무작위) + 422짜리 1건을 보냅니다.

```
마지막 응답 헤더: X-Request-ID = 9a0bc7d7 · X-Process-Time-Ms = 5.3
```

응답 헤더에 요청 ID와 처리시간이 실렸습니다 — 클라이언트가 "이 요청이요"라고 지목할 수
있는 손잡이입니다. `predictions.log` 의 마지막 세 줄:

```
{"ts": "2026-08-13T01:56:09", "kind": "prediction", "station": "노원구", "pm25_today": 59.9, "pm25_next_pred": 18.7, "grade": "보통", "model_version": "6ac527ba"}
{"ts": "2026-08-13T01:56:09", "request_id": "9a0bc7d7", "path": "/predict", "status": 200, "duration_ms": 5.3}
{"ts": "2026-08-13T01:56:09", "request_id": "f7373439", "path": "/predict", "status": 422, "duration_ms": 2.1}
```

예측 로그와 요청 로그가 섞여 쌓입니다 — kind 필드로 구분됩니다. 422 요청도 처리시간과 함께
기록된 것을 확인하세요 (실패도 관측 대상입니다).

### Step 3. 체크포인트 — 로그로 질문에 답하기 (5~6교시)

로그는 데이터입니다. pandas로 읽어 ②의 세 질문에 답합니다:

```python
import json
import pandas as pd
rows = [json.loads(l) for l in open("predictions.log", encoding="utf-8")]
df = pd.DataFrame(rows)
req = df[df.kind.isna()]                      # 요청 로그 (미들웨어)
pred = df[df.kind == "prediction"]            # 예측 로그
print(f"요청 {len(req)}건 · 예측 {len(pred)}건")
print(f"처리시간: p50 {req.duration_ms.quantile(0.5):.1f}ms · p95 {req.duration_ms.quantile(0.95):.1f}ms · 최대 {req.duration_ms.max():.1f}ms")
print(f"상태 코드 분포: {req.status.value_counts().to_dict()}")
print("예측 등급 분포:", pred.grade.value_counts().to_dict())
print("측정소별 평균 예측:", pred.groupby("station").pm25_next_pred.mean().round(1).to_dict())
```

실행 결과:

```
요청 31건 · 예측 30건
처리시간: p50 4.7ms · p95 6.1ms · 최대 12.5ms
상태 코드 분포: {200.0: 30, 422.0: 1}
예측 등급 분포: {'보통': 25, '나쁨': 5}
측정소별 평균 예측: {'강남구': 32.9, '노원구': 26.4, '마포구': 31.0, '서초구': 34.4, '종로구': 30.3}
```

세 질문에 전부 답이 나옵니다: 느렸나? → p95 6.1ms, 최대 12.5ms (아니오). 나쁨 비율은? →
30건 중 5건. 이상한 예측의 요청은? → request_id로 역추적. **p50/p95라는 눈금**도 오늘부터
씁니다 — 평균은 [Day 054](../03-machine-learning/day-054.md)에서 배웠듯 소수의 큰 값에 가려지므로,
지연시간의 세계에서는 분위수가 표준입니다 (내일 부하 측정의 주 지표가 p95입니다).

## ⑤ 자주 하는 실수

### 로그를 자유 문장으로 씀

**증상** — `logger.info(f"{station} 예측 완료: {pred}")` — 한 달 뒤 "나쁨 비율 추이"를 뽑으려니 정규식 지옥.
**원인** — 로그를 사람만 읽는 것으로 생각.
**해결** — 처음부터 JSON 한 줄 = 레코드 하나. 사람이 볼 일은 `tail predictions.log | jq` 같은 도구가 해결합니다.

### 입력 전체를 통째로 로깅

**증상** — 로그가 하루에 수 GB / 어느 날 입력에 섞여 온 개인정보가 로그에 영구 박제.
**원인** — "일단 다 남기면 나중에 좋겠지".
**해결** — 모니터링에 필요한 **요약 필드를 골라서** (오늘: station, pm25_today). 전량 보존이 정말 필요하면 로그가 아니라 접근 통제된 저장소에, 보관 기간과 함께.

### 헬스체크·모니터링 요청까지 다 로깅

**증상** — 로그의 95%가 로드밸런서의 /health — 정작 필요한 예측 로그가 소음에 묻힘.
**원인** — 미들웨어가 전 경로를 무차별 기록.
**해결** — 오늘 코드처럼 /health는 제외. 로그에도 신호 대 잡음비가 있습니다.

### 시간 측정을 핸들러 안에서 수동으로

**증상** — 엔드포인트가 늘 때마다 측정 코드 복붙, 하나는 빼먹음 — 구멍 난 관측.
**원인** — 횡단 관심사(모든 요청 공통)를 개별 코드에 흩음.
**해결** — 미들웨어 한 곳에서. [Day 063](../03-machine-learning/day-063.md)류의 원칙 재등장: 사람이 지킬 규칙을 구조가 지키게.

### 모델 버전 없는 예측 로그

**증상** — "지난달 이상 예측" 분석 — 그런데 그 사이 모델이 두 번 교체되어 어느 모델의 예측인지 불명.
**원인** — 로그 스키마에 model_version 누락.
**해결** — 예측 로그의 필수 필드: 입력 요약 · 출력 · **model_version** · ts. [Day 096](day-096.md)의 족보가 로그에서 완성됩니다.

"두 예보관" 논리로 설명하세요.

<details>
<summary>답 보기</summary>

지연시간 분포는 오른쪽 꼬리가 깁니다(가끔 아주 느린 요청). 평균은 그 소수의 큰 값에 끌려가
"보통 사용자의 체감"도 "최악 경험"도 대변하지 못합니다. p50은 절반의 사용자가 겪는 값,
p95는 "20명 중 1명이 겪는 나쁜 경험"의 하한 — RMSE가 대형 오차를 감시하듯, p95가 대형 지연을
감시합니다. 그래서 SLA도 보통 p95/p99로 씁니다.

</details>
