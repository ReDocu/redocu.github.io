## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- README를 **5분 규칙**(문제→그림→실행→결과)에 맞게 완성할 수 있다.
- 결과 보고서에 개선 과정·**사고와 수리**·한계를 증거와 함께 담을 수 있다.
- 운영 절차서를 **남이 수행하는 검증**으로 완성할 수 있다.
- 빈 서버 리허설로 심사위원의 첫 15분을 미리 살아볼 수 있다.

## ② 왜 필요한가

이번 주의 주제는 커리큘럼 문장 그대로입니다 — "코드가 아니라 **남에게 전달되는 것**을
완성한다." 냉정한 사실 하나로 시작합시다: 심사위원과 미래의 채용 담당자는 여러분의
4주를 보지 않았습니다. 그들이 경험하는 것은 저장소를 열고 나서의 15분입니다 — README를
읽고, clone하고, up하고, 문서를 따라 한 바퀴 돌아보는 시간. **그 15분의 경험이 4주의
평가를 대신합니다.** 억울하지만, 실무도 정확히 같습니다 — 인수인계받는 동료, 오픈소스의
첫 방문자, 장애 대응 중의 미래의 나. 저장소는 코드의 창고가 아니라 읽는 사람의 경험
입니다.

배점으로도 오늘이 가장 무거운 날 중 하나입니다: 재현성·품질 20점 + 문서·발표 중 문서
몫 ≈ 10점 — 어제까지 만든 시스템이 훌륭해도 전달이 무너지면 30점 구역이 흔들립니다.
그리고 어제 감사의 유일한 🔶(문서)를 오늘 ✅로 바꾸지 않으면 v1.0.0은 없습니다.

문서 작업의 함정은 "썼다 = 됐다"입니다. 코드에 테스트가 있듯 문서에도 검증이 있습니다 —
**그 문서만 보고 남이 수행해 보는 것.** 오늘 두 번의 검증(절차서 교차 수행 · 빈 서버
리허설)이 그래서 배치되어 있습니다.

## ③ 개념 설명

### README의 5분 규칙

첫 화면에서 5분 안에 이 순서가 읽혀야 합니다:

| 절 | 내용 | 독자의 질문 |
|---|---|---|
| 1. 문제 한 문장 + 데모 스크린샷 | 무엇을 왜 만들었나 | "이게 뭐지?" |
| 2. 아키텍처 그림 (현실의 사진) | 상자·흐름·기술 | "어떻게 생겼지?" |
| 3. 실행 방법 | clone → .env → up → 확인 (복붙 가능) | "돌려볼 수 있나?" |
| 4. 결과 요약 | 핵심 숫자 3개 + 보고서 링크 | "잘 됐나?" |
| 5. 구조·문서 지도 | 폴더 안내 + docs/ 링크 | "더 보려면?" |

[Day 136](../05-infra-mlops/day-136.md)의 원칙이 여기서도 판정 기준입니다 — 그림과
숫자는 전부 **현실의 사진**(증거 명령이 있는 것)이어야 합니다.

### 결과 보고서 — 과정의 증명

| 절 | 핵심 | 한산 팀의 재료 |
|---|---|---|
| 문제 정의와 범위 | 시나리오 + 자른 것과 이유 | 142의 3축 표 그대로 |
| 데이터 | 원천·규모·검증·**알려진 특성** | 48,756행 · D-4 · 결측 이력 |
| 모델 | 베이스라인→개선 계단 + 선정 근거 + **사고와 수리** | 1,914 → 1,183 (−38.2%) · 151 서사 |
| 시스템 | 아키텍처 + 운영 실측 표 | 배포 2m40s · 롤백 41s · 포화 57 req/s |
| 한계와 다음 단계 | 정직한 3종 세트 (아는 한계·감수 근거·넘어갈 방법) | 폭우 오차 · 연휴 지연 · 로드맵 |

"사고와 수리" 절이 모델 절 안에 정식으로 들어가는 것에 주목 — 부끄러운 부록이 아니라
본문입니다 (155 ⑥ Q3에서 확인한 그 이유로).

### 운영 절차서 — 상황이 목차다

기능이 아니라 **상황**으로 목차를 짭니다: "서비스가 안 떠요" / "배포를 되돌리고 싶어요" /
"모델이 이상해요" / "데이터가 안 들어와요" / "키를 교체해야 해요". 각 상황에 진단 명령 →
조치 명령 → 확인 명령. 독자는 침착하지 않은 상태임을 전제로, 복붙 가능한 명령과 예상
출력까지 씁니다 ([Day 139](../05-infra-mlops/day-139.md)의 OPERATIONS 규율).

## ④ 단계별 실습

### Step 1. 분담과 초안 (1~3교시)

어제 계획대로 — 서연(README·DATA 갱신) · 민준(보고서) · 지우(절차서) · 하람(리허설 환경
준비). 문서도 PR로, 리뷰 짝이 **독자 입장에서** 리뷰합니다 (155 회고의 Try 실행).

### Step 2. 절차서 교차 수행 (4~5교시)

지우가 쓴 절차서를 **민준이** (절차서만 보고, 지우는 입 닫고 관전) 수행합니다:

```
시나리오 3 "배포를 되돌리고 싶어요" — 민준 수행
  진단: gh run list → 최근 배포 sha 확인 ... OK
  조치: ./deploy.sh 9e3f21c ... ⚠ 막힘 — "sha를 어디서 보는지" 절차서에 없음
  → 절차서 수정: 배포 이력 로그 위치와 읽는 법 추가 → 재수행 41s OK
```

막힌 지점이 절차서의 버그입니다 — 쓴 사람은 절대 못 찾는 종류의 버그이고, 그래서
검증자는 반드시 다른 사람이어야 합니다.

### Step 3. 빈 서버 리허설 — 심사의 예행 (6~7교시)

하람이 준비한 깨끗한 VM(또는 새 계정의 컨테이너 환경)에서, **README만 보고**:

```
$ git clone https://github.com/team-hansan/hansan.git && cd hansan
$ cp .env.example .env && vi .env      # README의 안내대로 4개 값
$ docker compose up -d
$ curl -s localhost:8080/health
{"status":"ok","model_version":"hansan-daily-v3", ...}
⏱ clone → healthy 5/5: 2m18s
$ psql ... < snapshots/subway_20260821.sql && pytest -q     # 데이터 스냅숏 + 테스트
23 passed in 41.2s
```

**2m18s** — 이 숫자가 README의 "결과 요약"에 들어가고, 발표의 재현성 슬라이드가 됩니다.
막힘 없이 끝났다면 문서가 완성된 것이고, 막혔다면 오늘 안에 고칠 수 있는 가장 싼
시점에 발견한 것입니다.

### Step 4. 보고서 마감 (8교시)

민준의 보고서 핵심 표 — 발표(159) 슬라이드의 원본이 됩니다:

| 항목 | 수치 | 증거 |
|---|---|---|
| 베이스라인 → 최종 | MAE 1,914 → **1,183 (−38.2%)** · 등급 0.85 | MLflow run b7d31a52 |
| 데이터 | 51역 × 956일 = 48,756행 · 검증 4층 | validate_all 로그 |
| 운영 | 커밋→반영 2m40s · 롤백 41s · 기동 2m18s | Actions·리허설 실측 |
| 한계 | 폭우 오차 · 연휴 D-6 시 정확도 저하 · 신규 역 미지원 | 오차 리포트·대체 로그 |

**오늘 퇴근 체크** — □ README 5분 규칙 통과(짝 검증) □ 절차서 교차 수행(막힘 수리
포함) □ 빈 서버 2m18s 실측 □ 보고서(사고와 수리 절 포함) □ 155 감사표의 문서 항목 ✅

## ⑤ 자주 하는 실수

### README가 기능 명세서

**증상** — "본 프로젝트는 FastAPI 기반으로… 엔드포인트는 다음과 같으며…" 3,000자 —
그림도 실행 방법도 3화면 아래에.
**원인** — 독자를 "이미 관심 있는 사람"으로 가정 — 실제 독자는 15분 안에 떠날 사람입니다.
**해결** — 5분 규칙의 순서를 기계적으로 따르세요. 첫 화면 = 문제 한 문장 + 스크린샷 +
실행 3줄. 상세는 전부 docs/로 — README는 문서가 아니라 **관문**입니다.

### 보고서에서 사고가 사라짐

**증상** — 보고서의 모델 절이 "최종 MAE 1,183" 만 — 1,146의 흔적이 저장소 곳곳(MLflow
v1, 이슈 #33, 150의 데모 기록)에 남아 있는데 보고서에만 없음.
**원인** — 보고서를 홍보물로 오해.
**해결** — 심사자는 이력(커밋·이슈·MLflow)을 봅니다 — 기록과 보고서가 어긋나는 순간
보고서 전체가 의심받습니다. 사고 절은 정직의 비용이 아니라 신뢰의 투자입니다 (155 ⑥
Q3). 이력이 남는 시스템을 4주 내내 썼다는 사실이, 이제 정직을 강제하는 구조가 된
것입니다 — 그것이 이 과정이 설계된 방식입니다.

### 절차서를 쓴 사람이 검증

**증상** — "제가 해 보니 되던데요" — 발표 후 심사위원 수행에서 3분 만에 막힘.
**원인** — 쓴 사람의 머릿속 맥락이 문서의 구멍을 자동으로 메움 — 본인은 구멍을 볼 수
없습니다.
**해결** — 검증자 ≠ 작성자 규칙 (Step 2). 이상적 검증자는 "그 작업을 안 해 본 팀원"
입니다 — 한산 팀이 롤백 절차를 민준(모델 담당)에게 시킨 이유입니다.

### "재현 가능"의 근거가 기억

**증상** — "시드 고정했으니 같은 숫자 나와요" — 리허설에서 데이터가 달라(그날의 DB 상태)
숫자가 다름 — 150에서 겪고도 반복.
**원인** — 재현의 삼위일체(코드+데이터+설정) 중 데이터를 또 잊음.
**해결** — 보고서의 모든 숫자에 증거 열(run id·스냅숏·로그)을 붙이는 규칙이 그물입니다.
증거를 못 붙이는 숫자는 보고서에 쓸 수 없고, 쓸 수 없으면 재현 절차를 만들게 됩니다 —
규칙이 절차를 낳는 순서입니다.

## ⑥ 확인 문제

**Q1.** "저장소는 읽는 사람의 경험이다"라는 관점이 문서 작업의 우선순위를 어떻게
바꾸는지 — 15분 심사 시나리오를 분 단위로 가정하고, 각 구간에서 승부가 나는 문서를
짝지어 보세요.

<details>
<summary>답 보기</summary>

가정: 0~2분 README 첫 화면(문제·그림·숫자) — 여기서 "볼 가치"가 판정되므로 5분 규칙의
1·2·4절이 승부처. 2~7분 clone→up — 실행 방법의 복붙 가능성과 .env.example의 완결성,
그리고 실제 기동 성공(2m18s)이 승부처 — 재현성 20점의 대부분이 이 5분에 걸립니다.
7~12분 문서 산책 — 보고서의 표와 사고 절, 절차서의 상황 목차가 "깊이 있는 팀"의 인상을
만듭니다. 12~15분 이력 확인 — PR·이슈·MLflow가 보고서와 일치하는지. 이 시나리오에서
드러나는 우선순위: 완벽한 API 주석보다 README 첫 화면이, 코드 리팩터링보다 .env.example
한 줄이 점수에 가깝습니다 — 독자의 동선 위에 있는 것부터 완성하는 것이 문서 작업의
정렬 기준입니다.

</details>

**Q2.** 절차서 검증(민준의 교차 수행)에서 발견된 구멍("sha를 어디서 보는지")이 작성자
에게 보이지 않았던 인지적 이유와, 이것이 [Day 145](day-145.md)의 설계 리뷰와 같은
원리임을 설명하세요.

<details>
<summary>답 보기</summary>

작성자(지우)에게 "배포 sha는 이력 로그에서 본다"는 문서 이전의 배경 지식이라, 절차서를
읽을 때 뇌가 그 단계를 자동 보충합니다 — 문서의 구멍이 지식으로 메워져 보이지 않는
것이죠(지식의 저주). 검증자(민준)는 그 배경 지식이 없어 문서가 실제로 제공하는 정보만
으로 수행하고, 구멍에서 정확히 멈춥니다. 145의 설계 리뷰와 동일한 원리입니다 — 몰입한
팀에게 가정이 투명해지듯, 작성자에게 자기 지식이 투명해집니다. 해법도 동일합니다:
그 맥락이 없는 눈을 절차에 투입하는 것. 일반화하면, 전달물(설계·문서·발표)의 품질 검증
은 언제나 "수신자 조건의 재현"이어야 합니다.

</details>

구조가 없던 시절(예: 과제 제출물 하나로 평가받던 시절)과 비교해 보고서 작성의 규칙이
어떻게 달라지는지 설명하세요.

<details>
<summary>답 보기</summary>

장치: MLflow의 전 실험 run(폐기된 v1 포함), 이슈·PR 이력(#33 사고, 리뷰 코멘트), 커밋
로그, 배포·롤백 이력, 예측 로그와 대시보드 — 4주의 모든 결정이 타임스탬프와 함께
남아 있습니다. 제출물 하나로 평가받던 시절에는 최종본만 보이므로 보고서가 과거를
선택적으로 서술해도 검증이 어려웠습니다. 이력이 있는 구조에서는 보고서가 이력의 요약
이어야 하고, 요약과 원본의 불일치는 즉시 발견 가능합니다 — 따라서 규칙이 바뀝니다:
"잘된 것을 골라 쓴다"에서 "**일어난 일을 쓰되 해석을 단다**"로. 사고를 뺄 수 없으니
사고의 서사(발견→수리→방지)를 잘 쓰는 것이 유일한 전략이 되고, 그것이 결과적으로 더
강한 보고서를 만듭니다 — 투명성이 강제되는 환경에서는 정직이 최선의 전략이 아니라
유일한 전략입니다.

</details>
