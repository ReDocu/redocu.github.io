# Day 107 · merge vs rebase — 히스토리의 두 문체

> [← 이전 Day 106](day-106.md) · [목차](README.md) · [다음 → Day 108 PR 워크플로](day-108.md)

---

## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 같은 상황을 merge / rebase 로 각각 정리했을 때 **히스토리 모양이 어떻게 달라지는지** 그릴 수 있다.
- rebase가 커밋을 "옮기는" 게 아니라 **복제해서 다시 만드는** 연산임을 해시로 확인할 수 있다.
- **rebase의 황금률**(이미 공유한 커밋은 rebase 금지)을 위반하면 무슨 일이 나는지 설명할 수 있다.
- rebase 중 충돌을 `--continue` 로 이어 가고, `--abort` 로 물러날 수 있다.

---

## ② 왜 필요한가

어제 병합 커밋의 다이아몬드를 봤습니다. 팀 4명이 하루 3개씩 브랜치를 합치면 한 달 뒤
`git log --graph` 는 이렇게 됩니다:

```
*   병합 M12                      *  같은 한 달, rebase로 정리한 팀
|\                                *  지표 로그 추가
| *   병합 M11                    *  업로드 제한 상향
| |\                              *  헬스체크 상세화
| | * 지표 로그 추가               *  배치 상한 계약 명시
* | |   병합 M10                  *  ...
|\ \ \
| | | * ...    ← 어느 줄이 무슨 일인지 아무도 못 읽음
```

왼쪽 팀은 "지난주 목요일 배포가 왜 깨졌지?"를 조사할 때 그물망을 헤매고, 오른쪽 팀은 위에서
아래로 읽으면 끝납니다. **히스토리는 미래의 자신에게 보내는 운영 문서**인데, 그 문체가 오늘의
주제입니다 — 사실을 그대로 남기는 merge체와, 이야기를 정돈해 남기는 rebase체.

둘 중 하나가 정답이어서 배우는 게 아닙니다. **두 방식의 결과물이 다르다는 걸 모르는 채 섞어 쓰면**
히스토리도 그물이 되고, 최악의 경우 팀원의 커밋을 유실시키는 사고(황금률 위반)로 이어지기 때문입니다.

## ③ 개념 설명

### 출발 상황 — 갈라진 두 브랜치

모든 비교의 출발점은 같습니다. feature 작업 중에 main도 전진해서, 두 브랜치가 갈라진 상태:

```
main     ●──●──M1──M2
              \
feature        F1──F2
```

### 선택 1 — merge: 사실대로 기록

```
git switch main;  git merge feature
```

```
main     ●──●──M1──M2──◆ (병합 커밋)
              \        /
feature        F1──F2
```

- 기존 커밋을 **하나도 건드리지 않고**, 두 갈래를 잇는 병합 커밋 ◆를 새로 만듭니다.
- 장점: **비파괴** — 역사가 실제 일어난 그대로 남고, 언제 무엇을 합쳤는지 ◆가 증언합니다.
- 단점: 갈래가 많아질수록 그래프가 그물이 됩니다 (②의 왼쪽).

### 선택 2 — rebase: 기록을 다시 씀

```
git switch feature;  git rebase main
```

```
main     ●──●──M1──M2
                     \
feature               F1'──F2'     ← 갈라진 적이 없던 것처럼
```

- feature의 커밋들을 **main 끝에서 다시 만든 것**입니다. F1과 F1'은 내용이 같아도 **다른 커밋**
  (부모가 다르므로 해시가 다름 — 커밋 해시는 내용+부모+메타데이터의 지문이라는
  [Git 과정](../../../complate/Git/curriculum/01-beginner.md)의 그 원리).
- 장점: 이후 merge가 fast-forward로 끝나 **히스토리가 직선**이 됩니다.
- 단점: **역사를 고쳐 쓰는 파괴적 연산**입니다. 그래서 규칙이 하나 필요합니다 —

### 황금률 — push 한 커밋은 rebase 하지 않는다

F1을 이미 push 했고 팀원 B가 그 위에서 작업 중이라 합시다. 내가 rebase 하면 내 저장소의 F1은
F1'로 대체되지만, **B의 저장소에는 F1이 그대로** 있습니다. 이제 세상에 같은 작업의 다른 버전이
두 개 — B가 push 하는 순간 유령 커밋이 부활하고, 중복과 충돌이 팀 전체로 번집니다.

> **황금률: 나만 가진 커밋은 마음껏 rebase, 남과 공유한 커밋은 절대 rebase 금지.**
> "공유했다" = push 했다, 또는 누군가 내 브랜치를 받아 갔다.

### 팀 규칙은 보통 이렇게 조합된다

| 상황 | 권장 | 이유 |
|---|---|---|
| 내 feature 브랜치를 main 최신으로 따라잡기 | **rebase** | 아직 나만의 커밋 — 직선 유지 |
| feature → main 합치기 | **PR로 merge** (내일) | 언제 무엇이 들어왔는지 ◆가 남음 |
| 공유 브랜치(main, 남이 쓰는 브랜치) | **rebase 금지** | 황금률 |

즉 실무 기본형은 "**따라잡기는 rebase, 합치기는 merge**"입니다. 이 조합이면 ②의 오른쪽처럼
읽히는 히스토리가 유지됩니다.

## ④ 단계별 실습

### Step 1. 같은 상황을 두 번 만든다 (1~2교시)

비교 실험이니 실험 조건을 통일합니다. 어제의 `conflict-lab` 에서 스크립트처럼 상황을 조성하세요:

```powershell
cd conflict-lab
git switch main
git switch -c feature/metrics
"REQUEST_LOG = True" | Add-Content config.py
git commit -am "지표 로그 스위치 추가"
"LOG_SAMPLE_RATE = 1.0" | Add-Content config.py
git commit -am "로그 샘플링 비율 추가"
git switch main
"WORKERS = 1" | Add-Content app.py
git commit -am "워커 수 설정 분리"
```

이제 main(1커밋 전진)과 feature/metrics(2커밋)가 갈라졌습니다. **이 상태를 두 번 쓸 것이므로**
비교용 브랜치를 복제해 둡니다:

```powershell
git branch feature/metrics-rebase feature/metrics
```

### Step 2. merge 세계선 (3교시)

```powershell
git merge feature/metrics
git log --oneline --graph
```

```
$ git log --oneline --graph
*   c91f4e7 (HEAD -> main) Merge branch 'feature/metrics'
|\
| * 8b02d1c (feature/metrics) 로그 샘플링 비율 추가
| * f3a9d21 지표 로그 스위치 추가
* | 2e77c05 워커 수 설정 분리
|/
* 9d2c7be merge: 업로드 제한 충돌 해결 - 8MB 채택
```

다이아몬드 확인. 병합 커밋 c91f4e7이 "이 시점에 지표 로그 작업이 들어왔다"의 증거로 남습니다.

### Step 3. rebase 세계선 (4~5교시)

merge를 무르고(방금 만든 병합 커밋 전으로), 복제해 둔 브랜치로 rebase를 갑니다:

```powershell
git reset --hard 2e77c05        # main을 병합 전으로 (reset의 정식 수업은 모레)
git switch feature/metrics-rebase
git log --oneline -2            # rebase 전 해시를 기록해 두세요
git rebase main
git log --oneline -2            # 그리고 후
```

```
$ git log --oneline -2
8b02d1c (feature/metrics-rebase) 로그 샘플링 비율 추가
f3a9d21 지표 로그 스위치 추가
$ git rebase main
Successfully rebased and updated refs/heads/feature/metrics-rebase.
$ git log --oneline -2
5d19c3a (HEAD -> feature/metrics-rebase) 로그 샘플링 비율 추가
07e4b62 지표 로그 스위치 추가
```

**메시지는 같은데 해시가 전부 바뀌었습니다** (f3a9d21 → 07e4b62). rebase가 "이동"이 아니라
"재창조"라는 물증입니다 — 황금률이 왜 존재하는지가 이 두 줄에 있습니다. 이미 f3a9d21을 받아 간
사람이 있다면, 그 사람과 나는 이제 **다른 커밋**을 들고 있는 겁니다.

이어서 main에 합치면:

```powershell
git switch main
git merge feature/metrics-rebase
git log --oneline --graph -5
```

```
$ git merge feature/metrics-rebase
Updating 2e77c05..5d19c3a
Fast-forward
$ git log --oneline --graph -5
* 5d19c3a (HEAD -> main, feature/metrics-rebase) 로그 샘플링 비율 추가
* 07e4b62 지표 로그 스위치 추가
* 2e77c05 워커 수 설정 분리
* 9d2c7be merge: 업로드 제한 충돌 해결 - 8MB 채택
* 3e1f0a2 기준: 업로드 제한 5MB
```

`Fast-forward` — 병합 커밋조차 없이 이름표만 전진, 히스토리는 완전한 직선입니다.
Step 2의 그래프와 나란히 놓고 **같은 작업, 두 문체**를 눈에 새기세요.

### Step 4. rebase 중 충돌 (6~7교시)

rebase도 충돌이 납니다 — 단, **커밋을 하나씩 다시 적용하다가** 나기 때문에 어제와 모양이 조금 다릅니다.
main과 feature가 같은 줄을 고친 상황을 만들고 rebase 해 보면:

```
$ git rebase main
Auto-merging config.py
CONFLICT (content): Merge conflict in config.py
error: could not apply f7c210d... 샘플링 비율 0.5로 조정
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
```

해결 절차는 어제와 거의 같고 마지막 한 단어만 다릅니다:

1. 파일 열어 마커 정리 (결정)
2. `git add config.py` (신고)
3. **`git rebase --continue`** (commit이 아니라!) — 남은 커밋들의 재적용이 이어집니다

커밋이 5개인 브랜치라면 충돌이 **커밋마다 최대 5번** 날 수 있습니다 — rebase가 한 커밋씩
다시 만들기 때문입니다. 감당이 안 되면 언제든 `git rebase --abort` 로 시작 전 상태 복귀.
어제의 merge --abort와 같은 안전망입니다.

### Step 5. 정리와 과제 (8교시)

오늘 실험 전체를 그림 한 장으로 정리해 제출합니다.

**과제 — rebase 정리 실습.** ① Step 1~3을 처음부터 재현하되, 이번엔 feature 커밋을 3개로.
② merge 세계선과 rebase 세계선의 `git log --oneline --graph` 를 나란히 붙이고, 각 커밋 해시에
동그라미로 "바뀐 것/안 바뀐 것"을 표시하세요. ③ 마지막으로 두 문장: 우리 팀(MP4 페어 기준)에서
따라잡기와 합치기를 각각 어느 방식으로 할지, 근거와 함께.

## ⑤ 자주 하는 실수

### push 한 브랜치를 rebase 하고 push가 거절됨

**증상** —
```
 ! [rejected]        feature/metrics -> feature/metrics (non-fast-forward)
error: failed to push some refs to 'github.com:.../mlops-mp3.git'
hint: Updates were rejected because the tip of your current branch is behind
```
**원인** — rebase로 해시가 바뀌어, 원격의 옛 커밋들과 계보가 끊어졌습니다. 원격이 "당신 브랜치가
과거에 있다"고 착각하는 게 아니라, **정말로 다른 역사**가 된 겁니다.
**해결** — 이 브랜치를 나만 쓰는 게 확실할 때만 강제 push가 허용됩니다 — 안전장치가 달린
`git push --force-with-lease` 를 쓰며, 그 원리와 조건은 [Day 109](day-109.md)에서 다룹니다.
남과 공유한 브랜치였다면 이미 황금률 위반 — 팀에 즉시 알리는 것이 최선의 수습입니다.

### rebase 충돌에서 --continue 대신 git commit

**증상** — 충돌 해결 후 `git commit` 을 실행 — 커밋은 되는데 rebase가 끝나지 않고,
`git status` 에 `interactive rebase in progress` 가 계속 남습니다.
**원인** — rebase의 재개 신호는 commit이 아니라 `--continue` 입니다.
**해결** — 이어서 `git rebase --continue` 를 실행하면 진행됩니다. 꼬였다 싶으면 `--abort` 후 재시도.

### 따라잡기를 늘 merge로 해서 "Merge branch 'main' into ..." 커밋이 쌓임

**증상** — feature 브랜치 히스토리에 `Merge branch 'main' into feature/...` 가 서너 개 —
PR을 열면 리뷰어가 진짜 변경을 찾기 어려워합니다.
**원인** — main 최신화를 매번 merge로 (`git pull` 기본값 포함) 해결.
**해결** — 아직 공유 전인 feature의 따라잡기는 `git rebase main` 으로. `git pull` 이 병합 커밋을
만드는 게 싫다면 `git config pull.rebase true` (pull = fetch + rebase 로 변경)를 설정하세요.

### "rebase가 깔끔하니까" 공유 브랜치에도 적용

**증상** — 팀 공용 develop 브랜치를 누군가 rebase — 다음 날 전원 pull에서 충돌 폭발, 같은 커밋이
메시지만 같고 해시가 다른 채 두 벌씩 존재.
**원인** — 황금률 위반. 깔끔함은 **내 로컬 커밋**에만 허용되는 사치입니다.
**해결** — 공유 브랜치는 merge로만. 사고가 이미 났다면 팀 전체가 작업을 멈추고 어느 역사를
정본으로 할지 합의한 뒤 한 사람이 정리합니다 — 예방(황금률)이 수습보다 100배 쌉니다.

### 직선 히스토리에 집착해 병합 기록까지 없앰

**증상** — 모든 것을 rebase + fast-forward로만 — 히스토리는 완전한 직선인데, "이 기능이 언제
어떤 단위로 main에 들어왔는지"를 아무도 답 못 함.
**원인** — 직선 = 선(善)이라는 오해. 병합 커밋은 노이즈가 아니라 **기능 단위의 경계 표식**입니다.
**해결** — ③의 조합대로: 따라잡기는 rebase, 합치기는 merge(PR). 내일 배우는 PR 병합이
그 경계 표식을 자동으로 만들어 줍니다.

## ⑥ 확인 문제

**Q1.** rebase 후 커밋 메시지·코드 내용이 완전히 같은데도 해시가 바뀌는 이유를, 커밋 해시에
들어가는 재료로 설명하세요.

<details>
<summary>답 보기</summary>

커밋 해시는 스냅샷 내용뿐 아니라 **부모 커밋·작성 시각·커미터** 등 메타데이터 전체의 지문입니다.
rebase는 커밋을 새 부모(main의 끝) 위에서 다시 만들므로 최소한 부모가 달라지고, 따라서 해시가
반드시 달라집니다. "같은 작업"이어도 Git에게는 완전히 다른 커밋 — 이것이 공유 커밋 rebase가
사고인 이유의 전부입니다.

</details>

**Q2.** 팀원 B가 내 feature 브랜치를 받아서 그 위에 커밋을 쌓고 있는데, 내가 그 브랜치를 rebase
후 강제 push 했습니다. B의 화면에서 무슨 일이 벌어지는지 시간 순으로 서술하세요.

<details>
<summary>답 보기</summary>

① B가 pull 하는 순간 원격(내가 재창조한 역사)과 로컬(옛 역사 + 자기 커밋)이 갈라져 대량 충돌
또는 기묘한 병합이 발생합니다. ② 옛 커밋들이 B의 병합을 타고 원격에 되살아나 — 같은 변경이
해시만 다르게 두 벌 존재합니다. ③ 이후 로그·diff·리뷰 전부가 중복으로 오염되고, 어느 쪽이
정본인지 사람이 개입해 정리해야 합니다. 황금률("공유한 커밋은 rebase 금지")은 이 연쇄를 원천
차단하는 규칙입니다.

</details>

**Q3.** "따라잡기는 rebase, 합치기는 merge" 조합에서, 합치기를 merge로 하는 이유를 운영(사고
조사) 관점에서 한 가지 쓰세요.
