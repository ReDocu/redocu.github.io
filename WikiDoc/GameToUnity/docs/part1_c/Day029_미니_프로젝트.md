## 2. 오늘의 목표는 "완성"이다

## 3. 기획과 설계

### 3-1. 주제 선택 — 원본을 고르고 한 가지를 더한다

**왜 필요한가** — 처음부터 새로 만들면 하루에 못 끝낸다.

| 원본 | 확장 아이디어 | 난이도 |
|---|---|:--:|
| **01 텍스트 RPG** | 인벤토리 / 스킬 / 층별 던전 / 상점 | ★☆☆ |
| **02 탈출 루프** | 아이템 조합 / 시간 제한 이벤트 / 멀티 엔딩 확장 | ★☆☆ |
| **03 미로 탈출** | 추적 몬스터 / 시야 제한 / 랜덤 미로 생성 | ★★☆ |
| **04 갬블 게임** | 슬롯머신 / 블랙잭 / 카드 게임 | ★★☆ |
| **05 알카노이드** | 아이템 / 보스 블록 / 멀티볼 / 스테이지 에디터 | ★★★ |
| (새로) | 스네이크 / 테트리스 / 뿅뿅(Pong) / 두더지잡기 | ★★☆ |

**추천 조합**

```
   프로그래밍이 아직 버겁다  →  01 또는 02 + 기능 1개
   무난하게 완성하고 싶다    →  03 또는 05 + 기능 1~2개
   도전하고 싶다             →  새 게임 (단, 규칙이 단순한 것)
```

> **"새로 만들기"를 고른다면 규칙이 단순한 것으로 고른다.**
> 스네이크는 규칙이 3줄이다. 테트리스는 회전 처리만으로도 반나절이 걸린다.

### 3-2. 범위 확정 — Must / Should / Won't

**왜 필요한가** — 무엇을 **안 만들지** 정하는 것이 무엇을 만들지 정하는 것보다 중요하다.

```
   ┌──────────────────────────────────────────────┐
   │  Must   (반드시)   3개   ← 이게 없으면 게임이 아니다
   │  Should (되면)     1개   ← 시간이 남으면
   │  Won't  (안 함)    나머지 ← 명시적으로 적는다
   └──────────────────────────────────────────────┘
```

**예시 — 미로 탈출 확장**

| 구분 | 항목 |
|---|---|
| **Must** | ① 추적 몬스터 1종 ② 잡히면 게임오버 ③ 3스테이지 |
| **Should** | 시야 제한 (플레이어 주변 3칸만 보임) |
| **Won't** | 랜덤 미로 생성, 몬스터 AI 고도화, 아이템 시스템, 사운드 |

> **`Won't` 목록을 반드시 적는다.**
> 적어 두지 않으면 오후에 "이것도 넣을까?" 하다가 시간을 날린다.

### 3-3. 클래스 설계 — 종이에 먼저

**왜 필요한가** — 코드를 치기 전에 구조를 정하면 중간에 갈아엎지 않는다.

**설계 3단계**

```
   ① 화면에 무엇이 보이는가?        →  GameObject 후보
   ② 각각 무엇을 하는가?            →  Update / Render 내용
   ③ 무엇이 무엇에 반응하는가?      →  충돌 / 상호작용
```

**예시 — 미로 + 몬스터**

```
                    GameObject
                    m_x, m_y, m_active
                    virtual Update(dt)
                    virtual Render(screen)
                          ▲
         ┌────────────┬───┴────────┬─────────────┐
      Player       Monster       Item          Exit
      입력으로 이동   플레이어 추적   밟으면 획득    밟으면 클리어
```

**설계 체크 질문**

| 질문 | 답이 "예"면 |
|---|---|
| 화면에 그려지는가? | `GameObject` 상속 |
| 매 프레임 변하는가? | `Update` 구현 |
| 여러 개 존재하는가? | 매니저에 등록 |
| 다른 것과 부딪히는가? | `GetBounds` / `OnCollide` |

> **클래스를 5개 이상 만들지 않는다.** 하루 분량에 그 이상은 과하다.

### 3-4. 시간 배분

**왜 필요한가** — 시간을 나눠 두지 않으면 오전에 설계만 하다 끝난다.

```
   ┌────────────────────────────────────────────────────────┐
   │  09:00 ─ 10:00   주제 선정 · 범위 확정 · 강사 승인      │
   │  10:00 ─ 11:00   클래스 설계 (종이) · 프로젝트 세팅     │
   │  11:00 ─ 13:00   Must ① 구현                           │
   │  ─────────────────── 점심 ──────────────────────────── │
```

### Step 4~6 — Must 기능 하나씩 (11:00~17:00)

**각 기능을 30분 단위로 쪼갠다.**

예: "몬스터가 추적한다"

```
   ① Monster 클래스 만들고 화면에 M 표시        (30분)  →  빌드 ✔ 백업
   ② Monster가 매 초 한 칸씩 랜덤 이동          (30분)  →  빌드 ✔ 백업
   ③ Monster가 Player 방향으로 이동             (30분)  →  빌드 ✔ 백업
   ④ 벽을 통과하지 않게 (CanMove 재사용)         (30분)  →  빌드 ✔ 백업
```

```cpp
void Monster::Update(double dt)
{
    m_moveTimer += dt;
    if (m_moveTimer < m_moveInterval) return;

    m_moveTimer = 0;

    // 플레이어 방향으로 한 칸 (단순 추적)
    double dx = m_target->GetX() - m_x;
    double dy = m_target->GetY() - m_y;

    int stepX = 0, stepY = 0;

    if (fabs(dx) > fabs(dy))                    // 더 먼 축부터
        stepX = (dx > 0) ? 1 : -1;
    else
        stepY = (dy > 0) ? 1 : -1;

    if (CanMove((int)m_x + stepX, (int)m_y + stepY))    // Day 14 재사용
    {
        m_x += stepX;
        m_y += stepY;
    }
}
```

> 이 단순 추적이 **Day 61~63의 길찾기 알고리즘**의 출발점이다.
> 벽에 막히면 멈춰 버리는 한계를 오늘 직접 경험해 두면 그때 이해가 빠르다.

**✅ 각 단계마다** — 빌드하고 실행하고 백업한다.

```
   │    · 접촉 시 게임오버                         │
   │    · 3스테이지                                │
   │                                               │
   │  구현하지 못한 것:                            │
   │    · 시야 제한 (시간 부족)                    │
   │                                               │
   │  가장 어려웠던 점:                            │
   │    몬스터가 벽에 막히면 제자리에서 진동했다.   │
   │    "더 먼 축부터 이동" 규칙으로 완화했지만     │
   │    완전한 해결은 길찾기 알고리즘이 필요해 보인다.│
   └──────────────────────────────────────────────┘
```

**발표 대본 (3분)**

```
   ① 무엇을 만들었나       (30초)  — 실행하며 시연
   ② 어떻게 만들었나       (60초)  — 클래스 구조 설명
   ③ 무엇이 어려웠나       (60초)  — 막혔던 지점과 해결 방법
   ④ 다음에 한다면         (30초)  — 개선 아이디어
```

> **③이 가장 중요하다.** 잘 만든 것보다 **무엇을 배웠는지**가 평가의 핵심이다.
> 실패한 시도도 좋은 발표 소재다.

**✅ 여기까지 하면** — 내일 발표 준비가 끝난다.

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|
| 오전이 다 갔는데 코드가 없음 | 기획을 너무 오래 함 | 10시에 무조건 코딩 시작 |
| 범위가 계속 커짐 | `Won't` 목록 미작성 | 기획서로 돌아가 확인 |
| 오류 200개 | 한 번에 너무 많이 작성 | 30분 단위로 쪼개서 빌드 |
| 갑자기 전부 망가짐 | 백업 없음 | 마지막 백업으로 되돌린다 |
| 다른 PC에서 실행 안 됨 | 상대 경로 문제 | 리소스를 exe 옆에 두거나 경로 처리 |
| 시간이 부족함 | 계획대로 안 됨 (정상) | **범위를 줄인다.** 완성이 우선 |
| 클래스 설계가 꼬임 | 처음부터 완벽하려 함 | Day 28의 `GameObject`를 그대로 복사 |
| 몬스터가 제자리 진동 | 벽에 막힘 (단순 추적의 한계) | 정상. README에 적고 Day 61에서 해결 |
| 발표할 게 없다고 느낌 | 어려웠던 점을 안 적음 | 막혔던 순간을 떠올려 적는다 |
