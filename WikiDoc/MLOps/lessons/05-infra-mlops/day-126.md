## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- CI(지속적 통합)가 무엇을 자동화하는 것인지, **왜 "자주 + 자동"이 핵심**인지 설명할 수 있다.
- GitHub Actions 워크플로 파일의 구조(**on · jobs · steps · uses/run**)를 읽고 쓸 수 있다.
- **push마다 pytest가 자동 실행**되는 워크플로를 만들고, Actions 탭에서 로그를 읽어 실패를 고칠 수 있다.
- 러너가 **매번 새것인 빈 방**이라는 사실이 무엇을 요구하는지 말할 수 있다.

## ② 왜 필요한가

지난 금요일, 짝이 리뷰 기준표로 여러분의 저장소를 채점했습니다. 좋은 채점이었죠 — 단 한 번뿐
이라는 것만 빼면. 다음 주에 누가 또 채점해 줍니까? 그 다음 커밋은? 새벽 2시의 커밋은?

이번 주는 [Day 110](day-110.md)에서 예고한 어음을 갚는 주간입니다 — "규칙은 신사협정,
W26에서 시스템의 강제로". 그 시작이 CI(Continuous Integration, 지속적 통합)입니다:

```
지금:  코드 수정 → (기억나면) pytest → push          검증이 사람의 기억력에 달림
오늘:  코드 수정 → push → 기계가 무조건 pytest       검증이 이벤트에 묶임
```

"저는 테스트 잘 돌려요"라는 분께 — 문제는 성실성이 아니라 **구조**입니다. 4인 팀에서 한 명만
잊어도 main이 깨지고, [Day 115](day-115.md) deploy.sh의 3단계(테스트)는 배포 직전에야 —
가장 급한 순간에야 — 문제를 알려 줍니다. 검증은 **가장 이른 지점**(push)에서, **모든 사람에게
똑같이**, **잊을 수 없게** 걸려야 합니다. 그것이 CI의 전부입니다.

그리고 이미 준비는 끝나 있습니다 — [Day 104](../04-deep-learning-serving/day-104.md)에서
"한 줄로 도는 테스트"를 만들 때 예고했던 그대로, **CI가 돌리는 것은 바로 그 pytest**입니다.
오늘 할 일은 그 한 줄을 기계의 손에 쥐여 주는 것뿐입니다.

## ③ 개념 설명

### GitHub Actions 용어 지도

| 용어 | 뜻 | 우리말 비유 |
|---|---|---|
| workflow | 자동화 시나리오 1개 (`.github/workflows/*.yml`) | 작업 지시서 |
| `on:` (trigger) | 언제 실행되나 (push, pull_request, 예약…) | 초인종 |
| job | 워크플로 안의 작업 묶음 — **각자 새 러너에서** | 작업반 |
| step | job 안의 한 단계 | 지시서의 한 줄 |
| `run:` | 셸 명령 실행 | 직접 시킴 |
| `uses:` | 남이 만든 액션(부품) 사용 | 외주 |
| runner | 실행되는 기계 — GitHub이 빌려주는 **일회용 Ubuntu VM** | 매번 새 작업실 |

파일은 YAML — 지난주 Compose로 단련된 그 문법입니다 (탭 금지·들여쓰기가 구조).

### 러너는 빈 방이다 — 이 사실이 모든 것을 결정한다

워크플로가 돌 때마다 GitHub은 **깨끗한 Ubuntu 가상 머신**을 새로 내줍니다. 내 코드도, 파이썬
버전도, 패키지도, **모델 파일도** 없습니다. 그래서 워크플로의 앞 단계는 언제나 "방 꾸미기"입니다:

```yaml
steps:
  - uses: actions/checkout@v4         # ① 내 코드 가져오기 (이것조차 자동이 아님!)
  - uses: actions/setup-python@v5     # ② 파이썬 설치
  - run: pip install -r requirements.txt   # ③ 의존성 설치
  - run: pytest -q                    # ④ 드디어 본론
```

번거로워 보이지만 이것이 CI의 숨은 가치입니다 — **"빈 방에서 내 프로젝트를 일으켜 세우는
절차"가 코드로 강제**됩니다. 그 절차가 문서(README)와 어긋나면 CI가 먼저 깨집니다.
Day 125의 clone→up 리허설을 기계가 push마다 하는 셈입니다. "내 컴퓨터에선 되는데"의 마지막
서식지가 여기서 소멸합니다.

### 어디서 검증하나 — 세 겹의 그물

| 그물 | 시점 | 잡는 것 |
|---|---|---|
| 로컬 pytest | 커밋 전 | 내가 아는 문제 (가장 빠른 피드백) |
| **CI (오늘)** | push/PR마다 | 내가 잊은 실행 · 환경 차이 · 팀원의 커밋 |
| deploy.sh의 테스트 (115) | 배포 직전 | 최후의 안전망 |

CI가 생겨도 로컬 테스트는 계속합니다 — CI는 대체가 아니라 **잊음에 대한 보험**입니다.

## ④ 단계별 실습

### Step 1. 첫 워크플로 (1~2교시)

`mlops-mp3` 에서 브랜치 `feature/ci`. 파일 위치가 정확해야 합니다 —
`.github/workflows/ci.yml` (**workflows** — s까지):

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: 의존성 설치 (CPU 휠)
        run: |
          pip install -r requirements.txt \
            --index-url https://download.pytorch.org/whl/cpu \
            --extra-index-url https://pypi.org/simple

      - name: 테스트
        run: pytest -q
```

CPU 휠 지정에 주목 — 러너도 GPU 없는 리눅스입니다 ([Day 113](day-113.md)·[118](day-118.md)과
같은 이유, 없으면 CUDA 5GB를 매번 받다가 시간 초과급으로 느려집니다). push 하고 GitHub 저장소의
**Actions 탭**을 엽니다.

### Step 2. 첫 실행 — 그리고 예정된 빨간불 (3~4교시)

```
CI / test (push)                                        ✗ 1m 42s
```

실패했습니다. 로그를 열어 읽습니다 (실패한 step이 빨갛게 접혀 있습니다):

```
Run pytest -q
FFFFFFF                                                              [100%]
=================================== FAILURES ===================================
______________________ ERROR at setup of test_health_reports_model _____________
FileNotFoundError: [Errno 2] No such file or directory: 'models/antbee_resnet18.pt'
7 failed in 3.87s
Error: Process completed with exit code 1.
```

**러너는 빈 방** — 여러분 PC의 models/ 폴더에는 모델이 있지만, 저장소에는 없습니다
([Day 101](../04-deep-learning-serving/day-101.md)의 ".gitignore + 받는 법 README" 정책 —
사람에게는 통했지만 기계는 README를 읽지 않습니다). 이것이 CI의 첫 기여입니다: **"우리
저장소는 사실 자립할 수 없었다"는 사실**을 지금까지 아무도 몰랐습니다 — clone 리허설(104·125)
에서도 사람이 모델을 복사하는 "판단"으로 메워 왔으니까요.

오늘의 해결 — 45MB는 GitHub 한계(100MB) 안이므로 **일단 저장소에 넣습니다**:

```bash
git rm --cached -r models 2>/dev/null; sed -i '/^models\//d' .gitignore
git add .gitignore models/antbee_resnet18.pt
git commit -m "ci: 모델을 저장소에 포함 (임시 — 큰 모델의 정답은 W27 DVC)"
git push
```

커밋 메시지의 "임시"가 중요합니다 — 이 방법은 45MB니까 통하는 임시방편이고, BERT(420MB)면
불가능하며, 모델이 갱신될 때마다 저장소가 무거워집니다. **"큰 파일을 Git처럼 다루고 싶다"는
요구가 오늘 공식적으로 발생**했고, 정답([Day 131](day-131.md) DVC)은 W27에 있습니다.

### Step 3. 초록불, 그리고 PR 위의 체크 (5교시)

```
CI / test (push)                                        ✓ 2m 18s
```

```
Run pytest -q
.......                                                              [100%]
7 passed in 21.38s
```

로컬(4초)보다 느린 21초 — 러너가 매번 방을 새로 꾸미는 비용입니다 (⑤에서 캐시로 단축).
이제 이 브랜치로 PR을 열면 — PR 화면 하단에 새 식구가 보입니다:

```
● All checks have passed
  ✓ CI / test    Successful in 2m 18s
```

리뷰어(사람)의 Approve 옆에 **기계의 판정**이 나란히 섭니다. 아직 이 체크는 장식입니다 —
빨간불이어도 병합 버튼이 눌립니다. 내일 그 버튼을 잠급니다.

### Step 4. 실패를 일부러 — CI가 잡아내는 광경 (6교시)

체험 한 번이 백 마디보다 낫습니다. service.py의 임계값 하나를 일부러 틀리게 바꾸고 push:

```
CI / test (push)                                        ✗ 2m 09s
......F                                                              [100%]
FAILED tests/test_api.py::test_predict_matches_training_record - assert 0.6912 == 0.7214 ± 1.0e-03
1 failed, 6 passed in 21.05s
```

[Day 104](../04-deep-learning-serving/day-104.md)의 회귀 테스트(0.7214±0.001)가 CI 위에서
울렸습니다 — **push 2분 만에, 아무도 안 시켰는데.** revert 하고(109!) 초록을 되찾으세요.
이 사이클(깨짐 → 2분 내 발각 → 수정)이 CI가 파는 상품입니다.

### Step 5. 과제 — 뱃지와 이식 (7~8교시)

**① 뱃지.** Actions 탭 → 워크플로 선택 → ⋯ 메뉴 → "Create status badge" → README 최상단에:

```markdown
![CI](https://github.com/mlops-student/mlops-mp3/actions/workflows/ci.yml/badge.svg)
```

이제 저장소 첫 화면이 상시 건강 상태를 말합니다 — 포트폴리오를 여는 채용 담당자가 0.5초 만에
보는 신호입니다.

**② 이식.** `datapipe` 저장소에도 같은 구조의 CI를 붙이세요 (torch가 없어 더 단순합니다 —
그 차이를 워크플로에 어떻게 반영했는지 한 줄 메모). **③ 관찰.** 두 저장소의 CI 실행 시간을
기록하고, 시간을 가장 많이 먹는 step이 무엇인지 로그의 step별 시간으로 답하세요 (내일 캐시
논의의 재료).

## ⑤ 자주 하는 실수

### 워크플로가 아예 나타나지 않음

**증상** — push 했는데 Actions 탭이 텅 빔 — 에러조차 없음.
**원인** — 경로 오타: `.github/workflow/`(s 없음), `.yml.txt`, 또는 워크플로 파일이 push 안 됨.
**해결** — 경로 철자를 문자 단위로 확인: `.github/workflows/ci.yml`. "실행되고 실패"와 "아예
등록 안 됨"은 다른 병입니다 — 탭에 워크플로 이름조차 없으면 100% 경로/문법 문제입니다
(YAML 문법 오류는 탭에 빨간 배너로 뜹니다).

### 로컬은 되는데 CI에서만 import 에러

**증상** —
```
ModuleNotFoundError: No module named 'app'
```
**원인** — 로컬에선 IDE·작업 폴더가 경로를 눈치껏 맞춰 줬지만, 빈 방(러너)에는 그 눈치가
없습니다 — 프로젝트가 파이썬에게 정식으로 소개된 적이 없는 것.
**해결** — 정공법은 [Day 013](../01-python-data/day-013.md)의 그 구조 — 패키지로 만들고
`pip install -e .`. pytest 설정(rootdir/pythonpath)으로도 해결되지만, "빈 방에서도 서는
프로젝트"가 근본 답입니다. CI는 이런 잠복 문제를 드러내는 엑스레이입니다.

### 대소문자 때문에 CI에서만 파일을 못 찾음

**증상** — 로컬(Windows) 통과, CI(Linux)에서 `FileNotFoundError: tests/Data/ant_sample.jpg`.
**원인** — Windows는 대소문자를 안 가려 `Data`/`data` 혼용이 살아남지만, 러너는 Linux입니다
([Day 111](day-111.md)의 그 규칙이 CI에서 발병).
**해결** — 코드와 실제 파일명의 대소문자를 일치시키고, 이참에 전부 소문자로 통일. "CI에서만
깨지는 병"의 단골 1위 — CI가 있어서 **팀원 리눅스 노트북에서 터지기 전에** 잡힌 겁니다.

### 매 실행 pip install 2분 — 캐시를 모름

**증상** — 워크플로 시간의 대부분이 의존성 설치.
**원인** — 빈 방이니 당연 — 하지만 GitHub은 방 사이에 짐 보관소(캐시)를 제공합니다.
**해결** — setup-python의 내장 캐시 한 줄:
```yaml
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: "pip"
```
같은 requirements면 다운로드를 재사용합니다 (2m 18s → 50s 수준). Dockerfile 캐시(117)와 같은
원리 — **입력이 같으면 결과를 재사용** — 가 CI에도 있는 것입니다.

### 초록불을 "코드가 옳다"로 읽음

**증상** — "CI 통과했는데 왜 버그가 있죠?"
**원인** — CI는 **돌린 테스트만큼만** 보증합니다. 테스트가 안 덮는 경로는 초록불 뒤에 그대로.
**해결** — 초록불의 정확한 독법: "우리가 정의한 검사를 이 커밋이 통과했다". 보증 범위를 넓히는
것은 내일(품질 게이트 — 린트·커버리지)과 여러분이 쓰는 테스트 자신입니다. CI는 그물의 자동화지,
그물코의 크기가 아닙니다.

W22의 개념으로 설명하세요.

<details>

통합을 미루면 브랜치들이 오래 갈라져 있게 되고, 갈라진 시간에 비례해 충돌의 크기와 "누구 변경이
문제인가"의 탐색 공간이 자랍니다 (Day 106의 충돌 조건은 같은 곳을 각자 오래 고칠수록 충족되기
쉬움). 자주 통합하면 회차당 변경이 작아 충돌도 작고, 깨졌을 때 용의자가 "방금 그 커밋"으로
좁혀집니다. CI는 그 잦은 통합마다 검증을 자동으로 붙여 "자주 합쳐도 안전"을 만들고, 그래서
작은 PR(Day 108)과 CI는 한 세트입니다.

**Q2.** Step 2의 실패(모델 부재)는 로컬 pytest·clone 리허설에서도 잡히지 않았습니다. 왜 CI만
잡아냈는지, 그리고 이것이 드러낸 우리 저장소의 문제를 "재현성" 언어로 정리하세요.

<details>
<summary>답 보기</summary>

로컬에는 모델이 이미 있었고, 리허설에서도 사람이 "모델을 어디서 복사한다"는 암묵지로 구멍을
메웠습니다. 러너는 저장소 밖 지식이 0인 진짜 빈 방이라, "저장소만으로는 프로젝트가 서지 않는다"
는 사실이 처음으로 검증 가능한 실패가 됐습니다. 재현성 언어로: 코드·환경은 봉인됐지만
**아티팩트(모델)의 출처가 봉인 밖**이었던 것 — 임시로 저장소에 넣어 봉인했고, 크기·갱신 문제
때문에 전용 봉인 도구(DVC, Day 131)가 필요하다는 요구가 성립했습니다.

</details>

관점에서 반박하세요.

<details>
<summary>답 보기</summary>

피드백 속도: 로컬 pytest는 4초, CI는 2분+ — 코딩 리듬에서 30배의 차이이고, 실패를 CI에서
처음 알면 수정→push→대기의 루프가 반복됩니다. 팀 비용: 깨진 push는 PR의 빨간 체크로 팀
전체에 노출되고 (내일부터는 병합 차단으로 팀을 실제로 막습니다), 러너 시간도 공유 자원입니다.
CI는 "잊음과 환경 차이의 보험"이지 1차 검증이 아닙니다 — 그물 세 겹(로컬→CI→배포 전)은
각자 잡는 것이 다르므로 하나를 없애는 게 아니라 겹칩니다.
