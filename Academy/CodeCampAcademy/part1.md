# 제1부 · 일하는 방식이 바뀐다, 그리고 PRD (Day 1)

### 1. 직군의 경계가 허물어졌다

| | 과거 | 지금 |
|---|---|---|
| 기획자/PM | PRD 기획, 시장·경쟁사 조사 | 웹/앱 와이어프레임 → **프로토타입 개발** |
| 디자이너 | 배너, UX/UI 디자인 | 웹/앱 디자인 → **프로토타입 개발** |
| 개발자 | 웹/앱·게임 개발 | 웹/앱 → **프로덕트 개발** |
| 마케터 | 광고·홍보 영상, 콘텐츠 발행 | 웹/앱 마케팅 → **랜딩페이지 개발** |

- 과거에는 직군마다 담당 업무의 경계가 뚜렷했다. 지금은 **웹/앱 만들기가 모든 직군의 공통 업무**다.
- 각 직군의 결과물이 하나의 흐름으로 이어진다 — **와이어프레임 프로토타입 → 디자인 프로토타입 → 프로덕트 → 랜딩페이지.**

### 2. AI 도구의 지형도 — 두 개의 3단계

**AI의 발전 3단계 — 생성 → 조작 → 자율 실행**

| 단계 | 유형 | 형태 | 역할 | 대표 도구 |
|---|---|---|---|---|
| 1 | **생성형 AI** | 웹 | 글·이미지·코드 **생성** | ChatGPT, Gemini, Claude |
| 2 | **AI 에이전트** | 설치형 | 코딩 + **내 컴퓨터 조작** | Cursor(개별 파일), Codex·**Claude-Code**(전체 폴더) |
| 3 | **에이전틱 AI** | 설치형 | **자율적인 계획 및 실행** | Claude-Cowork, Open-Claw, Hermes-Agent |

**웹 제작 도구의 3단계 — 기능이 누적된다**

| 단계 | 결과물 | 다루는 기능 | 대표 도구 |
|---|---|---|---|
| **홈페이지** | 회사 홈페이지 | 템플릿 사용 | Wordpress, imweb, Wix |
| **프로토타입·MVP** | 최소 기능 제품 | AI채팅 + **DB 연동** | Lovable, Replit, V0, Bolt … |
| **프로덕트** | 운영 중인 서비스 | + **테스트 코드 + 병렬 구현** | Cursor, Codex, **Claude-Code** |

- **클로드코드 하나로 세 단계를 모두 커버한다.** 그래서 도구를 바꿔 가며 배우는 대신 하나에 집중한다.
- 실습 대상도 이 3단계를 그대로 따라간다 — 홈페이지(3D 홈페이지) → MVP(게임·노션) → 프로덕트(맛집 커뮤니티).

**생성형 AI vs AI 에이전트 — 챗봇과 비서**

| | 생성형 AI | AI 에이전트 |
|---|---|---|
| 비유 | **챗봇** | **비서** |
| 하는 일 | 결과물을 만들어 줌 | 파일 생성·수정, 명령 실행 등 **직접 처리** |
| 실행 주체 | 사람이 직접 | **AI가 직접** |

### 3. AI 에이전트의 5가지 핵심 요소

| 요소 | 의미 | 예시 |
|---|---|---|
| **컨텍스트** | 제한된 기억 | 200k(20만 토큰), 1M(100만 토큰) |
| **모델 / 에포트** | 똑똑한 정도(성능) | Opus-4.8, GPT-5.5 |
| **스킬** | 내장된 프롬프트 | Frontend-design, Ui-ux-pro-max |
| **훅스** | 작업 중단 / 제어 | PreToolUse, PostToolUse |
| **MCP** | 외부 연결 도구 | Supabase-mcp, Figma-mcp |

- **컨텍스트와 모델/에포트가 기본 체력**, **스킬·훅스·MCP가 확장·제어·연결**이다. 이 다섯이 이 책 전체의 뼈대이고, 각각 Day 2(컨텍스트)·Day 3(스킬)·Day 4(MCP)에서 다시 만난다.

### 4. 클로드코드의 자리 — CLI, 설치 구조, 두 개의 손잡이

- 컴퓨터 제어는 **CLI(명령어 입력)** 와 **GUI(마우스 클릭)** 로 나뉘고, 클로드코드는 **CLI**에서 동작한다.
- 설치는 두 갈래 — **내 컴퓨터**에 클로드코드 본체 + Node.js(한 번), **프로젝트 폴더**의 **`.claude/` 숨김 폴더**에 플러그인(스킬·훅스·MCP)(프로젝트마다).
- 만드는 것: **웹서비스**(HTML=구조 · CSS=색/정렬 · JS=기능 → React·Next로 확장)와 **업무 자동화**(JS/Electron, Python, Java).

**성능을 조절하는 두 손잡이**

| 설정 | 의미 | 단계 |
|---|---|---|
| **model** | 똑똑한 정도 | Haiku 4.5 → Sonnet 4.6 → **Opus 4.8** |
| **effort** | 생각의 깊이 | low → medium → high → xhigh → max → **(ultracode)** |

- **`ultracode`는 Opus에서만** 선택 가능하다. 똑똑한 모델 + 높은 effort일수록 성능은 좋지만 **비용·시간이 늘어난다** — 작업에 맞게 고른다.

### 5. PRD — 만들기 전에 쓰는 문서

**PRD(Product Requirements Document, 제품 요구사항 정의서)가 답하는 질문**

| 질문 | 산출 |
|---|---|
| **누가 사용?** | **페르소나** |
| **무엇을 사용?** | 기능 목록 |
| **왜 사용?** | 가치·동기 |
| 성공 검증 방법? | 지표 |
| 최소 기능, 추후 확장 기능? | MVP 범위 / 로드맵 |

**개발 순서는 항상 2단계다.**

```
[누가·무엇을·왜]  →  클로드코드  →  PRD.md
                                      │ (참고)
                                      ▼
[PRD.md 참고]     →  클로드코드  →  html, css, js
```

- ① *"이 내용으로 **PRD 만들어줘**"* → `prd.md` ② *"**prd.md 참고해서** 홈페이지 만들어줘"* → 코드.
- **1단계의 결과물이 2단계의 입력이 된다.** 요구사항을 문서로 남기면 AI가 방향을 잃지 않는다.
- 예시(자기소개 홈페이지) — **누가**: 채용담당자 / **무엇을**: 메뉴 4종(홈·포트폴리오·자기소개·연락처) + 스크롤·파티클 애니메이션 / **왜**: 자기소개·포트폴리오를 보고 **채용 여부를 검증**하기 위해.
- **타깃을 좁히면 기능과 목적이 명확해진다.** "누구나"가 아니라 "채용담당자"라고 적는 순간 필요한 화면이 정해진다.

**📝 과제** — 위 내용을 프롬프트로 옮겨 `prd.md` 생성 → 이어서 "prd.md 참고해서 홈페이지 만들어줘".

> **한 문장 요약(Day 1)** — *무엇을 왜 만들지를 먼저 문서로 정리하고, 클로드코드에게 맡겨라. 그러면 직군에 관계없이 누구나 만드는 사람이 된다.*

# 제2부 · 웹의 구조와 AI의 기억 (Day 2)

### 1. 홈페이지 vs 웹 서비스 — 기준은 DB의 유무

| | 홈페이지 | 웹 서비스 |
|---|---|---|
| 구성 | 프론트엔드 서버 | 프론트엔드 + **백엔드 + DB** |
| 데이터 흐름 | 사용자 ↔ 프론트엔드 | 사용자 ↔ 프론트 ↔ 백엔드 ↔ DB |
| DB 시스템 | 불필요 | **필요** — 보안·설계·백업 |
| 목적 | 정적 콘텐츠 제공 | 데이터 기반 동적 서비스 |

- 백엔드+DB는 직접 짓지 않고 **BaaS(Backend as a Service)** 로 빌려 쓴다 — **Firebase(NoSQL, 문서마다 자유)** vs **Supabase(SQL, 고정된 행·열)** ⭐.
- 즉 3계층의 **백엔드 서버 + DB 자리에 Supabase 하나**를 끼워 넣으면 구조가 단순해진다.

### 2. 프론트엔드의 진화 — 페이지를 언제 내려받는가

| | MPA | SPA |
|---|---|---|
| 최초 접속 | 해당 페이지만 | **전체를 미리 묶음 다운로드**(= `index.html` 하나) |
| 링크 이동 | 새로 다운로드 (**느림**) | 이미 받은 것 표시 (**빠름**) |

| 기술 | 방식 | 이동 속도 | 검색(SEO) |
|---|---|---|---|
| html/css/js | MPA | 느림 | — |
| **React** | SPA | 빠름 | **첫 페이지만** 검색됨 |
| **Next ⭐** | SPA + | 빠름 | **개별 상세 페이지까지 검색됨 — SEO 좋음** |

- 쇼핑몰이라면 키보드 상세·남성의류 상세가 **각각 검색되는가**가 갈림길이다. 그래서 검색 노출이 중요한 서비스에는 **Next**가 유리하다.

**현대적 웹 개발의 세 조각**

```
[Claude-Code (React/Next)]  +  [Vercel]  +  [Supabase]
        개발                프론트 배포      백엔드+DB
```

### 3. PRD에서 GDD로

- 만들려는 것이 **게임**이면 PRD가 **GDD(Game Design Document)** 가 된다. **틀은 동일**하다 — 누가/무엇을/왜.
- 소코반 예시 — **누가**: 단순한 논리 퍼즐을 좋아하는 사람 / **무엇을**: 1~10단계, 동굴 배경, 부드러운 이동 애니메이션 / **왜**: 버스·지하철에서 심심할 때.
- 2단계 흐름도 같다. 다른 것은 **결과물뿐** — 홈페이지는 html/css/js, 게임은 React/Next.

### 4. 컨텍스트 — AI의 제한된 기억

| 용량 | 토큰 수 | 영어 A4 | 한글 A4 |
|---|---|---|---|
| **200K** | 20만 | 400장 | **100장** |
| **1M** | 100만 | 2000장 | **500장** |

- 환산: **한글 1글자 ≈ 1토큰**, **영어 4글자 ≈ 1토큰**. 한글이 토큰을 더 많이 먹는다.
- 컨텍스트에 담기는 것: **기본 규칙(`CLAUDE.md`) + 상세 규칙(`.claude/rules/`) + 지난 대화 + 이번 대화.**

**두 가지 특징이 모든 문제의 출발점이다.**

- **① 매 대화마다 직전 컨텍스트를 재주입한다** → 규칙과 지난 대화에 대한 **비용을 반복 지불**한다.
- **② 처음과 끝은 잘 기억하고 중간은 잘 잊는다** → 중요한 지시는 **처음(규칙)이나 끝(최근)** 에 두거나 문서로 남긴다.

| 명령어 | 동작 | 언제 |
|---|---|---|
| **`/clear`** | 컨텍스트 **완전 초기화** | **새 기능**을 시작할 때 |
| **`/compact`** | 요약·압축 (맥락 유지) | 같은 기능을 **수정·보완**할 때 |

- 판단 기준은 한 줄이다 — **새 기능이면 `/clear`, 이어서 다듬으면 `/compact`.**

### 5. 모든 것은 어디에 사는가

```
프로젝트 폴더/
├── .claude/          (숨김 폴더)
│   ├── rules/        → 상세 규칙
│   ├── skills/       → 스킬
│   └── hooks/        → 훅스
├── CLAUDE.md         → 기본 규칙
├── .mcp.json         → MCP
└── 기타 (html, css, js …)
```

- 두 갈래로 이해한다 — **규칙**(`CLAUDE.md` + `.claude/rules/`, 컨텍스트로 매번 재주입) / **플러그인**(`skills` + `hooks` + `.mcp.json`).

**📝 과제** — GDD로 소코반 게임 제작 + 기능 추가마다 `/clear`(신규) · `/compact`(보완)로 컨텍스트 관리.

> **한 문장 요약(Day 2)** — *뒷단은 빌려 쓰고(Supabase·Vercel), 앞면은 진화한 도구로 만들며(React·Next), 설계는 문서로 먼저 하고, AI의 기억은 clear와 compact로 다스려라.*

# 제3부 · 클로드코드 잘 부리기 — 명령어와 스킬 (Day 3)

### 1. 슬래시 명령어 — 클로드코드의 리모컨

프롬프트에 **`/`** 를 입력하면 수십 개의 명령어가 펼쳐진다. 전부 외울 필요는 없고, 무리로 묶어 둔다.

| 묶음 | 명령어 |
|---|---|
| **컨텍스트 3종(가장 중요)** | **`/clear`**(초기화) · **`/compact`**(압축) · **`/context`**(상태 확인) |
| 설정 | `/init`(CLAUDE.md 생성) · `/effort` · `/model` · `/advisor`(상위 모델 조언) |
| 에이전트 | `/agents` · `/btw`(곁다리 질문) · `/goal`(목표 달성까지 반복) · `/fork`(분신) |
| 플러그인·스킬·MCP | `/plugin` · `/reload-plugins` · `/skills` · `/reload-skills` · `/mcp` |
| 세션·되돌리기 | `/plan` · `/resume` · `/rewind` · `/remote-control` |
| 검토·검증 | `/code-review` · `/security-review` · `/verify` · `/simplify` · `/deep-research` |
| 요금·상태 | `/usage` · `/usage-credits` · `/upgrade` · `/status` · `/statusline` |
| 문제 해결 | **`/doctor`**(설치·설정 진단) |

### 2. 사용량과 요금 — `/usage`

- 세션 총비용 + **모델별** 사용량을 보여준다. 실측 예: 같은 세션에서 **Haiku $0.0011 vs Opus $1.68** — **차이가 크다.** 간단한 작업엔 저렴한 모델.
- **한도 3종은 각각 독립**이다: **5시간(현재 세션)** · **1주 전체 모델** · **1주 Sonnet 전용**.
- **사용량의 약 절반(49%)이 서브에이전트가 많은 세션에서 발생**한다 — 서브에이전트는 각자 요청을 실행하므로 남발하면 비용이 급증한다.

### 3. 터미널 멀티플렉서 — 여러 일을 동시에

- 하나의 터미널을 여러 창(pane)으로 분할해 **여러 에이전트를 병렬 실행·모니터링**한다. 각 창을 **워크트리(wt1~wt4)** 로 분리하면 충돌 없이 작업할 수 있고, 오른쪽에 브라우저 패널을 두면 **실시간 미리보기**가 된다.

| 도구 | 특징 | OS |
|---|---|---|
| **tmux** | 터미널 분할 | Linux / MacOS |
| **cmux** | 분할 + **작업 완료 알람** + **브라우저 연동** | MacOS |
| **wmux** | 터미널 분할 | **Windows** |

- 단, 창을 많이 띄울수록 **사용량(비용)이 증가**한다.

### 4. 스킬 — 프롬프트를 자산으로 ⭐

**스킬 이전의 세계** — 매번 이런 프롬프트를 직접 썼다.

```
① 역할 부여    : 넌 이제부터 10년차 개발자야
② 진행 방식    : step by step 으로 생각하고 진행해줘
③ 방법론 지침  : 전체적인 설계를 먼저 하고, 그 다음에 진행해줘
─── === ───   (지침과 작업을 가르는 구분선)
④ 실제 작업    : 테트리스 코드 생성해줘
```

- 잘 만든 프롬프트는 **저장 → 재사용 · 판매 · 공유**의 가치가 있고, 특정 도구 전용이 아니라 **여러 에이전트에 붙여** 쓸 수 있다.
- 이것을 도구로 정식화한 것이 **스킬**이다 — **"매번 쓰기"에서 "등록 후 호출"로** 개발 방식이 바뀐다.

**스킬 만들기는 파일 하나다.**

```
.claude/skills/orange/SKILL.md
        └───┬───┘ └─┬─┘  └──┬──┘
        저장 위치  스킬 이름  프롬프트(텍스트)
```

- **폴더 이름 = 스킬 이름**, **`SKILL.md` 내용 = 프롬프트.** 작성 후 `/reload-skills` → `/orange 홈페이지 만들어줘`.
- 호출은 **`/스킬이름` + 작업요청** 구조다 — [스킬 지침] + [이번 요청]이 합쳐져 실행된다.

**직군별 유명 스킬**

| 직군 | 스킬 |
|---|---|
| 기획 / PM | **`pm-skills`** |
| 디자인 | **`frontend-design`**, `ui-ux-pro-max` |
| 개발 | **`test-driven-development`** |

**📝 과제** — 스킬을 만들거나 불러와 소코반 게임 완성. 성공 기준은 `.claude/skills/`에 폴더+`SKILL.md`가 있고, `/skills` 목록에 뜨고, **지침이 결과에 반영**되는 것.

> **한 문장 요약(Day 3)** — *명령어로 도구를 부리고, 컨텍스트로 기억을 다스리며, 반복되는 프롬프트는 스킬로 저장해 자산으로 만들어라.*

# 제4부 · 데이터를 연결하다 — Supabase와 MCP (Day 4)

### 1. 서버와 접속의 원리

| 프로그램 | 대상 | 식별 |
|---|---|---|
| **일반 프로그램**(포토샵·엑셀) | 사람 | — |
| **서버 프로그램** | 다른 프로그램(클라이언트) | **포트 번호 0~65535** |

**접속 = 호스트 + 포트.**

```
http://localhost:2763          →  내 컴퓨터의 2763번 서버 프로그램
http://naver.com:80  (생략)    →  HTTP 기본 포트
https://naver.com:443 (생략)   →  HTTPS 기본 포트
```

- **최초 접속 = html 파일 요청**, **새로고침 = html 파일 재요청** — 둘은 본질적으로 같은 동작이다. 서버가 응답하는 것은 결국 **화면 UI = html 파일**이다.

### 2. 데이터는 어디에, 어떤 모양으로

| | 로컬스토리지 | 외부 DB(Supabase) |
|---|---|---|
| 위치 | 브라우저 안 | 외부 서버 |
| 유지 범위 | **내 컴퓨터에서만** | **다른 기기에서도 유지** |
| 저장 모양 | Key–Value (`apple: 3`) | 테이블 (행·열) |

| | **NoSQL** | **SQL** |
|---|---|---|
| 저장 | 문서 기반 — 컬렉션 > 다큐먼트 > 필드 | 표 기반 — 테이블 > 행 / 열 |
| 성격 | **필드 추가 자유도 높음** | **구조적 안정성 높음** |
| 제품 | Redis, MongoDB | Oracle, MySQL, **PostgreSQL** |
| BaaS | **Firebase**(백엔드 + 구글 DB) | **Supabase**(백엔드 + PostgreSQL) |

- 두 방식 모두 각 레코드를 구분하는 **id**를 갖는다(Firebase는 다큐먼트 id 문자열, Supabase는 `uuid` 컬럼).

### 3. Supabase 실전

- 제공 기능 4종: **백엔드 · DB(Table Editor) · 이미지(Storage) · 로그인(Auth Providers — Email·구글·카카오…)**.
- 프로젝트 생성 시 정하는 것: 조직 · 이름 · **강력한 DB 비밀번호**(분실 주의) · **지역(한국이면 Seoul)**. 보안 옵션 중 **"새 테이블 자동 노출"은 해제 권장**, **RLS(행 수준 보안)** 는 필요 시 사용.
- 테이블의 뼈대는 **컬럼**이고, 컬럼은 네 가지로 정의된다.

| 항목 | 의미 |
|---|---|
| **Name** | 컬럼 이름 |
| **Type** | 데이터 타입 — `int8` · `text` · `uuid` · `date`/`timestamptz` · `json`/`jsonb` |
| **Default Value** | 값을 안 넣으면 들어갈 값 (보통 `NULL`) |
| **Primary** | 기본키 — 행을 고유하게 구분 (보통 `id`) |

### 4. MCP — AI를 외부 세계에 안전하게 연결

> **MCP(Model Context Protocol) = AI에게 설치하여, 외부 서비스에 연결하는 도구**

- 같은 MCP를 Cursor·Codex·Claude-Code가 공통으로 쓸 수 있고, MCP마다 **정해진 기능**을 제공한다(Supabase-mcp: 테이블 생성·조회 / Figma-mcp: UI 그리기·조회 / Notion-mcp: 페이지 생성·조회). **MCP를 제공하지 않는 서비스도 있다.**

**"AI가 내 컴퓨터를 조작할 수 있는데, 왜 MCP가 필요한가?"**

| | MCP 없을 때 | MCP 있을 때 |
|---|---|---|
| 접속 | 외부 서비스에 **직접** | MCP를 거쳐 |
| 로그인 | **제약**(인증 어려움) | **로그인 설정** 가능 |
| 통제 | **자유로운 접속 → 통제 불가** | **제한된 기능으로 통제** |

- 답은 이것이다 — AI는 **내 컴퓨터**는 조작해도 **외부 서비스**에는 직접 닿을 수 없고, 닿는다 해도 **통제되지 않는다.**

> **⚠️ Replit AI 에이전트 DB 삭제 사고 (2025-07)**
> 사용자가 **"코드를 절대 수정하지 말라"고 대문자로 11번** 지시했는데도, AI가 이를 무시하고 **운영 데이터베이스를 삭제**했다. 그 전에 **버그를 감추려 가짜 데이터를 만들고 단위 테스트 결과까지 조작**했다. 사고 후 '코드 프리징'을 시도했지만 *"몇 초 후 바로 코드가 다시 수정됐다"* — 변경을 막을 방법 자체가 없었다. 복구도 "불가능"이라고 답했다가 실제로는 가능했던 것으로 드러났다.
> **교훈:** 운영/테스트 DB 분리, 권한 최소화(RLS), 백업. 그리고 **명확한 지시도 무시될 수 있다** — 통제는 말이 아니라 구조로 한다.

### 5. 컨텍스트 로딩과 환경변수

| | **지연로딩(on-demand)** | 즉시로딩(eager) |
|---|---|---|
| 로드 시점 | **쓸 때만** | **처음부터** |
| 사용 전 토큰 | 거의 0 | 미리 차지 (예: MCP tools 5.9k) |

- MCP를 여러 개 등록해도 지연로딩이면 평소 토큰을 아낀다. `/context`로 사용량을, `/mcp`로 목록을 확인한다.

**`.env` — 비밀을 담는 파일**

```
VITE_SUPABASE_URL = https://xxxxxxxx.supabase.co
└─── 환경 변수 이름 ───┘ ↑ └────────── 값 ──────────┘
                        = (좌/우 분리 기준)
```

- 구조는 **`이름=값`**, **`#`으로 시작하는 줄은 주석**이다. 이 "이름(키) + 값(밸류)" 구조는 **NoSQL 필드**·**SQL 컬럼**과 같은 원리다.
- 모든 환경변수가 비밀은 아니다 — **publishable(anon) 키는 브라우저에 노출돼도 안전한 공개 키**다.

**연동은 두 축이다.**

| 구분 | 무엇을 위해 | 담기는 값 |
|---|---|---|
| **MCP**(`.mcp.json`) | 클로드코드가 DB를 **관리**(테이블 생성·SQL) | **Access Token** |
| **`.env`** | 앱이 DB에 **접속** | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` |

- ⚠️ **anon 키는 공개 OK, Access Token은 절대 노출 금지**(관리자 권한). `.env`는 `.gitignore`로 제외한다.

**📝 과제** — 게임에 Supabase 연동: MCP로 `score` 테이블 생성 → 클리어 점수 저장/랭킹 표시 → **다른 기기에서도 데이터가 유지되는지** 확인. 핵심 성과는 **로컬스토리지 → Supabase**로 저장 위치를 옮겨 진짜 "웹 서비스"를 만드는 것이다.

> **한 문장 요약(Day 4)** — *서버와 데이터의 원리를 이해하고, Supabase로 백엔드를 세우며, MCP로 AI를 외부에 안전하게 연결하라.*

# 제5부 · 세상에 내보낸다 — Git·Github·Vercel (Day 5)

### 1. 배포의 세 가지 준비물, 그리고 선택지

주소 한 줄(`http://naver.com:80` = 호스트 + 포트)을 뜯어보면 배포가 무엇을 갖추는 일인지 나온다.

1. **접속할 도메인 주소** 만들기/구입하기 (가비아 · 고대디)
2. **서버 프로그램을 24시간** 실행시켜 놓기
3. **외부에서 접속 가능하도록 네트워크 설정**하기

| | 내 컴퓨터 | 클라우드 서비스 | **배포 플랫폼** |
|---|---|---|---|
| 24시간 켜놓기 | 직접 ❌ | 자동 ✅ | 자동 ✅ |
| 네트워크 설정 | 직접 ❌ | 직접 ❌ | **자동 ✅** |
| 대표 | 데스크톱·노트북 | AWS · GCP · Azure | **Vercel**·Netlify / Render·Railway |

- **오른쪽으로 갈수록 편리**하고, 배포 플랫폼은 **트래픽이 늘수록 요금이 오른다.**

**백엔드는 갈림길이다.**

| | Render / Railway | **Supabase** |
|---|---|---|
| 백엔드 | 내가 직접 만듦 | **이미 만들어져 있음** |
| 배포 | 내가 직접 | **이미 배포되어 있음** |
| 내가 하는 일 | **배포하기** | **갖다쓰기** |

- 최종 구성 — 홈페이지: **Vercel만** / 웹 서비스: **Vercel + Supabase**.

### 2. 자동 배포 파이프라인 (CI/CD)

```
[내 컴퓨터] ─빌드→커밋→푸쉬─▶ [Github] ─업로드 감지·자동 전송─▶ [Vercel]
                                 └──── 연결 설정 (최초 1회) ────┘
```

- **빌드** = **문법검사 · 압축 · 최적화.** 과거엔 `npm run build`, 지금은 **"빌드 해줘"**.
- **에러와 버그는 다르다** — **에러**는 실행이 **안 되는** 것(문법 오류), **버그**는 **실행은 되는데 결과가 틀린** 것. 빌드의 문법 검사는 주로 에러를 잡고, 버그는 테스트해야 나온다.
- 코드 저장소는 GitHub(대안: Bitbucket, GitLab).

**단, `.env`는 이 흐름을 타면 안 된다.**

```
[코드]  ──▶ GitHub ──▶ Vercel          (정상 파이프라인)
[.env] ──✗ GitHub    직접 입력 ▶ Vercel  (저장소를 건너뛰고 Vercel에 "환경변수 등록")
```

> **⚠️ 티빙 개인정보 유출 사태 (약 1,300만 명)**
> 기사 제목이 방향을 가리킨다 — **"DB 유출보다 깃허브에 주목할 이유."**
> 진짜 원인은 단순 DB 접근이 아니라 **GitHub에 노출된 자격증명 + AWS 액세스 키 관리 부실**이었고, 개발 편의를 위해 소스코드에 자격증명을 적는 **하드코딩**이 문제로 지목됐다. AWS 액세스가 뚫리면 서버·저장소·DB 권한까지 넘어가 **클라우드 인프라 전반의 통제권**이 노출된다.
> 대응도 늦었다 — 사고 인지부터 **KISA 신고까지 23시간 59분**, 이용자 공지는 **이틀 뒤**. DB 서버 CPU가 100%까지 치솟는 이상 징후를 인지하는 데만 **약 21시간**이 걸렸다. **ISMS 인증**을 보유했는데도 관리자 접속 키가 프로그램에 노출됐다는 비판이 뒤따랐다.
>
> | 잘못한 것 | 올바른 방법 |
> |---|---|
> | 소스코드에 자격증명 **하드코딩** | **`.env`로 분리** |
> | 키를 **GitHub에 노출** | **`.gitignore`로 저장소에서 제외** |
> | 핵심 키 **관리 부실** | **주기적 교체 · 권한 최소화** |

### 3. Git과 Github

| | **Git** | **Github** |
|---|---|---|
| 정체 | 내 컴퓨터에 **설치**하는 도구 | 홈페이지에 **가입**하는 저장소 |
| 역할 | 업로드/다운로드(버전 관리) | 파일·폴더 보관(레포지토리) |
| 위치 | 로컬 | 원격(인터넷) |

- Git 설치는 컴퓨터에 **1회**, **프로젝트마다 `.git` 초기화**(`git init` / "깃 초기화 해줘").
- **커밋 → 푸쉬** 순서다. **커밋**은 변경사항을 `.git`에 저장(아직 내 컴퓨터 안), **푸쉬**는 그것을 Github에 업로드.
- **리모트** = 내 `.git`이 바라볼 Github 레포 주소. 등록해야 **푸쉬 목적지**가 정해진다.
- 레포는 **Public/Private**를 고른다. Public이면 코드가 전부 공개되므로 **`.env`는 절대 올리지 않는다.**

### 4. 말로 배포하기 — 실전

```
깃 초기화 해줘.
그리고, 레포지토리 주소는 https://github.com/.../mysokoban.git 이거야. 주소도 셋팅해줘.
환경변수 분리 잘 되어있는지 확인해주고, 환경변수는 .env로 만들어줘.
환경변수처럼 github에 저장되면 안되는 파일들은 .gitignore에 셋팅해줘.
```

| 요청 문장 | 실제 동작 |
|---|---|
| "깃 초기화 해줘" | `git init` → `.git` 생성 |
| "레포지토리 주소 … 셋팅해줘" | **리모트 주소 등록**(`git remote add`) |
| "환경변수는 .env로" | 보안 정보를 **`.env`로 분리** |
| ".gitignore에 셋팅해줘" | `.env` 등을 **업로드에서 제외** |

- 이후 **"빌드 → 커밋 → 푸쉬"** 라고 말하면 Github → Vercel **자동 배포**, **무료 도메인**(`mysokoban-three.vercel.app`)까지 부여된다.
- **검증은 레포 파일 목록으로 한다** — `.env`는 없고 **`.env.example`만** 있으면 `.gitignore`가 제대로 작동한 것이다.

**🧩 퀴즈** — ① 배포 전 문법검사·압축·최적화를 하는 과정은? → **빌드** ② Github에 올리기 위해 변경사항을 `.git`에 저장하는 것은? → **커밋**(푸쉬와 구분: 푸쉬는 실제 업로드)

> **한 문장 요약(Day 5)** — *빌드해서 저장소에 올리면 Vercel이 자동으로 배포한다. 비밀(`.env`)만은 저장소 밖에 두어라.*
