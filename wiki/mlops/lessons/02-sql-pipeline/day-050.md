## ③ 개념 설명

### 5분 발표 구성

| 시간 | 내용 | 슬라이드 |
|---|---|---|
| **0:00–0:30** | **문제** — 무슨 데이터, 무엇을 알고 싶었나 | 1장 |
| 0:30–1:00 | 아키텍처 — 어떻게 만들었나 (그림 1장) | 1장 |
| **1:00–3:00** | **시연** — 명령 한 줄 → 적재 → 상태 확인 | (터미널) |
| 3:00–4:00 | **결과** — 알아낸 것 3가지 (차트) | 2~3장 |
| 4:00–4:30 | 어려웠던 점 / 한계 | 1장 |
| 4:30–5:00 | 배운 것 / 다음 단계 | 1장 |

**시연에 2분을 쓰세요.** 이 프로젝트의 핵심은 **동작하는 파이프라인**입니다.
슬라이드로 설명하는 것보다 **실제로 도는 것**이 열 배 강합니다.

### 시연 대본

**말하면서 칠 명령을 미리 정합니다.** 즉흥으로 하면 오타로 30초를 씁니다.

```powershell
# ① 지금 상태 (5초)
datapipe status --limit 3

# ② 실행 — 이게 평가 기준 1번입니다 (30초)
datapipe etl --source air_seoul

# ③ 한 번 더 — 멱등성 (30초)
datapipe etl --source air_seoul
docker exec mlops-pg psql -U postgres -d mp1 -c "SELECT COUNT(*) FROM measurement"
#   "두 번 실행했는데 행 수가 같습니다"  ← 이 문장을 꼭 말하세요

# ④ 불량 데이터 처리 (30초)
docker exec mlops-pg psql -U postgres -d mp1 -c `
  "SELECT reason, COUNT(*) FROM measurement_rejected GROUP BY 1 ORDER BY 2 DESC LIMIT 3"

# ⑤ 품질 점검 (20세초)
datapipe check --days 7
```

**시연 실패 대비**

| 위험 | 대비 |
|---|---|
| 네트워크가 느림/끊김 | `data/raw/` 원본으로 도는 **오프라인 모드** 준비 |
| API 호출 한도 초과 | 미리 `--dry-run` 으로 확인 |
| Docker가 안 떠 있음 | **발표 10분 전에 `docker start` 하고 한 번 실행** |
| 명령 오타 | 명령을 메모장에 미리 적어 두고 복사 |
| 다 실패 | **터미널 스크린샷/GIF 백업** |

> **"백업 스크린샷이 있어도 라이브를 먼저 시도하세요."** 실제로 도는 것을 보여주는 것이 목적입니다.
> 다만 **30초 안에 안 되면 미련 없이 백업으로** 넘어가세요. 시간이 더 아깝습니다.

### 예상 질문 10개 ★

**이 질문들은 거의 반드시 나옵니다.** 답을 미리 준비하세요.

| # | 질문 | 답의 뼈대 |
|---|---|---|
| 1 | **두 번 실행하면 어떻게 되나요?** | 멱등 키 `(A, B)` + `ON CONFLICT DO UPDATE`. 3회 실행 테스트로 고정 |
| 2 | **왜 이 데이터를 골랐나요?** | 선정 기준 6가지 (시계열·관계·규모·개인정보 없음) |
| 3 | **결측을 왜 0으로 안 채웠나요?** | "측정 안 됨"과 "농도 0"은 다른 정보. 평균이 왜곡됨 |
| 4 | **범위 상한을 왜 2000으로?** | 실측 분포(`p99` 148, `max` 341) + 도메인 기준. 좁게 잡으면 황사 데이터를 버림 |
| 5 | **데이터가 잘못됐을 때 어떻게 아나요?** | 3중 방어 (파이썬 검증 · DB `CHECK` · SQL 점검) + `datapipe check` |
| 6 | **실패하면 어떻게 복구하나요?** | 멱등하므로 재실행. `runbook.md` 에 증상별 절차 |
| 7 | **가장 어려웠던 점은?** | 구체적으로. "시간대 때문에 9시간이 밀렸던 것" 같은 실제 경험 |
| 8 | **SQL 인젝션은 어떻게 막았나요?** | 파라미터 바인딩 + 식별자 허용 목록 + **테스트로 고정** |
| 9 | **이 분석의 한계는?** | 기간·표본·미측정 변수. **한계를 아는 것이 신뢰의 근거** |
| 10 | **다음에 무엇을 하고 싶나요?** | MP2 예고. 범위를 알고 관리한다는 인상 |

**7번이 가장 중요합니다.** "특별히 어려운 건 없었습니다"는 최악의 답입니다.
**구체적인 실패와 해결**을 하나 준비하세요.

```
❌ "데이터 처리가 좀 어려웠습니다"
✅ "시간대를 안 붙여서 9시간이 밀렸습니다. '어제 데이터'를 뽑았는데
   전날 오후 3시부터가 나오길래 이상해서 추적했더니, strptime 결과에
   tzinfo가 없어 서버 시간대(UTC)로 해석되고 있었습니다.
   지금은 변환 함수에 KST를 명시하고, 테스트로 고정해 뒀습니다."
```

**이 답 하나가 "코딩한 사람"과 "디버깅한 사람"을 가릅니다.**

### 회고 — KPT

| 항목 | 질문 |
|---|---|
| **Keep** | 계속할 것. 잘 작동한 습관·도구 |
| **Problem** | 문제였던 것. 시간을 낭비한 지점 |
| **Try** | 다음에 시도할 것. **구체적인 행동으로** |

**"Try"는 반드시 행동으로 적으세요.**

```
❌ "시간 관리를 잘하자"
✅ "MP2에서는 첫날 오후 3시까지 데이터 선정을 끝내고,
    안 되면 준비한 2순위 후보로 넘어간다"
```

### Step 1. 발표 자료 정리 (1~2교시)

**슬라이드 7장**을 넘기지 마세요.

**1장 — 제목과 한 줄**

```
서울시 대기질 수집·적재·분석 파이프라인
공공데이터 API → 검증 → PostgreSQL → 분석

홍길동 | 2026-08-16 | github.com/사용자명/mlops-mp1
```

**2장 — 문제**

```
질문
  Q1  일별 PM10 평균은 어떻게 변하는가?
  Q2  대기질이 나쁜 측정소는 어디인가?
  Q3  유독 다르게 움직이는 측정소가 있는가?

제약
  · 데이터는 매시간 새로 생긴다  →  자동 수집이 필요
  · API 응답에 결측·오류가 섞인다 →  검증이 필요
  · 배치는 반드시 실패한다        →  재실행이 안전해야 한다
```

**"제약" 세 줄이 이 프로젝트가 왜 파이프라인인지를 설명합니다.**

**3장 — 아키텍처** (그림 하나. 글자 최소)

```
[API] ──Extract──▶ [원본 JSON]
                        │ Transform  검증 9종 → 불량은 격리
                        ▼
                  [적재용 행] ──Load──▶ [PostgreSQL]
                                            │
                                     분석 SQL 10문 · 차트 3종
```

**4장 — 시연** (슬라이드 없음. 터미널로 전환)

**5~6장 — 결과** (차트 + 한 줄 결론)

```
[trend.png]

7월 28일 하루가 평균의 2.4배 (84.6 ㎍/㎥)
그날 40곳 중 37곳(92.5%)이 '나쁨' 이상 → 광역 현상
```

**차트 한 장에 문장 하나.** 차트 두 장을 한 슬라이드에 넣지 마세요.

**7장 — 배운 것 / 한계 / 다음**

```
배운 것
  · 멱등성이 없으면 재실행이 불가능하다 (첫날 중복 적재로 직접 겪음)
  · 검증 규칙은 상상이 아니라 데이터를 보고 만든다

한계
  · 31일치 → 계절성 판단 불가
  · 기상 데이터 없음 → 원인 분석 한계

다음
  · MP2: 전일-익일 상관 0.61 → 시계열 예측 시도
```

### Step 4. 회고 작성 (7교시)

`docs/retrospective.md`:

```markdown
# MP1 회고 (2026-08-16)

## 숫자로 본 결과
| 항목 | 값 |
|---|---|
| 기간 | 5일 (Day 046–050) |
| 커밋 | 34개 |
| 테스트 | 25개 (전부 통과) |
| 적재 행 수 | 29,074 |
| 분석 쿼리 | 12문 (윈도우 함수 5개) |
| 재현 소요 시간 | 6분 20초 (clone → 첫 적재) |

## Keep — 계속할 것
- **첫날에 데이터를 실제로 받아 본 것.** 문서와 실제 응답 형식이 달라서
  후보를 바꿨는데, 이걸 3일차에 발견했다면 프로젝트가 무너졌다.
- **원본 JSON 저장.** 파싱을 세 번 고쳤는데 API를 다시 호출하지 않아도 됐다.
- **커밋 메시지에 행 수 기록.** 언제 데이터가 늘었는지 되짚기 쉬웠다.

## Problem — 문제였던 것
- **시간대를 안 붙여 9시간이 밀렸다.** 발견까지 2시간 소모.
  `strptime` 결과에 `tzinfo` 가 없다는 걸 몰랐다.
- **검증 규칙 상한을 100으로 잡았다가** 7월 28일 황사 데이터를 전부 격리했다.
  데이터를 보기 전에 규칙을 만든 탓이다.
- **차트를 노트북에서 만들다가** 다시 그릴 때 순서가 꼬였다. 3일차에 스크립트로 옮겼다.

## Try — 다음에 할 것
- MP2에서는 **첫날 오후 3시까지 데이터 선정을 끝내고**, 안 되면 2순위로 넘어간다.
- **날짜·시각을 다루는 함수는 만들자마자 테스트를 쓴다.** 시간대는 눈으로 안 보인다.
- **검증 규칙 전에 프로파일링부터.** `MIN`·`MAX`·`p99`·결측률을 먼저 본다.
- 시각화는 처음부터 **스크립트로**. 노트북은 탐색용으로만.

## 다음 단원과의 연결
이 파이프라인이 계속 데이터를 쌓고 있으므로, MP2의 학습 데이터를
**SQL로 바로 꺼내 쓸 수 있다.** 전일 PM10과 익일 PM10의 상관이 0.61이므로
시계열 회귀를 시도해 볼 만하다.
```

## ⑤ 자주 하는 실수

### 배경 설명에 3분을 씀

**증상** — 미세먼지가 무엇인지, 공공데이터포털이 무엇인지 설명하다 시연을 못 합니다.
**해결** — **문제는 30초.** 청중은 이미 대기질이 뭔지 압니다. **여러분이 만든 것**을 보고 싶어 합니다.

### 시연 없이 슬라이드만

**증상** — 파이프라인 프로젝트인데 코드가 도는 걸 한 번도 안 보여줍니다.
**해결** — **시연 2분은 협상 불가**입니다. 이 프로젝트의 핵심 산출물입니다.

### 시연 준비를 안 함

**증상** — Docker가 안 떠 있어 1분을 씁니다. 명령 오타로 30초를 더 씁니다.
**해결** — **발표 10분 전 `docker start` + 예행 1회.** 명령은 메모장에 미리.

### 차트를 설명 없이 넘김

**증상** — "이건 시계열 그래프입니다" 하고 다음 장으로 갑니다.
**해결** — **차트마다 결론 한 문장.** "7월 28일에 평균의 2.4배로 급등했습니다."
그림을 띄우고 **3초는 침묵**하세요. 청중이 볼 시간을 줘야 합니다.

### "어려웠던 점이 없었습니다"

**증상** — 아무 문제 없이 됐다고 말합니다.
**해결** — **거짓이거나, 깊이 안 들어간 것**입니다. 둘 다 나쁩니다.
구체적인 실패 하나를 준비하세요. **실패-해결 이야기가 가장 기억에 남습니다.**

### 질문에 추측으로 답함

**증상** — "아마 될 것 같은데요"
**해결** — **"확인해 보겠습니다"** 또는 **"그건 안 해 봤습니다"** 가 정직하고 낫습니다.
그 자리에서 `pytest` 를 돌려 보여 줄 수 있으면 최고입니다.

### 회고를 형식적으로 씀

**증상** — "열심히 했다. 다음엔 더 잘하겠다."
**해결** — **Try 는 행동으로.** "다음엔 시간 관리를 잘하겠다"가 아니라
**"첫날 오후 3시까지 데이터를 확정하고, 안 되면 2순위로 넘어간다"** 입니다.

## ⑥ 확인 문제

**1.** 발표 중 "두 번 실행하면 데이터가 두 배가 되지 않나요?"라는 질문을 받았습니다. 30초 안에 어떻게 답하고, 어떻게 증명하겠습니까?

<details>
<summary>답 보기</summary>

**말로 20초 + 증명 10초.**

**말**

> "안 됩니다. `(station_id, measured_at)` 에 `UNIQUE` 제약을 걸고
> `ON CONFLICT DO UPDATE` 로 적재하기 때문입니다.
> 같은 측정소의 같은 시각 데이터는 세상에 하나뿐이니, 그것을 멱등 키로 잡았습니다.
> 이미 있으면 값만 갱신되고 행은 안 늘어납니다."

**증명 — 그 자리에서 보여줍니다**

```powershell
$ docker exec mlops-pg psql -U postgres -d mp1 -c "SELECT COUNT(*) FROM measurement"
 29074
$ datapipe etl --source air_seoul
[73] 적재 274행 · 제외 6행
$ docker exec mlops-pg psql -U postgres -d mp1 -c "SELECT COUNT(*) FROM measurement"
 29074
```

**"274행을 적재했다고 나오는데 총 행 수는 그대로입니다. 갱신된 것입니다."**

**또는 테스트로**

```powershell
$ pytest tests/test_pipeline.py::test_세번_실행해도_행수가_같다 -v
PASSED
```

**후속 질문 대비**

| 질문 | 답 |
|---|---|
| "값이 바뀌었으면요?" | `DO UPDATE` 라 최신 값으로 갱신됩니다. `ingested_at` 으로 언제 갱신됐는지 남습니다 |
| "원본에서 행이 사라지면요?" | upsert는 삭제를 반영 못 합니다. 그건 알려진 한계이고, 필요하면 `DELETE 구간 + INSERT` 방식으로 바꿉니다 |
| "제약이 없었으면요?" | 두 배가 됩니다. 에러도 안 나고요. 그래서 스키마 설계 때 멱등 키를 가장 먼저 정했습니다 |

**이 질문은 반드시 나옵니다.** 평가 기준 1번이기 때문입니다. **답과 증명을 세트로 준비하세요.**
</details>

**2.** "가장 어려웠던 점은?"에 대한 좋은 답과 나쁜 답의 차이는 무엇인가요? 여러분의 답을 준비해 보세요.

<details>
<summary>답 보기</summary>

**나쁜 답 3종**

| 답 | 왜 나쁜가 |
|---|---|
| "특별히 어렵진 않았습니다" | 깊이 안 들어갔거나 거짓 |
| "데이터 처리가 어려웠습니다" | 구체성이 없어 아무 정보도 없음 |
| "환경 설정이 오래 걸렸습니다" | 프로젝트의 본질과 무관 |

**좋은 답의 구조**

```
① 증상        무슨 일이 있었나 (관찰 가능한 사실)
② 원인 추적    어떻게 찾았나  ← 여기가 실력을 보여줍니다
③ 해결        무엇을 고쳤나
④ 재발 방지    다시 안 생기게 무엇을 했나  ← 여기가 엔지니어링입니다
```

**예시**

> **①** "'어제 데이터'를 뽑는 쿼리를 만들었는데, 결과에 전날 오후 3시부터가 섞여 나왔습니다.
> **②** 처음엔 쿼리 조건을 의심했는데 맞더군요. DB에 들어간 값을 직접 보니
> `measured_at` 이 API가 준 시각보다 9시간 앞서 있었습니다.
> `strptime` 으로 만든 datetime에 `tzinfo` 가 없어서, `timestamptz` 열에 들어갈 때
> 서버 시간대(UTC)로 해석된 것이었습니다.
> **③** 변환 함수에서 `.replace(tzinfo=KST)` 를 붙여 고쳤고, 기존 데이터는 백필로 다시 적재했습니다.
> **④** `test_시각에_KST가_붙는다` 테스트를 추가했습니다. 시간대는 눈으로 안 보여서
> 테스트가 없으면 또 같은 실수를 할 것 같았습니다."

**이 답이 보여주는 것**

| 요소 | 전달되는 것 |
|---|---|
| 이상을 알아챘다 | 결과를 검증하는 습관 |
| 원인을 추적했다 | 디버깅 능력 |
| 근본 원인을 찾았다 | 증상만 덮지 않음 |
| 백필로 과거를 고쳤다 | 파이프라인 이해 |
| 테스트를 추가했다 | **재발 방지 — 가장 중요** |

**여러분의 답을 지금 적어 보세요.** 5일 동안 분명히 하나는 있었습니다.

```
① 증상:
② 원인 추적:
③ 해결:
④ 재발 방지:
```

**④를 못 채우겠다면 지금 채우세요.** 테스트를 하나 추가하거나 문서에 한 줄 남기면 됩니다.
그러면 답도 완성되고 프로젝트도 좋아집니다.
</details>

**3.** 이 파이프라인을 대단원 03(머신러닝)에서 어떻게 활용할 수 있을까요? 지금 미리 해 둘 것이 있나요?

<details>
<summary>답 보기</summary>

**MP2는 "학습 데이터를 DB에서 조회"하는 것으로 시작합니다.** 즉 **MP1의 DB가 MP2의 입력**입니다.

| MP1의 산출물 | MP2에서의 역할 |
|---|---|
| `measurement` 테이블 | **학습 데이터의 원천** |
| 검증·격리 | 학습 데이터 품질 보장 |
| `ingest_run` · `ingested_at` | **데이터 버전 추적** (어느 시점 데이터로 학습했나) |
| 멱등 파이프라인 | 데이터가 계속 쌓임 → 재학습 가능 |
| 분석 SQL | 특징(feature) 후보 발굴 |

**지금 미리 해 두면 좋은 것 3가지**

**① 파이프라인을 계속 돌려 두기**

```powershell
# 작업 스케줄러 / cron 에 등록 (Day 045)
5 * * * * cd /opt/mlops-mp1 && datapipe etl --source air_seoul
```

**데이터가 많을수록 모델이 좋아집니다.** MP2 시작(W15)까지 5주가 남았으니
지금부터 돌려 두면 **약 4개월치 데이터**가 쌓입니다. 31일치와는 비교가 안 됩니다.

**② 특징 후보를 SQL로 미리 만들어 두기**

시계열 예측에 쓸 재료는 이미 [Day 037](day-037.md)에서 배운 것들입니다.

```sql
-- 학습용 특징 뷰 (MP2에서 그대로 씁니다)
CREATE VIEW v_features AS
SELECT station_id, measured_at,
       pm10                                                     AS target,
       LAG(pm10, 1)  OVER w                                      AS pm10_lag1,
       LAG(pm10, 24) OVER w                                      AS pm10_lag24,
       AVG(pm10) OVER (PARTITION BY station_id ORDER BY measured_at
                       ROWS BETWEEN 23 PRECEDING AND CURRENT ROW) AS pm10_ma24,
       EXTRACT(HOUR FROM measured_at)::int                        AS hour,
       EXTRACT(DOW  FROM measured_at)::int                        AS dow
FROM measurement
WINDOW w AS (PARTITION BY station_id ORDER BY measured_at);
```

**`LAG` · 이동평균 · 시간 특징 — 시계열 모델의 표준 입력**입니다.
[Day 037](day-037.md)에서 배운 윈도우 함수가 **그대로 머신러닝의 재료**가 됩니다.

**③ 데이터 누수를 만들지 않을 구조 확인**

대단원 03에서 가장 무서운 실수가 **데이터 누수(leakage)** 입니다.

```
❌ 미래 정보가 특징에 들어감
   "그날의 일평균"으로 "그날 오후 값"을 예측  →  이미 답을 아는 셈

✅ 시점 t 의 예측에는 t 이전 정보만
   LAG · 이동평균은 안전 (과거만 참조)
   LEAD 는 위험 (미래 참조)
```

**`ingested_at` 을 남겨 둔 것이 여기서 값을 합니다.**
"이 값을 그 시점에 실제로 알 수 있었는가"를 확인할 수 있습니다.
정정된 값이 소급 반영된 데이터로 학습하면 **평가가 실제보다 좋게 나옵니다.**

> **대단원 02의 진짜 목적지가 여기입니다.**
> 모델을 만드는 것은 W11부터 배우지만, **모델이 먹을 데이터를 만드는 것**은 이미 끝냈습니다.
> 그리고 실무에서 모델 성능의 대부분은 **데이터 품질**이 결정합니다.
</details>
