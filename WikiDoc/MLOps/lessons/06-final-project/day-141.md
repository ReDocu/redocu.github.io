## ② 왜 필요한가

최종 프로젝트가 무너지는 팀은 W31에 무너지지 않습니다. **오늘 무너집니다** — 다만 발견이
3주 뒤일 뿐입니다. 전형적인 시나리오는 늘 같습니다:

```
Day 141  "이 데이터 공공데이터포털에 있대" (링크만 확인)
Day 146  수집 코드를 짜 보니 — 신청 후 승인 5일 · CSV 수동 다운로드만 · 올해 것은 없음
Day 148  주제 변경 논의 — 그러나 설계·백로그·뼈대 코드가 전부 옛 주제의 것
Day 155  "시간이 없어서 여기까지 했습니다"
```

이 시나리오의 예방책은 단 하나, **첫날에 데이터를 실제로 받아보는 것**입니다. 문서를 읽는
것도, 블로그에서 "누가 해봤다"를 확인하는 것도 아닙니다 — 여러분의 인증키로, 여러분의
코드가, 오늘 날짜 기준의 응답을 받는 것. 이 단원에 "정답지가 없다"는 말의 첫 번째 의미가
이것입니다: 데이터가 진짜 있는지조차 이제 아무도 대신 확인해 주지 않습니다.

팀 구성도 마찬가지입니다. 4주 팀 개발의 갈등은 대부분 기술이 아니라 **합의되지 않은 기대**
에서 옵니다 — "당연히 리뷰하고 머지하는 줄", "당연히 스탠드업 하는 줄". W22에서 팀 규칙을
문서로 만들었던 이유([Day 110](../05-infra-mlops/day-110.md))가 오늘 실전이 됩니다.

## ③ 개념 설명

### 좋은 주제의 4 기준

| 기준 | 검사 질문 | 통과 증거 |
|---|---|---|
| 1. 데이터 실재 | 오늘 코드로 받아지는가? 양·기간·갱신 주기는? | **오늘 실행한 수집 코드 + 응답** |
| 2. 전 스택 관통 | 수집→DB→모델→API→운영 자동화가 전부 필요한 주제인가? | 필수 6종([커리큘럼](../../curriculum/06-final-project.md))과 1:1 매핑 |
| 3. 범위 조절 가능 | 축소판(1주 만에 관통)과 확장판이 둘 다 그려지는가? | "최소 범위" 한 문장 |
| 4. 이야기 가능 | 누가 왜 쓰는지 한 문장으로 말해지는가? | 사용자 한 줄 시나리오 |

주의할 것은 기준에 **"멋짐"이 없다**는 점입니다. 심사 배점표(사이클 30 · 재현성 20 ·
모델링 15 · 협업 15 · 문서·발표 20)의 어디에도 주제의 참신함 항목은 없습니다. 평범한
주제의 완주가 참신한 주제의 미완성을 항상 이깁니다.

### 팀 빌딩 — 감정이 아니라 자산과 규칙으로

첫 회의의 순서가 중요합니다. "뭐 만들까?"로 시작하면 아이디어 대결이 되고, 목소리 큰
사람의 주제가 남습니다. 순서를 바꾸세요:

1. **기술 자산 목록** — 각자 [Day 140](../05-infra-mlops/day-140.md) 회고의 Keep/Try를
   공유합니다. "나는 MP4에서 CD까지 완주했고 롤백 스크립트가 있다" / "나는 Airflow 과제를
   확장해 봤다" — 팀이 가진 부품의 재고 조사입니다.
2. **협업 규칙 초안** — W22의 team-playbook([Day 110](../05-infra-mlops/day-110.md))을
   바탕으로: 브랜치 전략 · 리뷰 규칙(승인 몇 명, 몇 시간 내) · 스탠드업 시각 · **결정
   규칙**(합의 안 되면 어떻게 정하나 — 예: 15분 논의 후 다수결, 동수면 담당자 결정).
3. 그다음에야 주제 후보를 4 기준으로 심사합니다.

### 주제 확정서 — 한 장이면 된다

| 항목 | 내용 |
|---|---|
| 서비스 한 문장 | 누가 · 언제 · 무엇을 얻는가 |
| 데이터 | 출처 · 접근 방법 · 양 · 기간 · 갱신 주기 · **오늘 확인한 증거** |
| 모델 문제 정의 | 입력 → 출력 · 문제 유형(회귀/분류) · 평가 지표 후보 |
| 최소 범위 | 이것만 되면 관통이다 — 한 문장 |
| 알려진 위험 | 오늘 발견한 불안 요소 전부 (숨기지 않기) |

## ④ 단계별 실습

### Step 1. 팀 빌딩 — 자산 목록과 규칙 초안 (1~2교시)

③의 순서대로 진행합니다. 예시 팀 **한산**(서연·민준·지우·하람 — 이 단원 내내 함께 갈
가상의 팀입니다)의 결과물 요약:

```
[팀 한산 · 규칙 초안 v1]
- 역할(주 담당): 서연 데이터·파이프라인 / 민준 모델·실험 / 지우 서빙·API / 하람 인프라·CI/CD
- 단, 전원이 코드를 쓴다. PR 교차 리뷰 짝: 서연↔지우, 민준↔하람 (서로의 영역을 본다)
- 스탠드업 매일 09:30, 15분, 진행자 일 로테이션
- PR: 승인 1 + CI 통과 필수, 24시간 내 리뷰, 500줄 초과 PR 금지
- 결정 규칙: 15분 논의 → 다수결 → 동수면 해당 영역 주 담당이 결정
```

리뷰 짝을 **영역 교차**로 묶은 것에 주목하세요 — 데이터 담당의 코드를 서빙 담당이 읽어야
발표 때 전원이 전 구간 질문에 답할 수 있습니다 ([Day 136](../05-infra-mlops/day-136.md)
⑤에서 페어 단위로 겪은 교훈의 팀 버전입니다).

### Step 2. 데이터 실재 확인 — 오늘, 코드로 (3~6교시)

후보를 2~3개로 좁히고, **후보마다 담당을 정해 실제로 받아봅니다.** 한산 팀의 기록:

**후보 A — 지하철 혼잡 예측** (서연 담당). 서울열린데이터광장에서 인증키를 발급받고
(즉시 발급·무료) 어제 날짜의 일별 승하차를 호출:

```
$ curl -s "http://openapi.seoul.go.kr:8088/${SEOUL_KEY}/json/CardSubwayStatsNew/1/5/20260809" \
    | python -m json.tool
{
    "RESULT": {
        "CODE": "INFO-200",
        "MESSAGE": "해당하는 데이터가 없습니다."
    }
}
```

**어제 데이터가 없습니다.** 여기서 포기하면 후보 A는 탈락입니다 — 하지만 서연은 API
문서를 다시 읽고 날짜를 며칠 물려 봅니다:

```
$ curl -s "http://openapi.seoul.go.kr:8088/${SEOUL_KEY}/json/CardSubwayStatsNew/1/2/20260806" \
    | python -m json.tool
{
    "CardSubwayStatsNew": {
        "list_total_count": 611,
        "RESULT": { "CODE": "INFO-000", "MESSAGE": "정상 처리되었습니다" },
        "row": [
            { "USE_YMD": "20260806", "SBWY_ROUT_LN_NM": "1호선", "SBWY_STNS_NM": "서울역",
              "GTON_TNOPE": 42183.0, "GTOFF_TNOPE": 39872.0, "REG_YMD": "20260810" },
            { "USE_YMD": "20260806", "SBWY_ROUT_LN_NM": "1호선", "SBWY_STNS_NM": "시청",
              "GTON_TNOPE": 21507.0, "GTOFF_TNOPE": 22940.0, "REG_YMD": "20260810" }
        ]
    }
}
```

발견 두 가지가 실재 확인서에 들어갑니다: ① 데이터는 **3~4일 지연 게시**된다(REG_YMD 참조,
이하 "D-4") — 실시간 서비스는 불가, **예보 서비스라면 문제없음**. ② 하루 응답이 전 호선
611행 — 일 단위 수집이 가볍다. 2024년 이후 백필 가능도 과거 날짜 몇 개로 확인했습니다.

**후보 B — 중고거래 시세 예측** (지우 담당): 공개 API 없음 — 크롤링 대상 사이트의
robots.txt와 약관 확인 결과 수집 허용 범위가 불명확. "4주 내내 수집 리스크를 안고 감"
으로 판정. **후보 C — 에너지 수요 예측** (하람 담당): 시간대별 전력 데이터가 월 단위
공개라 "시간 단위 예측" 시나리오와 갱신 주기가 안 맞음을 확인.

### Step 3. 주제 확정과 확정서 작성 (7교시)

한산 팀의 심사 결과와 확정서 핵심:

| 기준 | A 지하철 | B 중고시세 | C 에너지 |
|---|---|---|---|
| 데이터 실재 | ✅ 오늘 수신 (D-4 지연 명기) | 🔶 수집 불확실 | 🔶 주기 불일치 |
| 전 스택 관통 | ✅ 수집~재학습 전부 필요 | ✅ | ✅ |
| 범위 조절 | ✅ 노선·기간으로 축소 가능 | ✅ 품목 축소 | 🔶 |
| 이야기 | ✅ "내일 아침 몇 시에 탈까" | ✅ | ✅ |

```
[주제 확정서 — 팀 한산]
서비스 한 문장: 출근하는 서울 시민이 내일 지하철 2호선의 역·시간대별 혼잡을 미리 확인한다.
데이터: 서울열린데이터광장 일별 역별 승하차(D-4 게시) + 월별 시간대별 분포. 오늘 수신 확인.
모델: (역, 날짜) → 일 승차 인원 회귀 + 시간대 분포 결합 → 시간대 혼잡 등급.
최소 범위: 2호선, 내일 예보, 등급 3단계 — 이것만 되면 관통.
알려진 위험: D-4 지연(예보 프레임으로 흡수) · 인증키 일 1,000회 제한(백필 시 계획 필요) ·
             공휴일 패턴(모델 난도) — 전부 Day 142~143에서 설계로 대응.
```

### Step 4. 팀 저장소 개설과 첫 커밋 (8교시)

- GitHub Organization(또는 팀 저장소) 생성 → 전원 초대: 한산 팀은 `team-hansan/hansan`
- 브랜치 보호 규칙을 **오늘** 겁니다 (리뷰 1 + 상태 검사 — [Day 127](../05-infra-mlops/day-127.md)

**오늘 퇴근 체크** — □ 기술 자산 목록 □ 규칙 초안(결정 규칙 포함) □ 후보별 실재 확인

## ⑤ 자주 하는 실수

### 데이터 확인을 "문서 읽기"로 대체

**증상** — "API 문서에 있어요. 키도 신청했어요" — 그리고 Day 146에 처음 호출해 보고
지연·제한·형식 문제를 발견.
**원인** — 확인의 정의가 다름: 문서의 존재 ≠ 데이터의 실재.
**해결** — 오늘의 규칙: **호출 코드와 응답 원문이 없으면 그 후보는 심사 불가.** 한산 팀이
INFO-200을 첫날 만난 것이 행운이었음을 기억하세요 — 같은 발견이 Day 146이었다면 설계
전체가 재작업입니다.

### 멋짐으로 주제 선정

**증상** — "LLM 챗봇 붙이면 멋있을 것 같아요"가 결정타가 됨 — 배점표 어디에도 없는
기준으로 4주를 베팅.
**원인** — 심사 기준(배점표)을 읽지 않고 회의 시작.
**해결** — 4 기준 표를 먼저 그리고 후보를 채점하세요. 참신함이 진짜 무기가 되는 곳은
발표의 "이야기"(문제 정의의 설득력)이지 기술 스택의 화려함이 아닙니다.

### 규칙 없이 출발 — "우린 잘 맞으니까"

**증상** — 2주차에 "리뷰가 3일째 안 달려요" / "누가 머지했어요?" — 규칙이 없으니 갈등이
사람 문제가 됨.
**원인** — 규칙 만들기를 관료적 낭비로 취급.
**해결** — 규칙은 갈등을 **사람에서 문서로** 옮기는 장치입니다 ([Day 110](../05-infra-mlops/day-110.md)
의 결론). 특히 **결정 규칙**(합의 실패 시 절차)은 오늘 반드시 — 필요해진 순간에 만들면
이미 늦습니다.

### 역할 분담 = 영역 소유권으로 오해

**증상** — "데이터는 A 거니까 나는 몰라도 됨" — 발표 질의에서 담당자 외 전원 침묵,
개인 기여도 평가에서 전원 손해.
**원인** — "주 담당"과 "독점"의 혼동.
**해결** — 주 담당은 병목 방지용 책임 소재일 뿐입니다. 교차 리뷰 짝(Step 1)이 최소한의
상호 이해 장치 — 리뷰 짝의 영역은 "설명할 수 있을 만큼" 알아야 합니다.

## ⑥ 확인 문제

**Q1.** "데이터 실재 확인"의 통과 증거가 왜 "링크·문서·타인의 후기"가 아니라 "오늘 실행한
코드와 응답 원문"이어야 하는지, 한산 팀의 INFO-200 사건으로 논증하세요.

<details>
<summary>답 보기</summary>

문서는 데이터의 **이상적 상태**를 기술하고, 후기는 **과거의 상태**를 기술합니다. 오늘의
호출만이 현재 상태(지연·제한·형식·인증 절차)를 증언합니다. 한산 팀의 경우 문서 어디에도
"어제 데이터는 없다"고 크게 쓰여 있지 않았고, 실제 호출이 INFO-200을 돌려주고서야 D-4
지연이 드러났습니다. 이 발견이 첫날이었기에 "예보 서비스" 프레임으로 흡수할 수 있었지만,
구현 주간이었다면 아키텍처(수집 주기·서비스 시나리오) 재작업이었습니다. 위험은 제거가
아니라 **조기 발견**이 목표이고, 조기 발견의 유일한 도구가 실제 실행입니다.

</details>

**Q2.** 좋은 주제의 4 기준에 "참신함"이 없는 이유를 배점표와 연결해 설명하고, 참신함이
실제로 기여할 수 있는 자리를 찾아보세요.

<details>
<summary>답 보기</summary>

배점 100점의 구성(사이클 30 · 재현성 20 · 모델링 15 · 협업 15 · 문서·발표 20)은 전부
**과정과 증거**에 걸려 있습니다 — 주제가 무엇인지는 채점 대상이 아닙니다. 참신한 주제는
대개 데이터 불확실성과 범위 팽창을 동반하므로 4 기준 관점에서는 오히려 위험 요인입니다.
참신함이 기여하는 자리는 문서·발표 20점 안의 "이야기" — 같은 기술 스택이라도 문제 정의가
생생하면(누가, 언제, 왜) 발표 전달력이 오릅니다. 즉 참신함은 주제 선정 기준이 아니라
**문제 서술의 품질**로 쓰는 것이 합리적 배치입니다.

</details>

**Q3.** 한산 팀의 리뷰 짝(서연↔지우, 민준↔하람)이 같은 영역끼리(예: 데이터↔모델)가 아니라
교차(데이터↔서빙, 모델↔인프라)로 묶인 설계 의도를 두 가지 이상 설명하세요.

<details>
<summary>답 보기</summary>

① **경계 결함의 조기 발견** — 프로젝트 사고의 다발 지점은 영역 내부가 아니라 인터페이스
(데이터 스키마↔API 응답, 모델 산출물↔배포 이미지)입니다. 교차 리뷰는 인터페이스 양쪽
당사자가 서로의 코드를 읽게 만들어 계약 불일치를 리뷰 단계에서 잡습니다. ② **지식 독점
방지** — 전원이 시연 질의응답에 응해야 하는 평가 구조에서, 교차 리뷰는 최소 두 사람이
각 영역을 설명할 수 있게 하는 가장 싼 장치입니다. ③ (추가) 같은 영역끼리 묶으면 리뷰가
"둘만 아는 대화"가 되어 기록의 가치가 떨어지는 반면, 교차 리뷰는 "모르는 사람도 이해
가능한 설명"을 PR에 남기게 강제합니다 — 이 기록이 곧 협업 이력 15점의 증거가 됩니다.

</details>
