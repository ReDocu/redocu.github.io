## 2. 막히는 상황

Day 27에서 클래스로 정리한 `Game::Update`를 보자.

```cpp

{

    m_field.Render(m_screen);
    m_paddle.Render(m_screen);
```

이제 **아이템**을 추가하려고 한다.

```cpp
class Item { void Update(double dt); void Render(...); };

void Game::Update(double dt)
{
    m_paddle.Update(dt);
    m_ball.Update(dt);
    m_field.Update(dt);
    m_item.Update(dt);            // ← 추가

void Game::Render()
{
    // ... 여기도 추가
    m_item.Render(m_screen);

```

**이펙트**도 추가한다. **총알**도. **보스**도.

```
   오브젝트 종류 10개 →  Game::Update 에 10줄, Render 에 10줄
   오브젝트 종류 30개 →  60줄

   ★ 새 오브젝트를 추가할 때마다 Game 클래스를 고쳐야 한다
```

그리고 아이템이 **여러 개**면?

## 3. 개념

### 3-1. 상속 — 공통점을 위로 뽑아내기

**왜 필요한가** — 반복되는 것을 한 곳에 모은다.

```cpp
class GameObject                        // 부모(기반) 클래스
{
public:
    GameObject() : m_x(0), m_y(0), m_active(true) {}

    void SetPos(double x, double y) { m_x = x; m_y = y; }
    double GetX() const { return m_x; }
    double GetY() const { return m_y; }

    bool IsActive() const { return m_active; }
    void SetActive(bool a) { m_active = a; }

protected:                              // ★ 자식은 접근 가능, 밖에서는 불가
    double m_x, m_y;
    bool   m_active;
};

class Ball : public GameObject          // 자식(파생) 클래스
{
public:
    void Fire(double vx, double vy);

private:
    double m_vx, m_vy;                  // Ball 고유의 것만
};
```

```
                    GameObject
                    m_x, m_y, m_active
                    SetPos(), IsActive()
                          ▲
         ┌────────────┬───┴────┬────────────┐
       Ball        Paddle    Block        Item
       m_vx,m_vy   m_width   m_hp         m_type

   ★ 공통된 것(좌표, 활성 여부)은 부모가 갖는다
     자식은 자기만의 것만 추가한다
```

**접근 지정자 3종**

| 지정자 | 밖에서 | 자식에서 | 자기 안에서 |
|---|:--:|:--:|:--:|
| `public` | O | O | O |
| **`protected`** | X | **O** | O |
| `private` | X | X | O |

> **`protected`는 상속을 위한 것이다.** 밖에는 감추되 자식은 쓸 수 있게 한다.

**상속받으면 부모 것을 그대로 쓴다**

```cpp
Ball ball;

ball.SetPos(10, 20);            // GameObject의 함수
ball.Fire(25, -18);             // Ball의 함수
```

### 3-2. 생성자·소멸자 호출 순서

**왜 필요한가** — 순서를 알아야 초기화 버그를 피한다.

```cpp
class GameObject
{
public:
    GameObject()  { printf("GameObject 생성\n"); }
    ~GameObject() { printf("GameObject 소멸\n"); }
};

class Ball : public GameObject
{
public:
    Ball()  { printf("Ball 생성\n"); }
    ~Ball() { printf("Ball 소멸\n"); }
};
```

```cpp
    Ball b;
```

```
   출력:
     GameObject 생성       ← 부모 먼저
     Ball 생성             ← 자식 나중

     (블록 끝)

     Ball 소멸             ← 자식 먼저
     GameObject 소멸       ← 부모 나중

   ★ 생성은 부모→자식,  소멸은 자식→부모 (역순)
     집을 지을 때 기초부터, 허물 때는 위부터
```

**부모 생성자에 인자 넘기기**

```cpp
class GameObject
{
public:
    GameObject(double x, double y) : m_x(x), m_y(y) {}
protected:
    double m_x, m_y;
};

class Ball : public GameObject
{
public:
    Ball(double x, double y)
        : GameObject(x, y)              // ★ 초기화 리스트에서 부모 생성자 호출
        , m_vx(0), m_vy(0)
    {}
private:
    double m_vx, m_vy;
};
```

### 3-3. 가상 함수 — 자식이 다르게 행동하기

**왜 필요한가** — 오늘의 핵심.

**먼저 `virtual` 없이 해 본다.**

```cpp
class GameObject
{
public:
    void Update(double dt) { printf("GameObject::Update\n"); }
};

class Ball : public GameObject
{
public:
    void Update(double dt) { printf("Ball::Update\n"); }      // 같은 이름
};
```

```cpp
    Ball ball;
    ball.Update(0.016);                 // "Ball::Update"      ✔

    GameObject* p = &ball;              // 부모 포인터로 가리킨다
    p->Update(0.016);                   // "GameObject::Update"  ✘ 어?!
```

```
   왜 부모 것이 불렸나?

   GameObject* p 는 "이건 GameObject다"라고 선언되어 있다.
   컴파일러는 컴파일 시점에 GameObject::Update 를 호출하도록 코드를 만든다.

   ★ 실제로 무엇을 가리키는지는 실행할 때 정해지는데,
     호출할 함수는 컴파일할 때 이미 정해져 버렸다
```

**`virtual`을 붙이면 달라진다.**

```cpp
class GameObject
{
public:
    virtual void Update(double dt) { printf("GameObject::Update\n"); }
    //  ▲ 이 한 단어
};

class Ball : public GameObject
{
public:
    void Update(double dt) override { printf("Ball::Update\n"); }
    //                     ▲ C++11: 재정의임을 명시 (오타 방지)
};
```

```cpp
    GameObject* p = &ball;
    p->Update(0.016);                   // "Ball::Update"  ✔
```

```
   virtual 이 하는 일

   [virtual 없음]                     [virtual 있음]

   컴파일 시점에 결정                  실행 시점에 결정
   "GameObject 타입이니                "실제로 가리키는 게 Ball이니
    GameObject::Update 호출"            Ball::Update 호출"

   = 정적 바인딩                       = 동적 바인딩 (dynamic dispatch)
```

**동작 원리 (참고)**

```
   virtual 함수가 있는 클래스는 숨은 포인터를 하나 갖는다

   Ball 객체
   ┌──────────────┐
   │ vptr  ───────┼──▶  Ball의 가상 함수 테이블 (vtable)
   │ m_x          │      ┌──────────────────────┐
   │ m_y          │      │ Update → Ball::Update│
   │ m_vx         │      │ Render → Ball::Render│
   │ m_vy         │      └──────────────────────┘
   └──────────────┘

   p->Update()  →  vptr을 따라가 테이블에서 실제 함수를 찾아 호출

   ★ 그래서 아주 약간 느리다 (테이블 조회 한 번)
     대신 얻는 유연함이 훨씬 크다
```

### 3-4. 다형성 — 하나의 코드가 여러 동작을

**왜 필요한가** — 2절의 문제가 여기서 해결된다.

```cpp
GameObject* objects[100];
int count = 0;

objects[count++] = new Ball();
objects[count++] = new Paddle();
objects[count++] = new Block();
objects[count++] = new Item();

// ★ 이 한 줄이 각자 다르게 동작한다
for (int i = 0; i < count; i++)
    objects[i]->Update(dt);
```

```
   objects[0]->Update()  →  Ball::Update()     공이 날아간다
   objects[1]->Update()  →  Paddle::Update()   입력을 받는다
   objects[2]->Update()  →  Block::Update()    아무것도 안 한다
   objects[3]->Update()  →  Item::Update()     아래로 떨어진다

   ★ 코드는 한 줄인데 동작은 네 가지
     이것이 다형성(polymorphism)
```

**새 오브젝트를 추가할 때**

```cpp
class Effect : public GameObject        // ① 클래스 하나 만들고
{
public:
    void Update(double dt) override { /* ... */ }
    void Render(Screen& s) override { /* ... */ }
};

objects[count++] = new Effect();        // ② 배열에 넣는다
```

```
   ★ Game 클래스는 한 줄도 안 고친다
     for 루프가 알아서 처리한다
```

### 3-5. 순수 가상 함수와 추상 클래스

**왜 필요한가** — "자식은 반드시 이 함수를 만들어야 한다"를 강제한다.

```cpp
class GameObject
{
public:
    virtual void Update(double dt) = 0;          // ★ = 0 : 순수 가상 함수
    virtual void Render(Screen& s) = 0;
    virtual ~GameObject() {}
};
```

```cpp
    GameObject obj;                     // ✘ 컴파일 오류!
    // error: 추상 클래스는 인스턴스화할 수 없습니다
```

```
   순수 가상 함수가 하나라도 있으면  →  추상 클래스
   추상 클래스는 객체를 만들 수 없다  →  자식만 만들 수 있다

   그리고 자식이 Update/Render를 구현하지 않으면
   그 자식도 추상 클래스가 되어 객체를 못 만든다
   → 구현을 강제하게 된다
```

| | 일반 가상 함수 | 순수 가상 함수 |
|---|---|---|
| 부모의 구현 | 있다 | **없다** |
| 자식이 재정의 | 선택 | **필수** |
| 객체 생성 | 가능 | 불가 (추상 클래스) |
| 쓰는 곳 | 기본 동작이 있을 때 | 인터페이스 정의 |

### 3-6. ⚠️ 가상 소멸자 — 잊으면 메모리가 샌다

**왜 필요한가** — 오늘 가장 조용히 위험한 부분.

```cpp
class GameObject
{
public:
    ~GameObject() { printf("GameObject 소멸\n"); }       // virtual 없음
};

class Ball : public GameObject
{
public:
    Ball()  { m_trail = new double[100]; }
    ~Ball() { delete[] m_trail; printf("Ball 소멸\n"); }
private:
    double* m_trail;
};
```

```cpp
    GameObject* p = new Ball();
    delete p;
```

```
   출력:
     GameObject 소멸

   ★ Ball 소멸자가 안 불렸다!
     → m_trail (800바이트)이 영원히 누수된다
```

**해결 — 소멸자에 `virtual`**

```cpp
class GameObject
{
public:
    virtual ~GameObject() { printf("GameObject 소멸\n"); }      // ★
};
```

```
   출력:
     Ball 소멸               ← 자식부터
     GameObject 소멸         ← 그다음 부모
```

> ### 규칙
> **부모 포인터로 자식을 `delete`할 가능성이 있으면, 소멸자는 반드시 `virtual`.**
>
> 실무에서는 **"가상 함수가 하나라도 있으면 소멸자도 가상으로"** 를 규칙으로 삼는다.
> 잊기 쉽고, 잊으면 조용히 샌다.

### 3-7. ⚠️ 객체 슬라이싱

**왜 필요한가** — 값으로 담으면 자식 정보가 잘려 나간다.

```cpp
GameObject objects[10];         // ✘ 값 배열

```

```
   Ball 객체 (48바이트)         GameObject 배열 칸 (24바이트)
   ┌──────────────┐            ┌──────────────┐
   │ vptr         │            │ vptr         │
   │ m_x, m_y     │  ────────▶ │ m_x, m_y     │
   │ m_active     │   복사      │ m_active     │
   │ m_vx, m_vy   │            └──────────────┘

```

### 3-8. 오브젝트 매니저 구조

**왜 필요한가** — 오늘 배운 것을 실제로 쓰는 형태.

```cpp
class ObjectManager
{
public:
    ~ObjectManager() { Clear(); }

    void Add(GameObject* obj)
    {
        if (m_count >= MAX_OBJECTS) { delete obj; return; }
        m_objects[m_count++] = obj;
    }

    void UpdateAll(double dt)
    {
        for (int i = 0; i < m_count; i++)
            if (m_objects[i]->IsActive())
                m_objects[i]->Update(dt);
    }

    void RenderAll(Screen& s)
    {
        for (int i = 0; i < m_count; i++)
            if (m_objects[i]->IsActive())
                m_objects[i]->Render(s);
    }

    void RemoveInactive()
    {
        for (int i = m_count - 1; i >= 0; i--)       // ★ 뒤에서부터 (Day 11)
        {
            if (!m_objects[i]->IsActive())
            {
                delete m_objects[i];
                m_objects[i] = m_objects[--m_count];  // 마지막 것을 당겨온다
            }
        }
    }

    void Clear()
    {
        for (int i = 0; i < m_count; i++)
            delete m_objects[i];
        m_count = 0;
    }

private:
    GameObject* m_objects[MAX_OBJECTS] = { nullptr };
    int         m_count = 0;
};
```

> **이 `ObjectManager`가 Day 40의 `Scene` 클래스가 된다.**
> 그리고 `RemoveInactive`의 "삭제 대신 비활성화" 발상이 **Day 52의 오브젝트 풀링**으로 이어진다.

## 4. 따라 만들기

### Step 1 — `virtual` 없이 실패 확인

```cpp
class GameObject
{
public:
    void Update(double dt) { printf("GameObject::Update\n"); }
};

class Ball : public GameObject
{
public:
    void Update(double dt) { printf("Ball::Update\n"); }
};

int main()
{
    Ball ball;

    printf("--- 직접 호출 ---\n");
    ball.Update(0.016);

    printf("--- 부모 포인터로 호출 ---\n");
    GameObject* p = &ball;
    p->Update(0.016);

    return 0;
}
```

**✅ 여기까지 실행하면**

```
--- 직접 호출 ---
Ball::Update
--- 부모 포인터로 호출 ---
GameObject::Update        ← 문제 발생!
```

> **이 결과를 반드시 눈으로 본다.** `virtual`의 필요성이 여기서 나온다.

### Step 2 — `virtual` 추가

```cpp
class GameObject
{
public:
    virtual void Update(double dt) { printf("GameObject::Update\n"); }
    //  ▲ 추가
};

class Ball : public GameObject
{
public:
    void Update(double dt) override { printf("Ball::Update\n"); }
    //                     ▲ 추가
};
```

**✅ 여기까지 실행하면**

```
--- 부모 포인터로 호출 ---
Ball::Update              ← 해결!
```

> **단어 하나로 동작이 바뀐다.** 이것이 오늘의 핵심이다.

### Step 3 — `GameObject` 기반 클래스 설계

```cpp
class Screen;               // 전방 선언

class GameObject
{
public:
    GameObject() : m_x(0), m_y(0), m_active(true) {}
    virtual ~GameObject() {}                          // ★ 가상 소멸자

    virtual void Update(double dt) = 0;               // 순수 가상
    virtual void Render(Screen& screen) const = 0;

    virtual void OnCollide(GameObject* other) {}      // 기본은 아무것도 안 함

    void SetPos(double x, double y) { m_x = x; m_y = y; }
    double GetX() const { return m_x; }
    double GetY() const { return m_y; }

    bool IsActive() const  { return m_active; }
    void SetActive(bool a) { m_active = a; }

    virtual Rect GetBounds() const                    // 충돌 판정용
    {
        Rect r = { m_x, m_y, 1.0, 1.0 };
        return r;
    }

protected:
    double m_x, m_y;
    bool   m_active;
};
```

**✅ 여기까지 하면** — 모든 오브젝트의 공통 인터페이스가 정의된다.

### Step 4 — `Ball`을 자식으로 재작성

```cpp
class Ball : public GameObject
{
public:
    Ball();

    void Update(double dt) override;
    void Render(Screen& screen) const override;
    void OnCollide(GameObject* other) override;

    void Launch(double vx, double vy);
    void BounceX() { m_vx = -m_vx; }
    void BounceY() { m_vy = -m_vy; }

private:
    double m_vx, m_vy;
    char   m_symbol;
    bool   m_launched;
};

void Ball::Update(double dt)
{
    if (!m_launched) return;

    m_x += m_vx * dt;                    // 부모의 m_x 를 그대로 쓴다
    m_y += m_vy * dt;

    if (m_x < 0)            { m_x = 0;            m_vx = -m_vx; }
    if (m_x > SCREEN_W - 1) { m_x = SCREEN_W - 1; m_vx = -m_vx; }
    if (m_y < 0)            { m_y = 0;            m_vy = -m_vy; }
}
```

**✅ 여기까지 실행하면** — 공이 이전과 동일하게 동작한다.

### Step 10 — 충돌 처리를 다형성으로

```cpp
void Game::CheckCollisions()
{
    Rect ballRect = m_ball->GetBounds();

    for (int i = 0; i < m_objects.GetCount(); i++)
    {
        GameObject* obj = m_objects.Get(i);

        if (obj == m_ball || !obj->IsActive()) continue;

        if (IsOverlap(&ballRect, &obj->GetBounds()))
        {
            obj->OnCollide(m_ball);          // ★ 각자 알아서 반응한다
            m_ball->OnCollide(obj);
        }
    }
}
```

```
   obj->OnCollide()  →  Block::OnCollide()   HP 감소, 파괴 시 비활성화
                     →  Item::OnCollide()    효과 발동, 비활성화
                     →  Paddle::OnCollide()  아무것도 안 함

   ★ Game은 무엇과 부딪혔는지 알 필요가 없다
```

**✅ 여기까지 실행하면** — 충돌 처리에서 `if (블록이면) else if (아이템이면)` 분기가 사라진다.

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|
| 자식 함수가 안 불림 | **`virtual` 누락** | 부모 함수에 `virtual` |
| 메모리 누수 | **가상 소멸자 누락** | `virtual ~GameObject() {}` |
| 자식 정보가 사라짐 | 값으로 담음 (슬라이싱) | **포인터 배열** 사용 |
| `error: 추상 클래스 인스턴스화` | 순수 가상 함수를 구현 안 함 | 자식에서 모두 재정의 |
| `override` 오류 | 부모에 그런 가상 함수가 없음 | 시그니처(매개변수, `const`) 확인 |
| `protected` 멤버 접근 오류 | `private`로 선언 | `protected`로 변경 |
| 부모 생성자 인자 오류 | 초기화 리스트에서 호출 안 함 | `: GameObject(x, y)` |
| 순회 중 삭제 크래시 | 삭제하며 인덱스가 어긋남 | **뒤에서부터** 순회 |
| `delete` 두 번 | 매니저와 개별 포인터 양쪽에서 삭제 | 소유권을 매니저 하나로 |
| 성능이 걱정됨 | vtable 조회 비용 | 무시할 수준. 얻는 게 훨씬 크다 |

## 7. 정리

### 오늘 배운 것

| 개념 | 한 줄 요약 |
|---|---|
| **상속** | 공통점을 부모로 뽑는다. `class Ball : public GameObject` |
| `protected` | 밖에는 감추고 자식에게는 공개 |
| 생성/소멸 순서 | 생성은 부모→자식, 소멸은 자식→부모 |
| **`virtual`** | 실행 시점에 실제 타입의 함수를 부른다 |
| **다형성** | 하나의 코드가 여러 동작. **부모 포인터로만 동작** |
| 순수 가상 `= 0` | 자식에게 구현을 강제. 추상 클래스 |
| **가상 소멸자** | 없으면 자식 소멸자가 안 불려 **메모리가 샌다** |
| 슬라이싱 | 값으로 담으면 자식 정보가 잘린다 |
