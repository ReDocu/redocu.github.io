## 2. 막히는 상황

어제 만든 미로를 실행하고 벽 쪽으로 이동해 보자.

```
  # . # P # . #        ← P가 벽(#) 안에 들어가 있다
```

**벽을 그냥 지나간다.** 미로가 미로가 아니다.

그리고 어제 넣은 임시 경계 검사를 지우고 왼쪽 벽으로 계속 가 보면
프로그램이 죽거나 이상한 문자가 나온다.

```
   왜 죽나?

   g_playerX = -1  일 때

   g_map[y][-1]  →  배열 범위 밖 (Day 11에서 배운 그것)
                    남의 메모리를 읽는다
```

```
   지금:   키 입력  →  무조건 좌표 갱신  →  그리기
                          ▲
                          └── 아무 검사가 없다

   필요:   키 입력  →  갈 자리 계산  →  ① 맵 안인가?
                                       ② 벽인가?
                                       → 둘 다 통과해야 이동
```

> **이동해도 되는지 판단하는 방법이 필요하다.** 그리고 **검사 순서가 중요하다.**

## 3. 개념

### 3-1. 이동 전 검사 패턴

**왜 필요한가** — 움직이고 나서 되돌리면 이미 늦었다. 배열 범위를 넘은 뒤에는 크래시할 수도 있다.

```c
// ✘ 나쁜 방식 — 먼저 이동하고 되돌리기
g_playerX += dx;
if (g_map[g_playerY][g_playerX] == '#')      // ← 여기서 이미 범위 밖일 수 있다
    g_playerX -= dx;

// ✔ 좋은 방식 — 갈 자리를 먼저 확인
int nextX = g_playerX + dx;
int nextY = g_playerY + dy;

if (CanMove(nextX, nextY))
{
    g_playerX = nextX;
    g_playerY = nextY;
}
```

```
   ┌──────────────────────────────────────────────┐
   │  ① 갈 자리 계산     nextX = x + dx           │
   │                     nextY = y + dy           │
   │           ▼                                   │
   │  ② 갈 수 있나 검사   CanMove(nextX, nextY)    │
   │           ▼                                   │
   │  ③ 통과하면 이동     x = nextX;  y = nextY;   │
   └──────────────────────────────────────────────┘

   ★ 실제로 좌표를 바꾸는 것은 ③ 한 곳뿐이다
```

> 이 패턴이 앞으로 계속 나온다.
> Day 22(공의 벽 반사), Day 44(캐릭터 이동), Day 87(타워 배치)까지 전부 같은 형태다.

### 3-2. ⚠️ 검사 순서 — 경계가 먼저다

**왜 필요한가** — 순서를 바꾸면 크래시한다. 오늘 가장 중요한 내용이다.

```c
// ✘ 벽 검사가 먼저
if (g_map[nextY][nextX] != '#' && nextX >= 0 && nextX < MAP_W)
//  ▲ nextX가 -1이면 여기서 이미 범위 밖 접근 → 크래시

// ✔ 경계 검사가 먼저
if (nextX >= 0 && nextX < MAP_W && nextY >= 0 && nextY < MAP_H &&
    g_map[nextY][nextX] != '#')
//  └───────────── 여기를 통과해야만 ─────────────┘  여기에 도달한다
```

```
   C의 && 는 "단축 평가(short-circuit)"를 한다

   A && B && C

   A가 거짓이면  →  B, C는 아예 실행하지 않는다
                     ▲
                     └── 이 성질 덕분에 안전한 검사가 가능하다

   예)  nextX >= 0  &&  g_map[nextY][nextX] != '#'
        ▲ nextX가 -1이면 거짓         ▲ 여기는 실행 안 됨 → 안전
```

**검사 순서 규칙**

```
   ① 배열 범위 검사   (안전)
   ② 게임 규칙 검사   (의미)
```

> **"안전 먼저, 의미 나중."** 배열에 접근하기 전에 반드시 범위를 확인한다.

### 3-3. `CanMove` — 검사를 함수로

**왜 필요한가** — 검사 조건이 길어진다. 그리고 아이템·문·함정이 추가되면 더 길어진다.

```c
// 그 자리로 갈 수 있는가?
int CanMove(int x, int y)
{
    // ① 경계 검사 (안전)
    if (x < 0 || x >= MAP_W || y < 0 || y >= MAP_H)
        return 0;

    // ② 벽 검사 (의미)
    if (g_map[y][x] == TILE_WALL)
        return 0;

    // ③ 문 검사 — 열쇠가 있어야 통과
    if (g_map[y][x] == TILE_DOOR && g_keyCount <= 0)
        return 0;

    return 1;                       // 통과
}
```

```
   CanMove(x, y)

   ┌─ 맵 밖인가? ──── 예 ──▶ 0 (못 감)
   │        아니오
   ├─ 벽인가?   ──── 예 ──▶ 0
   │        아니오
   ├─ 잠긴 문인가? ── 예 ──▶ 0
   │        아니오
   └────────────────────▶ 1 (갈 수 있다)

   ★ 조건 하나당 return 하나. 중첩 if 보다 읽기 쉽다 (early return)
```

> **early return 패턴** — 안 되는 경우를 먼저 걸러내고, 마지막에 성공을 반환한다.
> `if` 안에 `if` 안에 `if`를 쌓는 것보다 훨씬 읽기 쉽다.

### 3-4. 타일별 처리 — 밟았을 때 일어나는 일

**왜 필요한가** — "갈 수 있는가"와 "가서 무슨 일이 생기는가"는 다른 문제다.

```
   CanMove()        →  갈 수 있는가?          (이동 전)
   OnEnterTile()    →  밟으면 무슨 일이?      (이동 후)
```

```c
void OnEnterTile(int x, int y)
{
    switch (g_map[y][x])
    {
    case TILE_ITEM:
        g_gemCount++;
        g_map[y][x] = TILE_FLOOR;                 // ★ 주웠으니 길로 바꾼다
        SetMessage(">> 보석을 주웠다!");
        break;

    case TILE_KEY:
        g_keyCount++;
        g_map[y][x] = TILE_FLOOR;
        SetMessage(">> 열쇠를 손에 넣었다!");
        break;

    case TILE_DOOR:
        g_keyCount--;                              // 열쇠 소모
        g_map[y][x] = TILE_FLOOR;                  // 문이 열림
        SetMessage(">> 열쇠로 문을 열었다.");
        break;

    case TILE_TRAP:
        g_hp--;
        SetMessage(">> 함정! 체력이 줄었다.");
        break;

    case TILE_EXIT:
        SetMessage(">> 출구다!");
        break;
    }
}
```

> ### ⚠️ 아이템을 주운 뒤 맵 데이터를 바꿔야 한다
>
> ```c
> case TILE_ITEM:
>     g_gemCount++;
>     // g_map[y][x] = TILE_FLOOR;   ← 이걸 빼먹으면
>     break;
> ```
>
> 그 자리에서 제자리걸음만 해도 보석이 무한정 늘어난다.
> **한 번만 일어나야 하는 일은 데이터를 바꿔서 표시한다.**

### 3-5. 타일 종류 정리

**왜 필요한가** — 맵 문자 하나하나가 규칙이다. 표로 정리해 두면 빠뜨리지 않는다.

| 문자 | 상수 | 통과 | 밟으면 |
|:--:|---|:--:|---|
| `#` | `TILE_WALL` | X | — |
| `.` | `TILE_FLOOR` | O | — |
| `*` | `TILE_ITEM` | O | 보석 +1, 길로 변경 |
| `K` | `TILE_KEY` | O | 열쇠 +1, 길로 변경 |
| `D` | `TILE_DOOR` | 열쇠 필요 | 열쇠 -1, 길로 변경 |
| `X` | `TILE_TRAP` | O | 체력 -1 |
| `E` | `TILE_EXIT` | O | 클리어 (Day 15) |

```c
#define TILE_WALL   '#'
#define TILE_FLOOR  '.'
#define TILE_ITEM   '*'
#define TILE_KEY    'K'
#define TILE_DOOR   'D'
#define TILE_TRAP   'X'
#define TILE_EXIT   'E'
```

### 3-6. 메시지 시스템 — 무슨 일이 일어났는지 알리기

**왜 필요한가** — `printf`로 바로 출력하면 `system("cls")`에 지워진다.

```
   ✘ 즉시 출력
   printf("보석을 주웠다!");     ← 출력
   system("cls");                 ← 바로 지워짐. 플레이어는 못 본다

   ✔ 메시지를 저장했다가 그릴 때 출력
   SetMessage("보석을 주웠다!");  ← 저장만
   ...
   system("cls");
   PrintMap();
   printf("%s", g_message);       ← 여기서 출력
```

```c
char g_message[64] = "";

void SetMessage(const char* msg)
{
    strcpy_s(g_message, sizeof(g_message), msg);
}
```

> 이것이 나중에 **HUD / UI 레이어**로 발전한다.
> "게임 상태를 바꾸는 코드"와 "화면에 그리는 코드"를 분리하는 첫걸음이다.
> Day 21의 게임 루프에서 `Update()`와 `Render()`가 나뉘는 이유가 바로 이것이다.


**✅ 여기까지 실행하면** — 아직 연결 전이라 변화 없다.

### Step 7 — 벽 밀기 판정 개선 (확장)

같은 벽에 계속 부딪히면 메시지가 반복된다. 카운트해서 힌트를 준다.

```c
        if (!CanMove(nextX, nextY))
        {
            static int bumpCount = 0;              // static: 값이 유지된다
            bumpCount++;

            if (g_map[nextY][nextX] == TILE_DOOR)
                SetMessage(">> 문이 잠겨 있다. 열쇠가 필요하다.");
            else if (bumpCount >= 3)
                SetMessage(">> 벽이다. 다른 길을 찾아보자.");
            else
                SetMessage(">> 쿵! 벽이다.");

            continue;
        }
```

> `static` 지역 변수 — 함수가 끝나도 값이 유지된다. (Day 4의 지역 변수와 다르다)

**✅ 여기까지 실행하면** — 문에 부딪히면 다른 메시지가 나오고, 벽에 3번 부딪히면 힌트가 바뀐다.

## 5. 실행 결과

**정상이라면 이렇게 보인다.**

```
=====================================
        미로 탈출  -  Stage 1
=====================================

  # # # # # # # # # #
  # . . . # . . . . #
  # . # P # . # # . #
  # . # . . . # . . #
  # . # # # . # X # #
  # K . . # . . . * #
  # # # . # # # # . #
  # . . . . . # . . #
  # . # # # . # D E #
  # # # # # # # # # #

  P 플레이어   # 벽   . 길   * 보석   K 열쇠   D 문   X 함정   E 출구

  소지품:  열쇠 x0   보석 x0   체력 3

  >> 쿵! 벽이다.

  위치 (3, 2)   이동 8회
=====================================
```

- [ ] 벽 쪽으로 키를 눌러도 `P`가 제자리에 있다
- [ ] 맵 가장자리에서 계속 밖으로 가려 해도 **크래시하지 않는다**
- [ ] 보석을 밟으면 사라지고 개수가 늘어난다
- [ ] 같은 자리에서 다시 밟아도 보석이 또 늘지 않는다
- [ ] 열쇠 없이 문에 가면 통과할 수 없다
- [ ] 열쇠를 얻은 뒤에는 문을 통과하고 열쇠가 소모된다
- [ ] 함정을 밟으면 체력이 줄어든다
- [ ] 검사 순서를 바꾸면 문제가 생긴다는 것을 확인했다

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|
| 가장자리에서 크래시 | **경계 검사가 벽 검사보다 뒤** | 경계 검사를 **맨 앞**으로 |
| 벽을 통과함 | `CanMove` 결과를 무시 | `if (!CanMove(...)) continue;` |
| 아이템이 무한정 늘어남 | 획득 후 맵 데이터 미변경 | `g_map[y][x] = TILE_FLOOR;` |
| 메시지가 안 보임 | `system("cls")` 뒤에 출력 | 메시지를 저장했다가 그릴 때 출력 |
| 메시지가 계속 남아 있음 | `default`에서 지우지 않음 | `SetMessage("")` 추가 |
| 열쇠가 음수가 됨 | 문 통과 조건과 소모 처리 불일치 | `CanMove`에서 `g_keyCount <= 0` 확인 |
| `strcpy_s` 오류 | `<string.h>` 누락 | `#include <string.h>` |
| 이동 횟수가 벽에 부딪혀도 증가 | `continue` 위치 | 카운트를 이동 성공 후로 |

## 7. 정리

### 오늘 배운 것

| 개념 | 한 줄 요약 |
|---|---|
| 이동 전 검사 | 갈 자리를 먼저 계산하고, 통과하면 이동 |
| **검사 순서** | **경계(안전) 먼저, 규칙(의미) 나중.** 순서가 바뀌면 크래시 |
| 단축 평가 | `&&`는 앞이 거짓이면 뒤를 실행하지 않는다 → 안전한 검사 |
| `CanMove` | 갈 수 있는가 (이동 전) |
| `OnEnterTile` | 밟으면 무슨 일이 (이동 후) |
| early return | 안 되는 경우를 먼저 걸러내고 마지막에 성공 반환 |
| 데이터 변경 | 한 번만 일어날 일은 맵 데이터를 바꿔 표시 |
| 메시지 분리 | 상태 변경과 화면 출력을 나눈다 |

### 직접 해보기

| 난이도 | 과제 | 힌트 |
|:--:|---|---|
| ★ | 체력이 0이 되면 게임 오버 | `if (g_hp <= 0) running = 0;` |
| ★★ | 밀 수 있는 상자 `O` 추가 (소코반) | 상자 뒤쪽 칸도 `CanMove`로 검사 |
| ★★★ | 워프 타일 `@` — 밟으면 맵의 다른 `@`로 순간이동 | 이중 루프로 다른 `@` 좌표를 찾는다 |
