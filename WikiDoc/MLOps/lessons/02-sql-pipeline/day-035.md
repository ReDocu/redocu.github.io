## ② 왜 필요한가

**오늘은 새 문법을 배우지 않습니다.** 4일간 배운 것을 실제 업무 형태로 조립합니다.

실무에서 여러분에게 오는 것은 SQL이 아닙니다. **이런 문장**입니다.

> "지난달 매출이 왜 떨어졌는지 좀 봐 주세요."
> "VIP 기준을 다시 잡으려는데, 상위 고객이 얼마나 쓰는지 알려주세요."
> "이 카테고리 접어도 될까요?"

문법을 다 알아도 **이 문장 앞에서 손이 멈추는 것**이 가장 흔한 벽입니다.
막히는 이유는 문법이 아니라 **질문을 분해하는 절차가 없기 때문**입니다. 오늘 그 절차를 만듭니다.

그리고 이 절차는 [Day 040](day-040.md)의 스키마 설계, [Day 048](day-048.md)의 MP1 분석 쿼리,
나아가 실무 면접의 SQL 문제까지 그대로 쓰입니다.

## ③ 개념 설명

### 질문 → SQL 번역 5단계 ★

```
① 답의 모양을 그린다      "몇 행 × 몇 열짜리 표가 나와야 하나?"
② 필요한 테이블을 찾는다   "그 열들은 어느 테이블에 있나?"
③ 조건을 두 종류로 나눈다  "행 조건(WHERE) vs 그룹 조건(HAVING)"
④ 뼈대부터 조립한다        FROM → JOIN → WHERE → GROUP BY → SELECT → ORDER BY
⑤ 검산한다                "합이 맞나? 행 수가 맞나? 다른 경로로도 같은 값인가?"
```

예를 들어 **"고객별 최근 3개월 구매액 상위 10명"** 을 옮겨 보겠습니다.

| 단계 | 생각 |
|---|---|
| ① 답의 모양 | `고객명 | 구매액` 2열, 최대 10행. **고객 하나가 한 줄** → 고객으로 `GROUP BY` |
| ② 테이블 | 고객명 → `customers` / 주문일 → `orders` / 금액 → `order_items` → **3개 조인** |
| ③ 조건 | 최근 3개월 = **행 조건**(`WHERE o.ordered_at >= ...`) · 취소 제외도 **행 조건** · 상위 10명은 `ORDER BY` + `LIMIT` |
| ④ 조립 | 아래 |
| ⑤ 검산 | 구매액 합계가 4~6월 매출 합과 같은가? |

```sql
SELECT c.name AS 고객, SUM(oi.quantity * oi.unit_price) AS 구매액
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
WHERE o.ordered_at >= '2025-04-01'
  AND o.status <> 'cancelled'
GROUP BY c.customer_id, c.name
ORDER BY 구매액 DESC
LIMIT 10;
```

### ①이 가장 중요합니다 — "답의 모양"

**결과 표의 한 줄이 무엇 하나인지**를 먼저 정하면 `GROUP BY` 가 저절로 정해집니다.

| 질문 | 한 줄 = | `GROUP BY` |
|---|---|---|
| "카테고리별 매출" | 카테고리 하나 | `p.category` |
| "고객별 주문 수" | 고객 하나 | `c.customer_id` |
| "월별 매출 추이" | 달 하나 | `TO_CHAR(ordered_at,'YYYY-MM')` |
| "총 매출" | 전체 하나 | (없음 — 집계만) |
| "주문 목록" | 주문 하나 | (없음 — 집계 아님) |

**"~별"이라는 말이 나오면 그게 `GROUP BY` 입니다.**

### ③ 조건을 두 종류로 나누기

| 질문 속 표현 | 어디로 |
|---|---|
| "2025년 상반기", "서울 고객", "취소 제외" | `WHERE` — **행** 하나로 판단 가능 |
| "3건 이상 주문한", "매출 100만 원 넘는 카테고리" | `HAVING` — **묶어 봐야** 알 수 있음 |
| "주문이 없는 고객도 포함해서" | `LEFT JOIN` + 조건을 `ON` 으로 |
| "상위 N개" | `ORDER BY` + `LIMIT` |

### ⑤ 검산 — 결과를 믿을 수 있게 만드는 절차

**쿼리를 짜는 것보다 검산이 어렵고, 검산이 실력입니다.**

| 검산법 | 방법 |
|---|---|
| **합계 대조** | 그룹별 합 = 전체 합인가? |
| **행 수 대조** | 조인 전후 `COUNT(*)` 가 예상대로인가? |
| **다른 경로** | 같은 숫자를 다른 쿼리로 구해 비교 |
| **극단값 확인** | 최댓값·최솟값 행을 눈으로 확인 |
| **0과 NULL** | 0건인 대상이 빠지지 않았나? NULL이 조용히 탈락하지 않았나? |

### 문제 1. 전체 요약 — 총 매출·주문 수·평균 주문 금액

```sql
SELECT COUNT(DISTINCT o.order_id)             AS 주문건수,
       SUM(oi.quantity)                       AS 총판매수량,
       SUM(oi.quantity * oi.unit_price)       AS 총매출,
       ROUND(SUM(oi.quantity * oi.unit_price)::numeric
             / COUNT(DISTINCT o.order_id))    AS 평균주문금액
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status <> 'cancelled';
```

```
 주문건수 | 총판매수량 | 총매출  | 평균주문금액
----------+------------+---------+--------------
       28 |         73 | 2796500 |        99875
(1 row)
```

**해석** — 상반기 28건에 279만 원, 건당 약 10만 원입니다.

> **`COUNT(DISTINCT o.order_id)` 를 쓴 이유** — 조인 결과는 47행이 아니라 45행(취소 2건의 상세 2줄 제외)입니다.
> `COUNT(*)` 로 나누면 분모가 45가 되어 평균이 62,144원으로 나옵니다. **분모를 항상 의심하세요.**

### 문제 2. 월별 매출 추이

```sql
SELECT TO_CHAR(o.ordered_at, 'YYYY-MM')       AS 월,
       COUNT(DISTINCT o.order_id)             AS 주문건수,
       SUM(oi.quantity * oi.unit_price)       AS 매출
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE o.status <> 'cancelled'
GROUP BY 1
ORDER BY 1;
```

```
   월    | 주문건수 |  매출
---------+----------+--------
 2025-01 |        3 | 182900
 2025-02 |        5 | 438200
 2025-03 |        5 | 779500
 2025-04 |        5 | 346800
 2025-05 |        5 | 535000
 2025-06 |        5 | 514100
(6 rows)
```

**검산** — `182900+438200+779500+346800+535000+514100 = 2796500` ✅ 문제 1의 총매출과 일치합니다.

**해석** — 3월이 최고점(779,500원), 1월이 최저점입니다. 4월에 절반 이하로 떨어졌다가 5·6월에 회복합니다.
**주문 건수는 5건으로 일정한데 매출만 출렁입니다.** 즉 "몇 명이 샀는가"가 아니라 **"무엇을 샀는가"** 가 변동 원인입니다.
(문제 4에서 확인합니다.)

### 문제 3. 카테고리별 매출과 비중

```sql
SELECT p.category                             AS 카테고리,
       COUNT(DISTINCT o.order_id)             AS 구매주문수,
       SUM(oi.quantity)                       AS 판매수량,
       SUM(oi.quantity * oi.unit_price)       AS 매출,
       ROUND(SUM(oi.quantity * oi.unit_price) * 100.0
             / (SELECT SUM(oi2.quantity * oi2.unit_price)
                FROM order_items oi2
                JOIN orders o2 ON oi2.order_id = o2.order_id
                WHERE o2.status <> 'cancelled'), 2) AS 비중
FROM order_items oi
JOIN orders   o ON oi.order_id   = o.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.category
ORDER BY 매출 DESC;
```

```
 카테고리 | 구매주문수 | 판매수량 |  매출   | 비중
----------+------------+----------+---------+-------
 전자기기 |         15 |       23 | 2085000 | 74.56
 사무용품 |         11 |       34 |  382500 | 13.68
 생활용품 |          8 |       16 |  329000 | 11.76
(3 rows)
```

**검산** — 매출 합 2,796,500 ✅ · 비중 합 `74.56+13.68+11.76 = 100.00` ✅

**해석** — 매출의 **4분의 3이 전자기기**입니다. 반면 판매 수량은 사무용품이 34개로 가장 많습니다.
**"많이 팔리는 것"과 "돈을 버는 것"이 정반대**입니다. 사무용품을 접으면 매출은 13.7%만 줄지만,
그 상품 때문에 방문한 고객이 함께 사는 전자기기까지 잃을 수 있습니다. 이 판단에는 문제 10의 정보가 필요합니다.

> **`(SELECT ...)` 가 `SELECT` 안에 들어갔습니다.** 이것이 서브쿼리이고, 내일([Day 036](day-036.md)) 정식으로 배웁니다.
> 오늘은 "전체 합계를 구해 오는 괄호"로만 이해하면 됩니다.

### 문제 4. 상품별 매출 TOP 5

```sql
SELECT p.name                                 AS 상품,
       p.category                             AS 카테고리,
       SUM(oi.quantity)                       AS 판매수량,
       SUM(oi.quantity * oi.unit_price)       AS 매출
FROM order_items oi
JOIN orders   o ON oi.order_id   = o.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.product_id, p.name, p.category
ORDER BY 매출 DESC
LIMIT 5;
```

```
      상품      | 카테고리 | 판매수량 |  매출
----------------+----------+----------+---------
 27인치모니터   | 전자기기 |        5 | 1295000
 기계식키보드   | 전자기기 |        4 |  356000
 무선마우스     | 전자기기 |        8 |  200000
 노트북거치대   | 사무용품 |        5 |  170000
 블루투스이어폰 | 전자기기 |        2 |  158000
(5 rows)
```

**해석** — 모니터 한 상품이 **전체 매출의 46.3%**(1,295,000 / 2,796,500)를 차지합니다.
문제 2에서 본 월별 출렁임의 정체가 이것입니다. **모니터가 팔린 달이 매출이 좋은 달**입니다.

확인해 봅니다.

```sql
SELECT TO_CHAR(o.ordered_at, 'YYYY-MM') AS 월, SUM(oi.quantity) AS 모니터판매수량
FROM order_items oi
JOIN orders o ON oi.order_id = o.order_id
WHERE oi.product_id = 3 AND o.status <> 'cancelled'
GROUP BY 1 ORDER BY 1;
```

```
   월    | 모니터판매수량
---------+----------------
 2025-02 |              1
 2025-03 |              2
 2025-05 |              1
 2025-06 |              1
(4 rows)
```

**1월과 4월에만 모니터가 안 팔렸습니다.** 그리고 그 두 달이 정확히 매출 최저 1·2위입니다.
**"매출이 왜 떨어졌나"의 답이 나왔습니다** — 특정 고가 상품 1개에 매출이 종속돼 있습니다.

> 이것이 오늘 배우는 **분석의 형태**입니다. 숫자 하나를 뽑는 것이 아니라,
> **이상한 곳을 발견 → 가설 → 확인 쿼리 → 결론** 으로 이어지는 사슬을 만드는 것입니다.

### 문제 5. 고객별 구매액 TOP 5

```sql
SELECT c.name                                 AS 고객,
       c.grade                                AS 등급,
       c.city                                 AS 도시,
       COUNT(DISTINCT o.order_id)             AS 주문수,
       SUM(oi.quantity * oi.unit_price)       AS 구매액
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
WHERE o.status <> 'cancelled'
GROUP BY c.customer_id, c.name, c.grade, c.city
ORDER BY 구매액 DESC
LIMIT 5;
```

```
  고객  | 등급   | 도시 | 주문수 | 구매액
--------+--------+------+--------+--------
 윤도현 | gold   | 서울 |      3 | 682000
 최수아 | gold   | 대구 |      3 | 621000
 이서연 | silver | 서울 |      5 | 464900
 김민수 | gold   | 서울 |      5 | 299200
 정우진 | silver | 서울 |      3 | 237000
(5 rows)
```

**해석** — 상위 5명이 230만 원, **전체 매출의 82.4%** 입니다. 10명의 구매 고객 중 절반이 대부분을 만듭니다.
등급 제도는 대체로 맞게 작동하고 있습니다(gold 3명이 모두 상위 4위 안). 다만 **이서연 님(silver)이 김민수 님(gold)보다 많이 씁니다.**
등급 기준을 재검토할 근거입니다.

### 문제 6. 도시별 매출과 고객당 평균

```sql
SELECT c.city                                          AS 도시,
       COUNT(DISTINCT c.customer_id)                   AS 고객수,
       COALESCE(SUM(oi.quantity * oi.unit_price), 0)   AS 매출,
       ROUND(COALESCE(SUM(oi.quantity * oi.unit_price), 0)::numeric
             / COUNT(DISTINCT c.customer_id))          AS 고객당평균
FROM customers c
LEFT JOIN orders      o  ON c.customer_id = o.customer_id
                        AND o.status <> 'cancelled'
LEFT JOIN order_items oi ON o.order_id    = oi.order_id
GROUP BY c.city
ORDER BY 매출 DESC;
```

```
 도시 | 고객수 |  매출   | 고객당평균
------+--------+---------+------------
 서울 |      5 | 1683100 |     336620
 대구 |      1 |  621000 |     621000
 부산 |      2 |  197800 |      98900
 인천 |      2 |  126000 |      63000
 대전 |      1 |  112000 |     112000
 광주 |      1 |   56600 |      56600
(6 rows)
```

**검산** — 고객수 합 `5+1+2+2+1+1 = 12` ✅ (전체 고객 12명) · 매출 합 2,796,500 ✅

**해석** — 서울이 매출 60%를 차지하지만, **고객당 평균은 대구가 62만 원으로 1위**입니다.
다만 대구는 고객이 1명뿐이라 **이 숫자는 통계가 아니라 개인**입니다. 최수아 님 한 명이 그만 쓴 것입니다.
표본 수가 1~2인 그룹의 평균으로 의사결정을 하면 안 됩니다.

> **`LEFT JOIN` 을 쓴 이유** — 인천의 신유진 님은 주문이 0건입니다. `INNER JOIN` 이면 인천 고객수가 1명으로 나와
> 고객당 평균이 126,000원으로 **두 배 부풀어 오릅니다.** 분모가 되는 대상은 항상 `LEFT JOIN` 으로 확보하세요.

### 문제 7. 등급별 인당 평균 구매액

```
 bronze |      4 |   210400 |    52600
 미지정 |      1 |        0 |        0
(4 rows)
```

## ⑥ 확인 문제

**1.** "카테고리별로 매출이 100만 원을 넘는 카테고리만, 매출 순으로" 를 5단계 절차에 따라 SQL로 옮기세요. 각 단계에서 무엇을 결정했는지도 쓰세요.

<details>
<summary>답 보기</summary>

| 단계 | 결정 |
|---|---|
| ① 답의 모양 | `카테고리 | 매출` — 한 줄 = 카테고리 하나 → `GROUP BY p.category` |
| ② 테이블 | 카테고리는 `products`, 금액은 `order_items`, 취소 여부는 `orders` → 3개 조인 |
| ③ 조건 | 취소 제외 = **행 조건**(`WHERE`) / 100만 원 초과 = **그룹 조건**(`HAVING`) |
| ④ 조립 | 아래 |
| ⑤ 검산 | 걸러지기 전 전체 매출 합이 2,796,500인지 확인 |

```sql
SELECT p.category AS 카테고리,
       SUM(oi.quantity * oi.unit_price) AS 매출
FROM order_items oi
JOIN orders   o ON oi.order_id   = o.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.status <> 'cancelled'
GROUP BY p.category
HAVING SUM(oi.quantity * oi.unit_price) > 1000000
ORDER BY 매출 DESC;
```

```
 카테고리 |  매출
----------+---------
 전자기기 | 2085000
(1 row)
```

**핵심은 ③입니다.** "매출 100만 원 초과"는 **묶어 봐야 알 수 있는 조건**이므로 `HAVING` 입니다.
`WHERE SUM(...) > 1000000` 은 `aggregate functions are not allowed in WHERE` 에러가 납니다.
</details>

**2.** 아래 쿼리로 "고객당 평균 구매액"을 구했더니 279,650원이 나왔습니다. 문제 6의 도시별 합계로 계산하면 2,796,500 / 12 = 233,042원입니다. 어느 쪽이 맞나요?

```sql
SELECT ROUND(AVG(t.구매액)) FROM (
    SELECT c.customer_id, SUM(oi.quantity * oi.unit_price) AS 구매액
    FROM customers c
    JOIN orders o       ON c.customer_id = o.customer_id
    JOIN order_items oi ON o.order_id    = oi.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY c.customer_id
) t;
```

<details>
<summary>답 보기</summary>

**둘 다 맞습니다. 질문이 다릅니다.**

| 값 | 분모 | 정확한 이름 |
|---|---|---|
| 279,650 | **10** (구매한 고객 수) | "**구매 고객** 1인당 평균 구매액" |
| 233,042 | **12** (전체 고객 수) | "**전체 회원** 1인당 평균 구매액" |

`INNER JOIN` 을 썼기 때문에 주문이 0건인 오세훈·신유진 님이 분모에서 빠져 279,650이 나왔습니다.
2,796,500 / 10 = 279,650 ✅

**어느 쪽을 써야 하나** — 목적에 따릅니다.

- **마케팅 효율**(광고비 대비 회수)을 볼 때는 **전체 회원 기준(12)** 이 맞습니다. 돈은 12명 모으는 데 들었으니까요.
- **구매 행태**(한 번 사면 얼마 쓰나)를 볼 때는 **구매 고객 기준(10)** 이 맞습니다.

**틀린 것은 "어느 기준인지 모르고 쓰는 것"입니다.**
리포트에는 반드시 `분모 = 구매 고객 10명` 처럼 적으세요. 두 숫자가 20% 차이 나고, 이 정도면 의사결정이 바뀝니다.

전체 회원 기준으로 구하려면 `LEFT JOIN` 을 쓰고 `COALESCE` 로 0을 채웁니다.

```sql
SELECT ROUND(AVG(t.구매액)) FROM (
    SELECT c.customer_id, COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS 구매액
    FROM customers c
    LEFT JOIN orders o       ON c.customer_id = o.customer_id AND o.status <> 'cancelled'
    LEFT JOIN order_items oi ON o.order_id    = oi.order_id
    GROUP BY c.customer_id
) t;
--  233042
```
</details>

**3.** 문제 8에서 "6월 주문 5건이 모두 배송 완료가 아니다"라는 결과를 보고 팀장이 "6월에 배송 사고가 났나?"라고 묻습니다. 어떻게 답해야 하며, 그 근거를 무슨 쿼리로 보여 주겠습니까?

<details>
<summary>답 보기</summary>

**답** — 배송 사고가 아니라 **데이터가 6월 25일까지만 있어서 생긴 착시**입니다.
6월 주문은 아직 배송 완료로 바뀔 시간이 없었을 뿐입니다. 이런 현상을 **절단(censoring)** 이라고 합니다.

**근거 쿼리 ① 데이터의 끝 확인**

```sql
SELECT MIN(ordered_at) AS 최초주문, MAX(ordered_at) AS 최종주문 FROM orders;
```

```
  최초주문  |  최종주문
------------+------------
 2025-01-05 | 2025-06-25
(1 row)
```

**근거 쿼리 ② 월별 상태 분포 — 최근일수록 미완료가 많음**

```sql
SELECT TO_CHAR(ordered_at, 'YYYY-MM') AS 월,
       COUNT(*) AS 전체,
       COUNT(*) FILTER (WHERE status = 'delivered') AS 배송완료,
       COUNT(*) FILTER (WHERE status IN ('paid','shipped')) AS 진행중
FROM orders GROUP BY 1 ORDER BY 1;
```

```
   월    | 전체 | 배송완료 | 진행중
---------+------+----------+--------
 2025-01 |    4 |        3 |      0
 2025-02 |    5 |        5 |      0
 2025-03 |    6 |        5 |      0
 2025-04 |    5 |        4 |      1
 2025-05 |    5 |        4 |      1
 2025-06 |    5 |        0 |      5
(6 rows)
```

**진행중 건수가 4월 1건 → 5월 1건 → 6월 5건으로 증가**합니다.
사고라면 특정 달만 튀어야 하는데, **최근으로 갈수록 늘어나는 계단 모양**은 절단의 전형적인 신호입니다.

**교훈** — "최근 데이터가 이상하다"는 보고를 받으면 **데이터 수집 시점부터 확인**하세요.
[Day 043](day-043.md)의 증분 적재와 [Day 044](day-044.md)의 품질 검증에서 이 문제를 다시 다룹니다.
모델 학습에서도 마찬가지입니다. 최근 라벨이 아직 안 붙은 데이터를 "부정 사례"로 학습시키는 사고가 여기서 나옵니다.
</details>

## 주간 퀴즈 7 — W07 (SQL 기초)

답은 아래에 접혀 있습니다. **먼저 다 풀고** 펼치세요.

1. `WHERE grade <> 'gold'` 가 등급 미입력 고객을 빼놓는 이유는?
2. SQL의 실행 순서 7단계를 쓰시오.
3. `COUNT(*)` 와 `COUNT(phone)` 의 차이는?
4. `WHERE` 와 `HAVING` 은 각각 무엇을 거르는가?
5. `INNER JOIN` 대신 `LEFT JOIN` 을 써야 하는 상황을 하나 드시오.
6. `LEFT JOIN` 의 조건을 `WHERE` 에 쓰면 무슨 일이 생기는가?
7. 팬아웃(조인 중복)이란 무엇이며 어떻게 진단하는가?
8. `COUNT(*) * 100 / COUNT(*)` 대신 `100.0` 을 써야 하는 이유는?
9. `LIMIT` 을 쓸 때 `ORDER BY` 가 반드시 필요한 이유는?
10. 날짜 구간을 `BETWEEN` 대신 `>= AND <` 로 쓰는 이유는?

<details>
<summary>정답 보기</summary>

1. `NULL <> 'gold'` 의 결과는 참이 아니라 `NULL`(모름)이고, `WHERE` 는 **참인 행만** 통과시키기 때문. → `IS DISTINCT FROM` 사용
2. `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`
3. `COUNT(*)` 는 **행** 수, `COUNT(phone)` 은 `phone` 이 **NULL이 아닌** 행 수 (12 vs 9)
4. `WHERE` 는 **행**을(그룹 만들기 전), `HAVING` 은 **그룹**을(집계 후)
5. "주문이 0건인 고객도 목록에 보여야 할 때" — 이탈 분석·미구매 회원·팔리지 않은 상품 등
6. 짝이 없는 행의 오른쪽 열은 `NULL` 이라 조건에 걸려 탈락 → **사실상 `INNER JOIN`** 이 됨
7. 1:N 조인으로 왼쪽 행이 복제되어 건수·금액이 부풀어 오르는 현상. **조인 단계마다 `COUNT(*)`** 를 찍어 진단
8. 정수 ÷ 정수는 소수점이 잘리는 **정수 나눗셈**이라 비율이 0이나 6 같은 값이 됨
9. DB는 행의 순서를 보장하지 않아 "아무 N개"가 나오고, 실행할 때마다 달라질 수 있음
10. `timestamp` 에서 `BETWEEN a AND '2025-05-31'` 은 `'2025-05-31 00:00:00'` 으로 해석되어 **마지막 날의 데이터가 통째로 누락**됨

**채점** — 8개 이상 맞으면 W08로 진행해도 좋습니다.
6개 이하라면 [Day 032](day-032.md)의 NULL 절과 [Day 034](day-034.md)의 팬아웃 절을 다시 읽으세요. **이 둘이 W08~W09의 전제**입니다.
</details>
