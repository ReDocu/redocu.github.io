## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `SELECT` · `FROM` · `WHERE` · `ORDER BY` · `LIMIT` 으로 원하는 행과 열만 골라낼 수 있다.
- 비교·논리 연산자와 `BETWEEN` · `IN` · `LIKE` 로 조건을 표현할 수 있다.
- **`NULL` 이 다른 값과 다르게 동작하는 이유**를 설명하고 `IS NULL` · `COALESCE` 로 다룰 수 있다.
- SQL이 **어떤 순서로 실행되는지** 알고, 그 순서 때문에 생기는 에러를 스스로 해결할 수 있다.

## ② 왜 필요한가

어제 만든 `shop` 데이터베이스에는 행이 101개(12+12+30+47) 있습니다. 눈으로 다 볼 수 있는 양입니다.
하지만 실무 테이블은 **수천만 행**입니다. `SELECT * FROM orders;` 를 치는 순간 터미널이 몇 분간 멈춥니다.

그래서 SQL의 첫 번째 기술은 **"필요한 것만 가져오기"** 입니다.

```
 SELECT *      FROM orders;                      →  3천만 행, 8GB, 3분
 SELECT order_id, ordered_at FROM orders
   WHERE ordered_at >= '2025-06-01' LIMIT 100;    →  100행, 40KB, 0.01초
```

같은 답을 얻는데 걸리는 시간이 **1만 배** 차이 납니다.

[Day 022](../01-python-data/day-022.md)에서 Pandas로 하던 일과 대응됩니다. 하는 일은 같고, **하는 장소가 다릅니다.**

| 하는 일 | Pandas | SQL |
|---|---|---|
| 열 고르기 | `df[["name", "price"]]` | `SELECT name, price` |
| 행 고르기 | `df[df.price >= 50000]` | `WHERE price >= 50000` |
| 정렬 | `df.sort_values("price", ascending=False)` | `ORDER BY price DESC` |
| 앞 몇 개 | `df.head(3)` | `LIMIT 3` |

결정적인 차이는 **Pandas는 전부 읽은 뒤 거르고, SQL은 거른 뒤 보낸다**는 점입니다.
그래서 실무 패턴은 **"DB에서 크게 줄여서 가져오고, Pandas로 마무리"** 입니다.

## ③ 개념 설명

### 기본 뼈대

```sql
SELECT   열 목록          -- 무엇을 보여줄까
FROM     테이블           -- 어디에서
WHERE    조건             -- 어떤 행만
ORDER BY 열 [ASC|DESC]    -- 어떤 순서로
LIMIT    개수;            -- 몇 개만
```

이 다섯 줄이 오늘의 전부입니다. **순서를 바꿔 쓰면 문법 에러**가 납니다.

### 작성 순서 ≠ 실행 순서 ★

오늘 가장 중요한 개념입니다. SQL은 **쓰는 순서와 실행되는 순서가 다릅니다.**

```
쓰는 순서 :  SELECT → FROM → WHERE → ORDER BY → LIMIT
실행 순서 :  FROM   → WHERE → SELECT → ORDER BY → LIMIT
             ①        ②       ③        ④          ⑤
```

`SELECT` 가 세 번째로 실행된다는 사실이 두 가지 결과를 낳습니다.

| 결과 | 예 |
|---|---|
| `WHERE` 에서는 **별칭(AS)을 쓸 수 없다** | `SELECT price*2 AS d FROM products WHERE d > 100` ❌ — `WHERE` 실행 시점엔 `d` 가 아직 없음 |
| `ORDER BY` 에서는 **별칭을 쓸 수 있다** | `SELECT price*2 AS d FROM products ORDER BY d` ✅ — `SELECT` 가 이미 끝났음 |

이 규칙 하나로 초보자 에러의 절반이 설명됩니다. 외우지 말고 **실행 순서를 떠올리세요.**

### 열 고르기

| 쓰는 법 | 뜻 |
|---|---|
| `SELECT *` | 모든 열 (**연습용. 실무 코드에는 쓰지 않습니다**) |
| `SELECT name, price` | 지정한 열만 |
| `SELECT name AS 상품명` | 결과 열 이름 바꾸기 (별칭) |
| `SELECT DISTINCT category` | 중복 제거 |
| `SELECT price * 0.9` | 계산식도 열이 됩니다 |

> **`SELECT *` 를 실무에서 쓰지 않는 이유** — 나중에 누군가 테이블에 열을 추가하면
> 내 코드가 갑자기 다른 결과를 받습니다. 필요한 열을 **명시**하면 그런 일이 없습니다.

### 비교·논리 연산자

| 연산자 | 뜻 | 예 |
|---|---|---|
| `=` `<>` (또는 `!=`) | 같다 / 다르다 | `category = '전자기기'` |
| `>` `>=` `<` `<=` | 크다 / 작다 | `price >= 50000` |
| `AND` `OR` `NOT` | 그리고 / 또는 / 부정 | `price >= 50000 AND stock > 0` |
| `BETWEEN a AND b` | a 이상 b 이하 (**양끝 포함**) | `price BETWEEN 10000 AND 30000` |
| `IN (...)` | 목록 중 하나 | `category IN ('사무용품', '생활용품')` |
| `LIKE` | 문자열 패턴 | `name LIKE '무%'` |
| `IS NULL` / `IS NOT NULL` | 값이 없다 / 있다 | `phone IS NULL` |

**문자열은 작은따옴표(`'`)** 로 감쌉니다. 큰따옴표(`"`)는 **열 이름**을 감쌀 때 쓰는 것이라 뜻이 완전히 다릅니다.

```sql
WHERE category = '전자기기'    -- ✅ 값
WHERE category = "전자기기"    -- ❌ ERROR: column "전자기기" does not exist
```

`LIKE` 의 와일드카드는 두 개뿐입니다.

| 기호 | 뜻 | 예 |
|---|---|---|
| `%` | 0글자 이상 아무거나 | `'무%'` → 무선마우스, 무드등 |
| `_` | 정확히 1글자 | `'_4%'` → A4용지500매 |

대소문자를 구분하지 않으려면 `ILIKE` 를 씁니다 (PostgreSQL 전용).

### `NULL` — 오늘의 핵심 ★

`NULL` 은 "0" 도 "빈 문자열" 도 아닙니다. **"값이 무엇인지 모른다"** 는 뜻입니다.

모르는 값끼리 비교하면 답은 참도 거짓도 아닌 **"모름"** 입니다. SQL은 이것을 `NULL` 로 돌려줍니다.

| 식 | 결과 | 이유 |
|---|---|---|
| `NULL = NULL` | `NULL` | 모르는 값 두 개가 같은지도 모릅니다 |
| `NULL <> 'gold'` | `NULL` | 마찬가지 |
| `NULL + 1` | `NULL` | 모르는 값에 1을 더해도 모릅니다 |
| `'a' \|\| NULL` | `NULL` | 문자열 이어붙이기도 마찬가지 |

그리고 **`WHERE` 는 결과가 참(true)인 행만 통과시킵니다.** `NULL`(모름)은 통과하지 못합니다.

```
WHERE grade <> 'gold'   →  NULL 인 행은 결과가 NULL → 탈락 → 결과에서 사라짐
```

**"조건에서 뺐다고 생각한 행이 아니라, 아무 조건에도 안 걸린 행이 조용히 사라집니다."**
이것이 SQL에서 데이터를 잃어버리는 가장 흔한 경로입니다.

해결책은 두 개입니다.

| 도구 | 하는 일 | 예 |
|---|---|---|
| `IS NULL` / `IS NOT NULL` | NULL 여부를 **제대로** 판정 | `WHERE grade IS NULL` |
| `COALESCE(a, b)` | `a` 가 NULL이면 `b` 를 대신 씀 | `COALESCE(grade, '미지정')` |

```sql
-- ❌ gold가 아닌 고객: 등급 미입력 고객이 빠짐 (8명)
WHERE grade <> 'gold'

-- ✅ 등급 미입력도 포함 (9명)
WHERE grade IS DISTINCT FROM 'gold'
--   또는
WHERE grade <> 'gold' OR grade IS NULL
```

> `IS DISTINCT FROM` 은 **NULL을 하나의 값처럼 취급해 비교**하는 연산자입니다.
> `<>` 의 NULL 안전 버전이라고 생각하면 됩니다.

### 정렬과 자르기

| 구문 | 뜻 |
|---|---|
| `ORDER BY price` | 오름차순 (기본값 `ASC`) |
| `ORDER BY price DESC` | 내림차순 |
| `ORDER BY category, price DESC` | 카테고리로 먼저, 같으면 가격 내림차순 |
| `ORDER BY price DESC NULLS LAST` | NULL을 뒤로 (PostgreSQL은 `DESC` 시 NULL이 **앞**에 옵니다) |
| `LIMIT 5` | 앞에서 5개 |
| `LIMIT 5 OFFSET 10` | 11번째부터 5개 (페이징) |

> **`ORDER BY` 없는 `LIMIT` 은 의미가 없습니다.** DB는 행 순서를 보장하지 않습니다.
> "아무거나 5개"가 나올 뿐이고, 같은 쿼리가 다음에 다른 결과를 줄 수도 있습니다.

### Step 2. `WHERE` — 행 고르기

```
shop=# SELECT name, price FROM products WHERE price >= 50000;
      name      | price
----------------+--------
 기계식키보드   |  89000
 27인치모니터   | 259000
 블루투스이어폰 |  79000
(3 rows)
```

조건 두 개를 `AND` 로 묶습니다. **재고가 있는 5만 원 이상 상품**입니다.

```
shop=# SELECT name, price, stock FROM products
shop-# WHERE price >= 50000 AND stock > 0;
     name     | price  | stock
--------------+--------+-------
 기계식키보드 |  89000 |    45
 27인치모니터 | 259000 |    18
(2 rows)
```

바로 앞 쿼리는 3행이었는데 2행이 됐습니다. 블루투스이어폰이 `stock = 0` 이라 빠진 것입니다.
**조건을 하나 추가할 때마다 `(N rows)` 가 얼마나 줄었는지 확인하는 습관**을 들이세요.
줄어든 개수가 예상과 다르면, 거기에 오늘의 주제인 `NULL` 이 숨어 있는 경우가 많습니다.

`AND` 와 `OR` 를 섞을 때는 **괄호를 반드시** 칩니다. `AND` 가 `OR` 보다 먼저 계산되기 때문입니다.

```
shop=# SELECT name, category, price FROM products
shop-# WHERE (category = '사무용품' OR category = '생활용품') AND price >= 20000;
     name     | category | price
--------------+----------+-------
 노트북거치대 | 사무용품 | 34000
 무드등       | 생활용품 | 32000
 데스크매트   | 사무용품 | 22000
(3 rows)
```

괄호를 빼면 뜻이 완전히 달라집니다. (`사무용품 전부` **또는** `2만원 이상 생활용품`)

### Step 5. 날짜 조건

`orders.ordered_at` 은 `date` 타입이라 문자열처럼 따옴표로 쓰되 **날짜로 비교**됩니다.

```
shop=# SELECT order_id, customer_id, ordered_at, status FROM orders
shop-# WHERE ordered_at >= '2025-06-01'
shop-# ORDER BY ordered_at;
 order_id | customer_id | ordered_at |  status
----------+-------------+------------+---------
       26 |           8 | 2025-06-03 | paid
       27 |           9 | 2025-06-09 | paid
       28 |           5 | 2025-06-15 | paid
       29 |           4 | 2025-06-20 | shipped
       30 |           2 | 2025-06-25 | paid
(5 rows)
```

기간을 자를 때는 `BETWEEN` 보다 **`>= 시작 AND < 다음달1일`** 이 안전합니다.
시각(`timestamp`)이 붙는 순간 `BETWEEN '2025-05-01' AND '2025-05-31'` 은 **5월 31일 오후 데이터를 통째로 놓치기** 때문입니다.

```
shop=# SELECT order_id, ordered_at, status FROM orders
shop-# WHERE ordered_at >= '2025-05-01' AND ordered_at < '2025-06-01'
shop-# ORDER BY ordered_at;
 order_id | ordered_at |  status
----------+------------+-----------
       21 | 2025-05-06 | delivered
       22 | 2025-05-13 | delivered
       23 | 2025-05-19 | delivered
       24 | 2025-05-24 | shipped
       25 | 2025-05-29 | delivered
(5 rows)
```

**이 습관은 [Day 043](day-043.md)의 증분 적재에서 그대로 다시 나옵니다.** 지금 몸에 붙여 두세요.

### Step 6. `NULL` 직접 확인하기 ★

먼저 NULL이 어떤 값인지 눈으로 봅니다. psql은 NULL을 **빈칸**으로 표시합니다.

```
shop=# SELECT customer_id, name, grade, phone FROM customers ORDER BY customer_id;
 customer_id |  name  | grade  |     phone
-------------+--------+--------+---------------
           1 | 김민수 | gold   | 010-1234-0001
           2 | 이서연 | silver | 010-1234-0002
           3 | 박지훈 | bronze |
           4 | 최수아 | gold   | 010-1234-0004
           5 | 정우진 | silver | 010-1234-0005
           6 | 강하은 | bronze |
           7 | 조은비 | silver | 010-1234-0007
           8 | 윤도현 | gold   | 010-1234-0008
           9 | 임채원 | bronze | 010-1234-0009
          10 | 한지민 | silver |
          11 | 오세훈 | bronze | 010-1234-0011
          12 | 신유진 |        | 010-1234-0012

```

빈칸이 정말 NULL인지, 아니면 공백 문자인지 구분하려면 `\pset null` 로 표시를 바꿉니다.

```
shop=# \pset null '(NULL)'
Null display is "(NULL)".
shop=# SELECT name, grade FROM customers WHERE customer_id = 12;
  name  | grade
--------+--------
 신유진 | (NULL)
(1 row)
```

이제 **함정**을 직접 만나 봅니다.

```
shop=# SELECT COUNT(*) FROM customers;
 count
-------
    12
(1 row)

shop=# SELECT COUNT(*) FROM customers WHERE grade = 'gold';
 count
-------
     3
(1 row)

shop=# SELECT COUNT(*) FROM customers WHERE grade <> 'gold';
 count
-------
     8
(1 row)
```

**3 + 8 = 11.** 12명인데 한 명이 사라졌습니다. 등급이 NULL인 신유진 님입니다.

```
shop=# SELECT name, grade FROM customers WHERE grade IS NULL;
  name  | grade
--------+--------
 신유진 | (NULL)
(1 row)
```

NULL까지 포함하려면 이렇게 씁니다.

```
shop=# SELECT COUNT(*) FROM customers WHERE grade IS DISTINCT FROM 'gold';
 count
-------
     9
(1 row)
```

**3 + 9 = 12.** 이제 맞습니다.

`COALESCE` 로 표시용 기본값을 채웁니다.

```
shop=# SELECT name, COALESCE(grade, '미지정') AS grade, COALESCE(phone, '연락처없음') AS phone
shop-# FROM customers
shop-# WHERE grade IS NULL OR phone IS NULL
shop-# ORDER BY customer_id;
  name  |  grade  |   phone
--------+---------+------------
 박지훈 | bronze  | 연락처없음
 강하은 | bronze  | 연락처없음
 한지민 | silver  | 연락처없음
 신유진 | 미지정  | 010-1234-0012
(4 rows)
```

정렬에서도 NULL은 특별합니다. PostgreSQL은 **오름차순일 때 NULL을 맨 뒤에, 내림차순일 때 맨 앞에** 둡니다.

```
shop=# SELECT name, grade FROM customers ORDER BY grade DESC LIMIT 3;
  name  | grade
--------+--------
 신유진 | (NULL)
 이서연 | silver
 정우진 | silver
(3 rows)

shop=# SELECT name, grade FROM customers ORDER BY grade DESC NULLS LAST LIMIT 3;
  name  | grade
--------+--------
 이서연 | silver
 정우진 | silver
 조은비 | silver
(3 rows)
```

"등급이 가장 높은 고객"을 뽑는 대시보드가 **NULL 고객을 1등으로 보여주는 사고**가 여기서 납니다.

## ⑤ 자주 하는 실수

### `column "전자기기" does not exist`

```
shop=# SELECT * FROM products WHERE category = "전자기기";
ERROR:  column "전자기기" does not exist
LINE 1: SELECT * FROM products WHERE category = "전자기기";
                                                ^
```

**원인** — 큰따옴표를 썼습니다. SQL에서 큰따옴표는 **열/테이블 이름**을 감싸는 기호입니다.
**해결** — 값은 **작은따옴표**로. `category = '전자기기'`

### `column "d" does not exist` — 별칭을 `WHERE` 에서 씀

```
shop=# SELECT name, price * 0.9 AS d FROM products WHERE d > 50000;
ERROR:  column "d" does not exist
LINE 1: ... price * 0.9 AS d FROM products WHERE d > 50000;
                                                 ^
```

**원인** — `WHERE`(②)가 `SELECT`(③)보다 **먼저** 실행됩니다. 그 시점에 별칭 `d` 는 아직 존재하지 않습니다.
**해결** — `WHERE` 에는 식을 그대로 씁니다. `ORDER BY` 에서는 별칭을 써도 됩니다.

```sql
SELECT name, price * 0.9 AS d FROM products
WHERE price * 0.9 > 50000     -- 식을 그대로
ORDER BY d DESC;              -- 여기선 별칭 OK
```

### 조건에 맞는 행이 예상보다 적습니다 (NULL)

```
shop=# SELECT COUNT(*) FROM customers WHERE grade <> 'gold';
 count
-------
     8
```

**원인** — `grade` 가 NULL인 행은 `NULL <> 'gold'` → `NULL` → **참이 아니므로 탈락**합니다.
**해결** — `WHERE grade IS DISTINCT FROM 'gold'` 또는 `WHERE grade <> 'gold' OR grade IS NULL`

**점검 습관** — 조건을 나눠 세었을 때 **합이 전체와 맞는지** 확인하세요. 안 맞으면 그 열에 NULL이 있습니다.

### `WHERE phone = NULL` 로 아무것도 안 나옵니다

```
shop=# SELECT name FROM customers WHERE phone = NULL;
 name
------
(0 rows)
```

**원인** — 에러도 안 나고 **0행**이 나옵니다. `phone = NULL` 은 항상 `NULL`(모름)이라 어떤 행도 통과하지 못합니다.
**해결** — `WHERE phone IS NULL`. **NULL 비교에는 `=` 를 절대 쓰지 않습니다.**

### `syntax error at or near "ORDER"` — 절 순서를 바꿈

```
shop=# SELECT name FROM products ORDER BY price WHERE price > 10000;
ERROR:  syntax error at or near "WHERE"
LINE 1: SELECT name FROM products ORDER BY price WHERE price > 10000;
                                                 ^
```

**원인** — `WHERE` 는 반드시 `ORDER BY` **앞**에 옵니다.
**해결** — `SELECT → FROM → WHERE → ORDER BY → LIMIT` 순서를 지킵니다.

### `AND` / `OR` 를 괄호 없이 섞음

```sql
-- 의도: (사무용품 또는 생활용품) 중 2만원 이상
WHERE category = '사무용품' OR category = '생활용품' AND price >= 20000
-- 실제 해석: 사무용품 전부 OR (생활용품이면서 2만원 이상)  →  6행
```

**원인** — `AND` 가 `OR` 보다 우선순위가 높습니다.
**해결** — **`OR` 를 쓸 때는 무조건 괄호**. 습관으로 만드세요. 에러가 안 나고 결과만 틀리는 종류의 버그입니다.

### `LIMIT` 만 쓰고 `ORDER BY` 를 안 씀

```sql
SELECT * FROM orders LIMIT 5;   -- "아무 5개". 다음에 실행하면 다를 수 있음
```

**원인** — DB는 행의 물리적 순서를 보장하지 않습니다.
**해결** — `LIMIT` 을 쓸 땐 **항상 `ORDER BY` 를 짝으로**. 정렬 기준이 같은 값일 때를 대비해 `ORDER BY price DESC, product_id` 처럼 **타이브레이커**까지 넣으면 완벽합니다.

### `SELECT` 결과가 끝없이 스크롤됩니다

```
--More--
```

**원인** — 결과가 화면보다 길면 psql이 페이저(pager)를 켭니다.
**해결** — `q` 를 눌러 빠져나옵니다. 아예 끄려면 `\pset pager off`.

## ⑥ 확인 문제

**1.** 아래 두 쿼리의 결과 행 수를 더하면 12가 되어야 할 것 같은데, 실제로는 11입니다. 왜 그런가요? 12가 되게 고치세요.

```sql
SELECT COUNT(*) FROM customers WHERE grade = 'gold';     -- 3
SELECT COUNT(*) FROM customers WHERE grade <> 'gold';    -- 8
```

<details>
<summary>답 보기</summary>

`grade` 가 `NULL` 인 고객(신유진)이 **양쪽 어디에도 안 들어가기** 때문입니다.

- `NULL = 'gold'` → `NULL` → 참이 아님 → 탈락
- `NULL <> 'gold'` → `NULL` → 참이 아님 → 탈락

`WHERE` 는 **결과가 참(true)인 행만** 통과시킵니다. `NULL`(모름)은 참이 아닙니다.

고치는 방법 (셋 중 아무거나):

```sql
SELECT COUNT(*) FROM customers WHERE grade IS DISTINCT FROM 'gold';   -- 9
SELECT COUNT(*) FROM customers WHERE grade <> 'gold' OR grade IS NULL; -- 9
SELECT COUNT(*) FROM customers WHERE COALESCE(grade, '') <> 'gold';    -- 9
```

**실무에서의 의미** — 이 함정은 "결제 실패 건수"나 "이탈 고객 수" 같은 지표를 **조용히 적게** 만듭니다.
에러가 안 나므로 몇 달간 아무도 모릅니다. 조건을 나눠 셌을 때 **합이 전체와 맞는지 확인**하는 것이 유일한 방어입니다.
</details>

**2.** 아래 쿼리는 에러가 납니다. 원인을 SQL 실행 순서로 설명하고, 두 가지 방법으로 고치세요.

```sql
SELECT name, price * quantity AS 금액
FROM order_items
WHERE 금액 > 100000;
```

<details>
<summary>답 보기</summary>

**원인** — 실행 순서가 `FROM`(①) → `WHERE`(②) → `SELECT`(③) 이기 때문입니다.
`WHERE` 가 돌아갈 때 별칭 `금액` 은 아직 만들어지지 않았습니다. (`SELECT` 는 그다음 차례)

> 참고로 이 쿼리에는 또 하나의 문제가 있습니다. `order_items` 에는 `name` · `price` 열이 없습니다.
> 실제 열은 `unit_price` 이고, 상품 이름을 함께 보려면 [Day 034](day-034.md)의 `JOIN` 이 필요합니다.

**해결 ① 식을 그대로 반복해서 쓴다**

```sql
SELECT order_id, product_id, quantity * unit_price AS 금액
FROM order_items
WHERE quantity * unit_price > 100000
ORDER BY 금액 DESC;
```

**해결 ② 서브쿼리로 감싸 별칭을 먼저 만든다** ([Day 036](day-036.md)에서 정식으로 배웁니다)

```sql
SELECT * FROM (
    SELECT order_id, product_id, quantity * unit_price AS 금액
    FROM order_items
) t
WHERE 금액 > 100000
ORDER BY 금액 DESC;
```

`ORDER BY` 는 `SELECT` **다음**에 실행되므로 별칭을 그대로 써도 됩니다.
</details>

**3.** "2025년 5월에 들어온 주문"을 조회하는 두 가지 방식이 있습니다. 어느 쪽이 안전하며, 그 이유는 무엇인가요?

```sql
-- A
WHERE ordered_at BETWEEN '2025-05-01' AND '2025-05-31'
-- B
WHERE ordered_at >= '2025-05-01' AND ordered_at < '2025-06-01'
```

<details>
<summary>답 보기</summary>

**B가 안전합니다.**

지금 `orders.ordered_at` 은 `date` 타입이라 두 쿼리 결과가 같습니다(둘 다 5행).
하지만 실무 테이블은 대부분 **시각까지 있는 `timestamp`** 입니다. 그 순간 A가 깨집니다.

```
'2025-05-31 14:30:00' 인 주문
  A: BETWEEN '2025-05-01' AND '2025-05-31'
     →  '2025-05-31' 은 '2025-05-31 00:00:00' 으로 해석됨
     →  14:30 은 그보다 크므로 탈락  ★ 5월 31일 하루가 통째로 사라짐
  B: < '2025-06-01'  →  포함  ✅
```

또 B는 **월말이 며칠인지 신경 쓸 필요가 없습니다.** 2월이든 윤년이든 `< 다음달 1일` 로 끝납니다.
A는 `'2025-02-28'` 인지 `'2025-02-29'` 인지 매번 판단해야 합니다.

**`>= 시작 AND < 끝`** — 이 형태를 반열림 구간(half-open interval)이라고 하며,
[Day 043](day-043.md)의 증분 적재에서 "어제 자정부터 오늘 자정까지"를 자를 때 그대로 씁니다.
</details>

## 오늘의 정리

| 구문 | 하는 일 |
|---|---|
| `SELECT 열 [AS 별칭]` | 보여줄 열 (계산식도 가능) |
| `SELECT DISTINCT 열` | 중복 제거 |
| `WHERE 조건` | 행 거르기 |
| `BETWEEN a AND b` | a 이상 b 이하 (**양끝 포함**) |
| `IN (...)` · `LIKE '%..%'` | 목록 · 패턴 |
| `IS NULL` · `IS DISTINCT FROM` | **NULL 안전 비교** |
| `COALESCE(a, b)` | NULL을 기본값으로 |
| `ORDER BY 열 DESC NULLS LAST` | 정렬 |
| `LIMIT n OFFSET m` | 자르기 · 페이징 |

| 꼭 기억할 것 | 왜 |
|---|---|
| 실행 순서 `FROM → WHERE → SELECT → ORDER BY → LIMIT` | `WHERE` 에서 별칭을 못 쓰는 이유 |
| 값은 `'작은따옴표'` | 큰따옴표는 열 이름 |
| `NULL` 비교는 `IS` 로만 | `= NULL` 은 항상 0행 |
| `OR` 를 쓸 땐 괄호 | `AND` 가 먼저 계산됨 |
| `LIMIT` 에는 `ORDER BY` 짝으로 | 행 순서는 보장되지 않음 |
| 날짜 구간은 `>= 시작 AND < 끝` | 시각이 붙는 순간 `BETWEEN` 이 깨짐 |

**오늘의 습관** — 조건을 하나 추가할 때마다 `(N rows)` 를 확인하세요. **줄어든 행 수가 예상과 다르면 거기에 NULL이 있습니다.**
