## ② 왜 필요한가

어제 이런 쿼리를 썼습니다.

```sql
ROUND(SUM(oi.quantity * oi.unit_price) * 100.0
      / (SELECT SUM(oi2.quantity * oi2.unit_price)
         FROM order_items oi2
         JOIN orders o2 ON oi2.order_id = o2.order_id
         WHERE o2.status <> 'cancelled'), 2) AS 비중
```

읽을 수 있나요? 저 괄호 안이 무엇을 구하는지 알려면 **8줄을 따라가야** 합니다.
그리고 저 값은 다른 곳에서도 필요한데, 쓸 때마다 8줄을 복사해야 합니다.

또 [Day 034](day-034.md)에서는 팬아웃을 피하려고 이렇게 썼습니다.

```sql
JOIN (SELECT order_id, SUM(quantity * unit_price) AS 주문금액
      FROM order_items GROUP BY order_id) t ON o.order_id = t.order_id
```

`FROM` 절 한가운데 쿼리가 통째로 들어가 있습니다. 두세 개만 겹쳐도 **아무도 못 읽는 코드**가 됩니다.

오늘 배우는 것은 **문제를 나눠서 이름 붙이는 방법**입니다.

```sql
WITH 주문금액 AS (
    SELECT order_id, SUM(quantity * unit_price) AS 금액
    FROM order_items GROUP BY order_id
),
전체매출 AS (
    SELECT SUM(금액) AS 총액 FROM 주문금액
)
SELECT ... FROM 주문금액, 전체매출 ...;
```

[Day 011](../01-python-data/day-011.md)에서 긴 함수를 작은 함수로 쪼갠 것과 **똑같은 일**입니다.
SQL도 코드이고, 코드는 읽히기 위해 존재합니다. **W09에서 파이썬으로 SQL을 다루기 시작하면
읽을 수 없는 쿼리는 유지보수 불가능한 자산**이 됩니다.

## ③ 개념 설명

### 서브쿼리 — 쿼리 안의 쿼리

**들어가는 자리**에 따라 세 종류로 나뉘고, 자리마다 **반환해야 하는 모양**이 다릅니다.

| 종류 | 들어가는 자리 | 반환 모양 | 예 |
|---|---|---|---|
| **스칼라 서브쿼리** | `SELECT` · `WHERE` 의 값 자리 | **1행 1열** | `(SELECT AVG(price) FROM products)` |
| **인라인 뷰** | `FROM` 절 | **표 (여러 행 여러 열)** | `FROM (SELECT ...) t` |
| **조건 서브쿼리** | `WHERE ... IN / EXISTS` | **1열 여러 행** | `WHERE id IN (SELECT ...)` |

```sql
-- ① 스칼라 — 평균보다 비싼 상품
SELECT name, price FROM products
WHERE price > (SELECT AVG(price) FROM products);

-- ② 인라인 뷰 — 주문별 금액을 먼저 만든 뒤 평균
SELECT AVG(금액) FROM (
    SELECT order_id, SUM(quantity * unit_price) AS 금액
    FROM order_items GROUP BY order_id
) t;

-- ③ 조건 — 6월에 주문한 고객
SELECT name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE ordered_at >= '2025-06-01');
```

> **인라인 뷰에는 별칭이 필수입니다.** `) t` 의 `t` 를 빼면 문법 에러입니다.

### 상관 서브쿼리 — 바깥 행을 참조하는 것

| 종류 | 특징 | 실행 |
|---|---|---|
| **비상관(uncorrelated)** | 바깥과 무관. 혼자 실행 가능 | **한 번만** 계산 |
| **상관(correlated)** | 바깥 행의 값을 씀 | **행마다** 계산 (느릴 수 있음) |

```sql
-- 상관 서브쿼리 — 각 카테고리의 최고가 상품
SELECT p.name, p.category, p.price
FROM products p
WHERE p.price = (SELECT MAX(p2.price) FROM products p2
                 WHERE p2.category = p.category);   -- ← 바깥의 p 를 참조
```

상관 서브쿼리는 **읽기 쉽지만 느립니다.** 같은 일을 [Day 037](day-037.md)의 윈도우 함수로 하면 한 번만 훑고 끝납니다.

### `IN` vs `EXISTS` vs `JOIN`

세 가지 모두 "다른 테이블에 있는지"를 묻습니다. **결과가 미묘하게 다릅니다.**

| 방법 | 특징 | 행이 늘어나나 |
|---|---|---|
| `IN (SELECT ...)` | 값 목록과 비교. 직관적 | **안 늘어남** |
| `EXISTS (SELECT 1 ...)` | 있는지만 확인. 찾으면 즉시 중단 | **안 늘어남** |
| `JOIN` | 실제로 붙임 | **늘어날 수 있음** (팬아웃) |

```sql
-- 6월에 주문한 고객 — 세 방법 모두 5행
SELECT name FROM customers WHERE customer_id IN
    (SELECT customer_id FROM orders WHERE ordered_at >= '2025-06-01');

SELECT name FROM customers c WHERE EXISTS
    (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.ordered_at >= '2025-06-01');

SELECT DISTINCT c.name FROM customers c        -- DISTINCT 를 빼면 중복!
    JOIN orders o ON c.customer_id = o.customer_id WHERE o.ordered_at >= '2025-06-01';
```

**"존재 여부만 궁금하다"면 `EXISTS` 를 쓰세요.** `JOIN` 은 붙일 값이 필요할 때만 씁니다.
`JOIN` + `DISTINCT` 조합이 보이면 대개 `EXISTS` 로 바꿔야 하는 신호입니다.

### `NOT IN` 의 NULL 함정 ★

**오늘 가장 위험한 내용입니다.**

```sql
SELECT name FROM customers
WHERE phone NOT IN (SELECT phone FROM customers WHERE grade = 'bronze');
--  결과: 0행  ★ 아무것도 안 나옵니다
```

bronze 고객 중에 `phone` 이 `NULL` 인 사람이 있기 때문입니다. `NOT IN` 은 이렇게 풀립니다.

```
phone NOT IN (A, B, NULL)
= phone <> A  AND  phone <> B  AND  phone <> NULL
                                    └── 항상 NULL(모름)
= (참) AND (참) AND NULL
= NULL   →  WHERE 통과 실패  →  모든 행 탈락
```

**목록에 `NULL` 이 하나라도 있으면 `NOT IN` 은 항상 0행**입니다. 에러도 경고도 없습니다.

| 방어법 | 코드 |
|---|---|
| **`NOT EXISTS` 를 쓴다** (권장) | `WHERE NOT EXISTS (SELECT 1 FROM ... WHERE ...)` |
| 서브쿼리에서 NULL 제거 | `... WHERE grade='bronze' AND phone IS NOT NULL` |
| 안티 조인 | `LEFT JOIN ... WHERE b.key IS NULL` ([Day 034](day-034.md)) |

> **`IN` 은 안전하고 `NOT IN` 만 위험합니다.** `IN` 은 하나라도 참이면 참이라 NULL이 섞여도 동작합니다.
> **실무 규칙: `NOT IN` 대신 `NOT EXISTS` 를 기본으로 쓴다.**

### `WITH` — CTE (공통 테이블 식)

**Common Table Expression** = "이 쿼리 안에서만 쓰는 임시 이름표"입니다.

```sql
WITH 이름 AS (
    SELECT ...
)
SELECT ... FROM 이름;
```

| CTE의 장점 | 설명 |
|---|---|
| **이름이 생긴다** | `t1`, `t2` 대신 `주문금액`, `월별매출` |
| **여러 번 쓸 수 있다** | 같은 서브쿼리를 복사할 필요 없음 |
| **위에서 아래로 읽힌다** | 중첩 괄호가 아니라 **단계 나열** |
| **단계별로 검증 가능** | 마지막 `SELECT` 만 바꿔 중간 결과 확인 |

여러 개를 이어 붙일 수 있고, **뒤의 CTE는 앞의 CTE를 참조**할 수 있습니다.

```sql
WITH 주문금액 AS ( ... ),
     고객별합계 AS ( SELECT ... FROM 주문금액 ... ),   -- 앞 것을 씀
     전체합계 AS ( SELECT ... FROM 고객별합계 )
SELECT * FROM 고객별합계, 전체합계;
```

### 서브쿼리 · CTE · 뷰 비교

| | 사는 곳 | 이름 | 재사용 |
|---|---|---|---|
| **서브쿼리** | 쿼리 안 | 없음(또는 `t`) | 그 자리에서만 |
| **CTE (`WITH`)** | 쿼리 안 | 있음 | **그 쿼리 안에서** 여러 번 |
| **뷰 (`VIEW`)** | **DB에 저장** | 있음 | **모든 쿼리에서** 영구히 |

```sql
CREATE VIEW v_order_amount AS
SELECT order_id, SUM(quantity * unit_price) AS 금액 FROM order_items GROUP BY order_id;
```

뷰는 [Day 038](day-038.md)에서 다룹니다. **자주 쓰는 CTE가 생기면 뷰로 승격**하는 것이 자연스러운 흐름입니다.

> **CTE는 공짜가 아닙니다.** PostgreSQL 12+ 부터는 CTE를 자동으로 펼쳐 최적화하지만,
> `WITH ... AS MATERIALIZED (...)` 로 강제하면 중간 결과를 실제로 만들어 둡니다.
> 같은 CTE를 여러 번 참조할 때는 `MATERIALIZED` 가 유리할 수 있습니다.

### Step 1. 스칼라 서브쿼리 — 평균과 비교하기

```
shop=# SELECT name, price,
shop-#        (SELECT ROUND(AVG(price)) FROM products) AS 전체평균,
shop-#        price - (SELECT ROUND(AVG(price)) FROM products) AS 차이
shop-# FROM products
shop-# WHERE price > (SELECT AVG(price) FROM products)
shop-# ORDER BY price DESC;
      name      | price  | 전체평균 |  차이
----------------+--------+----------+--------
 27인치모니터   | 259000 |    50142 | 208858

 블루투스이어폰 |  79000 |    50142 |  28858
(3 rows)
```

**12개 상품 중 3개만 평균 이상**입니다. 모니터 하나가 평균을 끌어올렸기 때문입니다.
(평균이 왜곡될 때는 중앙값을 봐야 합니다 — [Day 037](day-037.md)의 `PERCENTILE_CONT`.)

> **`WHERE price > (SELECT ...)` 가 되는 이유** — 서브쿼리가 **값 하나**를 돌려주기 때문입니다.
> 여러 행을 돌려주면 `more than one row returned by a subquery` 에러가 납니다.

### Step 2. `IN` 과 `EXISTS`

```
shop=# SELECT customer_id, name FROM customers
shop-# WHERE customer_id IN (
shop(#     SELECT customer_id FROM orders WHERE ordered_at >= '2025-06-01'
shop(# )
shop-# ORDER BY customer_id;
 customer_id |  name
-------------+--------
           2 | 이서연
           4 | 최수아
           5 | 정우진
           8 | 윤도현
           9 | 임채원

```

같은 것을 `EXISTS` 로 씁니다. 결과는 같습니다.

```
shop=# SELECT c.customer_id, c.name FROM customers c
shop-# WHERE EXISTS (
shop(#     SELECT 1 FROM orders o
shop(#     WHERE o.customer_id = c.customer_id AND o.ordered_at >= '2025-06-01'
shop(# )
shop-# ORDER BY c.customer_id;
 customer_id |  name
-------------+--------
           2 | 이서연
           4 | 최수아
           5 | 정우진
           8 | 윤도현
           9 | 임채원
(5 rows)
```

> `SELECT 1` 인 이유 — `EXISTS` 는 **행이 있는지만** 봅니다. 무엇을 고르든 상관없어서 관례로 `1` 을 씁니다.

조금 더 실무적인 질문 — **전자기기를 한 번이라도 산 고객**입니다.

```
shop=# SELECT c.customer_id, c.name FROM customers c
shop-# WHERE EXISTS (
shop(#     SELECT 1
shop(#     FROM orders o
shop(#     JOIN order_items oi ON o.order_id   = oi.order_id
shop(#     JOIN products    p  ON oi.product_id = p.product_id
shop(#     WHERE o.customer_id = c.customer_id
shop(#       AND o.status <> 'cancelled'
shop(#       AND p.category = '전자기기'
shop(# )
shop-# ORDER BY c.customer_id;
 customer_id |  name
-------------+--------
           1 | 김민수
           2 | 이서연
           4 | 최수아

           6 | 강하은
```

**박지훈(3) 님이 없습니다.** 4번 주문으로 모니터를 샀지만 **취소**됐기 때문입니다.
`AND o.status <> 'cancelled'` 한 줄이 결과를 바꿉니다. **조건을 어디에 넣느냐가 곧 정의**입니다.

### Step 3. `NOT IN` 함정 직접 만나기 ★

"bronze 등급 고객의 전화번호를 쓰지 않는 고객"을 찾아봅니다.

```
shop=# SELECT name, phone FROM customers
shop-# WHERE phone NOT IN (SELECT phone FROM customers WHERE grade = 'bronze');
 name | phone
------+-------
(0 rows)
```

**0행입니다.** 에러도 안 납니다. 범인을 확인합니다.

```
shop=# SELECT customer_id, name, phone FROM customers WHERE grade = 'bronze';
 customer_id |  name  |     phone
-------------+--------+---------------
           3 | 박지훈 |
           6 | 강하은 |
           9 | 임채원 | 010-1234-0009
          11 | 오세훈 | 010-1234-0011
(4 rows)
```

목록에 `NULL` 이 두 개 있습니다. `phone <> NULL` 은 항상 `NULL` 이므로 **모든 행이 탈락**했습니다.

**해결 ① `NOT EXISTS`**

```
shop=# SELECT c.name, c.phone FROM customers c
shop-# WHERE NOT EXISTS (
shop(#     SELECT 1 FROM customers b
shop(#     WHERE b.grade = 'bronze' AND b.phone = c.phone
shop(# )
shop-# ORDER BY c.customer_id;
  name  |     phone
--------+---------------
 김민수 | 010-1234-0001
 이서연 | 010-1234-0002
 박지훈 |
 최수아 | 010-1234-0004
 정우진 | 010-1234-0005
 강하은 |
 조은비 | 010-1234-0007
 윤도현 | 010-1234-0008
 한지민 |
 신유진 | 010-1234-0012
(10 rows)
```

**10행.** 12명 중 bronze 전화번호를 가진 임채원·오세훈 두 명만 빠졌습니다. 이것이 우리가 원한 답입니다.

**해결 ② 서브쿼리에서 NULL 제거**

```
shop=# SELECT name, phone FROM customers
shop-# WHERE phone NOT IN (
shop(#     SELECT phone FROM customers WHERE grade = 'bronze' AND phone IS NOT NULL
shop(# )
shop-# ORDER BY customer_id;
  name  |     phone
--------+---------------
 김민수 | 010-1234-0001
 이서연 | 010-1234-0002
 최수아 | 010-1234-0004
 정우진 | 010-1234-0005
 조은비 | 010-1234-0007
 윤도현 | 010-1234-0008
 신유진 | 010-1234-0012
(7 rows)
```

**7행.** ①과 다릅니다. 여기서는 **바깥 쪽의 `phone` 이 NULL인 3명**(박지훈·강하은·한지민)도 탈락했기 때문입니다.
`NULL NOT IN (...)` 역시 `NULL` 이니까요.

> **①과 ② 중 무엇이 맞나요?** 질문의 의도에 달렸습니다.
> "전화번호가 없는 사람도 포함"이면 ①, "전화번호가 있는 사람 중에서"면 ②입니다.
> **NULL이 있는 열을 다룰 때는 "없는 값은 어느 쪽인가"를 반드시 정하고 시작하세요.**

### Step 4. 인라인 뷰 — `FROM` 안의 표

[Day 034](day-034.md)에서 팬아웃을 피하려고 쓴 패턴입니다.

```
shop=# SELECT ROUND(AVG(t.금액)) AS 평균주문금액,
shop-#        MAX(t.금액)        AS 최대주문금액,
shop-#        COUNT(*)           AS 주문수
shop-# FROM (
shop(#     SELECT o.order_id, SUM(oi.quantity * oi.unit_price) AS 금액
shop(#     FROM orders o
shop(#     JOIN order_items oi ON o.order_id = oi.order_id
shop(#     WHERE o.status <> 'cancelled'
shop(#     GROUP BY o.order_id
shop(# ) t;
 평균주문금액 | 최대주문금액 | 주문수
--------------+--------------+--------
        99875 |       518000 |     28
(1 row)
```

**"집계한 결과를 다시 집계"** 하는 형태입니다. `GROUP BY` 한 번으로는 안 되는 질문이 여기 해당합니다.

### Step 5. 같은 쿼리를 CTE로 바꾸기

Step 4와 **완전히 같은 결과**입니다. 읽기 쉬워진 것만 다릅니다.

```
shop=# WITH 주문금액 AS (
shop(#     SELECT o.order_id, SUM(oi.quantity * oi.unit_price) AS 금액
shop(#     FROM orders o
shop(#     JOIN order_items oi ON o.order_id = oi.order_id
shop(#     WHERE o.status <> 'cancelled'
shop(#     GROUP BY o.order_id
shop(# )
shop-# SELECT ROUND(AVG(금액)) AS 평균주문금액,
shop-#        MAX(금액)        AS 최대주문금액,
shop-#        COUNT(*)         AS 주문수
shop-# FROM 주문금액;
 평균주문금액 | 최대주문금액 | 주문수
--------------+--------------+--------
        99875 |       518000 |     28
(1 row)
```

**CTE의 진짜 힘은 중간 결과를 확인할 수 있다는 것**입니다.
마지막 `SELECT` 만 바꾸면 각 단계가 제대로 됐는지 볼 수 있습니다.

```
shop=# WITH 주문금액 AS (
shop(#     SELECT o.order_id, SUM(oi.quantity * oi.unit_price) AS 금액
shop(#     FROM orders o JOIN order_items oi ON o.order_id = oi.order_id
shop(#     WHERE o.status <> 'cancelled' GROUP BY o.order_id
shop(# )
shop-# SELECT * FROM 주문금액 ORDER BY 금액 DESC LIMIT 3;
 order_id |  금액
----------+--------
       11 | 518000
        5 | 293000
       21 | 259000
(3 rows)
```

### Step 9. CTE로 분석 파이프라인 만들기

어제 리포트 문제 3의 **비중 계산**을 CTE로 다시 씁니다. 8줄짜리 괄호가 사라집니다.

```
shop=# WITH 유효주문 AS (
shop(#     SELECT order_id FROM orders WHERE status <> 'cancelled'
shop(# ),
shop(# 상세 AS (
shop(#     SELECT p.category, oi.quantity, oi.quantity * oi.unit_price AS 금액
shop(#     FROM order_items oi
shop(#     JOIN 유효주문 v  ON oi.order_id   = v.order_id
shop(#     JOIN products  p ON oi.product_id = p.product_id
shop(# ),
shop(# 총매출 AS (
shop(#     SELECT SUM(금액) AS 총액 FROM 상세
shop(# )
shop-# SELECT s.category                          AS 카테고리,
shop-#        SUM(s.quantity)                     AS 판매수량,
shop-#        SUM(s.금액)                         AS 매출,
shop-#        ROUND(SUM(s.금액) * 100.0 / t.총액, 2) AS 비중
shop-# FROM 상세 s
shop-# CROSS JOIN 총매출 t
shop-# GROUP BY s.category, t.총액
shop-# ORDER BY 매출 DESC;
 카테고리 | 판매수량 |  매출   | 비중
----------+----------+---------+-------
 전자기기 |       23 | 2085000 | 74.56
 사무용품 |       34 |  382500 | 13.68
 생활용품 |       16 |  329000 | 11.76
(3 rows)
```

**어제와 같은 결과인데 읽는 방식이 다릅니다.**

```
유효주문  → 취소 아닌 주문만 추린다
상세      → 거기에 상품 정보를 붙인다
총매출    → 전체 합계를 구한다
최종      → 카테고리별로 묶고 총액으로 나눈다
```

**위에서 아래로 읽으면 분석 절차가 그대로 보입니다.** 이것이 CTE를 쓰는 이유입니다.

> `CROSS JOIN 총매출` — `총매출` 은 1행이므로 모든 행에 그 값 하나를 붙입니다. 행 수는 안 늘어납니다.
> "전체 합계를 각 행에 붙이는" 표준 요령입니다. (내일 배울 `SUM(...) OVER ()` 로도 됩니다.)

## ⑤ 자주 하는 실수

### `subquery in FROM must have an alias`

```
shop=# SELECT AVG(금액) FROM (SELECT order_id, SUM(quantity*unit_price) AS 금액
shop(#                        FROM order_items GROUP BY order_id);
ERROR:  subquery in FROM must have an alias
LINE 1: SELECT AVG(금액) FROM (SELECT order_id, SUM(quantity*unit_pr...
                              ^
HINT:  For example, FROM (SELECT ...) [AS] foo.
```

**원인** — `FROM` 절의 서브쿼리에는 **이름이 필수**입니다.
**해결** — 닫는 괄호 뒤에 `t` 같은 별칭을 붙입니다. `) t;`

### `more than one row returned by a subquery used as an expression`

```
shop=# SELECT name FROM products WHERE price > (SELECT price FROM products WHERE category='전자기기');
ERROR:  more than one row returned by a subquery used as an expression
```

**원인** — 값이 와야 할 자리에 여러 행이 왔습니다.
**해결** — 집계로 **1행 1열**을 만들거나(`MAX(price)`), 비교 연산자를 `IN` 으로 바꿉니다.

### `NOT IN` 이 아무 행도 안 돌려줍니다 ★

```sql
WHERE phone NOT IN (SELECT phone FROM customers WHERE grade = 'bronze');  -- 0행
```

**원인** — 서브쿼리 결과에 `NULL` 이 섞여 있습니다. `NOT IN` 은 NULL이 하나만 있어도 **전부 탈락**시킵니다.
**해결** — `NOT EXISTS` 로 바꾸거나 서브쿼리에 `AND 열 IS NOT NULL` 을 추가합니다.

**실무 규칙 — `NOT IN` 을 보면 반사적으로 `NOT EXISTS` 로 바꾸세요.** 성능도 대개 더 좋습니다.

### CTE 이름을 `WITH` 안에서 앞뒤로 잘못 참조

```
shop=# WITH a AS (SELECT * FROM b), b AS (SELECT 1) SELECT * FROM a;
ERROR:  relation "b" does not exist
```

**원인** — CTE는 **위에서 아래로만** 참조할 수 있습니다. `a` 를 정의할 때 아직 `b` 가 없습니다.
**해결** — 순서를 바꿉니다. (서로 참조하는 구조가 필요하면 `WITH RECURSIVE`)

### `WITH` 뒤에 `SELECT` 를 빠뜨림

```
shop=# WITH t AS (SELECT 1 AS x);
ERROR:  syntax error at or near ";"
```

**원인** — `WITH` 는 **본 쿼리의 앞부분**일 뿐입니다. 그 자체로 완결된 문장이 아닙니다.
**해결** — 뒤에 `SELECT * FROM t;` 를 붙입니다.

### 상관 서브쿼리로 대용량 테이블을 훑음

```sql
SELECT c.name,
       (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id) AS 주문수
FROM customers c;
```

**증상** — 고객 12명이면 순식간이지만, 100만 명이면 **서브쿼리가 100만 번 실행**됩니다.
**해결** — 한 번에 집계한 뒤 조인합니다.

```sql
WITH 주문수 AS (SELECT customer_id, COUNT(*) AS n FROM orders GROUP BY customer_id)
SELECT c.name, COALESCE(o.n, 0) AS 주문수
FROM customers c LEFT JOIN 주문수 o ON c.customer_id = o.customer_id;
```

**판단 기준** — 상관 서브쿼리가 `SELECT` 절에 있고 바깥 테이블이 크면 무조건 다시 쓰세요.
느린지 확인하는 법은 [Day 038](day-038.md)의 `EXPLAIN` 에서 배웁니다.

### `JOIN` + `DISTINCT` 로 존재 여부를 확인함

```sql
SELECT DISTINCT c.name FROM customers c JOIN orders o ON ... WHERE ...;
```

**증상** — 동작은 하지만, 붙였다가 다시 지우는 낭비입니다. 조인 대상이 크면 느려집니다.
**해결** — `WHERE EXISTS (...)`. **`DISTINCT` 를 쓰고 있다면 왜 중복이 생겼는지 먼저 생각하세요.**
대개 팬아웃을 `DISTINCT` 로 덮고 있는 것이고, 그러면 `SUM` 은 여전히 틀립니다.

### CTE 이름에 한글을 쓸 때


## ⑥ 확인 문제

**1.** 아래 쿼리가 0행을 반환하는 이유를 설명하고, 두 가지 방법으로 고치세요. 두 방법의 결과가 다를 수 있다면 그 이유도 쓰세요.

```sql
SELECT name FROM customers
WHERE phone NOT IN (SELECT phone FROM customers WHERE grade = 'bronze');
```

<details>
<summary>답 보기</summary>

**원인** — bronze 고객 4명 중 박지훈·강하은 님의 `phone` 이 `NULL` 입니다.

```
phone NOT IN (NULL, NULL, '010-1234-0009', '010-1234-0011')
= phone <> NULL AND phone <> NULL AND phone <> '...0009' AND phone <> '...0011'
= NULL AND NULL AND (참) AND (참)
= NULL      →  WHERE 통과 실패  →  모든 행 탈락
```

**해결 ① `NOT EXISTS` — 10행**

```sql
SELECT c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM customers b WHERE b.grade='bronze' AND b.phone = c.phone);
```

**해결 ② 서브쿼리에서 NULL 제거 — 7행**

```sql
SELECT name FROM customers
WHERE phone NOT IN (SELECT phone FROM customers WHERE grade='bronze' AND phone IS NOT NULL);
```

**결과가 다른 이유** — ②는 **바깥쪽 `phone` 이 NULL인 3명**(박지훈·강하은·한지민)도 탈락시킵니다.
`NULL NOT IN (...)` 역시 `NULL` 이기 때문입니다. ①의 `NOT EXISTS` 는 "일치하는 행이 없다"만 보므로 이들이 살아남습니다.

| 방법 | 결과 | 포함되는 사람 |
|---|---|---|
| ① `NOT EXISTS` | 10행 | 전화번호 없는 고객 **포함** |
| ② `IS NOT NULL` | 7행 | 전화번호 있는 고객만 |

**교훈** — "고쳤다"고 끝이 아닙니다. **NULL을 어느 쪽으로 보낼지가 비즈니스 결정**입니다.
"연락 가능한 고객에게 문자 발송" 이라면 ②, "제외 대상이 아닌 전체" 라면 ①입니다.
</details>

**2.** 아래 두 쿼리는 같은 답을 냅니다. 어느 쪽이 더 좋으며, 데이터가 100만 행일 때 무엇이 달라지나요?

```sql
-- A
SELECT p.name, p.price FROM products p
WHERE p.price = (SELECT MAX(p2.price) FROM products p2 WHERE p2.category = p.category);

-- B
WITH m AS (SELECT category, MAX(price) AS 최고가 FROM products GROUP BY category)
SELECT p.name, p.price FROM products p
JOIN m ON p.category = m.category AND p.price = m.최고가;
```

<details>
<summary>답 보기</summary>

**B가 더 좋습니다.**

**A는 상관 서브쿼리**입니다. 바깥의 `p.category` 를 참조하므로 **바깥 행마다 한 번씩** 실행됩니다.

```
products 12행    →  서브쿼리 12번 실행     (체감 없음)
products 100만행 →  서브쿼리 100만번 실행  ★ 각각이 100만 행 스캔이면 사실상 멈춤
```

**B는 CTE를 한 번만** 계산합니다. 카테고리 수만큼(3행)의 작은 표를 만들고 조인 한 번으로 끝냅니다.

```
100만 행 1회 스캔 → 3행짜리 표 → 조인 1회
```

> 실제로는 PostgreSQL 옵티마이저가 A를 준조인(semi join)으로 바꿔 주는 경우도 있습니다.
> **추측하지 말고 `EXPLAIN ANALYZE` 로 확인**하는 방법을 [Day 038](day-038.md)에서 배웁니다.

**추가로 B가 좋은 이유** — 중간 단계에 `m` 이라는 **이름이 생겨** 검증이 쉽습니다.
`SELECT * FROM m;` 한 줄로 "카테고리별 최고가"가 맞는지 바로 볼 수 있습니다.

**다만 A/B 모두 한계가 있습니다.** 최고가가 동점이면 둘 다 여러 행을 내고,
"상위 3개"로 바꾸려면 완전히 다시 짜야 합니다. → [Day 037](day-037.md)의 `RANK()`
</details>

**3.** 아래 CTE 파이프라인은 어떤 순서로 무엇을 하나요? 단계마다 결과가 몇 행인지 예상하고, 마지막에서 두 번째 줄의 `CROSS JOIN` 이 왜 안전한지 설명하세요.

```sql
WITH 유효주문 AS (SELECT order_id FROM orders WHERE status <> 'cancelled'),
     상세     AS (SELECT p.category, oi.quantity * oi.unit_price AS 금액
                  FROM order_items oi
                  JOIN 유효주문 v ON oi.order_id = v.order_id
                  JOIN products p ON oi.product_id = p.product_id),
     총매출   AS (SELECT SUM(금액) AS 총액 FROM 상세)
SELECT s.category, SUM(s.금액), ROUND(SUM(s.금액) * 100.0 / t.총액, 2)
FROM 상세 s CROSS JOIN 총매출 t
GROUP BY s.category, t.총액;
```

<details>
<summary>답 보기</summary>

| 단계 | 하는 일 | 행 수 |
|---|---|---|
| `유효주문` | 취소가 아닌 주문 번호만 추림 | **28행** (30 − 취소 2) |
| `상세` | 그 주문의 상세에 카테고리를 붙임 | **45행** (47 − 취소 주문의 상세 2줄) |
| `총매출` | 전체 합계 | **1행** (2,796,500) |
| 최종 | 카테고리로 묶고 비중 계산 | **3행** |

**`CROSS JOIN` 이 안전한 이유** — `총매출` 이 **정확히 1행**이기 때문입니다.
`CROSS JOIN` 의 결과 행 수는 `왼쪽 × 오른쪽` 이므로 `45 × 1 = 45` — **행이 늘지 않습니다.**

```
45행 × 1행 = 45행   ✅ 모든 행에 총액이라는 상수 하나가 붙었을 뿐
45행 × 3행 = 135행  ❌ 만약 총매출이 3행이었다면 금액이 3배가 됨
```

**"1행짜리 결과를 모든 행에 붙이는" 표준 패턴**입니다.
같은 일을 내일 배울 `SUM(금액) OVER ()` 로 하면 CTE 하나가 통째로 사라집니다.

**`GROUP BY s.category, t.총액` 에 `t.총액` 이 들어간 이유** — `SELECT` 에 쓴 열은
집계 함수가 아니면 `GROUP BY` 에 있어야 하기 때문입니다 ([Day 033](day-033.md)).
값이 하나뿐이라 그룹이 늘어나지는 않습니다.
</details>

## 오늘의 정리

| 구문 | 하는 일 |
|---|---|
| `(SELECT ... )` 값 자리 | **스칼라** 서브쿼리 — 1행 1열 |
| `FROM (SELECT ...) t` | **인라인 뷰** — 별칭 필수 |
| `WHERE x IN (SELECT ...)` | 목록에 있는지 |
| `WHERE EXISTS (SELECT 1 ...)` | **존재 여부** — 있으면 즉시 중단 |
| `WHERE NOT EXISTS (...)` | **`NOT IN` 대신 이것을** |
| `WITH 이름 AS (...)` | CTE — 단계에 이름 붙이기 |
| `WITH a AS (...), b AS (SELECT ... FROM a)` | 다단계 파이프라인 |
| `CROSS JOIN 1행짜리CTE` | 전체 합계를 모든 행에 붙이기 |

| 원칙 | 이유 |
|---|---|
| **`NOT IN` 은 쓰지 않는다** | 목록에 NULL 하나면 결과가 0행 |
| **존재 확인은 `EXISTS`** | `JOIN` + `DISTINCT` 는 팬아웃을 덮는 것 |
| **상관 서브쿼리는 CTE + 조인으로** | 행마다 실행 → 한 번만 실행 |
| **긴 쿼리는 CTE로 단계 분리** | 마지막 `SELECT` 만 바꿔 중간 검증 |
| **CTE 이름은 무엇을 만드는지로** | `t1` 이 아니라 `월별매출` |

**오늘의 습관** — 쿼리가 20줄을 넘으면 **일단 CTE로 쪼개고** 단계마다 `SELECT *` 로 확인하세요.
"한 번에 맞히기"보다 "단계마다 확인하기"가 언제나 빠릅니다.
