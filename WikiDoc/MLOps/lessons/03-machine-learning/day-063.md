## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 전처리+모델을 **Pipeline 하나로** 묶고, 그것이 **구조적으로 누수를 막는 원리**를 설명할 수 있다.
- **ColumnTransformer**로 수치·범주 열에 서로 다른 전처리를 적용할 수 있다.
- 결측 대치(SimpleImputer)와 원-핫 인코딩(OneHotEncoder)을 파이프라인 안에서 처리할 수 있다.
- `단계__파라미터` 이름 규칙으로 **전처리까지 통째로 튜닝**할 수 있다.
- 결측과 문자열이 섞인 **새 데이터 한 행**을 `pipeline.predict()` 한 줄로 예측할 수 있다.

> 이 문서는 이 과정 전체가 전제하는 5개 핵심 문서 중 하나입니다. 여기서 만드는 구조가
> MP2 제출물의 뼈대이고, 대단원 04에서 **서빙 API가 로드하는 물건**이 바로 이 파이프라인입니다.

## ② 왜 필요한가

지금까지 우리 전처리는 코드 여기저기에 흩어져 있었습니다. 이 상태로 대단원 04에 가면
반드시 겪게 될 사고를 미리 보겠습니다.

```
[학습 코드]  d = df.dropna(...)                    [서빙 API — 석 달 뒤 다른 사람이 작성]
            sc = StandardScaler().fit(...)         값이 그냥 들어옴 (스케일 안 함!)
            X = sc.transform(...)                  결측이 오면 500 에러
            model.fit(X, y)                        station 인코딩 순서가 다름
```

**학습 때의 전처리와 서빙 때의 전처리가 다른 것** — 훈련-서빙 불일치(training-serving skew)는
ML 서비스 장애 원인의 고전입니다. 무섭게도 에러가 안 납니다. 숫자가 들어가고 숫자가 나오는데,
**조용히 엉뚱한 예측**을 합니다.

그리고 이미 겪은 문제들도 있습니다.

| 흩어진 전처리의 죄 | 어디서 겪었나 |
|---|---|
| fit을 전체 데이터에 해 버림 (전처리 누수) | [Day 052](day-052.md) 실험 4 |
| CV 폴드마다 전처리를 다시 해야 하는데 밖에서 한 번만 함 | [Day 061](day-061.md) ⑤ |
| 결측 행 145개를 그냥 버림 | Day 051부터 계속 (`dropna`) |
| 범주형(station)을 쓰지 못함 | [Day 053](day-053.md) ⑤ `could not convert string to float` |

오늘 이 모든 것을 **객체 하나**로 해결합니다. 전처리가 모델의 일부가 되면, 전처리를 잘못 쓸
방법 자체가 사라집니다.

## ③ 개념 설명

### Pipeline — 직렬 조립 라인

```python
pipe = Pipeline([("imputer", SimpleImputer()), ("scaler", StandardScaler()), ("model", Ridge())])
```

```
pipe.fit(X, y):      X ─▶ imputer.fit_transform ─▶ scaler.fit_transform ─▶ model.fit
pipe.predict(X_new): X ─▶ imputer.transform     ─▶ scaler.transform     ─▶ model.predict
                              ↑ fit이 없다!
```

핵심은 두 번째 줄입니다. **predict 경로에서는 모든 전처리가 transform만 수행**합니다.
즉 "fit은 train에만, test는 transform만"이라는 [Day 052](day-052.md)의 원칙이
사람의 기억력이 아니라 **객체의 구조로** 보장됩니다. `cross_val_score` 에 파이프라인을 넘기면
폴드마다 이 fit/transform 구분이 자동 반복됩니다 — [Day 061](day-061.md)에서 이미 써먹은 이유입니다.

### ColumnTransformer — 열마다 다른 대접

수치 열은 대치+스케일링이 필요하고, 범주 열은 원-핫 인코딩이 필요합니다.

```
                    ┌─ NUM 10개 열 ─▶ SimpleImputer ─▶ StandardScaler ─┐
X ─ ColumnTransformer                                                   ├─▶ 이어붙여 모델로
                    └─ station 열  ─▶ OneHotEncoder ────────────────────┘
```

| 도구 | 하는 일 | 오늘의 설정 |
|---|---|---|
| **SimpleImputer** | 결측을 통계량으로 채움 | `strategy="median"` (train의 중앙값을 **기억**해 둠) |
| **OneHotEncoder** | 범주 → 0/1 열들 (강남구 → `[1,0,0,0,0]`) | `handle_unknown="ignore"` (처음 보는 범주는 전부 0) |

### 이름 규칙 — 파이프라인 속 파라미터 주소

파이프라인 안의 모든 파라미터는 `단계이름__파라미터` 로 접근합니다 (밑줄 **두 개**).

```
model__alpha                          → 모델의 alpha
prep__num__imputer__strategy          → prep 안의 num 안의 imputer의 strategy
```

이 주소 체계 덕분에 **GridSearchCV가 전처리 선택지까지 한 번에 탐색**할 수 있습니다 —
"평균 대치가 나은가 중앙값 대치가 나은가"도 하이퍼파라미터입니다.

## ④ 단계별 실습

### Step 1. 우리가 버려 온 것 확인 (1교시)

```python
# day063_pipeline.py — Pipeline과 ColumnTransformer
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LinearRegression, Ridge
from sklearn.metrics import mean_absolute_error, r2_score
from sklearn.model_selection import GridSearchCV, TimeSeriesSplit
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

pd.set_option("display.width", 140)
df = pd.read_csv("data/air_daily.csv", parse_dates=["date"])
NUM = ["pm10", "pm25", "o3", "no2", "co", "so2", "temp", "humidity", "wind_speed", "precip"]
CAT = ["station"]

print("== A. 지금까지의 방식이 버려 온 것 ==")
d_all = df[df.pm25_next.notna()].copy()
d_drop = d_all.dropna(subset=NUM)
print(f"전체 {len(d_all)}행 중 결측 있는 행 {len(d_all) - len(d_drop)}행을 버려 왔음")
print(f"버린 행의 예:")
na_rows = d_all[d_all[NUM].isna().any(axis=1)]
print(na_rows[["date", "station", "pm10", "o3", "humidity", "pm25_next"]].head(3).to_string(index=False))
```

실행 결과:

```
== A. 지금까지의 방식이 버려 온 것 ==
전체 3642행 중 결측 있는 행 145행을 버려 왔음
버린 행의 예:
      date station  pm10     o3  humidity  pm25_next
2024-09-18     강남구   NaN 0.0335      67.0       16.6
2024-09-20     강남구  16.1    NaN      76.0       14.6
2024-10-04     강남구   NaN 0.0121      68.0       27.6
```

버려진 행들을 보세요 — pm10 하나가 없다고 **나머지 열한 개의 멀쩡한 값과 정답까지** 버렸습니다.
145행, train의 5%가 넘습니다. 게다가 결측은 무작위가 아니라 장비 점검(서초구 2025-11) 같은
사건과 붙어 다니므로, 버리는 것 자체가 데이터를 편향시킬 수 있습니다.

### Step 2. 어제까지 방식의 기준점 (2교시)

```python
tr_a = d_all[d_all.date < "2026-01-01"]; te_a = d_all[d_all.date >= "2026-01-01"]
tr_d = d_drop[d_drop.date < "2026-01-01"]; te_d = d_drop[d_drop.date >= "2026-01-01"]

print("\n== B. 어제까지 방식 (dropna + 수치만) ==")
m0 = LinearRegression().fit(tr_d[NUM], tr_d.pm25_next)
p0 = m0.predict(te_d[NUM])
print(f"train {len(tr_d)}행 → test R² {r2_score(te_d.pm25_next, p0):.3f}  MAE {mean_absolute_error(te_d.pm25_next, p0):.2f}")
```

실행 결과:

```
== B. 어제까지 방식 (dropna + 수치만) ==
train 2629행 → test R² 0.390  MAE 4.87
```

낯익은 0.390 — [Day 053](day-053.md)부터 우리의 회귀 기준점입니다.

### Step 3. 파이프라인 조립 (3~4교시)

```python
print("\n== C. Pipeline: 대치 + 스케일 + 원-핫 + 모델을 한 몸으로 ==")
prep = ColumnTransformer([
    ("num", Pipeline([
        ("imputer", SimpleImputer(strategy="median")),
        ("scaler", StandardScaler()),
    ]), NUM),
    ("cat", OneHotEncoder(handle_unknown="ignore"), CAT),
])
pipe = Pipeline([("prep", prep), ("model", LinearRegression())])
pipe.fit(tr_a[NUM + CAT], tr_a.pm25_next)
p1 = pipe.predict(te_a[NUM + CAT])
print(f"train {len(tr_a)}행 → test R² {r2_score(te_a.pm25_next, p1):.3f}  MAE {mean_absolute_error(te_a.pm25_next, p1):.2f}")
```

실행 결과:

```
== C. Pipeline: 대치 + 스케일 + 원-핫 + 모델을 한 몸으로 ==
train 2742행 → test R² 0.422  MAE 4.80
```

**0.390 → 0.422.** [Day 062](day-062.md)에서 108번 학습해 얻은 것(+0.015)보다 큰 개선을,
전처리 구조 하나로 얻었습니다. 개선의 출처는 ① 버리던 145행(그중 train 113행)을 살려낸 것,
② station 원-핫으로 측정소별 기저 농도 차이(강남 +, 노원 −)를 알게 된 것입니다.
그리고 이 개선은 **공짜가 아니라 안전하기까지** 합니다 — imputer의 중앙값·scaler의 평균은
`pipe.fit` 안에서 **train으로만** 계산됩니다.

### Step 4. 진짜 보상 — 한 행이 와도 predict 한 줄 (5교시)

주간 체크포인트("새 데이터 한 행이 와도 `pipeline.predict()` 한 줄로 예측되는가")를 직접 확인합니다.

```python
print("\n== D. 한 행이 와도 predict 한 줄 — 결측·문자열 포함 ==")
new_day = pd.DataFrame([{
    "pm10": np.nan,          # 오늘 pm10 센서 고장!
    "pm25": 41.0, "o3": 0.021, "no2": 0.031, "co": 0.62, "so2": 0.004,
    "temp": 3.5, "humidity": 74.0, "wind_speed": 1.2, "precip": 0.0,
    "station": "강남구",
}])
print(f"내일 pm25 예측: {pipe.predict(new_day)[0]:.1f}")
new_day2 = new_day.assign(station="세종시")   # 학습에 없던 측정소
print(f"처음 보는 측정소('세종시')도: {pipe.predict(new_day2)[0]:.1f}  (handle_unknown='ignore')")
```

실행 결과:

```
== D. 한 행이 와도 predict 한 줄 — 결측·문자열 포함 ==
내일 pm25 예측: 29.5
처음 보는 측정소('세종시')도: 27.7  (handle_unknown='ignore')
```

센서가 고장 난(pm10 NaN) 행도, 학습에 없던 측정소도 **에러 없이** 예측이 나옵니다 —
NaN은 train 중앙값으로 채워지고, 미지의 범주는 원-핫이 전부 0이 되어 "평균적인 측정소"로
처리됩니다. 이 관대함이 서빙 API의 안정성입니다. (물론 "조용히 처리됨"은 양날의 검이라,
운영에서는 결측률·미지 범주율을 모니터링합니다 — 대단원 05.)

### Step 5. 전처리까지 통째로 튜닝 (6교시)

```python
print("\n== E. 파이프라인 통째로 튜닝 — 전처리도 하이퍼파라미터다 ==")
pipe_r = Pipeline([("prep", prep), ("model", Ridge())])
grid = {
    "prep__num__imputer__strategy": ["mean", "median"],
    "model__alpha": [0.1, 1.0, 10.0, 100.0],
}
tr_s = tr_a.sort_values("date")
gs = GridSearchCV(pipe_r, grid, cv=TimeSeriesSplit(5), scoring="r2", n_jobs=-1)
gs.fit(tr_s[NUM + CAT], tr_s.pm25_next)
print(f"최고 CV R² {gs.best_score_:.3f} @ {gs.best_params_}")
p2 = gs.best_estimator_.predict(te_a[NUM + CAT])
print(f"test R² {r2_score(te_a.pm25_next, p2):.3f}")
```

실행 결과:

```
== E. 파이프라인 통째로 튜닝 — 전처리도 하이퍼파라미터다 ==
최고 CV R² 0.326 @ {'model__alpha': 100.0, 'prep__num__imputer__strategy': 'median'}
test R² 0.422
```

`prep__num__imputer__strategy` — 주소 체계로 **대치 전략까지 탐색 대상**이 됐습니다.
그리고 GridSearchCV + Pipeline 조합에서는 폴드마다 대치·스케일·인코딩이 그 폴드의 학습
조각으로만 다시 fit됩니다. 전처리 누수가 **일어날 수 없는 구조**입니다.

(CV 0.326이 test 0.422보다 한참 낮은 것이 이상한가요? TimeSeriesSplit의 초반 폴드는 train이
439행뿐이라 점수가 박합니다 — CV는 **후보끼리 비교**하는 자이지, 최종 성능의 예언이 아닙니다.)

## ⑤ 자주 하는 실수

### handle_unknown을 빼먹음

```
ValueError: Found unknown categories ['세종시'] in column 0 during transform
```

**원인** — OneHotEncoder 기본값은 `handle_unknown="error"`. 학습에 없던 범주가 서빙에서 오면 그대로 죽습니다.
**해결** — `OneHotEncoder(handle_unknown="ignore")`. 단, 운영에서는 미지 범주 비율을 모니터링해 "조용한 무시"가 쌓이는지 감시해야 합니다.

### predict에 넘기는 컬럼이 학습 때와 다름

```
ValueError: columns are missing: {'precip'}
```

**원인** — fit 때 있던 열이 predict 입력에 없습니다 (열 이름 오타, 컬럼 누락).
**해결** — 파이프라인은 **열 이름으로** 매칭하므로, 입력 스키마(NUM+CAT 목록)를 상수로 정의해 학습·서빙이 같은 목록을 import해 쓰게 합니다 ([Day 068](day-068.md)의 입력 스키마 관리로 이어짐).

### 파이프라인 파라미터 주소를 틀림

```
ValueError: Invalid parameter 'alpha' for estimator Pipeline(steps=[('prep', ...
```

**원인** — GridSearch에 `{"alpha": [...]}` 처럼 맨이름을 씀. 파이프라인 안에서는 전체 주소가 필요합니다.
**해결** — `model__alpha` 처럼 `단계이름__파라미터`(밑줄 2개). 주소가 헷갈리면 `pipe.get_params().keys()` 를 출력해 보세요.

### 대치를 "결측 해결"로 착각

**증상** — 결측 40%짜리 열도 중앙값으로 채우고 안심함.
**원인** — 대치는 정보를 만들어내지 않습니다. 40%가 같은 값으로 채워진 열은 사실상 왜곡된 상수입니다.
**해결** — 열별 결측률을 먼저 보고(우리는 최대 2%라 안전), 높은 열은 버리거나 "결측 여부" 플래그 열을 따로 만드는 것을 검토합니다.

### 파이프라인 밖에서 미리 전처리를 해 둠

**증상** — 스케일된 데이터를 만들어 두고 그걸 파이프라인에 또 넣거나, dropna를 여전히 밖에서 함.
**원인** — 습관. 그러나 밖에서 한 처리는 CV·서빙에서 **자동 반복되지 않으므로** 파이프라인의 보호 밖에 있습니다.
**해결** — 원칙: **원본에 가까운 DataFrame이 파이프라인의 입력**이 되게 하고, 모든 변환은 안으로 옮깁니다. (예외는 타깃 생성 같은 행 단위 정의뿐입니다.)

## ⑥ 확인 문제

**Q1.** `pipe.fit(X_train, y)` 후 `pipe.predict(X_test)` 를 호출할 때, StandardScaler는 X_test에 대해
fit과 transform 중 무엇을 수행하며, 그것이 왜 [Day 052](day-052.md)의 원칙을 지켜 주나요?

<details>
<summary>답 보기</summary>

**transform만** 수행합니다. predict 경로에서 파이프라인은 모든 전처리 단계의 transform만 호출하도록
만들어져 있어, test의 평균·표준편차가 스케일러에 스며들 방법이 없습니다. "fit은 train에만"이
사람의 규율이 아니라 객체의 구조로 강제되는 것입니다.

</details>

**Q2.** 오늘 R²가 0.390 → 0.422로 오른 두 가지 출처를 쓰고, 이 개선이 [Day 062](day-062.md)의
튜닝(+0.015)과 비교해 시사하는 바를 한 문장으로 쓰세요.

<details>
<summary>답 보기</summary>

① 결측 행을 버리는 대신 대치해 train 표본을 늘림(2,629→2,742행), ② station 원-핫으로 측정소별 기저
차이를 모델에 제공. 시사점: 모델 손잡이를 돌리는 것(튜닝)보다 **데이터를 더 쓰고 더 잘 표현하는 것**이
더 싸고 큰 개선을 준다 — 내일의 특성 엔지니어링이 그 연장선입니다.

</details>

**Q3.** 학습 코드와 서빙 API를 다른 사람이 관리하는 팀에서, "전처리를 Pipeline 안에 넣어 모델과 함께
저장한다"는 규칙이 방지하는 사고를 구체적으로 하나 쓰세요.

<details>
<summary>답 보기</summary>

훈련-서빙 불일치(training-serving skew): 예를 들어 학습 때는 중앙값 대치+표준화를 했는데 서빙 코드
작성자가 그 사실을 몰라 원시값을 그대로 모델에 넣으면, 에러 없이 조용히 엉뚱한 예측이 나갑니다.
파이프라인째 저장하면 서빙은 `load 후 predict` 만 하므로 전처리가 학습과 항상 동일합니다.

</details>
