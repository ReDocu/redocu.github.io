## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- W14의 부품(재현성 · MLflow · 직렬화 · 문서화)을 **학습 CLI 하나로** 조립할 수 있다.
- 설정(config)과 코드를 분리해, **코드 수정 없이** 실험 조건을 바꿀 수 있다.
- 학습 스크립트의 표준 6단계(로드·검증 → 특성 → CV → 학습·평가 → 기록 → 저장·검증)를 설계할 수 있다.
- `python train.py --config config.json` 한 줄로 재현 가능한 학습을 실행한다.

## ② 왜 필요한가

노트북(.ipynb)에서 셀을 위에서부터 눌러 가며 학습하던 시절을 끝낼 시간입니다.
과정 운영 원칙 3번 — **"노트북만으로 끝나는 결과물 금지"** — 의 이유가 이번 주에 모두 모였습니다.

| 노트북 학습의 문제 | 우리가 배운 해법 |
|---|---|
| 셀 실행 순서에 따라 결과가 다름 | 위→아래 한 방향으로만 흐르는 **스크립트** |
| "그때 그 조건"을 못 박을 수 없음 | **config 파일** + MLflow 기록 ([Day 067](day-067.md)) |
| 사람이 있어야 실행됨 | CLI 한 줄 → cron·Airflow가 대신 실행 (W27) |
| 산출물이 화면에만 존재 | 모델 파일 + 스키마 저장 ([Day 068](day-068.md)) |

그리고 이것이 **대단원 04·05로 가는 관문**입니다. W27에서 Airflow가 매주 이 명령을 자동
실행하고(재학습 파이프라인), 대단원 04의 서빙 API는 이 명령이 만든 모델 파일을 로드합니다.
`train.py` 는 과제가 아니라 **여러분의 첫 운영 부품**입니다.

> 오해 방지 — 노트북이 나쁜 게 아닙니다. 탐색·분석(EDA)은 노트북이 최고의 도구입니다.
> 문제는 **제출물·운영물**이 노트북인 것입니다. 탐색은 노트북에서, 확정된 절차는 스크립트로.

## ③ 개념 설명

### 학습 스크립트의 표준 6단계

이번 주 내내 손으로 하던 일들이 그대로 단계가 됩니다.

```
[1/6] 데이터 로드 + 지문 검증     ← Day 066 (해시가 다르면 즉시 중단)
[2/6] 특성 생성                   ← Day 064 (groupby 안에서!)
[3/6] 교차검증                    ← Day 061 (TimeSeriesSplit)
[4/6] 최종 학습과 test 평가       ← Day 052 (시간 분리, 최종 1회)
[5/6] MLflow 기록                 ← Day 067 (조건·결과·지문)
[6/6] 모델 저장 + 재로드 검증      ← Day 068 (동일 예측 확인 후에야 성공)
```

순서에 논리가 있습니다: 검증이 앞(잘못된 데이터로 시작도 안 함), 기록이 저장보다 앞
(run_id를 스키마에 넣기 위해), 재로드 검증이 마지막(이게 실패하면 전체 실패).

### config와 코드의 분리

```
train.py    ← 어떻게 학습하는가 (로직) — git으로 버전 관리
config.json ← 무엇으로 학습하는가 (조건) — 실험마다 바뀜, MLflow에 통째로 기록
```

조건을 코드에 하드코딩하면 실험마다 코드가 바뀌어 "코드 버전 = 실험 조건"이 얽힙니다.
분리하면 같은 코드로 조건만 갈아 끼우며 실험할 수 있고(`--config exp2.json`),
[Day 065](day-065.md) 여덟 칸의 ①~⑤가 파일 하나로 통째로 기록됩니다.

### argparse — 파이썬 표준 CLI 도구

```python
ap = argparse.ArgumentParser(description="…")
ap.add_argument("--config", required=True, help="설정 JSON 경로")
args = ap.parse_args()          # python train.py --config config.json
```

[Day 029](../01-python-data/day-029.md)에서 수집기 CLI를 만들 때 쓴 그 도구입니다 —
`datapipe etl --source air_seoul` 이 그랬듯, 오늘의 산출물도 인자 하나 받는 명령이 됩니다.


`expect_md5` 가 눈에 띌 겁니다 — [Day 066](day-066.md)의 데이터 지문을 **기대값**으로 박아,
다른 데이터로 학습이 시작되는 사고([Day 065](day-065.md)의 후임 사고)를 시작 전에 차단합니다.

### Step 2. train.py 작성 (2~5교시)

이번 주에 쓴 코드를 6단계 구조로 재조립합니다. 새 코드는 거의 없습니다 — **조립**이 오늘의 기술입니다.

```python
# train.py — 학습 → 평가 → 기록 → 저장을 명령 한 줄로
# 사용법: python train.py --config config.json
import argparse
import hashlib
import json
import os
import joblib
import mlflow
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LinearRegression
from sklearn.metrics import mean_absolute_error, r2_score
from sklearn.model_selection import TimeSeriesSplit, cross_val_score
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

NUM = ["pm10", "pm25", "o3", "no2", "co", "so2", "temp", "humidity", "wind_speed", "precip"]
TIME = ["pm25_lag1", "pm25_ma3", "seoul_pm25", "month"]
FC = ["wind_fc", "humidity_fc", "precip_fc"]
SETS = {"num10": NUM, "num+time": NUM + TIME, "num+time+fc": NUM + TIME + FC}


def make_features(df):
    """시계열·공간·예보 파생 (Day 064). 반드시 station 그룹 안에서."""
    df = df.sort_values(["station", "date"]).copy()
    g = df.groupby("station")
    df["pm25_lag1"] = g["pm25"].shift(1)
    df["pm25_ma3"] = g["pm25"].transform(lambda s: s.rolling(3).mean())
    df["seoul_pm25"] = df.groupby("date")["pm25"].transform("mean")
    df["month"] = df.date.dt.month
    df["wind_fc"] = g["wind_speed"].shift(-1)
    df["humidity_fc"] = g["humidity"].shift(-1)
    df["precip_fc"] = g["precip"].shift(-1)
    return df


def build_pipeline(feats):
    prep = ColumnTransformer([
        ("num", Pipeline([("imputer", SimpleImputer(strategy="median")),
                          ("scaler", StandardScaler())]), feats),
        ("cat", OneHotEncoder(handle_unknown="ignore"), ["station"]),
    ])
    return Pipeline([("prep", prep), ("model", LinearRegression())])


def main():
    ap = argparse.ArgumentParser(description="PM2.5 익일 예보 모델 학습")
    ap.add_argument("--config", required=True, help="설정 JSON 경로")
    args = ap.parse_args()
    cfg = json.load(open(args.config, encoding="utf-8"))

    print(f"[1/6] 데이터 로드: {cfg['data_path']}")
    md5 = hashlib.md5(open(cfg["data_path"], "rb").read()).hexdigest()
    if cfg.get("expect_md5") and md5 != cfg["expect_md5"]:
        raise SystemExit(f"  중단: 데이터 지문 불일치! 기대 {cfg['expect_md5']} / 실제 {md5}")
    print(f"  지문 확인: {md5[:8]}… 일치")
    df = pd.read_csv(cfg["data_path"], parse_dates=["date"])

    print("[2/6] 특성 생성")
    df = make_features(df)
    feats = SETS[cfg["feature_set"]]
    cols = feats + ["station"]
    d = df[df.pm25_next.notna() & df[FC].notna().all(axis=1)]
    tr = d[d.date < cfg["split_date"]]
    te = d[d.date >= cfg["split_date"]]
    print(f"  {cfg['feature_set']} ({len(cols)}열) · train {len(tr)} / test {len(te)}")

    print("[3/6] 교차검증 (TimeSeriesSplit 5)")
    pipe = build_pipeline(feats)
    trs = tr.sort_values("date")
    cv = cross_val_score(pipe, trs[cols], trs.pm25_next, cv=TimeSeriesSplit(5), scoring="r2")
    print(f"  CV R² {cv.mean():.3f} ± {cv.std():.3f}")

    print("[4/6] 최종 학습과 평가")
    pipe.fit(tr[cols], tr.pm25_next)
    pred = pipe.predict(te[cols])
    r2 = r2_score(te.pm25_next, pred)
    mae = mean_absolute_error(te.pm25_next, pred)
    print(f"  test R² {r2:.3f} · MAE {mae:.2f}")

    print("[5/6] MLflow 기록")
    mlflow.set_experiment(cfg["experiment"])
    with mlflow.start_run(run_name=f"train-{cfg['feature_set']}") as run:
        mlflow.log_params({**cfg, "data_md5": md5, "n_train": len(tr), "n_test": len(te)})
        mlflow.log_metrics({"cv_r2_mean": cv.mean(), "cv_r2_std": cv.std(),
                            "r2_test": r2, "mae_test": mae})
        run_id = run.info.run_id
    print(f"  run: {run_id[:8]}…")

    print("[6/6] 저장과 재로드 검증")
    os.makedirs("models", exist_ok=True)
    joblib.dump(pipe, cfg["model_path"])
    loaded = joblib.load(cfg["model_path"])
    assert np.array_equal(pred, loaded.predict(te[cols])), "재로드 예측 불일치!"
    schema = {"columns": cols, "target": "pm25_next", "data_md5": md5,
              "split_date": cfg["split_date"], "run_id": run_id}
    json.dump(schema, open(cfg["model_path"].replace(".joblib", "_schema.json"), "w",
                           encoding="utf-8"), ensure_ascii=False, indent=2)
    print(f"  저장: {cfg['model_path']} (+schema) · 동일 예측 확인 ✓")

    print(f"\n완료: test R² {r2:.3f} · MAE {mae:.2f} · run {run_id[:8]}")


if __name__ == "__main__":
    main()
```

### 오늘 새로 나오는 실수

**config에 비밀값을 넣음** — DB 비밀번호·API 키를 config.json에 쓰고 git에 커밋.
설정과 **비밀**은 다릅니다. 비밀은 환경 변수([Day 041](../02-sql-pipeline/day-041.md)에서 한 방식)로,
config에는 비밀 아닌 조건만.

**단계 실패를 무시하고 계속 진행** — CV가 예외로 죽었는데 try로 삼키고 저장까지 감.
파이프라인의 각 단계는 **이전 단계의 성공을 전제**합니다. 실패는 크게, 일찍, 명확하게
(`raise SystemExit`) — [Day 044](../02-sql-pipeline/day-044.md)의 실패 처리 정책 그대로입니다.

**노트북에서 개발한 코드를 복붙만 해 옴** — 전역 변수 순서 의존이 남아 CLI에선 다르게 동작.
함수 단위로 옮기고(오늘 구조), 새 폴더 클론 리허설([Day 066](day-066.md) Step 4)로 검증하세요.

<details>
<summary>3. 파일 해시(지문)로 판별할 수 있는 것과 없는 것은?</summary>

"두 파일이 완전히 같은가"는 판별 가능(1바이트만 달라도 지문이 다름). 무엇이·얼마나 다른지는 알 수 없음(그건 diff의 일).

</details>

<details>
<summary>4. MLflow의 experiment / run / param / metric / artifact를 한 줄씩.</summary>

experiment=프로젝트 폴더, run=실험 1회, param=조건(입력), metric=숫자 결과, artifact=실험이 낳은 파일.

</details>

<details>
<summary>5. metric과 param의 구분 기준은?</summary>

param은 실험 **전에** 정하는 조건(문자열 가능), metric은 실험이 **낸** 숫자 결과(정렬·그래프 대상, 숫자만).

</details>

<details>
<summary>6. 파이프라인째 직렬화하면 훈련-서빙 불일치가 왜 사라지나?</summary>

대치 통계·스케일·인코딩·모델이 한 파일에 봉인되어, 서빙은 로드 후 predict만 하므로 전처리를 다시 구현할 일(어긋날 일)이 없음.

</details>

<details>
<summary>7. joblib 저장이 실패하는 대표 사례와 해법은?</summary>

파이프라인 속 lambda/로컬 함수 (PicklingError). 모듈 최상위의 이름 있는 함수로 옮기고 그 모듈을 배포물에 포함.

</details>

<details>
<summary>8. 모델 카드에서 "비대상(out of scope)" 칸이 중요한 이유는?</summary>

사고는 대부분 학습 범위 밖 사용에서 나므로, 모델이 스스로 칠 수 없는 경계선을 문서가 대신 긋는 칸이기 때문.

</details>

<details>
<summary>9. 전체 MAE가 비슷해도 집단 격차가 클 수 있는 이유는? (노원 사례)</summary>

서비스 지표(나쁨재현)는 문턱 근처의 행동만 보므로, 기저 농도가 낮아 문턱을 살짝 넘는 집단은 같은 크기의 오차로도 체계적으로 더 자주 놓침.

</details>

<details>
<summary>10. config와 코드를 분리하는 이유 두 가지는?</summary>

① 코드 수정 없이 조건만 바꿔 실험 가능(코드 버전과 실험 조건의 분리) ② 조건이 파일 하나로 뭉쳐 MLflow에 통째로 기록·재현 가능.

</details>
