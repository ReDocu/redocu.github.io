## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- cron의 **네 가지 한계**를 실제 겪은 장면으로 말하고, 오케스트레이터가 무엇을 더해 주는지 설명할 수 있다.
- **DAG**(방향 비순환 그래프)로 "단계와 의존"을 선언하는 사고방식을 익힌다.
- Airflow에서 **수집→전처리→학습→평가 DAG**를 작성·실행하고, 그래프·로그로 상태를 읽을 수 있다.
- 실패한 단계에 **재시도**를 설정하고, 그 단계**만** 다시 실행할 수 있다.

---

## ② 왜 필요한가

[Day 115](day-115.md)에 cron을 심으며 한계를 기록해 뒀습니다 — "실패하면? 단계 간 의존은?
재시도는?" 그 기록이 오늘의 출발점입니다. 우리의 재학습 흐름을 cron으로 짜 본다고 합시다:

```
0 3 * * *  datapipe run          # 수집
30 3 * * * make_dataset.py       # 전처리 — 수집이 3:30까지 끝났기를 기도
0 4 * * *  train.py              # 학습 — 전처리가 끝났기를 기도
0 5 * * *  promote.py            # 평가·승격 — 학습이 끝났기를 기도
```

이 시간표의 이름은 **기도 기반 스케줄링**입니다. 문제를 세어 보면:

| cron의 한계 | 새벽에 벌어지는 일 |
|---|---|
| 의존을 표현 못 함 | 수집이 5분 늦으면 전처리는 **옛 데이터로** 진행 — 조용한 오염 |
| 실패에 무심 | 학습이 죽어도 5시의 승격은 돌아감 — 어제 모델을 재평가하는 헛일 (또는 사고) |
| 재시도 없음 | API 일시 장애 = 그날 파이프라인 전체 결번 |
| 이력·가시성 없음 | "지난 화요일 왜 안 돌았죠?" → syslog 고고학 |

핵심 결핍은 하나입니다 — cron은 **시각**만 알고 **관계**를 모릅니다. 우리가 원하는 선언은
"3시에 넷을 각각"이 아니라 "**수집이 성공하면 전처리를, 그것이 성공하면 학습을…**"이죠.
단계(task)와 의존(→)의 그래프 — 그것이 DAG이고, DAG를 받아 실행·감시·재시도·기록까지 해
주는 관제탑이 오케스트레이터(우리 도구: Airflow)입니다.

---

## ③ 개념 설명

### DAG — 시간표가 아니라 관계도

DAG(Directed Acyclic Graph): 방향(→)이 있고 순환이 없는 그래프. 우리의 재학습은:

```
fetch(수집) ──▶ preprocess(전처리) ──▶ train(학습) ──▶ evaluate_promote(평가·승격)
```

순환이 없어야 하는 이유는 자명합니다 — "A가 끝나야 B, B가 끝나야 A"는 실행 불가능한 선언
이니까. DAG의 각 노드가 **task**, 화살표가 의존이고, 스케줄은 DAG 전체에 하나("매일 3시에
이 그래프를 시작")만 줍니다 — 단계별 시각 기도는 사라집니다.

### Airflow — DAG의 관제탑

| 구성 요소 | 역할 |
|---|---|
| DAG 파일 (파이썬) | 그래프의 **선언** — dags/ 폴더에 두면 자동 인식 |
| 스케줄러 | 시각·의존을 보고 task를 실행 큐로 |
| 웹서버 (UI) | 그래프·이력·로그의 관제 화면 — cron에 없던 **가시성** |
| 메타데이터 DB | 모든 실행의 기록 |

그리고 설계 철학 하나 — **Airflow는 지휘하지, 연주하지 않습니다.** 무거운 계산(학습)은
task가 호출하는 외부 프로그램(우리의 CLI들)이 하고, Airflow는 시작·성공·실패만 관리합니다.
그래서 이 과정 내내 만들어 온 CLI들(datapipe·make_dataset·train.py·promote.py)이 **그대로
task가 됩니다** — [Day 029](../01-python-data/day-029.md)·[030](../01-python-data/day-030.md)에서
"명령 한 줄 + 종료 코드"로 다듬어 둔 설계의 마지막 보상입니다.

### DAG 파일의 문법 — 선언 세 덩어리

```python
with DAG(dag_id=..., schedule=..., default_args=...) as dag:   # ① 언제·어떻게
    a = BashOperator(task_id="fetch", bash_command="...")      # ② 무엇을 (task들)
    b = BashOperator(task_id="preprocess", bash_command="...")
    a >> b                                                     # ③ 어떤 순서로 (의존)
```

`>>` 가 화살표입니다 — 코드가 곧 ③의 그림입니다. default_args의 `retries`·`retry_delay` 가
cron에 없던 재시도를, `schedule` + 과거분 실행(catchup/백필)이 "빠진 날짜 메우기"를
담당합니다 — 단, 그 힘은 task가 **멱등**일 때만 안전합니다 ([Day 043](../02-sql-pipeline/day-043.md)이
세 번째로 소환되는 지점).

### Step 2. 재학습 DAG 선언 (3~5교시)

`dags/pm25_retrain.py`:

```python
# pm25_retrain.py — 수집→전처리→학습→평가·승격 (Day 133)
from datetime import datetime, timedelta

from airflow import DAG
from airflow.operators.bash import BashOperator

LAB = "/opt/mlops/mlops-mp2"        # 학습 저장소 (venv 포함)

default_args = {
    "retries": 2,                              # 실패 시 2회 재시도
    "retry_delay": timedelta(minutes=5),       # 5분 간격 (일시 장애 흡수)
}

with DAG(
    dag_id="pm25_retrain",
    description="주간 재학습: 수집→전처리→학습→평가·승격",
    schedule="0 3 * * 1",                      # 매주 월 03:00 (문법은 cron 그대로!)
    start_date=datetime(2026, 8, 1),
    catchup=False,                             # 과거분 자동 소급 금지 (⑤ 참고)
    default_args=default_args,
) as dag:

    fetch = BashOperator(
        task_id="fetch",
        bash_command=f"cd /opt/mlops/datapipe && venv/bin/datapipe run",
    )

    preprocess = BashOperator(
        task_id="preprocess",
        bash_command=f"cd {LAB} && .venv/bin/python make_dataset.py --until {{{{ ds }}}}",
    )

    train = BashOperator(
        task_id="train",
        bash_command=f"cd {LAB} && .venv/bin/python train.py",
    )

    evaluate_promote = BashOperator(
        task_id="evaluate_promote",
        bash_command=f"cd {LAB} && .venv/bin/python promote.py",
    )

    fetch >> preprocess >> train >> evaluate_promote
```

읽어 둘 것 — ① 각 task가 **어제까지 우리가 손으로 치던 명령 그대로** (Airflow는 지휘만),
② `{{ ds }}` 는 실행 기준 날짜가 주입되는 템플릿 (백필 때 "그 날짜의 실행"이 가능한 장치),
③ 절대 경로·venv 직접 지정 — cron에서 배운 규율이 그대로 유효합니다.

파일을 dags/에 넣고 1~2분 — UI에 pm25_retrain이 나타납니다. **Graph** 탭에서 ③의 그림이
코드에서 자동으로 그려진 것을 확인하고, ▶(Trigger DAG)로 수동 실행:

```
Graph: fetch ──▶ preprocess ──▶ train ──▶ evaluate_promote
        ■초록      ■초록          ■초록      ■초록          (11:42, 총 4m 12s)
```

네 칸이 차례로 초록 — 로그도 task별로 클릭 한 번입니다 (`journalctl`·syslog 고고학의 종언).

### Step 3. 실패의 관제 — 재시도와 부분 재실행 (6~7교시)

cron과의 차이는 실패에서 드러납니다. 수집 API 장애를 재현하고 (datapipe의 API 키를 잠시
무효화) 트리거:

```
fetch  ■노랑(up_for_retry)  →  5분 후 재시도 1  →  재시도 2  →  ■빨강(failed)
preprocess 이후: ■회색(upstream_failed) — 실행되지 않음!
```

두 가지를 관찰하세요 — ① 일시 장애면 재시도가 조용히 흡수했을 것 (retries=2), ② 최종 실패
시 **하류가 실행되지 않았습니다** — cron이라면 옛 데이터로 전처리·학습·승격까지 완주하며
오염을 만들었을 상황입니다. 실패는 시끄럽게, 오염은 구조적으로 차단 — 관제탑의 존재 이유.

API 키를 복구한 뒤, 실패한 fetch만 **Clear** — 그 지점부터 하류가 이어 돕니다. 4단계 중
3단계를 재실행하지 않는 것, 이것이 "부분 재실행"이고 12시간짜리 파이프라인에서는 이 기능이
곧 반나절입니다.

### Step 4. 큰 그림 확인 (7교시 계속)

지금 조립된 것을 한 발 물러나 보세요:

```
[cron: 매일] datapipe → DB                            (Day 115 — 데이터는 매일 신선)
[Airflow: 매주 월 3시] 수집분 정리 → 재학습 → 평가 →   (오늘)
        └─ 게이트 통과 시에만 @production 이동          (Day 132)
[서빙] 재로드 시 새 운영 모델                           (Day 132)
```

"새 데이터 → 자동 재학습 → 조건부 배포" — [Day 135](day-135.md) 종합 설계의 뼈대가 이미 서
있습니다. 남은 질문 "재학습을 **언제** 해야 하는지 어떻게 아나"(매주 월요일이 정답일 이유가
없죠)는 내일의 모니터링이 답합니다.

### Step 5. 과제 — 실패 설계 (8교시)

1. **재시도 설계** — task별로 retries·retry_delay를 차등 설정하고 근거를 쓰세요 (수집: 외부
   API라 재시도 가치 높음 / 학습: 실패가 대개 결정적(코드·데이터 문제)이라 재시도 무의미 —
   어느 쪽이 몇 회?)
2. **실패 알림** — `on_failure_callback` 으로 실패 시 로그에 구조화 경고를 남기는 콜백을
   달고, "알림이 웹훅(슬랙 등)이라면 무엇을 담아야 하나" 필드 목록 설계
3. **멱등성 점검표** — 네 task 각각에 대해 "재시도·재실행돼도 안전한가"를 판정하고 근거 제시
   (힌트: datapipe는 Day 030에서 검증 완료, train.py는 산출물 덮어쓰기 방식이 관건,
   promote는 게이트 재평가라 안전 — 맞습니까?)
4. **백필 사고 실험** — catchup=True로 바꾸면 지금 무슨 일이 벌어질지 **켜기 전에** 예측하고,
   start_date와의 관계로 설명 (켜 보는 건 예측을 적은 후에!)

## ⑤ 자주 하는 실수

### DAG 파일 최상위에서 무거운 일을 함

**증상** — DAG 파일에 `df = pd.read_csv(...)` 를 태스크 밖에 — UI가 굼뜨고 스케줄러 CPU가
치솟음.
**원인** — 스케줄러는 DAG 파일을 **주기적으로 다시 파싱**합니다 — 최상위 코드는 그때마다
실행됩니다 (선언문이 아니라 프로그램을 둔 것).
**해결** — DAG 파일은 **선언만**: 그래프 구조·명령 문자열. 데이터·모델을 만지는 코드는 전부
task가 호출하는 외부 스크립트로. "이 파일은 1초 안에 import 되는가"가 리트머스입니다.

### catchup을 모르고 켜서 과거 실행 폭탄

**증상** — start_date를 두 달 전으로 두고 catchup=True — 활성화 순간 **밀린 8주치 실행**이
한꺼번에 큐로.
**원인** — Airflow의 기본 세계관은 "스케줄의 모든 회차는 언젠가 실행되어야 한다"(백필) —
모르면 폭탄, 알면 강력한 기능입니다.
**해결** — 학습 단계에선 `catchup=False` 를 명시(오늘 코드). 과거분을 의도적으로 메울 때만
{{ ds }} 기반 멱등 task + 제한된 기간으로 백필을 켭니다 — "빠진 2주를 데이터 기준일별로
재실행"이 백필의 올바른 사용처입니다.

### task 사이에서 데이터를 XCom으로 나름

**증상** — fetch가 DataFrame을 반환해 XCom으로 preprocess에 전달 — 메타데이터 DB가 부풀고
직렬화 에러.
**원인** — XCom(태스크 간 쪽지)은 **작은 메타데이터**(경로·건수·플래그)용인데 화물칸으로 씀.
**해결** — 큰 데이터의 전달은 **바깥의 저장소**(파일·DB — 우리 구조는 이미 그렇게: datapipe →
DB → make_dataset)로 하고, XCom에는 "어디에 뒀다"만. 지휘자에게 악기를 들리지 마세요.

### 비멱등 태스크에 재시도·백필

**증상** — 적재 태스크가 재시도되며 같은 날짜 데이터가 두 벌 — 주간 집계가 조용히 2배.
**원인** — 재시도는 "다시 실행해도 같다"를 **전제**하는 기능인데, 태스크가 그 전제를 못 지킴.
**해결** — 오케스트레이터 도입의 선행 조건이 멱등성입니다 ([Day 043](../02-sql-pipeline/day-043.md)의
UPSERT·기준일 재작성 패턴). 과제 3(멱등성 점검표)이 형식적 숙제가 아닌 이유 — 점검표에서
"아니오"가 나온 태스크는 재시도를 끄는 게 아니라 **멱등하게 고치는 것**이 정답입니다.

### 관제탑 안에서 연주까지 시킴

**증상** — PythonOperator 안에서 torch 학습을 직접 — Airflow 컨테이너가 메모리 부족으로
사망, 관제탑과 연주자가 함께 추락.
**원인** — "파이썬이니까 그냥 여기서" — 실행 환경(의존성·자원)의 분리 실패.
**해결** — 무거운 일은 밖으로: BashOperator로 별도 venv의 CLI 호출(오늘 방식), 더 나가면
컨테이너 실행(DockerOperator — 학습 환경을 이미지로 봉인, W24의 원리). 관제탑이 죽으면 모든
파이프라인의 눈이 꺼진다는 점에서, 분리는 안정성 설계입니다.

모델이 승격되는 사고)이 가능합니다. DAG에서는 하류 실행의 조건이 시각이 아니라 **상류의 성공**
그 자체이므로, Step 3에서 fetch가 최종 실패하자 preprocess 이후가 upstream_failed로 아예
실행되지 않았습니다. 오염 대신 명시적 정지 — "틀리게 계속"보다 "시끄럽게 멈춤"이 파이프라인
설계의 원칙입니다.

</details>

**Q2.** Airflow가 "지휘하되 연주하지 않는" 설계일 때, 이 과정에서 만들어 온 어떤 자산들이
그대로 재사용됐는지 셋 이상 꼽고, 그 자산들의 공통 설계 요소를 지적하세요.

<details>
<summary>답 보기</summary>

datapipe run(030 — 수집), make_dataset.py(전처리), train.py(070 — 학습 CLI), promote.py(132 —
평가·승격)가 BashOperator의 명령으로 그대로 태스크가 됐습니다. 공통 요소: ① **명령 한 줄로
실행되는 CLI 형태** (인자로 동작 제어 — --until 등), ② **종료 코드로 성공/실패를 정직하게
보고** (오케스트레이터의 판정 근거), ③ **멱등성** (재시도·백필의 전제), ④ 출력·로그의 표준
스트림 사용 (Airflow가 로그를 수집). 즉 "좋은 자동화 부품"의 요건은 도구(cron→Airflow)가
바뀌어도 동일합니다 — 부품을 잘 깎아 두면 지휘자는 갈아 끼울 수 있습니다.

</details>

**Q3.** 우리 DAG의 스케줄은 "매주 월 3시"입니다. 이 고정 주기의 낭비와 위험을 각각 하나씩
지적하고, 내일 배울 모니터링이 어떤 대안 트리거를 가능하게 할지 예상해 보세요.

<details>
<summary>답 보기</summary>

낭비: 데이터 분포가 안정적인 주에도 재학습이 돌아 계산 자원과 (검증·승격 판단의) 주의를
소모합니다 — 바뀐 게 없으면 새 모델도 거의 같습니다. 위험: 월요일 **전에** 급격한 변화(계절
급변·센서 교체)가 오면 최대 일주일간 낡은 모델로 서빙합니다 — 주기가 문제 발생 시점과 무관
하기 때문. 대안: 모니터링이 계산하는 **드리프트 지표가 임계치를 넘을 때** DAG를 트리거하는
조건 기반 재학습 (스케줄은 안전망으로 유지) — "시간이 아니라 신호가 방아쇠"가 Day 135 설계의
핵심 아이디어입니다.

</details>
