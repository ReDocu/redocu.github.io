## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 학습-서빙 불일치의 두 형태(변환 불일치 · **시점 불일치**)를 구분하고 감사할 수 있다.
- 피처 생성을 **공용 모듈 하나**로 통일해 학습과 서빙이 같은 코드를 쓰게 만들 수 있다.
- 모델 로드에 폴백(로컬 캐시)을 설계해 외부 의존(레지스트리) 장애를 흡수할 수 있다.
- 추론 API를 완성하고(검증·예측 로그), 시점 감사를 테스트로 고정할 수 있다.

## ② 왜 필요한가

오늘은 더미가 진짜가 되는 날입니다 — 그리고 이 과정에서 가장 유명한 함정이 기다리는
날이기도 합니다. [Day 100](../04-deep-learning-serving/day-100.md)에서 배운 학습-서빙
불일치는 그때 "변환의 불일치"(전처리 코드가 두 벌)였습니다. 오늘 만날 것은 더 교묘한
두 번째 형태, **시점의 불일치**입니다: 학습 테이블에서는 존재하던 피처가, 서빙의 그
순간에는 아직 세상에 존재하지 않는 것.

이 함정이 교묘한 이유는 **오프라인 평가가 절대 잡아내지 못하기** 때문입니다. 홀드아웃은
과거이고, 과거에는 모든 데이터가 이미 도착해 있습니다. lag_1(하루 전 값)은 홀드아웃
어느 행에서나 조회되지만, 내일을 예측하는 오늘의 서빙에서 "하루 전"은 아직 게시되지 않은
미래입니다(D-4 지연을 기억하세요). 모델은 홀드아웃에서 정직하게 좋았고, 서빙에서
정직하게 불가능합니다 — [Day 052](../03-machine-learning/day-052.md)의 시점 누수가
평가의 문제였다면, 오늘 것은 **배포의 문제**로 나타나는 같은 병입니다.

한산 팀은 오늘 이 함정을 정통으로 밟습니다. 밟는 장면과 빠져나오는 절차까지가 오늘의
교재입니다 — 여러분 팀도 자기 피처로 같은 감사를 오늘 반드시 하세요.

## ③ 개념 설명

### 학습-서빙 불일치의 두 형태

| 형태 | 정체 | 잡는 도구 |
|---|---|---|
| 변환 불일치 | 같은 입력을 다르게 가공 (코드 두 벌) | **공용 모듈** + 회귀 테스트 ([Day 104](../04-deep-learning-serving/day-104.md)) |
| 시점 불일치 | 서빙 시점에 없는 데이터를 학습이 사용 | **시점 감사** — 피처별 가용성 표 |

### 시점 감사 — 피처마다 "서빙의 그 순간" 을 묻는다

예측 대상일 T(내일), 예측 실행일 T−1(오늘), 게시 지연 D-4 기준:

| 피처 | 필요한 데이터 | 서빙 시점 가용? |
|---|---|---|
| lag_1 | T−1 (오늘) | ❌ 게시일은 T+3 — **불가** |
| lag_5 | T−5 | ✅ 정확히 최신 게시분 (연휴 시 결측 → lag_7 대체 규칙) |
| lag_7 · lag_14 | T−7 · T−14 | ✅ |
| dow · is_holiday | 달력 | ✅ 항상 |

규칙은 하나입니다: **k ≥ (지연 일수 + 1)인 lag만 서빙 가능.** 이 표를 학습 전에 그렸어야
했다는 것이 오늘의 교훈이고, 여러분은 그리면 됩니다 — 지금이 그 "학습 전"입니다.

### 공용 피처 모듈 — 두 벌 금지의 구현

```
src/features.py  →  학습(train.py)과 서빙(api)이 같은 함수를 임포트
build_features(station, target_date, conn)   # 조회는 DB에서 — 학습도 서빙도
```

학습 때는 과거의 각 날짜를 target_date로, 서빙 때는 내일을 target_date로 — **같은
함수가 두 문맥에서 돌므로** 변환 불일치는 구조적으로 사라집니다. 시점 불일치도 이
함수에 "target_date 이후 데이터 접근 금지" assert를 심어 함께 방어합니다.

### 모델 로드 폴백 — 145에서 수용한 그 설계

```
기동 → 레지스트리에서 운영 별칭 로드 → 성공: 로컬 캐시 갱신 → 서빙
                                   └→ 실패: 캐시의 마지막 성공본으로 서빙 (로그 경고)
```

외부 의존(MLflow)의 장애가 서비스 장애로 전파되지 않게 하는 최소 장치입니다.

## ④ 단계별 실습

### Step 1. 통합 착수 — 그리고 사고 (1~2교시)

민준과 지우가 피처 모듈을 공용화하고 내일 날짜로 첫 실예측을 시도합니다:

```
$ python -c "from src.features import build_features; build_features('강남', '2026-08-25')"
FeatureError: lag_1 unavailable for 2026-08-25 (latest published: 2026-08-20)
```

민준: "어? 홀드아웃에선 잘 됐는데요." — 그 문장이 진단명입니다. 긴급 15분 회의에서
시점 감사 표(③)를 그리고 결론: **exp-03(lag_1 포함)은 서빙 불가능한 모델. W30의 MAE
1,146은 서빙 시점에 재현 불가능한 숫자였다.** 이슈 #33 "학습-서빙 시점 불일치" 등록 —
사고를 사고라고 이름 붙이는 것까지가 절차입니다.

### Step 2. 수리 — 가용 lag로 재학습 (3~4교시)

```
$ python -m src.train.train --config configs/train.yaml   # lags: [5, 7, 14]
[train] data_md5 e91c07a4 · features 8 · MAE 1183.2 · MAPE 4.8% · 등급 0.8517
[train] MLflow run b7d31a52 → registered: hansan-daily v2 (v1: archived — 사유 링크 #33)
```

새 성적표: **MAE 1,183 · 등급 0.85 — 베이스라인 대비 −38.2%, 품질 목표(≤1,531 · ≥0.85)
여전히 통과.** 1,146과의 차이 37명이 lag_1이 "빌려 왔던 미래"의 값어치였던 셈입니다.
v1은 서빙된 적 없이 보관 처리되고, 폐기 사유가 #33에 링크됩니다 — 레지스트리가 모델의
이력서라는 것([Day 132](../05-infra-mlops/day-132.md))이 이런 순간을 위한 규율입니다.

### Step 3. /predict 완성 (5~6교시)

모델 로드(+폴백) · 입력 검증 · 등급 계산 · 예측 로그까지 연결하고 실호출:

```
$ curl -s localhost:8080/predict -X POST -H "Content-Type: application/json" \
    -d '{"station": "강남", "date": "2026-08-25", "hour": 8}'
{"station":"강남","date":"2026-08-25","hour":8,"level":"혼잡","congestion":0.87,
 "expected_boardings":9120,"baseline_p90":10480,"model_version":"hansan-daily-v2"}
```

- 등급 계산: 일 예측 × 시간대 share(8시) = 9,120 → ÷ P90(10,480) = 0.87 → **혼잡**
- 폴백 시험: mlflow 컨테이너를 잠깐 내리고 api 재시작 → 캐시본으로 기동 + 경고 로그 확인
- 예측 로그: prediction_log에 (입력·출력·model_version·latency_ms) 1행 — [Day 154](day-154.md)
  대시보드의 원재료
- **데모 페이지는 한 줄도 안 바꿨는데 진짜 등급이 나옵니다** — 144에서 더미의 형식을
  명세와 같게 만든 것의 보상이 오늘 지급됐습니다.

### Step 4. 감사를 테스트로 고정 (7~8교시)

```python
def test_no_future_access():          # 시점 감사의 영구화
    feats = build_features("강남", tomorrow(), conn)
    assert feats.newest_source_date <= latest_published(conn)

def test_regression_prediction():     # 회귀 대조 (Day 104의 방식)
    assert predict_one(FIXED_INPUT) == pytest.approx(9120, abs=1)
```

```
$ pytest -q
19 passed in 8.6s
```

□ /predict 실응답 + 폴백 시험 로그 □ 예측 로그 적재 확인 □ 시점 감사·회귀 테스트 통과

## ⑤ 자주 하는 실수

### 피처 로직을 서빙 쪽에 다시 씀

**증상** — 학습은 pandas로, 서빙은 SQL로 "같은" lag를 계산 — 결측 처리 한 끗 차이로
예측이 미묘하게 어긋나는데 아무도 모름.
**원인** — "서빙은 빨라야 하니까 따로 짜야지"의 성급한 최적화.
**해결** — 공용 모듈이 기본값입니다. 성능 문제가 **실측으로 확인된 뒤에만**(154의 부하
측정) 최적화를 논하세요 — 그때도 회귀 테스트가 두 구현의 일치를 증명해야 합니다.

### "홀드아웃에서 됐으니 됐다"

**증상** — 오프라인 지표만 보고 배포 — 서빙에서 피처 NULL, 또는 몰래 최신값을 당겨 쓰는
코드가 들어가며 성능이 소리 없이 붕괴.
**원인** — 오프라인 가용성과 온라인 가용성을 같은 것으로 취급.
**해결** — 시점 감사 표를 **학습 전에** 그리는 것을 팀 절차로 (한산 팀은 오늘 배웠고,
문서 독자인 여러분은 오늘 무료로 배웠습니다). 감사의 자동화가 test_no_future_access
입니다 — 사람은 잊지만 CI는 잊지 않습니다.

### 외부 의존에 폴백 없음

**증상** — MLflow 컨테이너 재시작 30초 동안 api도 기동 실패 — 부팅 순서에 따라 서비스
전체가 안 뜨는 복불복.
**원인** — "레지스트리는 항상 떠 있겠지" — 분산 시스템에서 '항상'은 없습니다.
**해결** — 로드 경로마다 "이게 죽어 있으면?"을 묻고([Day 145](day-145.md)의 질문이
바로 이것이었습니다), 답이 "서비스도 죽음"이면 폴백을 답니다. 오늘의 캐시 폴백은 20줄
짜리 보험입니다.

### 사고를 조용히 덮음

**증상** — 보고서와 발표에 1,146이 계속 등장 — 심사 질의 "서빙에서 lag_1은 어떻게
얻나요?" 한 방에 프로젝트 전체의 신뢰 붕괴.
**원인** — 정정을 실패의 자백으로 오해.
**해결** — 반대입니다: **발견·수리·재발 방지(테스트)까지 갖춘 사고 기록은 이 프로젝트가
만들 수 있는 가장 값진 전시물입니다.** 156의 보고서에 "사고와 수리" 절로, 159의 발표에
한 장으로 넣습니다 — 실무자 심사위원이 가장 오래 기억할 장이 그 장입니다.

## ⑥ 확인 문제

**Q1.** exp-03의 MAE 1,146이 "거짓 숫자"인 이유를, Day 052의 무작위 분리 누수와 오늘의
시점 불일치가 같은 병의 두 얼굴이라는 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

두 경우 모두 본질은 "예측 시점에 알 수 없는 정보가 학습·평가에 스며든 것"입니다. 052의
무작위 분리는 미래 행 자체가 학습에 섞여 평가를 부풀렸고, 오늘의 lag_1은 행은 과거지만
그 행의 피처가 서빙 순간에는 아직 게시되지 않은 값이라 평가(과거에선 조회됨)와 서빙
(현재에선 부재)의 조건이 달랐습니다. 즉 1,146은 "서빙에서는 성립하지 않는 정보 조건"
에서 잰 성적이므로, 서비스가 실제로 낼 수 있는 성능의 추정치가 아닙니다. 교훈의 일반형:
평가는 서빙의 리허설이어야 하며, 리허설의 조건(사용 가능한 정보의 시점)이 본공연과
다르면 그 평가는 무엇을 측정했든 서비스 성능은 아닙니다.

</details>

**Q2.** 시점 감사 규칙 "k ≥ 지연+1인 lag만 가능"을 이 팀의 조건(D-4, 내일 예측)에 적용해
lag_5가 경계값임을 보이고, 연휴로 지연이 D-6이 되는 날 lag_5 피처에 생기는 일과 팀의
대체 규칙이 왜 합리적인지 설명하세요.

<details>
<summary>답 보기</summary>

대상일 T의 lag_k는 T−k 데이터를 요구하고, 예측 실행일 T−1에 게시 완료된 최신 데이터는
(T−1)−4 = T−5입니다. 따라서 T−k ≤ T−5, 즉 k ≥ 5 — lag_5가 정확히 경계(여유 0일)입니다.
연휴로 지연이 D-6이 되면 최신 게시분이 T−7이 되어 lag_5는 결측이 됩니다. 대체 규칙
(lag_7 값으로 대체)이 합리적인 이유: ① lag_7은 같은 요일이라 분포가 가장 가깝고(주간
주기), ② 모델 입력의 형태를 유지해 서빙이 멈추지 않으며, ③ 대체 발생이 로그에 남아
"연휴 직후 예보는 정확도 저하"라는 한계를 정량 추적할 수 있습니다. 완벽한 값이 아니라
**정직하게 기록되는 근사값**이라는 점이 핵심입니다.

</details>
