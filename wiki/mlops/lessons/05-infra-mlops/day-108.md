## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **GitHub Flow**(브랜치 → PR → 리뷰 → 병합 → 삭제)의 다섯 단계를 실제로 한 바퀴 돌 수 있다.
- 리뷰어가 5분 안에 파악할 수 있는 **PR 제목·본문**을 쓸 수 있다.
- 동료의 PR에 **근거 있는 리뷰 코멘트**를 달고, 받은 리뷰를 추가 커밋으로 반영할 수 있다.
- 병합 방식 세 가지(merge commit · squash · rebase)의 차이를 알고 팀 기준으로 고를 수 있다.

## ② 왜 필요한가

어제까지 여러분의 코드가 main에 들어가는 경로는 `git push` 한 줄 — **아무도 안 보고, 아무것도
안 막는** 경로였습니다. 혼자일 땐 문제가 없지만, 팀에서는 이 경로가 곧 사고 경로입니다:

```
지금:    내 커밋 ──(push)──▶ main = 곧 서비스           아무 관문 없음
이번 주: 내 커밋 ──▶ PR ──▶ 리뷰 ✓ ──▶ 병합 ──▶ main    사람의 관문
W26:     내 커밋 ──▶ PR ──▶ 리뷰 ✓ + 테스트 ✓ ──▶ 병합   사람 + 기계의 관문
```

PR(Pull Request)은 "내 브랜치를 main에 **당겨가 달라(pull)는 요청서**"입니다. 요청서이기 때문에
합쳐지기 **전에** 대화가 생깁니다 — 코드 리뷰, 질문, 수정 요청, 그리고 W26부터는 자동 테스트까지
전부 이 요청서 위에서 벌어집니다. **PR은 협업의 문서이자, 앞으로 만들 모든 자동화가 매달릴 고리**입니다.

그리고 취업 관점 하나 — 채용 담당자가 포트폴리오 저장소에서 커밋 목록 다음으로 보는 것이
PR 탭입니다. "PR 없이 main 직행"인 저장소와 "리뷰 대화가 남아 있는" 저장소는 협업 경험의 증거력이
다릅니다. 오늘부터 MP3 저장소의 모든 변경을 PR로 넣습니다.

## ③ 개념 설명

### GitHub Flow — 다섯 단계 한 바퀴

여러 브랜치 전략 중 가장 단순하고, 이 과정과 MP4가 채택하는 전략입니다.

| 단계 | 행동 | 규칙 |
|---|---|---|
| 1 브랜치 | `git switch -c feature/이름` | main에서 딴다 · 작업 단위 하나 = 브랜치 하나 |
| 2 PR | push 후 GitHub에서 PR 생성 | 제목·본문으로 의도를 설명 |
| 3 리뷰 | 동료가 코멘트 · 수정 요청 | 반영은 같은 브랜치에 **추가 커밋** |
| 4 병합 | 승인 후 Merge 버튼 | **main은 항상 배포 가능** 상태 유지 |
| 5 삭제 | 병합된 브랜치 삭제 | 브랜치는 소모품 — 오래 살수록 충돌만 자람 |

핵심 원칙은 4단계에 숨어 있습니다: **main은 언제 배포해도 되는 상태**여야 한다.
그래서 미완성 코드는 main이 아니라 브랜치에 살고, 관문(리뷰·테스트)을 통과한 것만 main에 들어갑니다.
W23에서 서버에 올라가는 것도, W26에서 자동 배포되는 것도 언제나 main입니다.

### 좋은 PR — 리뷰어의 5분을 설계한다

| 항목 | 나쁨 | 좋음 |
|---|---|---|
| 크기 | 파일 23개, +1,842줄 ("이번 주 작업 전부") | **한 가지 일**, ±300줄 이내 목표 |
| 제목 | `수정`, `fix` | `업로드 검사 순서 변경: 크기 검사를 내용 검증보다 앞으로` |
| 본문 | (비어 있음) | 무엇을/왜/어떻게 확인했나 3절 |

본문 템플릿 — 오늘부터 MP3 저장소의 `.github/PULL_REQUEST_TEMPLATE.md` 로 저장해 두면
PR을 열 때마다 자동으로 채워집니다:

```markdown
## 무엇을
<!-- 이 PR이 하는 일 한 문단 -->

## 왜
<!-- 배경·문제 상황. 이슈가 있으면 #번호 -->

## 확인 방법
<!-- 리뷰어가 검증할 수 있는 절차: 실행 명령, 테스트, 스크린샷 -->
```

### 리뷰 예절 — 코드에 말하고, 근거를 달고, 등급을 붙인다

| 원칙 | 나쁨 | 좋음 |
|---|---|---|
| 사람이 아니라 코드에 | "왜 이렇게 짰어요?" | "이 분기는 어떤 입력에서 타나요?" |
| 지적에는 근거 | "이건 별로예요" | "요청마다 open()하면 Day 096의 로드 문제와 같은 계열이라, lifespan으로 옮기면 어떨까요" |
| 중요도 표시 | 전부 같은 톤 | **[must]** 병합 전 수정 / **[q]** 질문 / **[nit]** 취향, 무시 가능 |
| 칭찬도 리뷰 | (지적만) | "3중 검사 순서 좋네요 — 큰 파일이 일찍 걸러지겠어요" |

리뷰를 **받는** 예절은 하나입니다: 코멘트는 코드에 대한 것이지 나에 대한 것이 아니다.
동의하면 반영 커밋, 동의하지 않으면 근거를 달아 토론 — 무반응이 유일한 결례입니다.

### 병합 버튼의 세 가지 얼굴

GitHub의 Merge 버튼에는 세 방식이 있습니다 — 어제 배운 두 문체가 여기서 다시 나옵니다.

| 방식 | 하는 일 | main 히스토리 | 언제 |
|---|---|---|---|
| **Merge commit** | 병합 커밋 생성 | 브랜치의 커밋들 + ◆ | 과정 커밋도 의미 있을 때 |
| **Squash and merge** | 커밋 전부를 **하나로 뭉쳐** 병합 | PR 하나 = 커밋 하나 | "wip", "오타" 커밋이 많을 때 · **이 과정의 기본값** |
| Rebase and merge | 커밋들을 main 끝에 재적용 | 직선 (병합 표식 없음) | 팀이 직선 히스토리를 강하게 원할 때 |

이 과정은 **squash**를 기본으로 합니다 — feature 브랜치에서는 자유롭게 커밋하고,
main에는 "PR 단위의 깔끔한 한 줄"만 남기는 절충안이라 초심 팀에 사고가 가장 적습니다.

## ④ 단계별 실습

오늘은 **2인 1조**입니다 — 서로의 `mlops-mp3` 에 리뷰어로 초대합니다.
(혼자 진행하는 경우: 두 계정 또는 셀프 리뷰로 흐름은 동일하게 밟을 수 있습니다. Approve만
본인 PR에는 불가하니 코멘트로 대신합니다.)

### Step 1. 리뷰어 초대와 템플릿 (1교시)

GitHub에서 `mlops-mp3` → Settings → Collaborators → **Add people** 로 짝을 초대합니다.
그리고 첫 PR 준비로 위의 PR 템플릿을 저장소에 넣습니다:

```powershell
cd mlops-mp3
git switch -c chore/pr-template
mkdir .github
# (위 템플릿 내용을 .github/PULL_REQUEST_TEMPLATE.md 로 저장)
git add .github; git commit -m "PR 템플릿 추가"
git push -u origin chore/pr-template
```

```
$ git push -u origin chore/pr-template
Enumerating objects: 5, done.
...
remote: Create a pull request for 'chore/pr-template' on GitHub by visiting:
remote:      https://github.com/mlops-student/mlops-mp3/pull/new/chore/pr-template
To github.com:mlops-student/mlops-mp3.git
 * [new branch]      chore/pr-template -> chore/pr-template
branch 'chore/pr-template' set up to track 'origin/chore/pr-template'.
```

push 출력이 **PR 생성 주소를 직접 알려 줍니다.** 접속해서 첫 PR을 열고 짝을 Reviewers에 지정 —
이 PR 자체가 오늘의 워밍업 리뷰 대상입니다.

### Step 2. 실전 PR — 기능 하나를 관문으로 통과시키기 (2~4교시)

각자 자기 저장소에서 **작은 실제 개선** 하나를 PR로 만듭니다. 추천 주제 (하나 선택):

- `/health` 응답에 모델 버전·기동 시각 추가 ([Day 096](../04-deep-learning-serving/day-096.md) 과제의 정식 반영)
- 업로드 에러 메시지에 허용 형식·최대 크기 명시 (413/415 응답 개선)
- README의 실행 절차를 clone 리허설 기준으로 갱신 ([Day 104](../04-deep-learning-serving/day-104.md))

```powershell
git switch main; git pull
git switch -c feature/health-verbose
# ... 코드 수정 + pytest 확인 ...
git commit -am "health 응답에 model_version과 시작 시각 추가"
git push -u origin feature/health-verbose
```

PR 본문은 템플릿을 채웁니다. "확인 방법"에는 리뷰어가 돌릴 수 있는 명령을 그대로:

```markdown
## 무엇을
/health 응답에 model_version, started_at 필드를 추가했습니다.

## 왜
운영에서 "지금 떠 있는 서버가 어떤 모델을 물고 있나"를 헬스체크만으로 확인하기
위해서입니다 (Day 096 과제 ①의 정식 반영). W25의 컨테이너 헬스체크가 이 응답을 씁니다.

## 확인 방법
uvicorn app.main:app --port 8000 → GET /health
→ {"status":"ok","model_loaded":true,"model_version":"resnet18-antbee-v1","started_at":"..."}
pytest -q → 7 passed (test_health_reports_model 이 새 필드 검증)
```

### Step 3. 리뷰어 되기 (5~6교시)

짝의 PR에서 **Files changed** 탭 → 줄 번호에 마우스를 올려 `+` → 코멘트.
오늘 과제 기준: **[must]/[q]/[nit] 합쳐 5개 이상**, 그중 최소 1개는 칭찬. 예시:

> **[q]** `started_at`을 lifespan에서 찍으셨는데, 워커가 여러 개면 워커마다 값이 다를 텐데
> 의도인가요? (지금은 워커 1이라 문제없지만 W25에서 만날 상황이라 여쭤요)
>
> **[nit]** ISO 8601이면 `datetime.now(timezone.utc).isoformat()` 쪽이 타임존 명시적이라
> 로그와 맞을 것 같아요 — Day 098에서 로그를 UTC로 통일했었죠.
>
> 3중 검사 순서를 안 건드리고 응답만 확장한 점 좋았습니다 — diff가 작아서 5분 리뷰가 되네요.

마무리는 **Review changes** 버튼에서 셋 중 하나: Comment(의견만) / **Approve**(승인) /
**Request changes**(수정 전 병합 반대). [must]가 하나라도 있으면 Request changes가 정직합니다.

### Step 4. 반영, 병합, 청소 (7교시)

리뷰 받은 사람은 **같은 브랜치에 추가 커밋**으로 반영합니다 (force push 금지 — ⑤ 참고):

```powershell
git commit -am "리뷰 반영: started_at을 UTC ISO 8601로"
git push
```

push 만으로 PR이 자동 갱신되고, 리뷰어가 재확인 후 Approve → **Squash and merge** →
**Delete branch**. 이제 로컬 청소:

```powershell
git switch main
git pull
git branch -d feature/health-verbose
git fetch --prune
```

```
$ git pull
Updating 41c8e07..b6f92d3
Fast-forward
 app/main.py           |  9 ++++++---
 tests/test_api.py     |  4 +++-
 2 files changed, 10 insertions(+), 3 deletions(-)
$ git branch -d feature/health-verbose
warning: deleting branch 'feature/health-verbose' that has been merged to
         'refs/remotes/origin/feature/health-verbose', but not yet merged to HEAD.
Deleted branch feature/health-verbose (was 8c1d940).
```

> warning이 뜨는 이유 — squash 병합은 브랜치의 커밋들을 **새 커밋 하나로 뭉쳐** main에 넣었기
> 때문에, Git 눈에는 원래 커밋들이 "main에 병합 안 된" 것으로 보입니다. squash를 쓰는 팀에서는
> 정상적인 메시지입니다 (내용은 이미 main에 있습니다).

### Step 5. 과제 (8교시)

**리뷰 코멘트 5개.** 오늘 짝의 PR에 단 코멘트 5개를 [must]/[q]/[nit] 분류와 함께 정리해 제출하세요.
각 코멘트에 대해 한 줄씩: 근거로 든 것은 무엇이었나 (배운 날짜, 문서, 실측 숫자 등).
그리고 자신이 **받은** 코멘트 중 가장 유익했던 것 하나와 그 이유.

## ⑤ 자주 하는 실수

### main에 직접 커밋해 버림

**증상** — 습관대로 main에서 작업하고 커밋까지 함 — PR로 넣을 방법이 없어 보임.
**원인** — 1단계(브랜치부터)를 건너뜀. 3주쯤은 누구나 한 번 합니다.
**해결** — 커밋을 아직 push 안 했다면 구제는 두 줄입니다:
```powershell
git branch feature/rescue      # 지금 커밋을 가리키는 브랜치를 만들고
git reset --hard origin/main   # main만 원격 상태로 되돌림 (내일 정식 수업)
```
브랜치에 작업이 안전하게 남고, main은 깨끗해집니다. push까지 했다면 팀에 알리고 [Day 109](day-109.md)의
revert로.

### PR이 너무 큼

**증상** — 파일 23개 ±1,800줄 PR — 리뷰어가 일주일 미루다 "LGTM 👍" 한 줄로 승인 (사실상 무리뷰).
**원인** — "기능이 다 되면 PR"이라는 오해. PR 단위 = 완성 단위가 아니라 **리뷰 가능 단위**입니다.
**해결** — 쪼개세요: 리팩터링 PR → 기능 PR → 테스트/문서 PR 식의 연속 PR이 정석입니다.
경험칙: **diff가 화면 3~4장을 넘으면 리뷰 품질이 급락**합니다.

### 리뷰 반영을 force push로

**증상** — 리뷰 반영 후 커밋을 amend/rebase 해서 `--force` push — 리뷰어의 코멘트가 달려 있던
커밋이 사라져 "Outdated" 표시로 맥락이 끊기고, 무엇이 바뀌었는지 diff 추적이 안 됨.
**원인** — "깔끔한 커밋" 욕심이 리뷰 중인 공유 브랜치에서 발동 (황금률의 PR 버전).
**해결** — **리뷰 중에는 추가 커밋**으로만 반영하세요. 지저분해진 커밋들은 병합 때 squash가
한 줄로 정리해 줍니다 — 그래서 squash 기본값이 초심 팀에 안전합니다.

### 병합 후 로컬 main을 안 갱신하고 다음 브랜치를 땀

**증상** — 다음 PR에 **지난 PR의 diff가 통째로 다시** 들어 있음 — 리뷰어 혼란.
**원인** — 원격 main은 병합으로 전진했는데, 로컬 main이 옛날인 채 `switch -c` — 옛 지점에서
갈라진 겁니다.
**해결** — 브랜치 따기 전 의식처럼: `git switch main` → `git pull` → `git switch -c ...`.
Step 4의 청소 절차를 몸에 붙이세요.

### Approve를 "친분"으로

**증상** — 안 읽고 Approve ("바쁜데 서로 좋게좋게") — 관문이 형식이 되고, 몇 주 뒤 사고 코드의
PR에 자기 승인이 박혀 있는 걸 발견.
**원인** — 리뷰를 호의/평가로 오해. 리뷰는 **품질의 공동 책임 서명**입니다.
**해결** — 최소 기준을 팀 규칙으로: "확인 방법"을 실제로 실행해 보고 Approve. 시간이 없으면
"오늘 못 봅니다"가 무리뷰 승인보다 낫습니다. Day 110에서 이 기준을 팀 규칙 문서로 명문화합니다.

겁니다. main에 미완성 코드가 들어올 수 있다면 자동 배포는 러시안룰렛이 됩니다. "관문을 통과한
것만 main에" 규칙이 지켜질 때에만 "main 병합 = 배포"라는 자동화 등식이 성립합니다 — PR 워크플로는
CI/CD의 전제 조건입니다.

</details>

**Q2.** squash 병합을 기본값으로 쓰는 팀에서, 병합 후 `git branch -d` 시 나오는 warning의 원인과
그것이 무해한 이유를 설명하세요.

<details>
<summary>답 보기</summary>

squash는 브랜치의 커밋들을 그대로 가져가지 않고 **내용만 뭉친 새 커밋**을 main에 만듭니다.
그래서 Git의 조상 추적으로는 원래 커밋들이 main에 "병합된 적 없음"으로 보여 warning이 납니다.
하지만 변경 내용 자체는 새 커밋으로 main에 전부 들어가 있으므로 브랜치를 지워도 잃는 것이
없습니다 — 조상 관계와 내용 포함 여부가 다를 수 있다는 걸 보여 주는 사례입니다.

</details>
