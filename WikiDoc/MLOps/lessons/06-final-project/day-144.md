## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 요구사항을 **1일 이하 크기의 이슈**로 쪼갠 스프린트 백로그를 만들 수 있다.
- "전원이 코드를 쓰는" 역할 분담을 백로그 위에서 확인할 수 있다.
- **걷는 뼈대**(walking skeleton) — 더미 응답이지만 전 구간이 연결된 빈 서비스 — 를
  세우고 CI를 붙일 수 있다.
- 클라우드 인스턴스를 수령해 배포 대상 서버의 기초 세팅을 마칠 수 있다.

## ② 왜 필요한가

어제까지 만든 것은 전부 문서입니다. 문서는 필요조건이지만, 문서만으로 2주 스프린트에
들어가면 두 가지가 없습니다.

첫째, **진척의 단위**가 없습니다. "아키텍처대로 만들자"는 진행률을 잴 수 없고, 잴 수
없는 것은 관리할 수 없습니다. 백로그는 계획을 "닫을 수 있는 이슈"의 목록으로 바꾸는
작업입니다 — 매일 닫힌 이슈 수가 곧 진척이고, 스탠드업의 공용 언어가 됩니다.

둘째, **통합의 뼈대**가 없습니다. 부품(수집·모델·API)을 각자 만들어 마지막에 붙이는
전략의 위험은 어제 배웠습니다 — 그 반대 전략이 걷는 뼈대입니다: **첫날에 전 구간을
더미로 연결해 두고, 이후 모든 작업은 동작하는 전체에 진짜 부품을 갈아 끼우는 일**이
되게 하는 것. 뼈대가 서 있으면 통합 문제는 매일 조금씩 발견되고, 뼈대가 없으면 W31에
한꺼번에 발견됩니다.

그리고 여러분에겐 뼈대를 하루 만에 세울 자산이 이미 있습니다 — [Day 140](../05-infra-mlops/day-140.md)
회고의 Try("팀 저장소를 이 파이프라인의 템플릿에서 시작")를 오늘 실행합니다.

## ③ 개념 설명

### 백로그 항목의 규격 — 이슈 하나의 조건

| 조건 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 크기 1일 이하 | "모델 만들기" | "베이스라인(지난주 같은 요일) 평가 스크립트" |
| 완료의 정의 | "수집 개발" | "…실행 시 어제 D-4분 51행이 upsert된다 (확인 SQL 포함)" |
| 담당 1명 | "데이터팀" | "@서연" (리뷰는 짝이) |
| 의존 명시 | — | "#6(스키마) 이후 착수 가능" |

"1일 이하"가 안 되는 항목은 **쪼개는 것이 담당자의 첫 작업**입니다. 큰 이슈는 3일째
"진행 중"으로 스탠드업을 침묵시키는 주범입니다.

### 스프린트 계획 — 상세한 것은 이번 주만

4주 전체를 오늘 다 계획하지 않습니다. **W30 백로그만 이슈 단위로 상세히**, W31은 굵은
덩어리로, W32는 커리큘럼의 틀 그대로 둡니다 — W30이 끝난 뒤의 우리가 지금의 우리보다
더 잘 알기 때문입니다 ([Day 150](day-150.md) 리뷰에서 W31을 상세화합니다).

### 걷는 뼈대 — 관통 먼저, 내용물은 나중

```
오늘의 뼈대:  수집(빈 스크립트) → db(스키마만) → 모델(상수 반환) → API(더미 등급) → compose up
2주 뒤 완성:  수집(진짜)       → db(48,756행)  → 모델(LightGBM)  → API(진짜 등급)  → CI/CD 배포
```

뼈대의 조건은 하나 — **오늘 clone → `docker compose up` → 응답이 온다.** 내용은 전부
가짜여도 됩니다. 이 순간부터 "우리 서비스는 항상 동작하는 상태"가 팀의 기본값이 되고,
그것을 깨는 PR은 CI가 막습니다.

### 템플릿 재사용 — 베끼기가 아니라 자산 회수

mlops-mp3의 `ci.yml`·`build.yml`·`compose.yaml`·`Dockerfile`은 7주에 걸쳐 검증된
자산입니다. 복제 후 서비스 이름·포트·이미지명을 바꾸는 것으로 CI/CD 골격이 하루 만에
섭니다. 단, **줄마다 "왜 있는지" 설명할 수 있어야** 자산이지, 설명 못 하면 부채입니다 —
리뷰 짝이 "이 줄 왜 있어요?"를 물어 주는 것이 오늘의 리뷰 포인트입니다.

## ④ 단계별 실습

### Step 1. 백로그 작성 (1~3교시)

요구사항 문서(142)의 필수 기능을 이슈로 분해합니다. 한산 팀의 W30 백로그 발췌
(GitHub Projects 보드에 등록):

| # | 이슈 | 담당 | 의존 |
|---|---|---|---|

| 6 | 수집 스크립트 — 일별 API 호출·2호선 필터·upsert (일 1,000회 제한 고려) | 서연 | #5 |
| 7 | 백필 스크립트 — 2024-01-01부터, 재실행 안전 | 서연 | #6 |

| 9 | mart_daily_features 뷰 + 피처 정의 문서 | 민준 | #5 |
| 10 | 평가 설계 + 베이스라인 스크립트 (홀드아웃 확정) | 민준 | #9 |
| 11 | LightGBM 학습 스크립트 + MLflow 기록 | 민준 | #10 |

전원의 이름이 백로그에 있는지 — "전원이 코드 작성" 규칙의 실체 검사가 바로 이 표입니다.

### Step 2. 걷는 뼈대 세우기 (4~6교시)

하람이 mlops-mp3에서 골격을 복제하고([Day 140](../05-infra-mlops/day-140.md) Try의 실행),
지우가 API 뼈대를 채웁니다:

```
$ git log --oneline -4
9a41f02 (#4) ci: mlops-mp3 ci.yml 이식 — 서비스명·경로만 교체
f3c78d1 (#3) feat: /predict 더미 응답 + /health
b82d509 (#2) chore: compose 뼈대 (api + db) — pgdata 볼륨
c1e04a7 (#1) chore: src 레이아웃 + ruff + pytest 세팅
```

뼈대 검증 — 오늘의 완료 조건:

```
$ docker compose up -d --build && sleep 5 && curl -s localhost:8080/predict \
    -X POST -H "Content-Type: application/json" \
    -d '{"station": "강남", "date": "2026-08-12", "hour": 8}'
{"station":"강남","date":"2026-08-12","hour":8,"level":"보통","congestion":0.5,
 "expected_boardings":0,"baseline_p90":0,"model_version":"dummy"}
```

응답 형식이 어제 확정한 API 명세와 **완전히 같은 모양**임에 주목 — 더미의 가치는 값이
아니라 **계약의 조기 검증**입니다. 데모 페이지(#13)는 내일부터 이 더미로 개발됩니다.

### Step 3. CI 가동 (7교시)

이식한 `ci.yml`(lint + pytest)이 PR에서 실제로 도는지 확인하고, 브랜치 보호의 필수
검사로 등록합니다 ([Day 127](../05-infra-mlops/day-127.md)의 절차 그대로). 테스트는
아직 2개(健康검사·더미 계약)지만, **빨간 PR이 물리적으로 못 들어오는 상태**가 오늘부터
시작된다는 것이 중요합니다.

### Step 4. 클라우드 인스턴스 기초 세팅 (8교시)

팀별 인스턴스를 수령하면 W23의 절차를 그대로 재연합니다 — 이번엔 진짜 원격 서버입니다:

- `deploy` 서비스 계정 생성 (sudo 불가, [Day 112](../05-infra-mlops/day-112.md))
- SSH 키 기반 접속 + 비밀번호 로그인 차단 ([Day 114](../05-infra-mlops/day-114.md))
- Docker Engine 설치, `deploy`를 docker 그룹에
- 확인: 팀원 전원이 자기 키로 접속해 `docker ps`가 도는 것까지

self-hosted runner 등록은 CD를 붙이는 [Day 153](day-153.md)에서 합니다 — 오늘은 서버가
"우리 것"이 된 상태까지.

**오늘 퇴근 체크** — □ W30 백로그(전원 이름 등장·완료의 정의) □ clone→up→더미 응답
□ CI가 PR을 실제로 막는 것 확인 □ 인스턴스 접속(전원) □ 내일 리뷰용 설계 문서 링크 정리

## ⑤ 자주 하는 실수

### 백로그 항목이 덩어리

**증상** — "#7 모델 개발" 이슈가 6일째 진행 중 — 스탠드업이 "계속 하고 있어요"만 반복.
**원인** — 크기 규격(1일 이하) 무시.
**해결** — 3일 이상 열려 있는 이슈는 무조건 분해 대상입니다. 쪼개기 어렵다면 대개
완료의 정의가 없어서입니다 — "무엇이 되면 닫히는가"부터 쓰세요.

### 뼈대 없이 부품부터

**증상** — 각자 열심히 2주 — W31 월요일 첫 통합에서 컬럼명·형식·포트가 전부 어긋남.
**원인** — "내 파트 먼저 완성하고 붙이자"의 병렬 착각.
**해결** — 오늘 뼈대가 서면 이후 모든 PR은 **동작하는 전체를 통과**해야 병합됩니다
(CI가 계약 테스트를 돌리므로). 통합을 이벤트가 아니라 일상으로 만드는 것 — 지속 통합
(CI)의 "통합"이 원래 이 뜻입니다.

### 템플릿 재사용을 부정행위처럼 여김

**증상** — "우리 힘으로 처음부터" — CI 골격에 이틀, 스프린트 시작 전에 이미 지연.
**원인** — 학습 과제와 프로젝트의 혼동: 과제는 과정이 목적이지만 프로젝트는 산출이 목적.
**해결** — 검증된 자기 자산의 재사용은 실무 그 자체입니다 (실무에서 CI를 매번 백지에서
쓰는 팀은 없습니다). 단 ③의 조건 — 줄마다 설명 가능 — 을 지켜야 심사 질의에서 자산임을
증명할 수 있습니다.

### 인스턴스 세팅을 "배포 주간에"

**증상** — Day 153에 처음 서버 접속 — 방화벽·키·권한 문제로 CD 하루를 세팅에 소모.
**원인** — 서버 세팅을 CD의 부속 작업으로 분류.
**해결** — 서버는 **W30 내내 쓰입니다** (짝 환경 재현 확인·중간 데모). 오늘 15분의
세팅이 153의 반나절을 삽니다. W23에 전부 해 본 작업이라 오늘이 가장 쌉니다.

## ⑥ 확인 문제

**Q1.** 걷는 뼈대의 조건이 "기능이 있다"가 아니라 "전 구간이 연결되어 응답한다"인 이유를,
통합 위험의 발견 시점 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

프로젝트의 큰 위험은 부품 내부가 아니라 부품 사이(계약 불일치·환경 차이·포트/스키마
어긋남)에 있고, 이 위험은 연결을 시도해야만 드러납니다. 뼈대는 내용물 없이 연결만 먼저
만들어 그 위험을 첫날에 전부 노출시키는 장치입니다 — 이후 남는 위험은 부품 내부(잘
쪼개진 이슈 단위)뿐이라 매일의 PR로 조금씩 소화됩니다. 기능부터 만들면 반대가 됩니다:
쉬운 위험(내부)을 먼저 풀고 비싼 위험(연결)을 마지막에 — 남은 시간이 가장 적을 때 가장
큰 위험을 만나는 배치입니다.

</details>

**Q2.** 더미 `/predict` 응답이 "값은 가짜지만 형식은 명세와 완전히 같아야" 하는 이유를,
병렬 작업(#13 데모 페이지)과 계약 테스트 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

데모 페이지는 오늘부터 이 더미를 상대로 개발됩니다 — 형식이 명세와 같으면 진짜 모델이
연결되는 날(151) 페이지는 한 줄도 안 바꿔도 됩니다. 형식이 다르면 더미 기준으로 짠
페이지가 통합 시점에 재작업됩니다(더미가 오히려 부채가 됨). 계약 테스트 관점: CI의
계약 테스트는 응답의 필드·타입을 검증하는데, 더미가 명세를 따르면 이 테스트가 첫날부터
가동되어 이후 누가 응답 형식을 깨면 즉시 빨간불이 됩니다 — 즉 형식이 같은 더미는 계약을
"문서"에서 "실행되는 검사"로 승격시키는 도구입니다.

</details>

**Q3.** "W30만 상세히, W31은 굵게, W32는 틀만" — 계획의 해상도를 시점에 따라 달리하는
이유를 설명하고, 이 방식에서 W31 계획이 상세화되는 최적 시점과 그 근거를 답하세요.

<details>
<summary>답 보기</summary>

계획의 정확도는 정보량에 비례하는데, 먼 주차일수록 지금 없는 정보(실제 속도, 발견될
문제, 데이터의 배신)에 의존합니다. 지금 W31을 이슈 단위로 상세화하면 그 계획은 낮은
정보로 만든 높은 해상도 — 겉보기만 정밀한 허위 정확도이고, 유지 비용(재계획)만 늘립니다.
W31의 상세화 최적 시점은 [Day 150](day-150.md) 스프린트 리뷰 직후입니다 — W30의 실측
속도(계획 대비 실제 닫힌 이슈), 중간 데모에서 드러난 문제, 조정된 범위라는 최신 정보가
모두 모이는 시점이기 때문입니다. 계획은 한 번 세우는 문서가 아니라 정보가 갱신될 때마다
다시 세우는 활동이라는 것 — 스프린트 구조 자체가 그 리듬입니다.

</details>
