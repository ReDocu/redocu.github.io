## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 서비스를 **사용자 시나리오**(누가·언제·무엇을 얻는가)에서 출발해 정의할 수 있다.
- 기능 후보를 **필수/선택으로 분리**하고, 그 기준을 배점표와 연결해 설명할 수 있다.
- 범위의 3축(데이터 폭 · 기능 수 · 품질 목표)에서 **"2주에 끝나는 크기"로 자를** 수 있다.
- 기능마다 **완료의 정의**(확인 방법)를 붙인 요구사항 문서를 만들 수 있다.

---

## ② 왜 필요한가

4주 팀 프로젝트의 사인(死因) 1위는 기술 부족이 아니라 **범위**입니다. 증상은 언제나
비슷합니다 — 모든 기능이 70%씩 되어 있고, 관통하는 것은 없는 상태로 발표 주간을 맞는 것.
배점표를 다시 보세요: 전체 사이클 완성도가 30점입니다. **부분적으로 화려한 것이 아니라
끝까지 관통하는 것**이 최대 배점이고, 커리큘럼 FAQ의 답("선택 기능부터 자릅니다")이
그래서 존재합니다.

"자르기"라는 말에 대한 오해부터 걷어냅시다. 자르기는 야망의 포기가 아니라 **순서의
설계**입니다. 걷어낸 기능은 사라지는 게 아니라 "관통 이후의 로드맵"이 됩니다 — 그리고
그 로드맵은 발표에서 "다음 단계" 슬라이드가 되어 점수로 돌아옵니다
([Day 136](../05-infra-mlops/day-136.md) ⑥ Q3의 원칙이 팀 규모로 확장된 것입니다).

어제 확정한 주제는 아직 "방향"일 뿐입니다. 오늘 그것이 "범위"가 됩니다 — 그리고 범위
문서는 앞으로 4주간 팀이 무언가를 추가하고 싶어질 때마다 돌아올 기준점입니다.

## ③ 개념 설명

### 사용자 시나리오 — 기능보다 먼저

기능 목록부터 시작하면 "있으면 좋은 것"이 끝없이 늘어납니다. 시나리오부터 시작하면
기능마다 "이 시나리오에 필요한가?"라는 심판이 생깁니다. 시나리오 규격:

```
[누가] [언제·어떤 상황에서] [무엇을 하면] [무엇을 얻는다]
```

시나리오는 2~3개면 충분하고, **첫 번째 시나리오가 곧 최소 범위**입니다.

### 필수/선택 분리 — 기준은 "관통에 필요한가"

| 구분 | 판정 기준 | 배점 연결 |
|---|---|---|
| **필수** | 이것이 없으면 필수 6종(수집·모델·API·배포·모니터링·문서) 중 하나가 비는가 | 사이클 30 + 재현성 20 |
| **선택** | 없어도 관통은 되지만 서비스가 좋아지는 것 | 가산 요소 · "다음 단계" |
| **제외** | 이번 4주의 시나리오에 등장하지 않는 것 | — |

선택 목록에는 **우선순위 번호**를 붙입니다. W31에 시간이 남으면(드뭅니다) 위에서부터
꺼내 쓰고, 시간이 모자라면(흔합니다) 아래에서부터 이미 잘려 있는 셈입니다.

### 범위의 3축 — 자를 곳은 세 군데다

| 축 | 질문 | 자르기 예 |
|---|---|---|
| 데이터 폭 | 대상(지역·품목·기간)을 좁힐 수 있나 | 전 노선 → 1개 노선 · 전 품목 → 3개 품목 |
| 기능 수 | 시나리오에 없는 기능이 섞여 있나 | 알림·시각화·관리자 화면 → 선택으로 |
| 품질 목표 | "얼마나 잘"을 숫자로 정했나 | "최고 성능" → "베이스라인 대비 MAE 20%↓" |

세 번째 축이 가장 자주 잊힙니다. 품질 목표가 없으면 모델 개선이 **끝나지 않는 작업**이
되어 W30 후반을 통째로 삼킵니다. 목표 숫자는 완벽할 필요가 없습니다 — "이 정도면 등급
안내로서 유용하다"의 팀 합의면 되고, [Day 148](day-148.md)에서 베이스라인을 재본 뒤
현실화합니다.

### 완료의 정의 — 기능마다 확인 방법을

"수집 파이프라인 완성"은 완료 판정이 불가능한 문장입니다. **확인 명령이 붙어야** 완료가
정의됩니다 — MP4 갭 감사([Day 136](../05-infra-mlops/day-136.md))의 "증거 명령" 규율을
이번엔 계획 단계부터 심는 것입니다.

---

## ④ 단계별 실습

### Step 1. 사용자 시나리오 확정 (1~2교시)

한산 팀의 시나리오:

```
S1 (최소 범위): 서울 직장인이 저녁에 "내일 아침 강남역 8시" 를 조회하면
                혼잡 등급(여유/보통/혼잡)과 근거 수치를 얻는다.
S2: 같은 사용자가 "내일 7시~10시 중 덜 붐비는 시간"을 비교해 출발 시각을 고른다.
S3 (선택 후보): 매주 이용 패턴이 바뀌는 사용자가 즐겨찾는 역의 주간 예보를 받아 본다.
```

S1이 관통 목표입니다. S2는 S1의 응답을 시간대 반복 조회로 재사용하므로 사실상 무료,
S3(알림·구독)은 저장·스케줄 부담이 커서 선택 후보로 내려갔습니다.

### Step 2. 기능 발산과 분리 (3~4교시)

포스트잇 발산(15분, 비판 금지) 후 ③의 기준으로 분류합니다. 한산 팀 결과:

| 기능 후보 | 판정 | 근거 |
|---|---|---|
| 일별 수집·적재 자동화 | **필수** | 6종 중 파이프라인 |
| 내일 역·시간대 혼잡 예측 API | **필수** | 6종 중 모델+API |
| 데모 페이지 (역·시간 선택) | **필수** | 시연의 최소 형태 (MP3 방식 재사용) |
| 주 1회 자동 재학습 | **필수** | 6종 중 운영 자동화 — 단 게이트는 단순하게 |
| 혼잡 임계 알림 (S3) | 선택 1순위 | 관통에 불요 |
| 노선 지도 시각화 | 선택 2순위 | 데모 페이지로 대체 가능 |
| 3·9호선 확장 | 선택 3순위 | 데이터 폭 축의 확장판 |
| 관리자 통계 화면 | 제외 | 시나리오에 없음 |

### Step 3. 범위의 3축으로 자르기 (5~6교시)

한산 팀의 자르기 기록 — **자른 이유를 남기는 것까지가 작업**입니다:

| 축 | 결정 | 이유 |
|---|---|---|
| 데이터 폭 | 전 노선(600여 역) → **2호선 51역** | 등급 기준선(역·요일·시간대) 관리량 1/12 · 데모 서사 명확("출근 노선") · 확장은 수집 필터 한 줄 |
| 시간 해상도 | 시간 단위 직접 학습 → **일 단위 예측 × 월별 시간대 분포 결합** | 시간 단위 학습 데이터가 월 집계뿐(141 확인) — 정직한 해상도 선택 |
| 서비스 시점 | 실시간 → **내일 예보** | D-4 게시 지연의 흡수 (141 발견의 설계 반영) |
| 품질 목표 | **베이스라인(지난주 같은 요일) 대비 MAE 20% 이상 개선 + 등급 정확도 0.85 이상** | 등급 안내 서비스로서의 최소 유용성 — 148에서 재검 |

### Step 4. 기능 명세와 응답/화면 설계 (7~8교시)

필수 기능마다 완료의 정의를 붙여 `docs/requirements.md`로 커밋합니다. 한산 팀 발췌:

| 기능 | 완료의 정의 (확인 방법) |
|---|---|
| 수집·적재 | 어제자 DAG 성공 로그 + `SELECT count(*)` 가 51행/일 증가 |
| 예측 API | `POST /predict {station, date, hour}` → 등급+수치, 계약 테스트 통과 |
| 데모 페이지 | 역·시간 선택 → 등급 표시, 시연 리허설 1회 |
| 자동 재학습 | 일요일 DAG가 새 run을 MLflow에 남기고 게이트 판정 로그를 남김 |

API 응답 초안(내일 [Day 143](day-143.md) 명세의 입력이 됩니다):

```json
{
  "station": "강남", "date": "2026-08-11", "hour": 8,
  "level": "혼잡", "congestion": 0.87,
  "expected_boardings": 9120, "baseline_p90": 10480,
  "model_version": "hansan-daily-v1"
}
```

**오늘 퇴근 체크** — □ 시나리오 2~3개(S1=최소 범위) □ 필수/선택/제외 표(선택엔 순위)
□ 3축 자르기 기록(이유 포함) □ 품질 목표 숫자 □ 완료의 정의가 붙은 요구사항 문서 커밋

## ⑤ 자주 하는 실수

### 시나리오 없이 기능 목록부터

**증상** — 회의 1시간 만에 기능 24개 — 전부 "있으면 좋은 것"이라 아무것도 못 자름.
**원인** — 심판(시나리오) 없이 발산만 함.
**해결** — 발산 전에 S1을 먼저 확정하세요. 모든 기능 후보는 "S1~S2에 등장하는가"의
심판을 받습니다. 등장하지 않으면 아무리 좋아도 선택 이하입니다.

### "일단 넣고 안 되면 빼자"

**증상** — 필수 12개로 출발 — W30 말에 빼기 시작하지만 이미 설계·코드가 얽혀 못 뺌.
**원인** — 추가는 쉽고 제거는 어렵다는 비대칭을 모름.
**해결** — 순서를 뒤집으세요: **최소로 시작해 여유가 있으면 추가.** 자르기의 골든타임은
오늘 하루뿐입니다 — 코드가 생기는 순간부터 모든 기능은 매몰 비용을 갖습니다.

### 품질 목표가 없거나 무한

**증상** — "성능은 높을수록 좋죠" — 모델 담당이 W30을 통째로 튜닝에 쓰고, 서빙 연결이
W31로 밀림.
**원인** — 범위의 3축 중 품질 축을 자르지 않음.
**해결** — 목표를 숫자로, 달성하면 **멈추는 규칙**과 함께 적으세요 (한산: "MAE 20%↓ +
등급 0.85 달성 시 개선 중단, 남는 시간은 관통에"). 모델링 배점은 15점이고 사이클이
30점입니다 — 시간 배분이 배점을 따라가야 합니다.

### 자른 것을 기록하지 않음

**증상** — 발표 질의 "알림 기능은 왜 없나요?"에 "시간이 없어서…" — 잘라낸 판단이
변명처럼 들림.
**원인** — 자르기를 부끄러운 일로 여겨 기록을 안 남김.
**해결** — 3축 자르기 표(이유 포함)를 문서로 남기면 같은 질문의 답이 "D-4 지연 데이터로
실시간은 정직하지 않아 예보로 설계했고, 알림은 선택 1순위로 로드맵에 있습니다"가 됩니다.
같은 사실, 다른 점수.

## ⑥ 확인 문제

**Q1.** "부분적으로 화려한 것보다 끝까지 관통하는 것"이 높게 평가되는 이유를, 배점표의
구조와 심사(발표 시연)의 실패 양상 두 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

배점 관점: 사이클 완성도 30 + 재현성 20 = 50점이 "전 구간이 실제로 도는가"에 걸려 있어,
관통 실패는 최대 배점 구역의 직접 손실입니다. 반면 화려한 부분 기능은 가산 구역(문서·발표
일부)에만 기여합니다. 시연 관점: 라이브 데모는 가장 약한 고리에서 실패하는데, 70%짜리
기능이 여럿이면 약한 고리도 여럿이라 시연 실패 확률이 곱으로 늘어납니다. 완주한 좁은
범위는 시연이 안전하고, 잘린 기능은 "다음 단계"로 발표에 편입되어 오히려 계획 능력의
증거가 됩니다.

</details>

**Q2.** 한산 팀이 "시간 단위 직접 학습" 대신 "일 단위 예측 × 월별 시간대 분포 결합"을
택한 것은 성능을 일부 포기하는 결정일 수 있습니다. 이 결정이 그럼에도 합리적인 이유를
데이터 실재·범위·정직성 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

데이터 실재: 시간 단위 학습에 필요한 시간대별 일별 데이터가 존재하지 않고(월 집계뿐),
없는 데이터를 보간해 학습하면 그 보간 가정이 성능 수치를 오염시킵니다. 범위: 시간 단위
모델은 학습·평가·기준선 관리가 전부 24배로 늘어나 2주 스프린트를 위협합니다. 정직성:
"월별 분포로 근사한 시간대 등급"이라고 밝히는 설계는 한계가 명확한 대신 설명 가능하고,
심사 질의("시간대 예측의 근거는?")에 데이터의 실제 해상도로 답할 수 있습니다. 성능의
잠재적 손실보다 검증 가능성과 완주 확률의 이득이 크다는 판단 — 이것이 범위 자르기의
전형적인 트레이드오프입니다.

</details>

**Q3.** "완료의 정의(확인 방법)"를 계획 단계에 붙이는 것이 MP4의 갭 감사([Day 136](../05-infra-mlops/day-136.md))와
어떻게 같은 철학인지, 그리고 팀 개발에서 추가로 얻는 효과 하나를 설명하세요.

<details>
<summary>답 보기</summary>

공통 철학은 "상태의 정의는 증거 명령이 지금 통과하는 것"입니다 — MP4에서는 완성된 것을
감사할 때 썼고, 여기서는 완성될 것을 정의할 때 씁니다. 계획 단계에 심으면 "완성됐다/안
됐다" 논쟁이 명령 실행으로 대체되어 판정 비용이 0이 됩니다. 팀 개발에서의 추가 효과:
완료의 정의는 **작업의 인수 조건**이 되어, 담당자가 아닌 팀원(리뷰 짝)도 PR을 객관적으로
승인/반려할 수 있게 합니다 — "내 기준엔 됐는데"라는 개인 기준의 충돌이 사라집니다.

</details>
