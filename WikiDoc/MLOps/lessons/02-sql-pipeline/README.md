## 이 단원을 마치면

- [ ] JOIN·집계·윈도우 함수가 들어간 **분석 SQL을 직접 설계**할 수 있다
- [ ] 목적에 맞는 **테이블 스키마(ERD)를 설계**하고 제약조건·인덱스를 붙일 수 있다
- [ ] 대단원 01의 수집기를 연결해 **수집 → 검증 → DB 적재 ETL 파이프라인**을 만들 수 있다
- [ ] SQL 인젝션이 왜 생기고 어떻게 막는지 설명할 수 있다

**단원 완료 조건 (MP1 제출 기준)**

- [ ] 명령 한 줄로 수집→적재가 재현된다 (**멱등**)
- [ ] JOIN·윈도우 함수가 포함된 분석 SQL을 설명할 수 있다
- [ ] 검증 규칙과 실패 처리 정책이 코드에 있다
- [ ] 보고서에 분석 질문 → 근거 → 결론이 이어진다

**단원 산출물** ETL 파이프라인 + 분석 보고서 → 포트폴리오 저장소 2번

## 대단원 01과의 연결

이 단원은 **앞 단원의 산출물을 입력으로 씁니다.**

```
datapipe (Day 030)                     이 단원에서
├── sources/     수집       ───────▶   Extract  단계 그대로 재사용
├── stages/clean 정제       ───────▶   Transform 단계 그대로 재사용
└── stages/store 파일 저장  ───────▶   Load 단계로 교체 (DB 적재)
```

## 자주 나오는 질문

| 질문 | 답 |
|---|---|
| Pandas로 다 되는데 왜 SQL을 쓰나요? | 데이터가 서비스 DB에 있고, 여러 사람·서비스가 동시에 쓰기 때문입니다. **"DB에서 크게 줄여서 가져오고, Pandas로 마무리"** 가 실무 패턴입니다 ([Day 031](day-031.md)). |
| 쿼리 결과가 미묘하게 중복됩니다 | 조인 키가 1:N 관계인데 1:1로 가정했을 가능성이 큽니다 ([Day 034](day-034.md)의 조인 중복 함정). |
| f-string으로 쿼리를 만들면 안 되나요? | 안 됩니다. **SQL 인젝션** 통로입니다. 값은 반드시 파라미터 바인딩으로 넣습니다 ([Day 041](day-041.md)). |
| `NULL` 비교가 이상하게 동작합니다 | `NULL = NULL` 은 참이 아니라 `NULL` 입니다. `IS NULL` 을 쓰세요 ([Day 032](day-032.md)). |
| 같은 파이프라인을 두 번 돌렸더니 데이터가 두 배가 됐습니다 | 멱등성이 없습니다. `ON CONFLICT` 또는 삭제 후 재적재로 해결합니다 ([Day 042](day-042.md)·[043](day-043.md)). |
