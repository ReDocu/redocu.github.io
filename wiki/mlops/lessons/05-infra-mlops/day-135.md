## ② 왜 필요한가

나흘의 부품을 늘어놓아 봅시다 — DVC(화물의 버전), 레지스트리(모델의 상태), Airflow(단계의
지휘), 모니터링(변화의 감지). 각각도 유용하지만, 이들의 진짜 정체는 **하나의 루프의 부품**
이라는 것입니다:

```
세상이 변한다 → 감지한다 → 다시 배운다 → 검증하고 교체한다 → 다시 감시한다 → …
```

이 루프가 돌지 않는 ML 서비스의 운명은 정해져 있습니다 — 배포 첫날이 성능의 정점이고,
그 뒤로는 조용한 하강. 이 루프를 돌게 만드는 공학 전체가 **MLOps라는 직무의 정의**이고,
과정명이 걸린 이 단원에서 여러분이 가져가야 할 한 문장입니다.

오늘 오전엔 그 루프를 설계도로 그리고 방아쇠(어제의 경보 → 그제의 DAG)를 실제로 연결합니다.
오후엔 고개를 들어 지형을 봅니다 — 이 루프가 커지면 만나는 것(K8s), 모델이 LLM으로 바뀌면
달라지는 것(LLMOps). 내일부터는 MP4 — 이 모든 것의 여러분 버전을 만듭니다.

## ③ 개념 설명

### MLOps 루프 — 완성형 설계도

```
            [cron 매일] datapipe ──▶ DB (신선한 데이터)                (115)
                                      │
            [Airflow 매일] check_drift.py ◀── 예측 로그 (입력·출력)     (134)
                  │ PSI 경보(exit 2)
                  ▼
   (사람: 원인 조사·승인) ──▶ [Airflow] 수집→전처리→학습→평가            (133)
                                      │                        데이터·모델 지문 (131)
                                      ▼
                          promote.py 게이트 — 홀드아웃 개선 시에만       (132)
                                      │ @production 이동
                                      ▼
                          서빙 재로드 → 새 model_version 응답            (132·096)
                                      │
                                      └──▶ 예측 로그 → 다시 감시로  (루프 폐쇄)
```

### 어디까지 자동인가 — 성숙도의 사다리

| 수준 | 모습 | 우리의 위치 |
|---|---|---|
| 0 수동 | 노트북에서 재학습, 파일 복사 배포 | 대단원 03의 우리 |
| 1 **파이프라인 자동** | 재학습·검증·승격이 한 번의 실행으로 | **어제까지 완성** |
| 2 **트리거 자동** | 신호(드리프트)가 파이프라인을 깨움 | **오늘 연결** |
| 3 전자동 | 경보→재학습→배포에 사람 0 | 오늘 **일부러 안 감** (사람 관문 유지) |

3으로 안 가는 것은 미완이 아니라 **설계 결정**입니다 — 어제 ⑤의 그 사고(센서 고장을 성실히
학습) 때문에, "경보 → 조사·승인 → 재학습"의 사람 관문 하나를 남깁니다. 단, 승인 **이후**는
전자동이므로 사람의 일은 판단 한 번으로 압축됩니다. 자동화의 목표는 사람 제거가 아니라
**사람을 판단에만 쓰는 것** ([Day 125](day-125.md) Q1과 같은 결론).

### K8s는 언제 필요한가 — 콤포즈가 아플 때

Kubernetes(K8s)는 **여러 서버에 걸친** 컨테이너 오케스트레이터입니다. Compose와 같은 질문
("무엇을 어떻게 띄울까")에 답하되, 규모가 다릅니다:

| | Compose (우리) | K8s |
|---|---|---|
| 범위 | 서버 **1대** | 서버 **군집** |
| 죽으면 | 그 서버가 죽으면 끝 | 다른 서버에 자동 재배치 (자가 치유) |
| 늘리려면 | 수동 (더 큰 서버) | 부하 따라 자동 증감 (오토스케일) |
| 배포 | 재시작 (순단) | 롤링·카나리 내장 ([Day 129](day-129.md)의 그 표가 기본 기능) |
| 비용 | 파일 하나 | 학습 곡선·운영 부담 — **전담이 필요한 수준** |

도입 신호는 "Compose가 아플 때"입니다 — 서버 한 대로 부하를 못 받거나, 순단이 용납 안 되거나,
서비스가 수십 개가 됐을 때. 우리 규모(서버 1대, 서비스 3컨테이너)에서 K8s는 **문제없는 곳에
복잡성만 더하는 선택**입니다. 커리큘럼 FAQ의 답 그대로 — 개념과 판단 기준까지가 지금의 몫이고,
실전은 이 기초(컨테이너·선언·헬스체크가 전부 K8s의 어휘입니다) 위에서 필요해질 때 얹으면
됩니다.

### LLMOps 개관 — 같은 뼈대, 다른 화물

LLM 서비스 운영은 이 과정의 개념들이 거의 그대로 번역됩니다:

| 이 과정에서 배운 것 | LLMOps에서의 대응 |
|---|---|
| 모델 버전 (레지스트리) | 모델 + **프롬프트 버전** (프롬프트가 코드·모델만큼 성능을 좌우 — 같이 버전·리뷰) |
| 재학습 파이프라인 | 파인튜닝 또는 **RAG 지식원 갱신** (모델은 그대로, 참조 데이터를 교체) |
| 홀드아웃 게이트 (promote) | **평가셋 회귀 테스트** — 정답이 서술형이라 채점도 모델이 (LLM-as-judge) |
| 드리프트 감시 (PSI) | 입력 주제 분포 + **출력 품질 표본 평가** (정답 없는 감시의 극단형) |
| p95·처리량 | + **토큰 비용** — 요청당 비용이 커서 비용이 1급 운영 지표 |
| 시크릿 관리 | + API 키·프롬프트 유출(인젝션) 방어 |

낯선 항목이 하나도 없죠 — 화물이 달라졌을 뿐 뼈대(버전·게이트·감시·비용)는 오늘까지 만든
그것입니다. 심화는 본 과정 수료 후의 **LLM 엔지니어링 과정** 영역입니다.

## ④ 단계별 실습

### Step 1. 내 설계도 (1~2교시)

③의 루프 그림을 **자기 저장소의 실제 상태**로 다시 그리세요 — 화살표마다 세 가지를 표기:
담당 도구 · 구현 상태(✅ 완성 / 🔶 오늘 연결 / ⬜ 미구현) · 실패 시 무슨 일이 (그 화살표가
끊기면 루프는 어떻게 되나). 이 문서가 MP4 설계(내일)와 최종 발표의 아키텍처 슬라이드 원형
입니다.

### Step 2. 방아쇠 연결 — 부분 구현 (3~5교시)

어제의 경보를 그제의 DAG에 잇습니다. `dags/drift_watch.py`:

```python
# drift_watch.py — 매일 드리프트 점검, 경보 시 재학습 DAG 트리거 (Day 135)
from datetime import datetime

from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.trigger_dagrun import TriggerDagRunOperator

with DAG(
    dag_id="drift_watch",
    schedule="0 7 * * *",              # 매일 07:00
    start_date=datetime(2026, 8, 1),
    catchup=False,
) as dag:

    check = BashOperator(
        task_id="check_drift",
        bash_command="cd /opt/mlops/mlops-mp2 && .venv/bin/python monitoring/check_drift.py --recent-days 7",
        # 종료 코드 0=안정 → 성공, 2=경보 → 실패로 표시되어 알림·후속을 깨움
    )

    retrain = TriggerDagRunOperator(
        task_id="trigger_retrain",
        trigger_dag_id="pm25_retrain",
        trigger_rule="all_failed",     # check가 '경보(실패)'일 때만 발화
    )

    check >> retrain
```

> **설계 메모** — 교실 버전은 경보 → 즉시 재학습으로 연결했습니다 (성숙도 2.5). 사람 관문
> 버전은 trigger_rule 대신 "경보 시 알림만 + 사람이 승인 후 수동 트리거"로 바꾸면 됩니다 —
> 어느 쪽이든 **promote 게이트가 최후 방어선**이라 나쁜 재학습이 운영에 직행하지는 못합니다.
> 여러분의 MP4에서는 선을 어디에 긋고, 그 근거를 설계 문서에 쓰세요 (그 근거가 심사 대상입니다).

### Step 3. 루프 전체 리허설 (5~7교시)

어제 주입해 둔 드리프트 상태 그대로, 루프를 처음부터 끝까지 굴립니다:

```
07:00 drift_watch 트리거 (수동 ▶)
  └ check_drift: PSI pm25_lag1=0.31 → 경보(exit 2) → task 빨강
      └ trigger_retrain 발화 → pm25_retrain 시작
          fetch ✓ → preprocess ✓ (드리프트 구간 포함 데이터로) → train ✓
          → evaluate_promote: production MAE 5.84 vs staging 4.02 → 승격! v3 → @production
09:41 서빙 재로드 → /model/info
```

```bash
$ curl -s localhost:8001/model/info
{"name":"pm25-forecaster","alias":"production","version":"3","run_id":"a90c4f17","data_md5":"c218b5e9"}
$ python monitoring/check_drift.py --recent-days 1 --baseline current-model
피처 전체 PSI < 0.10 — 안정 (새 기준선 대비)
```

읽어야 할 서사 — **세상이 변했고(주입한 가을), 시스템이 감지했고(PSI 0.31), 스스로 다시
배웠고(v3), 검증을 통과한 것만 교체됐고(게이트 — 이번엔 개선 폭이 커서 통과), 새 기준선에서
다시 감시가 시작**됐습니다. 사람이 한 일: 트리거 버튼 하나 (그마저 07:00 스케줄이 대신할
것). 대단원 03에서 "모델을 만들 줄 아는 사람"이었던 여러분은, 지금 "**모델이 계속 맞게
만드는 시스템**을 만드는 사람"이 됐습니다 — 그 차이가 직무명입니다.

### Step 4. 지형 세미나 — K8s와 LLMOps (7교시 계속)

2인 1조 — 한 사람이 ③의 K8s 표로 "우리가 지금 K8s를 안 쓰는 이유"를 3분 발표, 다른 사람이
LLMOps 대응표에서 두 줄을 골라 "우리 과정의 무엇이 어떻게 번역되는지" 3분 발표. 서로의
발표에 [q] 하나씩 — 발표는 최종 프로젝트 리허설이기도 합니다.

### Step 5. 주간 퀴즈와 단원의 문턱 (8교시)

### 오늘 새로 나오는 실수

### 성숙도 사다리 건너뛰기

**증상** — 수동 재학습도 재현이 안 되는 팀이 "드리프트 자동 재학습"부터 구축 — 신호가 울릴
때마다 **재현 안 되는 절차가 자동으로** 실행되는 괴물.
**원인** — 자동화가 절차의 품질을 올려 준다는 착각 — 자동화는 절차의 품질을 **증폭**할 뿐입니다
(나쁜 절차 × 자동 = 나쁜 일이 더 자주).
**해결** — 사다리 순서대로: 손으로 완주 가능(재현) → 한 번의 실행으로(파이프라인) → 신호로
(트리거). 우리 과정이 03→05를 이 순서로 밟아 온 이유입니다.

### "전자동이 최종 목표"라는 오해

**증상** — 사람 관문을 부끄러운 미완성으로 여기고 제거 — 어제 ⑤의 센서 고장 시나리오가 실현.
**원인** — 성숙도 표를 "3이 우등"으로 오독.
**해결** — 관문의 위치는 **오판 비용과 판단 빈도의 함수**입니다: 판단이 잦고 오판이 싸면
자동으로, 드물고 비싸면 사람에게. 재학습 승인은 주 1회·오판 비용 큼 — 사람 자리가 맞습니다.
설계서에 "여기 사람이 있는 이유"를 쓸 수 있으면 그것이 성숙입니다.

### K8s를 이력서 때문에 조기 도입

**증상** — 서버 1대 프로젝트를 K8s로 — 학습 시간의 80%가 YAML·클러스터 트러블슈팅으로,
정작 ML 루프는 미완.
**원인** — 채용 공고의 키워드가 기술 선택을 대신함.
**해결** — 면접에서 강한 것은 "K8s 써 봤어요"가 아니라 "**Compose로 충분한 규모였고, 어떤
신호가 오면 K8s로 갈지 판단 기준을 갖고 있다**"입니다 — 오늘 ③의 표가 그 답변입니다. 도구
목록보다 판단 근거가 경력의 증거입니다.

비율, 그리고 표본의 주기적 사람 검수. 공통: 서비스 지표(p95·에러율)는 이 질문에 **답하지
못함**을 명시하고, 경보는 조사 절차와 연결되어야 완성입니다.

</details>

**Q2.** Step 3의 리허설에서 "게이트가 최후 방어선"이라는 말의 의미를, 방아쇠(드리프트 경보)가
오발이었던 경우(실제로는 센서 고장)의 시나리오로 검증하세요.

<details>
<summary>답 보기</summary>

센서 고장으로 쓰레기 분포가 유입 → PSI 경보(정당 — 분포는 실제로 변했으니) → 재학습이 쓰레기
포함 데이터로 진행 → 새 모델은 홀드아웃(정상 시기 기준)에서 성능이 **나빠짐** → promote
게이트가 승격을 거부 — 운영은 기존 모델 그대로. 즉 방아쇠·학습이 오염돼도 "검증을 통과한
것만 운영에"라는 관문이 마지막에서 사고를 흡수합니다. 단 게이트의 홀드아웃 자체가 오염되면
방어선도 뚫리므로, 홀드아웃의 관리(고정 규약·오염 검사)가 게이트의 신뢰 조건이라는 것까지가
완전한 답입니다.

원칙(코드·데이터·환경·시드)의 언어로 설명하세요.

<details>
<summary>답 보기</summary>

응답(096)의 프롬프트판이 필요한 것. 게이트도 같은 논리로 프롬프트 변경마다 평가셋 회귀

## 주간 퀴즈 24 — W27 (MLOps 파이프라인)

<details>
<summary>1. Git에 큰 이진 파일이 부적합한 이유와 DVC의 우회 구조는?</summary>

모든 버전 영구 보관(저장소 비대·clone 비용) + diff/병합 무효. DVC는 Git에 md5 지문 파일만 커밋하고 실물은 캐시·원격 창고에 — checkout 시 지문대로 실물 교체.

</details>

<details>
<summary>2. "git push 전에 dvc push"인 이유는?</summary>

지문(송장)만 공개되고 실물(소포)이 창고에 없는 시차 동안 저장소가 재현 불가 상태가 됨 — 팀원·CI의 dvc pull이 깨짐.

</details>

<details>
<summary>3. DVC와 모델 레지스트리의 분업은?</summary>

DVC: 커밋 시간축의 화물 박제("그때의 데이터·모델"). 레지스트리: 커밋과 독립적인 배포 상태 명부("지금 운영은 v몇, 후보는 v몇"). 재현성과 운영성 — 다른 질문, 다른 층.

</details>

<details>
<summary>4. 별칭(@production) 방식 롤백이 빠른 이유와 그에 따르는 기록 규율은?</summary>

롤백 = 실체 복구가 아니라 포인터 이동(초 단위). 대신 "별칭이 언제 어느 버전을 가리켰나"의 이동 이력을 남겨야 조사가 가능 — 불변 식별자(버전)의 언어로 기록.

</details>

<details>
<summary>5. 승격 게이트(promote.py)의 원칙은?</summary>

현 운영 모델과 후보를 같은 홀드아웃에서 비교, 정한 기준(예: 2% 개선) 통과 시에만 별칭 이동. 미달이면 아무 일도 안 일어나는 것이 정상 동작 — main의 원리를 모델에.

</details>

<details>
<summary>6. cron의 네 한계와 DAG가 바꾸는 것은?</summary>

의존 표현 불가·실패 무심·재시도 없음·이력/가시성 없음. DAG는 시각이 아니라 관계(상류 성공)가 실행 조건 — 실패 시 하류가 upstream_failed로 정지해 조용한 오염을 차단.

</details>

<details>
<summary>7. "Airflow는 지휘하되 연주하지 않는다"의 실천 형태는?</summary>

무거운 계산은 외부 CLI(별도 venv/컨테이너)를 BashOperator 등으로 호출, DAG 파일은 1초에 import되는 선언만. task 간 큰 데이터는 XCom이 아니라 파일/DB로.

</details>

<details>
<summary>8. 서비스 지표가 완벽해도 모델이 실패 중일 수 있는 이유는?</summary>

드리프트된 입력도 유효한 요청이라 422/500/지연 어디에도 안 걸림 — 오답은 예외를 던지지 않는다. 모델 건강은 입력·출력 분포라는 별도 계기판 필요.

</details>

<details>
<summary>9. PSI의 원리와 관례 임계는?</summary>

기준(학습) 분포의 십분위로 구간을 고정하고 최근 분포와 구간 비율 차이를 합산. <0.1 안정 · 0.1~0.25 주의 · >0.25 경보 — 단 온도계이지 진단서가 아님(원인 조사 필수).

</details>

<details>
<summary>10. 드리프트 경보에 자동 재학습을 직결하면 위험한 이유와 이중 방어는?</summary>

분포 변화의 원인이 세상 변화가 아니라 데이터 결함(센서 고장)일 수 있음 — 쓰레기로 성실히 재학습하는 사고. 방어: 경보→조사의 사람 관문 + 승격 게이트(홀드아웃 검증)가 최후 방어선.

</details>
