## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 학습보다 **평가를 먼저** 설계할 수 있다 (지표 · 홀드아웃 · 비교 규칙 · 공용 평가 코드).

- 품질 목표를 베이스라인 실측 위에서 현실화하고, 모든 실험을 MLflow에 남길 수 있다.

## ② 왜 필요한가

다음 주에 여러분은 어떤 숫자를 얻을 것입니다 — 가령 MAE 1,146명. 이 숫자는 잘한 것일까요?
**그 자체로는 아무 의미가 없습니다.** 지하철 승차 인원 예측이 원래 쉬운 문제라면(주기성이
강하니까) 1,146은 부끄러운 숫자일 수 있고, 원래 어려운 문제라면 훌륭한 숫자일 수 있습니다.
문제의 원래 난이도를 재는 도구가 베이스라인입니다 — "아무 모델링도 하지 않고 얻을 수 있는
성능"이 기준 0점이 되어야, 그 위의 모든 숫자가 의미를 갖습니다.

[Day 055](../03-machine-learning/day-055.md)에서 이 규율을 처음 배웠습니다 — 평균 예측과
persistence(내일=오늘)를 먼저 재던 것. 오늘은 그 규율의 팀 버전이고, 걸린 것이 더 큽니다:
평가 배점 15점의 심사 기준이 "베이스라인 대비 개선 근거"이고, 품질 목표(MAE 20%↓)의 분모가
오늘 정해지며, 재학습 게이트(145에서 설계한 "+10% 악화 시 보류")의 비교 대상도 결국 오늘
만드는 평가 체계 위에서 돕니다.

순서가 중요합니다 — **베이스라인보다도 먼저, 평가 설계가 옵니다.** 저울이 고정되기 전에
잰 무게는 전부 다시 재야 하기 때문입니다.

## ③ 개념 설명

### 평가 설계의 4요소 — 저울 고정

| 요소 | 한산 팀 결정 | 근거 |
|---|---|---|
| 홀드아웃 | 2026-05-01~07-31 (4,692행) — 시간 분리 | 어제 팀 합의 · [Day 052](../03-machine-learning/day-052.md) |
| 주 지표 | MAE (명) | "평균 몇 명 틀리나" — 전원이 해석 가능 |
| 보조 지표 | MAPE · **등급 정확도** | 규모 다른 역 간 비교 · 서비스 관점 |
| 비교 규칙 | 같은 홀드아웃 · 같은 평가 함수 · MLflow 기록 필수 | 숫자의 호환성 |

### 모델 지표와 서비스 지표는 다르다

사용자는 MAE를 보지 않습니다 — **등급(여유/보통/혼잡)이 맞는가**를 봅니다. MAE가 500명
줄어도 등급 경계를 넘나드는 오차가 그대로면 서비스는 나아진 게 없습니다. 그래서 등급
정확도(예측 등급 = 실제 등급 비율)를 반드시 함께 봅니다 — 모델 지표는 개선의 방향을,
서비스 지표는 개선의 **의미**를 말해 줍니다.

### 베이스라인 후보 — 도메인이 주는 공짜 모델들

| 베이스라인 | 논리 | 강점/약점 |
|---|---|---|
| 전일 값 | 내일 ≈ 오늘 | 주기 무시 — 금→토를 항상 틀림 |
| **지난주 같은 요일** | 내일 ≈ 지난주 그 요일 | 주간 주기 포착 — 강력. 공휴일·추세에 약함 |
| 4주 같은 요일 평균 | 최근 4주 평활 | 노이즈에 강하고 추세에 둔함 |

지하철처럼 주기가 강한 도메인에서는 "지난주 같은 요일"이 **무섭게 강한** 베이스라인입니다.
이것을 이기지 못하는 ML 모델은 배포할 이유가 없습니다 — 그리고 실제로 이기기 어렵다는
사실이 오늘 팀의 겸손과 내일의 방향(공휴일·추세를 다루는 피처)을 정해 줍니다.

### MLflow 기록 규율 — 베이스라인도 run이다

[Day 068](../03-machine-learning/day-068.md)의 원칙: 비교하게 될 모든 숫자는 run으로.
베이스라인을 "코드 밖 상식"으로 두면 3주 뒤 "그 1,914가 어느 구간·어느 코드였지?"가
됩니다. run에는 데이터 버전(md5) · 홀드아웃 경계 · 지표 전부를 남깁니다.

## ④ 단계별 실습

### Step 1. 공용 평가 함수 — #10 (1~2교시)

민준의 `src/train/evaluate.py` — **모든 모델이 이 함수 하나로 채점받습니다**:

```python
def evaluate(pred_df: pd.DataFrame) -> dict:
    """pred_df: (use_ymd, station_id, y_true, y_pred) — 홀드아웃 전 행 필수"""
    assert_coverage(pred_df)              # 4,692행 전부 있는지 — 부분 평가 금지
    mae = (pred_df.y_true - pred_df.y_pred).abs().mean()
    mape = ((pred_df.y_true - pred_df.y_pred).abs() / pred_df.y_true).mean()
    grade_acc = (to_grade(pred_df.y_pred, pred_df) == to_grade(pred_df.y_true, pred_df)).mean()
    return {"mae": round(mae, 1), "mape": round(mape, 4), "grade_acc": round(grade_acc, 4)}
```

`assert_coverage`가 지키는 것: "어려운 행을 빼고 잰 성능"의 원천 차단. 평가 함수가
하나여야 하는 이유는 ⑤에서 다시 봅니다.

### Step 2. 베이스라인 3종 측정 (3~5교시)

```
$ python -m src.train.baseline --all
[baseline] 홀드아웃 2026-05-01~07-31 (4,692행) · data_md5 e91c07a4
  전일 값             MAE 2,847 · MAPE 11.8% · 등급 0.71
  지난주 같은 요일     MAE 1,914 · MAPE  7.9% · 등급 0.78   ← 채택 (공식 베이스라인)
  4주 같은 요일 평균   MAE 1,988 · MAPE  8.3% · 등급 0.77
```

읽는 법 — 세 숫자가 문제의 지형도를 그려 줍니다: 주간 주기만 잡아도 MAE가 33% 줄어드는
문제(2,847→1,914), 즉 **주기성이 지배하는 문제**입니다. 내일의 ML 모델이 넘어야 할 산은
1,914이고, 품질 목표 "20% 개선"은 이제 구체적인 숫자가 됩니다: **MAE ≤ 1,531**.

오차를 뜯어 보면 방향도 보입니다:

```
$ python -m src.train.baseline --worst 3
  2026-05-25 (월·대체공휴일)  평균 오차 8,120  ← 지난주 월요일(평일)로 예측
  2026-05-05 (화·어린이날)    평균 오차 7,644
  2026-06-08 (월·연휴 다음날) 평균 오차 4,210
```

최악 오차가 전부 공휴일 주변입니다 — 베이스라인의 약점이 곧 내일 피처 설계의 명세입니다
(`is_holiday`, `is_day_after_holiday`가 이렇게 태어납니다).

### Step 3. MLflow 기록 (6교시)

```
$ mlflow ui  # http://localhost:5000 (Compose의 mlflow 서비스)
run: baseline-lastweek   metrics: mae 1914.0 · mape 0.079 · grade_acc 0.78
     params: holdout=2026-05-01..07-31 · data_md5=e91c07a4 · method=same_dow_lag7
```

### Step 4. 품질 목표 현실화 — 팀 회의 15분 (7~8교시)

[Day 145](day-145.md) 강사 피드백("달성 판정을 누가 언제?")의 답을 오늘 명문화합니다:

```
[모델 품질 목표 v2 — 팀 합의]
- 목표: 홀드아웃 MAE ≤ 1,531 (베이스라인 1,914의 −20%) 그리고 등급 정확도 ≥ 0.85
- 판정: Day 149 오후 모델 선정 회의 (전원) — evaluate() 결과 + MLflow run으로만
- 멈춤 규칙: 목표 달성 시 개선 중단, 잔여 시간은 관통(서빙 연결)에 투입
- 미달 시: 등급 정확도 우선으로 재협상 + 원인 분석을 보고서에 (위험 등록부 R2)
```

**오늘 퇴근 체크** — □ evaluate() 공용 함수(커버리지 검사 포함) □ 베이스라인 3종 실측
+ 채택 근거 □ 최악 오차 분석(내일의 피처 명세) □ MLflow run 기록 □ 품질 목표 v2 합의

## ⑤ 자주 하는 실수

### 베이스라인 없이 부스팅부터

**증상** — 첫 실험이 LightGBM, MAE 1,600 — "오, 좋은데?" 그대로 채택. 실은 베이스라인
1,914 대비 16% 개선일 뿐인데 비교 대상이 없어 "좋다"의 근거가 평생 없음.
**원인** — 베이스라인을 시시한 요식으로 취급.
**해결** — 순서를 강제하세요: 베이스라인 run이 MLflow에 없으면 모델 실험 시작 금지.
심사 질문 1순위가 "베이스라인 대비 얼마나요?"입니다 — 답이 없으면 모델링 15점 전체가
흔들립니다.

### 지표가 R²뿐

**증상** — "R² 0.87입니다" — 심사자도 팀원도 그게 서비스에서 무슨 뜻인지 모름.
**원인** — 교과서 지표를 관성으로 사용.
**해결** — 주 지표는 **도메인 단위**로 (명·원·건). "평균 1,146명 틀립니다. 강남 아침
수요 9만 명 대비 1.3%입니다"는 모두가 알아듣습니다. R²는 보조로 두는 건 좋습니다 —
주인공만 아니면 됩니다.

### 평가 코드가 실험마다 제각각

**증상** — 민준의 노트북 셀 A와 셀 B의 MAE 계산이 미묘하게 다름(결측 처리·반올림) —
두 실험의 숫자가 비교 불능인 걸 아무도 모름.
**원인** — 평가를 각 실험의 부속 코드로 취급.
**해결** — evaluate() **하나만** 존재하고 전 실험이 임포트합니다. 저울이 하나여야 무게가
호환됩니다 — 재학습 게이트(W31)도 같은 함수를 쓰므로, 오늘의 규율이 운영까지 갑니다.

### 등급 정확도를 나중에

**증상** — MAE만 좇아 2주 — 발표 직전 등급 정확도를 처음 재 보니 0.79, 서비스 관점
개선이 미미함을 그제야 발견.
**원인** — 서비스 지표를 "마지막에 확인할 것"으로 분류.
**해결** — 두 지표를 **처음부터 나란히** 기록하세요(evaluate()가 이미 그렇게 되어
있습니다). 모델은 MAE로 고르더라도 보고와 목표에는 등급 정확도가 함께 있어야, "그래서
사용자가 뭘 얻는데?"에 항상 답이 있습니다.

## ⑥ 확인 문제

**Q1.** "지난주 같은 요일" 베이스라인이 ML 모델에게 위협적으로 강한 이유를 이 도메인의
구조로 설명하고, 그럼에도 ML 모델이 이길 수 있는 여지가 정확히 어디에 있는지 Step 2의
증거로 짚어 보세요.

<details>
<summary>답 보기</summary>

지하철 수요의 분산 대부분이 요일 주기(평일/주말·요일별 패턴)와 역별 수준이라는 두 구조에
설명되는데, "지난주 같은 요일"은 이 둘을 파라미터 0개로 완벽하게 흡수합니다 — 남는 오차는
주기 밖 요인뿐입니다. ML의 여지가 바로 그 잔차에 있고, Step 2의 최악 오차 분석이 그
잔차의 정체를 보여 줍니다: 공휴일·연휴 전후(달력 이벤트)와 완만한 추세. 즉 ML 모델의
승부처는 "주기를 더 잘 배우는 것"(이미 베이스라인이 만점)이 아니라 **달력 특성과 다중
lag의 결합**입니다 — 오늘의 오차 분석이 내일의 피처 목록을 직접 결정하는 구조입니다.

</details>

**Q2.** assert_coverage(홀드아웃 전 행 강제)가 없을 때 생길 수 있는 "정직해 보이는
부정"의 시나리오를 하나 구성하고, 커버리지 강제가 재학습 게이트(운영)에서 더 중요해지는
이유를 설명하세요.

<details>
<summary>답 보기</summary>

시나리오: 피처 생성에서 dropna가 공휴일 주변 행을 조용히 떨어뜨림 → 평가는 남은 행으로만
수행 → 공휴일(최대 오차원)이 빠진 MAE가 200명쯤 좋게 나옴 → 아무도 속이려 하지 않았지만
숫자는 부풀려짐. 비교 대상(베이스라인)은 전 행으로 쟀다면 이 비교는 무효입니다. 운영
게이트에서 더 위험한 이유: 게이트는 사람이 안 보는 자동 판정이라, 커버리지가 다른 두
run을 비교해 승격/보류를 결정하면 잘못된 모델이 소리 없이 운영에 갑니다. "같은 저울,
같은 접시"를 코드로 강제하는 assert 한 줄이 그 사고 계열 전체를 차단합니다.

</details>

**Q3.** "목표 달성 시 개선을 멈춘다"는 멈춤 규칙이 왜 필요한지, 배점 구조와 이 주의
목표(금요일 중간 데모) 관점에서 설명하세요. 멈춤이 아깝게 느껴질 때 팀이 확인해야 할
숫자는 무엇인가요?

<details>
<summary>답 보기</summary>

모델 개선은 수확 체감이 가파른 작업이라(첫 20%는 하루, 다음 5%는 사흘) 멈춤 규칙이
없으면 "조금만 더"가 시간을 무한 흡수합니다. 배점상 모델링은 15점이고 사이클 관통이
30점 — 모델에 사흘을 더 쓰는 것보다 서빙 연결(151)에 하루를 쓰는 것이 기대 점수가 높습
니다. 금요일 중간 데모의 완성도도 관통에 걸려 있습니다. 멈춤이 아까울 때 볼 숫자는
**등급 정확도의 증분**입니다 — MAE가 100 더 줄어도 등급 정확도가 안 움직이면 사용자가
얻는 것은 0입니다. 서비스 지표의 증분이 0에 수렴하면 멈추는 것이 낭만이 아니라 산수임을
팀 전원이 확인할 수 있습니다.

</details>
