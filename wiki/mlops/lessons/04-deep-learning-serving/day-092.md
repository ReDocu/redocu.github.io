## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- pydantic 모델로 **요청 바디의 계약**(타입 · 범위 · 허용값 · 필수 여부)을 선언할 수 있다.
- `Field` 제약과 커스텀 검증기로 도메인 규칙을 검증 계층에 넣을 수 있다.
- 잘못된 입력 시나리오별로 **의도된 4xx**(422 · 404 · 409)를 설계할 수 있다.
- `response_model` 로 **응답 계약**을 선언해 내부 필드 유출을 구조적으로 막을 수 있다.

---

## ② 왜 필요한가

어제의 공짜 검증은 타입까지였습니다. 그런데 실제 세상의 잘못된 입력은 타입이 맞습니다:

```
{"station": "강남구", "pm25": -5}        ← float 맞음. 물리적으로 불가능할 뿐
{"station": "부산", "pm25": 30}          ← str 맞음. 우리 서비스에 없는 측정소일 뿐
{"station": "강남구", "pm2_5": 41.5}     ← 전부 맞음. 필드명 오타일 뿐
```

세 번째가 특히 악질입니다 — 오타 필드는 **조용히 무시**되고 pm25는 기본값이나 누락 처리되어,
[Day 044](../02-sql-pipeline/day-044.md)의 "9999 센서값"이나 [Day 088](day-088.md)의 한국어
POSITIVE 같은 **조용한 실패**가 API 입구에서 재현됩니다. 다음 주에 이 입구 뒤에 모델이
앉는다는 걸 생각하면, 오늘의 주제는 곧 **모델을 쓰레기 입력에서 보호하는 방화벽**입니다.

pydantic의 발상은 [Day 068](../03-machine-learning/day-068.md)의 스키마 JSON + validate_input을
기억하면 익숙합니다 — 같은 일을 **선언형으로, 웹 계층의 표준 도구로** 하는 것입니다.

## ③ 개념 설명

### BaseModel — 실행되는 계약서

```python
class ReportIn(BaseModel):
    station: str
    measured_on: date                              # 문자열 "2026-08-13"을 date로 파싱까지
    pm25: float = Field(ge=0, le=300)              # 범위 제약
    grade: Literal["좋음", "보통", "나쁨", "매우나쁨"] | None = None   # 허용값 목록
```

| 선언 | 효과 |
|---|---|
| 타입 힌트 | 파싱 + 타입 검증 (문자열 날짜 → `date` 객체 변환까지) |
| `Field(ge=, le=, ...)` | 범위·길이·패턴 제약 |
| `Literal[...]` | 허용값 열거 |
| `= None` / 기본값 | 선택 필드 (없으면 **필수**) |
| `model_config = {"extra": "forbid"}` | **계약에 없는 필드 거부** — 오타 탐지기 |

검증을 통과하면 핸들러 안의 `r` 은 **타입이 보장된 객체**입니다. 핸들러 코드에서 방어적
if문이 사라지는 이유입니다.

### 커스텀 검증기 — 도메인 규칙의 자리

타입·범위로 안 되는 규칙("등록된 측정소인가")은 `@field_validator` 로 계약서 안에 넣습니다.
효과: 규칙 위반이 **다른 검증 오류와 같은 422 형식**으로 나가고, 규칙이 모델(계약서) 한곳에 모입니다.

### 4xx의 어휘 — 상황마다 다른 코드

| 코드 | 상황 | 오늘의 예 |
|---|---|---|
| 422 | 바디·파라미터가 계약 위반 | 범위 밖, 미등록 측정소, 오타 필드 |
| 404 | 자원이 없음 | 없는 리포트 조회 |
| 409 | 상태 충돌 | 같은 (측정소, 날짜) 중복 제출 |
| 400 | 그 외 잘못된 요청 | (위 셋으로 안 잡히는 것) |

422는 pydantic이 자동으로, 404/409는 우리가 `HTTPException` 으로 명시합니다.

### response_model — 나가는 것도 계약

응답에 선언된 필드만 담깁니다. 내부 필드(`_internal_id`, 원가, 디버그 정보)가 실수로
새는 사고를 **선언 한 줄**이 구조적으로 막습니다. 입력만큼 출력도 계약입니다.

## ④ 단계별 실습

### Step 1. 계약서가 있는 API (1~3교시)

`main.py` 를 새로 씁니다.

```python
# main.py — Day 092: pydantic 검증 — 계약을 선언한다
from datetime import date
from typing import Literal
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field, field_validator

app = FastAPI(title="검증이 있는 대기질 API", version="0.2.0")

STATIONS = {"강남구", "노원구", "마포구", "서초구", "종로구"}


class ReportIn(BaseModel):
    """측정 리포트 요청 바디 — 이 클래스가 곧 입력 계약서다."""
    model_config = {"extra": "forbid"}                  # 계약에 없는 필드는 거부

    station: str
    measured_on: date
    pm25: float = Field(ge=0, le=300, description="㎍/㎥ (일평균 물리 범위)")
    pm10: float | None = Field(default=None, ge=0, le=600)
    grade: Literal["좋음", "보통", "나쁨", "매우나쁨"] | None = None

    @field_validator("station")
    @classmethod
    def station_must_exist(cls, v):
        if v not in STATIONS:
            raise ValueError(f"등록되지 않은 측정소: {v}")
        return v


class ReportOut(BaseModel):
    """응답 계약 — 내부 필드는 여기 없으므로 절대 새어 나가지 않는다."""
    station: str
    measured_on: date
    pm25: float
    grade: str


def to_grade(pm25: float) -> str:
    return "좋음" if pm25 < 16 else "보통" if pm25 < 36 else "나쁨" if pm25 < 76 else "매우나쁨"


DB: dict[tuple, dict] = {}


@app.post("/reports", status_code=201, response_model=ReportOut)
def create_report(r: ReportIn):
    key = (r.station, r.measured_on)
    if key in DB:
        raise HTTPException(status_code=409, detail=f"{r.station} {r.measured_on} 리포트가 이미 있습니다")
    row = {**r.model_dump(), "grade": r.grade or to_grade(r.pm25),
           "_internal_id": len(DB) + 1}               # 내부 필드 — 응답엔 안 나감
    DB[key] = row
    return row


@app.get("/reports/{station}/{measured_on}", response_model=ReportOut)
def get_report(station: str, measured_on: date):
    row = DB.get((station, measured_on))
    if row is None:
        raise HTTPException(status_code=404, detail="리포트가 없습니다")
    return row
```

`uvicorn main:app --reload --port 8092` 로 띄워 둡니다.

### Step 2. 정상 경로와 충돌 (4교시)

```
$ POST /reports (정상)
  201 → {"station": "강남구", "measured_on": "2026-08-13", "pm25": 41.5, "grade": "나쁨"}
$ POST /reports (같은 것 또)
  409 → {"detail": "강남구 2026-08-13 리포트가 이미 있습니다"}
```

두 가지 확인: ① grade를 안 보냈는데 서버가 계산해 채웠고(41.5 → 나쁨 — [Day 060](../03-machine-learning/day-060.md)의
그 등급표), ② 같은 키 재제출은 422가 아니라 **409** — 계약은 맞지만 상태와 충돌한다는 다른 종류의 거절입니다.
멱등성을 배운 여러분이라면([Day 042](../02-sql-pipeline/day-042.md)) 409 대신 "덮어쓰기(upsert) 후 200"을
설계할 수도 있습니다 — 어느 쪽이든 **문서에 선언된 의도된 동작**이면 됩니다.

### Step 3. 잘못된 입력 퍼레이드 (5~6교시)

```
$ POST /reports pm25=-5 (물리 범위 밖)
  422 → {"detail": [{"type": "greater_than_equal", "loc": ["body", "pm25"], "msg": "Input should be greater than or equal to 0", "input": -5, "ctx": {"ge": 0.0}}]}
$ POST /reports station=부산 (미등록)
  422 → {"detail": [{"type": "value_error", "loc": ["body", "station"], "msg": "Value error, 등록되지 않은 측정소: 부산", "input": "부산", "ctx": {"error": {}}}]}
$ POST /reports measured_on=어제 (날짜 아님)
  422 → {"detail": [{"type": "date_from_datetime_parsing", "loc": ["body", "measured_on"], "msg": "Input should be a valid date or datetime, input is too short", "input": "어제", "ctx": {"error": "input is too short"}}]}
$ POST /reports 오타 필드 pm2_5 (계약 밖)
  422 → {"detail": [{"type": "missing", "loc": ["body", "pm25"], "msg": "Field required", "input": {...}}, {"type": "extra_forbidden", "loc": ["body", "pm2_5"], "msg": "Extra inputs are not permitted", "input": 41.5}]}
```

넷 다 서버는 멀쩡하고, 응답이 **무엇이·왜** 틀렸는지 말해 줍니다. 특히 마지막을 보세요 —
오타 필드 `pm2_5` 가 `extra_forbidden` 으로 **이름까지 지목**됩니다. `extra: "forbid"` 한 줄이
없었다면 이 요청은 "pm25 누락"으로만 보였을 것이고, 클라이언트 개발자는 자기 오타를
한참 뒤에 찾았을 겁니다. 다음 주 예측 API에서 특성 이름 오타는 **엉뚱한 예측**으로 직결되므로
([Day 068](../03-machine-learning/day-068.md) 과제 ②에서 체험한 그것), 이 옵션은 추론 API의 기본값입니다.

### Step 4. 404와 응답 계약 (7교시)

```
$ GET /reports/강남구/2026-08-13
  200 → {"station": "강남구", "measured_on": "2026-08-13", "pm25": 41.5, "grade": "나쁨"}
$ GET /reports/강남구/2026-01-01 (없음)
  404 → {"detail": "리포트가 없습니다"}

응답에 _internal_id가 있는가? False
```

저장할 때 분명히 넣은 `_internal_id` 가 응답에는 없습니다 — `response_model=ReportOut` 이
**선언된 필드만** 내보내기 때문입니다. "내부 정보를 빼먹지 말자"는 다짐(사람의 규율)이
아니라 계약(구조)이 지키는 것 — 이 과정에서 몇 번째 만나는 패턴인지 세어 보세요.

```powershell
git add api/main.py
git commit -m "Day 092: pydantic 계약 — 422/404/409 설계, extra forbid, 응답 모델"
```

**과제 — 검증 규칙 강화.** 오늘 API에 다음을 추가하고, 각각을 깨뜨리는 요청과 응답을 기록하세요.
① `measured_on` 은 미래 날짜 금지 (커스텀 검증기 — [Day 044](../02-sql-pipeline/day-044.md)의 미래 시각 검증과 같은 규칙)
② pm10이 오면 `pm25 <= pm10` 이어야 함 (힌트: `@model_validator(mode="after")` — 필드 둘을 함께 보는 검증)
③ station 목록을 `GET /stations` 로도 제공해, 클라이언트가 유효값을 미리 알 수 있게.

## ⑤ 자주 하는 실수

### 검증을 핸들러 안 if문으로 씀

**증상** — `if r.pm25 < 0: raise HTTPException(400, ...)` 가 핸들러마다 복붙됨.
**원인** — 계약(모델)의 일을 로직(핸들러)이 하고 있습니다. 에러 형식도 422와 달라져 클라이언트가 두 가지 형식을 처리해야 합니다.
**해결** — 값의 형태·범위·허용값은 전부 모델로 (Field·validator). 핸들러에는 **상태**에 관한 판단(404·409)만 남깁니다.

### extra 필드 기본 동작을 모름

**증상** — 클라이언트가 `pm2_5` 로 보냈는데 서버는 조용히 받고, pm25는 기본값으로 처리됨.
**원인** — pydantic 기본은 모르는 필드를 **무시**입니다.
**해결** — 입력 계약에는 `model_config = {"extra": "forbid"}`. 특히 추론 API처럼 필드 하나하나가 의미 있는 곳에서는 필수입니다.

### 422 응답을 그대로 두면 안 된다고 착각 (또는 그 반대)

**증상** — 422의 detail 배열을 감추려고 미들웨어로 "잘못된 요청입니다" 한 줄로 뭉개 버림 — 클라이언트 디버깅 불능.
**원인** — "에러를 자세히 주면 위험하다"의 과잉 적용입니다.
**해결** — 4xx의 loc/msg는 **클라이언트의 실수 교정 정보**라 두는 것이 기본. 감춰야 할 것은 5xx의 내부 정보(스택트레이스·경로)입니다 ([Day 098](day-098.md)).

### 응답 모델 없이 dict를 그대로 반환

**증상** — 리팩터링하다 내부 필드(원가·디버그 값)가 응답에 섞여 나감. 아무도 눈치 못 챔.
**원인** — 응답의 모양이 "그때그때 dict에 있는 것"으로 정의된 상태.
**해결** — 모든 엔드포인트에 `response_model` 선언. 응답 계약이 있으면 /docs의 응답 예시도 정확해집니다.

### date/datetime을 문자열로 받아서 손으로 파싱

**증상** — `measured_on: str` 로 받고 핸들러에서 `datetime.strptime` + try/except.
**원인** — pydantic이 해 주는 일을 모름.
**해결** — 타입을 `date` 로 선언하면 파싱·검증·에러 응답(`date_from_datetime_parsing`)까지 자동입니다. [Day 022](../01-python-data/day-022.md)에서 고생한 날짜 파싱의 상당 부분이 여기선 선언 한 줄입니다.

## ⑥ 확인 문제

**Q1.** 오늘 나온 세 가지 거절(422 · 404 · 409)의 구분 기준을 한 문장으로 정리하고,
"이미 삭제된 리포트를 다시 DELETE"하는 요청에는 무엇이 적절할지 논해 보세요.

<details>
<summary>답 보기</summary>

422는 **요청 자체**가 계약 위반, 404는 **대상 자원**이 없음, 409는 요청은 유효하나 **현재 상태와
충돌**입니다. 삭제된 것의 재삭제는 404(대상 없음)가 일반적이지만, "삭제는 멱등하게 — 이미 없어도
204"로 설계하는 유파도 있습니다 ([Day 042](../02-sql-pipeline/day-042.md)의 멱등성 관점). 중요한 것은
선택을 문서에 선언하는 것입니다.

</details>

**Q2.** `extra: "forbid"` 가 추론 API에서 특히 중요한 이유를, [Day 068](../03-machine-learning/day-068.md)
과제 ②(컬럼 값 뒤바꿈)와 연결해 설명하세요.

<details>
<summary>답 보기</summary>

추론 입력의 필드 하나가 곧 모델 특성 하나입니다. 오타 필드(pm2_5)가 조용히 무시되면 해당 특성이
누락·기본값 처리된 채 예측이 나가고 — 에러 없이 틀린 예측이라는 최악의 실패가 됩니다. forbid는
그 오타를 입구에서 이름까지 지목해 주므로, 조용한 실패를 시끄러운(고칠 수 있는) 실패로 바꿉니다.

</details>

**Q3.** 입력 계약(ReportIn)과 응답 계약(ReportOut)을 한 클래스로 합치지 않고 나눈 이유를
두 가지 쓰세요.

<details>
<summary>답 보기</summary>

① 방향이 다릅니다 — 입력엔 검증 규칙(범위·허용값·forbid)이, 응답엔 노출 범위(내부 필드 제외)가
필요해 요구사항이 서로 다릅니다. ② 진화가 다릅니다 — 입력 필드 추가는 클라이언트 호환성 문제,
응답 필드 추가는 비교적 안전 — 계약을 나눠야 각각 독립적으로 버전 관리할 수 있습니다.
(grade가 입력에선 선택, 응답에선 필수인 오늘 코드가 그 예입니다.)

</details>
