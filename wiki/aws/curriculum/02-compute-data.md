## 단원 개요

### 이 단원을 마치면

- 서버를 **손으로 만들지 않고** AMI와 사용자 데이터로 자동 구성되게 만들 수 있다.
- 부하와 장애에 따라 **인스턴스가 자동으로 늘고 교체되는 구조**를 만들 수 있다.
- 도메인과 인증서를 붙여 **HTTPS로 서비스되는 엔드포인트**를 제공할 수 있다.
- S3 · EBS · EFS · CloudFront를 **용도에 따라 선택**하고 근거를 댈 수 있다.
- 관계형 데이터베이스를 **프라이빗 서브넷에 이중화**해 배치하고 백업·복구를 수행할 수 있다.

### 왜 4주(8강)인가

이 단원은 **"인스턴스 1대"에서 "서비스"로 넘어가는 구간**입니다.
09–10강에서 서버를 일회용(disposable)으로 만드는 사고방식을 익히지 않으면, 11–12강의 로드밸런서도 16강의 무중단 배포도 성립하지 않습니다.
또한 여기서 만든 3계층 구조(ALB → 앱 → DB)가 **11주차 컨테이너, 12주차 IaC, 최종 프로젝트의 원형**입니다.
그래서 매주 산출물을 지우지 않고 **다음 주에 그 위에 얹는 방식**으로 진행합니다(단, NAT·ALB·RDS는 수업 후 삭제하고 재구축 스크립트로 복원).

## W05 · AMI · 사용자 데이터 · Auto Scaling

**09–10강** · 6시간 · 예상 비용 **$0.2 ~ 0.4**

> **주차 목표**
> - 서버 설정을 **이미지(AMI)와 스크립트(사용자 데이터)** 두 방식으로 재현하고 장단점을 비교한다.
> - 시작 템플릿과 Auto Scaling 그룹으로 **2개 AZ에 인스턴스를 자동 분산**한다.
> - 인스턴스를 일부러 종료해도 **서비스가 자동 복구**되는 것을 확인한다.

**이전 주차와의 연결** — 08강에서 만든 VPC의 프라이빗 앱 서브넷 2개가 이번 주 ASG의 배치 대상입니다. 06강에서 손으로 설치했던 nginx를 이번엔 **사용자 데이터로 자동 설치**합니다.

### 이론 수업 내용

**09강 (60분)**
1. **가축 vs 애완동물** — 서버를 고쳐 쓰는 대상이 아니라 언제든 버리고 새로 만드는 대상으로 보는 관점
2. AMI 구성 요소(루트 볼륨 스냅샷 + 권한 + 블록 디바이스 매핑)와 골든 AMI를 만드는 절차
3. 사용자 데이터(cloud-init)는 **최초 부팅 1회** 실행 — 실행 로그 위치(`/var/log/cloud-init-output.log`)와 디버깅
4. **선택 기준** — 부팅 속도가 중요하면 AMI에 미리 굽고(골든 AMI), 변경이 잦으면 스크립트로 내린다. 실무는 둘의 혼합
5. 인스턴스 타입 선택 — 범용(M/T) · 컴퓨팅(C) · 메모리(R) · 스토리지(I) 계열, 그리고 **버스터블 T 계열의 CPU 크레딧 소진 함정**
6. 구매 옵션 4종 비교 — 온디맨드 / Savings Plans / 예약 / 스팟, 각각 언제 쓰나

**10강 (60분)**
1. Auto Scaling의 3가지 역할 — ① 용량 자동 조절 ② **비정상 인스턴스 자동 교체** ③ AZ 간 균등 분산
2. 조정 정책 비교 — 타깃 추적(권장, "CPU 50% 유지") · 단계 조정 · 예약 조정, 그리고 쿨다운/워밍업
3. 헬스 체크 유형 — EC2 상태 검사만 볼 때와 **ELB 헬스 체크를 볼 때**의 차이(애플리케이션이 죽었지만 OS는 살아 있는 경우)
4. 인스턴스 새로 고침(Instance Refresh)으로 **무중단 롤링 배포**하기
5. 스케일 인 시 데이터 유실을 막는 법 — 상태를 인스턴스에 두지 않기(세션은 ElastiCache/DynamoDB, 파일은 S3/EFS)

### 보안 및 운영상 주의점

- 사용자 데이터에 **비밀번호·API 키를 절대 넣지 않습니다.** (메타데이터로 조회 가능) → 15강 Secrets Manager, 25강에서 정식 해결

- ASG의 최대 용량은 **비용 상한**이기도 합니다. 실습에서는 4를 넘기지 않습니다.

## W06 · ELB · Route 53 · HTTPS

**11–12강** · 6시간 · 예상 비용 **$0.6 ~ 0.8**

> **주차 목표**
> - ALB / NLB / GWLB의 차이를 계층과 용도로 구분하고 상황에 맞게 선택한다.
> - ASG를 대상 그룹에 연결해 **트래픽을 여러 AZ로 분산**하고 비정상 인스턴스를 자동 제외한다.
> - 도메인과 ACM 인증서를 연결해 **HTTPS 전용 서비스**를 제공한다.

**이전 주차와의 연결** — 10강에서 만든 ASG는 프라이빗 서브넷에 있어 아직 외부에서 접근할 수 없습니다. 이번 주에 **퍼블릭 서브넷의 ALB**를 그 앞에 세워 비로소 서비스가 됩니다.

### 이론 수업 내용

**11강 (60분)**
1. 로드밸런서가 해결하는 4가지 — 분산 · 가용성 · 확장 · **TLS 종료**
2. **선택 기준표** — ALB(HTTP/HTTPS, 경로·호스트 기반 라우팅, 대상 그룹에 Lambda/IP 가능) vs NLB(TCP/UDP, 초저지연, 고정 IP, 초당 수백만 요청) vs GWLB(보안 어플라이언스 삽입)
3. 리스너 → 규칙 → 대상 그룹의 3단 구조와 경로 기반 라우팅(`/api/*` → 다른 대상 그룹)
4. 헬스 체크 파라미터(경로·간격·임계값)와 **헬스 체크 실패가 곧 무중단 배포의 열쇠**인 이유
5. 교차 영역 부하 분산 · 스티키 세션 · 연결 드레이닝(등록 취소 지연)의 실전 의미
6. ALB 액세스 로그를 S3에 남기고 나중에 Athena로 분석(맛보기)

**12강 (60분)**
1. DNS가 요청을 찾아가는 순서(루트 → TLD → 권한 있는 네임서버)와 TTL의 의미
2. **Alias 레코드 vs CNAME** — Alias는 zone apex(`example.com`)에 사용 가능하고 **조회 요금이 무료**
3. 라우팅 정책 5종 — 단순 / 가중치(카나리 배포) / 지연 시간 / 장애 조치(액티브-패시브) / 지리 위치
4. ACM 인증서 — **ELB/CloudFront에 붙이면 무료**, DNS 검증 방식, 자동 갱신. (CloudFront용은 **버지니아 북부에서 발급**해야 함)
5. HTTPS 구성 3가지 결정 — 80 → 443 리다이렉트, 보안 정책(TLS 버전), 백엔드 구간 암호화 여부

### 보안 및 운영상 주의점

- ALB 보안 그룹은 **인터넷용(80/443)**, 인스턴스 보안 그룹은 **소스를 ALB 보안 그룹으로 지정**합니다. 인스턴스에 `0.0.0.0/0` 을 열지 않습니다.
- HTTP를 살려두지 말고 **443 리다이렉트**로 통일합니다. 보안 정책은 TLS 1.2 이상.
- 인증서 검증 CNAME 레코드를 **지우면 자동 갱신이 실패**합니다.
- ALB 액세스 로그를 켜면 S3 비용이 생깁니다. 실습에선 짧게 켜고 확인 후 끕니다.

### 이론 수업 내용

**13강 (60분)**
1. 객체 스토리지가 파일 시스템과 다른 점 — 경로가 아니라 **키**, 부분 수정 불가(전체 교체), 무한 확장
2. 11가지 9(99.999999999%) 내구성의 의미와 **가용성과의 차이**
3. 접근 제어 4중 구조 — 퍼블릭 액세스 차단 → 버킷 정책 → IAM 정책 → ACL(레거시). **버킷을 실수로 공개하는 사고**가 나는 지점
4. 스토리지 클래스 선택 기준 — Standard / Intelligent-Tiering / Standard-IA / One Zone-IA / Glacier Instant·Flexible / Deep Archive. **검색 비용과 최소 보관 기간**이 진짜 함정
5. 버전 관리 + 수명 주기 조합 — 실수 삭제 복구와 오래된 버전 자동 정리(**버전 관리만 켜면 비용이 늘어남**)
6. 사전 서명 URL(presigned URL) — 버킷을 열지 않고 임시 접근 권한을 주는 방법

**14강 (60분)**
1. **스토리지 3분류 선택 기준표**

| 유형 | 서비스 | 붙는 방식 | 언제 쓰나 | 주의 |
|---|---|---|---|---|
| 블록 | EBS | 인스턴스 1대에 연결(같은 AZ) | OS 디스크, 데이터베이스 | AZ 종속, 기본은 1:1 |
| 파일 | EFS | 여러 인스턴스가 동시 마운트(NFS) | 공유 업로드 폴더, 콘텐츠 공유 | GB 단가가 EBS보다 비쌈 |
| 객체 | S3 | HTTP API | 정적 자산, 백업, 로그, 데이터 레이크 | 부분 수정 불가 |

2. EBS 볼륨 타입 — gp3(기본·IOPS 독립 설정) / io2(고성능 DB) / st1·sc1(처리량형). **gp2에서 gp3로 바꾸면 대개 더 싸고 빠름**
3. 스냅샷은 **증분** 저장이지만 삭제 관리는 필요, DLM(수명 주기 관리자)로 자동화
4. CDN 원리 — 엣지 캐싱, 오리진 부하 감소, 지연 시간 단축, **전송 비용 절감**
5. CloudFront + S3의 정석 — **OAC(Origin Access Control)** 로 S3를 비공개 유지, 버킷 정책은 CloudFront만 허용
6. 캐시 동작 — 캐시 정책/TTL, 무효화(invalidation) 비용, 버전 파일명 전략(`app.a1b2.js`)

### 보안 및 운영상 주의점

- **버킷을 절대 퍼블릭으로 열지 않습니다.** 공개가 필요하면 CloudFront + OAC를 씁니다. (S3 퍼블릭 노출은 실무 최다 유출 사고 유형)
- S3 기본 암호화(SSE-S3)는 켜져 있습니다. 규제 요건이 있으면 **SSE-KMS**로 바꿉니다(25강).
- EFS는 **마운트 대상 보안 그룹**을 통해 접근합니다. 전체 개방 금지.
- 스냅샷을 다른 계정과 공유하면 **데이터가 그대로 넘어갑니다.** 공유 설정 주의.

- RDS는 **퍼블릭 액세스 "아니요"** 가 기본값이어야 합니다. 인터넷에서 직접 접근 가능한 DB는 즉시 스캔당합니다.

- 삭제 방지(deletion protection)는 운영에서는 켜고, 실습에서는 끄고 시작합니다(정리 실패 방지).

4. **월간 비용 산정서** — 구성 요소별 금액 + 30% 절감 방안 3가지(예: Savings Plans, NAT → 엔드포인트, gp2 → gp3)

## 이 단원에서 자주 나오는 질문

| 질문 | 답 |
|---|---|
| ASG가 있는데 ALB가 왜 필요한가요? | ASG는 **인스턴스 개수**를 관리하고, ALB는 **트래픽 분배와 비정상 인스턴스 제외**를 담당합니다. 둘은 역할이 다르며 함께 씁니다. (10·11강) |
| 인스턴스를 프라이빗에 두면 배포는 어떻게 하나요? | Session Manager, 사용자 데이터, 그리고 12주차의 CI/CD 파이프라인으로 합니다. SSH 포트 개방은 마지막 선택지입니다. (06·24강) |
| Multi-AZ면 읽기 성능도 좋아지나요? | 아니요. 가용성만 올라갑니다. 읽기 분산은 **읽기 전용 복제본**입니다. (15강) |
| S3를 퍼블릭으로 열면 안 되나요? | 됩니다만 사고의 대부분이 여기서 납니다. **CloudFront + OAC**로 비공개를 유지하는 것이 표준입니다. (13·14강) |
| 인증서는 왜 CloudFront만 버지니아인가요? | CloudFront는 **글로벌 서비스**라 인증서를 us-east-1에서 참조합니다. ALB용은 ALB와 같은 리전에서 발급합니다. (12강) |
| 실습 리소스를 다음 주까지 두면 안 되나요? | ALB·NAT·RDS Multi-AZ 세 개만 켜 두어도 **하루 약 $3, 월 $90** 입니다. 재구축 스크립트를 만들어 매주 다시 세우는 것이 이 과정의 훈련 목표이기도 합니다. |
