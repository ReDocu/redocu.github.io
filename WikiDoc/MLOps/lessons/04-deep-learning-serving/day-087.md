- 임베딩이 무엇인지(토큰 ID → 벡터 조회) 알고, **문장 임베딩**을 직접 만들 수 있다.
- 코사인 유사도로 **문장 사이의 의미 거리**를 계산할 수 있다.

## ② 왜 필요한가

어제 어텐션은 "단어 벡터"들이 이미 있다고 가정하고 시작했습니다. 오늘은 그 앞 단계 —
**"서울의 미세먼지가 심각하다"라는 문자열이 어떻게 벡터가 되는가** — 를 채웁니다.

```
문자열 ──[토큰화]──▶ 토큰 ID들 ──[임베딩 조회]──▶ 벡터들 ──[Transformer]──▶ 문맥 표현
```

이 경로를 알아야 하는 실무적 이유가 둘 있습니다.

1. **텍스트 서빙의 전처리가 바로 이것입니다.** [Day 097](day-097.md)에서 배울 "학습 전처리 =
   서빙 전처리" 원칙에서, 텍스트 모델의 전처리란 곧 토크나이저입니다. 토크나이저가 다르면
   같은 모델이 엉뚱한 답을 냅니다 — 오늘 그 사고를 일부러 냅니다.
2. **임베딩은 그 자체로 상품입니다.** 문장을 벡터로 만들 수 있으면 유사 문서 검색, 중복 탐지,
   추천, (별도 과정에서 다룰) RAG까지 — "의미로 검색하는" 모든 기능의 원료가 됩니다.

## ③ 개념 설명

### 서브워드 토큰화 — 단어와 글자 사이의 절충

| 방식 | 문제 |
|---|---|
| 단어 단위 | 사전에 없는 단어(신조어·오타)를 만나면 처리 불능 (OOV) |
| 글자 단위 | OOV는 없지만 시퀀스가 너무 길어지고 글자엔 뜻이 없음 |
| **서브워드** | **자주 쓰는 덩어리는 통째로, 처음 보는 말은 조각으로** — 두 문제를 동시에 해결 |

어휘집(vocabulary)은 학습 데이터에서 자주 등장한 조각 3~25만 개의 목록입니다.
`##` 접두는 "앞 토큰에 붙는 조각"이라는 표시입니다 (`미세먼지` + `##가`).

### 모델과 토크나이저는 한 몸

토큰 ID는 **그 어휘집 안에서만** 의미가 있습니다. ID 8315가 klue 어휘집에서는 '미세먼지'지만
다른 어휘집에서는 전혀 다른 조각입니다. 그래서:

> 모델을 바꾸면 토크나이저도 반드시 함께. 저장·배포·서빙 전 과정에서 **쌍으로** 움직입니다.
> (내일 배울 `AutoTokenizer.from_pretrained(같은 이름)` 이 이 쌍맞춤을 보장하는 장치입니다.)

### 임베딩 — 조회표일 뿐

임베딩 레이어는 신비한 것이 아니라 **(어휘 수 × 차원) 크기의 행렬**이고, 토큰 ID i의
임베딩은 그 행렬의 i번째 행입니다. 조회(lookup)가 전부입니다. 신비는 그 행들의 **값이
학습으로 채워졌다**는 데 있습니다 — 비슷한 문맥에 나오는 토큰들이 비슷한 방향을 갖게 되고,
그 위에 어제의 어텐션이 얹혀 문맥까지 반영됩니다.

### 문장 임베딩과 코사인 유사도

토큰 벡터들(문장당 수십 개)을 **하나의 문장 벡터**로 줄이는 표준 방법이
**평균(mean pooling)** 입니다 — 단, 패딩 토큰은 빼고 평균해야 합니다.
두 문장 벡터의 방향이 얼마나 비슷한지는 **코사인 유사도**(-1~1)로 잽니다.
오늘 쓰는 모델(paraphrase-multilingual-MiniLM)은 "같은 뜻이면 가깝게"를 목표로
추가 학습된 문장 임베딩 전용 모델입니다.

### Step 1. 한국어 토큰화 관찰 (1~2교시)

```python
# day087_tokens.py — 토큰화와 임베딩
import torch
import torch.nn.functional as F
from transformers import AutoModel, AutoTokenizer

print("== A. 토큰화 — 모델이 문장을 자르는 법 ==")
tok_ko = AutoTokenizer.from_pretrained("klue/bert-base")
sent = "서울의 미세먼지가 심각하다"
tokens = tok_ko.tokenize(sent)
ids = tok_ko.encode(sent)
print(f"문장   : {sent}")
print(f"토큰   : {tokens}")
print(f"ID     : {ids}")
print(f"복원   : {tok_ko.decode(ids)}")
print(f"어휘집 크기: {tok_ko.vocab_size:,}")

print("\n처음 보는 단어는? (신조어)")
print(f"'플로깅하다' → {tok_ko.tokenize('플로깅하다')}")
```

실행 결과:

```

문장   : 서울의 미세먼지가 심각하다
토큰   : ['서울', '##의', '미세먼지', '##가', '심각', '##하', '##다']
ID     : [2, 3671, 2079, 8315, 2116, 4927, 2205, 2062, 3]

'플로깅하다' → ['플로', '##깅', '##하', '##다']
```

관찰 세 가지. ① '미세먼지'는 자주 쓰여서 **한 토큰**, 조사 '의/가'는 `##` 조각.
② ID 맨 앞뒤의 2, 3은 자동으로 붙는 특수 토큰 `[CLS]`/`[SEP]`(문장 시작/끝 표지)입니다.
③ 어휘집에 없는 '플로깅'도 조각으로 쪼개져 **처리 불능이 없습니다** — [Day 063](../03-machine-learning/day-063.md)의
`handle_unknown="ignore"` 가 하던 걱정을 토큰화는 구조적으로 해결합니다.

### Step 3. 임베딩 — 조회표 확인과 문장 벡터 만들기 (4~5교시)

```python
print("\n== C. 임베딩 — 토큰 ID가 벡터가 되는 곳 ==")
model = AutoModel.from_pretrained("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")
tok = AutoTokenizer.from_pretrained("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")
emb_table = model.get_input_embeddings()
print(f"임베딩 테이블: {tuple(emb_table.weight.shape)}  (어휘 수 × 벡터 차원)")

def embed(sentences):
    """문장 → 벡터: 토큰화 → 모델 → 토큰 벡터들의 평균(mean pooling)"""
    batch = tok(sentences, padding=True, truncation=True, return_tensors="pt")
    with torch.no_grad():
        out = model(**batch).last_hidden_state          # (문장, 토큰, 384)
    mask = batch["attention_mask"].unsqueeze(-1)
    return (out * mask).sum(1) / mask.sum(1)            # 패딩 제외 평균
```

실행 결과 (해당 부분):

```
== C. 임베딩 — 토큰 ID가 벡터가 되는 곳 ==
임베딩 테이블: (250037, 384)  (어휘 수 × 벡터 차원)
```

25만 개 어휘 × 384차원 — 다국어 모델이라 어휘집이 큽니다. `embed` 함수의 재료를 보세요:
`padding`(문장 길이 맞추기), `attention_mask`(패딩을 평균에서 제외), 텐서 연산 —
전부 이번 단원에서 배운 부품입니다. 이 함수가 곧 **텍스트 서빙의 전처리+추론 코어**이고,
[Day 090](day-090.md)·[100](day-100.md)에서 재사용됩니다.

### Step 4. 문장 유사도 — 의미가 거리로 (6~7교시)

```python
print("\n== D. 문장 유사도 — 의미가 거리로 ==")
sentences = [
    "내일 서울의 미세먼지가 심할 예정이다",     # 기준
    "수도권 초미세먼지 농도가 나쁨 수준이겠다",  # 같은 뜻, 겹치는 단어 없음
    "내일 미세먼지 조심하세요",                  # 관련
    "주말에 등산을 가기로 했다",                 # 무관
    "주식 시장이 크게 하락했다",                 # 무관
]
vecs = embed(sentences)
print(f"문장 벡터: {tuple(vecs.shape)}")
base = vecs[0:1]
sims = F.cosine_similarity(base, vecs).tolist()
print(f"\n기준: \"{sentences[0]}\"")
for s, sim in zip(sentences[1:], sims[1:]):
    print(f"  {sim:.3f}  \"{s}\"")
```

실행 결과:

```
== D. 문장 유사도 — 의미가 거리로 ==
문장 벡터: (5, 384)

기준: "내일 서울의 미세먼지가 심할 예정이다"
  0.847  "수도권 초미세먼지 농도가 나쁨 수준이겠다"
  0.788  "내일 미세먼지 조심하세요"
  0.449  "주말에 등산을 가기로 했다"
  0.460  "주식 시장이 크게 하락했다"
```

주목 — 1위 문장(0.847)은 기준과 **겹치는 단어가 하나도 없습니다** (서울↔수도권,
미세먼지↔초미세먼지, 심하다↔나쁨). 단어 일치가 아니라 **의미의 방향**이 잰 것입니다.
무관한 문장들은 0.45 근처로 뚝 떨어집니다. "대기질 민원만 골라내기", "비슷한 과거 민원
찾기" 같은 기능이 이 숫자 하나로 만들어집니다.

값 자체의 감각도 잡아 두세요: 이 모델·이 pooling에서는 "0.8대 = 같은 얘기, 0.4대 = 남남"
입니다. **절대 눈금은 모델마다 다르므로**, 실무에서 임계값은 자기 데이터로 잡습니다
([Day 056](../03-machine-learning/day-056.md)의 임계값 논리 그대로).

## ⑤ 자주 하는 실수

### 모델과 토크나이저를 다른 곳에서 가져옴

**증상** — 에러 없이 돌아가는데 결과가 엉망 (Step 2에서 재현한 그것).
**원인** — 토큰 ID는 어휘집에 종속인데, A 모델에 B 어휘집의 ID를 넣었습니다.
**해결** — 항상 **같은 이름**으로 쌍을 로드: `AutoTokenizer.from_pretrained(name)` + `AutoModel.from_pretrained(name)`. 서빙 코드에서도 이름을 상수 하나로 공유하세요.

### mean pooling에서 패딩을 포함해 평균

**증상** — 짧은 문장일수록 유사도가 이상하게 낮거나 서로 비슷해짐.
**원인** — 배치 패딩으로 채워진 자리(뜻 없는 벡터)까지 평균에 들어가 문장 벡터가 희석됩니다.
**해결** — Step 3처럼 `attention_mask` 를 곱해 실제 토큰만 합산하고 실제 토큰 수로 나눕니다.

### 유사도의 절대값을 모델 간 비교

**증상** — "A 모델은 0.85, B 모델은 0.7이니 A가 더 잘 잡는다"는 결론.
**원인** — 코사인 값의 분포(눈금)는 모델·pooling마다 다릅니다. 같은 모델 **안에서의 순위·간격**만 의미가 있습니다.
**해결** — 모델 비교는 같은 과제(예: 과제의 10문장 분리력)에서의 **순위 품질**로. 임계값은 모델마다 다시 잡습니다.

### encode와 tokenize의 차이를 모름

**증상** — 토큰 7개라 생각했는데 모델 입력 길이는 9라 shape 계산이 어긋남.
**원인** — `encode` 는 `[CLS]`/`[SEP]` 특수 토큰을 자동으로 붙입니다 (Step 1의 ID 맨 앞뒤 2, 3).
**해결** — 길이 계산·비용 추정에는 `encode` 결과 기준으로. 특수 토큰의 존재를 항상 셈에 넣으세요 (긴 문서가 잘리는 `truncation` 한계 512에도 이 2개가 포함됩니다).

### 임베딩을 "그 단어의 뜻"으로 고정 해석

**증상** — 임베딩 테이블에서 꺼낸 '배'의 벡터로 과일/선박을 구분하려 함.
**원인** — 테이블의 행은 **문맥 없는** 기본 벡터입니다. 동음이의어 구분은 어텐션을 통과한 뒤(last_hidden_state)에야 생깁니다.
**해결** — 의미 작업에는 모델 출력(문맥 반영 벡터)을 쓰세요. 테이블 조회는 입구일 뿐입니다 — 어제 Step 2의 "새 표현 만들기"가 그 차이였습니다.

통째 토큰이라 효율도 지킵니다 — 단어 방식의 표현력과 글자 방식의 완전성을 절충한 설계입니다.

</details>

**Q2.** Step 4에서 1위 문장은 기준과 겹치는 단어가 없는데도 0.847이 나왔습니다. 키워드 검색과
임베딩 검색의 차이를 이 사례로 설명하세요.

<details>
<summary>답 보기</summary>

키워드 검색은 문자열 일치를 세므로 "서울/수도권", "심하다/나쁨" 같은 동의 표현을 놓칩니다.
임베딩은 학습 과정에서 비슷한 문맥의 표현들이 비슷한 방향을 갖게 되어, 단어가 달라도 **의미의
방향이 같으면 가깝게** 측정됩니다. 그래서 민원 분류·유사 문서 검색처럼 표현이 다양한 과제에서
임베딩 기반 접근이 강합니다.

</details>
