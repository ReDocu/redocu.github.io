## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 값을 **설정과 시크릿**으로 등급 분류하고, 각각의 올바른 주입 경로를 고를 수 있다.
- 시크릿의 **4대 금지처**(코드·저장소·이미지·로그)를 알고, 각각의 노출을 **검사하는 명령**을 쓸 수 있다.
- compose의 `${VAR}` 치환 + `.env` 로 어제의 평문 비밀번호를 수술할 수 있다.
- 같은 compose.yaml로 **개발/운영 환경을 분리**해 띄울 수 있다.

---

## ② 왜 필요한가

어제 PR에는 시한폭탄이 하나 실렸습니다 — `POSTGRES_PASSWORD: mp3pass` 가 평문으로 저장소에
들어갔죠. "실습용 비번인데 뭐"라고 넘기기 전에, 이 패턴이 실무에서 반복되면 무슨 일이 나는지
경로를 따라가 봅시다:

```
compose.yaml에 평문 → 저장소에 영구 기록 (히스토리 포함 — Day 109에서 배운 그 성질)
                   → 저장소를 보는 모두가 운영 DB 비밀번호를 앎
                   → 저장소가 공개되는 순간 (포트폴리오!) 전 세계가 앎
```

실제 유출 사고의 가장 흔한 경로가 해킹이 아니라 **커밋**입니다. 그리고 이미지에 구우면
(`ENV DB_PASSWORD=...`) 이미지를 받는 모두에게, 로그에 찍으면 로그를 보는 모두에게 —
시크릿은 놓는 자리마다 그 자리의 독자 전원에게 공개됩니다.

원칙은 한 문장입니다 — **코드·이미지는 공유물, 설정은 환경의 것, 시크릿은 주입되는 것.**
같은 이미지가 개발에선 개발 DB로, 운영에선 운영 DB로 붙는 것도 이 분리가 있어야 가능합니다
([Day 093](../04-deep-learning-serving/day-093.md)에서 설정을 코드에서 분리해 둔 것이 받는 쪽
준비였고, 오늘은 넣는 쪽을 완성합니다). 커리큘럼이 이 날을 "시크릿을 이미지에 굽지 않기"라고
굵게 적어 둔 이유 — MP4 완료 조건에 "시크릿이 저장소·이미지 어디에도 없다"가 있습니다.

## ③ 개념 설명

### 값의 세 등급

| 등급 | 예 | 어디 두나 |
|---|---|---|
| 상수 | 모델 입력 크기 224, 정규화 평균 | **코드/이미지에** — 환경 따라 안 변함 |
| 설정 | 포트, 로그 레벨, 워커 수, DB **호스트** | compose.yaml `environment:` — 공개돼도 무해, 리뷰 대상 |
| **시크릿** | DB **비밀번호**, API 키, 토큰 | **`.env` (커밋 금지) → `${VAR}` 로 주입** |

헷갈리면 질문 하나로 판별합니다: **"이 값이 공개 저장소에 올라가면 사고인가?"** — 예면 시크릿.

### 주입 경로와 우선순위

```
[코드 기본값]  <  [이미지의 ENV]  <  [compose environment / env_file]  <  [셸의 export]
 늘 있는 안전값     굽는 값(공개만!)      환경별 파일에서                     임시 재정의
```

compose.yaml에서 시크릿을 다루는 표준형은 **치환**입니다:

```yaml
environment:
  POSTGRES_PASSWORD: ${DB_PASSWORD}     # 값이 파일에 없음 — 이름만
```

`${DB_PASSWORD}` 의 실제 값은 compose가 실행 시점에 **같은 폴더의 `.env` 파일**(또는 셸 환경)
에서 찾아 채웁니다. 그래서:

| 파일 | 내용 | Git |
|---|---|---|
| `compose.yaml` | 구조 + `${변수}` 자리 | ✅ 커밋 (리뷰 대상) |
| `.env` | `DB_PASSWORD=진짜값` | ❌ **.gitignore** · 권한 600 (Day 112) |
| `.env.example` | `DB_PASSWORD=` (이름만, 값 없이) | ✅ 커밋 — "무엇이 필요한지"의 문서 |

### 시크릿의 4대 금지처와 검사 명령

| 금지처 | 새는 경로 | 검사 |
|---|---|---|
| ① 코드 | 소스에 하드코딩 | `grep -rE "password|secret|token" app/` |
| ② 저장소 | .env·설정 파일 커밋 | `git log --all --oneline -- .env` (히스토리까지!) |
| ③ **이미지** | Dockerfile ENV/ARG·COPY .env | `docker history 이미지` · `docker run --rm 이미지 cat /app/.env` |
| ④ 로그 | 기동 메시지·에러에 URL 통째 출력 | `docker compose logs \| grep -i pass` |

③이 오늘의 주인공입니다 — 이미지는 배포물이라 **받는 사람 모두가 내부를 볼 수 있다**는 사실이
자주 잊힙니다. 그리고 완전한 정직함을 위해: 환경 변수 주입도 만능이 아닙니다 — 서버에서
`docker inspect` 권한이 있으면 보입니다. 오늘의 목표는 "**공유물(코드·저장소·이미지)에서
시크릿 제거**"이고, 주입값 자체의 금고화(Vault·클라우드 시크릿 매니저)는 취업 후의 다음
단계입니다.

## ④ 단계별 실습

### Step 1. 사고 재현 A — 이미지에 구운 시크릿 (1~2교시)

백문이 불여일견 — 일부러 최악의 Dockerfile을 만들어 봅니다 (`Dockerfile.bad`, hello-api에서):

```dockerfile
FROM python:3.12-slim
ENV DB_PASSWORD=super-secret-2026
COPY . .
```

```bash
docker build -f Dockerfile.bad -t leaky:test . -q
docker history leaky:test --format "{{.CreatedBy}}" | head -3
```

```
$ docker history leaky:test --format "{{.CreatedBy}}" | head -3
COPY . . # buildkit
ENV DB_PASSWORD=super-secret-2026
FROM python:3.12-slim
```

**이미지의 이력서에 비밀번호가 그대로** 적혀 있습니다 — 이 이미지를 pull 할 수 있는 사람
전원이 볼 수 있습니다. `docker inspect leaky:test | grep -A3 Env` 로도 확인해 보고,
`docker rmi leaky:test` 로 폐기하세요. 빌드 ARG로 넘겨도 history에 남습니다 (⑤) —
**이미지에는 시크릿이 들어갈 안전한 자리가 없습니다.** 그래서 굽지 않고 주입합니다.

### Step 2. 수술 — 평문 제거와 ${VAR} 주입 (3~4교시)

`/opt/mlops-mp3` 에서 (브랜치 `fix/secrets`) 어제의 compose.yaml을 수술합니다:

```yaml
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql+psycopg://mp3:${DB_PASSWORD}@db:5432/mp3
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: mp3
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: mp3
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

`.env` 와 `.env.example` 을 만들고 (전자는 이미 .dockerignore와 .gitignore에 있는지 **반드시**
확인 — [Day 117](day-117.md)에서 넣어 뒀습니다), 치환 결과를 검증합니다:

```bash
echo "DB_PASSWORD=Zk9#mR2vLq8w" > .env && chmod 600 .env
echo "DB_PASSWORD=" > .env.example
docker compose config | grep -A2 "POSTGRES_PASSWORD"
```

```
$ docker compose config | grep -A2 "POSTGRES_PASSWORD"
      POSTGRES_PASSWORD: Zk9#mR2vLq8w
      POSTGRES_USER: mp3
```

`docker compose config` — 치환이 끝난 **최종 선언**을 보여 주는 디버깅 도구입니다. 파일에는
`${DB_PASSWORD}`, 실행에는 진짜 값, 저장소에는 이름만. 기동해서 어제의 기능(예측 로그)이
그대로인지 확인 후 PR — diff에서 평문이 사라지는 것이 이 PR의 존재 이유입니다.

> 어제 이미 평문을 push 했다는 사실은 그대로 남습니다 — [Day 109](day-109.md)의 규율대로
> **비밀번호 자체를 오늘 바꾼 것**(Zk9#...)이 정답이지, 커밋 삭제가 아닙니다.

### Step 3. 환경 분리 — 같은 선언, 다른 값 (5~6교시)

"개발은 느슨하게, 운영은 조이게"를 값의 차이로 표현합니다:

```bash
cat > .env.dev <<'EOF'
DB_PASSWORD=devpass
LOG_LEVEL=DEBUG
EOF
cat > .env.prod <<'EOF'
DB_PASSWORD=Zk9#mR2vLq8w
LOG_LEVEL=INFO
EOF
docker compose --env-file .env.dev up -d
docker compose exec api printenv LOG_LEVEL
docker compose --env-file .env.prod up -d
docker compose exec api printenv LOG_LEVEL
```

```
$ docker compose --env-file .env.dev up -d && docker compose exec api printenv LOG_LEVEL
DEBUG
$ docker compose --env-file .env.prod up -d && docker compose exec api printenv LOG_LEVEL
INFO
```

(compose.yaml의 api environment에 `LOG_LEVEL: ${LOG_LEVEL:-INFO}` 를 추가해 두세요 —
`:-INFO` 는 "미설정 시 기본값" 문법입니다.) **코드도 이미지도 compose.yaml도 동일**한데
환경만 갈아 끼웠습니다 — 이미지 태그 하나가 개발·운영 어디서나 같은 배포물이라는 원칙이
이렇게 지켜집니다. `.env.prod` 는 운영 서버에만 존재하고(600, deploy 소유), 저장소에는
.example만 — 파일들의 거처가 곧 보안 설계입니다.

### Step 4. 사고 재현 B — 로그로 새는 시크릿 (7교시)

마지막 금지처. 기동 로그에 설정을 찍는 흔한 습관을 재현합니다 — main.py lifespan에
`print(f"DB 연결: {os.environ['DATABASE_URL']}")` 를 넣어 보면:

```bash
docker compose logs api | head -3
```

```
$ docker compose logs api | head -3
mlops-mp3-api-1  | DB 연결: postgresql+psycopg://mp3:Zk9#mR2vLq8w@db:5432/mp3
mlops-mp3-api-1  | INFO:     Started server process [1]
mlops-mp3-api-1  | INFO:     Application startup complete.
```

로그를 보는 모두(팀원·로그 수집 시스템·화면 공유 중의 청중)에게 비밀번호가 공개됐습니다.
수정 — URL을 통째로 찍지 말고 **마스킹**해서:

```python
from sqlalchemy.engine import make_url
url = make_url(os.environ["DATABASE_URL"])
print(f"DB 연결: {url.host}:{url.port}/{url.database} (user={url.username})")   # 비밀번호 제외
```

[Day 098](../04-deep-learning-serving/day-098.md)의 "개인정보 로그 금지"와 같은 근육입니다 —
**로그는 공개 게시판이라고 전제하고 쓴다.**

### Step 5. 과제 — 설정 점검표 (8교시)

mlops-mp3의 모든 외부화된 값을 전수 조사해 표로 만드세요:

`값 이름 | 등급(상수/설정/시크릿) | 현재 주입 경로 | 기본값 유무 | 4대 금지처 검사 결과(①~④ 각 명령과 결과)`

최소 항목: DB_PASSWORD · DATABASE_URL · LOG_LEVEL · MODEL_PATH · 포트. 그리고 마지막 줄에
**"이 저장소를 지금 공개해도 되는가"** 에 대한 판정과 근거 (git 히스토리 검사 포함 — 어제의
평문 커밋을 어떻게 처리했는지 명시). 이 점검표는 MP4 제출물의 일부가 됩니다 (완료 조건:
"시크릿이 저장소·이미지 어디에도 없다").

## ⑤ 자주 하는 실수

### .env를 커밋

**증상** — `git status` 에 .env가 떠서 무심코 `git add .` — 진짜 값들이 저장소로.
**원인** — .gitignore 누락, 또는 "example인 줄" 착각.
**해결** — 예방: .gitignore에 `.env*` + 예외로 `!.env.example`. 사고 후: **값 전부 즉시 교체**
([Day 109](day-109.md) — 폐기가 먼저, 히스토리 청소는 그다음). 오늘 이후 여러분의 저장소에서
이 사고는 "몰랐다"가 아니라 "점검표를 안 돌렸다"가 됩니다.

### .env.example에 진짜 값을 넣어 둠

**증상** — "예시니까 돌아가는 값으로" — example이 사실상 .env 사본이 되어 커밋됨.
**원인** — example의 목적(필요한 **이름**의 문서화)을 값 제공으로 오해.
**해결** — example에는 이름과 형식 힌트만: `DB_PASSWORD=   # 16자 이상, 운영값은 팀 금고에서`.
신입이 그대로 복사해 채우는 "빈 서식"이어야 합니다.

### 시크릿을 빌드 ARG로 넘기면 안전하다는 오해

**증상** — `ARG DB_PASSWORD` + `--build-arg DB_PASSWORD=...` — "ENV 아니니까 괜찮겠지".
**원인** — ARG도 **layer 메타데이터에 남습니다** — `docker history` 에 `|1 DB_PASSWORD=...`
형태로 그대로.
**해결** — 원칙 재확인: 이미지에는 시크릿의 안전한 자리가 없다. 빌드 시점에 비밀이 꼭 필요한
특수 상황(사설 저장소 인증 등)은 BuildKit의 `--secret` 마운트라는 전용 장치가 있다는 것만
알아 두세요 — 우리 과정 범위에선 "빌드에 시크릿이 필요 없게 설계"가 답입니다.

### variable is not set 경고를 무시

**증상** —
```
WARN[0000] The "DB_PASSWORD" variable is not set. Defaulting to a blank string.
```
그리고 DB가 빈 비밀번호로 초기화되거나 기동 실패.
**원인** — .env가 없는 곳에서 up (다른 폴더, 새 서버, CI).
**해결** — 이 경고는 에러로 취급하세요. 필수 시크릿에는 기본값 문법을 **일부러 안 쓰는** 것도
방어입니다 — `${DB_PASSWORD:?required}` 로 쓰면 미설정 시 기동 자체가 거부됩니다 (조용한 빈
문자열보다 시끄러운 실패가 낫다 — Day 115의 -u와 같은 철학).

### environment와 env_file의 관계를 혼동

**증상** — `env_file: .env` 도 쓰고 `${VAR}` 치환도 쓰다가, 어느 값이 어디서 왔는지 미궁.
**원인** — 두 기능의 역할 차이: **`.env`(치환용)** 는 compose.yaml의 `${}` 를 채우는 파일이고,
**`env_file:`(주입용)** 은 그 파일 내용을 컨테이너 환경 변수로 통째로 넣는 서비스 옵션입니다.
**해결** — 이 과정의 표준은 치환(`${}` + .env) 하나로 통일 — 어떤 변수가 쓰이는지 compose.yaml에
**이름이 전부 드러나기** 때문입니다 (리뷰 가능성). 헷갈릴 땐 `docker compose config` 가 심판.

<summary>답 보기</summary>

저장소: 접근자 전원 + **전체 히스토리의 미래 독자**, 공개 전환 시 전 세계 (가장 넓고 영구적).
이미지: pull 권한자 전원 — 레지스트리 공개면 역시 전 세계 (배포될수록 확산). 로그: 로그 열람자
+ 수집·보관 시스템의 모든 하류 (화면 공유·스크린샷으로도 유출). 코드(하드코딩): 결국 저장소·
이미지에 실려 위 경로로 합류. 순서는 상황에 따르지만 공통점은 하나 — **놓는 순간 그 매체의
독자 전원에게 공개**이며, 시크릿의 자리는 "실행 직전 주입" 한 곳뿐입니다.

</details>

**Q3.** `${DB_PASSWORD:?required}` 와 `${LOG_LEVEL:-INFO}` — 두 문법의 동작 차이와, 어떤 값에
어느 쪽을 쓰는 게 옳은지 기준을 세워 보세요.

<details>
<summary>답 보기</summary>

`:?` 는 미설정 시 **에러로 기동 거부**, `:-` 는 미설정 시 **기본값으로 조용히 진행**. 기준:
없으면 사고가 나는 값(시크릿·필수 연결 정보)은 `:?` — 빈 문자열로 어중간히 뜨는 것보다 즉시
실패가 안전합니다 (fail fast). 없어도 합리적 기본이 있는 설정(로그 레벨·워커 수)은 `:-`.
"시끄러운 실패 vs 조용한 기본값"의 선택이며, 시크릿에 기본값을 주는 것은 항상 오답입니다.

</details>
