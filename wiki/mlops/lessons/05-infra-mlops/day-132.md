## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- DVC와 모델 레지스트리의 **역할 차이**(버전 박제 vs 배포 상태 관리)를 설명할 수 있다.
- MLflow Registry에 모델을 **등록**하고, **별칭(alias)** 으로 운영/후보 상태를 관리할 수 있다.
- 서빙이 "파일 경로"가 아니라 **"레지스트리의 운영 모델"** 을 로드하게 바꿀 수 있다.
- 모델을 **검증 → 승격 → 교체 → 롤백**하는 절차를 실행하고 소요 시간을 측정할 수 있다.

---

## ② 왜 필요한가

어제 DVC로 "그 커밋의 모델"을 복원할 수 있게 됐습니다. 그런데 운영의 질문은 조금 다릅니다:

> "**지금 운영에 물려 있는** 모델은 뭐고, 다음 후보는 뭐죠? 후보로 언제 바꿀 겁니까?"

이것은 시간축(커밋 히스토리)의 질문이 아니라 **상태**의 질문입니다 — 같은 모델 버전이 오늘은
후보였다가 내일은 운영이 되고 모레는 은퇴합니다. 코드에는 이 상태 관리가 이미 있습니다 —
브랜치(개발)와 main(운영), 그리고 승격 절차(PR·게이트). 모델에는? 없다면 이런 풍경이 됩니다:

```
models/
├── pm25_pipeline.joblib
├── pm25_pipeline_v2.joblib
├── pm25_pipeline_v2_fixed.joblib
├── pm25_pipeline_final.joblib          ← 운영은 이거? 
└── pm25_pipeline_final_진짜최종.joblib  ← 아니면 이거?
```

W01의 "보고서_최종_진짜최종.hwp"를 비웃던 우리가 모델로 같은 짓을 하게 되는 겁니다.
**모델 레지스트리**는 모델계의 "브랜치와 main" — 버전들의 명부와, 그중 무엇이 어느 상태인지
(운영·후보), 그리고 승격·강등의 공식 절차를 제공합니다. 도구는 새것이 아닙니다 —
[Day 067](../03-machine-learning/day-067.md)부터 실험을 기록해 온 **MLflow의 다른 방**입니다.
그리고 [Day 126](day-126.md) 임시방편의 남은 반쪽 — "서빙은 모델을 어디서 얻는가"의 정식
답이 오늘 나옵니다.

## ③ 개념 설명

### DVC와 레지스트리 — 겹치지 않는 분업

| | DVC (어제) | **레지스트리 (오늘)** |
|---|---|---|
| 관리 단위 | 커밋에 묶인 화물의 **지문** | 모델의 **버전 명부와 상태** |
| 답하는 질문 | "그 커밋 시점의 데이터·모델은?" | "지금 운영은 v몇? 후보는? 언제 바뀌었나?" |
| 시간축 | Git 히스토리에 종속 | 배포 수명 주기 (커밋과 독립) |
| 소비자 | 재현·조사하는 사람/CI | **서빙 서버·배포 절차** |

둘은 경쟁이 아니라 층입니다 — 학습의 재현성은 DVC·MLflow run이, 배포의 상태는 레지스트리가.

### MLflow Registry의 구조

```
Registered Model: "pm25-forecaster"          ← 모델의 이름 (하나)
 ├── Version 1   (run 6ac527ba…)             ← MP2의 그 모델
 ├── Version 2   (run f81c2e9d…, 어제 재학습) 
 │
 └── Aliases:  @production → Version 1       ← 상태는 별칭으로
               @staging    → Version 2
```

- **버전**은 등록 순서대로 자동 증가 — 각 버전은 **run에 연결**되어 학습의 전 족보(파라미터·
  지표·data_md5)가 따라옵니다 (067의 기록이 여기서 배당금을 줍니다).
- **별칭(alias)** 은 움직이는 이름표 — `@production` 이 가리키는 버전이 곧 운영 모델입니다.
  승격 = 별칭 이동. 롤백 = 별칭 되돌리기. **몇 초짜리 포인터 연산**이라는 것이 핵심입니다.

### 서빙의 계약 변경 — 경로가 아니라 이름으로

```python
# 지금까지 (Day 096):  파일 경로에 결합
pipe = joblib.load("models/pm25_pipeline.joblib")

# 오늘부터:           레지스트리의 "운영" 별칭에 결합
model = mlflow.sklearn.load_model("models:/pm25-forecaster@production")
```

서빙 코드는 이제 **"운영 모델이 무엇인지" 모릅니다** — 알 필요가 없습니다. 그 결정은
레지스트리의 별칭이 하고, 서빙은 로드 시점의 별칭을 따를 뿐. 결정과 실행의 분리 —
[Day 124](day-124.md)에서 프록시 뒤의 일꾼을 손님이 모르는 것과 같은 구도입니다.

## ④ 단계별 실습

### Step 1. 레지스트리 개장과 등록 (1~2교시)

MLflow 서버를 올립니다 (067의 mlflow.db 그대로 — 석 달치 실험 기록이 자산이 됩니다):

```bash
mlflow server --backend-store-uri sqlite:///mlflow.db --port 5000
```

MP2의 운영 모델(run `6ac527ba`)과 어제 재학습(run `f81c2e9d`)을 등록합니다:

```python
# register.py — 기존 run의 모델을 레지스트리에 등록
import mlflow

mlflow.set_tracking_uri("http://localhost:5000")

v1 = mlflow.register_model("runs:/6ac527baab8e45b4b9a85607b9ebf9f5/model", "pm25-forecaster")
v2 = mlflow.register_model("runs:/f81c2e9d3a7b40c8b2e5d90a1c4f7e28/model", "pm25-forecaster")
print(f"등록 완료: v{v1.version}, v{v2.version}")
```

```
$ python register.py
Successfully registered model 'pm25-forecaster'.
Created version '1' of model 'pm25-forecaster'.
Created version '2' of model 'pm25-forecaster'.
등록 완료: v1, v2
```

UI(localhost:5000)의 **Models** 탭 — 명부가 생겼습니다. 각 버전을 클릭하면 원 run으로
연결되어 파라미터·지표·data_md5까지 한 화면입니다.

### Step 2. 별칭 부여 — 상태의 선언 (3교시)

```python
from mlflow import MlflowClient

client = MlflowClient("http://localhost:5000")
client.set_registered_model_alias("pm25-forecaster", "production", 1)   # 현 운영 = 검증된 v1
client.set_registered_model_alias("pm25-forecaster", "staging", 2)      # 후보 = 어제의 v2
```

이 두 줄이 ②의 "파일명 지옥"을 대체합니다 — 운영이 무엇인지는 이제 **파일명도 기억도 아닌
레지스트리의 사실**입니다.

### Step 3. 승격 게이트 — 검증 없는 승격 금지 (4~5교시)

v2를 바로 운영에 올리지 않습니다 — 코드에 게이트(127)가 있듯 모델에도 게이트를 둡니다.
`promote.py`:

```python
# promote.py — staging 모델을 검증하고, 통과 시에만 production 승격
import mlflow
from mlflow import MlflowClient
from sklearn.metrics import mean_absolute_error

from evaluate import load_holdout          # 최근 4주 홀드아웃 (Day 052의 시간 분리 원칙)

TRACKING, NAME = "http://localhost:5000", "pm25-forecaster"
GATE_MARGIN = 0.98    # 신규가 현 운영 MAE의 98% 이하(=2% 이상 개선)일 때만 승격

mlflow.set_tracking_uri(TRACKING)
client = MlflowClient(TRACKING)

X, y = load_holdout()
mae = {}
for alias in ("production", "staging"):
    model = mlflow.sklearn.load_model(f"models:/{NAME}@{alias}")
    mae[alias] = mean_absolute_error(y, model.predict(X))
    print(f"{alias}: MAE {mae[alias]:.3f}")

if mae["staging"] <= mae["production"] * GATE_MARGIN:
    ver = client.get_model_version_by_alias(NAME, "staging").version
    client.set_registered_model_alias(NAME, "production", ver)
    print(f"승격: v{ver} → @production")
else:
    print("승격 보류: 개선 폭 미달 — staging 유지")
```

```
$ python promote.py
production: MAE 4.213
staging: MAE 3.897
승격: v2 → @production
```

같은 홀드아웃에서 7.5% 개선 — 게이트 통과, v2가 운영 별칭을 받았습니다. 숫자가 부족했다면
**아무 일도 일어나지 않는 것**이 이 스크립트의 미덕입니다 (배포되는 것은 언제나 검증 통과분 —
main의 원리가 모델에도).

### Step 4. 서빙 교체와 롤백 — 스톱워치를 들고 (6~7교시)

serve_pm25.py의 lifespan을 레지스트리 로드로 바꿉니다 (③의 그 두 줄 교체 +
`/model/info` 가 별칭·버전을 응답하게). 실행은 [Day 113](day-113.md) 과제의 요령대로
`pm25-api.service` 를 등록해 두면 좋고, 오늘은 uvicorn 직접 실행(포트 8001)이어도 충분합니다.
교체 시연:

```bash
sudo systemctl restart pm25-api        # (systemd 등록 시 — 직접 실행이면 Ctrl+C 후 재실행)
curl -s localhost:8001/model/info
```

```
$ curl -s localhost:8001/model/info
{"name":"pm25-forecaster","alias":"production","version":"2","run_id":"f81c2e9d","data_md5":"7f3e9a20"}
```

운영이 v2로 — 코드·이미지는 한 글자도 안 바뀌었습니다. 이제 **롤백 리허설** (v2에 문제가
발견됐다는 가정, 시간을 잽니다):

```bash
python -c "from mlflow import MlflowClient; MlflowClient('http://localhost:5000').set_registered_model_alias('pm25-forecaster','production',1)"
sudo systemctl restart pm25-api
curl -s localhost:8001/model/info | grep -o '"version":"1"'
```

```
"version":"1"
소요: 별칭 이동 1초 + 재시작·로드 6초 = 약 7초
```

**모델 롤백 7초** — MP4 평가 항목("모델 교체 소요 시간")의 기준 기록입니다. 파일 교체
방식이었다면? 어느 파일이 진짜 v1인지 찾는 시간부터 계산이 안 됩니다.

### Step 5. 과제 — 롤백 절차 문서화 (8교시)

`docs/MODEL_ROLLBACK.md` 를 작성하세요:

1. **판단** — 무엇이 보이면 롤백하는가 (에러율? 드리프트? 민원? — 내일 배울 지표로 다듬을
   초안), 판단 권한은 누구에게
2. **절차** — 명령 시퀀스 (별칭 확인 → 이동 → 재로드 → 검증) + 각 단계의 실측 소요
3. **검증** — 롤백 완료의 증거 (/model/info 대조 + 대표 입력 예측값 대조)
4. **기록** — 어디에 무엇을 남기나 (누가·언제·왜·v몇→v몇 — deploy_history.log의 모델판)
5. **한계** — 별칭 롤백이 못 되돌리는 것은? (힌트: 입력 스키마가 바뀐 교체였다면 — 서빙
   코드와 모델의 호환 계약. [Day 068](../03-machine-learning/day-068.md) 스키마의 재등장)

antbee 모델(MP3)도 같은 요령으로 "resnet-antbee" 등록 + 별칭 관리까지가 보너스 과제입니다 —
torch 모델은 `mlflow.pytorch` 로, 요령은 동일합니다.

## ⑤ 자주 하는 실수

### 레지스트리 도입 후에도 파일 복사로 배포

**증상** — 레지스트리는 만들어 놓고, 정작 교체는 여전히 scp로 joblib 덮어쓰기 — 명부와 현실이
곧 어긋남 ("레지스트리엔 v2가 운영인데 서버 파일은 v1").
**원인** — 서빙 코드가 여전히 파일 경로를 로드 — 계약 변경(③) 없이 명부만 도입.
**해결** — 서빙의 로드 경로를 `models:/이름@production` 으로 바꾸는 것까지가 도입입니다.
명부는 **유일한 진실**이어야 하고, 그러려면 소비자(서빙)가 명부를 읽어야 합니다.

### 별칭만 옮기고 서빙 재로드를 잊음

**증상** — 승격 완료 선언 — 그런데 응답의 model_version이 그대로. "레지스트리 버그인가요?"
**원인** — 서빙은 **로드 시점**의 별칭을 따랐을 뿐, 별칭 이동을 구독하지 않습니다
([Day 096](../04-deep-learning-serving/day-096.md)의 1회 로드 설계 — 그 장점의 이면).
**해결** — 교체 절차에 재로드 단계 명시 (재시작, 또는 관리용 /reload 엔드포인트 — 캐시
무효화까지, [Day 099](../04-deep-learning-serving/day-099.md)의 그 교훈). "별칭 이동 + 재로드 +
검증"이 한 절차입니다.

### 검증 없는 승격 — staging의 형해화

**증상** — "급하니까" MAE 확인 없이 별칭 이동 — staging이 그냥 경유지 이름이 됨. 어느 날
나쁜 모델이 무사통과.
**원인** — 절차는 도구가 아니라 규율 — 도구는 별칭 이동을 막지 않습니다.
**해결** — 승격을 promote.py **경유로만** 하기로 팀 규칙화 (게이트 수치와 홀드아웃 명시).
더 강하게는 W26의 방식 — 승격 스크립트를 CI 워크플로로 만들고 사람은 실행 버튼만
(Day 133~135에서 이 방향으로 조립합니다).

### 레지스트리 저장소를 백업 대상에서 누락

**증상** — mlflow.db(또는 백엔드 DB)가 날아감 — 모델 파일은 있는데 **명부가 증발**: 어느 게
운영이었는지, 버전 족보가 전부 소실.
**원인** — "모델 파일만 소중하다"는 착각 — 상태와 족보도 데이터입니다.
**해결** — 레지스트리 백엔드를 [Day 125](day-125.md)의 백업 체계에 편입 (sqlite면 파일 백업,
DB면 pg_dump). "명부 없는 창고는 창고가 아니다"를 기억하세요.

### 원 run을 지워 버전의 뿌리를 끊음

**증상** — mlflow 실험 정리한다고 옛 run들 삭제 — 레지스트리 버전이 고아가 되어 아티팩트
로드 실패.
**원인** — run(학습 기록·아티팩트의 실소유)과 버전(그 run을 가리키는 명부 항목)의 관계를
모른 채 청소.
**해결** — 레지스트리에 등록된 버전의 run은 보존 대상입니다 — 정리 전 `client.search_model_versions`
로 참조 여부 확인. 청소 규칙: "명부에 오른 것의 뿌리는 지우지 않는다."

**Q1.** "DVC가 있는데 레지스트리가 왜 또 필요한가"라는 질문에, 두 도구가 답하는 질문의 차이
(시간축 vs 상태)와 소비자의 차이로 답하세요.

<details>
<summary>답 보기</summary>

DVC는 "커밋 X 시점의 데이터·모델 실물"을 복원하는 도구 — 시간축이 Git 히스토리에 묶여 있고,
소비자는 재현·조사하는 사람과 CI입니다. 레지스트리는 커밋과 독립적인 **배포 수명 주기**(v1
운영 중, v2 후보, 승격·강등 이력)를 관리하며, 소비자는 서빙 서버와 배포 절차입니다. "지난달
그 실험을 재현하라" → DVC/run, "지금 운영을 후보로 바꿔라" → 레지스트리. 하나는 박제, 하나는
현역 명부 — 재현성과 운영성은 다른 요구이고, 그래서 층이 둘입니다.

</details>

**Q2.** 별칭 방식(@production 포인터)의 롤백이 이미지 sha 롤백([Day 128](day-128.md))과 구조적으로
동일함을 보이고, 두 경우 모두에서 "가변 이름표로 상태를 관리하지 말라"는 규율이 어떻게
변형되어 적용되는지 설명하세요.

<details>
<summary>답 보기</summary>

둘 다 "불변 실체(이미지 digest·모델 버전) + 움직이는 포인터(태그·별칭)" 구조이고, 롤백은 실체
복구가 아니라 **포인터 되돌리기**라 초 단위입니다. 규율의 변형: 이미지에서는 latest(가변)로
배포·기록하지 말고 sha(불변)로 말하라였고, 모델에서는 별칭이 **의도된 가변 포인터**로 승격된
대신 — "별칭이 언제 어느 버전을 가리켰는가"의 **이동 이력**을 기록하라(과제 4번)가 됩니다.
공통 원리: 상태는 가변 포인터가 갖되, 조사와 기록은 언제나 불변 식별자의 언어로.

</details>

**Q3.** promote.py의 게이트(현 운영 대비 2% 개선)가 코드 쪽 게이트(127)와 다른, 모델 특유의
어려움 두 가지를 지적하고 보완 방향을 제안하세요.

<details>
<summary>답 보기</summary>

① 판정 기준이 이진이 아닙니다 — 테스트는 통과/실패지만 MAE는 홀드아웃의 선택·기간에 따라
흔들리고, 전체 평균이 좋아져도 특정 구간(고농도일)이 나빠질 수 있습니다. 보완: 홀드아웃 고정
규약 + 구간별(계절·측정소) 세부 지표 병기, 경계선이면 사람 리뷰로. ② 오프라인 지표가 온라인
성능을 보장하지 않습니다 — 검증 데이터와 실제 유입 분포가 다르면(드리프트 — 내일!) 게이트가
무의미해집니다. 보완: 승격 후에도 운영 지표 감시(내일)와 점진 배포(카나리 — Day 135 개념)로
"승격 = 끝"이 아니라 "승격 = 감시 시작"으로 설계.

</details>
