## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 팀의 Git 규칙(브랜치 이름 · 커밋 메시지 · PR 기준)을 **한 장의 문서로 합의**할 수 있다.
- 4인 동시 작업에서 브랜치 → PR → 리뷰 → 병합 사이클을 **충돌을 겪으며** 완주할 수 있다.
- 팀원의 사고(잘못된 병합)를 revert PR로 수습할 수 있다.
- 이번 주 체크포인트에 답한다: **같은 파일을 고쳐 충돌이 나도 10분 안에 정리하는가.**

---

## ② 왜 필요한가

이번 주 나흘 동안 도구는 다 배웠습니다 — 충돌 해결(106), 히스토리 문체(107), PR 관문(108),
사고 대응(109). 그런데 도구를 아는 4명을 한 저장소에 넣으면 곧바로 이런 대화가 시작됩니다:

> "브랜치 이름 그냥 `test` 로 했는데요" · "커밋 메시지 영어예요 한글이에요?" ·
> "제 PR 누가 봐 줘요? 아무도 안 봐서 그냥 merge 했어요" · "어, main에 누가 직접 push 했지?"

기술 문제가 아니라 **합의 부재** 문제입니다. 그리고 합의는 머리로 아는 것과 문서로 적는 것과
몸으로 겪는 것이 다 다릅니다. 오늘 오전에 규칙을 **문서로** 만들고, 오후에 그 규칙 아래에서
일부러 충돌·사고를 겪습니다 — 최종 프로젝트(W29, 4인 팀)의 첫 3일에 벌어질 일을 미리
안전한 환경에서 소진하는 것이 오늘의 목적입니다.

## ③ 개념 설명

### 팀 규칙 문서 — 적을수록 지켜진다

규칙 문서(관례상 `CONTRIBUTING.md`)에 들어갈 것은 네 덩어리면 충분합니다:

| 덩어리 | 정할 것 | 이 과정의 기본값 |
|---|---|---|
| 브랜치 | 이름 규약 · 어디서 따나 | `feature/…` `fix/…` `chore/…` · 항상 최신 main에서 |
| 커밋 | 메시지 형식 · 언어 | `유형: 요약` 한 줄 (예: `fix: 업로드 413 경계값 수정`) · 한국어 |
| PR | 크기 · 리뷰어 수 · 병합 방식 | ±300줄 목표 · 승인 1명 이상 · squash · 병합 후 브랜치 삭제 |
| 금지 | 절대 안 되는 것 | main 직접 push · 공유 브랜치 rebase · `--force` |

규칙이 10개를 넘으면 아무도 안 읽습니다. **어기면 실제로 사고가 나는 것만** 적고, 취향 문제
(탭이냐 스페이스냐)는 도구(포매터 — W26의 ruff)에 맡기는 것이 요령입니다.

### 신사협정에서 강제로 — 이 규칙들의 미래

오늘 문서의 "금지" 항목은 아직 **신사협정**입니다 — 어겨도 Git이 막지 않습니다.
이 과정에서 그 간극이 메워지는 일정표:

| 규칙 | 오늘 (W22) | 나중 |
|---|---|---|
| main 직접 push 금지 | 약속 | [Day 127](day-127.md) 브랜치 보호 규칙으로 **차단** |
| 병합 전 테스트 통과 | 각자 pytest | [Day 126](day-126.md)–127 CI가 **강제** |
| 리뷰 1명 이상 | 약속 | [Day 127](day-127.md) 필수 승인 수로 **강제** |

규칙을 사람의 선의에 맡기지 않고 시스템에 옮기는 것 — 이 단원 전체의 주제이기도 합니다.

## ④ 단계별 실습

4인 1팀을 만듭니다. 역할: **리더**(저장소 소유·최종 병합), **기록**(회의 결정 문서화), 나머지는
개발자 — 단, 라운드마다 전원이 PR 작성자이자 리뷰어입니다.

### Step 1. 규칙 회의 (1~2교시)

팀 저장소 `team-playbook` 의 뼈대를 합의합니다. 리더가 저장소를 만들고 전원을 협업자로 초대:

```
team-playbook/
├── CONTRIBUTING.md        팀 규칙 (오늘 오전의 산출물)
├── cheatsheet.md          이번 주 명령 치트시트 (팀원별 섹션)
├── README.md              팀 소개 표 (충돌 훈련장이 될 파일)
└── .github/
    └── PULL_REQUEST_TEMPLATE.md
```

회의 안건은 ③의 표 그대로 네 덩어리입니다. **기본값을 그대로 채택해도 되지만, 각 항목마다
"왜"를 팀원 한 명이 설명할 수 있어야** 채택으로 인정합니다 (설명 못 하면 그 규칙은 장식입니다).
기록 담당이 결정을 CONTRIBUTING.md 초안으로 작성합니다.

### Step 2. 규칙의 첫 적용 — 규칙 문서 자체를 PR로 (3~4교시)

CONTRIBUTING.md를 **규칙대로** 넣습니다: 기록 담당이 `chore/contributing` 브랜치 → PR →
**전원 리뷰**(각자 [q]나 [nit] 하나 이상 — 규칙 문서야말로 오해의 소지를 지금 없애야 합니다) →
반영 → 리더가 squash 병합. 이 PR이 팀의 첫 관문 통과 기록이 됩니다.

```
$ git log --oneline
a3c92f1 (HEAD -> main, origin/main) chore: 팀 규칙 문서 추가 (#1)
f00c211 초기 커밋: 저장소 뼈대
```

### Step 3. 라운드 1 — 영역을 나눈 동시 작업 (5교시)

전원 동시에: `cheatsheet.md` 에 **자기 이름의 섹션**을 만들어 이번 주 명령 5개를 정리하고
PR을 엽니다 (`feature/cheatsheet-이름`). 리뷰는 옆 사람 것을 맡습니다 (원형으로: A→B→C→D→A).

4개의 PR이 순서대로 병합되는데 — **충돌이 나지 않습니다.** 같은 파일이지만 서로 다른 영역(자기
섹션)이기 때문입니다 ([Day 106](day-106.md) ③의 표). 단, 2번째 이후 병합자는 GitHub가
"This branch is out-of-date" 를 표시하면 **Update branch** (또는 로컬에서 `git rebase main` 후
force-with-lease)로 따라잡고 병합합니다.

> 여기서 팀이 몸으로 얻는 결론: **영역을 나누면 동시 작업은 무섭지 않다.** 분담 설계가 충돌
> 예방의 90%입니다.

### Step 4. 라운드 2 — 강제 충돌, 10분 타이머 (6~7교시)

이번엔 일부러 정면충돌입니다. README.md의 팀 소개 표에 **"이번 주 팀 목표" 한 줄**이 있습니다:

```markdown
| 이번 주 팀 목표 | (미정) |
```

전원 동시에 이 **같은 줄**을 서로 다른 문구로 고쳐 PR을 엽니다. 첫 PR이 병합되는 순간
나머지 3개는 전부 충돌 상태가 됩니다 — GitHub가 "This branch has conflicts that must be
resolved" 를 표시합니다. 각자 타이머를 켜고 해결합니다:

```powershell
git switch main; git pull                 # 최신 main 확보
git switch feature/goal-B
git rebase main                            # 충돌 발생 지점
# README.md 열어 마커 정리 — 팀 목표는 대화로 합의 (자기 문구 고집 금지!)
git add README.md
git rebase --continue
git push --force-with-lease               # 내 개인 브랜치이므로 허용
```

해결의 순간마다 **대화가 강제**된다는 걸 느낄 겁니다 — "팀 목표"의 정답은 코드가 아니라 합의이기
때문입니다. 마지막 사람까지 병합되면 타이머 기록을 공유하세요. **전원 10분 이내**면 이번 주
체크포인트 통과입니다.

### Step 5. 라운드 3 — 사고와 수습 (7교시 계속)

리더가 몰래 사고를 냅니다: 규칙을 어기고 **main에 직접** 커밋을 push 합니다 (cheatsheet에
잘못된 명령 — 예: `git push --force로 강제 푸시한다` 같은 위험 문장).

- 먼저 발견한 사람이 이슈 제기 → [Day 109](day-109.md)의 판단 기준 적용: main은 공유 역사 → **revert PR**
- revert PR 리뷰·병합 후, 회고 안건에 추가: "규칙 위반을 시스템이 못 막았다" → ③의 일정표(W26에서
  강제로 전환)를 전원이 확인

### Step 6. 회고와 주간 퀴즈 (8교시)

15분 회고 — 세 질문에 팀으로 답해 CONTRIBUTING.md 하단에 기록합니다:

1. 오늘 규칙 중 실제로 우리를 구한 것은? (예: "최신 main에서 브랜치" 덕에 라운드 1이 순탄)
2. 문서에 없어서 우왕좌왕한 것은? → 규칙 한 줄 추가 (10개 상한 유지!)
3. 최종 프로젝트에서 오늘과 달라질 위험 요소는? (파일 수십 개·5일 연속 작업)

이후 주간 퀴즈 19를 각자 풉니다.

### 오늘 새로 나오는 실수

### 4개의 PR이 서로를 기다리는 교착

**증상** — "제 PR 먼저 봐 주세요" 가 4방향으로 — 아무도 리뷰를 시작 안 해 1시간 정체.
**원인** — 리뷰 담당을 안 정함. 선의는 병목의 원인입니다.
**해결** — 오늘처럼 **원형 배정**(A→B→C→D→A)이나 라운드로빈을 규칙에 넣으세요. "리뷰 요청받고
2시간 내 첫 반응"처럼 SLA를 정하는 팀도 있습니다.

### 충돌 해결하며 남의 문구를 말없이 삭제

**증상** — 라운드 2에서 자기 문구만 남기고 병합 — 회고에서 "내 목표 어디 갔어요?" 발견.
**원인** — 충돌을 "이기는 것"으로 착각 ([Day 106 ⑤](day-106.md)의 팀 버전).
**해결** — 같은 줄 충돌의 해답이 코드 밖(합의)에 있을 땐 **해결 전에 묻는 것**이 규칙입니다.
30초 질문이 30분 감정 소모를 예방합니다.

### 규칙 과잉

**증상** — 열정 넘치는 첫 회의에서 규칙 23개 제정 — 다음 주부터 아무도 전부 기억 못 함.
**원인** — 규칙 수와 팀 성숙도를 혼동.
**해결** — "어기면 사고 나는 것"만 남기고 삭제. 규칙의 품질 지표는 개수가 아니라 **전원이 외우고
있는가**입니다.

## ⑥ 확인 문제

**Q1.** 라운드 1(영역 분담)은 충돌이 안 났고 라운드 2(같은 줄)는 전원 충돌이었습니다. 이 대비를
근거로, 최종 프로젝트에서 충돌을 구조적으로 줄이는 작업 분담 원칙을 두 가지 쓰세요.

<details>
<summary>답 보기</summary>

① **파일/모듈 단위로 소유를 나눈다** — 3-way 병합은 다른 파일·다른 영역이면 자동으로 합치므로,
담당 모듈이 갈리면 충돌 확률이 급감합니다 (MP3의 router/service/model_store 분리가 협업 설계이기도
한 이유). ② **공유 지점(설정 파일·공용 문서·requirements.txt)의 변경은 예고 후 짧게** — 어차피
겹칠 수밖에 없는 파일은 "고치기 전 팀 채널에 한 줄" + 작은 PR로 빨리 병합해 충돌 창을 좁힙니다.

</details>

**Q2.** 라운드 3에서 리더의 main 직접 push를 revert로 수습했습니다. reset --hard로 지우는 수습과
비교해, 팀 관점에서 revert가 옳은 이유 두 가지를 드세요.

<details>
<summary>답 보기</summary>

① main은 전원이 pull 해 간 **공유 역사** — reset은 역사를 되감아 팀원 전원의 로컬과 갈라지고
(force push까지 필요), revert는 앞으로만 자라서 아무의 저장소와도 충돌하지 않습니다.
② revert는 "사고가 있었고 이렇게 걷어냈다"는 **기록**을 남깁니다 — 회고와 재발 방지(규칙 개정,
W26 강제화)의 근거 자료가 됩니다. 사고를 지우는 팀보다 기록하는 팀이 빨리 좋아집니다.

</details>

**Q3.** 오늘 팀 규칙 중 "PR은 승인 1명 이상"이 있지만 아직 시스템이 막아 주지 않습니다.
이 간극이 실제 사고가 되는 시나리오와, W26에서 어떻게 메워지는지 쓰세요.

<details>
<summary>답 보기</summary>

시나리오: 마감 직전 "급해서요" 라며 셀프 병합 — 리뷰 없는 코드가 main에 들어가고, 그것이 곧
서버 배포(W26 이후엔 자동 배포)로 이어져 장애가 사용자에게 닿습니다. 메우는 법: [Day 127](day-127.md)의
**브랜치 보호 규칙** — main 직접 push 차단 + 필수 승인 수 + 필수 상태 검사(CI 통과)를 저장소
설정으로 강제하면, "급해서요"가 기술적으로 불가능해집니다. 규칙은 문서가 아니라 설정이 될 때
완성됩니다.

</details>

## 주간 퀴즈 19 — W22 (Git/GitHub 팀 협업)

<details>
<summary>1. 충돌이 나는 세 가지 조건은?</summary>

같은 파일 + 같은(또는 맞닿은) 줄 + 서로 다른 내용. 셋 중 하나라도 빠지면 3-way 병합이 자동으로 합칩니다.

</details>

<details>
<summary>2. 충돌 해결의 세 단계와, 병합에서 물러나는 명령은?</summary>

결정(마커 정리) → 신고(git add) → 마무리(git commit). 물러나기는 git merge --abort — 병합 전 상태로 완전 복귀.

</details>

<details>
<summary>3. 충돌 해결의 진짜 완료 조건은?</summary>

마커 삭제가 아니라 **실행·테스트 통과**. 병합은 텍스트 연산이라 호출 관계 같은 의미까지 보장하지 못합니다.

</details>

<details>
<summary>4. merge와 rebase가 남기는 히스토리 모양의 차이는?</summary>

merge는 두 갈래를 잇는 병합 커밋(다이아몬드)을 추가(비파괴), rebase는 내 커밋들을 상대 끝에서 재창조해 직선을 만듦(해시 변경 = 파괴적).

</details>

<details>
<summary>5. rebase의 황금률과 그 근거는?</summary>

push 등으로 공유한 커밋은 rebase 금지. rebase는 커밋을 재창조(해시 변경)하므로, 같은 작업의 두 버전이 세상에 존재하게 되어 팀 전체의 pull이 꼬입니다.

</details>

<details>
<summary>6. "따라잡기는 rebase, 합치기는 merge"에서 각각의 이유는?</summary>

따라잡기(내 feature를 main 최신으로): 아직 나만의 커밋이라 재창조 무해 + 직선 유지. 합치기(feature→main): 병합 커밋이 기능 단위 경계로 남아 사고 조사·revert 단위가 됨.

</details>

<details>
<summary>7. GitHub Flow의 대원칙과 다섯 단계는?</summary>

원칙: main은 항상 배포 가능. 단계: 브랜치 → PR → 리뷰 → 병합 → 브랜치 삭제.

</details>

<details>
<summary>8. squash 병합의 효과와 이 과정이 기본값으로 쓰는 이유는?</summary>

브랜치의 커밋 전부를 새 커밋 하나로 뭉쳐 main에 넣음 — PR 하나 = 커밋 하나. 작업 중 커밋은 자유롭게, main은 깔끔하게 유지되고, revert 단위도 PR 단위가 되어 초심 팀에 사고가 적습니다.

</details>

<details>
<summary>9. revert와 reset의 선택 기준은?</summary>

공유했는가. 공유된 역사(main 등)는 반대 커밋을 추가하는 revert, 나만의 역사는 되감는 reset/rebase -i. 공유 역사 reset은 팀 전체 사고로 번집니다.

</details>

<details>
<summary>10. --force-with-lease가 --force보다 안전한 이유와, 그래도 허용되는 범위는?</summary>

원격이 "내가 마지막으로 본 상태"일 때만 덮어써서, 그 사이 올라온 팀원 커밋의 증발을 차단. 그래도 역사 재작성 자체는 그대로이므로 내 개인 브랜치에서만 허용.

</details>
