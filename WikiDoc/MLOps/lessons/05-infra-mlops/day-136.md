## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- MP4의 배점표를 해부해 **5일의 힘을 어디에 쓸지** 결정할 수 있다.
- 운영 아키텍처를 **3장의 문서**(구성도 · 배포 흐름도 · 감시 항목표)로 그릴 수 있다.
- 필수 기능 목록에 대해 **갭 감사**(있다/없다가 아니라 **증거 명령으로** 증명)를 수행할 수 있다.
- Compose 구성과 시크릿 상태를 확정하고, 5일 일정과 위험 목록을 세울 수 있다.

## ② 왜 필요한가

"MP4요? 그거 우리가 6주 동안 수업에서 다 만들지 않았나요?" — 절반만 맞습니다.
수업의 산출물은 **부품과 리허설**입니다. 교사와 함께, 정답을 보며, 각자 조금씩 다른 상태로
만들어 왔죠. MP4는 그것을 **심사 가능한 완성품**으로 바꾸는 주간입니다. 차이는 세 가지:

1. **전부 여러분의 저장소에서** — "수업 때 됐었는데"는 증거가 아닙니다
2. **남이 실행해서** — 배점표를 보세요: 재현성 25 + CI/CD 완성도 30 = **55점이 "심사위원이
   직접 실행했을 때"** 에 걸려 있습니다 (clone→up, PR→자동 배포)
3. **문서와 함께** — 운영 절차서(10점)는 "미래의 팀원이 여러분 없이" 운영할 수 있는가의 시험

그리고 MP3 때의 교훈을 상기하세요 ([Day 101](../04-deep-learning-serving/day-101.md) —
"MP3는 모델 프로젝트가 아니라 서비스 프로젝트"). MP4의 버전은 이렇습니다: **MP4는 기능
프로젝트가 아니라 신뢰 프로젝트입니다.** 새 기능을 만드는 주간이 아니라, "이 시스템은 누가
언제 만져도 예측 가능하게 동작한다"를 증명하는 주간 — 그래서 첫날은 코드가 아니라 감사와
설계입니다.

## ③ 개념 설명

### 배점표 해부 — 힘의 배분

| 항목 | 배점 | 심사 방법 (예상) | 지금 우리의 위험 |
|---|---|---|---|
| 재현성 | 25 | 심사위원 PC에서 clone → .env → up → 데모 | 새 환경 리허설 부족분 |
| CI/CD 완성도 | 30 | PR 하나를 실제로 열어 게이트→병합→자동 배포 관찰 | 러너·시크릿의 환경 의존 |
| 운영 설계 | 25 | 로그·헬스·롤백을 질문과 실행으로 검증 | 절차의 문서화 미비 |
| 문서 | 10 | 운영 절차서만 보고 재시작·롤백 수행 | "머리로는 아는" 상태 |
| 발표 | 10 | 라이브 시연 (커밋→반영) | 시연 리스크 관리 |

읽는 법 — **새 코드를 쓸 곳이 거의 없습니다.** 5일의 힘은 검증(빈 환경 리허설), 문서화,
그리고 선택 기능 한두 개에 갑니다. 초급 트랙(Compose+CI까지)과 상급 트랙(+CD·모델 교체·
드리프트)의 갈림도 오늘 정합니다 — 기준은 야심이 아니라 **금요일에 시연 가능한가**입니다.

### 아키텍처 문서 — 3장이면 충분하다

`docs/ARCHITECTURE.md` 의 구성:

| 장 | 내용 | 원형 (이미 있음!) |
|---|---|---|
| 1. 구성도 | 컨테이너·볼륨·네트워크·포트 — **지금 실제로 도는 것** | [Day 125](day-125.md)의 최종 compose를 그림으로 |
| 2. 배포 흐름도 | push부터 서버 반영까지 관문들 | [Day 130](day-130.md) Step 1의 지도 |
| 3. 감시 항목표 | 무엇을·임계치·알림·대응 | [Day 134](day-134.md) 과제의 설계서 |

원칙 하나 — **그림은 이상이 아니라 현실의 사진**이어야 합니다. "이렇게 만들 예정"은 설계가
아니라 소망입니다. 오늘 그리는 그림과 실제 상태의 차이가 곧 이번 주의 작업 목록(갭)입니다.

### 갭 감사 — "있다"가 아니라 "증명된다"

필수 기능마다 세 열을 채웁니다: **상태**(✅/🔶/⬜) · **증거 명령** · **마지막 검증일**.
"있다고 기억함"은 🔶입니다 — MP4에서 상태의 정의는 "**증거 명령이 지금 통과한다**"뿐입니다.

## ④ 단계별 실습

### Step 1. 아키텍처 문서 초판 (1~3교시)

③의 3장 구조로 `docs/ARCHITECTURE.md` 를 작성합니다. 1장 구성도의 예 (자기 것으로):

```
                     ┌────────────────────────────── mlops-mp3 (서버 1대) ─┐
  인터넷 ── :8080 ──▶│ nginx ──▶ api (8000, 내부) ──▶ db (5432, 내부)      │
                     │  │ static/    │ healthcheck     │ volume: pgdata    │
                     │  └ 8m 제한    └ 모델 45MB 내장   └ prediction_log    │
                     └──────────────────────────────────────────────────┘
  GHCR ◀── build(CI) ── GitHub ◀── PR+게이트 ── 개발자
    └──── pull ──── deploy(self-hosted runner) ── 스모크·롤백 ── 이력 로그
```

각 요소 옆에 근거 문서를 링크하세요 (nginx 8m → [Day 124](day-124.md), 스모크 →
[Day 129](day-129.md)…) — 심사 질문("왜 이렇게 했나")의 답을 문서가 대신하게.

### Step 2. 갭 감사 — 증거 명령 실행 (4~5교시)

필수 기능 표를 **명령을 실제로 실행하며** 채웁니다. 예시 상태 (여러분 것은 다를 겁니다):

| 필수 기능 | 상태 | 증거 명령 | 결과 |
|---|---|---|---|
| Dockerfile 최적화 | ✅ | `docker images` — 1.61GB · `docker history` | 통과 |
| Compose 풀스택 | ✅ | 빈 폴더 clone → up → 데모 페이지 | **7분 — 목표 5분 초과** 🔶 |
| CI (테스트·린트) | ✅ | 일부러 깨진 PR → 병합 버튼 잠김 | 통과 |
| CD (자동 배포) | ✅ | README 오타 PR → 2분 후 서버 반영 | 통과 |
| 구조화 로그 | ✅ | `compose logs api \| head` — JSON · 시크릿 grep 빈 출력 | 통과 |
| 헬스체크 | ✅ | `compose ps` — (healthy) ×3 · kill 후 자동 회복 | 통과 |
| **모델 버전 교체 절차** | 🔶 | 문서 없음 — 132는 pm25에서만 리허설 | **antbee 미적용** |

이 표의 🔶들이 내일부터의 작업 목록입니다 — 예시 기준으로는 "리허설 시간 단축"과 "antbee
모델의 레지스트리 편입 + 교체 절차"가 상급 트랙의 몸통이 됩니다.

### Step 3. Compose 확정과 시크릿 정리 (6~7교시)

- compose.yaml **동결** — 이번 주 구성 변경은 오늘까지. [Day 125](day-125.md)의 다섯 축
  리뷰를 최종 실행하고, 남는 이슈는 "알려진 한계"로 문서에 (숨기는 것보다 선언이 점수입니다).
- **시크릿 전수 점검** — [Day 122](day-122.md) 과제의 점검표를 재실행: 4대 금지처 각각의
  검사 명령 + git 히스토리 검사까지. MP4 완료 조건("시크릿이 저장소·이미지 어디에도 없다")의
  증거 자료로 결과를 문서에 첨부합니다.

### Step 4. 일정과 위험 — 첫날 퇴근 조건 (8교시)

5일 계획을 세웁니다 (MP3 때 배운 그대로 — 뒤에서부터: 금요일 발표에서 역산):

| 날 | 목표 | 완료 판정 |
|---|---|---|
| 화 (137) | 풀스택 완성 — 빈 환경 5분 기동 | 새 폴더 리허설 스톱워치 |
| 수 (138) | CI/CD 완성 — 롤백 리허설 포함 | 심사 시나리오 자가 실행 |
| 목 (139) | 감시·모델 교체 + 운영 절차서 | 절차서만 보고 짝이 수행 |
| 금 (140) | 발표 — 커밋→반영 라이브 | 백업 시연 준비 완료 |

**위험 목록** 상위 3개와 대응을 적으세요 (예: "발표 중 빌드 4분 — 캐시 워밍으로 1분대 확보" /
"심사위원 PC에 Docker 미설치 — 내 서버 원격 시연으로 대체" / "페어의 분담 경계 — 앱/인프라
역할표를 README에 명시").

**오늘 퇴근 체크** — □ ARCHITECTURE.md 3장 초판 □ 갭 감사표 (전 항목 증거 명령 포함)
□ 시크릿 점검 결과 첨부 □ 5일 계획 + 위험 3 □ (페어) 역할 분담 명시

## ⑤ 자주 하는 실수

### 감사 없이 첫날부터 새 기능

**증상** — 의욕적으로 드리프트 대시보드부터 착수 — 목요일에야 "clone하면 안 뜨는데요"를 발견.
**원인** — 배점표를 안 읽음 — 선택 기능(가산점)이 필수(55점)를 잡아먹는 배분.
**해결** — 오늘의 순서(감사 → 갭 → 계획)가 그 방지책입니다. 새 기능은 "필수 전 항목 ✅ 증명"
이후의 사치로.

### 아키텍처 그림이 소망을 그림

**증상** — 그림에는 Airflow·드리프트 감지가 있는데 저장소에는 없음 — 심사 질의에서 그림
전체의 신뢰 붕괴.
**원인** — 설계도(할 것)와 현황도(있는 것)의 혼동.
**해결** — 그림은 현실의 사진 + 갭은 별도 표기 (점선·⬜ 범례). "그림의 실선은 전부 증거
명령이 있다"를 원칙으로 — 그래야 그림이 발표의 무기가 됩니다.

### 페어인데 역할이 "같이"

**증상** — 2인 페어가 모든 것을 같이 — 병목도 같이, 커밋 로그는 한 명 이름뿐.
**원인** — 분담 설계 생략 (기획서의 "역할: 앱/인프라 분담 명시"를 장식으로 취급).
**해결** — 지금 정하세요: 앱 담당(모델 교체·로그·대시보드)과 인프라 담당(리허설·CI/CD·절차서)
— 단 **PR 리뷰는 교차로** (서로의 영역을 리뷰해야 발표 때 전 범위 질문에 둘 다 답합니다).

### 시크릿 점검을 금요일로

**증상** — 발표 전날 히스토리에서 .env 발견 — 밤샘 키 교체, 최악엔 저장소 재작성.
**원인** — 점검을 "마지막 정리"로 분류.
**해결** — 오늘(Step 3) 하는 이유가 이것입니다 — 발견이 이르면 대응은 [Day 109](day-109.md)의
절차 30분, 늦으면 발표 리스크. 이후 나흘은 커밋 전 습관(pre-commit 수준의 자기 검사)으로
유지만 하면 됩니다.

## ⑥ 확인 문제

**Q1.** "재현성 25 + CI/CD 30 = 55점이 심사위원의 실행에 걸려 있다"는 사실이 이번 주 작업의
우선순위를 어떻게 정하는지, 갭 감사표의 🔶 두 개(리허설 7분·모델 교체 절차)로 논증하세요.

<details>
<summary>답 보기</summary>

심사위원의 실행은 우리가 통제할 수 없는 환경에서 일어나므로, "우리 환경에서 한 번 성공"은
0점 위험이 있습니다 — 리허설 7분(목표 초과)은 55점 중 25점 구역의 직접 감점 요인이라 최우선
수리 대상입니다 (원인: 첫 빌드 시간 → 개선: 이미지 pull 방식 확인·캐시). 모델 교체 절차(운영
설계 25점 구역)는 "문서 보고 수행 가능"까지 가야 점수가 되므로 문서화+리허설이 한 세트.
반면 선택 기능은 가산 구역 — 필수 구역의 🔶가 남아 있는 한 후순위입니다. 배점표가 곧 일정표
라는 것이 MP 주간의 제1기술입니다.

</details>

**Q2.** "그림은 현실의 사진이어야 한다"는 원칙과, [Day 130](day-130.md)의 "파이프라인 지도에
실측 시간·겪은 실패를 주석으로" 요구의 공통 철학을 한 문장으로 뽑고, 그것이 심사(또는 채용
면접)에서 왜 강한지 설명하세요.

<details>
<summary>답 보기</summary>

공통 철학: **"문서의 모든 주장에는 실행 가능한 증거가 붙어 있어야 한다"** (증거 기반 문서화).
심사·면접에서 강한 이유: 검증 질문("정말요? 해 보세요")에 문서가 즉시 명령으로 응답하므로
신뢰 비용이 0에 수렴하고, 반대로 소망이 섞인 그림은 한 번의 불일치로 문서 전체의 신뢰를
무너뜨립니다. "이상형 아키텍처를 아는 사람"은 많지만 "자기 시스템의 사진과 갭을 정직하게
말하는 사람"은 드물다 — 후자가 운영을 맡길 수 있는 사람의 신호입니다.

</details>

**Q3.** 초급 트랙(Compose+CI)과 상급 트랙(+CD·모델 교체·드리프트)의 선택 기준을 "금요일에
시연 가능한가"로 둔 이유를, 발표 배점과 시연 리스크의 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

발표(10점)는 라이브 시연이고, 시연은 **가장 약한 고리에서 실패**합니다 — 절반만 완성된 CD는
시연 중 최악의 순간(청중 앞 배포 실패, 롤백도 미완이라 복구 불능)을 만들 수 있어, 완성된
초급 트랙보다 총점이 낮아지기 쉽습니다. 완성도 있는 작은 범위 > 불안정한 큰 범위 — 이는 MP1
부터 반복된 원칙이고, 상급 기능은 "완성 + 리허설 2회"를 통과한 것만 시연 목록에 올린다는
규칙으로 리스크를 통제합니다 (미완이면 "다음 단계" 슬라이드로 — 정직한 로드맵도 점수입니다).

</details>
