## ③ 개념 설명

### 배포 방식 ① 로컬 실행 스크립트

```
┌─────────────────────────────────┐
│  PC                             │
│  ┌──────┐   ┌────────┐          │
│  │ 웹캠 │→ │ python │→ 화면    │
│  └──────┘   │ 스크립트│→ 파일   │
│             └────────┘          │
└─────────────────────────────────┘
```

| 항목 | 평가 |
|---|---|
| 구현 난이도 | ★ 가장 쉬움 (1일) |
| 지연 | ★ 최소 (수십 ms) |
| 비용 | 0 |
| 네트워크 | 불필요 |
| **원격 확인** | ✗ 불가 |
| **24시간 운영** | ✗ PC 를 켜 둬야 함 |
| 확장 | ✗ 카메라 1대 |

```
★ 언제 쓰나
  · 개발·디버깅
  · 데모
  · 일회성 분석 (녹화 영상 처리)

★ 우리 프로젝트에는 부적합
  현관 CCTV 를 PC 로 24시간 켜 둘 수 없음
```

### 배포 방식 ② 웹 서버 (Flask)

```
┌──────────┐        ┌──────────────────────┐
│ 브라우저  │  HTTP  │  Flask 서버          │
│ (휴대폰) │←─────→│  ┌────────┐          │
└──────────┘        │  │detector│  모델    │
                    │  └────────┘          │
┌──────────┐        │  ┌────────┐          │
│ 웹캠/파일 │───────→│  │ SQLite │  이력    │
└──────────┘        │  └────────┘          │
                    └──────────────────────┘
```

| 항목 | 평가 |
|---|---|
| 구현 난이도 | 보통 (W32~33, 10일) |
| 지연 | 업로드 + 추론 (1~3초) |
| 비용 | 서버 1대 |
| 네트워크 | ★ 필수 |
| **원격 확인** | ★ 가능 |
| **다중 사용자** | ★ 가능 |
| 확장 | 카메라 여러 대 가능 |

```
★ 언제 쓰나
  · 여러 사람이 결과를 봐야 할 때
  · 이미지 업로드 방식
  · 이력 조회가 필요할 때

★ 우리 프로젝트에서
  · 사용자 인터페이스로 ★ 필수
  · 단, "카메라 → 서버" 부분을 어떻게 할지가 남음
```

### 배포 방식 ③ 엣지 디바이스 단독

```
┌────────────────────────────────────┐
│  라즈베리파이                        │
│  ┌──────┐  ┌────────┐  ┌────────┐ │
│  │카메라│→│detector│→│ SQLite │ │
│  └──────┘  └────────┘  └────────┘ │
│                  ↓                 │
│            텔레그램 알림 ───────────┼──→ 인터넷
└────────────────────────────────────┘
```

| 항목 | 평가 |
|---|---|
| 구현 난이도 | 보통 (W34, 5일) |
| 지연 | ★ 최소 (네트워크 없음) |
| 비용 | 파이 1대 (7~12만원) |
| 네트워크 | ★ **알림만** (평소 불필요) |
| **개인정보** | ★ **영상이 밖으로 안 나감** |
| 성능 제약 | ★ 5.4 FPS |
| 확장 | 카메라마다 파이 1대 |

```
★ 언제 쓰나
  · 네트워크가 불안정한 곳
  · 개인정보 민감 (영상 외부 전송 금지)
  · 지연이 중요
  · 카메라가 1~2대

★ 우리 프로젝트에서
  · ★ 가장 유력한 후보
  · 단, "결과를 어떻게 보나"가 남음
```

### 배포 방식 ④ 엣지 + 서버 하이브리드

```
┌─────────────────┐         ┌──────────────────────┐
│ 라즈베리파이     │         │  서버 (PC)           │
│ ┌──────┐        │  이벤트  │  ┌──────┐            │
│ │카메라│→ 검출 ─┼────────→│  │Flask │← 브라우저  │
│ └──────┘        │  스냅샷  │  └──────┘            │
│  ★ 로컬 추론    │         │  ┌──────┐            │
│  이벤트만 전송   │         │  │SQLite│  이력      │
└─────────────────┘         │  └──────┘            │
                            └──────────────────────┘
```

| 항목 | 평가 |
|---|---|
| 구현 난이도 | ★ 가장 복잡 |
| 지연 | 검출 즉시 + 전송 (0.5~1초) |
| 비용 | 파이 + 서버 |
| 네트워크 | ★ **이벤트 시에만** (대역폭 적음) |
| **개인정보** | ★ 스냅샷만 전송 (선택적) |
| 원격 확인 | ★ 가능 |
| 확장 | ★ 파이 여러 대 → 서버 1대 |

```
★ 언제 쓰나
  · 카메라 여러 대
  · 원격 확인 필요 + 대역폭 절약
  · ★ 우리 프로젝트의 정답에 가까움
```

### 변형 ⑤ — 파이는 촬영만, 서버가 추론

```
┌─────────────┐  영상 스트림  ┌────────────────┐
│ 라즈베리파이 │ ───────────→ │ 서버 (GPU)     │
│  촬영만     │   (계속)     │  ★ 추론 담당   │
└─────────────┘              └────────────────┘
```

| 항목 | 평가 |
|---|---|
| 파이 부하 | ★ 매우 낮음 |
| 서버 성능 | ★ GPU 사용 가능 → 큰 모델 |
| **네트워크** | ★★ **항상 영상 전송** (2~8 Mbps/대) |
| 지연 | 전송 + 추론 (0.3~1초) |
| **개인정보** | ★ **영상이 계속 밖으로** |
| 네트워크 끊김 | ★ **완전 정지** |

```
★ 언제 쓰나
  · 서버에 GPU 가 있고
  · 네트워크가 안정적이고
  · 카메라가 많고
  · 큰 모델이 필요할 때

★ 우리 프로젝트에서는 부적합
  · Day 153 에서 파이 단독으로 5.4 FPS 확보
  · 영상 상시 전송은 개인정보 부담
```

### 지연 예산 (Latency Budget)

```
요구: 3초 이내 알림

  카메라 노출·전송        50 ms
  프레임 획득             20 ms
  ★ 추론                 190 ms
  이벤트 판정 (3프레임)    570 ms
  스냅샷 저장             80 ms
  DB 기록                 15 ms
  ★ 알림 전송 (텔레그램)   300~800 ms
  ────────────────────────────────
  합계                    1,225~1,725 ms   ✓ 여유 1.3~1.8초
```

> **★ 예산 표를 만들면 어디를 줄일지 보입니다.**
> 위 표에서 가장 큰 것은 **이벤트 판정(570ms)** 입니다.
> 3프레임 → 2프레임으로 줄이면 190ms 절약.

### 저장 용량 계산

```
이벤트 스냅샷
  1건 = 1920×1080 JPEG 약 250 KB
  하루 20건 × 250 KB = 5 MB
  7일 = 35 MB          ★ 무시할 수준

이벤트 전후 영상 (5초, 720p)
  1건 = 약 3 MB
  하루 20건 = 60 MB
  7일 = 420 MB         ★ 감당 가능

상시 녹화 (720p, 15 FPS)
  1시간 = 약 900 MB
  하루 = 21.6 GB
  7일 = ★ 151 GB       ✗ microSD 로는 불가
```

**★ 결론: 상시 녹화는 하지 않습니다.**

```
대안
  · 이벤트 전후 5~10초만 저장
  · 순환 버퍼 (최근 30초를 메모리에 유지 → 이벤트 시 저장)
  · 스냅샷만
```

### 시스템 구성도 그리기

**★ 좋은 구성도의 조건**

```
① 컴포넌트마다 ★ 책임이 한 줄로 적혀 있다

③ 프로토콜·형식이 명시되어 있다 (HTTP/JSON, MJPEG…)
④ ★ 경계가 표시되어 있다 (기기 · 네트워크 · 보안)
⑤ 실패 지점이 표시되어 있다
```


```python
])

opts = ["①", "②", "③", "④", "⑤"]
NAMES = {"①": "로컬 스크립트", "②": "웹서버", "③": "엣지 단독",
         "④": "하이브리드", "⑤": "서버 추론"}

for o in opts:
    CRITERIA[f"{o}_점"] = CRITERIA[o] * CRITERIA["가중치"]

print("=" * 108)
print("★ 결정 매트릭스 (1~5점 × 가중치)")
print("=" * 108)
show = ["기준", "가중치"] + opts
print(CRITERIA[show].to_string(index=False))
print("-" * 108)

scores = {o: CRITERIA[f"{o}_점"].sum() for o in opts}
maxscore = CRITERIA["가중치"].sum() * 5

print(f"{'합계':<24}{'':>8}" + "".join(f"{scores[o]:>8}" for o in opts))
print(f"{'백분율':<24}{'':>8}" +
      "".join(f"{scores[o]/maxscore*100:>7.0f}%" for o in opts))
print("-" * 108)

ranked = sorted(scores.items(), key=lambda x: -x[1])
print("\n[순위]")
for i, (o, s) in enumerate(ranked, 1):
    bar = "█" * int(s / maxscore * 50)
    mark = "★" if i == 1 else " "
    print(f"  {mark} {i}. {NAMES[o]:<16}{s:>4}점  {bar} {s/maxscore*100:.0f}%")

print(f"""
★ 1위: {NAMES[ranked[0][0]]}
   2위와 차이 {ranked[0][1] - ranked[1][1]}점

⚠️ 매트릭스는 ★ 참고이지 결정이 아닙니다
   · 가중치를 누가 어떻게 정했는가
   · 점수가 주관적이지 않은가
   → ★ 반드시 근거를 문장으로 설명해야 합니다
""")
```

## ⑤ 자주 하는 실수

### 요구사항을 모호하게 씀

```
"실시간으로 알림"
→ 3초? 1분?
→ ★ 아키텍처 선택이 불가능
```

**대응**: **숫자와 검증 방법**을 함께.

### 아키텍처를 먼저 정하고 요구사항을 맞춤

```
"하이브리드가 멋있으니까 그걸로 하자"
→ 요구사항을 거기 맞춰 씀
→ ★ 불필요한 복잡도
```

**대응**: **요구사항 → 비교 → 선택** 순서.

### 지연 예산을 안 만듦

```
"3초면 되겠지"
→ 실제로 재보니 4.2초
→ ★ 어디를 줄일지 모름
```

### 실패 지점을 설계 안 함

```
"네트워크는 잘 되겠지"
→ 랜선 뽑으면 시스템 정지
→ ★ 발표 당일 사고
```

**대응**: **구성도에 실패 지점과 대응**을 명시.

### 단일 실패점(SPOF)을 만듦

```
⑤ 서버 추론 방식
→ 서버가 죽으면 ★ 감지 자체가 중단
→ CCTV 로서 실격
```

### 개인정보를 나중에 생각함

```
설계 다 끝내고 "영상을 클라우드에 올리면 되겠네"
→ ★ 법적 문제
→ 아키텍처를 다시 그려야 함
```

**대응**: **설계 단계에서 데이터 흐름을 그리고 확인.**

### 저장 용량을 계산 안 함

```
"상시 녹화하자"
→ 하루 21.6 GB
→ ★ microSD 32GB 가 이틀 만에 참
```

### 인터페이스를 안 정하고 개발 시작

```
A: 이벤트에 "timestamp" 필드 만듦
C: "ts" 로 읽음
→ ★ 통합 때 발견 → 양쪽 수정
```

**대응**: **인터페이스 계약서를 먼저.**

### 구성도에 화살표만 그림

```
[파이] → [서버]
→ 무엇이? 얼마나? 어떤 프로토콜로?
```

### 2단계 계획 없이 최대치를 목표로

```
하이브리드를 목표로 하다가 시간 부족
→ ★ 아무것도 완성 안 됨

단계적 계획이면
→ 1단계는 완성 → 발표 가능
```

### ③ 두 방식을 모두 지원하는 설계

**★ 가능합니다. 그리고 좋은 설계입니다.**

**설계**

```python
"""inference_backend.py — 추론 위치를 추상화"""
from abc import ABC, abstractmethod


class InferenceBackend(ABC):
    """추론 백엔드 인터페이스 — 로컬이든 원격이든 같은 계약"""

    @abstractmethod
    def predict(self, frame) -> dict:
        """I-02 형식 응답 반환"""

    @abstractmethod
    def health(self) -> bool:
        """사용 가능한가"""


class LocalBackend(InferenceBackend):
    """★ 파이에서 직접 추론"""

    def __init__(self, profile="pi"):
        from detector import get_detector
        self.det = get_detector(profile=profile)

    def predict(self, frame):
        return self.det.predict(frame)

    def health(self):
        return True


class RemoteBackend(InferenceBackend):
    """★ 서버로 보내서 추론"""

    def __init__(self, url, timeout=2.0, quality=80):
        import requests
        self.url = url.rstrip("/") + "/api/infer"
        self.timeout = timeout
        self.quality = quality
        self.session = requests.Session()

    def predict(self, frame):
        import cv2
        ok, buf = cv2.imencode(".jpg", frame,
                               [cv2.IMWRITE_JPEG_QUALITY, self.quality])
        r = self.session.post(self.url, files={"image": buf.tobytes()},
                              timeout=self.timeout)
        r.raise_for_status()
        return r.json()

    def health(self):
        try:
            return self.session.get(self.url.replace("/infer", "/health"),
                                    timeout=1.0).ok
        except Exception:
            return False


class FallbackBackend(InferenceBackend):
    """★★ 원격을 우선 쓰되, 실패하면 로컬로 — 가장 견고"""

    def __init__(self, remote, local, check_interval=30):
        self.remote, self.local = remote, local
        self.check_interval = check_interval
        self._use_remote = remote.health()
        self._last_check = 0.0
        self.stats = {"remote": 0, "local": 0, "fallback": 0}

    def predict(self, frame):
        import time
        now = time.time()
        # 주기적으로 원격 복구 확인
        if not self._use_remote and now - self._last_check > self.check_interval:
            self._last_check = now
            self._use_remote = self.remote.health()

        if self._use_remote:
            try:
                res = self.remote.predict(frame)
                res["backend"] = "remote"
                self.stats["remote"] += 1
                return res
            except Exception:
                self._use_remote = False        # ★ 즉시 로컬로 전환
                self._last_check = now
                self.stats["fallback"] += 1

        res = self.local.predict(frame)
        res["backend"] = "local"
        self.stats["local"] += 1
        return res

    def health(self):
        return True                              # ★ 항상 동작
```

**설정**

```yaml
# configs/deployment.yaml
inference:
  mode: fallback          # local | remote | ★ fallback

  local:
    profile: pi

  remote:
    url: http://192.168.0.20:5000
    timeout: 2.0
    quality: 80

  fallback:
    check_interval: 30
```

```python
def build_backend(cfg):
    mode = cfg["inference"]["mode"]
    if mode == "local":
        return LocalBackend(**cfg["inference"]["local"])
    if mode == "remote":
        return RemoteBackend(**cfg["inference"]["remote"])
    if mode == "fallback":
        return FallbackBackend(
            RemoteBackend(**cfg["inference"]["remote"]),
            LocalBackend(**cfg["inference"]["local"]),
            **cfg["inference"].get("fallback", {}))
    raise ValueError(mode)
```

**★ 이 설계의 이점**

```
① 호출하는 코드는 ★ 전혀 바뀌지 않습니다
     backend = build_backend(cfg)
     res = backend.predict(frame)

② 실험이 쉽습니다
     mode 만 바꿔서 A/B 비교
     → "서버 추론이 정말 나은가"를 ★ 측정으로 답할 수 있음

③ ★ fallback 이 최고의 견고성

     · 네트워크 끊김: 자동으로 파이 로컬 추론
     · 복구: 자동으로 서버로 복귀
     → ★ 두 방식의 장점만

④ 발표에서 강력합니다
```
