## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 서비스를 **컴포넌트 그림 한 장**(구성 요소 · 데이터 흐름 · 포트)으로 그릴 수 있다.
- 기술 선택마다 **선택지·기준·탈락 이유**가 있는 근거표를 만들 수 있다.
- raw/mart를 분리한 **ERD**와, 팀 병렬 작업의 접점이 되는 **API 명세**를 확정할 수 있다.
- 저장소 구조와 브랜치 규칙을 세팅해 내일부터 4명이 동시에 작업할 수 있는 상태를 만든다.

---

## ② 왜 필요한가

내일부터 4명이 **동시에** 코드를 씁니다. 설계 없이 병렬 작업을 시작하면 각자의 머릿속
설계가 4개 생기고, 그 차이는 인터페이스에서 폭발합니다 — 데이터 담당이 만든 컬럼명과
모델 담당이 기대한 컬럼명이 다르고, 모델이 뱉는 출력과 API가 기대한 입력이 다르고,
그 발견은 각자의 부품이 "완성"된 뒤에야 옵니다. 통합이 늦게 실패할수록 수리는 비쌉니다.

아키텍처 문서는 그래서 그림 감상용이 아니라 **팀의 계약서**입니다. 그림은 "누가 어느
상자를 맡는가"를, ERD와 API 명세는 "상자 사이에 무엇이 오가는가"를 고정합니다. 계약이
고정되면 각자는 상자 안에서 자유롭습니다 — 이것이 4명이 서로를 기다리지 않고 일하는
유일한 방법입니다.

한 가지 주의: [Day 136](../05-infra-mlops/day-136.md)의 "그림은 현실의 사진" 원칙과
오늘의 그림은 시제가 다릅니다. 오늘 그리는 것은 **설계도(할 것)**가 맞습니다 — 대신
4주 뒤 최종 문서에서 이 그림은 사진(있는 것)으로 검증받게 되므로, 지을 수 있는 것만
그려야 합니다. 부품 전부를 이미 만들어 본 것으로만 조립하는 이유입니다.

## ③ 개념 설명

### 컴포넌트 그림 — 배운 부품의 조립도

그림의 상자는 전부 지난 140일에 등장한 부품이어야 합니다. 상자마다 "원형이 된 Day"를
주석으로 달아 보세요 — 주석이 안 달리는 상자가 있다면 그것이 위험 요소입니다 (새로
배워야 하는 것 = 일정의 지뢰).

### 기술 선택 근거표 — "왜"가 점수다

최종 심사와 채용 면접의 공통 질문은 "왜 이걸 썼나요?"입니다. 근거표의 형식:

| 결정 | 선택 | 탈락 후보와 이유 | 다시 고려할 조건 |
|---|---|---|---|

마지막 열이 핵심입니다 — "다시 고려할 조건"이 있어야 선택이 교리가 아니라 판단이 됩니다
([Day 135](../05-infra-mlops/day-135.md)의 K8s 판단 기준표와 같은 구조).

### ERD — raw와 mart의 분리

[Day 043](../02-sql-pipeline/day-043.md)의 원칙 그대로: **원본은 원본대로(raw), 가공은
가공대로(mart).** 수집이 적재하는 테이블과 모델이 읽는 테이블을 분리해야 ① 재처리가
가능하고(raw는 불변) ② 피처 로직 변경이 수집을 건드리지 않습니다.

### API 명세 — 병렬 작업의 접점

API 명세가 확정되는 순간 서빙 담당은 **가짜 응답으로 먼저 개발**할 수 있고(모델이 없어도),
모델 담당은 명세가 요구하는 출력 형식으로 산출물을 맞춥니다. 명세 없이는 순차 작업,
명세가 있으면 병렬 작업 — 하루짜리 문서가 일주일을 법니다.

## ④ 단계별 실습

### Step 1. 컴포넌트 그림 (1~2교시)

한산 팀의 구성도 — 상자마다 원형 Day가 달려 있음에 주목:

```
                         ┌── 클라우드 인스턴스 1대 (Ubuntu 22.04) ───────────────────┐
  사용자 ──:8080──▶ nginx ──▶ api (FastAPI :8000, 내부)  ──▶ db (PostgreSQL :5432)   │
                   │ [D124]    │ [D096·151에 구현]           │ [D031] raw+mart+로그   │
                   │ static/   │ 기동 시 모델 로드            │ volume: pgdata        │
                   │ 데모page  ▼                             ▲                       │
                   │        MLflow (:5000, 내부) ◀─ 재학습 ──┴─ 수집 ── airflow      │
                   │          [D067·132] Registry             [D133] 06:10 수집 DAG  │
                   └──────────────────────────────────────────── 일요일 재학습 DAG ──┘
  GitHub ── PR 게이트(CI) ── main 병합 ── 이미지 빌드(GHCR) ── self-hosted runner 배포
    [D127]              [D128]                       [D129]  ── 스모크 → 실패 시 롤백
```

외부 노출은 nginx :8080 하나 — [Day 124](../05-infra-mlops/day-124.md)에서 세운 원칙
그대로입니다. 여러분 팀의 그림에서 "원형 Day"가 빈 상자가 나오면 오늘 중 대응을 정하세요
(범위 제외가 1순위 대응입니다).

### Step 2. 기술 선택 근거표 (3~4교시)

한산 팀의 주요 결정 4건:

| 결정 | 선택 | 탈락 후보와 이유 | 다시 고려할 조건 |
|---|---|---|---|
| 모델 | LightGBM 회귀 | LSTM — 데이터가 일 단위 5만 행 규모로 소형, CPU 운영 전제, 해석 용이성 | 시간 해상도 데이터 확보 + 성능 정체 시 |
| 스케줄러 | Airflow | cron — 재시도·백필·의존 관리가 내장, W27 경험 자산 | 서비스 축소로 DAG 1개만 남으면 cron 회귀 |
| 모델 배포 | MLflow Registry 로드 (B방식) | 이미지에 굽기(A방식) — 주 1회 갱신이라 재빌드 없는 교체가 유리, 모델 ~2MB | 갱신이 분기 1회로 줄고 이미지 족보 단일화가 더 중요해지면 A |
| 서빙 | FastAPI 단일 API + 정적 데모 | 프론트 프레임워크 — 데모 페이지는 정적 HTML로 충분 (MP3 방식) | 사용자 인터랙션이 늘면 |

A/B 방식 논쟁은 [Day 118](../05-infra-mlops/day-118.md) Q3와 [Day 132](../05-infra-mlops/day-132.md)
에서 다뤘던 그 논쟁입니다 — mlops-mp3는 A(45MB를 굽기), pm25는 B(레지스트리)였고, 한산은
갱신 주기(주 1회)가 결정 변수가 되어 B를 택했습니다. 같은 질문, 다른 답, 각자의 근거 —
이것이 근거표의 존재 이유입니다.

### Step 3. ERD (5~6교시)

```
station (역 마스터, 51행)          subway_daily (raw — 수집이 쓰는 곳)
  station_id  PK                     use_ymd     date
  name        text                   station_id  FK ┐ PK(use_ymd, station_id)
  line        text = '2호선'          boardings   int│  ON CONFLICT DO UPDATE
                                     alightings  int┘  reg_ymd (게시일 추적)
hourly_share (월별 시간대 분포)
  month, station_id, hour PK        mart_daily_features (모델이 읽는 곳 — 뷰)
  share numeric                       lag_1 · lag_7 · lag_14 · dow · is_holiday …
prediction_log (서빙 기록)            = raw에서 SQL로 생성 (152 재현성의 근거)
  ts · station_id · target_date · hour · expected · level · model_version · latency_ms
```

멱등 키 `(use_ymd, station_id)`와 upsert는 [Day 043](../02-sql-pipeline/day-043.md)의
그 패턴입니다. `reg_ymd`를 함께 저장하는 것은 141에서 발견한 D-4 지연의 흔적 관리 —
"이 행이 언제 게시된 데이터인가"를 남겨야 재게시(수정)를 추적할 수 있습니다.

### Step 4. API 명세 · 저장소 구조 · 브랜치 규칙 (7~8교시)

```
POST /predict   {station, date, hour}  → 200 {level, congestion, expected_boardings,
                                              baseline_p90, model_version}
                                       → 422 (검증 실패: 없는 역, 과거 날짜, hour 범위)
GET  /stations  → 51개 역 목록 (데모 페이지의 선택지)
GET  /health    → {status, model_version, model_loaded_at}
```

저장소 구조는 [커리큘럼의 공통 구조](../../curriculum/06-final-project.md)를 그대로 —
`src/pipeline·train·api` + `tests` + `configs` + `docs`. 브랜치 규칙은 어제 건 보호
규칙에 더해: 브랜치명 `feat/이슈번호-설명`, PR 템플릿(변경·확인 방법·스크린샷), 이슈와
PR 연결(`Closes #N`).

산출물 `docs/ARCHITECTURE.md`(그림+근거표) · `docs/ERD.md` · `docs/API.md` 커밋 —
**전원 승인 리뷰**로 병합합니다 (계약서 서명입니다).

**오늘 퇴근 체크** — □ 구성도(전 상자에 원형 Day) □ 근거표(다시 고려할 조건 포함)

## ⑤ 자주 하는 실수

### 소망을 그림 — 이력서 주도 설계

**증상** — 그림에 Kafka·K8s·Redis가 등장 — 전부 이번 과정에서 안 배운 것, 근거는 "채용
공고에 있어서".
**원인** — 아키텍처를 서비스의 필요가 아니라 이력서의 필요로 설계.
**해결** — "원형 Day 주석" 규율이 방어선입니다. 새 기술 1개가 정 필요하면 **위험 요소로
등록**하고 대체 경로(없이도 관통하는 길)를 함께 설계하세요. 참고로 심사가 평가하는 것은
스택의 개수가 아니라 선택의 근거입니다 — "안 쓴 이유"가 "쓴 이유"만큼 점수가 됩니다.

### 인터페이스 미정의로 병렬 시작

**증상** — W30 수요일, 모델 산출물(컬럼 18개 DataFrame)과 API 기대 입력(JSON 5필드)이
안 맞음을 통합 시점에 발견.
**원인** — "각자 알아서 하고 나중에 붙이자" — 계약 없는 병렬은 병렬이 아니라 분열입니다.
**해결** — 오늘 ERD·API 명세를 전원 승인으로 확정하고, **명세 변경은 PR로만**(코드처럼
리뷰) 하세요. [Day 100](../04-deep-learning-serving/day-100.md)의 학습-서빙 불일치가
팀 규모에서는 사람-사람 불일치로 재현되는 것입니다.

### 근거 없는 기술 선택

**증상** — 심사 질의 "왜 Airflow인가요? cron이면 안 되나요?"에 "……배워서요".
**원인** — 선택은 했지만 비교를 안 함.
**해결** — 근거표의 "탈락 후보와 이유" 열이 그 답의 재고입니다. 실제로 한산 팀의 답은
"DAG 2개·재시도·백필이 필요해 Airflow가 이득이지만, DAG가 1개로 줄면 cron으로 회귀가
합리적"— 조건부의 답이 외운 답보다 강합니다.

### raw와 mart를 한 테이블에

**증상** — 피처 로직을 바꿨더니 원본까지 재수집해야 함 / 수집 버그 수리 후 과거 피처
재계산 불가.
**원인** — 수집의 산출물과 학습의 입력을 같은 테이블에 겹쳐 씀.
**해결** — raw는 불변(수집만 씀), mart는 파생(언제든 raw에서 재생성 가능) — 분리 자체가
재현성 점수의 근거가 됩니다 ("피처는 이 SQL 한 장으로 재생됩니다").

## ⑥ 확인 문제

**Q1.** "계약(ERD·API 명세)이 고정되면 각자는 상자 안에서 자유롭다"는 문장을, 통합 실패
비용의 관점에서 설명하세요. 계약이 없을 때 통합 실패가 늦게·비싸게 발견되는 이유는?

<details>
<summary>답 보기</summary>

계약이 없으면 각자의 가정이 코드에 암묵적으로 박히고, 가정의 충돌은 각 부품이 완성되어
붙는 순간(통합)에야 드러납니다. 이 시점에는 양쪽 모두 자기 가정 위에 코드를 쌓아 올린
뒤라 수리 = 한쪽의 재작업이 됩니다. 계약이 먼저 고정되면 가정이 명시적 문서가 되어 충돌이
설계 단계(문서 리뷰)에서 값싸게 발견되고, 이후 각자의 내부 구현은 계약만 지키면 서로에게
영향이 없으므로 자유롭습니다. 요약: 계약은 실패를 없애는 게 아니라 **실패의 발견 시점을
가장 싼 곳으로 옮기는** 장치입니다.

</details>

**Q2.** 한산 팀은 모델 배포를 B방식(레지스트리 로드)으로, mlops-mp3(W24~28)는 A방식
(이미지에 굽기)으로 정했습니다. 두 결정이 모두 옳을 수 있는 이유를 결정 변수로 설명하세요.

<details>
<summary>답 보기</summary>

결정 변수가 다릅니다. mlops-mp3의 antbee 모델은 45MB·갱신 드묾 — 이미지 태그 하나로
코드+모델의 족보가 완결되는 가치(추적 단순성)가 재빌드 비용(드묾)을 이깁니다. 한산은
주 1회 자동 재학습 — 갱신마다 이미지 재빌드·재배포(수 분)를 치르는 A보다, 레지스트리
별칭 교체로 재빌드 없이 갈아끼우는 B가 운영 비용에서 유리하고 모델도 ~2MB로 가볍습니다.
즉 "모델 크기 × 갱신 빈도 × 족보 단일화의 가치"라는 변수에 다른 값이 들어가 다른 답이
나온 것 — 아키텍처 결정의 정답은 보편이 아니라 조건부이며, 그래서 근거표에 "다시 고려할
조건" 열이 필요합니다.

</details>

**Q3.** 오늘의 설계도(할 것)와 Day 136의 사진(있는 것) — 같은 아키텍처 그림이 시제에
따라 다른 규율을 요구합니다. 각 시제에서 그림이 거짓이 되는 방식과 방지 장치를 짝지으세요.

<details>
<summary>답 보기</summary>

설계도의 거짓 = **지을 수 없는 것을 그리는 것**(배운 적 없는 부품, 확보 안 된 데이터) —
방지 장치는 원형 Day 주석(모든 상자에 출처)과 데이터 실재 확인(141)입니다. 사진의 거짓 =
**있지 않은 것을 있다고 그리는 것**(계획했지만 미구현인 상자를 실선으로) — 방지 장치는
증거 명령(그림의 실선마다 확인 명령이 통과)입니다. 최종 제출 시 오늘의 설계도는 사진으로
갱신되어야 하며, 설계도와 사진의 차이(잘린 것·바뀐 것)를 기록한 것이 곧 결과 보고서의
"계획 대비 변경" 절이 됩니다 — 차이의 존재가 아니라 차이의 은폐가 감점입니다.
