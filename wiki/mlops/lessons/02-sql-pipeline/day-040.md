## ③ 개념 설명

### 스키마 리뷰 6개 기준 ★

| # | 기준 | 확인 질문 |
|---|---|---|
| **1. 키** | 각 테이블에 PK가 있는가? **멱등 키가 `UNIQUE` 로 걸려 있는가?** | "같은 데이터를 두 번 넣으면 어떻게 되나?" |
| **2. 타입** | 금액은 `numeric`/`integer`, 시각은 `timestamptz` 인가? | "이 열에 들어올 수 있는 최댓값은?" |
| **3. 제약** | `NOT NULL` · `CHECK` · FK가 의도대로 붙어 있는가? | "NULL이 허용된 열은 **왜** 허용인가?" |
| **4. 인덱스** | FK 열에 인덱스가 있는가? 자주 쓰는 조회 조건은? | "가장 자주 실행될 쿼리 3개는?" |
| **5. 이름** | 규칙이 일관되는가? | "다른 테이블도 같은 규칙인가?" |
| **6. 운영** | 언제 누가 넣었는지 알 수 있는가? 삭제 정책은? | "이 행이 잘못됐을 때 어디서 왔는지 추적 가능한가?" |

**1번이 제일 중요합니다.** [Day 039](day-039.md)에서 봤듯이 멱등 키가 없으면
파이프라인 재실행 한 번에 데이터가 두 배가 되고, **아무도 모른 채 몇 주가 지납니다.**

### 명명 규칙

정답은 없지만 **일관성**은 필수입니다. 이 과정에서 쓸 규칙입니다.

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | **단수** · snake_case | `measurement` (not `Measurements`) |
| 열 | snake_case | `measured_at`, `station_id` |
| 기본키 | `<테이블>_id` | `station_id` |
| 외래키 | 참조하는 PK와 **같은 이름** | `measurement.station_id` |
| 시각 열 | `_at` 접미사 | `created_at`, `ingested_at` |
| 불리언 | `is_` / `has_` 접두사 | `is_valid` |
| 인덱스 | `idx_<테이블>_<열들>` | `idx_measurement_station_time` |
| 뷰 | `v_` 접두사 | `v_order_summary` |

> **대문자·한글 열 이름을 쓰지 마세요.** PostgreSQL은 따옴표 없는 식별자를 소문자로 바꿉니다.
> `"createdAt"` 처럼 큰따옴표로 만들면 **이후 모든 쿼리에서 큰따옴표를 써야** 합니다.

### 운영 열 3종

실무 테이블에는 데이터 자체와 무관한 열이 붙습니다.

| 열 | 용도 |
|---|---|
| `created_at timestamptz NOT NULL DEFAULT now()` | 언제 들어왔나 |
| `updated_at timestamptz` | 언제 바뀌었나 |
| `source` 또는 `run_id` | **어디서 왔나** (계보 · lineage) |

**`source` 가 MLOps에서 특히 중요합니다.**
"이 이상한 값이 어느 배치에서 들어왔나"를 못 찾으면 원인을 고칠 수 없습니다.
[Day 044](day-044.md)의 품질 검증과 [Day 045](day-045.md)의 운영에서 이 열들을 씁니다.

### 마이그레이션 — 스키마도 버전 관리한다

```
sql/migrations/
├── 001_create_station.sql
├── 002_create_measurement.sql
├── 003_add_index_measured_at.sql
└── 004_add_ingest_run.sql
```

| 규칙 | 이유 |
|---|---|
| **번호 순으로 실행하면 현재 상태가 재현된다** | 새 팀원·CI·운영 서버가 같은 스키마를 갖게 됨 |
| **이미 적용한 파일은 절대 수정하지 않는다** | 남의 DB엔 이미 적용됐으므로. 고치려면 **새 파일 추가** |
| 각 파일은 **한 가지 변경만** | 문제 생겼을 때 되돌리기 쉬움 |

`schema.sql` 한 장을 계속 고치는 방식은 "지금 운영 DB가 몇 번째 버전인지" 알 수 없습니다.
[Day 001](../01-python-data/day-001.md)에서 배운 `requirements.txt` 의 스키마 버전입니다. **재현 가능성**이 같은 이유입니다.

> 실무에서는 Alembic(Python) · Flyway 같은 도구가 이걸 자동화합니다.
> 지금은 **번호 붙인 SQL 파일**만으로 충분합니다. 원리를 알면 도구는 금방 익힙니다.

### 분석 쿼리 세트를 갖춘다는 것

MP1 보고서는 "쿼리 10개"가 아니라 **"질문 10개와 그 답"** 입니다.

```
sql/analysis/
├── 01_overview.sql         전체 요약 (규모 · 기간 · 결측)
├── 02_trend.sql            시계열 추이 · 전기 대비
├── 03_composition.sql      구성비 (카테고리 · 세그먼트)
├── 04_ranking.sql          순위 · 상위 N
├── 05_segment.sql          대상별 비교 (등급 · 지역)
├── 06_anomaly.sql          이상치 · 결측 · 특이 구간
└── README.md               질문 목록과 결론
```

**이 6가지 축이 거의 모든 데이터 분석 리포트의 뼈대**입니다.
데이터가 대기질이든 매출이든 모델 성능이든 같습니다.

| 축 | 질문 형태 | 주 문법 |
|---|---|---|
| 개요 | "얼마나 있나? 언제부터 언제까지?" | `COUNT` · `MIN/MAX` · 결측률 |
| 추이 | "늘고 있나 줄고 있나?" | `DATE_TRUNC` · `LAG` · 누적 |
| 구성 | "무엇이 얼마를 차지하나?" | `GROUP BY` · `SUM(...) OVER ()` |
| 순위 | "1등은 누구/무엇인가?" | `RANK` · `PARTITION BY` |
| 세그먼트 | "누가 다른가?" | `CASE` · `NTILE` · 조인 |
| 이상 | "이상한 곳은 어디인가?" | `HAVING` · 표준편차 · 결측 |

### Step 1. 스키마 리뷰 연습 — 나쁜 설계 고치기

아래는 실제로 흔히 보는 형태입니다. **6개 기준으로 지적할 점을 5개 이상** 찾아 보세요.

```sql
CREATE TABLE Sales (
    id          serial,
    Date        varchar(20),
    productName varchar(50),
    price       float,
    qty         varchar(10),
    customer    varchar(50),
    customerTel varchar(20),
    memo        text
);
```

<details>
<summary>리뷰 결과 보기</summary>

| # | 기준 | 지적 | 고침 |
|---|---|---|---|
| 1 | 키 | **PK 선언이 없다** (`serial` 은 자동 증가일 뿐) | `PRIMARY KEY` 명시 |
| 1 | 키 | **멱등 키가 없다** — 같은 판매를 두 번 넣어도 안 막힘 | `UNIQUE (order_no)` 같은 자연키 필요 |
| 2 | 타입 | `Date varchar(20)` — 날짜가 문자열 | `timestamptz` (`'2025/1/5'` 와 `'2025-01-05'` 가 섞임) |
| 2 | 타입 | **`price float`** — 금액에 부동소수 | `numeric(12,2)` 또는 `integer` |
| 2 | 타입 | `qty varchar(10)` — 수량이 문자열 | `integer` (`SUM` 도 정렬도 안 됨) |
| 3 | 제약 | `NOT NULL` 이 하나도 없다 | 필수 열에 추가 |
| 3 | 제약 | `CHECK` 없음 — 음수 수량·가격 가능 | `CHECK (qty > 0)`, `CHECK (price >= 0)` |
| 3 | 정규화 | `customer` · `customerTel` 이 반복 저장 (3NF 위반) | `customer` 테이블 분리 + FK |
| 3 | 정규화 | `productName` 반복 | `product` 테이블 분리 + FK |
| 4 | 인덱스 | 조회 조건(`Date`, `customer`)에 인덱스 없음 | 추가 |
| 5 | 이름 | `Sales`(대문자·복수) · `productName`(camelCase) 혼용 | `sale` · `product_name` 로 통일 |
| 5 | 이름 | `Date` 는 **예약어에 가까움** | `sold_at` |
| 6 | 운영 | 언제 들어왔는지 알 수 없음 | `created_at`, `source` 추가 |
| 6 | 개인정보 | **전화번호를 평문 저장** | 꼭 필요한지 재검토 → 필요하면 마스킹/암호화 ([Day 044](day-044.md)) |

**고친 결과**

```sql
CREATE TABLE customer (
    customer_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        text NOT NULL,
    phone       text,                       -- NULL 허용: 수집 안 할 수도 있음
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE product (
    product_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text NOT NULL UNIQUE,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sale (
    sale_id     bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_no    text    NOT NULL,
    customer_id integer NOT NULL REFERENCES customer(customer_id),
    product_id  integer NOT NULL REFERENCES product(product_id),
    sold_at     timestamptz NOT NULL,
    unit_price  numeric(12,2) NOT NULL CHECK (unit_price >= 0),
    quantity    integer NOT NULL CHECK (quantity > 0),
    memo        text,
    source      text    NOT NULL DEFAULT 'manual',
    created_at  timestamptz NOT NULL DEFAULT now(),

    UNIQUE (order_no, product_id)            -- ★ 멱등 키
);

CREATE INDEX idx_sale_sold_at  ON sale (sold_at);
CREATE INDEX idx_sale_customer ON sale (customer_id);
CREATE INDEX idx_sale_product  ON sale (product_id);
```

`unit_price` 를 `sale` 에 둔 것은 **의도된 비정규화**입니다 ([Day 039](day-039.md)) — 주문 시점 가격을 박제하기 위해서입니다.
**설계 문서에 이 문장을 적어 두세요.** 안 적으면 다음 사람이 "중복이네" 하고 지웁니다.

```sql
-- MP1 스키마 검증 — 제약이 실제로 막는지 확인
-- 실행: psql -U postgres -d mp1 -f mp1_schema_test.sql
-- 모든 블록이 ERROR 를 내야 정상입니다. 통과하면 제약이 빠진 것입니다.

BEGIN;

-- ① 정상 데이터는 들어가야 한다
INSERT INTO station (name, sido, latitude, longitude)
VALUES ('종로구', '서울', 37.572025, 126.979210);

INSERT INTO measurement (station_id, measured_at, pm10, pm25)
VALUES (1, '2025-06-01 14:00+09', 45, 22);
-- 기대: 성공

-- ② 멱등 키 — 같은 측정소·같은 시각은 두 번 못 들어감
INSERT INTO measurement (station_id, measured_at, pm10, pm25)
VALUES (1, '2025-06-01 14:00+09', 50, 25);
-- 기대: ERROR  duplicate key value violates unique constraint

ROLLBACK;
```

실행 결과입니다.

```
psql:/tmp/mp1_schema_test.sql:8: INSERT 0 1
psql:/tmp/mp1_schema_test.sql:12: INSERT 0 1
psql:/tmp/mp1_schema_test.sql:18: ERROR:  duplicate key value violates unique constraint "measurement_station_id_measured_at_key"
DETAIL:  Key (station_id, measured_at)=(1, 2025-06-01 14:00:00+09) already exists.
ROLLBACK
```

**`ERROR` 가 난 것이 성공입니다.** 나머지 제약도 같은 방식으로 하나씩 확인하세요.

| 검증 항목 | 기대 |
|---|---|
| 멱등 키 중복 | `duplicate key value violates unique constraint` |
| 없는 측정소 참조 | `violates foreign key constraint` |
| 필수 열 NULL | `violates not-null constraint` |
| 범위 밖 값 (`pm10 = -5`) | `violates check constraint` |
| 자식이 있는 부모 삭제 | `is still referenced from table` |

> **`BEGIN` ~ `ROLLBACK` 으로 감싼 이유** — 검증이 끝나면 데이터가 남지 않습니다.
> **몇 번을 돌려도 같은 결과**가 나옵니다. [Day 014](../01-python-data/day-014.md)의 테스트와 같은 원칙입니다.

### Step 5. 분석 쿼리 세트 — W08 종합 연습

`shop` 으로 돌아가 **6가지 축**에 맞춰 쿼리를 만듭니다.
이 형태 그대로 MP1 데이터에 적용하게 됩니다.

```powershell
$ docker exec -it mlops-pg psql -U postgres -d shop
```

**① 개요**

```sql

WITH 월별 AS (

           SUM(oi.quantity * oi.unit_price) AS 매출
    FROM orders o JOIN order_items oi ON o.order_id = oi.order_id

    GROUP BY 1
)

       SUM(매출) OVER (ORDER BY 월 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS 누적,
```

**④ 순위 — 카테고리별 상위 2개** ([Day 037](day-037.md))

```sql
WITH 상품매출 AS (
    SELECT p.category, p.name, SUM(oi.quantity * oi.unit_price) AS 매출
    FROM order_items oi
    JOIN orders   o ON oi.order_id   = o.order_id
    JOIN products p ON oi.product_id = p.product_id
    WHERE o.status <> 'cancelled'
    GROUP BY p.category, p.name
)

       RANK() OVER (PARTITION BY category ORDER BY 매출 DESC) AS 순위

```

**`QUALIFY` 는 PostgreSQL에 없습니다.** 반드시 CTE로 한 겹 더 감싸세요.

```sql
WITH 상품매출 AS (...),
     순위 AS (
    SELECT category, name, 매출,
           RANK() OVER (PARTITION BY category ORDER BY 매출 DESC) AS 순위
    FROM 상품매출
)
SELECT * FROM 순위 WHERE 순위 <= 2 ORDER BY category, 순위;
```

**⑤ 세그먼트 — 간이 RFM**

고객을 **최근성(R) · 빈도(F) · 금액(M)** 으로 나눕니다. 마케팅에서 가장 널리 쓰는 분류입니다.

```sql
WITH 고객지표 AS (
    SELECT c.customer_id, c.name,
           DATE '2025-06-30' - MAX(o.ordered_at)   AS 최근성일,
           COUNT(DISTINCT o.order_id)              AS 빈도,
           SUM(oi.quantity * oi.unit_price)        AS 금액
    FROM customers c
    JOIN orders      o  ON c.customer_id = o.customer_id
    JOIN order_items oi ON o.order_id    = oi.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY c.customer_id, c.name
)
SELECT name AS 고객, 최근성일, 빈도, 금액,
       NTILE(3) OVER (ORDER BY 최근성일)      AS R등급,   -- 1=최근
       NTILE(3) OVER (ORDER BY 빈도 DESC)     AS F등급,   -- 1=자주
       NTILE(3) OVER (ORDER BY 금액 DESC)     AS M등급    -- 1=많이
FROM 고객지표
ORDER BY 금액 DESC;
```

```
  고객  | 최근성일 | 빈도 | 금액   | R등급 | F등급 | M등급
--------+----------+------+--------+-------+-------+-------
 윤도현 |       27 |    3 | 682000 |     2 |     1 |     1
 최수아 |       10 |    3 | 621000 |     1 |     1 |     1
 이서연 |        5 |    5 | 464900 |     1 |     1 |     1
 김민수 |       32 |    5 | 299200 |     2 |     1 |     2
 정우진 |       15 |    3 | 237000 |     1 |     2 |     2
 조은비 |       48 |    2 | 170000 |     3 |     2 |     2
 강하은 |       63 |    2 | 126000 |     3 |     2 |     3
 한지민 |       37 |    2 | 112000 |     2 |     3 |     3
 임채원 |       21 |    2 |  56600 |     1 |     3 |     3
 박지훈 |       69 |    1 |  27800 |     3 |     3 |     3
(10 rows)
```

> **`NTILE(3)` 은 값이 아니라 "순서상 몇 번째 3분의 1인가"** 를 매깁니다.
> 동점이 많으면 같은 값이 다른 등급에 배정될 수 있습니다(빈도 3인 세 명이 F=1, 2로 갈림).
> 정확한 기준이 필요하면 `CASE WHEN 빈도 >= 3 THEN 1 ...` 로 **직접 경계를 정하세요.**
> 위 결과에서도 빈도 3인 정우진 님이 F등급 2를 받았습니다. **자동 분위수의 한계**입니다.

**⑥ 이상 — 첫 구매 vs 재구매**

```sql
WITH 주문금액 AS (
    SELECT o.order_id, o.customer_id, o.ordered_at,
           SUM(oi.quantity * oi.unit_price) AS 금액
    FROM orders o JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY o.order_id, o.customer_id, o.ordered_at
),
순번 AS (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id
                                 ORDER BY ordered_at, order_id) AS 주문순번
    FROM 주문금액
)
SELECT CASE WHEN 주문순번 = 1 THEN '첫 구매' ELSE '재구매' END AS 구분,
       COUNT(*)         AS 건수,
       SUM(금액)        AS 매출,
       ROUND(AVG(금액)) AS 평균금액
FROM 순번
GROUP BY 1 ORDER BY 1;
```

```
  구분   | 건수 |  매출   | 평균금액
---------+------+---------+----------
 재구매  |   18 | 1591300 |    88406
 첫 구매 |   10 | 1205200 |   120520
(2 rows)
```

**첫 구매 평균이 재구매보다 32,000원 높습니다.**
"처음에 크게 지르고, 이후엔 소모품을 산다"는 패턴입니다. **검산** — 10+18 = 28건 ✅ · 매출 합 2,796,500 ✅

**보너스 — 함께 팔리는 상품 (장바구니 분석)**

```sql
SELECT p1.name AS 상품A, p2.name AS 상품B, COUNT(*) AS 동시구매횟수
FROM order_items a
JOIN order_items b ON a.order_id = b.order_id AND a.product_id < b.product_id
JOIN products p1 ON a.product_id = p1.product_id
JOIN products p2 ON b.product_id = p2.product_id
GROUP BY p1.name, p2.name
HAVING COUNT(*) >= 2
ORDER BY 동시구매횟수 DESC, 상품A;
```

```
    상품A     |    상품B     | 동시구매횟수
-------------+--------------+--------------
 A4용지500매 | 형광펜세트   |            4
 무선마우스  | USB허브      |            2
 텀블러      | 캔들세트     |            2
(3 rows)
```

> **`a.product_id < b.product_id`** 가 핵심입니다. 이게 없으면 (A,B)와 (B,A)가 둘 다 나오고,
> 자기 자신과의 조합(A,A)까지 생깁니다. **자기 조인에서 쌍을 만들 때의 표준 요령**입니다.
>
> **해석** — [Day 035](day-035.md) 문제 10의 "저가 상품은 묶어 산다"가 데이터로 확인됐습니다.
> A4용지와 형광펜은 4번이나 함께 팔렸습니다. **사무용품 카테고리를 접으면 이 묶음 구매가 통째로 사라집니다.**

## ⑥ 확인 문제

**1.** 아래 스키마에서 **멱등 키**를 무엇으로 정해야 하나요? 정하지 않으면 어떤 문제가 생기는지 구체적으로 쓰세요.

```sql
CREATE TABLE stock_price (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ticker text NOT NULL,
    traded_on date NOT NULL,
    open_price  numeric(12,2),
    close_price numeric(12,2),
    volume  bigint
);
```

<details>
<summary>답 보기</summary>

**멱등 키는 `(ticker, traded_on)` 입니다.**

```sql
ALTER TABLE stock_price ADD CONSTRAINT stock_price_ticker_date_key
    UNIQUE (ticker, traded_on);
```

**"005930의 2025-06-01 종가"는 세상에 하나뿐**이기 때문입니다.
`id` 는 PK지만 **자동 증가값이라 멱등 키가 될 수 없습니다.** 같은 데이터를 두 번 넣으면 id만 다른 두 행이 생깁니다.

**정하지 않으면**

```
1차 수집  →  005930 / 2025-06-01 / 종가 74,300 / 거래량 12,000,000
API 지연으로 재시도  →  같은 행이 한 번 더
        ↓
SELECT AVG(close_price) ... WHERE ticker='005930'   →  평균은 우연히 같음
SELECT SUM(volume) ...                              →  거래량 2배 ★
SELECT COUNT(*) ...                                 →  거래일 수 2배 ★
시계열 차트                                          →  같은 날 점이 두 개
이 데이터로 학습한 모델                              →  중복 샘플로 가중치가 왜곡됨 ★★
```

**MLOps 관점에서 마지막이 가장 위험합니다.**
중복 행은 학습 데이터에서 **그 샘플의 가중치를 2배로** 만듭니다.
모델 성능이 미묘하게 나빠지는데, 원인이 데이터 중복이라는 걸 알아내기까지 몇 주가 걸립니다.

**추가 고려** — 상장폐지·티커 변경이 있으면 `(ticker, traded_on)` 만으로 부족할 수 있습니다.
그럴 때는 종목 마스터 테이블을 두고 `(security_id, traded_on)` 을 쓰는 것이 정석입니다.
**"무엇이 같으면 같은 데이터인가"를 정하는 것이 스키마 설계의 첫 단추**입니다.

**2.** Step 5의 ③번 피벗 결과에서 2025-01 생활용품이 빈칸입니다. 이 값을 0으로 바꿔야 할까요, NULL로 둬야 할까요? 판단 기준을 쓰세요.

<details>
<summary>답 보기</summary>

**용도에 따라 다르고, 무엇이든 "선택했다"는 것을 문서에 남겨야 합니다.**

| 용도 | 권장 | 이유 |
|---|---|---|
| **경영 리포트·대시보드** | **0** | 빈칸은 "데이터 누락"으로 오해받음. "1월 생활용품 매출 0원"이 사실 |
| **차트(선 그래프)** | **0** | NULL이면 선이 끊기거나 점이 빠짐 |
| **평균 계산** | **주의** | `AVG` 는 NULL을 **분모에서 제외**함. 0을 채우면 평균이 내려감 ([Day 033](day-033.md)) |
| **데이터 품질 점검** | **NULL 유지** | "이 달에 판매가 없었다"는 사실 자체가 신호 |
| **모델 학습 입력** | **문맥에 따라** | "매출 0"과 "데이터 없음"은 다른 정보. 별도 플래그 열을 두는 것이 안전 |

**핵심 구분**

```
0     = "측정했고, 값이 0이었다"      (판매가 실제로 없었음)
NULL  = "값을 모른다"                (수집이 안 됐을 수도 있음)
```

이 데이터에서는 **"1월에 생활용품이 실제로 안 팔린 것"이 확실**하므로 0이 맞습니다.
하지만 [Day 039](day-039.md)의 `measurement.pm10` 은 **센서 고장으로 값이 없을 수 있어** NULL이 맞습니다.

**결론** — 0으로 채우되, **6개월 전체 데이터가 다 있는지 먼저 확인**하고,
리포트 각주에 "판매 없음은 0으로 표기"라고 적습니다.

```sql
COALESCE(SUM(oi.quantity * oi.unit_price) FILTER (WHERE p.category = '생활용품'), 0) AS 생활용품
```
</details>

**3.** MP1 스키마를 확정한 뒤, [Day 043](day-043.md)에서 "측정 항목이 하나 더 필요하다"는 것을 알게 됐습니다. 어떻게 하겠습니까? `sql/mp1_schema.sql` 을 직접 고치면 안 되는 이유는?

<details>
<summary>답 보기</summary>

**새 마이그레이션 파일을 추가합니다.**

```sql
-- sql/migrations/005_add_measurement_no2.sql
-- 목적: 이산화질소(NO2) 측정값 추가. 2026-08-20 이후 수집분부터 값이 들어옴
-- 기존 행은 NULL 로 남음 (그 시점엔 수집하지 않았으므로 "0"이 아니라 "없음"이 맞음)

ALTER TABLE measurement ADD COLUMN no2 numeric(5,3) CHECK (no2 >= 0);
```

**`mp1_schema.sql` 을 직접 고치면 안 되는 이유**

| 문제 | 설명 |
|---|---|
| **이미 적용된 DB에 반영되지 않는다** | 내 로컬 DB엔 열이 없는데 파일엔 있음. 코드가 깨짐 |
| **현재 상태를 알 수 없다** | 팀원 A는 열이 있고 B는 없는데, 파일은 하나. 누가 어디까지 적용했는지 불명 |
| **되돌릴 수 없다** | 문제가 생겨도 "어느 변경 때문인지" 특정할 수 없음 |
| **Git 이력이 무의미해진다** | 파일 하나의 diff만 남고, 운영 DB에 언제 적용됐는지는 기록 없음 |

**핵심** — 마이그레이션 파일은 **"현재 상태의 그림"이 아니라 "변경의 기록"** 입니다.
`001 → 005` 를 순서대로 실행하면 항상 같은 스키마가 나오는 것이 보장돼야 합니다.

**추가로 결정해야 할 것 — 기존 행의 `no2` 를 어떻게 할 것인가**

| 선택 | 의미 |
|---|---|
| **NULL로 둔다** ✅ | "그때는 수집하지 않았다" — 사실에 맞음 |
| 0으로 채운다 ❌ | "NO2가 0이었다"는 **거짓 정보**. 평균이 조작됨 |
| 소급 수집한다 | API가 과거 데이터를 주면 최선. 단 `ingested_at` 으로 구분 가능해야 함 |

**"모르는 값을 0으로 채우지 않는다"** 는 이 단원의 반복 주제입니다
([Day 032](day-032.md) NULL · [Day 033](day-033.md) `AVG` · [Day 044](day-044.md) 품질 검증).
</details>

## 주간 퀴즈 8 — W08 (SQL 심화와 모델링)

1. 인라인 뷰(`FROM` 절 서브쿼리)에 반드시 필요한 것은?
2. `NOT IN` 대신 `NOT EXISTS` 를 쓰라는 이유는?
3. 상관 서브쿼리가 느린 이유는?
4. `RANK()` 와 `DENSE_RANK()` 의 차이를 예로 설명하시오.
5. `WHERE` 에 윈도우 함수를 쓸 수 없는 이유와 해결책은?
6. `SUM(x) OVER ()` 와 `SUM(x) OVER (ORDER BY t)` 의 차이는?
7. 복합 인덱스 `(a, b)` 가 `WHERE b = 1` 에 쓰이지 않는 이유는?
8. 대량 적재 전에 인덱스를 지우는 이유는?
9. 기본 격리 수준에서 갱신 손실이 막히지 않는 이유와, 막는 방법 두 가지는?
10. 3NF를 일부러 어겨도 되는 경우를 하나 들고 근거를 쓰시오.

<details>
<summary>정답 보기</summary>

1. **별칭(alias)**. `FROM (SELECT ...) t` — 없으면 `subquery in FROM must have an alias`
2. 서브쿼리 결과에 **`NULL` 이 하나라도 있으면 `NOT IN` 은 항상 0행**을 반환하기 때문. 에러도 안 남
3. **바깥 행마다 한 번씩 실행**되기 때문. 100만 행이면 100만 번 → CTE + 조인으로 한 번만 계산
4. 값이 `100, 90, 90, 80` 일 때 `RANK` = 1,2,2,**4** / `DENSE_RANK` = 1,2,2,**3**. 동점 뒤 번호를 건너뛰는지 여부
5. 실행 순서가 `WHERE`(②) → 윈도우 함수(⑤) 라서. **CTE로 감싸고 바깥에서 필터**
6. 앞은 **창 전체 합계**(모든 행에 같은 값), 뒤는 `ORDER BY` 때문에 기본 프레임이 "처음~현재 행"이 되어 **누적 합계**
7. B-tree 인덱스는 **선두 열부터 정렬**돼 있어서. `(성, 이름)` 명부에서 이름만으로 못 찾는 것과 같음
8. `INSERT` 마다 인덱스도 갱신되기 때문. **다 넣고 한 번에 만드는 편이 훨씬 빠름** (`ANALYZE` 도 잊지 말 것)
9. `READ COMMITTED` 는 "커밋된 값 읽기"만 보장하고, **읽은 값이 낡았는지는 관여하지 않기** 때문.
   막는 법: ① `SET x = x - n` 으로 계산을 DB에 맡김 ② `SELECT ... FOR UPDATE` (③ 낙관적 잠금 ④ 격리 수준 상향도 정답)
10. **시점 값 보존** — `order_items.unit_price`. 상품 가격이 바뀌어도 과거 매출은 변하면 안 되므로 중복 저장이 정당함.
    (집계 성능을 위한 카운터 열, 분석 전용 스타 스키마도 정답)

**채점** — 8개 이상이면 W09로 진행. 5·6·9번을 틀렸다면 각각
[Day 037](day-037.md) 실행 순서 · [Day 037](day-037.md) 프레임 · [Day 039](day-039.md) 갱신 손실 절을 다시 읽으세요.
**W09의 파이썬 연동에서 9번이 바로 실전 문제로 나옵니다.**
</details>

|---|---|
