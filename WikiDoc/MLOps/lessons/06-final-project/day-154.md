## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 예측 로그에서 **서비스 지표와 모델 관점 지표**를 함께 뽑는 대시보드를 만들 수 있다.
- 부하 측정으로 서비스의 **용량을 숫자로** 알고, 시연 조건과 비교 판단할 수 있다.
- 남은 이슈를 심사해 발표 전 필수만 남기는 **버그 스윕**을 운영할 수 있다.
- **기능 동결**을 선언하고, 이후의 유혹(작은 기능 하나만)을 규칙으로 방어할 수 있다.

---

## ② 왜 필요한가

서비스는 어제부로 "돌아갑니다". 오늘의 질문은 다릅니다 — **"잘 돌아가는가, 그리고
그것을 어떻게 아는가?"** 지금 이 순간 응답이 몇 ms인지, 어떤 입력이 들어오는지, 에러가
몇 %인지 답할 수 없다면, 서비스의 건강은 사용자 불만이 알려 줄 때까지 미지수입니다.
모니터링은 필수 6종의 하나이기 이전에, 다음 주 발표 질의의 최다 출제 영역입니다 —
"몇 명까지 버티나요?" "지금 모델이 이상해지면 어떻게 아나요?" 오늘 만든 대시보드와
실측 숫자가 그 답안지입니다.

그리고 오늘 오후, 이 프로젝트에서 심리적으로 가장 어려운 결정을 합니다 — **기능 동결.**
지금부터 발표까지 새 기능은 없습니다. 남은 시간은 수리·문서·리허설의 것입니다. 어려운
이유는 명확합니다: 아이디어는 지금이 가장 많고("시간대 그래프만 붙이면 훨씬 좋을 텐데"),
남은 시간은 가장 적어 보이지 않기 때문입니다. 그러나 [Day 136](../05-infra-mlops/day-136.md)
에서 본 원칙이 팀 규모에서는 더 강하게 작동합니다 — 발표 직전의 변경은 검증 시간이
없는 변경이고, 검증 없는 변경은 시연 리스크입니다. 동결은 포기가 아니라 **완성의 보호**
입니다.

## ③ 개념 설명

### 지표의 3층 — 무엇을 재는가

[Day 134](../05-infra-mlops/day-134.md)의 구분 그대로, 이번엔 우리 서비스로:

| 층 | 지표 | 원천 |
|---|---|---|
| 시스템 | CPU·메모리·디스크 (컨테이너별) | docker stats · 서버 |
| 서비스 | 요청 수 · p50/p95 지연 · 에러율(4xx/5xx) | **prediction_log + nginx 로그** |
| 모델 | 입력 분포(역·시간대) · 출력 분포(등급 비율) · 모델 버전별 요청 | prediction_log |

모델 층이 핵심 차별점입니다 — 정답(내일의 실제 승차)은 며칠 뒤에야 오므로, **정확도를
실시간으로 알 수는 없습니다.** 대신 입력·출력의 분포가 평소와 다른가(드리프트의 전조)는
지금 볼 수 있습니다. "정답 없이도 이상은 보인다"가 모델 모니터링의 출발점입니다.

### 부하 측정 — 목적은 기록 갱신이 아니라 용량 파악

측정의 산출물은 "우리 서비스는 초당 N건, p95 M ms" 라는 **용량 명세**입니다. 판단은
비교로 합니다: 발표 시연(동시 사용자 ~수 명)·수업 시연(전원 접속 ~40명)이 용량 안에
있는가? 있다면 최적화는 하지 않습니다 — 동결 기간의 최적화는 새 기능과 같은 취급입니다.

### 기능 동결의 규칙 — 예외를 어렵게

```
오늘부터 병합 가능한 PR: ① 버그 수리 ② 문서 ③ 테스트 — 끝.
새 기능 예외 승인 조건: 전원 동의 + "시연 실패 시 되돌릴 방법" 명시 + 리허설 2회
```

예외 조건을 일부러 무겁게 만들어 두는 것이 요령입니다 — "안 된다"보다 "이 비용을 내면
된다"가 지키기 쉽습니다 (그리고 그 비용을 낼 만한 기능은 거의 없습니다).

## ④ 단계별 실습

### Step 1. 대시보드 — #31 (1~3교시)

지우와 서연이 prediction_log 위에 집계 뷰 + 간단한 페이지(`/admin/stats`, 내부용)를
만듭니다. 오늘 아침 기준 실제 화면 값:

```
[hansan 대시보드 · 최근 24h]
요청 1,847건 · 에러 0.9% (422 17건 — 전부 잘못된 역명 · 5xx 0건)
지연 p50 8.4ms · p95 41ms
등급 분포: 여유 41% · 보통 44% · 혼잡 15%
입력 상위: 강남 312 · 잠실 201 · 홍대입구 188 … (팀 테스트 트래픽 포함)
모델: hansan-daily-v3 (일요일 승격분) · 폴백 기동 0회
```

읽기 훈련 — 422가 "에러"가 아니라 **검증이 일하고 있다는 증거**임을 구분하는 것,
등급 분포가 갑자기 "혼잡 60%"가 되면 모델·기준선 문제를 의심해야 한다는 것. 대시보드는
만드는 것보다 **읽는 약속**(누가 언제 보나 — 한산: 스탠드업 첫 화면)이 중요합니다.

### Step 2. 부하 측정 — #32 (4~5교시)

[Day 099](../04-deep-learning-serving/day-099.md)의 도구로, 클라우드 서버 상대:

```
$ python loadtest.py --url http://<server>:8080/predict --concurrency 1,4,8 --n 300
c=1   31.2 req/s · p50  8.4ms · p95  19ms
c=4   54.8 req/s · p50 14.1ms · p95  38ms
c=8   57.3 req/s · p50 27.9ms · p95  41ms   ← 포화 (~57 req/s)
```

용량 판단 기록: "포화 57 req/s — 발표 시연(동시 수 명)과 전원 접속 시연(40명이 각자
수 초 간격 조회 ≈ 10 req/s 미만)에 충분. 최적화 불요." **숫자 → 비교 → 판단 → 기록**
까지가 측정입니다.

### Step 3. 버그 스윕 (6~7교시)

열린 이슈 전부를 3분류로 심사합니다:

| 분류 | 기준 | 한산 결과 |
|---|---|---|
| 지금 수리 | 시연 경로 위에 있거나 데이터가 상함 | 2건 (데모 페이지 모바일 깨짐 · 결측 대체 시 로그 누락) |
| 알려진 한계 | 시연 밖 + 문서에 쓰면 됨 | 3건 (연휴 lag 대체 정확도 등 → 보고서 "한계") |
| 닫음 | 재현 안 되거나 범위 밖 | 4건 (사유와 함께 닫기) |

### Step 4. 기능 동결 선언 (8교시)

- README 상단에 동결 배너: `🧊 feature freeze until D-160 — 버그·문서·테스트만`
- 선택 기능의 최종 처분 기록: 지도 시각화 — **하지 않음** (142의 선택 2순위 그대로 종료,
  로드맵 문서로 이동) · 알림 — 로드맵
- 155 데모 시나리오 초안 작성 (내일 아침 리허설 1회 약속)

**오늘 퇴근 체크** — □ 대시보드 + 읽는 약속 □ 부하 실측·용량 판단 기록 □ 이슈 전수
심사(3분류) □ 동결 선언 배너 □ 내일 데모 시나리오

## ⑤ 자주 하는 실수

### 대시보드가 장식이 됨

**증상** — 만든 날 한 번 보고 아무도 안 봄 — 목요일에 5xx가 2%로 올라 있었는데 발견은
발표 리허설에서.
**원인** — 보는 절차 없이 보는 도구만 만듦.
**해결** — 도구에 **약속을 부착**하세요: "스탠드업 첫 화면은 대시보드" (한산 규칙).
30초면 됩니다 — 지표가 회의 의제가 되는 순간 대시보드는 장식에서 감각 기관이 됩니다.

### 부하 측정이 목적을 잃음

**증상** — "500 req/s는 나와야 하지 않아?" — 워커 수·캐시 튜닝으로 오후를 소모, 동결
전날 서빙 코드 대수술.
**원인** — 측정의 산출물을 "판단"이 아니라 "기록 갱신"으로 착각.
**해결** — 측정 전에 **요구 수치를 먼저** 적으세요 (시연 조건 ≈ 10 req/s). 용량이 요구의
5배를 넘으면 결론은 "충분, 종료"입니다. 남는 에너지는 지금 5배 남는 성능이 아니라 아직
0인 것(문서·리허설)에 쓰는 것이 배점 산수입니다.

### 동결 다음 날의 "작은 기능 하나만"

**증상** — "30분이면 붙여요" — 시간대 그래프가 금요일 데모 10분 전에 데모 페이지를
깨뜨림.
**원인** — 작은 기능의 위험을 코드 크기로 추정 — 위험은 크기가 아니라 **검증 안 된
변경의 수**에 비례합니다.
**해결** — 예외 승인 조건(전원 동의 + 복구 방법 + 리허설 2회)을 그대로 적용하세요.
이 비용을 듣고도 하고 싶은 기능은 거의 없고, 그래도 남는 것이라면 진짜 필요한 것일
수 있습니다 — 규칙은 유혹을 없애는 게 아니라 유혹에 가격을 붙입니다.

### "에러율 0%"를 자랑으로 읽음

**증상** — 대시보드의 422 0건을 보고 "완벽하네요" — 실은 검증 코드가 어제 리팩터링에서
빠져, 잘못된 역명이 500이 아니라 **빈 예측으로 조용히 성공**하고 있었음.
**원인** — 지표의 정상 범위를 "낮을수록 좋다"로만 해석.
**해결** — 지표마다 **정상 범위는 양쪽**입니다: 422가 평소 ~1%인데 0%가 되면 검증의
실종을, 5xx 0%는 좋지만 요청 수까지 0이면 서비스 정지를 의심해야 합니다. "이 지표가
0이면 무엇이 고장인가?"를 지표마다 한 번씩 물어 두세요.

## ⑥ 확인 문제

**Q1.** "정답 없이도 이상은 보인다" — 정확도를 실시간으로 알 수 없는 이 서비스에서
등급 분포·입력 분포가 조기 경보로 작동하는 원리를 설명하고, 분포 경보가 잡지 **못하는**
고장의 예를 하나 드세요.

<details>
<summary>답 보기</summary>

모델의 정답(실제 승차)은 D+4 이후에 오지만, 고장의 다수는 출력·입력의 분포를 먼저
비틉니다 — 기준선(P90) 테이블이 깨지면 등급 분포가 급변하고(혼잡 60%), 피처 조회
버그는 특정 역의 예측값을 이상하게 만들며, 클라이언트 문제는 입력 분포(역·시간)의
쏠림으로 나타납니다. 평소의 분포를 알고 있으면 "정답 대비 오차" 없이도 "평소 대비
이탈"로 경보가 가능합니다. 못 잡는 예: **분포는 그대로인 채 정확도만 나빠지는 경우** —
예컨대 개학·재택 정책 변화로 실제 수요 패턴이 바뀌었는데 예측은 과거 패턴을 유지하는
드리프트는, 예측 분포가 자연스러워 보이므로 정답이 도착해 오차를 계산할 때(주간 재학습
평가)에야 드러납니다. 그래서 분포 감시와 지연된 정답 대조는 상호 보완입니다.

</details>

**Q2.** 부하 측정 결과(포화 57 req/s)에서 "최적화 불요"라는 결론을 내리는 판단 과정을
일반화하면 어떤 절차가 되나요? 이 절차 없이 측정만 하면 팀에 어떤 일이 생기는지도
설명하세요.

<details>
<summary>답 보기</summary>

일반 절차: ① 요구를 먼저 수치화(시연·예상 사용의 최대 부하 ≈ 10 req/s) → ② 실측
(57 req/s) → ③ 여유율 계산(5.7배) → ④ 임계 기준과 비교해 판단(여유 ≥ N배면 종료) →
⑤ 판단과 근거를 기록. 핵심은 ①이 ②보다 먼저라는 것 — 요구가 없으면 어떤 숫자도 "더
높일 수 있을 것 같은" 숫자로 보입니다. 절차 없이 측정만 하면: 숫자가 목표가 되어(기록
갱신 심리) 필요 없는 최적화에 동결 기간을 쓰고, 최적화는 대개 코드 변경이므로 검증
안 된 변경이 시연 직전에 쌓입니다 — 측정이 안정화 도구가 아니라 불안정화 트리거가 되는
역설입니다.

</details>

**Q3.** 기능 동결이 "포기가 아니라 완성의 보호"인 이유를, 이 시점의 한계 효용 비교
(새 기능 1개 vs 리허설 1회 vs 문서 1편)로 논증하세요.

<details>
<summary>답 보기</summary>

배점 관점에서 지금 새 기능 1개의 기대 이득은 가산 몇 점 × 완성 확률(낮음)이고, 기대
손실은 시연 실패 리스크 × 사이클·발표 배점(큼)입니다 — 기대값이 음수에 가깝습니다.
반면 리허설 1회는 시연 실패 확률을 직접 낮춰 30~50점 구역(재현성·발표·사이클)을 보호
하고, 문서 1편(운영 절차서·보고서)은 문서 20점 구역에 직접 가산됩니다 — 둘 다 확실한
양수입니다. 즉 같은 시간의 한계 효용이 "만들기 < 검증하기 < 전달하기"로 역전된 시점이
왔고, 동결은 그 역전을 팀 전체의 기본값으로 선언하는 장치입니다. 아이디어가 아깝다면
로드맵 문서에 쓰면 됩니다 — 그 문서 역시 "다음 단계" 점수가 됩니다.

</details>
