## 3. 기획 → 구현 → 검증

### 3.1 기획을 먼저 고정

구현 전에 PRD에서 **목표·비목표·리스크**를 먼저 정했다. 특히 비목표가 범위를 지켰다.

| 비목표 (MVP) | 이유 |
|---|---|
| 대화 중 이미지 생성 | 지연과 외형 불일치. 미리 만든 그림만 쓴다 |
| 감정 분류 모델 | LLM이 포즈를 직접 고르게 하고, 부족하면 그때 추가 |
| 서버·계정·동기화 | 단일 사용자·단일 기기. 브라우저가 로컬 LLM을 직접 부른다 |

기능명세서는 기능마다 ID(F-01~F-15)와 우선순위(P0~P2)를 붙이고, 구현이 바뀔 때마다 같은 커밋에서 갱신했다. 응답 JSON 규격, 예외 처리 표, 프롬프트 골격이 여기서 먼저 정해졌다.

### 3.2 작게 시작해 넓히기

1. **Python CLI 시제품** — 표준 라이브러리만으로 151줄. 로컬 LLM과 캐릭터 대화가 되는지, 한국어 롤플레이 품질이 쓸 만한지부터 확인했다.
2. **웹판 MVP (P0)** — 화면, 스트리밍, JSON 응답, 포즈 전환, 저장.
3. **관계 시스템 (P1)** — 호감도, 배경, 사건·메모, 재생성.
4. **확장** — 음성, 현실 시간, 옷차림, 여러 캐릭터, 공략 완료.

### 3.3 설계를 줄인 결정들

| 처음 계획 | 바꾼 것 | 이유 |
|---|---|---|
| 사건 경계 규칙 + 별도 추출 요청 + 점수 검색 + 망각 단계 | 응답 JSON에 `event`·`memo` 한 줄씩, 최근 메모 30개 주입 | 추가 요청 없이 같은 응답에서 얻는다. 메시지에 붙어 있어 재생성과 자동으로 맞는다. 부족해지면 그때 검색을 붙인다 |
| 호감도를 따로 저장 | 메시지별 변화량을 매번 합산 | 재생성 시 되돌리기가 공짜 |
| 수동 저장 슬롯 3개 · 대화 되감기 | 삭제 | 되돌릴 수 있으면 관계의 무게가 없어진다 |
| localStorage 저장 | IndexedDB | 긴 대화가 5MB 한도를 넘는다. 오래된 대화를 잘라내지 않으려고 |
| 캐릭터마다 그림 필수 | 그림 없는 캐릭터 허용 | 그림 제작이 병목이 되지 않게. 설정만으로 캐릭터를 늘린다 |

### 3.4 검증

- **자동 테스트** — 결정이 틀리기 쉬운 순수 함수(부분 파싱, 응답 파싱, 호감도 경계, 일정의 자정 넘김, WAV 헤더)에만 단언 24개. 브라우저 코드와 같은 모듈을 Node에서 그대로 부른다. 테스트 프레임워크는 쓰지 않았다.
- **직접 플레이** — 포즈가 대사에 맞는지, 옷이 대사마다 바뀌지 않는지, 단계별 말투가 달라지는지는 실제 모델과 대화하며 확인했다. 이 과정에서 나온 문제가 설계로 이어졌다.

| 플레이·구현 중 나온 문제 | 대응 |
|---|---|
| 대사마다 옷이 바뀜 | 현재 옷차림의 포즈만 후보로, `outfit`을 적을 때만 갈아입기 |
| 목록 밖의 포즈 ID가 올 위험 | JSON 스키마 `enum`을 매 턴 생성 + 파서에서 직전 포즈 유지 |
| 사고형 모델에서 대사가 빈 채로 옴 | `reasoning_effort: "none"` 옵션 추가 |
| Gemma가 대화 순서 오류를 냄 | 연속 발화 합치기 + 입장 지문 user 메시지 |
| 처음 배경이 비어 있음 | 배경이 없을 때는 `enum`에서 `""`를 빼 반드시 고르게 |
| 그림 없는 캐릭터 카드가 깨진 이미지로 보임 | 이름 첫 글자 카드로 표시 |

## 4. Claude Code와의 협업

- **역할 분담** — 사람은 무엇을 만들지, 캐릭터가 어떤 사람인지, 어떤 기능을 빼야 하는지를 정했다. Claude Code는 코드 작성, 기능명세서·PRD 갱신, 테스트 실행, 브라우저로 화면 확인을 맡았다.
- **문서와 코드를 같이 바꾼다** — 기능을 바꾸는 커밋은 기능명세서의 해당 항목도 함께 고친다 (예: 되감기 삭제 → F-11, 공략 완료 → F-08a 신설).
- **짧은 코드 원칙** — 의존성을 들이지 않고, 필요해지기 전에는 추상화를 만들지 않았다. 일부러 단순하게 둔 곳에는 한계와 다음 단계를 주석으로 남겼다 (예: "메모는 최근 30개만, 넘치면 요약 단계 추가").
- **세션 간 분업** — 이 포트폴리오 문서는 포트폴리오 사이트를 맡은 세션의 요청을 받아, 코드를 아는 이 프로젝트 세션이 본문과 스크린샷을 쓰고 사이트 쪽 세션이 연결·적용했다.

## 5. 회고와 다음 단계

**잘된 점**

- LLM에게 "고를 수 있는 것만" 주는 방식(옷차림별 포즈, 해금, 스키마 `enum`)이 프롬프트 지시보다 훨씬 확실했다.
- 빌드·의존성이 없어 수정 → 새로고침만으로 확인이 끝난다.
- 비목표를 먼저 적어 둔 덕분에 범위가 커지지 않았다.

**아쉬운 점**

- 커밋 이후의 큰 작업(옷차림, 캐릭터 3명, 음성 출력, 인트로)이 아직 커밋되지 않았다. 기능 단위로 더 자주 끊었어야 했다.
- 포즈 적합도("10번 중 8번")를 수치로 재는 평가 절차를 아직 만들지 못했다.
- 플레이에 로컬 GPU와 LLM 설정이 필요해 다른 사람이 바로 해 보기 어렵다.

**다음 단계**

2. 나머지 두 캐릭터의 그림

4. 포즈 적합도 평가 스크립트
