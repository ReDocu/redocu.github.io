## ② 왜 필요한가

오늘의 두 주제는 서빙 직전의 마지막 준비물입니다.

**비동기** — 다음 주 추론 API는 요청 하나에 수십~수백 ms를 씁니다. 그때 다른 요청은
기다려야 할까요? 이 질문의 답이 sync/async 선택인데, 인터넷에는 "FastAPI는 async지!"라는
절반의 지식이 넘칩니다. 오늘 실측으로 확인할 진실: **잘못 쓴 async는 서버를 5배 느리게**
만들고(우리가 직접 잽니다), **모델 추론 같은 블로킹 작업에는 평범한 def가 정답**입니다 —
이 결론이 [Day 096](day-096.md)~MP3의 핸들러 설계를 결정합니다.

**테스트** — [Day 074](../03-machine-learning/day-074.md)에서 "ML의 버그는 조용하다"고 했는데,
API의 버그는 **남의 코드에서** 터집니다 (클라이언트 개발자의 앱에서). 매번 서버를 띄우고
수동으로 눌러 보는 검증은 오늘로 끝 — 상태 코드 계약(201/404/409/422) 전부를 0.6초 만에
검증하는 통합 테스트를 만듭니다. MP3 평가 기준 "테스트 15점"과 단원 완료 조건("통합 테스트가
한 줄로 실행")의 실체입니다.

## ③ 개념 설명

### 서버는 왜 "기다림"이 문제인가

요청 처리 시간의 대부분은 계산이 아니라 **대기**입니다 — DB 응답 대기, 외부 API 대기.
그 동안 서버가 놀면 동시 처리량이 무너집니다. 해법이 두 갈래:

| 방식 | 원리 | 코드 |
|---|---|---|
| **비동기 (async)** | 기다리는 동안 이벤트 루프가 다른 요청 처리 | `async def` + **await 가능한** 라이브러리 |
| **스레드풀 (sync)** | 블로킹 작업을 별도 스레드에서 | 평범한 `def` — FastAPI가 자동 처리 |

### 세 가지 핸들러, 세 가지 운명

```python
async def good():  await asyncio.sleep(1)   # ✓ 논블로킹 — 루프가 살아 있음
async def bad():   time.sleep(1)            # ✗ 루프를 통째로 잠금 — 전 요청 정지!
def plain():       time.sleep(1)            # ✓ 스레드풀 — 루프와 무관
```

규칙은 하나입니다: **async def 안에는 await 가능한 것만.** 블로킹 함수(time.sleep,
requests, DB 드라이버, **torch 추론**)를 넣을 거면 그냥 `def` 로 쓰세요 — FastAPI가
스레드풀로 알아서 돌립니다. "모르면 def" 가 안전한 기본값입니다.

### TestClient — 서버 없는 서버 테스트

```python
client = TestClient(app)
r = client.post("/reports", json={...})    # 진짜 HTTP처럼 — 포트·프로세스 없이
```

uvicorn 없이 앱 객체를 직접 호출합니다. 검증 계층·라우팅·예외 번역까지 전부 통과하는
**통합** 테스트인데 속도는 단위 테스트급 — [Day 074](../03-machine-learning/day-074.md)의
"빠르고 독립적이어야 매번 돌린다"를 API에서 실현하는 도구입니다.

### dependency_overrides — 어제 심은 소켓의 수확

```python
app.dependency_overrides[get_service] = lambda: ReportService(FakeRepository())
```

어제 Depends로 부품을 소켓화해 둔 덕에, 테스트에서 진짜 DB 대신 **딕셔너리 저장소**를
꽂을 수 있습니다. 테스트가 DB 파일을 더럽히지 않고, 순서에 무관해지고, 밀리초로 끝납니다.

## ④ 단계별 실습

### Step 1. 동시성 실측 — 세 핸들러의 운명 (1~3교시)

`async_demo.py`:

```python
# async_demo.py — sync vs async, 언제 갈리나
import asyncio
import time
from fastapi import FastAPI

app = FastAPI()


@app.get("/good-async")
async def good_async():
    """제대로 된 async — 기다리는 동안 다른 요청을 처리할 수 있다."""
    await asyncio.sleep(1)                 # 논블로킹 대기 (외부 API 호출 등을 흉내)
    return {"path": "good-async"}


@app.get("/bad-async")
async def bad_async():
    """잘못된 async — 이벤트 루프를 통째로 잠근다!"""
    time.sleep(1)                          # 블로킹 호출을 async 안에서 (버그)
    return {"path": "bad-async"}


@app.get("/plain-sync")
def plain_sync():
    """평범한 def — FastAPI가 알아서 스레드풀에서 돌려 준다."""
    time.sleep(1)                          # 블로킹이지만 괜찮다 (스레드풀)
    return {"path": "plain-sync"}
```

서버를 띄우고, **동시 요청 5개**를 각 경로에 보내 전체 소요 시간을 잽니다
(측정 스크립트는 httpx.AsyncClient + asyncio.gather — 저장소 참고):

```
동시 요청 5개를 보냈을 때 전체 응답까지 걸린 시간 (처리 자체는 각 1초):
  /good-async  1.1초
  /plain-sync  1.0초
  /bad-async   5.1초
```

해석:

| 경로 | 5개 동시 | 왜 |
|---|---|---|
| /good-async | **1.1초** | await하는 동안 루프가 나머지 4개를 받음 — 병렬 대기 |
| /plain-sync | **1.0초** | 5개가 각자 스레드에서 — FastAPI의 안전망 |
| /bad-async | **5.1초** | time.sleep이 루프를 잠가 **한 줄로 서서** 처리됨 |

`async` 라는 글자가 붙었다고 빨라지는 게 아니라, **잘못 붙이면 5배 느려집니다.**
그리고 bad-async가 잠그는 건 자기 경로만이 아닙니다 — 루프가 멈추면 /health까지 모든
요청이 얼어붙습니다 (직접 확인해 보세요: bad-async 처리 중에 /docs를 열어 보기).

**서빙에의 결론**: torch 추론은 블로킹입니다 → 추론 핸들러는 **평범한 def** 로.
(async가 꼭 필요한 곳은 "외부 API를 기다리는" 엔드포인트 — 그때도 httpx 같은
async 지원 라이브러리를 써야 합니다.)

## ⑤ 자주 하는 실수

### async def 안에서 블로킹 호출

**증상** — 서버가 요청 하나 처리하는 동안 **다른 모든 요청**(헬스체크까지)이 얼어붙음. 오늘 실측 5.1초의 그것.
**원인** — `async def` 안의 time.sleep / requests / torch 추론 — 이벤트 루프 위에서 도는 코드가 루프를 잠갔습니다.
**해결** — 블로킹 작업은 평범한 `def` 로 (스레드풀행). async를 고집하려면 라이브러리도 async여야 합니다(httpx, asyncpg 등). **모르면 def.**

### requests를 async 핸들러에서 씀

**증상** — 위와 동일한 동결 — "await 붙였는데요?" (requests에는 await가 안 붙습니다).
**원인** — requests([Day 016](../01-python-data/day-016.md))는 블로킹 전용 라이브러리입니다.
**해결** — async 핸들러에서 외부 호출은 `httpx.AsyncClient` + await. sync 핸들러라면 requests도 괜찮습니다.

### 테스트가 진짜 DB에 흔적을 남김

**증상** — 테스트를 돌릴 때마다 dev DB에 강남구 리포트가 쌓임 / 두 번째 실행부터 409로 실패.
**원인** — 부품 교체 없이 실제 repository로 테스트했습니다.
**해결** — dependency_overrides로 가짜(또는 테스트 전용 DB)를 주입하고, fixture에서 매 테스트 초기화. **테스트는 몇 번을 돌려도 같은 결과**여야 합니다 ([Day 042](../02-sql-pipeline/day-042.md) 멱등성의 테스트판).

### dependency_overrides를 지우지 않음

**증상** — 앞 테스트의 가짜 부품이 뒤 테스트(또는 다른 파일)에까지 꽂혀 있어 이상하게 통과/실패.
**원인** — overrides는 전역 상태입니다.
**해결** — fixture의 yield 뒤에 `app.dependency_overrides.clear()` (오늘 코드의 마지막 줄이 그것입니다).

### 성공 경로만 테스트

**증상** — 테스트 3개(전부 200/201)로 "테스트 있음" 처리 — 정작 사고는 4xx 경로에서.
**원인** — 실패 경로 설계([Day 092](day-092.md))가 테스트로 이어지지 않았습니다.
**해결** — 상태 코드 하나당 최소 테스트 하나 (오늘 10개의 배분: 2xx 4개 / 4xx 5개 / 경계값 2개... 실패 쪽이 더 많은 게 정상입니다). /docs에 선언된 응답 코드가 곧 테스트 목록입니다.

service 계층의 `to_grade` 를 직접 호출하는 순수 단위 테스트로 쓸 수 있습니다
(`assert to_grade(36) == "나쁨"`) — service가 HTTP를 모르기 때문에 가능한 일입니다. 실무 배분은
"규칙의 경우의 수는 service 단위 테스트로 촘촘히, API 테스트는 계약(상태 코드·번역) 위주로" —
같은 것을 두 층에서 중복 검증하지 않는 것이 유지비를 줄입니다.

</details>
