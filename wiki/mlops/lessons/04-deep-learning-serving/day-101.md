## ② 왜 필요한가

오늘부터 5일, MP3입니다. 그리고 시작하기 전에 관점 하나를 교정해야 합니다 —
**MP3는 모델 프로젝트가 아니라 서비스 프로젝트입니다.** 평가 배점을 보세요:

```
API 품질 30 + 서빙 정확성 25 + 로깅·측정 20 + 테스트 15 + 발표 10 = 100
```

모델 성능 점수가 **없습니다.** 모델은 W17·W18에서 이미 만들었고(정확도 0.954 / 0.815),
이번 주에 모델을 더 좋게 만드는 시간은 0분이어야 합니다. 심사위원이 보는 것은 "그 모델을
**다른 개발자가 믿고 호출할 수 있는 서비스**로 만들었는가"입니다.

두 번째 함정은 통합입니다. 부품(로드·전처리 일치·로그·테스트)은 전부 손에 있지만, 조립
순서 없이 시작하면 목요일에 구조를 재배치하게 됩니다. 다행히 [Day 100](day-100.md)의
리허설 대조표가 이미 "무엇이 있고 무엇이 없는지"를 말해 줍니다 — 오늘 기획은 그 ❌들을
5일에 배치하는 일입니다.

### 평가 기준이 실제로 보는 것

| 기준 (배점) | 심사위원이 확인하는 방법 |
|---|---|
| API 품질 (30) | 명세와 구현의 일치 · 모든 실패가 의도된 4xx인가 · /docs만 보고 쓸 수 있는가 ([Day 095](day-095.md)의 리뷰 3축) |
| 서빙 정확성 (25) | **학습 시점 기록과 서빙 응답의 대조표** — 같은 입력에 같은 확률이 나오는가 ([Day 100](day-100.md) Step 3) |
| 로깅·측정 (20) | 로그로 "어제의 p95"에 답할 수 있는가 · 부하 측정 전후 비교표 |
| 테스트 (15) | 명세 표의 각 칸에 테스트가 있는가 · 한 줄로 실행되는가 |
| 발표 (10) | 시연이 실제로 도는가 · "왜 이렇게 설계했나"에 근거로 답하는가 |

### 서비스 시나리오 — API의 "문제 정의"

MP2 기획의 첫 칸이 "문제 정의"였듯([Day 071](../03-machine-learning/day-071.md)), API 기획의
첫 칸은 시나리오입니다. 4요소를 채우면 한 문단이 됩니다:

```
누가:        사진 앱 개발자 (우리 API의 소비자 — 사람이 아니라 코드!)
무엇을 보내: 곤충 사진 1장 (5MB 이하 JPEG/PNG)
무엇을 받아: 개미/벌 판정 + 확신도 + 모델 버전 (JSON)
무엇을 하는가: 앱에서 "이 곤충은?" 기능을 만들고, 관리자는 로그로 사용량·지연을 확인
```

시나리오가 없으면 명세의 모든 결정(왜 5MB? 왜 batch가 필요/불필요?)이 임의가 됩니다.
시나리오가 있으면 **결정마다 근거가 생깁니다** — 심사 질문 "왜?"의 방파제입니다.

### API 명세 — 계약 표가 곧 설계도

[Day 095](day-095.md)의 명세 표 형식에 파일 입력의 상태 코드(413·415)가 추가된 것뿐입니다.
이 표의 각 칸이 그대로 ⑥ Day 104의 테스트 목록이 됩니다.

## ④ 단계별 실습

### Step 1. 모델 선정 — 30분 안에 (1교시)

[Day 100](day-100.md) 주말 과제의 기준표로 심사하고 **하나를 고릅니다.** 예시 프로젝트의 심사:

| 기준 | 이미지 (antbee) | 텍스트 (nsmc) | 판정 |
|---|---|---|---|
| 입력 처리 | multipart — 이번 주 배운 것을 쓸 기회 | JSON — 이미 익숙 | 이미지 우세 |
| 시연 효과 | /docs에서 사진 업로드 — 직관적 | 문장 입력 — 평범 | 이미지 우세 |
| 검증 다양성 | 413·415·422 셋 다 등장 | 422뿐 | 이미지 우세 |
| 지연 | ~25ms | ~38ms | 비슷 |

예시 프로젝트는 **이미지(개미/벌 분류 API)**로 갑니다 — 이후 문서의 예시가 전부 이것입니다.
텍스트를 골라도 이번 주 문서를 그대로 따라올 수 있습니다 (다른 곳마다 표시해 두겠습니다).
**어느 쪽이든 오늘 오전에 확정하고 다시 논하지 않습니다** — 5일 중 반나절을 선택 고민에 쓰는
것이 이 주간 최대의 시간 낭비입니다.

확신도, 모델 버전을 JSON으로 받는다. 운영자는 구조화 로그로 사용량·지연 분포·
예측 분포를 매일 확인한다.

## 2. 모델 (변경 금지 — 이번 주에 학습 없음)

## 3. API 명세 (구현 전 확정 — 이후 변경은 이력 남김)
| 메서드·경로 | 성공 | 실패 | 비고 |
|---|---|---|---|
| POST /predict (multipart) | 200 label·confidence·model_version·duration_ms | 413 초과 / 415 비이미지 / 422 파일 누락 | 5MB 상한 |

## ⑤ 자주 하는 실수

### 모델 성능부터 올리려 함

**증상** — 첫날을 "0.954를 0.97로" 실험에 씀 — 수요일까지 API가 없음.
**원인** — 4주간 모델 점수로 평가받던 관성. 하지만 MP3 배점표에 모델 성능은 **0점**입니다.
**해결** — 기획서 2절에 "변경 금지"를 선언하고, 모델 욕심은 회고에 "다음 기회"로 적으세요.

### 시나리오 없이 명세부터

**증상** — 엔드포인트 표는 있는데 "왜 5MB인가", "배치가 왜 필요한가"에 답을 못 함.
**원인** — 소비자(누가 쓰나)를 정하지 않고 기능 목록부터 썼습니다.
**해결** — 시나리오 4요소 먼저. 모든 명세 숫자는 시나리오에서 역산됩니다 (사진 앱 → 휴대폰 사진 ≤ 5MB).

### 명세 없이 코드부터

**증상** — 구현하며 즉흥으로 정한 응답 모양이 엔드포인트마다 다름 — 목요일 테스트 작성 때 발각.
**원인** — [Day 095](day-095.md)에서 겪은 그 문제가 프로젝트 규모로 재발.
**해결** — 오늘 명세 표를 확정하고, 변경은 이력을 남깁니다. 표가 곧 Day 104의 테스트 목록입니다.

### 웹 데모 페이지부터 만듦

**증상** — 화요일에 예쁜 업로드 페이지 완성 — 로그·테스트는 목요일 밤에 시작.
**원인** — 보이는 것부터 만들고 싶은 유혹. 하지만 데모는 배점 어디에도 없습니다 (선택 기능).
**해결** — /docs가 이미 시연 가능한 데모입니다 ([Day 100](day-100.md) Step 2). 커스텀 페이지는 필수 완료 커밋 이후에.

### 두 모델 다 서빙하려 함

**증상** — "이미지도 텍스트도 아까워서" — 결국 둘 다 로그·테스트가 반쪽.
**원인** — 선택의 어려움을 회피가 대신함.
**해결** — 하나를 완성도 있게. 2모델 서빙은 상급 확장(A/B 2버전)으로 명세에 적고, 필수 완료 후에만.

소비자 코드의 버그가 됩니다. (그 외: 버전 정책, 하위 호환, 멱등성 등도 같은 이유로 중요해집니다.)
