## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 이번 주에 만든 파이프라인 전체를 **한 장의 지도**로 그리고 각 관문의 역할을 설명할 수 있다.
- **파이프라인 점검 체크리스트**(신뢰·속도·안전·시크릿·가시성)로 자기 파이프라인을 채점할 수 있다.
- 팀원의 PR이 **내 서버에 자동 반영되는** 전 과정을 교차 검증할 수 있다.
- 배포에서 발견된 병을 **한 그물 앞으로** 당기는 개선을 실행할 수 있다.

---

## ② 왜 필요한가

나흘간 부품을 조립했습니다 — CI(126), 게이트(127), 빌드(128), CD(129). 오늘의 질문은
[Day 125](day-125.md)와 같은 종류입니다: **부품의 합이 시스템인가?**

그리고 새 관점 하나 — 이 파이프라인은 이제 여러분 팀의 **생산 수단**입니다. 코드에 리뷰와
테스트가 있듯, 파이프라인에도 점검과 개선이 있어야 합니다. 우회로가 하나라도 있으면 게이트
전체가 장식이 되고(최약점의 법칙 — [Day 128](day-128.md) Q1), PR 피드백이 15분이면 아무도
작은 PR을 안 만들며(속도는 문화를 결정), 빨간불이 방치되면 신호가 소음이 됩니다.

오늘 오전엔 그 점검을, 오후엔 이 시스템의 가장 통쾌한 순간을 체험합니다 — **남의 커밋이
관문 넷을 통과해 내 서버에 스스로 도착하는** 광경. W22에 "충돌 10분 컷"으로 시작한 협업이,
"병합하면 2분 뒤 서로의 운영에 반영"까지 왔습니다.

## ③ 개념 설명

### 파이프라인 전체 지도

```
개발자 push ──▶ PR
                │
                ├─[관문1] CI: lint (20초) ──────── 기계적 품질
                ├─[관문2] CI: test + cov (2분) ─── 동작 검증 (0.7214 회귀 포함)
                ├─[관문3] 리뷰어 승인 ──────────── 사람의 판단
                ▼
         main 병합 (보호 규칙 = 관문 우회 불가)
                │
                ├─[생산] build → GHCR (sha-태그 = 커밋 족보)
                ▼
         deploy (self-hosted)
                │
                ├─[관문4] 스모크: nginx 경유 헬스+예측 ── 운영 구성 검증
                │      └─ 실패 → 자동 롤백 + 빨간불
                ▼
         운영 반영 + 이력 기록 (deploy_history.log)
```

관문마다 **잡는 병이 다릅니다** — 겹치는 그물이 아니라 분업하는 그물입니다. 이 그림을 자기
저장소 기준으로 그릴 수 있어야 "파이프라인을 이해했다"입니다.

### 점검 체크리스트 — 다섯 축

[Day 125](day-125.md)의 운영 리뷰(구성의 다섯 축)와 짝을 이루는, **파이프라인의 다섯 축**:

| 축 | 질문 | 증거 명령/화면 |
|---|---|---|
| **신뢰** | 게이트를 우회하는 경로가 0인가 (관리자 포함) | main 직접 push → GH006 · 보호 규칙 화면 |
| **속도** | PR 피드백 몇 분? 커밋→운영 몇 분? | Actions 실행 시간 · Step 4(129) 타임라인 |
| **안전** | 배포가 스스로 검증·복귀하는가 · 이력이 남는가 | 스모크 로그 · 롤백 리허설 · history.log |
| **시크릿** | 4대 금지처 + **CI 로그**에 시크릿이 없는가 | 122 점검표 + Actions 로그 grep |
| **가시성** | 상태가 보이는가 — 뱃지·빨간불 통지·이력 | README 뱃지 · 알림 설정 |

### 초록 유지 문화 — 깨진 창문의 법칙

빨간불이 하루 방치되면 이틀째부터는 풍경이 됩니다 — "아 그거 원래 빨개요"가 나오는 순간
파이프라인은 죽은 것입니다. 규칙은 단순합니다: **main의 빨간불은 전원 최우선 이슈** —
고치거나(fix-forward), 되돌리거나(revert — 109), 둘 다 15분 내 판단. 이 문화가 없으면 오늘까지
만든 모든 자동화가 서서히 소음이 됩니다.

## ④ 단계별 실습

### Step 1. 내 지도 그리기 (1교시)

③의 지도를 **자기 저장소의 실제 값**으로 다시 그리세요 — 각 관문에 실측 시간(Actions 로그의
수치), 관문이 실제로 잡아 본 병(이번 주 겪은 실패 사례)을 주석으로. "겪은 실패가 없는 관문"이
있다면 그것이 오늘 오후 실험 대상입니다.

### Step 2. 다섯 축 채점 (2~3교시)

체크리스트의 증거를 하나씩 실행·수집합니다. 예상 결과와 실측:

```
[신뢰]  main 직접 push → GH006 ✓ · Include administrators ✓
[속도]  lint 18s · test 2m 05s (캐시 후 52s) · 커밋→운영 2m 01s ✓
[안전]  스모크 ✓ · 롤백 리허설 ✓ (129 Step 5) · 이력 4행 ✓
[시크릿] Actions 로그 grep → 마스킹 확인 ✓ · .env 계열 커밋 이력 없음 ✓
[가시성] 뱃지 ✓ · 빨간불 알림 — ✗ 설정 안 함!
```

빠진 것을 바로 메웁니다 — GitHub 알림은 기본으로 "자기 활동"만 오므로, Watch → Custom →
**Actions 실패 알림**을 켜거나, 저장소 Settings → Notifications로 팀 채널/메일 연결.
"빨간불을 아무도 모르는" 상태는 가시성 0점입니다.

### Step 3. 교차 검증 — 남의 커밋이 내 서버에 (4~6교시)

짝과 서로의 저장소에서 **전 과정을 상대 입장으로** 밟습니다:

1. 짝이 내 저장소에 작은 PR (협업자 권한 — W22에 이미 초대돼 있음): 예 — README의 운영
   섹션 개선, 데모 페이지 문구
2. **나는 리뷰어** — 게이트 화면(체크 진행 → 초록 → 병합 버튼 활성화)을 관찰하며 승인
3. 병합 — 그리고 **둘이 함께 내 서버를 관전**:

```bash
watch -n 5 'tail -3 /opt/mlops-mp3/deploy_history.log'
```

```
2026-08-25T11:42:19+09:00 sha-c40d17e ok      ← 짝의 커밋이 도착했다
```

4. 역할을 바꿔 반대 방향도.

관전 포인트 — 짝은 내 서버에 SSH 계정이 **없습니다.** 그런데 짝의 코드가 내 운영에 반영됐죠.
"접근 권한"이 서버 계정에서 **저장소 권한 + 게이트 통과**로 옮겨 간 것 — 이것이 이번 주가
협업의 규칙을 바꾼 방식입니다 (그래서 게이트의 신뢰 축이 보안 그 자체입니다).

### Step 4. 개선 1건 — 병을 앞 그물로 (7교시)

[Day 129](day-129.md) Step 5의 병(CI 초록·배포 실패)을 그물 앞당기기로 처방합니다 —
ci.yml에 **컨테이너 기동 테스트** job 추가:

```yaml
  container-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: false
          load: true
          tags: mp3-check:pr
          cache-from: type=gha
      - name: 기동 + 컨테이너 계약 검증
        run: |
          docker run -d --name check -p 8000:8000 mp3-check:pr
          for i in $(seq 1 20); do
            curl -sf localhost:8000/health && break; sleep 3
          done
          curl -sf localhost:8000/health | grep -q model_loaded
```

보호 규칙의 required checks에 container-check를 추가하면 — 지난주의 그 포트 병은 이제
**PR 단계에서** 빨간불입니다. 소요 +2분 (gha 캐시 공유 덕에). 같은 요령으로 팀의 다음 개선
후보를 백로그로: compose 통합 테스트, 시크릿 값 기반 검사(125 Q3), 배포 알림.

### Step 5. 주간 퀴즈 (8교시)

주간 퀴즈 23. 그리고 다음 주 예고 — 파이프라인은 코드를 나릅니다. 그런데 우리 서비스에는
코드가 아닌 화물이 있습니다: **데이터와 모델** (CI에서 만난 45MB의 임시방편을 기억하세요).
다음 주, 그 화물의 Git을 만듭니다.

### 오늘 새로 나오는 실수

### 빨간 main의 방치

**증상** — "그 실패는 플레이키(가끔 실패)라서요" — 2주 뒤 진짜 버그도 같은 이유로 무시됨.
**원인** — 신호의 신뢰도 관리 실패 — 한 번 무시가 허용되면 신호 전체가 소음화.
**해결** — ③의 규칙(15분 내 fix/revert 판단) + 플레이키 테스트는 무시가 아니라 **격리·수리
이슈화**. 뱃지가 빨간 포트폴리오는 없느니만 못합니다.

### 금요일 18시의 병합

**증상** — 퇴근 직전 병합 → 자동 배포 → 주말 내내 아무도 모르는 장애.
**원인** — "배포 = 코드가 나가는 사건"이라는 감각 부족 — 자동화가 배포의 무게를 잊게 만듦.
**해결** — 자동 배포 팀의 관례를 하나 고르세요: 지켜볼 수 있는 시간에만 병합, 또는 배포
시간창 설정(워크플로 조건), 또는 최소한 배포 알림+당번. 자동화는 책임을 없애는 게 아니라
**책임의 형태를 바꿉니다** (버튼 누르기 → 신호 감시).

### 파이프라인 개선의 무기한 연기

**증상** — "돌아가니까 건드리지 말자" — 6개월 뒤 CI 12분, 아무도 이유를 모름.
**원인** — 파이프라인을 완성품으로 취급 — 코드처럼 부채가 쌓이는 대상인데.
**해결** — 오늘의 Step 4를 관례화: **배포 실패 1건 = 그물 개선 1건** (사후 리뷰의 산출물로).
그리고 분기마다 속도 축 재측정 — 피드백 시간은 방치하면 늘기만 합니다.

## ⑥ 확인 문제

**Q1.** Step 3에서 "짝은 내 서버 계정이 없는데 내 운영을 바꿨다"는 사실이 보안상 후퇴가 아니라
전진인 이유를, W23의 접근 모델과 비교해 논하세요.

<details>
<summary>답 보기</summary>

W23 모델에서 협업자가 배포하려면 서버 계정·SSH 키를 줘야 했습니다 — 그 계정은 배포 외의 일도
할 수 있고(셸이므로), 회수·감사도 사람 일입니다. 지금 모델에서 짝이 가진 것은 저장소 권한뿐이고,
운영에 닿는 유일한 경로가 게이트(리뷰 포함 — **내가** 승인해야 통과)입니다. 모든 변경이 PR·
커밋·이력으로 남아 감사 가능하고, 권한 회수는 저장소에서 클릭 한 번입니다. 접근이 "기계에 대한
셸"에서 "**변경에 대한 절차**"로 승격된 것 — 자동화가 만든 보안 전진입니다. (그 대신 게이트
자체와 러너가 새 요새가 되므로 127·129의 규율이 필수 전제입니다.)

</details>

**Q2.** 다섯 축 중 "속도"가 나머지 축들의 성패에 영향을 주는 메커니즘을 두 가지 이상 쓰세요.

<details>
<summary>답 보기</summary>

① 피드백이 느리면 개발자가 검증을 우회하고 싶어집니다 — "급해서 로컬에서만 확인하고 병합
승인 부탁" 문화가 게이트(신뢰 축)를 침식합니다. ② PR당 대기가 길면 PR을 크게 만들게 되고
(모아서 한 번에), 큰 PR은 리뷰 품질(관문3)과 실패 시 원인 좁히기(안전 축)를 악화시킵니다.
③ 빨간불 수리 루프(수정→push→대기)가 느리면 초록 유지 문화가 무너집니다. 속도는 편의가
아니라 다른 모든 규율의 유지 비용을 정하는 변수입니다 — 캐시(126·128)에 시간을 쓴 이유.

</details>

**Q3.** "배포 실패 1건 = 그물 개선 1건" 규칙을 이번 주의 실제 사례 두 건(모델 부재 126,
포트 계약 129)에 적용해, 각 병 → 당겨진 그물 → 재발 시 잡히는 지점을 표로 정리하세요.

<details>
<summary>답 보기</summary>

| 병 | 원래 발견 지점 | 개선(당긴 그물) | 재발 시 잡히는 곳 |
|---|---|---|---|
| 모델 부재 (저장소 비자립) | CI 첫 실행의 빨간불 | 모델을 저장소에 포함 (임시) → W27 DVC로 정식 봉인 | PR 단계 test job |
| 컨테이너 포트 계약 위반 | 배포 스모크 → 자동 롤백 | container-check job (오늘 Step 4) | PR 단계, 병합 전 |

패턴: 병은 가장 늦은 그물에서 처음 발견되고, 개선은 그것을 검사 가능한 형태로 정의해 앞
그물에 심는 것 — 파이프라인은 이렇게 사고 이력을 먹으며 촘촘해집니다.

</details>

## 주간 퀴즈 23 — W26 (CI/CD)

<details>
<summary>1. CI의 핵심 두 요소와, 러너가 "빈 방"인 것의 가치는?</summary>

자주 통합 + 자동 검증. 빈 방이라 "저장소만으로 프로젝트가 서는가"가 push마다 검증됨 — 내 컴퓨터에선 되는데의 소멸 지점.

</details>

<details>
<summary>2. 린트와 포맷의 차이, 그리고 도구에 위임하는 진짜 목적은?</summary>

린트=버그 냄새 검출(check), 포맷=모양 통일(format). 목적은 스타일 논쟁 소거로 사람 리뷰를 설계·경계조건 판단으로 승격시키는 것.

</details>

<details>
<summary>3. 커버리지의 올바른 사용법과 목표화의 부작용은?</summary>

Missing 열(안 밟은 경로)을 비추는 손전등으로 — 위험도와 결합해 해석. 목표 수치화하면 assert 없는 테스트가 양산됨(굿하트).

</details>

<details>
<summary>4. 브랜치 보호 규칙 4종 세트는?</summary>

PR 필수(직접 push 차단) · 승인 1+ · required status checks(test·lint) · force push 금지. Include administrators까지 켜야 예외 없음.

</details>

<details>
<summary>5. 검증(ci.yml)과 생산(build.yml)을 나누고 생산에 브랜치 필터를 거는 이유는?</summary>

이미지는 게이트 통과분(main)에서만 태어나야 "창고의 모든 이미지 = 검증된 커밋의 산물"이 성립. 필터 없으면 미검증 이미지가 latest를 오염.

</details>

<details>
<summary>6. GITHUB_TOKEN이 PAT보다 나은 세 가지는?</summary>

실행 동안만 유효(수명) · 저장소+선언 권한으로 제한(범위) · 발급·폐기 자동(관리 부담 0). 필요한 건 permissions 선언뿐.

</details>

<details>
<summary>7. sha 태그가 "배포·롤백·조사의 언어"인 이유는?</summary>

불변이며 커밋과 1:1 — 이미지 이름만으로 코드·PR·작성자를 역추적 가능. latest는 가변이라 상태 기록·롤백 대상이 될 수 없음.

</details>

<details>
<summary>8. 스모크 테스트가 CI 테스트와 다른 점과 최소 구성은?</summary>

실제 운영 구성(nginx 경유·실 DB·실 모델)에서 배포 직후 실행 — CI가 못 보는 계약(포트·설정·프록시)을 검증. 최소: 헬스 200 + 대표 예측 1건 대조.

</details>

<details>
<summary>9. 자동 롤백에 성공해도 배포 워크플로를 실패로 끝내는 이유는?</summary>

롤백은 서비스 회복이지 배포 성공이 아님 — 초록이면 "배포 불가능한 커밋"이 통지되지 않고 main이 오염된 채 남음. 가용성은 자동으로, 문제는 시끄럽게.

</details>

<details>
<summary>10. self-hosted runner의 보안 수칙 두 가지는?</summary>

비공개 저장소에서만(외부 PR 코드가 내 서버에서 실행되는 문 차단) · 서비스 계정(deploy)으로 실행(러너 권한 = 워크플로 권한 — 최소 권한).

</details>

## 오늘의 정리

- 파이프라인이 지도 한 장과 다섯 축 점검표를 갖게 됐고, 짝의 커밋이 관문 넷을 지나 **내
  서버에 스스로 도착**하는 것을 봤습니다 — 체크포인트: 커밋→반영, 사람 손 **0번**.
- 협업의 접근 모델이 바뀌었습니다 — 서버 계정이 아니라 **게이트 통과**가 운영에 닿는 길입니다.
- 배포 실패 1건 = 그물 개선 1건 — 파이프라인은 완성품이 아니라 사고를 먹고 자라는 생물입니다.
  다음 주: 코드가 아닌 화물(데이터·모델)의 버전 관리로.
