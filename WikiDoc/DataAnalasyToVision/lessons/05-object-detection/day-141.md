## ② 왜 필요한가

### 어제 본 경고는 데이터 문제가 아닙니다

```
⚠ 클래스 불균형 160.0배
⚠ val 의 'box' 이 0개
```

`box` 를 클래스에 넣기로 한 순간부터 이 결과는 정해져 있었습니다.

```
person  : 카메라만 켜면 계속 나옴          → 데이터가 저절로 쌓임
helmet  : 사람이 쓰고 있어야 나옴          → person 의 일부
box     : 택배가 오는 순간에만 나옴        → ★ 하루에 몇 번
```

**클래스를 정하는 순간, 필요한 데이터의 양과 수집 난이도가 결정됩니다.**
그것을 계산해 보지 않고 정하면, 3주 뒤에 "데이터가 없어서 못 한다"가 됩니다.

### 클래스 목록이 곧 문제 정의입니다

같은 CCTV 프로젝트인데 클래스 설계에 따라 완전히 다른 것이 됩니다.

```
설계 A:  person
  → "사람이 지나갔는가"만 알 수 있음
  → 데이터 500장이면 충분
  → 2주면 완성

설계 B:  person, person_fallen
  → "사람이 쓰러졌는가"를 알 수 있음
  → ★ 쓰러진 사람 사진을 200장 만들어야 함 (연기 촬영)
  → 데이터 수집이 프로젝트의 절반

설계 C:  person, helmet, no_helmet, vest, no_vest
  → 건설현장 안전 감시
  → ★ "안전모를 안 쓴 사람"을 어떻게 라벨링할 것인가부터 문제
  → 5클래스 × 200장 = 1,000장 이상 필요
```

> **"무엇을 검출할까"는 기술 질문이 아니라 제품 질문입니다.**
> 답을 정하려면 **"누가 이걸 왜 쓰는가"** 부터 답해야 합니다.

### 세분화의 유혹과 그 대가

처음 설계할 때 거의 모든 팀이 이렇게 합니다.

```
"기왕 하는 거 자세하게 하자"

  person → adult_male, adult_female, child, elderly
  car    → sedan, suv, truck, bus, motorcycle
  ...
```

**대가 세 가지**

| 대가 | 설명 |
|---|---|
| **데이터 폭증** | 클래스당 최소 200~300 인스턴스 × 클래스 수 |
| **라벨링 불가능** | "성인 남성 vs 여성"을 뒤에서 본 사진으로 판정 가능한가? |
| **성능 붕괴** | 헷갈리는 클래스끼리 서로를 갉아먹음 |

```
실제 사례

  클래스 2개 (person, car)         → mAP50 0.84
  클래스 8개 (세분화)               → mAP50 0.51
  ★ 같은 데이터, 같은 모델
```

### 반대로 너무 뭉치면

```
설계: object  (사람도 차도 개도 전부 하나)

→ 검출은 잘 됨
→ 그런데 "사람이 왔을 때만 알림"을 못 만듦
→ ★ 쓸모가 없음
```

**적정선을 찾는 것이 오늘의 주제입니다.**

## ③ 개념 설명

### 클래스 개수와 데이터 요구량

**경험적 기준 — 클래스당 최소 인스턴스 수**

| 목적 | 클래스당 인스턴스 | 비고 |
|---|---|---|
| 동작 확인 (수업 데모) | **100~200개** | 성능은 기대하지 않음 |
| **우리 수업 목표** | **300~500개** | 실용 최소선 |
| 실무 초기 | 1,000~2,000개 | |
| 실무 안정 | 5,000개 이상 | |

> **★ "이미지 수"가 아니라 "인스턴스(박스) 수"입니다.**
> 한 사진에 사람이 5명이면 person 인스턴스는 5개입니다.
> 사람은 사진당 여러 명이지만, 택배 상자는 사진당 1개인 경우가 많습니다.

**필요 이미지 수 계산**

```
클래스 c 의 필요 이미지 수 ≈ 목표 인스턴스 수 / 이미지당 평균 등장 수

예:
  person  목표 500  ÷  이미지당 2.5명   =  200장
  helmet  목표 300  ÷  이미지당 1.2개   =  250장
  box     목표 300  ÷  이미지당 1.0개   =  300장
                                          ─────
                            ★ 겹치는 사진을 고려해도 400~500장
```

**클래스를 하나 늘릴 때의 실제 비용**

```
클래스 +1
  → 데이터 수집    +250~400장
  → 라벨링 시간    +2~3시간
  → 학습 시간      +5~10%
  → ★ 혼동 가능성  기존 클래스와 헷갈리면 전체 성능 하락
```

### ★ 클래스를 나눌 것인가 합칠 것인가 — 판단 5문항

새 클래스를 만들려 할 때마다 이 5개를 물어보세요.

```
Q1. 이 둘을 구분해서 시스템이 다르게 동작하는가?
    → NO 면 합칩니다

Q2. 사진만 보고 사람이 100% 판정할 수 있는가?
    → NO 면 합칩니다

Q3. 각각 300개 이상의 인스턴스를 모을 수 있는가?
    → NO 면 합치거나 프로젝트에서 뺍니다

Q4. 시각적으로 명확히 다른가?
    → NO 면 모델도 못 구분합니다

Q5. 팀원 3명이 같은 사진에 같은 클래스를 붙이는가?
    → NO 면 정의가 모호한 것입니다
```

**적용 예시**

| 후보 분리 | Q1 | Q2 | Q3 | Q4 | Q5 | 결론 |
|---|---|---|---|---|---|---|
| person / person_fallen | ✓ 알림 다름 | ✓ | △ 연기 촬영 필요 | ✓ | ✓ | **분리 (단 데이터 확보 계획 필수)** |
| car / suv | ✗ 동작 같음 | △ | ✓ | △ | ✗ | **합침 → vehicle** |
| helmet / hardhat | ✗ | ✗ | — | ✗ | ✗ | **합침** |
| person / child | ✗ | ✗ 뒷모습 판정 불가 | ✗ | ✗ | ✗ | **합침** |
| box / person | ✓ | ✓ | ✓ | ✓ | ✓ | **분리** |

> **★ Q1이 가장 중요합니다.**
> "구분해서 시스템이 뭘 다르게 하는가?"에 답을 못 하면 **그 클래스는 필요 없습니다.**
> 재미로 나눈 클래스가 프로젝트를 망칩니다.

### 어려운 사례 — "없음"을 어떻게 검출하는가

```
목표: 안전모를 안 쓴 사람을 찾아내기

설계 ①  helmet / no_helmet 두 클래스
  → "no_helmet" 박스를 어디에 치는가?
  → 머리? 사람 전체?
  → ★ "없는 것"에는 박스를 칠 수 없습니다

설계 ②  person_with_helmet / person_without_helmet
  → 사람 전체에 박스. 헬멧 유무로 클래스 구분
  → ✓ 라벨링 가능
  → 단, 멀리 있는 사람은 판정 불가

설계 ③  person + helmet 두 클래스, 후처리로 판정
  → 사람 박스 안에 헬멧 박스가 있는가를 코드로 확인
  → ✓ 가장 유연 (기준을 나중에 바꿀 수 있음)
  → ★ 우리 수업 권장
```

**설계 ③의 후처리 코드**

```python
def check_helmet(persons, helmets, iou_thr=0.0):
    """사람 박스 상단 1/3 안에 헬멧 중심이 있으면 착용으로 판정"""
    result = []
    for p in persons:
        px1, py1, px2, py2 = p["voc"]
        head_bottom = py1 + (py2 - py1) / 3          # 머리 영역
        worn = any(px1 <= (h["voc"][0] + h["voc"][2]) / 2 <= px2 and
                   py1 <= (h["voc"][1] + h["voc"][3]) / 2 <= head_bottom
                   for h in helmets)
        result.append({**p, "helmet": worn})
    return result
```

> **★ "규칙으로 풀 수 있는 것은 클래스로 만들지 마세요."**
> 클래스를 늘리면 데이터가 필요하지만, 후처리 규칙은 **코드 몇 줄**입니다.
> 그리고 규칙은 **나중에 바꿀 수 있지만, 라벨은 못 바꿉니다.**

### 클래스 불균형 — 미리 예측하기

**등장 빈도로 미리 계산해 봅니다.**

```
현관 카메라 1시간 촬영 (3,600초)

  person   사람이 지나가는 시간   약 180초 (5%)   × 평균 1.5명
  box      택배가 놓여 있는 시간  약 600초 (17%)  × 1개
  helmet   ✗ 현관에 안전모는 없음
  cat      우리 집 고양이         약 900초 (25%)  × 1마리

★ 1초 간격 추출 시 예상 인스턴스
  person  270
  box     600
  cat     900
```

**이 계산이 알려 주는 것**

```
① "택배 상자가 드물다"는 직관은 틀렸습니다
   → 놓여 있는 시간은 길기 때문
   → ★ 그런데 같은 상자 사진 600장은 다양성이 0

② person 이 270개면 부족합니다
   → 촬영 시간을 늘리거나
   → ★ 사람이 지나가는 시간대를 골라 촬영
```

> **★ "인스턴스 수"와 "다양성"은 다릅니다.**
> 같은 택배 상자를 600프레임 찍으면 인스턴스는 600개지만 **실질적으로는 1개**입니다.
> [Day 145](day-145.md)의 중복 제거에서 이 문제를 다룹니다.

**불균형 대응 방법**

| 방법 | 설명 | 언제 |
|---|---|---|
| **데이터 추가 수집** | 부족한 클래스를 집중 촬영 | ★ 1순위 |
| 오버샘플링 | 부족한 클래스가 있는 이미지를 반복 사용 | 보조 |
| 증강 강화 | 부족한 클래스에 증강을 더 많이 | [Day 144](day-144.md) |
| 클래스 가중치 | 손실 함수에서 가중치 조정 | 검출에서는 효과 제한적 |
| **클래스 제거** | 도저히 안 모이면 뺀다 | ★ 정직한 선택 |

> **검출에서는 분류만큼 클래스 가중치가 잘 듣지 않습니다.**
> 배경이 대부분인 문제라서, YOLO는 이미 내부적으로 불균형을 다루고 있습니다.
> **데이터를 더 모으는 것 말고 마법은 없습니다.**

### ★ 배경(negative) 이미지

**객체가 하나도 없는 이미지를 일부러 넣습니다.**

```
왜?
  · 모델에게 "이런 것은 객체가 아니다"를 가르침
  · 오검출(FP)이 크게 줄어듦
  · 실제 CCTV 운영 시간의 대부분이 이 상태
```

**어떤 배경 이미지를 넣어야 하는가**

```
✓ 좋은 배경 이미지 — ★ "헷갈릴 만한 것"
    · 사람 그림자만 있는 장면
    · 옷걸이에 걸린 코트 (사람 모양)
    · 마네킹 · 인형
    · 사람이 지나간 직후의 빈 복도
    · 나뭇가지가 흔들리는 장면
    · 포스터에 인쇄된 사람

✗ 별 도움 안 되는 배경 이미지
    · 하늘만 찍힌 사진
    · 완전히 어두운 화면
    · 프로젝트와 무관한 장소
```

**비율**

```
권장: 전체의 5~15%

너무 적으면  →  오검출이 많음
너무 많으면  →  모델이 소극적이 됨 (아무것도 안 찾으려 함)

★ 우리 기준: 10% (500장 데이터셋이면 50장)
```

> **★ 배경 이미지는 "하드 네거티브"일수록 가치가 큽니다.**
> 이미 잘 구분하는 장면 100장보다, **오검출이 실제로 발생하는 장면 10장**이 훨씬 낫습니다.
> [Day 150](day-150.md)에서 학습된 모델의 오검출을 모아 배경 이미지로 추가하는 기법을 다룹니다.

### CCTV 상황에서 무엇을 검출할 것인가

**브레인스토밍 후보 목록**

| 분야 | 클래스 후보 | COCO에 있나 | 데이터 난이도 |
|---|---|---|---|
| **침입 감지** | person | ✓ | 쉬움 |
| 차량 감시 | car, motorcycle, truck | ✓ | 쉬움 |
| **주차 관리** | car, parking_space(빈 자리) | 부분 | 중간 |
| 번호판 | license_plate | ✗ | 중간 (개인정보 주의) |
| **택배 감시** | person, box | 부분 | 중간 |
| 반려동물 | cat, dog | ✓ | 쉬움 |
| **안전 관리** | person, helmet, vest | 부분 | 중간 |
| 쓰러짐 감지 | person_fallen | ✗ | ★ **어려움** (연기 촬영) |
| 화재/연기 | fire, smoke | ✗ | ★ **매우 어려움** |
| 매장 카운팅 | person | ✓ | 쉬움 |
| 마스크 착용 | face_mask, face_nomask | ✗ | 중간 (얼굴 = 개인정보) |
| 흡연 감지 | person, cigarette | ✗ | ★ 매우 어려움 (너무 작음) |

**난이도를 결정하는 3요소**

```
① COCO에 있는가          → 있으면 의사 라벨로 시간 절약 (Day 137)
② 우리가 촬영할 수 있는가  → 화재는 못 만듦
③ 물체가 충분히 큰가      → 담배는 20픽셀. 검출 거의 불가
```

> ⚠️ **화재·연기·쓰러짐은 매력적이지만 4주 안에 데이터를 못 모읍니다.**
> 하고 싶다면 **공개 데이터셋이 있는지 먼저 확인**하고, 없으면 다른 주제를 고르세요.
> [Day 171](day-171.md) 최종 프로젝트 기획에서 이 판단을 다시 합니다.

### 클래스 이름 규칙

```
✓ 좋은 이름
    person   helmet   box   safety_vest   fallen_person

### ① 검출 vs 후처리 분리

| 목표 | 검출로 | 후처리로 |
|---|---|---|
| **빈 자리 개수** | `car` 검출 | ★ 전체 구역 수 − 차 있는 구역 수 |

| **이중 주차** | `car` 검출 | ★ 한 구역에 차 2대 또는 구역 경계 걸침 |

**핵심 통찰**

```
주차 구역은 ★ 움직이지 않습니다

  → 카메라를 고정하면 각 구역의 화면 좌표가 고정
  → 구역을 검출할 필요가 없음

**구역 좌표 정의 (설치 1회)**

# zones.json — 카메라 설치 후 한 번만 작성
ZONES = [
    {"id": "A-01", "type": "normal",   "poly": [[120, 300], [280, 300], [300, 460], [110, 460]]},
    {"id": "A-02", "type": "normal",   "poly": [[280, 300], [440, 300], [470, 460], [300, 460]]},
    {"id": "A-03", "type": "disabled", "poly": [[440, 300], [600, 300], [640, 460], [470, 460]]},

**후처리 판정**

```python
def analyze_parking(cars, zones, occupy_thr=0.4):
    """차 박스와 구역의 겹침으로 점유 판정"""
    report = []
    for z in zones:
        overlapping = []
        for c in cars:
            ratio = poly_box_overlap_ratio(z["poly"], c["voc"])
            if ratio >= occupy_thr:
                overlapping.append((c, ratio))

        state = "empty" if not overlapping else "occupied"
        warn = None
        if len(overlapping) >= 2:
            warn = "이중 주차"                                    # ③
        if z["type"] == "disabled" and overlapping:
            warn = warn or "장애인 구역 주차"                       # ②
        report.append({"zone": z["id"], "state": state,
                       "cars": len(overlapping), "warn": warn})
    return report
```
