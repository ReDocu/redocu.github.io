### Day 31 · 창을 띄우다 — WinMain과 메시지 큐

| | |
|---|---|
| **연결 문서** | 06 별 애니메이션 — Step 0 |
| **오늘의 목표** | 내가 만든 창이 하나 뜨고, X를 누르면 정상 종료된다 |

**오전 (4h)**
- **막히는 상황**: 콘솔은 글자만 찍는다. 원 하나를 그릴 수가 없다
- Windows 프로그램의 구조 — 운영체제가 메시지를 보내고, 프로그램이 응답한다 (도해)
- Win32 데스크톱 프로젝트 생성 / 프로젝트 설정 확인 (문자 집합, 서브시스템)
- `WinMain` 의 4개 인자 (`hInstance`, `hPrevInstance`, `lpCmdLine`, `nCmdShow`)
- 윈도우 클래스 등록 (`WNDCLASS`) → 창 생성 (`CreateWindow`) → 표시 (`ShowWindow`)

**오후 (4h)**
- 메시지 루프 (`GetMessage` / `TranslateMessage` / `DispatchMessage`)
- 창 크기·제목·스타일 조정 (`WS_OVERLAPPEDWINDOW`, `AdjustWindowRect`)
- **클라이언트 영역 vs 전체 창 크기** — 800×600을 원하면 실제로는 더 크게 만들어야 한다
- 실습: 창 2개 띄우기 / 크기와 위치 바꿔 보기

**모노스페이스 도해 — 메시지 흐름**
```
   [사용자] 마우스 클릭
       ↓
   [Windows] 메시지 생성 → 우리 프로그램의 메시지 큐에 넣음
       ↓
   [WinMain] GetMessage()로 꺼냄 → DispatchMessage()
       ↓
   [WndProc] WM_LBUTTONDOWN 처리
```

**✅ 실행 결과** — 제목 표시줄에 지정한 제목이 붙은 빈 창이 하나 뜨고, X 버튼을 누르면 창과 프로세스가 함께 종료된다.

**🔧 막히면**
- 창이 안 뜸 → `ShowWindow` / `UpdateWindow` 누락, 또는 `RegisterClass` 실패
- X를 눌러도 프로세스가 안 죽음 → `WM_DESTROY`에서 `PostQuitMessage(0)` 누락
- 유니코드 오류 (`LPCWSTR` 변환) → 프로젝트 문자 집합 설정 또는 `L"문자열"` 사용

### Day 32 · WndProc — 창이 보내오는 말 알아듣기

| | |
|---|---|
| **연결 문서** | 06 별 애니메이션 — Step 1 |
| **오늘의 목표** | 키를 누르고 마우스를 클릭하면 창이 반응한다 |

**오전 (4h)**
- `WndProc` 의 구조 — `switch (message)` 와 `DefWindowProc`
- 핵심 메시지 — `WM_CREATE` / `WM_DESTROY` / `WM_PAINT` / `WM_SIZE` / `WM_CLOSE`
- 입력 메시지 — `WM_KEYDOWN` / `WM_LBUTTONDOWN` / `WM_MOUSEMOVE`
- `wParam` / `lParam` 에서 정보 꺼내기 (`LOWORD`, `HIWORD`)
- 처리하지 않은 메시지를 `DefWindowProc`에 넘겨야 하는 이유

**오후 (4h)**
- 클릭한 좌표를 제목 표시줄에 출력 (`SetWindowText`)
- 키 입력에 따라 창 제목 변경
- `MessageBox` 로 종료 확인 대화상자
- 실습: 메시지 로그를 출력 창(`OutputDebugString`)에 찍어 어떤 메시지가 언제 오는지 관찰

**✅ 실행 결과** — 창 안을 클릭하면 제목 표시줄에 클릭 좌표가 표시되고, 키를 누르면 어떤 키인지 표시된다. X를 누르면 "종료하시겠습니까?" 대화상자가 뜬다.

**🔧 막히면**
- 창이 먹통 → `default` 에서 `DefWindowProc` 반환 누락
- 좌표가 이상함 → 클라이언트 좌표와 화면 좌표 혼동
- 종료가 두 번 물어봄 → `WM_CLOSE`와 `WM_DESTROY` 처리 중복

### Day 33 · GDI — 화면에 그리기

| | |
|---|---|
| **연결 문서** | 06 별 애니메이션 — Step 2 |
| **오늘의 목표** | 창 안에 도형이 그려지고, 창을 가렸다 열어도 그대로 있다 |

**오전 (4h)**
- **막히는 상황**: 창은 떴는데 아무것도 없다. `printf`는 여기서 안 통한다
- `WM_PAINT` 와 `BeginPaint` / `EndPaint` / **HDC(디바이스 컨텍스트)** 의 개념
- 기본 도형 — `Rectangle`, `Ellipse`, `MoveToEx`+`LineTo`, `SetPixel`
- **GDI 오브젝트** — 펜(`CreatePen`)과 브러시(`CreateSolidBrush`)
- `SelectObject` / **`DeleteObject`** — 안 지우면 리소스가 샌다

**오후 (4h)**
- 텍스트 출력 (`TextOut`, `DrawText`), 폰트 만들기
- 색상 `RGB(r, g, b)` 와 배경 모드 (`SetBkMode(TRANSPARENT)`)
- **무효 영역(invalid region)** 개념 — 왜 창을 가렸다 열면 다시 그려지는가
- 실습: 별 모양을 선으로 그리는 함수 `DrawStar(hdc, x, y, size)` 작성

**모노스페이스 도해 — GDI 오브젝트 사용 패턴**
```
   HPEN pen    = CreatePen(PS_SOLID, 2, RGB(255,255,0));
   HPEN oldPen = (HPEN)SelectObject(hdc, pen);   ← 기존 것을 받아 둔다

        ... 그리기 ...

   SelectObject(hdc, oldPen);   ← 원래대로 복구
   DeleteObject(pen);           ← 반드시 삭제 (누락 = GDI 누수)
```

**✅ 실행 결과** — 창 안에 노란 별 하나와 색이 다른 사각형·원이 그려진다. 다른 창으로 가렸다가 다시 띄워도 그림이 그대로 남아 있다.

**🔧 막히면**
- 창을 가렸다 열면 그림이 사라짐 → `WM_PAINT` 밖에서 그렸음. 그리기는 `WM_PAINT` 안에서
- 오래 쓰면 그림이 안 그려짐 → `DeleteObject` 누락으로 GDI 핸들 고갈
- `BeginPaint` 없이 `GetDC` 사용 후 `ReleaseDC` 누락 → 리소스 누수

### Day 34 · 2D 좌표계와 타이머 — 스스로 움직이게

| | |
|---|---|
| **연결 문서** | 06 별 애니메이션 — Step 3 |
| **오늘의 목표** | 별 하나가 저절로 화면을 가로질러 움직인다 |

**오전 (4h)**
- **화면 좌표계** — 원점은 좌상단, **y는 아래로 증가** (수학 좌표계와의 차이를 못 박는다)
- 좌표 변환 감각 — 중심 기준으로 그리려면 어떻게 계산하나
- `SetTimer` / `WM_TIMER` / `KillTimer`
- **`InvalidateRect`** — "여기 다시 그려 주세요"라고 요청하기. 안 하면 화면이 갱신되지 않는다
- 별 좌표를 타이머마다 갱신 → 무효화 → `WM_PAINT`에서 새 위치에 그리기

**모노스페이스 도해**
```
   수학 좌표계               화면(클라이언트) 좌표계
        y↑                    (0,0)────────────────▶ x
         │                      │
         │                      │       ★ (120, 80)
   ──────┼──────▶ x             │
         │                      ▼ y        ← y가 아래로 증가

   타이머 흐름:
   WM_TIMER → 좌표 갱신 → InvalidateRect → WM_PAINT → 다시 그림
      ▲                                                  │
      └──────────────── 다음 타이머 ─────────────────────┘
```

**오후 (4h)**
- 화면 밖으로 나간 별을 반대편에서 다시 등장시키기 (래핑)
- 타이머 간격을 바꿔 가며 속도 체감 (`SetTimer(hWnd, 1, 16, NULL)` ≈ 60FPS)
- **타이머의 한계 언급** — 정확도가 낮고 게임 루프로는 부적합 (Week 8 복선)
- 실습: 좌우로 왕복하는 별, 원운동하는 별

**✅ 실행 결과** — 별이 왼쪽에서 오른쪽으로 부드럽게 흘러가고, 화면 끝에 닿으면 반대편에서 다시 나온다.

**🔧 막히면**
- 움직이지 않음 → `InvalidateRect` 호출 누락 (가장 흔함)
- 좌표는 바뀌는데 화면이 그대로 → `WM_PAINT`에서 옛 좌표 변수를 참조
- 너무 느림/빠름 → 타이머 간격과 이동량 조절

### Day 36 · 깜빡임의 정체

| | |
|---|---|
| **연결 문서** | 07 프레임워크 제작 — Step 0 |
| **오늘의 목표** | 깜빡임이 왜 생기는지 코드로 재현하고 설명할 수 있다 |

**오전 (4h)**
- 어제 관찰한 깜빡임의 원인 규명
- `WM_PAINT` 직전에 `WM_ERASEBKGND`가 **배경을 흰색으로 지운다** → 그 순간이 눈에 보인다
- 실험 ① 배경 지우기를 막아 본다 (`WM_ERASEBKGND`에서 `return TRUE`) → **깜빡임은 줄지만 잔상이 남는다**
- 실험 ② 별을 1개만 그려 본다 → 깜빡임이 덜하다. 그리는 양이 많을수록 심해진다
- 결론 — **문제는 "중간 과정이 화면에 보이는 것"이다**

**모노스페이스 도해**
```
   [지금]  사용자가 중간 과정을 본다

   프레임 N   :  배경 지움 ──▶ (흰 화면!) ──▶ 별 500개 그림 ──▶ 완성
                                 ▲
                                 └─ 이 순간이 눈에 보인다 = 깜빡임

   그리는 양이 많을수록 "흰 화면" 구간이 길어진다 → 더 심해진다
```

**오후 (4h)**
- 해결의 방향 — "중간 과정을 안 보이게 하려면?" → **다른 곳에서 다 그리고, 완성본만 옮긴다**
- 메모리 DC(Device Context)의 개념 — 화면이 아닌 메모리 위의 도화지
- `CreateCompatibleDC` / `CreateCompatibleBitmap` 소개
- `BitBlt` — 화면 간 픽셀 복사
- 내일의 설계도를 종이에 그려 보기

**✅ 실행 결과** — `WM_ERASEBKGND` 토글, 별 개수 조절로 **깜빡임 정도를 마음대로 바꿔서 시연**할 수 있다. 원인을 한 문장으로 설명할 수 있다.

**🔧 막히면**
- 실험 ①에서 잔상이 안 남음 → 이전 프레임을 지우는 다른 코드가 있는지 확인
- 개념이 안 잡힘 → "그림을 그리는 중인 캔버스를 관객에게 보여주지 말자"로 비유

### Day 37 · 더블버퍼링 구현 ★

| | |
|---|---|
| **연결 문서** | 07 프레임워크 제작 — Step 1 |
| **오늘의 목표** | 깜빡임이 완전히 사라지고 별 500개가 매끄럽게 흐른다 |

**오전 (4h)**
- **백버퍼 만들기** — `CreateCompatibleDC(hdc)` + `CreateCompatibleBitmap(hdc, w, h)` + `SelectObject`
- 백버퍼 초기화 (`PatBlt` 또는 `FillRect`로 배경색 채우기)
- 모든 그리기를 백버퍼 DC에 수행
- **`BitBlt(hdc, 0, 0, w, h, backDC, 0, 0, SRCCOPY)`** — 완성본을 한 번에 화면으로
- `WM_ERASEBKGND`에서 `return TRUE` (배경 지우기 차단)

**모노스페이스 도해**
```
   [단일 버퍼]                          [더블 버퍼]

    화면 지움 ─▶ (흰 화면!) ─▶ 그림      백버퍼 지움 ─┐
        ▲ 깜빡임                        백버퍼에 그림 ─┤
                                                       └─ BitBlt 한 번 ─▶ 화면
                                                          (사용자는 완성본만 본다)

   HDC     backDC = CreateCompatibleDC(hdc);
   HBITMAP backBmp = CreateCompatibleBitmap(hdc, W, H);
   HBITMAP oldBmp = (HBITMAP)SelectObject(backDC, backBmp);
   ...
   SelectObject(backDC, oldBmp);
   DeleteObject(backBmp);  DeleteDC(backDC);   ← 정리 필수
```

**오후 (4h)**
- 백버퍼 생성 위치 정하기 — 매 프레임 만들면 느리다. `WM_CREATE`에서 한 번 만들고 재사용
- `WM_SIZE`에서 백버퍼 재생성 처리
- 리소스 해제 (`WM_DESTROY`) — DC와 비트맵 모두
- **비교 시연 준비** — `#define USE_DOUBLE_BUFFER` 토글 하나로 켜고 끄기
- 실습: 별 개수를 2000개로 올려도 깜빡이지 않는지 확인

**✅ 실행 결과** — 깜빡임이 **완전히** 사라진다. 별 2000개를 그려도 화면이 매끄럽다. 토글을 끄면 즉시 깜빡임이 돌아온다.

**🔧 막히면**
- 화면이 검게만 나옴 → 백버퍼 초기화(배경 채우기) 누락, 또는 `BitBlt` 인자 순서 오류
- 시간이 지날수록 느려짐 → 매 프레임 백버퍼를 새로 만들고 있음
- 창 크기 조절 시 깨짐 → `WM_SIZE`에서 백버퍼 재생성 미처리
- 여전히 깜빡임 → `WM_ERASEBKGND` 차단 누락

### Day 38 · 게임 루프 분리와 델타 타임

| | |
|---|---|
| **연결 문서** | 07 프레임워크 제작 — Step 2 |
| **오늘의 목표** | 창을 드래그하는 중에도 게임이 멈추지 않고, PC가 달라도 속도가 같다 |

**오전 (4h)**
- **막히는 상황 ①**: `GetMessage`는 메시지가 없으면 **거기서 멈춰 선다**. 게임은 계속 돌아야 한다
- **`PeekMessage`** — 메시지가 없으면 바로 반환. 그 틈에 게임을 갱신한다
- 게임 루프 재구성 (Day 21의 콘솔 게임 루프와 같은 구조임을 확인)
- 타이머(`WM_TIMER`) 방식 폐기 — 정확도와 제어권 문제

**모노스페이스 도해 — 메시지 루프 vs 게임 루프**
```
   [Day 31 방식 · GetMessage]          [오늘 방식 · PeekMessage]

   while (GetMessage(&msg,...))        while (running) {
   {                                     if (PeekMessage(&msg,...,PM_REMOVE)) {
     TranslateMessage(&msg);               if (msg.message == WM_QUIT) break;
     DispatchMessage(&msg);                TranslateMessage(&msg);
   }                                       DispatchMessage(&msg);
   ▲ 메시지가 없으면 여기서 대기          } else {
     → 게임이 멈춘다                        Update(dt);      ← 메시지 없을 때
                                            Render();          게임을 돌린다
                                          }
                                        }
```

**오후 (4h)**
- **막히는 상황 ②**: 빠른 PC에서는 별이 순간이동하고 느린 PC에서는 기어간다
- **델타 타임(dt)** — "지난 프레임 이후 흐른 시간"만큼 움직인다
- `QueryPerformanceCounter` / `QueryPerformanceFrequency` 로 고정밀 시간 측정
- `x += speed * dt` 로 전환 (`x += speed` 를 버린다)
- FPS 계산과 표시 / 프레임 상한 처리
- 실습: 일부러 무거운 연산을 넣어 FPS를 떨어뜨려도 별의 **이동 속도가 같은지** 확인

**✅ 실행 결과** — 창을 마우스로 드래그하는 동안에도 별이 계속 흐른다. FPS가 60에서 20으로 떨어져도 별이 화면을 건너는 데 걸리는 **실제 시간은 동일**하다.

**🔧 막히면**
- CPU 100% → `Sleep(1)` 또는 프레임 상한 처리 추가
- 창을 옮기면 게임이 튐 → 창 이동 중 누적된 큰 `dt` 처리 (최대값으로 클램프)
- 종료가 안 됨 → `WM_QUIT` 처리 후 루프 탈출 누락

### Day 39 · 엔진 골격 클래스화

| | |
|---|---|
| **연결 문서** | 07 프레임워크 제작 — Step 3 |
| **오늘의 목표** | 별 데모가 프레임워크 위에서 그대로 돌고, `main`은 5줄이다 |

**오전 (4h)**
- **막히는 상황**: `WinMain`이 300줄이 됐다. 다음 게임을 만들면 이걸 또 복붙해야 한다
- 재사용 가능한 부분(창 생성, 루프, 버퍼)과 게임마다 다른 부분(별의 로직) 구분
- **`Core` 클래스** — `Init()` / `Run()` / `Update(dt)` / `Render()` / `Release()`
- **`Timer` 클래스** — 델타 타임과 FPS 관리
- **`Device` / `Renderer`** — 백버퍼와 그리기 도구 관리

**모노스페이스 도해 — 프레임워크 구조**
```
   ┌──────────────────────────────────────────────────┐
   │ Core                                              │
   │  ├─ Init()      창 생성, 백버퍼 준비, 리소스 로드 │
   │  ├─ Run()       ┌──────────────────────────┐      │
   │  │              │ while(running)            │      │
   │  │              │   PeekMessage / Dispatch  │      │
   │  │              │   dt = Timer::Update()    │      │
   │  │              │   Update(dt)              │      │
   │  │              │   Render()                │      │
   │  │              └──────────────────────────┘      │
   │  └─ Release()   역순으로 정리                     │
   └──────────────────────────────────────────────────┘
       │            │             │
     Timer      Renderer      Scene (게임마다 교체되는 부분)
```

**오후 (4h)**
- `Init`/`Release`의 **역순 정리 원칙** — 나중에 만든 것을 먼저 지운다
- 헤더 정리 및 프로젝트 구조 (`Engine/` `Game/` 폴더 분리)
- **별 데모를 프레임워크 위로 이식** — 화면 결과는 Day 37과 동일해야 한다
- 실습: `WinMain`을 `Core core; core.Init(); core.Run(); core.Release();` 만으로 만들기

**✅ 실행 결과** — Day 37과 화면이 **완전히 동일**한 별 데모가, `WinMain`은 5줄인 상태로 돌아간다.

**🔧 막히면**
- 링크 오류 다수 → 헤더/구현 분리 시 정의 누락. 전역 `WndProc`를 클래스 멤버로 만들려다 나는 오류는 `static` + 인스턴스 포인터 패턴으로 해결
- 종료 시 크래시 → 해제 순서 오류 (Release를 역순으로)
- 창은 뜨는데 아무것도 안 그려짐 → `Render`가 루프에 연결되지 않음

### Day 42 · 스프라이트 시트 분할

| | |
|---|---|
| **연결 문서** | 08 격투게임 — Step 1 |
| **오늘의 목표** | 한 장의 시트에서 원하는 프레임 한 컷만 골라서 그려진다 |

**모노스페이스 도해**
```
   스프라이트 시트 (4열 × 3행, 프레임 크기 64×64)

    idx 0   1   2   3
       ┌───┬───┬───┬───┐
     0 │ 0 │ 1 │ 2 │ 3 │      srcX = (idx % 열수) * 프레임폭
       ├───┼───┼───┼───┤      srcY = (idx / 열수) * 프레임높이

     2 │ 8 │ 9 │10 │11 │              srcY = (6/4)*64 = 64
       └───┴───┴───┴───┘
```

**🔧 막히면**

### Day 44 · 입력 처리와 이동·점프

### Day 46 · 유한 상태 머신 (FSM)

| | |
|---|---|
| **연결 문서** | 08 격투게임 — Step 5 |
| **오늘의 목표** | 공격 중에는 방향키를 눌러도 움직이지 않는다 |

**오전 (4h)**
- **막히는 상황**: 공격 중에 점프하고, 맞는 중에 공격하고, 캐릭터가 통제 불능이다
- **유한 상태 머신** — 상태는 하나뿐이고, 정해진 경로로만 이동한다
- `enum class State` + 현재 상태 변수 하나로 통합 (여러 `bool` 폐기)
- 상태 진입(`Enter`) / 유지(`Update`) / 이탈(`Exit`) 구조
- 전이 규칙을 데이터(표)로 관리하기

**모노스페이스 도해 — 상태 전이표**
```
   현재 상태 \ 입력   ←→ 이동   ↑점프    공격키     피격
   ─────────────────────────────────────────────────────
   IDLE               WALK     JUMP     ATTACK     HIT
   WALK               WALK     JUMP     ATTACK     HIT
   JUMP                -        -       JUMP_ATK   HIT
   FALL                -        -       JUMP_ATK   HIT
   ATTACK              -        -         -        HIT     ← 공격 중 이동 불가
   HIT                 -        -         -         -      ← 경직 중 입력 무시
   DOWN                -        -         -         -      ← 쓰러짐, 기상까지 대기

   '-' = 전이 없음 (입력 무시)
```

**오후 (4h)**
- 전이 함수 `ChangeState(newState)` — 애니메이션 전환도 여기서 일괄 처리
- 애니메이션 종료 시 자동 복귀 (ATTACK 끝 → IDLE)
- 상태별 이동 가능 여부 / 중력 적용 여부 플래그
- 실습: 앉기(CROUCH) 상태 추가 — **상태 하나만 늘리면 되는지 확인**

**✅ 실행 결과** — 공격 키를 누르면 공격 모션이 끝날 때까지 방향키를 눌러도 캐릭터가 움직이지 않고, 모션이 끝나면 대기로 돌아온다. 디버그 표시의 상태 이름이 표와 정확히 일치한다.

**🔧 막히면**
- 공격이 끊김 → 매 프레임 상태를 IDLE로 되돌리는 코드가 남아 있음
- 전이가 안 됨 → 전이표에 해당 칸이 비어 있는지 확인 (설계 문제일 수 있음)
- 애니메이션과 상태가 어긋남 → `ChangeState`에서 애니메이션 전환을 함께 하지 않음

### Day 47 · 판정 박스 — hitbox와 hurtbox

| | |
|---|---|
| **연결 문서** | 08 격투게임 — Step 6 |
| **오늘의 목표** | 디버그 모드에서 공격 판정과 피격 판정 박스가 보이고, 겹치면 판정이 난다 |

**오전 (4h)**
- **막히는 상황**: 스프라이트가 겹치기만 하면 맞은 걸로 처리했더니, 팔을 뻗지도 않았는데 맞는다
- **hurtbox** (맞는 부위) 와 **hitbox** (때리는 부위) 분리
- 스프라이트 크기 ≠ 판정 크기 — 판정은 별도 데이터다
- 프레임별 판정 박스 — 공격 모션의 특정 프레임에서만 hitbox가 활성화된다

**모노스페이스 도해**
```
        캐릭터 A (공격 중)              캐릭터 B (대기)

        ┌───────┐                          ┌───────┐
        │ ┌───┐ │  hurtbox (파랑)          │ ┌───┐ │
        │ │몸 │ │███  hitbox (빨강)        │ │몸 │ │
        │ └───┘ │  ▲                       │ └───┘ │
        └───────┘  │                       └───────┘
                   └── A.hitbox 와 B.hurtbox 가 겹치면 → 히트

   판정 프레임:  0    1    2    3    4    5
   hitbox 활성:  X    X    O    O    X    X   ← 3~4프레임에만 나온다
```

- AABB 판정 재사용 (Day 24)
- 디버그 렌더 — 박스를 반투명/외곽선으로 그리기

**오후 (4h)**
- 판정 데이터를 애니메이션 프레임 데이터에 포함시키기
- 한 번의 공격이 여러 번 히트하는 문제 → **히트 기록(이번 공격에 이미 맞았는가)** 관리
- 방향 반전 시 판정 박스도 함께 반전
- 실습: 강공격 / 약공격의 판정 크기·발생 프레임 차이 만들기

**✅ 실행 결과** — F1 키로 디버그 모드를 켜면 파란 hurtbox와 빨간 hitbox가 보인다. 공격 모션의 3~4프레임에서만 빨간 박스가 나타나고, 그것이 상대 파란 박스와 겹칠 때만 "HIT" 로그가 한 번 출력된다.

**🔧 막히면**
- 한 번 공격에 여러 번 맞음 → 히트 기록 미구현
- 반전 시 판정이 반대쪽에 생김 → 반전 시 박스 x좌표 미러링 누락
- 항상 맞음 → hitbox 활성 프레임 조건 미적용

         [●]  [●]  [○]  [●]  [○]  [○]  [○]  [○]      ● 활성  ○ 비활성

   [화면밖] 해당 칸을 끈다 (idx 0 → ○)      ────▶ delete 없음
   [꽉 참]  이번 프레임 발사를 무시           ────▶ 풀 크기 = 성능 상한
```

**오후 (4h)**
- 템플릿으로 범용 풀 만들기 (`ObjectPool<T>`)
- 총알 / 적 / 이펙트에 각각 적용
- 성능 재측정 — 어제의 표에 "풀링" 열 추가
- 실습: 풀 크기를 바꿔 가며 한계 관찰

**표 — 성능 비교**

| 동시 총알 수 | new/delete | **오브젝트 풀** |
|:--:|:--:|:--:|
| 50 | 60 FPS | 60 FPS |
| 300 | 48 FPS | 60 FPS |
| 1000 | 21 FPS | **59 FPS** |

**✅ 실행 결과** — 어제와 동일하게 연사해도 FPS가 60을 유지한다. 화면에 "활성 총알 수 / 풀 크기"가 실시간 표시되며 숫자가 오르내린다.

**🔧 막히면**
- 총알이 안 나감 → 풀이 꽉 찼는데 회수가 안 됨 (화면 밖 판정 확인)
- 이전 총알의 값이 남음 → 풀에서 꺼낼 때 `Reset()` 으로 초기화 필요
- 여전히 느림 → 풀은 만들었는데 내부에서 여전히 `new` 호출

            나중에 일괄 삭제
```

**모노스페이스 도해 — 그리드 좌표 변환**
```
   타일 크기 32×32

   픽셀 (mouseX, mouseY) = (100, 70)

     tileX = 100 / 32 = 3
     tileY =  70 / 32 = 2      → map[2][3]

   역변환 (타일 → 픽셀, 그릴 때)
     drawX = tileX * 32 = 96

   ┌────┬────┬────┬────┐
   │0,0 │1,0 │2,0 │3,0 │
   ├────┼────┼────┼────┤
   │0,1 │1,1 │2,1 │3,1 │
   ├────┼────┼────┼────┤
   │0,2 │1,2 │2,2 │▓▓▓▓│ ← (3,2) 하이라이트
   └────┴────┴────┴────┘
```

- 실습: 맵 크기 100×100에서 스크롤하며 타일 하이라이트 확인

**✅ 실행 결과** — 마우스를 움직이면 커서 아래 타일이 노란 테두리로 강조되고, 좌상단에 해당 타일 좌표가 표시된다. 스크롤해도 정확히 맞는다.

### Day 58 · 아이소메트릭 좌표 변환 ★

| | |
|---|---|
| **연결 문서** | 10 맵툴 제작 — Step 3 |
| **오늘의 목표** | 쿼터뷰 격자에서도 클릭한 타일이 정확히 잡힌다 |

**오전 (4h)**
- **막히는 상황**: 쿼터뷰(아이소메트릭)는 사각 격자가 아니다. `x/32` 로는 계산이 안 된다
- 아이소메트릭 타일의 형태 — 다이아몬드, 폭:높이 = 2:1
- **정변환** (그리드 → 화면) 유도

**모노스페이스 도해 — 아이소메트릭 변환** (PRD 6절 예시)
```
  그리드 좌표 (x, y)          화면 좌표 (screenX, screenY)
                                        (0,0)
   (0,0) (1,0) (2,0)                     ◆
   (0,1) (1,1) (2,1)      →           ◆     ◆
   (0,2) (1,2) (2,2)               ◆     ◆     ◆

   screenX = (x - y) * (타일폭  / 2)
   screenY = (x + y) * (타일높이 / 2)
```

- 그리기 순서 — **뒤쪽(y가 작은 것)부터** 그려야 겹침이 자연스럽다
- 정변환으로 맵 렌더링

**오후 (4h)**
- **역변환** (화면 → 그리드) 유도 — 위 두 식을 연립해서 푼다
```
   x = (screenX / (타일폭/2) + screenY / (타일높이/2)) / 2
   y = (screenY / (타일높이/2) - screenX / (타일폭/2)) / 2
```
- 실수 → 정수 변환 시 `floor` 처리
- 다이아몬드 경계 정밀 판정 (마름모 내부 판정)
- 실습: 그리드 모드 ↔ 아이소메트릭 모드 토글로 같은 맵 데이터를 두 방식으로 보기

**✅ 실행 결과** — 아이소메트릭 모드에서 다이아몬드 타일 위에 마우스를 올리면 정확히 그 타일만 강조되고, 클릭하면 그 자리에 타일이 놓인다. 토글로 그리드 모드로 바꾸면 같은 데이터가 사각 격자로 보인다.

**🔧 막히면**
- 한 칸씩 어긋남 → `floor` 대신 정수 절삭 사용 (음수 구간에서 특히)
- 겹침이 이상함 → 그리기 순서를 y 오름차순으로
- 타일 경계에서 잘못 잡힘 → 사각 근사 대신 마름모 판정 적용

### Day 61 · BFS — 이동 가능 범위 칠하기

| | |
|---|---|
| **연결 문서** | 11 택틱스 게임 — Step 0~1 |
| **오늘의 목표** | 유닛 주변의 이동 가능 칸이 파랗게 칠해진다 |

**오전 (4h)**
- **막히는 상황**: "이동력 3"이라는데, 어디까지 갈 수 있는지 화면에 칠하려면?
- 맵을 **그래프**로 보기 — 타일 = 노드, 인접 타일 = 간선
- **BFS(너비 우선 탐색)** — 가까운 곳부터 물결처럼 퍼진다
- 큐(queue) 자료구조 / 방문 표시 배열
- 이동력 제한을 거리로 처리

**모노스페이스 도해 — BFS 확장 과정**
```
   이동력 3, S = 시작, # = 벽, 숫자 = 시작으로부터의 거리

   초기          1단계         2단계         3단계
   . . . . .     . . . . .     . 2 . . .     3 2 3 . .
   . . # . .     . 1 # . .     2 1 # . .     2 1 # 3 .
   . . S . .     . 1 S 1 .     2 1 0 1 2     2 1 0 1 2
   . . # . .     . 1 # . .     2 1 # . .     2 1 # 3 .
   . . . . .     . . . . .     . 2 . . .     3 2 3 . .

   거리 ≤ 3 인 칸을 파랗게 칠한다.  벽(#)은 큐에 넣지 않는다.
```

**오후 (4h)**
- 이동 범위 하이라이트 렌더링 (반투명 파란 타일)
- 다른 유닛이 서 있는 칸 처리 (아군은 통과 가능·정지 불가 / 적은 통과 불가)
- 유닛 선택 → 범위 표시 → 클릭 이동
- 실습: 이동력을 바꿔 가며 범위 변화 확인

**✅ 실행 결과** — 유닛을 클릭하면 이동력만큼의 칸이 파랗게 칠해지고, 벽 뒤로는 우회한 거리로 계산되어 칠해진다.

**🔧 막히면**
- 벽을 뚫고 칠해짐 → 큐에 넣기 전 통과 가능 판정 누락
- 무한 루프 → 방문 표시 미적용
- 대각선이 이상함 → 4방향/8방향 정책을 먼저 정할 것 (대각선은 비용이 다르다)

### Day 62 · 다익스트라 — 지형마다 다른 비용

| | |
|---|---|
| **연결 문서** | 11 택틱스 게임 — Step 2 |
| **오늘의 목표** | 숲은 2, 평지는 1의 비용이 적용되어 범위가 달라진다 |

**오전 (4h)**
- **막히는 상황**: 숲도 늪도 평지와 똑같이 한 칸이다. 지형이 의미가 없다
- BFS의 한계 — 모든 간선의 비용이 같다고 가정한다
- **다익스트라** — 비용이 다른 그래프의 최단 경로
- 우선순위 큐 (`priority_queue`) — 항상 비용이 가장 작은 노드부터
- 이동 비용 배열 (Week 12 맵 속성에서 로드)

**모노스페이스 도해 — 비용 반영**
```
   지형 비용:  . 평지=1   ♣ 숲=2   ~ 늪=3   # 벽=통과불가

   맵                  BFS(거리)          다익스트라(누적 비용)
   . ♣ ♣ .             1 1 1 1            1 3 5 6
   . ♣ S .             1 0 1              1 3 0 1
   . . # .             1 1 #              1 2 #

   이동력 3일 때:
     BFS      → 숲 너머까지 다 갈 수 있다고 표시  (틀림)
     다익스트라 → 숲 한 칸까지만 표시             (맞음)
```

**오후 (4h)**
- 다익스트라로 이동 범위 재계산
- 비용 표시 (디버그 모드에서 각 칸의 누적 비용 출력)
- BFS 결과와 나란히 비교 렌더
- 실습: 지형을 바꿔 가며 범위 변화 확인 / 비행 유닛(모든 지형 비용 1) 구현

**✅ 실행 결과** — 같은 이동력이어도 숲이 많은 방향으로는 적게, 평지 방향으로는 멀리 범위가 칠해진다. 디버그 모드에서 각 칸의 누적 비용 숫자가 보인다.

**🔧 막히면**
- 결과가 BFS와 같음 → 이동 비용이 전부 1로 로드됨 (맵 속성 확인)
- 최단 비용이 아님 → 이미 확정된 노드를 다시 갱신 중. 방문 확정 처리 확인
- 우선순위 큐 정렬 방향 오류 → 최소 힙이 되도록 비교자 확인

### Day 63 · A* — 목표를 알면 덜 뒤져도 된다 ★

| | |
|---|---|
| **연결 문서** | 11 택틱스 게임 — Step 3 |
| **오늘의 목표** | 같은 경로를 찾으면서 탐색 노드 수가 다익스트라보다 확연히 적다 |

**오전 (4h)**
- **막히는 상황**: 맵이 100×100이 되니 다익스트라가 사방으로 다 퍼져 느리다
- **A\*** — "목표 쪽으로 갈 것 같은 노드를 먼저 본다"
- `f = g + h` — `g`는 시작부터의 실제 비용, `h`는 목표까지의 **추정** 비용
- **휴리스틱(h)** — 맨해튼 거리 / 유클리드 거리 / 대각선 거리
- 휴리스틱이 실제 비용을 넘지 않아야 최단 경로가 보장된다 (admissible)

**표 — A\* 오픈/클로즈 리스트 추적** (PRD 6절 권장 표현)

| 단계 | 확정 노드 | g | h | f | 오픈 리스트 (f 오름차순) | 클로즈 리스트 |
|:--:|:--:|:--:|:--:|:--:|---|---|
| 0 | — | — | — | — | (1,1) f=5 | — |
| 1 | (1,1) | 0 | 5 | 5 | (2,1) f=5, (1,2) f=5 | (1,1) |
| 2 | (2,1) | 1 | 4 | 5 | (1,2) f=5, (3,1) f=5, (2,2) f=7 | (1,1),(2,1) |
| 3 | (3,1) | 2 | 3 | 5 | (1,2) f=5, (4,1) f=5, … | (1,1),(2,1),(3,1) |
| … | … | … | … | … | … | … |

**오후 (4h)**
- A\* 구현 — 오픈/클로즈 리스트, `parent` 기록
- **탐색 노드 수 카운트** — 세 알고리즘 비교
- 휴리스틱 가중치를 바꿔 가며 (h×1.0 / h×2.0) 속도와 최적성의 트레이드오프 관찰
- 실습: 세 알고리즘을 키로 전환하며 탐색 영역을 시각화

**표 — 알고리즘 비교 (같은 맵, 같은 출발/도착)**

| 알고리즘 | 탐색 노드 수 | 경로 길이 | 최단 보장 |
|---|:--:|:--:|:--:|
| BFS | 412 | 18 | 비용 균일할 때만 |
| 다익스트라 | 398 | 16 | O |
| **A\*** (h×1.0) | **97** | 16 | O |
| A\* (h×2.0) | 41 | 17 | X (근사) |

**✅ 실행 결과** — 세 알고리즘을 전환하면 탐색한 칸이 각각 다른 색으로 시각화된다. A\*는 목표 방향으로 좁게 뻗고, 다익스트라는 사방으로 퍼진다. 화면에 탐색 노드 수가 표시된다.

**🔧 막히면**
- A\*가 다익스트라와 똑같이 퍼짐 → `h`가 항상 0 (휴리스틱 미적용)
- 최단 경로가 아님 → 휴리스틱이 실제 비용을 과대평가
- 경로가 안 나옴 → `parent` 기록 누락 또는 역추적 방향 오류

### Day 66 · 각도와 발사 벡터

| | |
|---|---|
| **연결 문서** | 12 포트리스 — Step 0~1 |
| **오늘의 목표** | 각도 게이지를 조절하면 포신이 같이 돌고, 그 방향으로 포탄이 나간다 |

**오전 (4h)**
- **막히는 상황**: "45도로 쏴라"는데, 좌표는 x와 y뿐이다. 각도를 좌표로 어떻게 바꾸나
- **라디안과 도(degree)** — `<cmath>`의 삼각함수는 라디안을 쓴다 (`rad = deg * π / 180`)
- `cos`은 x 성분, `sin`은 y 성분
- **화면 y축이 아래로 증가**하므로 `vy`에 부호 반전이 필요하다

**모노스페이스 도해 — 발사 벡터**
```
   각도 θ, 힘 P

     vx =  cos(θ) * P
     vy = -sin(θ) * P     ← 화면 y는 아래가 +이므로 반전

        θ=90°
          ↑
    θ=135° ╲   ╱ θ=45°
            ╲ ╱
   θ=180° ───▲─── θ=0°      ▲ = 포대
           포신

   45도, 힘 100 → vx = 70.7,  vy = -70.7  (오른쪽 위로)
```

**오후 (4h)**
- 포신 회전 렌더 — 각도에 따라 선 또는 회전 스프라이트
- 힘(파워) 게이지 — 발사 키를 누르는 시간만큼 충전
- 각도 조절 입력 (위/아래 키)
- 실습: 각도와 힘을 화면에 표시하고, 예상 발사 방향을 선으로 미리보기

**✅ 실행 결과** — 위아래 키로 각도를 바꾸면 포신이 그 각도로 회전하고, 화면에 "각도 45° / 힘 78"이 표시된다. 발사하면 그 방향으로 포탄이 직선으로 나간다(아직 중력 없음).

**🔧 막히면**
- 방향이 위아래 반대 → `vy` 부호 반전 누락
- 각도가 이상함 → 도를 라디안으로 변환하지 않고 그대로 넣음
- 포신이 반대로 돎 → 회전 기준점(피벗)이 포신 끝에 있음. 포대 중심으로

### Day 67 · 중력과 포물선

| | |
|---|---|
| **연결 문서** | 12 포트리스 — Step 2 |
| **오늘의 목표** | 포탄이 곡선을 그리며 날아가 땅에 떨어진다 |

**오전 (4h)**
- **막히는 상황**: 직선으로만 날아가면 포격 게임이 아니다
- 중력 — 매 프레임 `vy`에 중력 가속도를 더한다
- 위치 갱신 — `x += vx * dt; y += vy * dt;`
- 델타 타임 적용의 중요성 (프레임에 따라 궤적이 달라지면 안 된다)

**모노스페이스 도해 — 포물선**
```
   매 프레임:
     vy += GRAVITY * dt      ← 중력이 vy를 계속 아래로 민다
     x  += vx * dt
     y  += vy * dt

              ·  ·  ·
          ·           ·
       ·                 ·
     ·                      ·
   ▲                          ·
  포대                          ▼ 착탄

   vy 변화:  -70 → -50 → -30 → -10 → +10 → +30 → +50  (위→정점→아래)
```

**오후 (4h)**
- 포탄 궤적 잔상 표시 (지나간 점들을 남겨 궤적 확인)
- 지형 충돌 판정 — 지형 높이 배열과 포탄 y 비교
- 착탄 판정과 폭발 처리
- 실습: 중력 값·힘 범위를 바꿔 가며 사거리 표 만들기

**표 — 각도별 사거리 (힘 100, 중력 9.8 기준)**

| 각도 | 최고 높이 | 사거리 | 비고 |
|:--:|:--:|:--:|---|
| 15° | 낮음 | 중간 | 저탄도 |
| 30° | 중간 | 김 | |
| **45°** | 높음 | **최대** | 이론상 최대 사거리 |
| 60° | 매우 높음 | 김 | 장애물 넘기기 좋음 |
| 75° | 최대 | 짧음 | 박격포형 |

**✅ 실행 결과** — 발사하면 포탄이 위로 솟았다가 곡선을 그리며 떨어져 지형에 착탄한다. 45도에서 사거리가 가장 길다.

**🔧 막히면**
- 궤적이 직선 → 중력 적용 누락, 또는 `vy` 갱신을 위치 갱신 뒤에 함
- 프레임에 따라 궤적이 다름 → 델타 타임 미적용
- 포탄이 지형을 뚫음 → 이동량이 커서 한 프레임에 지나침. 이동을 잘게 나눠 검사

### Day 68 · 지형 파괴와 알파 블렌딩

| | |
|---|---|
| **연결 문서** | 12 포트리스 — Step 3 |
| **오늘의 목표** | 착탄 지점의 땅이 원형으로 파이고, 반투명 폭발 이펙트가 보인다 |

**오전 (4h)**
- 지형 표현 방식 두 가지 — 높이 배열(간단) vs **픽셀 마스크**(자유로운 파괴)
- 픽셀 마스크 방식 — 지형 비트맵의 각 픽셀이 "있음/없음"
- 착탄 시 원형 영역을 지우기
- 파괴 후 지형 충돌 판정 갱신
- 공중에 뜬 지형 처리 (낙하 or 유지 — 게임 규칙으로 결정)

**오후 (4h)**
- **알파 블렌딩** — `AlphaBlend` (`msimg32.lib`) 와 `BLENDFUNCTION`
- 반투명 폭발 이펙트 / 페이드 인·아웃
- 알파값 애니메이션 (시간에 따라 사라지기)
- **알파 렌더 비용** — 남발하면 느려진다. 필요한 곳에만
- 실습: 폭발 반경별 이펙트 3종, 반투명 UI 패널

**모노스페이스 도해 — 지형 파괴**
```
   착탄 전                        착탄 후 (반경 R 원형 제거)

   ████████████████               ██████      ██████
   ████████████████               █████        █████
   ████████████████               ██████      ██████
   ████████████████               ████████████████

   마스크 배열에서 (cx,cy) 중심 반경 R 이내를 "없음"으로
   → (x-cx)² + (y-cy)² ≤ R² 인 픽셀
```

**✅ 실행 결과** — 포탄이 지형에 맞으면 그 자리가 원형으로 파이고, 반투명한 주황색 폭발이 커졌다가 서서히 사라진다. 파인 자리로 다음 포탄이 더 깊이 들어간다.

**🔧 막히면**
- `AlphaBlend` 링크 오류 → `msimg32.lib` 추가
- 반투명이 안 먹힘 → `BLENDFUNCTION`의 `SourceConstantAlpha` 설정 확인
- 파괴 후에도 충돌함 → 마스크 갱신 후 충돌 판정이 옛 데이터를 봄
- 심하게 느려짐 → 픽셀 단위 루프 최적화 (영향 범위만 순회)
