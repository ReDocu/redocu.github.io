## ② 왜 필요한가

셋째 날은 "개선의 날"입니다. 그런데 개선 수단마다 **기대 수익이 다르다**는 것을 우리는
이미 숫자로 알고 있습니다.

| 수단 | 이 과정에서 실측한 이득 | 오늘의 예산 |
|---|---|---|
| 특성 (새 정보) | **+0.093** ([Day 064](day-064.md)) | 오전 전체 |
| 전처리 구조 | +0.032 ([Day 063](day-063.md)) | (어제 완료) |
| 튜닝 | +0.015, 승자의 저주 위험 ([Day 062](day-062.md)) | **오후 반나절 시간박스** |

이 배분을 거꾸로 하는 것 — 아침부터 Optuna를 돌려 놓고 특성은 손도 못 대는 것 — 이
셋째 날의 대표적 파산 시나리오입니다. 그리고 오늘 저녁, 이 프로젝트에서 단 한 번뿐인
순간이 옵니다: **금고 개봉**(test 1회). 그 전까지의 모든 결정은 CV로만 내립니다.

## ③ 개념 설명

### 특성 가설은 오답 노트에서 나온다

무작위 아이디어("요일을 넣어 볼까?")보다 **모델이 틀리는 패턴**에서 출발한 가설이 명중률이
높습니다. 어제까지의 부품이 그대로 가설 공장이 됩니다.

| 오답 패턴 (어디서 보나) | 가설 |
|---|---|
| 특정 시기에 몰린 큰 잔차 ([Day 053](day-053.md) Step 5) | 그 시기를 설명할 정보가 입력에 없음 → 계절·예보 특성 |
| 특정 집단의 저성능 ([Day 069](day-069.md)) | 집단별 기저 차이 → 범주 특성·집단 통계 |
| 문턱 근처 오분류 ([Day 057](day-057.md)) | 경계 정보 부족 → 문턱 거리·변화율 특성 |

각 가설은 [Day 072](day-072.md)의 루프(예상 크기 명시 → 1변경 → run → 결론)로 처리합니다.

### 튜닝 시간박스의 규칙

1. **CV(TSS) 위에서만** — cv=5 기본값 금지 ([Day 062](day-062.md) ⑤).
2. Optuna 30회 안팎, **반나절 상한.** 그 안에 CV 표준편차를 넘는 개선이 없으면 기본값 유지.
3. best CV가 아니라 **채택 모델의 test**(오늘 저녁 1회)가 보고서 숫자입니다.

### 최종 모델 확정 절차 — 금고 개봉 의식

```
① CV 성적표 마감 (실험 대장 총정리, 승자 확정)
② 승자 구성으로 train "전체"를 재학습        ← CV 폴드 모델이 아님!
③ test를 처음이자 마지막으로 1회 평가         ← 이 숫자가 보고서의 숫자
④ 그 모델을 저장 + 재로드 검증 (train.py가 자동으로)
⑤ 이후 test를 다시 여는 개선은 없다 — 발견은 "향후 과제"로
```

②가 자주 빠집니다 — CV는 후보 **비교** 도구였으므로, 확정 후에는 갖고 있는 train 전부로
다시 학습해야 데이터를 낭비하지 않습니다.

## ④ 단계별 실습

### Step 1. 오전 — 특성 가설 3~5개 실험 (1~4교시)

예시 프로젝트의 오늘 오전 실험 대장입니다 (전부 [Day 064](day-064.md)에서 실측한 값):

```markdown
| run | 가설 (예상 크기) | 결과 (test가 아니라 시간분리 검증 기준) | 결론 |
|---|---|---|---|
| linear-time | 어제·3일평균이 +0.02 이상 | +0.006 | 기각 — 오늘 값의 재표현 |
| linear-fc | 예보 3종이 +0.05 이상 | **+0.093** | 채택 ★ 단원 최대 개선 |
| linear-fc-noise | 예보 오차에도 +0.05 유지 | 0.519→0.511 | 채택 유지 — 강건함 확인 |
```

여러분의 가설이 전부 기각이어도 괜찮습니다 — **기각 기록 자체가 실험 기록 25점의 재료**이고,
"시도했으나 효과 없음"은 보고서의 훌륭한 한 절입니다.

> 오전 내내 명심할 검문 하나: 새 특성마다 **"예측 시점에 아는 값인가?"**
> 점수가 갑자기 크게 뛰면 기뻐하기 전에 [Day 052](day-052.md)의 검문소로.

### Step 2. 오후 — 튜닝 시간박스 (5~6교시)

채택된 특성 세트 위에서 후보 2종을 튜닝합니다 ([Day 062](day-062.md)의 Optuna 코드 재사용,
MLflow nested run으로 기록). 예시 프로젝트의 결과:

```markdown
| run | 내용 | CV | 결론 |
|---|---|---|---|
| lgbm-optuna30 | LGBM 30 trial | 0.21 → 0.24 (±0.28) | 기각 — 표준편차 안 |
| linear-ridge-alpha | Ridge α 탐색 | 0.355 → 0.356 | 기각 — 기본 선형 유지 |
```

튜닝이 아무것도 못 바꿨습니다 — 실망스러운가요? 아닙니다. **"기본값이 이미 최적 근처"라는
확인**은 반나절 값어치의 정보이고, 보고서에 "튜닝 이득 없음(CV 분산 이내)을 확인"이라고
쓸 수 있게 해 줍니다. 시간박스 종료. 미련 없이 다음 단계로.

### Step 3. 저녁 — 금고 개봉 (7교시)

CV의 승자(선형 파이프라인 + 예보 특성)로 train 전체를 재학습하고, test를 **처음** 엽니다.
[Day 070](day-070.md)의 CLI가 이 의식을 그대로 수행합니다.

```powershell
python train.py --config configs/final.json
```

```
[4/6] 최종 학습과 평가
  test R² 0.519 · MAE 4.26
[6/6] 저장과 재로드 검증
  저장: models/pm25_pipeline.joblib (+schema) · 동일 예측 확인 ✓
```

**R² 0.519, MAE 4.26 — 이것이 보고서·모델 카드·발표에 들어갈 유일한 test 숫자입니다.**
CV(0.355±0.13)와 나란히 적습니다: "CV로 선택했고 test로 확인했다"가 방법론 30점의 문장입니다.
지금 이 순간 이후 test를 다시 여는 개선 실험은 없습니다. 아이디어가 남았다면
보고서의 "향후 과제"로 보냅니다.

### Step 4. 오류 분석 — 내일의 문서 재료 (8교시)

최종 모델의 오답을 세 축으로 자릅니다 ([Day 069](day-069.md)의 코드 재사용):

| 축 | 예시 프로젝트의 발견 | 어디에 쓰이나 |
|---|---|---|
| 시기별 | 4월(황사철) MAE 5.48 최약, 과소예측 -1.51 | 카드 "한계" · 발표 Q&A |
| 집단별 | 노원 나쁨재현 27% (강남 58%) | 카드 "편향" · 향후 과제 |
| 구간별 | 고농도 -5.78 과소 / 저농도 +5.25 과대 | "경보 용도 시 임계값 하향" 권고 |
| 최악 5건 | 전부 봄 에피소드 시작일 | "오늘 정보만으론 한계" 서사 |

```powershell
git add docs/experiments.md configs/final.json
git commit -m "MP2 Day3: 특성 채택(+0.093)·튜닝 기각 — 최종 test R² 0.519 (금고 1회)"
```

**오늘 퇴근 체크** — □ MLflow run 누적 10개+ □ 최종 모델 저장·검증 통과
□ test 열람 횟수 = 정확히 1 □ 오류 분석 표 완성

## ⑤ 자주 하는 실수

### 금고를 열어 보고 "한 번만 더"

**증상** — test 0.519를 보고 "0.52는 넘기고 싶은데" 특성 하나 추가 후 test 재평가.
**원인** — 그 순간부터 test는 검증 세트가 되고, 최종 숫자는 낙관 편향을 갖습니다 ([Day 052](day-052.md)·[062](day-062.md)).
**해결** — 개봉 전에 "이후 개선 금지"를 기획서에 썼습니다. 새 아이디어는 "향후 과제" 절로. 정말 중요한 발견이면 **test 구간을 새로 정의**(더 미래 데이터)해야 합니다 — 5일 프로젝트에선 불가능하므로, 즉 안 됩니다.

### CV 폴드 모델을 최종 모델로 제출

**증상** — 마지막 폴드에서 학습된 모델을 저장 — train의 1/5을 안 쓴 모델.
**원인** — CV의 목적(비교)과 최종 학습(전체 데이터 활용)을 섞었습니다.
**해결** — 확정 절차 ②: 승자 **구성**(특성·전처리·하이퍼파라미터)으로 train 전체를 재학습합니다. train.py가 하는 일이 바로 이것입니다.

### 튜닝 시간박스를 넘겨서라도 이기려 함

**증상** — "trial 100번만 더 돌리면…" — 저녁까지 Optuna, 문서·테스트는 내일로.
**원인** — 튜닝은 진행감(숫자가 움직임)을 주는 반면, 상한(+0.015 급)은 잊게 만듭니다.
**해결** — 시간박스는 알람으로 강제. 종료 시점의 결론("이득 없음"도 결론)을 기록하고 이동. 채점표에서 튜닝 자체의 배점은 0입니다 — 방법론과 기록이 배점입니다.

### 오류 분석 없이 점수만 들고 마무리로 넘어감

**증상** — 내일 모델 카드의 "한계" 칸 앞에서 백지 — "글쎄요, 대체로 잘 맞는데요?"
**원인** — 오류 분석은 오늘(모델이 확정된 직후)이 적기입니다. 내일은 문서 작성만으로도 빠듯합니다.
**해결** — Step 4의 세 축 표를 오늘 채우세요. 한계를 아는 것이 신뢰의 근거([Day 050](../02-sql-pipeline/day-050.md))라는 원칙은 MP2에서도 그대로입니다.

### "성능이 목표에 못 미쳐서" 제출을 망설임

**증상** — "베이스라인보다 겨우 +0.1인데 부끄러워요" — 범위를 뒤엎고 재시작 충동.
**원인** — MP2의 채점 기준을 다시 보세요. **절대 성능의 배점은 없습니다.** 방법론 30 + 기록 25 + 재현성 20 + 문서 15 + 발표 10.
**해결** — 개선이 작으면 작은 대로, "왜 작은지"(신호의 한계, 시도한 것들)를 분석해 보고하는 것이 만점 답안입니다.

## ⑥ 확인 문제

**Q1.** 오늘 하루의 예산 배분(오전 특성 / 오후 반나절 튜닝)의 근거가 된 실측 숫자 두 개를 대고,
이 배분이 뒤집힐 수 있는 상황을 하나 상상해 보세요.

<details>
<summary>답 보기</summary>

특성 +0.093([Day 064](day-064.md)) vs 튜닝 +0.015([Day 062](day-062.md)). 뒤집히는 상황: 도메인상 추가할
새 정보가 없고(특성 광맥 고갈) 모델이 튜닝에 민감한 계열(깊은 부스팅, 표본이 많을 때)이라면 튜닝의
한계 수익이 상대적으로 커질 수 있습니다 — 배분은 교리가 아니라 증거를 따라갑니다.

</details>

**Q2.** "CV 승자 구성으로 train 전체 재학습" 단계를 건너뛰고 CV 마지막 폴드의 모델을 제출하면
무엇을 잃나요?

<details>
<summary>답 보기</summary>

TSS 마지막 폴드의 모델은 train의 앞부분(약 5/6)로만 학습된 모델이므로, 사용할 수 있었던 최신 데이터
일부를 버린 셈입니다. 특히 시계열에서는 가장 최근 구간이 미래 예측에 제일 값진 데이터라 손실이 큽니다.
CV는 구성을 고르는 도구이고, 최종 모델은 전체 train으로 다시 굽습니다.

</details>

**Q3.** 금고 개봉 후 test 점수가 CV 추정보다 크게 낮았다면(예: CV 0.45 예상 → test 0.30),
제출 전 점검해야 할 원인 후보를 순서대로 쓰세요.

<details>
<summary>답 보기</summary>

① CV 설계가 데이터 구조와 안 맞았는가 (무작위 폴드로 부풀려진 심판 — [Day 061](day-061.md)),
② 후보 선택 과정에서 CV에 과적합했는가 (수십 후보 중 1등의 승자의 저주 — [Day 062](day-062.md)),
③ test 구간에 분포 변화가 있는가 (특정 계절·이벤트 — [Day 055](day-055.md)의 기후 배신).
어느 경우든 test를 다시 열어 고치는 게 아니라, 원인 분석을 보고서에 쓰는 것이 옳은 마무리입니다.

</details>
