## ② 왜 필요한가

채용 공고와 캐글을 조금이라도 봤다면 XGBoost·LightGBM이라는 이름을 이미 만났을 겁니다.
**정형(테이블) 데이터 대회의 우승 모델 목록은 십 년 가까이 부스팅 계열이 지배**해 왔고,
현업의 추천·신용평가·수요예측 모델의 기본기이기도 합니다. 이 계열을 못 다루면
테이블 데이터 판에서 대화가 안 됩니다.

그런데 어제 이상한 걸 봤습니다 — 그 대단하다는 트리 앙상블(포레스트 0.790)이 W07 수준의
로지스틱 회귀(0.818)를 못 이겼습니다. 오늘 부스팅까지 총출동시켜 결판을 내고,
**"어떤 판에서 누가 강한가"** 라는 진짜 엔지니어의 질문에 답합니다.

스포일러: 오늘도 로지스틱이 이깁니다. 그리고 그 이유를 이해하는 것이
부스팅 사용법 암기보다 백 배 중요합니다.

## ③ 개념 설명

### 배깅 vs 부스팅 — 병렬 평균 vs 직렬 보정

둘 다 "트리 여러 개"지만 철학이 정반대입니다.

| | 배깅 (랜덤포레스트) | 부스팅 |
|---|---|---|
| 학습 방식 | **병렬** — 각 트리가 독립적으로 학습 | **직렬** — 다음 트리가 이전까지의 **오답**을 학습 |
| 개별 트리 | 크고 제멋대로 (깊이 무제한) | 작고 약하게 (깊이 3~8) |
| 잡는 것 | 분산 (암기 노이즈 상쇄) | 편향 (덜 배운 구조를 추가 학습) |
| 나무 수 ↑ | 손해 없음 (수확 체감뿐) | **과적합 가능** — 오답 보정이 노이즈 보정으로 변질 |

```
부스팅의 한 걸음:
예측₀ = 작은 트리①          → 오차 계산
예측₁ = 예측₀ + η·트리②(오차를 학습)   → 오차 다시 계산
예측₂ = 예측₁ + η·트리③(남은 오차 학습) → …
```

η(learning_rate, 학습률)는 **보폭**입니다. 작게 하면 천천히·꼼꼼하게(나무가 더 필요),
크게 하면 빨리·거칠게. `n_estimators × learning_rate` 가 한 몸으로 움직이는 이유입니다.

### 조기 종료 — 꺾이는 순간 멈추기

부스팅은 계속 두면 train 오차 0까지 갑니다(= 노이즈까지 보정). 해법은 간단합니다 —
**검증 데이터 점수가 더 이상 좋아지지 않으면 멈춥니다.** 나무 수를 사람이 고르는 대신
데이터가 고르게 하는 것으로, 부스팅 계열의 표준 관행입니다.

### 라이브러리 지형

| 구현 | 특징 | 우리 수업에서 |
|---|---|---|
| `GradientBoostingClassifier` (sklearn 구형) | 원조. 느림. `staged_predict` 로 학습 과정 관찰 가능 | 오늘 학습 곡선 관찰용 |
| **`HistGradientBoosting…`** (sklearn 신형) | 히스토그램 방식으로 고속화, 결측 자체 처리 | sklearn만으로 될 때 |
| **XGBoost** | 2014~ 대회 평정. 규제 내장, 생태계 최대 | 실무 표준 중 하나 |
| **LightGBM** | MS제. 히스토그램+리프 우선 성장 = **가장 빠른 축** | 실무 표준 중 하나 |

셋 다 fit/predict 인터페이스는 같습니다([Day 051](day-051.md)의 위대함). 세부 파라미터 이름만 다릅니다
(`max_leaf_nodes` ↔ `num_leaves` ↔ `max_leaves` 같은 식).

### Step 1. 부스팅의 학습 과정 관찰 — 오답 공부의 명암 (1~2교시)

구형 `GradientBoostingClassifier` 의 `staged_predict_proba` 로 나무가 추가될 때마다의 점수를 봅니다.

```python
# day059_boosting.py — 그래디언트 부스팅
import time
import numpy as np
import pandas as pd
from sklearn.ensemble import GradientBoostingClassifier, HistGradientBoostingClassifier, RandomForestClassifier
from sklearn.metrics import roc_auc_score

pd.set_option("display.width", 140)
df = pd.read_csv("data/air_daily.csv", parse_dates=["date"])
F10 = ["pm10", "pm25", "o3", "no2", "co", "so2", "temp", "humidity", "wind_speed", "precip"]
d = df.dropna(subset=F10).copy()
d["bad_next"] = (d.pm25_next >= 36).astype(int)
tr = d[d.date < "2026-01-01"]; te = d[d.date >= "2026-01-01"]
Xtr, ytr, Xte, yte = tr[F10], tr.bad_next, te[F10], te.bad_next

print("== A. 부스팅은 오답을 이어서 공부한다 — 나무 수에 따른 점수 ==")
gb = GradientBoostingClassifier(random_state=42, n_estimators=500).fit(Xtr, ytr)
print("나무 수 | train AUC | test AUC")
stage_tr = list(gb.staged_predict_proba(Xtr))
stage_te = list(gb.staged_predict_proba(Xte))
for n in [1, 5, 20, 50, 100, 200, 500]:
    a_tr = roc_auc_score(ytr, stage_tr[n - 1][:, 1])
    a_te = roc_auc_score(yte, stage_te[n - 1][:, 1])
    print(f"  {n:>4}  |   {a_tr:.3f}   |  {a_te:.3f}")
```

실행 결과:

```
== A. 부스팅은 오답을 이어서 공부한다 — 나무 수에 따른 점수 ==
나무 수 | train AUC | test AUC
     1  |   0.923   |  0.658
     5  |   0.940   |  0.742
    20  |   0.956   |  0.782
    50  |   0.969   |  0.782
   100  |   0.981   |  0.791
   200  |   0.994   |  0.789
   500  |   1.000   |  0.778
```

곡선의 서사: 나무 1그루(0.658)에서 시작해 오답을 보정할수록 test가 오르다가(**100그루, 0.791**)
그 뒤로는 **내려갑니다**(500그루, 0.778). train은 1.000까지 직진하는데요.
어제 포레스트는 300그루까지 늘려도 손해가 없었지만(0.790), **부스팅에서 나무 수는
과적합 손잡이입니다** — 오답 보정이 어느 순간부터 "노이즈 외우기"로 변질되기 때문입니다.

### Step 2. 조기 종료 — 데이터가 나무 수를 고르게 하라 (3교시)

```python
print("\n== B. 조기 종료 — 검증 점수가 꺾이면 멈춘다 ==")
hgb = HistGradientBoostingClassifier(random_state=42, max_iter=1000,
                                     early_stopping=True, validation_fraction=0.15,
                                     n_iter_no_change=20)
hgb.fit(Xtr, ytr)
print(f"최대 1000회까지 허용 → 실제 멈춘 지점: {hgb.n_iter_}회")
print(f"test AUC: {roc_auc_score(yte, hgb.predict_proba(Xte)[:, 1]):.3f}")
```

실행 결과:

```
== B. 조기 종료 — 검증 점수가 꺾이면 멈춘다 ==
최대 1000회까지 허용 → 실제 멈춘 지점: 67회
test AUC: 0.793
```

train 내부에서 15%를 떼어 검증으로 삼고, 20회 연속 개선이 없자 **67회에서 스스로 멈췄습니다.**
Step 1에서 눈으로 찾던 "꺾이는 지점"을 자동화한 것입니다. 검증 데이터를 train **안에서** 떼는 것에
주목하세요 — test는 여전히 금고 안입니다([Day 052](day-052.md)).

### Step 3. 5파전 — 성능과 속도 (5교시)

```python
print("\n== C. 5파전 — 성능과 속도 ==")
from sklearn.linear_model import LogisticRegression
from sklearn.preprocessing import StandardScaler
from xgboost import XGBClassifier
from lightgbm import LGBMClassifier

sc = StandardScaler().fit(Xtr)
runs = [
    ("로지스틱", lambda: LogisticRegression(max_iter=5000).fit(sc.transform(Xtr), ytr), lambda m: m.predict_proba(sc.transform(Xte))[:, 1]),
    ("랜덤포레스트300", lambda: RandomForestClassifier(n_estimators=300, random_state=42, n_jobs=-1).fit(Xtr, ytr), lambda m: m.predict_proba(Xte)[:, 1]),
    ("HGB(sklearn)", lambda: HistGradientBoostingClassifier(random_state=42).fit(Xtr, ytr), lambda m: m.predict_proba(Xte)[:, 1]),
    ("XGBoost", lambda: XGBClassifier(random_state=42, verbosity=0, eval_metric="logloss").fit(Xtr, ytr), lambda m: m.predict_proba(Xte)[:, 1]),
    ("LightGBM", lambda: LGBMClassifier(random_state=42, verbosity=-1).fit(Xtr, ytr), lambda m: m.predict_proba(Xte)[:, 1]),
]
print(f"{'모델':<14} {'test AUC':>8} {'학습(초)':>8}")
for name, fit, prob in runs:
    t0 = time.perf_counter()
    m = fit()
    dt = time.perf_counter() - t0
    print(f"{name:<14} {roc_auc_score(yte, prob(m)):>8.3f} {dt:>8.2f}")
```

실행 결과:

```
== C. 5파전 — 성능과 속도 ==
모델             test AUC    학습(초)
로지스틱              0.818     0.01
랜덤포레스트300         0.790     0.28
HGB(sklearn)      0.787     0.16
XGBoost           0.779     0.07
LightGBM          0.797     0.06
```

커리큘럼의 질문 "부스팅 vs 포레스트"의 답: **LightGBM이 포레스트보다 조금 더 정확하고(0.797 vs
0.790) 다섯 배 빠릅니다**(0.06초 vs 0.28초). 지금은 다 1초 미만이라 시시해 보이지만, 행이 백만이
되고 [Day 062](day-062.md)에서 수백 번 재학습하게 되면 이 배율이 밥 먹는 시간을 결정합니다.

### Step 4. 그런데 왜 로지스틱을 못 이기는가 ★ (6~7교시)

오늘의 진짜 수업입니다. 대회를 평정했다는 부스팅 삼형제가 전부 **0.78~0.80** 에서 막히고,
0.01초짜리 로지스틱(0.818)이 1위입니다. 미신을 하나 부수겠습니다.

**트리 계열이 강한 판**과 **선형이 강한 판**은 다릅니다.

| 트리·부스팅이 강한 판 | 선형이 강한 판 |
|---|---|
| 문턱·구간 효과 (나이 19세 경계, 등급 컷) | 신호가 **매끈하고 단조로움** |
| 특성 간 상호작용이 지배적 | 신호가 **여러 상관 특성에 분산** — 평균 내면 노이즈 상쇄 |
| 특성이 이질적 (금액, 횟수, 코드가 뒤섞임) | 표본이 적어 복잡한 모델이 분산 손해 |

우리 데이터는 오른쪽 판입니다. 내일 농도의 신호는 pm10·pm25·no2·co·so2에 **비슷하게 퍼져**
있고(전부 오늘 대기 상태의 노이즈 낀 복사본), 선형 모델은 이 다섯을 **가중 평균해 노이즈를
지웁니다.** 트리는 한 번에 한 특성씩만 쪼개므로 이 평균화가 서툽니다.

```python
print("\n== D. 완화 튜닝 맛보기 (LightGBM) ==")
for name, params in [("기본값", {}),
                     ("완화(잎15·느린 학습)", dict(num_leaves=15, learning_rate=0.03, n_estimators=500, min_child_samples=40))]:
    m = LGBMClassifier(random_state=42, verbosity=-1, **params).fit(Xtr, ytr)
    print(f"  {name:<16} test AUC {roc_auc_score(yte, m.predict_proba(Xte)[:, 1]):.3f}")
```

실행 결과:

```
== D. 완화 튜닝 맛보기 (LightGBM) ==
  기본값              test AUC 0.797
  완화(잎15·느린 학습)    test AUC 0.797
```

손으로 몇 개 눌러 봐도 0.797에서 꿈쩍 않습니다. **모델 쪽 손잡이는 한계에 왔다**는 신호입니다.
그럼 부스팅은 영영 진 걸까요? 아닙니다 — 판을 바꾸면 됩니다. [Day 064](day-064.md)에서
상호작용이 살아 있는 특성(기상 예보)을 넣는 순간 순위가 어떻게 되는지 보게 됩니다.
오늘의 결론만 기록해 두세요:

> **모델 계열에 대한 믿음은 실험 앞에서만 유효하다.** 그리고 모델을 바꾸는 것보다
> **특성(데이터)을 바꾸는 것**이 더 큰 손잡이인 경우가 많다.

## ⑤ 자주 하는 실수

### import에서 넘어짐

```
ModuleNotFoundError: No module named 'xgboost'
```

**원인** — XGBoost·LightGBM은 sklearn과 별개 패키지입니다.
**해결** — `pip install xgboost lightgbm` (venv 활성화 확인). sklearn만으로 하려면 `HistGradientBoostingClassifier` 가 거의 같은 물건입니다.

### 나무 수를 랜덤포레스트 감각으로 늘림

**증상** — "많을수록 좋다며?" `n_estimators=2000` — test 점수가 오히려 하락.
**원인** — 그 직관은 **배깅** 것입니다. 부스팅은 직렬 보정이라 과하면 노이즈까지 학습합니다 (Step 1: 100그루 0.791 → 500그루 0.778).
**해결** — 부스팅에서는 조기 종료를 켜거나, 학습률과 함께 교차검증([Day 062](day-062.md))으로 고릅니다.

### 학습률을 키워 시간을 아끼려 함

**증상** — `learning_rate=0.5` 로 나무 50개만 — 점수가 불안정하게 출렁임.
**원인** — 보폭이 크면 오답 보정이 과격해져 수렴 품질이 나빠집니다.
**해결** — 관례는 반대 방향입니다: 학습률을 **낮추고**(0.03~0.1) 나무를 늘린 뒤 조기 종료로 자릅니다.

### 조기 종료의 검증 데이터로 test를 씀

**증상** — `eval_set=[(Xte, yte)]` 로 조기 종료 — 점수가 좋아 보임.
**원인** — 나무 수(=하이퍼파라미터)를 test로 고른 것입니다. [Day 052](day-052.md)의 "test는 한 번만" 위반.
**해결** — 검증은 train에서 떼어 씁니다 (Step 2의 `validation_fraction` 이 그 일을 합니다).

### 순위 하나로 계열 전체를 판정

**증상** — "우리 데이터에선 로지스틱이 1위니까 앞으로도 선형만 쓰자" (어제와 반대 방향의 같은 실수).
**원인** — 순위는 데이터·특성 구성의 함수입니다. 특성이 바뀌면 순위도 바뀝니다.
**해결** — 계열별 대표를 **후보군**으로 유지하고, 특성이 바뀔 때마다 재대결시킵니다 ([Day 064](day-064.md)에서 실제로 뒤집힙니다).

## ⑥ 확인 문제

**Q1.** 랜덤포레스트에서 나무 수를 늘리는 것과 부스팅에서 나무 수를 늘리는 것은 왜 위험도가 다른가요?

<details>
<summary>답 보기</summary>

포레스트의 나무들은 **독립적으로 병렬** 학습되어 평균 내므로, 수를 늘려도 분산이 줄 뿐 과적합하지 않습니다
(수확 체감뿐). 부스팅의 나무들은 **이전 오답을 직렬로 보정**하므로, 수가 과하면 train의 노이즈까지
보정 대상이 되어 과적합합니다 (test 0.791 → 0.778). 그래서 부스팅에만 조기 종료가 필수 관행입니다.

</details>

**Q2.** 조기 종료에 쓰는 검증 데이터를 test 세트로 대신하면 안 되는 이유를 [Day 052](day-052.md)의 언어로 설명하세요.

<details>
<summary>답 보기</summary>

조기 종료는 "나무 수"라는 하이퍼파라미터를 검증 점수로 **선택**하는 절차입니다. test로 선택하면 test가
학습 과정에 관여하게 되어(test는 한 번만 원칙 위반) 최종 점수가 낙관적으로 부풀고, 배포 후 성능이 그보다
낮게 나옵니다. 검증은 반드시 train 내부에서 떼어냅니다.

</details>

**Q3.** 우리 데이터에서 로지스틱(0.818)이 부스팅(0.797)을 이긴 구조적 이유와, 그럼에도 부스팅을
후보군에서 빼면 안 되는 이유를 각각 한 문장으로 쓰세요.

<details>
<summary>답 보기</summary>

이긴 이유: 신호가 서로 상관된 여러 특성(pm10·no2·co·so2 …)에 매끈하게 분산되어 있어, 이들을 가중 평균해
노이즈를 상쇄하는 선형 모델에 유리한 판이기 때문입니다. 빼면 안 되는 이유: 순위는 특성 구성의 함수라서,
상호작용이 살아 있는 특성이 추가되는 순간([Day 064](day-064.md)) 부스팅이 역전할 수 있기 때문입니다.

</details>
