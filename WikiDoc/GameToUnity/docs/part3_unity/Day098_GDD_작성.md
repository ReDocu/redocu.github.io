## 3. 개념

### 3-1. GDD란

**왜 필요한가** — 팀이 같은 것을 상상하게 만든다.

```
   ★ GDD (Game Design Document)

   "이 게임이 무엇인지"를 적은 문서
```

```
   ★ PRD와 같은 틀

   누가 (타깃)
   무엇을 (콘텐츠)
   왜 (재미의 원천)

   + 게임 고유 항목 (핵심 루프, 조작, 승패)
```

```
   ⚠️ GDD의 오해

   ✗ 두꺼울수록 좋다
   ✗ 모든 것을 미리 정해야 한다
   ✗ 한 번 쓰면 안 바꾼다

   ✔ 짧고 명확하게
   ✔ 만들면서 갱신한다
   ✔ 제외 목록이 가장 중요하다  ★
```

```
   ★ 4주 프로젝트의 GDD 분량

   A4 3~5쪽이면 충분하다
   → 더 길면 아무도 안 읽는다
```

### 3-2. 필수 항목

**왜 필요한가** — 빠지면 나중에 문제가 된다.

| 항목 | 내용 | 분량 |
|---|---|---|
| **한 줄 소개** | "OO하는 OO 게임" | 1줄 |
| 타깃 | 누가 왜 하는가 | 3줄 |
| **핵심 루프** | 반복되는 30초 | 그림 1개 |
| 조작 | 키/마우스 매핑 | 표 |
| 승패 조건 | 언제 이기고 지는가 | 3줄 |
| 콘텐츠 범위 | 스테이지/적/아이템 수 | 표 |
| 기술 | 엔진, 주요 기능, 재사용 코드 | 표 |
| **제외 목록** | **이번에 안 만드는 것** | 목록 ★ |

```
   ★ 이 8개면 충분하다

   그래픽 스타일, 사운드, 스토리는
   있으면 좋지만 필수는 아니다
```

### 3-3. 한 줄 소개

**왜 필요한가** — 이걸 못 쓰면 게임이 정해지지 않은 것이다.

```
   ★ 형식

   "[특징적인 동사]하는 [장르] 게임"
```

```
   ✗ 나쁜 예

   "재미있는 액션 게임"           → 특징이 없다
   "여러 무기로 적을 물리치는 게임" → 흔하다
   "로그라이크 RPG 액션 어드벤처"  → 장르 나열
```

```
   ✔ 좋은 예

   "무기를 버려야 다음 층으로 갈 수 있는 로그라이크"
   "시간이 멈춘 동안만 움직일 수 있는 퍼즐 슈터"
   "적을 죽일수록 화면이 어두워지는 생존 게임"
   "중력 방향을 바꿔 이동하는 플랫포머"
```

```
   ★ 좋은 한 줄의 조건

   ① 다른 게임과 구분된다
   ② 규칙이 하나 드러난다
   ③ 그 규칙이 재미를 만든다
```

```
   ⚠️ 한 줄에 두 개 이상의 특징이 들어가면

   → 4주에 못 만든다
   → 하나만 남긴다
```

### 3-4. 핵심 루프

**왜 필요한가** — 게임의 심장.

```
   ★ 핵심 루프 = 플레이어가 반복하는 30초
```

```
   예) 타워 디펜스

   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
   │ 웨이브 │──▶│ 방어   │──▶│ 골드   │──▶│ 타워   │
   │ 시작   │   │        │   │ 획득   │   │ 강화   │
   └────────┘   └────────┘   └────────┘   └───┬────┘
        ▲                                      │
        └──────────────────────────────────────┘
```

```
   예) 로그라이크

   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
   │ 방 입장│──▶│ 전투   │──▶│ 보상   │──▶│ 다음방 │
   │        │   │        │   │ 선택   │   │ 선택   │
   └────────┘   └────────┘   └────────┘   └───┬────┘
        ▲                                      │
        └──────────────────────────────────────┘
```

```
   ★ 좋은 루프의 조건

   ① 30초~2분 안에 한 바퀴
   ② 매번 조금씩 다르다 (선택, 랜덤)
   ③ 다음 바퀴가 기대된다 (성장, 목표)
```

```
   ⚠️ 루프에 없는 기능은 우선순위가 낮다

   "상점" 이 루프에 없다면 → 제외 목록으로
```

```
   ★ 루프를 그려보면 범위가 보인다

   상자 4개면 4주에 가능
   상자 10개면 불가능
```

### 3-5. 30초 검증

**왜 필요한가** — 재미의 최소 단위.

```
   ★ 질문

   "이 게임의 첫 30초를 문장으로 써 보세요"
```

```
   ✔ 좋은 예

   "방에 들어간다. 적 3마리가 다가온다.
    검을 휘둘러 둘을 처치하지만 하나가 뒤를 잡는다.
    구르기로 피하고 마지막을 처치한다.
    문이 열리고 무기 3개가 나타난다.
    지금 든 검을 버려야 새 무기를 들 수 있다.
    망설이다 활을 고른다."
```

```
   ★ 이 문장에서 알 수 있는 것

   ① 필요한 시스템: 적 AI, 전투, 회피, 무기 교체, 방 이동
   ② 재미의 원천: 무기 선택의 딜레마
   ③ 만들 순서: 전투 → 무기 → 방
```

```
   ⚠️ 30초를 못 쓰면

   → 게임이 아직 없다
   → 레퍼런스를 더 조사한다
```

### 3-6. 범위 — Must / Should / Won't

**왜 필요한가** — 오늘의 핵심.

```
   ★ MoSCoW 기법

   Must     반드시 있어야 게임이 성립
   Should   있으면 좋다
   Could    여유가 있으면
   Won't    이번엔 안 한다  ★
```

```
   ★ 4주 배분

   1주차 (W21): Must의 핵심 루프
   2주차 (W22): Must 전부
   3주차 (W23): Should
   4주차 (W24): 다듬기 + 버그 + 빌드

   → Should는 안 해도 게임이 나온다
   → Could는 거의 안 한다
```

```
   ⚠️ 흔한 실수

   Must에 10개를 넣는다
   → 2주차에 절반도 못 끝낸다
   → 3~4주차가 사라진다
   → 완성 못 한다
```

```
   ★ Must의 개수

   개인:  3~5개
   2인:   5~7개
   4인:   8~12개

   → 이보다 많으면 깎는다
```

### 3-7. 제외 목록 — 가장 중요

**왜 필요한가** — 적는 순간 결정된다.

```
   ★ 제외 목록에 흔히 들어가는 것

   × 멀티플레이          (네트워크는 그 자체로 프로젝트)
   × 세이브/로드         (모든 상태를 직렬화해야 한다)
   × 스토리·컷신         (분량이 무한하다)
   × 상점·경제 시스템     (밸런싱에 시간이 많이 든다)
   × 스킬 트리           (조합 폭발)
   × 캐릭터 커스터마이징
   × 절차적 생성         (밸런싱이 어렵다)
   × 다국어 지원
   × 업적·통계
   × 튜토리얼            (마지막에 만든다)
```

```
   ★ 제외 목록의 효과

   ① 팀이 "안 만든다"에 합의한다
   ② 중간에 "이것도 넣자"를 막는다
   ③ 발표 때 "왜 없나요?"에 답할 수 있다
```

```
   ★ 최소 3개는 적는다

   3개도 못 적으면
   → 범위를 제대로 생각하지 않은 것
```

```
   ⚠️ 스코프 크립 (Scope Creep)

   "이것만 더 넣으면 훨씬 재미있을 텐데"
   → 이 생각이 프로젝트를 죽인다

   ★ 대응
   "다음 버전에" 목록을 따로 만들어 적어 둔다
   → 아이디어는 버리지 않되, 이번엔 안 한다
```

### 3-8. 콘텐츠 범위표

**왜 필요한가** — 숫자로 적으면 일정이 나온다.

| 요소 | 수량 | 근거 |
|---|:--:|---|
| 스테이지(층) | 10 | 1층당 30초 = 5분 플레이 |
| 적 종류 | 4 | 근접/원거리/돌진/보스 |
| 무기 | 6 | 검/활/창/도끼/지팡이/단검 |
| 보스 | 1 | 10층 |
| 아이템 | 3 | 회복/방어/속도 |
| BGM | 2 | 전투/보스 |
| 효과음 | 12 | 공격4/피격3/획득2/UI3 |

```
   ★ 각 항목이 며칠인지 추정한다

   적 1종        = 0.5일 (모델 + AI + 애니메이션)
   무기 1종      = 0.3일
   보스          = 3일    ★ 가장 크다
   층 생성 시스템 = 2일
```

```
   ★ 합계가 20일(4주 × 5일)을 넘으면 깎는다

   ⚠️ 그리고 버그 수정·다듬기에 30%를 더 잡는다
   → 실제 개발 가능 일수는 14일 정도
```

### 3-9. 레퍼런스 조사

**왜 필요한가** — 바퀴를 다시 발명하지 않는다.

```
   ★ 유사 게임 2~3개를 정한다

   각각에 대해
   ① 핵심 루프는 무엇인가
   ② 무엇을 가져올 것인가
   ③ 무엇을 다르게 할 것인가
```

| 게임 | 가져올 것 | 다르게 할 것 |
|---|---|---|
| Hades | 방 이동, 보상 선택 | 무기 교체 강제 |
| Enter the Gungeon | 회피 구르기, 탄막 | 근접 중심 |
| Slay the Spire | 경로 선택 | 실시간 전투 |

```
   ★ 레퍼런스 플레이는 필수다

   ① 유튜브 영상 30분
   ② 가능하면 직접 플레이 1시간
   → "왜 재미있는가"를 관찰한다
```

```
   ⚠️ 표절과 참고의 차이

   참고: 시스템·구조를 배운다
   표절: 애셋·이름·UI를 그대로 쓴다

   → 포트폴리오에서 표절은 치명적
```

### 3-10. 기술 스택 선택

**왜 필요한가** — 근거를 남긴다.

| | WINAPI 자작 엔진 | Unity |
|---|---|---|
| 제어 | **완전** | 제한 |
| 개발 속도 | 느림 | **빠름** |
| 3D | 매우 어려움 | **쉬움** |
| 애셋 | 직접 제작 | **스토어·무료 애셋** |
| 포트폴리오 어필 | **기술 깊이** | **완성도** |
| 4주 적합성 | 2D 소품 | **대부분** ★ |

```
   ★ 선택 기준

   Unity를 고른다면
   → "4주 안에 완성도 있는 결과물"

   WINAPI를 고른다면
   → "엔진 없이 만들 수 있음을 보여준다"
   → 범위를 훨씬 작게 (2D, 단순한 시스템)
```

```
   ★ 문서에 근거를 적는다

   "Unity 선택 — 3D 액션이 핵심이고
    NavMesh·Animator를 재사용해 4주에 완성 가능"

   "WINAPI 선택 — 자체 엔진 구현 역량을 보이기 위해.
    2D 탑다운으로 범위 축소"
```

```
   │      └────────────────────────────────────────┘        │
   │                                                        │
   │  범위                                                   │
   │    Must  : 7개  (플레이어/적3/무기3/층6/보스/승패/HUD)  │
   │    Should: 4개                                          │
   │    Won't : 8개  ★                                       │
   │                                                        │
   │  예상 일수  15.0일 / 가용 20일   (버퍼 5일)             │
   │                                                        │
   │  최대 리스크  "무기 교체가 재미없다" → W21에 검증        │
   └────────────────────────────────────────────────────────┘
```

- [ ] 아이디어 후보 3개를 만들었다
- [ ] **한 줄 소개를 썼다** (특징이 드러난다)
- [ ] 첫 30초를 문장으로 썼다
- [ ] 그 문장에서 필요한 시스템을 뽑았다
- [ ] **핵심 루프를 그렸다** (30초~2분)
- [ ] 각 단계의 소요 시간을 적었다
- [ ] 레퍼런스 2~3개를 조사했다
- [ ] 조작 표를 만들었다
- [ ] 승패 조건이 명확하다
- [ ] 콘텐츠 범위를 수량으로 적었다
- [ ] 각 항목의 예상 일수를 계산했다
- [ ] **20일 → 15일로 깎았다**
- [ ] 시스템은 남기고 수량을 줄였다
- [ ] Must / Should / **Won't**를 분류했다
- [ ] **제외 목록이 최소 3개** (권장 8개)
- [ ] 기술 스택 선택 근거를 적었다
- [ ] 재사용 코드 목록을 만들었다
- [ ] 리스크 표를 만들었다
- [ ] 가장 큰 리스크를 W21에 배치했다
- [ ] 상호 리뷰를 받고 2차로 깎았다
- [ ] "다음 버전" 목록을 만들었다
- [ ] GDD를 저장소에 커밋했다

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|
| **범위가 크다** | 욕심 | **깎는 것이 오늘의 목적** |
| 아이디어가 없다 | 백지에서 시작 | Part 2·3에서 확장 |
| 한 줄이 안 나온다 | 게임이 안 정해짐 | 규칙 하나를 정한다 |
| 핵심 루프가 5분 | 루프가 아니라 진행 | 반복 단위를 찾는다 |
| 제외 목록이 비었다 | 범위 미검토 | 최소 3개 강제 |
| 일수가 안 나온다 | 경험 부족 | 유사 기능의 Day를 참고 |
| 팀원마다 다른 상상 | 문서 부재 | GDD를 함께 읽는다 |
| 리스크를 모르겠다 | 안 해본 것 | "가장 자신 없는 것"이 리스크 |
| 3주차에 범위 확대 | 스코프 크립 | "다음 버전" 목록으로 |

## 7. 정리

### 오늘 배운 것

| 개념 | 한 줄 요약 |

| **GDD** | 팀이 같은 것을 상상하게. 3~5쪽 |

| 스코프 크립 | "다음 버전" 목록으로 방어 |
| 레퍼런스 | 가져올 것 / 다르게 할 것 |
