### 3-5. 도전 예시 ①: 성능

**왜 필요한가** — 가장 쓰기 좋은 소재.

```markdown
## 1. 프레임 스파이크 38ms → 17ms

### 문제
후반 층(적 5마리 + 광역 공격)에서 최악 프레임이 38ms까지 튀었다.
평균은 52fps로 나쁘지 않았지만, 순간적으로 26fps까지 떨어져
전투 중 "끊긴다"는 피드백을 받았다.

### 원인 분석
Profiler로 측정한 결과 두 가지가 겹쳐 있었다.

| 항목 | 시간 |
|---|--:|
| ParticleSystem.Update | 12.4ms |
| GC.Collect | 8.1ms |

- 파티클: 타격 이펙트가 동시에 40개 이상 생성
- GC: HUD가 매 프레임 문자열을 생성 (2.1KB/frame)

### 접근
파티클을 줄이는 방법은 세 가지를 고려했다.

1. Burst Count 감소 — 시각적 손실
2. 이펙트 자체를 제거 — 타격감 손실
3. **풀 maxSize로 동시 개수 상한** — 채택

3번을 고른 이유는 "평소에는 화려하되 최악 상황에서만
자동으로 제한된다"는 성질 때문이다. 상한에 도달하면
가장 오래된 이펙트를 재사용하도록 해서
"안 나오는" 것이 아니라 "겹치지 않는" 결과를 얻었다.

GC는 값이 바뀔 때만 문자열을 생성하도록 캐싱했다.

### 결과
| 항목 | 전 | 후 |
|---|--:|--:|
| 최악 프레임 | 38.4ms | **17.2ms** |
| GC Alloc | 2.1KB | **0.1KB** |
| 파티클 최대 | 312 | 184 |

시각적 차이는 팀 내부 블라인드 테스트에서 구분하지 못했다.

### 배운 것
"평균이 아니라 최악을 본다."
평균 FPS가 좋아도 스파이크 하나가 체감을 결정한다.
```

```
   ★ 이 글의 강점

   ① 수치가 있다
   ② 대안을 비교했다
   ③ 왜 그것을 골랐는지 설명한다
   ④ 결과를 검증했다
```

### 3-6. 도전 예시 ②: 설계

**왜 필요한가** — 구조적 사고를 보여준다.

```markdown
## 2. 일시정지 상태 충돌 — 요청 카운터 설계

### 문제
QA 중 "무기 선택 화면에서 Esc를 누르면 게임이 영구히 멈춘다"는
치명 버그를 발견했다. 재현율 5/5.

### 원인 분석
`Time.timeScale`을 세 곳에서 각자 제어하고 있었다.

- 일시정지 메뉴: 0 / 1
- 무기 선택 UI: 0 / 1
- 결과 화면: 0

무기 선택 중(timeScale=0) 일시정지를 열었다 닫으면
일시정지가 `timeScale = 1`로 복구하지만
무기 선택은 여전히 0을 기대한다.
반대 순서면 영구히 0으로 남는다.

### 접근
세 가지를 고려했다.

1. 각 UI가 이전 값을 기억했다 복원 — 중첩되면 여전히 깨진다
2. GameManager가 전부 관리 — 상태 조합이 늘면 복잡해진다
3. **일시정지 요청 카운터** — 채택

3번은 "누가 요청했는지"를 집합으로 관리하고,
요청이 하나라도 남아 있으면 정지, 전부 해제되면 재개한다.

```csharp
TimeController.RequestPause("weapon_choice");
TimeController.ReleasePause("weapon_choice");
```

중첩 순서와 무관하게 동작하고, 새로운 일시정지 요인이
생겨도 코드 수정 없이 확장된다.

### 결과
- 해당 버그 해소
- 이후 발견된 유사 버그 2건도 같은 구조로 해결
- 씬 전환 시 `ClearAll()` 한 줄로 안전하게 초기화

### 배운 것
"전역 상태는 한곳에서만 쓴다."
여러 곳이 같은 전역 값을 직접 쓰면 순서 의존이 생긴다.
```

### 3-7. 도전 예시 ③: 방법론

**왜 필요한가** — 문제 정의 능력.

```markdown
## 3. 감으로 하던 밸런싱을 측정 기반으로

### 문제
알파 단계에서 클리어율이 20%였다. 팀원들은 "4층이 어렵다"고
느꼈지만, 얼마나 어려운지, 왜 어려운지 알 수 없었다.
조정해도 "나아진 것 같다" 이상의 판단이 안 됐다.

### 접근
층별 소요 시간·피해량·사망 여부를 CSV로 자동 기록하는
도구를 만들었다. 5회 플레이하면 40행의 데이터가 쌓인다.

집계 결과가 예상과 달랐다.

| 층 | 사망률 |
|:--:|--:|
| 3 | 5% |
| **4** | **60%** |
| 5 | 20% |

4층만 유독 높았다. 관찰 기록과 대조하니
"탱커 2마리가 동시에 접근해 회피 쿨다운이 부족"이 원인이었다.

### 결과
| 항목 | 전 | 후 |
|---|--:|--:|
| 클리어율 | 20% | **60%** |
| 4층 사망률 | 60% | 12% |
| 총 소요 | 11:08 | 9:07 |

조정은 JSON 수정만으로 이뤄져 재빌드가 없었고,
"조정 → 5회 측정 → 확인" 사이클이 20분이었다.

### 배운 것
"측정할 수 없으면 개선할 수 없다."
그리고 측정 도구를 만드는 데 쓴 2시간이
이후 3일의 밸런싱 시간을 절반으로 줄였다.
```

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|
| **기술적 도전에 쓸 게 없다** | 기록 부족 | 4주간 가장 오래 막힌 문제 |
| 도전이 "어려웠다"뿐 | 분석 부재 | 원인·대안·결과를 쓴다 |
| 수치가 없다 | 측정 안 함 | Docs/의 기록 활용 |
| 개인 기여 구분 어려움 | 협업 | `git shortlog -sn` |
| 이미지가 안 보임 | 경로 오류 | 상대 경로 확인 |
| GIF가 안 재생됨 | 크기 초과 | 5MB 이하 |
| 정리 후 빌드 실패 | 참조 삭제 | `git revert` |
| 발표가 길다 | 리허설 부족 | 줄일 순서대로 |
| 시연 중 실수 | 리허설 부족 | 백업 영상 |
| README가 길다 | 다 넣으려 함 | 핵심만. 상세는 Docs/ 링크 |
