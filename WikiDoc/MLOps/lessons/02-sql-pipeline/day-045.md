## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 파이프라인 운영 체크리스트 **6개 항목**으로 자기 파이프라인을 점검할 수 있다.
- `run_id` 가 포함된 **구조적 로그**를 남기고, 종료 코드로 성패를 알릴 수 있다.
- **명령 한 줄로 수집→적재가 재현**되는 파이프라인을 완성할 수 있다.
- 장애 상황을 재현하고 **복구 절차서(runbook)** 를 작성할 수 있다.

## ② 왜 필요한가

**오늘은 새 기능을 만들지 않습니다.** 만든 것을 **운영 가능한 상태**로 만듭니다.

```
"동작한다"                          "운영할 수 있다"
────────────────                    ─────────────────────────────
내 PC에서 돌아간다                  새벽 3시에 자동으로 돈다
에러가 나면 화면에 뜬다             에러가 나면 담당자가 안다
실패하면 다시 돌린다                실패 원인을 로그로 특정할 수 있다
잘 돌아가는 것 같다                 어제 몇 행 들어왔는지 숫자로 답한다
```

**MP1 평가 기준 1번이 "명령 한 줄로 수집→적재가 재현된다"** 입니다. 오늘 그것을 완성합니다.
그리고 이 파이프라인은 **W24에서 Docker 이미지가 되고, W26에서 CI가 돌리고, W28에서 스케줄러가 실행합니다.**
오늘 만드는 인터페이스가 그때까지 갑니다.

## ③ 개념 설명

### 운영 체크리스트 6항목 ★

| # | 항목 | 확인 질문 |
|---|---|---|
| **1. 재현** | 명령 한 줄로 돌아가나? | "새 PC에서 clone 하고 몇 분 안에 실행되나?" |
| **2. 멱등** | 두 번 돌려도 안전한가? | "지금 다시 실행해도 되나?" |
| **3. 로그** | 무슨 일이 있었는지 알 수 있나? | "3일 전 실행에서 몇 행 들어왔나?" |
| **4. 알림** | 실패를 사람이 아나? | "새벽 3시에 실패하면 누가 어떻게 아나?" |
| **5. 복구** | 어떻게 되돌리나? | "이 절차를 처음 보는 사람이 따라 할 수 있나?" |
| **6. 관측** | 지금 상태가 정상인가? | "마지막 성공이 언제인지 한 줄로 알 수 있나?" |

**1·2는 앞에서 만들었습니다.** 오늘은 **3·4·5·6**을 만듭니다.

### 로깅 — 무엇을 어떤 수준으로

| 레벨 | 언제 | 예 |
|---|---|---|
| `DEBUG` | 개발 중 상세 | 요청 URL · 응답 크기 |
| `INFO` | **정상 흐름의 이정표** | "수집 2412건" · "적재 2400행" |
| `WARNING` | 이상하지만 계속 진행 | "격리 12행" · "불량률 3%" |
| `ERROR` | 실패했지만 프로그램은 삶 | "소스 1개 수집 실패" |
| `CRITICAL` | 계속할 수 없음 | "DB 연결 불가" |

**로그에 반드시 넣어야 할 것**

```
[시각] [레벨] [run_id] [소스] 메시지 (숫자 포함)
2026-08-12 03:00:14 INFO  run=42 air_seoul 적재 완료 rows=2400 rejected=12 elapsed=2.31s
```

| 요소 | 없으면 |
|---|---|
| **`run_id`** | 여러 실행이 섞여 어느 것의 로그인지 모름 |
| **소스** | 여러 소스가 섞임 |
| **숫자** | "완료"만 있고 몇 행인지 모름 |
| **소요 시간** | 느려지는 추세를 못 봄 |

> **"성공했습니다" 같은 로그는 쓸모없습니다.** 숫자가 없으면 나중에 비교할 수 없습니다.
> **로그는 미래의 나에게 보내는 증거**입니다.

### 종료 코드 — 기계가 읽는 결과

```
0   성공
1   일반 오류
2   품질 게이트 실패      ← 재실행해도 같은 결과. 데이터를 봐야 함
3   설정 오류             ← 재실행 무의미. 사람이 고쳐야 함
4   외부 시스템 오류      ← 재시도하면 될 수도 있음
```

**스케줄러·CI는 종료 코드로 판단합니다.** 구분해 두면 **"재시도할 것"과 "사람을 불러야 할 것"** 이 갈립니다.

```powershell
$ datapipe etl --source air_seoul
$ echo $LASTEXITCODE
0
```

### 알림 — 실패를 사람이 알게 하기

| 방법 | 장점 | 단점 |
|---|---|---|
| **로그 + 종료 코드** | 가장 단순. 스케줄러가 감지 | 사람이 안 봄 |
| Slack/Discord 웹훅 | 즉시 도달 | 너무 자주 울리면 무시됨 |
| 이메일 | 기록 남음 | 느림 |
| 모니터링 도구 | 규칙·중복 억제 | 구축 비용 (W27) |

**알림 설계의 원칙**

| 원칙 | 이유 |
|---|---|
| **행동할 수 있는 것만 알린다** | 대응할 게 없는 알림은 소음 |
| **같은 문제를 반복해 알리지 않는다** | 알림 피로 → 진짜 장애를 놓침 |
| **알림에 다음 행동을 적는다** | "실패했음"이 아니라 "실패했음. runbook 3-2 참조" |

### 재실행 절차서 (runbook)

**장애는 새벽 3시에 납니다.** 그때 여러분은 자고 있고, 당직자는 이 코드를 처음 봅니다.

```markdown
## 증상: 어제 데이터가 없다

1. 실행 이력 확인
   $ datapipe status --source air_seoul
2. status = failed 라면 → error_message 확인
3. 원인별 대응
   - timeout        → 재실행 (아래 4번)
   - quality gate   → 격리 테이블 확인 후 담당자 호출 (원본 형식 변경 의심)
   - DB 연결 실패   → 컨테이너/서버 상태 확인
4. 재실행 (멱등하므로 안전)
   $ datapipe backfill --source air_seoul --from 2026-08-11 --to 2026-08-12
5. 확인
   $ datapipe status --source air_seoul
```

**runbook은 코드와 함께 저장소에** 둡니다. 위키에 두면 잊힙니다.

### 스케줄링

| 환경 | 도구 |
|---|---|
| Windows | 작업 스케줄러 (Task Scheduler) |
| Linux/macOS | `cron` |
| 컨테이너 | Kubernetes CronJob (W25) |
| 워크플로 | **Airflow · Prefect · Dagster** (W28) |

```cron
# 매시 5분에 실행 (정각은 피합니다 — 데이터 공개 지연 감안)
5 * * * * cd /opt/datapipe && /opt/venv/bin/datapipe etl --source air_seoul >> /var/log/datapipe.log 2>&1
```

> **정각을 피하는 이유** — 모두가 정각에 API를 호출하면 서버가 몰립니다.
> 그리고 **데이터가 아직 공개되지 않았을 수 있습니다** ([Day 043](day-043.md)의 겹침 여유와 같은 이유).

### 관측성 3요소

| 요소 | 무엇 | 우리 구현 |
|---|---|---|
| **로그(logs)** | 개별 사건 | 파일 + `ingest_run` |
| **지표(metrics)** | 시간에 따른 수치 | `rows_written` · 소요 시간 추이 |

### Step 1. 로깅 정비

`src/datapipe/utils/logging_config.py` 를 개선합니다 ([Day 014](../01-python-data/day-014.md)의 것을 확장).

```python
"""파이프라인 로깅 설정.

파일과 콘솔에 동시에 남기고, run_id 를 모든 줄에 붙입니다.
"""

from __future__ import annotations

import logging
import logging.handlers
import sys
from pathlib import Path


class RunIdFilter(logging.Filter):
    """모든 로그 레코드에 run_id 를 붙입니다."""

    def __init__(self) -> None:
        super().__init__()
        self.run_id: str = "-"

    def filter(self, record: logging.LogRecord) -> bool:
        record.run_id = self.run_id
        return True


run_filter = RunIdFilter()

FORMAT = "%(asctime)s %(levelname)-8s run=%(run_id)s %(name)s | %(message)s"


def setup_logging(log_dir: Path, level: str = "INFO") -> None:
    log_dir.mkdir(parents=True, exist_ok=True)

    root = logging.getLogger()
    root.setLevel(logging.DEBUG)
    root.handlers.clear()

    fmt = logging.Formatter(FORMAT, datefmt="%Y-%m-%d %H:%M:%S")

    console = logging.StreamHandler(sys.stderr)
    console.setLevel(getattr(logging, level.upper()))
    console.setFormatter(fmt)
    console.addFilter(run_filter)
    root.addHandler(console)

    # 날짜별 파일, 14일 보관
    file_handler = logging.handlers.TimedRotatingFileHandler(
        log_dir / "datapipe.log", when="midnight", backupCount=14, encoding="utf-8"
    )
    file_handler.setLevel(logging.DEBUG)      # 파일에는 DEBUG 까지
    file_handler.setFormatter(fmt)
    file_handler.addFilter(run_filter)
    root.addHandler(file_handler)

    # 시끄러운 외부 라이브러리 억제
    logging.getLogger("urllib3").setLevel(logging.WARNING)


def set_run_id(run_id: int | str) -> None:
    run_filter.run_id = str(run_id)
```

`runner.py` 에서 `run_id` 를 받자마자 설정합니다.

```python
run_id = start_run(source_name, since, until)
set_run_id(run_id)
logger.info("ETL 시작 source=%s window=%s~%s", source_name, since, until)
```

**콘솔은 `stderr`, 결과는 `stdout`** 으로 나누는 것이 중요합니다.
그래야 `datapipe status --json | jq` 같은 파이프 조합이 가능합니다.

**종료 코드**를 구분합니다.

```python
EXIT_OK, EXIT_ERROR, EXIT_QUALITY, EXIT_CONFIG, EXIT_EXTERNAL = 0, 1, 2, 3, 4


def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    setup_logging(Path("logs"), args.log_level)

    try:
        return args.func(args)
    except ConfigError as exc:
        logger.critical("설정 오류: %s", exc)
        return EXIT_CONFIG
    except QualityGateError as exc:
        logger.error("품질 기준 미달: %s", exc)
        return EXIT_QUALITY
    except (SourceError, DatabaseError) as exc:
        logger.error("외부 시스템 오류: %s", exc)
        return EXIT_EXTERNAL
    except KeyboardInterrupt:
        logger.warning("사용자 중단")
        return EXIT_ERROR
    except Exception:
        logger.exception("예상치 못한 오류")
        return EXIT_ERROR
```

> `except Exception:` 로 잡을 때는 반드시 이것을 쓰세요. `logger.error(str(e))` 만 하면
> **어디서 났는지 알 수 없어** 디버깅이 불가능합니다.

### Step 3. `status` — 운영 대시보드

```python
STATUS_SQL = """
SELECT run_id, source, status,
       started_at, finished_at,
       EXTRACT(EPOCH FROM (finished_at - started_at))::int AS elapsed_sec,
       rows_read, rows_written, error_message
FROM ingest_run
WHERE (%s IS NULL OR source = %s)
ORDER BY run_id DESC
LIMIT %s
"""

SUMMARY_SQL = """
SELECT source,
       MAX(finished_at) FILTER (WHERE status = 'success')  AS last_success,
       now() - MAX(finished_at) FILTER (WHERE status = 'success') AS since_success,
       COUNT(*) FILTER (WHERE status = 'failed'
                          AND started_at >= now() - interval '1 day') AS fail_24h,
       SUM(rows_written) FILTER (WHERE started_at >= now() - interval '1 day') AS rows_24h
FROM ingest_run
GROUP BY source
ORDER BY source
"""


def cmd_status(args) -> int:
    rows = db.fetch_all(STATUS_SQL, (args.source, args.source, args.limit))
    if args.json:
        print(json.dumps(rows, default=str, ensure_ascii=False, indent=2))
        return EXIT_OK

    print(f"{'run':>5} {'source':<12} {'status':<9} {'started':<20} "
          f"{'sec':>4} {'read':>7} {'write':>7}")
    print("-" * 76)
    for r in rows:
        mark = {"success": "✅", "failed": "❌", "running": "⏳"}.get(r["status"], "?")
        print(f"{r['run_id']:>5} {r['source']:<12} {mark} {r['status']:<7} "
              f"{r['started_at']:%Y-%m-%d %H:%M:%S} "
              f"{r['elapsed_sec'] or 0:>4} {r['rows_read']:>7,} {r['rows_written']:>7,}")
        if r["error_message"]:
            print(f"      └─ {r['error_message'][:70]}")

    print()
    for s in db.fetch_all(SUMMARY_SQL):
        stale = s["since_success"] and s["since_success"].total_seconds() > 7200
        print(f"{s['source']:<12} 마지막 성공 {s['last_success']:%m-%d %H:%M} "
              f"({s['since_success']} 전){' ⚠️ 지연' if stale else ''} · "
              f"24h 실패 {s['fail_24h']}회 · 적재 {s['rows_24h'] or 0:,}행")
    return EXIT_OK
```

### Step 4. `check` — 품질 점검 명령

[Day 044](day-044.md)의 SQL 점검 쿼리들을 명령으로 묶습니다.

```python
CHECKS = [
    ("결측률", """
        SELECT ROUND(COUNT(*) FILTER (WHERE pm10 IS NULL) * 100.0 / COUNT(*), 2) AS value
        FROM measurement WHERE measured_at >= now() - make_interval(days => %s)
    """, 20.0),           # 20% 넘으면 경고
    ("격리율", """
        SELECT ROUND(COUNT(*) * 100.0 / GREATEST(
                 (SELECT SUM(rows_read) FROM ingest_run
                  WHERE started_at >= now() - make_interval(days => %s)), 1), 2) AS value
        FROM measurement_rejected
        WHERE rejected_at >= now() - make_interval(days => %s)
    """, 5.0),
    ("최근 성공 후 경과시간(분)", """
        SELECT ROUND(EXTRACT(EPOCH FROM (now() - MAX(finished_at))) / 60)::numeric AS value
        FROM ingest_run WHERE status = 'success'
    """, 120.0),
]


def cmd_check(args) -> int:
    failed = 0
    print(f"{'점검 항목':<28} {'값':>10} {'임계':>8}  판정")
    print("-" * 60)
    for name, sql, threshold in CHECKS:
        params = tuple([args.days] * sql.count("%s"))
        value = db.fetch_value(sql, params) or 0
        ok = float(value) <= threshold
        failed += 0 if ok else 1
        print(f"{name:<28} {value:>10} {threshold:>8}  {'✅' if ok else '⚠️'}")

    holes = db.fetch_value(HOLE_COUNT_SQL, (args.days,))
    print(f"{'시간 구멍(측정소×시간)':<28} {holes:>10} {0:>8}  {'✅' if holes == 0 else '⚠️'}")
    failed += 0 if holes == 0 else 1

    print()
    if failed:
        print(f"⚠️  {failed}개 항목이 임계치를 넘었습니다.")
        return EXIT_QUALITY
    print("✅ 모든 점검 통과")
    return EXIT_OK
```

### Step 5. 알림 붙이기

`src/datapipe/notify.py`:

```python
"""실패 알림. 웹훅 URL 이 없으면 로그만 남깁니다."""

from __future__ import annotations

import json
import logging
import os
import urllib.request

logger = logging.getLogger(__name__)


def send(title: str, message: str, *, level: str = "error") -> bool:
    url = os.getenv("ALERT_WEBHOOK_URL")
    if not url:
        logger.warning("알림 미설정 (ALERT_WEBHOOK_URL 없음): %s / %s", title, message)
        return False

    icon = {"error": "🔴", "warn": "🟡", "info": "🔵"}.get(level, "⚪")
    payload = {"text": f"{icon} *{title}*\n{message}"}
    req = urllib.request.Request(
        url,
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"},
    )
    try:
        with urllib.request.urlopen(req, timeout=5) as resp:
            return 200 <= resp.status < 300
    except Exception:
        logger.exception("알림 전송 실패")     # 알림 실패가 배치를 죽이면 안 됩니다
        return False
```

`cli.py` 에서 실패 시 호출합니다.

```
   $ datapipe backfill --source air_seoul --from 2026-08-11 --to 2026-08-12
   $ datapipe check
```

**3.** `datapipe check` 가 모든 항목을 통과했는데도 데이터가 잘못돼 있을 수 있습니다. 어떤 경우이며, 어떤 점검을 추가하겠습니까?

<details>
<summary>답 보기</summary>

**점검은 "우리가 상상한 실패"만 잡습니다.**

| 통과하지만 잘못된 경우 | 왜 안 잡히나 | 추가할 점검 |
|---|---|---|
| **측정소 매핑이 뒤바뀜** (1번↔2번) | 행 수·범위·결측 전부 정상 | 측정소별 값 분포를 과거와 비교 (**z점수** — [Day 044](day-044.md)) |
| **전 측정소 값이 +50 이동** | 유효 범위 안 | 전체 평균의 급변 감지 |
| **시간대가 9시간 밀림** | 시각 형식은 정상 | **일중 패턴** 검사 (새벽에 최고치가 뜨면 이상) |
| **오래된 데이터를 계속 재적재** | 행 수 정상, 구멍 없음 | `MAX(measured_at)` 이 전진하는지 |
| **단위가 바뀜** (㎍/㎥ → ㎎/㎥) | 값이 1000배 작아져도 0~2000 안 | 값의 자릿수 분포 |

**추가할 점검 3가지**

**① 최신성 — 데이터 시각이 전진하는가**

```sql
SELECT MAX(measured_at) AS 최신측정,
       now() - MAX(measured_at) AS 지연,
       CASE WHEN now() - MAX(measured_at) > interval '3 hours'
            THEN '⚠️' ELSE '✅' END AS 판정
FROM measurement;
```

**`ingest_run` 은 성공인데 `measured_at` 이 안 움직이는 경우**를 잡습니다.
같은 과거 데이터를 계속 재적재하고 있는 상황입니다.

**② 일중 패턴 — 시간대 오류 탐지**

```sql
SELECT EXTRACT(HOUR FROM measured_at) AS 시각, ROUND(AVG(pm10), 1) AS 평균
FROM measurement
WHERE measured_at >= now() - interval '7 days'
GROUP BY 1 ORDER BY 2 DESC LIMIT 3;
```

미세먼지는 보통 **출퇴근 시간(8시·19시 전후)에 높습니다.**
최고치가 새벽 3~4시에 뜬다면 **시간대가 밀렸을 가능성**이 큽니다.

**③ 측정소별 상호 비교 — 매핑 오류 탐지**

```sql
-- 인접 측정소끼리는 값이 비슷해야 합니다. 갑자기 순위가 뒤바뀌면 의심
WITH r AS (
    SELECT station_id,
           AVG(pm10) FILTER (WHERE measured_at >= now() - interval '1 day')  AS 어제,
           AVG(pm10) FILTER (WHERE measured_at <  now() - interval '7 days') AS 평소
    FROM measurement
    WHERE measured_at >= now() - interval '30 days'
    GROUP BY station_id
)
SELECT station_id, ROUND(평소,1), ROUND(어제,1),
       RANK() OVER (ORDER BY 평소 DESC) AS 평소순위,
       RANK() OVER (ORDER BY 어제 DESC) AS 어제순위
FROM r
WHERE 평소 IS NOT NULL AND 어제 IS NOT NULL
ORDER BY ABS(RANK() OVER (ORDER BY 평소 DESC) - RANK() OVER (ORDER BY 어제 DESC)) DESC
LIMIT 5;
```

**순위가 크게 바뀐 측정소**가 매핑 오류 후보입니다. [Day 037](day-037.md)의 `RANK` 가 여기서 쓰입니다.

**가장 중요한 교훈**

> **점검 목록은 사고가 날 때마다 자라야 합니다.**
> 새로운 종류의 사고가 나면, 고친 뒤 반드시 **"이걸 잡았을 점검"을 추가**하세요.

>

</details>

## 주간 퀴즈 9 — W09 (Python–DB 연동과 ETL)

1. SQL 인젝션을 막는 유일하게 확실한 방법은?
2. 테이블 이름을 동적으로 정해야 할 때 어떻게 하나?
3. `COPY` 가 단건 `INSERT` 보다 빠른 이유 세 가지는?
4. `ON CONFLICT` 를 쓰려면 반드시 있어야 하는 것은?
5. 같은 배치 안에 중복 키가 있으면 어떤 에러가 나며, 어떻게 해결하나?
6. 멱등성을 정의하고, 구현 방법 두 가지를 쓰시오.
7. 워터마크를 언제 갱신해야 하며, 잘못 갱신하면 무슨 일이 생기나?
8. 겹침 여유(overlap)가 필요한 이유는?
9. Extract 결과를 파일로 남기는 이유는?
10. 결측을 0으로 채우면 안 되는 이유는?

<details>
<summary>정답 보기</summary>

1. **파라미터 바인딩** — 값은 `%s` 자리에 따로 넘긴다. SQL문과 값이 분리되어 서버에 전달되므로 값이 문장 구조를 바꿀 수 없음
2. `%s` 로는 불가. **허용 목록(allowlist) 검증** 후 사용하거나 `psycopg.sql.Identifier` 로 조립
3. ① 왕복 제거(스트림) ② SQL 파싱·계획 생략 ③ 커밋(fsync) 1회
4. 해당 열 조합의 **`UNIQUE` 제약** (또는 exclusion 제약). 없으면 `there is no unique or exclusion constraint...`
5. `ON CONFLICT DO UPDATE command cannot affect row a second time`.
   → 적재 전 파이썬에서 `dedupe()` 또는 SQL의 `SELECT DISTINCT ON (키)`
6. 같은 입력으로 몇 번을 실행해도 **결과 상태가 같은** 성질.
   ① `ON CONFLICT DO NOTHING/UPDATE` ② `DELETE 구간` + `INSERT` (③ `TRUNCATE` + 전체 재적재)
7. **적재 성공을 확인한 뒤에만.** 먼저 갱신하면 실패한 구간을 영원히 건너뛰어 **조용한 데이터 구멍**이 생김
8. **지연 도착 데이터**를 흡수하기 위해. 데이터가 항상 시간순으로 도착하지 않음. 멱등하면 겹쳐도 안전
9. Transform 이후는 언제든 재실행 가능하지만 **Extract는 시간이 지나면 다시 못 함**.
   파싱 버그를 나중에 발견해도 원본이 있으면 복구 가능
10. "측정 안 됨"과 "값이 0"은 **다른 정보**. 0으로 채우면 `AVG` 의 분모에 포함되어 **평균이 실제보다 낮아짐**

**채점** — 8개 이상이면 MP1로 진행.
1·4·7번을 틀렸다면 각각 [Day 041](day-041.md)·[042](day-042.md)·[043](day-043.md)의 해당 절을 다시 읽으세요.
**이 셋이 MP1 평가 기준과 직결됩니다.**
</details>
