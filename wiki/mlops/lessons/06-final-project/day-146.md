## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 데일리 스탠드업을 **보고회가 아니라 조정 회의**로 운영할 수 있다.
- 수집 스크립트(호출 → 필터 → 검증 → upsert)를 구현해 **수집→적재를 관통**시킬 수 있다.
- API 호출 한도를 고려한 **백필 계획**을 실행할 수 있다.
- 작은 PR + 24시간 리뷰의 **PR 사이클**을 팀의 리듬으로 가동할 수 있다.

---

## ② 왜 필요한가

스프린트 첫날이 2주의 관성을 정합니다. 오늘 스탠드업이 늘어지면 2주 내내 늘어지고,
오늘 PR이 커지면 2주 내내 큽니다. 반대로 오늘 "작은 PR이 몇 시간 안에 리뷰되어 병합되는"
사이클이 한 바퀴 돌면, 그것이 팀의 정상 상태가 됩니다. 습관은 첫날에 가장 쌉니다.

구현의 첫 작업이 수집인 이유는 의존성 때문입니다 — 모델(#9~11)도, 등급 기준선도, 데모의
설득력도 전부 DB에 쌓인 실데이터를 입력으로 합니다. 수집이 하루 늦으면 하류 전체가 하루
늦습니다. 그리고 수집은 **외부 세계와의 접점**이라 프로젝트에서 가장 예측 불가능한
부분입니다 — 한도·지연·형식 변화 같은 배신은 우리 일정을 봐주지 않으므로, 가장 불확실한
것을 가장 먼저 안정시키는 것이 스프린트 배치의 원칙입니다.

이번 주의 목표를 다시 확인하고 시작합시다: **수집·적재 파이프라인과 베이스라인 모델을
완성하고 API 뼈대에 연결한다.** 금요일(150)의 중간 데모가 이 문장의 시험입니다.

## ③ 개념 설명

### 스탠드업 — 15분의 규격

| 각자 3문장 | 아닌 것 |
|---|---|
| ① 어제: 닫은 이슈 번호 | 작업 내용의 상세 설명 |
| ② 오늘: 닫을 이슈 번호 | 희망 사항 ("모델 쪽 보려고요") |
| ③ 막힘: 없거나, 무엇이 누구를 기다리는지 | 침묵 (막힘 은폐가 최악) |

15분의 목적은 보고가 아니라 **조정**입니다 — "③ 막힘"이 나오면 그 자리에서 풀지 말고
"누가 누구와 스탠드업 직후 15분"만 정하고 끝냅니다. 상세 논의가 시작되는 순간 스탠드업은
전원의 시간을 소모하는 회의가 됩니다.

### 수집 파이프라인의 4단 구조

```
호출(fetch) → 필터(2호선) → 검증(행수·타입·범위) → 적재(upsert)
```

[Day 043](../02-sql-pipeline/day-043.md)의 ETL 골격 그대로입니다. 검증이 적재 **앞**에
있는 것이 요점 — 이상한 데이터는 DB에 들어가기 전에 거부되어야 하고, 거부는 소리 내야
합니다(로그 + 실패 종료 코드). 조용한 성공보다 시끄러운 실패가 낫습니다.

### 한도 안에서의 백필 — 산수 먼저

956일 × 날짜당 1호출 = 956호출. 일 1,000회 제한이므로 산술로는 하루에 들어가지만,
**당일 수집·재시도·개발 중 테스트 호출이 같은 키를 씁니다.** 한산 팀의 계획: 백필은
하루 500일씩 이틀(오늘 500 + 내일 456), 여유분은 개발·재시도 몫으로. 한도 산수를 계획에
쓰는 것 — [Day 145](day-145.md) 리뷰 질문("호출 몇 번이죠?")의 반영입니다.

### PR 사이클 — 작게, 자주, 교차로

- PR 1개 = 이슈 1개 = 리뷰 가능한 크기 (팀 규칙: 500줄 이하)
- 리뷰 짝(서연↔지우 · 민준↔하람)이 24시간 내, 목표는 **당일**
- 리뷰는 "동작 확인 방법"을 실제로 실행해 보고 승인 — 완료의 정의(142)가 인수 조건

## ④ 단계별 실습

### Step 1. 첫 스탠드업 (09:30, 진행: 서연)

한산 팀의 첫 스탠드업 — 15분의 실제 모습:

```
서연: 어제 #5 스키마 병합. 오늘 #6 수집 스크립트. 막힘 없음.
민준: 어제 #9 mart 뷰 절반. 오늘 마무리 — 단, lag 피처 정의에서 서연과 컬럼명 맞출 것 있음.
지우: 어제 #12 입력 검증 완료. 오늘 #13 데모 페이지(더미 상대). 막힘 없음.
하람: 어제 인스턴스에 mlflow·airflow 컨테이너 추가(#14). 오늘 #15 수집 DAG — #6 병합 대기.
서연: 민준과는 직후 15분. 하람은 #6을 오후 2시 전 PR 목표로. 끝. (11분)
```

"#6 병합 대기"가 막힘으로 선언되고, 그 자리에서 마감 시각이 조정됐습니다 — 이것이
스탠드업이 하는 일의 전부이자 핵심입니다.

### Step 2. 수집 스크립트 구현 — #6 (1~4교시)

서연의 `src/pipeline/collect.py` 핵심부 (전체 구조는 [Day 043](../02-sql-pipeline/day-043.md)
의 골격):

```python
def fetch_daily(date_str: str) -> list[dict]:
    url = f"{BASE}/{KEY}/json/CardSubwayStatsNew/1/1000/{date_str}"
    data = requests.get(url, timeout=10).json()
    body = data.get("CardSubwayStatsNew")
    if body is None:                      # INFO-200 등 — 데이터 없음
        raise DataNotReady(date_str, data.get("RESULT", {}).get("CODE"))
    rows = [r for r in body["row"] if r["SBWY_ROUT_LN_NM"] == "2호선"]
    validate(rows, date_str)              # 행수 51 · 음수 금지 · 타입 (내일 상세)
    return rows

UPSERT = """
INSERT INTO subway_daily (use_ymd, station_id, boardings, alightings, reg_ymd)
VALUES (%(use_ymd)s, %(station_id)s, %(boardings)s, %(alightings)s, %(reg_ymd)s)
ON CONFLICT (use_ymd, station_id) DO UPDATE
SET boardings = EXCLUDED.boardings, alightings = EXCLUDED.alightings,
    reg_ymd = EXCLUDED.reg_ymd;
"""
```

동작 확인 — D-4 하루치:

```
$ python -m src.pipeline.collect --date 2026-08-13
[collect] 2026-08-13 · 응답 611행 → 2호선 51행 · 검증 통과 · upsert 51행 (신규 51 / 갱신 0)
$ python -m src.pipeline.collect --date 2026-08-13
[collect] 2026-08-13 · 응답 611행 → 2호선 51행 · 검증 통과 · upsert 51행 (신규 0 / 갱신 51)
```

**같은 명령을 두 번 실행한 로그까지가 PR의 "동작 확인"입니다** — 두 번째 줄이 멱등성의
증거입니다 (신규 0).

### Step 3. 백필 1일차 — #7 (5~6교시)

```
$ python -m src.pipeline.backfill --from 2024-01-01 --to 2025-05-14
[backfill] 500일 처리 · upsert 25,500행 · 실패 0 · API 호출 500회 (금일 잔여 여유 ~450)
$ psql -c "SELECT count(*), min(use_ymd), max(use_ymd) FROM subway_daily;"
 count  |    min     |    max
--------+------------+------------
  25551 | 2024-01-01 | 2026-08-13
```

25,551 = 백필 25,500 + Step 2의 하루 51행. 나머지 456일은 내일 아침 잔여 한도로 —
분할 계획이 계획대로 실행되고 있음을 스탠드업에서 보고할 수 있는 상태입니다.

### Step 4. PR 사이클 가동 (7~8교시)

#6 PR에 달린 지우(리뷰 짝)의 리뷰 — 교차 리뷰가 하는 일의 예:

```
지우: validate()가 실패하면 예외인데, DAG에서 이 스크립트를 부를 때(#15) 재시도와
     구분되나요? "데이터 아직 없음(재시도 대상)"과 "데이터가 이상함(사람 호출)"은
     다른 실패 같은데요.
서연: 좋은 지적 — DataNotReady(재시도)와 ValidationError(알림+중단)로 분리할게요.
```

서빙 담당이 파이프라인 PR에서 실패의 종류를 물었습니다 — 영역 교차 리뷰(141)가 설계
결함을 코드 단계에서 잡는 순간이고, 이 구분은 내일 DAG의 재시도 정책이 됩니다.

**오늘 퇴근 체크** — □ 스탠드업 15분 내 종료 □ 수집→적재 관통(멱등 로그 2회분)
□ 백필 1일차 25,500행 □ PR 최소 2개가 리뷰 거쳐 병합 □ 내일 백필 잔여분 계획 확인

## ⑤ 자주 하는 실수

### 스탠드업이 30분 보고회

**증상** — 각자 5분씩 작업 내용을 설명 — 30분 소모, 조정은 0건, 사흘째부터 다들 늦게 옴.
**원인** — 청중을 향한 보고(내가 일했음의 증명)로 오해.
**해결** — 3문장 규격(이슈 번호로 말하기)을 진행자가 강제하세요. 상세가 필요한 주제는
"직후 15분, 관련자만" — 스탠드업의 산출물은 정보가 아니라 **오늘의 조정 목록**입니다.

### 첫 PR부터 거대

**증상** — "수집 전체 구현" PR 1,400줄 — 리뷰 짝이 이틀을 붙잡고, 그동안 DAG(#15)는 대기.
**원인** — "완성해서 보여 주고 싶은" 마음 — 그러나 리뷰 불가능한 PR은 검증 없이 병합되거나
병목이 됩니다.
**해결** — 이슈를 쪼갰으면 PR도 쪼개집니다(#6이 크면 fetch/validate/upsert로). 오늘 팀에
필요한 것은 완벽한 수집기가 아니라 **돌아가는 사이클**입니다.

### 백필 스크립트를 일회용 취급

**증상** — 백필을 로컬에서 즉석 코드로 돌리고 스크립트는 버림 — 재현성 심사에서 "이
48,756행은 어떻게 만들었죠?"에 답할 코드가 없음.
**원인** — "한 번 쓰고 말 건데"의 유혹.
**해결** — 백필도 저장소의 코드입니다(`src/pipeline/backfill.py`, 수집과 같은 upsert
경로 재사용). "데이터의 재현 절차가 저장소에 있다"가 재현성 20점의 데이터 쪽 절반입니다.

### 검증 없이 적재부터

**증상** — 일단 다 넣고 나중에 정리 — 2주 뒤 이상치의 출처(원천의 문제인지 우리 버그인지)
를 판별할 수 없음.
**원인** — 검증을 완성도의 사치로 분류.
**해결** — 검증은 사치가 아니라 **경계 방어**입니다. 원천의 문제는 적재 전에 거부되어야
"우리 DB 안은 전부 검증 통과분"이라는 불변식이 성립하고, 그 불변식이 하류(모델·API)의
방어 코드를 전부 절약해 줍니다. 상세 규칙은 내일 확정합니다.

시작한 팀에게 생기는 일로 반증해 보세요.

모델부터 시작하면 실데이터가 없으므로 샘플·가짜 데이터로 개발하게 되고, 두 가지 부채가
쌓입니다. ① 모델 코드가 가짜 데이터의 형태(분포·컬럼·결측 패턴)에 적응해 실데이터 연결
시 재작업이 남 — 통합 실패의 후불제. ② 수집의 배신(한도·지연·형식)은 언제 시작하든
같은 크기로 존재하는데, 늦게 시작할수록 그 충격을 흡수할 잔여 일정이 없습니다. 불확실성
은 시간이 지나도 저절로 줄지 않고 접촉해야만 줄기 때문에, 접촉을 앞당기는 것이 유일한
관리 수단입니다 — 데이터 실재 확인(141)을 첫날 한 것과 같은 원리의 스프린트 판입니다.

</details>

**Q2.** 수집 스크립트의 실패를 DataNotReady와 ValidationError로 분리하라는 지우의 리뷰가
"운영 설계"인 이유를, 이 구분이 없을 때 DAG(자동 재시도)에서 벌어지는 두 가지 오작동으로
설명하세요.

<details>
<summary>답 보기</summary>

실패의 의미가 다르면 올바른 대응도 다릅니다. DataNotReady(아직 게시 안 됨)는 시간이
해결하므로 재시도가 정답이고, ValidationError(데이터가 이상함)는 재시도해도 같은 결과
이므로 사람 호출이 정답입니다. 구분이 없으면 ① 검증 실패를 재시도 — 같은 실패를 기계가
반복하며 알림 없이 조용히 리소스만 소모하거나, 반대로 ② 미게시를 즉시 알림 — 매일 새벽
"정상적인 아직"에 사람이 깨어나 알림 자체를 무시하게 됩니다(늑대 소년화). 예외 타입은
코드 스타일 문제가 아니라 **자동화 시스템에게 주는 대응 지침**이라는 것 — 서빙 담당이
이를 물은 것이 교차 리뷰의 가치입니다.

</details>

**Q3.** 멱등 upsert의 증거로 "같은 명령 2회 실행 로그(두 번째는 신규 0)"를 PR에 요구하는
규칙은 무엇을 자동화한 것인가요? 이 증거가 W31 이후 운영에서 갖는 의미도 설명하세요.

<details>
<summary>답 보기</summary>

완료의 정의(142)의 인수 검사를 리뷰 절차에 내장한 것입니다 — "멱등하다"는 주장을 말이
아니라 재현 가능한 로그로 제출하게 하므로, 리뷰어는 믿음이 아니라 증거로 승인합니다.
운영에서의 의미: 멱등성은 재시도의 전제 조건입니다([Day 043](../02-sql-pipeline/day-043.md)).
DAG의 자동 재시도, 장애 후 수동 재실행, 연휴 지연분의 늦은 도착(D-6) — 전부 "같은 날짜를
다시 적재해도 안전하다"에 기대며, 오늘 PR에 남긴 2회 실행 로그가 그 안전의 최초 증명
문서가 됩니다. 심사에서 "재수집하면 중복되지 않나요?"라는 질문의 답이 이미 저장소 PR
이력에 있는 셈입니다.

</details>
