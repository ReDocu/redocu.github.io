## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 중간 데모를 **슬라이드 없이 실행만으로** 진행할 수 있다.
- 파이프라인이 **팀원 누구의 환경에서도 재현**되는지 교차 검사할 수 있다.
- 스프린트 속도를 실측(계획 대비 닫힌 이슈)하고, 그 위에서 W31 백로그를 상세화할 수 있다.
- 회고(KPT)를 사람이 아니라 **프로세스를 수리하는** 회의로 운영할 수 있다.

## ② 왜 필요한가

스프린트의 마지막 날은 쉬어 가는 날이 아니라 **궤도를 수정하는 날**입니다. 2주짜리
스프린트 두 개로 구성된 이 프로젝트에서, 오늘은 방향타를 잡을 수 있는 사실상 유일한
공식 지점입니다 — 오늘 속인 진척은 다음 금요일(155)에 두 배로 돌아옵니다.

그래서 오늘의 세 활동은 전부 "사실 확인" 장치입니다. **데모**는 진척 보고를 말에서
실행으로 바꿉니다 — "거의 다 됐어요"는 실행 앞에서 즉시 참/거짓이 판명됩니다. **속도
실측**은 다음 주 계획을 희망에서 산수로 바꿉니다 — 이번 주 계획 15개 중 13개를 닫은
팀이 다음 주에 20개를 계획하는 것은 계획이 아니라 소원입니다. **회고**는 문제의 원인을
사람에서 프로세스로 옮깁니다 — 그래야 고칠 수 있는 것이 남습니다.

그리고 이번 주 체크포인트가 하나 걸려 있습니다: **"파이프라인이 팀원 누구의 환경에서도
재현되는가."** 내 노트북에서만 도는 파이프라인은 아직 팀의 파이프라인이 아닙니다 —
W28에서 배운 재현성 규율([Day 137](../05-infra-mlops/day-137.md))의 팀 버전 검사를
데모 전에 통과해야 합니다.

## ③ 개념 설명

### 중간 데모의 규격 — 실행 외엔 금지

| 규칙 | 이유 |
|---|---|
| 슬라이드 0장, 터미널과 화면만 | 데모의 목적은 설득이 아니라 검증 |
| 시나리오는 데이터의 여정 순서 | 수집 → DB → 학습 → 기록 → (화면) — 관통의 증명 |
| 안 되는 것은 "안 됩니다"라고 실행으로 보여줌 | 더미 구간의 정직한 공개 — 다음 주 계획의 근거 |
| 타 팀 청중은 질문 1개 이상 | 145 상호 리뷰의 속편 — 남의 눈 재투입 |

### 속도 실측 — 다음 주를 계획하는 유일한 근거

```
이번 주 속도 = 닫힌 이슈 수 / 계획 이슈 수     (한산: 13/15 = 0.87)
다음 주 용량 ≈ 닫힌 이슈 수 × 1.0             (더 늘려 잡지 않는 것이 규율)
```

"다음 주엔 더 잘하겠지"는 계획 근거가 아닙니다 — 다음 주에는 통합(모델↔API)과 배포라는
이번 주에 없던 마찰이 추가됩니다. 실측 속도 그대로가 낙관입니다.

### KPT의 수신인 — 다음 주의 우리

[Day 140](../05-infra-mlops/day-140.md)에서 세운 규칙 그대로: 모든 항목은 "그래서 다음
주에 무엇을 한다"로 번역 가능해야 합니다. 그리고 하나 더 — **Keep(잘된 것)도 원인을
분석**합니다. 잘된 것의 원인을 모르면 그것은 운이고, 운은 다음 주에 재현되지 않습니다.

## ④ 단계별 실습

### Step 1. 재현성 교차 검사 (1~2교시)

규칙: **파이프라인을 만들지 않은 사람이**, 자기 환경에서, README만 보고 실행합니다.
한산 팀은 지우(서빙 담당)가 검사자:

```
$ git clone git@github.com:team-hansan/hansan.git && cd hansan
$ cp .env.example .env   # 값 채움 (API 키 · DB 비밀번호)
$ docker compose up -d db && python -m src.pipeline.backfill --from 2026-08-01 --to 2026-08-13
[backfill] 13일 처리 · upsert 663행 · 실패 0
$ python -m src.train.train --config configs/train.yaml
[train] data_md5 ea31f2c8 · MAE 1201.4 ...   ← ⚠ 어제의 1146.3과 다르다!
```

**숫자가 다릅니다.** 원인 추적 10분: 지우의 백필이 8월 13일치뿐이라 데이터가 다름 —
당연히 다른 결과. 검사 절차를 수정합니다: 재현 검사는 "같은 데이터(백필 전체 또는 DB
덤프) + 같은 config → 같은 지표"로 정의. 서연이 pg_dump 스냅숏 경로를 README에 추가하고
재검:

```
$ psql < snapshots/subway_20260821.sql && python -m src.train.train --config configs/train.yaml
[train] data_md5 e91c07a4 · MAE 1146.3 · run 등록 OK   ← 재현 ✓
```

이 소동 자체가 오늘의 수확입니다 — "재현"의 정의(코드+데이터+설정의 삼위일체,
[Day 131](../05-infra-mlops/day-131.md))가 문서에 명문화됐습니다.

### Step 2. 중간 데모 — 15분 (3~4교시)

한산 팀의 시나리오 (전부 라이브 실행):

```
1. 수집:   python -m src.pipeline.collect --date 2026-08-17  → upsert 51행 (멱등 재실행 포함)
2. DB:     SELECT count(*) FROM subway_daily → 48,960   ("매일 51행씩 자라는 중")
3. 검증:   validate_all → 4층 통과 · 결측 이력 2건 관리 중
4. 학습:   train --config → MAE 1146.3 · MLflow 화면에서 exp-01→04 계단 + 선정 근거
5. 화면:   데모 페이지에서 강남·8시 조회 → "보통 (더미)" ← "이 더미가 다음 주 월요일에
           진짜가 됩니다 — 명세가 같아서 화면은 한 줄도 안 바뀝니다"
```

타 팀 질문: "재학습 게이트는 어디 있죠?" → "W31 백로그 #26 — 오늘 상세화합니다"
(145에서 수용한 그 이슈가 추적되고 있음을 보여 주는 답).

### Step 3. 회고 — KPT 30분 (5~6교시)

```
Keep   달력 피처의 도약 — 원인: 오차 분석이 실험 대기열을 정함 (감이 아니라)
       PR 24시간 리뷰 — 원인: 교차 짝 + 작은 PR 규칙이 지켜짐 (최대 PR 480줄)
Problem 민준의 이슈 2개 이월 — 원인: mart 뷰 협의(#9)가 이슈 크기 추정보다 컸음.
        사람 문제 아님 — "협의가 필요한 이슈"는 1일 추정이 항상 낙관임을 학습
       스탠드업이 수요일 22분 — 원인: 오차 분석 논의가 침입. "직후 15분" 규칙 재확인
Try    통합(모델↔API)을 월요일 오전에 몰지 말고 오늘 오후 30분 사전 연결 테스트
       협의성 이슈는 처음부터 2일로 추정
```

## ⑤ 자주 하는 실수

### 데모를 슬라이드로 대체

**증상** — "아키텍처는 이렇고요, 수집은 완료됐고요" — 15분 발표, 실행 0회. 다음 주
월요일에 "완료"였던 수집이 실은 로컬에서 한 번 돈 적 있는 상태였음이 드러남.
**원인** — 데모를 평가(잘 보여야 하는 것)로 오해 — 데모는 검증(사실을 확인하는 것)입니다.
**해결** — 규격을 강제하세요: 터미널 실행만, 슬라이드 금지. "실행되지 않는 진척은 진척이
아니다"가 이 과정 전체의 문법입니다 — 중간 데모는 그 문법의 팀 내 적용일 뿐입니다.

### 회고가 재판이 됨

**증상** — "민준이 이슈를 늦게 닫아서…" — 회고 후 팀 분위기 급랭, 다음 회고부터 아무도
Problem을 말하지 않음.
**원인** — 원인 분석이 사람에서 멈춤.
**해결** — 규칙: 원인은 반드시 **프로세스 언어**로 끝나야 합니다 ("추정 방식이 협의
비용을 무시했다" — 고칠 수 있는 것). 사람을 지목해서 얻는 수정은 위축뿐이고, 위축된
팀은 문제를 숨깁니다 — 회고의 최대 적은 문제가 아니라 침묵입니다.

### 속도를 무시한 다음 주 계획

**증상** — 13개 닫은 팀이 "다음 주는 다들 익숙해졌으니까" 19개 계획 — 수요일에 이미
6개 뒤처지고, 목요일부터 리뷰 생략·테스트 생략의 부채 질주 시작.
**원인** — 실측보다 의욕을 믿음.
**해결** — 용량 = 실측 × 1.0 규칙을 기계적으로 적용하세요. 통합·배포 주간은 오히려
마찰이 늘어납니다. 계획이 남으면 선택 기능(142의 목록)에서 당겨오면 그만 — 모자라는
것보다 남는 것이 압도적으로 쌉니다.

### Keep을 분석하지 않음

**증상** — "잘된 건 잘됐고요" 3초 만에 Problem으로 — 다음 주에 같은 성공을 재현하지
못하고 "지난주엔 됐는데 왜 안 되지?".
**원인** — 성공은 설명이 필요 없다는 착각.
**해결** — Keep에도 "원인:" 을 강제하세요 (한산 팀 형식). 달력 피처의 도약이 "민준이
잘해서"가 아니라 "오차 분석이 실험을 정하는 절차 덕"임을 적어 두면, 그 절차는 W31의
모니터링 설계(오차→개선의 순환)로 이식됩니다 — 성공의 원인 분석이 곧 프로세스의 복리
입니다.

검사의 목적은 통과가 아니라 발견이고, 일찍 실패하는 검사가 좋은 검사입니다.
