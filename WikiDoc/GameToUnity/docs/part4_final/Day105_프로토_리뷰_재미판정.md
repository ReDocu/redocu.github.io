## 3. 개념

### 3-1. 왜 외부 테스터인가

**왜 필요한가** — 만든 사람은 판단할 수 없다.

```
   ★ 만든 사람의 편향

   ① 조작을 안다 (테스터는 모른다)
   ② 목표를 안다
   ③ 어디에 뭐가 있는지 안다
   ④ 3일간 봤으므로 익숙하다
   ⑤ 만든 정이 있다
```

```
   ★ 외부 테스터가 보는 것

   "처음 30초에 무엇을 느끼는가"
   → 실제 플레이어와 같은 조건
```

```
   ⚠️ 팀원끼리의 테스트는 오늘의 목적이 아니다

   어제(Day 104) 이미 했다
   → 오늘은 반드시 외부
```

### 3-2. 관찰이 응답보다 정확하다

**왜 필요한가** — 사람은 자기가 왜 답답했는지 모른다.

```
   ★ 응답의 한계

   Q: "어디가 답답했나요?"
   A: "음... 잘 모르겠어요. 그냥 재밌었어요"

   → 배려하느라 부정적인 말을 안 한다
   → 또는 정말 언어화하지 못한다
```

```
   ★ 관찰로 알 수 있는 것

   ① 어느 화면에서 멈칫하는가
   ② 어떤 키를 반복해서 누르는가
   ③ 어디서 표정이 바뀌는가
   ④ 언제 몸을 앞으로 기울이는가
   ⑤ 언제 한숨을 쉬는가
```

```
   ★ 관찰 기록의 예

   0:05  타이틀에서 3초 정지 (뭘 눌러야 할지 모름)
   0:12  WASD 시도, 이동 확인
   0:20  좌클릭 여러 번 (공격인지 확인 중)
   0:45  주변을 두리번 (적을 찾는 중)  ★ 4명 공통
   1:10  적 3마리 연속 처치 → "오" 소리  ★ 재미 지점
   1:40  공격 후 멈춤 (후딜) → 살짝 눈살
   2:14  클리어 → 미소
```

```
   ★ 이 기록이 응답보다 정확하다
```

### 3-3. 절대 하면 안 되는 것

**왜 필요한가** — 한 마디로 테스트가 무의미해진다.

```
   ⚠️ 금지 사항

   ✗ "그건 이렇게 하는 거예요"
   ✗ "아, 거기 적이 있어요"
   ✗ "그 키를 누르면 돼요"
   ✗ "원래는 이런 게 들어갈 건데요"
   ✗ (한숨) (웃음) (안절부절)
```

```
   ★ 왜 안 되는가

   ① 그 순간 테스터가 "정상 플레이어"가 아니게 된다
   ② 막히는 지점을 발견할 기회를 잃는다
   ③ 테스터가 눈치를 보게 된다
```

```
   ★ 참는 것이 가장 어렵다

   내 게임에서 사람이 헤매는 것을 보는 건 고통스럽다
   → 하지만 그것이 정보다
```

```
   ★ 허용되는 개입

   ① 진행 불가 버그로 완전히 멈췄을 때
   ② 5분 이상 같은 곳에서 막혔을 때
   → 그때도 "막힌 지점"을 먼저 기록한다
```

### 3-4. 질문지

**왜 필요한가** — 구조화된 응답.

| 질문 | 응답 |
|---|---|
| 무엇을 하는 게임이라고 생각했나요? | |
| 목표가 무엇인지 알았나요? (설명 없이) | 예 / 아니오 |
| 가장 재미있던 순간은? | |
| 가장 답답했던 순간은? | |
| **한 번 더 하고 싶었나요?** | 예 / 아니오 |
| 이 게임에 무엇이 하나 추가되면 좋을까요? | |

```
   ★ 질문 순서에 의미가 있다

   ① 열린 질문 (게임 이해)
   ② 닫힌 질문 (목표 파악)
   ③ 긍정 (재미)
   ④ 부정 (답답)  ← ③ 다음에 물으면 솔직해진다
   ⑤ 핵심 지표    ★
   ⑥ 개선 제안
```

```
   ★ "한 번 더 하고 싶었나요?"가 핵심 지표다

   재미의 가장 단순하고 정확한 측정
```

```
   ⚠️ "재미있었나요?"라고 묻지 않는다

   → 대부분 "네"라고 답한다 (배려)
   → "한 번 더 하고 싶었나요?"는 훨씬 정직하다
```

```
   ★ 추가로 물으면 좋은 것

   "이 게임을 친구에게 추천하겠어요?"  (NPS 방식)
   "3단어로 표현한다면?"
```

### 3-5. 완주율과 소요 시간

**왜 필요한가** — 객관적 수치.

```
   ★ 기록할 것

   테스터 | 완주 | 시간  | 사망 | 재시도
   ───────────────────────────────────
   A      | ✔    | 2:31 | 1    | 1
   B      | ✔    | 1:58 | 0    | 0
   C      | ✗    | —    | 3    | 2
   D      | ✔    | 3:12 | 2    | 1
   E      | ✔    | 2:05 | 0    | 0
```

```
   ★ 해석

   완주율 80% (4/5)
   → 난이도 적정

   완주율 20%
   → 너무 어렵다

   완주율 100% + 사망 0
   → 너무 쉽다
```

```
   ★ 재시도 횟수

   "졌는데 다시 했다"
   → 재미의 강력한 신호  ★
```

### 3-6. 판정 기준

**왜 필요한가** — 감정이 아니라 기준으로 결정한다.

| 판정 | 신호 | 대응 |
|---|---|---|
| **통과** | "한 번 더" 응답이 과반 | 그대로 W22 진행 |
| **범위 축소** | 재미는 있으나 구현량 과다 | 콘텐츠·기능을 깎고 진행 |
| **피벗** | 무엇을 하는 게임인지 전달 안 됨 | **오늘 안에** 핵심 루프를 바꾼다 |

```
   ★ 세부 신호
```

**통과 신호**

```
   ○ "한 번 더" 4/5 이상
   ○ 재미있던 순간이 구체적으로 나온다
   ○ 여러 명이 같은 순간을 꼽는다
   ○ 자발적 재시도가 있었다
```

**범위 축소 신호**

```
   △ "한 번 더" 3/5 정도
   △ 재미는 있으나 "이것도 있으면"이 많다
   △ 우리가 계산한 일수 > 남은 일수
   △ 구현이 W21 계획보다 늦었다
```

**피벗 신호**

```
   ✗ "무슨 게임인지 모르겠다" 다수
   ✗ "한 번 더" 2/5 이하
   ✗ 재미있던 순간을 못 꼽는다
   ✗ 우리 팀도 플레이하기 싫다  ★ 가장 확실한 신호
```

```
   ★ "우리도 재미없다"

   가장 정직한 신호다
   → 인정하기 어렵지만 인정해야 한다
```

### 3-7. 피벗하는 법

**왜 필요한가** — 오늘만 가능한 선택.

```
   ★ 피벗 = 핵심 루프를 바꾼다

   전부 버리는 것이 아니다
```

```
   ★ 살릴 것

   ① 이동·조작 코드 (Day 102)
   ② 판정·체력 코드 (Day 103)
   ③ 상태 머신 (Day 104)
   ④ 프로젝트 세팅 (Day 101)

   → 대부분 살아남는다
```

```
   ★ 바꿀 것

   핵심 루프의 "규칙" 하나
```

```
   ★ 피벗의 예

   원래: "무기를 버려야 다음 층"
   → 테스터: "무기 교체가 귀찮다"

   피벗 A: 무기를 합쳐서 강화 (버리지 않는다)
   피벗 B: 무기 대신 능력 선택 (로그라이크 방식)
   피벗 C: 무기 교체를 선택으로 (강제 해제)
```

```
   ★ 피벗 절차 (오후 2시간)

   ① "무엇이 재미없었나"를 한 문장으로
   ② 그 원인이 되는 규칙을 찾는다
   ③ 그 규칙만 바꾼 대안 3개
   ④ 팀이 하나를 고른다
   ⑤ GDD의 핵심 루프를 다시 그린다
   ⑥ 일정표를 갱신한다
```

```
   ⚠️ 완전히 다른 게임으로 바꾸지 않는다

   "액션이 안 되니 퍼즐로"
   → 3일치 코드를 버린다
   → 남은 3주로 새 게임은 무리
```

### 3-8. 범위 축소하는 법

**왜 필요한가** — 가장 흔한 판정.

```
   ★ 축소 기준 (Day 98과 같다)

   ① 핵심 루프에 없는 것부터
   ② 시스템은 남기고 수량을 줄인다
   ③ 재미의 원천은 절대 건드리지 않는다
```

```
   ★ 축소 예시
```

| 항목 | 전 | 후 | 절감 |
|---|:--:|:--:|:--:|
| 층 | 8 | 6 | 0.5일 |
| 적 종류 | 3 | 3 | — (재미의 원천) |
| 무기 | 4 | 3 | 0.4일 |
| 보스 패턴 | 2 | 1 | 1.0일 |
| 아이템 | 3 | 0 | 1.0일 (Should → Won't) |
| **합계** | | | **2.9일** |

```
   ★ 절감분을 어디에 쓰나

   ① 버퍼로 남긴다      ★ 권장
   ② 테스터가 지적한 문제 해결
   ③ 재미의 원천을 더 다듬는다
```

```
   ⚠️ 절감분으로 새 기능을 넣지 않는다

   → Day 105 이후 범위 확대 금지
```

### 3-9. 피드백 우선순위

**왜 필요한가** — 전부 반영할 수 없다.

```
   ★ 반영 판단
```

| 조건 | 판단 |
|---|---|
| **여러 명이 같은 지점에서 막힘** | **반영** (설계 문제) |
| 한 명의 취향 의견 | 보류 |
| 5분 이내 수정 + 개선 명확 | 반영 |
| 새 기능이 필요함 | 보류 (또는 제외) |
| 핵심 루프를 바꿔야 함 | 오늘 결정 |

```
   ★ 오늘 나온 예
```

| 피드백 | 인원 | 판단 | 대응 |
|---|:--:|---|---|
| 적이 어디 있는지 모름 | 4 | **반영** | 스폰 위치 표시 또는 범위 축소 |
| 공격 후딜이 길다 | 2 | **반영** | recovery 0.25 → 0.18 |
| 무기 교체가 헷갈림 | 2 | 반영 | 안내 텍스트 |
| 회피가 짧다 | 1 | 보류 | 취향 |
| 보스가 있으면 좋겠다 | 1 | (이미 계획) | — |
| 멀티플레이 | 1 | **제외** | 범위 밖 |

```
   ★ 반영 항목을 이슈로 등록한다

   → W22 일정에 배치
```
