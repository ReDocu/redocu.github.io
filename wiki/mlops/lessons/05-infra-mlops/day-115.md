## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 변수·조건·반복과 `set -euo pipefail` 을 갖춘 **bash 스크립트**를 작성할 수 있다.
- 어제의 RUNBOOK을 **한 줄로 실행되는 배포 스크립트**(deploy.sh)로 바꿀 수 있다.
- sudo 불가 계정에게 **딱 한 명령만** 허용하는 sudoers 설정을 할 수 있다.
- **cron**으로 W06의 수집 파이프라인을 매일 자동 실행하고, 그 로그를 남길 수 있다.
- 이번 주 체크포인트에 답한다: **서버가 재부팅돼도 API가 살아나고, 로그 위치를 아는가.**

## ② 왜 필요한가

어제의 과제(RUNBOOK.md)를 보세요 — 명령이 예닐곱 줄입니다. 문서가 있으니 안심입니까?
수동 절차는 **실행할 때마다 사람의 컨디션이 변수**입니다: 바쁜 금요일엔 pytest를 건너뛰고,
새로 온 팀원은 3번을 두 번 실행하고, 새벽 장애 대응 중엔 restart를 잊습니다.

```
문서(RUNBOOK)     사람이 읽고 → 사람이 실행     실수 확률 × 실행 횟수
스크립트(deploy.sh)  사람이 읽고 → 기계가 실행     실수는 코드 리뷰에서 한 번만 잡으면 됨
```

문서를 스크립트로 바꾸는 것이 자동화의 첫 계단이고, W26의 CI/CD는 그 스크립트를
"사람이 실행"에서 "**이벤트(push)가 실행**"으로 바꾸는 둘째 계단일 뿐입니다.

그리고 오래된 약속 하나를 갚습니다 — [Day 030](../01-python-data/day-030.md) 마지막에
"이 파이프라인은 매일 새벽 cron으로 돈다"며 보여 드렸던 그 한 줄, 기억합니까? 그때는 읽기만
했지만 오늘은 **진짜 서버의 crontab에 심습니다.** `datapipe run` 이 종료 코드를 성실히
반환하도록 설계했던 것([Day 029](../01-python-data/day-029.md)·030)이 오늘 보상받습니다 —
자동화는 종료 코드를 먹고 자랍니다.

## ③ 개념 설명

### bash 스크립트 — 명령들의 파이썬화

여러분은 이미 프로그래머라서, 대응표만 있으면 됩니다:

| 파이썬에서 | bash에서 | 예 |
|---|---|---|
| 변수 | `이름=값` (공백 금지!) · 사용은 `$이름` | `APP_DIR=/opt/mlops-mp3` |
| 인자 | `sys.argv[1]` | `$1` (스크립트 첫 인자) |
| if | `if [ 조건 ]; then ... fi` | `if [ -f .env ]; then` |
| for | `for x in a b c; do ... done` | `for i in 1 2 3; do` |
| 함수의 성공/실패 | **종료 코드** — 0이면 성공 | `if git pull; then` (Day 030에서 본 그 형태) |

그리고 스크립트 머리에 반드시 넣을 안전벨트:

```bash
#!/bin/bash
set -euo pipefail
```

| 옵션 | 뜻 | 없으면 생기는 일 |
|---|---|---|
| `-e` | 명령 하나라도 실패(≠0)하면 **즉시 중단** | pytest가 깨졌는데 restart까지 진행 — 반쯤 배포 |
| `-u` | 미정의 변수 사용 시 에러 | 오타 `$APP_DIRR` 가 빈 문자열로 — `rm -rf /` 계열 참사 |
| `-o pipefail` | 파이프 중간의 실패도 실패로 | `cmd | tee log` 에서 cmd가 죽어도 성공 처리되는 것 방지 |

### sudoers — "이 명령 하나만" 빌려주기

deploy는 sudo 불가(Day 112의 설계)인데 배포 마지막엔 `systemctl restart` 가 필요합니다.
전권을 주는 대신 **딱 한 줄만** 허용합니다 — `sudo visudo -f /etc/sudoers.d/deploy` 로:

```
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart mp3-api
```

deploy는 이제 이 **한 명령만** sudo로, 비밀번호 없이(자동화 필수) 실행할 수 있습니다.
다른 systemctl은 여전히 거부 — 최소 권한 원칙이 명령 단위까지 내려온 형태입니다.

### cron — 서버의 자명종

cron은 "시각표대로 명령을 실행"하는 오래된 데몬입니다. 등록은 `crontab -e`, 형식은 다섯 필드:

```
분  시  일  월  요일   명령
0   3   *   *   *      /opt/datapipe/run_daily.sh
│   │   └───┴───┴── * = 매번
│   └── 새벽 3시
└── 0분
```

| 예 | 뜻 |
|---|---|
| `0 3 * * *` | 매일 03:00 |
| `*/10 * * * *` | 10분마다 |
| `0 9 * * 1` | 매주 월요일 09:00 |

cron의 3대 성질 — 전부 이번 주 배운 것의 시험대입니다:

1. **환경이 없다시피 하다** — PATH 최소, venv도 .bashrc도 없음 → **절대 경로**로만 쓴다 (Day 113 ExecStart와 같은 원리)
2. **출력을 안 남기면 증발한다** → `>> 로그 2>&1` 필수 (Day 111의 리다이렉션)
3. **실패해도 다시 실행된다** → 명령이 **멱등**이어야 한다 ([Day 043](../02-sql-pipeline/day-043.md)이 여기를 위한 준비였습니다)

## ④ 단계별 실습

### Step 1. 스크립트 손 풀기 (1~2교시)

서버(WSL)의 `~/lab` 에서 안전벨트의 효과부터 실험합니다:

```bash
cat > guard_test.sh <<'EOF'
#!/bin/bash
set -euo pipefail
echo "1단계 완료"
false                      # 실패하는 명령 (종료 코드 1)
echo "2단계 완료 — 이 줄이 보이면 안 됩니다"
EOF
chmod +x guard_test.sh
./guard_test.sh; echo "스크립트 종료 코드: $?"
```

```
$ ./guard_test.sh; echo "스크립트 종료 코드: $?"
1단계 완료
스크립트 종료 코드: 1
```

`set -e` 가 실패 지점에서 즉시 멈췄고, 실패가 종료 코드로 **전파**됐습니다. 이 전파가 있어야
"스크립트를 부른 쪽"(cron, CI, 사람)이 성공/실패를 알 수 있습니다. `set -e` 를 지우고 다시
실행해 "2단계 완료"가 태연히 찍히는 것도 확인하세요 — 그것이 반쯤 배포 사고의 얼굴입니다.

### Step 2. RUNBOOK → deploy.sh (3~4교시)

어제의 문서를 코드로 옮깁니다. deploy 계정으로 `/opt/mlops-mp3/deploy.sh`:

```bash
#!/bin/bash
# deploy.sh — mlops-mp3 배포 (RUNBOOK.md의 코드화, Day 115)
set -euo pipefail

APP_DIR=/opt/mlops-mp3
HEALTH_URL=http://localhost:8000/health

echo "[1/5] 코드 갱신"
cd "$APP_DIR"
git pull

echo "[2/5] 의존성 동기화"
.venv/bin/pip install -q -r requirements.txt

echo "[3/5] 테스트 — 실패하면 여기서 중단됩니다"
.venv/bin/pytest -q

echo "[4/5] 서비스 재시작"
sudo systemctl restart mp3-api

echo "[5/5] 헬스체크 (최대 10초 대기)"
for i in $(seq 1 10); do
    if curl -sf "$HEALTH_URL" > /dev/null; then
        echo "배포 성공: $(curl -s $HEALTH_URL)"
        exit 0
    fi
    sleep 1
done
echo "배포 실패: 헬스체크 10초 초과 — journalctl -u mp3-api 를 확인하세요"
exit 1
```

설계 포인트 세 개 — ① 테스트가 재시작보다 **앞** (깨진 코드는 서비스에 닿기 전에 차단),
② 헬스체크는 재시도 루프 (재시작 직후엔 모델 로드 중일 수 있음 — [Day 096](../04-deep-learning-serving/day-096.md)의
로드 시간이 여기 반영), ③ 성공이든 실패든 **종료 코드로 보고**.

sudoers 한 줄을 넣고 (③ 절의 그 줄, student 계정에서 `sudo visudo -f /etc/sudoers.d/deploy`),
실행합니다:

```bash
chmod +x deploy.sh
./deploy.sh
```

```
$ ./deploy.sh
[1/5] 코드 갱신
Already up to date.
[2/5] 의존성 동기화
[3/5] 테스트 — 실패하면 여기서 중단됩니다
.......                                                              [100%]
7 passed in 5.94s
[4/5] 서비스 재시작
[5/5] 헬스체크 (최대 10초 대기)
배포 성공: {"status":"ok","model_loaded":true,"model_version":"resnet18-antbee-v1","started_at":"2026-08-14T02:12:39+00:00"}
```

이제 어제의 "ssh 뒤에 명령" 형태와 합치면 — **내 PC에서 한 줄 배포**가 완성됩니다:

```powershell
ssh deploy@localhost -p 2222 "/opt/mlops-mp3/deploy.sh"
```

이 한 줄을 기억해 두세요. W26에서 GitHub Actions가 치게 될 바로 그 줄입니다.

### Step 3. 실패 리허설 (5교시)

성공하는 자동화는 반쪽입니다 — **실패가 안전한지**가 나머지 반쪽. 일부러 테스트를 깨뜨리고
(tests/test_api.py의 기대값 하나 수정 → 커밋·푸시) 배포를 걸어 봅니다:

```bash
./deploy.sh; echo "종료 코드: $?"
```

```
$ ./deploy.sh; echo "종료 코드: $?"
[1/5] 코드 갱신
[2/5] 의존성 동기화
[3/5] 테스트 — 실패하면 여기서 중단됩니다
......F                                                              [100%]
=================================== FAILURES ===================================
______________________ test_health_reports_model _______________________________
...
1 failed, 6 passed in 6.02s
종료 코드: 1
```

**서비스는 재시작되지 않았고**(4단계 미도달), 기존 버전이 계속 돌고 있습니다 —
`curl localhost:8000/health` 로 확인하세요. 이것이 `set -e` 와 "테스트 먼저" 배치가 만드는
안전입니다. 깨뜨린 테스트는 revert([Day 109](day-109.md)!)로 복구하고 재배포해 둡니다.

### Step 4. cron — W06 파이프라인, 드디어 무인 가동 (6~7교시)

`datapipe` 를 서버에 설치하고 (deploy 계정, `/opt/datapipe` 에 clone + venv — Step 2와 같은
요령), 먼저 **1분 주기로 임시 등록**해 동작을 검증합니다. `crontab -e` (deploy 계정에서):

```
* * * * * cd /opt/datapipe && venv/bin/datapipe run >> /home/deploy/datapipe_cron.log 2>&1
```

2분쯤 기다렸다가:

```bash
crontab -l
grep CRON /var/log/syslog | tail -2
tail -3 ~/datapipe_cron.log
```

```
$ grep CRON /var/log/syslog | tail -2
Aug 14 14:31:01 DESKTOP CRON[7412]: (deploy) CMD (cd /opt/datapipe && venv/bin/datapipe run >> /home/deploy/datapipe_cron.log 2>&1)
Aug 14 14:32:01 DESKTOP CRON[7488]: (deploy) CMD (cd /opt/datapipe && venv/bin/datapipe run >> /home/deploy/datapipe_cron.log 2>&1)
$ tail -3 ~/datapipe_cron.log
[2026-08-14 14:32:03] INFO  run 완료: fetch=skip(캐시) clean=ok save=ok (2.1s)
```

두 가지를 관찰하세요 — ① syslog가 "cron이 실행했다"는 사실을, 내 로그가 "무엇이 어떻게 됐다"를
나눠 맡습니다. ② 1분마다 돌아도 사고가 없는 것은 `datapipe run` 이 **멱등**이기 때문입니다
(같은 날짜 재실행 = 캐시 skip — Day 030의 그 설계). 검증이 끝나면 시각표를 실전으로 교체합니다:

```
0 3 * * * cd /opt/datapipe && venv/bin/datapipe run >> /home/deploy/datapipe_cron.log 2>&1
```

Day 030에서 "언젠가 이렇게 돌 것"이라던 줄이, 오늘부로 **돌고 있는 줄**이 됐습니다.

> **WSL 한정 주의** — cron은 WSL이 켜져 있어야 돕니다 (진짜 서버는 24시간이라 무관).
> 그리고 cron의 한계 — "실패하면? 단계 간 의존은? 재시도는?" — 를 기록해 두세요.
> 그 질문들의 정식 답이 [Day 133](day-133.md)의 Airflow입니다.

### 오늘 새로 나오는 실수

### cron에서만 command not found

**증상** — 손으로 돌리면 되는데 cron 로그엔:
```
/bin/sh: 1: datapipe: not found
```
**원인** — cron의 PATH는 빈약하고 venv도 활성화되지 않습니다. "내 셸의 환경"은 상속 재산이지
전역이 아니라는 것 (Day 112) — cron은 내 셸의 자식이 아닙니다.
**해결** — crontab의 명령은 전부 **절대 경로**: `venv/bin/datapipe` 처럼 venv 안 실행 파일을
직접. cd가 필요하면 명령 안에 명시 (오늘 실습의 형태가 그것입니다).

### 출력 리다이렉션 없는 cron

**증상** — 파이프라인이 며칠째 안 돌았는데 아무도 몰랐음. 로그? 없음.
**원인** — cron은 출력을 버리거나(메일 미설정 시) 어딘가로 보내 버립니다 — 남기지 않으면 증발.
**해결** — 모든 cron 항목에 `>> 파일 2>&1` 을 관례로. "로그 없는 자동화는 자동화가 아니라
방치"입니다. 더 나아가 실패 알림이 필요해지는 시점이 Airflow([Day 133](day-133.md))로 넘어갈 신호입니다.

### set -e를 빼먹은 배포 스크립트

**증상** — pytest가 깨졌는데 스크립트는 restart까지 완주 — 깨진 코드가 서비스에 올라감.
**원인** — bash의 기본값은 "실패해도 다음 줄 계속"입니다.
**해결** — 모든 운영 스크립트 첫 줄 밑에 `set -euo pipefail`. 그리고 순서 설계 — 검증(테스트)이
파괴적 단계(재시작)보다 반드시 앞에 오게. 오늘 Step 3의 실패 리허설을 스크립트 만들 때마다
한 번씩 하는 습관이 최고의 보험입니다.

### visudo 안 쓰고 sudoers 직접 편집

**증상** — sudoers에 오타 → **모든 sudo가 고장** → 고치려면 sudo가 필요한 순환 감옥.
**원인** — sudoers는 문법 오류에 관용이 없는 파일입니다.
**해결** — 반드시 `sudo visudo -f /etc/sudoers.d/파일` 로 — 저장 시 문법 검사를 통과해야만
반영됩니다. 이미 잠겼다면 복구 셸(WSL은 `wsl -u root`)로 들어가 수정합니다.

### 1분 검증 crontab을 실전용으로 방치

**증상** — 검증용 `* * * * *` 를 지우지 않아 파이프라인이 하루 1,440번 실행 — API 쿼터 소진.
**원인** — 검증 단계와 운영 단계의 설정을 같은 자리에서 편집하다 교체를 잊음.
**해결** — 검증 후 **즉시** 실전 시각표로 교체하고 `crontab -l` 로 최종 상태를 확인하는 것까지가
한 절차입니다. 멱등 설계(캐시 skip) 덕에 오늘은 사고가 아니었다는 점도 확인해 두세요 — 멱등성은
이런 실수까지 흡수하는 방어막입니다.

## ⑥ 확인 문제

**Q1.** deploy.sh에서 pytest를 systemctl restart보다 앞에 둔 것과, W26에서 "CI 통과 없이 병합
불가"를 거는 것이 같은 원리임을 설명하세요.

<details>
<summary>답 보기</summary>

둘 다 **검증을 파괴적 단계 앞에 배치해, 실패 시 서비스가 무사한 상태로 남게** 하는 설계입니다.
deploy.sh는 "테스트 실패 → set -e 중단 → 기존 버전 계속 서빙", CI 게이트는 "테스트 실패 → 병합
차단 → main(=배포 대상)이 늘 통과 상태 유지". 검증 지점이 서버냐 저장소냐만 다를 뿐, "깨진 것은
앞 단계에서 멈춘다"는 동일 원리이고, W26은 이 검증을 사람 손에서 이벤트(push)로 옮길 뿐입니다.

</details>

**Q2.** cron 항목 `0 3 * * * cd /opt/datapipe && venv/bin/datapipe run >> ... 2>&1` 에서,
이번 주에 배운 개념이 적용된 지점을 세 군데 이상 찾아 각각 한 줄로 설명하세요.

<details>
<summary>답 보기</summary>

① `venv/bin/datapipe` 절대 경로 — cron은 셸 환경(PATH·venv)을 상속받지 않으므로 (Day 112의
상속 원리, Day 113 ExecStart와 동일). ② `>> 파일` — 출력 리다이렉션으로 로그를 남김 (Day 111).
③ `2>&1` — 에러 스트림을 합류시켜 실패 원인까지 한 파일에 (Day 111). ④ deploy 계정의
crontab — 최소 권한으로 실행 (Day 112). ⑤ 매일 재실행돼도 안전한 것은 datapipe run의 멱등성
(Day 030·043) 덕분.

</details>

**Q3.** sudoers에 `NOPASSWD: /usr/bin/systemctl restart mp3-api` 만 허용한 상태에서, 공격자가
deploy 계정을 탈취했다고 가정합니다. 공격자가 이 sudo 권한으로 할 수 있는 것과 없는 것을
구분하고, 이 설계의 의도를 쓰세요.

<details>
<summary>답 보기</summary>

할 수 있는 것: mp3-api 서비스의 재시작(서비스 순단 유발) 뿐입니다. 할 수 없는 것: stop/disable
(명령이 restart로 고정), 다른 서비스 조작, 패키지 설치, 계정 관리, 파일 열람 등 그 외 전부 —
sudoers가 **명령 문자열 단위**로 허용하기 때문입니다. 의도: 자동화(무인 배포)에 필요한 최소
동작만 뚫어 두어, 계정 탈취 시 피해를 "서비스 재시작 남발" 수준으로 묶는 것 — Day 112 최소
권한 원칙의 명령 단위 적용입니다.

</details>

## 주간 퀴즈 20 — W23 (Linux 서버 운영)

<details>
<summary>1. 처음 보는 서버에서 설정·로그·서비스 코드는 각각 어디부터 찾는가?</summary>

설정 /etc · 로그 /var/log · 직접 설치한 서비스 /opt. 표준 배치라 모든 리눅스 서버에서 통합니다.

</details>

<details>
<summary>2. `2>&1` 의 뜻과, cron·서버 스크립트에서 필수인 이유는?</summary>

표준 에러(2)를 표준 출력(1)이 가는 곳으로 합류. 무인 실행은 지켜보는 사람이 없어, 에러가 로그 파일에 함께 남지 않으면 실패 원인이 증발합니다.

</details>

<details>
<summary>3. 600 / 644 / 755 의 뜻과 대표 용도는?</summary>

600 주인만 읽쓰(시크릿: .env·SSH 비밀키) · 644 주인 읽쓰+남 읽기(일반 파일) · 755 주인 전부+남 읽기·실행(폴더·스크립트). r=4, w=2, x=1의 합.

</details>

<details>
<summary>4. 서비스 계정(deploy)을 sudo 그룹에 넣지 않는 이유는?</summary>

최소 권한 — 서비스가 뚫려도 피해 반경을 그 계정의 소유물로 제한. 꼭 필요한 명령(재시작)만 sudoers에 한 줄로 허용합니다.

</details>

<details>
<summary>5. nohup &와 systemd 서비스의 결정적 차이 두 가지는?</summary>

죽었을 때 자동 재시작(Restart=)과 재부팅 시 자동 기동(enable) — 항상성. 로그가 journal로 관리되는 것도 큰 차이.

</details>

<details>
<summary>6. 유닛 파일 수정 후 반영 절차는?</summary>

sudo systemctl daemon-reload → restart. systemd는 유닛을 캐시하므로 파일 수정만으로는 반영되지 않습니다.

</details>

<details>
<summary>7. SSH에서 서버에 저장되는 것은 무엇이고, 비밀키가 안전한 이유는?</summary>

서버엔 공개키(authorized_keys)만. 비밀키는 내 PC를 떠나지 않고 네트워크도 타지 않으며, 공개키로 역산 불가 — 서버 유출·도청에 모두 안전.

</details>

<details>
<summary>8. Connection refused와 timed out의 진단 차이는?</summary>

refused = 도달했지만 듣는 프로세스 없음(sshd 죽음·포트 오류 → 서버 쪽 status/ss 확인). timed out = 도달 자체가 안 됨(방화벽·보안 그룹·주소 → 네트워크 층 확인).

</details>

<details>
<summary>9. cron 명령이 절대 경로여야 하는 이유는?</summary>

cron은 내 셸의 자식이 아니라 PATH·venv·환경 변수를 상속받지 않기 때문 — systemd ExecStart와 같은 원리입니다.

</details>

<details>
<summary>10. set -euo pipefail 각각이 막는 사고는?</summary>

-e: 중간 실패 후 계속 진행(반쯤 배포). -u: 오타 변수가 빈 문자열로 실행(경로 참사). -o pipefail: 파이프 앞 명령의 실패 은폐.

</details>

  경로·리다이렉션·멱등성, 이번 주와 지난 단원들의 합작입니다.
