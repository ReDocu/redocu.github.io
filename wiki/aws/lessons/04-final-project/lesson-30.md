## ① 학습 목표

이 강을 마치면 이렇게 할 수 있습니다.

- 계획된 장애로 **팀의 대응 절차를 시험**(게임데이)할 수 있다.
- **MTTD/MTTR을 측정**하고 장애 3종을 탐지→복구까지 완주할 수 있다.
- 처음 보는 사람도 따라 할 수 있는 **런북**을 작성할 수 있다.
- 비난 없는 회고로 **재발 방지책을 도출**할 수 있다.
- EventBridge+Lambda로 **야간 자동 축소**를 구현해 비용을 줄일 수 있다.

## ② 왜 필요한가

29강까지 우리는 서비스를 만들고 관측했습니다. 그런데 [16강](../02-compute-data/lesson-16.md)의 그 문장이 아직 유효합니다.

> **"장애를 겪어 보지 않은 고가용성은 가설이다."**

M1에서 "AZ 하나 죽어도 지속"이라 설계했고, Multi-AZ와 2AZ ASG로 구현했습니다. 하지만 **정말 그런지 확인한 적이 없습니다.** 26강 M1 리뷰에서 던진 "죽는 시나리오"들 — 지금 실제로 일으켜 봅니다.

```
 [게임데이 없는 팀]
  진짜 장애 발생 → 처음 겪음 → 우왕좌왕 → 런북은 없거나 안 통함 → 긴 다운타임

 [게임데이 한 팀]
  계획된 장애로 미리 연습 → 런북 검증됨 → 진짜 장애 시 침착하게 → 짧은 다운타임
```

게임데이는 대부분의 교육 과정이 생략하는 부분입니다. 하지만 이것이 **"만들 줄 안다"와 "운영할 줄 안다"를 가르는 지점**입니다. 소방 훈련을 안 한 건물이 진짜 불이 나면 어떻게 되는지 생각해 보세요.

오늘 M3를 완성합니다 — 장애 3종을 탐지·복구하고, 그 과정을 런북과 회고로 남깁니다. 그리고 이 과정 최대 골칫거리인 **비용**을 야간 자동 축소로 마지막으로 손봅니다.

## ③ 워크숍 가이드 — 게임데이 진행법

### 게임데이란

**계획된 장애를 통제된 환경에서 주입해 시스템과 팀의 대응을 시험**하는 훈련. 목적은 시스템을 고치는 것이 아니라 **대응 절차(사람 + 자동화)를 검증**하는 것입니다.

### 측정할 두 시계

```
 장애 발생 ──[인지]──[복구 완료]──▶
          │◀ MTTD ▶│◀── MTTR ──▶│

 MTTD(평균 탐지 시간): 발생 → 인지  ← 알람이 좋을수록 짧다
 MTTR(평균 복구 시간): 인지 → 복구  ← 런북·자동화가 좋을수록 짧다
```

> 🔑 **이상적 게임데이 — 발견자가 사람이 아니라 알람**이어야 합니다. MTTD가 "사용자 신고까지 38분"이면 [29강](lesson-29.md) 관측성이 부족한 것입니다.

### 장애 시나리오 3종 (M1 리뷰 지적과 연결)

| 시나리오 | 주입 방법 | 검증하는 설계 |
|---|---|---|
| **A. 컴퓨팅 장애** | 태스크 절반 강제 종료 | ASG/서비스 자동 복구, 2AZ 분산 |
| **B. 데이터 계층 장애** | RDS 강제 장애 조치 | Multi-AZ 자동 전환, 앱 재연결 |
| **C. 의존성/설정 장애** | SG 규칙 삭제 or 시크릿 훼손 | 증상→원인 추적 능력(런북) |

> C가 가장 어렵습니다 — A·B는 "무엇이 죽었는지" 알지만, C는 **증상만 보고 원인을 찾아야** 합니다. 실제 장애가 대개 이렇습니다.

### 좋은 런북의 조건

```
 나쁜 런북: "DB 문제면 복구하면 됨"
 좋은 런북:
   [증상] 5XX 급증 + DatabaseConnections 급락 알람
   [확인] aws rds describe-db-instances ... Status 확인
   [판단] 5분 내 자동 복구 없으면 개입
   [복구] (구체적 명령)
   [검증] 신청 COUNT 확인, 스모크 테스트
   [에스컬레이션] 15분 내 미복구 시 강사/팀장 호출
```

**핵심 — 새벽 3시에 처음 보는 당직자가 따라 할 수 있는가.** 작성자만 아는 표현·생략은 실패입니다.

### 비난 없는 회고(Blameless Postmortem)

```
 ❌ "누가 SG를 지웠어?"        → 사람을 탓함 → 숨김 → 재발
 ✅ "왜 SG를 실수로 지울 수     → 시스템을 고침 → 가드레일 추가
     있었고, 어떻게 막을까?"
```

사람은 다시 실수합니다. **재발을 막는 것은 절차와 자동화**입니다 — 콘솔 쓰기 권한 회수, 드리프트 알람, IaC 강제 등.

### 게임데이 안전 수칙

| 수칙 | 이유 |
|---|---|
| 사전에 시나리오 공유 + 강사 확인 | 통제된 실험이어야 |
| 자기 팀 리소스만 | 타 팀 영향 금지 |
| 데이터 백업 확인 후 | B 시나리오 전 스냅샷 |
| 원복 계획 준비 | 훼손한 설정을 되돌릴 방법 |

## ④ 스프린트 작업 — 게임데이 + 야간 자동 축소

> 💰 **예상 비용 $0.5 ~ 1.0/팀·주** — 서비스 상시 + 장애 조치. **게임데이 후 정리 필수.**
> 29강 대시보드·알람, 28강 서비스가 살아 있어야 합니다.

### Step 0. 사전 준비 (팀, 15분)

- [ ] 시나리오 3개를 상대 팀과 교환(또는 강사 배포)
- [ ] 서비스 정상 + 알람 수신 확인
- [ ] RDS 스냅샷 하나 확보(B 시나리오 대비)
- [ ] 측정자·복구자·기록자 역할 분담

### Step 1. 시나리오 A — 컴퓨팅 장애 (인프라, 20분)

**요청 루프 시작**(사용자 관점 측정) 후 태스크 절반 종료.

```bash
$ DOMAIN=app.<팀도메인>
# 터미널 1: 사용자 관점
$ while true; do printf "%s " "$(date +%T)"; curl -s -o /dev/null -w "%{http_code}\n" -m 3 https://$DOMAIN/; sleep 1; done

# 터미널 2: 장애 주입 + 시각 기록
$ date
$ VICTIM=$(aws ecs list-tasks --cluster course-app-cluster --service-name course-app-svc \
    --query 'taskArns[0]' --output text)
$ aws ecs stop-task --cluster course-app-cluster --task $VICTIM --reason "gameday-A"
```

**측정**

| 항목 | 값 | 어떻게 |
|---|---|---|
| 발생 시각 | 15:02:10 | stop-task 시각 |
| MTTD | 알람이 울렸나? | HealthyHostCount 알람 or 이벤트 |
| MTTR | 복구까지 | 새 태스크 InService 시각 |
| 사용자 영향 | 200 유지? | 요청 루프의 비200 개수 |

> ✅ **2AZ 분산이 제대로면** 남은 태스크가 트래픽을 받아 200이 유지되고, 서비스가 자동으로 새 태스크를 띄웁니다. 비200이 있었다면 왜인지(용량 부족? 단일 AZ 편중?) 분석.

### Step 2. 시나리오 B — 데이터 계층 장애 (애플리케이션, 25분)

```bash
# 데이터 입력
$ for n in kim lee park; do curl -s -X POST https://$DOMAIN/ -d "{\"name\":\"$n\"}" > /dev/null; done
$ curl -s https://$DOMAIN/ | jq .total    # 3

# 장애 조치 강제
$ date
$ aws rds reboot-db-instance --db-instance-identifier course-data-mysql --force-failover

# 복구 후 데이터 일관성
$ sleep 90 && curl -s https://$DOMAIN/ | jq .total    # 3 (무손실!)
$ aws rds describe-events --source-identifier course-data-mysql --source-type db-instance \
    --duration 20 --query 'Events[*].[Date,Message]' --output table
```

**측정** — 다운타임(엔드포인트는 그대로), 데이터 손실 0, 앱 재연결 시간.

> ✅ **Multi-AZ면** 약 1분 다운 후 대기 인스턴스가 승격, 엔드포인트 불변, 데이터 무손실([15강](../02-compute-data/lesson-15.md)). 앱이 연결을 재수립하는지도 확인 — 커넥션 풀이 죽은 연결을 붙들고 있으면 재연결이 늦을 수 있습니다(병목 발견).

### Step 3. 시나리오 C — 의존성/설정 장애 ⭐ (운영/보안, 25분)

**가장 실전적** — 상대 팀이 "무엇을" 훼손했는지 알려주지 않고, 증상만 보고 추적합니다.

```bash
# 주입자(또는 상대 팀): 앱→DB 경로를 끊음
$ DB_SG=$(aws cloudformation describe-stacks --stack-name course-network \
    --query "Stacks[0].Outputs[?OutputKey=='DbSgId'].OutputValue" --output text)
$ APP_SG=...
$ aws ec2 revoke-security-group-ingress --group-id $DB_SG \
    --protocol tcp --port 3306 --source-group $APP_SG    # 😱 조용한 파괴
```

**복구 팀 — 증상에서 원인으로**

```
 ① 증상: 5XX 알람, 신청 실패
 ② 앱 로그: aws logs tail /ecs/course-app | grep -i error
    → "Can't connect to MySQL ... timed out"
 ③ 네트워크 5단계 점검([08강]) : 라우팅→SG→NACL→DNS→앱
    → SG 확인: aws ec2 describe-security-groups --group-ids $DB_SG
    → 3306 규칙이 사라짐! (드리프트)
 ④ 복구: 규칙 재추가 (또는 스택 재배포로 원복)
 ⑤ 검증: 신청 성공 확인
 ⑥ 원인: 누가 언제 지웠나 → CloudTrail([22강])
```

```bash
# 복구
$ aws ec2 authorize-security-group-ingress --group-id $DB_SG \
    --protocol tcp --port 3306 --source-group $APP_SG
# 또는 IaC 원복 (드리프트를 코드로 되돌림 — 근본적)
$ aws cloudformation deploy --stack-name course-network --template-file infra/network.yaml
```

> ✅ **C의 교훈** — 증상(5XX)과 원인(SG 규칙 삭제)은 멀리 떨어져 있습니다. [08강 네트워크 5단계](../01-cloud-foundation/lesson-08.md) + [22강 CloudTrail](../03-serverless-automation/lesson-22.md)로 좁혀 갑니다. **IaC 재배포가 드리프트를 근본 원복**한다는 것도 확인.

### Step 4. 런북 작성 (팀, 20분)

시나리오 3건 각각에 대해 런북을 완성합니다(워크숍 가이드 형식). **처음 보는 사람 기준**으로 — 증상·확인·판단·복구·검증·에스컬레이션.

### Step 5. 야간 자동 축소 구현 (인프라, 25분)

이 과정 최대 비용 문제를 마지막으로 해결합니다. EventBridge 스케줄 + Lambda로 야간에 ECS 0/RDS 중지.

```bash
# 축소 Lambda (야간)
$ cat > scaledown.py <<'EOF'
import boto3
def handler(event, context):
    ecs = boto3.client("ecs")
    ecs.update_service(cluster="course-app-cluster", service="course-app-svc", desiredCount=0)
    boto3.client("rds").stop_db_instance(DBInstanceIdentifier="course-data-mysql")
    return "scaled down"
EOF
# (역할·함수 생성, EventBridge cron(0 15 * * ? *) UTC=한국 00시 등록)
# 아침 복구 Lambda는 desiredCount=2 + start_db_instance
```

```bash
$ aws events put-rule --name course-nightly-down \
    --schedule-expression 'cron(0 15 * * ? *)'    # 한국 자정
# put-targets로 축소 Lambda 연결, 아침 규칙도 동일 패턴
```

> 💡 **절감 계산** — RDS+Fargate를 하루 8시간만 켜면 상시 대비 약 2/3 절감. 야간·주말 축소로 $100 → $35 수준. 이 자동화가 M4 비용 산정([31강](lesson-31.md))의 핵심 절감 항목이 됩니다.
> ⚠️ RDS 중지는 7일 후 자동 재시작하므로, 축소 스케줄이 매일 돌면 문제없지만 장기 미사용은 스냅샷+삭제.

### Step 6. 비난 없는 회고 (팀, 20분)

| 시나리오 | MTTD | MTTR | 근본 원인 | 재발 방지책 |
|---|---|---|---|---|
| A 컴퓨팅 | 1분(알람) | 4분 | (해당 없음-정상 복구) | 최소 용량 상향 검토 |
| B 데이터 | 즉시 | 1분 | Multi-AZ 정상 | 앱 커넥션 풀 재연결 튜닝 |
| C 설정 | 2분(5XX) | 6분 | 콘솔 수동 SG 삭제 | 콘솔 쓰기 권한 회수 + 드리프트 알람 |

**개선 항목 3개 도출** — 회고에서 나온 것을 다음 액션으로.

### 💰 이번 강 비용

## ⑤ 자주 하는 실수

### 발견자가 알람이 아니라 사람이다

**증상** — 장애를 주입했는데 알람이 안 오고, 요청 루프를 보던 사람이 먼저 발견.
**원인** — [29강](lesson-29.md) 알람이 이 시나리오를 못 잡습니다(HealthyHostCount 알람 누락 등).
**해결** — 게임데이는 알람의 시험이기도 합니다. MTTD가 나쁘면 알람을 보강하고 다시 시험합니다.

### 런북이 작성자만 이해할 수 있다

**증상** — 복구자가 아닌 팀원이 런북대로 못 따라 합니다.
**해결** — 구체적 명령·확인 방법·판단 기준. "처음 보는 사람" 테스트 — 작성 안 한 팀원에게 런북만 주고 복구시켜 봅니다. 막히면 그 지점이 런북의 구멍.

### 회고에서 사람을 탓한다

**증상** — "누가 그랬어?"로 끝나고 시스템은 그대로.
**해결** — "왜 그것이 **가능**했나"로 묻습니다. C 시나리오라면 "왜 콘솔에서 SG를 지울 수 있었나 → 운영 콘솔 쓰기 권한 회수 + 드리프트 알람". 사람이 아니라 가드레일을 고칩니다.

### B 시나리오에서 데이터가 손실됐다

**증상** — 장애 조치 후 신청 건수가 줄었습니다.
**원인** — Multi-AZ가 아니거나(단일 AZ), 비동기 복제본을 승격했거나, 앱이 실패한 쓰기를 재시도하지 않음.
**해결** — Multi-AZ 확인([15강](../02-compute-data/lesson-15.md)). 동기 복제라 무손실이어야 합니다. 손실이 있으면 설계 결함 — M4 전에 고칩니다.

### C 시나리오에서 원인을 못 찾고 헤맨다

**증상** — 5XX만 보고 아무 데나 찔러 봅니다.
**해결** — [08강 네트워크 5단계](../01-cloud-foundation/lesson-08.md)를 순서대로: 라우팅→SG→NACL→DNS→앱. 로그부터 봅니다(`Can't connect` = 네트워크). 체계적 추적이 훈련의 목표입니다.

### 야간 축소 Lambda가 권한 부족으로 실패한다

**원인** — 축소 Lambda 역할에 `ecs:UpdateService`·`rds:StopDBInstance` 권한 없음.
**해결** — 역할에 해당 리소스로 좁힌 권한 추가. 그리고 **아침 복구가 안 되면 서비스가 계속 죽어 있으므로**, 복구 규칙과 알람도 함께 검증합니다.

## ⑥ 마일스톤 점검 — 🏁 M3

**M3 통과 기준**

- [ ] 장애 시나리오 3건 탐지→복구 완주
- [ ] 각 MTTD/MTTR 측정 + 근본 원인
- [ ] 런북 3건(처음 보는 사람 기준)
- [ ] 비난 없는 회고 + 개선 항목 3개
- [ ] 야간 자동 축소 구현 + 절감액 추정

**M3 제출물**

- [ ] 대시보드 캡처 + 알람 수신 증빙(29강)
- [ ] 부하 테스트 리포트(29강)
- [ ] 게임데이 리포트 3건(시나리오·MTTD/MTTR·원인·방지책)
- [ ] 런북
- [ ] 야간 축소 코드 + 절감 추정

**스스로 점검하는 질문 3개**

<details>
<summary>1. 장애를 냈을 때 사람보다 알람이 먼저 알았나요?</summary>

이상적으로는 **예**여야 합니다. MTTD가 "알람 30초 vs 사람 3분"이면 관측성이 좋은 것입니다. 알람보다 사람이 먼저 발견했다면(요청 루프를 보다가), 그 시나리오를 잡는 알람이 없는 것 — [29강](lesson-29.md)으로 돌아가 보강합니다. 게임데이는 시스템뿐 아니라 **알람의 시험**입니다.
</details>

<details>
<summary>2. C 시나리오(설정 장애)에서 원인을 어떻게 좁혔나요?</summary>

**증상 → 로그 → 체계적 점검**입니다. 5XX 알람 → 앱 로그에서 `Can't connect to MySQL timed out`(네트워크 힌트) → [08강 5단계](../01-cloud-foundation/lesson-08.md)로 라우팅→SG 순 점검 → SG에서 3306 규칙 사라짐 발견 → [CloudTrail](../03-serverless-automation/lesson-22.md)로 누가 지웠나 → IaC 재배포로 근본 원복. 아무 데나 찌르지 않고 **로그가 가리키는 계층부터** 좁힌 것이 핵심입니다.
</details>

<details>
<summary>3. 회고에서 나온 재발 방지책이 "조심하자"가 아닌 구체적 조치인가요?</summary>

"조심하자"는 재발합니다. 구체적 조치여야 합니다: C 시나리오 → **콘솔 쓰기 권한 회수 + 드리프트 감지 스케줄 + 변경은 파이프라인만**. B의 재연결 지연 → **커넥션 풀 타임아웃 설정**. A의 순간 오류 → **최소 용량 3으로 상향**. 사람의 주의가 아니라 **시스템의 가드레일**로 막습니다 — 이것이 비난 없는 회고의 결과물입니다.
</details>

## 오늘의 정리

| 개념 | 핵심 |
|---|---|
| 게임데이 | 계획된 장애로 **대응 절차** 시험 |
| MTTD/MTTR | 탐지 시간(알람 의존) / 복구 시간(런북 의존) |
| 시나리오 3종 | 컴퓨팅·데이터·**설정(증상→원인 추적)** |
| 런북 | 처음 보는 사람이 새벽 3시에 |
| 비난 없는 회고 | 사람이 아니라 **시스템·절차를 고침** |
| 야간 축소 | EventBridge+Lambda로 비용 2/3 절감 |
| 근본 원복 | IaC 재배포가 드리프트를 코드로 되돌림 |

**한 장 요약**

```
  장애 주입(A 컴퓨팅 / B 데이터 / C 설정)
    → 알람이 먼저 탐지(MTTD) → 런북대로 복구(MTTR)
    → 데이터 무손실·서비스 지속 확인
    → 비난 없는 회고 → 재발 방지책(가드레일)
    → 야간 자동 축소로 비용 마무리 = M3 완성
```

**오늘 반드시 기억할 한 가지**
> **겪어 보지 않은 고가용성은 가설입니다.**
> 게임데이는 진짜 장애가 던질 질문을 안전한 강의실에서 미리 받는 소방 훈련입니다.

**과제 (팀) — M3 제출**
1. 게임데이 리포트 3건 — 시나리오·탐지 방법·MTTD/MTTR·근본 원인·재발 방지책.
2. 런북 3건(처음 보는 사람 기준).
3. 야간 자동 축소 코드 + 절감액 추정(상시 대비).
4. 비난 없는 회고 기록 + 개선 항목 3개.
5. (개인) "우리 서비스에서 아직 시험하지 못한 장애 시나리오 하나"와 그 대비를 3줄.
