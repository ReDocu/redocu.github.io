지금까지 모델의 수명은 **스크립트가 끝나는 순간까지**였습니다. `python day065_final.py` 가

대단원 04의 서빙 구조를 미리 보면, 왜 이게 문제인지 명확합니다.

```
[학습 컴퓨터]                          [서빙 서버 (대단원 04)]
```

학습과 서빙은 **다른 시간, 다른 컴퓨터**에서 일어납니다. 그 사이를 건너는 유일한 다리가
**파일로 저장된 모델**입니다. 그리고 이 다리에는 계약서가 필요합니다 — "이 모델은 어떤 컬럼을,
어떤 타입으로, 어떤 순서로 받는가"(입력 스키마). 계약서 없는 모델 파일을 받은 서빙 개발자는

오늘 모델은 코드에서 분리된 **물건**(artifact)이 됩니다. 물건이 되어야 버전을 매기고,
전달하고, 롤백할 수 있습니다.

## ③ 개념 설명

### 직렬화 — 객체를 파일로

**직렬화**(serialization)는 메모리 속 파이썬 객체를 바이트로 얼려 파일에 담는 것입니다.
sklearn 생태계의 표준은 **joblib**입니다 (pickle의 파생으로, 큰 numpy 배열에 효율적).

```python
joblib.dump(pipe, "models/pm25_pipeline.joblib")   # 저장
loaded = joblib.load("models/pm25_pipeline.joblib") # 복원 — fit 상태 그대로
```

핵심: [Day 063](day-063.md)에서 전처리를 파이프라인 안에 넣었기 때문에, **파일 하나에
대치 중앙값·스케일 통계·인코딩 사전·모델 계수가 전부** 들어갑니다. 서빙 쪽은 로드 후
predict만 하면 되고, 훈련-서빙 불일치는 구조적으로 불가능합니다.

### 직렬화의 두 가지 계약

| 계약 | 내용 | 위반 시 |
|---|---|---|
| **환경 계약** | 로드하는 쪽에 같은 라이브러리(버전 포함)가 있어야 함 | 버전이 다르면 경고 또는 로드 실패 — `requirements.txt`([Day 066](day-066.md))가 여기서 또 일함 |
| **입력 계약** | predict에 넣을 컬럼·타입·순서 | 에러(운 좋으면) 또는 조용히 틀린 예측(운 나쁘면) |

> **보안 주의** — pickle/joblib 파일은 로드 시 임의 코드가 실행될 수 있습니다.
> **신뢰할 수 없는 출처의 모델 파일을 로드하지 마세요.** 팀 내부 전달에도 해시 검증을 붙이는
> 것이 좋은 습관입니다.

### 입력 스키마와 모델 서명

입력 계약을 사람 말("컬럼 18개 넣으세요")이 아니라 **기계가 검사 가능한 파일**로 만듭니다.

| 수단 | 형태 | 특징 |
|---|---|---|
| 스키마 JSON (수제) | 컬럼·dtype 목록 + 검증 함수 | 단순, 어디서나 동작 — 오늘 만듭니다 |
| **MLflow 서명** | `infer_signature(X, y)` 로 자동 추론, 모델과 함께 기록 | 표준화 — MLflow에 모델을 올리면 스키마 검사가 자동화됨 |

### Step 1. 저장 → 재로드 → 동일 예측 검증 (1~2교시)

```python
# day068_save.py — 모델 저장과 로드 (특성 생성부는 Day 065와 동일)
import json, os
import joblib
import numpy as np
import pandas as pd
# … (Day 065의 load()·build() 정의로 pipe를 fit까지 만든 상태에서)

print("== A. 저장 → 재로드 → 동일 예측 검증 ==")
os.makedirs("models", exist_ok=True)
joblib.dump(pipe, "models/pm25_pipeline.joblib")
size = os.path.getsize("models/pm25_pipeline.joblib") / 1024

loaded = joblib.load("models/pm25_pipeline.joblib")
p_orig = pipe.predict(te[COLS])
p_load = loaded.predict(te[COLS])
print(f"원본과 로드본의 예측이 완전히 같은가: {np.array_equal(p_orig, p_load)}")
print(f"로드본 test R²: {r2_score(te.pm25_next, p_load):.3f}")
```

실행 결과:


W13 5일의 결과물이 **4KB짜리 파일**이 됐습니다. `np.array_equal(...) → True` —
"저장 → 재로드 → 동일 예측"의 3단 검증은 관례가 아니라 **의무**입니다.
이 검증 없이 전달한 모델 파일은 검증 없이 배포한 코드와 같습니다.
(선형 모델이라 4KB이지, 랜덤포레스트 300그루였다면 수십 MB입니다 — 서빙 메모리와 로드 시간의
차이이고, 모델 선택 기준에 "무게"가 들어가는 이유입니다.)

### Step 2. 입력 스키마 — 모델 옆의 계약서 (3~4교시)

```python
print("\n== B. 입력 스키마를 모델 옆에 저장 ==")
schema = {
    "columns": COLS,
    "dtypes": {c: str(te[c].dtype) for c in COLS},
    "target": "pm25_next",
    "trained_until": "2025-12-31",
    "data_md5": "21adc01f2409f9c2bda8ac0cf2452979",
    "sklearn": "1.7.2",
}
with open("models/pm25_schema.json", "w", encoding="utf-8") as f:
    json.dump(schema, f, ensure_ascii=False, indent=2)
print("저장: models/pm25_schema.json")

def validate_input(x: pd.DataFrame, schema):
    missing = [c for c in schema["columns"] if c not in x.columns]
    if missing:
        raise ValueError(f"입력에 누락된 컬럼: {missing}")
    return x[schema["columns"]]          # 순서까지 스키마 기준으로 정렬

bad = te[COLS].drop(columns=["wind_fc"]).head(1)
try:
    validate_input(bad, schema)
except ValueError as e:
    print(f"검증기 작동: {e}")
```

실행 결과:

```
== B. 입력 스키마를 모델 옆에 저장 ==
저장: models/pm25_schema.json
검증기 작동: 입력에 누락된 컬럼: ['wind_fc']
```

스키마 JSON에 넣은 항목들을 보세요 — 컬럼·타입뿐 아니라 **학습 구간·데이터 지문·라이브러리
버전**까지. 이 파일은 "이 모델이 무엇으로 만들어졌고 무엇을 받는가"의 여권입니다.
`validate_input` 은 잘못된 입력을 **모델에 닿기 전에** 명확한 한국어로 거절합니다 —
대단원 04에서 이 함수가 API의 입구 검증이 됩니다.

### Step 3. MLflow 서명 — 계약서의 표준 서식 (5교시)

수제 JSON도 좋지만, 표준 서식이 있으면 도구들이 알아서 검사해 줍니다.

```python
print("\n== C. MLflow 서명 — 스키마의 표준화 ==")
from mlflow.models import infer_signature
sig = infer_signature(te[COLS].head(), p_load[:5])
print(str(sig).strip()[:400])
```

실행 결과:

```
== C. MLflow 서명 — 스키마의 표준화 ==
inputs: 
  ['pm10': double (required), 'pm25': double (required), 'o3': double (required), 'no2': double (required), 'co': double (required), 'so2': double (required), 'temp': double (required), 'humidity': double (required), 'wind_speed': double (required), 'precip': double (required), 'pm25_lag1': double (required), 'pm25_ma3': double (required), 'seoul_pm25': double (required), 'month': integer
```

`infer_signature` 가 입출력 샘플에서 스키마를 추론했습니다. 이 서명을
`mlflow.sklearn.log_model(pipe, name="model", signature=sig)` 로 어제의 run에 붙이면,
**모델·서명·실험 기록이 한 몸**이 됩니다. 참고로 실행 시 "month가 integer라 결측을 표현할 수
없다"는 UserWarning이 함께 출력됩니다 — 서명이 벌써 잠재적 서빙 사고(정수 컬럼에 결측 유입)를
경고해 주고 있는 것입니다. month를 float으로 캐스팅해 두면 경고가 사라집니다.

### Step 4. 직렬화가 안 되는 파이프라인 — lambda 함정 (6교시)

전처리에 커스텀 함수를 끼우고 싶을 때 빠지는 유명한 구덩이를 일부러 밟아 봅니다.

```python
print("\n== D. 직렬화가 안 되는 파이프라인 — lambda 함정 ==")
from sklearn.preprocessing import FunctionTransformer
pipe_bad = Pipeline([
    ("clip", FunctionTransformer(lambda x: np.clip(x, 0, None))),   # lambda!
    ("m", LinearRegression()),
])
pipe_bad.fit(tr[NUM].fillna(0), tr.pm25_next)
try:
    joblib.dump(pipe_bad, "models/bad.joblib")
except Exception as e:
    print(f"{type(e).__name__}: {str(e)[:120]}")
```

실행 결과:

```
== D. 직렬화가 안 되는 파이프라인 — lambda 함정 ==
PicklingError: Can't pickle <function <lambda> at 0x000001DC2F991AB0>: it's not found as __main__.<lambda>
```

학습·예측은 멀쩡하다가 **저장하는 순간** 죽습니다. lambda는 이름이 없어 "나중에 로드할 때
어디서 다시 찾아올지"를 pickle이 기록할 수 없기 때문입니다. 해법은 이름 있는 함수를
**import 가능한 모듈**에 두는 것입니다:

```python
# features.py (모듈 파일)
def clip_nonneg(x):
    return np.clip(x, 0, None)

# 사용하는 쪽
from features import clip_nonneg
FunctionTransformer(clip_nonneg)      # 이제 직렬화 가능 — 단, 로드하는 쪽에도 features.py가 필요!
```

마지막 줄의 단서가 중요합니다 — 커스텀 코드가 파이프라인에 들어가면 **그 코드 파일도 배포물의
일부**가 됩니다. MP2에서 파이프라인을 패키지([Day 013](../01-python-data/day-013.md) 구조) 안에
두게 하는 이유입니다.

## ⑤ 자주 하는 실수

### 저장만 하고 재로드 검증을 안 함

**증상** — 서빙 팀에서 "모델이 이상한 값을 뱉는다"는 연락 — 학습 컴퓨터에서는 재현 안 됨.
**원인** — 저장 시점의 객체와 파일 내용이 같다는 보장은 **로드해서 비교해 보기 전엔** 없습니다.
**해결** — 저장 직후 3단 검증(저장→재로드→`np.array_equal`)을 학습 스크립트에 내장하세요 ([Day 070](day-070.md)의 CLI에 들어갑니다).

### 다른 버전의 sklearn에서 로드함

```
InconsistentVersionWarning: Trying to unpickle estimator ... from version 1.7.2 when using version 1.6.x
```

**원인** — joblib 파일은 만든 라이브러리 버전에 묶입니다. 경고로 끝나면 다행이고, 내부 구조가 바뀐 버전 간엔 로드 실패나 미묘한 동작 차이가 납니다.
**해결** — 스키마 JSON에 버전을 기록하고(오늘 Step 2), 서빙 환경을 `requirements.txt` 로 학습 환경과 일치시킵니다. 대단원 05의 Docker가 이것을 봉인합니다.

### lambda·로컬 함수를 파이프라인에 넣음

```
PicklingError: Can't pickle <function <lambda> at 0x...>: it's not found as __main__.<lambda>
```

**원인** — 이름 없는(또는 함수 안에 정의된) 함수는 로드 시 되찾을 주소가 없습니다.
**해결** — 모듈 최상위의 이름 있는 함수로 옮기고, 그 모듈을 배포물에 포함합니다 (Step 4).

### 모델 파일을 git에 커밋함

**증상** — 저장소가 무거워지고, "어느 커밋의 모델이 운영 중인가"가 여전히 불명.
**원인** — git은 코드의 집이지 바이너리 산출물의 집이 아닙니다.
**해결** — models/는 `.gitignore`. 모델의 집은 MLflow 아티팩트(어제)이고, run ID가 곧 모델의 버전표가 됩니다.

### 스키마 없이 모델 파일만 전달함

**증상** — 받은 쪽이 컬럼 구성을 추측으로 맞추다 순서·단위를 틀림. 에러 없이 이상한 예측.
**원인** — 입력 계약이 구두(또는 부재)였습니다.
**해결** — 모델 파일과 스키마 JSON(또는 MLflow 서명)은 **항상 한 쌍**으로 움직입니다. 받은 쪽 첫 코드는 `validate_input` 이어야 합니다.

또는 파이프라인에 로드 시 재실행되는 비직렬화 상태(전역 변수·난수 의존 커스텀 변환)가 섞인 경우.
어느 쪽이든 "같은 파일이면 같은 예측"이 깨진 것이므로 배포를 멈추고 원인을 소거법으로 찾아야 합니다.

</details>

**Q3.** 모델 파일(joblib), 코드(git), 실험 기록(MLflow)의 세 저장소가 서로를 어떻게 참조해야
"운영 중인 모델의 족보"가 완성되는지 설계해 보세요.

<details>
<summary>답 보기</summary>

MLflow run이 허브가 됩니다: run의 params에 **git 커밋 해시**와 **데이터 지문**을 기록하고,
모델 파일은 그 run의 **아티팩트**로 첨부합니다. 그러면 운영 모델 → (아티팩트 출처) run ID →
커밋 해시·데이터 지문 → 코드·데이터까지 역추적이 한 줄로 이어집니다. 이 족보가 [Day 069](day-069.md)
모델 카드의 "출처" 항목이 됩니다.

</details>
