## ③ 개념 설명

### MP1 요구사항 (평가 기준)

| 항목 | 배점 | 확인 방법 |
|---|---|---|
| **파이프라인 재현성** | 30 | 새 환경에서 clone → 명령 한 줄로 수집→적재 (**멱등**) |
| **SQL 품질** | 25 | JOIN · 집계 · 윈도우 함수가 포함된 분석 쿼리 10문 이상 |
| **분석 인사이트** | 20 | 질문 → 근거 → 결론이 이어지는가 |
| **테스트·문서** | 15 | pytest 통과 · README로 5분 안에 실행 |
| **발표** | 10 | 시연 5분 + 질의응답 |

**단원 완료 조건 4가지** (이걸 못 채우면 점수와 무관하게 미완성입니다)

- [ ] 명령 한 줄로 수집→적재가 재현된다 (멱등)
- [ ] JOIN·윈도우 함수가 포함된 분석 SQL을 **설명할 수 있다**
- [ ] 검증 규칙과 실패 처리 정책이 코드에 있다
- [ ] 보고서에 분석 질문 → 근거 → 결론이 이어진다

### 데이터 선정 기준 6가지 ★

| # | 기준 | 확인 방법 | 탈락 조건 |
|---|---|---|---|
| **1. 접근성** | 오늘 안에 받을 수 있나? | 실제로 한 번 받아 보기 | 인증키 승인이 며칠 걸림 |
| **2. 시계열성** | 시간 축이 있나? | 날짜/시각 열 확인 | 없으면 추이·윈도우 함수를 쓸 수 없음 |
| **3. 관계성** | 테이블 2개 이상으로 나뉘나? | 반복되는 속성 찾기 | 없으면 `JOIN` 을 쓸 수 없음 |
| **4. 규모** | 1만~100만 행 | 미리 확인 | 100행이면 분석할 게 없고, 1억 행은 5일에 무리 |
| **5. 적법성** | 이용약관·라이선스 확인 | 출처 페이지 확인 | 재배포 금지·상업적 이용 제한 표기 필요 |
| **6. 개인정보** | 개인 식별 가능 정보 없음 | 열 목록 확인 | **있으면 사용 금지** |

**2번과 3번이 핵심입니다.** 이 둘이 없으면 W07~W08에서 배운 것의 절반을 쓸 수 없습니다.

> **3번이 애매할 때** — 한 테이블짜리 데이터라도 **차원 테이블을 직접 만들면** 관계가 생깁니다.
> 예: 측정 데이터에 지역명이 반복되면 → `region` 테이블로 분리하고 FK를 겁니다.
> 이것이 [Day 039](day-039.md)에서 배운 정규화입니다. **직접 정규화하는 것도 실력의 증명**입니다.

### Step 1. 데이터 후보 3개 뽑고 실제로 받아 보기 (1~2교시)

**책상에서 고민하지 말고 실제로 요청해 보세요.** 문서와 실제가 다른 경우가 매우 흔합니다.

```python
# scripts/explore_source.py — 후보를 빠르게 확인하는 스크립트
import json
import os
import sys

import requests
from dotenv import load_dotenv

load_dotenv()


def peek(url: str, params: dict, *, n: int = 3) -> None:
    r = requests.get(url, params=params, timeout=15)
    print(f"상태: {r.status_code} · 크기: {len(r.content):,} bytes")
    r.raise_for_status()

    data = r.json()
    print(json.dumps(data, ensure_ascii=False, indent=2)[:1500])

    # 응답 구조는 API 마다 다릅니다. 실제 경로를 확인해 수정하세요.
    items = data.get("response", {}).get("body", {}).get("items", [])
    print(f"\n항목 수: {len(items)}")
    if items:
        print("열 목록:", list(items[0].keys()))
        for item in items[:n]:
            print(item)


if __name__ == "__main__":
    peek(
        "http://apis.data.go.kr/B552584/ArpltnInforInqireSvc/getCtprvnRltmMesureDnsty",
        {
            "serviceKey": os.environ["PUBLIC_DATA_KEY"],
            "returnType": "json",
            "numOfRows": 10,
            "sidoName": "서울",
            "ver": "1.0",
        },
    )
```

**확인해야 할 것**

```
□ 인증키가 지금 동작하는가          (승인 대기면 다른 후보로)
□ 열 목록에 시간 열이 있는가        (기준 2)
□ 반복되는 속성이 있는가            (기준 3 — 정규화 대상)
□ 한 번에 몇 행을 주는가            (페이징 필요 여부)
□ 과거 데이터를 주는가              (백필 가능 여부 ★)
□ 결측을 어떻게 표기하는가          ('-' · '' · null)
□ 개인정보로 볼 열이 있는가         (기준 6)
```

**"과거 데이터를 주는가"가 특히 중요합니다.** 현재 시점만 주는 API라면
5일 동안 모을 수 있는 데이터가 적어 분석이 빈약해집니다. **그럴 땐 과거 CSV를 함께 받으세요.**

### Step 4. 스키마 설계와 마이그레이션 (6교시)

[Day 039](day-039.md)의 5단계 절차를 씁니다.

**① 명사 뽑기** — 측정소, 시도, 측정값, 오염물질, 수집 실행
**② 관계** — 시도 1 : 측정소 N / 측정소 1 : 측정값 N
**③ N:M 없음**
**④ 속성 배치** — "이 속성은 무엇 하나에 대한 사실인가"
**⑤ 키와 제약** — **멱등 키를 먼저 정합니다**

```
멱등 키: (station_id, measured_at)
근거: "같은 측정소의 같은 시각 측정값"은 세상에 하나뿐이다.
```

`sql/migrations/001_create_station.sql`:

```sql
-- 001_create_station.sql
-- 목적: 측정소 마스터. 측정소명이 측정값 테이블에서 반복되는 것을 정규화 (3NF)
-- 작성: 2026-08-12

CREATE TABLE IF NOT EXISTS station (
    station_id integer     GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text        NOT NULL UNIQUE,      -- 측정소명은 전국 유일
    sido       text        NOT NULL,
    address    text,                             -- API가 항상 주지는 않음 → NULL 허용
    latitude   numeric(9,6),
    longitude  numeric(9,6),
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz
);

CREATE INDEX IF NOT EXISTS idx_station_sido ON station (sido);
```

`sql/migrations/002_create_measurement.sql`:

```sql
-- 002_create_measurement.sql
-- 목적: 시간별 측정값
-- 멱등 키: (station_id, measured_at) — 같은 측정소의 같은 시각은 하나뿐
-- NULL 허용 근거: 센서 점검·고장 시 값이 없음. 0(농도 0)과 구분해야 함

CREATE TABLE IF NOT EXISTS measurement (
    measurement_id bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    station_id     integer     NOT NULL REFERENCES station(station_id),
    measured_at    timestamptz NOT NULL,
    pm10           integer     CHECK (pm10 BETWEEN 0 AND 2000),
    pm25           integer     CHECK (pm25 BETWEEN 0 AND 1000),
    o3             numeric(5,3) CHECK (o3  >= 0),
    no2            numeric(5,3) CHECK (no2 >= 0),
    khai           integer     CHECK (khai BETWEEN 0 AND 600),
    grade          smallint    CHECK (grade BETWEEN 1 AND 4),
    ingested_at    timestamptz NOT NULL DEFAULT now(),
    run_id         bigint,                       -- 어느 실행에서 왔는지 (계보)

    CONSTRAINT measurement_key UNIQUE (station_id, measured_at),
    CONSTRAINT measurement_pm_consistency
        CHECK (pm25 IS NULL OR pm10 IS NULL OR pm25 <= pm10)
);

CREATE INDEX IF NOT EXISTS idx_measurement_station_time ON measurement (station_id, measured_at);
CREATE INDEX IF NOT EXISTS idx_measurement_time         ON measurement (measured_at);
```

- **접근성** — 영화진흥위원회 API는 키가 자동 승인되고 즉시 호출됩니다
- **시계열성** — 일별 데이터. **순위 변동·누적 관객수** 같은 윈도우 함수 소재가 풍부합니다
- **관계성** — `movie`(영화 마스터) · `distributor`(배급사) · `daily_boxoffice`(일별) 로 자연스럽게 3NF
- **규모** — 하루 10~50행이지만 **1년 백필하면 1만 행 이상**. 5일 프로젝트에 딱 맞습니다
- **멱등 키** — `(영화코드, 상영일)` 이 명확합니다

**B의 문제** — 연령대·회원구분은 **준식별자**입니다 ([Day 044](day-044.md)).
대여소 + 시각 + 연령대 조합이면 특정 개인이 식별될 수 있습니다.
"이미 익명화됐다"는 제공자 설명이 있어도, **공개 저장소에 올릴 것**이라면 피하는 편이 안전합니다.

**A의 문제** — 200만 행은 5일 프로젝트에 과합니다. 적재는 되지만
**분석 쿼리 하나 돌릴 때마다 기다리게 되어** 반복 속도가 떨어집니다.
꼭 쓰겠다면 **1개 시·도, 1년으로 범위를 좁히세요.** 그러면 좋은 후보가 됩니다.
그리고 CSV 다운로드라 **수집 자동화를 보여주기 어렵습니다.**

> **"범위를 좁혀 좋은 후보로 만드는 것"도 기획 능력입니다.**
> 데이터가 나쁜 것이 아니라 **범위가 안 맞는 것**입니다.

<summary>답 보기</summary>

**원래 질문의 문제** — "가장 심한"의 정의가 없습니다. 평균? 최댓값? 나쁨 이상인 날 수? 기간은?

|---|---|---|---|
| **V1 (평균)** | "최근 30일 PM10 **평균**이 가장 높은 측정소 5곳은?" | `JOIN` · `AVG` · `ORDER BY` · `LIMIT` | 5행 표 |
| **V2 (빈도)** | "PM10이 '나쁨'(81 이상)인 **시간이 가장 많은** 측정소 5곳은?" | `CASE` · `COUNT(*) FILTER` · `HAVING` | 5행 표 |
| **V3 (순위 변동)** | "월별로 **순위가 가장 많이 바뀐** 측정소는?" | `RANK() OVER (PARTITION BY 월)` · `LAG` | 표 + 선 그래프 |
| **V4 (지역 비교)** | "**시·도별** 평균과 그 안에서 가장 나쁜 측정소는?" | `PARTITION BY sido` · `RANK` | 계층 표 |
| **V5 (이상)** | "평소보다 **유독 나쁜 날**이 많은 측정소는?" | `AVG` · `STDDEV` · z점수 | 표 |

**답이 서로 다를 수 있습니다.** 그게 핵심입니다.

```
평균이 높은 곳   =  늘 조금씩 나쁜 곳
나쁨 시간이 많은 곳 =  가끔 아주 나쁜 곳
```

도로변 측정소는 평균이 높고, 산업단지 근처는 특정일에 극단값이 나옵니다.
**"어떤 정의로 물었는가"가 곧 정책 결정**입니다.

**보고서에는 이렇게 쓰세요.**

```markdown
### Q2. 대기질이 나쁜 지역은 어디인가?

'나쁨'의 정의를 두 가지로 나누어 봤습니다.

| 정의 | 1위 | 2위 | 3위 |
|---|---|---|---|
| 평균 PM10 | (측정소A) 58.2 | ... | ... |
| '나쁨' 이상 시간 비율 | (측정소C) 19.4% | ... | ... |

두 순위가 다릅니다. A는 항상 조금 나쁘고, C는 가끔 매우 나쁩니다.
건강 영향 관점에서는 C의 고농도 노출이 더 위험할 수 있습니다.
```

**이런 문단 하나가 "쿼리를 돌렸다"와 "분석했다"를 가릅니다.**

**3.** 5일 프로젝트에서 "예측 모델도 넣고 싶다"는 유혹이 생깁니다. 왜 하면 안 되는지, 그리고 정말 하고 싶다면 어떻게 하는 것이 맞는지 쓰세요.

<details>
<summary>답 보기</summary>

**하면 안 되는 이유**

| 이유 | 설명 |
|---|---|
| **평가 배점** | 파이프라인 재현성 30 + SQL 25 = **55점**. 예측 모델은 배점이 **0점** |
| **아직 안 배웠음** | 머신러닝은 W11–W15(대단원 03). 지금 하면 어설픈 결과만 나옴 |
| **시간 산술** | 26시간 중 모델에 8시간을 쓰면 파이프라인·분석에 18시간. **필수 항목이 부실해짐** |
| **MP2와 중복** | MP2가 정확히 "학습 데이터 조회 + 모델링"입니다. 지금 하면 두 번 하는 셈 |
| **위험** | 모델이 안 나오면 **발표할 게 없어집니다.** 파이프라인은 확실히 나옵니다 |

**가장 흔한 실패 패턴**

```
3일차: "이제 모델 붙여야지"  →  결측·스케일링 문제로 하루 소모
4일차: 정확도가 이상함       →  원인 조사
5일차: 발표 자료 못 만듦     →  파이프라인도 미완성, 모델도 미완성
```

**정말 하고 싶다면**

**① 필수 항목을 전부 끝낸 뒤에** — 4일차 저녁에 평가 기준 4가지가 다 체크됐다면, 그때 손대세요.

**② "예측"이 아니라 "분석"으로 표현** — 통계적 관계까지는 SQL로 할 수 있습니다.

```sql
-- 전날 값과 다음날 값의 상관 (예측이 아니라 관계 분석)
WITH d AS (
    SELECT station_id, measured_at::date AS day, AVG(pm10) AS avg_pm10
    FROM measurement WHERE pm10 IS NOT NULL
    GROUP BY 1, 2
),
lagged AS (
    SELECT station_id, day, avg_pm10,
           LAG(avg_pm10) OVER (PARTITION BY station_id ORDER BY day) AS prev_pm10
    FROM d
)
SELECT ROUND(CORR(avg_pm10, prev_pm10)::numeric, 3) AS 전일_상관계수,
       COUNT(*) AS 표본수
FROM lagged WHERE prev_pm10 IS NOT NULL;
```

**`CORR` 은 PostgreSQL 내장 함수**입니다. 윈도우 함수와 조합하면
"전날 값이 다음날을 얼마나 설명하는가"를 SQL 한 방에 보여줄 수 있습니다.
**평가 기준 25점짜리 "SQL 품질"에 정확히 들어가면서, 예측의 실마리도 보여 줍니다.**

**③ "다음 단계" 섹션에 적기** — 보고서 마지막에 이렇게 씁니다.

```markdown
## 다음 단계
전일 PM10과 익일 PM10의 상관계수가 0.61로 나타나, 시계열 예측 모델의
가능성이 있습니다. **MP2에서 이 데이터셋으로 회귀 모델을 시도할 예정입니다.**
현재 파이프라인은 `measurement` 테이블에 학습용 데이터를 계속 축적하고 있습니다.
```

**이것이 오히려 좋은 인상을 줍니다.** "범위를 알고 관리하는 사람"으로 보이기 때문입니다.
채용 면접에서도 **"왜 그건 안 했나요?"에 답할 수 있는 것**이 무작정 넣는 것보다 낫습니다.

> **범위 관리는 실력입니다.** 실무에서 마감을 지키는 엔지니어와 못 지키는 엔지니어를 가르는 것은
> 대개 기술력이 아니라 **"안 할 것을 정하는 능력"** 입니다.
</details>
