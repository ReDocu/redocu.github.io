PART 4 · DAY 32–34 · 결제의 뒷면

insert-only 원장 시뮬레이터 — 고치지 않는 장부

결제 화면 뒤에서 실제로 벌어지는 일 — 웹훅이 원장을 쓴다. 버튼을 눌러 결제·취소·재발송을 일으켜 보세요. 원장(payment)에는 행이 추가만 되고, 수정·삭제는 한 번도 일어나지 않습니다.

🧪 목업 안내 — 포트원·PG·카드사·Supabase는 전부 브라우저 안 시뮬레이션입니다. 실제 네트워크 요청은 없고, 키 값은 자리표시자입니다. 실전 연동은 PortoneMCP(Day 33)와 웹훅 URL 등록 + Vercel 배포(Day 34)로 합니다.

① 정산 — 결제 ≠ 입금 (Day 32)

돈은 사장님 통장으로 직행하지 않는다. 결제사 서버에 모였다가, 수수료를 떼고, 정해진 주기에 온다.

실습(Day 32)에서 페이앱 결제 링크로 1,000원을 실제로 결제하면 관리자 화면에 상태 미정산 · 정산 예정금액 956원(수수료 44원)이 뜬다 — 정산 개념의 실물.
💡 "오늘 판 돈은 오늘 못 쓴다." 정산 주기를 모르고 재고·인건비를 계획하면 흑자 도산이 난다. 비즈니스 검증 전이라면 시스템 구축 대신 결제 링크부터 — "먼저 팔고, 팔리면 계약서를 쓴다."

② 돈과 통지의 경로 — 웹훅은 localhost에 오지 않는다 (Day 32·34)

결제(브라우저 → 포트원)는 어디서든 되지만, 웹훅(포트원 → 내 서버)은 공인 주소가 있어야 도달한다.

그래서 웹훅 개발 순서도의 마지막은 언제나 "웹훅 API 배포"다. 화면·결제는 로컬에서 만들고, 웹훅 검증은 배포해서 한다.

③ 원장 시뮬레이터 — 웹훅이 쓰고, 화면은 읽는다 (Day 33·34)

버튼 = 사건. 왼쪽 터미널이 웹훅 처리(서명 검증 → 중복 검사 → INSERT), 오른쪽이 Supabase 원장이다.

POST /api/portone/webhook — BFF API (서버 로그)
사건을 기다리는 중… [결제하기]를 눌러 보세요.
서명 검증은 PORTONE_WEBHOOK_SECRET, 원장 기록은 세션 없는 서버 작업이라 SUPABASE_SERVICE_ROLE_KEY(RLS 우회)가 필요하다. 웹훅은 재발송될 수 있으므로 같은 통지가 두 번 와도 원장에 두 줄이 생기면 안 된다 — 중복 검증.

④ 키의 자리, 규칙의 자리 (Day 33·34)

환경변수공개?용도
NEXT_PUBLIC_PORTONE_STORE_ID공개 식별자브라우저 결제창 호출 — 감출 수도, 감출 필요도 없다

PORTONE_WEBHOOK_SECRET서버 전용웹훅 서명 검증 — 없으면 가짜 결제 통지를 막을 수 없다
SUPABASE_SERVICE_ROLE_KEY서버 전용RLS 우회 원장 기록 — 노출되는 순간 DB 전체가 열린다
값은 전부 자리표시자다(store-xxxx…). 로컬 .env.local과 Vercel 환경 변수 양쪽에 등록해야 프로덕션 웹훅이 산다.
# 결제 규칙 (결제 SSOT) — rules/payment.md 발췌

결제와 관련된 모든 규칙(결제창 연동 · 환경변수 · 웹훅 · 결제취소 · 결제 내역)은 이 문서가 유일한 기준이다.
결제 코드를 추가·수정하기 전에 반드시 이 문서를 따르고, 규칙이 바뀌면 이 문서를 먼저 고친다.

— 두 번째 웹훅(취소)부터는 프롬프트가 세 줄로 준다: "SSOT는 rules/payment.md에 있어. 먼저 확인하고 구현해줘." 문서에 투자한 것이 프롬프트 길이로 회수되는 순간이다.

⑤ 퀴즈

🧩 결제 취소 시 해당 건을 수정하지 않고 1줄 더 등록하는 로그 형태의 방식?

insert-only (append-only) — "테이블에 2건"은 버그가 아니라 설계다.

🧩 카드 정보를 입력하여 받을 수 있는, 결제가 가능한 키?

빌링키 — 정기 구독 전용. 카드번호 대신 저장하고, 표시는 마스킹(**23)만.

🧩 유저가 결제한 돈에서 수수료를 차감해 최종 받을 돈을 확정하는 일?

정산 — 주기(1일/2일/주/월2회/월1회)는 계약 조건이다.
