## ② 왜 필요한가

프로젝트 둘째 날의 목표는 하나입니다 — **"동작하는 API"를 오늘 저녁에 갖는 것.**
기능이 다가 아니라, 명세 표의 **모든 칸**(성공도 실패도)이 실측과 일치하는 상태 말입니다.

순서에 주의하세요. 화려한 것(배치·성능·데모)은 전부 내일 이후입니다. 오늘 완성하는
"단건 예측 + 검증 + 로그"가 MP3 필수 기능의 몸통이고, 배점으로는 55점(API 품질 30 +
서빙 정확성 25)+로깅 일부가 오늘 하루에 걸려 있습니다. 프로젝트의 무게중심이 오늘입니다.

## ③ 개념 설명

### 3계층의 ML판 — 각 층이 모르는 것

[Day 093](day-093.md)의 "service는 HTTP를 모른다"가 추론 서버에서는 이렇게 됩니다:

| 층 | 아는 것 | 모르는 것 | MP3에서 하는 일 |
|---|---|---|---|
| router | HTTP · multipart · 상태 코드 | 모델 | 업로드 파싱 · 3중 검사 · 4xx 번역 |
| service | PIL Image · 텐서 · 모델 | **HTTP** (UploadFile 금지!) | 전처리 + 순전파 → dict |
| model_store | 파일 · 체크포인트 | HTTP도 이미지도 | 로드 · 보관 · 버전 |

경계 규칙 하나만 지키면 됩니다: **service의 함수 서명에 fastapi의 타입이 등장하면 위반.**
service가 `Image.Image`를 받으면, 내일의 배치도(이미지 목록) 목요일의 테스트도(서버 없이
service만 호출) 공짜가 됩니다 — [Day 085](day-085.md)의 predict()가 정확히 이 모양이었습니다.

### 에러 처리는 명세의 구현이다

어제 명세 표에 적은 실패 칸이 오늘의 할 일 목록입니다:

| 입력 | 응답 | 구현 위치 |
|---|---|---|
| 5MB 초과 | 413 | router (내용을 읽기 전에 크기부터 — 순서가 방어선) |
| 이미지 아님 | 415 | router (PIL로 열어 봐서 — 확장자 불신) |
| 파일 누락 | 422 | FastAPI가 자동 (UploadFile 선언의 효과) |
| 그 외 모든 500 | **버그** | — 500은 처리 대상이 아니라 발견 즉시 수정 대상 |

### 서빙 정확성의 증거 만들기

"전처리가 일치한다"는 주장이 아니라 **표**입니다. [Day 100](day-100.md) Step 3에서 한
것을 여러분의 모델로 반복해 `docs/report.md`에 박아 두세요:

| 입력 | 학습 시점 기록 ([Day 085](day-085.md)) | 오늘 API 응답 | 일치 |
|---|---|---|---|
| 개미 사진 (val) | ants 0.7214 | ants 0.7214 | ✅ |
| 벌 사진 (val) | bees 0.7694 | bees 0.7694 | ✅ |

이 표가 심사에서 서빙 정확성 25점의 증거이고, 목요일에는 **회귀 테스트**로 승격됩니다.

## ④ 단계별 실습

### Step 1. service와 router 구현 (1~3교시)

[Day 100](day-100.md) 프로토타입의 코드를 두 층으로 가릅니다. `app/service.py`:

```python
# app/service.py — 추론: 전처리 + 순전파. HTTP를 모른다.
import torch
from PIL import Image
from torchvision import transforms

# 학습(Day 083)과 같은 전처리 — 이 상수가 전처리 일치의 단일 진실
PREPROCESS = transforms.Compose([
    transforms.Resize(256), transforms.CenterCrop(224),
    transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225]),
])


def predict_image(model, classes: list[str], img: Image.Image) -> dict:
    x = PREPROCESS(img).unsqueeze(0)
    with torch.no_grad():
        probs = torch.softmax(model(x), dim=1)[0]
    top = int(probs.argmax())
    return {"label": classes[top], "confidence": round(float(probs[top]), 4)}
```

`app/router.py` (핵심):

```python
@router.post("/predict")
def predict(file: UploadFile):
    raw = file.file.read(MAX_BYTES + 1)
    if len(raw) > MAX_BYTES:
        raise HTTPException(413, detail="파일이 5MB를 넘습니다")
    try:
        img = Image.open(io.BytesIO(raw)).convert("RGB")   # 내용으로 검증
    except UnidentifiedImageError:
        raise HTTPException(415, detail=f"이미지 파일이 아닙니다: {file.filename}")
    result = service.predict_image(store.model(), store.classes(), img)
    return {**result, "model_version": store.version()}
```

> 텍스트를 고른 경우: service는 `predict_text(model, tok, text: str) -> dict`,
> router의 3중 검사 대신 pydantic 계약(`min_length`·`max_length`)이 방어선입니다.

### Step 2. 관측 이식 (4~5교시)

## ⑤ 자주 하는 실수

### service가 UploadFile을 받음

**증상** — 내일 배치를 만들 때 service를 또 고치고, 목요일 테스트에서 가짜 UploadFile을 만드느라 밤샘.
**원인** — 프로토타입(한 파일)의 모양을 그대로 가른다는 게 HTTP 타입까지 딸려 들어감.
**해결** — service의 입력은 도메인 타입(Image, str)으로. 파일→이미지 번역은 router의 일입니다.

### 전처리 상수가 두 곳에 존재

**증상** — 학습 코드와 서빙 코드에 각각 PREPROCESS가 복사돼 있고, 어느 날 한쪽만 수정됨 — 조용한 정확도 하락.
**원인** — 복사-붙여넣기가 만든 이중 진실.
**해결** — 전처리 정의는 한 곳(service 또는 공용 모듈)에만 두고 학습·서빙이 같이 임포트 — [Day 097](day-097.md)의 "사람이 지킬 규칙을 구조가 지키게".

### except Exception으로 500을 "처리"함

**증상** — 모든 에러가 `{"detail": "오류가 발생했습니다"}` 200 또는 400 — 진짜 버그가 로그도 없이 증발.
**원인** — "500이 나면 감점"을 "500을 숨기면 된다"로 번역.
**해결** — 500은 숨기는 게 아니라 **없애는** 것입니다: 예상 가능한 실패는 명세의 4xx로 하나씩 승격하고, 나머지 500은 재현 → 수정. 포괄 예외 처리는 버그 은닉 장치입니다.

### 로그에 이미지 바이트를 남김

**증상** — 로그 파일이 시간당 수백 MB, 그리고 사람 얼굴이 섞인 업로드가 로그에 영구 박제.
**원인** — "디버깅에 편할 것 같아서" — 기획서 4절의 정책을 코드가 배신.
**해결** — 입력 요약(파일명·크기)만. 원본이 정말 필요한 디버깅은 재현 요청으로 해결합니다 (X-Request-ID가 그 손잡이).

### 확신도가 낮으면 에러를 반환하도록 임의 추가

**증상** — confidence 0.55짜리 정상 요청이 400을 받음 — 명세에 없는 동작에 소비자 코드가 깨짐.
**원인** — "불확실한 예측은 안 주는 게 좋지 않나"라는 제품 결정을 혼자 코드에 넣음.
**해결** — 확신도는 응답에 실어 **소비자가 결정**하게 두는 것이 기본. 거절 정책을 넣고 싶다면 명세에 선언하고 근거를 기획서에 — 코드에 몰래 넣는 것이 문제입니다.

## ⑥ 확인 문제

**Q1.** "500은 처리 대상이 아니라 수정 대상"이라는 오늘의 규칙과, [Day 095](day-095.md) 리뷰
기준의 "500이 나는 입력 찾기 게임"의 관계를 설명하세요.

<details>
<summary>답 보기</summary>

500은 "서버가 예상 못 한 상황"의 신호이므로, 존재 자체가 명세의 구멍(예상했어야 할 입력)이거나
버그입니다. 리뷰 게임은 그 구멍을 찾는 탐색이고, 오늘의 규칙은 찾은 뒤의 처방입니다 — 4xx로
승격(명세에 추가)하거나 버그 수정. except Exception으로 감싸 400으로 바꾸는 것은 신호를 끄는
것이지 구멍을 메우는 것이 아닙니다.

</details>

**Q2.** service가 `Image.Image`를 받도록 설계한 것이 내일(배치)과 모레(테스트)에 각각 어떻게
이득이 되는지 구체적으로 쓰세요.

<details>
<summary>답 보기</summary>

배치: router가 파일 n개를 이미지 n개로 번역해 넘기면, service는 `[PREPROCESS(im) for im in imgs]`를
stack하는 배치판 함수를 쉽게 추가할 수 있습니다 — HTTP 파싱과 무관하게. 테스트: 서버·multipart 없이
`predict_image(model, classes, Image.open("ant.jpg"))`를 직접 호출하는 단위 테스트가 가능해,
전처리 일치 회귀 테스트를 TestClient 없이도 빠르게 돌릴 수 있습니다. 경계가 곧 테스트 지점입니다.

</details>
