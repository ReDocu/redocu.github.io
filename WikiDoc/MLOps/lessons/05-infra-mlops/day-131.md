## ② 왜 필요한가

[Day 126](day-126.md)에 남긴 커밋 메시지를 기억하십니까 — "ci: 모델을 저장소에 포함 (**임시**
— 큰 모델의 정답은 W27 DVC)". 오늘이 그 W27입니다. 왜 45MB를 Git에 넣는 게 임시방편인지,
숫자로 봅시다.

Git은 모든 버전을 영원히 보관합니다(그게 장점이죠). 모델을 주 1회 재학습하면:

```
45MB 모델 × 주 1회 갱신 × 1년 = 저장소에 +2.3GB (지울 수 없음 — 히스토리니까)
BERT(420MB)였다면            = +21GB … clone에 커피 두 잔
```

게다가 이진 파일은 diff도 병합도 안 됩니다 — Git의 강점(줄 단위 비교·3-way 병합)이 전부
무효화되고, 저장 비용만 남습니다. **Git은 텍스트의 도구입니다.**

그렇다고 버전 관리를 포기할 수는 없습니다 — 오히려 데이터·모델이야말로 버전이 생명입니다:
[Day 066](../03-machine-learning/day-066.md)에서 data_md5로 데이터의 지문을 찍고,
[Day 068](../03-machine-learning/day-068.md)에서 "모델은 물건"이라며 run_id를 새긴 것이 전부
그 요구였죠. 다만 그때는 지문을 **수동으로** 관리했습니다 — 오늘은 그 지문 관리를 Git과 한
몸으로 시스템화합니다. 요구사항은 하나의 문장입니다:

> `git checkout 그때` 하면 — 코드만이 아니라 **그때의 데이터와 모델**까지 돌아올 것.

## ③ 개념 설명

### DVC의 원리 — 포인터와 실물의 분리

DVC(Data Version Control)의 아이디어는 단순합니다: **Git에는 실물 대신 지문(포인터 파일)만
넣는다.**

```
[Git 저장소]                      [실물의 세계]
models.dvc  ──md5 지문──▶  .dvc/cache/  ──push/pull──▶  원격 저장소
(몇 줄짜리 텍스트)          (로컬 캐시)                  (S3·GDrive·서버 폴더…)
data.dvc    ──md5 지문──▶      〃                           〃
```

`dvc add models/` 를 하면 DVC가 ① 실물을 캐시로 옮기고 ② md5 지문이 적힌 `models.dvc`
(텍스트 몇 줄)를 만들어 줍니다. **Git은 이 .dvc 파일만 커밋합니다** — 커밋마다 "그 시점의
지문"이 박제되므로, 과거 커밋으로 가면 그 지문으로 실물을 캐시·원격에서 꺼내 올 수 있습니다.

| 명령 | 하는 일 | Git 대응 감각 |
|---|---|---|
| `dvc add 경로` | 실물을 관리 대상으로 — 지문 파일 생성 | git add |
| `dvc push / pull` | 캐시 ↔ **원격 저장소** 동기화 | git push / pull |
| `dvc checkout` | **현재 .dvc 지문대로** 작업 폴더 실물 교체 | git checkout의 화물판 |

### 두 저장소의 동행

오늘부터 저장소는 **이중 구조**입니다 — Git(코드·지문)과 DVC 원격(실물). 흐름도 짝으로
움직입니다:

```
변경:  실물 수정 → dvc add → git add *.dvc → git commit → dvc push → git push
복원:  git checkout <커밋>  →  dvc checkout (또는 dvc pull)
```

이 동행이 깨지는 지점들이 오늘의 ⑤입니다 — "코드는 왔는데 화물이 안 왔다"(push 누락),
"포인터는 과거인데 실물은 현재"(checkout 누락).

### 무엇을 DVC에, 무엇을 Git에

| 화물 | 도구 | 이유 |
|---|---|---|
| 코드 · 설정 · .dvc 지문 · 문서 | Git | 텍스트 — diff·리뷰·병합의 대상 |
| **데이터셋** (air_daily.csv와 그 갱신 이력) | **DVC** | 크고 갱신되는 이진/대용량 |
| **모델 아티팩트** (재학습 산출물) | **DVC** (+ 내일의 레지스트리) | 위와 동일 + 배포 대상 |
| 데모용 고정 소품 (tests/data의 개미 사진 2장) | Git | 작고 불변 — 과잉 도구화 금지 |

## ⑤ 자주 하는 실수

### dvc add만 하고 .dvc 파일을 커밋 안 함

**증상** — 화물은 새 버전인데 Git 히스토리에 그 사실이 없음 — "언제 바뀐 거죠?"에 답 불능.
**원인** — 동행의 반쪽 누락 — DVC는 지문을 만들 뿐, 시간축에 박제하는 것은 git commit입니다.
**해결** — `dvc add` 와 `git add *.dvc && git commit` 을 한 호흡으로. dvc add 출력이 친절하게
"git add 하라"고 알려 줍니다 — 도구의 잔소리를 읽으세요.

### git push만 하고 dvc push를 잊음

**증상** — 팀원이 clone + dvc pull 했더니:
```
WARNING: Cache '7f3e9a20c5d18b4f6e2a90d1c8b7f634' not found.
ERROR: failed to pull data from the cloud
```
**원인** — 지문(Git)은 세상에 나갔는데 실물(DVC 원격)은 내 캐시에만 — 소포 없이 송장만 보낸 것.
**해결** — push도 쌍으로: `dvc push && git push`. 순서도 이대로가 안전합니다 (실물 먼저 —
지문이 공개됐는데 실물이 없는 시간을 최소화). Git 훅이나 CI 검사로 강제할 수도 있습니다.

### git checkout 후 dvc checkout을 잊음

**증상** — 과거 커밋으로 갔는데 "지난주 버그가 재현이 안 돼요" — 코드는 과거, **데이터·모델은
현재**인 키메라 상태로 실험 중.
**원인** — 포인터만 시간 여행하고 실물은 남겨 둠.
**해결** — 시간 여행은 두 단계가 한 동작: `git checkout ... && dvc checkout`. 지문 대조
(md5sum vs .dvc 파일)로 일치를 확인하는 습관이 안전망입니다.

### DVC 관리 파일을 직접 수정하고 add를 잊음

**증상** — air_daily.csv를 스크립트로 갱신하고 dvc add 없이 커밋 — .dvc 지문은 옛것.
`dvc status` 를 보면:
```
data/air_daily.csv.dvc:
        changed outs:
                modified:           data/air_daily.csv
```
**원인** — Git의 "수정 후 add" 규율이 화물에도 그대로 적용된다는 것을 놓침.
**해결** — 화물 변경 절차의 끝은 언제나 `dvc status` 확인. CI에 `dvc status --quiet` (불일치
시 실패)를 넣으면 지문-실물 불일치가 구조적으로 차단됩니다.

### 모든 파일을 DVC로 — 과잉 도구화

**증상** — 테스트용 개미 사진 2장, 2KB짜리 스키마 JSON까지 dvc add — clone 후 dvc pull 없이는
테스트도 안 도는 저장소가 됨 (신규 합류 마찰만 증가).
**원인** — "이진 파일 = DVC"의 기계적 적용.
**해결** — ③의 기준표대로: **크고 갱신되는 것**만 DVC로. 작고 불변인 소품은 Git이 더 낫습니다
— 도구는 문제 크기에 비례해서만 도입합니다.

DVC가 각각을 어떻게 우회하는지 쓰세요.

<summary>답 보기</summary>

저장 구조: Git은 모든 버전을 히스토리에 영구 보관하므로 갱신되는 대용량 파일은 저장소를
단조 증가시키고, 그 비용을 모든 clone이 치릅니다. 협업 기능: diff·병합·리뷰가 전부 텍스트
전제라 이진 파일에선 무효 — 남는 것은 비용뿐. DVC의 우회: 히스토리에는 몇 줄짜리 지문 파일만
넣어 저장소를 가볍게 유지하고(실물은 원격 창고에, 필요한 버전만 pull), 지문 파일은 텍스트라
diff·리뷰("md5가 이렇게 바뀌었다")가 다시 가능해집니다.

**Q2.** "dvc push 없이 git push"가 만드는 고장을, 코드와 화물의 **가시성 시차** 개념으로
설명하고, 팀 차원의 방지 장치를 두 가지 제안하세요.

<details>
<summary>답 보기</summary>

git push 순간 지문은 전 세계에 보이지만 실물은 아직 내 캐시에만 — 이 시차 동안 다른 모든
사람에게 저장소는 "재현 불가능한 상태"입니다 (checkout은 되는데 실물 확보가 안 됨). CI도 dvc
pull 단계에서 깨집니다. 방지: ① 습관의 원자화 — `dvc push && git push` 를 스크립트/alias로
묶기, ② 시스템 검사 — CI 첫 단계에 dvc pull을 두어 "실물 없는 지문"이 올라오면 즉시 빨간불
(불일치의 조기 검출 — W26의 그물 원리 그대로).

</details>

**Q3.** Day 066의 수동 data_md5 규율과 오늘의 DVC를 비교해 — 도구가 대신해 준 것과, 여전히
사람의 몫으로 남은 것을 구분하세요.

<details>
<summary>답 보기</summary>

도구가 가져간 것: 지문 계산·기록(자동 md5), 지문↔실물 정합(checkout/status), 버전별 실물
보관·전송(캐시·원격), 시간축 연동(커밋마다 지문 박제). 사람의 몫: **언제** 버전을 만들지
(의미 있는 갱신 단위의 판단), 커밋 메시지에 **무엇을** 남길지(재학습 이유·성능 — 오늘의 "MAE
3.9"), 무엇을 DVC 관리 대상으로 할지(과잉 도구화 경계), 그리고 push 쌍 규율. 도구는 기록을
자동화하지만 기록의 **의미**는 여전히 설계의 영역입니다 — 이 구분이 내일 레지스트리("의미를
가진 버전 승격")로 이어집니다.

</details>
