## ② 왜 필요한가

혼자였던 MP4와 달리, 이번 주 이 저장소에는 **하루 6~10개의 PR**이 들어옵니다. 수동
배포 체제에서 4인의 병렬 개발이 어떤 모습이 되는지는 상상만으로 충분합니다 — "지금
서버에 올라간 게 누구 버전이죠?" "제 것 머지됐는데 배포는 언제 해요?" "어제 하람이
올린 뒤로 뭔가 이상한데요." 배포가 사람의 손에 있으면 배포는 병목이자 블랙박스가 되고,
그 사람은 다른 일을 못 하게 됩니다.

CI/CD는 이 문제를 **관문의 기계화**로 풉니다 — 검증(게이트)도, 빌드도, 배포도, 실패 시
복구(롤백)도 사람의 기억이 아니라 파이프라인이 수행합니다. 여러분은 이 전부를 W26에서
만들어 봤습니다. 오늘 새로 배우는 것은 없고, 대신 **팀이라는 조건**이 추가하는 요구
사항들을 다룹니다: 누구의 병합이든 같은 관문을 통과할 것(예외 없음), 두 병합이 겹쳐도
배포가 꼬이지 않을 것(잠금), 시크릿의 주인이 개인이 아니라 팀일 것.

그리고 오늘이 끝나면 이 프로젝트의 유명한 순간이 가능해집니다 — **커밋을 밀고, 아무것도
하지 않고, 2분 40초 뒤 서비스가 바뀌어 있는 것.** 발표(159)의 라이브 시연이 바로 이
장면입니다.

## ③ 개념 설명

### 파이프라인 지도 — mlops-mp3 자산의 팀 판

```
PR ──▶ ci.yml: lint(14s) + pytest 23개(41s) ──▶ 초록이어야 병합 버튼 활성 (브랜치 보호)
main 병합 ──▶ build.yml: 이미지 빌드(캐시 58s) → GHCR push (태그 = 커밋 sha)
          ──▶ deploy(self-hosted runner): pull → compose up → 스모크(/health + /predict 1건)
                                          ├─ 통과: 배포 이력 기록
                                          └─ 실패: 직전 sha로 자동 롤백 + 알림
```

[Day 126](../05-infra-mlops/day-126.md)~[130](../05-infra-mlops/day-130.md)의 그
지도에서 달라진 곳만 굵게 보면 됩니다:

| 항목 | 개인 MP4 | 팀 판의 차이 |
|---|---|---|
| 게이트 | 자기 규율에 가까움 | **예외 없는 강제** — 관리자 포함 (설정으로 못 박음) |
| 배포 트리거 | 내 병합뿐 | 누구의 병합이든 — **concurrency 잠금**으로 순차화 |
| 시크릿 | 개인 계정 secrets | **팀 저장소 secrets** — 등록·교체 절차를 문서로 (담당 부재 대비) |
| 실패 알림 | 본인이 봄 | 팀 채널로 — 배포 실패는 전원의 정보 |

### 배포 잠금 — 겹치는 병합의 제어

두 PR이 3분 간격으로 병합되면 배포 두 개가 겹칠 수 있습니다 — 앞 배포의 compose up
도중에 뒤 배포가 pull을 시작하는 식으로. `concurrency: production` 선언 하나로 뒤
배포는 앞 배포가 끝날 때까지 대기합니다. 팀 규모에서 처음 필요해지는 장치입니다.

### 스모크의 범위 — 뜨는 것과 일하는 것

/health만 찌르는 스모크는 "떴다"만 봅니다. 한산 팀의 스모크는 **실제 예측 1건**(고정
입력 → 등급 응답 검사)을 포함합니다 — 모델 로드 실패·피처 조회 실패까지 잡는, "일한다"
의 검사입니다. 스모크가 깊을수록 롤백은 정확해집니다.

## ④ 단계별 실습

### Step 1. CI 강화 확인 (1교시)

```
$ gh pr checks 41
lint      ✓ 14s
test      ✓ 41s   (23 passed — 단위 17 · 계약 4 · 회귀 2)
```

151의 시점 감사·회귀 테스트가 CI에 들어 있는지 확인 — **사고의 재발 방지책은 CI에
있어야 방지책**입니다 (사람의 다짐은 2주를 못 갑니다).

### Step 2. 빌드와 레지스트리 — #29 (2~3교시)

```
$ gh run view --job build   (main 병합 후)
build-and-push  ✓ 2m03s (첫 회) → 58s (gha 캐시 워밍 후)
  → ghcr.io/team-hansan/hansan-api:9e3f21c   # 태그 = 커밋 sha — "지금 도는 게 어느 커밋?"의 답
```

### Step 3. 러너 등록과 배포 — #30 (4~6교시)

클라우드 서버에서 (144에 만든 deploy 계정으로 — root 아님):

```
$ ./config.sh --url https://github.com/team-hansan/hansan --token *** && ./run.sh &
$ # deploy.sh: pull(sha) → compose up -d → 스모크 → 실패 시 직전 sha 재기동
```

**롤백 리허설** — 일부러 /predict를 깨뜨린 커밋을 병합해 봅니다:

```
[deploy] 9f11a02 pull → up → smoke... FAIL (/predict 500)
[deploy] rollback → 9e3f21c 재기동 → smoke OK (41s)   # 사용자 관점 중단: 스모크 실패~복구 41초
```

롤백이 **실제로 일어나는 것을 본** 파이프라인만 믿을 수 있습니다 — 이 로그가 발표의
증거 자산이 됩니다 ([Day 129](../05-infra-mlops/day-129.md)의 리허설 규율 그대로).

### Step 4. 전 구간 실측과 잠금 (7~8교시)

```
$ git log --oneline -1 && date
d41f7a9 docs: 데모 페이지 안내 문구 수정
14:02:11
$ # (아무것도 하지 않는다)
$ curl -s localhost:8080/health | jq .build && date
"d41f7a9"
14:04:51        # 커밋 → 운영 반영 2m40s
```

이어서 PR 두 개를 3분 간격으로 병합 — Actions 화면에서 두 번째 배포가 `pending
(waiting for production lock)` 으로 대기했다가 순차 실행되는 것을 확인합니다.
마지막으로 파이프라인 지도에 실측 시간을 주석으로 단 `docs/PIPELINE.md`를 커밋 —
[Day 130](../05-infra-mlops/day-130.md)의 "실측 붙은 지도" 규율입니다.

**오늘 퇴근 체크** — □ CI 23개(재발 방지 테스트 포함) □ sha 태그 이미지 GHCR □ 배포+
스모크(예측 1건 포함) □ 롤백 리허설 로그 41s □ 커밋→운영 2m40s 실측 □ 잠금 동작 확인
□ 시크릿 등록·교체 절차 문서화

## ⑤ 자주 하는 실수

### CI를 원격 디버거로 사용

**증상** — "CI에서만 깨져서요" 커밋 11연타 — 팀원들의 PR 큐가 막히고 Actions 시간 소진.
**원인** — 로컬 재현 절차 부재.
**해결** — CI가 하는 일(lint·pytest)은 전부 로컬에서 같은 명령으로 돌 수 있어야 합니다.
환경 차이가 원인이면 Dockerfile 기준으로 로컬 재현([Day 128](../05-infra-mlops/day-128.md))
— "CI에서만"은 대부분 "내 환경에서만"의 거울상입니다.

### 시크릿이 워크플로 파일 안에

**증상** — `DB_PASSWORD: hansan1234` 가 build.yml에 — 저장소를 보는 전원+포크에 노출.
**원인** — secrets 등록이 귀찮아서 "임시로".
**해결** — 팀 저장소 Settings → Secrets에만. 그리고 **등록·교체 절차를 문서로** —
개인 프로젝트와 달리 팀에서는 "그 시크릿 누가 알아요?"가 실제 질문이 됩니다 (담당자
부재 시 교체 불능은 위험 등록부 감입니다).

### 러너를 root로, 아무 데나

**증상** — 러너가 root 홈에서 실행 — 배포 스크립트의 실수 하나가 서버 전체 권한으로
실행됨.
**원인** — "일단 되게" 세팅.
**해결** — 러너는 deploy 계정(sudo 불가), 작업 디렉터리는 서비스 경로로 — [Day 112](../05-infra-mlops/day-112.md)
의 최소 권한 원칙은 자동화된 실행자(러너)에게 더 중요합니다. 사람은 실수를 눈치라도
채지만 러너는 시키는 대로 전부 합니다.

### 롤백을 "만들어만" 둠

**증상** — 발표 질의 "롤백 해 보셨어요?" — "코드는 있습니다…" — 침묵.
**원인** — 실패 경로는 시연하기 무섭다는 심리 — 그래서 아무도 안 눌러 봄.
**해결** — 오늘 Step 3처럼 **일부러 깨서** 확인하는 것이 유일한 검증입니다. 부수 효과:
리허설에서 남긴 로그(FAIL → rollback → OK 41s)는 성공 시연보다 강한 발표 자산입니다 —
시스템의 신뢰는 실패 경로의 증명에서 나옵니다.

## ⑥ 확인 문제

**Q1.** "게이트에 예외 없음(관리자 포함)"이 팀에서 특히 중요한 이유를, 규칙의 강제
수단(설정 vs 합의)과 신뢰 비용의 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

합의로만 존재하는 규칙은 마감 압박 앞에서 "이번만"의 예외를 만들고, 예외는 반드시 가장
바쁜 순간(=가장 위험한 커밋)에 발생합니다. 설정으로 강제된 규칙은 예외 협상 자체가
불가능해 규칙 준수의 비용이 0이 됩니다 — 지키는 것이 아니라 어길 수 없는 것. 신뢰
관점: 예외가 한 번 목격되면 "그럼 저 초록 불은 항상 믿을 수 있는 게 아니네"가 되어,
리뷰어가 다시 사람 검증을 시작합니다 — 자동화가 주던 신뢰 절감이 사라집니다. 브랜치
보호의 "관리자 포함" 체크박스 하나가 그 신뢰의 물리적 담보입니다.

</details>

**Q2.** 스모크에 "실제 예측 1건"을 포함한 것이 /health만 찌르는 스모크 대비 어떤 실패
계열을 추가로 잡는지 구체적으로 나열하고, 스모크의 깊이와 롤백의 정확도가 왜 비례하는지
설명하세요.

<details>
<summary>답 보기</summary>

/health는 프로세스 기동과 웹 서버 응답만 증명합니다. 예측 1건은 그 뒤의 사슬 전체 —
모델 로드(레지스트리/캐시), DB 연결과 피처 조회(lag), 피처→모델 입력 변환, 등급 계산,
응답 직렬화 — 를 관통하므로, "떴지만 일 못 하는" 상태(모델 파일 손상, 마이그레이션
누락, 시점 감사 위반 등)를 배포 직후 수십 초 안에 잡습니다. 롤백 정확도와의 관계:
롤백은 스모크의 판정을 신뢰해 자동 발동되므로, 스모크가 얕으면 "떴으니 통과"로 나쁜
버전이 살아남고(거짓 통과), 그 발견은 사용자 불만이나 모니터링 지연 후로 밀립니다.
스모크가 검증하는 깊이까지가 "자동 복구가 보장되는 실패의 범위"입니다.

</details>

**Q3.** concurrency 잠금이 없을 때 두 배포가 겹치면 구체적으로 어떤 꼬임이 가능한지
시나리오 하나를 구성하고, 잠금이 "순차화"라는 단순한 해법으로 충분한 이유를 이 팀의
규모에서 논하세요.

<details>
<summary>답 보기</summary>

시나리오: PR-A(이미지 sha-a) 배포가 compose up 재기동 중인데 PR-B(sha-b) 배포가 시작 —
B의 pull이 끝나고 up을 실행하면 A의 스모크는 B의 컨테이너를 검사하게 됩니다. A 스모크가
실패로 판정되면 A의 롤백이 발동해 sha-a 이전으로 되돌리는데, 이때 B의 배포 기록은
"성공"으로 남아 — 서버 상태와 배포 이력이 어긋난, 디버깅 최악의 상태가 됩니다. 잠금의
충분성: 순차화의 비용은 뒤 배포의 대기(~3분)뿐인데, 하루 병합 6~10건 규모에서 대기의
기대 비용은 분 단위입니다. 병렬 배포·카나리 같은 정교한 해법이 주는 이득(대기 제거)이
복잡도 비용을 넘으려면 배포 빈도가 훨씬 높아야 합니다 — 규모에 맞는 가장 단순한 정합성
장치가 잠금입니다.

</details>
