## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `ps` · `top` 으로 서버에서 도는 프로세스를 찾고, 시그널(TERM/KILL)의 차이를 알고 종료할 수 있다.
- 터미널 종속 실행(`&`, nohup)이 왜 **서비스의 답이 아닌지** 설명할 수 있다.
- MP3 API를 **systemd 유닛**으로 등록해 `systemctl start/stop/status` 로 다룰 수 있다.
- **죽여도 살아나고, 재부팅에도 살아나는** 것을 실험으로 증명하고, `journalctl` 로 서비스 로그를 읽을 수 있다.

## ② 왜 필요한가

지금까지 MP3 API의 수명은 이랬습니다:

```
uvicorn 실행 → 서비스 가동 → 터미널 닫음(또는 노트북 절전) → 서비스 사망
```

서버로 무대를 옮겨도 `uvicorn ...` 을 손으로 치는 한 같은 운명입니다 — SSH 접속이 끊기면
(퇴근하면) 프로세스도 함께 죽습니다. "그럼 백그라운드로 돌리면 되지 않나요?" — 반쯤만 맞습니다:

| 방법 | 접속 끊겨도 사나 | 죽으면 살아나나 | 재부팅에 사나 | 로그는 |
|---|---|---|---|---|
| `uvicorn ...` (포그라운드) | ✗ | ✗ | ✗ | 터미널에 흘러감 |
| `nohup uvicorn ... &` | ✔ | **✗** | **✗** | nohup.out 방치 |
| **systemd 서비스** | ✔ | **✔ (자동 재시작)** | **✔ (자동 기동)** | journalctl로 관리 |

운영이 요구하는 것은 "실행"이 아니라 **항상성**입니다 — 프로세스가 튕겨도(메모리 초과, 버그)
스스로 일어나고, 서버가 재부팅돼도(커널 패치, 장애) 사람 없이 복귀하는 것. 리눅스에서 그
항상성을 담당하는 표준 관리자가 **systemd**이고, 오늘 MP3 API가 그 관리 아래로 들어갑니다.
이번 주 체크포인트("서버가 재부팅돼도 API가 살아나는가")를 오늘 통과합니다.

## ③ 개념 설명

### 프로세스 — 실행 중인 프로그램의 신분

| 용어 | 뜻 |
|---|---|
| 프로세스 | 실행 중인 프로그램 1개. 각자 **PID**(번호)를 가짐 |
| 부모/자식 | 프로세스는 프로세스가 낳음 (어제의 환경 변수 상속 경로) |
| 포그라운드 | 터미널을 점유하고 실행 (Ctrl+C가 닿는 상태) |
| 백그라운드 (`&`) | 터미널을 돌려주고 실행 — 단, 터미널이 죽으면 같이 죽는 건 대체로 마찬가지 |
| 데몬(daemon) | 터미널 없이 상주하는 프로세스 — nginx, sshd, 그리고 오늘의 mp3-api |

찾기와 종료:

```bash
ps aux | grep uvicorn        # 전체 프로세스에서 검색 (어제 배운 파이프!)
kill <PID>                   # SIGTERM: "정리하고 종료해라" (정중한 요청)
kill -9 <PID>                # SIGKILL: 즉사 — 정리 기회 없음 (최후 수단)
```

TERM과 KILL의 차이는 W25에서 중요해집니다 — 컨테이너 종료도 "TERM을 보내고 기다렸다가 KILL"
순서라서, TERM을 받았을 때 뒷정리(진행 중 요청 마무리)를 하는 앱이 **무중단 배포가 되는 앱**입니다.

### systemd — 서버의 모든 서비스를 관리하는 PID 1

systemd는 부팅 직후 가장 먼저 뜨는 프로세스(PID 1)로, 서버의 서비스 전부를 자식으로 거느립니다.
서비스 하나를 맡기려면 **유닛 파일** 하나를 쓰면 됩니다 — "무엇을, 누구로, 어떻게 돌리고,
죽으면 어쩔지"의 명세서:

```ini
[Unit]        ← 정체와 순서: 설명, 무엇이 뜬 다음에 시작할지 (After=network.target)
[Service]     ← 실행 명세: User, WorkingDirectory, ExecStart, Restart, 환경 주입
[Install]     ← 부팅 연결: enable 시 어느 단계에 걸어 둘지 (WantedBy=multi-user.target)
```

조작은 `systemctl` 다섯 동사가 전부입니다:

| 명령 | 뜻 |
|---|---|
| `systemctl start/stop/restart mp3-api` | 지금 켜기/끄기/재시작 |
| `systemctl status mp3-api` | 상태·최근 로그 요약 — **조사 1순위** |
| `systemctl enable mp3-api` | **부팅 시 자동 시작** 등록 (disable로 해제) |

start와 enable이 별개라는 것에 주의 — start는 "지금", enable은 "부팅마다"입니다. 배포 절차에는
보통 둘 다 들어갑니다.

### journalctl — 서비스 로그의 공식 창구

systemd가 관리하는 서비스의 stdout/stderr는 **journal**에 자동 수집됩니다.
[Day 098](../04-deep-learning-serving/day-098.md)에서 로그를 표준 스트림으로 흘려보내기만 하면
됐던 이유가 여기서 완성됩니다 — 수집·보관·조회는 플랫폼(systemd)의 일입니다:

```bash
journalctl -u mp3-api           # 이 서비스의 로그 전체
journalctl -u mp3-api -f        # 실시간 추적 (tail -f의 서비스판)
journalctl -u mp3-api --since "10 min ago"
```

### Step 3. systemd 가동 확인과 유닛 작성 (5~6교시)

WSL에서 systemd가 켜져 있는지 먼저 확인합니다:

```bash
systemctl list-units --type=service | head -3
```

정상 목록이 나오면 통과. 대신 `System has not been booted with systemd (PID 1)` 가 나오면
`/etc/wsl.conf` 에 두 줄을 넣고 WSL을 재시작합니다 (⑤ 첫 항목 참고):

```ini
[boot]
systemd=true
```

이제 유닛 파일 — root 영역(/etc)이므로 sudo로 편집합니다 (`sudo nano /etc/systemd/system/mp3-api.service`):

```ini
[Unit]
Description=MP3 inference API (mlops-mp3)
After=network.target

[Service]
User=deploy
Group=deploy
WorkingDirectory=/opt/mlops-mp3
EnvironmentFile=/opt/mlops-mp3/.env
ExecStart=/opt/mlops-mp3/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

읽어 둘 세 줄 — `User=deploy`(어제의 최소 권한이 여기서 결실), `EnvironmentFile=`(어제 Q3의
답 — systemd의 자식에게 설정을 물려주는 공식 통로), `ExecStart` 의 **venv 안 절대 경로**
(activate 없이도 그 venv의 uvicorn·패키지를 쓰는 방법 — ⑤ 세 번째 실수의 예방).

등록과 기동:

```bash
sudo systemctl daemon-reload
sudo systemctl start mp3-api
systemctl status mp3-api
```

```
$ systemctl status mp3-api
● mp3-api.service - MP3 inference API (mlops-mp3)
     Loaded: loaded (/etc/systemd/system/mp3-api.service; disabled; vendor preset: enabled)
     Active: active (running) since Wed 2026-08-13 13:41:07 KST; 12s ago
   Main PID: 5233 (uvicorn)
      Tasks: 5 (limit: 9421)
     Memory: 412.3M
     CGroup: /system.slice/mp3-api.service
             └─5233 /opt/mlops-mp3/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000

Aug 13 13:41:09 DESKTOP uvicorn[5233]: INFO:     Application startup complete.
```

`active (running)` + Memory 400MB대(모델이 실렸다는 물증) + 로그 끝의 startup complete —
석 줄이 "서비스가 정상"의 3중 확인입니다. `curl http://localhost:8000/health` 도 200.

운영자가 가장 알고 싶은 것: **죽으면 정말 살아나는가.** 직접 죽여서 확인합니다:

Aug 13 13:52:33 DESKTOP uvicorn[5871]: INFO:     Application startup complete.

## ⑤ 자주 하는 실수

### System has not been booted with systemd (PID 1)

**증상** —
```
System has not been booted with systemd as init system (PID 1). Can't operate.
Failed to connect to bus: Host is down
```
**원인** — WSL 배포판에서 systemd가 꺼져 있음 (구버전 설치본에 흔함).
**해결** — `/etc/wsl.conf` 에 `[boot]` `systemd=true` 두 줄 추가 → PowerShell에서
`wsl --shutdown` → 재진입. `systemctl list-units` 가 목록을 내면 성공입니다.

### 유닛 파일을 고쳤는데 반영이 안 됨

**증상** — ExecStart를 수정하고 restart 했는데 옛 명령으로 뜸.
**원인** — systemd는 유닛 파일을 **메모리에 캐시**합니다. 파일 수정 ≠ 반영.
**해결** — 수정 후엔 반드시 `sudo systemctl daemon-reload` → `restart`. "유닛을 고치면
daemon-reload"를 한 동작으로 묶어 기억하세요 (status 출력도 reload가 필요하면 경고를 띄워 줍니다).

### ExecStart가 셸 습관을 가정

**증상** — `status=203/EXEC` 또는 `ModuleNotFoundError` 로 즉사. 셸에서 직접 치면 되는데
서비스로는 안 됨.
**원인** — ExecStart는 **셸이 아닙니다** — `source .venv/bin/activate`, `cd`, `~`, 파이프 같은
셸 문법·상태를 모릅니다. PATH도 최소한입니다.
**해결** — 실행 파일은 **절대 경로**(venv 안 uvicorn), 작업 위치는 `WorkingDirectory=`,
환경은 `Environment=`/`EnvironmentFile=` — 유닛의 전용 통로로 전부 명시합니다.

### 죽었는데 status를 안 읽고 재시작만 반복

**증상** — `Active: failed` → 무조건 `restart` → 또 failed → 또 restart…
**원인** — 원인 조사 없이 증상 조치만 반복. Restart= 설정마저 on-failure면 systemd도 함께
헛재시작 중이었을 수 있습니다.
**해결** — `systemctl status` 의 마지막 로그 줄 → `journalctl -u mp3-api -n 50` 으로 사망 직전
스택을 읽습니다. `code=exited, status=1` 은 앱 에러(로그에 traceback), `status=203` 은 실행
경로 문제, `code=killed, status=9` 는 외부 kill 또는 OOM — 코드가 원인을 분류해 줍니다.

### Address already in use

**증상** —
```
ERROR:    [Errno 98] Address already in use
```
**원인** — 같은 포트(8000)를 쓰는 프로세스가 이미 있음 — 대개 Step 2에서 손으로 띄운 uvicorn을
안 끄고 서비스를 시작한 경우입니다.
**해결** — `sudo ss -tlnp | grep 8000` 으로 점유자를 찾아 정리합니다 (ss는 내일 정식으로 배웁니다).
교훈: **한 서비스의 실행 주체는 하나** — systemd에 맡겼으면 손 실행은 금지입니다.

## ⑥ 확인 문제

**Q1.** `nohup uvicorn ... &` 와 systemd 서비스의 차이를 "새벽 3시에 프로세스가 죽었다"는
시나리오로 비교 서술하세요.

<details>
<summary>답 보기</summary>

nohup: 프로세스는 조용히 사라지고 아무도 모릅니다. 아침에 사용자 신고로 발견 — 로그는 nohup.out
어딘가, 원인 조사도 수동, 복구도 수동(누군가 접속해 재실행). systemd: 죽는 즉시 journal에 종료
코드가 기록되고 Restart 정책이 수 초 내 재기동 — 서비스 공백이 초 단위로 끝나며, 아침에
`journalctl` 로 "몇 시에 왜 죽고 몇 번 재시작됐나"를 조사할 수 있습니다. 운영의 차이는 실행
방법이 아니라 **죽음 이후의 자동화**에서 갈립니다.

최소 권한 위반입니다. 예: MP3 API의 이미지 업로드 처리에 취약점이 있어 공격자가 원격 명령

**Q3.** `EnvironmentFile=/opt/mlops-mp3/.env` 가 어제 배운 "환경 변수는 상속 재산" 원리의
어떤 문제를 푸는지, 그리고 이 .env 파일에 어제 정한 권한이 왜 여전히 중요한지 쓰세요.

<details>
<summary>답 보기</summary>

서비스는 내 셸의 자식이 아니라 systemd의 자식이라 .bashrc의 export를 물려받지 못합니다 —
EnvironmentFile은 systemd가 서비스를 낳을 때 그 파일의 변수들을 **직접 물려주는** 공식 통로로,
"셸에선 되는데 서비스로는 안 되는" 설정 실종 문제를 풉니다. 권한이 여전히 중요한 이유: 이 파일엔
DB 비밀번호 같은 시크릿이 들어 있고, systemd는 root로 읽으므로 600이어도 동작에 지장이 없습니다
— 600이 아니면 같은 서버의 아무 계정이나 읽는 어제의 사고 A가 그대로 재현됩니다.

</details>
