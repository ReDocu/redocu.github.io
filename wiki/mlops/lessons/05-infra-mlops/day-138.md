## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 심사 시나리오(**그 자리에서 PR → 게이트 → 병합 → 자동 배포 → 반영 확인**)를 관찰 포인트와 함께 자가 실행할 수 있다.
- **롤백의 두 층**(응급: 이미지 sha / 정사: revert PR)을 구분하고, 둘 다 실측 시간과 함께 리허설할 수 있다.
- 금요일 시연에 쓸 **안전한 변경 목록**을 준비하고 각각을 리허설할 수 있다.
- 오늘의 산출물: **자동 배포** — 전 사이클 기록과 롤백 증거를 갖춘.

---

## ② 왜 필요한가

오늘은 최대 배점 — **CI/CD 완성도 30점**의 날입니다. 이 점수의 심사 방법을 구체적으로
상상하는 것이 오늘의 출발점입니다. 심사위원은 아마 이렇게 말할 겁니다:

> "지금, 여기서, 아무 변경이나 PR로 넣어 보세요. 서버에 반영되는 것까지 보겠습니다.
> …됐네요. 그럼 이제 **방금 그 배포를 되돌려 보세요.**"

앞 문장은 화요일까지의 파이프라인이 이미 답합니다. 뒷 문장이 오늘의 몸통입니다 — 배포
자동화의 완성은 전진이 아니라 **후진의 증명**이기 때문입니다 (평가 기준의 "롤백 리허설"이
명시된 이유). 그리고 라이브 시연의 철칙 하나를 오늘 체화합니다: **리허설하지 않은 것은
시연하지 않는다.** 금요일의 여러분은 즉흥 연주자가 아니라, 세 번 연습한 곡을 치는 연주자여야
합니다.

## ③ 개념 설명

### 심사 시나리오의 관찰 포인트 — 보여 줄 것의 목록

같은 사이클도 **무엇을 가리키며 보여 주느냐**가 점수를 가릅니다:

| 단계 | 가리킬 것 | 증명되는 것 |
|---|---|---|
| PR 직후 | 잠긴 병합 버튼 + 돌아가는 체크 | 게이트가 장식이 아님 |
| 체크 완료 | lint 20s·test 55s·container-check 병렬 | 검증의 분업·속도 |
| 병합 | Build & Push 자동 시작 | 병합=생산의 등식 |
| 빌드 완료 | GHCR의 새 sha 태그 | 커밋↔이미지 족보 |
| 배포 | self-hosted 러너의 deploy 로그 (스모크 포함) | 배포의 자가 검증 |
| 반영 | /health의 image_tag 변화 + 이력 파일 새 행 | 끝까지 자동 + 기록 |

### 롤백의 두 층 — 응급실과 정사(正史)

| | A. 응급 롤백 | B. 정사 롤백 |
|---|---|---|
| 수단 | 서버에서 `deploy.sh sha-이전` | **revert PR** → 게이트 → 자동 재배포 |
| 소요 | ~40초 | 3~5분 |
| main의 상태 | 문제 커밋이 **아직 정사에 남음** | 정사 자체가 수정됨 |
| 언제 | 장애 중 — 서비스부터 살린다 | 응급 처치 후, 또는 여유가 있을 때 |

**A 후에 반드시 B**가 따라와야 합니다 — A만 하면 main과 서버가 어긋난 채([Day 129](day-129.md)
②의 그 불일치) 다음 병합이 문제 커밋을 다시 배포합니다. "응급실에서 살리고, 정사를 고쳐
재발을 막는다" — 두 층의 순서까지가 롤백 절차입니다.

### 시연용 변경의 3조건

금요일에 "아무 변경"을 즉석에서 만들면 안 됩니다 (⑤). 시연 변경은 오늘 목록으로 준비합니다:

1. **눈에 보일 것** — 청중이 변화를 화면에서 확인 (데모 페이지 문구·버전 배지)
2. **안전할 것** — 실패해도 서비스 무해 (핵심 로직·설정 불가침)
3. **1분 내 확인** — 반영 확인이 새로고침 한 번

## ④ 단계별 실습

### Step 1. 심사 시나리오 자가 실행 (1~3교시)

③의 관찰 포인트 표를 옆에 두고, 풀 사이클을 **기록하며** 돌립니다. 변경: 데모 페이지에
버전 배지 추가 (`<footer>build: sha-미정</footer>` — 배포 시 태그가 치환되게 하면 반영
확인이 자명해집니다):

```
10:12:40  PR #31 열림 → 체크 3종 시작, Merge 버튼 잠김 확인 (스크린샷 1)
10:15:02  전부 초록 · 짝 승인 → Squash merge
10:15:11  Build & Push 시작 → 10:16:34 sha-d02f91c push (스크린샷 2)
10:16:37  deploy 시작 → 스모크 통과 → 10:17:19 이력 기록
10:17:30  데모 페이지 새로고침 → footer에 "build: sha-d02f91c" (스크린샷 3)
────────────────────────────────────────────
PR 병합부터 반영까지 2m 17s · 사람 개입: 승인 1회 (의도된 관문)
```

이 기록 자체가 `docs/DEPLOY.md` 의 "표준 사이클" 절이 됩니다 — 금요일에 같은 것을 라이브로
반복할 뿐입니다.

### Step 2. 롤백 리허설 — 두 층 다, 시간 재며 (4~6교시)

**A. 응급** — 방금 배포(sha-d02f91c)에 문제가 있다고 가정:

```bash
time ssh deploy@localhost -p 2222 "/opt/mlops-mp3/deploy.sh sha-9e21c47"
```

```
[deploy] sha-9e21c47 배포 (이전: sha-d02f91c)
[deploy] 성공 — 이력 기록 완료
real    0m38.7s
$ curl -s localhost:8080/health | grep -o '"image_tag":"[^"]*"'
"image_tag":"sha-9e21c47"
```

**38.7초** — 장애 상황에서 서비스가 옛 버전으로 돌아가는 시간입니다. 이력에는
`sha-9e21c47 ok (manual rollback from sha-d02f91c)` 가 남습니다.

**B. 정사** — 이제 main을 고칩니다 (문제 커밋이 실제로는 무해하므로 리허설로는 재-revert):

```bash
git revert d02f91c --no-edit && git push   # → PR → 게이트 → 병합
```

병합 순간부터 파이프라인이 알아서: 빌드 → 새 sha → 자동 배포. **4분 12초** 후 서버는 revert
반영분으로. 두 수치(38.7s / 4m12s)를 DEPLOY.md의 롤백 절에 기록 — "어느 상황에 어느 층을
쓰나"의 판단 기준([Day 129](day-129.md) ③의 표)과 함께.

> 상급 트랙 참고 — 모델의 롤백([Day 132](day-132.md)의 별칭 이동, 7초)은 **제3의 층**입니다.
> 코드·이미지는 그대로인데 모델만 되돌리는 경우 — 내일 운영 절차서에서 세 층을 한 표로
> 정리합니다.

### Step 3. 시연 변경 목록 만들기 (7교시)

3조건을 만족하는 변경 3개를 준비하고 **각각 리허설**합니다 (금요일에 하나를 골라 쓰고,
나머지는 예비):

| # | 변경 | 확인 방법 | 리허설 결과 |
|---|---|---|---|
| 1 | 데모 페이지 제목에 이모지 | 새로고침 | ✅ 2m 05s |
| 2 | /health에 uptime_s 필드 | curl 한 줄 | ✅ 2m 21s |
| 3 | 데모 결과에 신뢰도 % 표기 | 업로드 1회 | ✅ 2m 14s |

### Step 4. 시연 실패 대비 — 백업의 3층 (8교시)

[Day 105](../04-deep-learning-serving/day-105.md)에서 배운 백업 3층을 CI/CD 시연판으로:

1. **1층: 라이브** — Step 3의 목록에서 실행 (사전 점검: 러너 Idle 확인 · GHCR 정상 · 캐시 웜)
2. **2층: 오늘의 기록** — 라이브가 막히면 Step 1의 타임스탬프·스크린샷으로 대체 서술
3. **3층: 영상** — 오늘 사이클 하나를 화면 녹화로 남겨 두기 (소리 없이 2분 30초)

**오늘 퇴근 체크** — □ 풀 사이클 기록(DEPLOY.md) □ 롤백 A/B 실측 (38.7s·4m12s급) □ 시연
변경 3종 리허설 완료 □ 백업 3층 확보 □ 워크플로 **동결 선언** (내일부터 파이프라인 수정 금지)

## ⑤ 자주 하는 실수

### 시연 변경을 무대에서 즉석 작성

**증상** — 발표 중 "간단히 문구 하나 바꿔 보겠습니다" → 오타로 lint 실패 → 고치는 손이 떨림
→ 3분의 정적.
**원인** — 시연을 능력의 증명으로 착각 — 시연은 **재현의 증명**입니다.
**해결** — 오늘 Step 3이 그 방지책입니다: 변경은 준비된 목록에서, 브랜치까지 미리 만들어
두어도 됩니다 (커밋만 무대에서). 무대에서의 창의성은 질의응답에서 발휘하세요.

### 롤백을 문서로만 안다

**증상** — "롤백 절차 있습니다 (문서 가리킴)" → "지금 해 보세요" → 처음 해 보는 손놀림,
이전 sha를 찾느라 이력 파일을 헤맴.
**원인** — 절차서와 근육의 간극 — 읽은 것과 해 본 것의 차이.
**해결** — 오늘 A/B를 **실제로** 돌린 이유입니다. 실측 시간(38.7초)을 말할 수 있다는 것
자체가 "해 봤다"의 증거이고, 심사에서 가장 강한 답변 형식입니다.

### 발표 직전의 파이프라인 손질

**증상** — 목요일 밤 "워크플로 좀만 다듬자" → 캐시 키 변경 → 금요일 아침 첫 빌드 8분 (콜드) —
시연 시간 초과.
**원인** — 파이프라인도 배포물이라는 인식 부족 — 검증 안 된 변경은 코드든 YAML이든 위험.
**해결** — 오늘의 **동결 선언**: 이 시점부터 .github/·compose·nginx 설정은 불가침. 남은
이틀의 변경은 문서·데모 페이지·모델 절차(내일)로 한정 — 전부 파이프라인 위를 지나가므로
파이프라인 자체는 흔들리지 않습니다.

### 시연 환경의 사전 점검 생략

**증상** — 발표 시작, PR을 여는데 러너가 Offline (아침에 WSL을 재시작하고 잊음) — 배포 단계
에서 무한 대기.
**원인** — "어제 됐으니 오늘도"의 가정 — 시연 환경도 서비스입니다.
**해결** — 발표 직전 점검 절차를 DEPLOY.md에 명문화: 러너 Idle · `docker compose ps` 전부
healthy · GHCR 로그인 유효 · 데모 페이지 응답 · (백업 3층 준비 확인). 5분짜리 이 절차가
10점을 지킵니다.

## ⑥ 확인 문제

**Q1.** "배포 자동화의 완성은 후진의 증명"인 이유를 — 롤백이 안 되는 자동 배포가 수동 배포보다
위험한 시나리오로 설명하세요.

<details>
<summary>답 보기</summary>

자동 배포는 배포의 빈도를 높입니다 — 나쁜 변경이 운영에 닿는 속도도 함께 빨라집니다. 롤백이
준비되지 않았다면, 장애 시 "고쳐서 앞으로"(수정 커밋 → 게이트 → 빌드 → 배포 = 수 분~수십 분)
가 유일한 경로인데 그동안 장애는 진행 중입니다. 수동 배포 시대에는 배포가 드물어 나쁜 변경도
드물었죠. 즉 전진만 자동화하면 사고의 빈도는 늘고 복구 속도는 그대로 — 순 위험이 증가합니다.
응급 롤백(38.7초)이 있어야 "빠른 전진"이 정당화됩니다 — 브레이크 없는 가속은 성능이 아닙니다.

</details>

**Q2.** 응급 롤백(A) 후 정사 롤백(B)을 생략하면 벌어지는 사고를 시간 순으로 서술하고, 이를
시스템적으로 방지하는 장치를 제안하세요.

<details>
<summary>답 보기</summary>

A 직후: 서버는 sha-이전, main의 HEAD는 여전히 문제 커밋 — 불일치 상태. 다음 날 누군가 무관한
PR을 병합 → 빌드는 main HEAD(문제 커밋 포함)로 → 자동 배포가 **문제 커밋을 다시 운영에** —
장애 재발, 게다가 "어제 롤백했는데 왜?"라는 혼란까지. 방지 장치: ① 응급 롤백 시 이력에
"정사 미수정" 플래그를 남기고, deploy.sh가 그 플래그가 있으면 다음 자동 배포를 차단(사람
확인 요구), ② 롤백 알림에 "revert PR 생성"을 할 일로 자동 첨부. 원칙: 응급 처치는 상태를
바꾸고, 정사 수정만이 상태를 **끝냅니다**.

</details>

**Q3.** 오늘 준비한 시연 변경 3종이 모두 "표시 층"의 변경입니다. 심사위원이 "핵심 로직 변경도
이 파이프라인으로 안전히 나가나요?"라고 묻는다면, 즉석 시연 없이 무엇으로 답하겠습니까?

<details>
<summary>답 보기</summary>

증거의 계층으로 답합니다: ① 게이트의 구성 — 핵심 로직을 지키는 회귀 테스트(0.7214±0.001,
Day 104)와 container-check가 required이므로, 로직 변경도 같은 관문을 통과해야만 나갑니다.
② 실제 이력 — 이번 주 병합 목록에서 로직 변경 PR(predlog 등)의 체크·배포 기록을 보여 줍니다
("이미 여러 번 그렇게 나갔습니다"). ③ 실패 사례의 증거 — 회귀 테스트가 실제로 잡아낸 기록
(Day 126 Step 4)과 스모크가 잡아 롤백한 기록 (Day 129 Step 5). 시연은 재현의 증명이고,
이력은 신뢰의 증명 — 후자가 더 강할 때가 많습니다.

</details>
