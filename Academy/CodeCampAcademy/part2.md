# 제1부 · 실무형 협업 구조와 기획, 그리고 디자인 (Day 6~7)

### 1. 통합형 vs 분리형 — 실무가 분리형을 택하는 이유

| 방식 | 구성 | 장점 | 단점 |
|---|---|---|---|
| **역할 통합형** | 기획+디자인+개발을 **한 번에** | **빠르다** | ① 전체 페이지 **디자인 일관성**을 잡기 어렵다 ② 부분만 고쳐도 전체가 흔들려 **유지보수**가 어렵다 |
| **역할 분리형 ⭐** | 기획 → 디자인 → 개발 **단계로** | 일관성 확립 · **한 화면에서 전체 유지보수** | 상대적으로 느리다 |

- **서비스는 한 번 만들고 끝이 아니다.** 계속 고쳐 나가야 하므로 실무는 분리형을 택한다.

| 단계 | 업무 | 전통 도구 | **AI 도구** |
|---|---|---|---|
| 기획/PM | PRD·백로그·제품 문서화 | 지라, 컨플루언스 | **PM-Skills** |
| 디자인 | 디자인 시스템·컴포넌트·화면 | 피그마 | **클로드 디자인**(충실도↑), 구글 스티치 |
| 개발 | 프론트·백엔드 API·DB 설계 | IDE | **클로드 코드 + Supabase** (TDD·SDD) |

- **지라·피그마·코딩을 직접 배울 필요는 없다.** 각 역할의 업무를 AI 도구가 대체하거나 거든다.
- PM-Skills 설치: `claude plugin marketplace add phuryn/pm-skills` → `claude plugin install pm-execution@pm-skills` → `/plugin`으로 확인. (Codex CLI도 같은 마켓플레이스를 쓴다.)
- **PM 두 종류를 구분한다** — **Product Manager**(제품 전체의 사업성·고객·데이터) vs **Project Manager**(제품 안의 특정 프로젝트 일정).

### 2. 핸드오프 — 충실도가 점점 높아진다

```
[기획/PM] ──PRD──▶ [디자인] ──하이-파이──▶ [개발]
 PM-Skills        클로드 디자인      클로드 코드 + Supabase
```

- **로-파이 = UX(뼈대), 하이-파이 = UI(완성 디자인)**, 개발은 하이-파이를 **"똑같이" 구현**하는 일이다.
- **AI 시대에는 로-파이(와이어프레임) 단계가 생략된다** — PRD에서 곧바로 하이-파이로 간다.
- 산출물의 **충실도(fidelity)가 뒤로 갈수록 높아지는 것**이 이 흐름의 본질이다.

### 3. PM의 세 역할과 기획/인터뷰 7단계

> PM 3역할: **① 기획/인터뷰**(뭘 만들지) → **② 프로젝트 관리**(일정 조율) → **③ 데이터 분석**(만들고 나서)

| 단계 | 방식 | 명령어 | 산출물 |
|:---:|:---:|---|---|
| ① 유저 인터뷰 | 🖐 | (엑셀 정리) | 인터뷰 원본 |
| ② 인터뷰 요약 | ⚡ | `/summarize-meeting` | `미팅.md` |
| ③ 인사이트 추출·전략 가정 | 🖐 | — | `인사이트.md` |
| ④ 전략 가정 공격 | ⚡ | `/strategy-red-team` | 보완된 가정 |
| ⑤ 우선순위 추출 | ⚡ | `/prioritization-frameworks` | 필수·선택·확장 |
| ⑥ 제품 브리프 | 🖐 | — | `BRIEF` |
| ⑦ PRD 생성 | ⚡ | `/create-prd` | `PRD` |

**1인 여행 숙소 예약 앱 예시 — 숨은 진짜 니즈를 찾는 과정**

- ② 요약: *"예약할 숙소가 없어요."* / *"갔던 숙소만 다시 가게 돼요."*
- ③ 인사이트: 반복되는 타깃(**1인 여행 20대 여성**) → 숨은 진짜 뜻 **"1인 여행 시 안전한 숙소를 못 찾겠어요"** → 전략 가정 **"안전성 점수를 도입하자"**
- ④ 공격: *"여기서의 안전은 숙소 자체인가, 숙소 근처 환경인가?"* → **"안전성 점수는 숙소 근처 환경까지 포함하자"**
- ⑤ 우선순위: **필수**(안전성 점수) · **선택**(찜하기) · **확장**(동행 찾기) → **MVP 범위 = 필수 + 선택**

- **실전은 파일 파이프라인으로 돈다** — `01-interview.csv` → `02-summary.md` → … → `07-prd.md`. 앞 산출물을 **`@`로 이어받아** 다음 명령의 입력으로 넣는다.

### 4. 디자인 프로세스 — 규칙 먼저, 조립은 나중

```
[기초]  레퍼런스 조사 → 디자인 시스템 → 화면 디자인
[심화]  레퍼런스 조사 → 메인페이지 시안 2~3개 → 디자인 시스템 → 화면 디자인
```

- **디자인 시스템 = 규칙**을 세우는 단계, **화면 디자인 = 부품(버튼·입력창)을 조립**하는 단계다.

| 디자인 시스템 3요소 | 내용 |
|---|---|
| **컬러 파운데이션** | 주·부 컬러, Accent/Success/Warning/Danger, 뉴트럴 스케일, 텍스트 팔레트 |
| **타이포그래피** | Display 40 → H1 30 → H2 24 → H3 19 → Body 15 → Small 14 → Caption 13 → Label 12 |
| **컴포넌트** | 입력폼 · 내비게이션(사이드바·탭·브레드크럼) · 서피스(카드·콜아웃·메뉴) |

- **레퍼런스 도구** — **UI볼 · WWIT**(국내), **mobbin**(해외).
- **참고 샘플 3종** — ① 사진(스크린샷) ② 피그마 파일(`.fig`) ③ 소스코드(html/css/js + **`DESIGN.md`**). `DESIGN.md` 모음 사이트는 **겟디자인MD**(75종).
- ⚠️ **폰트 저작권** — **상업적이면서 무료**인 폰트만 쓴다. 추천은 **프리텐다드(Pretendard)**.
- 클로드 디자인의 `Design systems` 탭에서 서비스 소개 + 샘플 4가지(깃허브 코드 / 로컬 코드 / `.fig` / 폰트·스크린샷·`DESIGN.md`)를 첨부해 생성한다.

> **🧩 퀴즈** — 화면 디자인을 위해 먼저 만드는 시스템은? → **디자인 시스템**

**📝 과제** — 미니 노션 PRD 만들기: 사용자(개인 업무 관리) / 기능(구글 로그인 · 마이 페이지 · 업무 페이지 `/page`) / 목적(무료 · 개인 최적화) → `02-prd.md`.

# 제2부 · 디자인을 코드로, 데이터를 구조로 (Day 8~9)

### 1. DESIGN.md — 디자인의 단일 원본

- 디자인 시스템을 만들어도 **새 페이지·UI를 추가**할 때 톤앤매너가 제각각이면 일관성이 무너진다. 이를 막는 문서가 **`DESIGN.md`** — 배경 사용 방식, 글꼴 스타일, 포인트 컬러, 컬러 토큰(`primary`, `ink`, `body-muted`)을 글로 적어 둔 **source of truth**다.

### 2. 메타프롬프트 — "프롬프트를 만드는 프롬프트"

```
✗ 사람 ──"DESIGN.md 만들어줘"──▶ [프롬프트] ──▶ DESIGN.md         (품질 들쭉날쭉)

⭐ 사람 ──"DESIGN.md 만들기 위한 프롬프트 만들어줘"──▶ [메타프롬프트]
                                         └ 반드시 지킬 조건 / 피해야 될 예시 / 완료 기준
                                         ──▶ [프롬프트] ──▶ DESIGN.md
```

- 결과물이 아니라 **결과물을 만들 프롬프트**를 먼저 만들게 한다. 그 프롬프트에 **반드시 지킬 조건 · 피해야 될 예시 · 완료 기준**이 담기므로 결과 품질이 안정된다.
- **잘 만든 프롬프트 1개를 자산으로 쌓아 계속 재사용한다.**

### 3. CLAUDE.md 등록 — 확률적에서 결정론적으로

> **왜 CLAUDE.md인가** — 클로드 코드는 **매 채팅마다 CLAUDE.md를 먼저 읽고 시작한다.**

```markdown
# 디자인 작업 규칙
**IMPORTANT: 이 규칙은 기본 동작보다 우선한다. 예외 없이 적용된다.**

## 1. 언제 (트리거)     — 디자인/UI를 건드리는 모든 작업
## 2. 반드시 (강제 행동) — 작업 전 DESIGN.md를 먼저 읽는다
## 3. 어떻게 (적용 방식) — DESIGN.md의 규칙대로 구현/수정한다
```

- 지시가 없으면 AI는 **확률적**(이번엔 지킬 수도, 안 지킬 수도)이지만, CLAUDE.md에 못 박으면 **결정론적**이 된다.
- 형식이 중요하다 — **언제(트리거) / 반드시(강제) / 어떻게(적용)** 세 칸을 채운다.

> **🧩 퀴즈** — 디자인을 가이드 문서로 만든 파일은? → **`DESIGN.md`**

### 4. 데이터 정규화 — 중복을 줄여 변경에 강하게

**문제**: 게시판 시트에 작성자 정보(이름·학년)를 통째로 넣으면, *"철수가 이름을 바꾸면?"* 에 **모든 행을 다 고쳐야** 한다.

**해법**: 작성자 정보를 별도 `학생` 시트로 빼고, 게시판에는 **"몇 번 학생"만 참조**하게 한다 → **1회 수정으로 끝난다.**

**정규화 3규칙**

> ① **한 칸에는 1개씩** 저장한다.
> ② **태그처럼 같은 성격의 컬럼 개수가 늘어나면** 다른 테이블로 분리한다.
> ③ **이름이 바뀌면 다 고쳐야 하는 중복 정보**는 다른 테이블로 분리한다.

**관계 3유형**

| 관계 | 예시 | 처리 |
|---|---|---|
| **1:1** | 학생 : 주소 | 그대로 |
| **1:N** | 학생 : 게시글 | FK로 참조 |
| **N:M** | 학생 : 수강과목 | **중간 테이블**로 분해 |

- **N:M을 그대로 두면 컬럼 추가 시 충돌한다** — "2번·3번 학생이 함께 듣는 과목의 점수 90점"을 한 칸에 적을 수 없다(누구의 90점?).
- **중간 테이블**(`학생_수강과목`)을 두어 `1:N` + `M:1`로 쪼개면, **점수 같은 관계 고유의 데이터**를 깔끔히 담을 수 있다.

| 키 | 역할 |
|---|---|
| **PK**(Primary-Key, 기본키) | 각 행을 **고유하게 식별**하는 열 |
| **FK**(Foreign-Key, 외래키) | 다른 테이블의 PK를 **가리키는** 열 |
| **Join** | PK–FK를 매개로 나뉜 테이블을 **다시 합쳐** 보는 것 |
| **ERD** | 테이블·관계·키·타입을 한눈에 그린 설계도 (ERDCloud.com) |

- 게시판 정규화 결과: **[게시판] [회원] [카테고리] [게시판_태그](중간) [댓글]**.

### 5. Supabase 실전 설계 — auth.users와 Profile

- 한 테이블에 다 넣으면 작성자 이름이 중복된다 → **User를 분리하고 Page는 `user_id`(FK)로 참조**한다.
- Supabase는 **`auth.users`**(로그인/인증, UID=UUID)를 **자동 제공**한다. 직접 건드리기 어려우므로 **`public.Profile`** 테이블을 따로 만들어 서비스용 정보(별명 등)를 관리하고, `user_id`(FK)로 `auth.users`의 UID(PK)를 참조한다.
- FK Action: **No action**(참조가 있으면 삭제를 막음) vs **Cascade**(참조 레코드까지 함께 삭제).

### 6. UUID vs auto_increment

| | auto_increment | **UUID** |
|---|---|---|
| 형태 | 1, 2, 3… 순차 정수 | 랜덤 난수 (전 세계 유일) |
| 장점 | **속도↑** | **시스템 보안↑ · 비즈니스 보안↑** |

> **⚠️ 쿠팡 개인정보 3,370만 건 유출 (2025.12)**
> 유출 원인은 **잘못된 유저 인증 시스템 설계**였다. 내부 DB의 사용자 식별값(PK)을 암호화된 난수가 아니라 **순서대로 1씩 늘어나는 정수(Auto Increment Integer)** 로 설정한 것이 핵심 결함이다.
> 그 결과 해커는 **이메일을 알 필요조차 없이 숫자 1부터 차례대로 대입**하는 것만으로 모든 사용자 계정을 특정할 수 있었다.
> **교훈: 사용자 식별자는 auto_increment가 아니라 UUID로 설계한다.**

- 실습 설계: **Page** — `id`(uuid, `gen_random_uuid()`, PK) · `created_at`(timestamptz, `now()`) · `title` · `content` · `user_id`(uuid, FK→`auth.users.id`).

**📝 과제** — 쇼핑몰 [상품] 테이블 정규화: `[상품] + [카테고리] + [판매자] + [상품_태그]`로 분리. 여유가 있으면 ERD로.

# 제3부 · AI를 통제하는 법 — LLM 엔지니어링과 하네스, 그리고 API (Day 9~10)

### 1. 문제의식 — "혹시 나만 AI를 잘 못 쓰나?"

> *"똑같은 GPT 쓰는데… 왜 내 AI만 멍청할까"* · *"왜 내 AI는 일을 못할까? 문제는 워크플로우!"*

> **현 시점 AI 성능 = AI 모델 + 도구 제어**

같은 모델이라도 **도구를 어떻게 제어하느냐**에 따라 결과가 갈린다.

### 2. LLM 엔지니어링 4단계 — 뒤로 갈수록 누적된다

| 단계 | 이름 | 핵심 |
|:---:|---|---|
| 1 | **프롬프트 엔지니어링** | 잘 부탁하기 |
| 2 | **컨텍스트 엔지니어링** | + **자료(경로)까지** 주기 |
| 3 | **하네스 엔지니어링** | + **안전 장치**로 통제하기 |
| 4 | **루프 엔지니어링** | + **자동화**하기 |

**② 컨텍스트 엔지니어링의 실제 모습** — 경로를 명시한다.

```
넌 이제부터 10년차 개발자야.
============================
본 프로젝트에 메인페이지를 추가해줘.
  1. 메인페이지 경로: ./src/pages/Home.tsx
============================
톤앤매너는 이미 만들어져 있는 글로벌 CSS를 사용해줘.
  1. 글로벌스타일 경로: ./src/styles/global.css
============================
카드·버튼·인풋은 다음 공통 컴포넌트를 불러와서 작성해줘.
  1. 카드: ./src/components/ui/Card.tsx  2. 버튼: …  3. 인풋: …
```

**③ 하네스 엔지니어링의 흐름** — `/plan`(작업계획 `plan.md`) → `@plan.md` 참고해 구현 → `/simplify`(리팩토링) → `/code-review`(리뷰).

**④ 루프 엔지니어링** — 계획을 Github에 저장하고 상태를 Supabase에 기록(`{파일: 장바구니작업계획.md, 상태: 미완료}`) → Claude Code가 **미완료 조회 → 구현 → `/simplify` → `/code-review`** 를 스스로 순환한다.

> **🧩 퀴즈** — AI에게 **관련 자료를 주고** 요청하는 엔지니어링은? → **컨텍스트 엔지니어링**

### 3. TDD와 SDD — 테스트가 먼저냐, 명세가 먼저냐

| | **TDD** | **SDD** |
|---|---|---|
| 뜻 | Test-Driven Development | Spec-Driven Development |
| 순서 | **테스트코드 먼저** → 기능 | **기능명세 먼저** → 기능 |
| 도구 | **Superpowers** | **Spec-kit(Speckit)** |

**테스트코드의 목적은 회귀 방지다.**

> *"기능을 새로 추가하면, **기존에 잘 됐던 다른 기능**이 왜 갑자기 작동을 안 하냐고!"*

모든 기능에 테스트를 만들어 두면, 신규 기능을 추가할 때마다 **이전 기능 전체를 강제로 검증**할 수 있다.

| 방식 | 설명 | 도구 |
|---|---|---|
| 헤드풀 브라우저 (느림) | 실제 브라우저를 켜고 클릭 | Playwright |
| **헤드리스 브라우저 (빠름)** | 보이지 않는 가상 브라우저 — **가장 일반적인 E2E** | Playwright |
| **브라우저 미사용** | 소스코드를 직접 실행 — **가장 일반적인 기능 테스트** | Jest, Vitest, Testing-Library |

**SDD의 핵심 — "그냥 구현해줘" 대신 두 문장으로 나눈다.**

> ① *"구현하기 **전에** 전체 구조가 담긴 **명세서를 먼저** 만들어줘."*
> ② *"명세서를 읽고, **그대로** 만들어줘."*
> **AI는 한 번에 한 가지 일을 잘한다** → 명세와 구현을 분리하라.

**실서비스 기준 실측 비교**

| | SDD 미적용 | **SDD 적용** |
|---|---|---|
| 코드 규모 | **6,715줄** | **399줄** |
| 컨텍스트 | 전체 읽기에 비용 증가 | 효율적, 버그 찾기 쉬움 |
| 수정 | 실수 가능성 높음 | 실수 가능성 적음 |

### 4. 하네스 도구들과 전개도

| 도구 | 용도 | 출처 |
|---|---|---|
| **Superpowers** | TDD·브레인스토밍 | 클로드코드 공식 |
| **Speckit** | SDD | GitHub |
| gstack | 제품 기획·배포/운영 | YCombinator CEO |
| omc(oh-my-claudecode) | 멀티에이전트 | 한국인 개발자 |
| ecc(everything-claude-code) | 개발·창업/투자 | 앤트로픽 해커톤 우승팀 |

```
기능 명세 작성 → 기능 명세 재검토(2회★) → 설계도 작성 → 작업 목록 → 테스트코드 + 기능 구현
 /specify         /clarify                /plan        /tasks        /implement
                                                    └── + /test-driven-development ──┘
```

- **`/clarify`(명세 재검토)가 가장 중요하다** — **2회 권장**. "구체화하는" 것만으로는 부족하고, 명세를 확실히 다듬는 것이 핵심이다.
- 설계가 끝나면 **쌓인 컨텍스트를 한 번 초기화**(약 20% 남았을 때)하고, 이후는 **설계대로만 구현**하므로 **저렴한 모델**로 충분하다.
- 관점: **명세 = 결정론적 틀, 구현 = 그 틀을 따름.**
- 내장 스킬은 `/plan` `/simplify` `/code-review` `/security-review` `/verify`.

### 5. API와 JSON

| | 프론트엔드 API 주소 | **백엔드 API 주소** |
|---|---|---|
| 예 | `naver.com` (HTML) | `koreanjson.com/posts/1` (**JSON**) |

- **실무에서 "API"라고 하면 대부분 백엔드(JSON)** 를 뜻한다.
- **HTTP 메서드** — **GET**(조회) / **POST · PATCH · DELETE**(등록·수정·삭제).
- **API 3종** — 백엔드 API(내가 만든 것) · **오픈(퍼블릭) API**(남이 공개한 것) · **외부·공공기관 API**(**활용신청·허가** 필요).
- 데이터 표현은 **JSON**이 대세(XML보다 간결). 오픈 API 모음은 **public-apis**(공식) · **open-apis-korea**(국내).
- API-Docs의 `{text}` = **패스 변수**, **Swagger** = API 문서 뷰어. 예: CATAAS `GET /cat/says/{text}`.

**Postman과 개발자도구**

- **브라우저 주소창은 GET만 가능**하다 → POST/PATCH/DELETE 실습은 **포스트맨**으로. 상태코드·응답시간·크기·Body(JSON)를 확인한다.
- 개발자도구 **Network 탭**에서도 실제 API 요청/응답을 볼 수 있다(예: 네이버페이 결제 내역이 JSON으로 내려온다).

> **⚠️ '모두의창업' 정보 유출** — *"AI 도구로 백엔드 API에 비정상 접근"*.
> **화면에서 숨겨도 API 응답에 담기면 노출된다.** `env` 값이나 API 응답은 개발자·아는 사람에게 그대로 보인다 — **민감 정보를 응답에 담지 말 것.**

| 대역 | 의미 | 대표 코드 |
|---|---|---|
| **200번대** | 성공 | `200 OK` `201 Created` `204 No Content` |
| **400번대** | **클라이언트** 잘못 | `400` `401 Unauthorized` `403 Forbidden` `404 Not Found` |
| **500번대** | **서버** 잘못 | `500 Internal Server Error` `502` `503` |

- 비유로 기억한다 — 손님(클라이언트) ↔ 서버의 "서빙". **프론트는 html 서빙, 백엔드는 json 서빙.**

**📝 과제** — 오픈 API로 고양이 사진: 브라우저(`cataas.com/cat/cute`)와 포스트맨 두 방식으로 호출 → Network 탭·상태코드(`200 OK`) 확인, `?tags=cute&limit=5`로 쿼리 변수도 실험.

- 스펙 작성 단계에서 **로딩 방식까지 못 박는다** — 명시하지 않으면 기본 스피너로 구현된다.

### 2. SOP와 CORS — 브라우저만 검사한다

> **SOP(Same Origin Policy)** — 브라우저에 열린 사이트는 **자기 출처(Origin)의 API만** 호출할 수 있다.

- `naver.com` 브라우저 → 네이버 API **O** / `naver.com` 브라우저 → **다음 API X**.
- **CORS(Cross Origin Resource Sharing)** 는 그 예외를 여는 장치다. **서버 쪽에서 "이 출처는 허용한다"고 선언**해야 열린다.

> **★ 핵심 문장** — *Origin은 **브라우저에 해당**하며, 백엔드서버·프론트엔드서버·모바일앱 등은 사이트가 아닌 단순 프로그램으로 해당되지 않아요.*
> 즉 **CORS는 브라우저만 검사하는 규칙**이다. 이것이 프록시 해법의 근거다.

| | 차단 방식 |
|---|---|
| **간단한 요청** | 요청은 서버까지 가고 응답도 오지만, **브라우저가 열람을 금지**한다 |
| **복잡한 요청** | 본 요청 전에 **사전요청(preflight)** 을 보내고, 비허용이면 **실제요청 자체를 안 보낸다** |

**실제로 겪어 보기** — `localhost:3001`에서 오리 사진 API를 부르면:

```
Access to fetch at 'https://random-d.uk/api/random' from origin 'http://localhost:3001'
has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

GET https://random-d.uk/api/random net::ERR_FAILED 200 (OK)
```

- **`200 (OK)`인데도 실패했다.** 서버는 정상 응답했고 **브라우저가 막은 것**이다. "오픈 API인데 왜 안 되지? 무료가 아닌가?"가 아니라 CORS 문제다.

**프록시 서버 — 내 편인 서버가 대신 요청한다**

```
브라우저 → 내 서버(프록시) → 외부 API 서버 → 내 서버 → 브라우저
```

- 브라우저는 **자기 출처의 서버**와만 통신하므로 SOP 위반이 아니고, 내 서버 → 외부 API 구간은 **서버 간 통신이라 CORS 검사를 받지 않는다.**
- 선택지 둘 — ① **프론트엔드 서버 프록시** ② **Supabase Edge Function 프록시**(150초간 실행되는 임시 백엔드).
- ⚠️ **CORS 허용 여부는 API 서버 쪽이 결정한다.** 내 프론트엔드 코드만 고쳐서 열 수는 없다.

### 3. 보안의 시작 — 회원가입과 로그인

> 바이브코딩 시대의 진정한 수혜자? — **보안을 공부하는 바이브코더**

| | 본질 |
|---|---|
| **회원가입** | 회원 테이블에 **1줄 등록** |
| **로그인** | 내가 이미 등록된 **"철수"임을 증명** |

게시글 등록과 회원 등록은 사실 같은 구조다. 그런데 **회원으로 게시글을 등록**하려면 게시판의 `회원ID`를 채워야 하고, 그러려면 **"내가 a@a.com이 맞다"를 증명**해야 한다 — 여기서 인증과 인가가 나온다.

| | **① 인증 (Authentication)** | **② 인가 (Authorization)** |
|---|---|---|
| 정의 | 로그인 증표 **받기** | 증표로 **증명하기** |
| 시점 | 로그인할 때 **1회** | 이후 요청 **매번** |

- **인증 6단계(세션 방식)** — 이메일/비밀번호 전송 → 회원 테이블과 **비교(=인증)** → 세션 테이블에 1줄 기록 → **세션ID 응답** → 브라우저 저장소에 저장.
- **인가 4단계** — **header에 세션ID**, **body에 제목/내용** → 세션 테이블에서 로그인 여부 확인(=인가) → **회원ID와 함께** 게시글 등록.
- ⚠️ 브라우저 저장소의 증표를 노리는 공격이 **XSS · CSRF**다.

### 4. 암호화와 해시 — 무엇을 어떻게 저장하나

| | **양방향 암호화** | **단방향 암호화(해시)** |
|---|---|---|
| 되돌리기 | **복호화 가능** | **복호화 불가** |
| 예 | `390907` → `cijijg` → `390907` | `390907` → `997` (여러 입력이 같은 출력) |
| 용도 | **개인정보**(이름·학교) — 화면에 다시 보여줘야 하므로 | **비밀번호** — DB가 털려도 원문 복원 불가 |
| DB 저장 모습 | `U2FsdGVkX1+z…` | `$2b$10$X9cO8pW3fQ…` (bcrypt) |

- 해커의 논리 — *"암호화 알고리즘만 찾아내면 전부 복호화할 수 있어!"* → **비밀번호는 반드시 단방향 해시.**
- **레인보우 테이블** — 가능한 비밀번호와 해시값 쌍을 미리 계산해 둔 표로 원문을 역추적하는 공격.
- **SALT(소금)** — 해시 전에 무작위 문자열을 붙인다(`390907 + a71DFe` → `B2Adg`). 해시 이전값을 알아내도 **비밀번호와 소금을 다시 찾아야** 하므로 레인보우 테이블이 무력화된다.
- 👉 비밀번호는 **서비스 운영자도 복호화할 수 없다.** 그래서 "비밀번호 찾기"가 아니라 **재발급**이다.

### 5. 세션 vs 토큰, 그리고 소셜로그인

| | **세션 방식** | **토큰 방식** |
|---|---|---|
| 로그인 상태 저장 | **세션 테이블(DB)** | **토큰 문자열 자체** |
| 장점 | 중복 로그인 감지 · **강제 로그아웃 가능** | 세션 테이블 불필요, **효율적** |
| 약점 | DB 조회 필요 | **강제 로그아웃 불가** — 상태가 브라우저 토큰에만 있음 |
| Supabase | 구독제 | **무료(FREE)** |

- **설계 순서**: **토큰 방식으로 시작** → 중복 로그인 제한·강제 로그아웃이 필요해지면 **세션 방식 추가**.
- 토큰 안에는 `{이메일, 회원ID, 로그인여부(만료 시각)}`가 들어가고, 인가 때 그것을 풀어 확인한다. **JWT**가 바로 이 토큰이다.

**소셜로그인과 OAuth**

- 회원가입 폼은 **가입 이탈**을 부른다 → **소셜로그인** = 이전에 가입했던 서비스의 정보로 **자동 가입/로그인**.
- **OAuth(Open Authorization)** 는 그 표준이며, 로그인뿐 아니라 **활동 정보**(구글 연락처, 카카오 친구 목록)까지 위임받을 수 있다.
- **인증 9단계에서 토큰이 세 번 바뀐다** — 구글 로그인 → **비밀 CODE** 발급 → Supabase가 CODE로 **구글 전용 토큰** 수령 → 확인 후 **Supabase 전용 토큰(JWT)** 발급 → 브라우저 저장.
- **핵심은 ②~⑦ 구간이 브라우저를 거치지 않는다는 것**이다. 브라우저가 최종적으로 쥐는 건 **Supabase 전용 토큰 하나**뿐이고, 이후 인가에도 **구글 토큰이 아니라 Supabase 토큰**을 쓴다.

### 6. 구글로그인 실습 — 연동 설정이 8할

| 방향 | 값 | 어디서 → 어디로 |
|---|---|---|
| ① | **Client ID** | GCP 발급 → **Supabase**에 입력 |
| ② | **Client Secret** | GCP 발급 → **Supabase**에 입력 |
| ③ | **Callback URL** | Supabase 제공 → **GCP**에 등록 |

> ⚠️ **Client Secret은 생성 다이얼로그를 닫으면 다시 볼 수 없다.** 그 자리에서 복사하거나 Download JSON. 놓쳤으면 재발급해야 한다.
> **Client ID는 공개돼도 되는 값(public)** 이지만 **Secret은 절대 아니다(private)**. 유출되면 **커밋을 지우는 걸로 해결되지 않고 콘솔에서 재발급**해야 한다.

- **`redirect_uri_mismatch`가 터지는 자리** — Callback URL은 **완전 일치**여야 한다. 아래는 전부 **서로 다른 URI**다:

```
…/callback     ≠ …/callback/        (끝 슬래시)
localhost:3000 ≠ 127.0.0.1:3000     (호스트)
localhost:3000 ≠ localhost:3001     (포트)
https://       ≠ http://            (스킴)
example.com    ≠ www.example.com    (서브도메인)
```

- **Skip nonce checks**는 켜지 말 것 — nonce 검사는 재생 공격 방어이고, Supabase 설명에도 *"less secure"* 라고 적혀 있다.

### 7. ★ JWT의 정체 — 암호화가 아니라 인코딩이다

> **1. JWT는 사실 암호화/복호화 방식이 아니다**
> **2. 누구든지 안에 내용을 확인할 수 있다**
> → 그러므로 **자체 구축 시에는 중요한 정보를 넣으면 안 된다**

`jwt.io`에 붙여넣으면 키 없이도 내용이 그대로 보인다:

```jsonc
// Header
{ "alg": "ES256", "kid": "8afc541e-…", "typ": "JWT" }
// Payload
{ "iss": "https://<프로젝트>.supabase.co/auth/v1",  // 발급자
  "sub": "60c2f8d4-8743-…",                       // 사용자 고유 ID
  "aud": "authenticated", "exp": 1784087534, "iat": 1784083934,
  "email": "…", "app_metadata": { "provider": "google" } }
```

- **그럼 왜 안전한가?** 내용을 숨겨서가 아니라 **서명(signature)** 때문이다. 아무나 읽을 수는 있지만 **서버의 키 없이는 고쳐도 서명이 깨진다.** JWT가 보장하는 것은 **기밀성이 아니라 무결성**이다.
- **"누구나 읽을 수 있다"와 "누구나 만들 수 있다"는 다르다.** 읽는 데는 키가 필요 없지만(=인코딩), **만드는 데는 서명 키가 필요하다.** 그래서 서버는 **서명·`iss`·`aud`·`exp`를 반드시 검증**해야 한다.
- 인가의 실체는 요청 헤더 한 줄이다 — **`Authorization: Bearer <JWT>`**. 이때 **`Apikey`와 혼동하지 말 것** — Apikey는 "어느 프로젝트냐"(공개값), Authorization은 "너는 누구냐"(로그인 증표)다.

> **★ 인가는 "빼보고" 검증한다** — 포스트맨/브라우저에서 **토큰 없이** 요청했을 때 **거부되어야 정상**이다. 통과한다면 누구나 남의 프로필을 고칠 수 있다는 뜻이다.
> **"화면에서 잘 되니까 됐다"는 검증이 아니다.** 되는 걸 확인하는 것과 **안 되는 걸 확인하는 것**은 다르고, 보안은 후자로 증명된다.

- 그리고 **토큰이 곧 신원이다** — 브라우저가 아니어도, 우리 앱이 아니어도 **유효한 토큰만 있으면 수정된다.** 즉 **토큰 유출 = 계정 탈취**다. 실습에서 토큰은 로컬스토리지에 있어 **JS로 읽을 수 있고 XSS에 노출**된다 — 실서비스라면 **httpOnly · secure 쿠키**를 검토해야 한다.
- **사용자 키는 이메일이 아니라 고유 ID(`sub`/UID)** 를 쓴다. 이메일은 바뀔 수 있고, 바뀌는 순간 다른 사람 계정에 붙는다.

### 1. 훅스 — 사람도 AI도 잊는다

> **⚠️ 나이트 캐피탈 사건 (2012-08-01)** — 자동 매매 시스템 업데이트 이후 **약 45분 만에 4억 4,000만 달러**(약 5천억 원) 손실.
> 원인은 복잡한 알고리즘이 아니었다. 일부 서버에 **구버전 코드가 남아** 있었고, 과거 테스트용 기능이 실제 시장에서 작동했다. **핵심은 배포와 검증 과정이었다** — 업데이트가 모든 시스템에 동일하게 반영되지 않았고, **최종 점검 없이 시장에 투입**됐다.
> **자동화된 구조일수록 오류의 전파 속도도 빠르다.** 100번 잘 하다가 101번째 실수하면?

훅의 두 자리는 사람의 두 실수와 정확히 대응한다.

> 😠 *"**업무 시작하기 전에** 메뉴얼 보는 걸 깜빡 했습니다."* → **PreToolUse**
> 😫 *"**보고서 완료 전에** 맞춤법 검사를 깜빡했네…"* → **Stop**

| | **① PreToolUse** | **② Stop** |
|---|---|---|
| 시점 | **도구 사용 전** | **작업 종료 전** |
| 하는 일 | `.env` 조회·변경 감지 시 **차단** | 하드코딩된 환경설정 감지 → **`.env.example` 분리** |
| 메시지 | 🚫 "클로드가 조회/수정 금지!" | ✍️ "대신 여기다 작성하면 내가 직접 `.env`에 옮길게!" |

- **둘은 짝이다.** 막기만 하면 Claude가 필요한 키를 알릴 방법이 없다 → **`.env.example`이라는 우회로**를 열어주고 실제 값은 사람이 옮긴다.
- **규칙 문서와 훅의 결정적 차이** — `.gitignore`와 규칙 문서는 **사람이 지켜야** 작동하고, 사람은 잊는다. **훅은 하네스가 직접 실행한다. 모델의 선의나 기억에 의존하지 않는다.**
- 실제로 훅이 **Claude 자신의 커밋 명령까지 막아섰다** — 이것이 "선의에 의존하지 않는다"의 실물이다.
- 훅 이벤트는 **총 30개**(PreToolUse ~ MessageDisplay). 오늘 쓰는 건 **1번(PreToolUse)** 과 **10번(Stop)**.
- 위치: **`.claude/settings.json`에 등록 + `.claude/hooks/*.sh`로 로직 분리**(실행 권한 755). 생성·수정은 **`/update-config`**, 조회는 **`/hooks`**(⚠️ **읽기 전용**).
- **설계 원칙: 탐지는 스크립트, 판단은 모델.** 셸 스크립트만으로는 진짜 설정값인지 알 수 없으니 탐지만 하고, 판단·작성은 모델에게 넘긴다.
- **훅은 오탐한다** — `const KEY = "mini-notion-v1"`(localStorage 키)을 환경설정으로 착각했다. **오탐 없는 탐지기는 놓치는 것도 많다.**
- **안전장치**: `stop_hook_active` 체크로 **무한 루프 방지**(종료를 막는 훅이 다시 종료를 막으면 세션이 안 끝난다).
- **한계와 계층 방어** — Bash 차단은 **문자열 패턴 기반**이라 난독화 우회는 못 막는다.

| 구멍 | 막는 계층 |
|---|---|
| `git add .` (파일명이 명령에 안 보임) | **`.gitignore`** ← 1차 방어 |
| 사람이 터미널에서 직접 커밋 | git `pre-commit` 훅 |
| 난독화된 Bash 우회 | `permissions.deny` |
| 이미 push된 과거 커밋 | 없음 → **키 재발급** |

> **⚠️ `.env*` 한 줄이 `.env.example`을 죽인다** — Next.js 기본 `.gitignore`가 이 상태다. 애써 만든 명세 파일이 커밋되지 않아 **아무도 무슨 키가 필요한지 모르게 된다.**
> **고치는 법(순서가 중요, 나중 줄이 이긴다):**
> ```gitignore
> .env             # 실제 값
> .env.*           # .env.local, .env.production …
> !.env.example    # 단, 명세 파일은 예외 (반드시 뒤에)
> ```
> 확인: `git check-ignore -v .env.example` → **출력이 없어야 정상.**

- ⚠️ **`NEXT_PUBLIC_` 접두사가 붙으면 빌드 시점에 클라이언트 번들에 인라인된다** = 브라우저에서 다 보인다. **접두사가 붙은 것만 클라이언트용으로 취급**하고, 서버 전용 키에는 절대 붙이지 않는다.

### 3. 기능 병렬 구현 — 공통 파일 충돌과 Git 워크트리

**병렬 구현은 왜 실패하는가.** 각 기능의 작업이 **2단계**이기 때문이다.

| 기능 | ① 새 파일 만들기 | ② 연결하기 |
|---|---|---|
| 검색 기능 | `검색기능.js` | **`메인화면.html`에 연결** |
| 리스트 기능 | `리스트기능.js` | **`메인화면.html`에 연결** |
| 페이지 기능 | `페이지기능.js` | **`메인화면.html`에 연결** |

- ①은 서로 다른 파일이라 충돌이 없다. 그런데 ②는 **셋 다 같은 파일을 건드린다** → **동시 수정 충돌.**

| | 폴더 직접 복사 | **Git 워크트리** |
|---|---|---|
| 동시 작업 | 가능 | 가능 |
| **합치기** | ❌ **불가** — 3개 파일을 열어 직접 합쳐야 | ✅ **가능** |
| 이유 | 서로를 모른다 | **`.git`이 변경 사항을 공유·추적** |

> **★ 이것이 워크트리를 쓰는 유일하고 결정적인 이유다.** 폴더를 복사해도 "동시에 작업"은 된다 — 문제는 **합칠 수가 없다**는 것이다.

**작업 순서 5단계**

```
① 메인과 워크트리 분리 → ② 각 워크트리에서 병렬 구현 → ③ 메인에서 통합
   → ④ 메인 리팩토링 → ⑤ 각 워크트리를 통합된 메인으로 동기화
```

- **⑤를 빠뜨리면 안 된다.** 메인이 바뀌었는데 워크트리가 옛 상태로 남아 있으면 **다음 라운드에서 또 충돌**한다.
- 단계별 지시는 말 한마디씩이다 — ② *"검색 기능 구현하고 커밋 해줘"* / ③ *"워크트리 1,2,3,4를 모두 원본에 합쳐줘"* / ④ *"최적화 및 리팩토링하고 커밋 해줘"* / ⑤ *"메인 폴더로 동기화해줘"*.
- **통합 직후 커밋 금지** — **통합 → 간소화 → 리뷰 → 커밋.**

**★ 병렬화 단위는 "기능 개수"가 아니라 "독립성"이다.**

| 그룹 | 기능 | 워크트리 |
|---|---|---|
| 🟧 게시글 | 등록 · 수정 · 조회 · 삭제 | **wt1** |
| ⬜ 다크모드 | 사이드바 토글 | wt2 |
| 🟩 사이드바 | 접기/펼치기 | wt3 |
| 🟪 프로필 자기소개 | 등록 · 수정 · 조회 | wt4 |

- **왜 게시글 4개를 한 워크트리에?** 글이 등록되지 않으면 **조회할 것이 없고**, 조회가 없으면 **삭제를 확인할 수 없다.** 서로가 서로의 전제다.
- 워크트리 **사이**는 병렬, 워크트리 **안**은 순차(등록/수정 → 조회 → 삭제). 연습용은 **4개** 정도가 적당하다.
- 각 워크트리에서 `/speckit-specify`로 **제약까지 명시**한다 — *"**내가 만든 DB 테이블 구조는 변경하면 안 돼.** 로그인된 유저가 등록하고, **자신의 글만** 조회하고, **자신의 글만** 삭제할 수 있어야 해."*

> **⚠️ Part 1(훅)과 Part 2(워크트리)가 만나는 지점**
> `.env.local`은 `.gitignore` 대상이라 **워크트리에 딸려오지 않고**, PreToolUse 훅 때문에 **Claude가 복사할 수도 없다** → **사람이 직접 복사한다.**
> 훅이 의도대로 작동해서 생기는 수고다. **안전과 편의는 맞바꾸는 관계다.**

**통합할 때 AI가 하는 일** — 읽을 줄 알면 개입할 수 있다.

1. **개발 서버 종료**(`pkill -f "next dev"`, 포트 확인) 2. **워크트리별 변경 파일 파악**(`git diff --name-only`)으로 공통 수정 파일 식별 3. **순차 병합**(stash → wt1 → wt2 → …, 충돌 처리) 4. **재기동 검증**(전 페이지 200, `.env.local` 로드, 로그인 활성).

- 디버깅의 기본 순환: *"작동 왜 안 되는지 확인하기 위해서 **네가 로그 남겨줘.** 그러면 내가 로그 스크린샷 찍어서 보내줄게."* — **AI가 관찰 수단을 심게 하고 그 출력을 다시 AI에게 돌려준다.**

### 4. 이미지 — 픽셀에서 Storage까지

- 사진 한 장 = **무수히 많은 픽셀의 조합**, 픽셀 하나 = **RGB 세 숫자(각 0~255)**. 사진이 숫자라는 것은 곧 **DB에 저장도 가능**하다는 뜻이다.
- **왜 하필 256인가** — 컴퓨터는 스위치(비트)다. 끄면 0, 켜면 1. **비트 8개 = 2⁸ = 256가지** = **1바이트**. 그래서 RGB 각 채널이 0~255다.
- 해상도 `1920 × 1080` = 픽셀이 가로 1920 × 세로 1080개.
- 이미지는 DB에 **BLOB**로 직접 넣을 수도 있지만, **용량이 커서 화면 전체가 이미지를 기다리게 된다.**

> **비동기 프로세스** — 용량이 작은 데이터(숫자·텍스트)와 큰 데이터(이미지)를 **분리해서 각각 따로 불러온다.** 그러면 텍스트만이라도 먼저 보여줄 수 있다.

| 저장소 | 담는 것 |
|---|---|
| **Supabase (DB)** | 숫자, 텍스트, **이미지주소** |
| **Supabase Storage** | 이미지·파일 **실물** → 업로드하면 **다운로드 주소**를 돌려준다 |

- **등록 4단계**: 저장하기 클릭 → 이미지만 먼저 **Storage 업로드** → **다운로드 주소** 반환 → `{이름, 학교, 이미지주소}`를 **DB에 저장**.
- **조회 4단계**: 프로필 요청 → DB가 텍스트+주소를 **즉시 응답**(텍스트 렌더, 이미지는 **스켈레톤**) → 주소로 **Storage에 별도 요청** → 다운로드 완료 후 표시.

```
https://supabase주소/스토리지이름 / 버킷이름/파일명.jpg
└──────── 스토리지경로 ────────┘ └───── 파일경로 ─────┘
      환경변수(.env)에 저장            DB에 저장
```

- 공통 값인 **스토리지경로는 `.env`**, **파일경로만 DB**에 넣는 것이 정석이다 — 그래야 스토리지를 옮겨도 데이터 수정이 없다.
- 파일명은 날짜·원본 이름 대신 **UUID(uuidv4)** 로 — **이름 충돌과 추측 가능한 주소**를 피한다.
- Supabase Storage는 **S3 프로토콜 호환**이라 S3 도구를 그대로 붙일 수 있다.

### 5. 배포 환경 4단계와 모니터링

| 단계 | 용도 | 회원테이블에 담기는 사람 | 주소(예) |
|---|---|---|---|
| **프로덕션** | 유저가 실제로 사용 | **진짜 회원들** | `mynotion.com` |
| **스테이징** | 기획·디자인·개발이 **최종 확인** | **내부 팀원들** | `staging.mynotion.com` |
| **개발** | 개발팀 확인 | **개발자들** | `dev.mynotion.com` |
| **로컬** | 내가 확인 | **나 혼자 연습** | `localhost:3000` |

- **환경을 나누는 근본 이유는 격리다** — 테스트하다 실수로 진짜 회원 데이터를 지우거나, 반쯤 만든 기능이 진짜 유저에게 노출되는 사고를 막는다.
- 4단계를 전부 갖추려면 **도메인 4 · `.env` 4 · Supabase 4 · 스토리지 4 · 소셜로그인 설정 4번 · Vercel 3 + 로컬 1**이 필요하다.

> 🐰 **"로컬과 프로덕션을 공유하여 시작하고, 규모가 커지면 그때 분리해도 늦지 않아요!"**
> **완벽한 4단계를 만들려다 시작을 못 하는 것보다, 2단계로 빠르게 띄우고 필요할 때 쪼개는 게 낫다.**

**배포 3마디와 함정**

```
[기능 추가] ──"빌드 해줘" → "커밋 해줘" → "푸쉬 해줘"──▶ [Github] ──자동──▶ [Vercel]
                                                  └─ 연결 설정 ─┘  + 환경변수 등록
```

- ⚠️ **`.env`는 Github에 올리지 않으므로 Vercel에는 값이 없다** → **Vercel 대시보드에 직접 입력**한다. 빠뜨리면 배포된 앱이 Supabase에 붙지 못한다.
- ⚠️ **배포하면 로그인이 먼저 깨진다.** 소셜로그인은 **돌아올 주소(Redirect URL)** 를 Supabase가 미리 알아야 한다 → **Site URL**을 배포 주소로 바꾸고, **Redirect URLs에 프로덕션과 로컬을 둘 다** 등록한다(`https://…/**`, `http://localhost:3000/**`).
- 흔한 에러 **`requested path is invalid`** = **`https://` 스킴이나 콜백 경로가 빠진** 형태로 넣었을 때.
- 커스텀 도메인은 **DNS 레코드**로 — **A**(→IP) · **CNAME**(→다른 도메인) · **TXT**(소유권 검증), TTL 지정. 도메인을 바꿨다면 **Site URL·Redirect URL도 다시 갱신**해야 한다.

**모니터링 — 로그와 메트릭은 짝이다**

| | **로그(Log)** | **메트릭(Metric)** |
|---|---|---|
| 무엇 | **API 요청 기록** | **시간에 따라 변하는 수치** |
| 담기는 것 | 요청 목록, 내부 상세 진행 기록 | 요청 **횟수**, 에러 **횟수**, CPU |
| 성격 | 개별 사건 하나하나 | 추세·집계 |

- **메트릭으로 "에러가 늘었다"를 발견하고, 로그로 "그 에러가 정확히 무엇이었나"를 파고든다.**
- 이제는 **Vercel 에이전트**에게 말로 묻는다 — *"이번 달 가장 많이 발생한 에러가 뭐야?"* · *"이번 달 비용이 많이 나가는 프로젝트 분석해줘"*. 에이전트 3종: **Chat · Code Reviews · Investigations**.
- 좋은 질문의 조건은 **"프로젝트 / 기간 / 증상 / 원하는 결과"** 를 함께 주는 것이다.

> **🧩 퀴즈** — API 요청 수·에러 수·CPU처럼 시간이 지남에 따라 변하는 수치 데이터는? → **메트릭**

# 닫는 글

- **제1부** 실무는 **역할 분리형**을 택한다 — 일관성과 유지보수 때문이다. 기획/인터뷰 7단계로 **숨은 진짜 니즈**를 찾아 PRD로 확정하고, 디자인은 **규칙(디자인 시스템)을 먼저** 세운 뒤 화면을 조립한다.
- **제2부** `DESIGN.md`·**메타프롬프트**·`CLAUDE.md`로 디자인을 **확률적에서 결정론적으로** 넘기고, **정규화·PK/FK·중간 테이블**로 DB의 뼈대를 세운다. 사용자 식별자는 **UUID** — 쿠팡 3,370만 건이 그 이유다.
- **제3부** **AI 성능 = 모델 + 도구 제어.** 프롬프트 → 컨텍스트 → 하네스 → 루프로 올라가며, **명세 먼저(SDD)** 가 6,715줄을 399줄로 줄인다. `/clarify`는 2회. 그리고 실무의 API는 **백엔드·JSON**이고, 상태코드는 **400=클라이언트, 500=서버**다.
- **제4부** 로딩은 **스켈레톤**, CORS 차단은 **프록시**(CORS는 브라우저만 검사한다). 인증은 증표 받기·인가는 증표로 증명하기이며, **개인정보=양방향 암호화 / 비밀번호=해시+SALT**다. **JWT는 암호화가 아니라 인코딩** — 안전의 근거는 **서명(무결성)** 이고, 인가는 **토큰을 빼보고** 검증한다.
- **제5부** 사람도 AI도 잊는다 — **PreToolUse(시작 전 차단)와 Stop(종료 전 검사)** 을 짝으로 만들고 `.gitignore`·`permissions.deny`와 **계층 방어**한다. 토큰맥싱은 **굿하트의 법칙**으로 무너졌다. 병렬화는 **독립성 단위의 그룹화 + Git 워크트리 + 5단계**로, 이미지는 **Storage 분리 저장**으로, 배포는 **3마디 + Vercel 환경변수 + Redirect URL 갱신**으로 마무리한다.

> **한 문장 요약** — *기획(PRD)·디자인(디자인 시스템)·설계(명세)로 결정론적 틀을 먼저 세우고,
> 하네스와 훅으로 AI를 통제하며, 워크트리로 기능을 병렬 구현해 Vercel·Supabase 위에 올려라 —
> 모델의 선의가 아니라 구조가 품질과 안전을 만든다.*
