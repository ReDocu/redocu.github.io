## ③ 개념 설명

### 운영 구성 리뷰 기준 — 다섯 축

| 축 | 질문 | 우리 구성의 답 (어디서 왔나) |
|---|---|---|
| **로그** | 전 서비스의 로그를 한 명령으로 모을 수 있나 · 시크릿이 안 찍히나 | compose logs (stdout 표준 — 098·116) · 마스킹 (122) |
| **볼륨** | 상태가 전부 볼륨에 있나 · **백업 절차가 있나** | pgdata (119·121) · 오늘 pg_dump 추가 |
| **재시작** | 상주 서비스 전부에 정책이 있나 · 준비를 판정하나 | unless-stopped + healthcheck (123) |
| **보안** | 노출 포트 최소인가 · 시크릿이 공유물에 없나 | nginx 하나만 (124) · ${} 주입 (122) |
| **재현성** | 빈 환경에서 clone→up이 되나 · 절차가 README에 있나 | 오늘의 리허설 |

### 볼륨은 백업이 아니다

볼륨은 "컨테이너보다 오래 산다"일 뿐, **디스크 고장·볼륨 삭제 사고(down -v!)·호스트 분실**과
운명을 같이합니다. 백업은 **다른 곳에 복사된 시점 사본**이어야 하고, DB의 표준은 파일 복사가
아니라 **덤프**입니다:

```
pg_dump  : 실행 중인 DB에서 일관된 시점의 SQL 사본을 추출 (트랜잭션 고려)
파일 복사 : 쓰기 중인 데이터 파일을 복사하면 반쯤 쓰인 불일치 사본이 될 수 있음
```

## ④ 단계별 실습

### Step 1. 최종 구성 확정 (1~2교시)

이번 주 PR들이 전부 병합된 `compose.yaml` 전문 — 각 줄 옆에 출처의 요일을 주석으로 달아
보세요 (이 주석 달기가 그대로 복습입니다):

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"                                        # 유일한 바깥 문 (124)
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./static:/usr/share/nginx/html:ro
    depends_on:
      api:
        condition: service_healthy                       # 준비 대기 (123)
    restart: unless-stopped

  api:
    build: .
    environment:
      DATABASE_URL: postgresql+psycopg://mp3:${DB_PASSWORD:?required}@db:5432/mp3   # 주입 (122)
      LOG_LEVEL: ${LOG_LEVEL:-INFO}
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request,sys; r=urllib.request.urlopen('http://localhost:8000/health', timeout=2); sys.exit(0 if r.status==200 else 1)"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 30s                                  # 모델 로드 유예 (123)

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: mp3
      POSTGRES_PASSWORD: ${DB_PASSWORD:?required}
      POSTGRES_DB: mp3
    volumes:
      - pgdata:/var/lib/postgresql/data                  # 상태의 거처 (119·121)
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U mp3 -d mp3"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
```

README의 "실행" 섹션도 최종형으로 — 이것이 심사위원(그리고 미래의 팀원)의 첫 5분입니다:

```markdown
## 실행 (Docker)
git clone https://github.com/mlops-student/mlops-mp3.git && cd mlops-mp3
cp .env.example .env    # DB_PASSWORD 값을 채우세요
docker compose up -d    # 첫 실행은 빌드 포함 수 분
# 확인: http://localhost:8080/static/ (데모) · localhost:8080/health
```

### Step 3. 백업과 복원 — 잃어 보고, 되살린다 (5~6교시)

운영 폴더(/opt/mlops-mp3)로 돌아와, 예측 로그가 쌓인 DB를 백업합니다:

```bash
docker compose exec db pg_dump -U mp3 mp3 > backup_$(date +%Y%m%d).sql
wc -l backup_20260821.sql
```

```
$ wc -l backup_20260821.sql
187 backup_20260821.sql
```

이제 최악의 사고를 **일부러** — down -v (⑤에서 경고했던 그 명령):

```bash
docker compose down -v
docker compose up -d --wait
docker compose exec db psql -U mp3 -d mp3 -c "SELECT count(*) FROM prediction_log;"
```

```
 count
-------
     0
(1 row)
```

전멸 — 하지만 오늘은 사본이 있습니다. 복원:

```bash
docker compose exec -T db psql -U mp3 -d mp3 < backup_20260821.sql
docker compose exec db psql -U mp3 -d mp3 -c "SELECT count(*), max(ts) FROM prediction_log;"
```

```
 count |              max
-------+-------------------------------
    14 | 2026-08-21 05:12:44.918273+00
(1 row)
```

14건이 돌아왔습니다. **백업의 완성은 "복원해 봤다"입니다** — 복원 안 해 본 백업은 희망 사항일
뿐. 이 pg_dump 한 줄을 [Day 115](day-115.md)의 cron에 심는 것(매일 새벽, 날짜 파일명)을 과제에
포함합니다.

### Step 4. 교차 리뷰 — 남의 눈으로 채점 (7교시)

짝과 저장소를 바꿔 ③의 리뷰 기준표로 채점합니다 — 축마다 **증거 명령**을 실행해서
(로그: `docker compose logs | grep -i pass` 가 빈 출력인가 / 볼륨: down→up 후 데이터 생존 /
재시작: kill 후 복귀 / 보안: `docker compose ps` 의 노출 포트 · `docker history` / 재현성:
Step 2 리허설). 축당 5점, 총 25점 — 감점마다 이슈로 남기고, 서로의 이슈를 다음 PR로 처리합니다.

### 오늘 새로 나오는 실수

### 리허설을 자기 PC에서만

**증상** — "제 데선 5분 컷인데요" — 심사위원 노트북에선 15분 + 에러.
**원인** — 내 PC엔 이미지 캐시·이미 받은 베이스·채워진 .env가 있습니다 — 빈 환경이 아닙니다.
**해결** — 리허설의 표준 조건: 새 폴더(clone) + `docker builder prune` 까지는 안 가더라도
최소한 프로젝트 이미지 삭제 + .env 백지에서. 짝의 PC(Step 4)가 가장 정직한 시험장입니다.

### 볼륨 폴더를 tar로 뜨는 "백업"

**증상** — 실행 중인 DB의 볼륨을 통째로 복사 — 복원해 보니 인덱스 손상·기동 실패.
**원인** — 쓰기 진행 중인 데이터 파일의 복사본은 **시점 일관성**이 없습니다.
**해결** — DB는 덤프(pg_dump)가 표준입니다 — DB가 스스로 일관된 시점의 사본을 만들어 줍니다.
(파일 백업을 꼭 해야 하면 컨테이너 정지 후 — 그러나 그건 다운타임과의 거래입니다.)

### 백업 파일을 같은 서버에만 보관

**증상** — 백업은 매일 돌았는데, 서버(WSL·디스크)가 통째로 죽자 백업도 함께 사망.
**원인** — 백업의 정의(다른 곳의 사본) 위반 — 같은 디스크는 "다른 곳"이 아닙니다.
**해결** — 최소한 다른 매체로 복사(scp로 다른 기계, 클라우드 스토리지). 과제의 cron 백업에
"밖으로 나가는 단계"까지 포함해야 완성입니다.

### 리뷰 기준을 "완성 후 한 번"만 적용

**증상** — MP4 마감 전날 리뷰표를 처음 들이댐 — 감점 항목 수리에 밤샘.
**원인** — 리뷰 기준을 심사 도구로만 취급 — 사실은 **설계 도구**입니다.
**해결** — 새 서비스를 구성에 추가할 때마다 다섯 축을 지나가는 습관 (다음 주 CI에 이 중
일부 — 시크릿 grep·기동 테스트 — 를 자동 검사로 넣으면 습관이 시스템이 됩니다).

## ⑥ 확인 문제

**Q1.** Step 2 리허설에서 "사람의 판단이 필요한 지점"을 1개(.env)까지 줄였습니다. 이 1개마저
없앨 수 있을까요? 없앤다면 무엇을 잃는지와 함께 논하세요.

<details>
<summary>답 보기</summary>

기술적으로는 가능합니다 — 기본 비밀번호를 .env.example에 넣거나 compose에 기본값(`:-devpass`)을
주면 복사조차 필요 없어집니다. 그러나 그 순간 "시크릿이 저장소에 없다"(122)가 깨지고, 그
기본값으로 운영에 올라가는 사고(가장 흔한 실제 유출 유형)의 문이 열립니다. 남긴 1개는 게으름이
아니라 **의도된 마찰**입니다 — 자동화의 목표는 판단 0개가 아니라 "안전과 무관한 판단만 제거"
이고, 시크릿 주입은 안전 그 자체라 남습니다 (CI에서는 이 역할을 Actions secrets가 맡습니다 —
Day 128).

</details>

**Q2.** down -v가 Step 2(리허설 정리)에서는 옳고 Step 3(운영 재현)에서는 사고인 이유를,
"상태의 주인" 관점에서 한 단락으로 쓰세요.

<details>
<summary>답 보기</summary>

같은 명령의 옳고 그름은 그 볼륨에 든 상태가 **버려도 되는 것인가**로 갈립니다. 리허설 볼륨의
상태는 실험 부산물 — 주인이 없고, 남기면 오히려 다음 리허설의 "빈 환경" 조건을 오염시킵니다.
운영 볼륨의 상태는 서비스의 기억(예측 로그·데이터) — 주인은 서비스와 그 사용자들이며, 삭제는
복구 불능 손실입니다. 그래서 규율은 명령 금지가 아니라 "**-v를 치기 전에 '이 상태의 주인이
누구인가'를 묻는다**"입니다 — Step 3에서는 백업이 있었기에 그 질문에 답이 있었습니다.

</details>

**Q3.** 리뷰 다섯 축 중 "로그" 축의 검사(`docker compose logs | grep -i pass` 빈 출력)가
불충분한 이유를 찾고, 더 나은 검사를 설계해 보세요.

<details>
<summary>답 보기</summary>

grep -i pass는 ① 지금까지 찍힌 로그만 봅니다 — 아직 안 지나간 코드 경로(에러 핸들러의 URL
출력 등)는 잡지 못하고, ② "pass"라는 문자열만 봅니다 — 토큰(ghp_...)·키·다른 이름의 시크릿을
놓칩니다. 개선: 검사 대상을 넓히고(알려진 시크릿 **값 자체**를 .env에서 읽어 로그·이미지·
저장소에서 검색), 시점을 앞당깁니다(코드 리뷰 체크리스트 + 에러 경로를 일부러 밟는 테스트 후
로그 검사). 완전 자동화는 어렵지만 "값 기반 검색 + 경로 커버리지"만으로도 이름 기반 grep보다
훨씬 촘촘해집니다.

</details>

## 주간 퀴즈 22 — W25 (Docker Compose와 서비스 구성)

<details>
<summary>1. 선언형 도구의 멱등성이란? up을 두 번 실행하면?</summary>

원하는 상태를 선언하면 도구가 현실과의 차이만 조정 — 이미 일치하면 아무것도 안 함. 몇 번 실행해도 같은 최종 상태.

</details>

<details>
<summary>2. Compose에서 API가 DB를 부르는 주소는? 그 이름은 어디서 오나?</summary>

db:5432 — 서비스 이름이 프로젝트 전용 네트워크의 호스트명(DNS)이 됨. network create를 Compose가 대신해 주는 것.

</details>

<details>
<summary>3. 값의 세 등급과 각각의 자리는?</summary>

상수(코드/이미지) · 설정(compose environment — 리뷰 가능) · 시크릿(.env → ${} 주입, 커밋 금지). 판별 질문: "공개 저장소에 올라가면 사고인가".

</details>

<details>
<summary>4. 시크릿의 4대 금지처는?</summary>

코드 · 저장소 · 이미지(history/inspect로 노출!) · 로그. 공통 원리: 놓는 순간 그 매체의 독자 전원에게 공개.

</details>

<details>
<summary>5. ${VAR:?required}와 ${VAR:-기본값}의 사용 기준은?</summary>

없으면 사고인 값(시크릿)은 :?로 시끄럽게 실패, 합리적 기본이 있는 설정은 :-. 시크릿에 기본값은 항상 오답.

</details>

<details>
<summary>6. depends_on의 기본 보장과 완전한 형태는?</summary>

기본은 시작 순서뿐 — 준비(ready)는 안 기다림. condition: service_healthy + 상대의 healthcheck가 완전체.

</details>

<details>
<summary>7. start_period가 MP3에 특히 중요한 이유는?</summary>

모델 로드(수 초~수십 초) 동안의 헬스체크 실패에 벌점을 주지 않는 유예 — 없으면 정상 앱이 로드가 길다는 이유로 unhealthy 판정.

</details>

<details>
<summary>8. 상주 서비스의 표준 재시작 정책과 그 이유는?</summary>

unless-stopped — 죽으면 재시작 + 재부팅에도 부활하되, 운영자가 의도적으로 stop한 것은 존중. always는 정상 종료까지 되살려 크래시 루프를 가릴 수 있음.

</details>

<details>
<summary>9. 리버스 프록시의 네 가지 일은?</summary>

단일 진입점(포트 정리) · 문 앞 차단(크기 제한 등) · 정적 파일 서빙 · TLS 종료(HTTPS). 뒤의 일꾼 구성을 손님이 모르게 하는 것이 무중단 배포의 공간.

</details>

<details>
<summary>10. "볼륨이 있으니 백업은 필요 없다"가 틀린 이유와 DB 백업의 표준은?</summary>

볼륨은 컨테이너보다 오래 살 뿐, 디스크 고장·down -v·호스트 분실과 운명을 같이함. 표준은 pg_dump(일관된 시점 사본) + 다른 매체로 복사, 그리고 복원 리허설까지.

</details>
