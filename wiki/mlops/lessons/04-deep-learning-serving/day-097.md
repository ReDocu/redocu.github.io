## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **학습 전처리 = 서빙 전처리** 원칙이 깨질 때의 사고를 세 데이터 유형에서 재현할 수 있다.
- 전처리 불일치가 왜 **에러 없이**(조용히) 성능만 무너뜨리는지 설명할 수 있다.
- 유형별 **구조적 보장 장치**(파이프라인 봉인 · 공유 모듈 · 토크나이저 동봉)를 적용할 수 있다.
- 입력 검증(범위 체크)의 한계 — "검증은 필요조건, 일치는 구조로" — 를 안다.

---

## ② 왜 필요한가

커리큘럼 FAQ의 단골 질문에서 시작합니다:

> "서빙 정확도가 학습 때보다 낮아요."

원인의 대부분은 모델이 아니라 **전처리 불일치**입니다. 학습 때는 표준화·정규화·토큰화를
거친 데이터를 먹였는데, 서빙에서 조금이라도 다른 자(尺)로 잰 입력이 들어오면 —
모델 입장에서는 **다른 세계의 숫자**입니다. 그런데 이 사고의 악질적인 점은:

```
shape는 맞다 → 에러 없음
값도 그럴듯하다 → 범위 검증 통과
응답도 나온다 → 아무도 모름
정확도만 떨어져 있다 → 몇 주 뒤 "모델이 이상하다"는 민원으로 발견
```

오늘은 이 사고를 이미지·텍스트·테이블 세 유형에서 **일부러 내고 피해를 실측**합니다.
그리고 각 유형의 구조적 예방책을 확정합니다 — 어제 서버가 전처리 코드 없이도 정확했던
이유(파이프라인 봉인)가 세 예방책 중 하나였음을 확인하게 됩니다. MP3 평가 기준
"서빙 정확성(전처리 일치) 25점"의 실체가 오늘입니다.

## ③ 개념 설명

### 왜 "조용히" 무너지는가

모델은 숫자의 **의미**를 모릅니다. 학습 중 "정규화된 픽셀 -1.2~+1.8" 세계에서 경계를
그었는데 서빙에서 "0~1 픽셀"이 오면, 모델은 항의하지 않고 **그 경계를 그대로 적용**합니다 —
틀린 자리에서. 입력이 유효한 텐서인 한 forward는 성공하므로, 실패는 통계(정확도)에만
나타납니다. [Day 088](day-088.md)의 "학습 범위 밖 입력"과 같은 병의 다른 감염 경로입니다.

### 유형별 전처리와 구조적 보장

| 데이터 | 전처리의 정체 | 불일치 사고 예 | 구조적 보장 |
|---|---|---|---|
| 테이블 | 대치·스케일·인코딩 | 단위 다름, 컬럼 순서 | **파이프라인째 직렬화** ([Day 063](../03-machine-learning/day-063.md)·[068](../03-machine-learning/day-068.md)) |
| 이미지 | Resize·ToTensor·**Normalize** | Normalize 누락, 다른 통계 | 전처리 정의를 **한 모듈**에 — 학습·서빙이 같은 것을 import ([Day 085](day-085.md)) |
| 텍스트 | **토크나이저** | 다른 어휘집, 다른 max_length | 모델과 토크나이저 **동봉 배포** ([Day 087](day-087.md)·[089](day-089.md)) |

공통 원리는 하나입니다 — **전처리를 사람이 두 번 구현하지 않게 한다.** 두 벌이 존재하는
순간 언젠가 한쪽만 바뀝니다 ([Day 085](day-085.md) ⑤에서 예고).

### 검증의 자리와 한계

그럼 [Day 092](day-092.md)의 입력 검증은 무용한가? 아닙니다 — 역할이 다릅니다.

```
검증(Field ge/le, 타입): 명백히 불가능한 값을 입구에서 거절     → 필요조건
일치(구조적 보장):       유효해 보이는 값이 같은 자로 측정됨을 보장 → 충분조건
```

오늘 사고 3에서 봅니다 — 화씨로 보낸 겨울 기온(38°F)은 섭씨 범위 검증(-30~45)을
**통과**합니다. 범위 검증은 여름 화씨(80°F)는 잡아도 겨울은 못 잡습니다. 검증만 믿으면
계절 따라 새는 사고가 됩니다.

## ④ 단계별 실습

`day097_mismatch.py` — 세 사고를 재현합니다. (모델 로드 부분은 저장소 스크립트 참고)

### Step 1. 사고 1 — 이미지: Normalize를 깜빡 (1~2교시)

서빙 개발자가 transform을 다시 쓰다 Normalize 한 줄을 빠뜨렸다고 합시다.

```python
tf_ok = transforms.Compose([
    transforms.Resize(256), transforms.CenterCrop(224), transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225]),
])
tf_bad = transforms.Compose([
    transforms.Resize(256), transforms.CenterCrop(224), transforms.ToTensor(),
    # Normalize를 "깜빡"
])
```

같은 모델([Day 083](day-083.md)의 0.954짜리)로 val 153장을 두 전처리로 평가:

```
== 사고 1 (이미지): 서빙에서 Normalize를 빼먹음 ==
  학습과 같은 전처리:   valid acc 0.954
  Normalize 빠뜨림:    valid acc 0.784   ← 에러는 없다!
```

한 줄 누락에 **-17%p.** shape도 (3,224,224)로 같고 값도 0~1의 "멀쩡한" 텐서라 어떤 예외도
없습니다. 0.784라는 성적이 미묘하게 나쁜 점도 악질입니다 — 완전히 망가졌다면(0.5) 금방
들켰을 텐데, "쓸 만해 보여서" 배포될 수 있는 수준입니다.

### Step 2. 사고 2 — 텍스트: 토크나이저가 다름 (3교시)

[Day 087](day-087.md)에서 예고한 사고를 성능으로 확인합니다. NSMC 분류기([Day 089](day-089.md))에
klue 대신 영어 토크나이저의 ID를 넣으면:

```
== 사고 2 (텍스트): 다른 토크나이저를 씀 ==
  학습과 같은 토크나이저(klue):      acc 0.765
  영어 토크나이저(bert-base-uncased): acc 0.490   ← 역시 에러는 없다!
```

**0.490 — 동전 던지기.** ID는 어휘집에 종속이라, 다른 토크나이저의 ID는 이 모델에게
무작위 잡음입니다. 그런데도 forward는 성공하고 확신도까지 붙은 응답이 나갑니다.
(200건 표본 평가라 0.815가 아닌 0.765가 기준인 것도 확인 — 표본이 작으면 기준선부터 흔들립니다.)

### Step 3. 사고 3 — 테이블: 단위가 다름 (4교시)

클라이언트 앱이 기온을 화씨로 보내기 시작했다고 합시다 (미국 API에서 값을 받아 그대로 전달).

```
== 사고 3 (테이블): 클라이언트가 기온을 화씨(°F)로 보냄 ==
  올바른 단위(°C): R² 0.519 · MAE 4.26 · 예측 평균 28.3
  화씨(°F)로 보냄: R² 0.195 · MAE 5.73 · 예측 평균 23.7
  ← 겨울의 화씨 값(38°F 등)은 섭씨 범위 검증(-30~45)도 통과한다!
```

R² 0.519 → **0.195** (베이스라인 수준으로 추락), 예측이 전반적으로 -4.6 치우칩니다.
주목 — 이 사고는 **파이프라인 봉인으로도 못 막습니다.** 파이프라인은 "받은 숫자"를 학습 때의
자로 재 줄 뿐, 그 숫자의 단위가 뭔지는 모릅니다. 그리고 겨울 화씨(32~50°F)는 섭씨 범위
검증도 통과합니다 — **계절 따라 잡혔다 안 잡혔다 하는 최악의 유형**입니다. 방어선은
계약 문서(단위를 스키마·API 문서에 명시 — [Day 092](day-092.md)의 `description="㎍/㎥"` 가
그 자리)와 운영 감시(입력 분포 모니터링 — [Day 098](day-098.md)·W27)입니다.

### Step 4. 구조적 보장 3종 확정 (5~6교시)

사고를 봤으니 예방을 구조로 만듭니다. MP3 저장소에 그대로 적용할 규약입니다:

**테이블** — 이미 되어 있습니다. [Day 063](../03-machine-learning/day-063.md)의 파이프라인 봉인
덕에 어제 서버는 전처리 코드 0줄로 정확했습니다.

**이미지** — 전처리 정의를 한 모듈로 (두 벌 금지):

```python
# src/preprocess.py — 유일한 전처리 정의
IMAGE_PREPROCESS = transforms.Compose([...])

# train.py 도, serve.py 도:
from src.preprocess import IMAGE_PREPROCESS      # 같은 것을 import — 어긋날 방법이 없다
```

**텍스트** — 토크나이저를 모델과 동봉:

```python
model.save_pretrained("models/nsmc/")            # 가중치 + 설정
tok.save_pretrained("models/nsmc/")              # 토크나이저 + 어휘집 — 같은 폴더에!
# 서빙: 같은 폴더에서 쌍으로 로드 → 짝이 어긋날 방법이 없다
```

그리고 세 유형 공통으로 — **일치 스모크 테스트**: 학습 마지막에 검증 표본 몇 건의 예측값을
파일로 저장하고, 서빙 쪽 테스트가 같은 입력으로 같은 값이 나오는지 확인합니다
([Day 074](../03-machine-learning/day-074.md)의 "재로드 동일 예측"의 확장판 — 과제 ②).

### Step 5. 커밋과 과제 (7~8교시)

```powershell
git add day097_mismatch.py src/preprocess.py
git commit -m "Day 097: 전처리 불일치 3종 실측 (-17%p / 동전 / R² 0.195) + 구조적 보장"
```

**과제 — 불일치 사고 재현·수정.** ① 이미지에서 Normalize 통계를 CIFAR 값(0.49…)으로
잘못 쓴 경우의 acc를 재서 오늘 표에 한 행 추가 (통계가 "있지만 다른" 경우 — 누락보다 흔한 사고).
② "일치 스모크 테스트"를 구현: [Day 089](day-089.md) 학습 직후 검증 5문장의 확률을
`models/nsmc_expected.json` 으로 저장하고, 서빙 로드 후 같은 문장에서 오차 1e-4 이내인지
확인하는 pytest를 작성. ③ 사고 3의 방어로 PredictIn의 각 필드에 `description` (단위 포함)을
달고 /docs에서 확인 — 문서도 방어선입니다.

## ⑤ 자주 하는 실수

### 전처리를 서빙 쪽에서 "기억으로" 재구현

**증상** — 오늘의 사고 1 (-17%p). 코드 리뷰로도 잡기 어렵습니다 — 그럴듯해 보이니까.
**원인** — 학습 코드의 transform을 보고 옮겨 적는 과정에서 한 줄·한 값이 어긋남.
**해결** — 옮겨 적지 말고 **같은 것을 import** (Step 4). 재구현이 불가피한 언어 경계(파이썬→모바일)에서는 일치 스모크 테스트가 유일한 안전망입니다.

### 다운로드 편의로 다른 토크나이저를 씀

**증상** — "같은 BERT 계열이니 되겠지" — 오늘의 사고 2 (동전).
**원인** — 토크나이저를 교체 가능한 부품으로 오해.
**해결** — 어휘집이 다르면 다른 세계입니다. save_pretrained로 동봉하고, 서빙 코드에 모델 이름을 두 번 쓰지 마세요 (상수 하나로 — [Day 090](day-090.md)의 BASE).

### 범위 검증을 통과하면 안전하다고 믿음

**증상** — 사고 3 — 겨울 화씨가 섭씨 검증을 통과하며 계절성 있는 성능 저하.
**원인** — 검증(필요조건)과 일치(충분조건)의 혼동.
**해결** — 단위·좌표계·시간대 같은 **의미 수준의 계약**은 문서(description)와 클라이언트 합의로, 위반 탐지는 입력 분포 모니터링으로 ([Day 098](day-098.md)의 로그가 그 재료).

### 성능 저하를 보고 모델부터 재학습

**증상** — "서빙 정확도가 낮으니 데이터 더 모아 재학습하자" — 몇 주 뒤에도 그대로.
**원인** — 원인 진단 없이 가장 비싼 처방부터. 불일치는 재학습으로 안 고쳐집니다 (새 모델도 같은 자 어긋남을 겪음).
**해결** — 순서: ① 같은 입력을 학습 환경과 서빙 환경에 넣어 예측 비교 (다르면 불일치!) → ② 전처리 단계별 중간값 대조 → ③ 그래도 같으면 그때 데이터·모델을 의심.

### 스모크 테스트 없이 모델 교체 배포

**증상** — 새 모델 배포 직후 정확도 급락 — 새 모델은 전처리 통계가 다른데 서빙 전처리는 옛것.
**원인** — 모델 파일만 갈아 끼우고 전처리 계약은 확인 안 함.
**해결** — 모델과 전처리(파이프라인·transform·토크나이저)는 **한 세트로 버전 관리**하고, 배포 절차에 일치 스모크 테스트를 포함합니다 (W26 CI/CD에서 자동화).

"모델은 숫자의 의미를 모른다"로 설명하세요.

런타임 예외가 아니라 **구조(같은 코드)와 절차(스모크 테스트)** 여야 합니다.

<details>
<summary>답 보기</summary>

같은 점: "같은 입력 → 같은 출력"이라는 계약을 자동 검증한다는 발상. 확장: 재로드 테스트는 같은
프로세스에서 파일 왕복만 검증하지만, 스모크 테스트는 **다른 환경**(서빙 서버, 다른 머신, 컨테이너)에서
전처리를 포함한 전체 경로가 학습과 일치하는지를 검증합니다 — 즉 검증 대상이 직렬화에서
"전처리+모델+환경"의 합으로 넓어진 것입니다.

</details>
