## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 개인 저장소 5종을 감사하고 **통일된 README 템플릿**으로 정리할 수 있다.
- 이력서의 프로젝트 항목을 **문제·행동·수치 결과**의 3줄 공식으로 쓸 수 있다.
- 팀 프로젝트에서 **개인 기여를 링크로 증명**할 수 있다.
- 채용 담당자의 15분 동선(이력서 → 프로필 → 저장소)을 설계할 수 있다.

## ② 왜 필요한가

어제까지는 심사를 위한 전달이었다면, 오늘은 **취업을 위한 전달**입니다. 서류 심사의
현실을 그대로 봅시다: 담당자는 이력서에서 프로젝트 3줄을 읽고, 흥미가 생기면 GitHub
링크를 누르고, 15분 안에 "면접에서 물어볼 것이 있는 사람인가"를 정합니다. 여러분에게
그 15분을 위한 자산이 이미 5개 있습니다 — [Day 030](../01-python-data/day-030.md)의
수집 패키지부터 어제 완성한 팀 프로젝트까지, 과정 설계가 처음부터 "수료 시점 공개
저장소 5개"를 향해 있었습니다.

문제는 그 5개가 지금 **만들어진 시점의 수준**으로 남아 있다는 것입니다. MP1의 README는
W10의 여러분이 쓴 것이고, 그 시절엔 Docker도 CI도 몰랐습니다. 담당자는 5개를 시간순으로
읽지 않습니다 — 아무거나 누른 하나가 첫인상입니다. 오늘의 작업은 리팩터링이 아니라
(코드는 그 시절의 정직한 기록으로 두는 것이 낫습니다) **표지의 통일**입니다: 어느
저장소를 열어도 같은 구조의 README가 문제·역할·결과를 말하게 하는 것.

그리고 팀 프로젝트에는 개인 자격의 숙제가 하나 더 있습니다 — "팀이 한 것"과 "내가 한
것"의 구분. "저희 팀이 만들었습니다"만 말할 수 있는 지원자는 면접에서 무너집니다.
다행히 여러분에겐 4주치 커밋·PR·리뷰 이력이 있습니다 — 그것을 **링크로 인용 가능한
증거**로 정리하는 것이 오늘의 두 번째 작업입니다.

## ③ 개념 설명

### 5종 저장소 — 각각이 증명하는 것

| # | 저장소 | 증명하는 역량 | 완성 시점 |
|---|---|---|---|
| 1 | 수집·전처리 패키지 | 파이썬 기본기 · 패키지 구조 · 테스트 | [Day 030](../01-python-data/day-030.md) |
| 2 | MP1 — 데이터 분석 (SQL) | DB 설계 · ETL · 분석적 사고 | [Day 050](../02-sql-pipeline/day-050.md) |
| 3 | MP2 — ML 실험 | 평가 설계 · 실험 규율 (MLflow) | [Day 075](../03-machine-learning/day-075.md) |
| 4 | MP3+MP4 — 서빙·운영 | API · Docker · CI/CD · 모니터링 | [Day 140](../05-infra-mlops/day-140.md) |
| 5 | **최종 팀 프로젝트** | 전 스택 통합 + **팀 협업** | 이번 주 |

같은 템플릿, 다른 강조 — 각 README의 "결과" 절이 그 저장소 고유의 숫자를 말해야
5개가 서로를 반복하지 않습니다.

### README 통일 템플릿 — 상단 여섯 줄

```
# <프로젝트명> — <문제 한 문장>
무엇: <누가 어떤 문제를 겪고, 이것이 무엇을 해 주는가>
역할: <개인: "단독" / 팀: 담당 파트 + 기여 링크>
기술: <핵심만 — 나열이 아니라 선택 이유 한 줄과 함께>
결과: <숫자 2~3개 — 성능·규모·운영 실측>
더 보기: [아키텍처] [보고서] [실행 방법]
```

### 이력서 3줄 공식 — 문제 · 행동 · 수치

```
[문제]  왜 하는 일이었는지 한 줄 (규모·제약 포함)
[행동]  내가 무엇을 했는지 — 기술은 행동의 부사구로
[결과]  숫자로 끝나는 한 줄 — 성능·시간·규모
```

나쁜 예: "FastAPI, Docker, Airflow를 활용한 지하철 혼잡 예측 서비스 개발" (기술 나열,
행동·결과 없음). 좋은 예는 Step 3에서.

### 개인 기여의 증거 — 주장에서 링크로

팀 저장소의 기여는 세 종류 링크로 증명됩니다: **대표 PR 3~5개**(설계 판단이 보이는 것),
**리뷰 코멘트**(교차 리뷰 덕에 자기 영역 밖 리뷰가 남아 있습니다 — 협업의 증거),
**이슈·문서**(사고 조사, 설계 문서). 커밋 수 자랑이 아니라 판단의 표본을 고르는 것입니다.

## ④ 단계별 실습

### Step 1. 5종 감사 (1~2교시)

각자 자기 5종을 표로 감사합니다 — 서연의 감사 결과 (예시):

| 저장소 | README | 실행 재현 | 결과 숫자 | 오늘 할 일 |
|---|---|---|---|---|
| 수집 패키지 | 🔶 설치법뿐 | ✅ | ❌ 없음 | 템플릿 적용 + 테스트 수 명시 |
| MP1 | 🔶 과제 안내문 톤 | ✅ | 🔶 그래프만 | 핵심 발견 3개를 숫자로 |
| MP2 | ✅ (W15에 정리) | ✅ | ✅ | 템플릿 상단만 통일 |
| MP3+4 | ✅ (140에 완성) | ✅ | ✅ | 링크 확인만 |
| hansan | ✅ (어제 완성) | ✅ 2m18s | ✅ | 역할 절에 기여 링크 |

**코드 수정은 없습니다** — 표지(README)와 링크만. 코드까지 손대면 오늘 안에 못 끝나고,
그 시절 코드는 성장의 증거로 두는 편이 이야기가 됩니다.

### Step 2. 템플릿 적용 (3~5교시)

서연의 hansan README "역할" 절 (팀 저장소용):

```
역할: 데이터·파이프라인 담당 (4인 팀)
  - 수집·백필·검증 4층 설계 — PR #6 #7 #21 (결측 사건 조사: 이슈 #21)
  - 재학습 DAG 게이트 공동 구현 — PR #26
  - 서빙 영역 교차 리뷰 12건 — 예: 실패 유형 분리 제안 (#6 리뷰 스레드)
```

전부 클릭 가능한 링크입니다 — "데이터 담당이었습니다"라는 주장과, 열어 보면 판단
과정이 보이는 링크의 차이가 면접 통과율의 차이입니다.

### Step 3. 이력서 3줄 (6교시)

서연의 최종 프로젝트 항목:

```
[문제]  지하철 이용자가 내일의 역·시간대별 혼잡을 미리 알 수 없는 문제 — 공공 데이터
        (일 5만 행 규모, 4일 게시 지연)로 4인 팀 4주 개발
[행동]  수집~적재 파이프라인(멱등 upsert·검증 4층)과 주간 재학습 게이트를 설계·구현하고,
        학습-서빙 시점 불일치 사고의 조사·재발 방지를 주도
[결과]  베이스라인 대비 MAE 38% 개선(등급 정확도 0.85), 커밋→배포 2분 40초 자동화,
        신규 환경 기동 2분 18초 재현
```

같은 프로젝트라도 민준의 3줄은 모델·실험이, 하람의 3줄은 CI/CD·인프라가 [행동]에
옵니다 — 팀원끼리 3줄이 같다면 그것이 바로 기여 구분 실패의 신호입니다.

### Step 4. 상호 리뷰 — 담당자 역할극 (7~8교시)

짝에게 이력서 3줄과 프로필 링크만 주고 15분을 줍니다. 짝은 채용 담당자로서 세 질문에
답합니다: ① 3줄에서 무엇이 궁금해졌나 ② 저장소에서 그 답을 찾았나 ③ 면접에서 뭘
물어보고 싶나. — ②가 "못 찾았다"면 동선(링크)의 버그입니다. 마지막으로 GitHub 프로필
(고정 저장소 5종 순서 · 프로필 README 한 단락)을 정리합니다.

**오늘 퇴근 체크** — □ 5종 감사표 □ 전 저장소 README 템플릿 통일 □ 기여 링크
(PR·리뷰) 정리 □ 이력서 3줄(짝 검증) □ 프로필 고정 5종 · 전부 공개 상태

## ⑤ 자주 하는 실수

### 기술 나열형 이력서

**증상** — "Python, SQL, FastAPI, Docker, Airflow, MLflow 활용 프로젝트 다수" — 담당자
기억에 남는 것 0.
**원인** — 키워드 검색 대비라는 미신 — 키워드는 프로젝트 서술 안에 자연히 들어갑니다.
**해결** — 3줄 공식으로 프로젝트당 한 덩어리. 기술명은 [행동]의 부사구로만 ("멱등
upsert로", "Actions 게이트로") — 기술이 아니라 기술로 **한 일**이 기억에 남습니다.

### 팀 성과와 개인 기여의 경계 실종

**증상** — 면접: "게이트 로직 직접 짜셨어요?" — "아 그건 팀원이…" 가 세 번 반복되면
그 면접은 끝났습니다.
**원인** — README·이력서가 팀 성과를 1인칭으로 서술.
**해결** — 팀 산출물은 "팀이", 내 기여는 "내가"로 문법부터 분리하고, 내 것에만 링크를
겁니다. 겸손의 문제가 아니라 정확성의 문제이고, 정확한 사람이 신뢰를 삽니다 — 그리고
교차 리뷰 이력 덕분에 "내 담당 밖도 설명 가능"이 여러분의 추가 무기입니다.

### 다섯 저장소가 같은 문장

**증상** — 템플릿을 문자 그대로 복붙 — "본 프로젝트는 데이터 수집부터 서빙까지…"가
5개 저장소에 동일하게 등장, 담당자는 두 번째부터 안 읽음.
**원인** — 템플릿의 구조와 내용을 혼동.
**해결** — 구조(여섯 줄)는 같게, 내용은 그 저장소 고유의 문제·숫자로. ③의 표("각각이
증명하는 것")가 차별화의 지도입니다 — 5개가 하나의 성장 서사(패키지→분석→실험→운영→
팀)로 읽히는 것이 목표입니다.

### 사고 이야기를 이력서에서 검열

**증상** — "실수한 걸 왜 써요" — 학습-서빙 사고를 행동 절에서 뺌 — 가장 강한 면접
카드를 스스로 버림.
**원인** — 이력서 = 자랑 목록이라는 오해.
**해결** — "사고의 조사·재발 방지를 주도"는 실수의 고백이 아니라 **문제 해결 역량의
주장**입니다. 면접관의 단골 질문("실패 경험 말해 보세요")에 링크 달린 답을 미리 준비해
둔 셈이고, 155~156에서 다듬은 그 서사가 여기서 세 번째로 일합니다.

채용 담당자가 실제로 평가하려는 것과 연결해 설명하세요.

<details>
<summary>답 보기</summary>

담당자가 알고 싶은 것은 노동량이 아니라 **판단의 품질**입니다 — 이 사람이 우리 팀에서
설계 결정을 하고 리뷰를 하게 될 때의 모습. 커밋 수는 노동량의 대리 지표조차 못 됩니다
(쪼개기·스타일 수정으로 부풀 수 있음). 반면 대표 PR에는 문제 정의→접근→검증(동작 확인
로그)의 사고 과정이, 리뷰 코멘트에는 남의 코드에서 위험을 보는 눈(예: 서연의 실패 유형
분리 제안)이 그대로 남아 있습니다 — 면접 전에 이미 "일하는 모습의 표본"을 제출하는
셈입니다. 그래서 잘 고른 3~5개가 300커밋보다 강하고, 고르는 행위 자체(무엇이 대표작
인지 아는 것)도 평가 대상입니다.

안 되는 이유를 설명하고, 만약 [행동]까지 자연스럽게 겹친다면 그것이 팀 운영의 어떤
문제를 소급 진단하는 것인지 답하세요.

<details>
<summary>답 보기</summary>

[문제]는 팀이 공유한 과제, [결과]는 팀이 공동 달성한 수치라 겹침이 자연스럽습니다 —

분담 원칙("주 담당 + 전원 코드 + 교차 리뷰")이 운영되지 않았다는 뜻이고, 개인 기여도
평가(팀 점수의 30%)와 면접 양쪽에서 전원이 약해집니다. 역설적으로, 좋은 팀 운영의
증거는 "우리는 하나였다"가 아니라 "각자의 문장이 있고 서로의 문장을 설명할 수 있다"
입니다.

</details>
