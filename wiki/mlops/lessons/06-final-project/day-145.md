## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 타 팀의 설계를 **실패 시나리오 질문**으로 리뷰할 수 있다.
- 받은 리뷰를 **수용/보류/기각으로 분류하고 이유를 기록**할 수 있다.
- 위험 등록부(확률 · 피해 · 조기 신호 · 대응)를 만들 수 있다.
- 설계를 확정(`design-v1` 태그)하고 스프린트에 들어갈 준비를 마칠 수 있다.

---

## ② 왜 필요한가

나흘간 설계에 몰입한 팀은 자기 설계의 가정을 더 이상 가정으로 **보지 못합니다** — 매일
봐 온 문장은 검증된 사실처럼 읽히기 때문입니다. "D-4 지연은 예보 프레임으로 흡수했다"고
쓴 팀은 "그럼 연휴 직후엔 D-6이 되는데요?"라는 질문을 스스로 던지기 어렵습니다. 그
질문은 그 문서를 오늘 처음 읽는 사람에게서 옵니다.

설계 리뷰는 그래서 심사도, 품평회도 아닙니다 — **위험의 무료 채굴**입니다. 오늘 타 팀이
찾아 주는 구멍 하나는 W31에 스스로 발견할 구멍보다 열 배 쌉니다. 반대 방향도 같습니다:
남의 설계를 리뷰하는 것은 자기 설계를 다시 보는 가장 좋은 훈련입니다 ("저 팀도 갱신
주기를 안 정했네 — 어, 우리도?").

그리고 오늘이 설계의 **동결 시점**입니다. 내일부터 2주는 구현입니다 — 설계가 계속
움직이면 스프린트는 움직이는 과녁에 활을 쏘는 일이 됩니다. 오늘의 태그(`design-v1`)
이후 설계 변경은 "긴급 수리"가 아니라 PR과 팀 합의를 거치는 공식 절차가 됩니다.

## ③ 개념 설명

### 리뷰어의 기술 — 실패 시나리오 질문

좋은 설계 리뷰 질문은 취향("저라면 이렇게…")이 아니라 **실패 시나리오**("~이면 어떻게
되나요")입니다. 유형별 질문 목록:

| 유형 | 질문 틀 | 예 |
|---|---|---|
| 데이터의 배신 | 입력이 약속을 어기면? | "데이터가 하루 안 오면? 이틀 연속이면?" |
| 규모·한도 | 한도에 닿으면? | "API 일 1,000회 제한, 백필에 며칠 걸리죠?" |
| 시간의 문제 | 시점이 어긋나면? | "재학습 중 예측 요청이 오면 어느 모델이 답하죠?" |
| 사람의 문제 | 담당자가 없으면? | "이 DAG 죽으면 누가 어떻게 아나요?" |
| 정의의 구멍 | 기준의 근거는? | "혼잡 등급 경계 0.5/0.8의 근거는 뭔가요?" |

리뷰이가 즉답하지 못하는 질문이 **좋은 질문**입니다 — 그것이 채굴된 위험입니다.

### 리뷰이의 기술 — 방어하지 않고 기록한다

받은 질문에 그 자리에서 이기려 하지 마세요. 리뷰 세션의 산출물은 승리가 아니라
**질문 목록**입니다. 답이 있으면 짧게 답하고, 없으면 "기록했습니다"가 최선의 응답입니다.
분류는 세션이 끝난 뒤 팀끼리:

| 분류 | 기준 | 처리 |
|---|---|---|
| 수용 | 실제 위험이고 대응 비용이 감당됨 | 백로그 이슈로 등록 |
| 보류 | 실제 위험이지만 이번 범위 밖 | 위험 등록부 + "다음 단계"에 기록 |
| 기각 | 우리 조건에선 성립 안 함 | **이유를 문서에 기록** (심사 대비 자산) |

기각도 기록하는 이유 — 같은 질문이 최종 심사에서 다시 옵니다. 오늘 정리한 기각 사유가
그날의 모범 답안입니다.

### 위험 등록부 — "조심한다"는 대응이 아니다

| 열 | 내용 | 나쁜 예 → 좋은 예 |
|---|---|---|
| 위험 | 무엇이 잘못될 수 있나 | — |
| 확률·피해 | 상/중/하 | — |
| **조기 신호** | 무엇을 보면 시작을 아는가 | "잘 지켜본다" → "DAG 실패 알림 2회 연속" |
| **대응** | 신호가 오면 무엇을 하는가 | "조심한다" → "축소 경로: 재학습 주기를 수동 실행으로 강등" |

핵심은 대응이 **미리 설계된 축소 경로**여야 한다는 것 — 위험이 현실이 된 날 회의를
시작하는 팀과 준비된 플랜 B를 꺼내는 팀의 차이가 W31의 차이입니다.

## ④ 단계별 실습

### Step 1. 리뷰 준비 (1교시)

새 자료를 만들지 않습니다 — 이미 있는 문서(확정서·요구사항·ARCHITECTURE·ERD·API 명세)
링크와 10분 발표 순서만 정합니다: 시나리오 → 그림 → 자른 것과 이유 → 가장 불안한 곳
2개. **"가장 불안한 곳"을 스스로 공개하는 것**이 좋은 리뷰를 부르는 미끼입니다.

### Step 2. 팀 간 상호 리뷰 (2~5교시)

팀당 발표 10분 + 질의 20분, 교차로 진행합니다. 한산 팀이 받은 질문과 현장 응답:

| 질문 (타 팀) | 유형 | 현장 응답 |
|---|---|---|
| 재학습으로 나온 새 모델이 기존보다 나쁘면 그대로 배포되나요? | 시간 | **즉답 실패 — 기록** |
| 연휴 직후엔 D-4가 아니라 D-6일 텐데 수집 DAG는? | 데이터 | upsert라 늦게 와도 채워짐 — 단 "그날 예보 품질"은 기록 |
| 등급 경계 0.5/0.8의 근거는? 강남과 한적한 역이 같은 경계? | 정의 | 역·요일·시간대별 P90 대비 **비율**이라 역 규모는 정규화됨 — 경계값 자체는 보류 |
| 백필 48,756행이면 호출 몇 번? 1,000회 제한은? | 한도 | 날짜당 1호출 × 956일 — 하루 1,000회 제한에 걸리므로 이틀 분할, 이슈 #7에 반영됨 |
| MLflow 서버가 죽어 있으면 API는 모델을 어떻게 로드하죠? | 시간 | **즉답 실패 — 기록** |

강사 피드백 하나가 추가됩니다 — "품질 목표(MAE 20%↓)의 달성 여부를 **누가 언제
판정하는지**가 계획에 없다" → [Day 149](day-149.md)의 모델 선정 회의로 명문화.

### Step 3. 분류와 반영 (6~7교시)

한산 팀의 분류 결과:

| 질문 | 분류 | 처리 |
|---|---|---|
| 재학습 게이트 부재 | **수용** | 규칙 명문화: "새 run의 홀드아웃 MAE가 운영 모델 대비 +10% 초과 악화면 승격 보류 + 스탠드업 보고" — W31 백로그에 이슈 등록 |
| MLflow 다운 시 로드 실패 | **수용** | API가 마지막 성공 로드 모델을 로컬 캐시에 보관, 기동 시 레지스트리 실패하면 캐시로 폴백 — [Day 151](day-151.md)에 구현 |
| 연휴 D-6 지연 | 보류 | 위험 등록부 + 보고서 "한계"에 기록 (연휴 직후 예보는 최신성 저하) |
| 등급 경계값 근거 | 보류 | 경계 튜닝은 선택 기능 — 현 경계의 의미("P90의 절반/8할")를 문서에 명시 |
| 백필 분할 | 기각(이미 반영) | 이슈 #7에 분할 계획 있음 — 질문 덕에 문서에도 명시 |

### Step 4. 위험 등록부와 설계 확정 (8교시)

```
[한산 · 위험 등록부 v1 — docs/RISKS.md]
R1 수집 원천 장애(API 중단·키 차단) 확률中 피해上
   신호: DAG 실패 2회 연속 알림 / 대응: 수동 CSV 다운로드 경로(문서화됨)로 D+1 내 복구
R2 모델 성능 목표(MAE 20%↓) 미달        확률中 피해中
   신호: 149 선정 회의 / 대응: 등급 정확도 우선으로 목표 재협상 + 원인 분석을 보고서에
R3 통합 지연(모델↔API)                  확률低(뼈대 有) 피해上
   신호: 계약 테스트 red 12h 초과 / 대응: 기능 동결, 전원 통합 투입
R4 팀원 1인 공백(질병 등)               확률低 피해中
   신호: — / 대응: 교차 리뷰 짝이 인수, 선택 기능 1개 자동 하차
```

설계 문서 일체를 병합하고 태그를 남깁니다: `git tag design-v1`. 오늘 이후 설계 변경은
PR + 전원 리뷰 — 스프린트의 과녁이 고정됐습니다.

**오늘 퇴근 체크** — □ 타 팀에 실패 시나리오 질문 3개 이상 던짐 □ 받은 질문 전부
분류·기록(기각도 이유와 함께) □ 위험 등록부(조기 신호·축소 경로) □ `design-v1` 태그
□ 내일 스탠드업 시각·진행자 확인

## ⑤ 자주 하는 실수

### 리뷰 세션이 발표회로 끝남

**증상** — 발표 10분, 질문 "잘 들었습니다" — 채굴량 0.
**원인** — 리뷰어가 질문 규격 없이 들어옴 + 예의를 비판 회피로 오해.
**해결** — ③의 질문 틀 5유형에서 **팀당 최소 3개**를 의무로 하세요. 좋은 질문은 공격이
아니라 선물입니다 — 여러분이 W31에 겪을 사고를 남의 입으로 미리 듣는 것.

### 방어 모드

**증상** — 질문마다 "그건 이래서 괜찮습니다"로 즉시 반격 — 세션이 토론 대회가 되고,
기록은 0, 리뷰어는 입을 닫음.
**원인** — 설계에 대한 지적을 팀에 대한 지적으로 받아들임.
**해결** — 리뷰이의 목표를 "질문 목록 수집"으로 재정의하세요. 즉답 실패("기록했습니다")
가 부끄러운 게 아니라 세션의 최대 수확입니다 — 한산 팀의 게이트·폴백 설계는 즉답 실패
두 개에서 나왔습니다.

### 받은 리뷰를 전부 수용

**증상** — 리뷰 반영 이슈 14개 등록 — Day 142에 잘랐던 범위가 하루 만에 원상 복구.
**원인** — 분류 없이 수용 = 타인의 우선순위로 내 백로그를 채우는 것.
**해결** — 분류 기준을 다시: 수용은 "실제 위험 + 감당 가능 비용"의 교집합뿐입니다.
나머지는 보류(등록부·다음 단계)로도 충분히 존중한 것입니다 — 기록이 곧 응답입니다.

### 위험 대응이 정신력

**증상** — 등록부의 대응 열이 "주의 깊게 모니터링한다"·"열심히 한다"로 채워짐.
**원인** — 대응을 태도로 착각 — 태도는 위험이 현실이 된 날 아무것도 실행해 주지 않습니다.
**해결** — 대응 열의 검사 규칙: **동사가 실행 가능한가, 조기 신호가 관측 가능한가.**
"모니터링한다" → "무엇을(DAG 실패 알림) 보고, 몇 회(2회 연속)면, 무엇을(수동 경로 전환)
한다"로 바꿔야 통과입니다.

설계 리뷰가 이 문제의 해법으로 작동하는 구조적 이유(리뷰어의 어떤 속성 때문인지)를
설명하세요.

<summary>답 보기</summary>

같은 문장을 반복해서 읽으면 그 문장은 검토 대상에서 배경 지식으로 이동합니다 — 가정이
문서에 오래 머물수록 "우리가 결정한 것"이 "원래 그런 것"으로 굳는 것이죠. 리뷰어의 힘은
더 똑똑해서가 아니라 **그 배경 지식이 없다는 것**에서 옵니다: 처음 읽는 사람에게는 모든
문장이 아직 검토 대상이라, 팀에게는 투명해진 가정("D-4는 흡수됨")이 리뷰어에게는 질문
("연휴엔?")으로 보입니다. 같은 원리로, 남의 설계를 리뷰하는 행위가 자기 설계 재검토를
유발합니다 — 남의 문서에서 구멍을 찾는 눈이 켜진 채로 자기 문서로 돌아오기 때문입니다.

백필 분할 질문 사례로 설명하세요.

<details>

입니다. 백필 사례: "1,000회 제한은?"이라는 질문에 한산 팀은 이미 이슈 #7에 분할 계획이

주 설계 리뷰에서도 나온 질문이고, 이렇게 계획해 이렇게 실행됐다"고 문서를 열어 답하게
됩니다. 준비된 답과 즉석 답의 신뢰 차이가 협업·문서 배점으로 연결됩니다.

</details>

원천 장애)을 예로 신호의 유무가 실제 사고 대응에서 만드는 차이를 설명하세요.

<details>
<summary>답 보기</summary>

신호가 없으면 등록부는 "걱정 목록" — 알고는 있었지만 아무도 발견하지 못하는 위험의
명단이 됩니다. 위험은 선언이 아니라 관측으로 발견되기 때문입니다. R1의 경우: 신호(DAG
실패 알림 2회 연속)가 정의되어 있으면 장애 발생 이튿날 아침 스탠드업에서 자동으로
의제가 되고, 준비된 대응(수동 CSV 경로)이 즉시 실행됩니다 — 데이터 공백 1~2일. 신호가
없으면 발견은 "어? 요즘 예측이 이상한데?"(모델 품질 저하로 뒤늦게 표출)가 되고, 원인
추적부터 시작해 공백은 일주일 단위가 됩니다. 같은 위험, 같은 대응 수단 — 발견 시점만이
피해 크기를 정합니다.

</details>
