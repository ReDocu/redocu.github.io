## 3. 개념

### 3-1. 성능 목표 설정

**왜 필요한가** — 기준이 없으면 판단 못 한다.

```
   ★ 목표를 정한다

   ① 대상 사양 (개발 PC? 저사양?)
   ② 목표 프레임 (60? 30?)
   ③ 목표 해상도
```

| 항목 | 목표 |
|---|---|
| 평균 FPS | 60 |
| **최악 프레임** | **20ms 이하** ★ |
| GC Alloc | 0.5KB/frame 이하 |
| 메모리 | 1GB 이하 |
| 빌드 크기 | 300MB 이하 |

```
   ★ 최악 프레임이 가장 중요하다 (Day 70·89)

   평균 60인데 가끔 40ms면 "끊긴다"고 느낀다
```

```
   ★ 30fps도 목표가 될 수 있다

   ① 그래픽이 무거운 게임
   ② 저사양 대상
   → 안정적인 30이 불안정한 60보다 낫다
```

### 3-3. Release Build로 측정

**왜 필요한가** — Development Build는 느리다.

```
   ★ 차이

   에디터:             가장 느림 (2~3배)
   Development Build:  약간 느림 (10~20%)
   Release Build:      실제 성능  ★
```

```
   ⚠️ Release는 프로파일러 연결이 안 된다

   ★ 해결
   ① Development로 병목을 찾는다
   ② Release로 최종 수치를 잰다
```

```csharp
    // Release에서도 측정 가능한 간이 도구 (Day 96)
    public class PerfRecorder : MonoBehaviour
    {
        private float worstDt;
        private int frames;
        private float totalDt;

        private void Update()
        {
            float dt = Time.unscaledDeltaTime;

            frames++;
            totalDt += dt;
            if (dt > worstDt) worstDt = dt;
        }

        private void OnGUI()
        {
            if (!show) return;

            GUI.Label(new Rect(10, 10, 400, 100),
                $"평균 {frames / totalDt:F1} fps\n" +
                $"최악 {worstDt * 1000f:F1} ms\n" +
                $"메모리 {System.GC.GetTotalMemory(false) / 1048576f:F0} MB");
        }
    }
```

```
   ★ 릴리즈 빌드에서도 F3으로 볼 수 있게
   → Day 118에서 끈다
```

### 3-4. 최적화 체크리스트

**왜 필요한가** — Day 96의 재확인.

| 항목 | 확인 | 대응 |
|---|---|---|
| **GC Alloc** | 프레임당 할당 | 풀, 문자열, 캐싱 |
| **Draw Call** | Batches 수 | 배칭, 아틀라스 |
| `Update` 남발 | 스크립트 수 | 매니저 일괄 |
| `Find` 계열 | 호출 위치 | `Awake` 캐싱 |
| **텍스처** | 임포트 설정 | 크기, 압축 |
| 물리 | Fixed Timestep | 레이어 매트릭스 |
| **파티클** | 개수·오버드로우 | 상한, 크기 |
| 그림자 | Shadow Distance | 줄인다 |
| 오디오 | Load Type | 짧은 것은 Decompress |

```
   ★ 우선순위

   ① GC (프레임 튐의 주범)
   ② 파티클 (우리 게임의 특성)
   ③ 텍스처 (빌드 크기·메모리)
   ④ Draw Call
```
