## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **main 병합마다** 이미지가 빌드되어 GHCR로 push되는 워크플로를 만들 수 있다.
- **GITHUB_TOKEN**과 **Actions secrets**로 워크플로 안의 인증을 시크릿 유출 없이 처리할 수 있다.
- **태그 전략**(latest · sha · 버전)을 설계하고, 커밋 ↔ 이미지의 1:1 족보를 만들 수 있다.
- 서버의 compose를 `build:` 에서 `image:` 로 전환해 "**서버는 빌드하지 않는다**"를 완성할 수 있다.

---

## ② 왜 필요한가

[Day 120](day-120.md)의 push는 사람 손이었습니다. 그날의 절차를 상기하면 — tag 붙이고, login
하고, push 하고. 사람 손의 문제는 고생이 아니라 **족보의 구멍**입니다:

> 지금 GHCR의 0.1.0은 **어느 커밋**의 코드입니까? — "아마 그때쯤 제 로컬에 있던..."

이 대답이 운영에서 얼마나 위험한지는 [Day 119](day-119.md) Q3에서 봤습니다 — 이미지 태그의
족보가 무효화되는 순간, "그 서버만 이상해요"가 시작됩니다. 커밋 안 된 수정이 섞인 로컬 빌드,
잊어버린 push, 태그 재사용… 사람 손이 닿는 모든 지점이 구멍입니다.

오늘의 목표는 회선의 국유화입니다 — **이미지를 만들 수 있는 유일한 손을 CI로**:

```
어제까지:  main 병합 ✓ (게이트) ─┈┈─ 이미지는 언젠가 사람이 (구멍)
오늘부터:  main 병합 ✓ ──▶ 기계가 즉시 빌드 ──▶ sha 태그로 push
                              └─ 커밋 ↔ 이미지가 1:1 — 족보 완성
```

main은 보호 규칙(어제) 덕에 게이트 통과분만 담고, 이미지는 그 main에서만 태어나므로 —
**"GHCR의 모든 이미지는 검증된 커밋의 산물"** 이라는 문장이 성립하게 됩니다. 내일의 CD는
이 회선 끝에 "서버 반영"을 잇기만 하면 됩니다.

## ③ 개념 설명

### 워크플로의 분업 — 검증과 생산

| 파일 | 트리거 | 하는 일 |
|---|---|---|
| ci.yml (126~127) | 모든 push·PR | **검증** — test·lint (산출물 없음) |
| **build.yml (오늘)** | **main에 push된 때만** (=병합 순간) | **생산** — 이미지 빌드→GHCR |

`on: push: branches: [main]` — 이 필터가 분업의 전부입니다. PR 단계에서 이미지를 만들지 않는
이유: 아직 게이트를 통과 못 한 코드의 산출물이 창고에 쌓이면 안 되니까요 (⑤ 참고).

### GITHUB_TOKEN — PAT의 은퇴

[Day 120](day-120.md)의 PAT는 수동 시대의 열쇠였습니다 — 만들고, 간수하고, 만료되면 갱신.
Actions 러너에는 더 좋은 것이 있습니다: **GITHUB_TOKEN** — 워크플로 실행마다 GitHub이
자동 발급하는 **임시 토큰**입니다. 실행이 끝나면 무효가 되므로 유출·만료 걱정이 구조적으로
없습니다. 필요한 것은 권한 선언뿐:

```yaml
permissions:
  contents: read      # 코드 checkout
  packages: write     # GHCR push
```

### Actions secrets — 워크플로의 .env

GITHUB_TOKEN으로 안 되는 비밀(외부 서비스 키, 내일의 SSH 키)은 저장소 Settings → Secrets and
variables → Actions에 보관하고 `${{ secrets.이름 }}` 으로 씁니다. 성질 세 가지 — ① 한번
저장하면 **다시 볼 수 없음**(쓰기 전용), ② 로그에 값이 찍히면 `***` 로 **자동 마스킹**,
③ 그래도 [Day 122](day-122.md)의 4대 금지처 규율은 그대로 (echo로 가공해 우회 노출하는 사고가
실존합니다 — ⑤).

### 태그 전략 — 세 이름의 분업

| 태그 | 예 | 성질 | 용도 |
|---|---|---|---|
| `latest` | latest | **가변** — 최신 main 빌드를 따라다님 | 개발 편의·문서의 기본값 |
| **`sha-…`** | sha-b6f92d3 | **불변** — 커밋과 1:1 | **배포·롤백·장애 조사의 언어** |
| `vX.Y.Z` | v0.2.0 | 불변 — 사람이 의미를 부여한 지점 | 릴리스·발표 (MP4 제출 태그) |

핵심은 sha 태그입니다 — 이미지 이름만 보고 `git log b6f92d3` 으로 **정확한 코드·PR·작성자**를
역추적할 수 있습니다. [Day 096](../04-deep-learning-serving/day-096.md)의 model_version(모델의
족보), [Day 120](day-120.md)의 digest(바이트의 족보)에 이어 — **커밋의 족보**가 완성됩니다.

## ④ 단계별 실습

### Step 1. build.yml (1~3교시)

브랜치 `feature/build-pipeline`, 파일 `.github/workflows/build.yml`:

```yaml
name: Build & Push

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=raw,value=latest
            type=sha,prefix=sha-

      - uses: docker/setup-buildx-action@v3

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

읽어 둘 세 곳 — ① login의 password가 `secrets.GITHUB_TOKEN` (PAT 은퇴 — 저장할 시크릿조차
없음), ② metadata-action이 태그 두 벌(latest + sha-커밋)을 계산, ③ `cache-from/to: gha` —
러너는 빈 방이라 Docker 층 캐시도 없는데, GitHub의 캐시 창고에 층을 보관해 다음 빌드가
재사용합니다 (Day 117 캐시 원리의 CI판).

### Step 2. 병합 → 자동 생산 확인 (4교시)

PR을 열고(체크 통과·리뷰) 병합하면 — Actions 탭에 Build & Push가 스스로 시작됩니다:

```
Build & Push / build (push)                              ✓ 4m 07s
  ✓ docker/build-push-action
    #18 pushing manifest for ghcr.io/mlops-student/mlops-mp3:sha-b6f92d3
    #18 pushing manifest for ghcr.io/mlops-student/mlops-mp3:latest
```

GHCR 패키지 페이지에 `latest` 와 `sha-b6f92d3` 이 나란히 — 그리고 b6f92d3은 방금 병합 커밋의
해시입니다. **한 번 더 병합해 보세요** (README 오타 수정 등 소소한 PR) — 이번엔 gha 캐시 덕에:

```
Build & Push / build (push)                              ✓ 1m 21s
```

torch 층이 캐시에서 나와 4분 → 1분대. 층 순서 설계(117)가 CI 요금·리드타임으로 세 번째 보상을
주는 순간입니다.

### Step 3. 서버의 전환 — "서버는 빌드하지 않는다" (5~6교시)

서버(WSL)의 compose.yaml에서 api의 `build: .` 를 **이미지 참조로 교체**합니다:

```yaml
  api:
    image: ghcr.io/mlops-student/mlops-mp3:latest    # build: . 에서 전환!
```

이제 서버의 갱신 절차는 "받아서 갈아 끼우기" 두 동사입니다:

```bash
docker compose pull api
docker compose up -d
```

```
$ docker compose pull api
[+] Pulling 6/6
 ✔ api Pulled                                                              8.3s
$ docker compose up -d
[+] Running 3/3
 ✔ Container mlops-mp3-db-1     Running
 ✔ Container mlops-mp3-api-1    Started
 ✔ Container mlops-mp3-nginx-1  Started
```

서버에서 소스 코드·빌드가 할 일이 사라졌습니다 — 서버가 아는 것은 이미지 이름뿐. 이것이
[Day 122](day-122.md) Q1의 "빌드 1회 → 어디서나 같은 바이트" 원칙의 완성형이고, 내일 CD가
자동화할 두 동사가 바로 이 pull·up입니다.

### Step 4. 족보로 롤백 리허설 (7교시)

sha 태그의 존재 이유를 몸으로 — 방금 배포가 문제라고 가정하고, **직전 커밋의 이미지**로
되돌립니다:

```bash
sed -i 's|mlops-mp3:latest|mlops-mp3:sha-41c8e07|' compose.yaml
docker compose pull api && docker compose up -d
curl -s localhost:8080/health
```

```
$ curl -s localhost:8080/health
{"status":"ok","model_loaded":true,"model_version":"resnet18-antbee-v1","started_at":"2026-08-24T06:19:52+00:00"}
```

몇 초 만에 "지난 버전"이 돌아왔습니다 — 어느 커밋인지 이름에 적혀 있으니 조사도 명확합니다.
확인 후 latest로 복귀. (운영 팁: 배포 기록에 "언제 어떤 sha를 올렸나"를 남기면 롤백은 언제나
그 기록을 거꾸로 읽는 일이 됩니다 — 내일 CD가 이 기록을 자동으로 만들게 합니다.)

### Step 5. 과제 — 태그 정책 문서화 (8교시)

`docs/TAGGING.md` 를 작성해 PR로 제출하세요. 필수 항목:

1. **생성 규칙** — 어떤 이벤트가 어떤 태그를 만드는가 (표: 이벤트 | 태그 | 불변? | 만든 주체)
2. **사용 규칙** — 배포는 무엇으로, 롤백은 무엇으로, 문서 예시는 무엇으로
3. **금지 규칙** — 태그 재사용 금지, 사람 손 push 금지 (예외 절차 포함)
4. **역추적 절차** — "지금 운영 중인 이미지가 어느 커밋인가"에 답하는 명령 시퀀스
   (`docker inspect` 의 digest → GHCR에서 태그 확인 → git log)

그리고 생각 문제: v0.2.0 같은 **릴리스 태그**는 언제 누가 붙여야 할까요? (git tag와 연동하는
`on: push: tags:` 트리거를 조사해 한 단락 — MP4 제출물에 v1.0.0을 쓰게 됩니다.)

## ⑤ 자주 하는 실수

### permissions 누락으로 403

**증상** —
```
ERROR: denied: installation not allowed to Write organization package
```
(또는 개인 계정에서 `denied: permission_denied: write_package`)
**원인** — GITHUB_TOKEN의 기본 권한이 좁습니다 — packages: write를 **선언**해야 부여됩니다.
**해결** — 워크플로 상단 `permissions:` 블록 확인. 최소 선언 원칙(contents: read + packages:
write만)은 Day 112의 최소 권한이 토큰에 적용된 형태입니다 — 넓게 열지 마세요.

### 브랜치 필터 없는 build

**증상** — `on: push` (필터 없음)로 만든 build.yml — 모든 브랜치의 모든 push가 이미지를
생산, latest가 미검증 코드로 갈아치워짐.
**원인** — ci.yml을 복사하며 트리거를 그대로 둠.
**해결** — 생산 워크플로는 반드시 `branches: [main]`. "검증은 넓게, 생산은 좁게" — 트리거
필터가 곧 품질 정책입니다.

### 시크릿을 가공해서 마스킹을 우회

**증상** — 디버깅한다고 `echo ${{ secrets.DEPLOY_KEY }} | base64` — 마스킹은 원문만 가리므로
인코딩된 값이 로그에 그대로. 공개 저장소면 전 세계 공개.
**원인** — "어차피 *** 로 가려지니까"라는 과신.
**해결** — 시크릿은 로그로 확인하지 않습니다 — 존재 확인은 `if [ -n "$KEY" ]` 식 분기로,
값 검증은 실제 사용(로그인 성공 여부)으로. Day 122 금지처 ④(로그)는 CI 로그에도 그대로
적용됩니다 — CI 로그는 팀 전원+α가 보는 매체입니다.

### 서버에 build: 를 남겨 둠

**증상** — compose에 build: 가 남아 있어, 서버의 `up -d --build` 습관이 **서버 로컬 코드**로
이미지를 만들어 버림 — GHCR 족보와 무관한 유령 이미지가 운영에.
**원인** — 전환 미완 — 두 시대의 방식이 공존.
**해결** — 운영 compose에서 build: 제거(오늘 Step 3), 소스는 서버에서 지워도 됩니다 (모델·
.env 등 이미지 밖 자산만 남기고). "서버에서 빌드하고 싶은 충동"이 들면 그것은 대개 핫픽스
유혹 — 정로(PR→병합→자동 빌드)가 15분이면 도는데, 우회는 족보 없는 15일짜리 미스터리를
만듭니다.

### latest로 배포 상태를 관리

**증상** — "지금 운영이 무슨 버전이죠?" — "latest요" — 정보량 0. 롤백하려니 이전 latest는
소멸.
**원인** — 가변 태그를 상태 기록으로 오용 (Day 118 ⑤의 재발).
**해결** — 배포·기록·롤백은 **sha 태그의 언어**로 말합니다. latest는 "따라가기"가 필요한
자리(개발 편의)에만. 내일 CD 워크플로가 배포 시 sha를 기록하게 만들면 이 규율이 자동화됩니다.

## ⑥ 확인 문제

**Q1.** "GHCR의 모든 이미지는 검증된 커밋의 산물"이라는 문장이 성립하기 위해 이번 주에 쌓은
장치 세 가지를 연결해 설명하세요.

<details>
<summary>답 보기</summary>

① 브랜치 보호(127) — main에는 test·lint·리뷰를 통과한 PR만 병합됩니다. ② 트리거 필터(오늘) —
이미지는 main push(=병합)에서만 빌드됩니다. ③ 유일 생산자 원칙 — 사람 손 push를 규약(TAGGING.md)
으로 금지해 CI가 유일한 생산 경로가 됩니다. 세 고리가 하나라도 빠지면(관리자 우회 병합, 필터
없는 빌드, 로컬 push) 창고에 족보 없는 이미지가 생깁니다 — 공급망의 신뢰는 사슬 전체의
최약점만큼만 강합니다.

</details>

**Q2.** GITHUB_TOKEN이 PAT보다 안전한 이유를 수명·범위·관리 부담 세 축으로 비교하세요.

<details>
<summary>답 보기</summary>

수명: PAT는 수십 일 단위로 살아 유출 시 그 기간 내내 위험하지만, GITHUB_TOKEN은 **그 실행
동안만** 유효 — 로그에 새어도 실행 종료와 함께 무효입니다. 범위: PAT는 계정 전체에 걸친 권한이
되기 쉽지만, GITHUB_TOKEN은 그 저장소 + 선언한 permissions로 제한됩니다. 관리: PAT는 발급·보관·
만료 갱신·폐기가 전부 사람 일(각 단계가 사고 지점)이지만, GITHUB_TOKEN은 발급·폐기가 자동 —
관리할 비밀이 존재하지 않는 것이 최고의 비밀 관리입니다.

</details>

**Q3.** PR 단계에서는 이미지를 push하지 않지만, "PR에서 **빌드만** 해 보는 것"(push: false)은
가치가 있습니다. 무엇을 조기에 잡을 수 있는지 예를 들고, 오늘 구조에 어떻게 추가할지
설계하세요.

<details>
<summary>답 보기</summary>

Dockerfile 자체의 회귀 — COPY 경로 오타, .dockerignore 과잉(모델 제외 사고 — Day 118 ⑤),
의존성 설치 실패 — 는 test·lint로는 안 잡히고 병합 후 build.yml에서야 터집니다 (main이 "빌드
불가" 상태로 오염). ci.yml에 build-check job을 추가하면 됩니다: 같은 build-push-action에
`push: false` (+ gha 캐시 공유)로 — 산출물은 안 만들고 빌드 가능성만 검증. 게이트(127)의
required checks에 넣으면 "빌드 안 되는 코드는 main에 못 들어온다"까지 완성됩니다.
