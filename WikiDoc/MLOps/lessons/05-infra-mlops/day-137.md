## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 빈 환경 기동(clone→up→데모)을 **5분 이내**로 만들고, 시간의 내역을 해부할 수 있다.
- **장애 매트릭스**(무엇을 어떻게 죽이면 어떻게 회복되나)를 설계하고 전 항목을 실증할 수 있다.
- README의 실행 절차를 **"모르는 사람이 그대로 성공하는"** 수준으로 완결할 수 있다.
- 오늘의 산출물: **한 줄 기동** — 증거(리허설 기록·장애 실험 로그)와 함께.

## ② 왜 필요한가

오늘은 배점표의 첫 번째 큰 덩어리 — **재현성 25점**의 날입니다. 심사 시나리오를 그대로
상상하세요: 심사위원이 여러분의 README를 열고, 낯선 PC에서, 여러분 없이:

```
git clone … && cd …
cp .env.example .env      (값 채우기 — 허용된 유일한 판단)
docker compose up -d
→ http://localhost:8080/static/ 에서 개미 사진 판정
```

이 4줄 사이의 모든 마찰 — 없는 명령, 틀린 경로, 7분의 침묵, 알 수 없는 에러 — 이 전부
감점입니다. 어제 감사에서 잡힌 🔶(리허설 7분)를 오늘 수리하고, 더 나아가 **기동 후의 신뢰**
까지 증명합니다: 뜨는 것과 계속 떠 있는 것은 다르니까요. "컨테이너 kill 후 자동 회복"은
서비스 평가 기준에 명시된 항목입니다 — 오늘 그것을 매트릭스로 전수 실험합니다.

## ③ 개념 설명

### 기동 시간의 해부 — 어디서 7분이 갔나

```
clone(10s) → .env(사람) → up: 이미지 확보 + 컨테이너 기동 + healthy 대기 → 첫 요청
                              └─ 여기가 승부처
```

| 이미지 확보 방식 | 시간 | 언제 이렇게 되나 |
|---|---|---|
| **build:** — 그 자리에서 빌드 | 2~5분 (torch 설치) | compose에 build: 가 남아 있으면 |
| **image:** — GHCR에서 pull | 40~90초 (1.6GB) | [Day 128](day-128.md) 전환을 완료했으면 |

어제 리허설 7분의 범인은 대부분 이것입니다 — 심사위원은 빌드하는 사람이 아니라 **받는
사람**이어야 합니다 (서버는 빌드하지 않는다의 심사판). 나머지는 healthy 대기(DB 초기화 +
모델 로드 — start_period 설계 덕에 예측 가능)와 데모 첫 클릭입니다.

### 장애 매트릭스 — 회복의 전수 조사

행은 구성 요소, 열은 "죽이는 방법 → 기대 회복 → 증거". 우리 구성의 전수표:

| # | 실험 | 기대 | 근거 장치 |
|---|---|---|---|
| 1 | api를 `docker kill` | 수십 초 내 자동 재기동, 데모 재개 | restart + healthcheck (123) |
| 2 | db를 `docker kill` | db 재기동 · **api는 안 죽고** 요청 처리 지속 | restart + pool_pre_ping (121·123) |
| 3 | nginx를 `docker kill` | 재기동, 그동안만 8080 단절 | restart (124) |
| 4 | 서버 재부팅 (`wsl --shutdown`) | 전 서비스 무인 복귀 | unless-stopped (123) |
| 5 | down → up | **데이터(예측 로그) 생존** | volume (119·121) |

이 표가 문서(ARCHITECTURE.md 감시 항목표의 이웃)에 들어가고, 각 행의 실험 로그가 증거로
첨부됩니다 — "복원력이 있습니다"가 아니라 "**다섯 방법으로 죽여 봤고 전부 살아났습니다**".

## ④ 단계별 실습

### Step 1. 리허설 병목 수리 (1~3교시)

먼저 측정 — 진짜 빈 환경을 만들고 (이미지·볼륨까지 청소) 스톱워치:

```bash
cd /tmp && rm -rf rehearsal
docker rmi ghcr.io/mlops-student/mlops-mp3:latest 2>/dev/null
git clone https://github.com/mlops-student/mlops-mp3.git rehearsal && cd rehearsal
cp .env.example .env && nano .env
time docker compose up -d --wait
```

```
$ time docker compose up -d --wait
[+] Running 4/4
 ✔ Container rehearsal-db-1     Healthy    11.8s
 ✔ Container rehearsal-api-1    Healthy    68.4s
 ✔ Container rehearsal-nginx-1  Started    69.0s
real    1m52.3s
```

7분 → **1분 52초** — 어제 감사의 범인이 compose에 남아 있던 `build:` 였다면 image: 참조로
바꾸는 것만으로 이 수치가 나옵니다 (1.6GB pull 72초 + healthy 대기). 내역을 기록하세요:
clone 9s · pull 72s · db healthy 12s · api healthy(모델 로드 포함) 57s. **"어디에 몇 초"를
말할 수 있는 것**까지가 오늘의 완성 기준입니다 — 심사 질문 1순위이기도 합니다.

> `--wait` 옵션 — healthy까지 기다렸다가 돌아옵니다. 리허설·스크립트에서 "up은 됐는데 아직
> 로드 중" 혼동을 없애 주는 한 단어 ([Day 125](day-125.md) Step 3에서 이미 슬쩍 썼습니다).

### Step 2. 장애 매트릭스 전수 실험 (4~6교시)

③의 표를 위에서부터. 실험마다 형식은 동일 — **예상 적기 → 실행 → 관찰 → 표에 증거 링크**:

```bash
# 실험 2 — DB 급사: api가 버티는가
docker kill rehearsal-db-1
sleep 3
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8080/predict   # api 살아 있나
sleep 15
docker compose ps                                                      # db 돌아왔나
docker compose exec db psql -U mp3 -d mp3 -c "SELECT count(*) FROM prediction_log;"
```

```
$ curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8080/predict
{"label":"ants","confidence":0.7214,"model_version":"resnet18-antbee-v1","elapsed_ms":30.9}
$ docker compose ps | grep db
rehearsal-db-1   postgres:16   db   Up 12 seconds (healthy)
```

DB가 죽은 사이에도 예측은 성공(로그 적재만 best-effort로 건너뜀 — [Day 123](day-123.md)
과제 1의 그 설계가 여기서 점수가 됩니다), DB는 스스로 복귀. 다섯 실험 전부 이 형식으로
`docs/RESILIENCE.md` 에 적재합니다. 실패한 항목이 있다면 — 오늘 최고의 수확입니다: 금요일
심사장이 아니라 오늘 발견했으니까요. 원인 수리 후 재실험까지.

### Step 3. README 최종과 타인 검증 (7교시)

실행 섹션을 완결하고 (필요 조건 명시: Docker Desktop 버전 · 디스크 2GB · GHCR 로그인이
필요한 경우 그 절차까지), **짝 교차 검증** — 짝이 자기 PC에서 README만 보고 수행, 막힌
지점마다 README를 고칩니다 ([Day 125](day-125.md)의 규칙: README에 없는 지식이 필요했다면
그것이 버그). 목표 기록: **짝의 PC에서 5분 내·질문 0회.**

### Step 4. 오늘의 봉인 (8교시)

```powershell
git add docs/RESILIENCE.md README.md
git commit -m "MP4 Day2: 한 줄 기동 1m52s(빈 환경) + 장애 매트릭스 5종 통과"
git push   # → CI → 자동 배포 — 어제까지의 파이프라인이 오늘의 작업도 실어 나릅니다
```

**오늘 퇴근 체크** — □ 빈 환경 기동 실측 (내역 포함) □ 장애 매트릭스 5행 전부 증거 확보
□ 짝의 PC에서 재현 성공 □ RESILIENCE.md 커밋 □ (상급 트랙) 내일 CD 검증 시나리오 초안

## ⑤ 자주 하는 실수

### "빈 환경"이 사실은 웜 환경

**증상** — 내 리허설 1분 52초, 심사위원 PC에서 4분 — 베이스 이미지(python:3.12-slim 등)가
내 쪽엔 캐시돼 있었음.
**원인** — rmi로 프로젝트 이미지만 지우고 베이스·중간층은 남음.
**해결** — 최소한 한 번은 진짜 콜드로: 다른 기계(짝 PC — Step 3이 그 역할)에서 측정. 문서에는
콜드/웜 두 수치를 병기하는 것이 정직하고, 병기 자체가 이해도의 증거가 됩니다.

### 장애 실험을 운영 데이터 위에서

**증상** — 실험 5(down→up)를 하다 손이 미끄러져 `-v` — 2주치 예측 로그 증발.
**원인** — 실험장과 운영장의 미분리.
**해결** — 오늘 실험이 /tmp/rehearsal(리허설 환경)에서 도는 이유입니다. 운영 폴더에서 해야
하는 실험(재부팅)은 **백업 먼저** ([Day 125](day-125.md) pg_dump) — 실험 전 백업은 겁이
아니라 절차입니다.

### healthy = 데모 성공이라는 비약

**증상** — `--wait` 통과를 보고 "기동 완료"로 기록 — 심사위원의 첫 데모 클릭에서 정적 페이지
404 (static 마운트 경로 오타).
**원인** — healthcheck는 api의 /health만 봅니다 — nginx의 정적 서빙, 프록시 경로는 검사 밖.
**해결** — 리허설의 종점은 healthy가 아니라 **사용자 행동의 재현**입니다: 데모 페이지 열기 →
사진 업로드 → 0.7214. 스모크 테스트(129)가 predict까지 보는 것과 같은 이유 — 검증은 소비자의
경로를 따라갑니다.

### README가 자기 환경의 사투리로

**증상** — README에 `/opt/mlops-mp3` 경로, `deploy` 계정, 포트 8080이 "당연히 있는 것"처럼 —
심사위원의 Windows PC에서 줄줄이 마찰.
**원인** — 6주간 우리 서버에서 살아온 관성 — 독자가 우리 환경에 있지 않다는 것을 잊음.
**해결** — README의 실행 섹션은 **"Docker만 있는 새 컴퓨터"를 독자로** 다시 읽으세요. 서버
운영 절차(deploy 계정·systemd 러너)는 별도 문서(OPERATIONS — 내일·모레의 산출물)로 분리 —
독자가 다르면 문서도 다릅니다.

## ⑥ 확인 문제

**Q1.** "심사위원은 빌드하는 사람이 아니라 받는 사람이어야 한다"를 이번 단원의 두 원칙
(빌드 1회·서버는 빌드하지 않는다)과 연결해 설명하고, 예외적으로 build: 를 남겨 두는 것이
정당한 경우가 있는지 논하세요.

<details>
<summary>답 보기</summary>

빌드는 환경 의존(네트워크·캐시·플랫폼)이 가장 큰 단계라, 심사위원 PC에서의 빌드는 "검증된
바이트가 아닌 것"을 그 자리에서 만드는 행위입니다 — CI가 빌드한 이미지를 pull 받게 하면
심사위원도 서버와 같은 digest를 실행합니다 (빌드 1회 원칙의 확장). 정당한 예외: 개발 문서의
"소스에서 빌드" 경로(기여자용), 또는 심사 요건이 "오프라인 실행"일 때 — 그 경우에도 기본
경로(pull)와 대안 경로(build)를 분리해 명시하는 것이 답이지, 기본을 build로 두는 것은 아닙니다.

</details>

**Q2.** 장애 매트릭스 실험 2에서 "DB가 죽어도 예측은 성공"이 좋은 설계인 이유와, 반대로
"그래서는 안 되는" 서비스의 예를 들어 — 이 판단이 기술이 아니라 **업무 요구**의 문제임을
보이세요.

<details>
<summary>답 보기</summary>

우리 서비스에서 예측 로그는 부가 기능(분석용)이라, 그 실패가 핵심 기능(추론)을 인질로 잡으면
안 됩니다 — 격리(best-effort)가 옳습니다. 반대 예: 대출 심사 API처럼 **모든 판정이 감사
기록으로 남아야 하는** 서비스라면, 기록 실패 시 판정을 반환하는 것이 규정 위반 — DB 실패는
서비스 실패여야 하고(fail closed), 가용성보다 기록 무결성이 우선입니다. 같은 아키텍처 질문
("부가 경로 실패가 핵심 경로를 막아야 하나")의 답이 도메인 요구에 따라 정반대 — 그래서 이
결정은 문서에 근거와 함께 남겨야 하는 설계 결정입니다 (123 과제 1이 그 연습이었습니다).

</details>

**Q3.** 기동 내역(clone 9s·pull 72s·db 12s·api 57s)에서 추가로 30초를 줄여야 한다면 어디를
어떻게 공략할지, 각 항목의 지배 요인과 함께 우선순위를 매기세요.

<details>
<summary>답 보기</summary>

api 57s의 지배 요인은 모델 로드 + 파이썬 기동 — 모델을 45MB ResNet 그대로 두는 한 큰 폭은
어렵고 start_period 튜닝은 체감만 바꿉니다. **pull 72s가 최적 공략지**: 이미지 1.61GB에서
더 깎을 층(불필요 의존성 정리, 모델 외부화 — 단 재현성 트레이드오프는 119 과제의 그 표로
판단)을 찾거나, 심사 안내에 "사전 pull" 단계를 명시하는 운영적 해법(콜드→웜 전환)이 가장
싸게 30초를 법니다. db 12s·clone 9s는 하한에 가깝습니다. 원칙: 측정 내역 없이 최적화 없다 —
내역이 있으니 우선순위가 계산됩니다.

</details>
