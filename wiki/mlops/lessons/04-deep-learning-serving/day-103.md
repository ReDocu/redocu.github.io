## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 배치 엔드포인트를 **상한이 명시된 계약**과 함께 설계·구현할 수 있다.
- `/model/info`를 운영 질문에 답하는 수준으로 확장할 수 있다 (가동 시각 · 처리 건수).

- **성능 비교표**(오늘의 산출물)를 측정 조건과 함께 작성할 수 있다.

## ② 왜 필요한가

어제로 필수 기능의 몸통이 끝났습니다. 오늘은 두 가지를 얹습니다: **운영 편의**(배치·버전
정보·헬스체크 확장)와 **성능의 증거**(부하 측정 전후 비교표 — 로깅·측정 20점의 절반).

오늘 가장 경계할 것은 **최적화의 늪**입니다. MP2에서 튜닝 시간박스를 배웠듯
([Day 073](../03-machine-learning/day-073.md)), 오늘의 개선은 **딱 1회**입니다. 측정하고,
지렛대 하나를 골라 당기고, 재측정하고, 표를 만들면 끝 — 효과가 없어도 그 자체가 결론입니다
(워커 실험이 그랬듯, [Day 099](day-099.md) Step 4).

## ③ 개념 설명

### 배치 계약 — 상한이 없는 배치는 계약이 아니다

[Day 100](day-100.md) Q3의 설계를 구현합니다. 핵심은 상한:

| 항목 | 예시 프로젝트 결정 | 근거 |
|---|---|---|
| 운반 | multipart 복수 파일 (`files: list[UploadFile]`) | 단건과 같은 방식 — 소비자 학습 비용 0 |
| 배치 상한 | **16장 → 초과 시 413** | 요청 지연 상한(16 × ~25ms ≈ 0.4초)과 메모리에서 역산 |
| 실패 정책 | 한 장이라도 불량이면 요청 전체 4xx | 부분 성공의 애매함 제거 — 명세에 명시 |

실패 정책은 다른 선택(불량 항목만 표시하고 나머지 성공)도 유효합니다 — 중요한 것은
**명세에 적고 테스트로 고정**하는 것입니다.

### /model/info의 승격 — 운영 질문에 답하는 창구

[Day 096](day-096.md) 과제 ①을 이제 프로젝트에 넣습니다:

```json
{"model_version": "antbee-resnet18-d085", "classes": ["ants", "bees"],
 "input": "이미지 파일 (multipart/form-data · 5MB 이하)",
 "started_at": "2026-08-13T09:00:12", "predictions_served": 1847}
```

"언제부터 이 버전이 돌고 있고, 얼마나 일했나" — 배포 확인과 장애 대응의 첫 질문이
API 한 번으로 끝납니다.

### 개선 후보 고르기 — 측정이 고른다

| 지렛대 | 우리 API에 맞는가 | 판단 근거 ([Day 099](day-099.md)) |
|---|---|---|
| **배치** | ✅ 후보 | "폴더째 분류" 시나리오 존재 + 건당 오버헤드(업로드 파싱·디코드)가 큼 |
| 캐시 | ❌ | 사진마다 바이트가 달라 히트율 ≈ 0 (Q3에서 판정한 그대로) |
| 워커 | ❌ | 추론이 이미 코어 포화 + 윈도우 개발 PC (⑤ 참고) |

예시 프로젝트는 배치를 고릅니다. **여러분의 선택이 달라도 됩니다** — 근거가 측정과 시나리오에서
나왔다면. (텍스트 API라면: 문장 배열 배치가 후보 1순위, BERT는 배치 이득이 더 큽니다.)

## ④ 단계별 실습

### Step 1. 배치 엔드포인트 (1~2교시)

router에 검사 루프, service에 배치판 함수를 추가합니다 (어제의 경계 설계 덕에 각 층 몇 줄씩):

```python
@router.post("/predict/batch")
def predict_batch(files: list[UploadFile]):
    """배치 예측 — n장을 순전파 1회로. 상한은 계약의 일부다."""
    if len(files) > 16:
        raise HTTPException(413, detail="배치는 16장까지입니다")
    imgs = []
    for f in files:
        raw = f.file.read(MAX_BYTES + 1)
        if len(raw) > MAX_BYTES:
            raise HTTPException(413, detail=f"파일이 5MB를 넘습니다: {f.filename}")
        try:
            imgs.append(Image.open(io.BytesIO(raw)).convert("RGB"))
        except UnidentifiedImageError:
            raise HTTPException(415, detail=f"이미지 파일이 아닙니다: {f.filename}")
    return service.predict_batch(store.model(), store.classes(), files, imgs)
```

동작 확인 — **배치의 답이 단건과 같은지부터** 봅니다 (정확성이 성능보다 먼저!):

```
$ POST /predict/batch (개미 사진 + 벌 사진)
  200 → {'results': [{'filename': 'ant.jpg', 'label': 'ants', 'confidence': 0.7214},
                     {'filename': 'bee.jpg', 'label': 'bees', 'confidence': 0.7694}],
         'model_version': 'antbee-resnet18-d085'}
```

0.7214 · 0.7694 — 단건 응답([Day 100](day-100.md))과 동일합니다. `torch.stack` 배치
순전파가 한 장씩과 같은 답을 낸다는 확인이며, 이 대조도 보고서 재료입니다.

### Step 2. 베이스라인 측정 (3~4교시)

부하 측정기는 [Day 099](day-099.md)의 loadtest.py에 **진짜 업로드를 싣는** 수정판을 씁니다
(요청마다 `files=`로 검증 이미지 첨부 — multipart 파싱·디코드 비용까지 포함해야 실전 숫자입니다).

```
$ python loadup.py http://127.0.0.1:8103/predict 1 80 1,4,8
동시성  1 · 80요청 × 1장:  24.7 장/s · 요청 p50    40ms · p95    46ms
동시성  4 · 80요청 × 1장:  33.4 장/s · 요청 p50   111ms · p95   197ms
동시성  8 · 80요청 × 1장:  31.3 장/s · 요청 p50   253ms · p95   450ms
```

읽기: 포화점 ~33장/s. [Day 099](day-099.md)의 부하 재현용(48 req/s)보다 낮습니다 — 업로드
파싱과 JPEG 디코드가 요청마다 붙었기 때문입니다 (같은 모델도 **입출력 경로가 다르면 용량이
다릅니다**. 측정 대상은 언제나 실전 경로 전체).

### Step 3. 개선 1회와 재측정 (5~6교시)

같은 80장을 배치 8장 × 10요청으로:

```
$ python loadup.py http://127.0.0.1:8103/predict/batch 8 10 1,2
동시성  1 · 10요청 × 8장:  39.4 장/s · 요청 p50   202ms · p95   214ms
동시성  2 · 10요청 × 8장:  46.5 장/s · 요청 p50   336ms · p95   383ms
```

**성능 비교표** (오늘의 산출물 — `docs/report.md`에 측정 조건과 함께):

| 구성 | 처리량 | 요청 p50 | 장당 지연 |
|---|---|---|---|
| 단건 · 동시성 4 (최적) | 33.4장/s | 111ms | 111ms |
| 단건 · 동시성 8 (포화) | 31.3장/s | 253ms | 253ms |
| **배치 8 · 동시성 2** | **46.5장/s (+39%)** | 336ms | **42ms** |

> 측정 조건: 로컬 CPU 16코어 · 워커 1 · 측정기와 서버 동일 PC (구성 간 비교용 — [Day 099](day-099.md) ⑤)

결론 두 줄로 씁니다: "대량 작업은 배치로 +39%. 단건 실시간 경로는 동시성 4 이하에서
p95 200ms 이내 유지." — 숫자에 **용도별 처방**이 붙어야 보고서 문장이 됩니다.

### Step 4. /model/info 확장·실험 대장·커밋 (7~8교시)

- state에 `started_at`과 예측 카운터를 추가하고 /model/info에 노출 ([Day 096](day-096.md) 과제 ① — 카운터 증가 위치는 예측 성공 직후).
- 오늘의 측정·결정을 `docs/experiments.md`에 기록: 시도한 것 · 숫자 · 채택/기각 · 이유
  ([Day 065](../03-machine-learning/day-065.md)의 실험 대장이 서빙판으로 돌아온 것).

```powershell
git add app docs
git commit -m "MP3 Day3: 배치(+39%)·버전 정보 확장 — 전후 비교표 완성"
```

**오늘 퇴근 체크** — □ 배치 응답 = 단건 응답 (정확성 대조) □ 배치 상한·실패 정책이 명세에
□ 전후 비교표 (측정 조건 포함) □ /model/info에 가동 시각·처리 건수

## ⑤ 자주 하는 실수

### 개선을 여러 개 동시에 적용

**증상** — 배치+캐시+워커를 한꺼번에 넣고 "빨라졌다" — 무엇이 효과였는지 모름, 하나는 사실 역효과였는데 가려짐.
**원인** — [Day 057](../03-machine-learning/day-057.md)·[072](../03-machine-learning/day-072.md)의 1실험 1변경 규율을 성능 작업에서 잊음.
**해결** — 오늘의 개선은 1회. 표의 행마다 바뀐 것이 하나여야 비교표가 증거가 됩니다.

### 측정 조건을 바꿔 가며 비교

**증상** — 베이스라인은 어제 저녁(다른 프로세스 잔뜩), 개선 후는 오늘 아침 — +39%가 진짜인지 알 수 없음.
**원인** — 비교의 전제(동일 조건)를 놓침.
**해결** — 전후 측정은 같은 세션에서 연달아, 같은 n·같은 동시성으로. 표에 측정 조건을 명시하는 것까지가 측정입니다.

### 배치 상한 없이 출시

**증상** — 소비자가 500장을 한 요청에 — 메모리 스파이크, 다른 요청 전부 지연, 타임아웃.
**원인** — "많이 보낼수록 효율적"의 이면(지연·메모리·실패 반경)을 계약에 안 넣음.
**해결** — 상한 + 초과 시 413. 상한값은 지연 목표에서 역산해 명세에 적습니다.

### 부하 측정을 데모 엔드포인트로만 함

**증상** — 보고서엔 48 req/s인데 실제 업로드 경로는 33장/s — 시연 날 숫자가 어긋남.
**원인** — 파싱·디코드가 빠진 반쪽 경로를 측정.
**해결** — 측정은 소비자가 실제로 때리는 경로 전체로. 오늘 loadup처럼 진짜 파일을 실어 보냅니다.

### 평균 지연으로 보고

**증상** — "평균 60ms입니다" — 시연 질의응답에서 "p95는요?"에 침묵.
**원인** — [Day 098](day-098.md)의 분위수 감각이 보고서에 반영 안 됨.
**해결** — 처리량 + p50 + p95 세 개가 한 세트입니다. MP3 평가 기준에도 "p95 지연시간"이 명시돼 있습니다.

## ⑥ 확인 문제

**Q1.** 배치 상한 16의 근거를 "지연에서 역산"으로 설명해 보세요. 상한을 64로 올리면 무엇이
달라집니까?

<details>
<summary>답 보기</summary>

장당 배치 처리 ~25ms이므로 16장 요청의 지연은 ~0.4초 — "대량 작업 요청 하나가 0.5초 안에"라는
목표에서 역산한 값입니다. 64로 올리면 요청 하나가 ~1.6초를 점유해 그 뒤에 줄 선 단건 요청들의
p95가 급등하고, 메모리 사용과 실패 반경(한 장 불량 → 64장 재전송)도 4배가 됩니다. 상한은 성능
숫자가 아니라 **지연 목표와 실패 정책의 함수**입니다.

</details>

**Q2.** Step 2에서 같은 모델인데 부하 재현용 엔드포인트(48 req/s)와 실제 업로드 경로(33장/s)의
용량이 다르게 측정됐습니다. 이 차이가 주는 교훈은 무엇인가요?

<details>
<summary>답 보기</summary>

서버의 용량은 모델 순전파만이 아니라 **경로 전체**(multipart 파싱, JPEG 디코드, 전처리, 직렬화)의
합으로 결정됩니다. 데모 경로로 측정한 숫자로 용량 계획을 세우면 실전에서 30% 이상 부족할 수 있습니다.
"측정은 소비자가 때리는 그 경로로" — 그리고 병목 분석도 달라집니다(이 경우 개선 후보에 '디코드
최적화'가 새로 등장할 수 있습니다).

</details>

**Q3.** 실패 정책 "한 장이라도 불량이면 전체 4xx"의 장단점과, 반대 정책(부분 성공)을 채택해야
할 시나리오를 하나 들어 보세요.

<details>
<summary>답 보기</summary>

전체 거부는 계약이 단순하고(성공 = 전부 성공) 소비자의 오류 처리가 명확하지만, 대량 업로드에서 한 장
때문에 나머지를 재전송해야 합니다. 부분 성공(항목별 성공/실패 표시)은 "밤새 수만 장을 돌리는 백오피스
배치"처럼 재전송 비용이 크고 항목이 독립적인 시나리오에 적합합니다 — 대신 응답 스키마가 복잡해지고
소비자가 항목별 분기를 해야 하므로, 어느 쪽이든 명세에 선언하고 테스트로 고정해야 합니다.

</details>
