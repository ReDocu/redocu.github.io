## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `BEGIN` · `COMMIT` · `ROLLBACK` 으로 여러 명령을 **하나의 단위**로 묶을 수 있다.
- 동시 실행에서 생기는 **갱신 손실**을 재현하고 `FOR UPDATE` 등으로 막을 수 있다.
- 정규화(1NF~3NF) 원칙으로 테이블을 분해하고, **일부러 어길 때의 근거**를 댈 수 있다.
- 수집 데이터를 담을 스키마를 설계하고 **ERD로 표현**할 수 있다.

## ② 왜 필요한가

[Day 031](day-031.md)에서 파일 저장의 한계 ②로 **갱신 손실(lost update)** 을 꼽았습니다.

```
10:00  A: 파일 읽기 (1000행)
10:01                        B: 파일 읽기 (1000행)
10:02  A: +50행 저장 → 1050
10:03                        B: +20행 저장 → 1020  ★ A의 50행 증발
```

"DB를 쓰면 해결된다"고 했습니다. **절반만 맞습니다.**
DB는 **도구**를 줄 뿐이고, 그 도구를 안 쓰면 **DB에서도 똑같이 데이터가 사라집니다.**
오늘 그것을 직접 재현해 보고, 막는 법을 배웁니다.

후반부는 **모델링**입니다. [Day 038](day-038.md)에서 "테이블을 만드는 법"을 배웠지만,
**"어떤 테이블을 몇 개 만들 것인가"** 는 다루지 않았습니다.

```
❌ 주문 테이블 하나에 고객 이름 · 주소 · 상품명 3개 · 수량 3개를 전부 넣기
✅ customers / orders / order_items / products 로 나누기
```

왜 후자인지 설명할 수 있어야 [Day 040](day-040.md)에서 MP1 스키마를 확정할 수 있습니다.
그리고 이 스키마는 **MP2·MP3·최종 프로젝트까지** 따라다닙니다.

## ③ 개념 설명

### 트랜잭션 — "전부 되거나, 전부 안 되거나"

계좌 이체를 생각해 봅시다.

```
① A 계좌에서 10만 원 빼기
② B 계좌에 10만 원 넣기
```

①만 되고 ②가 실패하면 **10만 원이 증발**합니다.
**두 명령을 하나의 덩어리로 묶어, 중간 실패 시 통째로 되돌리는 장치**가 트랜잭션입니다.

```sql
BEGIN;                            -- 시작
UPDATE accounts SET bal = bal - 100000 WHERE id = 'A';
UPDATE accounts SET bal = bal + 100000 WHERE id = 'B';
COMMIT;                           -- 확정 (여기서 진짜 저장)
--  또는
ROLLBACK;                         -- 취소 (BEGIN 이전으로)
```

### ACID

| 글자 | 이름 | 뜻 |
|---|---|---|
| **A** | 원자성 (Atomicity) | 전부 되거나 전부 안 되거나 |
| **C** | 일관성 (Consistency) | 제약조건이 깨지지 않음 ([Day 038](day-038.md)) |
| **I** | 격리성 (Isolation) | 동시 실행이 서로 방해하지 않음 |
| **D** | 지속성 (Durability) | `COMMIT` 했으면 정전이 나도 남음 |

**오늘의 주제는 I(격리성)** 입니다. 나머지 셋은 DB가 알아서 해주지만, I는 **우리가 수준을 골라야** 합니다.

### psql의 자동 커밋

psql은 기본이 **자동 커밋**입니다. `BEGIN` 없이 친 명령은 **즉시 확정**됩니다.

```
shop=#     ← 자동 커밋 상태
shop=*#    ← 트랜잭션 진행 중 (BEGIN 이후, * 표시)
shop=!#    ← 트랜잭션 안에서 에러 발생 (ROLLBACK 해야 풀림)
```

**프롬프트의 `*` 와 `!` 를 보는 습관**이 사고를 막습니다.

> **운영 DB에서 `UPDATE`/`DELETE` 를 칠 때는 반드시 `BEGIN` 부터.**
> `WHERE` 를 빠뜨려 전체 행을 날려도 `ROLLBACK` 으로 살릴 수 있습니다.

### 동시성 문제 4종

두 트랜잭션이 같은 데이터를 만질 때 생기는 문제입니다.

| 문제 | 상황 |
|---|---|
| **Dirty Read** | 아직 커밋 안 된 남의 변경을 읽음 |
| **Non-repeatable Read** | 같은 행을 두 번 읽었는데 값이 달라짐 |
| **Phantom Read** | 같은 조건으로 두 번 읽었는데 행 개수가 달라짐 |
| **Lost Update** | 읽고 계산해서 쓰는 사이에 남의 갱신이 덮임 ★ |

**앞의 세 개는 격리 수준으로 막지만, 갱신 손실은 우리가 코드로 막아야 합니다.**

### 격리 수준

| 수준 | Dirty | Non-repeat | Phantom | 비고 |
|---|---|---|---|---|
| READ UNCOMMITTED | 허용 | 허용 | 허용 | PostgreSQL은 지원 안 함 |
| **READ COMMITTED** | 막음 | 허용 | 허용 | **PostgreSQL 기본값** |
| REPEATABLE READ | 막음 | 막음 | 막음 | PostgreSQL은 팬텀도 막음 |
| SERIALIZABLE | 막음 | 막음 | 막음 | 가장 안전 · 가장 느림 |

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

> **수준을 올릴수록 안전하지만, 충돌 시 트랜잭션이 실패(직렬화 오류)합니다.**
> `REPEATABLE READ` 이상을 쓰면 **애플리케이션이 재시도 로직을 갖춰야** 합니다.
> 그래서 대부분의 서비스는 기본값(`READ COMMITTED`)에 **명시적 잠금**을 조합합니다.

### 갱신 손실 막는 법 3가지

```sql
-- ① 계산을 DB에 맡긴다 (가장 간단하고 확실)
UPDATE products SET stock = stock - 5 WHERE product_id = 1;

-- ② 읽을 때 잠근다 (읽은 값으로 복잡한 판단이 필요할 때)
SELECT stock FROM products WHERE product_id = 1 FOR UPDATE;

-- ③ 버전 열로 검사한다 (낙관적 잠금)
UPDATE products SET stock = 110, version = version + 1
WHERE product_id = 1 AND version = 3;      -- 0행이 갱신되면 충돌 → 재시도
```

**①이 가능하면 언제나 ①입니다.** `SELECT` 로 읽어 파이썬에서 계산한 뒤 `UPDATE` 하는 코드는
[Day 041](day-041.md)부터 여러분이 매일 쓰게 될 형태인데, **그게 정확히 갱신 손실이 나는 형태**입니다.

### 데드락

```
A: products(1) 잠금 → products(2) 요청  ┐
B: products(2) 잠금 → products(1) 요청  ┘  서로 영원히 대기
```

PostgreSQL은 이것을 감지해 **한쪽을 강제 종료**합니다.

| 예방 | 방법 |
|---|---|
| **잠금 순서를 통일** | 항상 `product_id` 오름차순으로 갱신 |
| **트랜잭션을 짧게** | 사용자 입력 대기를 트랜잭션 안에 넣지 않기 |
| **재시도 준비** | 데드락은 완전히 막을 수 없음. 잡아서 다시 실행 |

### 정규화 — 테이블을 몇 개로 나눌 것인가

**한 곳에 몰아넣으면 생기는 문제(이상 현상)** 부터 봅시다.

```
order_sheet (나쁜 예)
order_id | customer_name | customer_city | product_names        | quantities | ordered_at
---------+---------------+---------------+----------------------+------------+-----------
    1    | 김민수        | 서울          | 무선마우스, USB허브  | 2, 1       | 2025-01-05
    3    | 김민수        | 서울          | 기계식키보드         | 1          | 2025-01-17
```

| 이상 현상 | 무슨 일 |
|---|---|
| **삽입 이상** | 주문한 적 없는 고객을 등록할 수 없음 (주문 행이 있어야 하므로) |
| **갱신 이상** | 김민수 님이 부산으로 이사 → **주문 행을 전부** 고쳐야 함. 하나 놓치면 같은 사람이 두 도시에 |
| **삭제 이상** | 마지막 주문을 지우면 **고객 정보까지 사라짐** |

정규화는 이 세 가지를 없애는 절차입니다.

| 단계 | 규칙 | 위 예에서 |
|---|---|---|
| **1NF** | 한 칸에 값 하나. 반복 그룹 금지 | `product_names = '무선마우스, USB허브'` ❌ → 행으로 분리 |
| **2NF** | 1NF + **기본키 전체**에 종속 (부분 종속 제거) | 키가 `(order_id, product_id)` 인데 `ordered_at` 은 `order_id` 에만 종속 → `orders` 분리 |
| **3NF** | 2NF + 비키 열이 **다른 비키 열에 종속되지 않음** (이행 종속 제거) | `customer_name`·`customer_city` 는 `customer_id` 에 종속 → `customers` 분리 |

결과가 우리가 쓰고 있는 `shop` 스키마입니다.

```
order_sheet (1개)  →  customers · orders · order_items · products (4개)
```

### 일부러 정규화를 어길 때 — 비정규화

**`order_items.unit_price` 가 그 예입니다.**

```
products.price       = 현재 정가              (바뀔 수 있음)
order_items.unit_price = 주문 당시 가격        (박제돼야 함) ← 중복처럼 보이지만 필수
```

3NF만 따지면 "가격은 `products` 에 있으니 중복"입니다. 하지만 **가격이 바뀌면 과거 매출이 변합니다.**
[Day 034](day-034.md) 확인 문제 3에서 본 문제입니다.

| 비정규화가 정당한 경우 | 예 |
|---|---|
| **시점 값을 보존해야 할 때** | 주문 당시 가격·주소·등급 |
| **집계 성능이 절실할 때** | 게시글의 `comment_count` (매번 세는 대신 저장) |
| **분석 전용 테이블** | 데이터 웨어하우스의 스타 스키마 |

> **원칙 — 먼저 3NF로 설계하고, 근거가 있을 때만 되돌린다.**
> "귀찮아서 안 나눴다"와 "시점 값 보존을 위해 일부러 중복했다"는 완전히 다릅니다.
> **설계 문서에 그 이유를 적어 두세요.** [Day 040](day-040.md) 스키마 리뷰의 항목입니다.

### ERD 표기법 (까마귀발)

```
customers ─────┼──○<  orders          "고객 1명은 주문 0건 이상"
               │
  기호        의미
  ─┼─         정확히 1
  ─○─         0 또는 1
  ─<          여러 개 (까마귀발)
  ─○<         0개 이상
  ─┼<         1개 이상
```

```
┌───────────┐         ┌────────┐         ┌─────────────┐        ┌──────────┐
│ customers │─┼───○< │ orders │─┼───┼< │ order_items │ >○──┼─│ products │
│ ───────── │         │ ────── │         │ ─────────── │        │ ──────── │
│ PK cust_id│         │PK ord_id│        │PK item_id   │        │PK prod_id│
│    name   │         │FK cust_id│       │FK order_id  │        │   name   │
│    email  │         │  ordered_at│     │FK product_id│        │  category│
│    city   │         │  status  │       │   quantity  │        │   price  │
│    grade  │         └────────┘         │  unit_price │        │   stock  │
└───────────┘                            └─────────────┘        └──────────┘
```

**읽는 법** — "고객 1명은 주문을 **0건 이상**", "주문 1건은 상세를 **1줄 이상**", "상품 1개는 상세에 **0번 이상**".
`0 이상`인지 `1 이상`인지가 곧 `LEFT JOIN` 을 써야 하는지의 답입니다 ([Day 034](day-034.md)).

### 설계 절차 5단계

```
① 명사 뽑기        문제 설명에서 명사를 전부 적는다 → 엔티티 후보
② 관계 정하기      "A 하나에 B가 몇 개?" → 1:1 / 1:N / N:M
③ N:M 은 쪼갠다    주문 ↔ 상품 (N:M) → order_items 라는 연결 테이블
④ 속성 배치        각 속성이 "무엇 하나에 대한 사실인가"로 소속을 정함
⑤ 키와 제약        PK · FK · UNIQUE(중복 방지) · CHECK · NOT NULL
```

**④가 3NF의 실전 버전입니다.** "도시는 고객에 대한 사실이지 주문에 대한 사실이 아니다" — 그래서 `customers` 에 갑니다.

### Step 1. `BEGIN` · `ROLLBACK` 체험

```
shop=# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   120
(1 row)

shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = 0 WHERE product_id = 1;
UPDATE 1
shop=*# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
     0
(1 row)

shop=*# ROLLBACK;
ROLLBACK
shop=# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   120
(1 row)
```

**프롬프트가 `shop=#` → `shop=*#` → `shop=#` 으로 바뀐 것**을 확인하세요.
`*` 가 붙어 있는 동안은 **아직 아무것도 확정되지 않았습니다.**

**`WHERE` 를 빠뜨렸을 때 살아나는 방법**도 연습해 둡니다.

```
shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = 0;
UPDATE 12
shop=*# SELECT COUNT(*) FROM products WHERE stock = 0;
 count
-------
    12
(1 row)

shop=*# ROLLBACK;
ROLLBACK
```

**`UPDATE 12` 를 보고 "어? 1이어야 하는데"** 하고 알아챌 수 있습니다.
`BEGIN` 없이 쳤다면 12행이 이미 날아갔습니다.

에러가 나면 트랜잭션 전체가 중단 상태가 됩니다.

```
shop=# BEGIN;
BEGIN
shop=*# INSERT INTO orders (customer_id, ordered_at, status) VALUES (999, '2025-07-01', 'paid');
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".
shop=!# SELECT COUNT(*) FROM orders;
ERROR:  current transaction is aborted, commands ignored until end of transaction block
shop=!# ROLLBACK;
ROLLBACK
shop=#
```

**`shop=!#`** 상태에서는 아무 명령도 안 먹습니다. `ROLLBACK` 으로 빠져나와야 합니다.
일부만 되돌리고 싶다면 `SAVEPOINT` 를 씁니다.

```sql
BEGIN;
INSERT INTO ... ;
SAVEPOINT sp1;
INSERT INTO ... ;          -- 실패해도
ROLLBACK TO SAVEPOINT sp1; -- 여기까지만 되돌림
COMMIT;                    -- 앞의 INSERT 는 살아남음
```

### Step 2. 갱신 손실 재현하기 ★★

**창 A와 창 B를 번갈아 가며** 아래 순서대로 정확히 입력하세요.
"재고 120개에서 A가 10개, B가 5개를 빼면 105개가 되어야 합니다."

**① 창 A**

```
shop=# BEGIN;
BEGIN
shop=*# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   120
(1 row)
```

**② 창 B** (A는 아직 커밋 안 함)

```
shop=# BEGIN;
BEGIN
shop=*# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   120
(1 row)
```

**③ 창 A — 파이썬에서 `120 - 10 = 110` 을 계산했다고 치고**

```
shop=*# UPDATE products SET stock = 110 WHERE product_id = 1;
UPDATE 1
shop=*# COMMIT;
COMMIT
```

**④ 창 B — `120 - 5 = 115` 를 계산했다고 치고**

```
shop=*# UPDATE products SET stock = 115 WHERE product_id = 1;
UPDATE 1
shop=*# COMMIT;
COMMIT
```

**⑤ 결과 확인**

```
shop=# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   115
(1 row)
```

**105가 아니라 115입니다. A가 뺀 10개가 사라졌습니다.**

에러도 경고도 없었습니다. 두 트랜잭션 다 `COMMIT` 에 성공했습니다.
**DB를 쓴다고 자동으로 안전해지지 않는다**는 것이 오늘의 핵심입니다.

원인은 "**읽고 → 계산하고 → 쓰기**" 사이에 남이 끼어들었기 때문입니다.
[Day 031](day-031.md)의 파일 갱신 손실과 **정확히 같은 구조**입니다.

### Step 3. 방법 ① — 계산을 DB에 맡기기

재고를 120으로 되돌리고 다시 해 봅니다.

```
shop=# UPDATE products SET stock = 120 WHERE product_id = 1;
UPDATE 1
```

**① 창 A**

```
shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = stock - 10 WHERE product_id = 1;
UPDATE 1
```

**② 창 B** — 여기서 **화면이 멈춥니다.**

```
shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = stock - 5 WHERE product_id = 1;
_
```

**A가 그 행을 잠갔기 때문에 B는 기다립니다.** 이것이 **행 수준 잠금(row lock)** 입니다.

**③ 창 A — 커밋**

```
shop=*# COMMIT;
COMMIT
```

**④ 창 B — 그 순간 대기가 풀립니다**

```
UPDATE 1
shop=*# COMMIT;
COMMIT
```

**⑤ 결과**

```
shop=# SELECT stock FROM products WHERE product_id = 1;
 stock
-------
   105
(1 row)
```

**105입니다.** B가 기다렸다가 **A가 반영한 110에서** 5를 뺐기 때문입니다.

> **`SET stock = stock - 5` 와 `SET stock = 115` 의 차이가 이것입니다.**
> 앞은 "현재 값에서 5를 빼라"(DB가 잠금 안에서 계산),
> 뒤는 "115로 만들어라"(내가 이미 계산해 온 값 — 낡았을 수 있음).

### Step 4. 방법 ② — `FOR UPDATE` 로 읽을 때 잠그기

읽은 값으로 조건 판단이 필요할 때 씁니다. (예: "재고가 충분하면 차감")

재고를 120으로 되돌립니다.

```
shop=# UPDATE products SET stock = 120 WHERE product_id = 1;
UPDATE 1
```

**① 창 A**

```
shop=# BEGIN;
BEGIN
shop=*# SELECT stock FROM products WHERE product_id = 1 FOR UPDATE;
 stock
-------
   120
(1 row)
```

**② 창 B** — `SELECT` 인데도 **멈춥니다.**

```
shop=# BEGIN;
BEGIN
shop=*# SELECT stock FROM products WHERE product_id = 1 FOR UPDATE;
_
```

**③ 창 A**

```
shop=*# UPDATE products SET stock = 110 WHERE product_id = 1;
UPDATE 1
shop=*# COMMIT;
COMMIT
```

**④ 창 B — 대기가 풀리고, 최신 값이 보입니다**

```
 stock
-------
   110
(1 row)

shop=*# UPDATE products SET stock = 105 WHERE product_id = 1;
UPDATE 1
shop=*# COMMIT;
COMMIT
```

**B가 본 값이 120이 아니라 110입니다.** 그래서 105라는 올바른 결과를 계산할 수 있었습니다.

> **`FOR UPDATE` 는 "이 행을 곧 고칠 거니까 잡아 둬라"** 는 선언입니다.
> [Day 041](day-041.md)에서 파이썬으로 "조회 → 판단 → 수정"을 할 때 이것이 필요합니다.
> 기다리기 싫다면 `FOR UPDATE NOWAIT`(즉시 에러) 이나 `SKIP LOCKED`(잠긴 행 건너뛰기 — 작업 큐에 유용)를 씁니다.

### Step 5. 데드락 재현

**① 창 A**

```
shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = stock - 1 WHERE product_id = 1;
UPDATE 1
```

**② 창 B**

```
shop=# BEGIN;
BEGIN
shop=*# UPDATE products SET stock = stock - 1 WHERE product_id = 2;
UPDATE 1
```

**③ 창 A — 2번을 요청 (B가 잡고 있어 대기)**

```
shop=*# UPDATE products SET stock = stock - 1 WHERE product_id = 2;
_
```

**④ 창 B — 1번을 요청 → 데드락**

```
shop=*# UPDATE products SET stock = stock - 1 WHERE product_id = 1;
ERROR:  deadlock detected
DETAIL:  Process 412 waits for ShareLock on transaction 1053; blocked by process 388.
        Process 388 waits for ShareLock on transaction 1054; blocked by process 412.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,13) in relation "products"
```

**PostgreSQL이 감지해 B를 강제 종료했습니다.** A는 그 순간 대기가 풀려 정상 진행합니다.

```
-- 창 A
UPDATE 1
shop=*# ROLLBACK;
ROLLBACK

-- 창 B
shop=!# ROLLBACK;
ROLLBACK
```

**예방** — 두 창 모두 `product_id` **오름차순으로** 갱신했다면 데드락이 나지 않습니다.
`1 → 2` 와 `1 → 2` 는 뒤에 온 쪽이 그냥 기다릴 뿐입니다.

> **여러 행을 갱신할 때는 항상 같은 순서로.** 실무 규칙입니다.
> 그래도 데드락은 완전히 막을 수 없으므로, [Day 043](day-043.md)의 파이프라인에는 **재시도 로직**을 넣습니다.

### Step 6. 정규화 실습 — 나쁜 테이블 고치기

정규화 전 테이블을 만들어 봅니다.

```
shop=# CREATE TABLE order_sheet_bad (
shop(#     order_id      integer,
shop(#     customer_name text,
shop(#     customer_city text,
shop(#     product_names text,
shop(#     quantities    text,
shop(#     ordered_at    date
shop(# );
CREATE TABLE

shop=# INSERT INTO order_sheet_bad VALUES
shop-# (1, '김민수', '서울', '무선마우스, USB허브', '2, 1', '2025-01-05'),
shop-# (3, '김민수', '서울', '기계식키보드',        '1',    '2025-01-17'),
shop-# (2, '이서연', '서울', 'A4용지500매, 형광펜세트', '3, 2', '2025-01-09');
INSERT 0 3
```

이 테이블로 **"무선마우스가 몇 개 팔렸나"** 를 구해 보세요.

```
shop=# SELECT SUM(quantities::integer) FROM order_sheet_bad WHERE product_names LIKE '%무선마우스%';
ERROR:  invalid input syntax for type integer: "2, 1"
```

**불가능합니다.** 문자열을 쪼개서 짝을 맞춰야 하는데, 그건 SQL이 할 일이 아닙니다.

| 단계 | 위반 | 고침 |
|---|---|---|
| **1NF** | `'무선마우스, USB허브'` — 한 칸에 값 2개 | 상품마다 **행을 분리** |
| **2NF** | 키가 `(order_id, product)` 인데 `ordered_at` 은 `order_id` 에만 종속 | `orders` 테이블 분리 |
| **3NF** | `customer_city` 가 `customer_name` 에 종속 (이행 종속) | `customers` 테이블 분리 |

**1NF 적용** — 행으로 펼칩니다.

```
order_id | customer_name | customer_city | product      | quantity | ordered_at
---------+---------------+---------------+--------------+----------+-----------
    1    | 김민수        | 서울          | 무선마우스   |    2     | 2025-01-05
    1    | 김민수        | 서울          | USB허브      |    1     | 2025-01-05
    3    | 김민수        | 서울          | 기계식키보드 |    1     | 2025-01-17
```

이제 집계는 되지만, **김민수·서울이 계속 반복**됩니다. 이사하면 3행을 다 고쳐야 합니다.

**2NF·3NF 적용** — 우리가 쓰는 `shop` 스키마가 됩니다.

```
customers(customer_id, name, city, ...)          ← 고객에 대한 사실
orders(order_id, customer_id, ordered_at, ...)   ← 주문에 대한 사실
order_items(order_id, product_id, quantity, unit_price)  ← 주문 한 줄에 대한 사실
products(product_id, name, category, price)      ← 상품에 대한 사실
```

**"이 속성은 무엇 하나에 대한 사실인가"** — 이 질문 하나로 소속이 정해집니다.

실습 테이블을 지웁니다.

```
shop=# DROP TABLE order_sheet_bad;
DROP TABLE
```

### Step 7. 수집 데이터용 스키마 설계

[Day 038](day-038.md) 과제에서 만든 설계를 정리합니다. `datapipe` 가 수집하는 대기질 데이터입니다.

**① 명사 뽑기** — 측정소, 측정값, 지역, 오염물질, 수집 실행
**② 관계** — 측정소 1개 : 측정값 N개 / 지역 1개 : 측정소 N개
**③ N:M 없음**
**④ 속성 배치**

| 속성 | 무엇에 대한 사실? | 소속 |
|---|---|---|
| 측정소명, 위도, 경도, 주소 | **측정소** | `station` |
| PM10, PM2.5, 측정시각 | **측정 한 건** | `measurement` |
| 수집 시작·종료 시각, 성공 여부, 행 수 | **수집 실행 한 번** | `ingest_run` |

**⑤ 키와 제약**

```sql
CREATE TABLE station (
    station_id  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        text    NOT NULL UNIQUE,        -- 측정소명은 유일
    sido        text    NOT NULL,
    latitude    numeric(9,6),
    longitude   numeric(9,6),
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE measurement (
    measurement_id bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    station_id     integer NOT NULL REFERENCES station(station_id),
    measured_at    timestamptz NOT NULL,
    pm10           integer CHECK (pm10  BETWEEN 0 AND 2000),
    pm25           integer CHECK (pm25  BETWEEN 0 AND 2000),
    o3             numeric(5,3) CHECK (o3 >= 0),
    khai           integer CHECK (khai BETWEEN 0 AND 600),
    ingested_at    timestamptz NOT NULL DEFAULT now(),

    -- ★ 멱등성의 핵심: 같은 측정소·같은 시각 데이터는 하나뿐
    UNIQUE (station_id, measured_at)
);

CREATE INDEX idx_measurement_station_time ON measurement (station_id, measured_at);
CREATE INDEX idx_measurement_time         ON measurement (measured_at);

CREATE TABLE ingest_run (
    run_id       bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    source       text    NOT NULL,
    started_at   timestamptz NOT NULL DEFAULT now(),
    finished_at  timestamptz,
    status       text    NOT NULL DEFAULT 'running'
                 CHECK (status IN ('running','success','failed')),
    rows_read    integer NOT NULL DEFAULT 0,
    rows_written integer NOT NULL DEFAULT 0,
    error_message text
);
```

**설계 결정 세 가지를 기억하세요.**

| 결정 | 이유 |
|---|---|
| `UNIQUE (station_id, measured_at)` | **같은 배치를 두 번 돌려도 중복되지 않음** → [Day 042](day-042.md)의 `ON CONFLICT` |
| `pm10` 이 **NULL 허용** | 센서 고장으로 값이 없을 수 있음. **0과 "없음"은 다름** ([Day 032](day-032.md)) |
| `ingest_run` 테이블 | 언제 무엇을 몇 행 넣었는지 기록 → [Day 045](day-045.md)의 운영 |

`o3` 를 `numeric(5,3)` 으로 한 것도 의도가 있습니다. 오존은 `0.045` 처럼 소수 셋째 자리까지 쓰는데,
`float` 로 저장하면 합계·평균에서 오차가 누적됩니다 ([Day 038](day-038.md)).

## ⑤ 자주 하는 실수

### `current transaction is aborted, commands ignored until end of transaction block`

```
shop=!# SELECT 1;
ERROR:  current transaction is aborted, commands ignored until end of transaction block
```

**원인** — 트랜잭션 안에서 에러가 나면 **그 트랜잭션 전체가 중단 상태**가 됩니다.
**해결** — `ROLLBACK;`(전부 취소) 또는 `ROLLBACK TO SAVEPOINT sp1;`(일부만).
**프롬프트의 `!` 를 보면 바로 알 수 있습니다.**

### `COMMIT` 을 안 하고 창을 닫음

**증상** — 분명히 `UPDATE 1` 이 나왔는데 다른 창에서는 안 바뀌어 있습니다.
**원인** — `BEGIN` 후 `COMMIT` 을 안 했습니다. 세션이 끊기면 **자동 롤백**됩니다.
**해결** — `COMMIT;` 을 치는 습관. 프롬프트에 `*` 가 있으면 아직 끝나지 않은 것입니다.

### 다른 사람의 쿼리가 멈춰 있습니다

**원인** — 누군가 `BEGIN` 하고 `COMMIT` 을 안 한 채 자리를 비웠습니다. 그 행이 잠겨 있습니다.
**진단**

```sql
SELECT pid, state, wait_event_type, LEFT(query, 60) AS query
FROM pg_stat_activity
WHERE datname = 'shop' AND state <> 'idle';
```

**해결** — 원인 세션을 찾아 커밋하게 하거나, 최후에는 `SELECT pg_terminate_backend(pid);`
**운영 DB에서 함부로 쓰지 마세요.** 남의 트랜잭션을 강제 종료하는 명령입니다.

### 갱신 손실 — 에러 없이 값이 틀림 ★

```python
# ❌ Day 041 부터 여러분이 쓸 코드에서 가장 흔한 형태
stock = query("SELECT stock FROM products WHERE product_id = %s", (1,))
query("UPDATE products SET stock = %s WHERE product_id = %s", (stock - 5, 1))
```

**원인** — 읽고 쓰는 사이에 남이 끼어듭니다.
**해결** — 계산을 DB로 옮기거나, `FOR UPDATE` 로 잠급니다.

```python
# ✅
query("UPDATE products SET stock = stock - %s WHERE product_id = %s", (5, 1))
```

**증상이 안 보이는 게 문제입니다.** 테스트는 통과하고, 운영에서 동시 접속이 늘 때만 어긋납니다.

### 트랜잭션 안에서 오래 기다림

```python
conn.begin()
row = fetch_one("SELECT ... FOR UPDATE")
answer = input("승인하시겠습니까? ")     # ★ 사람을 기다리는 동안 행이 잠겨 있음
conn.commit()
```

**원인** — 트랜잭션 안에 **사람 입력·외부 API 호출** 같은 느린 작업이 들어갔습니다.
그동안 다른 모든 요청이 대기합니다.
**해결** — **트랜잭션은 짧게.** 느린 작업은 트랜잭션 밖에서 하고, 마지막에 짧게 열어 쓰기만 합니다.

### 정규화를 과하게 함

**증상** — 테이블이 20개가 되고, 간단한 화면 하나 그리는 데 조인이 8개 필요합니다.
**해결** — 정규화는 **목적이 아니라 수단**입니다. 이상 현상(삽입·갱신·삭제)이 실제로 생기지 않는다면 나눌 이유가 없습니다.

| 나눠야 하는 신호 | 안 나눠도 되는 경우 |
|---|---|
| 같은 값이 여러 행에 반복됨 | 값이 1:1로 딱 붙어 다님 |
| 한 곳을 고치려면 여러 행을 고쳐야 함 | 시점 값을 보존해야 함 (`unit_price`) |
| 한 칸에 여러 값이 들어감 | — |

### `TRUNCATE` 와 `DELETE` 를 혼동

```sql
DELETE FROM measurement;      -- 행마다 삭제. 느림. 롤백 가능. 트리거 동작
TRUNCATE measurement;         -- 통째로 비움. 매우 빠름. FK가 있으면 거부
```

`TRUNCATE` 는 PostgreSQL에서 **트랜잭션 안에서 롤백 가능**하지만, 다른 DBMS에서는 아닙니다.
그리고 **자식 테이블이 참조 중이면 거부**됩니다 (`TRUNCATE ... CASCADE` 는 자식까지 비움 — 위험).

## ⑥ 확인 문제

**1.** Step 2에서 두 트랜잭션이 모두 성공했는데 결과가 틀렸습니다. 에러도 나지 않았습니다. ACID 중 어느 성질과 관련이 있으며, 왜 DB가 막아 주지 못했나요?

<details>
<summary>답 보기</summary>

**격리성(Isolation)** 과 관련이 있습니다. 그런데 **PostgreSQL 기본 격리 수준(`READ COMMITTED`)이 갱신 손실을 막아 주지 않기 때문**입니다.

**DB가 보기에는 아무 문제가 없습니다.**

```
A: UPDATE products SET stock = 110 WHERE product_id = 1;   ← 유효한 명령
B: UPDATE products SET stock = 115 WHERE product_id = 1;   ← 역시 유효한 명령
```

DB는 "B가 115라고 했으니 115"로 처리했을 뿐입니다.
**"B가 계산에 쓴 120이 이미 낡은 값이었다"** 는 사실은 **애플리케이션만 압니다.**

**막는 방법**

| 방법 | 코드 |
|---|---|
| ① 계산을 DB로 | `SET stock = stock - 5` |
| ② 읽을 때 잠금 | `SELECT ... FOR UPDATE` |
| ③ 낙관적 잠금 | `WHERE version = 3` → 0행이면 재시도 |
| ④ 격리 수준 상향 | `REPEATABLE READ` → B가 **에러로 실패** (재시도 필요) |

④를 쓰면 B가 이런 에러를 받습니다.

```
ERROR:  could not serialize access due to concurrent update
```

**"조용히 틀리는 것보다 시끄럽게 실패하는 것이 낫다"** 는 원칙에서는 ④가 좋습니다.
다만 재시도 로직이 필수라, 실무에서는 ①이나 ②를 먼저 씁니다.

**MLOps 맥락** — [Day 043](day-043.md)의 ETL이 여러 개 동시에 돌면 이 문제가 그대로 나옵니다.
"어디까지 처리했는지"를 기록하는 상태 테이블이 특히 위험합니다.
</details>

```sql
CREATE TABLE model_run (
    run_id       integer PRIMARY KEY,
    model_name   text,
    model_author text,
    model_authors_email text,
    dataset_name text,
    dataset_rows integer,
    metrics      text,     -- 'accuracy=0.91, f1=0.88, auc=0.94'
    run_at       timestamptz
);
```

<details>
<summary>답 보기</summary>

**1NF와 3NF를 위반합니다.**

**1NF 위반** — `metrics` 한 칸에 지표 3개가 들어 있습니다.
"AUC가 0.9 이상인 실행"을 찾으려면 문자열을 파싱해야 하고, 지표가 하나 늘면 형식이 깨집니다.

**3NF 위반 (이행 종속)** — `model_authors_email` 은 `run_id` 가 아니라 **`model_author` 에 종속**됩니다.
`dataset_rows` 도 `run_id` 가 아니라 **`dataset_name` 에 종속**됩니다.
같은 저자가 100번 실험하면 이메일이 100번 저장되고, 이메일이 바뀌면 100행을 고쳐야 합니다.

**최종 스키마**

```sql
CREATE TABLE author (
    author_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      text NOT NULL,
    email     text NOT NULL UNIQUE
);

CREATE TABLE model (
    model_id  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      text NOT NULL UNIQUE,
    author_id integer NOT NULL REFERENCES author(author_id)
);

CREATE TABLE dataset (
    dataset_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text NOT NULL UNIQUE,
    row_count  integer NOT NULL CHECK (row_count >= 0)
);

CREATE TABLE model_run (
    run_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    model_id   integer NOT NULL REFERENCES model(model_id),
    dataset_id integer NOT NULL REFERENCES dataset(dataset_id),
    run_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE run_metric (                      -- 1NF: 지표마다 한 행
    run_id      bigint  NOT NULL REFERENCES model_run(run_id) ON DELETE CASCADE,
    metric_name text    NOT NULL,
    metric_value numeric NOT NULL,
    PRIMARY KEY (run_id, metric_name)          -- 같은 실행에 같은 지표는 하나
);

CREATE INDEX idx_model_run_model  ON model_run  (model_id);
CREATE INDEX idx_model_run_at     ON model_run  (run_at);
CREATE INDEX idx_run_metric_name  ON run_metric (metric_name, metric_value);
```

이제 "AUC 0.9 이상인 실행"이 SQL 한 줄입니다.

```sql
SELECT r.run_id, m.name, rm.metric_value
FROM run_metric rm
JOIN model_run r ON rm.run_id = r.run_id
JOIN model m     ON r.model_id = m.model_id
WHERE rm.metric_name = 'auc' AND rm.metric_value >= 0.9;
```

> **이 스키마가 실제로 MLflow가 쓰는 구조와 거의 같습니다.** W13([Day 061](../03-machine-learning/README.md) 부근)에서
> 실험 관리 도구를 배울 때 "왜 이렇게 생겼는지" 오늘 설계해 본 덕분에 이해할 수 있습니다.
>
> `run_metric` 에 `ON DELETE CASCADE` 를 쓴 것은 **지표가 실행에 완전히 종속**되기 때문입니다.
> 실행을 지우면 그 지표는 존재 의미가 없습니다. 반대로 `model_run` 의 FK에는 `CASCADE` 를 쓰지 않았습니다.
> 모델을 지운다고 실험 기록이 사라지면 안 되니까요.
</details>

**3.** [Day 038](day-038.md)에서 만든 `measurement` 테이블에 `UNIQUE (station_id, measured_at)` 을 건 이유는 무엇인가요? 이 제약이 없으면 [Day 043](day-043.md)의 파이프라인에서 어떤 일이 생기나요?

<details>
<summary>답 보기</summary>

**이유 — 같은 측정소의 같은 시각 데이터는 논리적으로 하나뿐이기 때문입니다.**
"2025-06-01 14:00 종로구 측정소의 PM10"은 세상에 하나의 값만 존재합니다.

**제약이 없으면 — 파이프라인을 두 번 돌릴 때 데이터가 두 배가 됩니다.**

```
1차 실행 (10:00)  →  measurement 에 2,400행
네트워크 오류로 재실행 (10:05)  →  같은 2,400행이 또 들어감  →  총 4,800행

이후 모든 집계가 틀립니다:
  일평균 PM10  →  같은 값이 두 번 들어가므로 평균 자체는 같지만
  측정 횟수    →  2배
  COUNT(*)     →  2배
  시계열 그래프 →  같은 시각에 점이 두 개
```

**에러가 안 납니다.** 그리고 원인을 찾기까지 몇 주가 걸립니다.

**제약이 있으면 — 두 번째 실행이 거부됩니다.**

```
ERROR:  duplicate key value violates unique constraint "measurement_station_id_measured_at_key"
DETAIL:  Key (station_id, measured_at)=(1, 2025-06-01 14:00:00+09) already exists.
```

거부만 되면 배치가 실패하니, [Day 042](day-042.md)에서 **"이미 있으면 무시하거나 갱신"** 으로 바꿉니다.

```sql
INSERT INTO measurement (station_id, measured_at, pm10, ...)
VALUES (...)
ON CONFLICT (station_id, measured_at) DO NOTHING;      -- 또는 DO UPDATE SET ...
```

**이 한 줄이 성립하려면 `UNIQUE` 제약이 반드시 있어야 합니다.**
`ON CONFLICT` 는 "어떤 제약과 충돌했을 때"인지를 지정해야 하기 때문입니다.

> **정리 — `UNIQUE` 제약은 "중복 방지"이자 "멱등성의 전제"입니다.**
> 파이프라인을 설계할 때 가장 먼저 정해야 할 것이 **"무엇이 같으면 같은 데이터인가"**(자연키)입니다.
> 이것을 **멱등 키(idempotency key)** 라고 부르며, [Day 043](day-043.md)의 핵심 개념입니다.
</details>

## 오늘의 정리

| 구문 | 하는 일 |
|---|---|
| `BEGIN` · `COMMIT` · `ROLLBACK` | 트랜잭션 시작 · 확정 · 취소 |
| `SAVEPOINT sp` · `ROLLBACK TO sp` | 부분 취소 |
| `SELECT ... FOR UPDATE` | 읽으면서 행 잠금 |
| `FOR UPDATE NOWAIT` · `SKIP LOCKED` | 안 기다림 · 잠긴 행 건너뜀 |
| `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ` | 격리 수준 상향 |
| `SELECT * FROM pg_stat_activity` | 누가 무엇을 하고 있는지 |

| 개념 | 요약 |
|---|---|
| ACID | 원자성 · 일관성 · **격리성** · 지속성 |
| 갱신 손실 | **기본 격리 수준은 막아 주지 않음** → 코드로 막아야 함 |
| 잠금 순서 | 항상 같은 순서로 → 데드락 예방 |
| 1NF | 한 칸에 값 하나 |
| 2NF | 기본키 **전체**에 종속 |
| 3NF | 비키 열이 다른 비키 열에 종속되지 않음 |
| 비정규화 | **근거가 있을 때만** (시점 값 보존 · 집계 성능) |

| 프롬프트 | 상태 |
|---|---|
| `shop=#` | 자동 커밋 |
| `shop=*#` | **트랜잭션 진행 중** (아직 확정 안 됨) |
| `shop=!#` | **에러로 중단됨** (`ROLLBACK` 필요) |

**오늘의 습관** — 운영 DB에서 `UPDATE`/`DELETE` 를 칠 때는 **무조건 `BEGIN` 부터**.
`UPDATE 1` 이 나올 줄 알았는데 `UPDATE 4823` 이 나오면 그때 `ROLLBACK` 하면 됩니다.
이 습관 하나가 경력 전체에서 몇 번은 여러분을 구합니다.

**과제 — MP1 스키마 초안**

내일 [Day 040](day-040.md)에서 이 초안을 **리뷰하고 확정**합니다.

1. `sql/mp1_schema.sql` — MP1에서 쓸 스키마 전체
   - 테이블 3개 이상 (원천 데이터 + 메타/운영 테이블 포함)
   - 모든 열에 타입 · `NOT NULL` · `DEFAULT` 판단
   - **멱등 키를 `UNIQUE` 로** 명시 (가장 중요)
   - FK와 그 인덱스 · `CHECK` 제약
2. `docs/erd.md` — ERD (ASCII 또는 <https://dbdiagram.io> 이미지)
   - 관계마다 `1:N` · `0 이상`/`1 이상` 표기
3. `docs/schema_decisions.md` — **설계 판단 기록** (3개 이상)
   - "왜 이 열을 NULL 허용으로 했는가"
   - "왜 이 값을 중복 저장(비정규화)했는가"
   - "멱등 키를 무엇으로 정했고, 왜 그것이 유일한가"

**3번이 내일 리뷰의 핵심 자료입니다.** 스키마는 고칠 수 있지만, **판단의 근거가 없으면 고칠 수도 없습니다.**
