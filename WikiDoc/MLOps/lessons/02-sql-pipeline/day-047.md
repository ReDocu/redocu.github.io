## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 선정한 데이터에 맞게 **수집기를 설정하고 페이징·재시도**를 확인할 수 있다.
- **실제 데이터를 관찰해** 검증 규칙을 도출하고 임계치를 정할 수 있다.
- 수집 → 검증 → 적재가 **명령 한 줄로 재현되는** 파이프라인을 완성할 수 있다.
- 품질 문제를 발견하고 **보정할지 격리할지 판단**할 수 있다.

## ② 왜 필요한가

**오늘 평가 배점 30점(파이프라인 재현성)이 결정됩니다.**

어제 데이터가 들어가는 것까지 확인했습니다. 하지만 "들어간다"와 "완성됐다"는 다릅니다.

| 어제 상태 | 오늘 목표 |
|---|---|
| 한 번 실행해 봤다 | **세 번 실행해도 행 수가 같다** |
| 값이 들어갔다 | **불량 값이 걸러지고 격리된다** |
| 내 PC에서 됐다 | **새 폴더에서 clone 해도 된다** |
| 잘 된 것 같다 | **`datapipe status` 로 숫자를 보여줄 수 있다** |

그리고 오늘 하루는 **데이터를 들여다보는 시간**이기도 합니다.
검증 규칙은 상상해서 만드는 것이 아니라 **실제 값을 보고 만드는 것**입니다.

### 검증 규칙은 데이터를 보고 만든다 ★

[Day 044](day-044.md)에서 규칙 만드는 법을 배웠습니다. 그런데 **"pm10 범위를 0~2000으로"** 같은 숫자는 어디서 나올까요?

```
① 실제 값의 분포를 본다        MIN · MAX · 백분위수
② 도메인 기준을 찾는다          환경부 대기질 기준표
③ 둘을 비교해 경계를 정한다     "실제 최댓값 340, 기준상 매우나쁨 151+ → 상한 2000은 넉넉"
④ 근거를 주석에 적는다          숫자만 있으면 나중에 못 고침
```

**분포를 보는 쿼리**

```sql
SELECT COUNT(*)                                              AS 전체,
       COUNT(pm10)                                           AS 값있음,
       MIN(pm10), MAX(pm10),
       ROUND(AVG(pm10), 1)                                   AS 평균,
       PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY pm10)    AS 중앙값,
       PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY pm10)    AS p99
FROM measurement;
```

**`p99` 와 `MAX` 의 차이가 크면** 극단값이 있다는 뜻입니다. 그게 진짜인지 오류인지 확인해야 합니다.

### 보정할까 격리할까

불량 값을 발견했을 때의 선택입니다.

| 상황 | 판단 | 이유 |
|---|---|---|
| `'-'`, `''` → `NULL` | **보정** | 표기법의 차이일 뿐. 의미는 "값 없음" |
| `"1,234"` → `1234` | **보정** | 천 단위 구분자. 명확한 규칙 |
| 앞뒤 공백 제거 | **보정** | 무해 |
| `9999` (센서 고장) | **격리** | 진짜 값을 알 수 없음 |
| `pm25 > pm10` | **격리** | 어느 쪽이 틀렸는지 모름 |
| 미래 시각 | **격리** | 원인 파악 필요 |

> **원칙 — "값을 되살릴 명확한 규칙이 있으면 보정, 없으면 격리."**
> 추측으로 값을 채우면 **데이터가 조용히 거짓이 됩니다.**
> 특히 **평균으로 결측을 채우는 것**은 이 단계에서 하지 마세요. 그건 모델링 단계의 선택입니다 (W12).

### 페이징과 재시도

API는 한 번에 다 주지 않습니다.

```python
page = 1
while True:
    data = fetch(page=page, rows=100)
    items = extract_items(data)
    if not items:
        break
    yield from items
    if len(items) < 100:      # 마지막 페이지
        break
    page += 1
    if page > MAX_PAGES:      # ★ 무한 루프 방어
        logger.warning("최대 페이지 도달: %d", MAX_PAGES)
        break
```

**`MAX_PAGES` 가 없으면** API가 이상하게 동작할 때 무한 루프에 빠집니다.
[Day 019](../01-python-data/day-019.md)에서 만든 재시도·간격 로직을 그대로 씁니다.

### 마스터 데이터 시딩

`station` 같은 마스터 테이블은 **측정값보다 먼저** 들어가야 합니다 (FK 때문).

| 전략 | 방법 |
|---|---|
| **별도 명령** | `datapipe seed-station` — 명시적. 권장 |
| 자동 생성 | 측정값 적재 중 없는 측정소를 만들어 넣음 |

**자동 생성은 편하지만 위험합니다.** 오타 난 측정소명이 새 마스터 행을 만들어 버립니다.

### Step 2. 마스터 데이터 시딩 (2교시)

```python
# src/datapipe/stages/seed.py
"""마스터 데이터 적재 — 측정값보다 먼저 실행해야 합니다."""

SEED_STATION_SQL = """
INSERT INTO station (name, sido)
VALUES (%s, %s)
ON CONFLICT (name) DO UPDATE SET sido = EXCLUDED.sido, updated_at = now()
"""


def seed_stations(records: list[dict]) -> int:
    """수집 응답에서 측정소 목록을 뽑아 마스터에 반영합니다 (멱등)."""
    seen: dict[str, str] = {}
    for rec in records:
        name = (rec.get("stationName") or "").strip()
        sido = (rec.get("sidoName") or "").strip()
        if name and sido:
            seen[name] = sido

    if not seen:
        raise StageError("측정소 정보를 하나도 찾지 못했습니다. 응답 형식을 확인하세요.")

    with connect() as conn, conn.cursor() as cur:
        cur.executemany(SEED_STATION_SQL, list(seen.items()))
    logger.info("측정소 마스터 반영: %d개", len(seen))
    return len(seen)
```

### Step 3. 실제 데이터 관찰 (3교시) ★

**검증 규칙을 만들기 전에 데이터를 봅니다.** 어제 백필한 데이터가 있습니다.

```sql
-- sql/checks/profile.sql — 데이터 프로파일링
SELECT 'pm10' AS 항목,
       COUNT(*)                                            AS 전체,
       COUNT(pm10)                                         AS 값있음,
       ROUND(100.0 * (COUNT(*) - COUNT(pm10)) / COUNT(*), 1) AS 결측률,
       MIN(pm10), MAX(pm10),
       ROUND(AVG(pm10), 1)                                 AS 평균,
       PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY pm10)  AS 중앙값,
       PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY pm10)  AS p99
FROM measurement
UNION ALL
SELECT 'pm25', COUNT(*), COUNT(pm25),
       ROUND(100.0 * (COUNT(*) - COUNT(pm25)) / COUNT(*), 1),
       MIN(pm25), MAX(pm25), ROUND(AVG(pm25), 1),
       PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY pm25),
       PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY pm25)
FROM measurement;
```

```
 항목 | 전체  | 값있음 | 결측률 | min | max  | 평균 | 중앙값 | p99
------+-------+--------+--------+-----+------+------+--------+------
 pm10 | 28800 |  27412 |    4.8 |   1 |  341 | 34.7 |     29 |  148
 pm25 | 28800 |  27109 |    5.9 |   1 |  186 | 19.2 |     16 |   83
(2 rows)
```

**읽어야 할 것**

| 관찰 | 판단 |
|---|---|
| 결측률 4.8% · 5.9% | **정상 범위.** 센서 점검·통신 오류로 이 정도는 늘 있습니다 |
| `max` 341 vs `p99` 148 | 상위 1%가 148 이하인데 최댓값이 341 — **황사일 가능성. 확인 필요** |
| `min` 1 (0이 아님) | API가 0을 안 주는 듯. 0을 격리 대상으로 삼을 필요 없음 |

**극단값의 정체를 확인합니다.**

```sql
SELECT s.name AS 측정소, m.measured_at, m.pm10, m.pm25
FROM measurement m JOIN station s ON m.station_id = s.station_id
WHERE m.pm10 > 200
ORDER BY m.pm10 DESC
LIMIT 10;
```

```
   측정소   |      measured_at       | pm10 | pm25
------------+------------------------+------+------
 강북구     | 2026-07-28 08:00:00+09 |  341 |  118
 도봉구     | 2026-07-28 08:00:00+09 |  327 |  112
 노원구     | 2026-07-28 09:00:00+09 |  318 |  109
 강북구     | 2026-07-28 09:00:00+09 |  312 |  115
 성북구     | 2026-07-28 08:00:00+09 |  305 |  104
(5 rows)
```

**같은 날 같은 시간대에 여러 측정소에서 동시에** 높습니다.
**센서 고장이 아니라 실제 대기 현상**(황사·연무)입니다. 격리하면 안 됩니다.

> **한 측정소만 튄다면 센서 고장, 여러 측정소가 동시에 튀면 실제 현상.**
> 이 구분이 검증 규칙 설계의 핵심입니다. **범위 상한을 너무 좁게 잡으면 진짜 데이터를 버립니다.**

### Step 4. 검증 규칙 확정 (4교시)

관찰 결과를 근거로 규칙을 씁니다.

```python
# src/datapipe/rules_air.py
"""대기질 검증 규칙.

임계치 근거 (2026-08-13, 28,800행 관찰 기준):
  pm10  실측 1~341, p99=148  →  상한 2000
        (환경부 '매우나쁨' 151+, 역대 황사 최고 약 1,000 ㎍/㎥ 고려한 여유)
  pm25  실측 1~186, p99=83   →  상한 1000
  결측률 pm10 4.8% · pm25 5.9%  →  결측은 정상. NULL 로 통과시킴
  일관성 pm25 <= pm10 은 물리적 필연 (PM2.5 ⊂ PM10)
"""

from datetime import timedelta

from .validators import consistent, in_set, not_future, numeric_range, required


def _pm25_le_pm10(r: dict) -> bool:
    a, b = r.get("pm25Value"), r.get("pm10Value")
    if a in (None, "", "-") or b in (None, "", "-"):
        return True
    return float(a) <= float(b)


AIR_RULES = [
    required("stationName"),
    required("dataTime"),
    numeric_range("pm10Value", 0, 2000),
    numeric_range("pm25Value", 0, 1000),
    numeric_range("o3Value",  0, 1),          # ppm 단위. 실측 최대 0.152
    numeric_range("no2Value", 0, 1),
    numeric_range("khaiValue", 0, 600),
    in_set("khaiGrade", {"1", "2", "3", "4", None, ""}, "통합지수 등급"),
    consistent("pm25_le_pm10", _pm25_le_pm10, "일관성 위반: pm25 > pm10"),
    not_future("measured_at", tolerance=timedelta(hours=1)),
]
```

**규칙마다 근거를 파일 상단에 모아 두었습니다.**
[Day 050](day-050.md) 질의응답에서 "왜 2000인가요?"라는 질문이 반드시 나옵니다.

## ⑥ 확인 문제

**1.** 프로파일링 결과 `pm10` 의 `MAX` 가 341, `p99` 가 148로 나왔습니다. 341을 격리해야 할까요? 어떻게 판단하겠습니까?

<details>
<summary>답 보기</summary>

**판단 절차 — "혼자 튀는가, 같이 튀는가"**

```sql
-- ① 그 시각에 다른 측정소도 높았는가
SELECT s.name, m.pm10
FROM measurement m JOIN station s ON m.station_id = s.station_id
WHERE m.measured_at = '2026-07-28 08:00+09'
ORDER BY m.pm10 DESC LIMIT 10;

-- ② 그 측정소의 앞뒤 시간은 어땠는가
SELECT measured_at, pm10
FROM measurement m JOIN station s ON m.station_id = s.station_id
WHERE s.name = '강북구'
  AND measured_at BETWEEN '2026-07-28 04:00+09' AND '2026-07-28 14:00+09'
ORDER BY measured_at;
```

| 관찰 | 판단 |
|---|---|
| **여러 측정소가 동시에 높음** | **실제 현상** (황사·연무). 격리하면 안 됨 ★ |
| 그 측정소만 높음 | 센서 이상 의심 |
| 앞뒤 시간이 완만하게 오르내림 | 실제 현상 (대기는 급변하지 않음) |
| 한 시점만 뾰족하게 튐 | 센서 오류 가능성 |
| 같은 값(9999 등)이 반복 | **확실한 센서 고장** |

**이 사례에서는 격리하면 안 됩니다.**
7월 28일 8~9시에 강북·도봉·노원·성북이 동시에 300 이상입니다. **광역적 대기 현상**입니다.
상한을 200으로 잡았다면 **가장 중요한 데이터를 버릴 뻔했습니다.**

**규칙 설계 원칙**

```
범위 상한은 "물리적으로 불가능한 값"을 막는 선에서 넉넉하게.
"평소보다 이상한 값"은 격리가 아니라 통계적 탐지(z점수)로.
```

**격리는 "이 값은 틀렸다"는 확신이 있을 때만.**
"이상하다"는 격리 사유가 아니라 **조사 사유**입니다.

> 이 구분은 W12의 **이상치 처리**에서 다시 나옵니다.
> "이상치를 제거한다"는 결정이 **가장 중요한 신호를 지우는 일**이 되는 경우가 많습니다.
</details>

**2.** 서초구 측정소에 172시간의 데이터 구멍이 있습니다. 세 가지 대응 중 무엇을 고르고, 분석 쿼리에는 어떻게 반영하겠습니까?

<details>
<summary>답 보기</summary>

**"그대로 두고 문서화 + 분석에서 명시적으로 처리"** 를 고릅니다.

**① 값을 채우지 않는 이유**

```
평균으로 채우면  →  서초구의 8월 평균이 7월 평균과 같아짐
                 →  "서초구는 변동이 없다"는 거짓 결론
중앙값·직전값도 마찬가지 — 없는 사실을 만들어 냅니다
```

**② 측정소를 삭제하지 않는 이유** — 7월 13일~8월 5일의 576행은 **유효한 데이터**입니다.

**③ 분석 쿼리에서의 반영**

```sql
-- (a) 측정소 비교: 관측 수 조건으로 제외
SELECT s.name, COUNT(*) AS 관측수, ROUND(AVG(m.pm10), 1) AS 평균
FROM measurement m JOIN station s ON m.station_id = s.station_id
WHERE m.pm10 IS NOT NULL
GROUP BY s.name
HAVING COUNT(*) >= 500
ORDER BY 평균 DESC;

-- (b) 시계열 분석: 기간을 맞춰서 비교
SELECT s.name, ROUND(AVG(m.pm10), 1) AS 평균_7월
FROM measurement m JOIN station s ON m.station_id = s.station_id
WHERE m.measured_at >= '2026-07-13' AND m.measured_at < '2026-08-01'
  AND m.pm10 IS NOT NULL
GROUP BY s.name;

-- (c) 커버리지 자체를 보여주기 — 이것도 분석 결과입니다
SELECT s.name AS 측정소,
       COUNT(*)                                          AS 관측수,
       ROUND(COUNT(*) * 100.0 / (30 * 24), 1)            AS 커버리지,
       MIN(m.measured_at)::date AS 시작, MAX(m.measured_at)::date AS 종료
FROM measurement m JOIN station s ON m.station_id = s.station_id
GROUP BY s.name
ORDER BY 커버리지;
```

**(c)를 보고서 앞부분에 넣으세요.** "데이터가 얼마나 온전한가"를 먼저 보여주는 것이
**신뢰할 수 있는 분석의 조건**입니다. [Day 040](day-040.md)의 분석 6축 중 "개요"에 해당합니다.

**보고서 문장 예시**

```markdown
서초구 측정소는 2026-08-05 이후 데이터가 없어 관측 수가 576건(커버리지 80%)에 그칩니다.
측정소 간 비교에서는 관측 수 500건 이상인 39개 측정소만 대상으로 했습니다.
```

**한 문장이 있고 없고가 보고서의 신뢰도를 가릅니다.**
채점자·면접관은 **"데이터의 한계를 알고 있는가"** 를 봅니다.
</details>

| 완료 정의 | 확인 방법 |
|---|---|
| 파이프라인 성공 | `datapipe etl` |

| 관측 | `datapipe status` |

| **재현** | 새 폴더 clone → 실행 성공 |

| 판단 원칙 | |
|---|---|
| 검증 규칙은 **데이터를 보고** 만든다 | `MIN`·`MAX`·`p99`·결측률 프로파일링 |

**오늘의 습관** — 매 실행 후 **격리 행의 사유 분포**를 한 번씩 보세요.
