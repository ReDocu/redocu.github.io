## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 컨테이너의 **"시작됨"과 "준비됨"** 이 다른 사건임을 실험으로 보이고, `depends_on` 의 한계를 설명할 수 있다.
- DB와 API에 **healthcheck** 를 달고, `condition: service_healthy` 로 기동 순서를 제어할 수 있다.
- **재시작 정책** 4종을 구분하고, 서비스에 맞는 것을 고를 수 있다.
- 구성 요소를 일부러 죽이는 **장애 실험**으로 자기 구성의 복원력을 증명할 수 있다.

## ② 왜 필요한가

어제까지의 compose에는 시한폭탄이 하나 더 있습니다 — 오늘은 운입니다. `docker compose down`
후 볼륨까지 새로 만들며 올려 보면 (`down -v` 로 DB 초기화를 느리게 만들면) 이런 장면을 만납니다:

```
api-1  | sqlalchemy.exc.OperationalError: connection to server at "db" (172.19.0.2),
api-1  | port 5432 failed: Connection refused
api-1  |     Is the server running on that host and accepting TCP/IP connections?
api-1 exited with code 1
```

API가 죽었습니다. DB 컨테이너는 **시작**됐지만 PostgreSQL이 아직 접속을 받을 **준비**가
안 된 몇 초 사이에, API의 lifespan(predlog.init)이 먼저 문을 두드린 겁니다. `depends_on` 을
줬는데도요 — depends_on의 기본 약속은 "먼저 **시작**시켜 준다"까지이지, "준비될 때까지
기다려 준다"가 아니기 때문입니다.

이런 **경쟁 상태(race)** 의 고약함은 "가끔만" 난다는 데 있습니다 — 내 PC에선 DB가 빨라 늘
성공하고, 새 서버(볼륨 초기화 = 초기화 몇 초 추가)에서만 터집니다. "clone 직후 `docker compose
up` 만으로 뜬다"는 이번 주 목표는 **운이 아니라 설계**로 보장돼야 합니다.

설계의 재료는 이미 있습니다 — [Day 096](../04-deep-learning-serving/day-096.md)에서 만든
`/health`. 그날 "로드밸런서·모니터링이 쓴다(W25~)"고 예고했던 그 엔드포인트가 오늘 드디어
첫 기계 소비자를 만납니다.

## ③ 개념 설명

### 시작됨 ≠ 준비됨

| 사건 | 뜻 | 예 |
|---|---|---|
| 시작됨 (started) | 프로세스가 떴다 | postgres 프로세스 실행 (초기화는 이제부터) · uvicorn 실행 (모델 로드는 이제부터) |
| **준비됨 (ready)** | **일을 받을 수 있다** | 접속 수락·쿼리 응답 · 모델 로드 완료 후 /health 200 |

그 사이가 수 초~수십 초입니다 — MP3는 모델 로드(ResNet 174ms + 앱 초기화)로, DB는 초기화로.
운영의 모든 대기·판단은 "준비됨" 기준이어야 하고, 그것을 기계가 판정하게 하는 장치가
healthcheck입니다.

### healthcheck — 컨테이너의 자가 진단 문진표

```yaml
healthcheck:
  test: ["CMD", "pg_isready", "-U", "mp3"]   # 이 명령의 종료 코드 0 = 건강
  interval: 5s        # 검사 주기
  timeout: 3s         # 검사 하나의 제한 시간
  retries: 5          # 연속 몇 번 실패해야 unhealthy 판정
  start_period: 15s   # 기동 유예 — 이 동안의 실패는 벌점 없음
```

상태는 `starting → healthy / unhealthy` 로 움직이고 `docker compose ps` 에 표시됩니다.
**test는 컨테이너 안에서** 실행된다는 것이 함정 포인트 — 그 이미지 안에 있는 도구만 쓸 수
있습니다 (slim 이미지에 curl은 없습니다 — ⑤).

### depends_on의 완전체

```yaml
depends_on:
  db:
    condition: service_healthy    # "시작"이 아니라 "healthy"를 기다림
```

이제 Compose는 db가 **healthy 판정을 받을 때까지** api의 기동을 보류합니다 — 경쟁 상태가
구조적으로 사라집니다.

### 재시작 정책 — 죽음 이후의 계약

[Day 113](day-113.md) systemd의 `Restart=` 가 컨테이너 세계로 온 것입니다:

| 정책 | 동작 | 용도 |
|---|---|---|
| `no` (기본) | 안 살림 | 일회성 잡 (datapipe) |
| `on-failure` | 비정상 종료(≠0)만 재시작 | 배치·워커 |
| `always` | 무조건 (정상 종료도!) | 드묾 — ⑤의 함정 |
| **`unless-stopped`** | 죽으면 재시작 + **재부팅에도 부활**, 단 내가 stop 한 건 존중 | **상주 서비스의 표준** |

## ④ 단계별 실습

### Step 1. 경쟁 상태를 확정적으로 재현 (1~2교시)

운에 맡기지 않고 재현합니다 — DB 초기화가 확실히 느린 조건(새 볼륨)으로:

```bash
docker compose down -v          # 실습 볼륨 폐기 — DB가 처음부터 초기화하게
docker compose up -d
docker compose ps -a
docker compose logs api | tail -3
```

```
$ docker compose ps -a
NAME               IMAGE           SERVICE   STATUS
mlops-mp3-api-1    mlops-mp3-api   api       Exited (1) 8 seconds ago
mlops-mp3-db-1     postgres:16     db        Up 12 seconds
$ docker compose logs api | tail -3
api-1  | sqlalchemy.exc.OperationalError: connection to server at "db" (172.19.0.2), port 5432 failed: Connection refused
api-1  |        Is the server running on that host and accepting TCP/IP connections?
api-1  | [주의] 예측 로그 초기화 실패로 기동 중단
```

②에서 예고한 그 장면 — db는 Up인데 api는 Exited(1). "떴다"와 "준비됐다" 사이의 골짜기에
빠진 것입니다. (여러분의 환경에서 운 좋게 성공했다면 down -v 후 몇 번 반복 — 경쟁 상태는
확률임을 그 자체로 확인하게 됩니다.)

### Step 2. 순서의 제어 — DB healthcheck (3~4교시)

compose.yaml을 완전체로 (브랜치 `feature/health-restart`):

```yaml
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql+psycopg://mp3:${DB_PASSWORD:?required}@db:5432/mp3
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request,sys; r=urllib.request.urlopen('http://localhost:8000/health', timeout=2); sys.exit(0 if r.status==200 else 1)"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 30s

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: mp3
      POSTGRES_PASSWORD: ${DB_PASSWORD:?required}
      POSTGRES_DB: mp3
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U mp3 -d mp3"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  pgdata:
```

읽어 둘 점 — ① api의 test가 curl이 아니라 **python** (slim 이미지 안에 확실히 있는 도구,
그리고 그 /health가 모델 적재까지 확인하는 Day 096 설계라 "준비됨"의 정의로 완벽),
② `start_period: 30s` — 모델 로드 시간의 유예 (없으면 로드 중 실패가 벌점으로 쌓입니다 — ⑤),
③ 어제의 `:?required` 가 그대로. 검증:

```bash
docker compose down -v && docker compose up -d && docker compose ps
```

```
$ docker compose up -d
[+] Running 3/3
 ✔ Network mlops-mp3_default   Created                                    0.1s
 ✔ Container mlops-mp3-db-1    Healthy                                   11.3s
 ✔ Container mlops-mp3-api-1   Started                                   11.9s
$ docker compose ps
NAME               IMAGE           SERVICE   STATUS
mlops-mp3-api-1    mlops-mp3-api   api       Up 25 seconds (healthy)
mlops-mp3-db-1     postgres:16     db        Up 36 seconds (healthy)
```

up 출력이 달라졌습니다 — db가 **Healthy** 가 된 뒤에야 api가 Started. 새 볼륨(가장 느린
조건)에서도 결정적으로 성공합니다. Step 1을 몇 번 더 반복해도 이제 전패는 없습니다 —
운이 설계가 됐습니다.

### Step 3. 죽여도 되살아나는가 — 재시작 정책 실험 (5~6교시)

**실험 A — API 급사.** [Day 113](day-113.md) Step 4의 컨테이너판:

```bash
docker kill mlops-mp3-api-1
sleep 5; docker compose ps
```

```
$ docker compose ps
NAME               IMAGE           SERVICE   STATUS
mlops-mp3-api-1    mlops-mp3-api   api       Up 4 seconds (health: starting)
mlops-mp3-db-1     postgres:16     db        Up 3 minutes (healthy)
```

`restart: unless-stopped` 가 일했습니다 — kill 직후 자동 재기동, start_period 유예 속에서
모델 로드 중(`health: starting`). MP4 평가 항목 "장애 복구(컨테이너 kill 후 자동 회복)"가
이 한 줄입니다.

**실험 B — DB 순단.** API가 살아 있는 채로 DB만 재시작하면:

```bash
docker compose restart db
sleep 8
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8000/predict
```

```
$ curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8000/predict
{"label":"ants","confidence":0.7214,"model_version":"resnet18-antbee-v1","elapsed_ms":32.0}
```

API가 **버텼습니다** — 어제 predlog의 `pool_pre_ping=True` (끊긴 연결을 쓰기 전에 확인하고
새로 맺는 옵션)가 조용히 일한 덕입니다. 운영의 복원력은 이렇게 인프라(재시작 정책)와
앱(연결 관리)의 합작입니다.

### Step 4. 과제 — 장애 시나리오 실험 보고서 (7~8교시)

다음 시나리오를 각각 실행하고, `예상 → 실행 명령 → 관찰(로그·ps 발췌) → 결론` 형식으로
기록하세요. **실험 전 예상을 먼저 적는 것**이 규칙입니다.

1. **DB 영구 사망** — `docker compose stop db` 상태에서 /predict를 부르면 API는 어떻게
   되는가? (500? 응답 지연? 예측은 되는데 로그만 실패?) — 관찰 후, "예측 로그 실패가 예측
   자체를 막아야 하는가"에 대한 설계 의견을 predlog.write의 예외 처리와 함께 제시
2. **unhealthy 방치** — api의 healthcheck test를 일부러 실패하게 바꾸면 (`exit 1`) 무슨 일이
   벌어지는가? unhealthy가 되면 Compose가 재시작해 주는가? (스포일러: 아닙니다 — 그럼 이
   상태를 누가 소비해야 하는가?)
3. **재부팅 생존** — `wsl --shutdown` 후 Docker Desktop 재기동 — 두 컨테이너가 스스로
   돌아오는가? (Day 113 Step 5의 컨테이너판 — unless-stopped의 "재부팅 부활" 검증)

## ⑤ 자주 하는 실수

### depends_on만 믿고 준비를 안 기다림

**증상** — Step 1의 그 크래시 — "depends_on 있는데요?"
**원인** — 기본 depends_on은 시작 **순서**만 보장 (준비 대기는 안 함).
**해결** — 기다림이 필요한 의존에는 반드시 `condition: service_healthy` + 상대의 healthcheck.
보조 수단으로 앱 쪽 재시도(연결 백오프)까지 있으면 금상첨화 — 인프라와 앱의 이중 방어입니다.

### healthcheck에 그 이미지에 없는 도구를 씀

**증상** — 서비스는 멀쩡한데 영원히 `(unhealthy)`:
```
OCI runtime exec failed: exec: "curl": executable file not found in $PATH
```
**원인** — test는 **컨테이너 안**에서 실행됩니다 — slim 이미지에 curl·wget은 없습니다.
**해결** — 이미지 안에 확실히 있는 것으로: 파이썬 앱이면 python -c urllib (오늘 방식),
postgres면 pg_isready. "무엇이 안에 있나"는 `docker compose exec api which python curl` 로
확인 가능합니다.

### start_period 없이 로드가 긴 앱을 판정

**증상** — 모델 로드 중 검사 3연속 실패 → unhealthy 판정 → (오케스트레이터에 따라) 죽였다
살렸다 무한 반복 — **정상인 앱이 로드가 길다는 이유로 살해**당함.
**원인** — 기동 유예 없이 retries가 로드 시간을 소모.
**해결** — `start_period` 를 **최악 로드 시간 + 여유**로. MP3는 모델 로드 실측(Day 096)이
있으니 근거 있는 30s입니다 — 감이 아니라 실측으로 정하는 것이 우리 과정의 방식입니다.

### restart: always로 크래시 루프를 가림

**증상** — 설정 오타로 기동 즉시 죽는 컨테이너가 always 덕에 초당 재시작 — CPU는 타고,
ps는 언뜻 Up으로 보여 발견이 늦음.
**원인** — 재시작 정책을 "가용성 보험"으로만 이해 — 반복 사망의 **신호**를 소음으로 만듦.
**해결** — `docker compose ps` 의 `Restarting (1) n seconds ago` 와 재시작 횟수를 읽는 습관.
재시작은 일시 장애의 처방이지 버그의 처방이 아닙니다 — 반복되면 로그(logs --tail)로 원인
조사가 먼저입니다 (Day 113 ⑤의 "status 안 읽고 재시작만"과 같은 병).

### 헬스체크를 너무 자주, 너무 무겁게

**증상** — interval: 1s에 실제 추론까지 하는 test — 헬스체크가 트래픽이 되어 p95를 밀어 올림.
**원인** — "자주 볼수록 안전"이라는 직감.
**해결** — 검사는 가볍게(상태 조회 수준), 주기는 장애 감지 요구에 맞게 (우리 규모엔 5~10s면
충분). 그리고 /health 자체를 가볍게 유지하는 것 — Day 096에서 모델 **적재 여부**만 보고 추론은
안 하게 설계한 이유가 이것입니다.

이런 부류의 버그를 잡기 위한 테스트 원칙을 한 줄로 제안하세요.

<details>
<summary>답 보기</summary>

경쟁 상태의 승부는 DB 준비 시간과 API 기동 시간의 상대 속도로 갈립니다 — 내 PC는 볼륨에 이미
초기화된 데이터가 있어 DB가 1초 내 준비되고(API가 늘 짐), 새 서버는 initdb 수 초 동안 API가
먼저 도착합니다. 원칙: **"가장 느린 조건(빈 볼륨·새 환경)에서의 up을 테스트 표준으로"** —
그래서 오늘 검증마다 down -v를 썼고, MP4 평가 기준도 "clone → up"(빈 상태 기동)입니다.

</details>

**Q2.** healthcheck의 unhealthy는 (compose 단독 환경에선) 자동 재시작을 일으키지 않습니다.
그럼에도 healthcheck가 가치 있는 이유를, 그 상태의 소비자 두 종류를 들어 설명하세요.

<details>
<summary>답 보기</summary>

첫 소비자는 **기동 순서 제어** — depends_on condition이 healthy를 기다려 경쟁 상태를 제거합니다
(오늘의 주 사용처). 둘째는 **관찰자들** — docker compose ps의 상태 표시로 운영자가 즉시 이상을
보고, W26의 배포 후 스모크 테스트·[Day 124](day-124.md) 프록시·W27 모니터링이 이 판정을 읽어
트래픽 차단·알림으로 잇습니다. 즉 healthcheck는 행동(재시작)이 아니라 **판정의 표준화**이고,
행동은 그 판정의 소비자들이 각자 결정합니다 (재시작까지 자동으로 잇는 것은 K8s 같은
오케스트레이터의 영역 — Day 135).

</details>

**Q3.** 실험 B에서 DB 순단에도 API가 버틴 것은 `pool_pre_ping` 덕이었습니다. 만약 predlog.write가
"DB 실패 시 예외를 그대로 올리는" 구현이라면, DB 10초 순단 동안 서비스에 무슨 일이 벌어질지
추적하고, 올바른 설계를 제안하세요.
