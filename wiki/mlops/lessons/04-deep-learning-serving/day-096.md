## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 모델 **로드와 추론의 비용 차이**를 실측하고, 요청당 로드가 왜 금지인지 산수로 보일 수 있다.
- **lifespan**(수명주기)으로 서버 시작 시 1회 로드 구조를 구현할 수 있다.
- MP2 모델을 `/predict` · `/model/info` · `/health` 를 갖춘 API로 서빙할 수 있다.
- 응답에 **모델 버전**을 담아 예측의 족보를 남길 수 있다.

> 이 문서는 이 과정 전체가 전제하는 5개 핵심 문서 중 하나입니다. 여기서 만드는 구조가
> MP3의 뼈대이고, W24 이후 컨테이너에 실리는 것도 이 서버입니다.

---

## ② 왜 필요한가

드디어 만남의 날입니다 — 대단원 03의 산출물([Day 068](../03-machine-learning/day-068.md)의
`pm25_pipeline.joblib` + 스키마)과 지난주의 FastAPI가 오늘 결합합니다.

```
[Day 075의 목표]  POST /predict {"pm25": 41.0, ...} → {"pred": 29.5}    ← 오늘 실현
```

그런데 결합 방식에 함정이 있습니다. 가장 자연스러워 보이는 코드가 최악의 서버를 만듭니다:

```python
@app.post("/predict")
def predict(r: PredictIn):
    pipe = joblib.load("model.joblib")     # ← 요청마다 로드?!
    return pipe.predict(...)
```

동작합니다. 테스트도 통과합니다. 그리고 운영에서 무너집니다 — 오늘 실측할 숫자로 미리 보면,
ResNet18의 로드는 174ms, 추론은 22ms입니다. 요청마다 로드하면 **응답의 89%가 낭비**이고,
LLM급 모델(로드 수십 초)이면 서비스가 성립 자체를 안 합니다. 커리큘럼 FAQ의 그 질문
("요청마다 모델을 로드하면 왜 안 되나요?")에 오늘 숫자로 답합니다.

## ③ 개념 설명

### 서버의 세 시간대 — 다운로드 · 로드 · 추론

[Day 088](day-088.md) ⑤에서 구분한 3단이 서버 설계의 뼈대가 됩니다.

| 시간대 | 일 | 비용 | 언제 |
|---|---|---|---|
| 다운로드 | 모델 파일 확보 | 분 단위 (1회) | 배포 시 (이미지에 포함 — W24) |
| **로드** | 파일 → 메모리, 가중치 복원 | **수백 ms ~ 수십 초** | **서버 시작 시 1회** |
| 추론 | 순전파 | ms ~ 수백 ms | 요청마다 |

설계 원칙은 표가 말해 줍니다: **비싼 것은 앞으로, 요청 경로에는 추론만.**

### lifespan — 시작과 끝의 공식 자리

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    state["pipe"] = joblib.load(MODEL_PATH)     # 시작 시 1회
    yield                                        # ← 이 사이가 서버의 일생
    state.clear()                                # 종료 시 정리

app = FastAPI(lifespan=lifespan)
```

[Day 085](day-085.md)에서 함수 경계로 나눠 둔 `load_model()` / `predict()` 가 서버에서는
lifespan / 핸들러로 각각 들어갑니다 — 그날의 설계가 오늘을 위한 것이었습니다.
로드가 끝나기 전에는 서버가 요청을 받지 않으므로, "모델 없이 응답하는" 사고도 없습니다.

### 추론 API의 3종 기본 엔드포인트

| 엔드포인트 | 역할 | 누가 쓰나 |
|---|---|---|
| `POST /predict` | 예측 | 클라이언트 |
| `GET /model/info` | 지금 실린 모델의 정체 (run_id·특성 수·학습 데이터 지문) | 운영자·디버깅 |
| `GET /health` | 살아 있고 모델이 실려 있는가 | 로드밸런서·모니터링 (W25~) |

`/predict` 응답의 **model_version** — 운영 중 모델이 교체되어도 "이 예측은 어느 모델의
판단인가"를 추적하게 하는 족보([Day 068](../03-machine-learning/day-068.md) Q3)입니다.
MP3 필수 기능이자 이번 주 체크포인트("응답에 모델 버전이 담기는가")입니다.

## ④ 단계별 실습

### Step 1. 로드 vs 추론 — 실측 (1~2교시)

먼저 우리가 가진 두 모델의 비용을 잽니다 (측정: 각 5회 중 최솟값).

```
| MP2 파이프라인 (4KB) | 로드 0.8ms | 예측 1건 2.3ms |
| ResNet18 (45MB)     | 로드 174ms | 예측 1건 22ms |
```

산수를 해 봅시다. ResNet을 요청당 로드하면 응답이 22ms → **196ms (9배)**. 초당 처리량은
45건 → 5건로 추락합니다. 4KB짜리 MP2 파이프라인조차 로드가 예측의 1/3을 차지합니다.
그리고 이것은 시간만의 문제가 아닙니다 — 동시 요청 10개가 각자 로드하면 메모리에 모델
사본 10개가 뜹니다(45MB × 10). **모델은 프로세스당 1개, 시작 시 1회** — 예외 없는 규칙입니다.

### Step 2. 표준 구조의 추론 서버 (3~5교시)

`serve_pm25.py`:

```python
# serve_pm25.py — MP2 모델을 FastAPI로 — 추론 서버의 표준 구조
import json
from contextlib import asynccontextmanager

import joblib
import pandas as pd
from fastapi import FastAPI
from pydantic import BaseModel, Field

MODEL_PATH = "../models/pm25_pipeline.joblib"
SCHEMA_PATH = "../models/pm25_pipeline_schema.json"

state = {}                                   # 로드된 모델의 거처 (프로세스당 1개)


@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── 서버 시작 시 딱 1회: 모델과 스키마를 메모리에 상주 ──
    state["pipe"] = joblib.load(MODEL_PATH)
    state["schema"] = json.load(open(SCHEMA_PATH, encoding="utf-8"))
    print(f"모델 로드 완료: run {state['schema']['run_id'][:8]} · 컬럼 {len(state['schema']['columns'])}개")
    yield
    state.clear()                            # 종료 시 정리


app = FastAPI(title="PM2.5 익일 예보 API", version="1.0.0", lifespan=lifespan)


class PredictIn(BaseModel):
    """입력 계약 — models/pm25_pipeline_schema.json의 columns를 그대로 번역 (Day 068→092)"""
    model_config = {"extra": "forbid"}

    pm10: float = Field(ge=0, le=600)
    pm25: float = Field(ge=0, le=300)
    o3: float; no2: float; co: float; so2: float
    temp: float; humidity: float; wind_speed: float; precip: float
    pm25_lag1: float; pm25_ma3: float; seoul_pm25: float
    month: int = Field(ge=1, le=12)
    wind_fc: float; humidity_fc: float; precip_fc: float
    station: str


def to_grade(pm25: float) -> str:
    return "좋음" if pm25 < 16 else "보통" if pm25 < 36 else "나쁨" if pm25 < 76 else "매우나쁨"


@app.post("/predict")
def predict(r: PredictIn):                   # 블로킹 추론이므로 평범한 def (Day 094!)
    x = pd.DataFrame([r.model_dump()])[state["schema"]["columns"]]   # 스키마 순서로 정렬
    pred = float(state["pipe"].predict(x)[0])
    return {"pm25_next_pred": round(pred, 1),
            "grade": to_grade(pred),
            "model_version": state["schema"]["run_id"][:8]}          # 족보 (Day 068 Q3)


@app.get("/model/info")
def model_info():
    s = state["schema"]
    return {"run_id": s["run_id"], "target": s["target"],
            "n_features": len(s["columns"]), "split_date": s["split_date"],
            "data_md5": s["data_md5"][:8]}


@app.get("/health")
def health():
    return {"status": "ok", "model_loaded": "pipe" in state}
```

코드 곳곳이 지난 배움의 총집합입니다: PredictIn은 [Day 068](../03-machine-learning/day-068.md)
스키마 JSON의 pydantic 번역([Day 075](../03-machine-learning/day-075.md) Q3에서 예고한 그것),
`extra: forbid` 는 [Day 092](day-092.md), 핸들러가 `def` 인 이유는 [Day 094](day-094.md)의
실측 5.1초, DataFrame을 스키마 순서로 정렬하는 한 줄은 [Day 068](../03-machine-learning/day-068.md)의
validate_input입니다.

### Step 3. 가동과 검증 (6~7교시)

```powershell
uvicorn serve_pm25:app --port 8096
```

```
$ GET /health
  200 → {"status": "ok", "model_loaded": true}
$ GET /model/info
  200 → {"run_id": "6ac527baab8e45b4b9a85607b9ebf9f5", "target": "pm25_next", "n_features": 18, "split_date": "2026-01-01", "data_md5": "21adc01f"}
$ POST /predict (겨울 정체일)
  200 → {"pm25_next_pred": 34.1, "grade": "보통", "model_version": "6ac527ba"}
$ POST /predict (내일 비바람 예보)
  200 → {"pm25_next_pred": 20.4, "grade": "보통", "model_version": "6ac527ba"}
$ POST /predict (pm25 오타 → pm2_5)
  422 → {"detail": [..., {"type": "extra_forbidden", "loc": ["body", "pm2_5"], "msg": "Extra inputs are not permitted", "input": 28.4}]}
연속 20회 평균 응답: 20ms
```

읽을거리가 가득합니다.

1. **두 예측의 차이를 보세요** — 같은 오늘 관측인데, 내일 예보만 바람 1.0→5.5·비 0→18mm로
   바꾸자 예측이 34.1 → 20.4로 내려갑니다. [Day 064](../03-machine-learning/day-064.md)에서
   넣은 예보 특성(비바람의 세정 효과)이 **API 위에서 살아 움직이는** 것입니다.
2. 필드 오타(pm2_5)는 모델 근처에도 못 가고 입구에서 422 — 이름까지 지목됩니다.
3. `model/info` 에는 run_id와 **학습 데이터 지문**(21adc01f — [Day 066](../03-machine-learning/day-066.md)의
   그 MD5)까지. "지금 서빙 중인 모델의 족보"가 API 한 번에 나옵니다.
4. 평균 20ms — 로드가 요청 경로에 없기 때문입니다.

편인데도 차이가 날 겁니다 — ResNet이었다면?을 Step 1의 표로 계산).
③ 잘못된 station("부산")이 현재는 그대로 통과합니다 — 왜 에러가 안 나는지
([Day 063](../03-machine-learning/day-063.md)의 handle_unknown!) 확인하고, 등록 측정소
목록 검증을 PredictIn에 추가할지 말지 논거와 함께 결정하세요.

## ⑤ 자주 하는 실수

### 요청마다 모델을 로드

**증상** — 기능은 정상, 응답만 느림 — 그리고 부하가 오르면 메모리 폭발.
**원인** — 로드(174ms급)를 요청 경로에 넣었습니다.
**해결** — lifespan에서 1회. 코드 리뷰 규칙: **핸들러 안에 load/from_pretrained가 보이면 반려.**

### 전역에서 import 시점에 로드

**증상** — lifespan 없이 모듈 최상단에서 `pipe = joblib.load(...)` — 대개 돌아가지만, 테스트가 모듈 import만 해도 로드가 일어나고, 로드 실패 시 에러가 어디서 났는지 불분명해집니다.
**원인** — "전역이면 1회 아닌가?" — 맞지만 **시점 제어**가 안 됩니다.
**해결** — lifespan이 공식 자리입니다: 시작·종료가 명시되고, 실패가 기동 실패로 명확히 드러나며, /health가 로드 여부를 정직하게 반영합니다.

### 추론 핸들러를 async def로 선언

**증상** — 부하가 오르면 헬스체크까지 전부 느려짐.
**원인** — torch/sklearn 추론은 블로킹인데 이벤트 루프 위에서 돌렸습니다 ([Day 094](day-094.md)의 5.1초).
**해결** — 추론 핸들러는 평범한 `def`. (그래야 FastAPI가 스레드풀로 돌립니다.)

### 모델 파일 경로를 상대 경로 습관대로 씀

**증상** — 로컬에선 되는데 서비스 등록·컨테이너에서 `FileNotFoundError` — 실행 위치가 다르면 상대 경로가 깨집니다.
**원인** — 경로가 "누가 어디서 실행하나"에 종속.
**해결** — 경로를 설정([Day 093](day-093.md)의 config — 환경 변수 `MODEL_PATH`)으로 빼세요. W24 컨테이너에서 이 값이 이미지 내 절대 경로로 주입됩니다.

### /health가 항상 ok를 반환

**증상** — 모델 로드가 실패했는데 health는 초록 — 로드밸런서가 고장 난 서버로 트래픽을 보냄.
**원인** — health가 "프로세스 살아 있음"만 확인.
**해결** — 오늘 코드처럼 **모델 적재 여부까지** 응답에 포함. 더 나가면 "마지막 예측 성공 시각" 같은 심층 점검도 — W25의 모니터링에서 확장합니다.

## ⑥ 확인 문제

**Q1.** Step 1의 실측(ResNet 로드 174ms / 추론 22ms)으로, 요청당 로드 서버와 표준 서버의
초당 최대 처리량(단일 프로세스, 순차 처리 가정)을 각각 계산하세요.

<details>
<summary>답 보기</summary>

요청당 로드: 요청 하나에 174+22 = 196ms → 초당 약 **5.1건**. 표준 구조: 22ms → 초당 약 **45.5건**.
같은 하드웨어에서 9배 차이이며, 로드가 수십 초인 대형 모델이면 전자는 아예 서비스가 성립하지
않습니다. "비싼 것은 시작 시로" 원칙의 정량적 근거입니다.

</details>

**Q2.** 응답의 model_version과 /model/info의 data_md5가 운영 중 어떤 질문에 답해 주는지,
각각 시나리오 하나씩으로 설명하세요.

<details>
<summary>답 보기</summary>

model_version: "지난주 화요일의 이 이상한 예측, 어느 모델이 낸 것인가?" — 로그의 응답과 버전을
대조해 당시 모델을 특정하고 재현·분석할 수 있습니다 (모델 교체가 잦은 운영에서 필수).
data_md5: "지금 서빙 중인 모델이 어떤 데이터로 학습됐나?" — 데이터 오염 사고가 발견됐을 때
영향받는 모델(그 지문으로 학습된)을 즉시 식별해 롤백 범위를 정할 수 있습니다.

</details>

**Q3.** MP2 파이프라인을 서빙했는데 전처리 코드를 한 줄도 쓰지 않았습니다. 대치·스케일·원핫은
어디서 일어나고 있으며, 이것이 내일(Day 097)의 주제와 어떻게 연결되나요?

<details>
<summary>답 보기</summary>

전부 `state["pipe"].predict()` **안에서** — [Day 063](../03-machine-learning/day-063.md)에서 전처리를
파이프라인에 봉인해 저장했기 때문에, 서빙은 로드 후 predict만 하면 학습과 동일한 전처리가 자동
수행됩니다. 내일은 이 봉인이 **없을 때**(전처리를 서빙 쪽에서 재구현할 때) 무슨 사고가 나는지
일부러 재현합니다 — 전처리 일치가 왜 "원칙"이 아니라 "구조"여야 하는지의 실증입니다.

</details>
