## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `INNER JOIN` · `LEFT JOIN` 의 차이를 설명하고 상황에 맞게 고를 수 있다.
- 3개 이상의 테이블을 연결해 **하나의 분석 결과**를 만들 수 있다.
- 조인 키의 관계(1:1 · 1:N)를 확인하고 **행이 부풀어 오르는 함정**을 진단·수정할 수 있다.
- `ON` 과 `WHERE` 에 조건을 두는 것의 차이를 설명할 수 있다.

---

## ② 왜 필요한가

어제 이런 결과를 봤습니다.

```
 product_id | 판매수량 |  매출
------------+----------+---------
          3 |        6 | 1554000
```

**"3번 상품이 뭔데요?"** — 답을 못 합니다. 상품 이름은 `products` 테이블에 있고, 판매 기록은 `order_items` 에 있기 때문입니다.

이건 실수가 아니라 **의도된 설계**입니다. [Day 031](day-031.md)에서 봤듯이 관계형 DB는 정보를 나눠 저장하고 **키로 연결**합니다.

```
order_items          products
┌────────────┐      ┌────────────┐
│ product_id │─────▶│ product_id │
│ quantity   │      │ name       │  ← 여기 있음
│ unit_price │      │ category   │
└────────────┘      └────────────┘
```

**나눠 둔 것을 다시 합치는 연산이 `JOIN`** 입니다. 그리고 실무 SQL의 90%에는 `JOIN` 이 들어갑니다.
데이터가 한 테이블에 다 있는 경우는 거의 없기 때문입니다.

[Day 024](../01-python-data/day-024.md)의 `pd.merge(df1, df2, on="product_id", how="left")` 와 같은 일입니다.
`how="inner"` / `"left"` 가 오늘 배울 `INNER JOIN` / `LEFT JOIN` 에 그대로 대응합니다.

그리고 오늘 **이 단원에서 가장 위험한 버그**를 배웁니다. `JOIN` 을 잘못 쓰면 **에러 없이 매출이 몇 배로 부풀어 오릅니다.**

## ③ 개념 설명

### 기본 문법

```sql
SELECT oi.quantity, p.name
FROM      order_items oi          -- 왼쪽 테이블 (별칭 oi)
JOIN      products    p           -- 오른쪽 테이블 (별칭 p)
  ON      oi.product_id = p.product_id;   -- 연결 조건 (조인 키)
```

| 요소 | 설명 |
|---|---|
| **별칭(alias)** | `order_items oi` — 긴 테이블 이름 대신 짧게. 조인이 3개만 넘어가도 필수 |
| **`ON` 조건** | 두 테이블의 행을 **어떤 기준으로 짝지을지**. 보통 `외래키 = 기본키` |
| **`테이블.열`** | 양쪽에 같은 이름의 열이 있으면 반드시 앞에 테이블(별칭)을 붙입니다 |

> **별칭은 선택이 아니라 습관입니다.** 열 앞에 `c.` · `o.` 를 붙이면
> "이 열이 어느 테이블에서 왔는지"가 코드에 드러나 리뷰가 쉬워집니다.

### JOIN의 종류

| 종류 | 결과에 남는 행 | 언제 쓰나 |
|---|---|---|
| **`INNER JOIN`** (`JOIN`) | **양쪽 모두**에 짝이 있는 행만 | 기본. 짝 없는 데이터가 의미 없을 때 |
| **`LEFT JOIN`** | **왼쪽 전부** + 짝이 있으면 오른쪽 (없으면 NULL) | **"0건인 대상도 보여야 할 때"** ★ |
| `RIGHT JOIN` | 오른쪽 전부 + 짝 | 거의 안 씀 (테이블 순서를 바꿔 `LEFT` 로) |
| `FULL OUTER JOIN` | 양쪽 전부 | 두 시스템 데이터 대조 |
| `CROSS JOIN` | 모든 조합 (행수 = M × N) | 달력·격자 만들 때. 실수로 쓰면 재앙 |

```
customers (12)          orders (30)
   ●─────────────────────── ● ●        ← 짝이 있는 고객 10명 / 주문 30건
   ●─────────────────────── ●
   ●  (오세훈 · 주문 없음)
   ●  (신유진 · 주문 없음)

INNER JOIN  →  30행   (주문이 있는 짝만)
LEFT  JOIN  →  32행   (30 + 짝 없는 고객 2명, 주문 열은 NULL)
```

**`LEFT JOIN` 의 존재 이유**는 [Day 033](day-033.md)에서 만난 문제입니다.
`GROUP BY customer_id` 로 고객별 주문 수를 셌더니 **주문이 0건인 고객 2명이 결과에서 통째로 사라졌습니다.**
"미구매 회원", "판매 이력 없는 상품", "결제 실패한 사용자" — **비즈니스에서 중요한 건 대개 0인 쪽**입니다.

### 조인 키의 관계 — 행 수가 어떻게 변하는가 ★

오늘의 핵심입니다. **조인은 행 수를 바꿉니다.**

| 관계 | 뜻 | 조인 결과 행 수 |
|---|---|---|
| **1 : 1** | 양쪽 다 유일 | 그대로 |
| **1 : N** | 왼쪽 1개에 오른쪽 여러 개 | **오른쪽 기준으로 늘어남** |
| **N : M** | 양쪽 다 여러 개 | **곱셈으로 폭발** |

`shop` 데이터베이스에서는 이렇습니다.

```
customers 12행
     │ 1 : N   (고객 1명 → 주문 여러 건)
orders    30행                 ← customers JOIN orders = 30행
     │ 1 : N   (주문 1건 → 상세 여러 줄)
order_items 47행               ← 위에 또 조인하면 47행
```

**고객 정보가 47번 반복됩니다.** 김민수 님은 주문 5건에 상세 8줄이므로 **8번** 나타납니다.

그래서 이런 일이 벌어집니다.

```sql
SELECT c.name, COUNT(o.order_id) AS 주문수
FROM customers c
JOIN orders o       ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
GROUP BY c.customer_id, c.name;
--   김민수의 주문수 = 8   ← 실제로는 5건!
```

이것을 **팬아웃(fan-out) 문제** 또는 **조인 중복**이라고 합니다.
**에러가 안 납니다.** 그냥 숫자가 틀립니다. 그리고 대개 **부풀어 오릅니다.**

| 증상 | 방어법 |
|---|---|
| 건수가 뻥튀기 | `COUNT(DISTINCT o.order_id)` |
| 금액이 뻥튀기 | **먼저 집계한 뒤 조인** (서브쿼리 / CTE — [Day 036](day-036.md)) |
| 원인 진단 | 조인 전후 **행 수를 세어 비교** |

> **조인하기 전에 항상 확인하세요.**
> ① 조인 키가 오른쪽 테이블에서 **유일한가?** → 유일하면 행 수가 안 늘어납니다.
> ② 조인 후 `COUNT(*)` 가 조인 전과 같은가? → 다르면 1:N입니다. 그 자체는 정상이지만, **집계할 때 조심해야 한다는 신호**입니다.

### `ON` 조건과 `WHERE` 조건의 차이

`INNER JOIN` 에서는 둘이 같습니다. 하지만 **`LEFT JOIN` 에서는 완전히 다릅니다.**

```sql
-- A. ON 에 조건 → LEFT JOIN 유지 (12명 전부 나옴, 조건 밖은 NULL)
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'delivered'

-- B. WHERE 에 조건 → 사실상 INNER JOIN (NULL 행이 조건에 걸려 탈락)
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'delivered'
```

**B는 `LEFT JOIN` 이라고 써 놓고 `INNER JOIN` 처럼 동작합니다.**
짝이 없는 고객의 `o.status` 는 `NULL` 이고, `NULL = 'delivered'` 는 참이 아니므로 탈락하기 때문입니다.
([Day 032](day-032.md)에서 배운 NULL의 성질이 여기서 다시 나옵니다.)

| 목적 | 어디에 조건을 쓰나 |
|---|---|
| **오른쪽 테이블을 걸러내되 왼쪽은 다 보고 싶다** | `ON` |
| 조인 결과 전체에서 걸러내고 싶다 | `WHERE` |
| 짝이 **없는 것만** 찾고 싶다 (안티 조인) | `WHERE 오른쪽.키 IS NULL` |

### 안티 조인 — "없는 것" 찾기

```sql
SELECT c.name
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;     -- 짝이 없어서 NULL인 행만
```

"한 번도 주문하지 않은 고객", "팔린 적 없는 상품", "로그인만 하고 결제 안 한 사용자" — 전부 이 패턴입니다.

### `USING` — 열 이름이 같을 때

```sql
JOIN products p ON oi.product_id = p.product_id
JOIN products p USING (product_id)      -- 같은 뜻, 더 짧음
```

`USING` 은 결과에서 조인 키를 **한 번만** 보여 줍니다. 열 이름이 정확히 같을 때만 쓸 수 있습니다.

**행 수를 반드시 확인합니다.**

shop=# SELECT COUNT(*) FROM orders;

### Step 3. 세 테이블 연결 — 카테고리별 매출

`order_items` → `products`(카테고리) + `orders`(주문 상태) 를 동시에 봐야 합니다.

```
shop=# SELECT p.category,
shop-#        COUNT(DISTINCT o.order_id)       AS 주문건수,
shop-#        SUM(oi.quantity)                 AS 판매수량,
shop-#        SUM(oi.quantity * oi.unit_price) AS 매출
shop-# FROM order_items oi
shop-# JOIN orders   o ON oi.order_id   = o.order_id
shop-# JOIN products p ON oi.product_id = p.product_id
shop-# WHERE o.status <> 'cancelled'
shop-# GROUP BY p.category
shop-# ORDER BY 매출 DESC;
 category | 주문건수 | 판매수량 |  매출
----------+----------+----------+---------
 전자기기 |       15 |       23 | 2085000
 사무용품 |       11 |       34 |  382500
 생활용품 |        8 |       16 |  329000
(3 rows)
```

**검산** — 매출 합계 `2085000 + 382500 + 329000 = 2796500`.
전체 매출 3,073,500에서 취소된 두 건(259,000 + 18,000 = 277,000)을 뺀 값과 일치합니다. ✅

> **주문건수 합(15+11+8=34)이 취소 제외 주문 28건보다 큰 것은 정상입니다.**
> 한 주문에 여러 카테고리 상품이 담기면 그 주문이 카테고리마다 한 번씩 세어지기 때문입니다.
> `COUNT(DISTINCT o.order_id)` 는 **그룹 안에서만** 중복을 제거합니다. 그룹을 넘나드는 중복은 못 없앱니다.
> 이런 값은 "카테고리를 구매한 주문 수"라고 불러야지 "주문 수"라고 부르면 안 됩니다.

### Step 5. `LEFT JOIN` — 0건인 고객까지 ★

```
shop=# SELECT c.name AS 고객,
shop-#        COUNT(DISTINCT o.order_id)                    AS 주문수,
shop-#        COALESCE(SUM(oi.quantity * oi.unit_price), 0) AS 총구매액
shop-# FROM customers   c
shop-# LEFT JOIN orders      o  ON c.customer_id = o.customer_id
shop-#                         AND o.status <> 'cancelled'
shop-# LEFT JOIN order_items oi ON o.order_id    = oi.order_id
shop-# GROUP BY c.customer_id, c.name
shop-# ORDER BY 총구매액 DESC, c.customer_id;
  고객  | 주문수 | 총구매액
--------+--------+----------
 윤도현 |      3 |   682000
 최수아 |      3 |   621000
 이서연 |      5 |   464900
 김민수 |      5 |   299200
 정우진 |      3 |   237000
 조은비 |      2 |   170000
 강하은 |      2 |   126000
 한지민 |      2 |   112000
 임채원 |      2 |    56600
 박지훈 |      1 |    27800
 오세훈 |      0 |        0
 신유진 |      0 |        0
(12 rows)
```

**12명 전부 나왔습니다.** 두 가지가 핵심입니다.

| 기법 | 없으면 |
|---|---|
| `LEFT JOIN` | 주문 0건인 고객이 사라짐 |
| **`AND o.status <> 'cancelled'` 를 `ON` 에** | `WHERE` 에 쓰면 `LEFT JOIN` 이 `INNER JOIN` 이 됨 |
| `COALESCE(SUM(...), 0)` | 구매액이 `NULL` 로 표시됨 |
| `COUNT(DISTINCT o.order_id)` | `COUNT(*)` 는 짝 없는 행도 1로 세어 **주문 0건이 1건**이 됨 |

`WHERE` 에 뒀을 때 무슨 일이 생기는지 직접 확인합니다.

```
shop=# SELECT COUNT(*) FROM (
shop(#   SELECT c.customer_id
shop(#   FROM customers c
shop(#   LEFT JOIN orders o ON c.customer_id = o.customer_id
shop(#   WHERE o.status <> 'cancelled'
shop(#   GROUP BY c.customer_id
shop(# ) t;
 count
-------
    10
(1 row)
```

**12명이 아니라 10명입니다.** `LEFT JOIN` 이라고 써 놓고 `INNER JOIN` 을 한 셈입니다.
짝이 없는 고객의 `o.status` 는 NULL이고, `NULL <> 'cancelled'` 는 참이 아니라 탈락하기 때문입니다.

## ⑤ 자주 하는 실수

### `column reference "customer_id" is ambiguous`

```
shop=# SELECT customer_id, name FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
ERROR:  column reference "customer_id" is ambiguous
LINE 1: SELECT customer_id, name FROM orders o JOIN customers c ON o....
               ^
```

**원인** — 양쪽 테이블에 같은 이름의 열이 있어서 어느 쪽인지 모릅니다.
**해결** — `c.customer_id` 처럼 **별칭을 붙입니다.** 조인 쿼리에서는 **모든 열에 항상** 붙이는 것을 습관으로 하세요.

### 결과가 몇 배로 부풀어 있습니다 (팬아웃) ★

```sql
SELECT c.name, COUNT(o.order_id) FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY c.customer_id, c.name;      -- 이서연: 10 (실제 5)
```

**원인** — 1:N 조인으로 왼쪽 행이 복제됐습니다. **에러가 안 납니다.**
**해결** — 셋 중 하나.

```sql
COUNT(DISTINCT o.order_id)                       -- ① 건수라면 DISTINCT
JOIN (SELECT order_id, SUM(...) ... GROUP BY order_id) t  -- ② 금액이라면 먼저 집계
-- ③ 애초에 그 테이블을 조인할 필요가 있었는지 다시 본다
```

**진단법** — 조인을 하나씩 추가하며 `SELECT COUNT(*)` 를 찍어 보세요. 늘어난 지점이 범인입니다.

### `LEFT JOIN` 했는데 왼쪽 행이 사라집니다

```sql
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status <> 'cancelled'        -- ← 여기
```

**원인** — 짝이 없는 행의 `o.status` 는 `NULL` 이고, `NULL <> 'cancelled'` 는 참이 아니라 `WHERE` 에서 탈락합니다.
**해결** — 오른쪽 테이블 조건은 **`ON` 절로** 옮깁니다.

```sql
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status <> 'cancelled'
```

**구분법** — "왼쪽을 다 보고 싶은 조건"이면 `ON`, "조인 결과 전체를 거르는 조건"이면 `WHERE`.

### `LEFT JOIN` 인데 0이 아니라 1로 세어집니다

```sql
SELECT c.name, COUNT(*) FROM customers c LEFT JOIN orders o ON ... GROUP BY ...;
-- 오세훈: 1  (주문 0건인데!)
```

**원인** — `COUNT(*)` 는 **행**을 셉니다. 짝이 없어도 왼쪽 행 하나는 남아 있으므로 1이 됩니다.
**해결** — `COUNT(o.order_id)` — **오른쪽 테이블의 열**을 세면 NULL은 안 세어져 0이 됩니다.

### 합계가 `NULL` 로 나옵니다

```
 오세훈 |      0 |
```

**원인** — `SUM` 할 값이 하나도 없으면 결과는 0이 아니라 `NULL` 입니다.
**해결** — `COALESCE(SUM(...), 0)`. 리포트·대시보드에 넘기는 쿼리에는 **항상** 감싸세요.

### `ON` 을 빠뜨려 모든 조합이 나옵니다

```
shop=# SELECT COUNT(*) FROM customers c, orders o;
 count
-------
   360
(1 row)
```

**원인** — `12 × 30 = 360`. 조인 조건이 없으면 **모든 조합**(CROSS JOIN)이 만들어집니다.
쉼표 조인(`FROM a, b`) 문법에서 특히 잘 생깁니다.
**해결** — **항상 `JOIN ... ON ...` 형태로 쓰세요.** `ON` 을 빠뜨리면 문법 에러가 나서 바로 잡힙니다.

실무 테이블에서 이 실수를 하면 100만 × 100만 = 1조 행을 계산하려다 서버가 멈춥니다.

### 조인 키의 타입이 달라 안 붙습니다

```
ERROR:  operator does not exist: integer = text
LINE 3:   ON o.customer_id = c.customer_id
                           ^
HINT:  No operator matches the given name and argument types.
```

**원인** — 한쪽은 숫자, 한쪽은 문자열입니다. 외부 CSV를 적재하면 흔히 생깁니다 ([Day 043](day-043.md)).
**해결** — 임시로는 `o.customer_id = c.customer_id::integer`, **근본적으로는 적재할 때 타입을 맞춥니다.**
캐스팅으로 조인하면 인덱스를 못 쓰기 때문입니다 ([Day 038](day-038.md)).

### 조인 후 행 수가 줄었습니다

`INNER JOIN` 을 했는데 30행이 25행이 된 경우입니다.

**원인** — 짝이 없는 행이 버려졌습니다. 외래키가 NULL이거나, 참조 대상이 삭제됐거나, 키 값이 안 맞습니다.
**해결** — 진짜 없는 것인지 확인합니다.

```sql
SELECT COUNT(*) FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;      -- 짝 없는 주문 수
```

**조인 전후 행 수를 비교하는 습관** 하나로 이 종류의 사고를 전부 잡을 수 있습니다.

## ⑥ 확인 문제

**1.** 아래 쿼리는 이서연 님의 주문을 10건으로 표시합니다. 실제로는 5건입니다. 원인을 설명하고 두 가지 방법으로 고치세요.

```sql
SELECT c.name, COUNT(o.order_id) AS 주문수, SUM(oi.quantity * oi.unit_price) AS 구매액
FROM customers c
JOIN orders o       ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
GROUP BY c.customer_id, c.name;
```

<details>
<summary>답 보기</summary>

**원인 — 팬아웃(조인 중복).**
`orders` 와 `order_items` 는 1:N 입니다. 주문 한 건이 상세 줄 수만큼 복제되면서 `orders` 쪽 행이 여러 번 세어집니다.

```
이서연의 주문:  2번(상세 2줄) · 7번(2) · 14번(2) · 23번(3) · 30번(1)
조인 결과 행:   2+2+2+3+1 = 10행  →  COUNT(o.order_id) = 10
```

**구매액(`SUM`)은 맞습니다.** 상세 줄마다 금액이 다르므로 중복 없이 더해집니다.
**건수만 틀립니다.** 이렇게 **같은 쿼리 안에서 어떤 값은 맞고 어떤 값은 틀린 것**이 팬아웃을 무서운 버그로 만듭니다.

**해결 ① `COUNT(DISTINCT ...)`**

```sql
SELECT c.name, COUNT(DISTINCT o.order_id) AS 주문수,
       SUM(oi.quantity * oi.unit_price) AS 구매액
FROM customers c
JOIN orders o       ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id    = oi.order_id
GROUP BY c.customer_id, c.name;
```

**해결 ② 먼저 집계한 뒤 1:1로 조인**

```sql
SELECT c.name, COUNT(*) AS 주문수, SUM(t.주문금액) AS 구매액
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN (SELECT order_id, SUM(quantity * unit_price) AS 주문금액
      FROM order_items GROUP BY order_id) t
  ON o.order_id = t.order_id
GROUP BY c.customer_id, c.name;
```

②가 더 좋은 이유 — `COUNT(DISTINCT)` 는 느리고, 집계 대상이 여러 개가 되면 전부에 `DISTINCT` 를 붙여야 합니다.
**"집계는 조인 전에 끝낸다"** 를 원칙으로 삼으세요.
</details>

**2.** 아래 두 쿼리는 결과 행 수가 다릅니다. 각각 몇 행이며, 왜 다른가요?

```sql
-- A
SELECT c.name, o.status FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'delivered';

-- B
SELECT c.name, o.status FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'delivered';
```

<details>
<summary>답 보기</summary>

**A는 23행, B는 21행입니다.**

**A** — `ON` 에 조건이 있으므로 조인 단계에서 `delivered` 인 주문만 짝지어집니다.
`LEFT JOIN` 이니 **짝을 못 찾은 고객도 남습니다.**

```
delivered 주문 21건            → 21행
배송완료 주문이 하나도 없는 고객 → 오세훈, 신유진  → 2행 (status 는 NULL)
합계 23행
```

**B** — 조인은 전체(32행: 주문 30 + 짝 없는 고객 2)로 하고 나서 `WHERE o.status = 'delivered'` 로 거릅니다.
짝 없는 고객의 `o.status` 는 `NULL` 이고 `NULL = 'delivered'` 는 참이 아니므로 **탈락**합니다.
결과는 `INNER JOIN` 과 같은 **21행**.

| | 조인 시점 | 필터 시점 | 결과 |
|---|---|---|---|
| A (`ON`) | delivered만 짝지음 | — | 23행 (**고객 12명 전부** 등장) |
| B (`WHERE`) | 전부 짝지음 (32행) | NULL 행 탈락 | 21행 (고객 10명) |

**실무에서의 의미** — "고객별 배송완료 건수" 대시보드를 B로 만들면
**배송완료가 0건인 고객이 목록에서 사라집니다.** 이탈 징후를 봐야 할 대상이 정확히 그 사람들입니다.
</details>

**3.** "카테고리별 매출"을 구하려고 아래처럼 썼더니 매출이 이상하게 큽니다. 무엇이 문제인가요?

```sql
SELECT p.category, SUM(p.price * oi.quantity) AS 매출
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category;
```

<details>
<summary>답 보기</summary>

**문제 — `p.price`(현재 정가)를 쓰고 있습니다. `oi.unit_price`(주문 당시 가격)를 써야 합니다.**

지금 샘플 데이터는 두 값이 같아서 결과가 우연히 일치합니다. 하지만 실제 서비스에서는 다릅니다.

```
2025-01-05  모니터를 259,000원에 판매  →  order_items.unit_price = 259000
2025-06-01  가격을 299,000원으로 인상  →  products.price        = 299000

p.price 로 계산하면 → 1월 매출이 갑자기 늘어남 ★ 과거 매출이 바뀝니다
```

**과거의 매출은 절대 변하면 안 됩니다.** 그래서 [Day 031](day-031.md)에서 `unit_price` 를 따로 저장한 것입니다.

```sql
SELECT p.category, SUM(oi.quantity * oi.unit_price) AS 매출
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category;
```

**두 번째 문제** — 취소 주문이 포함돼 있습니다. `orders` 를 조인해 `WHERE o.status <> 'cancelled'` 를 걸어야
"실제 매출"이 됩니다. (2,344,000 → 2,085,000 처럼 카테고리별로 달라집니다.)

**교훈** — 조인은 "붙일 수 있는 열"을 잔뜩 늘려 줍니다. 그중 **어느 열이 이 계산의 정답인지**는
데이터 모델을 이해해야만 알 수 있습니다. 문법보다 이쪽이 훨씬 중요합니다.
</details>

## 오늘의 정리

| 구문 | 하는 일 |
|---|---|
| `JOIN b ON a.k = b.k` | 양쪽에 짝이 있는 행만 (`INNER`) |
| `LEFT JOIN b ON ...` | 왼쪽 전부 + 짝 (없으면 NULL) |
| `LEFT JOIN b ON ... AND 조건` | 오른쪽만 걸러내고 **왼쪽은 유지** |
| `WHERE b.키 IS NULL` | 안티 조인 — **짝이 없는 것만** |
| `COUNT(DISTINCT a.id)` | 팬아웃 상황에서 건수 세기 |
| `COUNT(b.열)` | `LEFT JOIN` 에서 0을 0으로 세기 |
| `COALESCE(SUM(...), 0)` | 값이 없을 때 NULL 대신 0 |
| `JOIN (SELECT ... GROUP BY ...) t ON ...` | **집계 후 조인** — 팬아웃 근본 해결 |

| 원칙 | 이유 |
|---|---|
| **조인 전후 `COUNT(*)` 를 비교한다** | 팬아웃을 잡는 유일한 진단법 |
| **집계는 조인 전에 끝낸다** | 행이 안 늘어난 상태에서 더해야 정확 |
| **오른쪽 테이블 조건은 `ON` 에** | `WHERE` 에 쓰면 `LEFT JOIN` 이 무력화 |
| **모든 열에 테이블 별칭을 붙인다** | 모호성 에러 방지 + 읽기 쉬움 |
| **다른 경로로 구한 숫자와 검산한다** | 조인 결과를 신뢰할 수 있는 유일한 방법 |

**오늘의 습관** — 조인을 하나 추가할 때마다 `SELECT COUNT(*)` 를 찍어 보세요.
**행 수가 언제 늘어났는지 아는 사람만 집계를 믿을 수 있습니다.**
