**오전 (4h)**

- 새 프로젝트 생성 (3D · URP 템플릿)
- 에디터 인터페이스 — Scene / Game / Hierarchy / Inspector / Project / Console
- 씬 뷰 조작 (궤도·팬·줌, F로 포커스, 기즈모)
- Transform — Position / Rotation / Scale, 부모-자식 관계와 로컬/월드 좌표

**오후 (4h)**
- **GameObject + Component 구조** — Part 2의 상속 구조와 무엇이 다른가

**모노스페이스 도해 — 상속 vs 조합**
```
   [Part 2 · 상속]                    [Unity · 조합]

        GameObject                      GameObject "Player"
             ▲                            ├─ Transform
      ┌──────┼──────┐                     ├─ MeshRenderer
   Player  Enemy  Bullet                  ├─ Rigidbody
                                          ├─ Collider
   "무엇인가"로 분류                       └─ PlayerController (내 스크립트)

                                       "무엇을 가지고 있는가"로 조립
                                       → 클래스 폭발이 없다
```

- 기본 도형 배치, 머티리얼 만들어 색 입히기
- 프로젝트 폴더 구조 규칙 (`Scenes/`, `Scripts/`, `Prefabs/`, `Materials/`, `Art/`)
- 실습: 바닥 + 큐브 + 조명 + 카메라로 간단한 씬 구성

**✅ 실행 결과** — 씬에 바닥과 큐브가 놓이고, Play 버튼을 누르면 Game 뷰에 카메라 시점으로 그 장면이 보인다. 각자 만든 머티리얼 색이 적용돼 있다.

**🔧 막히면**
- 버전이 다름 → **즉시 통일**. 나중에 프로젝트를 열 수 없게 된다
- Game 뷰가 검음 → 카메라가 없거나 방향이 반대, 또는 조명 없음
- 씬 저장이 안 됨 → `Scenes/` 폴더에 저장하고 Build Settings에 등록

### Day 72 · C# 스크립트와 MonoBehaviour 생명주기

| | |
|---|---|
| **연결 문서** | 13 런닝 게임 — Step 1 |
| **오늘의 목표** | 스크립트를 붙여 오브젝트를 코드로 움직인다 |

**오전 (4h)**
- C# 기초 — C++와 다른 점 (가비지 컬렉션, `class`만 존재, 속성, `var`)
- `MonoBehaviour` 상속과 컴포넌트로서의 스크립트
- **생명주기** — `Awake` → `OnEnable` → `Start` → `Update` → `LateUpdate` → `OnDisable` → `OnDestroy`
- `Update`는 Part 2의 `Core::Update()`와 같은 자리

**모노스페이스 도해 — 생명주기와 Part 2 대응**
```
   Unity                        Part 2 프레임워크
   ─────────────────────────────────────────────
   Awake()      1회, 가장 먼저   Core::Init()
   Start()      1회, Update 전   Scene::Init()
   Update()     매 프레임        Core::Update(dt)
   LateUpdate() 매 프레임 끝     (카메라 추적 등)
   FixedUpdate() 물리 고정 간격  (Part 2엔 없던 개념)
   OnDestroy()  파괴 시          Core::Release()
```

- `Time.deltaTime` — Part 2에서 직접 만든 델타 타임이 이미 들어 있다
- `Debug.Log` 로 실행 순서 확인

**오후 (4h)**
- Inspector 노출 — `public` 필드 / `[SerializeField] private`
- 컴포넌트 참조 — `GetComponent<T>()`, 캐싱의 중요성
- `FixedUpdate`와 물리 — `Update`에서 물리를 만지면 안 되는 이유
- 코루틴 소개 (`IEnumerator`, `yield return`)
- 실습: 큐브를 좌우로 왕복시키기 (속도를 Inspector에서 조절)

**✅ 실행 결과** — Console 창에 `Awake → Start → Update…` 순서가 찍히고, 큐브가 Inspector에서 지정한 속도로 좌우로 왕복한다. 속도를 플레이 중에 바꾸면 즉시 반영된다.

**🔧 막히면**
- 스크립트가 안 붙음 → 파일명과 클래스명 불일치
- 값이 Inspector에 안 보임 → `private`에 `[SerializeField]` 누락
- 프레임마다 속도가 다름 → `Time.deltaTime` 미적용 (Part 2에서 겪은 그 문제)
- `GetComponent`를 `Update`에서 호출 → 성능 저하. `Awake`에서 캐싱

### Day 73 · 입력과 물리 — Rigidbody, Collider, Trigger

| | |
|---|---|
| **연결 문서** | 13 런닝 게임 — Step 2 |
| **오늘의 목표** | 캐릭터가 달리고 점프하며 바닥에 착지한다 |

**오전 (4h)**
- 입력 처리 (`Input.GetKey` / `GetKeyDown` / `GetAxis`) — Part 2 입력 매니저의 3상태와 동일
- `Rigidbody` — 질량, 항력, 중력, `isKinematic`
- 이동 방식 3종 비교 — `transform.Translate` / `rigidbody.velocity` / `AddForce`
- 점프 구현 (`AddForce(Vector3.up, ForceMode.Impulse)`)

**오후 (4h)**
- `Collider` 종류와 **`isTrigger`** 의 차이

**표 — Collision vs Trigger**

| | Collision | Trigger |
|---|---|---|
| 물리적으로 막히나 | O | X (통과) |
| 콜백 | `OnCollisionEnter/Stay/Exit` | `OnTriggerEnter/Stay/Exit` |
| 쓰는 곳 | 바닥, 벽 | 아이템 획득, 감지 범위 |
| Part 2 대응 | AABB + 위치 보정 | AABB 판정만 |

- 바닥 판정 — Raycast 또는 트리거 방식
- 레이어와 충돌 매트릭스 (Part 2의 "그룹별 충돌"이 설정으로 존재)
- 실습: 아이템 트리거로 점수 획득, 장애물 충돌로 게임오버

**✅ 실행 결과** — 스페이스로 점프하면 캐릭터가 뛰어올랐다가 중력으로 착지하고, 공중에서 다시 눌러도 뛰지 않는다. 코인 위를 지나면 코인이 사라지며 Console에 점수가 찍힌다.

**🔧 막히면**
- 물체를 뚫고 지나감 → 속도가 빠를 때. Rigidbody의 Collision Detection을 `Continuous`로
- 트리거가 안 불림 → 양쪽 중 하나에 Rigidbody 필요, `isTrigger` 체크 확인
- 점프가 무한 → 바닥 판정 없이 입력만 처리
- 캐릭터가 넘어짐 → Rigidbody Constraints에서 회전 고정

### Day 76 · Canvas와 RectTransform

| | |
|---|---|
| **연결 문서** | 14 보드게임 — Step 0~1 |
| **오늘의 목표** | 창 크기를 바꿔도 UI가 제자리를 지킨다 |

**오전 (4h)**
- **막히는 상황**: 해상도를 바꾸니 버튼이 화면 밖으로 나갔다
- Canvas Render Mode 3종 — Screen Space Overlay / Camera / World Space
- **Canvas Scaler** — `Scale With Screen Size` + 기준 해상도 설정 (해상도 대응의 핵심)
- **RectTransform** — Transform과 무엇이 다른가

**모노스페이스 도해 — 앵커와 피벗**
```
   앵커(Anchor) = 부모의 어디에 붙을 것인가
   피벗(Pivot)  = 자기 자신의 어느 점을 기준으로 할 것인가

   ┌─────────────────────────┐    앵커 = 좌상단        ┌───────────────────────────────┐
   │ ▣                       │    → 창이 커져도        │ ▣                             │
   │                         │      좌상단에 붙어 있음  │                               │
   │                    ▣    │                        │                            ▣  │
   └─────────────────────────┘    앵커 = 우하단        └───────────────────────────────┘
                                  → 우하단을 따라감

   앵커를 늘려서(stretch) 잡으면 → 부모 크기에 맞춰 늘어난다
```

- 앵커 프리셋 / Alt·Shift 조합 단축키
- 실습: 좌상단 체력바, 우하단 버튼, 상단 전체 늘어나는 헤더 만들고 창 크기 조절 테스트

**오후 (4h)**
- UI 컴포넌트 — Image, TextMeshPro, Button, Slider, Toggle
- TMP 한글 폰트 애셋 만들기 (**한글은 별도 폰트 애셋 필수**)
- 버튼 이벤트 연결 (Inspector 방식 / 코드 방식)
- 실습: 카드 게임 화면 레이아웃 뼈대 (상대 영역 / 필드 / 내 손패 / 정보 패널)

**✅ 실행 결과** — 창 크기를 자유롭게 바꿔도 체력바는 좌상단에, 버튼은 우하단에 붙어 있고, 헤더는 폭에 맞춰 늘어난다. 한글 텍스트가 깨지지 않는다.

**🔧 막히면**
- 한글이 네모로 나옴 → TMP Font Asset 미생성. 한글 폰트로 애셋 만들고 Atlas 설정
- 해상도 바꾸면 다 어긋남 → Canvas Scaler가 `Constant Pixel Size`
- 앵커를 옮겼는데 위치가 튐 → 피벗과 앵커를 혼동. 둘의 역할 재확인

### Day 82 · Animator Controller — 메카님 ★

| | |
|---|---|
| **연결 문서** | 15 액션 게임 — Step 1 |

**오전 (4h)**
- **Part 2 Day 46의 FSM이 GUI로 들어 있다** — 상태 = 노드, 전이 = 화살표
- Animator Controller 만들기 / Animator 컴포넌트 연결
- 상태(State) 배치 및 기본 상태(Entry → Default) 설정
- **파라미터** 4종 — Float / Int / Bool / **Trigger**
- 전이(Transition) 조건 설정

**모노스페이스 도해 — 상태 전이표와 메카님의 대응**
```
   [Part 2 Day 46 · 손으로 짠 표]        [Unity 메카님]

   IDLE  --이동입력--> WALK              ┌──────┐  Speed > 0.1   ┌──────┐
   WALK  --입력없음--> IDLE              │ Idle │ ─────────────▶ │ Walk │
   IDLE  --공격키--> ATTACK              └──────┘ ◀───────────── └──────┘
   ATTACK --애니끝--> IDLE                   │      Speed < 0.1      │
                                             │ Attack(Trigger)       │
                                             ▼                       │
                                          ┌────────┐                 │
                                          │ Attack │ ◀───────────────┘
                                          └────────┘
                                             │ Exit Time (애니 종료)
                                             └──▶ Idle
```

- 코드에서 파라미터 제어 (`animator.SetFloat("Speed", …)`, `SetTrigger("Attack")`)
- **Has Exit Time** 의 의미 — 체크하면 현재 애니가 끝나야 전이한다

**오후 (4h)**
- 전이 시간(Transition Duration)과 블렌딩 — 뚝뚝 끊기지 않게
- Any State 활용 (피격은 어느 상태에서든 가능)
- 레이어와 아바타 마스크 (상체는 공격, 하체는 이동)
- 실습: Idle / Walk / Run / Attack / Hit 5개 상태로 컨트롤러 완성

**✅ 실행 결과** — 방향키를 누르면 캐릭터가 걷기 모션으로 부드럽게 전환되고, 놓으면 대기로 돌아온다. 공격 키를 누르면 공격 모션이 끝까지 재생된 뒤 대기로 복귀한다.

**🔧 막히면**
- 전이가 안 됨 → 파라미터 이름 오타 (문자열이라 컴파일 오류가 안 난다). `Animator.StringToHash` 권장
- 공격이 반복 재생 → Trigger를 `SetBool`로 처리했거나 Trigger 소비 안 됨
- 전환이 뚝뚝 끊김 → Transition Duration이 0
- 조건 없이 즉시 넘어감 → Has Exit Time 체크 상태 확인

- 에디터에서 점 배치 및 기즈모 시각화 (`OnDrawGizmos`)
- 점 사이 보간 — 선형 vs 스플라인(Catmull-Rom)

**모노스페이스 도해 — 웨이포인트와 선행 지점**
```
   트랙 위 경로 점군

     P0 ── P1 ── P2 ── P3
                        ╲
                         P4      ← 선행 지점(lookahead) = 현재 위치 기준 N개 앞
                          ╲
                           P5

   조향     = (선행 지점 방향) - (현재 진행 방향)
   목표 속도 = 최대속도 × (1 - 각도차 / 180)

   각도차가 크다 = 코너다 → 미리 감속
```

**오후 (4h)**
- 경로 데이터를 ScriptableObject 또는 JSON으로 저장 (Day 78~79 재사용)
- 현재 위치에서 가장 가까운 경로 점 찾기 (진행 방향 고려한 탐색)
- 트랙 이탈 판정 (경로에서의 수직 거리 > 트랙 폭)
- 실습: 트랙 1바퀴에 점 40~60개 배치하고 스플라인으로 부드럽게 연결

**✅ 실행 결과** — 씬 뷰에 트랙을 따라 점들과 연결선, 각 점의 진행 방향 화살표가 표시된다. 차량이 코스를 벗어나면 화면에 "코스 이탈" 경고가 뜬다.

**🔧 막히면**
- 점 순서가 꼬임 → 자식 오브젝트 이름 정렬 또는 인덱스 명시
- 가장 가까운 점을 잘못 찾음 (역주행 판정) → 진행 방향과의 내적으로 후보 필터링
- 스플라인이 튐 → Catmull-Rom의 양 끝점 처리 (첫/마지막 점 중복)
