## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 사고 상황을 듣고 **revert / reset / restore / reflog** 중 맞는 도구를 고를 수 있다 — 기준은 단 하나, "공유했는가".
- `reset` 의 세 모드(soft/mixed/hard)가 각각 **무엇까지 되돌리는지** 표로 그릴 수 있다.
- `rebase -i` 로 push 전의 지저분한 커밋들을 **합치고·고치고·버릴** 수 있다.
- `--force` 대신 `--force-with-lease` 를 쓰는 이유를 설명하고, reflog로 "날린" 커밋을 구조할 수 있다.

## ② 왜 필요한가

이번 주 내내 예고한 어음을 오늘 갚습니다 — Day 107의 "강제 push는 Day 109에서",
Day 108의 "main 직행 사고 구제는 Day 109에서". 팀 저장소에서 실제로 벌어지는 사고 목록을 보죠:

| 사고 | 잘못된 대응 (실화) | 오늘 배울 대응 |
|---|---|---|
| 버그 커밋이 main에 병합됨 | main에서 코드를 손으로 고쳐 재커밋 | `revert` 한 방 |
| "wip", "오타", "진짜최종" 커밋 7개로 PR | 그대로 PR → 리뷰어 고통 | push 전 `rebase -i` 로 정리 |
| `.env` 를 커밋해 버림 | 지운 커밋을 하나 더 쌓고 안심 | 단계별 구제 + **키 폐기** |
| `reset --hard` 로 어제 작업 증발 | 저장소 삭제, 처음부터 | `reflog` 구조대 |

공통 패턴이 보입니까 — 사고 자체보다 **잘못된 수습이 피해를 키웁니다.** Git은 커밋된 것을
거의 잃어버리지 않는 도구라서, 도구를 아는 사람에게 대부분의 사고는 10분짜리입니다.
운영 단원(W23~)로 넘어가기 전에 이 목록을 끝내는 이유입니다 — **서버 위에서 사고 나면
"저장소 삭제하고 다시"가 통하지 않으니까요.**

## ③ 개념 설명

### 도구 선택의 유일한 기준 — 공유했는가

| 상황 | 공유 여부 | 도구 | 성질 |
|---|---|---|---|
| main에 들어간 잘못된 커밋 취소 | **공유됨** | `git revert <커밋>` | 반대 커밋을 **추가** (역사 보존) |
| 내 로컬 커밋을 없던 것으로 | 나만 가짐 | `git reset` | 역사를 **되감기** |
| 내 로컬 커밋들을 정리(합치기·고치기) | 나만 가짐 | `git rebase -i` | 역사를 **다시 쓰기** |
| 파일 하나만 과거 버전으로 | 무관 | `git restore --source <커밋> <파일>` | 작업 폴더만 변경 |
| 되감았다가 후회 — 커밋을 잃어버림 | 무관 | `git reflog` | HEAD 이동 일지에서 **구조** |

Day 107의 황금률이 여기서도 그대로 적용됩니다: **공유된 역사는 고치지 말고(revert로 추가),
나만의 역사는 마음껏 정리한다(reset·rebase -i).**

### revert — 취소를 "기록"하는 커밋

```
main   ●──●──B(버그)──●──R(B의 반대 커밋)
```

`git revert B` 는 B가 바꾼 것을 정확히 반대로 바꾸는 **새 커밋 R**을 만듭니다. B는 역사에 그대로 —
그래서 이미 B를 pull 해 간 팀원들과 아무 마찰이 없습니다. "언제 무엇이 잘못됐고 언제 걷어냈는지"까지
역사에 남는, **공유 브랜치에서 유일하게 안전한 취소**입니다. squash 병합을 쓰면 PR 하나 = 커밋
하나이므로, 문제 기능 전체를 revert 하나로 걷어낼 수 있습니다 (Day 107 Q3의 복선 회수).

### reset — 세 모드는 "어디까지 되돌리나"의 차이

`git reset <지점>` 은 브랜치 이름표를 과거로 옮깁니다. 모드는 **함께 되돌리는 범위**를 정합니다:

| 모드 | 브랜치 이름표 | 스테이징 | 작업 폴더 | 쓰임 |
|---|---|---|---|---|
| `--soft` | 이동 | 유지 | 유지 | 커밋만 무르고 다시 커밋 (메시지 고치기, 쪼개기) |
| `--mixed` (기본) | 이동 | 초기화 | 유지 | 커밋+add 를 무르되 **코드는 그대로** |
| `--hard` | 이동 | 초기화 | **초기화** | 전부 그 시점으로 — **미커밋 작업은 영구 소멸** ⚠️ |

hard만 위험한 이유가 표에 있습니다 — soft/mixed는 코드를 건드리지 않지만, hard는 작업 폴더까지
밀어 버립니다. 그리고 **커밋된 적 없는 것은 reflog로도 못 구합니다.**

### rebase -i — push 전 커밋 편집실

`git rebase -i <시작점>` 은 시작점 이후의 커밋 목록을 편집기로 열어 줍니다:

```
pick f30ab21 이미지 전처리 검증 추가
pick 9c40d1e wip
pick 22c8f01 오타
```

각 줄의 첫 단어를 바꿔 지시합니다:

| 명령 | 효과 |
|---|---|
| `pick` | 그대로 둠 |
| `reword` | 커밋은 유지, **메시지만** 고침 |
| `squash` | **위 커밋에 합침** (메시지도 합쳐서 편집) |
| `fixup` | 위 커밋에 합치되 메시지는 버림 — "오타"류에 최적 |
| `drop` (또는 줄 삭제) | 커밋 폐기 |

### force-with-lease — 자물쇠 달린 강제 push

정리(rebase·reset)를 하면 내 브랜치와 원격의 역사가 갈라져 push가 거절됩니다(Day 107 ⑤).
내 개인 브랜치라면 강제로 덮어써야 하는데, 두 명령의 차이가 팀의 안전을 가릅니다:

| 명령 | 하는 일 | 위험 |
|---|---|---|
| `--force` | 원격을 **무조건** 내 걸로 덮음 | 그 사이 팀원이 올린 커밋도 **말없이 증발** |
| `--force-with-lease` | 원격이 **내가 마지막으로 본 상태일 때만** 덮음 | 그 사이 누가 push 했으면 거절 — 사고 차단 |

lease(임대)라는 이름 그대로 — "내가 알던 상태"라는 조건부로만 강제합니다. **force를 쓸 일이
생기면 언제나 force-with-lease입니다.** (그리고 공유 브랜치라면 둘 다 금지 — 황금률.)

### reflog — HEAD가 지나온 모든 자리

`git log` 는 현재 브랜치의 조상만 보여 주지만, `git reflog` 는 **HEAD가 지나간 모든 지점**의
일지입니다 — reset으로 버린 커밋, 지운 브랜치의 끝, rebase 전의 원본까지. 커밋이 "사라졌다"는 말은
대부분 "가리키는 이름표가 없어졌다"는 뜻이라, reflog에서 해시를 찾아 이름표만 다시 붙이면 살아납니다.

## ④ 단계별 실습

훈련장은 `conflict-lab`, 실전 시나리오는 `mlops-mp3` 에서 진행합니다.

### Step 1. push 전 정리 — rebase -i (1~2교시)

mlops-mp3에서 브랜치를 따고, 일부러 지저분하게 3커밋을 만듭니다:

```powershell
git switch -c feature/batch-limit
# 코드 수정 1 …
git commit -am "배치 예측 상한 추가"
# 수정 2 …
git commit -am "wip"
# 수정 3 …
git commit -am "오타"
git rebase -i main
```

편집기에 커밋 목록이 뜨면 이렇게 고치고 저장합니다:

```
pick 3fc1a02 배치 예측 상한 추가
fixup 7be3d19 wip
fixup c25e480 오타
```

```
$ git rebase -i main
Successfully rebased and updated refs/heads/feature/batch-limit.
$ git log --oneline main..HEAD
e8a30f7 (HEAD -> feature/batch-limit) 배치 예측 상한 추가
```

3커밋이 의미 단위 1커밋으로. **아직 push 전이므로** 마음껏 허용되는 정리입니다 — 이제 push 하고
PR을 열면 리뷰어는 깨끗한 diff 하나만 봅니다.

### Step 2. 사고 시나리오 A — main에 들어간 버그 (3~4교시)

어제 병합한 PR에 버그가 있었다고 합시다 (업로드 제한을 실수로 0MB로!). main은 공유 역사 —
**revert** 입니다. 문제 커밋 해시를 log에서 찾아서:

```powershell
git switch main; git pull
git log --oneline -3
git revert b6f92d3
```

```
$ git log --oneline -3
b6f92d3 (HEAD -> main, origin/main) 업로드 제한 설정 정리 (#12)
41c8e07 health 응답에 model_version과 시작 시각 추가 (#11)
9f02c11 PR 템플릿 추가 (#10)
$ git revert b6f92d3
[main 4d1e8c2] Revert "업로드 제한 설정 정리 (#12)"
 1 file changed, 1 insertion(+), 1 deletion(-)
```

revert 커밋이 자동 생성됩니다 (메시지도 자동 — 어느 커밋의 취소인지 명시). push 하면 상황 종료 —
팀원 누구의 저장소와도 충돌하지 않고, 역사에는 "12번 PR이 들어왔고, 문제가 있어 걷어냈다"가
정직하게 남습니다. 실무라면 이 revert도 PR로 넣습니다 (급한 장애면 팀 규칙에 따라 직행 허용).

### Step 3. 사고 시나리오 B — 시크릿을 커밋 (5교시)

`.env` (DB 비밀번호가 든)를 실수로 커밋했습니다. **push 전/후가 완전히 다른 사고**입니다.

**push 전** — 로컬 역사이므로 되감으면 됩니다:

```powershell
git reset --mixed HEAD~1        # 커밋 취소, 파일은 작업 폴더에 남음
"`n.env" | Add-Content .gitignore
git add .gitignore; git commit -m ".env를 추적 제외에 추가"
```

`--mixed` 를 쓴 이유 — .env **파일 자체는 지우면 안 되고**(서버가 쓰는 진짜 설정), 커밋에서만
빠져야 하기 때문입니다. hard였다면 파일까지 날아갔습니다.

**push 후** — 순서가 생명입니다:

1. **그 비밀번호/키를 즉시 폐기·재발급** — 커밋을 지워도 이미 본 사람·봇이 있을 수 있습니다.
   GitHub의 공개 저장소 푸시는 수 분 내에 크롤러가 훑는다고 전제하세요.
2. revert는 **해결이 아닙니다** — 반대 커밋을 쌓아도 히스토리의 옛 커밋에 시크릿이 그대로 남습니다.
3. 히스토리 자체에서 제거하는 절차(`git filter-repo`)는 [Git 과정 고급](../../../complate/Git/curriculum/03-advanced.md)
   범위 — 팀 전원 재clone이 필요한 대수술이므로, 1번(폐기)이 언제나 우선입니다.

W25([Day 122](day-122.md))에서 이 사고가 **구조적으로 불가능한** 설정 관리로 갑니다 — 오늘은
"났을 때의 순서"만 몸에 넣으세요: **폐기 먼저, 청소는 그다음.**

### Step 4. reflog 구조대 (6교시)

conflict-lab에서 참사를 재연합니다 — hard reset으로 커밋 2개를 날린 뒤 구조:

```powershell
git switch main
git log --oneline -2
git reset --hard HEAD~2
git log --oneline -1            # 날아감
git reflog | Select-Object -First 4
```

```
$ git reflog | Select-Object -First 4
2e77c05 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
5d19c3a HEAD@{1}: merge feature/metrics-rebase: Fast-forward
07e4b62 HEAD@{2}: rebase (pick): 지표 로그 스위치 추가
2e77c05 HEAD@{3}: rebase (start): checkout main
```

`HEAD@{1}` 이 reset 직전의 자리입니다. 이름표를 도로 붙이면 끝:

```powershell
git reset --hard 5d19c3a
git log --oneline -1
```

```
$ git log --oneline -1
5d19c3a (HEAD -> main, feature/metrics-rebase) 로그 샘플링 비율 추가
```

**커밋했던 것은 웬만해선 안 죽습니다.** 이 안전망을 아는 것과 모르는 것이, 사고 앞에서
침착한 사람과 저장소를 지우는 사람을 가릅니다. (단, 커밋 안 된 작업 폴더 변경은 예외 —
hard 전에 status 확인이 철칙인 이유.)

### Step 5. force-with-lease 와 과제 (7~8교시)

Step 1에서 정리한 브랜치를 이미 push 해 뒀었다고 가정하고 (일부러 정리 전에 push 해 두세요),
정리 후 push → 거절 → 안전 강제:

```powershell
git push
git push --force-with-lease
```

```
$ git push
 ! [rejected]        feature/batch-limit -> feature/batch-limit (non-fast-forward)
$ git push --force-with-lease
+ 3fc1a02...e8a30f7 feature/batch-limit -> feature/batch-limit (forced update)
```

**과제 — 사고 대응 시나리오 2건.** 다음 두 상황에 대해 각각 ① 판단(공유 여부) ② 명령 순서
③ 팀에 알릴 내용 을 문서로 작성하고, conflict-lab에서 실제로 재연·구제해 로그를 첨부하세요.

1. 동료가 main에 직접 push한 커밋이 서버를 깨뜨림 (여러분은 그 사실을 배포 후 발견)
2. 자신이 `reset --hard` 직후, 그 안에 오늘 오전의 커밋 3개가 포함돼 있었음을 깨달음

## ⑤ 자주 하는 실수

### hard reset이 미커밋 작업까지 지운다는 걸 모름

**증상** — `git reset --hard` 후 아침부터 짠 (커밋 안 한) 코드가 증발 — reflog에도 없음.
**원인** — reflog는 **커밋의** 일지입니다. 커밋된 적 없는 변경은 Git 어디에도 기록이 없습니다.
**해결** — 구조 불가가 정답인 경우입니다 (IDE 로컬 히스토리가 마지막 희망). 예방이 전부:
hard 전에 `git status` 로 작업 폴더가 깨끗한지 확인하거나, 불안하면 `git stash` 로 치워 두고 실행.

### 공유 브랜치를 reset으로 "취소"

**증상** — main의 잘못된 커밋을 reset으로 지우고 `--force` push — 팀원들의 pull이 전부 꼬이고,
그 사이 올라온 다른 커밋 하나가 조용히 사라짐.
**원인** — 도구 선택 기준(공유 여부)을 건너뜀 + force의 무조건 덮어쓰기.
**해결** — 공유 역사는 **revert**. force가 필요한 상황 자체가 "공유 역사를 고치려 한다"는
경고등입니다. 이미 저질렀다면 팀 공지 → reflog로 사라진 커밋 확인 → 복구 커밋.

### revert 했는데 충돌이 남

**증상** —
```
error: could not revert b6f92d3... 업로드 제한 설정 정리
hint: After resolving the conflicts, mark them with "git add/rm <pathspec>", then run
hint: "git revert --continue".
```
**원인** — 취소하려는 커밋이 고친 줄을 **그 뒤의 커밋이 또 고쳤기** 때문 — 반대 패치가 그대로
적용될 수 없는 상태입니다.
**해결** — 충돌 해결 3단계 그대로 (결정 → add → `git revert --continue`). 이번 주 배운 충돌
해결이 merge/rebase/revert 어디서나 같은 절차라는 걸 확인하는 기회입니다.

### rebase -i 범위를 잘못 잡아 남의 커밋까지 편집

**증상** — `git rebase -i HEAD~10` 을 열었더니 팀원들의 (이미 공유된) 커밋까지 목록에 —
그대로 진행하면 황금률 위반.
**원인** — "내 것만" 고르는 시작점을 손으로 세다가 실수.
**해결** — 시작점은 숫자 대신 **경계 이름**으로: `git rebase -i main` (main 이후 = 내 브랜치의
커밋만) 또는 `git rebase -i origin/feature/x` (마지막 push 이후 = 아직 공유 안 된 것만).

### amend를 push 후에

**증상** — 마지막 커밋 메시지를 `git commit --amend` 로 고쳤는데 push가 거절됨.
**원인** — amend도 rebase처럼 **커밋을 재창조**합니다 (해시 변경). push 후의 amend는 소규모
황금률 위반입니다.
**해결** — push 전이면 자유, push 후면 그냥 두거나(메시지 오타는 사고가 아닙니다) 개인 브랜치인
경우에만 `--force-with-lease`. 공유 브랜치면 포기가 정답입니다.

## ⑥ 확인 문제

**Q1.** "커밋을 취소한다"는 같은 목표에 대해 revert와 reset이 역사에 남기는 결과가 어떻게 다른지
그림으로 그리고, 각각이 허용되는 조건을 쓰세요.

<details>
<summary>답 보기</summary>

revert: `●──B──●──R` — B는 남고 반대 커밋 R이 **추가**됩니다 (역사가 앞으로만 자람 → 공유
브랜치에서 안전, 언제나 허용). reset: `●──(B 이후를 되감아 이름표를 뒤로)` — B가 역사에서
사라집니다 (역사를 되감음 → 그 역사를 나만 가졌을 때만 허용). 기준은 단 하나 "공유했는가"이고,
공유 후 reset은 팀원들의 저장소와 다른 역사를 만들어 Day 107 Q2의 연쇄 사고로 이어집니다.

</details>

**Q2.** `.env` 시크릿 커밋 사고에서 "revert는 해결이 아니다"인 이유와, push 후 대응의 올바른
1순위를 쓰세요.

<details>
<summary>답 보기</summary>

revert는 반대 커밋을 **추가**할 뿐, 시크릿이 담긴 원래 커밋은 히스토리에 그대로 남아 누구든
`git log`/GitHub UI로 열람할 수 있습니다. 1순위는 **그 시크릿 자체의 폐기·재발급** — 히스토리
청소(filter-repo)는 그다음이며, 이미 유출됐다고 전제하는 것이 안전합니다. "커밋을 지웠으니 안전"은
순서가 뒤집힌 대응입니다.

</details>

**Q3.** `--force-with-lease` 가 막아 주는 구체적 사고 시나리오를 시간 순으로 쓰고, 그런
force-with-lease조차 공유 브랜치에서 금지인 이유를 덧붙이세요.

<details>
<summary>답 보기</summary>

① 내가 브랜치를 rebase 하는 동안 ② 팀원 B가 같은 브랜치에 커밋 하나를 push ③ 내가 `--force` 하면
B의 커밋이 말없이 덮여 증발하지만, `--force-with-lease` 는 "원격이 내가 마지막으로 본 상태와
다르다"며 **거절** — B의 작업이 보호됩니다. 그러나 이것은 "모르는 사이의 덮어쓰기"만 막을 뿐,
공유 브랜치의 역사를 다시 쓰는 행위 자체(pull 꼬임, 유령 커밋)는 그대로이므로 황금률의 예외가
되지 못합니다 — 어디까지나 **개인 브랜치 정리용** 안전장치입니다.

</details>
