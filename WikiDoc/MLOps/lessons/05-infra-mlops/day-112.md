## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `ls -al` 의 권한 문자열(`-rw-r--r--`)을 **소유자·그룹·기타의 3벌**로 해독할 수 있다.
- `chmod` · `chown` 으로 파일의 권한과 주인을 바꾸고, **600/644/755** 를 상황에 맞게 고를 수 있다.
- `sudo` 가 무엇을 빌려주는 것인지 알고, **배포 전용 사용자(deploy)** 를 sudo 없이 만들 수 있다.
- 환경 변수를 세션·영구(.bashrc)로 설정하고, 그것이 **프로세스에 상속**되는 원리를 설명할 수 있다.

## ② 왜 필요한가

어제 만난 벽을 기억하십니까 — `/var/log` 에 쓰려다 `Permission denied`. 오늘은 그 벽의
설계도를 배웁니다. 그런데 왜 서버는 이렇게 곳곳이 잠겨 있을까요?

서버는 **여러 주체가 함께 쓰는 공간**이기 때문입니다. 사람(운영자 여러 명)만이 아니라
프로그램들도 각자 사용자입니다 — nginx는 nginx 사용자로, PostgreSQL은 postgres 사용자로 돕니다.
자물쇠가 없다면 이런 일이 생깁니다:

| 사고 | 원인 |
|---|---|
| 웹 서버가 해킹당했는데 DB 데이터까지 유출 | 웹 서버 계정이 DB 파일을 읽을 수 있었음 |
| 신입의 실수 한 줄에 서비스 전체 삭제 | 모두가 root(전권)로 작업 |
| `.env` 의 DB 비밀번호를 같은 서버의 다른 계정이 열람 | 파일이 아무나 읽는 권한(644)이었음 |

해법은 하나의 원칙으로 수렴합니다 — **최소 권한: 각 주체에게 일에 필요한 만큼만.**
오늘 만들 `deploy` 사용자가 그 원칙의 실물입니다: MP3 API를 돌릴 수는 있지만, 시스템을
망가뜨릴 권한은 없는 계정. 내일 systemd가 이 계정으로 서비스를 올리고, W24 이후 컨테이너의
권한 이야기도 전부 오늘의 연장선입니다. (그리고 [Day 109](day-109.md)에서 "시크릿 유출은 폐기가
먼저"였다면, 오늘은 **애초에 읽히지 않게** 만드는 쪽입니다.)

## ③ 개념 설명

### 권한 문자열 해부 — 10글자, 1+3+3+3

```
-  rw-  r--  r--   1  student  student  220  Aug 13 09:10  .env
│  ───  ───  ───          │
│   │    │    └ 기타(others): 나머지 전원        └ 이 파일의 소유자 · 그룹
│   │    └ 그룹(group): 같은 그룹원
│   └ 소유자(user): 파일의 주인
└ 타입: - 파일, d 폴더, l 링크
```

| 글자 | 파일에서 | 폴더에서 |
|---|---|---|
| `r` | 내용 읽기 | 목록 보기 (ls) |
| `w` | 내용 수정 | 안에 파일 만들기/지우기 |
| `x` | **실행** | **들어가기 (cd)** |

폴더의 x가 함정 포인트입니다 — 폴더는 r이 있어도 x가 없으면 들어가지 못합니다.

### 숫자 표기 — r=4, w=2, x=1의 합

세 자리 숫자는 소유자·그룹·기타 순서의 합계입니다:

| 숫자 | 풀이 | 뜻 | 표준 용도 |
|---|---|---|---|
| **755** | rwx r-x r-x | 주인 전부, 남은 읽기+실행 | 폴더 · 실행 스크립트 |
| **644** | rw- r-- r-- | 주인 읽쓰, 남은 읽기만 | 일반 파일 (코드·문서) |
| **600** | rw- --- --- | **주인만** 읽쓰 | **시크릿** (.env · SSH 키) |
| **700** | rwx --- --- | 주인만 전부 | 개인 폴더 (~/.ssh) |

바꾸는 명령 두 가지:

```bash
chmod 600 .env                    # 권한 변경 (숫자 또는 +x 같은 기호식)
sudo chown deploy:deploy app.py   # 주인 변경 (소유자:그룹) — 주인 변경은 root 권한 필요
```

### sudo — root를 "한 명령만" 빌린다

리눅스에는 모든 자물쇠를 여는 관리자 **root**가 있습니다. root로 상주하면 편하지만 오타 하나의
사고 반경이 서버 전체가 됩니다. 그래서 현대 서버 운영의 표준은:

> root 로그인은 봉인하고, 관리자 그룹(sudo 그룹)의 사용자가 **필요한 명령 앞에만 `sudo`** 를 붙인다.

`sudo` = "superuser do". 붙인 그 한 줄만 root 권한으로 실행되고, 끝나면 원래 신분으로
돌아옵니다. 실행 기록도 남습니다(`/var/log/auth.log`) — 권한과 책임이 함께 갑니다.

### 사용자와 그룹 — 사람만이 아니다

| 명령 | 하는 일 |
|---|---|
| `sudo adduser deploy` | 사용자 생성 (홈 폴더·기본 그룹 포함) |
| `sudo usermod -aG sudo student` | 그룹에 **추가** (-aG의 a를 빼먹으면 대참사 — ⑤) |
| `su - deploy` | 다른 사용자로 전환 (`-` 는 그 사용자의 환경까지 로드) |
| `whoami` / `groups` | 지금 나는 누구인가 / 어느 그룹인가 |

운영 서버의 계정 설계 관례 — **사람 계정**(sudo 가능, 개인별)과 **서비스 계정**(sudo 불가,
로그인 불가로도 만듦)을 분리합니다. 오늘의 deploy가 후자입니다: MP3 API는 deploy 소유의
파일을 deploy 권한으로 돌리고, 뚫려도 deploy가 할 수 있는 것 이상은 못 합니다.

### 환경 변수 — 프로세스에게 물려주는 설정

[Day 093](../04-deep-learning-serving/day-093.md)의 config가 읽던 `MODEL_PATH` — 서버에서 그 값을
넣어 주는 쪽이 환경 변수입니다:

```bash
export MODEL_PATH=/opt/mlops-mp3/models/antbee_resnet18.pt   # 이 셸과 자식들에게
printenv MODEL_PATH                                           # 확인
echo 'export API_ENV=prod' >> ~/.bashrc                       # 로그인마다 자동 설정 (영구)
```

핵심 원리는 **상속**입니다: 환경 변수는 "그 셸이 낳는 자식 프로세스"에게 복사되어 전달됩니다.
그래서 셸에서 export 하고 uvicorn을 띄우면 API가 그 값을 보지만, **다른 셸이나 내일 배울
systemd가 띄운 프로세스는 못 봅니다** — systemd에는 systemd의 주입 방법(Environment=)이 따로
있는 이유입니다. "환경 변수는 전역 설정이 아니라 상속 재산"이라는 문장을 기억하세요.

## ④ 단계별 실습

### Step 1. 해독 훈련 (1교시)

```bash
ls -al ~ | head -6
ls -al /etc/passwd /etc/shadow
```

```
$ ls -al /etc/passwd /etc/shadow
-rw-r--r-- 1 root root   1743 Aug 13 09:10 /etc/passwd
-rw-r----- 1 root shadow 1002 Aug 13 09:10 /etc/shadow
```

읽어 봅시다 — 사용자 목록(passwd)은 644 "누구나 읽기", 비밀번호 해시(shadow)는 640에
그룹도 shadow 전용 — **민감도에 비례해 조여진 권한**의 표준 예시입니다. `cat /etc/shadow` 를
시도해 보세요 — 어제의 그 `Permission denied` 가 이제는 **읽히는 에러**일 겁니다.

### Step 2. 실행 권한 — 스크립트가 안 돌 때 (2교시)

```bash
cd ~/lab
echo -e '#!/bin/bash\necho "MP3 API 상태: 정상"' > check.sh
./check.sh
```

```
$ ./check.sh
-bash: ./check.sh: Permission denied
```

`>` 로 만든 파일은 644 — **x가 없어서** 실행이 거부됩니다. 실행권을 주면:

```bash
chmod +x check.sh    # 또는 chmod 755 check.sh
./check.sh
ls -al check.sh
```

```
$ ./check.sh
MP3 API 상태: 정상
$ ls -al check.sh
-rwxr-xr-x 1 student student 47 Aug 13 10:02 check.sh
```

Day 115의 배포 스크립트에서 이 `chmod +x` 가 관례처럼 다시 나옵니다.

### Step 3. 배포 사용자 만들기 (3~4교시)

```bash
sudo adduser deploy
```

```
$ sudo adduser deploy
Adding user `deploy' ...
Adding new group `deploy' (1001) ...
Adding new user `deploy' (1001) with group `deploy' ...
Creating home directory `/home/deploy' ...
Copying files from `/etc/skel' ...
New password:
```

비밀번호를 설정하고 나머지 질문은 Enter로 넘깁니다. **sudo 그룹에는 넣지 않습니다** — 이것이
설계입니다. 확인:

```bash
su - deploy
whoami && groups
sudo ls /root
```

```
$ whoami && groups
deploy
deploy
$ sudo ls /root
[sudo] password for deploy:
deploy is not in the sudoers file.  This incident will be reported.
```

deploy는 시스템 관리를 **못 합니다** — 서비스 계정의 올바른 모습입니다. `exit` 로 student로
복귀한 뒤, MP3 API가 살 집을 마련하고 주인을 deploy로:

```bash
exit
sudo mkdir -p /opt/mlops-mp3
sudo chown -R deploy:deploy /opt/mlops-mp3
ls -al /opt
```

```
$ ls -al /opt
total 12
drwxr-xr-x  3 root   root   4096 Aug 13 10:31 .
drwxr-xr-x 19 root   root   4096 Aug 13 09:10 ..
drwxr-xr-x  2 deploy deploy 4096 Aug 13 10:31 mlops-mp3
```

`/opt/mlops-mp3` 은 deploy의 영토입니다 — 내일 코드가 여기 들어오고, systemd가 deploy 신분으로
API를 올립니다.

### Step 4. 권한 사고 2건 재현 (5~6교시)

**사고 A — 시크릿이 읽힌다.** deploy로 `.env` 를 만들고, 기본 권한의 허점을 확인합니다:

```bash
su - deploy
echo "DB_PASSWORD=super-secret-pw" > /opt/mlops-mp3/.env
ls -al /opt/mlops-mp3/.env
exit
cat /opt/mlops-mp3/.env        # student 신분으로 읽기 시도
```

```
$ ls -al /opt/mlops-mp3/.env
-rw-r--r-- 1 deploy deploy 29 Aug 13 10:40 /opt/mlops-mp3/.env
$ cat /opt/mlops-mp3/.env
DB_PASSWORD=super-secret-pw
```

**읽힙니다.** 644의 마지막 4(기타 읽기) 때문 — 같은 서버의 아무 계정이나 DB 비밀번호를 볼 수
있는 상태였습니다. 봉인:

```bash
su - deploy -c "chmod 600 /opt/mlops-mp3/.env"
cat /opt/mlops-mp3/.env
```

```
$ cat /opt/mlops-mp3/.env
cat: /opt/mlops-mp3/.env: Permission denied
```

**시크릿 파일은 600** — 예외 없는 규칙으로 새기세요 (Day 114의 SSH 키에서 재등장합니다).

**사고 B — root 소유물이 서비스 길을 막는다.** 이번엔 반대 방향의 흔한 사고:

```bash
sudo touch /opt/mlops-mp3/models_v2.pt        # sudo로 파일을 만들었다 (root 소유!)
su - deploy -c "rm /opt/mlops-mp3/models_v2.pt"
```

```
$ su - deploy -c "rm /opt/mlops-mp3/models_v2.pt"
rm: remove write-protected regular empty file '/opt/mlops-mp3/models_v2.pt'? y
rm: cannot remove '/opt/mlops-mp3/models_v2.pt': Permission denied
```

sudo로 무심코 만든 파일은 root 소유가 되어, 정작 **서비스 계정이 지우지도 덮어쓰지도 못하는**
장애물이 됩니다 (모델 교체 배포가 이 지점에서 자주 멈춥니다). 수습은 주인 교정:

```bash
sudo chown deploy:deploy /opt/mlops-mp3/models_v2.pt
```

교훈 — **deploy의 영토에서는 deploy로 작업**하고, sudo는 영토 밖 시스템 일에만 씁니다.

### Step 5. 환경 변수와 상속 실험 (7교시)

```bash
export API_ENV=prod
python3 -c "import os; print('자식 프로세스가 본 값:', os.environ.get('API_ENV'))"
```

```
$ python3 -c "import os; print('자식 프로세스가 본 값:', os.environ.get('API_ENV'))"
자식 프로세스가 본 값: prod
```

python3은 이 셸의 **자식**이라 값을 물려받았습니다. 이제 새 터미널(=다른 셸)을 열어 같은 명령을
실행해 보세요 — `None` 입니다. 상속은 부모→자식 한 방향뿐이고, 그래서 "로그인마다 자동"이
필요하면 `~/.bashrc` 에 export를 적어 두는 것입니다. 내일 systemd 유닛의 `Environment=` 가
"systemd가 낳는 자식(=서비스)에게 물려주는" 같은 원리의 공식 통로임을 확인하게 됩니다.

### Step 6. 과제 — 권한 설계 실습 (8교시)

내일 배포될 MP3 API의 파일 트리에 대해 **소유자:그룹과 권한 숫자를 설계**하고 근거를 쓰세요.

```
/opt/mlops-mp3/
├── app/            (코드)
├── models/antbee_resnet18.pt
├── .env            (DB 비밀번호)
├── deploy.sh       (배포 스크립트 — 실행돼야 함)
└── logs/           (API가 로그를 쓰는 곳)
```

형식: `경로 | 소유자:그룹 | 권한 | 근거` 표. 추가 질문 2개 — ① logs/에 다른 운영자(student)도
읽기 접근이 필요하다면 어디를 어떻게 바꿀 것인가? ② 이 트리에서 600이 **아니면 사고**인 항목은
무엇이고, 오늘 재현한 어느 사고에 해당하는가?

## ⑤ 자주 하는 실수

### 막히면 chmod 777

**증상** — Permission denied가 뜰 때마다 `chmod -R 777` — "되게는" 만들었지만, 이제 아무나
읽고 고치고 실행하는 파일들이 서버에 굴러다닙니다.
**원인** — 777은 해결이 아니라 **자물쇠 철거**입니다.
**해결** — 진단부터: `ls -al` 로 소유자와 권한을 보고, "누가 이 파일에 무엇을 해야 하는가"에
맞는 최소 숫자(600/644/755)를 고릅니다. 777이 정답인 상황은 실무에 사실상 없습니다.

### sudo pip install

**증상** — `pip install` 이 Permission denied라서 `sudo pip install torch` — 시스템 파이썬이
오염되고, 나중에 apt와 pip가 서로 파일을 밟는 미궁이 됩니다.
**원인** — 시스템 영역에 쓰려는 pip를 root 권한으로 밀어붙임.
**해결** — 서버에서도 답은 [Day 001](../01-python-data/day-001.md)과 같습니다 — **venv**.
`python3 -m venv .venv` 는 내 소유 폴더에 만들어지므로 sudo가 필요 없습니다. "pip 앞에 sudo가
필요해 보인다"는 것 자체가 venv 활성화를 잊었다는 신호입니다.

### usermod -G (a를 빠뜨림)

**증상** — `sudo usermod -G docker deploy` 실행 후, deploy가 **기존에 속했던 다른 그룹에서
전부 빠져** 있음.
**원인** — `-G` 는 그룹 목록을 **통째로 교체**합니다. `-aG` 의 `a`(append)가 "추가"입니다.
**해결** — 그룹 추가는 반드시 `usermod -aG 그룹 사용자`. 사고가 났다면 `groups` 백업이 없는 한
`/etc/group` 을 뒤져 복원해야 합니다 — a 한 글자가 이만큼 큽니다 (W24에서 docker 그룹 추가 때
실전으로 만납니다).

### 그룹 추가 후 "여전히 안 되는데요"

**증상** — 그룹에 분명히 추가했는데 권한이 그대로.
**원인** — 그룹 멤버십은 **로그인 시점**에 확정됩니다. 지금 세션은 옛 명단.
**해결** — 로그아웃 후 재로그인 (WSL이면 터미널 재시작 또는 `wsl --shutdown`). `groups` 로
반영을 확인하고 나서 재시도하세요.

### sudo su로 root 상주

**증상** — 매번 sudo 치기 귀찮아 `sudo su` 로 root 셸에 눌러앉음 — 어느 날 홈 정리한다는 게
`/` 에서 rm을 실행.
**원인** — 편의가 사고 반경을 서버 전체로 키움. root 프롬프트(`#`)는 경고색이 없습니다.
**해결** — root 셸은 "그 작업 동안만" 열고 즉시 exit. 일상 명령은 개인 계정 + 건별 sudo가
표준입니다 — 로그(auth.log)에 "누가 무엇을" 이 남는 것도 건별 sudo일 때입니다.

## ⑥ 확인 문제

**Q1.** `-rw-r-----  1 deploy webteam  512  .env` 파일을 ① deploy ② webteam 그룹의 student
③ 그룹 밖의 guest 가 각각 cat 하면 어떻게 되는지, 근거 비트와 함께 답하세요.

<details>
<summary>답 보기</summary>

① 성공 — 소유자 벌이 rw. ② 성공 — 그룹 벌이 r (webteam 소속이므로 읽기 가능, 쓰기는 불가).
③ Permission denied — 기타 벌이 `---`. 640은 "주인은 관리, 팀은 열람, 외부인은 차단"의 전형이며,
/etc/shadow(Step 1)와 같은 패턴입니다.

</details>

**Q2.** Step 4의 사고 B(root 소유 파일이 배포를 막음)가 **자동 배포**(W26) 환경에서 특히 위험한
이유와, 예방 규칙을 한 줄로 쓰세요.

<details>
<summary>답 보기</summary>

자동 배포는 deploy 계정으로 무인 실행되므로, root 소유물에 막히는 순간 **사람이 없는 새벽에
배포가 실패**하고 서비스는 옛 버전으로 남습니다 (혹은 반쯤 교체된 불일치 상태). 예방 규칙:
"서비스 영토(/opt/mlops-mp3)의 모든 파일은 서비스 계정 소유 — sudo로 그 안을 만지지 않는다."
설치 직후 `chown -R deploy:deploy` 로 영토를 넘기는 것까지가 세팅입니다.

</details>

**Q3.** "환경 변수는 전역 설정이 아니라 상속 재산"임을 보여 주는 실험을 오늘 했습니다. 이 성질
때문에 내일(systemd 서비스)에서 무엇이 문제가 되고, 공식 해법이 무엇인지 예측해 보세요.

<details>
<summary>답 보기</summary>

systemd가 띄우는 서비스는 **내 셸의 자식이 아니라** systemd(PID 1)의 자식입니다 — 내가 .bashrc에
export 한 MODEL_PATH를 서비스는 물려받지 못해 "셸에서 직접 실행하면 되는데 서비스로는
FileNotFoundError"가 납니다. 해법은 systemd 유닛 파일의 `Environment=` / `EnvironmentFile=`
(내일 Step에서 .env를 EnvironmentFile로 주입) — "누가 낳는 프로세스인가"에 맞는 통로로 설정을
주입하는 것입니다.

</details>
