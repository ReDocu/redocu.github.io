## ② 왜 필요한가

이번 주 월~목, 서버 한 대를 손으로 만들었습니다. 몇 단계였는지 세어 봅시다 — apt 업데이트,
deploy 사용자, 권한, venv, **CPU 휠 지정** pip install, .env, systemd 유닛, sshd 설정…
스무 단계쯤 됩니다. 이제 질문:

> 서버가 한 대 더 필요하면? 팀원 PC에도? 클라우드로 이사하면? — **또 스무 단계.**
> 그리고 그 스무 번 중 한 번은 반드시 다르게 됩니다 — 파이썬이 3.10이거나, CPU 휠을 잊거나.

이것이 "내 컴퓨터에선 되는데(works on my machine)"의 정체입니다: 코드는 같은데 **코드가 딛고 선
환경**(OS 패키지·파이썬 버전·라이브러리·설정)이 기계마다 달라서 나는 사고. [Day 066](../03-machine-learning/day-066.md)에서
재현성을 "데이터·코드·환경·시드"로 분해했을 때의 그 **환경**이 마지막 남은 구멍이었죠.

컨테이너의 답은 발상 전환입니다 — **환경째로 포장해서 배포하자.** 코드만 보내고 환경은 저쪽에서
재구성하는 게 아니라, "실행에 필요한 전부(OS 라이브러리부터 내 코드까지)"를 이미지 한 덩어리로
찍어 보내고, 어디서든 그대로 실행합니다. 사실 여러분은 이 마법의 수혜자였습니다 — W07의
PostgreSQL, 설치 지옥 없이 명령 한 줄로 떴던 것을 기억하십니까? 오늘 그 한 줄의 전모를 밝힙니다.

## ③ 개념 설명

### 이미지 vs 컨테이너 — 틀과 붕어빵

| | 이미지 (image) | 컨테이너 (container) |
|---|---|---|
| 정체 | 실행 환경의 **읽기 전용 스냅샷** | 이미지를 **실행 중인 인스턴스** |
| 비유 | 클래스 · 붕어빵 틀 · 설치 CD | 인스턴스 · 붕어빵 · 켜진 프로그램 |
| 개수 | 한 벌 | 같은 이미지로 몇 개든 |
| 파이썬으로 | `class Postgres16:` | `pg1 = Postgres16()` |

`postgres:16` 이 이미지, `mlops-pg` 가 그 이미지로 띄운 컨테이너였습니다. 이미지는 불변이고,
컨테이너는 그 위에 얇은 쓰기 층을 얹어 돌아갑니다 — 그래서 **컨테이너는 일회용**입니다.
지우고 다시 만들면 이미지 그대로의 깨끗한 상태 (컨테이너 안에 쌓인 변경은 소멸 — W07에서
`-v` 로 데이터를 따로 빼 둔 이유이고, 목요일(Day 119)의 주제입니다).

### VM과 뭐가 다른가 — 커널을 공유한다

"환경째 포장"은 가상 머신(VM)도 합니다. 차이는 **어디까지 포장하나**입니다:

| | VM | 컨테이너 |
|---|---|---|
| 포장 범위 | OS **전체** (커널 포함) | OS 위의 것들만 (커널은 **호스트와 공유**) |
| 크기 | 수~수십 GB | 수십 MB~수 GB |
| 기동 | 분 단위 (부팅) | **초 단위** (프로세스 실행) |
| 격리 강도 | 강함 (하드웨어 수준) | 충분함 (커널 기능으로 벽) |

컨테이너의 본질은 "가벼운 VM"이 아니라 **잘 격리된 프로세스**입니다. 호스트 커널 위에서
보통 프로세스로 돌되, 커널의 격리 기능으로 파일 시스템·프로세스 목록·네트워크를 각자 딴 세상처럼
보이게 한 것 — 그래서 초 단위로 뜨고, 서버 한 대에 수십 개를 얹을 수 있습니다.
(WSL2 위의 Docker Desktop 구조가 딱 이 그림입니다: Linux 커널은 WSL2 것 하나, 컨테이너들이
그 위에 얹힘.)

### 컨테이너의 생애와 여섯 동사

```
이미지 ──run──▶ 실행 중 ──stop──▶ 정지 ──rm──▶ 소멸
   ▲               │ start ▲┘
   └─ pull(다운로드) │
                    ├─ ps      지금 누가 살아 있나
                    ├─ logs    저 안에서 무슨 일이 (stdout/stderr — Day 098!)
                    └─ exec    저 안에 들어가 명령 실행
```

W07의 네 동사(run/ps/stop·start/exec)에 오늘 logs와 rm이 추가됩니다. 특히 `logs` —
컨테이너 앱은 로그를 파일이 아니라 **표준 출력으로** 흘리는 게 표준이고, 그래서
[Day 098](../04-deep-learning-serving/day-098.md)에서 stderr로 보냈던 설계가 컨테이너 세계의
표준과 정확히 접붙습니다.

### Step 3. 3개월 늦은 해설 — W07의 주문 (5교시)

[Day 031](../02-sql-pipeline/day-031.md)에서 "그대로 복사하세요" 했던 한 줄, 이제 전부 읽힙니다:

```
docker run --name mlops-pg -e POSTGRES_PASSWORD=mlops1234 -e TZ=Asia/Seoul \
           -p 5432:5432 -v mlops-pgdata:/var/lib/postgresql/data -d postgres:16
```

| 조각 | 오늘의 언어로 |
|---|---|
| `--name mlops-pg` | 컨테이너 이름 — start/stop/exec 때 부를 손잡이 |
| `-e POSTGRES_PASSWORD=…` | **환경 변수 주입** — Day 112의 상속 재산을 컨테이너에게 (Day 122에서 정식으로) |
| `-p 5432:5432` | 호스트 5432 ↔ 컨테이너 5432 — 그래서 DBeaver가 localhost:5432로 접속됐던 것 |
| `-v mlops-pgdata:/var/lib/postgresql/data` | **볼륨** — DB 데이터를 컨테이너 밖에 보존 (Day 119의 주제) |
| `-d` | 백그라운드 |
| `postgres:16` | 이미지 이름:태그 — PostgreSQL 16이 설치 없이 떴던 이유 |

석 달간 `docker start mlops-pg` 만 치고도 DB가 멀쩡했던 것, 컨테이너를 실수로 지웠어도
데이터가 살았을 이유(-v), 전부 이 한 줄에 있었습니다.

### Step 4. 격리를 증명하는 세 실험 (6~7교시)

**실험 A — 컨테이너는 일회용.** 컨테이너 안에 파일을 만들고, 지웠다 다시 띄우면:

```bash
docker run -it --name scratch python:3.12-slim bash
```
```bash
root@c3a9e1b2f4d5:/# echo "소중한 결과" > /result.txt && exit
```
```bash
docker rm scratch
docker run -it --rm python:3.12-slim ls /result.txt
```

```
$ docker run -it --rm python:3.12-slim ls /result.txt
ls: cannot access '/result.txt': No such file or directory
```

새 컨테이너는 이미지의 깨끗한 상태에서 시작 — **컨테이너 안은 저장소가 아닙니다.**
(모델 파일·DB 데이터를 어디 둘 것인가 → Day 119.)

**실험 B — 서로 딴 세상.** 컨테이너 두 개를 띄우고 각각 `hostname` 과 `ps aux` 를 보면,
서로의 존재도 프로세스도 보이지 않습니다 — 파일·프로세스·네트워크가 각자 격리.

**실험 C — 그러나 커널은 하나.** 호스트(WSL)에서:

```bash
docker run -d --name web -p 8080:80 nginx:1.27-alpine
ps aux | grep "nginx: master" | grep -v grep
```

```
$ ps aux | grep "nginx: master" | grep -v grep
root       9182  0.0  0.1   9532  5892 ?        Ss   10:41   0:00 nginx: master process nginx -g daemon off;
```

컨테이너 "안"의 nginx가 호스트 `ps` 에 **그대로 보입니다** — VM이라면 불가능한 장면.
컨테이너는 결국 호스트 커널 위의 보통 프로세스이며, 벽은 커널이 쳐 준 시야 가림막이라는 것 —
③의 표가 실물로 확인됐습니다. (`docker stop web && docker rm web` 로 정리.)

### Step 5. 과제 — 명령 정리표 (8교시)

오늘 쓴 명령 전부를 아래 형식의 표로 정리해 제출하세요:

`명령 | 대상(이미지/컨테이너) | 하는 일 | 자주 쓰는 옵션 | 내가 낸 에러와 원인`

최소 10행 (run·ps·ps -a·logs·exec·stop·start·rm·rmi·images·pull). **"대상" 열이 채점
포인트**입니다 — 이미지에 거는 명령과 컨테이너에 거는 명령을 섞으면 ⑤의 첫 실수가 됩니다.
마지막 행에는 W07 주문을 자기 문장으로 한 줄 해설.

## ⑤ 자주 하는 실수

### 이미지와 컨테이너를 섞어 부름

**증상** —
```
$ docker rm python:3.12-slim
Error response from daemon: No such container: python:3.12-slim
```
**원인** — `rm` 은 컨테이너용, 이미지 삭제는 `rmi` 입니다. 반대로 `docker rmi web` 도 같은 계열.
**해결** — 명령 전에 대상부터: 컨테이너 목록은 `docker ps -a`, 이미지 목록은 `docker images`.
"틀을 지우는가, 붕어빵을 지우는가"를 한 박자 생각하는 것으로 충분합니다.

### 컨테이너 안에 데이터를 두고 rm

**증상** — 컨테이너 안에서 며칠 작업한 결과·데이터가 `docker rm` 한 방에 증발.
**원인** — 실험 A를 역방향으로 겪은 것 — 컨테이너 쓰기 층은 컨테이너와 운명을 같이합니다.
**해결** — 보존할 데이터는 **볼륨**에 (W07의 `-v mlops-pgdata:...` 가 DB를 구해 온 방식,
Day 119에서 정식 수업). 응급 구조는 `docker cp 컨테이너:경로 호스트경로` — 단 rm **전에만**.

### -d 없이 띄우고 Ctrl+C

**증상** — `docker run nginx...` 후 터미널이 로그에 점령됨 → Ctrl+C → 컨테이너도 사망.
**원인** — 포그라운드 실행에서 Ctrl+C는 컨테이너의 주 프로세스에게 갑니다 (Day 113의 시그널).
**해결** — 상주 서비스는 `-d`, 일회성 대화는 `-it --rm`. 이미 포그라운드로 띄웠다면 다른
터미널에서 `docker stop` 이 정중한 종료입니다.

### Bind for 0.0.0.0:8080 failed: port is already allocated

**증상** —
```
docker: Error response from daemon: driver failed programming external connectivity on endpoint web2: Bind for 0.0.0.0:8080 failed: port is already allocated.
```
**원인** — 호스트 포트는 선착순 하나입니다 — 아까 띄운 컨테이너(또는 다른 프로세스)가 8080을
이미 점유 (Day 113의 Address already in use와 같은 병의 컨테이너판).
**해결** — `docker ps` 로 점유자 확인 후 stop, 또는 왼쪽 숫자만 바꿔 `-p 8081:80` — 컨테이너
쪽 80은 그대로 두는 것에 주목 (안 세상과 바깥 세상의 분리).

### permission denied ... /var/run/docker.sock

**증상** — WSL에서 docker 명령마다:
```
permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
```
**원인** — docker 데몬과의 통로(docker.sock)는 docker 그룹 소유 — 내 계정이 그 그룹이 아님.
**해결** — `sudo usermod -aG docker $USER` 후 **재로그인** (Day 112에서 배운 두 가지가 동시에
시험대: `-aG` 의 a, 그리고 그룹은 재로그인부터). Docker Desktop 통합을 켜면 보통 자동이지만,
클라우드 서버에 Docker Engine을 직접 깔면 반드시 만나는 관문입니다.

nginx가 호스트 ps에 그대로 보였습니다 — 컨테이너는 **호스트 커널을 공유하는 보통 프로세스**이고,
격리는 커널이 파일·프로세스·네트워크의 시야를 가려 주는 방식입니다. 그래서 부팅이 없어 초 단위로
뜨고 크기도 작습니다. 정확한 문장은 "컨테이너는 잘 격리된 프로세스"입니다.

</details>

**Q2.** 이번 주 월~목의 수동 서버 구축(스무 단계)과 오늘의 관점을 대비할 때, "컨테이너 이미지"가
[Day 066](../03-machine-learning/day-066.md) 재현성 4요소 중 무엇을 어떻게 봉인하는지 설명하세요.

<details>
<summary>답 보기</summary>

**환경**입니다. 데이터는 MD5로, 코드는 Git 커밋으로, 시드는 고정값으로 봉인했지만 환경(OS
라이브러리·파이썬 버전·패키지)은 "requirements.txt + 설치 절차 문서"라는 느슨한 봉인뿐이었고,
그래서 기계마다 달라질 수 있었습니다. 이미지는 그 환경 전체를 **실행 가능한 불변 스냅샷**으로
찍어 어디서든 동일하게 재생합니다 — "내 컴퓨터에선 되는데"가 원리적으로 소멸하는 지점입니다.
(그 스냅샷을 코드로 정의하는 법이 내일의 Dockerfile입니다.)

</details>

**Q3.** `-p 8080:80` 에서 두 숫자의 역할을 구분하고, 같은 nginx 이미지로 컨테이너 3개를 한
서버에서 동시에 돌리려면 어떻게 해야 하는지 쓰세요.

<details>
<summary>답 보기</summary>

왼쪽 8080은 **호스트의 문**(바깥에서 접속하는 포트), 오른쪽 80은 **컨테이너 안의 문**(nginx가
듣는 포트). 안 세상은 격리라 세 컨테이너 모두 안에서는 80을 써도 충돌이 없고, 바깥 문만
겹치지 않게 하면 됩니다: `-p 8080:80`, `-p 8081:80`, `-p 8082:80`. 호스트 포트는 선착순
하나라는 규칙(⑤)과, 격리 덕에 안쪽 포트는 표준을 유지할 수 있다는 것이 요점입니다.

</details>
