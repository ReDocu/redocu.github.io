## ② 왜 필요한가

회사에서 새 서비스를 하나 만든다고 해 봅시다. 클라우드가 없던 시절의 절차는 이랬습니다.

```
1. 예상 트래픽을 추정한다              (며칠)
2. 서버 견적을 받는다                  (1~2주)
3. 결재를 올린다                       (1~3주)
4. 서버가 배송된다                     (2~6주)
5. 데이터센터에 설치하고 회선을 뚫는다   (1~2주)
6. OS를 올리고 네트워크를 잡는다        (며칠)
────────────────────────────────────────
   서비스 오픈까지: 두세 달
```

문제는 시간만이 아닙니다. **1번에서 추정을 틀리면 어느 쪽으로 틀려도 손해**입니다.

| 추정 실패 | 결과 |
|---|---|
| 트래픽을 크게 잡았다 | 서버 10대 중 8대가 3년 내내 놀고, 그 돈은 이미 나갔다 |
| 트래픽을 작게 잡았다 | 오픈 첫날 서비스가 죽고, 증설에 또 두 달이 걸린다 |

클라우드는 이 문제를 **"추정을 안 해도 되게"** 만들어 해결합니다. 서버가 필요하면 몇 분 안에 켜고, 필요 없어지면 끄고, 끈 만큼 돈을 안 냅니다.

그런데 여기서 **새로운 위험**이 생깁니다. 클릭 몇 번으로 리소스를 만들 수 있다는 것은, **클릭 몇 번으로 청구서를 만들 수 있다**는 뜻이기도 합니다. 실제로 이 과정에서 가장 흔한 사고는 "서비스가 안 되는 것"이 아니라 **"안 쓰는 리소스를 켜 둔 채 잊는 것"** 입니다.

그래서 이 강에서는 **"무엇을 빌리는가"** 와 **"어떻게 과금되는가"** 를 같은 무게로 봅니다. 그리고 다음 강([02강](lesson-02.md))에서 곧바로 안전장치를 겁니다.

## ③ 개념 설명

### 클라우드 컴퓨팅이란

**필요한 IT 자원(서버·스토리지·네트워크·데이터베이스)을 인터넷을 통해 필요한 만큼 빌려 쓰고, 쓴 만큼 지불하는 방식**입니다.

핵심은 다섯 가지입니다.

| 특징 | 뜻 | 실제 예 |
|---|---|---|
| **온디맨드 셀프서비스** | 사람에게 요청하지 않고 내가 직접 만든다 | 콘솔에서 클릭 → 2분 뒤 서버 사용 가능 |
| **광범위한 네트워크 접근** | 인터넷만 있으면 어디서든 | 카페에서 노트북으로 서버 관리 |
| **자원 풀링** | 거대한 자원 풀을 여러 고객이 나눠 씀 | 물리 서버 1대 위에 여러 고객의 가상 서버 |
| **빠른 탄력성** | 수요에 따라 자동으로 늘고 준다 | 트래픽 3배 → 서버 자동 3대 추가 ([10강](../02-compute-data/lesson-10.md)) |
| **측정 가능한 서비스** | 사용량이 측정되고 그만큼 과금 | 초 단위 과금, 사용 내역 조회 |

### 온프레미스와 무엇이 다른가

| 항목 | 온프레미스(직접 구축) | 클라우드 |
|---|---|---|
| 비용 성격 | **CapEx**(자산 구매, 선지출) | **OpEx**(운영비, 쓴 만큼) |
| 조달 시간 | 수 주 ~ 수 개월 | **수 분** |
| 용량 결정 | 미리 최대치로 추정해 구매 | 나중에 조절 |
| 실패 비용 | 잘못 사면 3년간 감가상각 | 끄면 그만 |
| 책임 범위 | 전원·냉각·하드웨어까지 전부 | 하드웨어 아래는 AWS |
| 잘 맞는 경우 | 규제·초저지연·매우 안정적인 부하 | 변동 부하·신규 서비스·글로벌 확장 |

> **클라우드가 항상 싼 것은 아닙니다.** 24시간 100% 부하가 3년간 일정하다면 직접 사는 쪽이 쌀 수도 있습니다.
> 클라우드의 진짜 이점은 **"틀려도 되는 것"** — 즉 의사결정을 되돌릴 수 있다는 점입니다.

### AWS 글로벌 인프라 3층 구조

이 그림 하나가 앞으로 16주 내내 모든 고가용성 설계의 바탕이 됩니다.

```
         🌍 리전 (Region)  — 지리적으로 분리된 지역
         예: ap-northeast-2 (서울)
         ┌──────────────────────────────────────────┐
         │                                          │
         │  🏢 AZ-2a        🏢 AZ-2b     🏢 AZ-2c   │  ← 물리적으로 분리된
         │  ┌────────┐     ┌────────┐   ┌────────┐  │     데이터센터 묶음
         │  │ DC DC  │     │ DC DC  │   │ DC DC  │  │     (전원·냉각·회선 독립)
         │  └────────┘     └────────┘   └────────┘  │
         │       └──────────┴────────────┘          │
         │        수 km 이내 · 초저지연 전용 회선     │
         └──────────────────────────────────────────┘

    ⚡ 엣지 로케이션 (Edge Location) — 전 세계 수백 곳
       CloudFront 캐시가 놓이는 접점. 리전보다 훨씬 촘촘하다.
```

| 계층 | 정체 | 이 과정에서 쓰는 곳 |
|---|---|---|
| **리전** | 지리적으로 분리된 AWS 인프라 지역. 서로 완전히 독립 | 전 과정 서울 `ap-northeast-2` 고정 |
| **가용 영역(AZ)** | 한 리전 안에서 **전원·냉각·네트워크가 물리적으로 분리된** 데이터센터 하나 이상의 묶음 | 07강 서브넷, 10강 ASG, 15강 Multi-AZ |
| **엣지 로케이션** | 콘텐츠를 캐싱해 사용자 가까이서 응답하는 접점 | [14강 CloudFront](../02-compute-data/lesson-14.md) |

> **핵심 문장** — **"고가용성이란 여러 AZ에 걸치는 것"** 입니다.
> AZ 하나가 통째로 정전되어도 다른 AZ의 서버가 살아 있으면 서비스는 계속됩니다.
> 반대로 서버를 10대 띄워도 **전부 같은 AZ에 있으면 가용성은 1대와 다르지 않습니다.**

### 리전은 무엇을 보고 고르는가

| 기준 | 설명 |
|---|---|
| **지연 시간** | 사용자와 가까울수록 빠릅니다. 한국 사용자 → 서울 리전 |
| **법규·데이터 주권** | 개인정보를 국외로 못 보내는 규제가 있으면 국내 리전 필수 |
| **서비스 가용 범위** | 새 서비스는 보통 버지니아 북부(`us-east-1`)에 먼저 나옵니다 |
| **가격** | **리전마다 가격이 다릅니다.** 대체로 버지니아가 가장 쌉니다 |

> 이번 실습(Step 1)에서 **같은 인스턴스의 가격이 리전마다 다른 것**을 직접 눈으로 확인합니다.

### 책임 공유 모델 — 어디까지가 내 일인가

AWS 보안의 출발점입니다. **"of the cloud"는 AWS, "in the cloud"는 고객**입니다.

```
 ┌──────────────────────────────────────────────┐
 │  고객 책임 (Security IN the cloud)            │
 │  · 데이터 (암호화 여부, 무엇을 저장할지)        │
 │  · 접근 권한 (IAM 정책)                        │
 │  · 방화벽 설정 (보안 그룹)                     │
 │  · 게스트 OS 패치, 애플리케이션 취약점          │
 ├──────────────────────────────────────────────┤
 │  AWS 책임 (Security OF the cloud)             │
 │  · 물리 데이터센터 보안 · 전원 · 냉각           │
 │  · 하드웨어 · 하이퍼바이저 · 글로벌 네트워크     │
 └──────────────────────────────────────────────┘
```

**경계는 서비스 유형마다 움직입니다.** 이게 시험에도 실무에도 자주 나옵니다.

| 서비스 | 게스트 OS 패치 | 데이터 암호화 설정 | 물리 보안 |
|---|---|---|---|
| **EC2**(IaaS) | 🙋 고객 | 🙋 고객 | 🅰️ AWS |
| **RDS**(관리형) | 🅰️ AWS | 🙋 고객(켤지 말지) | 🅰️ AWS |
| **Lambda / S3**(서버리스) | 🅰️ AWS | 🙋 고객 | 🅰️ AWS |

> **관리형 서비스를 쓸수록 내 책임이 줄어듭니다.** 대신 자유도도 줄어듭니다. 이 트레이드오프가 앞으로 "EC2냐 RDS냐, EC2냐 Lambda냐"를 고르는 기준이 됩니다.
> 단, **어떤 서비스를 쓰든 "누가 접근할 수 있는가(IAM)"와 "무엇을 저장하는가(데이터)"는 항상 고객 책임**입니다.

### 요금 모델 — "쓴 만큼"이 아니라 "켜 둔 만큼"

가장 많이 오해하는 지점입니다.

> ⚠️ EC2 인스턴스는 **아무도 접속하지 않아도, 아무 일도 하지 않아도** 켜져 있는 동안 계속 과금됩니다.
> "쓴 만큼 낸다"의 **'쓴다'는 '켜 둔다'** 는 뜻입니다.

| 구매 옵션 | 할인 | 약정 | 언제 쓰나 |
|---|---|---|---|
| **온디맨드** | 없음(기준가) | 없음 | 예측 불가·단기·개발 환경. **이 과정의 기본** |
| **Savings Plans** | 최대 72% | 1년 또는 3년 시간당 사용액 | 상시 운영되는 서비스 |
| **예약 인스턴스(RI)** | 최대 72% | 1년 또는 3년, 특정 사양 | 사양이 고정된 장기 워크로드 |
| **스팟 인스턴스** | 최대 90% | 없음 (단, **2분 통보 후 회수 가능**) | 배치·렌더링·CI 빌드처럼 **중단돼도 되는** 작업 |

**스팟을 쓰면 안 되는 것** — 단일 데이터베이스 서버, 세션을 들고 있는 웹 서버처럼 **중단되면 곤란한** 워크로드.

### 프리 티어 3종류

| 유형 | 예 | 주의 |
|---|---|---|
| **12개월 무료** | EC2 t3.micro 750시간/월, RDS 750시간/월, S3 5GB | 계정 생성일로부터 12개월 |
| **상시 무료** | Lambda 월 100만 요청, DynamoDB 25GB, CloudFront 월 1TB 전송 | 기간 제한 없음 |
| **평가판** | 일부 서비스 단기 체험 | 기간 지나면 자동 과금 |

> 🔴 **프리 티어에 아예 없는 대표 리소스** — **NAT Gateway · Application Load Balancer · ECS Fargate · KMS 고객 관리 키 · WAF.**
> 이 다섯은 만드는 순간부터 시간당 과금됩니다. 각각 [07강](lesson-07.md), [11강](../02-compute-data/lesson-11.md), [21강](../03-serverless-automation/lesson-21.md)에서 다시 경고합니다.

> 📌 **2025년 7월 이후 개설 계정**은 기존 12개월 프리 티어 대신 **크레딧 기반 무료 플랜**이 적용될 수 있습니다.
> 정책은 계속 바뀌므로 문서를 믿지 말고 **[02강](lesson-02.md) Step 5에서 본인 콘솔 화면으로 직접 확인**합니다.

## ④ 단계별 실습

> **이번 강은 리소스를 하나도 만들지 않습니다.** 조회와 계산만 합니다. 따라서 **비용은 $0** 입니다.
> AWS 계정이 아직 없다면 [02강](lesson-02.md) Step 1을 먼저 하고 돌아와도 됩니다.

### Step 1. 리전에 따라 가격이 얼마나 다른지 직접 보기

AWS 콘솔에 로그인한 뒤, **화면 오른쪽 위의 리전 표시**를 확인합니다. 이 과정의 기준은 **아시아 태평양(서울) ap-northeast-2** 입니다.

**① EC2 요금 페이지 열기** — 콘솔 검색창에 `EC2` → 왼쪽 메뉴 아래쪽의 **인스턴스 유형(Instance Types)** 을 엽니다.
여기서 인스턴스 유형별 **온디맨드 시간당 요금**을 볼 수 있습니다.

**② `t3.micro` 로 필터링**한 뒤 시간당 요금을 적어 둡니다.

**③ 오른쪽 위 리전을 바꿔 가며** 같은 값을 확인합니다.

| 리전 | 코드 | t3.micro 온디맨드(Linux, 시간당) | 720시간(약 1개월) |
|---|---|---|---|
| 미국 동부(버지니아 북부) | `us-east-1` | 약 $0.0104 | 약 $7.5 |
| 아시아 태평양(도쿄) | `ap-northeast-1` | 약 $0.0136 | 약 $9.8 |
| **아시아 태평양(서울)** | **`ap-northeast-2`** | **약 $0.0130** | **약 $9.4** |

> 값은 **2026년 8월 기준 예시**이며 실제 화면 값과 다를 수 있습니다. **화면에 보이는 값을 정답으로** 적으세요.
> 서울이 버지니아보다 약 25% 비싼 것이 보일 겁니다. 그럼에도 한국 서비스는 대개 서울을 씁니다. **지연 시간과 규제가 가격보다 중요하기 때문**입니다.

⚠️ **리전을 바꿨다면 반드시 서울로 되돌려 놓으세요.** 다른 리전에 리소스를 만들어 놓고 잊는 것이 이 과정의 대표 사고 유형입니다.

### Step 2. Pricing Calculator로 견적서 만들기

브라우저에서 **AWS Pricing Calculator**(`calculator.aws`)를 엽니다. 로그인 없이도 됩니다.

**만들 견적** — "서울 리전에서 t3.small 1대를 24시간 운영 + EBS gp3 30GB"

| 입력 항목 | 값 |
|---|---|
| 리전 | Asia Pacific (Seoul) |
| 서비스 | Amazon EC2 |
| 운영 체제 | Linux |
| 인스턴스 유형 | `t3.small` |
| 사용률 | 100% (월 730시간) |
| 결제 옵션 | On-Demand |
| EBS 볼륨 | General Purpose SSD (gp3), 30 GB |

**예상 결과 (약)**

```
EC2 인스턴스 (t3.small, 730시간)     약 $19.0 /월
EBS gp3 스토리지 (30GB)              약  $2.8 /월
─────────────────────────────────────────────
합계                                 약 $21.8 /월  (연 약 $262)
```

오른쪽 위 **[공유(Share)]** 버튼으로 견적 링크를 만들 수 있습니다. 이 링크를 과제로 제출합니다.

> 💡 **여기서 확인할 것** — 서버 값(₩)만 계산하면 실제 청구액과 항상 어긋납니다.
> **스토리지·데이터 전송·퍼블릭 IP** 같은 부속 비용이 전체의 20~40%를 차지하는 일이 흔합니다.

### Step 3. 내 리전에 AZ가 몇 개인지 확인하기

콘솔 검색창에 `VPC` → 왼쪽 메뉴 **서브넷(Subnets)** 을 엽니다.
새 계정에는 **기본 VPC(default VPC)** 가 이미 있고, 그 안에 AZ마다 서브넷이 하나씩 만들어져 있습니다.

**가용 영역** 열을 보면 이렇게 나옵니다.

```
서브넷 ID              가용 영역           IPv4 CIDR
subnet-0a1b2c3d...    ap-northeast-2a    172.31.0.0/20
subnet-0e4f5g6h...    ap-northeast-2b    172.31.16.0/20
subnet-0i7j8k9l...    ap-northeast-2c    172.31.32.0/20
subnet-0m1n2o3p...    ap-northeast-2d    172.31.48.0/20
```

**서울 리전에는 AZ가 4개**(`2a` `2b` `2c` `2d`) 있습니다. 이 중 **2개 이상에 걸쳐 배치하는 것**이 앞으로 만들 모든 구조의 기본형입니다.

> 📌 **AZ 이름은 계정마다 물리적 위치가 다릅니다.** 내 계정의 `2a`와 다른 사람의 `2a`가 같은 건물이라는 보장이 없습니다.
> (물리적으로 같은 곳을 가리키는 것은 `AvailabilityZoneId`, 예: `apne2-az1` 입니다.)

### Step 4. 온프레미스 vs 클라우드 3년 비용 비교표 만들기

**상황** — 웹 서버 3대(4 vCPU / 16GB)를 3년간 운영한다.

아래 표를 채워 과제로 제출합니다. 값은 직접 조사하거나 아래 예시를 참고하세요.

## ⑤ 자주 하는 실수

### 리전을 바꿔 놓고 잊어서 리소스를 못 찾는다

**증상** — 어제 분명히 만든 인스턴스가 EC2 목록에 없습니다. 목록이 텅 비어 있습니다.

```
현재 리전에 실행 중인 인스턴스가 없습니다
No instances found in this Region
```

**원인** — AWS 콘솔은 **대부분의 서비스가 리전별로 완전히 분리**되어 있습니다. 버지니아에서 만든 인스턴스는 서울 화면에 절대 나오지 않습니다.
**해결** — 오른쪽 위 리전 표시를 바꿔 가며 찾습니다. 어느 리전인지 모르겠다면 **결제 대시보드 → 비용 및 사용 보고서**에서 리전별 비용을 보면 어디에 뭐가 살아 있는지 드러납니다.
**예방** — 이 과정은 **서울 고정**입니다. 실습 시작 전 리전을 확인하는 것을 습관으로 만드세요.

> 예외적으로 **IAM · Route 53 · CloudFront · S3 버킷 이름**은 리전에 종속되지 않는(글로벌) 개념입니다.

### "프리 티어니까 공짜"라고 생각한다

**증상** — 프리 티어 계정인데 $30 청구서를 받습니다.
**원인** 세 가지 중 하나입니다.

| 원인 | 예 |
|---|---|
| 프리 티어에 **없는 서비스**를 씀 | NAT Gateway(월 $42), ALB(월 $17), Fargate |
| 무료 **한도를 초과** | EC2 750시간/월인데 4대를 켜면 8일 만에 소진 |
| **12개월이 지남** | 13개월째부터 전액 과금 |

**해결** — [02강](lesson-02.md)에서 예산 알림을 걸고, 매 강 마지막의 정리 체크리스트를 반드시 수행합니다.

### 인스턴스를 "중지"했으니 돈이 안 나갈 거라 생각한다

**원인** — 중지(stop)하면 **컴퓨팅 요금만** 멈춥니다. 붙어 있는 **EBS 볼륨과 탄력적 IP는 계속 과금**됩니다.
**해결** — 실습 리소스는 중지가 아니라 **종료(terminate) + 볼륨 삭제**가 정답입니다. [06강](lesson-06.md)에서 실습합니다.

### AZ 이름이 모든 계정에서 같은 물리 위치라고 생각한다

**원인** — AWS는 특정 AZ에 부하가 몰리지 않도록 **계정마다 AZ 이름을 무작위로 매핑**합니다.
**해결** — 계정 간에 물리적 위치를 맞춰야 한다면 이름(`ap-northeast-2a`)이 아니라 **AZ ID(`apne2-az1`)** 를 기준으로 봐야 합니다. 혼자 쓰는 계정에서는 신경 쓸 일이 없습니다.

### 가격을 원화로 계산해 두고 청구서와 다르다고 놀란다

**원인** — AWS 청구는 **USD 기준**이며, 국내 카드로 결제할 때 **환율과 카드사 수수료**가 붙습니다.
**해결** — 견적은 달러로 관리하고, 원화는 참고값으로만 씁니다. 결제 통화를 KRW로 설정할 수도 있지만 AWS 환율이 적용됩니다.

### 서버를 여러 대 띄웠으니 안전하다고 생각한다

**원인** — 3대를 띄웠지만 **전부 같은 AZ**에 있으면 그 AZ에 문제가 생길 때 3대가 동시에 죽습니다.
**해결** — 가용성은 대수가 아니라 **분산 범위**로 만듭니다. [10강 Auto Scaling](../02-compute-data/lesson-10.md)에서 2개 AZ에 나눠 배치하는 것을 실습합니다.

## ⑥ 확인 문제

**1.** 어떤 서비스가 "AZ 3개에 서버를 3대 배치했다"고 합니다. 이때 **AZ 하나가 통째로 정전**되면 무슨 일이 벌어지나요? 반대로 "같은 AZ에 3대"였다면요?

<details>
<summary>답 보기</summary>

**AZ 3개에 1대씩 → 서비스는 계속됩니다.** 1대(전체의 1/3)를 잃지만 나머지 2대가 요청을 받습니다. (단, 남은 2대가 늘어난 부하를 감당할 수 있어야 하므로 용량 설계 시 **AZ 하나가 빠진 상태**를 가정합니다.)

**같은 AZ에 3대 → 3대가 동시에 죽고 서비스가 중단됩니다.** 대수를 늘린 것은 **성능**에는 도움이 되지만 **가용성**에는 아무 도움이 되지 않았습니다.

> **가용성 = 물리적으로 분리된 곳에 나눠 두는 것.** AZ는 전원·냉각·네트워크가 독립된 데이터센터 묶음이므로 이 분리의 최소 단위입니다.
</details>

**2.** 다음 각 항목은 **AWS 책임**인가요, **고객 책임**인가요?

| # | 항목 |
|---|---|
| ① | EC2 안의 리눅스 커널 보안 패치 |
| ② | S3에 저장한 파일이 하드디스크 고장으로 손상되는 것 |
| ③ | S3 버킷을 전체 공개로 설정해 정보가 유출된 것 |
| ④ | RDS의 MySQL 마이너 버전 패치 |
| ⑤ | 데이터센터에 외부인이 침입하는 것 |

<details>
<summary>답 보기</summary>

| # | 책임 | 이유 |
|---|---|---|
| ① | **고객** | EC2는 IaaS. 게스트 OS 위쪽은 전부 고객 몫 |
| ② | **AWS** | 스토리지 하드웨어와 내구성은 AWS 책임(11개의 9) |
| ③ | **고객** | 접근 제어 설정은 언제나 고객 책임 |
| ④ | **AWS** | RDS는 관리형 서비스. 단, **적용 시점(유지 관리 기간) 선택은 고객** |
| ⑤ | **AWS** | 물리 보안은 "of the cloud" |

**한 줄 판별법** — **"내가 콘솔에서 켜고 끌 수 있는 설정이면 내 책임"** 입니다. ③처럼 설정이 존재하는 항목은 전부 고객 책임입니다.
</details>

**3.** 다음 3개 워크로드에 온디맨드 · Savings Plans · 스팟 중 무엇을 추천하겠습니까? 근거도 한 줄씩 쓰세요.

```
㉮ 3년째 24시간 돌고 있는 사내 그룹웨어 웹 서버 3대
㉯ 매일 새벽 2시에 2시간 도는 영상 인코딩 배치 작업
㉰ 이번 주에 처음 띄워 보는 신규 서비스 테스트 서버
```

<details>
<summary>답 보기</summary>

| 워크로드 | 선택 | 근거 |
|---|---|---|
| ㉮ 상시 그룹웨어 | **Savings Plans** (또는 예약 인스턴스) | 3년간 사용량이 확실하므로 약정으로 최대 72% 절감. 사용량이 확실한데 온디맨드를 쓰는 것은 순수한 낭비 |
| ㉯ 새벽 인코딩 배치 | **스팟** | 중단돼도 재시도하면 그만인 작업. 최대 90% 절감. (회수되면 다음 배치에서 이어서 처리하도록 설계) |
| ㉰ 신규 테스트 | **온디맨드** | 얼마나 쓸지 모르고 곧 지울 수도 있음. 약정은 위험, 스팟은 개발 흐름이 끊겨 불편 |

**함정** — ㉯를 "중요한 작업이니 온디맨드"로 고르는 경우가 많습니다. 판단 기준은 **중요도가 아니라 "중단을 견딜 수 있는가"** 입니다. 인코딩은 중요하지만 **중단 후 재시작이 가능**하므로 스팟에 적합합니다.
</details>

## 오늘의 정리

| 개념 | 핵심 |
|---|---|
| 클라우드 | 필요한 만큼 빌려 쓰고 **켜 둔 만큼** 지불 |
| CapEx / OpEx | 자산 구매(선지출) / 운영비(사용량) |
| **리전** | 지리적으로 분리된 지역. 서로 독립. 이 과정은 `ap-northeast-2` |
| **AZ** | 리전 안에서 전원·냉각·회선이 분리된 데이터센터 묶음. **고가용성의 최소 단위** |
| 엣지 로케이션 | CloudFront 캐시가 놓이는 전 세계 접점 |
| 책임 공유 모델 | AWS는 "of the cloud", 고객은 "in the cloud" |
| 요금 모델 | 온디맨드 / Savings Plans / 예약 / **스팟(중단 허용 작업)** |
| 프리 티어 | 12개월 무료 · 상시 무료 · 평가판. **NAT·ALB·Fargate는 미포함** |

**한 장 요약**

```
   리전 (서울)
     └─ AZ 2a · 2b · 2c · 2d      ← 여기에 "나눠 두는 것"이 고가용성
          └─ 내 서버 · DB · 로드밸런서

   과금 = 켜 둔 시간 × 단가 (+ 스토리지 + 전송 + 퍼블릭 IP)
```

**오늘 반드시 기억할 한 가지**
> **리전은 고정, 리소스는 AZ에 분산, 청구는 켜 둔 시간 기준.**
> 이 세 문장이 앞으로 16주 동안 나오는 거의 모든 결정의 배경입니다.

**과제**
1. Step 2의 Pricing Calculator 견적을 만들고 **공유 링크**를 제출하세요.
2. 서울 · 도쿄 · 버지니아 3개 리전의 `t3.small` 시간당 요금과 월 요금을 표로 만들고, **어느 리전을 택할지와 근거 3줄**을 쓰세요.
3. Step 4의 온프레미스 vs 클라우드 3년 비교표를 완성하고 질문 3개에 답하세요.
4. 내가 자주 쓰는 서비스(예: 유튜브, 배달 앱) 하나를 골라 **"리전·AZ·엣지 로케이션이 각각 어디에 쓰일까"** 를 세 줄로 추측해 보세요.
