## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- SSH **키 쌍(공개키/비밀키)** 의 역할 분담을 설명하고, 비밀번호 없는 키 기반 접속을 설정할 수 있다.
- **포트**가 무엇인지 알고, `ss` 로 "지금 이 서버가 어느 문을 열고 있는지" 조사할 수 있다.
- `scp` 와 `rsync` 로 파일·코드를 서버에 배포하고, 두 도구의 용도 차이를 말할 수 있다.
- 방화벽의 역할을 이해하고, 접속 실패를 **단계별로 진단**할 수 있다.

## ② 왜 필요한가

어제까지의 실습에는 눈속임이 하나 있었습니다 — WSL 터미널을 "서버 접속"이라 불렀지만, 사실은
같은 컴퓨터 안이었죠. 진짜 서버는 데이터센터에 있고, 여러분이 만질 수 있는 건 네트워크 너머의
**문**뿐입니다. 그 문의 표준이 SSH(Secure Shell)입니다.

그런데 문에는 자물쇠가 필요하고, 비밀번호는 나쁜 자물쇠입니다. 공개 인터넷의 서버는 개통
수 분 내에 전 세계 봇들의 비밀번호 무차별 대입(brute force)을 받기 시작합니다 —
`/var/log/auth.log` 를 열어 본 운영자는 압니다, `Failed password for root from ...` 가
초 단위로 쌓이는 풍경을. 그래서 실무 서버의 표준은:

> **비밀번호 인증은 끄고, 키(key)로만 연다.** — 오늘 우리 서버도 이 상태로 만듭니다.

낯선 이야기가 아닙니다 — 여러분은 이미 W01부터 GitHub에 SSH 키로 push 해 왔습니다.
오늘은 그 원리를 이해하고, **내 서버의 문**에 같은 자물쇠를 다는 날입니다. 그리고 문이 열리면
드디어 배포다운 배포를 합니다: `/mnt/c` 뒷문이 아니라, 어느 서버에나 통하는 정문(scp/rsync)으로.

## ③ 개념 설명

### SSH 키 — 자물쇠는 서버에, 열쇠는 나에게

키 쌍은 수학적으로 엮인 파일 두 개입니다:

| 파일 | 별명 | 어디에 | 권한 |
|---|---|---|---|
| `id_ed25519` | **비밀키** = 열쇠 | **내 PC에만** — 절대 이동 금지 | 600 |
| `id_ed25519.pub` | **공개키** = 자물쇠 | 서버의 `~/.ssh/authorized_keys` 에 등록 | 644 |

접속 순서: 서버가 "이 자물쇠(공개키)를 열 수 있으면 들어와" 라고 난수 문제를 내고, 내 SSH
클라이언트가 비밀키로 서명해 답합니다. **비밀키는 네트워크를 타지 않습니다** — 그래서 도청도
재사용 공격도 통하지 않고, 비밀번호처럼 추측할 수도 없습니다.

역할 분담 문장으로 기억하세요: **공개키는 뿌리는 것**(서버마다, GitHub에도), **비밀키는 내
PC를 떠나지 않는 것.** 비밀키가 어딘가로 복사되는 순간이 곧 유출 사고입니다 ([Day 109](day-109.md)의
"폐기 먼저" 절차 대상).

### 포트 — IP가 건물이면 포트는 호실

서버 한 대(IP 하나)는 여러 서비스를 동시에 돌립니다. 어느 서비스로 갈지 정하는 번호가
**포트**(0~65535)입니다:

| 포트 | 관례 | 우리 서버에서 |
|---|---|---|
| 22 | SSH | (우리는 2222 사용 — WSL 사정, Step 1) |
| 80 / 443 | HTTP / HTTPS | W25에서 nginx가 엶 |
| 8000 | 개발용 웹 앱 관례 | **mp3-api** (어제부터) |
| 5432 | PostgreSQL | W07부터 쓰던 그 번호! |

지금 열린 문 조사가 운영 기본기입니다:

```bash
sudo ss -tlnp        # t=TCP, l=듣는 중(listen), n=숫자로, p=프로세스 표시
```

### 방화벽 — 문 앞의 문지기

포트가 열려 있어도(프로세스가 listen) **방화벽**이 밖에서 오는 접속을 거를 수 있습니다.
Ubuntu의 표준은 `ufw` 입니다: `sudo ufw allow 2222/tcp` → `sudo ufw enable` 식으로 "허용 목록"을
만듭니다. 원칙은 권한 때와 같은 **최소 개방** — SSH와 서비스 포트만 열고 나머지는 닫습니다.
(WSL은 Windows 뒤에 숨어 있어 오늘은 개념과 명령만 익히고, 클라우드 서버에서는 필수 절차입니다 —
클라우드는 보통 "보안 그룹"이라는 이름의 방화벽이 하나 더 있습니다.)

### scp vs rsync — 복사와 동기화

| | scp | rsync |
|---|---|---|
| 동작 | 무조건 전체 복사 | **차이만** 전송 (증분) |
| 용도 | 파일 몇 개, 단발 | 폴더 동기화, 반복 배포 |
| 대표형 | `scp -P 2222 model.pt deploy@host:/opt/...` | `rsync -avz -e "ssh -p 2222" ./app/ deploy@host:/opt/.../app/` |

45MB 모델을 처음 보낼 땐 둘이 같지만, 코드 한 줄 고치고 재배포할 때 rsync는 바뀐 파일만
보냅니다 — 내일 배포 스크립트의 주인공입니다.

## ④ 단계별 실습

오늘의 배치: **Windows PowerShell = 내 PC(클라이언트)**, **WSL Ubuntu = 원격 서버**.
같은 기계라는 사실은 잊습니다 — 모든 통신을 SSH로만 합니다.

### Step 1. 서버에 SSH 문 달기 (1~2교시)

WSL(서버) 쪽에서 SSH 서버를 설치하고, 포트를 2222로 지정합니다 (Windows 자체 OpenSSH 서비스와의
22번 충돌을 피하는 실습 환경 사정 — 진짜 서버라면 22 그대로 둡니다):

```bash
sudo apt install -y openssh-server
sudo sed -i 's/^#Port 22/Port 2222/' /etc/ssh/sshd_config
sudo systemctl enable --now ssh
systemctl status ssh | head -3
sudo ss -tlnp | grep -E "2222|8000"
```

```
$ systemctl status ssh | head -3
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/lib/systemd/system/ssh.service; enabled; vendor preset: enabled)
     Active: active (running) since Thu 2026-08-14 09:12:44 KST; 8s ago
$ sudo ss -tlnp | grep -E "2222|8000"
LISTEN 0      128          0.0.0.0:2222      0.0.0.0:*    users:(("sshd",pid=612,fd=3))
LISTEN 0      2048         0.0.0.0:8000      0.0.0.0:*    users:(("uvicorn",pid=598,fd=13))
```

문 두 개가 열려 있습니다 — 2222(SSH)와 8000(어제의 mp3-api, enable 덕분에 이미 떠 있음).
어제 배운 systemctl 동사들이 ssh 서비스에도 똑같이 통한다는 것도 확인하세요.

### Step 2. 첫 접속 — 비밀번호로 (3교시)

PowerShell(클라이언트)에서:

```powershell
ssh student@localhost -p 2222
```

```
$ ssh student@localhost -p 2222
The authenticity of host '[localhost]:2222 ([::1]:2222)' can't be established.
ED25519 key fingerprint is SHA256:hK3mZk1xQ9dTz2fW8pLr4vYqNc6jB0aGse5UonXhIw4.
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added '[localhost]:2222' (ED25519) to the list of known hosts.

Welcome to Ubuntu 22.04.4 LTS (GNU/Linux 5.15.167.4-microsoft-standard-WSL2 x86_64)
student@DESKTOP:~$
```

첫 질문은 **서버의 지문 확인**입니다 — "이 서버가 진짜 내가 아는 그 서버인가"를 사람이 한 번
보증하는 절차 (yes 후 known_hosts에 기록되어 다음부턴 안 묻습니다). `exit` 로 나옵니다.
비밀번호를 쳤죠 — 이제 이 문을 키로 바꿉니다.

### Step 3. 열쇠 만들기, 자물쇠 달기 (4~5교시)

PowerShell에서 키 쌍 생성 (이미 GitHub용 키가 있다면 그대로 써도 됩니다):

```powershell
ssh-keygen -t ed25519 -C "student@mlops-course"
```

```
$ ssh-keygen -t ed25519 -C "student@mlops-course"
Generating public/private ed25519 key pair.
Enter file in which to save the key (C:\Users\LEE/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Your identification has been saved in C:\Users\LEE/.ssh/id_ed25519
Your public key has been saved in C:\Users\LEE/.ssh/id_ed25519.pub
```

공개키(자물쇠)를 서버의 student와 **deploy 둘 다**에 등록합니다 (Windows에는 ssh-copy-id가
없어 파이프로 — 어제까지 배운 조합입니다):

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh student@localhost -p 2222 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh student@localhost -p 2222 "sudo -u deploy mkdir -p /home/deploy/.ssh && sudo -u deploy tee -a /home/deploy/.ssh/authorized_keys > $null && sudo chmod -R u=rwX,go= /home/deploy/.ssh"
```

`chmod 700 ~/.ssh` 와 `600 authorized_keys` — 어제의 권한 수업이 그대로 보안 요건입니다
(sshd는 이 권한이 느슨하면 **키를 무시**합니다, ⑤ 참고). 확인:

```powershell
ssh deploy@localhost -p 2222 "whoami && hostname"
```

```
$ ssh deploy@localhost -p 2222 "whoami && hostname"
deploy
DESKTOP
```

**비밀번호를 묻지 않고** 들어갔습니다. 이제 문을 잠급니다 — 서버에서 비밀번호 인증 자체를 차단:

```bash
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo systemctl restart ssh
```

> 진짜 원격 서버에서 이 잠금은 **키 접속이 되는 것을 확인한 뒤에!** 순서를 바꾸면 자기 서버에서
> 자신이 잠기는(lockout) 고전 사고가 납니다.

### Step 4. 정문으로 배포 — scp와 rsync (6~7교시)

모델 파일을 정식 경로로 배포합니다 (그동안의 /mnt/c 뒷문 금지):

```powershell
scp -P 2222 .\models\antbee_resnet18.pt deploy@localhost:/opt/mlops-mp3/models/
```

```
$ scp -P 2222 .\models\antbee_resnet18.pt deploy@localhost:/opt/mlops-mp3/models/
antbee_resnet18.pt                            100%   45MB 118.3MB/s   00:00
```

코드는 rsync로 — mlops-mp3 폴더에서 (rsync는 Git Bash/WSL 쪽에 있으므로 서버 쪽 pull 방식과
비교해 봅니다). 실무에서 더 흔한 배포는 사실 **서버가 Git에서 당겨오는** 방식입니다:

```powershell
ssh deploy@localhost -p 2222 "cd /opt/mlops-mp3 && git pull && .venv/bin/pytest -q"
```

```
$ ssh deploy@localhost -p 2222 "cd /opt/mlops-mp3 && git pull && .venv/bin/pytest -q"
Already up to date.
.......                                                              [100%]
7 passed in 5.92s
```

**ssh 뒤에 명령을 붙이면 접속-실행-종료가 한 번에** 됩니다 — 원격 자동화의 원자 단위이고,
내일 배포 스크립트와 W26 CD가 전부 이 형태의 확장입니다. 마지막으로 서비스 재시작에 sudo가
필요한 문제를 만나게 되는데(deploy는 sudo 불가), 오늘은 student로 재시작하고 이 불편을
기록해 두세요 — 내일 restart 권한만 콕 집어 허용하는 법(sudoers 한 줄)으로 해결합니다.

### Step 5. 과제 — 배포 절차 문서화 (8교시)

오늘까지의 수동 배포 전 과정을 `RUNBOOK.md` 로 문서화하세요. 형식:

1. **전제** — 서버 주소/포트, 계정, 키 등록 상태
2. **절차** — 순서대로 실행할 명령 (코드 갱신 → 의존성 → 테스트 → 재시작 → 확인)
3. **검증** — 배포가 성공했음을 확인하는 명령과 기대 출력 (`curl /health`, `systemctl status`)
4. **롤백** — 실패 시 되돌리는 명령 (git 어느 지점으로? 서비스 재시작은?)

내일 이 문서가 그대로 **스크립트의 설계도**가 됩니다 — "문서화 안 된 절차는 자동화도 안 된다"를
체험하게 될 겁니다.

## ⑤ 자주 하는 실수

### 비밀키 권한이 느슨해서 무시됨

**증상** —
```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Permissions 0644 for 'id_ed25519' are too open.
```
**원인** — 비밀키가 남이 읽을 수 있는 권한 — SSH는 이런 키를 **거부**합니다 (Day 112의 600
원칙을 도구가 강제하는 것).
**해결** — 리눅스라면 `chmod 600 ~/.ssh/id_ed25519`. Windows라면 파일 속성 → 보안에서 본인
외 계정 제거 (또는 `icacls` 로 상속 제거).

### Permission denied (publickey) — 서버 쪽 권한

**증상** — 키를 분명 등록했는데 `Permission denied (publickey)`.
**원인** — 서버 쪽 `~/.ssh`(700 아님)나 `authorized_keys`(600 아님)의 권한이 느슨하면 sshd가
그 자물쇠를 **통째로 무시**합니다. 홈 폴더가 그룹 쓰기 가능이어도 같습니다.
**해결** — 서버에서 `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`. 그래도 안 되면
`ssh -v` (자세한 로그)로 어느 단계에서 거절되는지 읽습니다 — 진단 없는 재시도 금지.

### Connection refused와 timeout을 구분 못 함

**증상** — 접속 불가. 그런데 메시지가 두 종류입니다:
```
ssh: connect to host localhost port 2222: Connection refused
ssh: connect to host 10.0.3.7 port 22: Connection timed out
```
**원인/해결** — **refused = 문까지 갔는데 아무도 안 듣는 것** → 서버 쪽 sshd가 죽었거나 포트가
다름 (`systemctl status ssh`, `ss -tlnp`). **timeout = 문까지 가지도 못한 것** → 방화벽/보안
그룹/주소 문제. 에러 한 단어가 조사할 층을 알려 줍니다 — 네트워크 진단의 첫 갈림길입니다.

### 비밀키를 서버·저장소에 복사

**증상** — "서버에서 GitHub pull이 안 돼서" 내 비밀키를 서버에 올리거나, 백업한다고 저장소에
커밋 — 열쇠 유출.
**원인** — 공개키/비밀키의 역할 분담 혼동.
**해결** — 서버가 GitHub에서 당겨와야 하면 **서버의 키 쌍을 새로 만들어**(deploy 계정에서
ssh-keygen) 그 **공개키**를 GitHub에 Deploy Key로 등록합니다. 비밀키는 태어난 기계를 떠나지
않는다 — 예외를 만들지 마세요. 커밋했다면 [Day 109](day-109.md) 절차(즉시 폐기)입니다.

### REMOTE HOST IDENTIFICATION HAS CHANGED

**증상** —
```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```
**원인** — known_hosts에 기록된 서버 지문과 다름. 실습에선 대개 WSL 재설치·서버 재구축 때문이지만,
**원리상으로는 중간자 공격 경고**입니다.
**해결** — 서버를 내가 다시 깔았다는 확신이 있을 때만 `ssh-keygen -R "[localhost]:2222"` 로 옛
지문을 지우고 재접속. 남의 서버·운영 서버에서 이 경고가 떴다면 지우기 전에 관리자에게 확인 —
경고를 기계적으로 지우는 습관이 최악입니다.

통째로 유출되어도 계정이 뚫리지 않는 이유를 설명하세요.

<summary>답 보기</summary>

authorized_keys에 있는 것은 **자물쇠**(공개키)입니다. 접속에 필요한 것은 그 자물쇠에 대응하는
**열쇠**(비밀키)의 서명인데, 공개키로는 비밀키를 역산할 수 없습니다 (수학적 일방향성). 유출된
자물쇠로 할 수 있는 일은 "이 자물쇠를 다른 문에도 달기"뿐 — 그 문 역시 원래 열쇠 주인만 엽니다.
반면 비밀번호 인증은 서버가 검증 자료(해시)를 갖고, 사용자가 비밀 그 자체를 매번 전송하므로
서버 침해·도청·추측 모두에 취약합니다.

</details>

**Q2.** `sudo ss -tlnp` 출력에 `0.0.0.0:8000` 이 있습니다. `127.0.0.1:8000` 과의 차이는
무엇이고, 어제 유닛의 `--host 0.0.0.0` 은 무엇을 의도한 것인지 쓰세요.

<details>
<summary>답 보기</summary>

listen 주소는 "어느 방향에서 오는 손님을 받나"입니다. `127.0.0.1:8000` 은 **같은 기계 안**에서
오는 접속만(외부 차단), `0.0.0.0:8000` 은 이 서버의 **모든 네트워크 인터페이스**로 오는 접속을
받습니다. 서비스는 외부 클라이언트를 받아야 하므로 0.0.0.0으로 열었습니다 — 단, 그만큼 방화벽과
(W25에서) 프록시 뒤로 정리하는 설계가 함께 가야 합니다. DB처럼 내부 전용인 것은 반대로
127.0.0.1(또는 내부망)로 조입니다.

</details>

**Q3.** Step 4의 두 배포 방식 — ① 내 PC에서 rsync/scp로 밀어 넣기(push형) ② 서버가 git pull로
당겨오기(pull형) — 각각의 장단점을 하나씩 대고, W26의 자동 배포는 어느 쪽에 가까울지 예상해
보세요.

<details>
<summary>답 보기</summary>

push형: 장점 — Git에 없는 대용량(모델 파일)도 보낼 수 있고 임의 시점 배포가 자유. 단점 — "지금
내 PC에 있는 것"이 나가므로 커밋 안 된 변경이 섞여 재현성이 깨질 수 있음. pull형: 장점 — 서버
상태가 항상 **저장소의 특정 커밋**과 일치해 족보가 명확 (재현성·롤백 용이). 단점 — 저장소 밖
자산은 별도 채널 필요. W26의 CD는 pull형의 정신(저장소가 유일한 진실)을 따르되, 실행 주체가
사람에서 GitHub Actions로 바뀐 형태입니다 — 커밋이 곧 배포 단위가 됩니다.

</details>
