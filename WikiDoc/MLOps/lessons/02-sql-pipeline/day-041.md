## ② 왜 필요한가

지금까지 열흘 동안 SQL을 **손으로** 쳤습니다. 이제 자동화할 차례입니다.

```
Day 030 datapipe          Day 041 오늘             Day 043 완성형
─────────────────         ────────────────         ─────────────────
수집 → 정제 → 파일         수집 → 정제 → ???        수집 → 정제 → DB
                                    ↑
                          여기를 파이썬 코드로 잇는다
```

**그리고 오늘 이 단원에서 가장 중요한 보안 주제를 배웁니다.**

```python
# 어디서나 볼 수 있는 코드. 그리고 사고의 원인.
city = request.args.get("city")
cur.execute(f"SELECT * FROM customers WHERE city = '{city}'")
```

`city` 에 `서울' OR '1'='1` 이 들어오면 **고객 전체가 유출**됩니다.
`'; DROP TABLE customers; --` 가 들어오면 **테이블이 사라집니다.**

이것이 **SQL 인젝션**이고, 20년 넘게 웹 취약점 1~3위를 지키고 있습니다.
막는 방법은 아주 간단한데, **모르면 100% 뚫립니다.** 오늘 직접 뚫어 보고 막습니다.

## ③ 개념 설명

### 파이썬에서 DB를 쓰는 층

```
[내 코드]
   │
   ├── psycopg 3          PostgreSQL 전용 드라이버 (DB-API 2.0 표준)
   │                      → 세밀한 제어. ETL·배치에 적합
   │
   └── SQLAlchemy 2       DB 종류에 상관없는 상위 도구 + 커넥션 풀
       ├── Core           SQL을 직접 쓰되 연결 관리를 맡김  ← 이 과정에서 사용
       └── ORM            테이블을 파이썬 클래스로 (W19 FastAPI에서)
```

| 도구 | 언제 |
|---|---|
| **psycopg 3** | 대량 적재(`COPY`), PostgreSQL 고유 기능, 세밀한 트랜잭션 제어 |
| **SQLAlchemy Core** | 여러 곳에서 연결을 재사용, Pandas 연동, 웹 서비스 |
| ORM | 모델이 복잡한 애플리케이션 (W19–W20) |

**둘 다 씁니다.** 서로 배타적이지 않습니다.

### DB-API 2.0 — 파이썬 표준

```python
conn = psycopg.connect(...)      # ① 연결
cur  = conn.cursor()             # ② 커서 (명령을 보내고 결과를 받는 창구)
cur.execute("SELECT ...")        # ③ 실행
rows = cur.fetchall()            # ④ 결과 받기
conn.commit()                    # ⑤ 확정
conn.close()                     # ⑥ 정리
```

| 메서드 | 반환 |
|---|---|
| `fetchone()` | 한 행 (없으면 `None`) |
| `fetchall()` | 전체 행 리스트 |
| `fetchmany(n)` | n행씩 |
| `cur.rowcount` | 영향받은 행 수 (`UPDATE`/`DELETE` 확인용) |

`for row in cur:` 처럼 **커서를 순회**할 수도 있습니다. 큰 결과에서는 이쪽이 메모리에 유리합니다.

### `with` 문 — 닫는 걸 잊지 않는 방법

```python
with psycopg.connect(dsn) as conn:        # 블록 끝에서 commit (예외 시 rollback)
    with conn.cursor() as cur:            # 블록 끝에서 커서 닫힘
        cur.execute("...")
```

> **psycopg 3에서 `with conn` 은 트랜잭션 경계입니다.**
> 블록을 정상적으로 빠져나오면 `COMMIT`, 예외가 나면 `ROLLBACK` 됩니다. **연결은 닫히지 않습니다**(재사용 가능).
> 명시적으로 트랜잭션을 나누고 싶으면 `with conn.transaction():` 을 씁니다.

[Day 012](../01-python-data/day-012.md)에서 파일에 `with open(...)` 을 쓴 것과 같은 이유입니다.
**예외가 나도 정리되는 것**이 핵심입니다.

### 파라미터 바인딩 ★

**절대 규칙 — 값은 문자열로 붙이지 않고, `%s` 자리에 따로 넘깁니다.**

```python
# ❌ 절대 금지
cur.execute(f"SELECT * FROM customers WHERE city = '{city}'")
cur.execute("SELECT * FROM customers WHERE city = '" + city + "'")
cur.execute("SELECT * FROM customers WHERE city = '%s'" % city)

# ✅ 올바른 방법
cur.execute("SELECT * FROM customers WHERE city = %s", (city,))
```

**왜 안전한가** — 드라이버가 SQL문과 값을 **따로** 서버에 보냅니다.
서버는 이미 문장 구조를 확정한 뒤 값을 끼워 넣으므로, 값 안에 `'` 나 `;` 가 있어도 **그냥 문자로 취급**됩니다.

```
❌ 문자열 조립:  "SELECT ... WHERE city = '서울' OR '1'='1'"   ← 구조가 바뀜
✅ 바인딩:       "SELECT ... WHERE city = $1"  +  값: "서울' OR '1'='1"
                                                    └── 그런 이름의 도시를 찾을 뿐
```

| 주의 | 설명 |
|---|---|
| 값 1개여도 **튜플** | `(city,)` — 쉼표를 빠뜨리면 `(city)` 는 그냥 문자열 |
| `%s` 에 **따옴표를 치지 않는다** | `'%s'` ❌ → `%s` ✅ |
| 타입 상관없이 `%s` | 숫자·날짜·`None` 전부 `%s` |
| `LIKE` 는 값 쪽에 `%` 를 넣는다 | `cur.execute("... LIKE %s", (f"%{q}%",))` |

### 테이블·열 이름은 바인딩할 수 없다

```python
cur.execute("SELECT * FROM %s", (table,))     # ❌ 동작하지 않음
```

`%s` 는 **값** 자리에만 쓸 수 있습니다. 식별자가 동적이어야 한다면 두 가지 중 하나입니다.

```python
from psycopg import sql

# ① psycopg.sql 로 안전하게 조립 (자동으로 따옴표 처리)
cur.execute(sql.SQL("SELECT * FROM {}").format(sql.Identifier(table)))

# ② 허용 목록으로 검증 (더 안전. 대부분 이걸로 충분)
ALLOWED = {"customers", "orders", "products"}
if table not in ALLOWED:
    raise ValueError(f"허용되지 않은 테이블: {table}")
cur.execute(f"SELECT * FROM {table}")
```

**②를 우선하세요.** "동적 테이블 이름이 정말 필요한가"를 먼저 의심하는 것이 좋습니다.

### 커넥션 풀 — 연결은 비싸다

```
매 요청마다 connect()  →  TCP 핸드셰이크 + 인증 + 프로세스 생성 (수십 ms)
풀에서 빌려 쓰기        →  거의 0 ms
```

배치 스크립트는 연결 하나를 계속 쓰면 되지만, **웹 서비스(W19)에서는 풀이 필수**입니다.
SQLAlchemy `create_engine` 은 **기본으로 풀을 만들어 줍니다.**

### SQLAlchemy Core

```python
from sqlalchemy import create_engine, text

engine = create_engine("postgresql+psycopg://user:pw@host:5432/shop")

with engine.connect() as conn:
    rows = conn.execute(text("SELECT * FROM products WHERE price > :p"), {"p": 50000}).all()
```

| psycopg | SQLAlchemy |
|---|---|
| `%s` + 튜플 | `:이름` + 딕셔너리 |
| `conn.commit()` | `conn.commit()` 또는 `engine.begin()` 블록 |

**Pandas와의 연동**이 SQLAlchemy를 쓰는 가장 큰 이유입니다.

```python
import pandas as pd
df = pd.read_sql("SELECT * FROM products", engine)
```

> **`pd.read_sql` 에도 파라미터를 넘길 수 있습니다.** f-string으로 만들지 마세요.
> `pd.read_sql(text("... WHERE price > :p"), engine, params={"p": 50000})`

### Step 2. 연결 확인

`db_check.py`:

```python
import os

import psycopg
from dotenv import load_dotenv

load_dotenv()


def get_conninfo() -> str:
    """환경변수에서 접속 정보를 조립합니다."""
    required = ["PGHOST", "PGPORT", "PGDATABASE", "PGUSER", "PGPASSWORD"]
    missing = [k for k in required if not os.getenv(k)]
    if missing:
        raise RuntimeError(f".env 에 다음 값이 없습니다: {', '.join(missing)}")

    return (
        f"host={os.environ['PGHOST']} "
        f"port={os.environ['PGPORT']} "
        f"dbname={os.environ['PGDATABASE']} "
        f"user={os.environ['PGUSER']} "
        f"password={os.environ['PGPASSWORD']}"
    )


def main() -> None:
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT version()")
            print("서버:", cur.fetchone()[0].split(",")[0])

            cur.execute("SELECT current_database(), current_user")
            db, user = cur.fetchone()
            print(f"접속: {db} / {user}")

            cur.execute("SELECT COUNT(*) FROM customers")
            print("고객 수:", cur.fetchone()[0])


if __name__ == "__main__":
    main()
```

```python
from db_check import get_conninfo


def main() -> None:
```

### Step 4. SQL 인젝션 재현하기 ★★

**이 실습은 `shop` 이라는 학습용 DB에서만 하세요.**

`injection_demo.py`:

```python
import psycopg
from psycopg.rows import dict_row

from db_check import get_conninfo


def find_by_city_BAD(city: str) -> list[dict]:
    """❌ 절대 따라 하지 마세요 — 문자열을 직접 조립합니다."""
    sql = f"SELECT customer_id, name, city FROM customers WHERE city = '{city}'"
    print(f"  실행된 SQL: {sql}")
    with psycopg.connect(get_conninfo(), row_factory=dict_row) as conn:
        with conn.cursor() as cur:
            cur.execute(sql)
            return cur.fetchall()


def find_by_city_GOOD(city: str) -> list[dict]:
    """✅ 파라미터 바인딩."""
    with psycopg.connect(get_conninfo(), row_factory=dict_row) as conn:
        with conn.cursor() as cur:
            cur.execute(
                "SELECT customer_id, name, city FROM customers WHERE city = %s",
                (city,),
            )
            return cur.fetchall()


if __name__ == "__main__":
    print("=== 정상 입력 ===")
    rows = find_by_city_BAD("서울")
    print(f"  결과 {len(rows)}행\n")

    print("=== 공격 입력 ===")
    attack = "서울' OR '1'='1"
    rows = find_by_city_BAD(attack)
    print(f"  결과 {len(rows)}행  ← 전체 고객이 유출됨\n")

    print("=== 같은 공격, 바인딩 사용 ===")
    rows = find_by_city_GOOD(attack)
    print(f"  결과 {len(rows)}행  ← 그런 도시가 없으므로 0행")
```

```powershell
(venv) $ python injection_demo.py
=== 정상 입력 ===
  실행된 SQL: SELECT customer_id, name, city FROM customers WHERE city = '서울'
  결과 5행

=== 공격 입력 ===
  실행된 SQL: SELECT customer_id, name, city FROM customers WHERE city = '서울' OR '1'='1'
  결과 12행  ← 전체 고객이 유출됨

=== 같은 공격, 바인딩 사용 ===
  결과 0행  ← 그런 도시가 없으므로 0행
```

**5행이 12행이 됐습니다.** 공격자가 넣은 `' OR '1'='1` 이 **문장 구조를 바꿔** `WHERE` 조건을 항상 참으로 만들었습니다.

실제 사고에서는 여기서 그치지 않습니다. `UNION SELECT` 로 다른 테이블까지 뽑아냅니다.

```
서울' UNION SELECT customer_id, email, phone FROM customers WHERE '1'='1
    →  이름 자리에 이메일과 전화번호가 실려 나옵니다
```

**파괴형도 확인해 봅니다.** 희생용 테이블을 만들어 실험합니다.

```
shop=# CREATE TABLE victim (id integer);
CREATE TABLE
shop=# INSERT INTO victim VALUES (1), (2), (3);
INSERT 0 3
```

```python
>>> from injection_demo import find_by_city_BAD
>>> find_by_city_BAD("서울'; DROP TABLE victim; --")
  실행된 SQL: SELECT customer_id, name, city FROM customers WHERE city = '서울'; DROP TABLE victim; --'
[]
```

```
shop=# SELECT * FROM victim;
ERROR:  relation "victim" does not exist
LINE 1: SELECT * FROM victim;
                      ^
```

**테이블이 사라졌습니다.**

| 조각 | 역할 |
|---|---|
| `서울'` | 원래 문자열을 **닫는다** |
| `;` | 문장을 **끝낸다** |
| `DROP TABLE victim` | 새 문장을 **끼워 넣는다** |
| `--` | 뒤에 남은 `'` 를 **주석 처리** |

> **"우리 서비스는 사용자 입력을 안 받는데요"** 라는 말이 가장 위험합니다.
> 검색창·정렬 옵션·페이지 번호·쿠키·헤더·**수집한 외부 데이터** 전부가 입력입니다.
> [Day 043](day-043.md)에서 API로 받아 온 값을 그대로 SQL에 넣으면 똑같이 뚫립니다.

**규칙은 하나입니다 — 값은 무조건 `%s` 로 넘긴다.** 예외는 없습니다.

### Step 5. 쓰기와 트랜잭션

`write_demo.py`:

```python
import psycopg

from db_check import get_conninfo


def add_customer(name: str, email: str, city: str, grade: str) -> int:
    """고객을 추가하고 새 customer_id 를 반환합니다."""
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            cur.execute(
                """
                INSERT INTO customers (name, email, city, grade, joined_at)
                VALUES (%s, %s, %s, %s, CURRENT_DATE)
                RETURNING customer_id
                """,
                (name, email, city, grade),
            )
            new_id = cur.fetchone()[0]
        # with 블록을 정상 종료 → COMMIT
    return new_id


def place_order(customer_id: int, items: list[tuple[int, int]]) -> int:
    """주문 1건과 상세 여러 줄을 하나의 트랜잭션으로 넣습니다."""
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            cur.execute(
                """
                INSERT INTO orders (customer_id, ordered_at, status)
                VALUES (%s, CURRENT_DATE, 'paid')
                RETURNING order_id
                """,
                (customer_id,),
            )
            order_id = cur.fetchone()[0]

            for product_id, qty in items:
                cur.execute(
                    """
                    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
                    SELECT %s, %s, %s, price FROM products WHERE product_id = %s
                    """,
                    (order_id, product_id, qty, product_id),
                )
                if cur.rowcount == 0:
                    raise ValueError(f"존재하지 않는 상품: {product_id}")
    return order_id


if __name__ == "__main__":
    cid = add_customer("테스트유저", "test@example.com", "서울", "bronze")
    print(f"고객 생성: customer_id={cid}")

    oid = place_order(cid, [(1, 2), (4, 1)])

    # 실패 시 전부 롤백되는지 확인
    try:
        place_order(cid, [(1, 1), (999, 1)])       # 999번 상품은 없음
```

```python
"""데이터베이스 연결과 기본 CRUD.

- 접속 정보는 환경변수에서만 읽습니다 (코드에 하드코딩 금지).
- 모든 값은 파라미터 바인딩으로 전달합니다 (SQL 인젝션 방지).
"""

from __future__ import annotations

import logging
import os
from contextlib import contextmanager
from typing import Any, Iterator, Sequence

import psycopg
from psycopg.rows import dict_row

logger = logging.getLogger(__name__)

_REQUIRED = ("PGHOST", "PGPORT", "PGDATABASE", "PGUSER", "PGPASSWORD")


class DatabaseError(RuntimeError):
    """DB 계층에서 발생한 오류."""


def get_conninfo() -> str:
    missing = [k for k in _REQUIRED if not os.getenv(k)]
    if missing:
        raise DatabaseError(f"환경변수 누락: {', '.join(missing)}")
    return (
        f"host={os.environ['PGHOST']} port={os.environ['PGPORT']} "
        f"dbname={os.environ['PGDATABASE']} user={os.environ['PGUSER']} "
        f"password={os.environ['PGPASSWORD']}"
    )


@contextmanager
def connect(*, autocommit: bool = False) -> Iterator[psycopg.Connection]:
    """연결을 열고 블록이 끝나면 정리합니다."""
    conn = psycopg.connect(get_conninfo(), row_factory=dict_row, autocommit=autocommit)
    try:
        yield conn
        if not autocommit:
            conn.commit()
    except Exception:
        if not autocommit:
            conn.rollback()
        logger.exception("트랜잭션 롤백")
        raise
    finally:
        conn.close()


def fetch_all(sql: str, params: Sequence[Any] | None = None) -> list[dict]:
    with connect() as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        return cur.fetchall()


def fetch_one(sql: str, params: Sequence[Any] | None = None) -> dict | None:
    with connect() as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        return cur.fetchone()


def fetch_value(sql: str, params: Sequence[Any] | None = None) -> Any:
    row = fetch_one(sql, params)
    return next(iter(row.values())) if row else None


def execute(sql: str, params: Sequence[Any] | None = None) -> int:
    """INSERT/UPDATE/DELETE 를 실행하고 영향받은 행 수를 반환합니다."""
    with connect() as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        return cur.rowcount
```

## ⑥ 확인 문제

**1.** 아래 함수의 취약점을 지적하고, 공격 예시와 수정 코드를 쓰세요.

```python
def search_products(keyword, min_price, order_by):
    sql = f"""
        SELECT * FROM products
        WHERE name LIKE '%{keyword}%' AND price >= {min_price}
        ORDER BY {order_by}
    """
    cur.execute(sql)
    return cur.fetchall()
```

<details>
<summary>답 보기</summary>

**취약점 3개**

| 위치 | 문제 |
|---|---|
| `keyword` | 문자열 조립 → 인젝션 |
| `min_price` | 숫자라도 문자열로 조립되면 인젝션 (`0 OR 1=1`) |
| `order_by` | **식별자**라 바인딩 불가 → 허용 목록 검증 필요 |

**공격 예시**

```python
search_products("마우스", "0 OR 1=1", "price")
#  → WHERE ... AND price >= 0 OR 1=1        모든 상품 노출

search_products("' UNION SELECT customer_id, name, email, phone, grade FROM customers --", 0, "1")
#  → 고객 개인정보가 상품 목록 자리에 실려 나옴
```

> `UNION` 공격은 **열 개수와 타입이 맞아야** 성공합니다.
> 공격자는 `ORDER BY 1,2,3...` 으로 열 개수를 알아냅니다. 그래서 `order_by` 노출이 특히 위험합니다.

**수정 코드**

```python
ALLOWED_ORDER = {
    "price_asc":  "price ASC",
    "price_desc": "price DESC",
    "name":       "name ASC",
}

def search_products(keyword: str, min_price: int, order_by: str = "price_desc"):
    if order_by not in ALLOWED_ORDER:
        raise ValueError(f"허용되지 않은 정렬: {order_by}")

    sql = f"""
        SELECT product_id, name, category, price, stock
        FROM products
        WHERE name LIKE %s AND price >= %s
        ORDER BY {ALLOWED_ORDER[order_by]}
    """
    cur.execute(sql, (f"%{keyword}%", min_price))
    return cur.fetchall()
```

**세 가지 원칙이 들어 있습니다.**

1. **값은 `%s`** — `keyword` · `min_price`
2. **`%` 와일드카드는 값 쪽에** — `f"%{keyword}%"` (SQL 안이 아니라)
3. **식별자는 허용 목록으로** — 사용자 입력이 SQL에 **직접 닿지 않습니다.**
   `ALLOWED_ORDER[order_by]` 는 **우리가 작성한 문자열**입니다.

`SELECT *` 를 열 목록으로 바꾼 것도 개선입니다 ([Day 032](day-032.md)).
열이 추가되면 의도치 않은 정보가 노출될 수 있습니다.
</details>

**2.** 아래 코드에는 [Day 039](day-039.md)에서 배운 문제가 있습니다. 무엇이며 어떻게 고치나요?

```python
def decrease_stock(product_id: int, qty: int) -> None:
    with db.connect() as conn, conn.cursor() as cur:
        cur.execute("SELECT stock FROM products WHERE product_id = %s", (product_id,))
        stock = cur.fetchone()["stock"]
        if stock < qty:
            raise ValueError("재고 부족")
        cur.execute(
            "UPDATE products SET stock = %s WHERE product_id = %s",
            (stock - qty, product_id),
        )
```

<details>
<summary>답 보기</summary>

**갱신 손실(lost update)** 입니다.

`SELECT` 와 `UPDATE` 사이에 다른 프로세스가 같은 상품의 재고를 바꾸면, **그 변경이 덮어써집니다.**

```
재고 100

A: SELECT → 100      B: SELECT → 100
A: 100-30 = 70 로 UPDATE
                     B: 100-50 = 50 로 UPDATE   ★ A의 30 차감이 사라짐

기대: 20   실제: 50
```

**해결 ① 계산을 DB에 맡기고 조건도 SQL에 넣는다 (권장)**

```python
def decrease_stock(product_id: int, qty: int) -> None:
    with db.connect() as conn, conn.cursor() as cur:
        cur.execute(
            """
            UPDATE products
            SET stock = stock - %s
            WHERE product_id = %s AND stock >= %s
            """,
            (qty, product_id, qty),
        )
        if cur.rowcount == 0:
            raise ValueError("재고 부족 또는 없는 상품")
```

**`AND stock >= %s`** 가 핵심입니다. 재고 검사와 차감이 **하나의 원자적 명령**이 됩니다.
조건에 안 맞으면 `rowcount` 가 0이 되어 그것으로 실패를 판정합니다.

**해결 ② `FOR UPDATE` 로 잠근다** (읽은 값으로 복잡한 판단이 필요할 때)

```python
cur.execute(
    "SELECT stock FROM products WHERE product_id = %s FOR UPDATE",
    (product_id,),
)
```

`FOR UPDATE` 는 **같은 트랜잭션 안에서만** 유효합니다.
`db.connect()` 블록이 트랜잭션 경계이므로 위 코드에서는 그대로 동작합니다.

> **①이 가능하면 언제나 ①입니다.** 잠금은 대기와 데드락을 부릅니다.
> "읽어서 파이썬에서 계산하고 다시 쓰기"가 보이면 **일단 의심**하세요.
> [Day 042](day-042.md)의 `ON CONFLICT DO UPDATE` 도 같은 발상 — DB 안에서 한 번에 끝냅니다.
</details>

**3.** `db.py` 의 `fetch_all` 은 `sql` 을 문자열로 받습니다. 이것은 인젝션 위험이 아닌가요? 안전한 이유와, 그럼에도 지켜야 할 규칙을 설명하세요.

<details>
<summary>답 보기</summary>

**`fetch_all` 자체는 안전합니다. 위험은 호출하는 쪽에 있습니다.**

```python
db.fetch_all(queries.CUSTOMER_BY_CITY, (user_input,))     # ✅ 안전
db.fetch_all(f"SELECT * FROM customers WHERE city='{user_input}'")   # ❌ 위험
```

`fetch_all` 은 받은 문자열을 그대로 실행할 뿐입니다.
**SQL 문자열이 어떻게 만들어졌는지**가 안전을 가릅니다.

| 안전 | 위험 |
|---|---|
| **개발자가 소스에 쓴** SQL 상수 | **사용자 입력이 섞인** 문자열 |

**지켜야 할 규칙**

1. **SQL은 `queries.py` 에만 둔다** — SQL이 코드 곳곳에 흩어지면 f-string이 언제 끼어들었는지 알 수 없습니다.
   한 파일에 모여 있으면 **`f"` 로 시작하는 SQL이 있는지 눈으로 검사**할 수 있습니다.
2. **값은 반드시 `params` 로** — `fetch_all(sql, params)` 의 두 번째 인자.
3. **CI에서 자동 검사** — 위험 패턴을 잡습니다.

```powershell
# f-string 으로 SQL을 만드는 곳이 있는지
$ grep -rn 'execute(f"' src/
$ grep -rn 'f"""SELECT\|f"SELECT\|f"INSERT\|f"UPDATE\|f"DELETE' src/
```

W26의 CI([Day 130](../05-infra-mlops/README.md) 부근)에서 이 검사를 자동화합니다.
`bandit`(파이썬 보안 린터)의 `B608: hardcoded_sql_expressions` 규칙이 같은 일을 해 줍니다.

```powershell
$ pip install bandit
$ bandit -r src/ -ll
```

4. **테스트로 고정한다** — `test_인젝션_문자열이_무력화된다` 처럼 **공격 문자열을 넣는 테스트**를 남겨 두면
   누군가 f-string으로 "고쳐도" CI가 막습니다.

> **더 근본적인 방어** — DB 사용자 권한을 최소화합니다.
> 조회 전용 서비스는 `SELECT` 권한만 가진 계정으로 붙습니다. 그러면 인젝션이 성공해도 `DROP TABLE` 은 못 합니다.
> 우리는 실습이라 `postgres`(슈퍼유저)를 쓰고 있지만, **운영에서는 절대 안 됩니다.** W22에서 다룹니다.
</details>

## 오늘의 정리

| 코드 | 하는 일 |
|---|---|
| `psycopg.connect(conninfo, row_factory=dict_row)` | 연결 (딕셔너리로 결과 받기) |
| `with conn: ... ` | **트랜잭션 경계** — 정상 종료 시 커밋, 예외 시 롤백 |
| `cur.execute(sql, (a, b))` | **파라미터 바인딩** ★ |
| `cur.fetchone()` · `fetchall()` · `rowcount` | 결과 · 영향 행 수 |
| `INSERT ... RETURNING id` | 넣고 바로 새 id 받기 |
| `create_engine(url, pool_pre_ping=True)` | SQLAlchemy 엔진 (풀 포함) |
| `pd.read_sql(text(sql), engine, params={...})` | DataFrame으로 |

| 규칙 | 이유 |
|---|---|
| **값은 무조건 `%s`, 예외 없음** | SQL 인젝션 |
| **식별자는 허용 목록으로** | `%s` 로 바인딩 불가 |
| **`%` 와일드카드는 값 쪽에** | `f"%{q}%"` |
| **접속 정보는 `.env`, 절대 커밋 금지** | 공개 저장소는 몇 분 만에 스캔됨 |
| **"읽고-계산-쓰기" 대신 한 문장으로** | 갱신 손실 ([Day 039](day-039.md)) |
| **SQL은 `queries.py` 에 모은다** | f-string이 끼어들었는지 눈으로 검사 가능 |
| **배치에는 `pool_pre_ping=True`** | 유휴 연결 끊김 방어 |

**오늘의 습관** — SQL 문자열 안에 `{` 나 `+` 가 보이면 **손을 멈추세요.**
값이라면 `%s` 로, 식별자라면 허용 목록으로. 이 반사 신경 하나가 사고의 대부분을 막습니다.
