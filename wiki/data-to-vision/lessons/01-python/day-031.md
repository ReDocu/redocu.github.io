```python
entries = load()               # ① 파일 전체를 읽어 메모리에 올림

```

기록이 10만 건이면 **1건 추가에 10만 건을 읽고 씁니다.**

| 작업 | JSON | 데이터베이스 |
|---|---|---|
| 1건 추가 | 전체 읽고 → 전체 쓰기 | `INSERT` 한 줄 |
| "홍길동의 최고 점수" | 전체를 순회하며 비교 | `WHERE name='홍길동'` |

| 동시에 두 명이 저장 | **한쪽이 사라짐** | 안전하게 처리 |
| 저장 중 프로그램 종료 | **파일이 깨짐** | 트랜잭션으로 복구 |

**"파일 저장으로 충분한가?"의 답은 데이터 양과 접근 방식이 결정합니다.**

그리고 대단원 05에서 CCTV 검출 기록을 저장할 때 이 지식을 그대로 씁니다.

## ③ 개념 설명

### 데이터 저장 방법 비교

| 방식 | 장점 | 단점 | 적합한 경우 |
|---|---|---|---|
| **변수** | 가장 빠름 | 프로그램 종료 시 사라짐 | 실행 중 임시 데이터 |
| **텍스트 파일** | 단순 | 구조가 없음 | 로그, 메모 |
| **CSV** | 엑셀로 열림 | 중첩 불가, 전부 문자열 | 표 형태 소량 데이터 |
| **JSON** | 중첩 가능, 사람이 읽음 | 부분 수정 불가, 검색 느림 | 설정값, 소량 데이터 |
| **데이터베이스** | 검색·정렬 빠름, 안전 | 학습 필요 | **여러 건을 검색·집계** |

### 데이터베이스란

**데이터를 체계적으로 저장하고 빠르게 찾을 수 있게 하는 시스템.**

```
    엑셀 시트           →      데이터베이스 테이블
┌────┬──────┬─────┐        ┌────┬──────┬─────┐
│ id │ name │score│        │ id │ name │score│  ← 열(column) / 필드
├────┼──────┼─────┤        ├────┼──────┼─────┤
│ 1  │홍길동 │15000│        │ 1  │홍길동 │15000│  ← 행(row) / 레코드
│ 2  │김철수 │23000│        │ 2  │김철수 │23000│
└────┴──────┴─────┘        └────┴──────┴─────┘
```

| 용어 | 뜻 | 파이썬 비유 |
|---|---|---|
| **데이터베이스** | 표들의 모음 | 폴더 |
| **테이블(table)** | 하나의 표 | 딕셔너리 리스트 |
| **행(row) / 레코드** | 한 건의 데이터 | 딕셔너리 하나 |
| **열(column) / 필드** | 항목 | 딕셔너리의 키 |
| **기본키(primary key)** | 각 행을 구분하는 고유값 | 딕셔너리의 키 |
| **스키마(schema)** | 표의 설계도 | 클래스 정의 |

### SQL — 데이터베이스에 말하는 언어

**SQL(Structured Query Language)** 은 데이터베이스와 대화하는 언어입니다.

```sql
-- 표 만들기
CREATE TABLE scores (id INTEGER PRIMARY KEY, name TEXT, score INTEGER);

-- 넣기
INSERT INTO scores (name, score) VALUES ('홍길동', 15000);

-- 꺼내기
SELECT * FROM scores WHERE score > 10000 ORDER BY score DESC LIMIT 10;

-- 고치기
UPDATE scores SET score = 20000 WHERE name = '홍길동';

-- 지우기
DELETE FROM scores WHERE score < 1000;
```

> **SQL은 "어떻게 찾을지"가 아니라 "무엇을 원하는지"를 씁니다.**
> 파이썬은 "리스트를 처음부터 순회하며 비교하라"고 쓰지만, SQL은 "점수 1만 이상인 것"이라고만 씁니다.
> 찾는 방법은 데이터베이스가 알아서 최적화합니다.

### 관계형 DB의 종류

| DB | 특징 | 쓰는 곳 |
|---|---|---|
| **SQLite** | 서버 불필요, 파일 하나 | 모바일 앱, 소규모, **학습** |
| MySQL / MariaDB | 무료, 널리 쓰임 | 웹 서비스 |
| PostgreSQL | 기능 풍부, 표준 준수 | 데이터 분석, 대규모 |
| Oracle / MS SQL | 상용, 대기업 | 금융, 대규모 기업 |

**SQLite를 쓰는 이유**

- **설치가 필요 없습니다.** 파이썬에 이미 들어 있습니다(`sqlite3`).
- **파일 하나**입니다. `game.db` 를 복사하면 데이터 전체가 복사됩니다.
- 서버를 켤 필요가 없습니다.
- SQL 문법은 다른 DB와 거의 같아, **여기서 배운 것이 그대로 통합니다.**

> 여러분의 휴대폰 안에도 SQLite 가 수십 개 들어 있습니다. 카카오톡 대화 기록, 브라우저 방문 기록 등.

### SQLite 자료형

SQLite 는 자료형이 5가지뿐입니다.

| 타입 | 뜻 | 파이썬 |
|---|---|---|
| `INTEGER` | 정수 | `int` |
| `REAL` | 실수 | `float` |
| `TEXT` | 문자열 | `str` |
| `BLOB` | 이진 데이터 | `bytes` |
| `NULL` | 값 없음 | `None` |

> **날짜·시간 타입이 없습니다.** `TEXT` 로 `'2026-08-07 14:30:00'` 형태로 저장하거나, `INTEGER` 로 유닉스 타임스탬프를 저장합니다.
> **불리언도 없습니다.** `INTEGER` 로 0/1 을 씁니다.

### 테이블 설계 — 무엇을 어떤 열로

**나쁜 설계**

```
scores
┌────┬──────────────────────────────────┐
│ id │ data                             │
├────┼──────────────────────────────────┤
│ 1  │ 홍길동,15000,2026-08-07,152,3분  │
└────┴──────────────────────────────────┘
```

"점수가 1만 이상인 것"을 찾으려면 문자열을 잘라야 합니다. DB의 장점이 사라집니다.

**좋은 설계**

```
scores
┌────┬────────┬───────┬───────┬─────────┬─────────────────────┐
│ id │ name   │ score │ kills │ seconds │ created_at          │
├────┼────────┼───────┼───────┼─────────┼─────────────────────┤
│ 1  │ 홍길동  │ 15000 │  152  │   180   │ 2026-08-07 14:30:00 │
└────┴────────┴───────┴───────┴─────────┴─────────────────────┘
```

**설계 원칙 네 가지**

| 원칙 | 설명 |
|---|---|
| **하나의 열에 하나의 값** | `"사과,바나나"` ❌ → 별도 테이블 |
| **검색·정렬할 것은 별도 열로** | 점수로 정렬하려면 점수 열이 필요 |
| **계산할 수 있는 것은 저장하지 않기** | 평균은 `SELECT AVG()` 로 |
| **각 행을 구분할 기본키** | `id INTEGER PRIMARY KEY` |

### 정규화 맛보기

**중복이 있는 설계**

```
scores
┌────┬────────┬──────┬───────┐
│ id │ name   │ tier │ score │
├────┼────────┼──────┼───────┤
│ 1  │ 홍길동  │ GOLD │ 15000 │
│ 2  │ 홍길동  │ GOLD │ 18000 │   ← 홍길동의 등급이 두 번 저장
│ 3  │ 홍길동  │ GOLD │ 12000 │   ← 등급이 바뀌면 3곳을 고쳐야 함
└────┴────────┴──────┴───────┘
```

**분리한 설계**

```
players                      scores
┌────┬────────┬──────┐      ┌────┬───────────┬───────┐
│ id │ name   │ tier │      │ id │ player_id │ score │
├────┼────────┼──────┤      ├────┼───────────┼───────┤
│ 1  │ 홍길동  │ GOLD │      │ 1  │     1     │ 15000 │
└────┴────────┴──────┘      │ 2  │     1     │ 18000 │
                             └────┴───────────┴───────┘
                                       ↑
                                  외래키(foreign key)
```

등급을 바꾸려면 `players` 한 행만 고치면 됩니다.

> **정규화**는 중복을 없애 일관성을 지키는 설계 기법입니다.
> 이 과정에서는 개념만 알고, 실습은 단일 테이블로 진행합니다.

### Step 1. JSON의 한계 직접 겪기

`json_limit.py`

```python
"""JSON 저장의 한계를 직접 확인합니다."""

import json
import random
import time
from pathlib import Path

RANKING_FILE = Path("ranking_test.json")


def load():
    if not RANKING_FILE.exists():
        return []
    return json.loads(RANKING_FILE.read_text(encoding="utf-8"))


def save(entries):
    RANKING_FILE.write_text(
        json.dumps(entries, ensure_ascii=False),
        encoding="utf-8",
    )


def add_score(name, score):
    """기록 하나를 추가합니다 — 전체를 읽고 전체를 씁니다."""
    entries = load()                   # ① 전체 읽기
    entries.append({"name": name, "score": score})
    entries.sort(key=lambda e: e["score"], reverse=True)   # ② 전체 정렬
    save(entries)                      # ③ 전체 쓰기


def find_by_name(name):
    """이름으로 검색 — 전체를 순회합니다."""
    return [e for e in load() if e["name"] == name]


def get_top(n=10):
    """상위 n개 — 이미 정렬돼 있지만 전체를 읽어야 합니다."""
    return load()[:n]


# ══════════ 실험 ══════════
NAMES = ["홍길동", "김철수", "이영희", "박민수", "최지우"]

print("=" * 60)
print("        JSON 저장 성능 실험")
print("=" * 60)

for target in (100, 1000, 5000):
    # 초기화
    if RANKING_FILE.exists():
        RANKING_FILE.unlink()
    save([])

    # 기록 추가 시간 측정
    start = time.time()
    for i in range(target):
        add_score(random.choice(NAMES), random.randint(1000, 99999))
    add_time = time.time() - start

    # 검색 시간 측정
    start = time.time()
    for _ in range(100):
        find_by_name("홍길동")
    search_time = time.time() - start

    file_size = RANKING_FILE.stat().st_size / 1024

    print(f"\n[기록 {target:,}건]")
    print(f"  추가 소요:        {add_time:>7.2f}초  ({add_time / target * 1000:.2f}ms/건)")
    print(f"  검색 100회:       {search_time:>7.3f}초")
    print(f"  파일 크기:        {file_size:>7.1f} KB")
    print(f"  1건 추가 시 처리:  약 {target:,}건 읽고 {target:,}건 쓰기")

print("\n" + "=" * 60)
print("결론: 기록이 늘수록 1건 추가 비용이 비례해 증가합니다.")
print("      데이터베이스는 1건 추가에 1건만 처리합니다.")
print("=" * 60)

RANKING_FILE.unlink()
```

**실행 결과 (환경에 따라 다름)**

```

============================================================

  1건 추가 시 처리:  약 100건 읽고 100건 쓰기
```

> 데이터베이스는 같은 작업을 **선형 시간**에 처리합니다. 다음 주에 직접 비교해 봅니다.

### Step 2. JSON의 또 다른 한계 — 동시 접근과 중단

`json_danger.py`

```python
"""JSON 저장의 위험 상황을 재현합니다."""

import json
from pathlib import Path

TEST_FILE = Path("danger_test.json")


def demo_partial_write():
    """저장 중 프로그램이 종료되면 파일이 깨집니다."""
    print("\n[① 저장 중 중단]")

    data = [{"name": f"player{i}", "score": i * 100} for i in range(100)]
    text = json.dumps(data, ensure_ascii=False, indent=2)

    # 파일의 절반만 쓰고 중단된 상황을 흉내
    TEST_FILE.write_text(text[:len(text) // 2], encoding="utf-8")

    print(f"  파일 크기: {TEST_FILE.stat().st_size} 바이트 (원래의 절반)")

    try:
        json.loads(TEST_FILE.read_text(encoding="utf-8"))
        print("  읽기 성공")
    except json.JSONDecodeError as e:
        print(f"  ✗ 읽기 실패: {e}")
        print("  → 데이터 100건이 전부 사라졌습니다!")


def demo_lost_update():
    """두 곳에서 동시에 수정하면 한쪽이 사라집니다."""
    print("\n[② 동시 수정]")

    TEST_FILE.write_text(json.dumps([{"name": "기존", "score": 100}]),
                         encoding="utf-8")

    # 프로그램 A 가 읽음
    data_a = json.loads(TEST_FILE.read_text(encoding="utf-8"))
    print(f"  A가 읽음: {len(data_a)}건")

    # 프로그램 B 도 읽음 (거의 동시에)
    data_b = json.loads(TEST_FILE.read_text(encoding="utf-8"))
    print(f"  B가 읽음: {len(data_b)}건")

    # A 가 추가하고 저장
    data_a.append({"name": "A의 기록", "score": 500})
    TEST_FILE.write_text(json.dumps(data_a, ensure_ascii=False), encoding="utf-8")
    print(f"  A가 저장: {len(data_a)}건")

    # B 도 추가하고 저장 — A 의 기록을 모른 채 덮어씀!
    data_b.append({"name": "B의 기록", "score": 700})
    TEST_FILE.write_text(json.dumps(data_b, ensure_ascii=False), encoding="utf-8")
    print(f"  B가 저장: {len(data_b)}건")

    final = json.loads(TEST_FILE.read_text(encoding="utf-8"))
    names = [e["name"] for e in final]
    print(f"\n  최종 결과: {names}")
    print(f"  ✗ 'A의 기록' 이 사라졌습니다! (Lost Update)")


def demo_no_partial_query():
    """일부만 조회할 수 없습니다."""
    print("\n[③ 부분 조회 불가]")

    data = [{"name": f"player{i}", "score": i * 100} for i in range(10000)]
    TEST_FILE.write_text(json.dumps(data), encoding="utf-8")

    size = TEST_FILE.stat().st_size / 1024
    print(f"  파일 크기: {size:.1f} KB (1만 건)")

    # 상위 3개만 필요한데...
    loaded = json.loads(TEST_FILE.read_text(encoding="utf-8"))
    top3 = sorted(loaded, key=lambda e: e["score"], reverse=True)[:3]

    print(f"  필요한 것: 상위 3건")
    print(f"  실제 읽은 것: {len(loaded):,}건 ({size:.1f} KB 전부)")
    print(f"  ✗ 3건을 위해 1만 건을 메모리에 올렸습니다.")
    print(f"\n  SQL 이라면: SELECT * FROM scores ORDER BY score DESC LIMIT 3")


print("=" * 60)
print("        JSON 저장의 위험 상황")
print("=" * 60)

demo_partial_write()
demo_lost_update()
demo_no_partial_query()

print("\n" + "=" * 60)
print("데이터베이스는 이 세 문제를 모두 해결합니다:")
```

### Step 3. 게임 DB 설계서 작성 (오늘의 종합 예제)

내일부터 만들 데이터베이스를 **먼저 설계**합니다.

`db_design.md`

```markdown
# 슈팅게임 데이터베이스 설계서

## 1. 저장할 데이터

| 무엇을 | 왜 | 조회 방식 |
|---|---|---|
| 게임 기록 | 랭킹 표시 | 점수 순 상위 10건 |
| 플레이어별 통계 | 개인 기록 확인 | 이름으로 검색 |
| 게임 설정 | 다음 실행 시 복원 | 키로 조회 |

## 2. 테이블 설계

### 2.1 scores — 게임 기록

| 열 이름 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 고유 번호 |
| player_name | TEXT | NOT NULL | 플레이어 이름 |
| score | INTEGER | NOT NULL DEFAULT 0 | 최종 점수 |
| kills | INTEGER | NOT NULL DEFAULT 0 | 처치 수 |
| max_combo | INTEGER | NOT NULL DEFAULT 0 | 최고 콤보 |
| shots | INTEGER | NOT NULL DEFAULT 0 | 발사 수 |
| hits | INTEGER | NOT NULL DEFAULT 0 | 명중 수 |
| play_seconds | INTEGER | NOT NULL DEFAULT 0 | 플레이 시간(초) |
| stage | INTEGER | NOT NULL DEFAULT 1 | 도달 스테이지 |
| created_at | TEXT | NOT NULL | 기록 시각 |

**설계 근거**
- `id` 를 AUTOINCREMENT 로 두어 각 기록을 구분합니다.
- **명중률은 저장하지 않습니다.** `hits / shots` 로 계산할 수 있습니다.
  (계산할 수 있는 것은 저장하지 않는다 — 일관성 유지)
- `created_at` 은 SQLite 에 날짜 타입이 없으므로 TEXT 로 `'YYYY-MM-DD HH:MM:SS'` 형식.
- `play_seconds` 를 INTEGER 로 저장해 정렬·집계가 가능하게 합니다.

### 2.2 settings — 게임 설정

| 열 이름 | 타입 | 제약 | 설명 |
|---|---|---|---|
| key | TEXT | PRIMARY KEY | 설정 이름 |
| value | TEXT | NOT NULL | 설정 값 |

**설계 근거**
- 설정 항목이 늘어도 **표 구조를 바꿀 필요가 없습니다.**
- 모든 값을 TEXT 로 저장하고, 읽을 때 파이썬에서 변환합니다.

## 3. 자주 쓸 질의

| 목적 | SQL |
|---|---|
| TOP 10 랭킹 | `SELECT * FROM scores ORDER BY score DESC LIMIT 10` |
| 특정 플레이어 최고 기록 | `SELECT MAX(score) FROM scores WHERE player_name = ?` |
| 플레이어별 평균 | `SELECT player_name, AVG(score) FROM scores GROUP BY player_name` |
| 오늘의 기록 | `SELECT * FROM scores WHERE created_at LIKE '2026-08-07%'` |
| 전체 통계 | `SELECT COUNT(*), SUM(kills), MAX(score) FROM scores` |
| 명중률 상위 | `SELECT player_name, hits*100.0/shots AS acc FROM scores WHERE shots>0 ORDER BY acc DESC` |

## 4. 확장 계획 (이번 과정 범위 밖)

기록이 많아지면 정규화를 검토합니다.

players (id, name, tier, created_at)
   ↓ 1:N
scores (id, player_id, score, ...)

- 지금은 `player_name` 을 직접 저장 (단순함 우선)
- 플레이어별 정보(등급·아바타)가 생기면 분리
```

> **설계서를 먼저 쓰는 이유** — 테이블을 만들고 데이터를 넣은 뒤에 구조를 바꾸려면
> 기존 데이터를 옮기는 작업(마이그레이션)이 필요합니다. **처음에 잘 설계하는 것이 훨씬 쌉니다.**

### "파일 저장이면 충분한데 왜 DB를 쓰나" 라고 생각

**언제 파일로 충분한가**

| 상황 | 파일 | DB |
|---|---|---|
| 설정값 20개 | ✅ JSON | 과함 |
| 게임 세이브 1개 | ✅ JSON | 과함 |
| 랭킹 10건 | ✅ JSON | 과함 |
| 랭킹 1만 건 | ❌ | ✅ |
| 여러 조건으로 검색 | ❌ | ✅ |
| 여러 프로그램이 동시 접근 | ❌ | ✅ |
| 통계·집계가 필요 | ❌ | ✅ |

> **도구는 문제에 맞춰 고릅니다.** DB가 항상 정답은 아닙니다.

### 한 열에 여러 값을 넣음

```
tags 열:  "액션,슈팅,아케이드"
```

**문제** — "액션 태그가 있는 게임 찾기"를 하려면 문자열을 잘라야 합니다.
**해결** — 별도 테이블로 분리하거나, 최소한 검색이 필요 없는 경우에만 씁니다.

### 계산할 수 있는 값을 저장

```
scores 테이블에 accuracy 열 추가 (hits/shots)
```

**문제** — `hits` 를 수정했는데 `accuracy` 를 안 고치면 **데이터가 어긋납니다.**
**해결** — 조회할 때 계산합니다. `SELECT hits*100.0/shots FROM scores`

> [Day 021](day-021.md)의 "같은 정보를 두 곳에 저장하면 어긋난다" 와 같은 원리입니다.

### 기본키를 안 만듦

```sql
CREATE TABLE scores (name TEXT, score INTEGER);
```

**문제** — 같은 이름·같은 점수가 두 건이면 하나만 지울 방법이 없습니다.
**해결** — 항상 `id INTEGER PRIMARY KEY AUTOINCREMENT` 를 둡니다.

### 이름을 기본키로 사용

```sql
CREATE TABLE players (name TEXT PRIMARY KEY, ...);
```

**문제** — 이름은 바뀔 수 있고, 동명이인이 있을 수 있습니다.
**해결** — 의미 없는 숫자 `id` 를 기본키로 쓰고, 이름은 일반 열로 둡니다.

### 날짜를 제각각 형식으로 저장

```
"2026-08-07"
"2026/8/7"
"08-07-2026"
```

**문제** — 정렬과 범위 검색이 안 됩니다.
**해결** — **`YYYY-MM-DD HH:MM:SS` 형식으로 통일**합니다. 이 형식은 문자열 정렬 = 시간 순 정렬입니다.

**핵심 설계 판단 4가지**

**① `books` 에 `is_borrowed` 열을 두지 않았습니다.**
대출 여부는 `loans` 에서 계산할 수 있습니다. 저장하면 어긋날 위험이 있습니다.

```sql
-- 현재 대출 중인 책
SELECT b.* FROM books b
JOIN loans l ON b.id = l.book_id
WHERE l.returned_at IS NULL;
```

**② `returned_at` 이 NULL 이면 "아직 반납 안 함"** 입니다.
별도의 `is_returned` 열을 두는 것보다 정보가 하나 더 많습니다(언제 반납했는지).

**③ 대출 기록을 별도 테이블로 분리했습니다.**
`books` 에 `borrower` 열을 두면 **과거 이력이 사라집니다.** 누가 언제 빌렸는지 알 수 없습니다.

**④ `isbn` 에 UNIQUE 제약을 걸었습니다.**
같은 책을 두 번 등록하는 실수를 DB가 막아 줍니다.

**주요 질의**

```sql
-- 현재 대출 중인 책 목록
SELECT b.title, m.name, l.due_at
FROM loans l
JOIN books b ON l.book_id = b.id
JOIN members m ON l.member_id = m.id
WHERE l.returned_at IS NULL
ORDER BY l.due_at;

-- 특정 회원의 대출 이력
SELECT b.title, l.loaned_at, l.returned_at
FROM loans l
JOIN books b ON l.book_id = b.id
WHERE l.member_id = ?
ORDER BY l.loaned_at DESC;

-- 연체 목록 (오늘 기준)
SELECT b.title, m.name, l.due_at
FROM loans l
JOIN books b ON l.book_id = b.id
JOIN members m ON l.member_id = m.id
WHERE l.returned_at IS NULL AND l.due_at < DATE('now');

-- 인기 도서 TOP 5
SELECT b.title, COUNT(*) AS loan_count
FROM loans l JOIN books b ON l.book_id = b.id
GROUP BY b.id ORDER BY loan_count DESC LIMIT 5;
```

**3.** 아래 테이블 설계의 문제점 3가지를 지적하고 개선하세요.

```
game_records
┌────────┬───────┬─────────────────┬──────────┬──────────┐
│ name   │ score │ items           │ accuracy │ date     │
├────────┼───────┼─────────────────┼──────────┼──────────┤
│ 홍길동  │ 15000 │ 검,방패,회복약   │ 78.5     │ 8/7/2026 │
│ 홍길동  │ 18000 │ 검,활           │ 82.1     │ 8/7/2026 │
└────────┴───────┴─────────────────┴──────────┴──────────┘
```

<details>
<summary>답 보기</summary>

**문제 ① 기본키가 없습니다.**

같은 이름·같은 점수의 기록이 두 건이면 하나만 지울 방법이 없습니다.
`DELETE FROM game_records WHERE name='홍길동' AND score=15000` 은 둘 다 지울 수 있습니다.

**개선** — `id INTEGER PRIMARY KEY AUTOINCREMENT` 추가.

**문제 ② `items` 한 열에 여러 값이 들어 있습니다.**

```sql
-- "검을 가진 기록 찾기" — 문자열 검색에 의존
SELECT * FROM game_records WHERE items LIKE '%검%';
```

이 질의는 `"목검"`, `"검은날개"` 도 걸립니다. 정확하지 않습니다.
아이템 개수를 세거나, 아이템별 통계를 내는 것도 불가능합니다.

**개선** — 별도 테이블로 분리합니다.

```
record_items
┌────┬───────────┬───────────┐
│ id │ record_id │ item_name │
├────┼───────────┼───────────┤
│ 1  │     1     │ 검        │
│ 2  │     1     │ 방패      │
│ 3  │     1     │ 회복약    │
└────┴───────────┴───────────┘
```

```sql
-- 정확한 검색
SELECT r.* FROM game_records r
JOIN record_items i ON r.id = i.record_id
WHERE i.item_name = '검';

-- 아이템별 인기도
SELECT item_name, COUNT(*) FROM record_items GROUP BY item_name;
```

**문제 ③ `accuracy` 는 계산할 수 있는 값입니다.**

명중률은 `hits / shots × 100` 입니다. 저장하면 **원본과 어긋날 위험**이 있습니다.
`hits` 를 수정했는데 `accuracy` 를 안 고치면 데이터가 거짓말을 합니다.

**개선** — `shots`, `hits` 를 저장하고 조회 시 계산합니다.

```sql
SELECT name, score,
       CASE WHEN shots > 0 THEN hits * 100.0 / shots ELSE 0 END AS accuracy
FROM game_records;
```

**문제 ④ (추가) 날짜 형식이 잘못되었습니다.**

`8/7/2026` 은 **정렬이 안 됩니다.** 문자열로 정렬하면 `10/1/2026` 이 `8/7/2026` 보다 앞에 옵니다.
그리고 8월 7일인지 7월 8일인지 모호합니다.

**개선** — `2026-08-07 14:30:00` 형식(ISO 8601)으로 통일합니다.
이 형식은 **문자열 정렬 = 시간 순 정렬**이라 매우 편리합니다.

**개선된 최종 설계**

```sql
CREATE TABLE game_records (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    player_name TEXT    NOT NULL,
    score       INTEGER NOT NULL DEFAULT 0,
    shots       INTEGER NOT NULL DEFAULT 0,
    hits        INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT    NOT NULL          -- 'YYYY-MM-DD HH:MM:SS'
);

CREATE TABLE record_items (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    record_id INTEGER NOT NULL,
    item_name TEXT    NOT NULL,
    FOREIGN KEY (record_id) REFERENCES game_records(id)
);
```

> **정리하면 설계 원칙 네 가지입니다.**
> ① 기본키를 반드시 둔다
> ② 한 열에 하나의 값
> ③ 계산할 수 있는 값은 저장하지 않는다
> ④ 날짜는 `YYYY-MM-DD HH:MM:SS` 로 통일
</details>

| DB 구조 | 테이블(표) · 행(레코드) · 열(필드) · 기본키 |
| SQL | "무엇을 원하는지" 를 쓰는 언어 |
| SQLite | 서버 불필요 · 파일 하나 · 파이썬 내장 |
| 자료형 | `INTEGER` `REAL` `TEXT` `BLOB` `NULL` (날짜·불리언 없음) |
| 설계 원칙 | 한 열에 한 값 · 계산 값은 저장 ❌ · 기본키 필수 |
| 날짜 형식 | **`YYYY-MM-DD HH:MM:SS`** (문자열 정렬 = 시간순) |
| DB 선택 기준 | 1000건 초과 / 조건 검색 / 동시 접근 |

**오늘 반드시 기억할 세 가지**
> ① **계산할 수 있는 값은 저장하지 마세요.** 원본과 어긋납니다.
> ② 기본키 `id INTEGER PRIMARY KEY AUTOINCREMENT` 를 항상 두세요.
> ③ 날짜는 `YYYY-MM-DD HH:MM:SS` 로 통일하세요.
