## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **서비스 지표**(지연·에러율)와 **모델 지표**(입력 분포·확신도)가 왜 별개의 층인지 설명할 수 있다.
- **라벨 지연** 문제를 이해하고, 정확도를 기다리는 대신 볼 **대리 신호**를 고를 수 있다.
- 예측 로그로 **입력 분포 대시보드**를 만들고, **PSI**로 드리프트를 수치화할 수 있다.
- 드리프트를 일부러 주입해 감지 장치가 울리는 것을 실험으로 확인하고, **행동 가능한 알림**을 설계할 수 있다.

## ② 왜 필요한가

이번 주 체크포인트가 곧 오늘의 문제입니다 — **"모델 성능이 언제 나빠졌는지 어떻게 아는가."**

직관적 답은 "정확도를 지켜본다"인데, 운영에서 이 답은 반쯤 불가능합니다. 정확도를 계산하려면
**정답(라벨)** 이 필요한데:

| 서비스 | 정답이 오는 시점 |
|---|---|
| pm25 내일 예보 | **다음 날** 실측이 도착 — 운 좋은 케이스 (하루 지연) |
| antbee 분류 | 사용자는 정답을 알려 주지 않음 — **영원히 안 옴** |
| 대출 부도 예측 (실무 예) | 수개월 뒤 |

그리고 더 고약한 사실 — **서비스 지표는 모델 부패를 전혀 감지하지 못합니다.** 200 OK,
p95 6ms, 에러율 0% — 완벽한 계기판 뒤에서 모델은 낡은 세계관으로 헛소리를 하고 있을 수
있습니다. 배포 순간부터 세상은 변하는데(계절·센서·이용자) 모델은 학습 시점에 얼어 있으니까요
(README FAQ의 "모델은 배포 순간부터 낡기 시작합니다"가 이것).

해법의 열쇠는 이미 우리 손에 있습니다 — [Day 121](day-121.md)부터 쌓여 온 **예측 로그**.
정답 없이도 볼 수 있는 것들 — 모델에게 **무엇이 들어오고**(입력 분포) 모델이 **무엇을
내보내는가**(예측·확신도 분포) — 의 변화가 성능 악화의 조기 경보입니다. 들어오는 것이 학습
때와 달라졌다면, 성능은 물어볼 것도 없이 의심 대상입니다.

## ③ 개념 설명

### 두 층의 건강 — 계기판이 다르다

| | 서비스 건강 (시스템) | **모델 건강 (ML 고유)** |
|---|---|---|
| 질문 | 살아 있고 빠른가 | **여전히 맞는 말을 하는가** |
| 지표 | p50/p95 지연 · 에러율 · 처리량 | 입력 분포 · 예측/확신도 분포 · (지연 도착) 실성능 |
| 도구 | 로그·헬스체크 (098·123) | **예측 로그 + 오늘의 분석** |
| 고장 모드 | 500, 타임아웃 — **시끄러움** | 정상 응답 속의 오답 — **조용함** |

시끄러운 고장은 이미 잡을 수 있습니다(W25까지의 체계). 오늘은 조용한 고장의 감지입니다.

### 드리프트 — 두 종류의 세상 변화

| 종류 | 정의 | 우리 예 |
|---|---|---|
| **데이터 드리프트** | 입력의 분포가 변함 P(X)↗ | 가을 진입 — 습도·풍속 분포 이동 · 센서 교체 |
| 컨셉 드리프트 | 입력→정답의 **관계**가 변함 P(y\|X)↗ | 새 배출 규제로 같은 기상에도 농도 패턴이 바뀜 |

데이터 드리프트는 **정답 없이 감지 가능**합니다(입력만 보면 되니까) — 오늘의 주 대상.
컨셉 드리프트는 정답이 와야 확정되므로, pm25처럼 라벨이 (하루 늦게라도) 오는 서비스에서는
"어제 예측 vs 오늘 실측"의 지연 성능 추적으로 잡습니다.

### PSI — 분포 변화의 온도계

PSI(Population Stability Index): 기준 분포(학습 데이터)와 최근 분포(운영 입력)를 같은 구간
으로 나눠 비율 차이를 합산한 값입니다:

```
PSI = Σ (최근비율ᵢ − 기준비율ᵢ) × ln(최근비율ᵢ / 기준비율ᵢ)      (구간 i마다)
```

| PSI | 관례적 해석 |
|---|---|
| < 0.10 | 안정 |
| 0.10 ~ 0.25 | 주의 — 관찰 강화 |
| **> 0.25** | **경보 — 조사 (재학습 후보)** |

피처마다 하나씩 계산해 "무엇이 얼마나 변했나"의 표를 만듭니다 — 온도계이지 진단서가 아니라는
것(⑤의 마지막 실수)만 기억하면 강력한 도구입니다.

### 알림 — 행동 가능한 것만 울린다

대시보드는 **보러 가는** 것이라 안 보게 되고, 알림은 **찾아오는** 것이라 설계를 잘못하면
소음이 됩니다. 규칙 세 개: ① 알림에는 **받은 사람이 할 행동**이 정의되어 있을 것 ("PSI 0.31 —
조사 절차 X를 시작하라"), ② 임계치는 실측 분포로 정할 것 (감으로 정한 임계치 = 소음 발생기),
③ 울리면 반드시 반응할 것 — 무시가 허용되는 알림은 알림 전체를 죽입니다 ([Day 130](day-130.md)
깨진 창문의 알림판).

### Step 3. PSI — 드리프트의 수치화 (4~5교시)

`monitoring/check_drift.py` 의 핵심:

```python
# check_drift.py — 기준(학습 데이터) vs 최근 7일 입력의 PSI (Day 134)
import numpy as np


def psi(expected: np.ndarray, actual: np.ndarray, bins: int = 10) -> float:
    """기준 분포의 십분위로 구간을 고정하고, 두 분포의 구간 비율 차이를 합산."""
    edges = np.percentile(expected, np.linspace(0, 100, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.clip(np.histogram(expected, edges)[0] / len(expected), 1e-4, None)
    a = np.clip(np.histogram(actual, edges)[0] / len(actual), 1e-4, None)
    return float(np.sum((a - e) * np.log(a / e)))
```

기준은 **학습 데이터**(air_daily.csv — DVC 지문 21adc01f의 그것), 최근은 로그의 마지막 7일:

```bash
python monitoring/check_drift.py --recent-days 7
```

```

pm25            0.08    안정

```

주입한 바로 그 피처들(pm25_lag1·humidity)이 경보에 걸렸습니다 — 감지 장치가 **울려야 할 때
운다**는 검증입니다. 반대 검증도 하세요: `--recent-days 14 --until day7` (평시 구간만)로
돌리면 전 피처 안정 — **안 울려야 할 때 안 우는지**까지가 알림 장치의 자격입니다.

## ⑤ 자주 하는 실수

### 서비스 계기판만 보고 "이상 없음" 보고

**증상** — 200 OK·p95 정상만 확인하고 모델 방치 — 석 달 뒤 "예보가 요즘 왜 이래요" 민원으로
발각.
**원인** — 두 층의 구분 부재 — 시스템 건강을 모델 건강으로 오독.
**해결** — Step 2와 3의 대비를 기억하세요: 같은 2주가 서비스 층에선 평화, 모델 층에선 경보
였습니다. 점검 루틴에 두 층을 명시적으로 분리해 두는 것이 시작입니다.

### 정확도가 올 때까지 기다림

**증상** — "라벨이 없어서 모니터링을 못 해요" — 대리 신호를 안 보고 유일 지표(정확도)만 기다림.
**원인** — 학습 때의 지표 습관(정답 있는 세계)을 운영(정답 지연·부재)에 그대로 이식.
**해결** — 순서를 바꾸세요: 입력 분포·예측 분포·확신도는 **오늘부터** 볼 수 있고, 대부분의
성능 악화는 입력 변화가 선행합니다. 라벨이 늦게라도 오는 서비스(pm25)는 지연 성능 추적을
**추가로** — 대리 신호의 알람을 라벨로 사후 검증하는 이중 구조가 정석입니다.

### 대시보드만 만들고 알림이 없음

**증상** — 훌륭한 대시보드 — 아무도 안 봄. 사고 후 회고: "대시보드엔 3주 전부터 나와 있었네요".
**원인** — 감시를 "보러 가는 것"으로 설계 — 사람의 주의력은 감시 장치가 아닙니다.
**해결** — 지표마다 임계치와 알림(찾아오는 신호)을 붙이고, 대시보드는 **알림을 받은 뒤의 조사
도구**로 자리매김합니다. "임계치 없는 지표는 장식"을 설계서(과제)의 기준으로.

### 알림 남발 — 그리고 전체 무시

**증상** — PSI 0.11에도, 요청 0건인 새벽에도 알림 — 2주 뒤 채널 음소거, 진짜 경보도 함께 매장.
**원인** — "많이 알리면 안전"의 착각 — 알림의 자원은 채널이 아니라 **받는 사람의 신뢰**입니다.
**해결** — ③의 세 규칙(행동 정의·실측 기반 임계치·무시 불허)으로 목록을 다이어트하세요.
좋은 점검 질문: "이 알림을 받고 내가 늘 하는 행동이 '닫기'라면, 그 알림은 삭제 대상이다."

### 드리프트 경보 = 자동 재학습이라는 반사

**증상** — PSI 경보에 자동 재학습을 물려 둠 — 센서 고장으로 쓰레기 입력이 들어온 날, 시스템이
**쓰레기로 성실하게 재학습**해 모델을 망침.
**원인** — 온도계(PSI)를 진단서로 오용 — 분포 변화의 **원인**은 여럿입니다 (세상의 진짜 변화 /
데이터 결함 / 시뮬레이터·클라이언트 버그).
**해결** — 경보 → **조사**(원인 분류) → 처방(재학습 / 데이터 수리 / 롤백)의 사람 관문을
남기세요. 자동화하더라도 재학습 후 게이트([Day 132](day-132.md) promote)가 최후 방어선이
되도록 — 내일 종합 설계에서 이 "어디까지 자동인가" 선긋기를 정면으로 다룹니다.

**Q1.** "서비스 지표가 완벽해도 모델은 실패 중일 수 있다"를 오늘 실습의 구체적 수치(Step 2와
Step 3의 대비)로 증명하고, 이 고장이 "조용한" 이유를 시스템 관점에서 설명하세요.

<details>
<summary>답 보기</summary>

같은 2주에 대해 p95는 6.1~6.3ms·에러율 0%로 평탄(Step 2)했지만, PSI는 pm25_lag1 0.31·humidity
0.27로 경보(Step 3)였습니다. 조용한 이유: 드리프트된 입력도 스키마상 **유효한 요청**이라 검증

시스템의 모든 계기판은 "요청이 정상 처리됨"만 봅니다. 오답은 예외를 던지지 않는다 — 그래서
모델 건강은 별도의 계기판(입력·출력 분포)이 필요합니다.

**Q2.** PSI 계산에서 구간(edges)을 **기준 분포의 십분위로 고정**하는 이유를, 최근 분포 기준으로
구간을 잡았을 때 생기는 문제와 대비해 설명하세요.

<details>
<summary>답 보기</summary>

비교의 자는 고정되어야 변화를 잴 수 있습니다. 기준 분포의 십분위로 구간을 고정하면 "학습 때
10%씩 담기던 칸에 지금은 몇 %가 담기는가"라는 일관된 질문이 되고, 시점 간 PSI 추이(Step 4의
패널)도 같은 자로 잰 값이라 비교 가능합니다. 최근 분포로 구간을 잡으면 자가 매번 달라져 —
극단적으로는 어떤 분포든 최근 기준 십분위로는 균등(10%씩)하게 담겨 변화가 은폐되고, 추이
비교도 무의미해집니다. "기준선은 고정, 관측만 갱신" — 모니터링 설계의 일반 원칙입니다.

</details>
