## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 팀 발표(시연 10분 + 아키텍처 10분)를 **전원 발화**로 구성할 수 있다.
- 리허설을 **실측 도구**로 사용해 구성을 다듬을 수 있다 (감상평이 아니라 스톱워치로).
- 시연의 백업 3층과 **시연 전 점검 절차**를 준비할 수 있다.
- 검증을 통과한 상태에 **v1.0.0**을 선언하고 발표 환경을 동결할 수 있다.

## ② 왜 필요한가

내일의 형식을 다시 읽어 봅시다 — 팀당 **시연 10분 + 아키텍처 설명 10분 + 질의응답**,
그리고 "전원이 시연 질의응답에 응답합니다"라는 조건. 이 형식은 개인 발표(MP3·MP4)의
확장판이 아니라 다른 종목입니다. 개인 발표의 리스크가 시연 실패 하나였다면, 팀 발표에는
세 개가 더 붙습니다: **전환의 마찰**(발표자 교대마다 흐름이 끊길 위험), **역할의 불균형**
(한 명이 다 말하면 개인 기여도 평가에서 침묵한 사람이 다침), **질문의 무작위성**(질문은
담당을 가리지 않고 날아옴).

세 리스크의 공통 해법이 오늘의 리허설입니다 — 단, 리허설을 "한번 돌려 보기"가 아니라
**실측**으로 씁니다. 시간을 재고, 전환 지점을 세고, 모의 질문에 누가 몇 번 답했는지
기록합니다. [Day 105](../04-deep-learning-serving/day-105.md)와 [Day 140](../05-infra-mlops/day-140.md)
에서 두 번 연습한 개인 발표의 근육 위에, 오늘은 팀의 합을 얹는 날입니다.

그리고 오늘 v1.0.0을 답니다 — 155에서 약속한 그 조건("검증을 통과한 것")이 어제로
충족됐기 때문입니다: 빈 서버 리허설 2m18s, 절차서 교차 수행, 문서 ✅. 내일 발표에서
시연되는 것은 이 태그입니다 — 오늘 밤의 "마지막 수정" 유혹이 그래서 금지됩니다.

## ③ 개념 설명

### 20분의 구조 — 배점을 따라 배분한다

| 구간 | 시간 | 내용 | 담당 (한산) |
|---|---|---|---|
| 문제와 범위 | 3분 | 시나리오 한 문장 · 자른 것과 이유 (3축 표) | 서연 |
| 아키텍처 | 5분 | 현실의 사진 1장 + 기술 선택 근거 2건 (A/B·게이트) | 하람 |
| **라이브 시연** | 8분 | 수집 로그 → 예측 → **커밋→배포 2m40s** (대기 중 해설) → 대시보드 | 지우 (해설 민준) |
| 배운 것 | 3분 | **사고와 수리 1장** · 한계와 다음 단계 | 민준 |
| 여유 | 1분 | 전환 4회 × 15초 | — |

전환마다 15초를 **예산으로 배정**한 것에 주목 — 계획에 없는 전환 시간은 반드시 시연
시간에서 빠져나갑니다.

### 전원 발화 · 전원 응답

발화 분담은 위 표로 끝나지 않습니다 — 질의응답이 남습니다. 규칙: 질문의 1차 응답은
해당 영역 담당, 그러나 **모든 예상 질문에 전원이 2문장 요약본**을 갖습니다 (교차 리뷰
덕에 가능한 일입니다 — 4주간 서로의 영역을 읽어 왔으니까요). "그건 제 담당이 아니라서요"
는 내일 금지어입니다 — "상세는 서연이 답하겠지만, 요지는 ~입니다"가 대체 문장입니다.

### 백업 3층 + 시연 전 점검

[Day 105](../04-deep-learning-serving/day-105.md)의 3층(라이브 → 기록 → 영상)에
[Day 138](../05-infra-mlops/day-138.md)의 시연 전 점검을 더합니다 — 한산 팀의 점검
목록: 러너 Idle · 컨테이너 healthy 5/5 · GHCR 정상 · 캐시 웜(빌드 58s 상태) · 데모
페이지 응답 · **발표 직전 30초 재점검**. 오늘 리허설 2회가 백업 2층(기록)을 최신으로
만들어 줍니다.

## ④ 단계별 실습

### Step 1. 자료 확정 (1~2교시)

슬라이드는 **10장 이내** — 구성표의 구간당 1~2장. 시연 구간은 슬라이드가 아니라 실제
화면이므로 "시연 순서 카드"(발표자용 컨닝 페이퍼)를 따로 만듭니다. 사고와 수리 1장은
156 보고서의 그 절을 그림 하나(타임라인: 발견→진단→수리→방지)로 압축합니다.

### Step 2. 리허설 1회차 — 실측 (3~4교시)

```
[리허설 1회차 실측]
합계 24m 40s (목표 20m 초과 ⚠)
  문제와 범위 3m 10s ✓ · 아키텍처 8m 05s ⚠ (+3m) · 시연 9m 20s ⚠ · 배운 것 2m 55s ✓
  전환 4회 = 1m 10s ⚠ (화면 케이블 교체 2회 발생)
조치: 아키텍처에서 ERD 상세 설명 삭제 (질문 오면 답하기로) · 시연 중 해설과 조작 분리
      (지우 조작 + 민준 해설 병행) · 노트북 1대로 통일해 전환 마찰 제거
```

초과분을 "빨리 말하기"로 해결하지 않는 것 — **내용을 빼는 것**이 유일한 해법입니다.
발표에서 뺀 것은 사라지는 게 아니라 질의응답의 답으로 이동합니다.

### Step 3. 팀 간 모의 질의 (5~6교시)

두 팀이 서로의 리허설을 보고 질문 공세를 합니다 — 145 상호 리뷰의 마지막 재연입니다.
규칙: 질문 10개 이상, **담당 아닌 사람 지목 3회 이상** ("이 질문, 민준 님 말고 지우 님이
답해 주세요"). 전원 2문장 요약본의 실전 시험입니다. 막힌 질문은 오늘 저녁 답의 뼈대에
추가됩니다.

### Step 4. v1.0.0과 환경 동결 (7~8교시)

```
$ git tag -a v1.0.0 -m "release: 검증 통과 (빈 서버 2m18s · 절차서 교차 수행 · 문서 완결)"
$ git push --tags
```

리허설 2회차(수정 반영, 19m 30s 확인) 후 — 시연 환경 점검 절차를 실행하고 **동결**합니다:
서버·저장소·노트북 화면 배치까지. 백업 영상(오늘 2회차 시연 녹화)을 3층에 배치. 오늘
밤의 코드 변경은 어떤 이유로도 없습니다 — 내일 시연되는 것은 v1.0.0이라는 **검증된
과거**이지, 오늘 밤의 희망이 아닙니다.

**오늘 퇴근 체크** — □ 슬라이드 ≤10장 + 시연 카드 □ 리허설 2회(실측→수정→재확인)
□ 모의 질의(전원 응답 시험) □ v1.0.0 태그 □ 점검 절차 + 백업 3층 □ 환경 동결 선언

## ⑤ 자주 하는 실수

### 슬라이드가 보고서의 복제

**증상** — 38장 슬라이드에 표와 문단이 빼곡 — 청중은 읽느라 안 듣고, 20분에 21장에서
끊김.
**원인** — "발표 = 보고서 요약"이라는 오해 — 발표는 저장소·보고서로 안내하는 **예고편**
입니다.
**해결** — 장당 주장 하나 + 증거 하나(그림·숫자·로그). 상세를 묻는 질문이 나오면
"보고서 N절에 있습니다"가 정답이 되는 구조 — 문서가 튼튼하면 발표는 가벼워도 됩니다.

### 에이스 원맨쇼

**증상** — 가장 말 잘하는 한 명이 18분 발표 — 질의응답에서 침묵한 세 명에게 질문이
집중되고, 개인 기여도 평가가 무너짐.
**원인** — "발표 품질"만 최적화 — 평가 구조(전원 응답 조건, 기여도 30%)를 잊음.
**해결** — 구성표에 이름을 박고(Step 1), 모의 질의에서 지목 규칙(Step 3)으로 전원을
단련하세요. 심사자는 매끄러운 원맨쇼보다 **네 명이 각자의 영역에서 단단한 팀**에 높은
점수를 줍니다 — 그것이 이 평가가 측정하려는 것이기 때문입니다.

### 시연을 리허설에서 처음 돌려 봄

**증상** — 리허설 1회차에서 시연 구간이 처음으로 실제 실행됨 — 데모 페이지가 어제의
동결 배너 PR로 어긋나 있음을 그때 발견 (다행), 또는 내일 발견 (재앙).
**원인** — "맨날 돌던 거니까"의 방심.
**해결** — 시연은 **발표의 코드**입니다 — 코드에 테스트가 있듯 시연에는 리허설이
있습니다. 오늘 2회 + 내일 자기 순서 직전 30초 점검이 최소 규격입니다 ([Day 140](../05-infra-mlops/day-140.md)
의 안전 수칙 그대로).

### 질문 대비 = 정답 암기

**증상** — 예상 질문 10개의 모범 답안을 통째로 외움 — 변형 질문("게이트 임계값을 왜
10%로?")에 암기가 무너지고 침묵.
**원인** — 답을 외우고 근거를 안 외움.
**해결** — 답의 뼈대는 전부 **문서의 위치**입니다 (③의 표 오른쪽 열처럼). "임계값의
근거는 노이즈 대비 사고 크기 — 상세 판단은 152 기록에"처럼, 답변의 종착지를 문서로
삼으면 변형 질문에도 같은 뼈대가 작동합니다. 4주간 문서를 쌓은 팀만 쓸 수 있는 전략
입니다 — 여러분이 그 팀입니다.

**Q1.** 리허설 1회차의 조치("아키텍처 3분 삭감, 삭제분은 질의응답으로")가 단순한 시간
조정이 아니라 정보 전달 전략인 이유를, 발표와 질의응답의 정보 특성 차이로 설명하세요.

<details>
<summary>답 보기</summary>

발표는 일방향·고정 순서라 청중 전원에게 같은 정보를 강제 전달합니다 — 여기에 넣을
정보는 "전원이 반드시 알아야 이후가 이해되는 것"(문제·구조·핵심 증명)이어야 합니다.
질의응답은 수요 기반입니다 — 궁금한 사람이 있는 정보만, 궁금한 깊이만큼 전달됩니다.
ERD 상세는 후자에 속합니다: 관심 있는 심사자에게는 깊은 답(+준비된 문서 링크)이 강한
인상을 주고, 관심 없는 다수의 8분을 아낍니다. 즉 "빼기"는 정보의 손실이 아니라 정보를
적절한 채널(푸시→풀)로 재배치하는 것이고, 질문이 나왔을 때 "기다렸다는 듯 답하는" 팀의
모습은 발표에 넣었을 때보다 오히려 신뢰를 더 삽니다.

</details>

규칙을 어기고 싶어지는 전형적 상황과 그때의 올바른 판단 절차를 설명하세요.

<details>
<summary>답 보기</summary>

v1.0.0은 "이 커밋은 빈 서버 기동·절차 수행·문서 검증을 통과했다"는 상태 증명입니다.
태그 뒤의 변경은 그 증명 밖의 코드이므로, 내일 시연되는 것이 "검증된 것"이라는 명제를
깨뜨립니다 — 검증 없는 변경의 위험은 154(동결)에서 확립한 그대로입니다. 어기고 싶어지는
전형: 리허설 중 사소한 거슬림 발견(문구, 색상, 미미한 버그). 올바른 절차: ① 시연 실패를
유발하는가? 아니오 → 이슈로 기록, 손대지 않음(발표에서 언급할 필요도 없음). ② 예 →
동결 예외 절차(전원 동의 + 수정 후 시연 리허설 재실행 + 필요시 태그 갱신) — 즉 고치려면
검증도 다시 사야 합니다. "고치는 비용 = 수정 + 재검증"임을 상기하는 것이 유혹의 해독제
입니다.

전부 문서에), 그리고 리뷰가 남긴 "모르는 사람도 이해 가능한 설명"(141 Q3). 이 장치들이
없었다면 2문장 요약은 벼락치기 암기가 됐을 것입니다. 측정하는 것: 지식의 공유 정도 —
즉 이 팀이 "분업한 개인들의 합"인지 "서로를 설명할 수 있는 팀"인지. 실무 대응 역량:
장애 대응(담당자 부재 시 1차 대응), 온보딩(아무나 붙잡고 물어도 방향이 나옴), 인수인계
비용 — 버스 팩터가 1이 아닌 팀의 조건이며, 채용자가 팀 프로젝트 경험자에게 정확히
기대하는 것입니다.
