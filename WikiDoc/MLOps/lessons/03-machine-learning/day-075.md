## ② 왜 필요한가

MP1 발표에서 여러분은 "동작하는 파이프라인"을 보여주며 살아남았습니다. MP2 발표의 심사
포인트는 다릅니다 — 예측 프로젝트에서 심사위원이 확인하고 싶은 것은 단 하나,
**"이 사람이 자기 숫자를 믿어도 되는 방식으로 만들었는가"** 입니다.

```
MP1 발표의 킬러 질문: "두 번 실행하면 어떻게 되나요?"        (멱등성)
MP2 발표의 킬러 질문: "그 0.519, 어떻게 잰 겁니까?"          (평가의 정직성)
```

그래서 오늘 발표의 주인공은 데모가 아니라 **방법론의 서사**입니다: 베이스라인에서 출발해,
정직한 심판(시간 분리·CV) 아래서, 기록된 실험으로, 금고를 한 번만 열었다 — 이 이야기를
5분에 담습니다. 채용 면접의 포트폴리오 발표가 정확히 이 형식입니다.

### 예상 질문 10 ★

거의 반드시 나옵니다. 답의 뼈대까지 준비하세요.

| # | 질문 | 답의 뼈대 |
|---|---|---|
| 1 | **그 점수, 어떻게 쟀나요?** | 시간 분리(train ~12월/test 1~6월) + TSS CV로 선택 + **test는 최종 1회** |
| 2 | **누수는 어떻게 확인했나요?** | 특성별 "예측 시점에 아는 값인가" 검문표 + 파이프라인이 전처리 누수를 구조로 차단 |
| 3 | 왜 이 지표인가요? | 기획서에 실험 **전** 날짜로 확정 — 서비스 비용 구조(놓침 vs 헛경보)로 설명 |
| 4 | 왜 (복잡한 모델이 아니라) 이 모델인가요? | CV 성적 + 동률이면 단순한 쪽 규칙 + 운영 비용(4KB, 0.01초) |
| 5 | 딥러닝을 쓰면 더 좋지 않았을까요? | 테이블 데이터·소표본에선 근거 없음 — 계열 대표 비교 결과로 답 |
| 6 | CV와 test 점수가 왜 다른가요? | 역할이 다름(비교 자 vs 최종 보고) + TSS 초반 폴드 구조 |
| 7 | 가장 큰 개선은 뭐였나요? | 특성(새 정보) — 튜닝(+0.015)과의 크기 비교까지 |
| 8 | 이 모델이 불리하게 작동하는 집단은? | 분리 평가 결과(노원 27%)와 원인 가설, 대응 계획 |
| 9 | 재현하려면 어떻게 하나요? | README 복붙 3분 — clone 리허설 통과 사실 |
| 10 | 다음에 뭘 하고 싶나요? | 오답 분석이 가리키는 방향 + "이 모델을 API로" (MP3 예고) |

**8번을 준비한 발표자는 드뭅니다.** 준비돼 있으면 그 순간 발표의 급이 달라집니다.

## ④ 단계별 실습

### Step 1. 발표 준비 (1~2교시)

③의 구성대로 슬라이드 5장을 만들고, 시연 2종을 **직전에 한 번** 돌려 둡니다
(MLflow UI는 발표 전에 미리 띄워 두기 — 시연 실패 대비는 [Day 050](../02-sql-pipeline/day-050.md)의
백업 원칙 그대로: 스크린샷 준비, 30초 안에 안 되면 미련 없이 백업).

### Step 2. 발표회 (3~6교시)

1인 5분 + 질의 3분. 듣는 사람의 임무:

- 발표마다 **질문 1개 이상** (③의 표에서 골라도 좋음)
- 채점표(방법론 30 · 기록 25 · 재현성 20 · 문서 15 · 발표 10)로 상호 평가
- "가장 훔치고 싶은 것" 한 가지 기록 — 남의 저장소에서 배우는 것이 오늘의 숨은 수확입니다

### Step 3. 회고 (7교시)

`docs/retro.md` 에 세 질문만:

| 질문 | 예시 (예시 프로젝트의 회고) |
|---|---|
| 다시 한다면 다르게 할 것? | "시간 파생에 하루를 썼다 — 오답 노트부터 봤으면 반나절이었을 것" |
| 가장 비쌌던 교훈? | "무작위 CV 0.944를 믿을 뻔한 것 ([Day 061](day-061.md))" |
| 다음 프로젝트로 가져갈 습관? | "베이스라인 없이 퇴근 금지 · test는 금고에" |

### 다음 단원 예고 — 모델을 세상에 내놓기

지금 여러분의 모델을 쓰려면 파이썬과 sklearn을 설치하고 저장소를 clone해야 합니다.
기획자도, 앱 개발자도, 그렇게는 안 씁니다. 필요한 것은:

```
지금:  joblib.load(...) → pipe.predict(df)          (파이썬 사용자만)
목표:  POST /predict {"pm25": 41.0, ...} → {"pred": 29.5}   (누구나, 어디서나)
```

만듭니다. [Day 068](day-068.md)에서 저장한 그 파일과 스키마가 그대로 서빙의 재료가 됩니다.

## ⑤ 자주 하는 실수

### 발표에서 배경 설명에 2분을 씀

**증상** — "미세먼지란 무엇인가"로 시작 — 방법론 이야기 전에 시간 종료.
**원인** — 청중이 모를 거라는 불안. 하지만 심사위원이 궁금한 건 여러분의 **방법**입니다.
**해결** — 문제 정의는 30초 한 장(입력·출력·지표)으로 끝내고 평가 설계로 직행하세요.

### 점수를 자랑하고 방법을 생략함

**증상** — "R² 0.519 달성!"만 크게 — 1번 질문("어떻게 쟀나")에 버벅임.
**원인** — 절대 성능에 배점이 없다는 것을 잊었습니다.
**해결** — 점수는 반드시 **베이스라인·측정 방법과 한 문장에** 넣으세요: "내일=오늘(0.207) 대비, 시간 분리 test 1회 기준 0.519".

### 질문에 즉석 실험으로 답하려 함

**증상** — "어… 그건 지금 돌려 볼게요" — 3분 질의가 침묵의 디버깅으로.
**원인** — 예상 질문 준비 부족.
**해결** — ③의 10문항에 대한 답을 **숫자와 문서 위치**("report 3절에 있습니다")로 준비하세요. 모르는 질문은 "확인해서 이슈로 남기겠다"가 정답입니다.

### 회고를 감상문으로 씀

**증상** — "힘들었지만 보람찼다" — 다음 프로젝트에 남는 게 없음.
**원인** — 질문이 구체적이지 않아서입니다.
**해결** — Step 3의 세 질문(다르게 할 것 / 비쌌던 교훈 / 가져갈 습관)은 전부 **행동**을 답으로 요구합니다. 감정이 아니라 행동을 적으세요.

### 발표가 끝나자 저장소를 방치함

**증상** — 석 달 뒤 면접에서 "이 프로젝트 설명해 주세요" — README를 본인이 다시 읽으며 기억을 더듬음.

## ⑥ 확인 문제

**Q1.** MP1의 킬러 질문("두 번 실행하면?")과 MP2의 킬러 질문("그 점수 어떻게 쟀나?")이 각각
검증하려는 역량을 한 단어씩으로 요약하고, 공통점을 쓰세요.

<details>
<summary>답 보기</summary>

MP1은 **멱등성**(운영 가능한 파이프라인), MP2는 **평가의 정직성**(신뢰 가능한 성능 주장)입니다.
공통점: 둘 다 "결과물이 아니라 **결과물을 믿을 수 있게 만든 방식**"을 묻습니다 — 엔지니어링 성숙도는
산출물이 아니라 절차에서 드러납니다.

</details>

**Q2.** 질문 8("불리하게 작동하는 집단은?")에 "없습니다"라고 답하면 왜 감점인가요?

<details>
<summary>답 보기</summary>

집단별 분리 평가([Day 069](day-069.md))를 **안 해 봤다**는 자백이기 때문입니다. 격차는 대부분 존재하며
(우리 사례: 노원 27% vs 강남 58%), 좋은 답은 "찾았고, 원인은 이것으로 보이며, 대응은 이렇다"입니다.
격차의 존재가 아니라 격차에 대한 무지가 감점 사유입니다.

</details>

**Q3.** 대단원 03의 산출물(파이프라인 파일 + 스키마 + train.py)이 대단원 04에서 각각 무엇의
재료가 되는지 연결해 보세요.

<details>
<summary>답 보기</summary>

파이프라인 파일(joblib)은 서빙 API가 시작 시 **로드하는 모델**, 스키마 JSON은 API 요청의
**입력 검증 규칙**(FastAPI의 요청 모델로 번역됨), train.py는 운영 중 **재학습 파이프라인**의 실행 단위
(W27 Airflow의 태스크)가 됩니다. 이번 단원의 마무리 품질이 곧 다음 단원의 출발 속도입니다.

</details>
