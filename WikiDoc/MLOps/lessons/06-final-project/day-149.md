## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 개선 실험을 **오차 분석에서 도출**하고, 한 번에 하나씩 검증할 수 있다.
- "모델보다 특성" 원칙을 팀 프로젝트에서 재현할 수 있다.
- 모델 선정을 **지표 + 운영 비용 + 설명 가능성**의 3축 회의로 결정하고 기록할 수 있다.
- 선정 모델을 재현 가능한 학습 CLI와 함께 MLflow Registry에 등록할 수 있다.

---

## ② 왜 필요한가

"모델을 개선한다"고 하면 손이 먼저 가는 곳은 하이퍼파라미터 튜닝입니다 — 코드 한 줄로
시작되고, 돌아가는 동안 일하는 기분이 들기 때문입니다. 그러나 [Day 064](../03-machine-learning/day-064.md)
에서 확인했던 사실이 여기서도 반복됩니다: **큰 개선은 모델을 조이는 데서가 아니라 모델이
못 보던 것을 보여 주는 데서** 옵니다. 어제의 오차 분석이 이미 말해 줬습니다 — 베이스라인이
무너지는 곳은 공휴일 주변이고, 그렇다면 오늘 할 일은 트리 개수 조정이 아니라 달력을
피처로 만드는 것입니다.

그리고 오늘 오후, 이 주의 가장 중요한 회의가 있습니다 — **모델 선정 회의**. 여기서
연습해야 할 것은 기술이 아니라 결정의 형식입니다: 숫자가 가장 좋은 모델과 팀이 배포할
모델은 다를 수 있다는 것, 그 판단에는 지표 외의 축(운영 비용·설명 가능성)이 있다는 것,
그리고 어느 쪽이든 **이유가 기록되어야** 심사와 면접에서 자산이 된다는 것. "왜 이
모델인가요?"는 "왜 이 기술인가요?"(143)와 함께 채용 면접 단골 질문의 양대 축입니다.

## ③ 개념 설명

### 개선 실험의 두 규율

1. **한 번에 하나** — 피처 셋과 하이퍼파라미터를 같이 바꾸면, 개선이 어디서 왔는지 영원히
   모릅니다. run 하나 = 변경 하나.
2. **오차에서 출발** — "뭘 넣어 볼까"가 아니라 "어디서 틀리나"에서 실험이 나옵니다.
   어제의 최악 오차 목록이 오늘의 실험 대기열입니다.

### 피처 먼저, 튜닝은 마지막에

| 단계 | 기대 효과 | 비용 |
|---|---|---|
| 오차 원인을 피처로 (달력·lag 조합) | 크다 — 모델이 못 보던 정보 | 설계 필요 |
| 모델 교체 (선형→부스팅) | 중간 — 상호작용 학습 | 낮음 |
| 하이퍼파라미터 튜닝 | 작다 — 마지막 한 방울 | 시간 소모 큼 |

튜닝을 마지막에 두는 이유는 효과가 작아서만이 아니라, **피처가 바뀌면 튜닝을 다시 해야**
하기 때문입니다. 순서를 어기면 같은 일을 두 번 합니다.

### 선정의 3축 — 숫자가 전부가 아니다

| 축 | 질문 |
|---|---|
| 지표 | 홀드아웃에서 목표를 넘는가 (MAE·등급 정확도) |
| 운영 비용 | 재학습 시간 · 의존성 · 실패 모드 — **주 1회 자동으로 돌 물건**인가 |
| 설명 가능성 | 팀 전원이 "왜 이 예측이 나왔나"를 설명할 수 있는가 |

한산 팀은 주 1회 자동 재학습(무인)을 설계했습니다 — 모델은 일회성 제출물이 아니라
**운영 부품**이고, 운영 부품의 단순함은 성능 몇 명과 바꿀 가치가 있는 자질입니다.

## ④ 단계별 실습

### Step 1. 실험 시리즈 — 오차 대기열 순서대로 (1~4교시)

민준의 실험 기록 (전부 같은 evaluate() · 같은 홀드아웃 · MLflow run):

```
$ mlflow runs list --experiment hansan  (요약)
exp-01  lgbm + lag_7                      MAE 1,742 · 등급 0.80   주기를 lag로 재확인
exp-02  + lag_1 · lag_14                  MAE 1,538 · 등급 0.82   추세·최근성 반영
exp-03  + dow · is_holiday · day_after    MAE 1,146 · 등급 0.86   ← 달력 피처의 도약
exp-04  exp-03 + Optuna 30 trials         MAE 1,131 · 등급 0.86   튜닝의 마지막 한 방울
```

베이스라인 1,914 → exp-03 **1,146 (−40.1%)**. 목표(MAE ≤ 1,531 · 등급 ≥ 0.85)를 exp-03이
넘었습니다. 도약이 어디서 왔는지 보세요 — 어제 최악 오차 3건이 전부 공휴일 관련이었고,
공휴일 피처가 그 오차를 직접 지웠습니다:

```
$ python -m src.train.error_report --run exp-03 --worst 3
  2026-05-25 (대체공휴일)  오차 8,120 → 2,384   is_holiday가 흡수
  2026-05-05 (어린이날)    오차 7,644 → 2,041
  2026-07-13 (폭우)        오차 3,890 → 3,912   ← 남은 한계: 날씨 (범위 밖 — 보고서로)
```

폭우가 새 최악 오차로 올라왔습니다 — 날씨 피처는 이번 범위 밖(선택 로드맵)이므로,
이 표가 그대로 결과 보고서의 "한계와 개선 방향" 절 초안이 됩니다.

### Step 2. 모델 선정 회의 — 전원, 30분 (5교시)

의제는 하나: exp-03 vs exp-04. 숫자는 exp-04가 15명 좋습니다. 회의 기록:

```
민준: exp-04는 −15명(−1.3%). 대신 재학습에 Optuna 30 trial이 들어가 4분 → 22분.
하람: 주 1회 새벽 DAG가 22분 도는 건 괜찮지만, 실패 지점이 늘어남 (튜닝 중 타임아웃 등).
      게이트 비교도 "튜닝 운"이 섞여 주간 변동이 커질 수 있음.
지우: 등급 정확도는 동일 — 사용자가 얻는 차이는 0.
서연: 결정: exp-03 채택. 근거 3축 — 지표(목표 초과 달성, 서비스 지표 동일) ·
      운영(재학습 단순·안정) · 설명(피처 8개, 전원 설명 가능). exp-04는 기록으로 보존.
```

**exp-03 채택 — 숫자가 낮은 쪽을 고르고 이유를 남겼습니다.** 이 기록이 docs/MODEL.md의
"선정 근거" 절이 됩니다.

### Step 3. 등록과 재현 명령 고정 (6~7교시)

```
$ python -m src.train.train --config configs/train.yaml
[train] data_md5 e91c07a4 · features 8 · MAE 1146.3 · 등급 0.8604
[train] MLflow run 4c9d21e7 → registered: hansan-daily v1
```

재현 명령 한 줄(`--config`가 피처·구간·시드 전부 고정)이 저장소에 있는 것 — 이것이
"실험 기록이 남은 모델"(필수 6종)의 완성 조건입니다.

### Step 4. 병렬 트랙 확인 (8교시)

이번 주 내내 지우는 더미 API 위에서 #12·#13을 진행해 왔습니다 — 데모 페이지가 더미
등급을 표시하는 상태까지 완료. 내일 중간 데모의 그림이 모입니다: 서연·하람의 파이프라인
(수집→DB), 민준의 모델(hansan-daily v1), 지우의 화면(더미) — **모델과 화면의 결합이
다음 주 151의 첫 작업**임을 스탠드업에서 확인합니다.

**오늘 퇴근 체크** — □ 실험 4 run(변경 1개씩) □ 오차 재분석(남은 한계 기록) □ 선정
회의록(3축 근거) □ hansan-daily v1 등록 + 재현 명령 □ 내일 데모 시나리오 초안

## ⑤ 자주 하는 실수

### 개선 = 튜닝이라는 착각

**증상** — 첫 실험부터 Optuna 200 trials 6시간 — MAE 1,742 → 1,715. 달력 피처는 아직
코드에 없음.
**원인** — 효과의 크기가 아니라 착수의 쉬움으로 작업을 고름.
**해결** — 실험 대기열은 오차 분석에서만 나옵니다(Step 1의 순서 그대로). 튜닝은 피처가
확정된 뒤 마지막 한 번 — 그리고 그마저 채택 안 될 수 있음(한산 팀의 exp-04)을 정상으로
여기세요.

### 한 run에 변경 세 개

**증상** — "lag도 늘리고 달력도 넣고 depth도 바꿨더니 좋아졌어요!" — 무엇이 효과였는지
모르므로, 다음 실험 설계도 감으로 하게 됨.
**원인** — 빨리 좋아지고 싶은 조급함.
**해결** — run 하나 = 변경 하나의 규율이 실험을 **누적 가능한 지식**으로 만듭니다.
exp-01→04의 계단이 그대로 보고서의 "개선 과정" 절이 되는 것을 보세요 — 규율이 곧
문서입니다.

### 노트북 최고 기록, 재현 불가

**증상** — "그때 1,120 나왔었는데…" — 셀 실행 순서가 뒤엉킨 노트북, 그 숫자를 다시
만들 수 없음.
**원인** — 탐색용 노트북과 기록용 스크립트의 구분 없음.
**해결** — 탐색은 노트북에서 자유롭게, **주장할 숫자는 반드시 train.py + config + MLflow
run**으로 남기세요 ([Day 070](../03-machine-learning/day-070.md)의 그 구조). 재현 명령
없는 숫자는 팀의 공식 기록이 될 수 없습니다 — 게이트도, 보고서도, 발표도 run만 믿습니다.

### 선정 이유를 기록하지 않음

**증상** — 3주 뒤 발표 준비 중 "우리 왜 튜닝 버전 안 썼지?" — 아무도 정확히 기억 못 함.
재학습 게이트 개선 논의에서도 같은 논쟁이 처음부터 반복됨.
**원인** — 결정과 기록의 분리 — 결정은 회의에서 증발합니다.
**해결** — 선정 회의록(3축 근거)을 docs/MODEL.md에 그날 남기세요. "숫자가 낮은 쪽을
근거와 함께 골랐다"는 기록은 심사·면접에서 가장 강한 종류의 증거입니다 — 지표를 넘어
운영을 생각했다는 직접 증명이기 때문입니다.

## ⑥ 확인 문제

**Q1.** exp-03의 도약(1,538→1,146)과 exp-04의 개선(1,146→1,131)의 크기 차이를, "모델이
못 보던 정보" vs "보던 정보의 더 나은 활용"이라는 프레임으로 설명하세요.

<details>
<summary>답 보기</summary>

exp-03 이전의 모델에게 공휴일은 존재하지 않는 정보였습니다 — lag 피처 어디에도 "다음
주 월요일은 쉬는 날"이 없으므로, 모델이 아무리 잘 배워도 그 오차는 구조적으로 남습니다.
달력 피처는 오차의 **원인 자체를 입력으로** 넣은 것이라 해당 오차가 통째로 사라집니다
(8,120→2,384). 반면 exp-04의 튜닝은 이미 주어진 정보 안에서 분할·가중치를 미세 조정하는
것 — 정보의 총량이 같으므로 개선은 잔여 오차의 가장자리에서만 나옵니다(−15명). 일반화
하면: 오차가 구조적(입력에 원인 부재)이면 피처가, 오차가 통계적(활용 미숙)이면 튜닝이
답이고, 큰 도약은 거의 언제나 전자에서 옵니다.

</details>

**Q2.** "주 1회 무인 재학습"이라는 운영 설계가 모델 선정 기준을 어떻게 바꾸는지 — 같은
두 후보(exp-03/04)를 "일회성 제출물"로 고를 때와 비교해 설명하세요.

<details>
<summary>답 보기</summary>

일회성 제출물이라면 재학습 시간 22분도, 실패 지점 증가도 비용이 아닙니다 — 한 번 돌려
가장 좋은 숫자를 내면 끝이므로 exp-04가 합리적일 수 있습니다. 무인 운영 부품이 되는
순간 평가 축이 늘어납니다: 매주 새벽에 사람 없이 성공해야 하고(실패 모드가 적을수록
좋음), 게이트 비교의 주간 변동이 작아야 하며(튜닝의 확률적 요소는 노이즈가 됨), 문제가
생겼을 때 팀 누구나 원인을 추적할 수 있어야 합니다(단순성 = 디버깅 가능성). exp-04의
−15명은 이 세 비용을 상쇄하지 못합니다. 요약: 배포 주기가 반복이 되는 순간, 모델의
"성능"에 안정성·단순성·설명 가능성이 포함되기 시작합니다 — MLOps가 모델 선정 기준을
바꾸는 지점입니다.

</details>

**Q3.** 폭우일 오차(3,890→3,912)가 개선되지 않은 것을 팀은 "수리"가 아니라 "보고서 기록"
으로 처리했습니다. 이 처리가 옳은 이유를 범위(142)·품질 목표(148)·발표 전략(136 Q3)과
연결해 설명하세요.

<details>
<summary>답 보기</summary>

범위: 날씨 피처는 새 데이터 원천(기상 API) 연동을 뜻하므로 "데이터 폭" 축의 확장 —
142에서 자른 범위를 다시 여는 일이고, 지금은 W30 목요일입니다. 품질 목표: exp-03이 이미
목표(MAE ≤ 1,531 · 등급 ≥ 0.85)를 넘었으므로 멈춤 규칙이 발동한 상태 — 추가 개선은
관통(서빙 연결)에서 시간을 빼앗는 일입니다. 발표 전략: "폭우일 오차는 남아 있고, 원인
(날씨 정보 부재)과 해법(기상 피처)을 안다"는 기록은 정직한 한계 선언의 3종 세트(알고
있음·감수 근거·넘어갈 방법)를 정확히 충족합니다 — 숨겨진 약점이 아니라 관리되는 한계는
점수입니다. 요약: 모든 오차를 지우는 것이 목표가 아니라, 지울 오차와 기록할 오차를
구분하는 것이 프로젝트 관리입니다.

</details>
