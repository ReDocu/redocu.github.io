## 단원 개요

### 이 단원을 마치면

- 온프레미스와 클라우드의 차이를 **비용 구조와 책임 범위로 설명**할 수 있다.
- 새 AWS 계정에 **루트 보호 · IAM 사용자 · 예산 알림이라는 3중 기준선을 설정**할 수 있다.
- IAM 정책 JSON을 읽고 **"이 요청이 허용되는가"를 스스로 판정**할 수 있다.
- AWS CLI로 **리소스를 생성·조회·삭제**하고 결과를 필터링해 확인할 수 있다.
- CIDR를 계산해 **퍼블릭/프라이빗 서브넷을 가진 VPC를 처음부터 설계·구축**할 수 있다.

### 왜 4주(8강)인가

이 단원은 **뒤의 12주 전체가 올라설 바닥**입니다.
05강 이후 모든 리소스는 03–04강에서 만든 **IAM 역할**로 권한을 받고, 09강 이후 모든 컴퓨팅은 07–08강에서 만든 **VPC 안**에 들어갑니다.
IAM을 대충 넘기면 11주차 ECS 태스크 역할에서, VPC를 대충 넘기면 15강 RDS 서브넷 그룹에서 반드시 막힙니다.
그래서 이 단원은 서비스 개수는 적지만 **직접 만들어 보고 일부러 망가뜨려 보는 시간**을 가장 길게 씁니다.

### 이론 수업 내용

**01강 (60분)**
1. "서버를 산다"와 "서버를 빌린다"의 차이 — 3년 감가상각 vs 시간당 과금, 실제 견적 비교
2. AWS 글로벌 인프라 3층 구조 — 리전(Region) → 가용 영역(AZ) → 엣지 로케이션. **AZ가 물리적으로 분리된 데이터센터 묶음**이라는 점이 이후 모든 고가용성 설계의 출발점
3. 리전 선택 기준 4가지 — 지연 시간 · 법규(데이터 주권) · 서비스 가용 범위 · 가격 (서울 리전이 버지니아보다 비싼 이유)
4. 책임 공유 모델 — "of the cloud"(AWS) vs "in the cloud"(고객), EC2와 S3와 Lambda에서 경계가 각각 어떻게 달라지는지
5. 요금 모델 — 온디맨드 · Savings Plans · 예약 인스턴스 · 스팟 · 프리 티어. **"쓴 만큼"이 아니라 "켜 둔 만큼"** 과금된다는 사실

**02강 (60분)**
1. 루트 계정으로 할 수 있는 일과 루트 자격 증명이 유출됐을 때 벌어지는 일(실제 사례: 유출 키로 채굴 인스턴스 대량 생성 → 수천 달러 청구)
2. 계정 개설 직후 체크리스트 7항목과 각 항목의 이유
3. Budgets · Cost Explorer · Cost Anomaly Detection의 역할 차이
4. 프리 티어의 3종류(12개월 무료 / 상시 무료 / 평가판)와 **프리 티어에 포함되지 않아 사고가 나는 대표 리소스**(NAT Gateway, ALB, 퍼블릭 IPv4, Fargate)

1. 리전과 가용 영역(AZ)의 차이는? → **리전은 지리적으로 분리된 지역, AZ는 한 리전 안에서 전원·냉각·네트워크가 물리적으로 분리된 하나 이상의 데이터센터.** 고가용성은 "여러 AZ에 걸치는 것"이 기본이다.

4. 스팟 인스턴스를 쓰면 안 되는 워크로드는? → **중단되면 안 되는 상태 유지형 워크로드**(예: 단일 DB 서버). AWS가 2분 통보 후 회수할 수 있으므로 배치·렌더링 등 중단 허용 작업에 적합.
5. 예산 알림을 설정했는데 왜 청구가 계속 늘 수 있는가? → **Budgets는 알림일 뿐 차단 기능이 아니다.** 차단하려면 SNS+Lambda로 리소스를 정지하거나 SCP로 사전 차단해야 한다.

## W02 · IAM과 최소 권한

**03–04강** · 6시간 · 예상 비용 **$0**

> **주차 목표**
> - 사용자 · 그룹 · 역할 · 정책의 관계를 그림으로 그리고, 언제 역할을 쓰는지 판단한다.
> - 정책 JSON을 읽고 특정 요청의 허용/거부 결과를 **평가 로직에 따라 예측**한다.
> - 액세스 키 없이 동작하는 **역할 기반 권한 체계**를 구성한다.

**이전 주차와의 연결** — 01강 책임 공유 모델의 "고객 책임" 중 가장 첫 번째가 접근 제어입니다. 02강에서 만든 IAM 사용자에 이번 주에 **최소 권한**을 입힙니다.

| 강 | 제목 | 핵심 개념 | 다룰 서비스 |
|---|---|---|---|
| [**03**](../lessons/01-cloud-foundation/lesson-03.md) | IAM 핵심 — 사용자·그룹·역할·정책 | 자격 증명 vs 권한 · 정책 JSON 6요소 · 관리형/인라인 정책 · **역할과 신뢰 정책** · 임시 자격 증명(STS) | IAM, STS |
| [**04**](../lessons/01-cloud-foundation/lesson-04.md) | 최소 권한 실전 | 정책 평가 로직(암묵적 거부 → 명시적 거부 우선) · 조건 키 · 권한 경계 · Access Analyzer · 자격 증명 유출 대응 | IAM Access Analyzer, IAM Identity Center(소개), CloudTrail(맛보기) |

### 이론 수업 내용

**03강 (60분)**
1. "누가(Principal) 무엇을(Action) 어디에(Resource) 어떤 조건에서(Condition)" — 정책 JSON 6요소를 문장으로 읽는 훈련
2. 사용자 vs 역할 — **사람은 사용자, 애플리케이션/서비스는 역할.** EC2가 S3를 읽어야 할 때 액세스 키를 심으면 안 되는 이유
3. 신뢰 정책(Trust policy)과 권한 정책(Permission policy)의 2단 구조 — `AssumeRole`이 실제로 하는 일과 STS 임시 자격 증명(만료 시간)
4. AWS 관리형 정책 vs 고객 관리형 정책 vs 인라인 정책 — 언제 무엇을 쓰나
5. **대안 비교** — IAM 사용자 다수 운영 vs IAM Identity Center(SSO). 조직 규모가 커지면 왜 후자로 가는가

**04강 (60분)**
1. 정책 평가 순서 — 기본 거부 → 명시적 Deny 확인 → Allow 확인. "Allow가 있는데 왜 막히지?"의 원인 5가지
2. 조건 키 실전 — `aws:SourceIp`, `aws:MultiFactorAuthPresent`, `aws:RequestedRegion`(서울 외 리전 차단), `aws:ResourceTag`
3. 최소 권한을 만드는 현실적인 절차 — 넓게 시작 → CloudTrail/Access Analyzer로 실제 사용 액션 확인 → 좁히기
4. 자격 증명이 유출됐을 때 대응 순서 — 키 비활성화 → 새 키 발급 → 리소스 점검 → CloudTrail 조사 → 사후 조치

## W04 · VPC 설계와 미니 프로젝트

**07–08강** · 6시간 · 예상 비용 **$0.4 ~ 0.6** · 🏁 **기초 미니 프로젝트**

> **주차 목표**
> - CIDR 블록을 계산해 2개 AZ에 걸친 퍼블릭/프라이빗 서브넷 구조를 설계한다.
> - 라우팅 테이블 · IGW · NAT Gateway가 각각 어떤 경로를 만드는지 설명하고 구성한다.
> - 인터넷에서 직접 접근할 수 없는 서버가 **어떻게 외부와 통신하는지** 3가지 방법으로 구현한다.

**이전 주차와의 연결** — 06강에서 "기본 VPC"에 아무 생각 없이 띄웠던 인스턴스를, 이번 주에는 **직접 설계한 VPC의 프라이빗 서브넷**으로 옮깁니다. 이 VPC가 16주 내내 사용될 실습 무대입니다.

| 강 | 제목 | 핵심 개념 | 다룰 서비스 |
|---|---|---|---|
| [**07**](../lessons/01-cloud-foundation/lesson-07.md) | VPC 설계 — 서브넷·라우팅·게이트웨이 | CIDR 설계와 AWS 예약 IP 5개 · 퍼블릭/프라이빗의 정의(=라우팅) · IGW · NAT Gateway vs NAT 인스턴스 · 보안 그룹 vs NACL · VPC 엔드포인트 | VPC, Subnet, Route Table, IGW, NAT Gateway, NACL, VPC Endpoint |
| [**08**](../lessons/01-cloud-foundation/lesson-08.md) | 🏁 미니 프로젝트 — 안전한 3계층 네트워크 | 설계 → 구축 → 검증 → 정리 전 과정 · 네트워크 문제 해결 절차 · 흐름 로그로 원인 찾기 | VPC 전체, EC2, SSM, VPC Flow Logs |

### 이론 수업 내용

**07강 (60분)**
1. VPC = 내 전용 가상 네트워크. `10.0.0.0/16` 을 고르는 이유와 **온프레미스/다른 VPC와 겹치면 안 되는 이유**
2. 서브넷 CIDR 계산 — `/24` 는 몇 개의 사용 가능 IP인가(251개, AWS가 5개 예약)
3. **"퍼블릭 서브넷"이라는 설정값은 없다** — IGW로 향하는 `0.0.0.0/0` 라우트가 있으면 퍼블릭, 없으면 프라이빗
4. NAT Gateway — 프라이빗에서 나가는 통신만 허용. **시간당 $0.059 + 데이터 처리 $0.059/GB** 라는 비용 구조와 AZ당 하나씩 두는 이유
5. **대안 비교표** — 프라이빗 서브넷에서 외부 접근이 필요할 때: ① NAT Gateway(관리형·비쌈) ② NAT 인스턴스(싸지만 직접 관리·SPOF) ③ VPC 엔드포인트(특정 AWS 서비스만, 인터넷 경유 없음·가장 안전)
6. 보안 그룹 vs 네트워크 ACL 비교 — 적용 대상(ENI vs 서브넷) · 상태 저장 여부 · 허용/거부 규칙 · 평가 순서

**08강 (30분 이론 + 프로젝트)**
1. 네트워크 문제 해결 5단계 체크 순서 — 라우팅 → 보안 그룹 → NACL → DNS → 애플리케이션
2. VPC Flow Logs 읽는 법 — `ACCEPT`/`REJECT` 로 어디서 막혔는지 판정

### 단계별 실습 — 07강

| Step | 내용 | 시간 |
|---|---|---|
| 1 | 종이/화이트보드에 **CIDR 설계** — VPC `10.0.0.0/16`, 퍼블릭 `10.0.1.0/24`(2a)·`10.0.2.0/24`(2c), 프라이빗 앱 `10.0.11.0/24`·`10.0.12.0/24`, 프라이빗 DB `10.0.21.0/24`·`10.0.22.0/24` | 15분 |
| 2 | VPC 생성 → 서브넷 6개 생성(AZ 분산) | 20분 |
| 3 | IGW 생성·연결 → **퍼블릭 라우팅 테이블** 작성 후 퍼블릭 서브넷 2개에 연결 | 20분 |
| 4 | NAT Gateway 1개 생성(퍼블릭 2a) → 프라이빗 라우팅 테이블에 `0.0.0.0/0 → NAT` 추가 | 20분 |
| 5 | NACL 실습 — DB 서브넷에 앱 서브넷만 허용하는 규칙 작성, 보안 그룹과의 차이 확인 | 15분 |
| 6 | **S3 게이트웨이 엔드포인트** 생성 → 프라이빗 인스턴스에서 NAT 없이 S3 접근되는지 확인 | 10분 |

### 단계별 실습 — 08강 🏁 미니 프로젝트

> **과제 문장** — "사내 관리 도구를 운영한다. 웹 서버는 인터넷에서 직접 접근할 수 없어야 하고, 운영자는 SSH 포트를 열지 않고 접속해야 하며, 서버는 보안 패치를 위해 외부에서 패키지를 내려받을 수 있어야 한다."

| Step | 내용 | 시간 |
|---|---|---|
| 1 | 07강 VPC 위에 **프라이빗 서브넷(2a)에 EC2** 시작 — 퍼블릭 IP 없음, IAM 역할에 SSM 권한 | 20분 |
| 2 | **접속 검증** — Session Manager로 접속 성공 확인. (SSM 엔드포인트 3종 또는 NAT 경유 중 택1하고 근거 기록) | 20분 |
| 3 | **아웃바운드 검증** — `dnf update` 로 패키지 다운로드 성공 확인 → NAT 경로가 살아 있음을 증명 | 10분 |
| 4 | **격리 검증** — 퍼블릭 서브넷의 배스천 없이 인터넷에서 이 인스턴스에 접근 불가함을 확인(퍼블릭 IP 없음, 라우팅 없음) | 10분 |
| 5 | **VPC Flow Logs** 활성화 → 차단된 요청 1건을 일부러 만들고 `REJECT` 레코드 확인 | 20분 |
| 6 | 아키텍처 다이어그램 작성(draw.io) + 리소스 목록·비용 표 정리 | 10분 |
| 7 | **전체 정리** — NAT → EC2 → 엔드포인트 → 서브넷 → VPC 순서로 삭제하며 의존 관계 체감 | 10분 |

### 예상 비용과 과금 주의 사항

| 리소스 | 프리 티어 | 예상 비용 | 과금 위험 |
|---|---|---|---|
| VPC · 서브넷 · 라우팅 테이블 · IGW | 무료 | $0 | 없음 |
| **NAT Gateway** | ❌ **미포함** | 6시간 약 **$0.36** + 데이터 처리 | **방치 시 월 $42+** — 이 과정 최대 위험 |
| VPC 엔드포인트 (게이트웨이형: S3/DynamoDB) | 무료 | $0 | 없음 |
| VPC 엔드포인트 (인터페이스형: SSM 등) | ❌ | 시간당 약 $0.013 × 엔드포인트 수 × AZ 수 | 3종 × 2AZ = 시간당 약 $0.078 |
| EC2 t3.micro | ✅ | $0 | — |
| VPC Flow Logs | ❌(CloudWatch Logs 5GB 무료) | $0~0.1 | 트래픽 많으면 로그 비용 급증 |

> 🔴 **NAT Gateway는 반드시 수업 종료 전에 삭제합니다.** 삭제 확인은 콘솔이 아니라 `aws ec2 describe-nat-gateways --filter "Name=state,Values=available"` 로 합니다.
> 인터페이스 엔드포인트를 쓰는 방식과 NAT를 쓰는 방식 중 **어느 쪽이 이번 실습에서 더 싼지 계산해 보는 것**이 08강 Step 2의 숨은 목표입니다.

### 보안 및 운영상 주의점

- **DB 서브넷은 NAT 라우트도 주지 않습니다.** 데이터 계층은 나가는 통신도 필요 없어야 합니다.
- NACL은 상태 비저장이므로 **응답 트래픽용 임시 포트(1024–65535) 아웃바운드**를 함께 열어야 합니다. 이것을 빠뜨려 생기는 장애가 매우 흔합니다.
- 보안 그룹은 **다른 보안 그룹을 소스로 지정**할 수 있습니다(IP 대신). 앱 → DB 규칙은 이 방식이 정답입니다.
- 기본 VPC를 실습에 계속 쓰지 않습니다. 기본 VPC의 서브넷은 전부 퍼블릭입니다.

<summary>정답 보기</summary>

1. 서브넷을 "퍼블릭"으로 만드는 것은 정확히 무엇인가? → **라우팅 테이블에 인터넷 게이트웨이(IGW)로 향하는 `0.0.0.0/0` 경로가 있는 것.** 서브넷 자체에 퍼블릭 옵션이 있는 것이 아니다.
2. `10.0.1.0/24` 서브넷에서 실제로 쓸 수 있는 IP는 몇 개인가? → **251개.** 256개 중 네트워크 주소·브로드캐스트·AWS 예약 3개(라우터, DNS, 미래 예약) 총 5개를 뺀다.
3. NAT Gateway와 인터넷 게이트웨이의 차이는? → IGW는 **양방향**(인바운드 가능, 퍼블릭 IP 필요), NAT Gateway는 프라이빗 리소스의 **아웃바운드 전용**. NAT는 유료, IGW는 무료.
4. 보안 그룹에서 허용했는데도 통신이 안 된다. NACL을 의심해야 하는 이유는? → NACL은 **상태 비저장**이라 인바운드를 허용해도 **응답용 임시 포트 아웃바운드**가 막혀 있으면 통신이 실패한다.
5. 프라이빗 인스턴스가 S3에 접근해야 한다. NAT Gateway 없이 하는 방법과 그 이점은? → **S3 게이트웨이 VPC 엔드포인트.** 비용이 무료이고 트래픽이 인터넷을 경유하지 않아 더 안전하다.

| NAT Gateway가 그렇게 비싼가요? | 시간당 $0.059 + 데이터 처리 $0.059/GB로 **켜 두면 월 $42 이상**입니다. 실습에선 만들었다 지우고, AWS 서비스만 접근한다면 VPC 엔드포인트로 대체합니다. (07강) |
| 인스턴스를 중지했는데 왜 돈이 나가나요? | EBS 볼륨과 탄력적 IP는 **중지 상태에서도 과금**됩니다. 실습 리소스는 중지가 아니라 **종료 + 볼륨 삭제**가 정답입니다. (06강) |
| SSH 키 없이 접속이 되나요? | 됩니다. Session Manager는 인스턴스가 **아웃바운드로** SSM에 연결하는 방식이라 인바운드 포트를 열 필요가 없고, 접속 기록도 남습니다. (06강) |
