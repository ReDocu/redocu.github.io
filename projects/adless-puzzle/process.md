## 1. 요약

| 항목 | 값 |
|---|---|
| 기간 | 2026-10-01 ~ 10-11 (11일), 이후 배포 |
| 커밋 | 15개 — 기능 단위로 크게 묶음 |
| 작업 방식 | 사람 1명이 방향을 정하고, 여러 Claude Code 세션이 게임·화면을 나눠 병렬로 작업 |
| 결과 | 게임 32종 × 100레벨, 무한모드 26종, 오늘의 퍼즐, 로그인·랭킹, 그림 약 1,800장, 합성 사운드 32세트 |
| 자동 검증 | 테스트 1,855개 (게임 1,849 + 공용 6), 실패 0 |
| 사람 플레이 QA | 3차례 사용성 평가 + 크기·그림·소리 라운드, 기록 1,000줄 이상 |

전체 흐름:

```text
기획(GDD 32개) → 구현(1~50레벨) → 100레벨 확장 → 그림·튜토리얼
  → QA 1차(사용성 303건) → 반영 1·2차 → 크기 키우기 → 로그인·랭킹
  → 게임별 소리 → 그림 평가(336곳) → 사용성 3차(449줄) → 반영 3차(378줄)
  → 보류 재조정 + 오늘의 퍼즐 → IP 위험 점검 → 기록 동기화 정리 → 배포
```

## 3. 기획: 게임마다 기획서 하나

시작은 "모바일 광고에서 자주 보는 퍼즐 미니게임을, 광고 없이 끝까지 할 수 있게"였다. 먼저 장르 목록을 정하고 게임마다 기획서(GDD)를 썼다.

| GDD 목차 | 내용 |
|---|---|
| 1~3 | 개요, 핵심 재미, 대상 |
| 4~6 | 규칙, 조작, 승패·별 조건 |
| 7 | 화면·연출 (색만으로 구분하지 않기 포함) |
| 8 | 레벨 설계, 난이도 곡선, 기믹 등장 순서 |
| 9~12 | 튜토리얼, 소리, 금지 사항(광고·하트·에너지·결제 없음), 테스트 기준 |
| 13 | 웹 구현 노트 — 구현한 세션이 실제로 어떻게 만들었는지 적음 |

- 1번 기획서를 기준 형식으로 먼저 쓰고, 나머지는 그 목차를 그대로 따르게 했다. 형식이 같아 세션이 바뀌어도 이어받기 쉬웠다.
- 13장(웹 구현 노트)을 기획서 안에 둬서, "기획 의도"와 "실제 구현"이 한 문서에서 비교된다.

## 4. 구현과 검증 순서

게임 하나를 만드는 순서는 모든 게임에서 같았다.

```text
1. logic.ts       규칙을 React 없이 순수 함수로 (init · step · isWon · starsFor)
2. 솔버            같은 규칙으로 탐색하는 풀이기
3. 레벨            수작업(지도·시나리오·픽셀 그림) 또는 생성기(gen.ts)
4. levels.test.ts  100개 전부 풀림 + 함정 존재 + 결정론
5. Game.tsx        화면 · 입력 · 애니메이션 · 되돌리기
6. 튜토리얼 · 그림 · 소리
```

**규칙과 테스트를 화면보다 먼저** 만들었다. 화면이 없어도 "이 레벨이 풀리는가"를 바로 확인할 수 있어서, 레벨을 대량으로 만들고 고치는 속도가 빨랐다.

### 4.1 레벨 100개를 만드는 방법

- **1~50 고정, 51~100 덧붙이기**: 처음 50개는 손대지 않고, 난이도 6~10단계를 나중에 붙였다. 생성기를 고쳐도 기존 레벨은 바뀌지 않는다는 테스트를 둔다.
- **생성기는 후보를 많이 만들고 솔버로 고른다**: "풀린다" + "기준 수가 맞다" + "생각 없이 하면 진다"를 모두 통과한 것만 남긴다.
- **역순 생성**: 탈출·짝 잇기 게임은 "다 푼 상태"에서 거꾸로 배치해 반드시 풀리는 판을 만든다.
- **사람 손떨림 검사**: 선을 그리는 게임은 정답 선을 몇 픽셀씩 흔들어도 이기는지 25곳을 시험해, 정밀하게 그려야만 이기는 판을 걸러냈다.

### 4.2 매번 돌리는 검사

```bash
npm test                      # 게임 1,849개
node --test "lib/*.test.ts"   # 공용 6개
npx tsc --noEmit              # 타입
npm run lint                  # 린트
```

세션마다 자기 작업이 끝나면 이 네 가지를 통과시킨 뒤에 "완료"로 표시했다.

## 5. 여러 Claude Code 세션 병렬 작업

사람 1명과 여러 Claude Code 세션이 함께 일했다. 동시에 3~8개 세션이 돌았다.

### 5.1 나누는 법

| 원칙 | 방법 |
|---|---|
| 겹치지 않게 | 게임 번호 범위로 나눔 (예: 1~8 + 공통 화면 / 9~16 / 17~24 / 25~32) |
| 먼저 말하고 시작 | 작업표(Markdown)에 담당 칸 이름을 적고 상태를 `대기 → 진행중 → 완료`로 바꿈 |
| 기록은 세션 폴더에 | 세션마다 `_parts/<세션>/` 폴더에 CSV로 기록, 끝나면 하나로 합침 |
| 공통 파일은 조율 세션만 | 공용 쉘·서버·문서 합본은 조율 세션 하나가 맡음 |
| 큰 범위는 보조 에이전트로 | 조율 세션이 게임 5개씩 맡는 보조 에이전트를 띄워 나눔 |

### 5.2 지침 문서 → 세션별 기록 → 합본

라운드마다 같은 형태로 진행했다.

```text
지침 문서 (무엇을, 어떤 기준으로, 어떤 열로 기록할지)
  ├─ 세션 A: 게임 1~8   → _parts/A/*.csv
  ├─ 세션 B: 게임 9~16  → _parts/B/*.csv
  ├─ 세션 C: 게임 17~24 → _parts/C/*.csv
  └─ 세션 D: 게임 25~32 → _parts/D/*.csv
        ↓ 합치기 (게임번호 · 우선순위 순 정렬, ID 부여)
결과 문서 + 합본 CSV (Excel에서 바로 열리게 UTF-8 BOM)
        ↓ 다음 라운드
반영 지침 → 세션별 status.csv (ID · 상태 · 메모) → 반영 결과 문서
```

- 기록 열을 지침에서 고정해 두면 세션이 달라도 합치기가 기계적으로 된다.
- 반영 라운드는 평가 라운드의 ID를 그대로 받아 행마다 `완료 / 보류 / 이미지 필요`를 남긴다. 무엇이 처리됐는지 행 단위로 추적된다.

### 5.3 브라우저 충돌 피하기

처음 사용성 평가 때 4개 세션이 한 크롬 창을 나눠 쓰다가, 백그라운드 탭에서는 애니메이션 타이밍이 다르게 보이는 문제가 있었다. 이후에는 **세션마다 자기 포트의 헤드리스 크롬**을 띄우고, 공용 조작 스크립트(이동·탭·드래그·캡처, 390×844 고정)로 플레이했다. 끝나면 자기 포트의 크롬만 끈다.

## 6. QA 라운드

모든 라운드는 폰 화면 크기(390×844)에서 실제로 플레이하며 진행했다.

| 날짜 | 라운드 | 규모 | 결과 |
|---|---|---|---|
| 10-07 | 사용성 평가 1차 | 4개 세션 × 8게임, 303건 (애니메이션 66 · 소리 59 · 그림 50 · 개선 108 · 버그 20) | 반영 1차·2차로 처리 |
| 10-08 | 크기 키우기 | 크기 스캔 119건 | 탭 대상 44px · 플레이 글씨 14px 기준 적용 |
| 10-08 | 게임별 소리 | 32세트 | 소리 실험실에서 음량·길이 측정해 게임끼리 맞춤 |
| 10-09 | 그림 평가 2차 | 화면의 그림 자리 336곳 | 있는 그림 중에서 고르고, 없는 28곳은 새로 제작(93장) |
| 10-10 | 사용성 평가 3차 | 449줄 (버그 40 · 문제점 170 · 개선 168 · 사용자 맥락 38 · 점수 33) | P1 24줄 = 6건 |
| 10-10 | 반영 3차 | 378줄 | 완료 359 · 보류 17 · 그림 필요 2, P1 6건 전부 해결 |
| 10-11 | 보류 재조정 | 20줄 | 권장안대로 처리 (완료 18 · 일부 2) |

### 6.1 우선순위

| 등급 | 뜻 |
|---|---|
| P1 | 출시 전 필수 |
| P2 | 있으면 크게 좋아짐 |
| P3 | 여유 있을 때 |

### 6.2 평가 관점의 변화

- **1차(10-07)는 "무엇이 없나"**를 봤다. 그 결과 32종 모두 전용 효과음이 없고, 튜토리얼 카드가 가르치려는 대상을 가리고, 조작 대상이 너무 작다는 공통 문제가 나왔다.
- **3차(10-10)는 "사람이 어디서 헷갈리고, 답답하고, 그만두나"**를 봤다. 페르소나 3명을 두고, 게임마다 "광고를 보고 기대한 것 / 첫 30초 / 오해하기 쉬운 점 / 한 판 길이 / 그만두는 순간"을 기록했고, 7개 항목 1~5점으로 사용성 점수를 매겼다.
- 평가는 레벨 1 → 2~3 → 50 → 90대 → 무한모드 순으로 했다. 초반만 보면 놓치는 난이도 문제를 찾기 위해서다.

### 6.3 반영 예

| 문제 | 반영 |
|---|---|
| 선 그리기 게임이 정밀하게 그려야만 이김 | 정답 선을 흔들어도 이기는지 검사를 생성기와 테스트에 넣음. 못 넘던 67판 → 0판 |
| 줄 자르기의 정답 순간이 너무 짧음 | 초반 레벨 정답 창을 0.6~0.8초 이상으로 재생성 |
| 같은 단계 안에서 난이도가 들쭉날쭉 | 10판 단계 안에서 "생각 없이 해서 이기는 비율" 높은 → 낮은 순으로 재정렬, 단계 끝 판을 보스로 |
| 무한모드 점수를 클라이언트가 보냄 | 판 시작 시각을 서버가 기록하고, 판당 최소 시간을 서버가 검사 |
| 게임 화면에 이모지가 섞여 있음 | 그림으로 바꿔 32종 게임 화면 이모지 0개 |

### 6.4 한계

QA는 데스크톱 크롬의 모바일 에뮬레이션으로 했다. 헤드리스라 소리를 사람 귀로 듣지 못했고, 실제 폰의 터치감·진동·저사양 성능은 아직 확인하지 못했다.

## 7. IP 위험 점검

콘셉트가 "광고에서 본 그 퍼즐"이라서, 출시 전에 저작권·상표·부정경쟁 위험을 따로 점검했다.

### 7.1 점검한 것

| 영역 | 기준 |
|---|---|
| 게임 이름 | 기존 게임 이름과 같거나 비슷하면 바꿈. 장르 이름 + 자체 캐릭터 이름으로 |
| 마케팅 문구 | 다른 게임 이름을 어디에도 쓰지 않음. 장르 이름("핀 뽑기", "물 정렬")만 |
| 규칙 조합 | 규칙 하나하나는 아이디어지만, **규칙을 고르고 묶은 방식**은 보호받을 수 있다는 판례를 기준으로 원작과 조합이 너무 가까운 게임을 찾음 |
| 외형 | 보드 비율·색·버튼 배치가 원작과 같지 않게 |
| 그림·소리·폰트 | AI 그림은 사람이 고친 기록을 남기고, 소리는 전부 자체 합성, 폰트는 오픈 라이선스 |
| 클린룸 | 원작 화면을 옆에 띄워 놓고 만들지 않음. 레벨은 생성기로 |

### 7.2 바꾼 것

- **게임 이름 11개**를 바꿨다 (예: Coco's Pins, Leo's Flood, Bibi's Hive, Paper Swap). 자체 캐릭터 이름이나 앱만의 단어(종이 공작 그림체 → Paper)를 넣었다. 주소(slug)는 그대로 둬서 저장 기록과 랭킹이 끊기지 않았다.
- **규칙 2개**를 바꿨다:
  - 헥사 정렬: "꽃 칸" 기믹 추가 — 꽃 칸 위에서 10장이 터져야 꽃이 피고, 목표는 꽃 전부 피우기.
  - 컨베이어 픽셀 사격: 대기칸을 없애고, 쏠 색이 없는 대포가 벨트를 차지하는 규칙으로.
- 바꾼 게임은 기획서에 "원작과 다른 점" 목록을 남겼다.
- 신고가 들어왔을 때의 절차(그 게임만 숨김 → 검토 → 고치거나 삭제)를 정해 두었다. 게임별 숨김 스위치는 앱 포장 때 넣는다.

## 8. 배포

- 웹은 Vercel, 백엔드(인증·DB)는 Supabase.
- 서버 런타임 의존이 없는 정적 빌드라 Vercel 설정이 단순하다.
- DB 변경은 마이그레이션 파일로 관리한다 (스키마·RLS·RPC 3개 파일).
- 로그인은 선택이다. 첫 방문 때 로그인 카드가 뜨지만 "로그인 없이 하기"를 고르면 다시 묻지 않는다 (앱 심사 기준에 맞춤).

## 9. 회고

### 9.1 잘 된 것

- **규칙을 순수 함수로, 테스트를 화면보다 먼저.** 3,200레벨을 사람이 다 풀어 볼 수는 없다. 자동 증명 덕분에 레벨을 재생성·재정렬하는 큰 변경도 겁 없이 할 수 있었다.
- **결정론 하나로 여러 기능.** 되돌리기, 솔버 검증, 테스트, 서버 점수 검증이 모두 "같은 입력 = 같은 결과"에서 나왔다.
- **같은 형식의 문서.** 기획서 목차, 지침 문서, 기록 CSV 열을 고정해 두니 세션이 바뀌어도 이어받기가 쉬웠고 합치기가 기계적이었다.
- **라운드형 QA.** 평가 → 반영 → 보류 재조정을 ID로 이어서, "지적된 것 중 무엇이 남았나"를 언제든 셀 수 있었다.

### 9.2 아쉬운 것

- 그림을 나중에 넣어서, 처음엔 이모지로 채운 자리를 다시 찾아 바꾸는 라운드가 두 번 필요했다.
- 소리도 처음엔 공용 3개뿐이라 1차 평가에서 32종 모두 P1으로 지적됐다. 장르별 소리를 처음부터 기획서 단계에 넣었으면 한 라운드를 줄였을 것이다.
- 사람 손으로 하는 실기기 테스트가 아직 없다.

4. 무한모드를 실행 중 레벨 생성으로 바꾸기
