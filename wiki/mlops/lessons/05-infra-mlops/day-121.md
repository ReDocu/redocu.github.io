## ② 왜 필요한가

Day 119의 실습 노트를 다시 펴 보세요. 컨테이너 둘을 올리는 데 명령이 몇 줄이었습니까:

```bash
docker network create mp3-net
docker volume create ...        # (postgres run의 -v가 대신했지만)
docker run -d --name mp3-db --network mp3-net -e POSTGRES_PASSWORD=... -e POSTGRES_DB=shop -v mp3-pgdata:/var/lib/... postgres:16
docker run -d --name mp3 --network mp3-net -p 8000:8000 ...
```

이 **명령의 역사**가 지금 서버 상태의 유일한 기록입니다. 문제는:

- 팀원이 같은 구성을 만들려면? — 이 역사를 순서대로, 옵션 하나 안 틀리고 재연해야 합니다.
- 한 달 뒤의 나는? — "-e가 뭐뭐였더라"를 셸 히스토리에서 고고학 발굴.
- 리뷰는? — 명령은 PR에 올릴 수 없습니다. 실행되고 사라지니까.

W23에서 절차를 스크립트로(Day 115), 환경을 Dockerfile로(Day 117) 코드화했듯, 오늘은
**구성(무엇을 어떻게 연결해 띄우나)** 을 코드화합니다. 도구가 Docker Compose이고, 산출물은
`compose.yaml` 파일 하나 — 이 파일이 저장소에 들어가는 순간, 서비스 구성도 리뷰(PR)와 버전
관리(Git)의 대상이 됩니다. 그리고 이번 주 금요일의 목표가 이 파일로 달성됩니다:
**clone 직후 `docker compose up` 만으로 전체 서비스가 뜨는가.**

## ③ 개념 설명

### 명령형에서 선언형으로

| | 명령형 (imperative) | 선언형 (declarative) |
|---|---|---|
| 말하는 것 | **어떻게** — 절차를 순서대로 | **무엇** — 원하는 최종 상태 |
| 예 | "network 만들고, db 띄우고, api 띄워" | "이 시스템엔 db와 api가 있고 이렇게 연결된다" |
| 재실행하면 | 중복 실행·순서 실수 위험 | 도구가 현재 상태와 비교해 **차이만 조정** |
| 기록 | 셸 히스토리 (휘발) | 파일 (Git·리뷰 가능) |

Compose에게 여러분은 절차를 지시하지 않습니다 — 상태를 선언하면, up이 알아서 "없으면 만들고,
다르면 고치고, 같으면 둡니다". `datapipe run` 의 멱등성([Day 043](../02-sql-pipeline/day-043.md))과
같은 감각이 인프라에 온 것입니다.

### compose.yaml 해부 — 3대 항목

```yaml
services:          # 컨테이너들 — "무엇을 돌리나"
  api:
    build: .                    # 이 폴더의 Dockerfile로 빌드 (또는 image: 로 기성품)
    ports: ["8000:8000"]        # -p 의 선언판
    environment: ...            # -e 의 선언판
    depends_on: [db]            # 기동 순서 힌트 (완전한 답은 Day 123)
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]   # -v 의 선언판

volumes:           # named volume 들 — "상태를 어디 보관하나"
  pgdata:

networks:          # (생략 가능) — 생략하면 전용 네트워크 자동 생성
```

읽는 법은 지난 2주의 번역입니다 — run 옵션 하나하나가 YAML 항목 하나로 대응됩니다. 그리고
공짜 선물: Compose는 프로젝트마다 **사용자 정의 네트워크를 자동 생성**하고 모든 서비스를
태웁니다 — Day 119의 `network create` 가 사라지고, **서비스 이름이 곧 호스트명**이 됩니다
(`db:5432` 로 접속).

### 일상 동사

| 명령 | 하는 일 |
|---|---|
| `docker compose up -d` | 선언된 상태로 만들기 (빌드·생성·기동) |
| `docker compose down` | 이 구성의 컨테이너·네트워크 정리 (**볼륨은 남김**) |
| `docker compose ps / logs -f [서비스]` | 이 구성만의 목록 / 로그 |
| `docker compose up -d --build` | 이미지 재빌드 포함 (코드 수정 반영 — ⑤) |
| `docker compose restart api` | 특정 서비스만 재시작 |

### Step 1. 첫 compose.yaml — 어제의 상태를 선언으로 (1~3교시)

`/opt/mlops-mp3` 에 (브랜치 `feature/compose` 에서) `compose.yaml`:

```yaml
services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql+psycopg://mp3:mp3pass@db:5432/mp3
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: mp3
      POSTGRES_PASSWORD: mp3pass        # 평문?! — 내일 수술 예정
```

### Step 2. DB에게 일 주기 — 예측 로그 적재 (4~6교시)

지금 DB는 승객일 뿐 일이 없습니다. MP3의 실제 요구를 연결합니다 — [Day 098](../04-deep-learning-serving/day-098.md)에서
파일(stdout)로 남기던 **예측 로그를 DB에도 적재**해서, W27의 모니터링([Day 134](day-134.md))이
SQL로 집계할 수 있게 합니다. `app/predlog.py` 를 추가:

```python
# app/predlog.py — 예측 로그의 DB 적재 (없으면 조용히 꺼짐: DATABASE_URL 미설정 = 로컬 개발)
import os
from datetime import datetime, timezone

from sqlalchemy import create_engine, text

_url = os.environ.get("DATABASE_URL")
engine = create_engine(_url, pool_pre_ping=True) if _url else None

DDL = """CREATE TABLE IF NOT EXISTS prediction_log (
    id bigserial PRIMARY KEY,
    ts timestamptz NOT NULL,
    label text NOT NULL,
    confidence double precision NOT NULL,
    model_version text NOT NULL,
    elapsed_ms double precision NOT NULL
)"""


def init() -> None:                      # lifespan에서 1회 (Day 096의 그 자리)
    if engine:
        with engine.begin() as conn:
            conn.execute(text(DDL))


def write(label: str, confidence: float, model_version: str, elapsed_ms: float) -> None:
    if not engine:
        return
    with engine.begin() as conn:
        conn.execute(text("INSERT INTO prediction_log (ts, label, confidence, model_version, elapsed_ms) "
                          "VALUES (:ts, :label, :conf, :ver, :ms)"),
                     {"ts": datetime.now(timezone.utc), "label": label,
                      "conf": confidence, "ver": model_version, "ms": elapsed_ms})
```

lifespan에서 `predlog.init()`, service의 예측 반환 직전에 `predlog.write(...)` 한 줄씩 —
W10의 SQLAlchemy가 그대로라 낯설 게 없습니다 (requirements.txt에 `sqlalchemy` 와 `psycopg[binary]`
추가). 재빌드·재기동 후 검증:

```bash
docker compose up -d --build
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8000/predict > /dev/null
curl -s -F "file=@tests/data/bee_sample.jpg" localhost:8000/predict > /dev/null
docker compose exec db psql -U mp3 -d mp3 -c "SELECT label, confidence, model_version FROM prediction_log ORDER BY id;"
```

```
$ docker compose exec db psql -U mp3 -d mp3 -c "SELECT label, confidence, model_version FROM prediction_log ORDER BY id;"

-------+------------+---------------------

(2 rows)
```

예측이 SQL로 조회됩니다 — 0.7214와 0.7694, [Day 100](../04-deep-learning-serving/day-100.md)의
그 대조값들이 이제 **테이블의 행**입니다. W27에서 이 테이블로 "입력 분포가 변했는가"를 묻게
됩니다.

## ⑤ 자주 하는 실수

### YAML 들여쓰기에 탭

**증상** —
```
yaml: line 5: found character that cannot start any token
```
**원인** — YAML은 **탭을 금지**합니다. 스페이스만, 형제끼리 같은 깊이.
**해결** — 에디터를 "탭 → 스페이스 2칸" 설정으로. 파이썬에서 IndentationError를 졸업한
여러분이라 낯설지 않을 겁니다 — 같은 병의 YAML판입니다.

### ports를 따옴표 없이 쓰다 시간으로 해석됨

**증상** — `ports: [60:60]` 같은 항목이 이상한 값으로 — YAML이 `60:60` 을 **60진법 시간**으로
해석하는 고전 함정.
**원인** — 콜론 포함 값의 무따옴표 표기.
**해결** — 포트 매핑은 습관적으로 따옴표: `"8000:8000"`. 오늘 파일이 전부 그렇게 쓰인 이유입니다.

### 코드를 고쳤는데 up을 해도 그대로

**증상** — service.py 수정 → `docker compose up -d` → 응답은 옛날 코드.
**원인** — up은 **이미지가 이미 있으면 재빌드하지 않습니다.** 이미지는 빌드 시점의 스냅샷
(Day 119 Q3의 그 원리)이고, 코드 수정은 이미지 밖의 사건입니다.
**해결** — 코드 반영은 `docker compose up -d --build`. "빌드는 명시적으로"가 규칙입니다 —
W26에서는 이 빌드가 CI의 일이 되어 혼동 자체가 사라집니다.

### down -v 를 습관처럼

**증상** — "깨끗하게 내린다"고 늘 `docker compose down -v` — 예측 로그·DB가 매번 초기화.
어느 날 운영에서 같은 손버릇 → 데이터 전멸.
**원인** — `-v` 는 **볼륨(상태)까지 삭제**하는 옵션인데 정리 옵션쯤으로 오해.
**해결** — 기본은 down (상태 보존). `-v` 는 "이 상태를 버린다"는 **의도적 결정**일 때만 —
치기 전에 psql로 뭐가 들었는지 한 번 보는 버릇이 안전망입니다 (Day 119 prune과 같은 계열).

### 서비스 이름과 컨테이너 이름을 혼동

**증상** — `docker logs api` → `Error: No such container: api`.
**원인** — 컨테이너 실명은 `mlops-mp3-api-1` (프로젝트 접두). `api` 는 Compose 안의 서비스
이름입니다.
**해결** — Compose 세계에선 Compose 동사로: `docker compose logs api`, `docker compose exec api bash`.
(단, **네트워크 안에서의 호스트명**은 서비스 이름 `api`/`db` 그대로입니다 — 바깥 명령과 안
통신의 이름이 다른 것뿐입니다.)

### environment에 시크릿을 평문으로 (오늘의 우리!)

**증상** — compose.yaml의 `POSTGRES_PASSWORD: mp3pass` — 이 파일은 PR로 올라가 저장소에
영구 기록됩니다. [Day 109](day-109.md)의 그 사고를 **구성 파일로** 저지르는 중.
**원인** — 편의. 그리고 "실습이니까"의 관성.
**해결** — 오늘만 유예된 기술 부채입니다. 내일(Day 122) .env 분리와 주입 구조로 전면 수술
합니다 — 오늘 PR 리뷰에서 짝이 이 줄에 [must]를 달았다면, 그 짝은 이번 주 수업을 다 이해한
겁니다.

## ⑥ 확인 문제

**Q1.** "Compose는 절차가 아니라 상태를 선언한다"를, `docker compose up -d` 를 **연속 두 번**
실행했을 때의 동작으로 설명하세요.

<details>
<summary>답 보기</summary>

첫 up은 선언과 현실의 차이(아무것도 없음)를 메우려 네트워크·컨테이너를 만듭니다. 두 번째 up은
현실이 이미 선언과 일치하므로 **아무것도 하지 않습니다** (출력: Running... 모두 초록, 재생성
없음). 명령형 스크립트였다면 두 번째 실행에서 "이미 존재함" 에러나 중복이 났을 것 — 선언형
도구는 멱등이라 "몇 번 실행해도 같은 최종 상태"가 보장됩니다. 구성 파일을 고친 뒤의 up도 같은
원리로 바뀐 서비스만 재생성합니다.

</details>

**Q2.** compose.yaml에서 db 서비스에 ports를 주지 않았는데 API는 잘 붙습니다. 그런데 팀원이
"DBeaver로 이 DB를 봐야 한다"고 합니다. 두 요구(내부 전용 유지 vs 조회 편의)를 절충하는 방법을
제시하세요.

<details>
<summary>답 보기</summary>

임시 조회라면 포트를 여는 대신 `docker compose exec db psql -U mp3 -d mp3` 로 컨테이너 안에서
직접 — 노출 없이 해결됩니다. 상시 GUI가 꼭 필요하면 `ports: ["127.0.0.1:5432:5432"]` 처럼
**호스트의 루프백에만** 바인딩해 같은 기계의 DBeaver만 접속 가능하게 절충합니다 (외부망 차단
유지). 무조건 "5432:5432"로 여는 것은 내부 전용 설계(Day 119 Q2)를 무너뜨리는 최후의 선택지입니다.

</details>

**Q3.** 오늘 예측 로그를 stdout(JSON, Day 098)과 DB(prediction_log) **양쪽**에 남기게 됐습니다.
중복일까요? 각각의 소비자와 용도를 구분해 정당화해 보세요.

<details>
<summary>답 보기</summary>

소비자가 다릅니다. stdout 로그는 **운영 이벤트의 흐름** — docker logs/journal로 수집되어 장애
조사("그 시각에 무슨 일이"), 에러 추적의 재료입니다 (플랫폼이 수집을 담당 — Day 113·116).

버전별 비교(Day 134의 드리프트 감지)를 만드는 재료입니다. 전자는 "시스템이 건강한가", 후자는
"모델이 건강한가"에 답합니다 — 형식과 보존 기간도 달라, 중복이 아니라 역할 분담입니다.
