## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **볼륨과 바인드 마운트**를 구분하고, "컨테이너보다 오래 살아야 하는 것"을 올바른 곳에 둘 수 있다.
- DB 컨테이너를 지웠다 다시 만들어도 **데이터가 생존**함을 실험으로 증명할 수 있다.
- 사용자 정의 **네트워크**에서 컨테이너들이 **이름으로** 서로를 찾게 할 수 있다.
- 컨테이너 안의 `localhost` 가 왜 함정인지 설명하고, 그 사고를 스스로 재현·수리할 수 있다.

## ② 왜 필요한가

어제 과제의 질문 — "컨테이너보다 오래 살아야 하는 것"의 목록을 뽑아 보셨습니까? MP3 기준으로:

| 오래 살아야 하는 것 | 컨테이너 안에 두면 |
|---|---|
| DB 데이터 (shop·수집 데이터·예측 로그) | `docker rm` 한 방에 **석 달치 증발** |
| 학습된 모델의 새 버전 | 배포마다 리셋 |
| 수집 파이프라인의 산출 파일 | cron이 돌 때마다 리셋 |

컨테이너의 미덕(일회용·불변·언제든 갈아 끼움)과 데이터의 요구(영속)가 정면충돌합니다.
해법은 분리입니다 — **계산은 일회용 컨테이너가, 상태는 컨테이너 밖(볼륨)이.** 사실 여러분의
shop DB가 석 달을 산 것도 W07의 그 `-v mlops-pgdata:...` 덕분이었습니다. 오늘 그 안전망의
원리를 확인하고, 반대로 안전망이 **없으면** 무슨 일이 나는지도 일부러 겪습니다.

두 번째 주제는 통신입니다. 컨테이너가 둘 이상이 되는 순간(오늘: 수집기+DB, 다음 주:
nginx+API+DB) "쟤를 어떻게 부르지?"가 문제가 됩니다 — 격리된 세상끼리는 localhost가 통하지
않으니까요. 답은 도커의 네트워크와 **이름 기반 통신**이고, 이것이 다음 주 Compose를 읽는
문해력의 절반입니다.

## ③ 개념 설명

### 볼륨 vs 바인드 마운트 — 관리자가 누구인가

둘 다 "컨테이너 밖의 저장 공간을 안에 접붙이는" 것이고, 차이는 그 공간을 누가 관리하느냐입니다:

| | **볼륨 (named volume)** | **바인드 마운트 (bind mount)** |
|---|---|---|
| 형태 | `-v 이름:/컨테이너/경로` | `-v /호스트/경로:/컨테이너/경로` |
| 관리자 | **Docker** (호스트 어딘가 — 알 필요 없음) | **나** (내가 지정한 실제 폴더) |
| 주 용도 | **운영 데이터** (DB·로그·모델) | **개발 편의** (코드 즉시 반영·설정 주입) |
| 이식성 | 높음 (경로 무관) | 낮음 (그 호스트의 그 경로에 종속) |
| 목록/삭제 | `docker volume ls / rm` | 그냥 폴더 |

기준 문장: **서비스의 상태는 볼륨에, 개발 중의 내 파일은 바인드로.**

### 컨테이너 네트워크 — 이름이 주소다

`docker network create net이름` 으로 사용자 정의 네트워크를 만들고 컨테이너들을 거기 붙이면,
**컨테이너 이름이 곧 호스트명(DNS)** 이 됩니다:

```
[mp3-net 네트워크]
  mp3-db      ◀── "mp3-db:5432" 로 접속 ──  datapipe / API
  mp3-api     ◀── "mp3-api:8000"        ──  (다른 컨테이너)
```

세 가지 규칙이 오늘의 전부입니다:

1. **같은 네트워크 안**끼리는 `이름:포트` 로 통신 — `-p` 필요 없음 (내부 통신)
2. `-p` 는 **바깥세상(호스트 밖)** 에 공개할 때만 — DB처럼 내부 전용이면 안 다는 게 보안상 옳음
3. 컨테이너 안에서 `localhost` 는 **그 컨테이너 자신** — 호스트도, 옆 컨테이너도 아님

3번이 이 주간 최다 사고 지점입니다. 격리(Day 116 실험 B)의 당연한 귀결인데, 습관이 격리를
이깁니다 — 오늘 일부러 부딪혀 봅니다.

## ④ 단계별 실습

### Step 1. 볼륨 없는 DB의 최후, 볼륨 있는 DB의 생존 (1~3교시)

**A. 안전망 없이.** 볼륨 없는 PostgreSQL에 데이터를 넣고, 컨테이너를 교체해 봅니다:

```bash
docker run -d --name db-naked -e POSTGRES_PASSWORD=test postgres:16
docker exec -it db-naked psql -U postgres -c "CREATE TABLE t (msg text); INSERT INTO t VALUES ('소중한 데이터');"
docker rm -f db-naked
docker run -d --name db-naked -e POSTGRES_PASSWORD=test postgres:16
sleep 3; docker exec -it db-naked psql -U postgres -c "SELECT * FROM t;"
```

```
$ docker exec -it db-naked psql -U postgres -c "SELECT * FROM t;"
ERROR:  relation "t" does not exist
LINE 1: SELECT * FROM t;
```

테이블째 증발 — Day 116 실험 A(컨테이너는 일회용)의 데이터베이스판입니다. `docker rm -f db-naked` 로 정리.

**B. 볼륨과 함께.** 같은 실험을 named volume으로:

```bash
docker volume create pg-lab
docker run -d --name db-safe -e POSTGRES_PASSWORD=test -v pg-lab:/var/lib/postgresql/data postgres:16
sleep 3; docker exec -it db-safe psql -U postgres -c "CREATE TABLE t (msg text); INSERT INTO t VALUES ('소중한 데이터');"
docker rm -f db-safe
docker run -d --name db-safe -e POSTGRES_PASSWORD=test -v pg-lab:/var/lib/postgresql/data postgres:16
sleep 3; docker exec -it db-safe psql -U postgres -c "SELECT * FROM t;"
```

```
$ docker exec -it db-safe psql -U postgres -c "SELECT * FROM t;"
      msg
----------------
 소중한 데이터
(1 row)
```

컨테이너는 두 번째 개체인데 데이터는 첫 개체의 것 — **상태가 컨테이너와 분리**됐습니다.
PostgreSQL 데이터가 `/var/lib/postgresql/data` 에 산다는 걸 알기에 가능한 접붙임이고
(이미지 문서가 알려 줍니다), W07의 주문이 정확히 이 형태였음을 이제 완전히 설명할 수 있습니다.

### Step 2. 바인드 마운트 — 개발 모드의 컨테이너 (4교시)

hello-api(어제 것)로 개발 편의를 체험합니다 — 코드를 이미지에 굽지 않고 접붙이면:

```bash
cd ~/lab/hello-api
docker run -d --name hello-dev -p 8000:8000 -v "$PWD":/app hello-api:0.1 \
  uvicorn main:app --host 0.0.0.0 --port 8000 --reload
sed -i 's/"status": "ok"/"status": "ok", "mode": "dev"/' main.py
curl -s localhost:8000/health
```

```
$ curl -s localhost:8000/health
{"status":"ok","mode":"dev","from":"container"}
```

호스트에서 고친 코드가 **재빌드 없이** 즉시 반영됩니다 (--reload가 파일 변경을 감지).
운영에서는 금물이지만(이미지 = 불변의 족보라는 원칙이 깨짐), 개발 루프에서는 표준 기법입니다 —
"운영은 굽고(COPY), 개발은 접붙인다(bind)"로 정리하세요. `docker rm -f hello-dev` 정리.

### Step 3. 네트워크 — 수집기가 DB를 이름으로 찾는다 (5~6교시)

W07~W10의 구성을 컨테이너 두 개로 재현합니다 — 어제 과제로 만든 `datapipe:0.1` 이미지가
DB 컨테이너에 적재하는 그림:

```bash
docker network create mp3-net
docker run -d --name mp3-db --network mp3-net \
  -e POSTGRES_PASSWORD=mlops1234 -e POSTGRES_DB=shop \
  -v mp3-pgdata:/var/lib/postgresql/data postgres:16
```

`-p` 가 **없다**는 점을 보세요 — 이 DB는 바깥에 공개되지 않습니다. 같은 네트워크의 이웃만
접근 가능 (W23에서 배운 "내부 전용은 조인다"의 컨테이너식 구현). 이제 수집기를 같은 네트워크에
태워, DB 주소를 **이름으로** 주입합니다:

```bash
docker run --rm --network mp3-net \
  -e DATAPIPE_DB_HOST=mp3-db -e DATAPIPE_DB_PASSWORD=mlops1234 \
  datapipe:0.1
```

```
$ docker run --rm --network mp3-net -e DATAPIPE_DB_HOST=mp3-db -e DATAPIPE_DB_PASSWORD=mlops1234 datapipe:0.1
[2026-08-19 11:42:07] INFO  run 시작 (config: 환경 변수 병합)
[2026-08-19 11:42:09] INFO  fetch=ok(184건) clean=ok save=ok → db=mp3-db:5432/shop
[2026-08-19 11:42:09] INFO  run 완료 (2.3s)
```

`mp3-db` 라는 호스트명이 그대로 통했습니다 — 사용자 정의 네트워크의 이름 해석입니다.
확인 사살:

```bash
docker exec -it mp3-db psql -U postgres -d shop -c "SELECT count(*) FROM air_quality_raw;"
```

```
 count
-------
   184
(1 row)
```

일하고 사라지는 컨테이너(--rm 수집기)와 상태를 지키는 볼륨(mp3-pgdata), 그 사이의 이름 기반
통신 — **다음 주 Compose가 자동화할 그림을 오늘 손으로 완성**했습니다.

### Step 4. localhost 함정 — 일부러 빠지기 (7교시)

주입 값을 습관대로 바꿔 봅니다:

```bash
docker run --rm --network mp3-net \
  -e DATAPIPE_DB_HOST=localhost -e DATAPIPE_DB_PASSWORD=mlops1234 \
  datapipe:0.1
```

```
[2026-08-19 11:51:33] ERROR fetch 이후 save 실패: connection to server at "localhost" (127.0.0.1), port 5432 failed: Connection refused
        Is the server running on that host and accepting TCP/IP connections?
```

컨테이너 안의 localhost는 **자기 자신** — 수집기 컨테이너 안에는 PostgreSQL이 없으니
refused(듣는 프로세스 없음 — [Day 114](day-114.md)의 그 진단)입니다. 에러 문구를 눈에
새겨 두세요. 다음 주 Compose에서 누군가는 반드시 이 문구를 다시 만나고, 여러분은 3초 만에
"host를 서비스 이름으로" 라고 답하게 될 겁니다.

## ⑤ 자주 하는 실수

### DB 컨테이너를 볼륨 없이 운영

**증상** — 디스크 정리하다 `docker rm` — 몇 주치 데이터 전멸. 백업? 없음.
**원인** — "컨테이너가 곧 DB"라는 착각. 컨테이너는 계산기이고 데이터는 별도 존재여야 합니다.
**해결** — 상태 있는 컨테이너(DB·모델 저장소·로그 수집기)는 **볼륨이 계약 조건**입니다.
`docker inspect 컨테이너 | grep -A5 Mounts` 로 지금 도는 것들의 안전망을 점검하는 습관을 —
그리고 볼륨이 있어도 백업은 별개 문제라는 것도 (덤프는 W25 운영 리뷰에서).

### 바인드 마운트 경로 오타 — 조용한 빈 폴더

**증상** — `-v /opt/mlops-mp3/model:/app/models` (models의 s 누락) — 에러 없이 뜨는데 앱은
`FileNotFoundError`.
**원인** — 호스트에 없는 경로를 바인드하면 Docker가 **빈 폴더를 만들어서** 마운트합니다.
오타가 에러가 아니라 빈 방이 되는 것.
**해결** — 기동 후 `docker exec 컨테이너 ls /app/models` 로 내용 확인을 절차에 포함.
경로는 변수로 한 곳에서 관리 — 다음 주 Compose 파일이 그 "한 곳"이 됩니다.

### 컨테이너 간 통신에 localhost

**증상** — Step 4의 그 refused. 변형: 호스트의 서비스에 접속하려고 localhost.
**원인** — 컨테이너 안의 localhost = 자기 자신 (격리의 귀결).
**해결** — 옆 컨테이너는 **같은 네트워크 + 이름**으로. (호스트 자체에 접속해야 하는 특수한
경우엔 `host.docker.internal` 이라는 특별 이름이 있습니다 — 다만 그게 필요해 보인다면 대개
그 서비스도 컨테이너로 들이는 게 맞는 설계입니다.)

### 기본 bridge 네트워크에서 이름 호출

**증상** — network create 없이 띄운 컨테이너끼리 `mp3-db` 를 못 찾음:
```
could not translate host name "mp3-db" to address: Name or service not known
```
**원인** — **기본** bridge 네트워크는 이름 해석(DNS)을 제공하지 않습니다. 이름 통신은
**사용자 정의** 네트워크의 기능입니다.
**해결** — `docker network create` 후 `--network` 로 합류. 다음 주부터는 Compose가 프로젝트마다
전용 네트워크를 자동 생성해 줘서 이 실수 자체가 사라집니다 — 오늘 원리를 아는 것이 목적입니다.

### docker volume prune의 학살

**증상** — 청소한다고 `docker volume prune -f` — 정지된 DB 컨테이너의 볼륨까지 삭제.
**원인** — prune은 "지금 어떤 컨테이너에도 붙어 있지 않은" 볼륨을 지웁니다 — 잠깐 컨테이너를
지워 둔 상태의 소중한 볼륨도 그 기준에 걸립니다.
**해결** — 볼륨 삭제는 개별(`docker volume rm 이름`)로, prune은 목록(`docker volume ls`)을
읽고 나서. 운영 서버에서 `-f` 옵션은 손가락 봉인 대상입니다.

<details>
<summary>답 보기</summary>

`-p` 는 호스트 바깥으로의 공개이고, 같은 사용자 정의 네트워크 안의 컨테이너끼리는 내부
네트워크로 직접 통신합니다(mp3-db:5432 이름 해석). 수집기는 내부 경로로 접속했으므로 공개가
필요 없었습니다. 이점: DB가 호스트 밖 어디에서도 접근 불가 — 포트 스캔·무차별 대입의 대상에서
아예 빠집니다. W23의 "내부 전용은 127.0.0.1로 조인다"와 같은 원칙의 컨테이너식 표현이며,
다음 주 nginx만 -p를 갖는 3단 구성으로 완성됩니다.

</details>

**Q3.** "운영은 굽고(COPY), 개발은 접붙인다(bind)" — 각각의 이유를 재현성 관점에서 설명하고,
운영 컨테이너에 코드를 bind 마운트하면 무엇이 깨지는지 쓰세요.

<details>
<summary>답 보기</summary>

운영에서 이미지는 "태그 = 코드+환경의 불변 스냅샷"이라는 족보 역할을 합니다 — 굽기(COPY) 덕에
`mlops-mp3:0.1.0` 을 실행하면 언제 어디서든 같은 코드가 돕니다. 개발에서는 수정→확인 루프의
속도가 우선이라 bind+--reload가 맞습니다. 운영에 bind를 쓰면 "지금 도는 코드"가 호스트 폴더의
현재 상태에 종속되어 — 태그는 0.1.0인데 실제 코드는 아무도 모르는 상태 — 이미지 태그의 족보가
무효화됩니다. 재현 불가능한 장애("그 서버만 이상해요")의 전형적 원인입니다.

</details>
