## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 부하 도구로 **지연(p50/p95)과 처리량**을 측정하고, 서버의 **포화점**을 찾을 수 있다.
- **배치 추론**이 왜 빠른지, 그리고 어떤 모델에서 극적인지 실측으로 설명할 수 있다.
- **캐시**를 적용해도 되는 조건을 판단하고 `lru_cache`로 구현할 수 있다.
- **워커(프로세스 복제)**의 효과와 한계를 설명할 수 있다 — "늘리면 빨라진다"가 왜 틀린 말인지.

## ② 왜 필요한가

어제까지의 서버는 사실 **손님이 한 명**이었습니다. 내일 아침 출근길, 수천 명이 동시에
"오늘 미세먼지 어때?"를 물으면 무슨 일이 일어날까요? — 모릅니다. **재 본 적이 없으니까요.**

성능 작업의 최대 함정은 감으로 하는 최적화입니다:

```
"일단 async로 바꾸자"     → Day 094에서 이미 봤듯, 오히려 5.1초짜리 참사가 될 수 있음
"워커를 8개로 늘리자"     → 오늘 실측: 우리 서버에선 처리량이 1도 안 늘어남
"캐시를 붙이자"           → 입력이 매번 다른 API라면 히트율 0%
```

그래서 오늘의 루프는 **측정 → 병목 확인 → 개선 1개 → 재측정**입니다. MP3 평가 기준에
"서비스 평가: p95 지연시간 · 처리량"이 명시되어 있고([커리큘럼](../../curriculum/04-deep-learning-serving.md)),
그 숫자를 만드는 방법이 오늘 수업입니다.

## ③ 개념 설명

### 지연과 처리량은 다른 것이다

| | 지연 (latency) | 처리량 (throughput) |
|---|---|---|
| 질문 | 요청 **하나**가 얼마나 기다리나 | 초당 **몇 건**을 처리하나 |
| 단위 | ms (p50/p95 — [Day 098](day-098.md)) | req/s |
| 식당 비유 | 내 주문이 나오기까지 | 시간당 손님 수 |

둘은 함께 움직이지 않습니다. 동시 접속을 늘리면 **처리량은 천장에 닿고, 지연만 늘어납니다** —
주방(CPU)은 이미 풀가동인데 손님만 늘어난 식당의 대기줄입니다. 처리량이 더 늘지 않기 시작하는
지점이 **포화점**이고, 오늘 실측으로 우리 서버의 포화점을 직접 찾습니다.

### 성능의 세 지렛대

| 지렛대 | 원리 | 효과 조건 |
|---|---|---|
| **배치** | 모아서 한 번에 — 건당 오버헤드를 분산 | 건당 고정 비용(함수 호출·검증·프레임워크 오버헤드)이 큰 모델일수록 극적 |
| **캐시** | 같은 질문에는 계산 없이 같은 답 | **같은 입력이 반복**될 때만 (히트율이 전부) |
| **워커/스레드** | 하드웨어를 더 쓴다 (프로세스 복제) | **코어가 놀고 있을 때만** — 이미 포화면 무효 |

셋 다 공짜가 아닙니다: 배치는 지연을 처리량과 맞바꾸고, 캐시는 무효화 책임이 생기고,
워커는 메모리(모델 사본 × N)를 먹습니다. 그래서 **측정이 먼저**입니다.

### 부하 도구

전문 도구(locust, k6 등)가 많지만, 오늘은 [Day 094](day-094.md)의 httpx로 **직접 만듭니다** —
40줄이면 충분하고, "동시성 c로 n건"이 코드로 보이는 것이 교육적으로 더 낫습니다.
(도구가 무엇이든 보고할 숫자는 같습니다: 동시성별 p50 · p95 · req/s.)

## ④ 단계별 실습

### Step 1. 부하 측정기와 베이스라인 (1~2교시)

측정 대상은 [Day 085](day-085.md)의 이미지 분류 모델(ResNet18)입니다 — MP2 파이프라인(예측
2ms)보다 무거워서(순전파 ~21ms) 부하 실험이 선명합니다. 업로드 처리는 내일 배우므로,
오늘은 부하 재현용 엔드포인트로 측정합니다. `serve_image.py` (핵심):

```python
@app.post("/predict-demo")
def predict_demo():
    """CPU 추론 부하 재현용 — 고정 크기 입력으로 순전파 1회 (20ms급 CPU 작업)."""
    x = torch.rand(1, 3, 224, 224)
    with torch.no_grad():
        probs = torch.softmax(state["model"](x), dim=1)[0]
    top = probs.argmax().item()
    return {"label": state["classes"][top], "confidence": round(probs[top].item(), 4)}
```

측정기 `loadtest.py` — 전체가 이것뿐입니다:

```python
# loadtest.py — 소형 부하 측정기: 동시성 c로 n건을 보내 처리량·지연 분위수 측정
import asyncio
import sys
import time

import httpx


async def run(url: str, n: int, c: int):
    latencies = []
    sem = asyncio.Semaphore(c)

    async def one(client):
        async with sem:
            t0 = time.perf_counter()
            r = await client.post(url)
            latencies.append((time.perf_counter() - t0) * 1000)
            assert r.status_code == 200

    async with httpx.AsyncClient(timeout=60) as client:
        t0 = time.perf_counter()
        await asyncio.gather(*[one(client) for _ in range(n)])
        total = time.perf_counter() - t0

    latencies.sort()
    p = lambda q: latencies[int(len(latencies) * q)]
    print(f"동시성 {c:>2} · {n}건: 처리량 {n/total:5.1f} req/s · "
          f"p50 {p(0.50):5.0f}ms · p95 {p(0.95):5.0f}ms")


if __name__ == "__main__":
    url = sys.argv[1]                                        # 사용법: loadtest.py URL [건수] [동시성,동시성,...]
    n = int(sys.argv[2]) if len(sys.argv) > 2 else 80
    cs = [int(c) for c in sys.argv[3].split(",")] if len(sys.argv) > 3 else [1, 4, 8]
    for c in cs:
        asyncio.run(run(url, n=n, c=c))
```

서버를 띄우고(`uvicorn serve_image:app --port 8099`) 워밍업 몇 건 후 측정:

```
$ python loadtest.py http://127.0.0.1:8099/predict-demo
동시성  1 · 80건: 처리량  37.3 req/s · p50    26ms · p95    29ms
동시성  4 · 80건: 처리량  51.4 req/s · p50    77ms · p95    94ms
동시성  8 · 80건: 처리량  48.0 req/s · p50   142ms · p95   343ms
```

**표를 읽는 법** — 이 세 줄이 오늘 수업의 절반입니다:

1. 동시성 1→4: 처리량 37→51 (코어가 남아 있어 조금 늘었지만, 지연도 26→77ms).
2. 동시성 4→8: **처리량은 그대로(≈50 req/s 천장), p50은 142ms로 배가.** 포화점을 지났습니다 —
   추가된 요청은 처리되는 게 아니라 **줄을 서는** 것입니다. p95 343ms가 그 대기줄의 끝입니다.
3. 우리 서버의 용량은 **약 50 req/s**. 이 숫자를 알아야 "충분한가?"를 논할 수 있습니다
   (예상 트래픽이 10 req/s면 끝, 500 req/s면 서버 10대 또는 아래의 지렛대).

### Step 2. 지렛대 ① 배치 — 모아서 한 번에 (3~4교시)

먼저 서버 없이 순수 추론만 재 봅니다. `bench_batch.py` 실행 결과:

```
== ResNet18 · 64장을 처리하는 두 방법 (CPU) ==
한 장씩 64회:      1332ms  (장당  20.8ms)
배치  8로  8회:    1023ms  (장당  16.0ms)
배치 16로  4회:    1092ms  (장당  17.1ms)
배치 64로  1회:    1004ms  (장당  15.7ms)

== MP2 파이프라인 · 868행(테스트 세트 하루치 시뮬레이션) ==
한 행씩 868회:    1743ms  (행당  2.01ms)
한 번에 868행:       2ms  (행당 0.002ms)
```

같은 "모아서 한 번에"인데 효과가 하늘과 땅입니다:

| 모델 | 개선 | 이유 |
|---|---|---|
| MP2 파이프라인 | **1,000배** (2.01 → 0.002ms) | 행당 2ms의 정체가 거의 전부 **오버헤드**(pandas 생성·검증·파이프라인 단계 호출)였음 — 계산 자체는 행당 2μs |
| ResNet18 (CPU) | 1.3배 (20.8 → 15.7ms) | 순전파가 진짜 **계산 지배**라 이미 torch가 코어를 쓰고 있음. (GPU라면 이 격차가 다시 극적으로 벌어집니다 — 병렬 하드웨어가 놀고 있으므로) |

교훈: **배치의 이득 = 건당 오버헤드의 비중.** 그래서 [Day 068](../03-machine-learning/day-068.md)의
`predict.py`가 CSV를 통째로 받던 것이 옳은 설계였습니다. 서버에도 배치 엔드포인트를 답니다:

```python
@app.post("/predict-demo/batch")
def predict_demo_batch(n: int = 8):
    """배치 추론: n장을 순전파 1회로 — 요청 1번에 결과 n개."""
    x = torch.rand(n, 3, 224, 224)
    with torch.no_grad():
        probs = torch.softmax(state["model"](x), dim=1)
    tops = probs.argmax(dim=1)
    return {"results": [{"label": state["classes"][t.item()],
                         "confidence": round(probs[i, t].item(), 4)}
                        for i, t in enumerate(tops)]}
```

같은 80장을 "8장씩 10요청"으로 보내면:

```
$ python loadtest.py "http://127.0.0.1:8099/predict-demo/batch?n=8" 10 1,2
동시성  1 · 10건: 처리량   7.2 req/s · p50   137ms · p95   144ms
동시성  2 · 10건: 처리량   8.2 req/s · p50   240ms · p95   267ms
```

req/s가 아니라 **장/s로 환산해서** 비교해야 합니다: 7.2 × 8 = **57.6장/s**, 8.2 × 8 = **65.6장/s** —
단건 최고치(51.4장/s)보다 **28% 많은 이미지**를 같은 하드웨어로 처리합니다. 대신 요청 하나의
지연은 137ms(장당 17ms) — **배치는 지연을 내주고 처리량을 얻는 거래**입니다. 실시간 단건
예측에는 부적합하고, "폴더째 분류" 같은 대량 작업에 적합합니다 (MP3의 선택 기능 `/predict/batch`가
정확히 이것입니다).

### Step 3. 지렛대 ② 캐시 — 같은 질문에는 같은 답 (5교시)

우리 예보 API의 트래픽을 상상해 보세요. 아침 8시, 수천 명이 묻는 것은 사실상 **같은 질문**입니다
— 오늘의 관측값은 하나뿐이니까요. 입력이 같으면 답도 같은데 매번 모델을 돌릴 이유가 없습니다.
`serve_cached.py` (핵심):

```python
from functools import lru_cache

@lru_cache(maxsize=4096)
def predict_cached(vals: tuple) -> float:
    """키 = 입력값 전체의 튜플. 같은 입력이 다시 오면 모델을 건너뛴다.
    주의: 모델을 교체하면 반드시 cache_clear() — 옛 모델의 답이 남는다."""
    x = pd.DataFrame([dict(vals)])[state["schema"]["columns"]]
    return float(state["pipe"].predict(x)[0])


@app.post("/predict")
def predict(r: PredictIn):
    pred = predict_cached(tuple(sorted(r.model_dump().items())))
    return {"pm25_next_pred": round(pred, 1), "grade": to_grade(pred),
            "model_version": state["schema"]["run_id"][:8]}


@app.get("/cache/info")
def cache_info():
    i = predict_cached.cache_info()
    return {"hits": i.hits, "misses": i.misses, "size": i.currsize}
```

같은 입력(겨울 정체일) 200회를 캐시 없는 서버([Day 096](day-096.md)의 `serve_pm25`)와 비교:

```
== 캐시 없음 (serve_pm25) ==
응답: {'pm25_next_pred': 43.4, 'grade': '나쁨', 'model_version': '6ac527ba'}
동일 입력 200회: p50 4.2ms · p95 5.4ms
== 캐시 있음 (serve_cached) ==
응답: {'pm25_next_pred': 43.4, 'grade': '나쁨', 'model_version': '6ac527ba'}
동일 입력 200회: p50 0.8ms · p95 1.3ms
== 캐시 통계 ==
{'hits': 200, 'misses': 1, 'size': 1}
```

**5배** 빨라졌고(4.2 → 0.8ms), 캐시 통계가 서사를 그대로 보여 줍니다: 첫 1건만 모델을 돌리고
(misses 1) 나머지 200건은 재활용(hits 200). 모델이 무거울수록 이득도 큽니다 — BERT(순전파
수백 ms)라면 5배가 아니라 수백 배입니다. 단, 두 가지를 반드시 같이 가져가야 합니다:

- **히트율이 전부** — 입력에 타임스탬프·랜덤값이 섞이면 히트율 0%, 캐시는 메모리 낭비가 됩니다.
- **무효화 책임** — 모델을 교체하면 `cache_clear()`. 안 하면 새 모델을 실어 놓고 **옛 모델의
  답을 서빙**하는, 조용하고 지독한 사고가 납니다.

### Step 4. 지렛대 ③ 워커 — 늘리면 빨라질까? (6교시)

uvicorn은 `--workers N`으로 서버 **프로세스를 N개 복제**할 수 있습니다 (각자 모델을 로드하고,
OS가 요청을 분배). 그럼 워커 2면 처리량 2배? — **측정해 봅니다**:

```
$ uvicorn serve_image:app --port 8099 --workers 2
동시성  4 · 80건: 처리량  52.2 req/s · p50    75ms · p95    87ms   ← 워커 1일 때 51.4와 사실상 동일
(동시성 8 측정은 요청 하나가 60초를 넘겨 실패 — 아래 ⑤ 참고)
```

처리량이 **전혀 늘지 않았습니다.** 이유는 Step 1에 이미 있습니다: 워커 1일 때도 torch가
프로세스 안에서 스레드 병렬로 **코어를 이미 다 쓰고 있었습니다**(그래서 50 req/s가 천장).
워커는 프로세스를 복제하지 **CPU 코어를 복제하지 않습니다.** 대신 메모리는 정직하게 2배
(모델 사본 2개)가 됐습니다.

그럼 워커는 언제 쓰나:

| 워커가 효과 있는 경우 | 이유 |
|---|---|
| 파이썬 코드(전처리·직렬화)가 병목 | GIL은 프로세스 단위 — 복제로만 병렬화됨 |
| 추론 스레드를 제한한 운영 환경 | 관례: 워커당 스레드 1~2 × 워커 N — 지연 예측 가능성↑ |
| I/O 대기가 섞인 서버 | 한 워커가 기다리는 동안 다른 워커가 계산 |

다중 워커 운영은 리눅스/컨테이너 환경이 표준이고, **W24에서 컨테이너에 실어 다시 실험**합니다.
오늘의 결론만 기억하세요: **워커 수는 설정이 아니라 측정 결과다.**


**과제 — 병목 분석 리포트.** MP3에서 서빙할 모델(이미지 또는 텍스트)로 오늘의 루프를 한 바퀴
도세요: ① 베이스라인 측정(동시성 1/4/8의 p50·p95·req/s 표) → ② 포화점과 병목 판단(근거 한
문단) → ③ 지렛대 셋 중 **하나만 골라**(선택 이유 포함) 적용 → ④ 재측정 전후 비교표.
"적용해 봤더니 효과가 없었다"도 훌륭한 결론입니다 — 워커 실험처럼, 그것이 측정의 존재 이유입니다.

## ⑤ 자주 하는 실수

### 측정 없이 최적화부터

**증상** — "느린 것 같아서" async로 바꾸고 워커를 늘리고 캐시를 붙였는데 여전히 느림 — 무엇이 효과였는지도 모름.
**원인** — 병목을 모르는 채 지렛대부터 당김.
**해결** — 오늘의 루프: 측정 → 병목 → **개선 1개** → 재측정. 한 번에 하나만 바꿔야 인과를 압니다 ([Day 057](../03-machine-learning/day-057.md)의 실험 규율 그대로).

### 워밍업 없이 첫 요청부터 측정

**증상** — p95가 이상하게 큼 — 알고 보니 첫 요청 하나가 수백 ms.
**원인** — 첫 요청에는 스레드풀 기동·지연 초기화 같은 1회성 비용이 섞입니다.
**해결** — 측정 전 워밍업 몇 건을 버리세요. (반대로 **콜드 스타트 자체를 재는 것**이 목적이면 첫 요청만 따로 보고합니다.)

### 배치 크기를 무한정 키움

**증상** — 처리량을 더 짜내려 배치 512 — p95가 SLA를 넘고, 메모리 폭발, 한 건의 불량 입력이 511건을 같이 죽임.
**원인** — 배치가 지연·메모리·실패 반경을 함께 키우는 거래임을 잊음.
**해결** — 배치 크기도 측정으로: 처리량 곡선이 꺾이는 지점(오늘은 8만 돼도 이득 대부분 확보)에서 멈추고, 지연 상한을 함께 명시.

### 모델 교체 후 캐시를 그대로 둠

**증상** — 새 모델을 배포했는데 일부 응답이 옛 예측값 — 로그의 model_version은 새것이라 더 혼란.
**원인** — 캐시 키에 모델 버전이 없고, 배포 시 cache_clear()도 안 함.
**해결** — 로드 직후 `cache_clear()`를 lifespan에 넣거나, 캐시 키에 run_id를 포함. "캐시를 만들 때 무효화 계획을 같이 쓴다"가 규칙입니다.

### 부하 측정기를 서버와 같은 PC에서 돌리며 숫자를 절대시함

**증상** — 보고서의 처리량이 실제 운영과 다름.
**원인** — 측정기 자신도 CPU를 쓰고(오늘 우리도 같은 PC), localhost는 네트워크 지연이 0입니다.
**해결** — 오늘 숫자는 **구성 간 비교용**으로 읽으세요 (배치 vs 단건, 캐시 유무). 절대 성능 보고는 별도 머신에서 — MP3 보고서에도 측정 환경을 명시합니다.

### 윈도우 개발 PC에서 --workers로 성능 보고서를 씀

**증상** — 오늘 우리 실측처럼, 다중 워커에서 요청 하나가 60초를 넘겨 타임아웃 — 숫자가 요동침.
**원인** — 윈도우의 다중 워커 소켓 분배는 불안정하기로 유명합니다. 워커 운영의 표준 무대는 리눅스입니다.
**해결** — 개발 PC에서는 워커 1로 측정·비교하고, 다중 워커 성능은 W24 컨테이너(리눅스)에서 측정합니다.

## ⑥ 확인 문제

**Q1.** Step 1에서 동시성 4→8일 때 처리량은 51.4→48.0으로 제자리인데 p50은 77→142ms로
거의 2배가 됐습니다. 늘어난 65ms 동안 요청은 무엇을 하고 있었을까요?

<details>
<summary>답 보기</summary>

**줄을 서 있었습니다.** 서버의 처리 용량(~50 req/s)은 그대로인데 동시에 들어오는 요청만 늘었으므로,
초과분은 처리 중이 아니라 대기열에서 차례를 기다립니다. 지연 = 대기 시간 + 실제 처리 시간이고,
포화점 이후에는 동시성을 늘릴수록 대기 시간만 자랍니다. 그래서 "서버가 느려졌다"의 절반은
"서버가 포화됐다"이고, 처방은 코드 최적화가 아니라 용량(지렛대) 쪽입니다.

</details>

**Q2.** 같은 배치 처리인데 MP2 파이프라인은 1,000배, ResNet18(CPU)은 1.3배 빨라졌습니다.
이 차이로 "배치의 이득이 어디서 오는지"를 설명해 보세요.

<details>
<summary>답 보기</summary>

배치의 이득은 **건당 고정 오버헤드를 나눠 갖는 데서** 옵니다. MP2 파이프라인의 행당 2ms는
계산이 아니라 오버헤드(DataFrame 생성, 파이프라인 단계 dispatch, 검증)가 거의 전부라 —
868행을 한 번에 보내면 그 비용을 868이 나눠 갖습니다(행당 0.002ms). 반면 ResNet의 20.8ms는
대부분 진짜 행렬 연산이고 torch가 이미 코어를 병렬로 쓰고 있어, 모아 보내도 절약되는 것은
호출 오버헤드 조각뿐입니다. 즉 "오버헤드 지배 → 배치 극적, 계산 지배 → 배치 완만"이고,
GPU에서는 노는 병렬 유닛을 채우므로 계산 지배 모델도 배치 이득이 다시 커집니다.

</details>

**Q3.** 다음 세 API 중 캐시를 붙일 가치가 있는 것을 고르고, 나머지는 왜 아닌지 설명하세요.
(a) 오늘 관측값으로 내일 PM2.5를 예측 (b) 업로드된 사진 분류 (c) 문장 감성 분류(고객 리뷰 실시간 유입)

<details>
<summary>답 보기</summary>

**(a)만 확실한 캐시 대상**입니다 — 입력(오늘의 관측)이 하루 동안 사실상 하나라 히트율이 극단적으로
높습니다 (오늘 실측: hits 200 / misses 1). (b)는 사진마다 바이트가 달라 같은 키가 사실상 다시 오지
않고(히트율 ≈ 0), (c)는 리뷰 문장이 매번 달라 마찬가지입니다 — 단, (c)에서 "같은 문장 재제출"이
잦은 서비스(중복 신고 등)라면 부분적으로 유효할 수 있습니다. 판단 기준은 언제나 **예상 히트율**이고,
붙였다면 `cache/info`로 실제 히트율을 관측해 가설을 검증합니다.

</details>
