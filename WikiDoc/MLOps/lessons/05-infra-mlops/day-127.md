## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **린트와 포맷**(ruff)을 도입해, 스타일 논쟁을 사람의 일에서 도구의 일로 옮길 수 있다.
- CI에 **lint job을 병렬로** 추가하고, **커버리지**를 측정해 그 숫자의 의미와 한계를 말할 수 있다.
- **브랜치 보호 규칙**으로 main 직접 push를 차단하고, "테스트+린트+리뷰 통과 없이 병합 불가"를 설정할 수 있다.
- [Day 110](day-110.md)의 신사협정이 **시스템의 강제**로 바뀌는 순간을 완성할 수 있다.

## ② 왜 필요한가

어제의 마지막 장면 — PR에 기계의 체크가 생겼지만 **장식**이었습니다. 빨간불이어도 병합 버튼은
눌립니다. 그리고 W22의 팀 규칙 문서에는 아직도 "약속"인 항목이 남아 있죠:

| Day 110의 규칙 | 지금 상태 |
|---|---|
| main 직접 push 금지 | 약속 (리더가 어겼고, 아무도 못 막았음 — 라운드 3) |
| 병합 전 테스트 통과 | 어제부터 보이지만 **강제 아님** |
| 리뷰 1명 이상 | 약속 |

오늘 이 표의 오른쪽 열을 전부 "**차단됨**"으로 바꿉니다.

하나 더 — 테스트로 못 잡는 품질이 있습니다. 리뷰에서 이런 코멘트에 시간을 써 본 적 있죠:
"import 순서가", "여기 안 쓰는 변수가", "따옴표 통일 좀". 전부 정답이 기계적으로 정해지는
지적입니다 — 그런데 사람이 하면 감정이 상하고, 리뷰 시간을 **판단이 필요한 지적**(설계·경계
조건 — [Day 108](day-108.md)의 [must])에서 빼앗아 갑니다. Day 110에서 "취향 문제는 도구에
맡긴다(W26의 ruff)"고 미뤄 둔 그 도구를 오늘 장착합니다.

## ③ 개념 설명

### 린트와 포맷 — 두 가지 기계적 품질

| | 린트 (ruff check) | 포맷 (ruff format) |
|---|---|---|
| 보는 것 | **버그 냄새·죽은 코드** — 안 쓰는 import/변수, 위험한 비교, 미정의 이름 | **모양** — 줄바꿈, 따옴표, 공백 |
| 결과 | 지적 목록 (일부는 --fix로 자동 수정) | 코드를 규격으로 재작성 |
| 논쟁 여지 | 낮음 (대부분 명백) | **0** — 도구의 출력이 곧 표준 |

ruff는 이 둘을 한 도구로, 그리고 매우 빠르게 (전체 프로젝트에 밀리초급) 처리합니다.
포맷의 요점은 "어느 스타일이 옳은가"가 아닙니다 — **"논쟁을 끝낸다"** 입니다. 도구가 정한
모양이 팀의 모양이고, diff에는 이제 의미 있는 변경만 남습니다.

### 커버리지 — 유용한 계기판, 위험한 목표

커버리지 = 테스트가 실행해 본 코드의 비율. 읽는 법이 중요합니다:

- **낮은 곳을 비추는 손전등으로** — "app/router.py의 에러 경로가 0%"는 행동 가능한 정보
- **목표 숫자로 삼으면 부패** — "80% 넘겨라"가 목표가 되면 assert 없는 실행-만-하는 테스트가
  양산됩니다 (지표가 목표가 되면 좋은 지표이기를 멈춘다 — 굿하트의 법칙)

이 과정의 규칙: 커버리지는 **보고만 하고, 게이트는 테스트 통과 여부로만** 겁니다.

### 브랜치 보호 규칙 — 약속의 시스템화

GitHub 저장소 Settings → Branches → **Add branch protection rule** (대상: main):

| 설정 | 효과 | Day 110 규칙과의 대응 |
|---|---|---|
| Require a pull request before merging | main 직접 push **차단** | "main 직접 push 금지" |
| Require approvals: 1 | 승인 없이 병합 불가 | "리뷰 1명 이상" |
| Require status checks to pass (test, lint) | **빨간불이면 병합 버튼 잠김** | "병합 전 테스트 통과" |
| Do not allow force pushes (기본) | 공유 역사 재작성 차단 | "force push 금지" (107·109) |

이 화면이 이번 단원의 작은 정점입니다 — 문서(CONTRIBUTING.md)가 설정(시스템)이 되는 순간.

## ④ 단계별 실습

### Step 1. ruff 도입 — 첫 지적들 (1~2교시)

브랜치 `feature/quality-gate` 에서:

```bash
pip install ruff==0.9.4
ruff check .
```

```
$ ruff check .
app/predlog.py:3:8: F401 [*] `json` imported but unused
app/router.py:41:9: F841 [*] Local variable `t0` is assigned to but never used
tests/test_api.py:12:1: E402 Module level import not at top of file
Found 3 errors.
[*] 2 fixable with the `--fix` option.
```

석 달치 코드에서 3건 — 나쁘지 않습니다. F841(안 쓰는 변수 t0)은 [Day 098](../04-deep-learning-serving/day-098.md)
시절 시간 측정을 미들웨어로 옮기고 남은 흔적 — **린트가 죽은 코드의 고고학자**입니다.
`ruff check . --fix` 로 자동 수정, E402는 손으로. 이어서 포맷:

```bash
ruff format .
```

```
$ ruff format .
4 files reformatted, 7 files left unchanged
```

설정은 `pyproject.toml` 에 고정합니다 (도구 버전과 규칙이 저장소에 — 팀 전원·CI가 같은 자):

```toml
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B"]    # 기본 오류 + import 정리 + 버그 패턴
```

### Step 2. CI 확장 — lint job과 커버리지 (3~4교시)

ci.yml에 job을 **병렬로** 추가합니다 (job끼리는 각자 새 러너 — 서로 기다리지 않습니다):

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install ruff==0.9.4
      - run: ruff check . && ruff format --check .

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: "pip"
      - name: 의존성 설치 (CPU 휠)
        run: |
          pip install -r requirements.txt \
            --index-url https://download.pytorch.org/whl/cpu \
            --extra-index-url https://pypi.org/simple
          pip install pytest-cov
      - name: 테스트 + 커버리지
        run: pytest -q --cov=app --cov-report=term-missing
```

두 가지 포인트 — ① lint job은 ruff만 설치해 **20초 만에** 끝납니다 (빠른 그물을 앞에), ②
`ruff format --check` 는 고치지 않고 **어긋남을 실패로만** 보고합니다 (CI는 심판이지 수리공이
아님 — 수리는 로컬에서). push 후 커버리지 출력:

```
---------- coverage: platform linux, python 3.12.8 ----------
Name                  Stmts   Miss  Cover   Missing
---------------------------------------------------
app/config.py            11      0   100%
app/main.py              24      1    96%   41
app/model_store.py       31      2    94%   55-56
app/predlog.py           28      6    79%   31-38
app/router.py            42      3    93%   77, 84-85
app/service.py           26      0   100%
---------------------------------------------------
TOTAL                   162     12    93%
```

93% — 하지만 오늘의 독법은 숫자가 아니라 **Missing 열**입니다. predlog.py 31-38(DB 실패
경로!)이 안 덮여 있습니다 — [Day 123](day-123.md) 과제 1에서 설계한 그 best-effort 예외 처리가
무검증 상태라는 뜻. 이 발견을 이슈로 남기세요 (커버리지의 올바른 사용법 실연).

### Step 3. 자물쇠 채우기 — 브랜치 보호 (5교시)

PR을 병합한 뒤, Settings → Branches → Add rule (Branch name pattern: `main`):
③의 네 설정을 켜고 status checks에 **test와 lint를 지정**합니다. 그리고 시험 —
[Day 110](day-110.md) 라운드 3의 리더처럼 main에 직접 push 해 봅니다:

```bash
git switch main && git pull
echo "# 몰래 수정" >> README.md
git commit -am "직접 push 시험" && git push
```

```
$ git push
Total 3 (delta 2), reused 0 (delta 0), pack-reused 0
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: - Changes must be made through a pull request.
To github.com:mlops-student/mlops-mp3.git
 ! [remote rejected] main -> main (protected branch)
error: failed to push some refs to 'github.com:mlops-student/mlops-mp3.git'
```

**차단됐습니다.** W22에는 회고 안건이었던 사고가 이제 물리적으로 불가능합니다.
(`git reset --hard origin/main` 으로 시험 커밋 정리 — 로컬만의 역사이니 reset이 옳은 도구,
[Day 109](day-109.md)의 그 판단입니다.)

### Step 4. 잠긴 병합 버튼 구경 (6교시)

일부러 린트에 걸리는 PR을 만들어 봅니다 (안 쓰는 import 하나 추가). PR 화면:

```
✗ Some checks were not successful
  ✗ CI / lint    Failing after 18s  — Required
  ✓ CI / test    Successful in 2m 05s — Required

⊘ Merge blocked: Required status check "lint" is failing.
```

병합 버튼이 회색입니다 — 어제와 결정적으로 다른 지점. 팀의 그 누구도(관리자 포함 — ⑤ 참고)
빨간불을 지나갈 수 없습니다.

### Step 5. 과제 — 실패 PR 3종을 고쳐 통과 (7~8교시)

일부러 만든 세 가지 실패 PR을 각각 **잠긴 화면 캡처 → 원인 규명 → 수정 커밋 → 병합**까지
완주하고 기록을 제출하세요:

1. **린트 실패** — Step 4의 그것 (ruff 로컬 실행으로 잡고 수정)
2. **테스트 실패** — 회귀 테스트를 깨는 변경 (0.7214 대조 — 어제 Step 4의 재활용 가능)
3. **리뷰 부재** — 체크는 다 초록인데 승인이 없는 PR (버튼 문구가 어떻게 다른지 관찰)

각 건에 한 줄씩: **이 실패가 게이트 없이 main에 들어갔다면 언제 어떤 모습으로 발견됐을까?**
(datapipe 저장소에도 같은 게이트를 이식하는 것까지가 과제입니다.)

## ⑤ 자주 하는 실수

### 포맷을 도구에 맡기고도 스타일 리뷰를 계속함

**증상** — ruff format 도입 후에도 리뷰에 "여기 한 줄로 합치죠" 류의 코멘트 — 도구와 사람이
서로 고친 것을 되돌리는 핑퐁.
**원인** — "도구의 출력이 표준"이라는 합의 미완 — 절반만 위임한 상태.
**해결** — 팀 규칙 한 줄 추가: "포맷은 ruff format의 출력이 최종이다 — 모양 코멘트 금지."
사람의 리뷰는 이름·설계·경계 조건으로 승격됩니다. 도구 위임의 목적이 리뷰의 **수준 상승**임을
기억하세요.

### 로컬과 CI의 ruff 버전이 다름

**증상** — 로컬은 통과, CI만 실패 (또는 반대) — 같은 코드가 사람마다 다른 판정.
**원인** — 버전마다 규칙이 조금씩 다른데 로컬은 `pip install ruff`(최신), CI는 다른 버전.
**해결** — 버전을 **한 곳에 고정**하고 (오늘 0.9.4처럼 명시) 로컬·CI가 같은 값을 쓰게.
"같아야 하는 값은 한 번만 적는다"([Day 124](day-124.md) Q3)의 도구판입니다.

### 커버리지 목표제

**증상** — "90% 미만 병합 금지" 도입 후, assert 없는 테스트·게터 테스트가 급증 — 숫자는 오르고
버그는 그대로.
**원인** — 계기판을 목표로 만든 순간 계기판이 조작 대상이 됨 (굿하트).
**해결** — 게이트는 통과/실패로만, 커버리지는 리뷰의 **대화 재료**로 ("이 PR로 에러 경로가
0%→80%가 됐네요" / "새 코드가 전부 Missing인데요?"). 숫자가 아니라 Missing 줄 목록을 읽는
팀이 이깁니다.

### 보호 규칙에서 관리자를 예외로 둠

**증상** — "급해서" 소유자가 자꾸 우회 병합 — 게이트가 팀원에게만 적용되는 이중 규범이 되고,
정작 사고는 권한 큰 사람의 커밋에서.
**원인** — "Include administrators"(관리자도 포함) 미체크.
**해결** — 체크하세요. 게이트의 신뢰는 **예외 없음**에서 나옵니다 — 권한이 클수록 사고 반경도
크므로(Day 112의 원리) 더 필요합니다. 진짜 비상용 우회는 규칙을 잠깐 끄는 것으로 — 그 행위
자체가 감사 로그에 남게.

### 체크 이름을 바꾸고 영원히 기다리는 PR

**증상** — 워크플로의 job 이름을 test → tests로 바꿨더니 모든 PR이:
```
● Expected — Waiting for status to be reported: test
```
**원인** — 보호 규칙은 **이름 문자열**로 체크를 기다립니다 — 옛 이름 "test"는 이제 영원히
보고되지 않습니다.
**해결** — Settings의 required checks 목록을 새 이름으로 갱신. job 이름 변경은 워크플로만의
일이 아니라 **설정과의 계약 변경**임을 기억하세요.

## ⑥ 확인 문제

**Q1.** lint job(20초)과 test job(2분)을 하나의 job으로 합치지 않고 병렬로 나눈 설계의 이점
두 가지를 쓰세요.

<details>
<summary>답 보기</summary>

① 피드백 속도 — 린트 실패는 20초 만에 보고됩니다. 합쳐져 있으면 (step 순서에 따라) 2분을
기다리거나, 린트를 먼저 두면 테스트 결과를 못 봅니다. 나누면 두 판정이 독립적으로, 각자 최속으로
도착합니다. ② 판정의 명확성 — PR 화면에 "무엇이 실패했나"가 job 단위로 표시되고, 보호 규칙도
체크별로 걸립니다. 덤으로 러너 병렬이라 총 대기 시간은 느린 쪽(2분)에 수렴 — 직렬 합산(2분
20초)보다 빠릅니다. pipeline 설계의 기본 감각입니다.

</details>

**Q2.** Step 2에서 커버리지 93%인데도 "predlog의 DB 실패 경로 무검증"이 더 중요한 발견이었습니다.
"커버리지가 높은데 위험한 코드"와 "커버리지가 낮은데 안전한 코드"의 예를 하나씩 들어, 숫자
단독 해석의 한계를 보이세요.

<details>
<summary>답 보기</summary>

높은데 위험: 실행은 되지만 assert가 빈약한 테스트로 채워진 코어 로직 — 라인은 밟혔으나 결과
검증이 없어 회귀를 못 잡습니다 (커버리지는 "실행됨"만 셉니다). 낮은데 안전: 자동 생성 코드나
단순 위임 계층 — 실질 로직이 없어 테스트 가치가 낮고, 낮은 수치가 위험을 뜻하지 않습니다.
결론: 커버리지는 "어디를 안 밟았나"의 지도로 쓰고, 위험도(그 경로가 실패하면 무슨 일이)와
결합해야 행동 가능한 정보가 됩니다 — 그래서 Missing 열 독해가 총평 숫자보다 중요합니다.

</details>

**Q3.** 브랜치 보호가 켜진 지금, [Day 115](day-115.md)의 deploy.sh 안에 있는 pytest는 이제
중복이니 제거해도 될까요? 세 겹 그물(126 ③)의 관점에서 판단하세요.

<details>
<summary>답 보기</summary>

제거하면 안 됩니다 — 두 검증은 다른 것을 봅니다. CI는 "그 커밋의 코드"를 러너 환경에서 검증
하지만, deploy.sh의 pytest는 "**배포 직전의 서버 환경**"(그 서버의 의존성·모델 파일·설정)에서
돌아 환경 표류·모델 파일 문제 같은 서버 쪽 사고를 잡습니다. 또한 배포는 CI를 거치지 않은
경로(수동 배포·롤백)로도 일어날 수 있습니다. 그물은 겹치라고 있는 것 — 다만 내일부터 배포
자체가 CI의 연장(CD)이 되면서 이 중복의 모양이 정리됩니다.

</details>
