## ② 왜 필요한가

25강에서 요구사항과 보안을 설계했습니다. 아직 답하지 않은 질문이 하나 남았습니다.

> **"이 서비스가 무너지면, 얼마나 잃어도 되고, 얼마나 빨리 되살려야 하나요?"**

이 질문에 답이 없으면 백업을 얼마나 자주 할지, 다중 리전이 필요한지, 예산을 어디에 쓸지 **결정할 수 없습니다.** 그리고 이 결정은 사고가 난 **뒤**에는 너무 늦습니다.

```
 [RPO/RTO를 안 정한 팀]
  장애 발생 → "백업이... 어제 게 있나?" → "복구가 몇 시간 걸리죠?" → 즉흥 대응 → 데이터 유실

 [정한 팀]
  RPO 5분 → 자동 백업 + 트랜잭션 로그로 5분 내 시점 복구
  RTO 30분 → 복구 절차서(런북)대로 → 27분 만에 복구
```

그리고 오늘은 이 단원 첫 관문 — **M1 설계 리뷰**입니다. 팀이 지금까지 만든 설계를 발표하고, 다른 팀과 강사가 **"이 구성이 죽는 시나리오"** 를 던집니다. 방어하지 못하는 지점이 곧 W14에서 고칠 지점입니다.

리뷰는 비판이 아니라 **선물**입니다 — 실제 장애가 던질 질문을, 안전한 강의실에서 미리 받는 것입니다. [30강 게임데이](lesson-30.md)에서 이 시나리오들을 실제로 일으켜 검증합니다.

## ③ 워크숍 가이드 — DR 설계와 리뷰

### RPO vs RTO — 두 개의 시계

```
 정상 ──────[백업]──────[장애!]──────[복구 완료]────▶ 시간
              │◀── RPO ──▶│◀──── RTO ────▶│
              │            │               │
        마지막 안전 지점   무슨 일이 남      다시 정상

 RPO(복구 시점 목표): 얼마나 과거로 돌아가도 되나 = 허용 데이터 손실
 RTO(복구 시간 목표): 얼마나 빨리 되살려야 하나 = 허용 다운타임
```

| 서비스 예 | RPO | RTO | 이유 |
|---|---|---|---|
| 은행 거래 | ~0(무손실) | 초~분 | 1원도 못 잃음 |
| 이벤트 신청 | 5분 | 30분 | 신청 몇 건은 재접수 가능, 오래 멈추면 곤란 |
| 사내 위키 | 24시간 | 4시간 | 일 1회 백업으로 충분 |

> 🔑 **RPO/RTO를 낮출수록 비용이 급등합니다.** RPO 0(동기 복제)과 RPO 5분(자동 백업)은 비용이 몇 배 차이입니다. **"필요한 만큼만"** 이 핵심 — 사내 위키에 은행 수준을 적용하면 돈만 낭비합니다.

### DR 4전략 — 비용과 복구 시간의 사다리

```
 비용 ▲
      │                                    ● 액티브-액티브 (양쪽 상시 서비스)
      │                          ● 웜 스탠바이 (축소 규모 상시 가동)
      │              ● 파일럿 라이트 (데이터만 복제, 컴퓨팅 꺼둠)
      │  ● 백업 & 복구 (스냅샷 + 리전 복사)
      └────────────────────────────────────────▶ 복구 속도(빠를수록 오른쪽)
```

| 전략 | RPO/RTO | 월 비용 | 구성 | 이 프로젝트 |
|---|---|---|---|---|
| **백업 & 복구** | 시간 단위 | 최저 | 스냅샷 + 리전 간 복사 | ✅ **기본 채택** |
| 파일럿 라이트 | 수십 분 | 낮음 | 데이터만 복제, 컴퓨팅 정지 | 여유 시 |
| 웜 스탠바이 | 분 단위 | 중간 | 축소 규모 상시 가동 | 과함 |
| 액티브-액티브 | 초 단위 | 최고 | 양 리전 동시 서비스 | 과함 |

> 💡 **이 과정 최종 프로젝트는 "백업 & 복구"로 충분**합니다(RPO 5분 / RTO 30분). 그 이상은 비용($60 한도)을 넘고, "왜 이 전략인가"를 설명하는 것이 다중 리전을 구현하는 것보다 중요합니다.

### 우리가 이미 가진 DR 도구들

24주간 배운 것 중 DR 도구가 이미 여럿입니다.

| 도구 | 어디서 | DR 역할 |
|---|---|---|
| RDS 자동 백업 + PITR | [15강](../02-compute-data/lesson-15.md) | RPO 5분 (5분 단위 시점 복구) |
| RDS Multi-AZ | [15강](../02-compute-data/lesson-15.md) | AZ 장애 자동 조치(DR 아닌 HA) |
| EBS 스냅샷 리전 복사 | [14강](../02-compute-data/lesson-14.md) | 리전 장애 대비 |
| S3 버전 관리·복제 | [13강](../02-compute-data/lesson-13.md) | 정적 자산 보호 |
| IaC 템플릿 | [23강](../03-serverless-automation/lesson-23.md) | **다른 리전에 환경 재구축** |
| Route 53 장애 조치 | [12강](../02-compute-data/lesson-12.md) | 주 리전 죽으면 보조로 |

> ⭐ **IaC가 최고의 DR 도구입니다.** 인프라가 코드면, 리전이 통째로 죽어도 다른 리전에 `deploy` 한 번으로 환경을 재현합니다. 데이터(스냅샷)만 복사되어 있으면 됩니다.

### 고가용성(HA) vs 재해 복구(DR) — 혼동 주의

| | 고가용성(HA) | 재해 복구(DR) |
|---|---|---|
| 범위 | AZ 장애 | **리전 장애·대규모 재해** |
| 예 | Multi-AZ, 2AZ ASG | 리전 간 백업, 다중 리전 |
| 자동/수동 | 대개 자동 | 대개 절차(런북) 기반 |

이 프로젝트는 **HA는 필수(2AZ), DR은 백업&복구로 최소** 구현합니다.

### 설계 리뷰 진행법

**형식** — 팀당 발표 5분 + 상호 질의 5분.

**리뷰어의 의무** — 각 팀에 **"이 구성이 죽는 시나리오"를 최소 하나** 제시합니다. 좋은 시나리오의 조건:

```
 나쁜 질문: "그거 안전한가요?"           (막연함)
 좋은 질문: "AZ-2a가 통째로 죽으면 NAT가
            거기 하나뿐인데 앱이 인터넷에
            못 나가지 않나요?"           (구체적 실패 경로)
```

> [16강](../02-compute-data/lesson-16.md) 확인 문제 1번의 "가장 먼저 죽는 지점"을 떠올리세요 — 그런 질문을 서로에게 던지는 것이 리뷰입니다.

**발표 팀의 자세** — 방어하되, **모르면 "그건 미처 생각 못 했다, W14에서 반영하겠다"** 가 정답입니다. 완벽을 증명하는 자리가 아니라 **구멍을 찾는 자리**입니다.

## ④ 스프린트 작업 (M1 리뷰)

> 💰 **예상 비용 $0 ~ 0.2** — 대부분 설계·리뷰(무료). AWS Backup 계획만 잠깐 만듭니다.

### Step 1. RPO/RTO 확정 (팀, 20분)

25강의 비기능 요구 N4를 숫자로 확정하고 근거를 답니다.

| 항목 | 우리 목표 | 근거 |
|---|---|---|
| RPO | 5분 | 신청 데이터는 재접수 가능하나 대량 유실은 곤란 |
| RTO | 30분 | 이벤트 특성상 30분 내 복구면 사용자 이탈 최소 |
| 달성 수단 | RDS 자동 백업(PITR) + Multi-AZ + IaC 재배포 | — |

### Step 2. DR 전략 선택 + 복구 절차서 초안 (팀, 30분)

**전략 선택** — 4전략 표에서 하나를 고르고 **왜 이것이고 왜 다른 것은 아닌지** 적습니다.

**복구 절차서(런북) 초안** — 새벽 3시에 처음 보는 사람이 따라 할 수 있게.

```
 [시나리오: RDS 데이터 손상/실수 삭제]
  1. 탐지: CloudWatch 알람(DB 연결 급감) 또는 사용자 신고
  2. 판단: 데이터 문제인가 인프라 문제인가 (5분 룰: 넘으면 복구 개시)
  3. 복구: PITR로 손상 직전 시점 새 인스턴스 복원
           aws rds restore-db-instance-to-point-in-time ...
  4. 전환: 앱의 DB 엔드포인트를 복원본으로 (또는 데이터만 이관)
  5. 검증: 신청 COUNT 확인, 스모크 테스트
  6. 사후: 원인 기록, 재발 방지책 → 게임데이(30강)에서 실제 훈련
```

> 이 런북이 [30강 게임데이](lesson-30.md)에서 실제로 실행됩니다 — 지금 대충 쓰면 그때 고생합니다.

### Step 3. AWS Backup 계획 (인프라, 20분)

리소스별 백업을 하나로 중앙화합니다.

```bash
$ ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

# 백업 볼트
$ aws backup create-backup-vault --backup-vault-name course-vault \
    --backup-vault-tags Project=aws-course 2>/dev/null || true

# 백업 계획 — 일 1회, 7일 보존
$ PLAN_ID=$(aws backup create-backup-plan --backup-plan '{
    "BackupPlanName": "course-daily",
    "Rules": [{
      "RuleName": "daily-7day",
      "TargetBackupVaultName": "course-vault",
      "ScheduleExpression": "cron(0 18 * * ? *)",
      "StartWindowMinutes": 60,
      "Lifecycle": {"DeleteAfterDays": 7}
    }]
  }' --query 'BackupPlanId' --output text)

$ echo "백업 계획: $PLAN_ID"
```

> 📌 **태그 기반 리소스 선택** — 실제 리소스 할당(`create-backup-selection`)은 W14에서 리소스가 생긴 뒤, `Project=aws-course` 태그로 한 번에 겁니다. 오늘은 계획 구조만 확인합니다.
> 💡 RDS는 자동 백업(PITR)이 이미 있으므로 AWS Backup은 **EBS·EFS·크로스 리전 통합 관리**에 주로 씁니다.

### Step 4. 🏁 M1 설계 리뷰 진행 (전체, 45분)

**진행 순서**

```
 팀당 10분:
   ├─ 발표 5분: 서비스 소개 → 아키텍처 다이어그램 → 핵심 결정 3개 → DR 전략
   └─ 질의 5분: 다른 팀 + 강사가 "죽는 시나리오" 제시
```

**리뷰 체크리스트** — 발표 팀은 아래에 답할 수 있어야 합니다.

- [ ] 이 서비스가 **가장 먼저 죽는 지점**은? 그 대비책은?
- [ ] 트래픽이 **10배**가 되면 무엇이 먼저 한계에 닿나?
- [ ] 데이터가 손상되면 **얼마나 잃고 얼마나 빨리** 복구되나?(RPO/RTO)
- [ ] 가장 민감한 데이터의 **보호 경로**는?
- [ ] IAM 역할 중 **과대 권한**은 없나?
- [ ] 이 구성의 **월 비용**은 대략 얼마고 한도 안인가?

**리뷰 기록** — 받은 지적을 표로 남깁니다.

| # | 지적한 팀/사람 | 시나리오 | W14 반영 계획 |

| 1 | B팀 | AZ-2a 장애 시 단일 NAT로 앱 인터넷 끊김 | NAT를 AZ마다 or VPC 엔드포인트로 |
| 2 | 강사 | deploy 역할이 넓음 | Access Analyzer로 좁히기 |
| ... | | | |

### Step 5. 설계 확정 (팀, 30분)

리뷰 피드백을 반영해 다이어그램과 문서를 수정합니다. **최종 다이어그램**에 반드시:

- [ ] VPC·AZ·서브넷(퍼블릭/앱/DB)·CIDR
- [ ] 보안 경계(SG 체인, WAF 위치)
- [ ] 데이터 흐름(사용자 → CDN/ALB → 앱 → DB, 비동기 큐)
- [ ] 암호화 지점(KMS)·시크릿·HTTPS
- [ ] DR 요소(백업·리전 복사·복구 경로)

## ⑤ 자주 하는 실수

### RPO와 RTO를 혼동한다

**증상** — "RTO 5분"이라 적어 놓고 실제론 데이터 손실 허용을 말하고 있습니다.
**구분법** — **RPO는 "얼마나 잃나"(과거 방향), RTO는 "얼마나 빨리"(미래 방향)**. 백업 시점과 장애 사이 = RPO, 장애와 복구 완료 사이 = RTO. Step 1의 그림을 다시 보세요.

### RPO/RTO를 무조건 낮게 잡는다

**증상** — 사내 위키인데 "RPO 0, RTO 1분"으로 적습니다.
**문제** — RPO 0은 동기 다중 리전 복제를, RTO 1분은 상시 대기 환경을 요구합니다 — **비용이 폭증**하고 $60 한도를 넘습니다.
**해결** — 서비스 성격에 맞게. "이 데이터를 5분 치 잃으면 회사가 망하나?"를 물어 필요한 수준만 정합니다. 과소도 과대도 실패입니다.

### DR과 HA를 같은 것으로 취급한다

**증상** — "Multi-AZ 했으니 재해 복구는 끝"이라고 생각합니다.
**문제** — Multi-AZ는 **AZ** 장애 대비(HA)입니다. **리전 전체**가 죽으면(드물지만 발생) 두 AZ가 함께 사라집니다.
**해결** — HA(2AZ, Multi-AZ)와 DR(리전 간 백업·재배포)을 구분해 설계합니다. 이 프로젝트는 HA 필수 + DR은 백업&복구로 최소.

### 복구 절차서를 "나만 아는 언어"로 쓴다

**증상** — "그때 그거 하면 됨" 수준의 런북.
**문제** — 새벽 3시에 당직자(작성자가 아닌 사람)가 못 따라 합니다. [30강](lesson-30.md)에서 실제로 막힙니다.
**해결** — 실행 명령·확인 방법·판단 기준(5분 룰 등)을 구체적으로. "처음 보는 사람 기준"으로 씁니다.

### 리뷰에서 방어만 하고 배우지 않는다

**증상** — 지적받을 때마다 "그건 괜찮아요"로 넘깁니다.
**문제** — 리뷰의 목적은 **구멍을 찾는 것**인데, 방어에 성공하면 구멍이 그대로 남습니다.
**해결** — 지적을 **선물로** 받습니다. 모르면 "미처 생각 못 했다, 반영하겠다"가 만점 답변입니다. 리뷰 기록표에 남겨 W14에서 고칩니다.

### AWS Backup 볼트가 안 지워진다

```
An error occurred: Backup vault cannot be deleted because it contains recovery points
```
**원인** — 볼트 안에 복구 지점(백업)이 남아 있습니다.
**해결** — 복구 지점을 먼저 삭제하거나, 백업이 만료(보존 기간)될 때까지 기다립니다. 실습에서 백업을 실제로 뜨지 않았다면 비어 있어 바로 지워집니다.

## ⑥ 마일스톤 점검 — 🏁 M1

**M1 통과 기준 — 아래를 발표에서 증명했는가**

- [ ] 요구사항 정의서(기능 8+ / 비기능 6+ 숫자) 제출
- [ ] 구성 요소 결정표(대안·근거·비용) 제출
- [ ] 아키텍처 다이어그램(리뷰 반영 최종본) 제출
- [ ] 보안 기준선 문서(KMS·시크릿·WAF·IAM 역할표) 제출
- [ ] **RPO/RTO + DR 전략서 + 복구 절차서 초안** 제출
- [ ] 리뷰에서 제기된 시나리오에 대응 계획을 세웠다

**M1을 통과하지 못하면?** — 다음 주 첫 시간에 보완 발표를 합니다. **설계가 부실하면 W14 구축이 흔들리므로**, 여기서 제대로 잡는 것이 전체 프로젝트의 성패를 가릅니다.

**스스로 점검하는 질문 3개**

<details>
<summary>1. RPO 5분을 실제로 어떤 AWS 기능이 달성하나요?</summary>

**RDS 자동 백업(트랜잭션 로그 기반 PITR)** 입니다. 자동 백업을 켜면 5분 단위로 특정 시점 복구가 가능합니다([15강](../02-compute-data/lesson-15.md)). RPO를 더 낮추려면(예: 초 단위) 동기 복제·다중 리전이 필요하고 비용이 급등합니다. "우리 RPO는 5분이고, RDS 자동 백업 보존 7일로 달성한다"까지 말할 수 있어야 합니다.
</details>

<details>
<summary>2. 리전 전체가 죽는 재해에서, 우리 서비스를 어떻게 되살리나요?</summary>

**IaC + 스냅샷**입니다. ① 인프라가 코드(CFN 템플릿)이므로 다른 리전에 `deploy` 로 재구축 ② RDS 스냅샷을 리전 간 복사해 두었다면 그것으로 복원 ③ Route 53으로 트래픽 전환. 이 프로젝트는 "백업&복구" 전략이라 이 과정이 자동이 아니라 **런북 기반 수동**이며, RTO 30분 안에 하는 것이 목표입니다. (자동화하면 파일럿 라이트/웜 스탠바이 — 비용 증가)
</details>

<details>
<summary>3. 우리 팀 리뷰에서 나온 "가장 아픈 지적"은 무엇이고 어떻게 고칠 건가요?</summary>

팀마다 다르지만, 답이 있어야 합니다. 흔한 것: 단일 NAT(→ AZ별 NAT 또는 엔드포인트), 넓은 IAM 역할(→ 좁히기), 캐시 없이 DB 직격(→ 필요 시 ElastiCache), 정적 자산을 EC2에서 서빙(→ CloudFront). **지적을 기억하지 못한다면 리뷰를 선물로 받지 않은 것**입니다.
</details>

## 오늘의 정리

| 개념 | 핵심 |
|---|---|
| RPO | 허용 데이터 손실(과거 방향) |
| RTO | 허용 다운타임(미래 방향) |
| 낮출수록 | 비용 급등 — **필요한 만큼만** |
| DR 4전략 | 백업&복구 < 파일럿 라이트 < 웜 스탠바이 < 액티브-액티브 |
| HA vs DR | AZ 장애(자동) vs 리전 장애(런북) |
| **IaC = DR 도구** | 코드면 다른 리전에 재배포 |
| 리뷰 | 구멍을 찾는 자리 · 지적은 선물 · 모르면 "반영하겠다" |
| 런북 | 처음 보는 사람이 새벽 3시에 따라 할 수 있게 |

**한 장 요약**

```
  RPO 5분 / RTO 30분 확정 → DR 전략(백업&복구) → 복구 절차서
                                                    │
  M1 리뷰: 발표 5분 + "죽는 시나리오" 질의 5분 → 리뷰 기록 → 설계 확정
                                                    ▼
                                              W14 구축 시작
```

**오늘 반드시 기억할 한 가지**
> **"얼마나 잃어도 되고 얼마나 빨리 되살릴까"를 정하지 않으면, 백업도 예산도 결정할 수 없습니다.**
> 그리고 리뷰의 지적은 실제 장애가 던질 질문의 예고편입니다 — 지금 받으세요.

**과제 (팀) — M1 최종 제출**
1. RPO/RTO 확정서 + 달성 수단.
2. DR 전략 선택서(왜 이것/왜 아닌 것) + 복구 절차서 초안.
3. 리뷰 반영 최종 아키텍처 다이어그램.
4. **리뷰 기록표** — 받은 지적과 W14 반영 계획.
5. (개인) "우리 서비스의 RPO를 절반으로 줄이려면 무엇이 얼마나 더 필요한가"를 3줄로.
