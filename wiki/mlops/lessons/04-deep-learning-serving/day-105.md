## ② 왜 필요한가

MP3 발표는 MP2와 결이 다릅니다. MP2는 **숫자(성능)의 서사**였다면, MP3는 **동작의 서사**입니다 —
슬라이드 속 표가 아니라, 지금 이 자리에서 사진을 올리면 판정이 돌아오는 것을 보여 주는 발표.

그래서 시연이 왕이고, 시연의 적은 긴장이 아니라 **준비 안 된 데모**입니다. 오늘 오전의
리허설이 발표의 절반입니다. 그리고 발표가 끝나면 이 저장소는 끝이 아니라 **다음 단원의
입력**이 됩니다 — W24에서 컨테이너에 실리고, W26의 CI가 여러분이 어제 만든 pytest를
자동으로 돌리며, W27의 모니터링이 여러분의 예측 로그를 소비합니다.

## ③ 개념 설명

### 5분 발표 구성 — MP3판

| 분 | 내용 | 도구 |
|---|---|---|
| 0–1 | 서비스 시나리오 (누가 · 무엇을 · 왜) — 한 문단 | 기획서 1절 |
| 1–3 | **라이브 시연** ★ | /docs |
| 3–4 | 증거 두 표: 서빙 정확성 대조표 · 성능 전후 비교표 | 보고서 2·3절 |
| 4–5 | 관측(로그 집계 한 화면) · 한계 · 다음 계획 | 보고서 4·5절 |

시연 대본 — 성공만 보여 주면 절반입니다. **실패의 우아함**이 API 품질의 증거입니다:

```
① GET /health           → 초록 확인 ("모델이 실려 있습니다")
② 개미 사진 업로드       → ants 0.72 ("학습 기록과 같은 확률입니다 — 전처리 일치")  ← 이 문장을 꼭
③ cat.jpg(위장 텍스트)   → 415 ("확장자가 아니라 내용으로 검증합니다")             ← 이 문장을 꼭
④ pytest -q             → 7 passed ("명세 표의 칸마다 테스트가 있습니다")
```

### 시연 리스크 관리 — 백업의 3층

| 리스크 | 대비 |
|---|---|
| 서버가 안 뜸 | 발표 **전에** 띄워 놓고 /health까지 확인 (발표 중 기동 금지) |
| 네트워크·화면 문제 | 시연 전체를 담은 스크린샷 세트(또는 녹화)를 슬라이드 뒤에 예비 |
| 예상 밖 입력 질문 ("이거 넣어 보세요") | 즉석 수용 — 어제의 "500 찾기 게임"을 통과했다면 두려울 것 없음. 만약 500이 나면: "버그 발견 감사합니다, 이슈로 기록하겠습니다" — 그 대응 자체가 점수 |

### 예상 질문 10 ★

| 질문 | 답의 뼈대 (출처) |
|---|---|

| 캐시는 왜 안 붙였나 | 사진 입력 히트율 ≈ 0 — 측정 근거로 기각 ([099](day-099.md) Q3) |

## ④ 단계별 실습

### Step 1. 발표 준비 (1~2교시)

- 시연 리허설 2회 — 순서 ①~④를 실제로, 시간 재며. 서버 기동·/health 확인까지 포함.
- 백업 스크린샷 촬영 (시연 각 단계 + pytest 결과).
- 예상 질문 10을 **내 프로젝트의 숫자**로 답해 보기 (짝과 모의 질의응답 추천).

### Step 2. 발표회 (3~6교시)

5분 발표 + 3분 질의응답. 듣는 사람의 역할이 절반입니다 — [Day 095](day-095.md) 리뷰 축으로
질문 하나 이상: 상대의 명세와 시연이 일치하는가, 실패 응답을 보여 줬는가, 측정 조건을 밝혔는가.

들으면서 채울 한 줄 평가표: "시연 동작 □ · 실패 처리 □ · 증거 표 □ · 질문 답변 □ —
가장 배울 점 하나: ___"

### Step 3. 회고 (7교시)

`docs/retro.md` — 감상문이 아니라 다음 행동으로:

```markdown
## 계속할 것 (Keep)     예: 명세 표 먼저 — 목요일 테스트가 공짜였다
## 바꿀 것 (Change)     예: 프로토타입→3계층 재배치에 반나절 — 다음엔 처음부터 구조로
## 시도할 것 (Try)      예: W24 컨테이너에서 워커 재실험 · 텍스트 모델 2버전 서빙
```

### Step 4. 단원 완료 조건 점검과 제출 (8교시)

| 완료 조건 | 점검 방법 |
|---|---|
| 학습과 서빙의 전처리가 같은 코드에서 나온다 | PREPROCESS 정의가 한 곳 + 회귀 테스트 초록 |
| 잘못된 입력이 의도된 에러 응답으로 처리된다 | 413·415·422 테스트 + "500 찾기" 게임 생존 |
| 로그에서 요청별 처리시간을 집계할 수 있다 | 집계 스크립트로 p50/p95 세 줄 출력 |
| API 통합 테스트가 CI 없이도 한 줄로 실행된다 | 새 clone에서 `pytest -q` 초록 |

네 칸이 모두 ✅면 제출: 저장소 URL + 보고서 + (백업 스크린샷). GitHub에 올릴 때 모델
파일(45MB)은 저장소 포함 가능 범위지만, 100MB급이면 받는 법을 README에 씁니다.

```powershell
git tag mp3-final
git push origin main --tags
```

### 다음 단원 예고 — 서비스를 세상에 내놓기

여러분의 API는 지금 **여러분의 노트북에서만** 돕니다. 대단원 05(7주)가 그것을 바꿉니다:

```
W22  Git 협업        — 팀으로 일하는 법 (브랜치·PR·리뷰)
W23  Linux 서버      — 노트북이 아닌 곳에서 돌리기
W24–25  Docker/컨테이너 — MP3가 이미지에 실린다 ("제 컴퓨터에선 되는데요"의 종말)
W26  CI/CD           — 어제 만든 pytest가 자동으로 돌고, 통과하면 자동 배포
W27  모니터링·재학습   — 여러분의 예측 로그가 드리프트 경보가 된다
```

월요일에 만나는 것은 Git의 **팀전**입니다 — 지금까지 혼자 쓰던 Git에 브랜치 전략과 PR이
붙습니다. MP3 저장소가 그 실습의 재료가 되니, 잘 밀어 올려 두세요.

## ⑤ 자주 하는 실수

### 시연이 라이브 코딩이 됨

**증상** — "잠깐만요, 서버 좀 띄우고… 어 왜 안 되지" — 3분 증발, 분위기 싸늘.
**원인** — 발표 중에 처음 하는 동작이 있음.
**해결** — 발표 시작 전 서버 기동·/health 확인까지 끝. 발표 중 타이핑은 URL과 파일 선택뿐이어야 합니다.

### 성공 케이스만 시연

**증상** — 개미 사진 → 판정, 끝. "잘못된 입력은요?"라는 질문에 즉석 대응.
**원인** — 실패 처리가 감점 요소라고 생각 — 반대입니다. **의도된 실패는 자랑거리**입니다.
**해결** — 415 시연을 대본에 넣으세요. "확장자가 아니라 내용으로 검증합니다"는 이 단원 최고의 발표 문장입니다.

### 숫자를 읽기만 하고 의미를 안 붙임

**증상** — "처리량이 46.5입니다" — 그래서 좋다는 건지 나쁘다는 건지.
**원인** — 표를 보여 주는 것과 표로 말하는 것의 차이.
**해결** — 모든 숫자에 비교 대상과 처방을: "단건 대비 +39% — 대량 작업은 배치로, 실시간 단건은 동시성 4 이하 유지".

### 질문에 즉석 실험으로 답하려 함

**증상** — "그 입력은 어떻게 되나요?" → 발표 화면에서 즉석 시도 → 예상 밖 결과 → 수습 불능.
**원인** — 모른다고 말하는 것보다 해 보는 게 성실해 보인다는 착각.
**해결** — 아는 것은 근거로, 모르는 것은 "좋은 지적입니다 — 이슈로 기록하고 확인해 보겠습니다". 기록하는 모습이 답니다.

### 발표가 끝나자 저장소를 방치함

**증상** — 3주 뒤 W24에서 열어 보니 어디까지가 최종인지 불명.
**원인** — 프로젝트의 끝을 발표로 착각 — 이 저장소는 W24·W26·W27의 **입력**입니다.
**해결** — 오늘 `mp3-final` 태그와 회고 커밋까지가 프로젝트입니다. 리뷰 지적 중 반영 못 한 것은 이슈로 남겨 두세요.
