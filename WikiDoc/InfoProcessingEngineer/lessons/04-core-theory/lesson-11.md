## ② 왜 필요한가

**이론 단답은 "아는데 못 쓰는" 일이 가장 억울한 영역입니다.** 코드 문제는 추론이 필요하지만, 이론 문제는 "인스턴스를 하나만 만들도록 보장하는 패턴은?"이라는 설명을 읽고 **싱글턴**이라고 쓰면 끝입니다. 관건은 두 가지 — ①설명→용어 방향으로 연습했는가(책은 용어→설명 순서라 반대 방향 훈련이 안 됨), ②철자·표기가 정확한가(옵저버/옵서버 같은 통용 표기 포함).

이 강의 다섯 주제(요구사항·UML·패턴·테스트·결합도/응집도)는 기출 복원 기준 SW 공학 계열에서 반복 출제되는 핵심입니다(비공식 경향). 특히 **결합도·응집도는 순서 나열형**으로, **패턴·테스트 기법은 설명→용어형**으로 나옵니다.

**시험에서의 중요도와 출제 형태** — 단답(용어 쓰기), 순서 나열, 분류(보기 골라 묶기), 사례 판정. 영역별 배정 시간은 [커리큘럼 04 중요도 표](../../curriculum/04-core-theory.md) 기준: 테스트 50분 > 결합도·응집도 40분 = 패턴 40분 > 요구사항·UML 30분 > 통합·인터페이스 10분(⬇ 저빈출 축소).

## ③ 개념 설명

### 3-1. 요구사항 — 기능 vs 비기능

**요구사항(requirement)** 은 시스템이 무엇을 해야 하는지에 대한 요구입니다.

⚖️ **혼동 비교 (판정 빈출)**

| 구분 | 기능 요구사항 | 비기능 요구사항 |
|---|---|---|
| 뜻 | 시스템이 **수행해야 하는 기능** | 기능 외의 **품질·제약** 조건 |
| 판정 키워드 | "~할 수 있어야 한다"(동작) | 성능·응답시간·보안·가용성·신뢰성·이식성 |
| 예 | "회원은 상품을 검색할 수 있어야 한다" | "검색 결과는 2초 이내에 표시되어야 한다" |

같은 문장 안의 "검색한다(기능)"와 "2초 이내(비기능)"를 갈라 읽는 것이 판정 요령입니다. 요구사항 개발 절차 📌: **도출 → 분석 → 명세 → 확인** (도분명확).

### 3-2. UML — 표준 모델링 언어

**UML(Unified Modeling Language)** — 시험 표현: "객체지향 시스템을 시각적으로 모델링하는 **표준화된 범용 언어**".

📌 **다이어그램 분류 (분류형 출제)**

| 분류 | 성격 | 다이어그램 |
|---|---|---|
| **구조(정적)** | 시스템의 짜임새 | **클래스**, 객체, **컴포넌트**, **배치**, 패키지, 복합체 구조 |
| **행위(동적)** | 시간에 따른 동작 | **유스케이스**, **시퀀스**, 활동, 상태, 통신, 타이밍, 상호작용 개요 |

대표 3종의 시험 표현 — **유스케이스**: 사용자(액터) 관점에서 시스템의 기능과 관계를 표현 / **시퀀스**: 객체 간 **메시지를 시간 순서**로 표현 / **클래스**: 클래스의 속성·연산과 클래스 사이의 관계를 표현.

📌 **관계 6종**: 연관(선), 집합(빈 마름모 ◇ — 부분이 독립 가능), 복합(찬 마름모 ◆ — 전체가 사라지면 부분도), 일반화(빈 삼각형 ▷ — 상속, "is-a"), 의존(점선 화살표), 실체화(점선+빈 삼각형 — 인터페이스 구현). ⚖️ 집합 vs 복합은 "부분이 혼자 살 수 있는가"로 판정합니다.

### 3-3. 디자인 패턴 — GoF 3분류

**디자인 패턴(design pattern)** — 시험 표현: "자주 발생하는 설계 문제에 대한 **재사용 가능한 해결 방법**". GoF(Gang of Four) 패턴 23개를 3분류로 나눕니다.

📌 **3분류와 소속 패턴 (분류형 출제)**

| 분류 | 목적 | 패턴 (굵게 = 단답 빈출) |
|---|---|---|
| **생성(Creational)** 5개 | 객체 생성 방식 | **싱글턴**, **팩토리 메서드**, 추상 팩토리, **빌더**, **프로토타입** |
| **구조(Structural)** 7개 | 클래스·객체의 조합 | **어댑터**, 브리지, 컴포지트, **데코레이터**, **퍼사드**, 플라이웨이트, **프록시** |
| **행위(Behavioral)** 11개 | 객체 간 상호작용·책임 분배 | **옵서버**, **스트래티지**(전략), 커맨드, 스테이트, **템플릿 메서드**, 이터레이터(반복자), 미디에이터(중재자), 메멘토, 비지터(방문자), 책임 연쇄, 인터프리터 |

📌 **대표 패턴의 시험 표현 (설명→용어 방향으로 암기)**

| 설명 (이렇게 출제됨) | 정답 |
|---|---|
| 클래스의 **인스턴스가 하나**임을 보장하고 전역 접근점을 제공 | 싱글턴 (Singleton) |
| 객체의 **상태 변화를 관찰자들에게 자동 통지** (1:N 의존) | 옵서버 (Observer) |
| **호환되지 않는 인터페이스를 변환**해 함께 동작하게 함 | 어댑터 (Adapter) |
| **알고리즘군을 캡슐화**해 상호 교체 가능하게 함 | 스트래티지 (Strategy) |
| 서브시스템의 복잡한 기능을 **단순한 통합 인터페이스**로 제공 | 퍼사드 (Facade) |
| 원본 객체를 **복제(clone)** 하여 새 객체 생성 | 프로토타입 (Prototype) |
| 상위 클래스가 **알고리즘의 골격**을 정하고 일부 단계를 하위 클래스에 위임 | 템플릿 메서드 (Template Method) |
| 실제 객체에 대한 **대리 객체**를 두어 접근을 제어 | 프록시 (Proxy) |

⚖️ 표기: 옵서버/옵저버, 스트래티지/전략 패턴 등 통용 표기는 모두 인정되는 것이 일반적이나, 영문 표기(Observer)를 병기하면 가장 안전합니다.

### 3-4. 테스트 — 레벨·기법·커버리지

📌 **테스트 레벨 4단계 (V모델 순서)**: **단위**(모듈 하나) → **통합**(모듈 결합부) → **시스템**(전체가 요구대로) → **인수**(사용자 관점 — 알파: 개발 환경에서 사용자가 / 베타: 사용자 환경에서).

⚖️ **혼동 비교 — 블랙박스 vs 화이트박스 (최빈출)**

| 구분 | 블랙박스 테스트 | 화이트박스 테스트 |
|---|---|---|
| 보는 것 | 내부 구조 모름 — **입출력(명세)** 만 | **내부 구조·논리**를 보며 수행 |
| 별명 | 명세 기반 | 구조 기반 |
| 기법 | **동등(동치) 분할**, **경계값 분석**, 원인-효과 그래프, 오류 예측 | **기초 경로 검사**, 조건 검사, 루프 검사, 데이터 흐름 검사 |

| 블랙박스 기법 시험 표현 | 정답 |
|---|---|
| 입력을 유효/무효 그룹으로 나눠 **대표값**을 시험 | 동등 분할 (동치 분할) |
| 오류가 몰리는 **경계(양 끝) 값**을 시험 | 경계값 분석 |

📌 **커버리지 (약→강)**: 구문(문장 — 모든 문장 1회 이상) → 결정(분기 — 모든 분기의 참/거짓) → 조건(개별 조건식의 참/거짓) → 조건/결정 → 변경 조건/결정(MC/DC) → 다중 조건.

📌 **통합 테스트 방식과 보조 도구 (⚖️ 스텁 vs 드라이버 — 빈출)**

| 방식 | 진행 | 필요한 가짜 모듈 |
|---|---|---|
| 하향식 | 상위 모듈부터 | **스텁(stub)** — 아직 없는 **하위** 모듈 흉내 |
| 상향식 | 하위 모듈부터 | **드라이버(driver)** — 아직 없는 **상위** 모듈 흉내(호출자) |

기억법: "하향식은 아래가 비어서 스텁(받침), 상향식은 위가 비어서 드라이버(운전자)".

### 3-5. 결합도·응집도 — 모듈 품질의 자

시험 표현: "**결합도는 낮을수록, 응집도는 높을수록** 좋은 설계다."

📌 **결합도 6단계 — 낮음(좋음) → 높음(나쁨)**: **자료 → 스탬프 → 제어 → 외부 → 공통 → 내용** (두문자: 자스제외공내)

| 결합도 | 판정 키워드 |
|---|---|
| 자료 (data) | **값(데이터)만** 매개변수로 주고받음 |
| 스탬프 (stamp) | **자료 구조(배열·객체) 전체**를 넘김 |
| 제어 (control) | 상대 모듈의 **동작을 지시하는 플래그** 전달 |
| 외부 (external) | 외부에 선언된 데이터를 참조 |
| 공통 (common) | **전역 변수**를 여러 모듈이 공유 |
| 내용 (content) | 다른 모듈의 **내부를 직접 참조·수정** |

📌 **응집도 7단계 — 높음(좋음) → 낮음(나쁨)**: **기능 → 순차 → 통신(교환) → 절차 → 시간 → 논리 → 우연** (두문자: 기순통절시논우)

| 응집도 | 판정 키워드 |
|---|---|
| 기능 (functional) | **단일 기능 하나**만 수행 |
| 순차 (sequential) | 앞 요소의 **출력이 다음 요소의 입력** |
| 통신 (communication) | **같은 데이터**를 사용하는 요소들의 묶음 |
| 절차 (procedural) | 정해진 **순서대로** 수행되는 묶음 |
| 시간 (temporal) | **같은 시점**(초기화 등)에 실행되는 묶음 |
| 논리 (logical) | **유사한 성격**의 기능을 하나로 묶고 골라 씀 |
| 우연 (coincidental) | **아무 관련 없는** 요소의 묶음 |

**팬인/팬아웃** — 팬인: 해당 모듈을 **호출하는** 상위 모듈 수(높으면 재사용 잘됨), 팬아웃: 해당 모듈이 **호출하는** 하위 모듈 수.

### 3-6. 통합·인터페이스 용어 (⬇ 저빈출 — 용어만)

기출 복원 기준 출제 빈도가 낮아 이름과 한 줄 정의만 정리합니다(축소 사유 표기): **JSON**(속성-값 쌍의 경량 데이터 교환 형식), **XML**(태그 기반 마크업), **AJAX**(비동기 통신으로 페이지 전체 새로고침 없이 데이터 갱신), **EAI**(기업 내 애플리케이션 통합 — 포인트 투 포인트/허브 앤 스포크/메시지 버스/하이브리드 유형).

| `계산(합계, 인원수)` — 값 두 개만 넘김 | **자료 결합도** | 데이터만 전달 (가장 바람직) |
| `출력(성적표객체)` — 필요한 건 평균뿐인데 객체 전체를 넘김 | **스탬프 결합도** | 자료 구조째 전달 |
| `처리(data, flag)` — flag가 1이면 저장, 2면 삭제하도록 지시 | **제어 결합도** | 동작 지시 플래그 |
| 모든 모듈이 전역 변수 `g_total`을 읽고 씀 | **공통 결합도** | 전역 공유 |
| 한 모듈이 "파일 열기 → 읽기 → 닫기"를 순서대로 수행 | **절차적 응집도** | 순서 기반 묶음 |
| `초기화()` — 시작 시점에 화면·변수·로그를 한꺼번에 준비 | **시간적 응집도** | 같은 시점 묶음 |

판정 절차: 결합도는 "**무엇을** 주고받는가"(값<구조<지시<전역<내부), 응집도는 "**왜** 한 모듈에 모였는가"(단일 기능이 최선, 우연이 최악).

### Step 4. 경계값 분석 미니 실습

> 문제: 입력 점수의 유효 범위가 1~100일 때, 경계값 분석으로 시험할 대표 값을 고르시오.

**답: 0, 1, 100, 101** (경계 바로 안팎) — 필요 시 2, 99까지 확장. 동등 분할이라면 유효(예: 50)·무효(예: -10, 200) 대표값 하나씩입니다. 두 기법의 답이 어떻게 다른지가 출제 포인트입니다.

### Step 5. 커버리지 세기

**언어: C · 난이도: 🔴 심화 · 학습 개념: 구문 vs 분기 커버리지**

```c
void f(int x) {
    if (x > 0) {
        printf("P");
    }
    printf("E");
}
```

| 테스트 케이스 | 구문(문장) 커버리지 | 결정(분기) 커버리지 |
|---|---|---|
| `x = 5` 하나만 | **100%** (모든 문장 실행) | 50% (참 분기만 — 거짓 미실행) |
| `x = 5`, `x = -1` | 100% | **100%** (참·거짓 모두) |

"구문 100%여도 분기는 100%가 아닐 수 있다" — 커버리지 강도의 차이를 보여 주는 전형 예제입니다.

## ⑤ 자주 하는 실수

| 혼동/실수 | 왜 틀리나 | 해결 |
|---|---|---|
| 기능 vs 비기능 판정 | "2초 이내 검색"에서 검색만 보고 기능으로 판정 | **숫자·품질 단어(초·%·보안)** 가 보이면 비기능 |
| 스텁 ↔ 드라이버 반대로 | 방향 감각 없이 외움 | 하향식(위부터)→아래 빈자리 **스텁**, 상향식→위 빈자리 **드라이버** |
| 결합도 순서를 좋은 쪽부터인지 헷갈림 | 문제마다 "낮은 것부터/높은 것부터"가 다름 | 두문자(자스제외공내)는 **좋음→나쁨** 고정으로 외우고, 문제 방향에 맞춰 뒤집기 |
| 응집도에서 순차 vs 절차 | 둘 다 "순서"가 있음 | **출력→입력으로 이어지면 순차**, 그냥 실행 순서만 있으면 절차 |
| 패턴 분류 착오 (옵서버를 구조로 등) | 이름만 외우고 분류를 안 외움 | 생성 5개(싱팩추빌프)를 먼저 고정 — 나머지에서 구조 7·행위 11 |
| 템플릿 메서드 vs 스트래티지 | 둘 다 "알고리즘 교체" 느낌 | **상속으로 골격 고정 = 템플릿 메서드**, **객체 교체로 알고리즘 선택 = 스트래티지** |
| 유스케이스를 구조 다이어그램으로 분류 | 그림이 정적으로 보임 | 유스케이스는 **행위(동적)** — 기능(동작)을 표현 |
| 알파 ↔ 베타 반대로 | 순서만 외움 | **알파 = 개발자 환경**(통제된 곳), **베타 = 사용자 환경** |

## 마무리

**오늘의 요약** — 요구사항은 동작(기능) vs 품질·숫자(비기능), 개발 절차는 도출→분석→명세→확인입니다. UML은 구조(클래스·컴포넌트·배치…) vs 행위(유스케이스·시퀀스·활동…), 패턴은 생성 5(싱팩추빌프)·구조 7·행위 11이며 설명→용어 방향이 실전입니다. 테스트는 단위→통합→시스템→인수, 블랙박스(명세: 동등 분할·경계값) vs 화이트박스(구조: 커버리지), 하향식-스텁·상향식-드라이버. 결합도는 자스제외공내(좋음→나쁨), 응집도는 기순통절시논우(좋음→나쁨)입니다.

**복습 체크리스트**

- [ ] 결합도 6단계·응집도 7단계를 두문자로 재현할 수 있다
- [ ] 대표 패턴 8개의 시험 표현을 설명→용어 방향으로 즉답할 수 있다
- [ ] 스텁/드라이버를 방향과 함께 설명할 수 있다
- [ ] 구문 100% ≠ 분기 100%인 이유를 Step 5 예제로 설명할 수 있다
- [ ] UML 구조/행위 분류에서 대표 3종(클래스·유스케이스·시퀀스)을 짝지을 수 있다

**과제** — ① Step 2의 10문항을 카드(앞: 설명, 뒤: 용어)로 만들어 3회전, ② 결합도·응집도 각 단계의 판정 키워드를 자기 말로 한 줄씩 정리, ③ 오답노트에 이론 오답 전용 구역 만들기(철자 틀린 용어는 3회 반복 기입). (형성평가는 12강 과제에 통합)

**다음 강 예고** — 12강은 시스템 계열(네트워크·보안·운영체제)입니다. OSI 7계층 짝짓기, 암호화 분류(대칭/비대칭/해시), 공격 유형 용어에 더해 **HRN 우선순위와 페이지 교체(FIFO/LRU) 계산 문제**를 손으로 풉니다. 6주차 형성평가가 과제로 나갑니다.
