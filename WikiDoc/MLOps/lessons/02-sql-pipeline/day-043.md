## ③ 개념 설명

### ETL — 세 단계

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| **Extract** | 외부에서 **원본 그대로** 가져오기 | 재시도 (원본이 안 바뀌면 안전) |
| **Transform** | 정제·검증·스키마에 맞게 변환 | 코드 고치고 재실행 (**API 재호출 불필요**) |
| **Load** | DB에 적재 | 재실행 (**멱등이면 안전**) |

```
   [외부 API]
        │  Extract          원본을 파일로 저장 (raw/)      ← 되돌아올 수 있는 지점
        ▼
   [원본 JSON/CSV]
        │  Transform        정제·타입 변환·키 매핑
        ▼
   [적재용 행 목록]
        │  Load             staged_upsert
        ▼
   [PostgreSQL]
```

**Extract 결과를 파일로 남기는 것**이 핵심입니다.

> **"파싱 로직이 틀렸다"는 것은 대개 며칠 뒤에 발견됩니다.**
> 원본을 남겨 뒀다면 Transform만 고쳐 다시 돌리면 됩니다.
> 안 남겼다면 그 기간 데이터는 **영원히 복구 불가**입니다. API가 과거 데이터를 안 주는 경우가 많습니다.

### ETL vs ELT

| | 변환 위치 | 언제 |
|---|---|---|
| **ETL** | 적재 **전에** 파이썬에서 | 원본이 크고, 필요한 부분만 쓸 때 |
| **ELT** | 적재 **후에** SQL로 | DB가 강력할 때 (클라우드 웨어하우스) |

**실무는 대개 섞어 씁니다.** 원본을 거의 그대로 적재하고(`raw` 스키마), SQL로 정제해 분석용 테이블을 만듭니다.
이 과정에서는 **ETL을 기본**으로 하되, 원본 보존은 파일로 합니다.

### 의존 방향 ★

```
cli.py  ──▶  runner.py  ──▶  stages/  ──▶  sources/ · loader.py · db.py
                                              (아무도 위를 모름)
```

| 규칙 | 이유 |
|---|---|
| **아래층은 위층을 모른다** | `loader.py` 가 `runner` 를 import 하면 순환 참조 |
| **각 단계는 입력과 출력만 안다** | Transform은 데이터가 어디서 왔는지 몰라야 테스트 가능 |
| **설정은 위에서 아래로 주입** | 하위 모듈이 `os.getenv` 를 직접 읽지 않기 |

[Day 013](../01-python-data/day-013.md)의 그 규칙입니다. **데이터 파이프라인이라고 다르지 않습니다.**

### 멱등성 (idempotency) ★★

> **같은 입력으로 몇 번을 실행해도 결과가 같은 성질.**

```
f(f(x)) = f(x)
```

**왜 중요한가** — 배치는 **반드시 실패합니다.** 네트워크·디스크·배포·타임아웃.
멱등하지 않으면 실패할 때마다 **사람이 데이터를 손으로 정리**해야 합니다.

멱등하면 복구 절차가 **"다시 실행"** 한 줄이 됩니다.

| 방법 | 구현 | 적합 |
|---|---|---|
| **① upsert** | `ON CONFLICT (멱등키) DO UPDATE` | 대부분 ★ |
| **② 파티션 교체** | `DELETE WHERE 날짜=X` → `INSERT` | 하루치를 통째로 다시 만들 때 |
| **③ 전체 교체** | `TRUNCATE` → `COPY` | 작은 마스터 테이블 |

②는 이렇게 씁니다. **한 트랜잭션 안에서** 해야 안전합니다.

```sql
BEGIN;
DELETE FROM measurement WHERE measured_at >= :day AND measured_at < :next_day;
INSERT INTO measurement ...;
COMMIT;
```

> **②의 장점** — 원본에서 **행이 사라진 경우**도 반영됩니다.
> upsert는 새로 온 것만 반영하므로, 원본에서 삭제된 행이 DB에 남습니다.
> **"원본이 진실의 원천"** 이라면 ②가 정확합니다.

### 증분 적재와 워터마크

매일 전체를 다시 받으면 낭비입니다. **"어디까지 처리했는지"** 를 기록해 그 뒤만 가져옵니다.

```
watermark = 2025-06-01 09:00     ← 여기까지 처리함
다음 실행  →  measured_at >= 09:00 - 여유  AND  < now()
```

| 개념 | 설명 |
|---|---|
| **워터마크(watermark)** | 처리 완료 지점. 보통 `MAX(측정시각)` |
| **겹침 여유(overlap)** | 워터마크에서 조금 **앞으로 되돌려** 다시 가져옴 |
| **지연 도착(late arriving)** | 늦게 들어오는 데이터. 겹침 여유로 흡수 |

**겹침 여유가 왜 필요한가** — 데이터가 항상 시간순으로 도착하지 않기 때문입니다.

```
09:00 배치 실행  →  08:00~08:59 데이터 수집, 워터마크 = 08:59
09:10  08:30 측정값이 뒤늦게 API에 올라옴    ★ 다음 배치는 09:00 이후만 봄 → 영원히 누락

겹침 여유 3시간을 두면  →  다음 배치가 05:59 부터 다시 훑어 흡수
```

**겹침이 안전한 이유가 바로 멱등성입니다.** 이미 있는 건 `DO UPDATE` 로 덮어쓸 뿐입니다.

> **구간은 반열림(`>= 시작 AND < 끝`)으로.** [Day 032](day-032.md)에서 배운 그대로입니다.
> `<=` 를 쓰면 경계의 데이터가 두 배치에 걸쳐 처리되거나 누락됩니다.

### 백필 (backfill)

과거 구간을 다시 채우는 작업입니다.

| 언제 | 예 |
|---|---|
| 파싱 버그를 고쳤을 때 | 지난 한 달치를 다시 변환 |
| 새 열을 추가했을 때 | 과거 데이터에 값 채우기 |
| 배치가 며칠 죽어 있었을 때 | 빈 구간 메우기 |

```powershell
$ datapipe backfill --from 2025-05-01 --to 2025-06-01
```

**하루씩 끊어서** 처리합니다. 한 번에 하면 메모리·트랜잭션이 커지고, 실패 시 되돌릴 양이 큽니다.

### 실행 기록 — `ingest_run`

```
run_id 1  | air_seoul | 09:00 시작 | 09:02 종료 | success | 읽음 2400 | 쓴 2400
run_id 2  | air_seoul | 10:00 시작 | 10:00 종료 | failed  | 읽음    0 | 오류: timeout
```

**있으면 답할 수 있는 질문들**

- "어제 데이터가 왜 없죠?" → 그 시각 실행이 실패했는지 즉시 확인
- "이 이상한 값이 언제 들어왔죠?" → `run_id` 로 추적
- "배치가 점점 느려지나요?" → 소요 시간 추이

### Step 3. Transform — 정제와 키 매핑

`src/datapipe/stages/load_db.py` 의 앞부분입니다.

```python
"""수집 결과를 DB 스키마에 맞는 행으로 변환하고 적재합니다."""

from __future__ import annotations

import logging
from datetime import datetime, timezone, timedelta
from typing import Any, Iterable

from ..db import connect, fetch_all
from ..loader import staged_upsert
from ..models import StageError

logger = logging.getLogger(__name__)

KST = timezone(timedelta(hours=9))

MEASUREMENT_COLUMNS = ("station_id", "measured_at", "pm10", "pm25")
MEASUREMENT_KEYS = ("station_id", "measured_at")


def _to_int(value: Any) -> int | None:
    """'45' → 45, '-' · '' · None → None.

    공공데이터 API 는 결측을 '-' 로 표기합니다. 0 으로 바꾸면 안 됩니다
    ("측정 안 됨"과 "농도 0"은 다른 정보입니다 — Day 032).
    """
    if value in (None, "", "-", "N/A"):
        return None
    try:
        return int(float(value))
    except (TypeError, ValueError):
        logger.warning("정수 변환 실패, NULL 처리: %r", value)
        return None


def _to_timestamp(value: str) -> datetime | None:
    """'2025-06-01 14:00' → timezone-aware datetime.

    API 가 시간대 없는 문자열을 주므로 KST 를 명시합니다.
    이걸 빠뜨리면 서버 시간대에 따라 9시간이 어긋납니다 (Day 038).
    """
    if not value:
        return None
    text = value.strip()
    if text.endswith("24:00"):                     # API가 자정을 24:00 으로 표기
        base = datetime.strptime(text[:10], "%Y-%m-%d").replace(tzinfo=KST)
        return base + timedelta(days=1)
    try:
        return datetime.strptime(text, "%Y-%m-%d %H:%M").replace(tzinfo=KST)
    except ValueError:
        logger.warning("시각 변환 실패: %r", value)
        return None


def load_station_map() -> dict[str, int]:
    """측정소명 → station_id 매핑을 미리 읽어 둡니다.

    행마다 SELECT 하면 2400번 왕복합니다 (Day 036 상관 서브쿼리와 같은 문제).
    """
    rows = fetch_all("SELECT station_id, name FROM station")
    return {r["name"]: r["station_id"] for r in rows}


def transform(records: Iterable[dict], station_map: dict[str, int]) -> tuple[list[tuple], list[dict]]:
    """API 응답을 적재용 행으로 변환합니다.

    Returns:
        (적재할 행 목록, 버려진 행과 사유 목록)
    """
    rows: list[tuple] = []
    rejected: list[dict] = []

    for rec in records:
        name = (rec.get("stationName") or "").strip()
        station_id = station_map.get(name)
        if station_id is None:
            rejected.append({"reason": "unknown_station", "record": rec})
            continue

        measured_at = _to_timestamp(rec.get("dataTime", ""))
        if measured_at is None:
            rejected.append({"reason": "bad_timestamp", "record": rec})
            continue

        rows.append((
            station_id,
            measured_at,
            _to_int(rec.get("pm10Value")),
            _to_int(rec.get("pm25Value")),
        ))

    logger.info("변환: 입력 %d건 → 적재 %d행 · 제외 %d행",
                len(rows) + len(rejected), len(rows), len(rejected))
    return rows, rejected
```

**세 가지에 주목하세요.**

| 설계 | 이유 |
|---|---|
| `_to_int` 가 `'-'` 를 **`None` 으로** (0 아님) | "측정 안 됨"과 "농도 0"은 다른 정보 |
| `_to_timestamp` 가 **시간대를 명시** | 안 하면 9시간이 조용히 어긋남 |
| `rejected` 를 **버리지 않고 반환** | 왜 빠졌는지 알아야 함 → [Day 044](day-044.md)에서 격리 테이블로 |

**이 함수들은 DB도 API도 필요 없습니다.** 그래서 테스트가 쉽습니다.

```python
def test_결측은_None_이_된다():
    assert _to_int("-") is None
    assert _to_int("") is None
    assert _to_int("45") == 45


def test_시각에_KST_가_붙는다():
    ts = _to_timestamp("2025-06-01 14:00")
    assert ts.utcoffset() == timedelta(hours=9)


def test_자정_24시_표기():
    ts = _to_timestamp("2025-06-01 24:00")
    assert ts.day == 2 and ts.hour == 0
```

### Step 4. Load 단계

같은 파일의 뒷부분입니다.

```python
from .base import Stage


class LoadDBStage(Stage):
    """정제된 레코드를 DB에 멱등 적재합니다."""

    name = "load_db"

    def run(self, records: list[dict], ctx) -> dict:
        station_map = load_station_map()
        if not station_map:
            raise StageError("station 테이블이 비어 있습니다. 마스터 데이터를 먼저 적재하세요.")

        rows, rejected = transform(records, station_map)

        if not rows:
            logger.warning("적재할 행이 없습니다 (입력 %d건)", len(records))
            return {"loaded": 0, "rejected": len(rejected)}

        affected = staged_upsert(
            rows,
            table="measurement",
            columns=MEASUREMENT_COLUMNS,
            conflict_keys=MEASUREMENT_KEYS,
            update_columns=("pm10", "pm25"),
        )
        return {"loaded": affected, "rejected": len(rejected), "rejected_rows": rejected}
```

### Step 5. 워터마크

`src/datapipe/watermark.py`:

```python
"""증분 적재를 위한 워터마크 관리."""

from __future__ import annotations

import logging
from datetime import datetime, timedelta, timezone

from .db import execute, fetch_one

logger = logging.getLogger(__name__)

KST = timezone(timedelta(hours=9))

# 지연 도착 데이터를 흡수하기 위한 겹침 여유.
# 3시간으로 정한 근거: 공공데이터 API 가 관측 후 최대 2시간 지연 공개 (2026-08 기준 측정),
# 여기에 1시간 안전 마진. 멱등 적재이므로 겹쳐도 중복되지 않습니다.
OVERLAP = timedelta(hours=3)


def get_watermark(source: str, default_days: int = 7) -> datetime:
    """마지막 처리 지점을 반환합니다. 기록이 없으면 default_days 전부터."""
    row = fetch_one(
        "SELECT watermark_at FROM ingest_watermark WHERE source = %s", (source,)
    )
    if row is None:
        start = datetime.now(KST) - timedelta(days=default_days)
        logger.info("워터마크 없음 — %s 부터 시작", start.date())
        return start
    return row["watermark_at"]


def set_watermark(source: str, value: datetime) -> None:
    """워터마크를 갱신합니다. 뒤로 되돌아가지는 않습니다."""
    execute(
        """
        INSERT INTO ingest_watermark (source, watermark_at, updated_at)
        VALUES (%s, %s, now())
        ON CONFLICT (source) DO UPDATE
        SET watermark_at = GREATEST(ingest_watermark.watermark_at, EXCLUDED.watermark_at),
            updated_at   = now()
        """,
        (source, value),
    )


def window(source: str) -> tuple[datetime, datetime]:
    """이번 실행에서 가져올 구간 [시작, 끝) 을 반환합니다."""
    start = get_watermark(source) - OVERLAP
    end = datetime.now(KST)
    logger.info("수집 구간: %s ~ %s (겹침 %s)", start, end, OVERLAP)
    return start, end
```

**`GREATEST` 를 쓴 이유** — 백필로 과거를 처리했을 때 워터마크가 **뒤로 밀리면 안 되기** 때문입니다.
과거 구간을 다시 돌렸다고 "여기까지만 처리했다"로 기록되면, 그 사이 데이터를 다시 수집하게 됩니다.

테이블도 만들어 둡니다.


### Step 6. 파이프라인 조립

`src/datapipe/runner.py` 에 ETL 실행 함수를 추가합니다.

```python
def run_etl(source_name: str, ctx: Context, *, since=None, until=None) -> dict:
    """Extract → Transform → Load 를 한 번 실행합니다."""
    from .watermark import set_watermark, window

    if since is None or until is None:
        since, until = window(source_name)

    run_id = start_run(source_name, since, until)          # ingest_run 에 기록
    try:
        # ① Extract — 원본을 파일로 남긴 뒤 파싱
        records = collect_stage.run(source_name, since, until, ctx)
        logger.info("수집 %d건", len(records))

        # ② Transform + ③ Load
        result = load_db_stage.run(records, ctx)

        # ④ 워터마크 갱신 — 성공했을 때만
        if result["loaded"] > 0:
            set_watermark(source_name, until)

        finish_run(run_id, "success", read=len(records), written=result["loaded"])
        return {"run_id": run_id, **result}

    except Exception as exc:
        finish_run(run_id, "failed", error=str(exc))
        logger.exception("ETL 실패: %s", source_name)
        raise
```

**순서가 중요합니다.**

| 순서 | 이유 |
|---|---|
| 워터마크 갱신을 **마지막에** | 적재가 실패했는데 워터마크가 올라가면 **그 구간을 영원히 건너뜀** ★ |
| `finish_run` 을 **성공·실패 모두** | 실패 기록이 없으면 "왜 데이터가 없는지" 알 수 없음 |
| 예외를 **다시 던짐(`raise`)** | 삼켜 버리면 스케줄러가 성공으로 오인 |

`ingest_run` 기록 함수입니다.

```python
def start_run(source: str, since, until) -> int:
    return fetch_value(
        """
        INSERT INTO ingest_run (source, window_start, window_end, status)
        VALUES (%s, %s, %s, 'running')
        RETURNING run_id
        """,
        (source, since, until),
    )


def finish_run(run_id: int, status: str, *, read: int = 0,
               written: int = 0, error: str | None = None) -> None:
    execute(
        """
        UPDATE ingest_run
        SET status = %s, finished_at = now(),
            rows_read = %s, rows_written = %s, error_message = %s
        WHERE run_id = %s
        """,
        (status, read, written, error, run_id),
    )
```

### 워터마크를 적재 **전에** 갱신함

**해결** — 워터마크는 **적재 성공을 확인한 뒤에만** 갱신합니다.

## ⑥ 확인 문제

**1.** 멱등성을 한 문장으로 정의하고, 아래 세 가지 구현 중 이 데이터에 무엇이 맞는지 고르세요.

> 상황: 증권사 API에서 일별 시세를 받습니다. **거래 후 정정 공시로 과거 값이 바뀔 수 있습니다.**

```
① ON CONFLICT DO NOTHING
② ON CONFLICT DO UPDATE
③ DELETE WHERE 날짜=X → INSERT
```

<details>
<summary>답 보기</summary>

**정의** — 같은 입력으로 몇 번을 실행해도 **결과 상태가 같은** 성질. `f(f(x)) = f(x)`

**②와 ③ 중에서 고르고, ①은 탈락입니다.**

| 방법 | 정정 반영 | 삭제 반영 | 판정 |
|---|---|---|---|
| ① `DO NOTHING` | ❌ 첫 값이 남음 | ❌ | **탈락** — 정정 공시가 반영 안 됨 |
| ② `DO UPDATE` | ✅ | ❌ 원본에서 사라진 행이 DB에 남음 | 조건부 적합 |
| ③ `DELETE`+`INSERT` | ✅ | ✅ | **가장 정확** |

**"원본이 진실의 원천"이라면 ③입니다.**
상장폐지·거래정지로 원본에서 행이 사라졌을 때, ②는 옛 데이터를 계속 들고 있습니다.

```sql
BEGIN;
DELETE FROM stock_price WHERE traded_on = %s;
INSERT INTO stock_price (...) SELECT ... FROM stg;
COMMIT;
```

**반드시 한 트랜잭션 안에서** 해야 합니다. 중간에 죽으면 그날 데이터가 **통째로 사라진 상태**로 남습니다.

**②를 고르는 경우** — 데이터가 워낙 커서 하루치를 통째로 다시 받는 비용이 큰 경우입니다.
그때는 "삭제 반영이 안 된다"는 **한계를 문서에 명시**하고, 주기적으로(주 1회) ③으로 전체 재구축합니다.

> **이 결정은 데이터의 성질에서 나옵니다.**
> 센서 측정값처럼 **한 번 기록되면 안 바뀌는** 데이터는 ①이 가장 빠르고 안전합니다.
> "이 데이터는 나중에 바뀔 수 있는가?"를 먼저 물으세요.
</details>

**2.** 아래 코드에 심각한 버그가 있습니다. 찾아서 고치고, 이 버그가 만드는 **최악의 시나리오**를 쓰세요.

```python
def run_etl(source: str) -> None:
    since, until = window(source)
    set_watermark(source, until)
    records = extract(source, since, until)
    rows = transform(records)
    load(rows)
```

<details>
<summary>답 보기</summary>

**버그 — 워터마크를 적재 전에 갱신합니다.**

**최악의 시나리오**

```
09:00  워터마크 갱신 (09:00)  →  extract 성공  →  load 에서 DB 연결 끊김 → 실패
10:00  다음 실행: 09:00 - 겹침 3시간 = 06:00 부터 수집

        06:00~09:00 구간은 겹침 덕분에 우연히 복구됨.

그러나 배치가 4시간 이상 죽어 있었다면:
09:00  워터마크 09:00 로 갱신, 적재 실패
13:00  겹침 3시간 → 10:00 부터 수집  ★ 09:00~10:00 데이터 영구 누락
```

**더 나쁜 경우** — 실패가 반복되면 워터마크만 계속 전진합니다.

```
09:00 실패 (워터마크 09:00) → 10:00 실패 (10:00) → 11:00 실패 (11:00) → 12:00 성공
  →  09:00 ~ 09:00 구간만 수집. 3시간이 통째로 비어 있음
  →  에러 로그는 남지만, 12:00 성공 로그만 보면 "정상"으로 보임 ★
```

**그리고 이 구멍은 조용합니다.** 나중에 그 시간대 데이터로 학습한 모델이 이상해지고 나서야 발견됩니다.

**고친 코드**

```python
def run_etl(source: str) -> dict:
    since, until = window(source)
    run_id = start_run(source, since, until)
    try:
        records = extract(source, since, until)
        rows, rejected = transform(records)
        loaded = load(rows)

        if loaded > 0:                      # ① 적재 성공을 확인한 뒤에만
            set_watermark(source, until)

        finish_run(run_id, "success", read=len(records), written=loaded)
        return {"loaded": loaded, "rejected": len(rejected)}

    except Exception as exc:
        finish_run(run_id, "failed", error=str(exc))   # ② 실패도 기록
        raise                                          # ③ 스케줄러에 알림
```

**세 가지가 필요합니다.**

1. **워터마크는 마지막에** — 적재 성공 후
2. **실패 기록** — `ingest_run` 에 남겨야 구멍을 발견할 수 있음
3. **예외 재전파** — 삼키면 스케줄러가 성공으로 오인

**추가 방어** — [Day 045](day-045.md)에서 배울 **구멍 탐지 쿼리**를 정기적으로 돌립니다.

```sql
-- 시간당 데이터가 있어야 하는데 비어 있는 시각 찾기
SELECT g.hour
FROM generate_series(
        date_trunc('hour', now() - interval '7 days'),
        date_trunc('hour', now()), interval '1 hour') AS g(hour)
LEFT JOIN measurement m ON date_trunc('hour', m.measured_at) = g.hour
WHERE m.measurement_id IS NULL
ORDER BY g.hour;
```

**멱등성 덕분에 구멍을 발견하면 백필 한 줄로 메울 수 있습니다.**

**3.** Extract 결과를 파일로 남기는 것이 왜 중요한가요? 남기지 않았을 때만 생기는 문제를 구체적으로 쓰세요.

<details>
<summary>답 보기</summary>

**핵심 — Transform 이후 단계는 언제든 다시 할 수 있지만, Extract는 시간이 지나면 다시 못 합니다.**

```
[외부 API]  ←─── 과거 데이터를 안 주거나, 주더라도 값이 달라져 있을 수 있음
     │ Extract
     ▼
[원본 파일]  ←─── 여기가 있으면 아래는 몇 번이든 다시 가능
     │ Transform  ← 코드 버그를 고치고 재실행
     ▼
[적재용 행]
     │ Load       ← 멱등이므로 재실행 안전
     ▼
[DB]
```

**남기지 않았을 때만 생기는 문제**

| 상황 | 원본이 있으면 | 없으면 |
|---|---|---|
| 파싱 버그 발견 (열 매핑 오류) | Transform만 고쳐 백필 | **그 기간 데이터 영구 손실** |
| 새 필드가 필요해짐 (O3를 추가하기로) | 과거 원본에서 추출 | 과거는 NULL로 남음 |
| "이 값이 맞나?" 검증 요청 | 원본과 대조 | 확인 불가 |
| API 스펙이 바뀌어 이전 코드가 깨짐 | 옛 원본으로 회귀 테스트 | 재현 불가 |
| 감사·규제 대응 | "서버가 준 그대로" 제시 | 증빙 없음 |

**실제 사례 형태** — 공공데이터 API가 예고 없이 `pm25Value` 필드명을 `pm25` 로 바꾸면
파싱이 조용히 `None` 을 넣습니다. 대시보드에서 PM2.5가 빈칸이 되고 나서야 발견합니다.
그때 **원본만 있으면** 파서를 고쳐 며칠치를 되돌립니다.

**저장 규칙**

| 규칙 | 이유 |
|---|---|
| **가공하지 않는다** | 인코딩 변환·정렬·들여쓰기 전부 금지. 바이트 그대로 |
| 날짜별 디렉터리 + `run_id` | 어느 실행의 결과인지 추적 |
| 압축 (`.json.gz`) | 용량 (텍스트는 보통 10:1) |
| 보관 기간 정책 | 무한 보관은 비쌈. 90일 후 아카이브 등 |

> **비용 감각** — 하루 10MB면 1년에 3.6GB, 압축하면 400MB 남짓입니다.
> 클라우드 오브젝트 스토리지에서 몇백 원 수준입니다.
> **"데이터 손실 한 번"의 비용과 비교하면 무료나 마찬가지**입니다.
>
> 이 개념을 확장하면 **데이터 레이크**(원본 그대로 보관)와
> **메달리온 아키텍처**(bronze 원본 → silver 정제 → gold 집계)가 됩니다.
> W23–W24에서 다시 만납니다.

## 오늘의 정리

| 개념 | 요약 |
|---|---|
| **Extract** | 원본을 **가공 없이** 파일로 저장 → 되돌아올 수 있는 지점 |
| **Transform** | 정제·타입 변환·키 매핑. **DB·API 없이 테스트 가능해야 함** |
| **Load** | `staged_upsert` — 멱등 |
| **멱등성** | `f(f(x)) = f(x)` — 몇 번을 돌려도 결과가 같음 |
| **워터마크** | 처리 완료 지점. **적재 성공 후에만** 갱신 |
| **겹침 여유** | 지연 도착 흡수. 멱등하면 공짜 |
| **백필** | 과거 재처리. **하루씩 끊어서** |
| **`ingest_run`** | 성공·실패 모두 기록. **실패 기록이 더 중요** |

| 함정 | 방어 |
|---|---|
| 워터마크를 적재 전에 갱신 | 성공 확인 후에만 (구멍이 조용히 생김) |
| 겹침 없이 `MAX(시각)` | 지연 도착 영구 누락 |
| 원본 미저장 | 파싱 버그 = 영구 손실 |
| 결측을 0으로 | 평균이 왜곡됨 |
| 시간대 누락 | 9시간 어긋남 |
| 행마다 `SELECT` 로 키 조회 | 매핑을 딕셔너리로 미리 |
| 예외를 삼킴 | 배치는 성공, 데이터는 0행 |
