## 3. 개념

### 3-1. 마일스톤

**왜 필요한가** — "완료"의 기준.

| 주차 | 마일스톤 | 완료 기준 |
|:--:|---|---|
| **W21** | 프로토타입 | 핵심 조작 루프가 플레이 가능 |
| **W22** | 알파 | 모든 시스템 구현, 빌드로 완주 가능 |
| **W23** | 베타 | 콘텐츠·연출 완료, 외부 테스트 |
| **W24** | 릴리즈 | 치명 버그 0, 패키징·문서 완료 |

```
   ★ 각 단계의 의미

   프로토타입: "재미있는가?"를 확인
   알파:       "게임이 되는가?"를 확인
   베타:       "완성도가 있는가?"를 확인
   릴리즈:     "남에게 줄 수 있는가?"를 확인
```

```
   ★ 완료 기준은 검증 가능해야 한다

   ✗ "전투가 재미있다"          → 주관적
   ✔ "적 3마리를 처치할 수 있다" → 확인 가능
```

### 3-2. 프로토타입 (W21)

**왜 필요한가** — 가장 중요한 주.

```
   ★ 목적

   "이 게임이 재미있는가?"를 확인한다
```

```
   ★ 만드는 것

   ① 핵심 루프 한 바퀴
   ② 회색 박스로 (아트 없이)
   ③ 임시 값으로 (밸런싱 없이)
```

```
   ★ 안 만드는 것

   × UI 꾸미기
   × 메뉴·타이틀
   × 사운드
   × 이펙트
   × 최적화
```

```
   ⚠️ 프로토타입에서 아트를 하면

   "예뻐 보여서" 재미 없는 게임을 계속 만들게 된다
   → 회색 박스로 판단한다
```

```
   ★ W21 종료 시점의 질문

   "이 루프를 10번 반복하고 싶은가?"

   NO → 지금 바꾼다. 아직 늦지 않았다
   YES → 계속 진행
```

### 3-3. 알파 (W22)

**왜 필요한가** — 기능 완성.

```
   ★ 목적

   "처음부터 끝까지 플레이할 수 있는가?"
```

```
   ★ 완료 기준

   ① Must 목록 전부 구현
   ② 타이틀 → 게임 → 결과 → 재시작
   ③ 빌드해서 완주 가능
   ④ 치명 버그(진행 불가)가 없다
```

```
   ⚠️ 알파에서 반드시 빌드한다

   "에디터에서만 되는" 상태를 3주차까지 끌면 위험
   → Day 96의 빌드 문제를 미리 발견
```

```
   ★ Feature Freeze

   W22 종료 = 새 기능 추가 금지
   → 이후는 다듬기만
```

### 3-4. 베타 (W23)

**왜 필요한가** — 완성도.

```
   ★ 목적

   "남에게 보여줄 수 있는가?"
```

```
   ★ 하는 일

   ① 콘텐츠 채우기 (층, 적, 무기 수량)
   ② 연출 (이펙트, 사운드, 타격감)
   ③ 밸런싱
   ④ UI 다듬기
   ⑤ 외부 테스트  ★
```

```
   ★ 외부 테스트가 핵심이다

   만든 사람은 게임을 안다
   → 처음 보는 사람이 헤매는 곳을 못 본다

   ★ 방법
   ① 다른 팀원 3명에게 빌드를 준다
   ② 아무 설명 없이 플레이하게 한다
   ③ 옆에서 관찰만 한다 (도와주지 않는다)  ★
   ④ 막히는 지점을 기록한다
```

```
   ⚠️ 관찰 시 절대 하면 안 되는 말

   "아, 그건 이렇게 하는 거예요"
   → 그 순간 테스트가 무의미해진다
   → 참는다
```

### 3-5. 릴리즈 (W24)

**왜 필요한가** — 전달 가능한 상태.

```
   ★ 완료 기준

   ① 치명 버그 0 (진행 불가, 크래시)
   ② 빌드가 다른 PC에서 실행됨
   ③ README + 조작 설명
   ④ 시연 영상 (선택)
   ⑤ 포트폴리오 문서
```

```
   ★ W24는 버퍼다

   ① 새 기능 없음
   ② 밀린 일정을 흡수
   ③ 발표 준비
```

```
   ⚠️ W24에 기능을 만들고 있으면

   → 일정이 실패한 것
   → W21~22에서 범위를 못 깎은 결과
```

### 3-6. 역할 분담

**왜 필요한가** — 충돌을 줄인다.

```
   ★ 분담 기준 3가지

   ① 기능 단위    가장 흔하다
   ② 씬 단위      Unity에서 효과적 (Day 97)
   ③ 레이어 단위  로직/UI/아트
```

**4인 팀 예시**

| 역할 | 담당 | 주요 파일 |
|---|---|---|
| **A** 게임플레이 | 플레이어, 전투, 무기 | `Scripts/Player/`, `Scripts/Combat/` |
| **B** AI | 적, 보스, 밸런싱 | `Scripts/AI/`, `Data/Enemies/` |
| **C** 시스템·UI | 층 진행, UI, 세이브 | `Scripts/Game/`, `Scripts/UI/` |
| **D** 아트·연출 | 애셋, 이펙트, 사운드 | `Art/`, `Audio/`, `Prefabs/FX/` |

```
   ★ 폴더로 나누면 충돌이 거의 없다

   A는 Scripts/Player/ 만 만진다
   B는 Scripts/AI/ 만 만진다
```

```
   ⚠️ 공유 파일 관리

   GameManager.cs 같은 것은 여럿이 만진다
   → 담당자를 정한다 (예: C)
   → 다른 사람은 요청한다
```

**2인 팀 예시**

| 역할 | 담당 |
|---|---|
| A | 플레이어·전투·적 AI |
| B | 시스템·UI·아트·사운드 |

**개인 프로젝트**

```
   ★ 순서를 정한다

   1주차: 핵심 루프 (전투)
   2주차: 시스템 (진행, UI)
   3주차: 콘텐츠·연출
   4주차: 다듬기

   → 한 번에 하나씩
```

### 3-7. 작업 분해 (WBS)

**왜 필요한가** — "만든다"를 "오늘 할 일"로.

```
   ★ 분해 원칙

   한 작업 = 반나절~하루
   → 더 크면 쪼갠다
```

```
   ✗ 너무 크다
   "전투 시스템 구현"          (3일?)

   ✔ 적당하다
   "플레이어 이동·회전"        (0.5일)
   "공격 애니메이션 + 이벤트"   (0.5일)
   "히트박스 판정"             (0.5일)
   "데미지 처리 + HP"          (0.5일)
   "회피 (무적 프레임)"        (0.5일)
```

```
   ★ 분해가 잘 됐는지 확인

   "오늘 이걸 끝낼 수 있나?"
   → 확신이 안 서면 더 쪼갠다
```

```
   ★ 각 작업에 완료 조건을 적는다

   "히트박스 판정"
   완료 조건: 공격 시 프레임 12~18에만 판정이 켜지고
             Scene 뷰에서 기즈모로 확인 가능
```

### 3-8. 의존성

**왜 필요한가** — 서로 기다리지 않게.

```
   ★ 문제

   A: "적이 있어야 전투를 테스트하는데"
   B: "플레이어가 있어야 AI가 추격하는데"
   → 둘 다 멈춘다
```

```
   ★ 해결 — 임시 대체물(스텁)

   A: 정지한 캡슐을 적으로 삼아 전투 개발
   B: 자동으로 움직이는 캡슐을 플레이어로 삼아 AI 개발

   → 나중에 교체
```

```csharp
    // ★ 인터페이스로 미리 합의
    public interface IDamageable
    {
        void TakeDamage(DamageInfo info);
        bool IsAlive { get; }
    }
```

```
   ★ Day 83에서 만든 그 인터페이스

   A는 IDamageable에 데미지를 준다
   B는 IDamageable을 구현한다
   → 서로의 구현을 몰라도 된다
```

```
   ★ 의존성 표

   작업              선행 작업          담당
   ─────────────────────────────────────────
   공격 판정         이동 완료          A
   적 추격           NavMesh 베이크     B
   무기 선택 UI      무기 데이터 정의   C
   이펙트 연결       공격 판정          D
```

### 3-9. 일정 배치 원칙

**왜 필요한가** — 순서가 성패를 가른다.

```
   ★ 원칙 1 — 어려운 것을 앞으로

   가장 불확실한 것을 W21에
   → 안 되면 방향을 바꿀 시간이 있다
```

```
   ★ 원칙 2 — 세로로 자른다 (수직 슬라이스)

   ✗ 수평: 모든 시스템을 조금씩
   ✔ 수직: 하나의 완결된 흐름을 먼저

   예)
   ✗ 플레이어 30% + 적 30% + UI 30%
   ✔ "적 1마리를 죽이고 다음 층으로" 완결
```

```
   ★ 원칙 3 — 매일 실행 가능한 상태 유지

   커밋 전 Play가 되는지 확인
   → "빌드가 깨진 채로" 두지 않는다
```

```
   ★ 원칙 4 — 버퍼를 남긴다

   계획: 15일
   가용: 20일
   → 5일 버퍼 (25%)

   ⚠️ 버퍼 없이 짜면 반드시 밀린다
```

```
   ★ 원칙 5 — 금요일은 통합의 날

   각자 작업을 합치고 테스트
   → 주말에 문제를 안고 가지 않는다
```

## 4. 따라 만들기

### Step 1 — 팀 구성

```
   ★ 팀 크기별 특징

   개인:  의사결정 빠름. 범위가 작아야 한다
   2인:   협업 부담 적음. 역할이 명확해야
   3~4인: 콘텐츠가 많아진다. 관리 비용 증가
   5인+:  4주에는 비권장
```

```
   ★ 팀을 짤 때 확인

   ① 만들고 싶은 게임이 비슷한가
   ② 작업 시간대가 맞는가

```

## 6. 자주 막히는 곳

| 증상 | 원인 | 해결 |
|---|---|---|

| 서로 기다림 | 의존성 미고려 | 인터페이스 + 스텁 |
| 씬 충돌 | 여러 명이 수정 | 담당자 1명 + 프리팹 분리 |
| 진척을 모름 | 완료 기준 없음 | 검증 가능한 기준 |
| 버퍼 없음 | 범위 과다 | Day 98로 돌아가 깎는다 |
| 작업이 너무 큼 | 분해 부족 | 반나절 단위로 |
| 한 명이 클론 실패 | 환경 차이 | **오늘 해결** |
| 역할이 겹침 | 폴더 미지정 | 담당 폴더 명시 |
| 애셋을 못 구함 | 계획 없음 | 첫날 목록 확보 |
| 커밋이 안 됨 | 규칙 부재 | 하루 1회 강제 |
| W24에 기능 개발 | 범위 실패 | W22 Feature Freeze |
