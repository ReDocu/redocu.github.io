## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 서비스의 Dockerfile을 작성하고 **층 설계와 다이어트**로 이미지를 절반 이하로 줄일 수 있다.
- 풀스택 Compose(5개 서비스)를 구성해 **팀원 전원의 환경에서 한 줄 기동**을 검증할 수 있다.
- 재학습 DAG에 **게이트(승격/보류)** 를 달고 양쪽 경로를 리허설할 수 있다.
- 시크릿이 저장소·이미지 어디에도 없는 상태를 유지할 수 있다.

## ② 왜 필요한가

W30 내내 "내 환경에서는 되는데"가 네 번 있었습니다 — 서연의 psycopg 버전, 민준의
LightGBM 빌드, 지우의 Node 데모 서버, 하람의 Python 3.11. 각각 30분씩을 먹었죠.
4인 팀에서 환경은 4개가 아니라, 서버까지 5개입니다 — 그리고 다음 주엔 심사위원의
환경이 6번째로 추가됩니다. 환경 차이를 사람이 맞추는 비용은 인원수에 비례해 늘고,
컨테이너는 그 비용을 파일 하나(이미지)로 고정합니다. [Day 116](../05-infra-mlops/day-116.md)
에서 배운 명제의 팀 버전입니다: **"내 컴퓨터에선 되는데"의 종말.**

오늘의 산출물이 이후 전부의 기반이 됩니다 — 내일의 CI/CD는 이 이미지를 빌드·배포하고,
154의 부하 측정은 이 Compose 위에서 돌며, 156의 "빈 서버 리허설"과 최종 심사의
clone→up도 오늘 만든 파일 두 개(Dockerfile · compose.yaml)가 전부입니다. 재현성 20점의
인프라 쪽 절반이 오늘 결정됩니다.

병렬 트랙도 하나 있습니다 — 서연·민준이 재학습 DAG(#26)에 게이트를 답니다. 145 설계
리뷰에서 즉답하지 못했던 그 질문("나쁜 모델이 나오면 그대로 배포되나요?")의 답이 오늘
코드가 됩니다.

## ③ 개념 설명

### Dockerfile 층 설계 — 바뀌는 것을 아래로 보내지 않는다

```
[안 바뀜]  베이스(python:3.12-slim) → 시스템 패키지 → pip 의존(requirements.txt)
[자주 바뀜]                                            → 소스 코드 → 설정
```

의존 설치가 코드 복사보다 **위**에 있어야 코드만 바뀐 빌드에서 의존 층이 캐시로 재사용
됩니다 ([Day 117](../05-infra-mlops/day-117.md)). 내일 CI의 빌드 시간이 이 순서 하나에
달려 있습니다.

### 다이어트의 순서 — 큰 것부터, 실측으로

| 수단 | 효과 (한산 실측) |
|---|---|
| slim 베이스 + `--no-install-recommends` | 1.24GB → 913MB |
| `pip --no-cache-dir` + 빌드 도구 정리 | 913MB → 748MB |
| `.dockerignore` (data/ · mlruns/ · .git · 노트북) | 748MB → **687MB** |

모델 파일이 이미지에 없다는 점에 주목 — 한산은 B방식(레지스트리 로드, 143)이므로
`.dockerignore`에 모델·데이터가 반드시 들어가야 합니다. 항목별로 줄어든 크기를 기록해
두면([Day 118](../05-infra-mlops/day-118.md)의 규율) 발표의 "왜 이 크기인가" 답이 됩니다.

### Compose 5서비스 — 뜨는 순서까지 선언

| 서비스 | 포트 | 헬스체크 | 기동 조건 |
|---|---|---|---|
| nginx | **8080 (유일 노출)** | /health 프록시 | api healthy |
| api | 8000 (내부) | GET /health | db healthy (+ mlflow는 폴백 있어 미대기) |
| db | 5432 (내부) | pg_isready | — · volume: pgdata |
| mlflow | 5000 (내부) | /health | volume: mlartifacts |
| airflow | 8081 (내부) | webserver ping | db healthy · DAG 2개 탑재 |

api가 mlflow를 **기다리지 않는** 것은 어제 만든 폴백 캐시 덕입니다 — 의존성 설계가
코드 설계(폴백)와 맞물리는 지점입니다. 시크릿은 전부 `.env` 주입, `${DB_PASSWORD:?required}`
로 미설정 기동을 차단합니다 ([Day 122](../05-infra-mlops/day-122.md)).

### 재학습 게이트 — 자동화에는 관문이 필요하다

```
일요일 03:00  학습(최근 데이터) → evaluate() → 운영 모델과 비교
              ├─ MAE 악화 +10% 이내 → 승격 (신선한 데이터의 가치 우선)
              └─ +10% 초과 악화     → 보류 + 스탠드업 알림 (사람 판단으로)
```

"조금 나빠져도 승격"이 이상해 보일 수 있지만, 주간 홀드아웃은 매번 달라 소폭 변동은
정상 노이즈입니다 — 게이트의 임무는 미세 조정이 아니라 **대형 사고(데이터 파손·버그로
망가진 모델)의 차단**입니다.

## ④ 단계별 실습

### Step 1. Dockerfile과 다이어트 — #27 (1~2교시)

```
$ docker build -t hansan-api:dev . && docker images hansan-api:dev
REPOSITORY    TAG   SIZE
hansan-api    dev   687MB     # v1 1.24GB → 층 정리·no-cache·.dockerignore
$ docker history hansan-api:dev | head -4    # 어느 층이 큰지 — 근거 기록
```

### Step 2. Compose 풀스택 — #28 (3~4교시)

```
$ docker compose up -d && docker compose ps --format "table {{.Name}}\t{{.Status}}"
NAME             STATUS
hansan-nginx-1   Up 41s (healthy)
hansan-api-1     Up 52s (healthy)
hansan-db-1      Up 58s (healthy)
hansan-mlflow-1  Up 58s (healthy)
hansan-airflow-1 Up 55s (healthy)
$ curl -s localhost:8080/health
{"status":"ok","model_version":"hansan-daily-v2","model_loaded_at":"2026-08-25T09:12:40Z"}
```

### Step 3. 전원 교차 기동 (5~6교시)

컨테이너화의 완료 판정은 빌드 성공이 아니라 **남의 환경에서의 기동**입니다:

| 환경 | clone → up → /health | 비고 |
|---|---|---|
| 서연 (Windows/WSL2) | 3m 12s | 첫 빌드 포함 |
| 민준 (macOS, ARM) | 4m 05s | ⚠ lightgbm 휠 이슈 → `--platform` 명시로 해결, README 반영 |
| 지우 (Windows/WSL2) | 2m 58s | — |
| 클라우드 서버 (Ubuntu) | 2m 41s | 내일 CD의 무대 |

민준의 ARM 이슈처럼 **한 명의 환경에서만 나는 문제**가 오늘의 진짜 수확입니다 — 심사위원
환경에서 났다면 사고였을 것이 오늘은 README 한 줄이 됩니다.

### Step 4. 재학습 DAG와 게이트 — #26 (7~8교시)

수동 트리거로 **양쪽 경로를 다 리허설**합니다:

```
$ airflow dags trigger retrain_weekly            # 경로 1: 정상
[retrain] 학습 데이터 ~2026-08-20 · 신규 run 9f21c4d0 · MAE 1,178 (운영 1,183 대비 −0.4%)
[gate] 악화 아님 → hansan-daily v3 승격 · api는 다음 기동/일 갱신 시 로드

$ airflow dags trigger retrain_weekly --conf '{"inject_fault": "truncate"}'   # 경로 2: 사고 주입
[retrain] 학습 데이터 반토막(주입) · 신규 run 77e0a1b3 · MAE 1,530 (+29.3%)
[gate] +10% 초과 악화 → 승격 보류 · 알림 발송 · run은 보관 (원인 분석용)
```

보류 경로를 **일부러 고장을 주입해** 시험하는 것 — 게이트는 통과가 아니라 차단이 존재
이유이므로, 차단이 실제로 일어나는 것을 봐야 완성입니다 ([Day 129](../05-infra-mlops/day-129.md)
의 롤백 리허설과 같은 철학).

**오늘 퇴근 체크** — □ 이미지 687MB(단계별 실측 기록) □ 풀스택 healthy 5/5 □ 전원
교차 기동(문제→README 반영) □ 게이트 양쪽 경로 리허설 □ 시크릿 4대 금지처 점검
([Day 122](../05-infra-mlops/day-122.md) 표) 재실행

## ⑤ 자주 하는 실수

### latest 태그 하나로 운영

**증상** — "어제는 됐는데 오늘 안 떠요" — latest가 가리키는 것이 바뀌었는데 아무도
언제·무엇으로 바뀌었는지 모름.
**원인** — 태그를 버전이 아니라 별명으로 사용.
**해결** — 내일 CI가 커밋 sha 태그를 강제하게 됩니다 ([Day 128](../05-infra-mlops/day-128.md)
의 태그 전략). 오늘부터 습관을: 로컬 시험 빌드도 `:dev`, `:sha-xxxx`처럼 정체가 있는
태그로.

### 모델·데이터가 이미지 안에 (B방식인데)

**증상** — 이미지가 2.3GB — `docker history`를 보니 data/ 48,756행 CSV와 mlruns/가
통째로 들어가 있음.
**원인** — `.dockerignore` 부재 — COPY . 이 전부를 쓸어 담음.
**해결** — `.dockerignore`는 Dockerfile과 한 세트입니다. 한산의 설계(B방식)에서 모델은
레지스트리에서, 데이터는 DB에서 옵니다 — 이미지에는 코드와 의존만. "이미지 안에 뭐가
있는지 설명 못 하는 층이 없다"가 검사 기준입니다.

### db 볼륨 없이 재시작

**증상** — compose down 후 up — 48,756행이 사라짐. 백필 재실행 30분.
**원인** — 데이터는 컨테이너보다 오래 살아야 한다는 원칙([Day 119](../05-infra-mlops/day-119.md))
을 선언(volumes)으로 옮기지 않음.
**해결** — pgdata·mlartifacts 볼륨을 확인하고, **down→up 후 행수가 그대로인지**를
오늘의 검사 항목에 넣으세요 (한산 체크리스트에 있습니다).

### 시크릿이 compose.yaml에 하드코딩

**증상** — `POSTGRES_PASSWORD: hansan1234` 가 저장소에 커밋됨 — 내일 CI가 이 파일을
그대로 씀 → 공개 저장소라면 유출 완료.
**원인** — "일단 돌게 하고 나중에 정리" — 나중은 오지 않습니다.
**해결** — 처음부터 `${DB_PASSWORD:?required}` + `.env`(.gitignore) + `.env.example`
(자리표시자만). 오늘 퇴근 체크의 4대 금지처 점검이 이 실수의 그물입니다 — 발견이
오늘이면 수정 5분, 발표 주간이면 키 교체 + 히스토리 세탁입니다.

## ⑥ 확인 문제

**Q1.** "환경 차이를 사람이 맞추는 비용은 인원수에 비례한다"를 이번 주 상황(팀 4 + 서버
+ 심사위원)으로 구체화하고, 컨테이너가 이 비용 구조를 어떻게 바꾸는지 설명하세요.

<details>
<summary>답 보기</summary>

사람이 맞추는 방식에서는 새 환경이 하나 늘 때마다 "설치 문서 따라 하기 + 그 환경 고유의
문제 해결"이 반복됩니다 — W30의 4건(각 30분)이 그 표본이고, 서버·심사위원까지 6개 환경
이면 문제의 종류도 6벌입니다(민준의 ARM 이슈처럼 환경 고유 문제는 예측 불가). 컨테이너는
실행 환경 자체를 산출물(이미지)로 만들어, 환경 추가의 한계 비용을 "Docker 있는가"라는
단일 전제 확인으로 떨어뜨립니다. 비용이 O(환경 수 × 문제 수)에서 O(1) + 이미지 관리
고정비로 바뀌는 것 — 오늘 교차 기동 표가 그 증명 실험입니다.

</details>

**Q2.** 게이트 규칙이 "+10% 초과 악화만 차단"인 이유를 두 오류(대형 사고 통과 vs 정상
변동 차단)의 비용 비대칭으로 설명하고, 이 임계값이 재검토되어야 할 신호를 하나 제안하세요.

<details>
<summary>답 보기</summary>

주간 재학습에서 홀드아웃이 매번 달라 ±수 % 변동은 정상 노이즈입니다. 임계를 0%로 조이면
정상 변동의 절반이 차단되어 매주 사람이 개입("알림 피로")하고, 재학습의 목적(신선한
데이터 반영)이 무산됩니다 — 차단 오류의 비용은 매주 발생하는 운영 마찰입니다. 반면
게이트가 막아야 할 진짜 표적(데이터 파손·버그로 MAE가 수십 % 튀는 모델)은 +10%를 크게
넘겨 걸립니다 — 통과 오류의 비용은 크지만 임계 10%로도 충분히 잡히는 것이죠. 재검토
신호의 예: 보류가 수 주 연속 발생(임계가 현실 변동보다 좁아졌거나 데이터 품질이 흔들림),
또는 승격된 모델의 운영 지표(154의 대시보드)가 홀드아웃과 계속 어긋남 — 게이트 임계값도
모델처럼 운영 데이터로 재평가되어야 합니다.

</details>

**Q3.** api 서비스가 db는 기다리되(healthy) mlflow는 기다리지 않는 의존성 설계를, "의존의
종류"라는 관점에서 정당화하세요. 만약 폴백 캐시가 없었다면 이 설계는 어떻게 달라져야
했을까요?

<details>
<summary>답 보기</summary>

db는 **경성 의존**입니다 — 피처 조회(lag)가 요청 경로에 있어, db 없이는 어떤 요청도
처리할 수 없으므로 기동을 기다리는 것이 맞습니다. mlflow는 **연성 의존**입니다 — 필요한
순간이 기동 시 모델 로드 한 번이고, 실패 시 대체 경로(로컬 캐시의 마지막 성공본)가
있으므로 기다릴 이유가 없습니다. 기다리게 하면 오히려 mlflow 장애가 api 기동 장애로
전파되어 가용성이 하락합니다. 폴백이 없었다면 mlflow는 경성 의존이 되므로 depends_on
healthy를 걸어야 하고, 그래도 운영 중 mlflow 다운 → api 재시작 시나리오에서 서비스가
죽는 창이 남습니다 — 즉 폴백 캐시(코드)와 미대기(구성)는 한 세트의 결정이며, 의존성
그래프는 코드의 실패 처리 능력을 반영해야 합니다.

</details>
