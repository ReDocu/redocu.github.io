````markdown
## 파이썬 슈팅게임 — 몬스터를 찾아서

**문제**
pygame 을 처음 다루면서 "게임 루프 안에 전부 때려 넣는" 코드를 만들었습니다.
````

````markdown
## CCTV Object Detection 시스템 (팀 4인)

**문제**
작업 구역의 안전모 미착용을 사람이 CCTV 화면으로 감시하는 방식은
1시간을 넘기면 놓치기 시작합니다. 야간에는 아무도 보지 않습니다.
"놓치지 않는 감시"를 자동화하되, **현장에 PC 를 둘 수 없다**는 제약이 있었습니다.

**접근**
- 데이터를 직접 만들었습니다. 실제 설치 각도와 유사한 조건에서 촬영 → 프레임 추출 →
  CVAT 라벨링 → **교차 검수** 순으로 1,240장 / 3클래스 / 박스 3,867개를 구축했습니다.
- 모델은 YOLO11n(640px, 100 epoch). 미검출 유형을 분석해 **역광·원거리 240장을 추가**했습니다.
- 배포 형태 5가지를 비교표로 평가해 **하이브리드(엣지 추론 + 서버 연동)** 를 선택했습니다.
  서버 추론안은 하루 43GB 전송과 영상 외부 유출 때문에 기각했습니다. (`docs/DECISION_154.md`)
- 파이의 PyTorch 원본은 실용 불가여서 **NCNN 으로 변환**했고, 서버가 죽어도 감시가 계속되도록
  **로컬 SQLite 에 먼저 쓰고** 전송 실패 시 큐에 쌓아 재전송하게 했습니다.

**결과**
| 지표 | 목표 | 달성 |
|---|---|---|
| mAP@50 | 0.80 | **0.871** |
| 라즈베리파이 5 FPS | 2.0 | **3.58** (여유 79%) |
| 이벤트 → 알림 지연 | 5초 | **2.4초** |
| 오탐 | — | 시간당 **14건 → 1.2건** |
| 무중단 동작 | 1시간 | **26시간** |

**배운 것**
- ★ 정확도보다 **오탐**이 시스템의 수명을 결정합니다. 알림이 하루 300건 오면 아무도 안 봅니다.
- ★ 라벨 품질이 학습 설정보다 영향이 컸습니다. 교차 검수 전후로 mAP 가 0.79 → 0.84 로 올랐습니다.
````

### 카테고리 A — 프로젝트 심화 (검출)

**Q. 왜 YOLO 인가요? R-CNN 계열이나 DETR 은 왜 안 썼나요?**

```
★ 답변 요령 — "유명해서" 는 답이 아닙니다. 제약을 말하세요.
  결론: 라즈베리파이 CPU 에서 실시간이 필요했기 때문입니다.
  근거: 목표는 파이 5 에서 2 FPS 이상이었는데, 2-stage 계열(Faster R-CNN)은
        파이에서 1 FPS 도 안 나왔고, DETR 은 수렴 에폭이 많아 1,240장으로는
        과적합 위험이 컸습니다. 1-stage 중 NCNN/TFLite 변환 지원이 가장
        갖춰진 것이 Ultralytics YOLO 였습니다.
  한계: 작은 객체(원거리 안전모)는 여전히 약합니다. 재현율 0.62 입니다.
```

**Q. mAP 가 뭔가요? mAP@50 과 mAP@50-95 의 차이는요?**

```
결론: 클래스별 AP(Precision-Recall 곡선 아래 면적)의 평균입니다.
근거: AP 는 conf 임계값을 0→1 로 훑으면서 만든 P-R 곡선의 면적입니다.
      ★ 임계값 하나에 의존하지 않는다는 것이 정확도(accuracy)와의 차이입니다.
      mAP@50 은 IoU 0.5 이상이면 정답, mAP@50-95 는 IoU 0.5~0.95 를
      0.05 간격 10개로 평균한 더 엄격한 지표입니다.
      우리 모델은 0.871 / 0.612 — 격차가 크다는 건 검출은 하는데
      박스가 정밀하지 않다는 뜻입니다.
한계: mAP 는 "몇 건을 놓쳤나" 를 직접 말해 주지 않아,
      안전 용도에서는 재현율을 따로 봅니다.
```

**Q. IoU 와 NMS 를 설명해 보세요.**

```
IoU = 교집합 넓이 / 합집합 넓이   (0~1)

    ┌───────┐
    │  A ┌──┼────┐        IoU = ▨ / (A ∪ B)
    │    │▨▨│    │
    └────┼──┘ B  │        0.5 이상이면 보통 "같은 물체"
         └───────┘

NMS (Non-Maximum Suppression)
  ① conf 내림차순 정렬
  ② 가장 높은 박스를 채택
  ③ 그것과 IoU > 임계값 인 박스를 ★ 제거
  ④ 남은 것에 대해 반복

★ 두 곳에서 IoU 가 쓰입니다 — 헷갈리기 쉬움
  · NMS 의 iou : 중복 박스 제거 기준 (예: 0.45~0.7)
  · 평가의 IoU : 정답 판정 기준 (mAP@50 의 0.5)
```

**Q. conf 임계값은 어떻게 정했나요?**

```
★ 이 질문은 "감으로 정했는지" 를 봅니다.

결론: 검증셋에서 임계값을 훑어 재현율과 오탐률을 함께 보고 0.45 로 정했습니다.
근거: 0.25 는 재현율 0.91 이지만 시간당 오탐 14건, 0.60 은 오탐 0.4건인데
      재현율이 0.71 로 떨어졌습니다. 미착용을 놓치는 비용이 오탐보다 크지만
      ★ 알림이 하루 300건 오면 아무도 안 보게 됩니다.

한계: 야간 영상에는 이 값이 맞지 않습니다. 시간대별 임계값은 미구현입니다.
```

**Q. GIL 이 무엇인가요? 우리 프로젝트에 어떤 영향이 있었나요?**

```
결론: 한 프로세스 안에서 파이썬 바이트코드를 한 번에 하나의 스레드만
      실행하게 하는 전역 잠금입니다.

      카메라 읽기(I/O) 스레드는 효과가 있었고, 추론 병렬화는 효과가 없었습니다.
      (다만 PyTorch/NCNN 내부는 C 레벨에서 GIL 을 풀어 멀티코어를 씁니다)
한계: 진짜 병렬이 필요하면 multiprocessing 인데,
      파이 5 메모리로는 모델을 두 번 올릴 수 없어 쓰지 않았습니다.
```

|---|---|---|
| 메모리 | 공유 | 분리 (IPC 필요) |
| 생성 비용 | 낮음 | 높음 |
| GIL 영향 | 받음 | 안 받음 |
| CPU 바운드 | ✗ | ✓ |
| I/O 바운드 | ✓ | ✓ (과함) |
| 죽으면 | 프로세스 전체 위험 | 격리됨 |
| 우리 사례 | 카메라 캡처 · Flask 요청 | (미사용) |

**Q. HTTP 요청/응답 구조를 설명해 보세요.**

```
요청
  POST /api/events HTTP/1.1        ← 메서드 · 경로 · 버전
  Host: 192.168.0.10:5000          ← 헤더
  Content-Type: application/json
  Content-Length: 284
                                    ← 빈 줄
  {"event_id":"...", "class":"person", ...}     ← 본문

응답
  HTTP/1.1 201 Created             ← 버전 · 상태코드 · 사유구
  Content-Type: application/json
  Content-Length: 42

  {"ok":true,"id":1043}

★ 상태코드
  2xx 성공   200 OK · 201 Created · 204 No Content
  3xx 이동   301 영구 · 302 임시 · 304 Not Modified
  4xx 클라이언트  400 · 401 인증 · 403 권한 · 404 · ★ 413 용량초과 · 429 과다요청
  5xx 서버   500 · 502 · 503
```

**Q. GET 과 POST 의 차이는요?** → 위치와 부작용. 파일은 POST 만 가능하고,
새로고침 재전송 경고 때문에 PRG(Post/Redirect/Get) 패턴을 썼습니다. ([Day 159](day-159.md))

**Q. SQL 인덱스는 왜 쓰나요? 단점은요?**

```
결론: 조회를 전체 스캔에서 B-tree 탐색으로 바꿔 줍니다. O(n) → O(log n).
근거: events 테이블은 하루 400건, 30일이면 12,000행입니다.
      "최근 7일, class='person'" 조회가 느려져서 인덱스를 걸었습니다.

        CREATE INDEX idx_events_ts_class ON events(ts DESC, class_name);

      ★ 복합 인덱스는 왼쪽부터 쓰입니다. (ts, class_name) 은 ts 단독 조회에는
        쓰이지만 class_name 단독 조회에는 안 쓰입니다.
단점: INSERT/UPDATE 마다 인덱스도 갱신되어 쓰기가 느려지고 디스크를 더 씁니다.
      카디널리티가 낮은 컬럼(예: 3종 클래스)은 효과가 작습니다.
```

**Q. 파이썬 리스트와 제너레이터의 차이는요?**

```
결론: 리스트는 전부 메모리에 만들고, 제너레이터는 요청할 때 하나씩 만듭니다.
근거: 영상 스트리밍(`/video_feed`)에서 제너레이터를 썼습니다. 720p 프레임 하나가
      약 2.7MB 라 1분치 900프레임을 리스트에 담으면 ★ 2.4GB — 불가능합니다.
      `yield` 로 하나씩 내보내면 메모리는 프레임 1~2장분입니다.
한계: 제너레이터는 한 번만 순회할 수 있고 `len()` 을 쓸 수 없습니다.
```

```bash
#!/usr/bin/env bash
# 사용법: ./make_gif.sh input.mp4 output.gif [시작초] [길이초]
set -euo pipefail

IN="${1:?input mp4}"
OUT="${2:?output gif}"
SS="${3:-0}"
DUR="${4:-12}"
FPS=10
WIDTH=720

TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT

echo "[1/3] 구간 자르기  ${SS}s 부터 ${DUR}s"
ffmpeg -v error -ss "$SS" -t "$DUR" -i "$IN" -c copy "$TMP/cut.mp4"

echo "[2/3] 팔레트 생성"
ffmpeg -v error -i "$TMP/cut.mp4" \
  -vf "fps=${FPS},scale=${WIDTH}:-1:flags=lanczos,palettegen=stats_mode=diff" \
  -y "$TMP/palette.png"

echo "[3/3] GIF 변환"
ffmpeg -v error -i "$TMP/cut.mp4" -i "$TMP/palette.png" \
  -lavfi "fps=${FPS},scale=${WIDTH}:-1:flags=lanczos [x]; [x][1:v] paletteuse=dither=bayer:bayer_scale=3" \
  -y "$OUT"

SIZE=$(du -h "$OUT" | cut -f1)
echo "완료: $OUT ($SIZE)"
case "$SIZE" in
  *M) MB="${SIZE%M}"
      awk "BEGIN{exit !($MB > 5)}" && echo "★ 경고: 5MB 초과. FPS 나 WIDTH 를 줄이세요." ;;
esac
```

### Step 3. GitHub 저장소 정리 + 비밀값 점검

`portfolio/scripts/audit_repo.sh`

```bash
#!/usr/bin/env bash
# 저장소 위생 점검. 저장소 루트에서 실행합니다.
set -uo pipefail

echo "=================================================="
echo " 저장소 위생 점검  $(basename "$(pwd)")"
echo "=================================================="

echo; echo "[1] 저장소 크기"
git count-objects -vH | grep -E "size-pack|count"

echo; echo "[2] 히스토리에 남은 큰 파일 상위 10개"
git rev-list --objects --all 2>/dev/null \
 | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' 2>/dev/null \
 | awk '$1=="blob" && $3>1048576 {printf "  %6.1f MB  %s\n", $3/1048576, $4}' \
 | sort -rn | head -10

echo; echo "[3] 현재 파일에서 의심 문자열"
grep -rInE "(api[_-]?key|secret[_-]?key|bot[_-]?token|passwd|password|bearer )" \
  --include="*.py" --include="*.yaml" --include="*.yml" --include="*.json" \
  --include="*.ipynb" --include="*.env*" --include="*.md" --include="*.sh" . \
  2>/dev/null | grep -v "\.env\.example" | grep -v "os\.environ" | head -20

echo; echo "[4] ★ 과거 커밋에 남은 비밀값 (핵심)"
for KEY in bot_token api_key secret_key password TELEGRAM_BOT_TOKEN AWS_SECRET; do
  N=$(git log --all --oneline -S "$KEY" 2>/dev/null | wc -l)
  if [ "$N" -gt 0 ]; then
    echo "  '$KEY' 를 포함/제거한 커밋 ${N}개"
    git log --all --oneline -S "$KEY" | head -3 | sed 's/^/      /'
  fi
done

echo; echo "[5] 텔레그램 봇 토큰 패턴"
git grep -nIE "[0-9]{8,10}:[A-Za-z0-9_-]{35}" $(git rev-list --all) 2>/dev/null | head -5 \
  || echo "  없음"

echo; echo "[6] .env 계열 파일이 커밋된 적 있는지"
git log --all --pretty=format: --name-only --diff-filter=A 2>/dev/null \
 | sort -u | grep -iE "(^|/)(\.env|secrets?|credential)" | head -10 \
 || echo "  없음"

echo; echo "[7] .gitignore 필수 항목"
for P in ".env" "__pycache__/" "*.pt" "runs/" "*.db" ".venv/"; do
  if grep -qxF "$P" .gitignore 2>/dev/null; then
    echo "  ✓ $P"
  else
    echo "  ✗ $P     ← 추가하세요"
  fi
done

echo; echo "[8] 브랜치"
git for-each-ref --sort=-committerdate refs/heads/ \
  --format='  %(committerdate:short)  %(refname:short)'

echo; echo "[9] 커밋 통계"
echo "  총 커밋: $(git rev-list --count HEAD) · 기여자: $(git shortlog -sn HEAD | wc -l)"
echo "  기간: $(git log --reverse --format=%ad --date=short | head -1) ~ $(git log -1 --format=%ad --date=short)"
echo "  무의미한 메시지: $(git log --format=%s | grep -cEi '^(update|fix|test|asdf|final|wip)$')건"

echo; echo "[10] 추적 중인 파일 중 위험한 것"
git ls-files | grep -iE "\.(pt|pth|onnx|h5|keras|tflite|zip|mp4|db|sqlite3)$" | head -10 \
  || echo "  없음"

echo "=================================================="
```

| 15분 발표 | 문제 2 / 접근 3 / **시연 5** / 결과·한계 3 / 마무리 2 |
| 슬라이드 | 한 장 한 메시지 · 제목은 **주장** · **코드 최대 1장** |
| 백업 영상 | 슬라이드에 **삽입** · USB · 발표 노트북에서 재생 확인 |
| 리허설 | 소리 내어 · 스톱워치 · 구간별 · 실장비 · **2회** |

**오늘 반드시 기억할 세 가지**
> ① **5개를 궤적으로 엮으세요.** 나열은 개수만 남기고, 궤적은 "무엇을 할 수 있는 사람인가"를 남깁니다.
> ② **비밀값은 폐기가 먼저입니다.** 히스토리를 지워도 노출된 토큰은 그대로 살아 있습니다.
> ③ **리허설은 소리 내어 2회.** 머릿속 15분은 실제로 20분입니다. 백업 영상 없이 무대에 오르지 마세요.

**과제 — 포트폴리오 · 발표 자료 · 데모 영상**

```
1. 5개 프로젝트를 정리표로 만듭니다.
     · 한 줄 소개 · 기술 · 핵심 성과(숫자) · 어필 포인트
     · 기억나지 않는 숫자는 다시 측정

2. 5개를 하나의 궤적으로 엮는 한 문장을 씁니다.
     · 기술 이름 없이 · 누구에게나 통하게

3. 저장소 5개를 정리합니다.
     · README 첫 화면 (한 줄 + 이미지 + 배지 + 성능표 + 실행)
     · 약한 프로젝트에 "지금이라면" 3줄 · Topics · About · 라이선스

4. 저장소 위생을 점검하고 조치합니다.
     · 비밀값 (과거 커밋 포함) → 발견 시 ★ 폐기 먼저
     · .gitignore · 대용량 파일 · 브랜치

5. 프로필 README 를 만듭니다.
     · 저장소 이름 = 본인 ID · 5개 안내 표 + 기술 3단 분류

6. 이력서 1장을 씁니다.
     · 서술 공식 · 숫자 10개 이상 · 팀 프로젝트는 담당 범위 명시

7. 면접 질문 30개에 답변 요지(결론/근거/한계)를 씁니다.
     · 답을 못 쓰는 질문이 오늘의 공부 목록입니다

8. 발표 슬라이드 12장과 데모 영상을 완성합니다.
     · 시간 배분표대로 · 코드 슬라이드 최대 1장 · 데모 3분 + 백업 영상

9. ★ 리허설 2회를 하고 구간별 시간을 기록합니다.
     · 소리 내어 · 실장비 · 다른 팀 1명 참관 · 시연 실패 전환을 1회 연습

10. 장비 체크리스트를 작성하고 전날 확인까지 마칩니다.
```
