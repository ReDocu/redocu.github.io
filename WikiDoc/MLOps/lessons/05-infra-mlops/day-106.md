## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 브랜치가 **커밋을 가리키는 포인터**임을 그림으로 설명할 수 있다.
- 충돌이 나는 **세 가지 조건**을 말하고, 어떤 수정이 자동 병합되고 어떤 수정이 충돌인지 예측할 수 있다.
- 충돌 마커(`<<<<<<<` `=======` `>>>>>>>`)를 읽고 **세 단계 절차**로 해결할 수 있다.
- 병합을 잘못 시작했을 때 `git merge --abort` 로 안전하게 물러날 수 있다.

> 이번 주는 기존 [Git 과정 중급](../../../complate/Git/curriculum/02-intermediate.md)과 같은 범위를
> 5일로 압축해서 갑니다. 차이는 재료 — 예제 저장소가 아니라 **여러분의 MP3 저장소**로 연습합니다.
> W26에서 이 저장소에 CI가 붙는 순간, 이번 주의 규칙들은 "예절"에서 "강제"로 바뀝니다.

## ② 왜 필요한가

Day 001부터 지금까지 여러분은 Git을 **혼자** 썼습니다. add → commit → push, 브랜치는 main 하나.
그래서 한 번도 충돌을 본 적이 없습니다 — 같은 파일을 두 사람이 고칠 일이 없었으니까.

이 단원이 끝나면 상황이 다릅니다. MP4는 2인 페어를 허용하고, 최종 프로젝트(W29~)는 **4인 팀**입니다.
팀 저장소에서 벌어질 일을 미리 보죠:

```
당신:   app/config.py 의 업로드 제한을 5MB → 8MB 로 (고해상도 사진 지원)
팀원 B: 같은 줄을         5MB → 2MB 로 (서버 메모리 보호)
둘 다 push 하면?  →  나중에 push 한 쪽이 거절되고, pull 하는 순간 —  CONFLICT
```

이때 충돌 마커를 처음 보는 사람은 얼어붙습니다. 최악의 대응 두 가지가 모두 실제로 자주 일어납니다:
**① 마커째로 커밋**해서 서버를 `SyntaxError`로 죽이거나, **② 폴더를 통째로 지우고 새로 clone**해서
자기 작업을 날립니다. 오늘 목표는 단순합니다 — 충돌을 **10분 안에, 아무것도 잃지 않고** 정리하는 몸.

충돌은 Git의 실패가 아닙니다. "**두 사람의 의도가 다른데, 어느 쪽이 맞는지 나는 결정할 수 없다**"는
Git의 정직한 질문입니다. 질문에는 답을 하면 됩니다.

## ③ 개념 설명

### 브랜치 — 커밋을 가리키는 포인터

브랜치는 폴더 복사본이 아닙니다. **커밋 하나를 가리키는 이름표**일 뿐이라 만드는 데 1ms도 안 걸립니다.

```
main     ●──●──●  C3
                ↑
feature         └──●──●  C5      ← feature 브랜치 = "C5를 가리키는 이름표"
```

커밋하면 지금 있는 브랜치의 이름표만 한 칸 전진합니다. 그래서 브랜치를 나눠 작업하는 비용은 0이고,
**"작업 단위마다 브랜치"**가 팀의 기본 습관이 됩니다 (내일과 모레에서 이 습관이 전략이 됩니다).

### 병합과 3-way — Git이 비교하는 것은 세 지점

`git merge` 는 두 브랜치를 그냥 겹치는 게 아니라 **세 지점**을 비교합니다:
공통 조상(base) · 내 쪽(HEAD) · 상대 쪽(합칠 브랜치).

| base 대비 | 내 쪽 | 상대 쪽 | 결과 |
|---|---|---|---|
| 다른 파일 수정 | ✔ | ✔ | 자동 병합 |
| 같은 파일, **다른 줄** 수정 | ✔ | ✔ | 자동 병합 |
| 같은 파일, **같은 줄**을 서로 다르게 | ✔ | ✔ | **충돌** |
| 한쪽만 수정 | ✔ | — | 자동 (수정한 쪽 채택) |

충돌의 조건은 그래서 세 가지가 전부 겹칠 때입니다: **같은 파일 + 같은 줄(또는 맞닿은 줄) + 서로 다른 내용**.
"팀원과 동시에 작업하면 무조건 충돌"이 아닙니다 — 파일과 영역을 나누면 대부분 자동으로 합쳐집니다.

### 충돌 마커 — 세 줄만 알면 읽힌다

충돌이 난 파일을 열면 Git이 문제 지점을 이렇게 표시해 둡니다:

```python
<<<<<<< HEAD
MAX_UPLOAD_MB = 8        # ← 내 쪽 (지금 체크아웃된 브랜치)
=======
MAX_UPLOAD_MB = 2        # ← 상대 쪽 (병합하려는 브랜치)
>>>>>>> feature/limit-down
```

| 마커 | 뜻 |
|---|---|
| `<<<<<<< HEAD` ~ `=======` | **내 쪽** 내용 |
| `=======` ~ `>>>>>>> 브랜치명` | **상대 쪽** 내용 |
| 마커 3줄 자체 | Git이 꽂아 둔 표식 — **해결 후 반드시 삭제** |

해결은 언제나 같은 세 단계입니다:

1. **결정** — 내 쪽 / 상대 쪽 / 제3의 답 중 하나로 파일을 고친다 (마커 3줄 삭제 포함)
2. **신고** — `git add <파일>` : "이 파일의 충돌은 해결했다"는 선언
3. **마무리** — `git commit` : 병합 커밋 완성

기억할 것 — 결정하는 주체는 **사람**입니다. 위 예시에서 8과 2는 코드 문법상 둘 다 옳지만,
어느 쪽이 서비스에 맞는지는 팀의 논의가 정합니다. 도구는 그 결정을 기록할 뿐입니다.

## ④ 단계별 실습

이번 주 실습은 지금까지처럼 PowerShell에서 합니다 (Linux는 다음 주부터).
훈련장은 깨끗한 새 저장소로 만들고, 마지막에 MP3 저장소에서 실전 1회를 치릅니다.

### Step 1. 충돌 훈련장 만들기 (1~2교시)

혼자서 두 사람을 연기합니다 — 브랜치 두 개면 충분합니다.

```powershell
mkdir conflict-lab; cd conflict-lab
git init
"MAX_UPLOAD_MB = 5" | Out-File -Encoding utf8 config.py
git add .; git commit -m "기준: 업로드 제한 5MB"
```

**A 역할** — 제한을 올리는 브랜치:

```powershell
git switch -c feature/limit-up
"MAX_UPLOAD_MB = 8" | Out-File -Encoding utf8 config.py
git commit -am "업로드 제한 8MB로 상향 (고해상도 지원)"
```

**B 역할** — main에서 갈라져, 제한을 내리는 브랜치:

```powershell
git switch main
git switch -c feature/limit-down
"MAX_UPLOAD_MB = 2" | Out-File -Encoding utf8 config.py
git commit -am "업로드 제한 2MB로 하향 (메모리 보호)"
```

이제 main에 A를 먼저 합치고, B를 합쳐 봅니다:

```powershell
git switch main
git merge feature/limit-up
git merge feature/limit-down
```

```
$ git merge feature/limit-up
Updating 3e1f0a2..7c48d91
Fast-forward
 config.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git merge feature/limit-down
Auto-merging config.py
CONFLICT (content): Merge conflict in config.py
Automatic merge failed; fix conflicts and then commit the result.
```

첫 병합은 조용히 통과(main이 그동안 안 움직였으니 이름표만 전진 — `Fast-forward`),
두 번째에서 예고대로 **CONFLICT** 입니다. 지금 상태를 확인하는 습관부터:

```powershell
git status
```

```
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   config.py
```

status가 **탈출구까지 알려 줍니다** — 해결하고 commit 하거나, `--abort`로 없던 일로 하거나.
겁먹을 이유가 없는 이유가 이 두 줄에 있습니다.

### Step 2. 해결 세 단계 (3~4교시)

`config.py` 를 열면 ③에서 본 그 마커가 있습니다. 팀 논의 결과가 "8MB로 가되, 추후 재검토"라고
합시다. 파일을 **마커까지 지우고** 이렇게 만듭니다:

```python
MAX_UPLOAD_MB = 8    # 2026-08 팀 결정: 상향. 메모리 이슈 재발 시 재검토
```

그리고 신고 → 마무리:

```powershell
git add config.py
git commit -m "merge: 업로드 제한 충돌 해결 - 8MB 채택"
git log --oneline --graph --all
```

```
$ git log --oneline --graph --all
*   9d2c7be (HEAD -> main) merge: 업로드 제한 충돌 해결 - 8MB 채택
|\
| * a410f8e (feature/limit-down) 업로드 제한 2MB로 하향 (메모리 보호)
* | 7c48d91 (feature/limit-up) 업로드 제한 8MB로 상향 (고해상도 지원)
|/
* 3e1f0a2 기준: 업로드 제한 5MB
```

그래프에서 **두 갈래가 병합 커밋에서 다시 만나는 다이아몬드**를 확인하세요. 충돌 해결의 결과는
커밋 하나 — 사고 흔적이 아니라 "두 의도를 이렇게 정리했다"는 **기록**입니다.

### Step 3. 충돌이 안 나는 경우 체험 (5교시)

이번엔 **같은 파일, 다른 줄**입니다. config.py에 줄을 추가해 두고:

```python
MAX_UPLOAD_MB = 8    # 2026-08 팀 결정: 상향. 메모리 이슈 재발 시 재검토
LOG_LEVEL = "INFO"
```

한 브랜치는 첫 줄만, 다른 브랜치는 둘째 줄만 고친 뒤 병합해 보세요.

```
$ git merge feature/log-debug
Auto-merging config.py
Merge made by the 'ort' strategy.
 config.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`Auto-merging` 후 그대로 완료 — 같은 파일이라도 **줄이 다르면 Git이 알아서 합칩니다.**
③의 표가 몸으로 확인됐습니다. 팀 작업 분담의 근거이기도 합니다: 모듈·영역을 나누면
충돌은 예외적 사건이 됩니다 ([Day 093](../04-deep-learning-serving/day-093.md)에서 파일을
router/service/model_store로 쪼개 둔 것이 협업에서도 효자인 이유).

### Step 4. 실전 — MP3 저장소에서, 그리고 --abort (6~7교시)

이제 실제 `mlops-mp3` 저장소에서 같은 시나리오를 재연합니다. `app/config.py` 의 업로드 제한
(여러분이 [Day 100](../04-deep-learning-serving/day-100.md)에서 넣은 그 값)으로 브랜치 두 개를
만들어 충돌 → 해결까지. 단, 이번엔 해결 **후** 서버가 여전히 뜨는지까지가 완료 조건입니다:

```powershell
uvicorn app.main:app --port 8000
pytest -q
```

```
$ pytest -q
.......                                                              [100%]
7 passed in 4.31s
```

**충돌 해결의 진짜 완료 조건은 "마커가 없다"가 아니라 "테스트가 통과한다"입니다.**
마커를 지우고도 코드를 뒤섞어 망가뜨리는 경우가 있기 때문에, 해결 → 실행 확인까지가 한 세트입니다.

마지막으로 탈출 훈련 — 충돌을 하나 더 만들고, 이번엔 해결하지 말고 물러납니다:

```powershell
git merge feature/practice
git merge --abort
git status
```

```
$ git status
On branch main
nothing to commit, working tree clean
```

병합 시작 전과 완전히 같은 상태입니다. **`--abort`가 있는 한, 병합은 언제든 무를 수 있는 행동**입니다 —
"급한 배포 전에 충돌 큰 게 났다 → 일단 abort, 배포 후 차분히" 같은 운영 판단이 가능해집니다.

### Step 5. 과제 (8교시)

**충돌 해결 3세트.** 다음 세 종류를 각각 만들고 해결해서, `git log --oneline --graph` 캡처와
함께 제출하세요.

1. **값 충돌** — 오늘 실습의 변형 (다른 설정값으로)
2. **양쪽 추가 충돌** — 두 브랜치가 같은 위치에 서로 다른 **새 줄**을 추가 (예: requirements.txt 마지막 줄에 서로 다른 패키지)
3. **제3의 답 충돌** — 해결 결과가 내 쪽도 상대 쪽도 아닌 새 코드가 되는 경우 (예: 두 브랜치가 각각 만든 함수를 둘 다 남기되 이름 정리)

각 세트마다 한 줄씩: **이 충돌에서 Git이 물은 질문은 무엇이었고, 나는 무엇을 근거로 답했나?**

## ⑤ 자주 하는 실수

### 마커를 그대로 커밋

**증상** — 커밋은 됐는데 서버가 죽습니다:
```
    <<<<<<< HEAD
    ^^
SyntaxError: invalid syntax
```
**원인** — 마커 3줄은 Git의 표식이지 코드가 아닌데, 해결 없이 add → commit 했습니다.
**해결** — 파일에서 `<<<<<<<` 를 검색해 남은 마커를 정리하고 다시 커밋. **커밋 전 실행/테스트**가
이걸 막는 안전망입니다 (Step 4의 완료 조건이 그래서 pytest였습니다).

### 충돌났다고 폴더 삭제 후 재clone

**증상** — 충돌이 무서워 저장소를 지우고 새로 받음 — push 안 한 커밋과 작업 중 파일이 전부 증발.
**원인** — 충돌 상태를 "고장"으로 오해.
**해결** — 고장이 아니라 질문입니다. 물러나고 싶으면 `git merge --abort` 한 줄이면 병합 전으로
완전 복귀합니다 (Step 4에서 확인). 삭제는 답이 아니라 손실입니다.

### `Your local changes would be overwritten by merge`

**증상** —
```
error: Your local changes to the following files would be overwritten by merge:
        app/config.py
Please commit your changes or stash them before you merge.
```
**원인** — 커밋 안 한 수정이 작업 폴더에 있는 채로 merge/pull을 시작 — Git이 여러분의 미저장
작업을 보호하려고 거부한 것입니다 (충돌도 아닙니다).
**해결** — 메시지가 시키는 대로: 커밋하고 병합하거나, 아직 커밋할 단계가 아니면 `git stash` 로
잠시 치워 두고 병합 후 `git stash pop`.

### 한쪽을 무조건 이기게 하고 끝

**증상** — 늘 자기 쪽(HEAD)만 남기고 상대 쪽을 지움 — 팀원 B의 "메모리 보호" 의도가 소리 없이 소멸,
몇 주 뒤 서버 메모리 사고로 재발견.
**원인** — 충돌을 "빨리 없앨 장애물"로만 취급.
**해결** — 마커의 양쪽은 **둘 다 동료의 의도**입니다. 판단이 안 서면 상대를 불러 2분 대화가 정답이고,
그 결정을 커밋 메시지나 주석에 남깁니다 (Step 2에서 주석을 남긴 이유).

### 병합 커밋 메시지 편집기(Vim)에 갇힘

**증상** — `git commit` 을 쳤더니 낯선 화면이 뜨고 키가 안 먹음 — `:q` 소동.
**원인** — 메시지를 안 줘서 기본 편집기가 열렸습니다 (기본 설정이 Vim인 환경).
**해결** — `Esc` 후 `:wq` 입력으로 저장·종료. 애초에 `git commit -m "..."` 으로 메시지를 함께 주면
편집기가 열리지 않습니다. 다음 주 Linux에서도 똑같이 만나는 상황이니 오늘 탈출법을 외워 두세요.

<details>
<summary>답 보기</summary>

충돌이 아닙니다 — 자동 병합됩니다. Git은 공통 조상(base)·내 쪽·상대 쪽 3-way로 비교하는데,
두 수정이 같은 파일이라도 **서로 다른 줄(맞닿지 않은)**이면 각 수정을 모두 채택한 결과를 기계적으로
만들 수 있기 때문입니다. 충돌은 같은 파일 + 같은(또는 맞닿은) 줄 + 다른 내용일 때만 납니다.

</details>

**Q2.** 충돌 해결 절차의 2단계 `git add` 는 파일을 스테이징하는 평소의 add와 어떤 의미가 다른가요?

<details>
<summary>답 보기</summary>

평소의 add는 "이 변경을 다음 커밋에 담겠다"이지만, 충돌 상태(unmerged)의 add는
"**이 파일의 충돌을 사람이 해결했다**"는 선언입니다. add 하는 순간 그 파일이 unmerged 목록에서
빠지고, 모든 파일이 빠져야 commit(병합 완성)이 가능해집니다. 그래서 마커가 남았는데 add 하면
Git은 그것도 '해결됐다'고 믿어 버립니다 — ⑤의 첫 사고가 나는 경로입니다.

</details>

**Q3.** "충돌 해결의 완료 조건은 마커 삭제가 아니라 테스트 통과"인 이유를, 마커 없이도 망가진
해결의 예를 하나 들어 설명하세요.

<details>
<summary>답 보기</summary>

예: 내 쪽은 함수 이름을 `validate_size` 로 바꿨고 상대 쪽은 옛 이름 `check_size` 를 호출하는 코드를
추가한 경우 — 각각 다른 줄이라 충돌 없이 합쳐지거나, 충돌을 이름만 남기고 정리해도 **호출부가 깨진
상태**가 됩니다. 문법도 마커도 문제없지만 실행하면 `AttributeError`. 병합은 텍스트 연산이라
의미(호출 관계)까지 보장하지 못하므로, 실행·테스트만이 진짜 완료 조건입니다. W26의 CI가 병합마다
테스트를 강제로 돌리는 이유이기도 합니다.

</details>
