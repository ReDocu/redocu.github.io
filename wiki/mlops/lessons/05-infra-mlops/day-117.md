## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **Dockerfile 6개 명령**(FROM·WORKDIR·COPY·RUN·EXPOSE·CMD)으로 파이썬 앱을 이미지로 만들 수 있다.
- **레이어와 캐시**의 원리를 알고, "requirements를 코드보다 먼저 COPY"하는 순서의 이유를 실측으로 설명할 수 있다.
- `.dockerignore` 로 빌드에 들어가면 안 되는 것(.venv·.git·데이터)을 차단할 수 있다.
- **RUN(빌드 시)과 CMD(실행 시)** 를 혼동 없이 구분할 수 있다.

> 이 문서는 이 과정 전체가 전제하는 5개 핵심 문서 중 하나입니다. 오늘 이후의 모든 것 —
> 내일의 최적화, W25의 Compose, W26의 CI/CD, MP4, 최종 프로젝트 — 이 여기서 쓰는
> Dockerfile 위에서 돌아갑니다.

## ② 왜 필요한가

어제 여러분은 남이 만든 이미지(postgres·nginx·python)를 썼습니다. 그 이미지들은 어디서
왔을까요 — 누군가가 **환경 구축 절차를 코드로 적어** 두었고, 그 코드를 빌드한 결과물입니다.
그 코드가 Dockerfile입니다.

W23의 수동 구축 절차와 나란히 놓으면 정체가 선명해집니다:

```
W23에 손으로 한 것                          Dockerfile로 쓰면
─────────────────────                      ─────────────────────
Ubuntu 서버를 준비한다                      FROM python:3.12-slim
/opt/mlops-mp3 폴더에서 작업한다             WORKDIR /app
코드를 가져온다 (git pull/scp)              COPY . .
pip install -r requirements.txt            RUN pip install -r requirements.txt
"8000 포트를 쓴다"고 RUNBOOK에 적음         EXPOSE 8000
systemd ExecStart에 실행 명령               CMD ["uvicorn", "app.main:app", ...]
```

차이는 단 하나 — 왼쪽은 사람이 서버마다 반복하고 그때마다 조금씩 달라지지만, 오른쪽은
**빌드할 때마다 같은 결과**가 나오고, Git으로 리뷰·버전 관리되며(어제 Q2의 "환경 봉인"이
코드가 된 것), 팀원의 PC에서도 CI에서도 클라우드에서도 같은 이미지를 찍어 냅니다.
[Day 115](day-115.md)에서 "문서 → 스크립트"가 첫 계단이었다면, 오늘은 "환경 → 코드" —
**Infrastructure as Code**의 첫 실전입니다.

## ③ 개념 설명

### Dockerfile 6개 명령 — 당분간 이것이 전부

| 명령 | 하는 일 | 시점 |
|---|---|---|
| `FROM 이미지:태그` | 출발점 (베이스 이미지) — 항상 첫 줄 | 빌드 |
| `WORKDIR /app` | 이후 명령들의 작업 폴더 (없으면 생성) | 빌드 |
| `COPY 원본 대상` | 내 폴더(빌드 컨텍스트)의 파일을 이미지 안으로 | 빌드 |
| `RUN 명령` | 이미지 안에서 명령 실행 (설치 등) — 결과가 **이미지에 저장** | **빌드** |
| `EXPOSE 8000` | "이 포트를 씁니다"라는 **문서** (실제 개방은 -p가) | — |
| `CMD ["명령", "인자"]` | 컨테이너가 **시작될 때** 실행할 것 — 이미지당 하나 | **실행** |

혼동 1순위가 RUN vs CMD입니다: **RUN은 굽는 동안(빌드), CMD는 서빙할 때(실행).**
`pip install` 은 RUN(한 번 구워 두면 끝), `uvicorn` 은 CMD(컨테이너가 뜰 때마다)입니다.

### 레이어와 캐시 — Dockerfile 순서가 빌드 속도를 결정한다

이미지는 통짜가 아니라 **명령 하나 = 층(layer) 하나**의 지층입니다. 그리고 빌드할 때 Docker는
각 층에 대해 "명령도 입력 파일도 지난번과 같은가?"를 검사해 같으면 **캐시를 재사용**합니다.
규칙은 하나뿐입니다:

> **한 층이 바뀌면, 그 층부터 아래(이후)의 모든 층은 다시 만든다.**

이 규칙이 파이썬 이미지의 표준 순서를 강제합니다:

```dockerfile
# 나쁜 순서                          # 좋은 순서
COPY . .                            COPY requirements.txt .
RUN pip install -r requirements.txt  RUN pip install -r requirements.txt
                                    COPY . .
```

나쁜 순서에서는 **코드 한 글자만 고쳐도** COPY 층이 바뀌고 → 그 아래 pip install까지 매번
재실행됩니다 (torch급이면 매번 수 분). 좋은 순서에서는 requirements.txt가 그대로인 한
설치 층은 캐시 — 코드 수정 후 재빌드가 초 단위입니다. **"자주 바뀌는 것일수록 아래로"** —
Dockerfile 설계의 제1원칙입니다.

### 빌드 컨텍스트와 .dockerignore

`docker build .` 의 그 `.` — 현재 폴더 전체가 "빌드 컨텍스트"로 Docker에게 전달됩니다.
`.venv`(수백 MB)·`.git`·데이터가 섞여 있으면 전송부터 느리고, `COPY . .` 에 딸려 들어가
이미지가 오염됩니다. `.gitignore` 의 쌍둥이인 **`.dockerignore`** 로 차단합니다:

```
.venv/
.git/
__pycache__/
*.log
data/
mlruns/
```

## ④ 단계별 실습

### Step 1. 첫 Dockerfile — 최소 API를 이미지로 (1~3교시)

캐시 실험용 미니 프로젝트를 만듭니다 (서버 WSL에서):

```bash
mkdir -p ~/lab/hello-api && cd ~/lab/hello-api
cat > main.py <<'EOF'
from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok", "from": "container"}
EOF
printf "fastapi==0.115.6\nuvicorn==0.34.0\n" > requirements.txt
```

`Dockerfile` (확장자 없음, 대문자 D):

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

빌드:

```bash
docker build -t hello-api:0.1 .
```


### Step 2. 캐시 실험 ① — 코드만 수정 (4교시)

main.py의 응답에 필드 하나를 추가하고 재빌드해 봅니다:

```bash
sed -i 's/"from": "container"/"from": "container", "version": "0.2"/' main.py
docker build -t hello-api:0.2 .
```

```
$ docker build -t hello-api:0.2 .
[+] Building 0.9s (11/11) FINISHED
 => [2/5] WORKDIR /app                                                     0.0s  CACHED
 => [3/5] COPY requirements.txt .                                          0.0s  CACHED
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt               0.0s  CACHED
 => [5/5] COPY . .                                                         0.1s
```

**18.7초 → 0.9초.** pip install 층이 `CACHED` — requirements.txt가 안 바뀌었으니 재사용됐고,
바뀐 코드가 닿는 마지막 COPY 층만 다시 만들어졌습니다.

### Step 3. 캐시 실험 ② — 순서를 망가뜨려 본다 (5교시)

Dockerfile을 "나쁜 순서"로 바꿔(COPY . . 를 pip install 위로) 같은 실험을 반복하세요.
코드 한 글자 수정에도:

```
 => [3/4] COPY . .                                                         0.1s
 => [4/4] RUN pip install --no-cache-dir -r requirements.txt              16.2s
```

pip install이 **매번 16초** — 층 하나가 바뀌면 이후 전부 재빌드라는 규칙의 체감입니다.
지금은 16초지만 내일 torch가 들어오면 **매번 수 분**입니다. 실험 후 좋은 순서로 복구하세요.

### Step 4. .dockerignore — 컨텍스트 다이어트 (6교시)

일부러 오염시켜 봅니다 — venv를 만들고 빌드:

```bash
python3 -m venv .venv
docker build -t hello-api:dirty . 2>&1 | grep "transferring context"
```

```
 => => transferring context: 42.17MB                                       1.8s
```

412B였던 컨텍스트가 42MB로 — `.venv` 가 통째로 Docker에게 전송되고 있고, `COPY . .` 로
이미지 안에까지 들어갑니다 (리눅스 컨테이너에 Windows용까지 뒤섞인 venv가!). 차단:

```bash
printf ".venv/\n.git/\n__pycache__/\n*.log\n" > .dockerignore
docker build -t hello-api:clean . 2>&1 | grep "transferring context"
```

```
 => => transferring context: 583B                                          0.0s
```

**venv는 절대 이미지에 넣지 않습니다** — 이미지 자체가 venv의 역할(격리된 환경)을 하기 때문에,
컨테이너 세계에서 pip install은 시스템에 바로 합니다 (오늘 Dockerfile에 venv가 없는 이유).

### Step 5. 과제 — 수집기 패키지 이미지화 (7~8교시)

W06의 `datapipe` 패키지([Day 030](../01-python-data/day-030.md))를 이미지로 만드세요.

1. datapipe 저장소에 Dockerfile과 .dockerignore 작성 — 오늘의 표준 순서대로.
   CMD는 `["datapipe", "run"]` (pyproject의 콘솔 스크립트가 설치되도록 `RUN pip install .` 사용)
2. `docker build -t datapipe:0.1 .` → `docker run --rm datapipe:0.1` 로 1회 실행형 잡 확인
   (API 서버와 달리 **일하고 종료하는 컨테이너**입니다 — --rm이 어울리는 이유를 한 줄로)
3. 캐시 실험 기록: 코드만 수정/의존성 수정 각각의 재빌드 시간
4. 생각 문제: [Day 115](day-115.md)의 cron 줄이 이 이미지를 쓰면 어떻게 바뀔까?
   (`venv/bin/datapipe run` → `docker run --rm datapipe:0.1` — venv·경로 문제가 왜 사라지는지)

## ⑤ 자주 하는 실수

### COPY . . 을 requirements 설치보다 위에

**증상** — 코드 한 줄 고칠 때마다 재빌드가 수 분 — "Docker 원래 이렇게 느려요?"
**원인** — 캐시 규칙(한 층이 바뀌면 이후 전부 재빌드)에 정면으로 어긋난 순서.
**해결** — 표준 순서 고정: `COPY requirements.txt .` → `RUN pip install` → `COPY . .`.
"자주 바뀌는 것일수록 아래로"를 리뷰 체크리스트에 넣으세요 (Step 3에서 몸으로 확인한 그것).

### CMD 자리에 RUN 감각으로 서버 실행

**증상** — `RUN uvicorn main:app ...` 라고 쓰면 **빌드가 영원히 안 끝납니다** — uvicorn이
빌드 단계에서 포그라운드로 떠 버렸기 때문.
**원인** — RUN(빌드 시 실행·결과 저장)과 CMD(컨테이너 시작 시 실행)의 혼동.
**해결** — 굽는 일(설치·컴파일)은 RUN, 서빙(상주 프로세스)은 CMD. "이미지에 저장될 결과가
있는가?"로 구분하면 틀리지 않습니다.

### CMD를 셸 문자열로 써서 종료 신호를 못 받음

**증상** — `CMD uvicorn main:app --port 8000` (배열 아님) → `docker stop` 이 10초씩 걸리고
매번 강제 종료됨.
**원인** — 셸형 CMD는 `/bin/sh -c` 가 1번 프로세스가 되고 uvicorn은 그 자식 — stop의
SIGTERM([Day 113](day-113.md)의 그 신호)이 셸에 막혀 앱에 전달되지 않습니다. 10초 대기 후
SIGKILL — 진행 중 요청이 끊깁니다.
**해결** — **exec형(JSON 배열)** `CMD ["uvicorn", ...]` — 앱이 1번 프로세스가 되어 신호를 직접
받습니다. 무중단 배포(W25 헬스체크·W26 CD)의 숨은 전제 조건입니다.

### EXPOSE만 쓰고 -p를 잊음

**증상** — Dockerfile에 EXPOSE 8000을 썼는데 `curl localhost:8000` 이 connection refused.
**원인** — EXPOSE는 "이 포트를 쓴다"는 **문서/메타데이터**일 뿐, 실제 포트 개방이 아닙니다.
**해결** — 개방은 실행 시점의 `-p 8000:8000` (또는 W25의 Compose ports:). EXPOSE는 읽는 사람과
도구를 위한 표지판으로 계속 쓰되, 동작을 기대하진 마세요.

### 빌드 컨텍스트에 시크릿이 들어감

**증상** — `.env` 가 `COPY . .` 에 딸려 이미지 안에 — 이미지를 받은 누구든
`docker run --rm 이미지 cat /app/.env` 로 열람 가능.
**원인** — .dockerignore 미비 + "일단 다 복사" 습관.
**해결** — `.env` 를 .dockerignore에 **반드시** 추가 — 시크릿은 이미지에 굽는 게 아니라 실행
시점에 주입하는 것입니다 ([Day 122](day-122.md)의 주제, 커리큘럼의 "시크릿을 이미지에 굽지
않기"가 이것). [Day 109](day-109.md)의 "커밋된 시크릿"과 같은 계열 — **이미지도 배포물**입니다.

**Q2.** 다음 Dockerfile에서 `pandas` 를 requirements.txt에 추가하면 어느 층부터 재빌드되는지,
main.py만 수정하면 어느 층부터인지 각각 답하세요.

```dockerfile
FROM python:3.12-slim        # L1
WORKDIR /app                 # L2
COPY requirements.txt .      # L3
RUN pip install -r requirements.txt   # L4
COPY . .                     # L5
CMD ["uvicorn", "main:app"]  # (메타데이터)
```

<details>
<summary>답 보기</summary>

requirements.txt 수정 → L3의 입력 파일이 바뀌므로 **L3부터** (L3·L4·L5 재빌드 — pip 재실행
포함). main.py만 수정 → L3의 입력(requirements.txt)은 그대로라 L3·L4는 CACHED, **L5만** 재빌드.
"한 층이 바뀌면 그 층부터 이후 전부"라는 규칙 하나에서 두 답이 다 나옵니다 — 그래서 변경
빈도가 낮은 층(의존성)을 위로 올리는 것입니다.

</details>

**Q3.** "이미지 안에는 venv를 만들지 않는다"가 표준인 이유를, venv의 원래 목적과 컨테이너의
성질로 설명하세요.

<details>
<summary>답 보기</summary>

venv의 목적은 **한 기계 위 여러 프로젝트의 패키지 격리**입니다. 그런데 컨테이너 이미지는
그 자체가 앱 하나를 위한 격리된 파일 시스템 전체 — 이미지 안에는 프로젝트가 하나뿐이라
격리할 이웃이 없습니다. venv를 넣으면 격리 위에 격리를 얹어 경로만 복잡해지고(-.venv 경로
지정 문제) 층 크기만 커집니다. 같은 이유로, 호스트에서 만든 .venv가 COPY로 딸려 들어가는 것도
.dockerignore로 차단합니다 — 컨테이너 세계의 venv 역할은 이미지가 합니다.

</details>
