## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **레지스트리**가 이미지 배포 흐름에서 하는 역할을 그림으로 그릴 수 있다 (코드의 GitHub = 이미지의 레지스트리).
- 이미지의 **전체 이름**(`ghcr.io/계정/이름:태그`)을 해부하고, GHCR에 로그인·push·pull 할 수 있다.
- 이미지를 지운 "새 서버"에서 **`docker run` 한 줄로 MP3를 기동**할 수 있다.
- 이번 주 체크포인트에 답한다: **팀원 PC에서 docker run 한 줄로 내 API가 뜨는가.**

## ② 왜 필요한가

이번 주의 성과물 `mlops-mp3:0.1.0` — 지금 어디에 있습니까? **내 서버의 로컬 저장소에만**
있습니다. 팀원에게 주려면? 새 서버에 배포하려면? 코드라면 답을 이미 압니다 — push 하고
pull 하죠. 이미지에도 정확히 같은 허브가 있습니다:

```
코드:    내 저장소 ──push──▶ GitHub ──pull/clone──▶ 서버·팀원
이미지:  내 Docker ──push──▶ 레지스트리 ──pull──▶ 서버·팀원
```

사실 여러분은 이 흐름의 절반을 석 달째 쓰고 있습니다 — `postgres:16` 이 처음에
`Pulling from library/postgres` 하며 내려온 곳이 레지스트리(Docker Hub)였습니다.
오늘은 반대 방향, **우리가 생산자로서 올리는** 첫날입니다.

이 push→pull 회선이 뚫리면 배포의 문법이 바뀝니다. W23의 배포는 "코드를 보내고 서버에서
환경을 조립"(git pull + venv + …)이었지만, 이제는 "**완성품을 내려받아 실행**" 한 줄입니다.
그리고 W26의 CD는 이 회선 위에 자동화를 얹은 것에 불과합니다: 병합 → CI가 빌드·push →
서버가 pull·재기동. 오늘 손으로 하는 모든 단계가 그날 기계의 일이 됩니다.

## ③ 개념 설명

### 이미지의 전체 이름 — 네 조각

```
ghcr.io / mlops-student / mlops-mp3 : 0.1.0
───────   ─────────────   ─────────   ─────
레지스트리   네임스페이스      이미지 이름    태그
(어느 창고)  (누구의 선반)     (무엇)       (어느 버전)
```

`postgres:16` 처럼 짧은 이름은 사실 `docker.io/library/postgres:16` 의 준말입니다 —
레지스트리를 생략하면 Docker Hub로 갑니다. **push가 어디로 갈지는 이름이 정합니다** —
그래서 올리기 전에 `docker tag` 로 전체 이름을 부여하는 절차가 필요합니다 (⑤의 사고 참고).

### 어느 레지스트리 — 이 과정은 GHCR

| 레지스트리 | 성격 | 우리가 고른 이유 |
|---|---|---|
| Docker Hub | 원조 공용 창고 | 공식 이미지(postgres 등)는 계속 여기서 pull |
| **GHCR** (ghcr.io) | GitHub 내장 | **코드와 이미지가 한 지붕** · 저장소 권한 공유 · Actions와 무설정 통합 (W26) |
| 클라우드 사설 (ECR 등) | 회사 인프라용 | 취업 후 만날 것 — 원리는 오늘과 동일 |

### 로그인 — 비밀번호가 아니라 토큰

GHCR push에는 GitHub **PAT**(Personal Access Token, `write:packages` 권한)가 필요합니다.
PAT는 "내 계정의 부분 권한을 담은 열쇠"로, 취급은 SSH 비밀키와 동급입니다 —
어디에도 커밋·평문 저장 금지 ([Day 109](day-109.md)의 그 규율, 그리고 [Day 122](day-122.md)에서
시크릿 관리로 정식 승격). 로그인부터 그 규율대로 합니다: 토큰을 명령줄에 직접 치지 않고
표준 입력으로 흘립니다 (`--password-stdin`).

### pull은 레이어 단위 — 다이어트의 두 번째 보상

이미지는 층의 지층(Day 117)이고, 전송도 층 단위입니다. 서버에 python:3.12-slim 층이 이미
있으면 그 층은 `Already exists` 로 건너뜁니다 — 코드만 바뀐 새 버전의 pull은 바뀐 층
수십 MB만 내려받습니다. 어제까지의 최적화(층 분리·slim)가 **전송량 절감으로 두 번째 보상**을
주는 지점입니다.

## ④ 단계별 실습

### Step 1. 열쇠 발급과 로그인 (1~2교시)

GitHub → Settings → Developer settings → Personal access tokens (classic) →
**Generate new token** — 권한은 `write:packages` (read 포함됨)만, 만료 90일.
생성된 `ghp_...` 값을 복사해 두고 (다시 안 보여 줍니다), 서버(WSL)에서:

```bash
read -s CR_PAT          # 붙여넣고 Enter — 화면에도 히스토리에도 안 남음
echo $CR_PAT | docker login ghcr.io -u mlops-student --password-stdin
```

```
$ echo $CR_PAT | docker login ghcr.io -u mlops-student --password-stdin
Login Succeeded
```

> `read -s` → `--password-stdin` 조합이 오늘의 시크릿 규율입니다. `docker login ghcr.io -u 계정 -p ghp_...`
> 처럼 치면 토큰이 **셸 히스토리에 평문으로** 남습니다 (⑤).

### 오늘 새로 나오는 실수

### push가 docker.io로 가서 거절됨

**증상** —
```
$ docker push mlops-mp3:0.1.0
The push refers to repository [docker.io/library/mlops-mp3]
denied: requested access to the resource is denied
```
**원인** — 레지스트리를 생략한 이름은 Docker Hub의 공식(library) 선반으로 해석됩니다 —
당연히 내 권한이 없습니다.
**해결** — push 전 전체 이름 태그가 필수: `docker tag mlops-mp3:0.1.0 ghcr.io/계정/mlops-mp3:0.1.0`.
"이름이 목적지"라는 규칙만 기억하면 다시는 안 겪습니다.

### denied: permission_denied (GHCR)

**증상** — 전체 이름도 맞는데 push에서 `denied: permission_denied: write_package`.
**원인** — PAT 권한에 write:packages가 없거나, 토큰 만료, 또는 조직 저장소의 패키지 권한 문제.
**해결** — 토큰 권한·만료 확인 후 재로그인 (`docker logout ghcr.io` → login). W26에서는 이
로그인 자체가 Actions의 자동 토큰(GITHUB_TOKEN)으로 대체되어 만료 문제도 사라집니다 — 오늘의
PAT는 수동 시대의 열쇠입니다.

### 토큰을 명령줄에 평문으로

**증상** — `docker login ghcr.io -u me -p ghp_xxxx` — 경고까지 떠 줍니다:
```
WARNING! Using --password via the CLI is insecure. Use --password-stdin.
```
그리고 그 토큰이 `~/.bash_history` 에 영구 기록.
**원인** — 편의가 규율을 이김.
**해결** — 오늘 배운 `read -s` + `--password-stdin`. 이미 쳤다면? [Day 109](day-109.md) 규율
그대로 — **토큰 즉시 폐기·재발급**이 먼저, `history -d` 는 그다음.

### 이미지를 무심코 Public으로

**증상** — 패키지 공개 설정을 Public으로 — 이미지 안의 코드·모델·(만약 굽혔다면) 설정까지
전 세계 다운로드 가능.
**원인** — "포트폴리오니까 공개"를 이미지에도 반사적으로 적용.
**해결** — 코드 공개와 이미지 공개는 별개 결정입니다. 이미지는 실행 가능한 완성품 — 기본
Private, 공개는 내용물 검토(시크릿·데이터·모델 라이선스, [Day 088](../04-deep-learning-serving/day-088.md)의
그 확인) 후에만.

### 팀원이 pull이 안 된다는데 나는 된다

**증상** — 짝의 PC에서 `denied` — 내 PC에선 잘 되는데.
**원인** — Private 패키지는 **권한 + 로그인** 둘 다 필요합니다. 권한만 주고 짝이 login을
안 했거나, 짝이 read:packages 없는 토큰으로 로그인.
**해결** — 체크리스트로: ① 패키지에 협업자 read 권한 ② 짝의 PAT에 read:packages ③ 짝이
docker login ghcr.io 성공. "안 되는 쪽의 로그인 상태"부터 보는 것이 순서입니다.

내일 코드 한 줄 고쳐 0.1.1을 push하면 1~2개 층만 올라갈 것입니다. 세 현상을 관통하는 원리를
설명하세요.

<details>
<summary>답 보기</summary>

레지스트리는 이미지를 **내용 주소(digest) 기반의 층 단위**로 저장합니다. :latest는 같은 층들에

Git의 객체 저장과 같은 철학이고, 층 순서를 잘 설계할수록(변경이 아래층에 국한) 전송·저장 모두
이득입니다.

**Q3.** 태그 0.1.0과 digest(sha256:f4a9...)의 차이를 설명하고, "정확히 지금 운영 중인 그
이미지"를 지목해야 하는 상황(장애 조사·롤백)에서 어느 쪽을 기록해야 하는지 답하세요.

<details>
<summary>답 보기</summary>

태그는 **움직일 수 있는 이름표**(같은 0.1.0에 다른 이미지를 다시 push하면 갈아탐)이고, digest는
**내용의 해시**라 불변입니다. 장애 조사·감사 기록에는 digest(또는 태그+digest 병기)를 남겨야
"그때 그 바이트"를 특정할 수 있습니다. 운영 관례는 사람용으로는 불변 규칙을 지키는 태그(버전·
커밋 sha 태그)를 쓰되, 배포 기록·락 파일에는 digest를 남기는 것 — Day 128의 CI 태그 전략에서
sha 태그가 이 역할을 맡습니다.

</details>

## 주간 퀴즈 21 — W24 (Docker)

<details>
<summary>1. 이미지와 컨테이너의 관계를 한 문장으로, 각각을 지우는 명령은?</summary>

이미지는 읽기 전용 스냅샷(틀), 컨테이너는 그것을 실행 중인 인스턴스(붕어빵). 컨테이너는 docker rm, 이미지는 docker rmi.

</details>

<details>
<summary>2. 컨테이너가 "가벼운 VM"이 아닌 이유는?</summary>

커널을 호스트와 공유하는 격리된 프로세스이기 때문 — 부팅이 없어 초 단위 기동, 호스트 ps에 컨테이너 프로세스가 보임.

</details>

<details>
<summary>3. RUN과 CMD의 차이는?</summary>

RUN은 빌드 시 실행되어 결과가 이미지 층에 저장(설치), CMD는 컨테이너 시작 시 실행(서버 기동). CMD는 exec형(JSON 배열)으로 써야 SIGTERM을 앱이 직접 받는다.

</details>

<details>
<summary>4. "COPY requirements.txt → pip install → COPY . ." 순서인 이유는?</summary>

캐시 규칙(한 층이 바뀌면 이후 전부 재빌드) 때문 — 자주 바뀌는 코드를 아래로 보내 의존성 설치 층의 캐시를 보존, 재빌드를 초 단위로.

</details>

<details>
<summary>5. 이미지 다이어트 4단 처방은?</summary>

slim 베이스(-900MB) · CPU 휠 지정(CUDA 5GB 차단) · --no-cache-dir(pip 캐시) · 멀티스테이지(공사장 폐기). MP3 실측 3.46GB → 1.61GB.

</details>

<details>
<summary>6. RUN rm이 이미지 크기를 못 줄이는 이유는?</summary>

레이어는 불변 — 뒤 층의 삭제는 가림막일 뿐 앞 층의 바이트는 그대로 실림. 같은 RUN 안에서 지우거나 멀티스테이지로 층째 버려야 한다.

</details>

<details>
<summary>7. 볼륨과 바인드 마운트의 선택 기준은?</summary>

운영 상태(DB·로그·모델)는 Docker가 관리하는 named volume, 개발 중 코드·설정 주입은 바인드 마운트. "운영은 굽고 개발은 접붙인다".

</details>

<details>
<summary>8. 컨테이너 안에서 localhost로 옆 컨테이너를 부르면 안 되는 이유와 올바른 방법은?</summary>

localhost는 그 컨테이너 자신(격리). 사용자 정의 네트워크에 함께 태우고 컨테이너 이름을 호스트명으로 사용 (mp3-db:5432).

</details>

<details>
<summary>9. -p를 달지 않은 DB 컨테이너가 보안상 좋은 이유는?</summary>

-p는 호스트 밖 공개 — 없으면 같은 도커 네트워크의 이웃만 접근 가능해, 외부 스캔·무차별 대입 대상에서 제외된다. 내부 전용은 내부에만.

</details>

<details>
<summary>10. 이미지 전체 이름 네 조각과, 생략 시 기본값은?</summary>

레지스트리/네임스페이스/이름:태그 (ghcr.io/mlops-student/mlops-mp3:0.1.0). 레지스트리 생략 = docker.io(Hub), 태그 생략 = :latest — push 목적지는 이름이 정한다.

</details>
