## ③ 개념 설명

### 데이터 파이프라인에서 무엇을 테스트하나

일반 애플리케이션과 다릅니다. **코드뿐 아니라 데이터도 테스트 대상**입니다.

| 층 | 테스트 대상 | 예 | 속도 |
|---|---|---|---|
| **단위** | 순수 함수 | `_to_int('-') is None` · 검증 규칙 | 빠름 (ms) |
| **통합** | DB와의 상호작용 | 멱등 적재 · 격리 저장 | 보통 (초) |
| **계약** | 외부 API 응답 형식 | 필드가 그대로인가 | 느림 (네트워크) |
| **데이터** | 실제 데이터의 성질 | 결측률 · 행 수 · 중복 | 보통 |

**대부분을 단위 테스트로 만들 수 있게 설계하는 것이 중요합니다.**
[Day 043](day-043.md)에서 `transform()` 을 **DB·API 없는 순수 함수**로 만든 이유가 이것입니다.

### 반드시 있어야 할 테스트 6개 ★

| # | 테스트 | 왜 |
|---|---|---|
| 1 | **멱등성** — 3회 실행 후 행 수 동일 | 평가 기준 1번. 리팩터링으로 가장 잘 깨짐 |
| 2 | **인젝션 무력화** — 공격 문자열이 0행 | 누가 f-string으로 "고치면" 즉시 빨개짐 |
| 3 | **변환 함수** — 결측·시간대·경계값 | 조용히 틀리는 대표 지점 |
| 4 | **검증 규칙** — 통과 케이스 + 격리 케이스 | 규칙이 실제로 걸러내는지 |
| 5 | **트랜잭션 롤백** — 실패 시 되돌아가는지 | 부분 적재 사고 방지 |
| 6 | **집계 검산** — 알려진 값과 일치 | 쿼리를 고쳤을 때 결과가 바뀌면 감지 |

> **4번에서 "통과 케이스"를 빠뜨리기 쉽습니다.**
> 규칙이 **모든 것을 거부해도** 격리 테스트는 통과합니다. **정상 데이터가 통과하는지도 확인**해야 합니다.

### 테스트를 빠르고 안정적으로

| 문제 | 해결 |
|---|---|
| 실제 API 호출로 느리고 불안정 | `tests/fixtures/` 에 응답 저장 → 가짜 소스 |
| DB 상태에 따라 결과가 달라짐 | 테스트마다 트랜잭션 롤백, 또는 전용 DB |
| 실행 순서에 의존 | 각 테스트가 스스로 준비하고 정리 |
| 오늘 날짜에 따라 결과가 달라짐 | 시각을 **인자로 주입** (`now` 를 파라미터로) |

```python
# ❌ 테스트할 수 없음
def window(source): 
    return get_watermark(source) - OVERLAP, datetime.now(KST)

# ✅ 시각을 주입받으면 테스트 가능
def window(source, *, now: datetime | None = None):
    now = now or datetime.now(KST)
    return get_watermark(source) - OVERLAP, now
```

# tests/test_transform.py — ③ 변환 함수
import pytest
from datetime import datetime, timedelta, timezone

from datapipe.stages.load_db import _to_int, _to_timestamp

KST = timezone(timedelta(hours=9))


@pytest.mark.parametrize("raw,expected", [
    ("45", 45), ("0", 0), ("45.7", 45),
    ("-", None), ("", None), (None, None), ("N/A", None),
    ("abc", None),                       # 변환 실패도 NULL (예외 아님)
])
def test_정수_변환(raw, expected):
    assert _to_int(raw) == expected


def test_결측을_0으로_바꾸지_않는다():
    """'-'(측정 안 됨)과 '0'(농도 0)은 다른 정보입니다."""
    assert _to_int("-") is None
    assert _to_int("0") == 0


def test_시각에_KST가_붙는다():
    ts = _to_timestamp("2025-06-01 14:00")
    assert ts.utcoffset() == timedelta(hours=9)
    assert ts == datetime(2025, 6, 1, 14, 0, tzinfo=KST)


def test_자정_24시_표기를_다음날_0시로():
    ts = _to_timestamp("2025-06-01 24:00")
    assert ts.day == 2 and ts.hour == 0


def test_잘못된_시각은_None():
    assert _to_timestamp("2025/06/01") is None
    assert _to_timestamp("") is None

# tests/test_rules.py — ④ 검증 규칙 (통과 + 격리 양쪽)
from datapipe.rules_air import AIR_RULES
from datapipe.validators import validate

VALID = {"stationName": "종로구", "dataTime": "2025-06-01 14:00",
         "pm10Value": "45", "pm25Value": "22"}


def test_정상_데이터는_통과한다():
    """규칙이 모든 것을 거부하지 않는지 — 빠뜨리기 쉬운 테스트."""
    r = validate([VALID], AIR_RULES)
    assert len(r.valid) == 1 and len(r.rejected) == 0


def test_결측은_통과한다():
    rec = {**VALID, "pm10Value": "-", "pm25Value": "-"}
    r = validate([rec], AIR_RULES)
    assert len(r.valid) == 1, "결측은 불량이 아닙니다"


@pytest.mark.parametrize("field,value,reason_part", [
    ("stationName", "",     "필수값"),
    ("dataTime",    "",     "필수값"),
    ("pm10Value",   "9999", "범위"),
    ("pm25Value",   "-5",   "범위"),
])
def test_불량_데이터는_격리된다(field, value, reason_part):
    r = validate([{**VALID, field: value}], AIR_RULES)
    assert len(r.rejected) == 1
    assert reason_part in r.rejected[0]["reason"]


def test_pm25가_pm10보다_크면_격리():
    r = validate([{**VALID, "pm10Value": "40", "pm25Value": "60"}], AIR_RULES)

# tests/test_pipeline.py — ①②⑤⑥ 통합
def test_세번_실행해도_행수가_같다(fake_source):
    """MP1 평가 기준 1번: 멱등성."""
    counts = []
    for _ in range(3):
        run_etl("air_seoul", test_context())
        counts.append(db.fetch_value("SELECT COUNT(*) FROM measurement"))
    assert counts[0] == counts[1] == counts[2], f"멱등성 위반: {counts}"


def test_인젝션_문자열이_무력화된다():
    rows = db.fetch_all(
        "SELECT * FROM station WHERE name = %s", ("종로구' OR '1'='1",)
    )
    assert rows == []


def test_트랜잭션_롤백():
    before = db.fetch_value("SELECT COUNT(*) FROM station")
    with pytest.raises(RuntimeError):
        with db.connect() as conn, conn.cursor() as cur:
            cur.execute("INSERT INTO station (name, sido) VALUES ('테스트', '서울')")
            raise RuntimeError("일부러 실패")
    assert db.fetch_value("SELECT COUNT(*) FROM station") == before


def test_집계_검산():
    """등급 분포의 합이 전체 관측 수와 같아야 합니다."""
    total = db.fetch_value("SELECT COUNT(*) FROM measurement WHERE pm10 IS NOT NULL")
    by_grade = db.fetch_all("""
        SELECT CASE WHEN pm10 <= 30 THEN 'A' WHEN pm10 <= 80 THEN 'B'
                    WHEN pm10 <= 150 THEN 'C' ELSE 'D' END AS g, COUNT(*) AS n
        FROM measurement WHERE pm10 IS NOT NULL GROUP BY 1
    """)
    assert sum(r["n"] for r in by_grade) == total
```

```markdown
# 서울시 대기질 수집·적재·분석 파이프라인

공공데이터 API에서 서울 40개 측정소의 시간별 대기질을 자동 수집해

![일별 PM10 추이](docs/img/trend.png)

## 무엇을 하는가

- **수집** — 한국환경공단 에어코리아 API, 시간당 1회, 재시도·간격 준수
- **검증** — 9종 규칙으로 불량 행을 격리 테이블에 원본과 함께 보관
- **적재** — `ON CONFLICT` 기반 멱등 적재. 몇 번을 실행해도 결과가 같음
- **분석** — 윈도우 함수를 포함한 SQL 10문 + 차트 3종

2026-07-13 ~ 08-12 기준 **29,074행** 적재. 자세한 결과는 [보고서](docs/report.md).

## 아키텍처

```
[에어코리아 API]
      │ Extract   원본 JSON 을 data/raw/<날짜>/ 에 그대로 보관
      ▼
[원본 파일]
      │ Transform 타입 변환 · 시간대 부여 · 측정소 매핑 · 검증 9종
      ▼                     └─ 불량 행 → measurement_rejected (원본 jsonb)
[적재용 행]
      │ Load      임시 테이블 + COPY + ON CONFLICT (멱등)
      ▼
[PostgreSQL]  station · measurement · ingest_run · ingest_watermark
```

**문제 — `assert result >= 0` 은 항상 참입니다.** 행 수는 음수가 될 수 없으므로

**"이 테스트가 실패하려면 무엇이 잘못돼야 하나?"** → 예외가 나야만 합니다.

```python
def test_적재되고_조회된다():
    before = db.fetch_value("SELECT COUNT(*) FROM measurement")

    rows = [(1, datetime(2025, 6, 1, 14, tzinfo=KST), 45, 22)]
    affected = staged_upsert(rows, table="measurement", columns=COLUMNS,
                             conflict_keys=KEYS, update_columns=("pm10", "pm25"))

    assert affected == 1
    after = db.fetch_value("SELECT COUNT(*) FROM measurement")
    assert after == before + 1

    row = db.fetch_one(
        "SELECT pm10, pm25 FROM measurement WHERE station_id = %s AND measured_at = %s",
        (1, datetime(2025, 6, 1, 14, tzinfo=KST)),
    )
    assert row["pm10"] == 45 and row["pm25"] == 22


def test_같은_키를_다시_넣으면_갱신된다():
    """멱등성 + DO UPDATE 동작 확인."""
    ts = datetime(2025, 6, 1, 15, tzinfo=KST)
    staged_upsert([(1, ts, 45, 22)], **KW)
    before = db.fetch_value("SELECT COUNT(*) FROM measurement")

    staged_upsert([(1, ts, 99, 50)], **KW)          # 같은 키, 다른 값

    assert db.fetch_value("SELECT COUNT(*) FROM measurement") == before   # 안 늘어남
    row = db.fetch_one("SELECT pm10 FROM measurement "
                       "WHERE station_id = %s AND measured_at = %s", (1, ts))
    assert row["pm10"] == 99                        # 값은 갱신됨
```

|---|---|
| **실패할 수 있는가** | 코드를 망가뜨리면 빨개지는가 |
| **구체적인 값을 단언하는가** | `is not None` 이 아니라 `== 45` |
| **상태 변화를 확인하는가** | 반환값뿐 아니라 **DB의 실제 상태** |
| **혼자 돌아가는가** | 실행 순서·이전 테스트에 의존하지 않음 |

`staged_upsert` 의 `INSERT` 를 주석 처리하고 테스트를 돌립니다. **빨개지지 않으면 그 테스트는 가짜입니다.**
</details>

**2.** 리뷰어가 "README를 보고 실행했는데 3단계에서 `relation "station" does not exist` 가 났다"고 합니다. 무엇이 문제이며 어떻게 고치나요?

<details>
<summary>답 보기</summary>

**원인 후보를 순서대로 확인합니다.**

| # | 가능성 | 확인 |
|---|---|---|
| 1 | **마이그레이션 단계가 README에 없음** | 빠른 시작에 `.\scripts\migrate.ps1` 이 있는가 |
| 2 | **마이그레이션 스크립트가 커밋 안 됨** | `git ls-files scripts/` |
| 3 | `PGDATABASE` 가 다른 DB를 가리킴 | `.env.example` 에 `PGDATABASE` 가 있는가 |
| 4 | 마이그레이션 파일 순서가 틀림 | 001 → 002 순으로 실행되는가 |
| 5 | `CREATE DATABASE` 단계가 빠짐 | README에 있는가 |

**가장 흔한 것은 1과 3입니다.**

**3번이 특히 교묘합니다.** `.env.example` 에 `PGDATABASE` 가 없으면
리뷰어가 [Day 041](day-041.md) 실습 때 쓰던 `shop` 에 그대로 붙습니다.
`shop` 에는 `station` 테이블이 없으니 정확히 저 에러가 납니다.

**고침**

```
# .env.example
PGHOST=localhost
PGPORT=5432
PGDATABASE=mp1          ← 값을 채워 두세요. 빈 값보다 기본값이 낫습니다
PGUSER=postgres
PGPASSWORD=
PUBLIC_DATA_KEY=
```

**README에도 명시**

```markdown
> **주의** — `.env` 의 `PGDATABASE` 가 `mp1` 인지 확인하세요.
> 다른 실습 DB에 연결되면 `relation "station" does not exist` 가 발생합니다.
```

**더 나은 해결 — 코드가 먼저 확인하게 합니다**

```python
def check_schema() -> None:
    """필수 테이블이 있는지 확인하고, 없으면 안내와 함께 종료합니다."""
    required = {"station", "measurement", "ingest_run"}
    existing = {
        r["table_name"]
        for r in fetch_all(
            "SELECT table_name FROM information_schema.tables WHERE table_schema = %s",
            ("public",),
        )
    }
    missing = required - existing
    if missing:
        raise ConfigError(
            f"테이블 없음: {', '.join(sorted(missing))} "
            f"(현재 DB: {fetch_value('SELECT current_database()')})\n"
            f"→ scripts/migrate.ps1 을 실행하고 .env 의 PGDATABASE 를 확인하세요."
        )
```

```powershell
$ datapipe etl --source air_seoul
CRITICAL 설정 오류: 테이블 없음: measurement, station (현재 DB: shop)
→ scripts/migrate.ps1 을 실행하고 .env 의 PGDATABASE 를 확인하세요.
```

**에러 메시지가 다음 행동을 알려 주는 것**이 좋은 도구의 조건입니다.
[Day 045](day-045.md)에서 "알림에 다음 행동을 적는다"고 한 것과 같은 원칙입니다.
</details>

**3.** 보고서 "요약" 3줄을 쓰려는데 결론이 7개입니다. 어떻게 3개로 줄이겠습니까?

<details>
<summary>답 보기</summary>

**"읽는 사람이 이것만 기억한다면 무엇이어야 하나"** 를 기준으로 고릅니다.

**선별 기준 4가지**

| 기준 | 질문 |
|---|---|
| **행동을 바꾸는가** | 이걸 알면 무언가 달라지는가? |
| **예상과 다른가** | 당연한 결과는 요약에 들어갈 가치가 낮음 |
| **근거가 강한가** | 표본이 충분하고 검산된 것 |
| **다른 것을 포함하는가** | 상위 결론이 하위를 함축하면 상위만 |

**예시 — 7개를 3개로**

```
① 기간 평균 34.7 (좋음~보통)              → ③에 흡수 (배경 정보)
② 7월 28일 84.6 으로 급등                 → ★ 유지 (예상 밖 + 근거 강함)
③ 37/40 측정소가 동시에 나쁨               → ★ ②와 합쳐 하나로
④ 도로변 측정소가 이상 이탈 상위            → ★ 유지 (행동을 바꿈)
⑤ 시간대별 패턴 존재                       → 본문으로 (④의 근거)
⑥ 평균 순위와 빈도 순위가 다름              → ★ 유지 (행동을 바꿈)
⑦ 서초구 데이터 결측                       → 한계 섹션으로 (결론이 아님)
```

**최종 3줄**

```markdown
1. 기간 평균 PM10은 34.7 ㎍/㎥('좋음~보통')이나, **7월 28일 하루가 84.6으로 2.4배 급등**했다.
   그날 40개 측정소 중 37곳(92.5%)이 '나쁨' 이상이어서 **광역 현상**으로 확인된다.
2. '평균이 높은 측정소'(강북구)와 "'나쁨' 발생이 잦은 측정소"(도로변A)가 **서로 다르다.**
   만성 노출과 급성 고농도 노출은 다른 대응이 필요하다.
3. 이상 이탈 상위 5곳 중 3곳이 도로변 측정소로, **측정소 유형별 분리 관리 기준**이 필요하다.
```

**줄인 것들의 행선지**

| 항목 | 어디로 |
|---|---|
| ① 배경 정보 | 3장 "데이터와 방법" |
| ⑤ 세부 근거 | 4장 해당 질문의 본문 |
| ⑦ 데이터 한계 | 6장 "한계와 다음 단계" |

**버리는 것이 아니라 자리를 옮기는 것입니다.**

> **요약은 마지막에 쓰고 맨 앞에 놓습니다.**
> 그리고 **요약만 읽어도 의사결정이 가능한지** 스스로 확인하세요.
> "자세한 건 본문에서"라고 쓰고 싶어진다면, 그건 요약이 아직 요약이 아니라는 뜻입니다.
</details>
