## ② 왜 필요한가

혹시 이런 폴더를 가지고 계신가요.

```
보고서.hwp
보고서_수정.hwp
보고서_최종.hwp
보고서_최종_진짜최종.hwp
보고서_최종_진짜최종_v2.hwp
보고서_최종_진짜최종_v2_이거씀.hwp
```

웃기지만 이것도 나름의 **버전 관리**입니다. 다만 세 가지가 안 됩니다.

| 안 되는 것 | 구체적으로 |
|---|---|
| **무엇이 바뀌었는지 모른다** | `_v2` 와 `_이거씀` 의 차이가 뭐였죠? 열어서 눈으로 찾아야 합니다 |
| **왜 바꿨는지 모른다** | 3개월 뒤의 나는 이 수정이 왜 필요했는지 기억하지 못합니다 |
| **같이 못 한다** | 둘이 동시에 고치면 한 명의 작업이 통째로 사라집니다 |

코드에서는 이 문제가 훨씬 심각해집니다.

- **"어제까지 잘 되던 게 오늘 안 됩니다."** — 어디를 건드렸는지 알 수가 없습니다.
- **`Ctrl + Z` 는 구세주가 아닙니다.** 에디터를 껐다 켜면 되돌리기 기록은 사라집니다.
- **지운 코드가 나중에 필요해집니다.** 혹시 몰라 주석 처리해 두면 파일이 주석 무덤이 됩니다.

```python
# def old_login(id, pw):        ← 혹시 몰라서 안 지움
#     ...                          (그리고 영원히 남음)
# def old_login_v2(id, pw):
#     ...
```

Git은 이 셋을 한 번에 해결합니다. **"언제 · 누가 · 무엇을 · 왜 바꿨는지"** 를 전부 기록해 두고, 원하는 시점으로 언제든 돌아갈 수 있게 해 줍니다. 그래서 코드에서 주석 무덤이 사라집니다. **지워도 됩니다. 기록에 남아 있으니까요.**

## ③ 개념 설명

### 버전 관리 시스템(VCS)이란

**버전 관리 시스템(Version Control System)** 은 파일의 변경 이력을 자동으로 기록하고, 원하는 시점으로 되돌릴 수 있게 해 주는 프로그램입니다. 소프트웨어 분야에서는 **형상관리** 라고도 부릅니다.

게임의 **세이브 파일**을 떠올리면 정확합니다.

| 게임 | Git |
|---|---|
| 보스전 직전에 저장 | 기능 하나를 완성하고 **커밋** |
| 죽으면 마지막 세이브로 로드 | 망가지면 마지막 커밋으로 **되돌리기** |
| 슬롯을 여러 개 만들어 다른 선택지 시험 | **브랜치**를 파서 다른 방식 시도 |
| 세이브 파일을 친구에게 전송 | **push / pull** 로 팀원과 공유 |

### 두 가지 방식 — 중앙집중식과 분산형

| | 중앙집중식 (SVN, CVS) | **분산형 (Git)** |
|---|---|---|
| 이력이 있는 곳 | 서버에만 | **내 컴퓨터에도 전부** |
| 인터넷이 끊기면 | 아무것도 못 함 | 커밋·이력 조회 다 됨 |
| 서버가 날아가면 | 이력 전부 소실 | 누구 컴퓨터에서든 복원 가능 |
| 속도 | 서버 왕복 필요 | 대부분 로컬에서 처리 → 빠름 |

> Git이 사실상 표준이 된 가장 큰 이유가 **"내 컴퓨터에 저장소 전체 사본이 있다"** 는 점입니다.
> 그래서 비행기 안에서도 커밋할 수 있고, 실수해도 복구할 데이터가 여러 곳에 남아 있습니다.

### Git은 "변경분"이 아니라 "스냅샷"을 저장합니다

많은 사람이 Git이 "바뀐 부분만 차곡차곡 쌓는다"고 생각하지만, 실제로는 **커밋할 때마다 프로젝트 전체의 사진(스냅샷)을 한 장 찍습니다.**

```
커밋 1        커밋 2        커밋 3
┌────────┐   ┌────────┐   ┌────────┐
│ a.py A │   │ a.py A │   │ a.py A │   ← 안 바뀐 파일은
│ b.py B │   │ b.py B'│   │ b.py B'│      이전 것을 "가리키기"만 함
│ c.py C │   │ c.py C │   │ c.py C'│      (그래서 용량이 안 늘어남)
└────────┘   └────────┘   └────────┘
```

바뀌지 않은 파일은 새로 저장하지 않고 **이전 것을 가리키는 링크**만 남깁니다. 그래서 커밋 100개를 쌓아도 폴더를 100번 복사한 것보다 훨씬 가볍습니다.

이 구조 덕분에 **"3번째 커밋 시점의 프로젝트 전체"** 를 통째로 즉시 꺼낼 수 있습니다. 변경분만 쌓는 방식이라면 처음부터 전부 다시 계산해야 합니다.

> `.git` 폴더 안에 실제로 어떤 모양으로 들어가는지는 [21강 `.git` 폴더 해부](lesson-21.md)에서 직접 열어 봅니다.
> 지금은 **"커밋 = 그 시점 프로젝트의 사진 한 장 + 메모"** 로 기억하면 충분합니다.

### Git과 GitHub는 다릅니다

가장 많이 헷갈리는 부분이고, 면접에서도 자주 묻습니다.

| | **Git** | **GitHub** |
|---|---|---|
| 정체 | 내 컴퓨터에 설치하는 **프로그램** | 인터넷의 **웹 서비스** |
| 하는 일 | 변경 이력을 기록·관리 | Git 저장소를 올려 두고 공유 |
| 만든 곳 | 리누스 토르발스 (2005) | GitHub 사 (2008, 현재 Microsoft) |
| 없어도 되나 | **없으면 아무것도 안 됨** | 없어도 Git은 잘 돌아감 |
| 비슷한 것 | (사실상 없음) | GitLab, Bitbucket, Gitea |

> **비유** — Git은 **한글·워드** 같은 프로그램이고, GitHub는 **구글 드라이브** 같은 저장 공간입니다.
> 워드 없이 구글 드라이브만 쓸 수는 없지요. Git 없이 GitHub만 쓰는 것도 마찬가지입니다.

GitHub는 단순 저장소를 넘어 **협업 도구**를 얹은 것이 진짜 가치입니다.

| 기능 | 용도 |
|---|---|
| Pull Request | "제 코드 검토하고 합쳐 주세요" 요청 |
| Issues | 할 일·버그 관리 |
| Actions | 코드가 올라오면 자동으로 검사·배포 |
| Pages | 저장소를 그대로 웹사이트로 공개 (이 사이트도 여기로 운영합니다) |

## ④ 단계별 실습

### Step 1. Git이 설치되어 있는지 확인하기

터미널(Windows는 **PowerShell** 또는 **Git Bash**)을 열고 입력합니다.

```bash
git --version
```

실행 결과:

```
git version 2.45.2.windows.1
```

버전 번호가 나오면 설치되어 있는 것입니다. 아래처럼 나오면 아직 설치 전입니다.

```
'git'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는
배치 파일이 아닙니다.
```

> 설치는 [02강](lesson-02.md)에서 처음부터 같이 합니다. 지금 안 되어 있어도 괜찮습니다.

### Step 2. 버전 관리를 손으로 해 보기 (불편함 체감하기)

Git을 쓰기 전에, **왜 필요한지 몸으로 느껴 보는 것**이 이 강의 진짜 목적입니다.
바탕화면에 `manual-backup` 폴더를 만들고 그 안에서 작업합니다.

```bash
mkdir manual-backup
cd manual-backup
```

메모장이나 VS Code로 `recipe.txt` 를 만들고 이렇게 씁니다.

```
김치찌개 레시피
1. 김치를 볶는다
2. 물을 붓는다
```

이제 "버전 1"을 백업합니다. **폴더째 복사하는 방식**입니다.

```bash
mkdir v1
cp recipe.txt v1/
```

> PowerShell이라면 `cp` 대신 `Copy-Item recipe.txt v1/` 를 씁니다. Git Bash에서는 `cp` 가 그대로 됩니다.

`recipe.txt` 를 고칩니다.

```
김치찌개 레시피
1. 김치를 잘게 썬다
2. 김치를 볶는다
3. 물을 붓는다
4. 두부를 넣는다
```

또 백업합니다.

```bash
mkdir v2
cp recipe.txt v2/
```

이제 스스로에게 물어보세요.

1. **v1과 v2의 차이가 정확히 무엇인가요?** → 두 파일을 나란히 놓고 눈으로 비교해야 합니다.
2. **왜 v2로 바꿨나요?** → 어디에도 안 적혀 있습니다.
3. **레시피가 30번 바뀌면?** → `v1` … `v30` 폴더가 생기고, 원본 용량의 30배가 됩니다.
4. **친구도 같이 고치면?** → `v2_철수`, `v2_영희` … 누가 최신인지 아무도 모릅니다.

이 네 가지가 정확히 **Git이 해결하는 문제**입니다.

### Step 3. 같은 일을 Git으로 하면 (미리보기)

지금은 이해하지 않아도 됩니다. **그냥 따라 쳐 보세요.** 각 명령의 의미는 03~06강에서 하나씩 배웁니다.

```bash
cd manual-backup
git init
git add recipe.txt
git commit -m "김치찌개 레시피 초안"
```

`recipe.txt` 를 한 번 더 고친 다음:

```bash
git add recipe.txt
git commit -m "김치를 썰어 넣는 단계 추가, 두부 추가"
```

이제 이력을 봅니다.

```bash
git log --oneline
```

실행 결과:

```
9f3c1a7 (HEAD -> main) 김치를 썰어 넣는 단계 추가, 두부 추가
4b8e2d5 김치찌개 레시피 초안
```

무엇이 바뀌었는지도 바로 볼 수 있습니다.

```bash
git diff 4b8e2d5 9f3c1a7
```

실행 결과:

```diff
diff --git a/recipe.txt b/recipe.txt
index 8a1f3c2..d4e7b90 100644
--- a/recipe.txt
+++ b/recipe.txt
@@ -1,3 +1,5 @@
 김치찌개 레시피
-1. 김치를 볶는다
-2. 물을 붓는다
+1. 김치를 잘게 썬다
+2. 김치를 볶는다
+3. 물을 붓는다
+4. 두부를 넣는다
```

Step 2에서 눈으로 비교해야 했던 것을 **`-` 는 지워진 줄, `+` 는 추가된 줄**로 한눈에 보여 줍니다.
그리고 `v1`, `v2` 같은 폴더가 **하나도 안 생겼습니다.**

> 방금 만든 `manual-backup` 폴더는 연습용이니 나중에 지워도 됩니다.
> 03강부터는 `git-practice` 라는 새 폴더로 10강까지 쭉 이어서 실습합니다.

### Step 4. 실제 프로젝트의 이력 구경하기

브라우저에서 아무 오픈소스 저장소나 열어 보세요. 예를 들어 파이썬 웹 프레임워크 Flask입니다.

<https://github.com/pallets/flask/commits/main>

- 커밋 하나를 클릭하면 **초록색(추가) / 빨간색(삭제)** 으로 변경된 줄이 보입니다.
- 커밋 메시지에 **왜 바꿨는지**가 적혀 있습니다.
- 오른쪽 위 시계 아이콘(`History`)으로 파일 한 개의 역사만 따라갈 수도 있습니다.

수십 명이 10년 넘게 고쳐 온 코드인데도 "누가 언제 왜"가 전부 남아 있습니다. 이것이 우리가 만들 결과물입니다.

### 같은 일을 GUI로 하면

VS Code에는 Git이 내장되어 있습니다.

| 위치 | 기능 |
|---|---|
| 왼쪽 사이드바 **Source Control** (가지 모양 아이콘, `Ctrl+Shift+G`) | 변경된 파일 목록 · 스테이지 · 커밋 |
| 파일을 클릭 | 왼쪽=이전, 오른쪽=현재 로 **나란히 비교**(diff) |
| 왼쪽 아래 브랜치 이름 | 클릭하면 브랜치 전환 |

> 이 커리큘럼은 **명령어를 기준**으로 진행합니다. 원리를 명령어로 익힌 다음 GUI를 쓰면 편하지만,
> 반대로 GUI만 먼저 익히면 문제가 생겼을 때 손을 못 댑니다. 순서를 지켜 주세요.

## ⑤ 자주 하는 실수

### `'git'은(는) 내부 또는 외부 명령 ... 이 아닙니다`

```
'git'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는
배치 파일이 아닙니다.
```

macOS·Linux나 Git Bash에서는 이렇게 나옵니다.

```
bash: git: command not found
```

**원인** — ① Git이 설치되지 않았거나 ② 설치는 됐는데 **터미널을 껐다 켜지 않았습니다.**
**해결** — 설치 후 **터미널 창을 완전히 닫고 새로 여세요.** 환경 변수 PATH는 새 창부터 적용됩니다. VS Code를 쓰고 있다면 VS Code 자체를 재시작해야 할 수도 있습니다.

### "Git 계정 만들었어요" — Git에는 계정이 없습니다

**원인** — Git과 GitHub를 같은 것으로 알고 있는 경우입니다.
Git은 그냥 내 컴퓨터에 깔리는 프로그램이라 **로그인이라는 개념 자체가 없습니다.** 계정은 GitHub의 것입니다.

**해결** — 이렇게 구분하세요.

- "커밋했어요" → Git이 한 일 (내 컴퓨터 안)
- "올렸어요 / 링크 공유했어요" → GitHub가 한 일 (인터넷)

### 백업 = 버전 관리 라고 생각하기

**원인** — 둘 다 "복사본을 둔다"는 점이 닮아서 헷갈립니다.

| | 백업 | 버전 관리 |
|---|---|---|
| 목적 | **소실 방지** | **변경 추적** |
| 남는 것 | 최신 사본(보통 1~며칠 치) | **모든 시점 + 이유** |
| 되돌리기 | 통째로 | 파일 하나, 한 줄 단위까지 |

**해결** — 서로 대체하지 않습니다. 둘 다 필요합니다. 다만 코드에는 버전 관리가 **먼저**입니다.

### 압축파일로 버전 관리하기

```
project_20260801.zip
project_20260805.zip
project_20260810_최종.zip
```

**원인** — Step 2의 폴더 복사와 같은 방식이고, 같은 한계를 그대로 갖습니다.
**해결** — 압축파일 안은 **검색도 비교도 안 됩니다.** 커밋 하나면 되는 일입니다.

### Git을 배우면 코드를 잃어버릴까 봐 겁내기

**원인** — `reset`, `rebase` 같은 무서운 이름의 명령들 때문입니다.
**해결** — 한 번이라도 **커밋한 것은 거의 잃어버릴 수 없습니다.** 실수로 지운 것처럼 보여도 [23강 reflog](lesson-23.md)로 대부분 되살립니다.

> 진짜 위험한 것은 **커밋을 안 한 변경**입니다. 그래서 초급의 핵심 습관은 딱 하나입니다.
> **작게, 자주 커밋하기.**

## ⑥ 확인 문제

**1.** 다음 중 **Git**이 하는 일과 **GitHub**가 하는 일을 나누어 보세요.

```
ⓐ 변경 이력을 기록한다
ⓑ 코드 리뷰(Pull Request)를 주고받는다
ⓒ 인터넷 없이도 어제 상태로 되돌린다
ⓓ 저장소를 웹사이트로 공개한다
ⓔ 브랜치를 만들어 다른 방식을 시험한다
```

<details>
<summary>답 보기</summary>

| Git | GitHub |
|---|---|
| ⓐ, ⓒ, ⓔ | ⓑ, ⓓ |

**판별 기준** — **인터넷이 끊겨도 되는 일이면 Git, 인터넷이 필요하면 GitHub**입니다.

ⓔ는 헷갈리기 쉽습니다. 브랜치는 GitHub 화면에서도 만들 수 있지만 **기능 자체는 Git의 것**입니다. GitHub는 그 기능을 웹에서 대신 눌러 주는 것뿐입니다.
</details>

**2.** 커밋을 100번 했습니다. 프로젝트 폴더를 100번 복사해 둔 것과 비교하면 용량은 어떨까요? 그 이유는 무엇인가요?

<details>
<summary>답 보기</summary>

**Git 쪽이 훨씬 작습니다.**

폴더 100번 복사는 안 바뀐 파일까지 100벌이 그대로 생깁니다. 반면 Git은 스냅샷을 찍되 **바뀌지 않은 파일은 새로 저장하지 않고 이전 것을 가리키기만** 합니다.

```
커밋 1: a.py(저장) b.py(저장) c.py(저장)
커밋 2: a.py(→커밋1 것) b.py(저장) c.py(→커밋1 것)   ← b.py만 실제로 늘어남
```

**주의할 점** — 이 절약은 **텍스트 파일**에서 잘 통합니다. 이미지·동영상·`.zip` 같은 **바이너리 파일은 조금만 바뀌어도 통째로 새로 저장**되므로 저장소가 급격히 무거워집니다. 그래서 그런 파일은 보통 Git에 넣지 않거나([05강 .gitignore](lesson-05.md)) LFS를 씁니다([28강](lesson-28.md)).
</details>

**3.** 팀원이 이렇게 말합니다. **"우리는 매일 밤 서버에 프로젝트 폴더를 백업하니까 Git은 필요 없어요."** 어떤 점을 반박할 수 있을까요? 세 가지 이상 들어 보세요.

<details>
<summary>답 보기</summary>

1. **하루 단위밖에 못 돌아갑니다.** 오전 10시에 망가뜨렸으면 어젯밤 상태로 돌아가야 하고, 그날 한 일은 전부 날아갑니다.
2. **무엇이 왜 바뀌었는지 남지 않습니다.** 백업본에는 결과만 있고 이유가 없습니다. "이 코드 왜 이렇게 됐지?"에 답할 수 없습니다.
3. **동시 작업이 안 됩니다.** 두 명이 같은 파일을 고치면 나중에 저장한 사람이 앞사람 작업을 덮어씁니다. Git은 이런 상황을 **충돌**로 알려 주고 합칠 기회를 줍니다([11강](lesson-11.md)).
4. **부분 되돌리기가 안 됩니다.** "A 기능은 살리고 B 기능만 취소" 는 백업으로 불가능합니다.
5. **시험해 보기가 어렵습니다.** 위험한 시도를 하려면 폴더를 또 복사해야 합니다. Git은 브랜치 하나로 끝납니다.

**정리** — 백업은 *"컴퓨터가 고장 났을 때"* 를 대비하고, 버전 관리는 *"내가 실수했을 때 · 왜 그런지 알아야 할 때"* 를 대비합니다. 목적이 다르므로 **둘 다** 하는 것이 맞습니다.
</details>

## 오늘의 정리

| 개념 | 핵심 |
|---|---|
| 버전 관리 | 변경 이력을 **언제·누가·무엇을·왜** 로 기록하고 되돌릴 수 있게 하는 것 |
| 분산형 | 내 컴퓨터에 **저장소 전체 사본**이 있음 → 오프라인 작업 · 빠름 · 복구 쉬움 |
| 스냅샷 | 커밋 = 그 시점 프로젝트의 **사진 한 장 + 메모**. 안 바뀐 파일은 가리키기만 함 |
| Git | 내 컴퓨터에 설치하는 **프로그램** (계정 없음) |
| GitHub | Git 저장소를 올려 두고 협업하는 **웹 서비스** (계정 있음) |
| 백업 ≠ 버전 관리 | 백업은 소실 방지, 버전 관리는 변경 추적. 목적이 다름 |

**오늘 반드시 기억할 한 가지**
> Git은 프로그램, GitHub는 웹사이트입니다. 그리고 **커밋한 것은 웬만해선 잃어버리지 않습니다.**
> 그러니 겁내지 말고 **작게, 자주** 커밋하세요.

**과제**
1. 앞으로 Git으로 관리하고 싶은 내 프로젝트(또는 폴더) 하나를 정해 두세요. 03강부터 실제로 씁니다.
2. GitHub 계정이 없다면 <https://github.com> 에서 만들어 두세요. **09강부터 필요합니다.**
   - 아이디는 앞으로 포트폴리오 주소가 됩니다(`github.com/내아이디`). 신중하게 정하세요.
   - 회사·학교 이메일보다 **개인 이메일**을 권합니다. 졸업·퇴사해도 계정이 남습니다.
