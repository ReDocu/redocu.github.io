## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 이미지 크기가 왜 **돈과 시간**의 문제인지 말하고, `docker history` 로 어느 층이 무거운지 진단할 수 있다.
- **slim 베이스 · CPU 휠 · --no-cache-dir · 멀티스테이지**의 4단 최적화를 적용할 수 있다.
- MP3 API를 이미지로 만들고, **크기를 절반 이하로** 줄인 근거를 층 단위로 제시할 수 있다.
- `:latest` 태그의 함정을 알고, 버전 태그를 붙일 수 있다.

## ② 왜 필요한가

오늘 드디어 MP3가 이미지가 됩니다. 그런데 순진하게 만들면 **3.46GB**가 나옵니다.
"디스크 싼데 뭐 어때요?" — 이미지는 디스크에 가만히 있는 물건이 아니라 **끊임없이 이동하는
물건**이라서 문제입니다:

| 이미지가 이동하는 순간 | 3.46GB면 | 1.6GB면 |
|---|---|---|
| CI가 빌드 후 레지스트리로 push (W26 — **병합마다**) | ~5분 | ~2분 |
| 서버가 pull 받아 배포 (배포마다) | ~4분 | <2분 |
| 장애 시 새 서버에 긴급 배포 | 그 4분이 장애 시간 | 절반 |
| 레지스트리 보관 (버전 × 수십 개) | 요금 2배 | — |

배포가 하루 수십 번인 팀에서 이미지 1GB는 곧 **분 단위의 비용**입니다. 그리고 크기는 보안
문제이기도 합니다 — 이미지 안의 모든 패키지가 잠재적 취약점 목록이라, 안 쓰는 것이 없을수록
공격면이 좁아집니다.

좋은 소식: 오늘 줄일 3.46GB의 대부분은 "몰라서 실려 간 짐"입니다. 층별로 짐 검사를 하고,
필요한 것만 남기는 4단계를 밟습니다 — 마지막 단계가 끝나면 같은 API, 같은 예측(0.7214!),
절반 이하의 몸무게가 됩니다.

## ③ 개념 설명

### 어디가 무거운가 — 진단 먼저

```bash
docker history 이미지:태그
```

층마다 크기가 나옵니다 — 최적화는 **큰 층부터**입니다. MP3 이미지의 예상 짐 목록:

| 짐 | 크기 급 | 처방 |
|---|---|---|
| 베이스 이미지의 여분 (컴파일러·문서·도구) | ~900MB | **slim** 베이스 |
| pip 다운로드 캐시 | ~400MB | **--no-cache-dir** |
| torch를 CUDA판으로 받은 경우 | +5GB ⚠️ | **CPU 휠** ([Day 113](day-113.md)의 그 URL) |
| 빌드에만 필요했던 것들 | 수백 MB | **멀티스테이지** |
| 모델 파일 (45MB) | 45MB | 정당한 짐 — 싣고 갑니다 (BERT 420MB라면? → 내일) |

### slim — 뺄 것을 미리 빼 둔 베이스

| 베이스 | 크기 | 들어 있는 것 |
|---|---|---|
| `python:3.12` | 1.02GB | 파이썬 + 컴파일러 + 각종 개발 도구 (풀옵션) |
| `python:3.12-slim` | **125MB** | 파이썬 + 최소한의 OS |
| `python:3.12-alpine` | 52MB | 더 작지만 **다른 계열 OS** — 파이썬 생태계와 마찰(⑤) |

기본 선택은 slim입니다 — 900MB를 그냥 벌고, 우리가 쓰는 휠(wheel) 패키지들은 컴파일러가
필요 없어 잃는 것도 없습니다.

### 멀티스테이지 — 짓는 곳과 사는 곳의 분리

pip install 과정은 임시 파일·메타데이터·빌드 부산물을 남깁니다. 그리고 레이어의 성질상
**"나중에 지워도" 앞 층에 이미 실린 것은 그대로**입니다 (RUN rm은 위에 "가림막 층"을 얹을 뿐).
그래서 아예 **공사장과 입주 공간을 분리**합니다:

```dockerfile
FROM python:3.12-slim AS builder     # ← 공사장: 여기서 설치
RUN pip install --prefix=/install ...

FROM python:3.12-slim                # ← 새집: 깨끗한 베이스에서 다시 시작
COPY --from=builder /install /usr/local   # 완성품만 이사
```

공사장 스테이지는 최종 이미지에 **포함되지 않습니다** — 결과물만 `COPY --from` 으로 가져오므로,
설치 과정의 모든 부산물이 자동으로 버려집니다.

### 태그 — :latest는 버전이 아니다

`hello-api:0.1` 처럼 태그는 이미지의 이름표인데, 태그를 생략하면 `:latest` 가 됩니다.
문제는 latest가 "최신"을 뜻하는 게 아니라 **"태그 없이 push된 아무거나"**라는 것 — 오늘의
latest와 어제의 latest는 다른 이미지일 수 있고, 그러면 "지난주 버전으로 롤백"이 불가능합니다.
규칙: **배포용 이미지에는 반드시 불변 태그**(버전 `v0.3.1` 또는 커밋 `sha-a1b2c3d`)를 함께
붙입니다. 자동화된 태그 전략은 [Day 128](day-128.md)에서 CI에 넣습니다.

## ④ 단계별 실습

무대는 서버(WSL)의 `/opt/mlops-mp3` — deploy 계정으로, 브랜치 `feature/dockerize` 를 따고
시작합니다 (이번 주 작업도 전부 PR로 — W22가 습관이 됐는지 시험대입니다).

### Step 1. v1 — 일단 돌아가는 이미지 (1~2교시)

어제의 표준 순서 그대로, 베이스만 풀옵션으로:

```dockerfile
# Dockerfile.v1 — 최적화 전 (교육용 비교 기준)
FROM python:3.12

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt --index-url https://download.pytorch.org/whl/cpu --extra-index-url https://pypi.org/simple

COPY . .

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

.dockerignore부터 챙기고 (어제 ⑤의 시크릿 사고 예방 — `.env` 필수!) 빌드:

```bash
printf ".venv/\n.git/\n__pycache__/\n.env\nmlruns/\n*.log\n" > .dockerignore
docker build -f Dockerfile.v1 -t mlops-mp3:v1 .
docker images mlops-mp3
```

```
$ docker images mlops-mp3
REPOSITORY   TAG   IMAGE ID       CREATED          SIZE
mlops-mp3    v1    7c2f91d0a3b4   40 seconds ago   3.46GB
```

동작 검증 — 크기를 줄이는 내내 이 대조가 우리의 안전망입니다:

```bash
docker run -d --name mp3-v1 -p 8001:8000 mlops-mp3:v1
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8001/predict
```

```
$ curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8001/predict
{"label":"ants","confidence":0.7214,"model_version":"resnet18-antbee-v1","elapsed_ms":31.4}
```

**0.7214** — [Day 100](../04-deep-learning-serving/day-100.md)에서 학습 기록과 대조했던 바로
그 확신도가 컨테이너 안에서도 나옵니다. 환경이 통째로 포장됐다는 가장 강한 증거입니다.

### Step 2. 진단 — 누가 무거운가 (3교시)

```bash
docker history mlops-mp3:v1 --format "{{.Size}}\t{{.CreatedBy}}" | head -5
```


큰 순서대로 — pip 층 1.92GB, 베이스 1.02GB. 처방도 그 순서로 갑니다.

### Step 3. v2 — slim + --no-cache-dir (4교시)

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt --index-url https://download.pytorch.org/whl/cpu --extra-index-url https://pypi.org/simple

COPY . .

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```
$ docker images mlops-mp3
REPOSITORY   TAG   IMAGE ID       CREATED          SIZE
mlops-mp3    v2    e91b3c8d20f7   30 seconds ago   2.14GB
mlops-mp3    v1    7c2f91d0a3b4   12 minutes ago   3.46GB
```

베이스 교체(-900MB)와 pip 캐시 차단(-400MB급)으로 **-1.32GB.** curl 대조 — 여전히 0.7214.

### Step 4. v3 — 멀티스테이지 (5~6교시)

최종본 `Dockerfile`:

```dockerfile
# ── 1단계: 공사장 — 의존성 설치 ──────────────────────────
FROM python:3.12-slim AS builder

COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt \
    --index-url https://download.pytorch.org/whl/cpu \
    --extra-index-url https://pypi.org/simple

# ── 2단계: 새집 — 완성품만 이사 ──────────────────────────
FROM python:3.12-slim

WORKDIR /app

COPY --from=builder /install /usr/local
COPY . .

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker build -t mlops-mp3:v3 .
docker images mlops-mp3
```

```
$ docker images mlops-mp3
REPOSITORY   TAG   IMAGE ID       CREATED          SIZE
mlops-mp3    v3    4f8a2e91c6d0   25 seconds ago   1.61GB
mlops-mp3    v2    e91b3c8d20f7   14 minutes ago   2.14GB
mlops-mp3    v1    7c2f91d0a3b4   26 minutes ago   3.46GB
```

**3.46GB → 1.61GB (46%)** — 목표(절반 이하) 달성. 남은 1.6GB의 대부분은 torch CPU 스택
(정당한 짐 — 이게 없으면 추론이 없습니다)과 모델입니다. 마지막 검증:

```bash
docker run -d --name mp3 -p 8000:8000 mlops-mp3:v3
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8000/predict
```

```
$ curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8000/predict
{"label":"ants","confidence":0.7214,"model_version":"resnet18-antbee-v1","elapsed_ms":30.8}
```

같은 API, 같은 0.7214, 절반의 몸무게. 참고로 systemd의 mp3-api(8000)가 아직 돌고 있다면 포트가
충돌합니다 — `sudo systemctl stop mp3-api && sudo systemctl disable mp3-api` 로 은퇴시키세요.
**오늘부터 MP3의 공식 실행 형태는 컨테이너입니다** (W23의 유닛은 "컨테이너 이전 시대"의 유물로
RUNBOOK에 기록).

### Step 5. 버전 태그와 PR (7~8교시)

```bash
docker tag mlops-mp3:v3 mlops-mp3:0.1.0
docker rmi mlops-mp3:v1 mlops-mp3:v2        # 비교용 폐기 (v3=0.1.0 유지)
```

Dockerfile·.dockerignore를 PR로 올립니다 — PR 본문의 "확인 방법"에 빌드 명령과 0.7214 대조를
명시 (리뷰어가 그대로 재현). **과제 — 최적화 전후 비교.** ① v1→v2→v3 크기 표와 각 단계에서
무엇이 왜 줄었는지 `docker history` 발췌로 증명. ② 만약 CPU 휠 지정을 빠뜨렸다면 크기가
어떻게 됐을지 실측 또는 계산으로 추정. ③ 생각 문제: 내일을 위한 질문 — 컨테이너를 지우면
그 안의 예측 로그도 사라집니다. 로그·모델처럼 "컨테이너보다 오래 살아야 하는 것"의 목록을
MP3에서 뽑아 보세요.

## ⑤ 자주 하는 실수

### GPU 없는 서버에 CUDA판 torch

**증상** — 이미지가 8GB급으로 폭발, pull에 10분 — 서버엔 GPU도 없는데.
**원인** — 리눅스에서 `pip install torch` 기본값은 CUDA 포함 빌드입니다 ([Day 113](day-113.md)에서
서버 venv에 겪은 그 일의 이미지판 — 컨테이너도 리눅스입니다).
**해결** — CPU 전용 인덱스 명시 (`--index-url .../whl/cpu`). 역으로 GPU 서버에 배포하는 이미지라면
CUDA판이 정답이니, "실행 하드웨어에 맞는 휠"이 규칙입니다.

### RUN rm으로 지웠는데 크기가 안 줄어듦

**증상** — `RUN pip install ...` 다음 줄에 `RUN rm -rf /root/.cache` — docker images 크기 그대로.
**원인** — 레이어는 불변입니다. 뒤 층의 삭제는 가림막일 뿐, 앞 층의 짐은 이미지에 실려 있습니다.
**해결** — 같은 층에서 안 만들거나(`--no-cache-dir`), 같은 RUN 안에서 만들고 지우거나
(`RUN 설치 && rm ...`), 멀티스테이지로 공사장째 버리거나 — 삭제는 **층이 닫히기 전에만**
유효합니다.

### alpine으로 갔다가 미궁에 빠짐

**증상** — 크기 욕심에 `python:3.12-alpine` 선택 → 일부 패키지가 휠이 없어 소스 컴파일 시작 →
빌드 10분+, `gcc not found`, 알 수 없는 런타임 차이.
**원인** — alpine은 musl 계열이라 표준 리눅스(glibc)용 휠이 안 맞는 경우가 있습니다 — 특히
과학 스택(numpy·torch)에서.
**해결** — 파이썬 + ML 스택은 **slim이 기본값**입니다. alpine은 정적 바이너리·초소형 도구
이미지의 영역으로 남겨 두세요. 52MB와 125MB의 차이는 torch 1.4GB 앞에서 의미가 없습니다.

### .dockerignore에 models/까지 넣음

**증상** — 이미지는 날씬해졌는데 컨테이너가 기동 직후 사망:
```
FileNotFoundError: [Errno 2] No such file or directory: 'models/antbee_resnet18.pt'
```
**원인** — 다이어트 의욕이 정당한 짐까지 버림 — COPY . . 에서 모델이 빠졌습니다.
**해결** — 오늘 설계에서 모델(45MB)은 **이미지의 일부**입니다 (이미지 = 코드+환경+모델이라
태그 하나로 전체 재현 가능 — 이 결정의 대안(볼륨·레지스트리)은 내일과 W27에서 비교합니다).
.dockerignore는 "빌드에 불필요한 것" 목록이지 "큰 것" 목록이 아닙니다.

### 배포를 :latest로만

**증상** — "어제 버전으로 롤백해 주세요" — 어제의 latest가 뭐였는지 아무도 모름.
**원인** — latest는 가변 이름표라 시점 특정이 불가능합니다.
**해결** — 빌드마다 불변 태그(버전·커밋 sha)를 함께: `docker tag mlops-mp3:0.1.0 ...`.
"응답의 model_version"([Day 096](../04-deep-learning-serving/day-096.md))이 모델의 족보이듯,
이미지 태그는 **배포물의 족보**입니다 — W26에서 CI가 자동으로 붙이게 만듭니다.

## ⑥ 확인 문제

**Q1.** 이미지 크기가 "저장 비용"보다 "시간 비용" 문제인 이유를, W26 이후의 파이프라인
(병합→빌드→push→pull→배포)을 근거로 설명하세요.

<details>
<summary>답 보기</summary>

이미지는 병합마다 빌드되어 레지스트리로 push되고, 배포마다 서버로 pull됩니다 — 크기가 모든
이동 구간의 소요 시간에 곱해집니다. 특히 장애 복구·긴급 배포에서 pull 시간은 곧 서비스 중단
시간이고, CI 실행 시간은 개발 리드타임입니다. 저장은 한 번이지만 이동은 반복되므로, GB는
디스크가 아니라 **분(分)의 단위**로 청구됩니다.

</details>

**Q2.** 멀티스테이지가 없던 시절의 꼼수 `RUN pip install ... && rm -rf /root/.cache/pip` 이
효과가 있는 이유와, `RUN pip install ...` 뒤 **별도의** `RUN rm -rf /root/.cache/pip` 이
효과가 없는 이유를 레이어 원리로 설명하세요.

<details>
<summary>답 보기</summary>

레이어는 RUN 하나가 끝날 때 불변으로 봉인됩니다. 같은 RUN 안에서 설치와 삭제를 하면 캐시가
**층에 기록되기 전에** 사라져 층이 애초에 가볍습니다. 별도 RUN이면 첫 층에 캐시가 이미 봉인된
뒤이고, 둘째 층의 rm은 "위에서 가리기"일 뿐 아래 층의 바이트는 그대로 이미지에 실립니다.
멀티스테이지는 이 문제를 구조로 풉니다 — 공사장 층 전체를 최종 이미지에서 제외.

</details>

**Q3.** v3 이미지(모델 포함 1.61GB)에서 모델이 BERT(420MB)로 바뀌고 매주 재학습으로 갱신된다면,
"모델을 이미지에 굽는" 오늘의 설계를 유지해야 할까요? 장단점을 대고 대안을 제시하세요.

<details>
<summary>답 보기</summary>

오늘 설계의 장점은 "태그 하나 = 코드+환경+모델의 완전한 족보"라 재현·롤백이 원자적이라는 것.
단점은 모델만 바뀌어도 GB급 이미지를 재빌드·재배포해야 한다는 것 — 매주 갱신이면 낭비가
누적됩니다. 대안: 모델을 이미지 밖(볼륨 마운트, 내일)에 두거나 모델 레지스트리([Day 132](day-132.md))에서
기동 시 특정 버전을 받아오게 하고, **응답의 model_version으로 족보를 보존**합니다. 갱신 주기가
코드와 같으면 굽고, 다르면 분리 — "변경 주기가 다른 것은 분리한다"는 캐시 순서 원칙의 배포판입니다.

</details>
