## ② 왜 필요한가

MP3 발표([Day 105](../04-deep-learning-serving/day-105.md))에서 여러분은 "동작하는 API"를
보여 줬습니다. 오늘 보여 줄 것은 종류가 다릅니다 — **동작을 유지하는 시스템**입니다.
그 차이는 데모의 형식에서 그대로 드러납니다:

```
MP3 발표: 요청을 보낸다 → 응답이 온다               (기능의 증명)
MP4 발표: 커밋을 민다 → 관문들을 통과한다 → 서비스가 바뀐다 → 죽여도 살아난다 → 되돌린다
                                                     (신뢰의 증명)
```

청중(그리고 미래의 면접관)이 이 발표에서 확인하려는 것은 화면의 결과가 아니라 **과정의
기계성**입니다 — 사람의 손재주가 아니라 시스템이 일하고 있다는 것. 그래서 오늘의 시연은
역설적으로 "여러분이 아무것도 특별히 하지 않는 것"을 보여 주는 자리입니다. 준비는 어제까지
끝났습니다 — 오늘은 리허설한 것을 리허설한 대로.

## ④ 단계별 실습

### Step 1. 최종 점검과 발표 준비 (1~2교시)

- README·보고서(docs/report.md — MP4판: 갭 감사에서 출발해 무엇을 수리·증명했나) 최종 정리
- 발표 리허설 1회 (짝 앞에서, 시간 재며) — 라이브 구간은 **진짜로** 한 번 더 (오늘의 사이클
  기록이 백업 2층을 최신화합니다)
- 시연 전 점검 절차 실행 → 결과를 발표 자료 마지막 장 뒤에 숨겨 두기 (질문 대비)

### Step 2. 발표회 (3~6교시)

1인(팀) 5분 + 질의 3분. 듣는 사람의 역할도 채점 대상입니다 — 발표마다 질문 또는 [q] 하나,
그리고 **"이 시스템에 지금 PR을 보낸다면 무엇이 걱정되나"** 관점의 피드백 하나.

발표 순서의 관례 하나 — 라이브 시연의 병합 버튼은 **누르기 전에 청중에게 예고**하세요
("지금부터 2분, 사람 손은 여기까지입니다"). 그 선언이 이 발표의 주제문입니다.

### Step 3. 회고 (7교시)

KPT — 단, 이번엔 최종 프로젝트(4인 팀·4주)를 수신인으로:

```
## 계속할 것 (Keep)    예: 대조값 한 파일 규율 — v2 교체가 PR 하나로 끝났다
## 바꿀 것 (Change)   예: 시크릿 점검을 첫날로 당긴 것은 옳았다 — 최종엔 주간 루틴으로
## 시도할 것 (Try)     예: 팀 저장소를 이 파이프라인의 템플릿에서 시작 · 무중단 배포 실험
```

팀 단위 공유 — 특히 Try는 다음 주 팀 빌딩에서 "우리 팀의 기술 자산 목록"이 됩니다.

### Step 4. 단원 완료 조건 점검과 제출 (8교시)

넷 다 **증거와 함께** 체크합니다:

- [ ] 새 서버에서 clone → `docker compose up` 으로 서비스가 뜬다 — 짝 PC 실측 기록 ([137](day-137.md))
- [ ] PR에 테스트가 강제되고 main 병합이 자동 배포로 이어진다 — 오늘 라이브가 증거
- [ ] 시크릿이 저장소·이미지 어디에도 없다 — 점검표 결과 첨부 ([136](day-136.md))
- [ ] 모델 교체·롤백 절차가 문서와 함께 동작한다 — 실측 4m07s·롤백 3층 표 ([139](day-139.md))

제출: 저장소 URL + 릴리스 태그 **v1.0.0** ([Day 128](day-128.md) 과제의 그 릴리스 절차로 —
태그 push가 마지막 커밋입니다).

## ⑤ 자주 하는 실수

### 라이브 대기 2분을 침묵으로

**증상** — 병합 후 "음… 빌드 중입니다…" — 청중의 주의가 흩어지고, 발표자는 진행 바만 응시.
**원인** — 대기를 공백으로 설계 (준비는 시연만, 해설은 미준비).
**해결** — 그 2분이 **발표의 본론**입니다 — 관문 지도를 띄우고 "지금 lint가, 지금 러너가"를
중계하세요. 시스템이 일하는 동안 사람이 설명한다 — 이 그림 자체가 MP4의 주제 재현입니다.

### 실측 없는 형용사

**증상** — "빠르게 배포되고요, 금방 복구됩니다" — 질문: "몇 초인데요?" — 침묵.
**원인** — 숫자를 재 놓고도 형용사로 발표 (또는 재지 않음).
**해결** — 이 단원 발표의 언어는 실측입니다: 1m52s·38.7s·4m07s·2m17s. 숫자는 기억 못 해도
됩니다 — 표를 띄우면 됩니다. "쟀다"는 사실이 "안다"의 증거입니다.

### 완료 조건을 발표 후에 몰아서 점검

**증상** — 발표는 성공 — 제출 직전 점검에서 시크릿 히스토리 발견, v1.0.0 태그가 옛 커밋에.
**원인** — 발표를 종점으로 착각 (제출물은 저장소이고, 심사는 발표 후에도 저장소를 봅니다).
**해결** — Step 4가 발표 **후**에 배치된 이유 — 증거 링크까지 채우는 것이 진짜 종점입니다.
[Day 105](../04-deep-learning-serving/day-105.md) ⑤의 "발표 끝나자 저장소 방치"와 같은 병의
예방이기도 합니다 — 이 저장소는 다음 주에도 삽니다 (포트폴리오 4번이자 최종 프로젝트의 템플릿).

### 회고가 감상문이 됨

**증상** — "힘들었지만 많이 배웠습니다" — 다음 주 팀 빌딩에서 재사용 불가.
**원인** — 수신인 없는 회고.
**해결** — KPT의 수신인을 "다음 주의 우리 팀"으로 고정하세요 — 모든 항목이 "그래서 팀
저장소 첫 주에 무엇을 한다"로 번역 가능해야 합니다. 오늘의 Try 목록이 Day 141의 준비물입니다.

## ⑥ 확인 문제

**Q1.** "기능의 증명"과 "신뢰의 증명"의 차이를, MP3와 MP4의 시연 각각에서 **실패가 났을 때
벌어지는 일**로 대비해 설명하세요.

<details>
<summary>답 보기</summary>

MP3 시연의 실패(응답 에러)는 그 기능의 실패로 끝나고, 복구는 발표자의 손(재시작·재시도)에
달려 있습니다. MP4 시연에서는 실패조차 시스템의 일부입니다 — 게이트가 막으면 "관문이 일한다"
의 증명이 되고, 스모크가 잡아 롤백하면 "자가 복구"의 증명이 됩니다 (실제로 129 Step 5의
기록이 발표의 증거 자산이죠). 신뢰의 증명이란 성공 경로가 아니라 **실패 경로의 설계**를
보여 주는 것 — 그래서 MP4 발표에는 롤백 시연·장애 매트릭스가 들어가고, 그것이 두 발표의
본질적 차이입니다.

</details>

**Q2.** 예상 질문 표의 "배포 중 요청은 안 끊기나?"에 대한 답이 "순단 있음 — 다음 단계"인
것은 감점 요인일까요? 정직한 한계 선언의 전략적 가치를 논하세요.

<details>
<summary>답 보기</summary>

감점이 아니라 득점 요인입니다 — 조건이 붙습니다: ① 한계를 **알고 있고**(순단이 몇 초인지
실측), ② 왜 지금은 감수하는지 근거가 있고(트래픽 규모·재시작 배포의 단순성), ③ 넘어갈 신호와
방법을 안다(다중 인스턴스+프록시, K8s의 롤링 — 개념은 이미 학습). 이 3종 세트를 갖춘 한계
선언은 "모든 걸 다 했다"는 주장보다 신뢰를 삽니다 — 심사자는 완벽한 시스템이 아니라 **자기
시스템을 정확히 아는 사람**을 찾기 때문입니다. 모르는 한계(질문받고 처음 생각)만이 감점입니다.

</details>

서버의 표류. ③ 시크릿 부재: 커밋·이미지를 통한 자격 증명 유출 — 저장소 공개·이미지 공유의
순간이 사고의 순간이 되는 위험. ④ 모델 교체·롤백 문서: 파일명 지옥·되돌릴 수 없는 교체 —
"지금 운영 모델이 무엇인지 아무도 모르는" 상태. 넷의 공통 구조: 사람의 기억·선의에 걸려
있던 것을 시스템과 문서로 옮긴 것 — 이 단원의 제목이 "인프라와 MLOps"인 이유입니다.
