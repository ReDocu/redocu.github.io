## ① 학습 목표

이 강을 마치면 이렇게 할 수 있습니다.

- Well-Architected 6개 기둥으로 **자기 아키텍처의 위험을 스스로** 찾을 수 있다.
- 리뷰 결과를 **위험 목록(HRI)** 으로 정리하고 개선 우선순위를 정할 수 있다.
- 월간 비용을 **구성 요소별로 산정**하고 실제 사용과 대조할 수 있다.
- 비용 최적화 7수단으로 **30% 절감안**을 근거와 함께 제시할 수 있다.
- Compute Optimizer·Trusted Advisor로 **낭비를 자동 탐지**할 수 있다.

## ② 왜 필요한가

30강까지 서비스를 만들고, 관측하고, 장애를 견뎠습니다. 마지막 질문이 남았습니다.

> **"이 아키텍처, 정말 잘 만든 건가요?"**

"동작한다"와 "잘 만들었다"는 다릅니다. 동작하는 아키텍처에도 숨은 위험이 있습니다 — 단일 장애점, 과대 권한, 비용 낭비, 검증 안 된 복구. 이것을 **체계적으로** 찾는 도구가 AWS Well-Architected Framework입니다.

```
 [자기 점검 없이 발표]
  "잘 만들었습니다" → 심사위원 "이건 어떻게 되나요?" → 몰랐던 구멍 노출

 [WA 리뷰 후 발표]
  "위험 5개를 찾았고 2개를 고쳤으며 나머지는 이렇게 관리합니다" → 신뢰
```

그리고 이 과정 내내 강조한 **비용** — 오늘 최종 정산합니다. M1에서 산정한 예상 비용, 4주간 실제 사용액, 그리고 30% 절감안. "월 $125짜리를 $80으로 줄이는 방법과 그 대가"를 근거와 함께 말할 수 있어야 합니다.

WA 리뷰의 결과물은 점수가 아니라 **위험 목록과 개선 계획**입니다. 완벽한 아키텍처를 증명하는 게 아니라 **위험을 알고 관리한다는 것을 증명**하는 것 — 이것이 실무 아키텍트의 성숙도입니다. M4 발표(32강)의 핵심 재료가 됩니다.

## ③ 워크숍 가이드 — WA 6기둥과 비용 최적화

### Well-Architected 6개 기둥

| 기둥 | 질문 | 이 과정에서 |
|---|---|---|
| **운영 우수성** | 운영·모니터링·개선이 되나 | [22·29강](../03-serverless-automation/lesson-22.md) 관측성, 런북 |
| **보안** | 데이터·접근이 보호되나 | [03·04·25강](lesson-25.md) IAM·암호화·WAF |
| **안정성** | 장애·부하에 견디나 | [10·15·30강](lesson-30.md) HA·게임데이 |
| **성능 효율성** | 자원을 효율적으로 쓰나 | [17·21·29강](lesson-29.md) 저장소 선택·부하 |
| **비용 최적화** | 낭비 없이 쓰나 | 오늘 정산 |
| **지속 가능성** | 자원 사용을 최소화하나 | Graviton·오토스케일링·서버리스 |

### 리뷰는 점수가 아니라 위험 목록

```
 WA 리뷰의 산출물:
   ❌ "우리는 85점입니다"          (의미 없음)
   ✅ HRI(High Risk Issues) 목록:
      - [높음] 단일 NAT — AZ 장애 시 앱 격리
      - [높음] 배포 역할 과대 권한
      - [중간] 캐시 없어 부하 시 DB 포화
      + 각 위험의 개선 계획
```

> 🔑 **위험이 없는 아키텍처는 없습니다.** 위험을 **모르는 것**이 진짜 위험입니다. 리뷰는 위험을 드러내고 우선순위를 매기는 과정입니다.

### 기둥별 자기 점검 질문 (샘플)

**보안**
- 저장 데이터가 암호화됐나? 가장 민감한 데이터의 보호 경로는?
- IAM 역할에 과대 권한(AdministratorAccess·`Resource:*`)이 없나?
- 시크릿이 코드·이미지·템플릿 어디에도 평문이 아닌가?

**안정성**
- 단일 장애점은? (30강 게임데이에서 드러난 것)
- RPO/RTO를 실제 복구로 검증했나?
- AZ 하나가 죽어도 지속되나?

**비용 최적화**
- 유휴·과대 리소스는? (야간 축소 대상)
- 구매 옵션을 최적화했나? (온디맨드 vs SP)
- 데이터 전송 경로가 효율적인가? (NAT vs 엔드포인트)

### 비용 최적화 7수단 ⭐

| # | 수단 | 이 프로젝트 적용 |
|---|---|---|
| 1 | **적정 크기 조정** | 부하 테스트로 t3.micro 충분 확인 |
| 2 | **구매 옵션** | 상시 부분 Savings Plans, 배치는 스팟 |
| 3 | **스토리지 계층화** | S3 수명 주기(IA/Glacier), gp2→gp3 |
| 4 | **유휴 제거** | 야간 자동 축소(30강) |
| 5 | **전송 경로** | NAT → VPC 엔드포인트, CloudFront |
| 6 | **관리형 전환** | 서버 운영비 절감(Fargate) |
| 7 | **일정 기반 축소** | 비운영 시간 ECS 0/RDS 중지 |

> 💡 **순서가 중요** — 먼저 "안 쓰는 것 끄기"(4·7)와 "과대 사양 줄이기"(1), 그다음 "구매 옵션"(2), 마지막이 "아키텍처 변경"(5). 쉬운 것부터.

### 자동 탐지 도구

| 도구 | 찾아 주는 것 | 비용 |
|---|---|---|
| **Compute Optimizer** | 과대·과소 프로비저닝 인스턴스 | 무료 |
| **Trusted Advisor** | 유휴 리소스·보안·한도 | 일부 무료 |
| **Cost Explorer** | 서비스·태그별 비용 추이 | UI 무료 |
| Cost Anomaly Detection | 이상 급증 | 무료 |

## ④ 스프린트 작업 — WA 리뷰와 비용 정산

> 💰 **예상 비용 $0.5 ~ 1.0/팀·주** — 리뷰·분석은 무료, 서비스 상시분만.

### Step 1. Well-Architected Tool 리뷰 (아키텍트, 30분)

```bash
# 워크로드 등록 (또는 콘솔에서)
$ aws wellarchitected create-workload \
    --workload-name course-final-team-N \
    --description "이벤트 신청 서비스" \
    --environment PRODUCTION \
    --lenses wellarchitected \
    --review-owner "팀N" \
    --query 'WorkloadId' --output text
```

콘솔의 Well-Architected Tool에서 **6개 기둥 질문에 응답**합니다. 각 질문에 "예/아니오/해당 없음"과 메모. 솔직하게 — 안 한 것을 했다고 하면 리뷰의 의미가 없습니다.

### Step 2. 위험 항목(HRI) 도출 (팀, 25분)

리뷰에서 나온 위험을 우선순위로 정리합니다.

| # | 위험 | 기둥 | 심각도 | 개선 |
|---|---|---|---|---|
| 1 | 단일 NAT | 안정성 | 높음 | 엔드포인트로 대체(비용도↓) |
| 2 | 배포 역할 과대 권한 | 보안 | 높음 | Access Analyzer로 좁힘 |
| 3 | 캐시 없어 DB 포화 위험 | 성능 | 중간 | 부하 커지면 ElastiCache |
| 4 | 단일 리전 | 안정성 | 낮음 | 백업&복구로 관리(비용상 수용) |
| 5 | ... | | | |

**상위 5개 중 최소 2개를 실제로 개선**하고, 나머지는 "왜 지금 안 고치는지"(비용·시간 trade-off)를 기록합니다.

### Step 3. 개선 2건 실제 적용 (팀, 30분)

예: 위험 1(단일 NAT) → VPC 엔드포인트로 이미 바꿨다면 문서화, 위험 2(과대 권한) → Access Analyzer로 좁힘.

```bash
# Access Analyzer로 배포 역할의 실제 사용 액션 확인 → 정책 좁히기 (04강)
$ aws accessanalyzer list-findings ...
# Compute Optimizer 권장 확인
$ aws compute-optimizer get-ecs-service-recommendations 2>/dev/null || \
  echo "Compute Optimizer 콘솔에서 확인"
```

### Step 4. 월간 비용 산정 ⭐ (운영/보안, 30분)

**24시간 상시 운영 기준**으로 구성 요소별 산정(16강 방식).

| 구성 요소 | 사양 | 월 비용 |
|---|---|---|
| ALB | 1 | $16.4 |
| Fargate | 0.25vCPU·0.5GB × 2 | $18 |
| RDS Multi-AZ | db.t3.micro | $38 |
| NAT or 엔드포인트 | | $42 or $28 |
| KMS·Secrets·WAF | | $6.4 |
| Route 53·S3·CloudFront | | ~$1 |
| **합계** | | **약 $110~125** |

**실제 사용액과 대조** — Cost Explorer로 팀 4주 실비.

```bash
$ aws ce get-cost-and-usage \
    --time-period Start=2026-08-01,End=2026-08-31 \
    --granularity MONTHLY --metrics UnblendedCost \
    --group-by Type=DIMENSION,Key=SERVICE \
    --filter '{"Tags":{"Key":"Project","Values":["aws-course"]}}' \
    --query 'ResultsByTime[0].Groups[*].[Keys[0],Metrics.UnblendedCost.Amount]' --output table
```

> 실제 사용액이 산정보다 낮으면(야간 축소 덕) 그 차이를 절감 실적으로 제시.

### Step 5. 30% 절감안 (팀, 25분)

큰 항목부터 절감안을 근거·trade-off와 함께.

| # | 방안 | 절감 | Trade-off | 권장 |
|---|---|---|---|---|
| 1 | NAT → 엔드포인트 | $14 | 외부 API 불가 | ⭐ |
| 2 | Fargate Graviton(ARM) | $4 | ARM 이미지 | ⭐ |
| 3 | Savings Plans 1년 | $7 | 약정 | ⭐ |
| 4 | 야간 자동 축소(적용됨) | $25 | 비운영만 | ⭐ |
| 5 | RDS 단일 AZ | $19 | 🔴 가용성 포기 | ❌ 운영 부적합 |

**1+2+3+4로 30% 초과 달성**하면서 가용성을 해치지 않습니다. 5번(요구사항 훼손)은 안 함.

### Step 6. Trusted Advisor·Compute Optimizer 반영 (운영/보안, 15분)

콘솔에서 권장 사항 확인 → 반영 가능한 것 적용, 나머지는 위험 목록에 기록.

### 💰 이번 강 비용

| 리소스 | 프리 티어 | 이번 강 |
|---|---|---|
| WA Tool·Compute Optimizer·Trusted Advisor(기본) | ✅ 무료 | $0 |
| Cost Explorer UI | ✅ | $0 |
| 서비스 상시분 | ❌ | $0.5~1.0 |
| **합계** | | **약 $0.7** |

### 🧹 리소스 정리 체크리스트

```bash
# 리뷰·분석은 리소스 안 남김. 서비스는 32강 발표까지 유지 or 재배포
# 32강 시연을 위해 app 스택은 발표 직전 재배포 계획
```

- [ ] WA 리뷰 응답 저장(위험 목록)

## ⑤ 자주 하는 실수

### WA 리뷰를 점수 매기기로 오해한다

**증상** — "우리 몇 점이에요?"에 매달립니다.
**해결** — WA는 점수가 아니라 **위험 목록과 개선 계획**을 만드는 것. "위험 5개를 찾았고 관리한다"가 목표입니다.

### 리뷰에서 자기 아키텍처를 방어만 한다

**증상** — 모든 질문에 "잘하고 있음"으로 답합니다.
**문제** — 위험을 안 찾으면 리뷰가 무의미. 솔직하게 "아니오"를 인정한 곳이 개선 기회입니다.
**해결** — 30강 게임데이에서 드러난 것, M1 리뷰 지적을 위험 목록에 반영합니다.

### 비용 절감으로 요구사항을 깬다

**증상** — 30% 달성하려고 RDS를 단일 AZ로, ALB를 제거.
**문제** — 이것은 절감이 아니라 **범위 축소**이며 M1 요구(가용성)를 위반합니다.
**해결** — 요구를 지키는 절감(엔드포인트·Graviton·SP·야간 축소)으로. 요구를 바꿔야 한다면 **의사결정자 승인**을 받고 명시([16강](../02-compute-data/lesson-16.md)).

### 산정과 실비가 크게 다른데 설명 못 한다

**원인** — 태그를 안 붙여 비용이 안 나뉘거나, 산정에서 빠뜨린 항목(데이터 전송 등).
**해결** — 모든 리소스에 `Project` 태그([02강](../01-cloud-foundation/lesson-02.md)). 차이가 나면 Cost Explorer에서 서비스별로 분해해 원인 특정.

### 절감안에 trade-off를 안 쓴다

**증상** — "이렇게 하면 싸집니다"만 있고 대가가 없습니다.
**해결** — 모든 절감에는 대가가 있습니다. 엔드포인트→외부 API 불가, Graviton→ARM 이미지, SP→약정. trade-off를 함께 써야 판단이 됩니다.

## ⑥ 마일스톤 점검 (M4 진행 중)

오늘은 M4(32강 완료)의 절반 — WA 리뷰·비용입니다.

**오늘 완료 확인**

- [ ] WA Tool 6기둥 리뷰 응답
- [ ] 위험 5개 도출 + 2개 이상 개선
- [ ] 월간 비용 산정 + 실비 대조
- [ ] 30% 절감안(근거·trade-off)
- [ ] Compute Optimizer·Trusted Advisor 확인

**스스로 점검하는 질문 3개**

<details>
<summary>1. 우리 아키텍처의 가장 높은 위험 2개는 무엇이고, 왜 그것이 높은가요?</summary>

팀마다 다르지만 답이 있어야 합니다. 흔한 것: 단일 NAT(AZ 장애 시 앱 격리 — 안정성), 배포 역할 과대 권한(저장소 접근자가 곧 관리자 — 보안). "높음"의 근거는 **발생 시 영향**입니다. 30강 게임데이에서 실제로 문제가 된 것, M1 리뷰에서 지적된 것이 대개 여기 옵니다. 못 고친 위험은 "왜 지금 안 고치나"(비용·시간)를 설명할 수 있어야 합니다.
</details>

<details>
<summary>2. 30% 절감을 요구사항을 깨지 않고 달성했나요?</summary>

달성했어야 합니다. 큰 항목(NAT·RDS·ALB)부터 보되, **가용성을 해치는 절감(단일 AZ·ALB 제거)은 제외**하고 엔드포인트·Graviton·Savings Plans·야간 축소로 채웁니다. "요구를 지키면서 30%"가 핵심 — 요구를 버린 절감은 절감이 아니라 다른 서비스를 만든 것입니다.
</details>

<details>
<summary>3. 비용 산정과 실제 사용액이 왜 다른가요?</summary>

대개 **야간 축소로 실비가 낮거나**, 산정에서 데이터 전송·요청 비용을 빠뜨렸거나, 태그 누락으로 일부가 안 잡힌 것입니다. 차이를 설명할 수 있어야 합니다 — "산정은 24시간 상시 $125, 실비는 야간 축소로 $70, 차이 $55는 절감 실적." 설명 못 하면 태그·산정을 재점검합니다.
</details>

| 리뷰 산출물 | 점수 아님 — **위험 목록(HRI) + 개선 계획** |
| 위험 관리 | 위험이 없는 게 아니라 **아는 것**이 중요 |
| 비용 7수단 | 유휴 제거·적정 크기 먼저, 아키텍처 변경 나중 |
| 절감 | 항상 **trade-off**와 함께, 요구는 안 깸 |
| 자동 탐지 | Compute Optimizer·Trusted Advisor·Cost Explorer |

**한 장 요약**

```
  WA 6기둥 리뷰 → 위험 목록(HRI) → 상위 2개 개선 + 나머지 관리 계획
  비용: 산정(상시 $125) ↔ 실비 대조 → 30% 절감안(엔드포인트·Graviton·SP·축소)
                                        └ 요구 안 깨고, trade-off 명시
                                        ▼
                                  M4 발표 재료(32강)
```

**오늘 반드시 기억할 한 가지**
> **잘 만든 아키텍처는 위험이 없는 게 아니라 위험을 알고 관리하는 것입니다.**
> 그리고 절감은 요구를 지키면서, 대가를 밝히면서 합니다.

**과제 (팀)**
1. WA 자체 검토서 — 6기둥 응답 + 위험 5개 + 개선 2건 반영 기록.
2. 월간 비용 산정서 + Cost Explorer 실비 대조 + 차이 설명.
3. 30% 절감안 — 각 방안의 절감액·trade-off·권장 여부.
4. Compute Optimizer/Trusted Advisor 권장 사항 확인 결과.
5. (개인) "지금 안 고치기로 한 위험 하나"와 그 이유(언제 고칠지)를 3줄.
