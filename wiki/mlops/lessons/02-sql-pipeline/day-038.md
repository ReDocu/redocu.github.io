## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- `CREATE TABLE` · `ALTER TABLE` 로 테이블을 만들고 고칠 수 있다.
- `NOT NULL` · `UNIQUE` · `PK` · `FK` · `CHECK` · `DEFAULT` 를 목적에 맞게 붙일 수 있다.
- 인덱스가 왜 빠른지, 그 대가가 무엇인지 설명하고 **어떤 열에 걸지 판단**할 수 있다.
- `EXPLAIN ANALYZE` 를 읽고 `Seq Scan` 과 `Index Scan` 을 구분할 수 있다.

## ② 왜 필요한가

지금까지 우리는 **남이 만들어 준 테이블을 읽기만** 했습니다.
[Day 043](day-043.md)부터는 여러분이 만든 테이블에 **파이프라인이 매일 데이터를 밀어 넣습니다.**
그때 두 가지 문제가 기다립니다.

### 문제 ① — 쓰레기가 들어옵니다

수집기가 이런 데이터를 보냈다고 합시다.

| 문제 데이터 | 파일 저장이었다면 | DB 제약이 있다면 |
|---|---|---|
| 가격이 `-5000` | 그냥 저장됨 → 매출이 음수 | **`INSERT` 거부** |
| 같은 주문이 두 번 | 중복 행 → 매출 2배 | **`UNIQUE` 위반으로 거부** |
| 없는 고객 번호로 주문 | 조인하면 사라짐 | **`FK` 위반으로 거부** |
| 필수 항목이 비어 있음 | NULL 채로 저장 | **`NOT NULL` 위반으로 거부** |

[Day 023](../01-python-data/day-023.md)에서 이런 걸 파이썬 코드로 잡았습니다.
**하지만 코드는 우회할 수 있습니다.** 누군가 다른 스크립트로, 혹은 psql로 직접 넣으면 그만입니다.

> **제약조건은 "마지막 방어선"입니다.**
> 애플리케이션 코드가 몇 개든, 개발자가 몇 명이든, **DB를 통과하지 않고는 데이터가 들어갈 수 없습니다.**
> 그래서 실무에서는 "코드에서 막았으니 DB 제약은 없어도 된다"고 하지 않습니다. **양쪽 다 겁니다.**

### 문제 ② — 느려집니다

[Day 031](day-031.md)에서 파일의 첫 번째 한계로 "조건 하나 걸려면 전부 읽어야 한다"를 꼽았습니다.
**DB도 인덱스가 없으면 똑같이 전부 읽습니다.**

```
event_log 100만 행에서 user_id = 42 를 찾기
  인덱스 없음  →  100만 행 전부 확인  →  62 ms
  인덱스 있음  →  색인으로 바로 점프  →  0.2 ms      약 270배
```

오늘 이 차이를 **직접 측정**합니다.

## ③ 개념 설명

### DDL — 구조를 다루는 명령

| 명령 | 하는 일 | 되돌릴 수 있나 |
|---|---|---|
| `CREATE TABLE` | 테이블 생성 | `DROP` 으로 |
| `ALTER TABLE` | 열·제약 추가/변경/삭제 | 반대 `ALTER` 로 |
| `DROP TABLE` | 테이블 삭제 (**구조까지**) | ❌ |
| `TRUNCATE` | 모든 행 삭제 (**구조는 유지**) | ❌ (`DELETE` 보다 훨씬 빠름) |

> **PostgreSQL의 DDL은 트랜잭션 안에서 되돌릴 수 있습니다.**
> `BEGIN; ALTER TABLE ...; ROLLBACK;` 이 동작합니다 ([Day 039](day-039.md)).
> MySQL은 안 됩니다. **운영 DB에서 DDL을 칠 때는 반드시 `BEGIN` 부터 시작하세요.**

### 타입 고르기 — MLOps 관점

| 용도 | 권장 타입 | 이유 |
|---|---|---|
| 식별자 | `integer` / `bigint` | 20억 넘을 것 같으면 `bigint` |
| **금액** | `numeric(12,2)` 또는 `integer`(원 단위) | **`float` 절대 금지** — 오차가 누적됨 |
| 측정값·확률 | `real` / `double precision` | 오차가 허용되는 값 |
| 짧은 문자열 | `text` | PostgreSQL에서 `varchar(n)` 대비 성능 차이 없음 |
| 날짜 | `date` | 시각이 필요 없을 때 |
| **시각** | `timestamptz` | **`timestamp`(시간대 없음) 대신** ★ |
| 참/거짓 | `boolean` | `'Y'`/`'N'` 문자열 금지 |
| 반정형 | `jsonb` | API 원본 보관 등 ([Day 043](day-043.md)) |

> **`timestamptz` 를 쓰는 이유** — 서버가 UTC, 사용자가 KST면 `timestamp` 는 9시간이 조용히 어긋납니다.
> 배치가 "어제 자정부터"를 잘못 계산해 **하루치 데이터를 통째로 빠뜨립니다** ([Day 043](day-043.md)).
> 실습 `shop` 은 학습용이라 `date` 를 썼지만, **실무 파이프라인은 무조건 `timestamptz`** 입니다.

### 제약조건 6종

| 제약 | 막는 것 | 예 |
|---|---|---|
| `NOT NULL` | 값 없음 | `name text NOT NULL` |
| `DEFAULT` | (막지 않고) 기본값 채움 | `stock integer NOT NULL DEFAULT 0` |
| `UNIQUE` | 중복 | `email text UNIQUE` |
| `PRIMARY KEY` | 중복 + NULL (= `UNIQUE` + `NOT NULL`) | `id integer PRIMARY KEY` |
| `FOREIGN KEY` | 없는 대상 참조 | `REFERENCES customers(customer_id)` |
| `CHECK` | 규칙 위반 | `CHECK (price >= 0)` |

**`FOREIGN KEY` 의 삭제 정책**이 실무에서 자주 문제가 됩니다.

| 옵션 | 부모를 지우면 |
|---|---|
| (기본) `NO ACTION` / `RESTRICT` | **에러** — 자식이 있으면 못 지움 |
| `ON DELETE CASCADE` | 자식도 **함께 삭제** ⚠️ |
| `ON DELETE SET NULL` | 자식의 FK 열을 NULL로 |

> **`CASCADE` 는 신중하게.** 고객 한 명을 지웠는데 주문 5,000건이 같이 사라질 수 있습니다.
> 실무에서는 대개 **삭제 대신 `deleted_at` 열로 표시**(소프트 삭제)합니다.

### 인덱스 — 책 뒤의 색인

```
색인 없는 책에서 "트랜잭션"을 찾기   →  1페이지부터 끝까지 넘김     (Seq Scan)
색인이 있는 책                       →  색인에서 "트랜잭션 → 271p"  (Index Scan)
```

PostgreSQL의 기본 인덱스는 **B-tree** 입니다. 값을 정렬해 트리로 저장하므로

| 잘하는 것 | 못 하는 것 |
|---|---|
| `=` · `<` · `>` · `BETWEEN` · `IN` | `LIKE '%중간%'` (앞이 `%`) |
| `ORDER BY` (정렬 생략 가능) | 열에 함수를 씌운 조건 |
| `앞%` 형태의 `LIKE` | 타입이 다른 비교 |

### 인덱스의 대가 ★

**인덱스는 공짜가 아닙니다.**

| 비용 | 설명 |
|---|---|
| **쓰기가 느려진다** | `INSERT`/`UPDATE`/`DELETE` 마다 인덱스도 갱신 |
| **용량을 먹는다** | 테이블의 10~30% 추가 |
| **관리 대상이 는다** | 안 쓰는 인덱스도 계속 갱신 비용을 냄 |

**[Day 042](day-042.md)의 대량 적재에서 이것이 결정적입니다.**
100만 행을 넣을 때 인덱스 5개가 걸려 있으면 몇 배 느려집니다.
그래서 실무에서는 **인덱스를 지우고 → 적재하고 → 다시 만듭니다.**

### 어떤 열에 인덱스를 걸까

| 걸어야 하는 열 | 이유 |
|---|---|
| **외래키 열** | 조인에 매번 쓰임. PostgreSQL은 FK에 인덱스를 **자동 생성하지 않음** ★ |
| `WHERE` 에 자주 오는 열 | 조회 조건 |
| `ORDER BY` 에 자주 오는 열 | 정렬 생략 |
| 날짜 열 (기간 조회) | 범위 검색 |

| 걸면 안 되는 열 | 이유 |
|---|---|
| 값 종류가 적은 열 (`status`, `gender`) | 어차피 절반을 읽어야 함 |
| 자주 바뀌는 열 | 갱신 비용 |
| 작은 테이블 | 전체 읽기가 더 빠름 |

### 복합 인덱스와 선두 열 규칙

```sql
CREATE INDEX idx ON orders (customer_id, ordered_at);
```

| 쿼리 | 인덱스 사용 |
|---|---|
| `WHERE customer_id = 1` | ✅ |
| `WHERE customer_id = 1 AND ordered_at >= '...'` | ✅ (가장 좋음) |
| `WHERE ordered_at >= '...'` | ❌ **선두 열이 없으면 못 씀** |

**전화번호부와 같습니다.** `(성, 이름)` 순으로 정렬된 명부에서 "이름이 민수인 사람"은 못 찾습니다.
**자주 쓰는 조건을 앞에** 두세요.

### `EXPLAIN` 읽는 법

| 명령 | 하는 일 |
|---|---|
| `EXPLAIN 쿼리` | **실행 계획만** 보여줌 (실행 안 함) |
| `EXPLAIN ANALYZE 쿼리` | **실제로 실행**하고 걸린 시간까지 ⚠️ |

> **`EXPLAIN ANALYZE` 는 쿼리를 진짜 실행합니다.** `UPDATE`/`DELETE` 에 쓰면 데이터가 바뀝니다.
> 확인만 하고 싶다면 `BEGIN; EXPLAIN ANALYZE DELETE ...; ROLLBACK;`

읽어야 할 것은 네 가지입니다.

| 항목 | 의미 | 나쁜 신호 |
|---|---|---|
| **스캔 종류** | `Seq Scan` (전체) / `Index Scan` / `Bitmap Heap Scan` | 큰 테이블에 `Seq Scan` |
| `rows=N` (cost 안) | 옵티마이저의 **예상** 행 수 | `actual` 과 크게 다르면 통계가 낡음 → `ANALYZE` |
| `actual time` | **실제** 걸린 시간 (ms) | — |
| `Rows Removed by Filter` | 읽었다가 버린 행 수 | 이 값이 크면 인덱스가 필요 |

### 뷰(VIEW)

자주 쓰는 쿼리에 **영구적인 이름**을 붙입니다. CTE의 저장 버전입니다.

```sql
CREATE VIEW v_order_summary AS SELECT ...;
SELECT * FROM v_order_summary WHERE ...;      -- 테이블처럼 씀
```

| | 저장되는 것 | 조회 시 |
|---|---|---|
| **일반 뷰** | **쿼리문만** | 매번 다시 계산 |
| **머티리얼라이즈드 뷰** | **결과 데이터** | 즉시 (단, `REFRESH` 필요) |

### Step 1. 제약조건이 실제로 막는지 확인하기

`shop` 테이블에는 이미 제약이 걸려 있습니다. 하나씩 어겨 봅니다.

**① `UNIQUE` — 같은 이메일로 가입**

```
shop=# INSERT INTO customers (name, email, city, grade, phone, joined_at)
shop-# VALUES ('테스트', 'minsu@example.com', '서울', 'gold', NULL, '2025-01-01');
ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(minsu@example.com) already exists.
```

**② `FOREIGN KEY` — 없는 고객이 주문**

```
shop=# INSERT INTO orders (customer_id, ordered_at, status) VALUES (999, '2025-07-01', 'paid');
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".
```

**③ `NOT NULL` — 이름 없는 상품**

```
shop=# INSERT INTO products (name, category, price) VALUES (NULL, '전자기기', 1000);
ERROR:  null value in column "name" of relation "products" violates not-null constraint
DETAIL:  Failing row contains (13, null, 전자기기, 1000, 0).
```

**④ `CHECK` — 음수 가격**

```
shop=# INSERT INTO products (name, category, price) VALUES ('불량상품', '전자기기', -1000);
ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (14, 불량상품, 전자기기, -1000, 0).
```

**⑤ 타입 — 숫자 열에 문자열**

```
shop=# INSERT INTO products (name, category, price) VALUES ('테스트', '전자기기', '이만원');
ERROR:  invalid input syntax for type integer: "이만원"
LINE 1: ...ucts (name, category, price) VALUES ('테스트', '전자기기', '이만...
                                                                        ^
```

**⑥ `FOREIGN KEY` — 주문이 있는 고객 삭제**

```
shop=# DELETE FROM customers WHERE customer_id = 1;
ERROR:  update or delete on table "customers" violates foreign key constraint "orders_customer_id_fkey" on table "orders"
DETAIL:  Key (customer_id)=(1) is still referenced from table "orders".
```

**여섯 번 모두 데이터가 들어가지 못했습니다.** 이것이 제약조건의 값어치입니다.

> **`DETAIL: Failing row contains (13, ...)` 의 13** — 실패했는데도 `product_id` 가 소비됐습니다.
> 식별자 시퀀스는 **롤백돼도 되돌아가지 않습니다**(성능 때문에). 그래서 실패가 쌓이면 번호에 구멍이 생깁니다.
> **정상 동작입니다.** id에 빈 번호가 있다고 데이터가 사라진 게 아닙니다.

### Step 2. `ALTER TABLE` — 제약 추가하기

`orders.status` 에는 아무 문자열이나 들어갈 수 있습니다. 값을 4개로 제한합니다.

```
shop=# ALTER TABLE orders ADD CONSTRAINT orders_status_check
shop-#     CHECK (status IN ('paid', 'shipped', 'delivered', 'cancelled'));
ALTER TABLE
```

> **기존 30행이 전부 이 조건을 만족하기 때문에** 성공했습니다.
> 하나라도 어기는 행이 있으면 `ALTER TABLE` 자체가 실패합니다. **제약을 추가하기 전에 데이터부터 정리**해야 합니다.

이제 오타가 막힙니다.

```
shop=# UPDATE orders SET status = 'deliverd' WHERE order_id = 1;
ERROR:  new row for relation "orders" violates check constraint "orders_status_check"
DETAIL:  Failing row contains (1, 1, 2025-01-05, deliverd).
```

열도 추가해 봅니다.

```
shop=# ALTER TABLE orders ADD COLUMN channel text NOT NULL DEFAULT 'web';
ALTER TABLE

shop=# SELECT order_id, status, channel FROM orders LIMIT 3;
 order_id |  status   | channel
----------+-----------+---------
        1 | delivered | web
        2 | delivered | web
        3 | delivered | web
(3 rows)
```

기존 30행에 전부 `'web'` 이 채워졌습니다. **`DEFAULT` 없이 `NOT NULL` 열을 추가하면 실패**합니다.

```
shop=# ALTER TABLE orders ADD COLUMN memo text NOT NULL;
ERROR:  column "memo" of relation "orders" contains null values
```

실습을 되돌립니다.

```
shop=# ALTER TABLE orders DROP COLUMN channel;
ALTER TABLE
```

### Step 3. 대용량 테이블 만들기 — 인덱스 실험 준비

100만 행짜리 이벤트 로그를 만듭니다. **10~30초 걸립니다.**

```
shop=# CREATE TABLE event_log (
shop(#     event_id   bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
shop(#     user_id    integer     NOT NULL,
shop(#     event_type text        NOT NULL,
shop(#     event_at   timestamptz NOT NULL,
shop(#     value      integer     NOT NULL
shop(# );
CREATE TABLE

shop=# INSERT INTO event_log (user_id, event_type, event_at, value)
shop-# SELECT (random() * 9999)::int + 1,
shop-#        (ARRAY['view','click','purchase','logout'])[(random() * 3)::int + 1],
shop-#        TIMESTAMPTZ '2025-01-01 00:00:00+09' + (random() * 365 * 86400)::int * INTERVAL '1 second',
shop-#        (random() * 1000)::int
shop-# FROM generate_series(1, 1000000);
INSERT 0 1000000
```

> `generate_series(1, 1000000)` 은 1부터 100만까지의 숫자를 만들어 냅니다.
> 테스트 데이터를 만들 때 가장 많이 쓰는 함수입니다. **값은 난수라 여러분의 결과와 제 결과가 다릅니다.**
> 오늘 중요한 것은 **절대 숫자가 아니라 인덱스 전후의 배수**입니다.

크기를 확인합니다.

```
shop=# SELECT pg_size_pretty(pg_total_relation_size('event_log')) AS 총크기,
shop-#        pg_size_pretty(pg_relation_size('event_log'))       AS 테이블,
shop-#        pg_size_pretty(pg_indexes_size('event_log'))        AS 인덱스;
 총크기 | 테이블 | 인덱스
--------+--------+---------
 78 MB  | 57 MB  | 21 MB
(1 row)
```

인덱스가 벌써 21MB입니다. **기본키 인덱스**가 자동으로 만들어졌기 때문입니다.

### Step 4. `EXPLAIN ANALYZE` — 인덱스 없이 조회 ★

```
shop=# EXPLAIN ANALYZE SELECT * FROM event_log WHERE user_id = 42;
                                                     QUERY PLAN
--------------------------------------------------------------------------------------------------------------------
 Gather  (cost=1000.00..15541.33 rows=98 width=24) (actual time=0.398..62.114 rows=104 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on event_log  (cost=0.00..14531.53 rows=41 width=24) (actual time=0.271..54.882 rows=35 loops=3)
         Filter: (user_id = 42)
         Rows Removed by Filter: 333299
 Planning Time: 0.089 ms
 Execution Time: 62.201 ms
(8 rows)
```

읽는 법입니다.

| 줄 | 의미 |
|---|---|
| `Parallel Seq Scan` | **테이블 전체를 읽었다** (병렬로 3개 프로세스가 나눠서) |
| `Rows Removed by Filter: 333299` | 읽고 나서 **33만 행을 버렸다** — 프로세스당. 합치면 100만 |
| `rows=104` (actual) | 실제로 필요했던 건 **104행** |
| `Execution Time: 62.201 ms` | 62밀리초 |

**104행을 얻으려고 100만 행을 읽었습니다.** 인덱스가 필요하다는 명확한 신호입니다.

> **실행 시간은 컴퓨터마다 다릅니다.** 제 환경에서 62ms가 여러분 환경에서는 30ms일 수도 200ms일 수도 있습니다.
> 봐야 할 것은 **`Seq Scan` 이라는 단어**와 **`Rows Removed by Filter` 가 크다**는 사실입니다.

### Step 5. 인덱스 만들고 다시 측정

```
shop=# CREATE INDEX idx_event_log_user ON event_log (user_id);
CREATE INDEX

shop=# EXPLAIN ANALYZE SELECT * FROM event_log WHERE user_id = 42;
                                                            QUERY PLAN
----------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on event_log  (cost=5.15..385.62 rows=98 width=24) (actual time=0.062..0.184 rows=104 loops=1)
   Recheck Cond: (user_id = 42)
   Heap Blocks: exact=103
   ->  Bitmap Index Scan on idx_event_log_user  (cost=0.00..5.13 rows=98 width=0) (actual time=0.042..0.043 rows=104 loops=1)
         Index Cond: (user_id = 42)
 Planning Time: 0.214 ms
 Execution Time: 0.231 ms
(7 rows)
```

| 변화 | 전 | 후 |
|---|---|---|
| 스캔 | `Parallel Seq Scan` | **`Bitmap Index Scan`** |
| 버린 행 | 100만 | **0** |
| 실행 시간 | 62.201 ms | **0.231 ms** (약 270배) |

**`Rows Removed by Filter` 가 사라진 것**이 핵심입니다. 필요한 104행만 정확히 읽었습니다.

기간 조회에도 인덱스를 겁니다.

```
shop=# CREATE INDEX idx_event_log_at ON event_log (event_at);
CREATE INDEX

shop=# EXPLAIN ANALYZE
shop-# SELECT COUNT(*) FROM event_log
shop-# WHERE event_at >= '2025-06-01' AND event_at < '2025-06-02';
```

이 쿼리는 하루치(약 2,700행)만 읽으므로 인덱스를 씁니다.
반면 **한 달치**(약 8만 행, 전체의 8%)를 조회하면 PostgreSQL이 **일부러 `Seq Scan` 을 고를 수도** 있습니다.
"흩어진 8만 행을 인덱스로 하나씩 찾아가느니 통째로 읽는 게 빠르다"고 판단하는 것입니다.

> **인덱스가 있는데 안 쓴다고 옵티마이저가 틀린 게 아닙니다.**
> 대개는 그쪽이 정말 빠릅니다. 의심되면 `EXPLAIN ANALYZE` 로 양쪽을 재 보세요.

### Step 6. 인덱스가 안 먹는 경우 ★

**① 열에 함수를 씌운 조건**

```
shop=# EXPLAIN SELECT * FROM event_log WHERE DATE(event_at) = '2025-06-01';
                                     QUERY PLAN
-------------------------------------------------------------------------------------
 Gather  (cost=1000.00..16583.33 rows=5000 width=24)
   Workers Planned: 2
   ->  Parallel Seq Scan on event_log  (cost=0.00..15083.33 rows=2083 width=24)
         Filter: (date(event_at) = '2025-06-01'::date)
(4 rows)
```

**`Seq Scan` 입니다.** 인덱스는 `event_at` 원본값으로 정렬돼 있는데, 조건은 `DATE(event_at)` 을 묻고 있습니다.
인덱스에 그 값은 없습니다.

**해결 ① 조건을 범위로 바꾼다 (권장)**

```sql
WHERE event_at >= '2025-06-01' AND event_at < '2025-06-02'
```

**해결 ② 표현식 인덱스를 만든다**

```sql
CREATE INDEX idx_event_log_date ON event_log (DATE(event_at));
```

**"열을 가공하지 말고 값을 가공하라"** — 인덱스를 살리는 제1 원칙입니다.

**② 앞이 `%` 인 `LIKE`**

```sql
WHERE event_type LIKE '%chase'   -- ❌ 인덱스 못 씀
WHERE event_type LIKE 'pur%'     -- ✅ 씀
```

앞부분을 모르면 정렬된 색인에서 출발점을 찾을 수 없습니다.
(전문 검색이 필요하면 `pg_trgm` 확장이나 GIN 인덱스를 씁니다.)

**③ 타입이 다른 비교** — [Day 034](day-034.md)에서 본 `integer = text` 문제입니다.
캐스팅으로 억지로 붙이면 인덱스를 못 씁니다.

### Step 7. 인덱스의 대가 측정하기

**쓰기가 얼마나 느려지는지** 직접 재 봅니다.

```
shop=# \timing on
Timing is on.

shop=# INSERT INTO event_log (user_id, event_type, event_at, value)
shop-# SELECT 1, 'view', now(), 1 FROM generate_series(1, 100000);
INSERT 0 100000
Time: 613.284 ms
```

인덱스를 지우고 같은 일을 합니다.

```
shop=# DROP INDEX idx_event_log_user, idx_event_log_at;
DROP INDEX

shop=# INSERT INTO event_log (user_id, event_type, event_at, value)
shop-# SELECT 1, 'view', now(), 1 FROM generate_series(1, 100000);
INSERT 0 100000
Time: 271.905 ms
```

**인덱스 2개 때문에 삽입이 2배 이상 느려졌습니다.**
이것이 [Day 042](day-042.md)에서 "대량 적재 전에 인덱스를 지운다"고 하는 이유입니다.

```
shop=# CREATE INDEX idx_event_log_user ON event_log (user_id);
CREATE INDEX
Time: 892.117 ms

shop=# \timing off
Timing is off.
```

> **`\timing on`** 은 psql이 모든 쿼리의 소요 시간을 표시하게 합니다. 성능 실험할 때 항상 켜세요.

### Step 8. 복합 인덱스와 선두 열

```
shop=# CREATE INDEX idx_event_log_user_at ON event_log (user_id, event_at);
CREATE INDEX

shop=# EXPLAIN SELECT * FROM event_log WHERE user_id = 42 AND event_at >= '2025-06-01';
                                            QUERY PLAN
---------------------------------------------------------------------------------------------------
 Index Scan using idx_event_log_user_at on event_log  (cost=0.42..8.45 rows=1 width=24)
   Index Cond: ((user_id = 42) AND (event_at >= '2025-06-01 00:00:00+09'::timestamp with time zone))
(2 rows)
```

**두 조건이 모두 `Index Cond` 에 들어갔습니다.** 가장 효율적인 형태입니다.

선두 열 없이 두 번째 열만으로 조회하면 어떻게 될까요?

```
shop=# EXPLAIN SELECT * FROM event_log WHERE event_at >= '2025-12-25';
                                       QUERY PLAN
-----------------------------------------------------------------------------------------
 Gather  (cost=1000.00..16193.10 rows=7215 width=24)
   Workers Planned: 2
   ->  Parallel Seq Scan on event_log  (cost=0.00..14471.60 rows=3006 width=24)
         Filter: (event_at >= '2025-12-25 00:00:00+09'::timestamp with time zone)
(4 rows)
```

**`(user_id, event_at)` 인덱스가 있는데도 `Seq Scan` 입니다.**
전화번호부가 `(성, 이름)` 순인데 "이름이 민수인 사람"을 찾는 것과 같습니다.

> **교훈** — 복합 인덱스는 **선두 열부터** 써야 합니다.
> `event_at` 단독 조회가 잦다면 `event_at` 인덱스를 **따로** 만들어야 합니다.

### Step 9. 작은 테이블에는 인덱스가 무용지물

`shop` 의 `orders` 에 인덱스를 걸고 확인해 봅니다.

```
shop=# CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE INDEX

shop=# EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 1;
                                            QUERY PLAN
--------------------------------------------------------------------------------------------------
 Seq Scan on orders  (cost=0.00..1.38 rows=5 width=25) (actual time=0.012..0.016 rows=5 loops=1)
   Filter: (customer_id = 1)
   Rows Removed by Filter: 25
 Planning Time: 0.093 ms
 Execution Time: 0.031 ms
(5 rows)
```

**인덱스를 만들었는데도 `Seq Scan` 입니다.** 그리고 그게 맞습니다.

```
orders 30행 = 디스크 1블록(8KB)
  Seq Scan       →  1블록 읽기
  Index Scan     →  인덱스 블록 + 테이블 블록 = 2블록 이상  ← 오히려 손해
```

> **"인덱스를 걸었는데 안 빨라져요"** 의 가장 흔한 원인이 이것입니다.
> 인덱스는 **큰 테이블에서 작은 결과를 뽑을 때**만 이깁니다.
> 그래도 `orders(customer_id)` 인덱스는 남겨 두세요. 데이터가 쌓이면 결국 필요해집니다.

`shop` 에 필요한 나머지 인덱스를 만듭니다. **외래키 열은 자동 인덱스가 없습니다.**

## ⑤ 자주 하는 실수

### `relation "xxx" already exists`

```
shop=# CREATE TABLE products (...);
ERROR:  relation "products" already exists
```

**해결** — `CREATE TABLE IF NOT EXISTS` 를 쓰거나, 재실행 가능한 스크립트라면 `DROP TABLE IF EXISTS` 를 앞에 둡니다
([Day 031](day-031.md)의 `shop_sample.sql` 패턴).

### `cannot drop table ... because other objects depend on it`

```
shop=# DROP TABLE customers;
ERROR:  cannot drop table customers because other objects depend on it
DETAIL:  constraint orders_customer_id_fkey on table orders depends on table customers
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

**원인** — 자식 테이블이 참조 중입니다.
**해결** — **자식부터 지웁니다.** `DROP ... CASCADE` 는 편하지만 **뭐가 같이 지워질지 모르는** 위험한 명령입니다.
운영 DB에서는 쓰지 마세요.

### `column ... contains null values`

```
shop=# ALTER TABLE orders ADD COLUMN memo text NOT NULL;
ERROR:  column "memo" of relation "orders" contains null values
```

**원인** — 기존 행에 채울 값이 없습니다.
**해결** — `DEFAULT` 를 함께 주거나, 3단계로 나눕니다.

```sql
ALTER TABLE orders ADD COLUMN memo text;          -- ① NULL 허용으로 추가
UPDATE orders SET memo = '';                      -- ② 값 채우기
ALTER TABLE orders ALTER COLUMN memo SET NOT NULL;-- ③ 제약 추가
```

**운영 중인 테이블에 열을 추가할 때의 표준 절차**입니다.

### `check constraint ... is violated by some row`

```
shop=# ALTER TABLE products ADD CONSTRAINT products_stock_check CHECK (stock > 0);
ERROR:  check constraint "products_stock_check" of relation "products" is violated by some row
```

**원인** — 이미 위반하는 행이 있습니다. (블루투스이어폰의 `stock = 0`)
**해결** — 어떤 행인지 먼저 찾고, 데이터를 고치거나 제약을 완화합니다.

```sql
SELECT * FROM products WHERE NOT (stock > 0);   -- 위반 행 확인
```

**제약을 추가하기 전에 항상 이 확인 쿼리를 먼저 돌리세요.**

### 인덱스를 만들었는데 안 빨라집니다

**원인 후보를 순서대로 확인합니다.**

| # | 확인 | 방법 |
|---|---|---|
| 1 | 테이블이 작다 | 몇천 행 이하면 `Seq Scan` 이 맞습니다 |
| 2 | 조건에 함수가 씌워져 있다 | `WHERE DATE(t) = ...` → 범위 조건으로 |
| 3 | 결과가 전체의 큰 비율 | 30% 넘으면 옵티마이저가 `Seq Scan` 을 고름 |
| 4 | 복합 인덱스의 선두 열이 없다 | 인덱스를 따로 만들거나 순서 변경 |
| 5 | 통계가 낡았다 | `ANALYZE 테이블명;` |

```sql
ANALYZE event_log;      -- 통계 갱신. 대량 적재 후에는 필수 (Day 042)
```

### `EXPLAIN ANALYZE` 로 `DELETE` 를 실행해 버림

```sql
EXPLAIN ANALYZE DELETE FROM orders WHERE ordered_at < '2025-01-01';
--  → 진짜로 지워집니다 ★
```

**원인** — `ANALYZE` 는 **실제 실행**입니다.
**해결** — 트랜잭션으로 감쌉니다.

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders WHERE ...;
ROLLBACK;
```

### 외래키 열에 인덱스가 없어 삭제가 느림

**증상** — 부모 행 하나를 지우는 데 몇 초씩 걸립니다.
**원인** — PostgreSQL은 FK를 만들 때 **자식 쪽에 인덱스를 자동 생성하지 않습니다.**
부모를 지울 때마다 자식 테이블을 전체 스캔해 참조 여부를 확인합니다.
**해결** — **모든 외래키 열에 인덱스를 만드세요.** 조인 성능에도 도움이 됩니다.

### 인덱스를 너무 많이 만듦

**증상** — 조회는 빠른데 적재가 갈수록 느려지고, DB 용량이 테이블보다 인덱스가 큽니다.
**해결** — 안 쓰이는 인덱스를 찾아 지웁니다.

```sql
SELECT relname AS 테이블, indexrelname AS 인덱스, idx_scan AS 사용횟수
FROM pg_stat_user_indexes
ORDER BY idx_scan;      -- 0에 가까운 것이 후보
```

## ⑥ 확인 문제

**1.** 아래 테이블 정의에서 문제점을 3개 이상 찾고 고치세요.

```sql
CREATE TABLE sensor_reading (
    id        text,
    device    varchar(10),
    temp      float,
    recorded  timestamp,
    is_valid  text
);
```

<details>
<summary>답 보기</summary>

| # | 문제 | 고침 | 이유 |
|---|---|---|---|
| 1 | **기본키가 없다** | `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | 행을 유일하게 가리킬 수 없음. 중복 적재도 못 막음 |
| 2 | `id` 가 `text` | `bigint` | 식별자는 숫자가 저장·비교·인덱스 모두 유리 |
| 3 | `temp` 가 `float` | `numeric(5,2)` (또는 측정값이면 `real` 유지) | **금액이라면 반드시 `numeric`**. 온도는 오차 허용이라 `real` 도 가능 |
| 4 | **`recorded` 가 `timestamp`** | `timestamptz` | 시간대 없이 저장하면 서버·클라이언트 시간대가 다를 때 조용히 어긋남 ★ |
| 5 | `is_valid` 가 `text` | `boolean` | `'Y'`/`'y'`/`'true'`/`'1'` 이 뒤섞임 |
| 6 | **`NOT NULL` 이 하나도 없다** | 필수 열에 추가 | 전부 NULL인 행도 들어감 |
| 7 | 범위 검증이 없다 | `CHECK (temp BETWEEN -50 AND 100)` | 센서 오작동 값 차단 |
| 8 | `varchar(10)` | `text` | PostgreSQL에서 길이 제한은 성능 이득이 없고, 나중에 늘릴 때 `ALTER` 가 필요 |

**고친 결과**

```sql
CREATE TABLE sensor_reading (
    id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    device_id   text        NOT NULL,
    temp        numeric(5,2) NOT NULL CHECK (temp BETWEEN -50 AND 100),
    recorded_at timestamptz NOT NULL,
    is_valid    boolean     NOT NULL DEFAULT true,
    UNIQUE (device_id, recorded_at)          -- 같은 기기·같은 시각 중복 방지 (멱등성!)
);
CREATE INDEX idx_sensor_reading_device_time ON sensor_reading (device_id, recorded_at);
```

**마지막 `UNIQUE (device_id, recorded_at)` 가 가장 중요합니다.**
이것이 [Day 042](day-042.md)의 `ON CONFLICT` 와 [Day 043](day-043.md)의 **멱등성**을 가능하게 하는 장치입니다.
같은 배치를 두 번 돌려도 데이터가 두 배가 되지 않습니다.
</details>

**2.** 아래 쿼리가 느립니다. `EXPLAIN` 결과가 `Seq Scan` 인 이유와 해결책 두 가지를 쓰세요.

```sql
SELECT * FROM event_log WHERE DATE(event_at) = '2025-06-01';
-- 인덱스: CREATE INDEX idx_event_log_at ON event_log (event_at);
```

<details>
<summary>답 보기</summary>

**원인** — 인덱스는 **`event_at` 의 원본값**(예: `2025-06-01 14:23:11+09`)으로 정렬돼 있습니다.
조건은 `DATE(event_at)` — **가공한 값**을 묻고 있어서 인덱스에서 찾을 수가 없습니다.
DB는 모든 행에 `DATE()` 를 적용해 봐야 하므로 전체 스캔이 됩니다.

**해결 ① 범위 조건으로 바꾼다 (권장)**

```sql
SELECT * FROM event_log
WHERE event_at >= '2025-06-01' AND event_at < '2025-06-02';
```

기존 인덱스를 그대로 씁니다. 추가 비용이 없고, [Day 032](day-032.md)에서 배운 반열림 구간과 같은 형태입니다.

**해결 ② 표현식 인덱스를 만든다**

```sql
CREATE INDEX idx_event_log_date ON event_log (DATE(event_at));
```

쿼리를 못 고치는 상황(예: BI 툴이 생성하는 SQL)에서 유효합니다.
대신 **인덱스가 하나 늘어** 쓰기 비용과 용량이 증가합니다.

**일반화된 원칙 — "열을 가공하지 말고 값을 가공하라"**

```sql
WHERE UPPER(name) = 'ABC'          ❌  →  WHERE name = 'abc'  (또는 표현식 인덱스)
WHERE price * 1.1 > 10000          ❌  →  WHERE price > 10000 / 1.1
WHERE customer_id::text = '42'     ❌  →  WHERE customer_id = 42
```

같은 이유로 [Day 034](day-034.md)의 `조인 키 캐스팅` 도 인덱스를 죽입니다.
**적재 시점에 타입을 맞추는 것**이 근본 해결입니다 ([Day 043](day-043.md)).
</details>

**3.** 매일 밤 100만 행을 적재하는 테이블이 있습니다. 조회 성능을 위해 인덱스 6개를 걸었더니 적재가 20분에서 55분으로 늘었습니다. 어떻게 하겠습니까?

<details>
<summary>답 보기</summary>

**순서대로 검토합니다.**

**① 정말 6개가 다 필요한지 확인**

```sql
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE relname = '대상테이블'
ORDER BY idx_scan;
```

`idx_scan` 이 0이거나 아주 작은 인덱스는 **아무도 안 쓰는데 매일 갱신 비용만 내는** 것입니다. 지웁니다.
실무에서 인덱스 6개 중 2~3개가 여기 해당하는 경우가 흔합니다.

**② 중복 인덱스 통합**

```
(user_id)             ← 삭제 가능
(user_id, event_at)   ← 이것이 (user_id) 단독 조회도 처리함 (선두 열 규칙)
```

**③ 적재 중에는 인덱스를 내린다 (핵심)**

```sql
DROP INDEX idx_a, idx_b, idx_c;
-- 대량 적재 (COPY 등 — Day 042)
CREATE INDEX idx_a ON ...;
CREATE INDEX idx_b ON ...;
ANALYZE 대상테이블;          -- 통계 갱신을 잊지 마세요
```

**"넣으면서 정렬"보다 "다 넣고 한 번에 정렬"이 훨씬 빠릅니다.**
단, 재생성 동안 조회가 느려지므로 **서비스 영향이 적은 시간대**여야 합니다.
`CREATE INDEX CONCURRENTLY` 를 쓰면 조회를 막지 않지만 더 오래 걸립니다.

**④ 적재 방식 자체를 바꾼다** — `INSERT` 대신 `COPY` ([Day 042](day-042.md)).

**⑤ 파티셔닝을 검토한다** — 날짜별로 테이블을 쪼개면 오늘 파티션에만 쓰면 됩니다.
[Day 027](../01-python-data/day-027.md)의 Parquet 파티션과 같은 발상입니다.

**판단 기준** — "조회가 얼마나 느려지는가"와 "적재가 얼마나 느려지는가"를 **둘 다 측정**해서 비교합니다.
55분 적재가 서비스에 문제가 없다면 그냥 두는 것도 답입니다.
**측정 없이 인덱스를 추가하거나 삭제하지 마세요.**
</details>

## 오늘의 정리

| 구문 | 하는 일 |
|---|---|
| `CREATE TABLE ... (열 타입 제약)` | 테이블 생성 |
| `ALTER TABLE t ADD COLUMN c 타입 NOT NULL DEFAULT v` | 열 추가 |
| `ALTER TABLE t ADD CONSTRAINT n CHECK (...)` | 제약 추가 |
| `CREATE INDEX i ON t (a, b)` | 복합 인덱스 (**선두 열부터**) |
| `EXPLAIN ANALYZE 쿼리` | 실행 계획 + 실제 시간 (**진짜 실행됨**) |
| `ANALYZE t` | 통계 갱신 (대량 적재 후 필수) |
| `CREATE VIEW v AS ...` | 쿼리에 영구 이름 |
| `\di` · `\d+ t` · `pg_size_pretty(...)` | 인덱스 목록 · 구조 · 크기 |
| `\timing on` | 쿼리 소요 시간 표시 |

| 원칙 | 이유 |
|---|---|
| **제약은 코드와 별개로 DB에도 건다** | 코드는 우회 가능, DB는 못 지나감 |
| **금액은 `numeric`, 시각은 `timestamptz`** | `float` 오차 · 시간대 어긋남 |
| **외래키 열에는 반드시 인덱스** | 자동 생성 안 됨. 조인·삭제 성능 |
| **열을 가공하지 말고 값을 가공하라** | `DATE(t) = x` 는 인덱스를 죽임 |
| **복합 인덱스는 선두 열부터** | 전화번호부 `(성, 이름)` 규칙 |
| **`UNIQUE` 는 멱등성의 전제** | [Day 042](day-042.md) `ON CONFLICT` |
| **측정 없이 인덱스를 만들지 않는다** | 쓰기 비용·용량이라는 대가가 있음 |

**오늘의 습관** — 느린 쿼리를 만나면 **추측하지 말고 `EXPLAIN ANALYZE`** 를 붙이세요.
`Seq Scan` 인지, `Rows Removed by Filter` 가 몇인지 — **두 줄만 봐도 절반은 풀립니다.**
