## Part 4의 한마디 — "결제는 코드가 전부가 아니다"

Part 3가 *"내 서비스를, 시스템으로 만들어, 세상에 내놓는다"* 였다면 Part 4는 **"내놓은 제품에 돈이 흐르게 하고, 끝까지 책임진다"** 입니다.

- **Day 30–31** — 방치된 PRD를 **3단계 업데이트**로 살리고, 결제 기획을 **기존 배너에 새 역할을 주는 방식**으로 디자인·핸드오프한 뒤, **카피·CTA**로 팔 준비를 합니다.
- **Day 32** — **정산**(결제 ≠ 입금)을 이해하고, 비즈니스 검증 전에는 **결제 링크로 먼저 팔고**, 본격 시스템(카드사 ← PG ← 결제솔루션)의 구조를 익힙니다.
- **Day 33–34** — **insert-only 원장**(취소 = 음수 행, 과거 = 스냅샷, 정체성 = 트랜잭션키)을 설계해 Supabase에 만들고, **포트원MCP**로 실연동한 뒤 **웹훅 → 내역 조회 → 취소 → 취소 웹훅**으로 사이클을 완성합니다.

> 반복되는 네 문장 — **디자인은 결과를 남기고, PRD는 이유를 남긴다. 먼저 팔고, 팔리면 계약서를 쓴다. 결제 데이터는 고치지 않고 쌓는다. 그리고 웹훅은 localhost에 오지 않는다.**

## Day 30 · PRD 업데이트 — 문서 → 디자인 → 코드까지 한 흐름

**배우는 것**

- *"Premium 구독하면 쿠폰 2개 주기로 했었나?"* — 결정도 번복도 기록이 없다. **디자인은 "왜"를 못 남긴다**
- PRD **최초 작성 7단계** vs **업데이트 3단계**(추가 기획 내용(수동) → `/strategy-red-team` → `/create-prd`)
- `delta.txt` — 델타(δ) = **변화량**, 날짜 폴더로 쌓으면 기획 이력
- 공격 문서의 6항목: 스틸맨 · 공격 · **Fails if** · 증거 · **Kill criterion** · **가장 싼 테스트**
- 결제 기획 4페이지 — **기존 배너에 새 역할**(강연/모임 결제 상품), 결제 바텀시트, 마이 2탭
- Pencil 4지시(신규 / **복사 후 수정** / 재사용만 / 없으면 다이렉트) · 디자인에서 **DB 필드 8개** 도출 · **Node ID 8개** 증분 핸드오프

**실습·과제** — `delta.txt` 작성 → 전략 가정 공격 → PRD 업데이트(Change Log 확인) → 결제 4화면 디자인 → Node ID 핸드오프.

**이걸 할 수 있으면 통과**

- [ ] 업데이트에서 **빠진 4단계**와 그 이유(이미 했다)를 말할 수 있다
- [ ] **Kill criterion 없는 기획서**가 무엇을 못 하는지 설명할 수 있다
- [ ] 핸드오프에 이름 대신 **Node ID**를 쓰는 이유를 말할 수 있다

## Day 31 · 핸드오프 점검과 모바일 배너

**배우는 것**

- **핸드오프는 끝이 아니라 시작** — 초보 디자인 징후: ① 타이포그래피 ② 레이아웃·간격 ③ **사진·컨텐츠**(해법: unsplash)
- 정적 디자인에 없는 **동작은 말로 지시**한다 — 스와이핑, 핀치줌 인/아웃(양방향)
- 레퍼런스는 구조로 환원 — **파란 상자 = 고정(헤더·탭바) / 빨간 상자 = 스크롤** · **"카드 디자인 X"**
- **카피**(마음을 움직인다 — 묻는다) vs **CTA**(손가락을 움직인다 — 시킨다) — 마케터가 넘기는 건 딱 이 둘
- 배너 2종 — **실물 O → 사진 / 실물 X → 3D 아이콘** · AI 느낌은 "실존하는 것을 그리게 하지 않는 것"으로 피한다
- 프롬프트 5요소(사이즈 `360*180` · 카피 · CTA · 폰트 · 구현) — "절반은 밖으로 잘리게", **"과하게 넓은 여백"**

**실습·과제** — 투명 배경 소재 + 빈 배경 준비 → 두 모델에 같은 프롬프트 → 모바일/데스크톱 배너 각각 제작.

**이걸 할 수 있으면 통과**

- [ ] 카피와 CTA를 예시 문장과 함께 구분할 수 있다
- [ ] "배경이미지 + 코딩글자"와 "이미지에 글자 포함"의 트레이드오프를 다섯 기준으로 비교할 수 있다

## Day 32 · 결제와 정산 — 먼저 팔고, 그다음 시스템

**배우는 것**

- **정산** = 결제한 돈에서 수수료를 차감해 최종 받을 돈을 확정하는 일 — 돈은 결제사 서버에 쌓였다가 **주기**로 온다
- *"클로드가 못해주나?"* — 코드 밖의 넷: **사업자 등록 · 통신판매업 신고 · PG 가입 · 카드사 심사**
- **결제 링크**(10분내, 아이디어 검증, *"먼저 팔고 팔리면 계약서"*) vs **결제 시스템 구축**(본격 판매)
- 3층 구조: **카드사 ← PG사 ← 결제솔루션(포트원) ← 내 서비스** · 연동 4단계와 `paymentId`(중복 결제 방지)
- **웹훅** — 브라우저가 꺼져도 결제 기록을 지키는 서버 대 서버 통지
- 정기 결제 — **빌링키**(카드번호는 저장하지 않는다) · 다음결제예약일 = 만료일 + 30일(**UTC**) · **빌링키는 정기 구독 전용**

**실습·과제** — 페이앱 결제 링크 생성 → 원페이지 판매 사이트(원샷 개발) → 1,000원 실결제 → 정산 예정 금액(956원) 확인.

**이걸 할 수 있으면 통과**

- [ ] "오늘 판 돈은 오늘 못 쓴다"를 정산 주기로 설명할 수 있다
- [ ] 검증용 사이트에 디자인 시스템을 강요하지 않는 이유를 말할 수 있다

## Day 33 · 고치지 않는 장부 — 결제 DB와 포트원 실연동

**배우는 것**

- 이미지 **4컬럼**(큰/작은 × 배너/상세) · **`공개상태`**(지우는 대신 내린다) · 유저는 Supabase **참조만**
- **`insert-only / append-only`** — 취소는 수정이 아니라 **`-30000` 음수 행**, 합산하면 0 (회계 장부 방식)
- **결제스냅샷** — 결제 당시의 상품 정보를 JSON으로 보존 · **트랜잭션키** — 결제·취소는 같은 키, 재결제는 새 키
- default value의 자리(지금은 Supabase / 이전 계획이면 코드) · **이미지 주소 = 앞단(환경변수) + 뒷단(DB 컬럼)**
- PortoneMCP 설치(공식 가이드 URL) · `orderName`·`totalAmount`는 **DB에서 조회**(1원 결제 조작 방지) · `customData: {productId, userId}`
- 환경변수 2분법(`NEXT_PUBLIC_` vs 서버 전용) · **`rules/payment.md`(결제 SSOT)** — 규칙이 바뀌면 문서를 먼저 고친다

**실습·과제** — 시트 정규화 → `product`·`payment`·`payment_snapshot` 생성 → PortoneMCP 설치 → 테스트 모드 결제 → 콘솔 확인.

**이걸 할 수 있으면 통과**

- [ ] 스냅샷이 없으면 석 달 뒤 환불 분쟁에서 무슨 일이 생기는지 말할 수 있다
- [ ] 금액을 브라우저에서 받으면 안 되는 이유를 설명할 수 있다

## Day 34 · 끝까지 책임진다 — 웹훅과 취소

**배우는 것**

- **웹훅은 localhost에 오지 않는다** — 화면·결제는 로컬 테스트, 웹훅 검증은 배포(Vercel) 후에
- 웹훅 프롬프트 3원칙 — insert-only + type · **transaction_key = 포트원 payment_id** · **중복결제 검증**(웹훅은 재발송된다)
- 두 개의 비밀키 — `PORTONE_WEBHOOK_SECRET`(서명 검증) · `SUPABASE_SERVICE_ROLE_KEY`(**RLS 우회, 노출 금지**)
- 취소의 분류학 — 일반 / 정기(**전체 취소** vs **예약만 취소** — 돈 이동 없으면 **원장에 행 없음**)
- *"테이블에 2건이 들어있는 게 정상"* — insert-only의 실물 · 취소 웹훅 프롬프트는 **SSOT 세 줄**이면 된다

**실습·과제** — 웹훅 API 구현 → 콘솔에 웹훅 URL 등록 → Vercel 재배포 → 결제·취소 후 원장(`PAYMENT +30000` / `CANCEL −30000`) 확인.

**이걸 할 수 있으면 통과**

- [ ] 웹훅 개발 순서도의 마지막이 왜 항상 "배포"인지 설명할 수 있다
- [ ] 취소 웹훅 프롬프트가 세 줄로 줄어든 이유(SSOT)를 말할 수 있다

## Part 4 졸업 체크리스트

- [ ] PRD에 **Change Log**가 있고, 이번 결제 기획이 `delta.txt` → 공격 → 반영 순서로 들어갔다
- [ ] 새 기획을 **기존 UI에 새 역할을 주는 방식**으로 먼저 검토했다 (배너 → 결제 상품)
- [ ] 기존 페이지는 **복사 후 수정**했고, 디자인 시스템 밖의 새 컴포넌트를 만들지 않았다
- [ ] 스와이핑·핀치줌 등 **정적 디자인에 없는 동작**을 지시문으로 채웠다
- [ ] 배너에 **카피와 CTA**가 한 쌍으로 있고, 실물 없는 상품이라 3D 아이콘을 썼다
- [ ] **정산 주기**를 알고 있고, 검증 단계면 결제 링크부터 검토했다
- [ ] 결제 테이블이 **insert-only**다 — 취소가 음수 행이고, 수정·삭제 쿼리가 없다
- [ ] 결제 시점의 상품 정보가 **스냅샷**으로 남고, 결제·취소가 **같은 트랜잭션키**로 묶인다
