## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- CD의 두 수준(**Delivery vs Deployment**)을 구분하고, 우리 파이프라인의 선택을 정당화할 수 있다.
- **self-hosted runner** 를 서버에 설치해, 빌드 완료가 곧바로 서버 배포로 이어지게 할 수 있다.
- 배포 스크립트에 **스모크 테스트와 자동 롤백**을 넣어, 실패한 배포가 스스로 물러나게 할 수 있다.
- **배포 이력**(언제·어떤 sha가·어떻게 됐나)을 기록으로 남길 수 있다.

---

## ② 왜 필요한가

파이프라인의 현재 상태를 봅시다 — 딱 한 구간만 사람이 남았습니다:

```
push → [CI: test·lint] → 병합 → [CI: build→GHCR] → ❗사람이 서버에서 pull·up❗ → 반영
```

"pull·up 두 줄인데 뭐 어때요?" — 그 두 줄이 문제인 이유는 [Day 115](day-115.md)의 논리
그대로입니다. 사람은 잊고(금요일 오후의 병합은 월요일까지 미배포 — 그동안 main과 서버가
불일치), 사람은 자고(새벽의 긴급 수정), 사람은 실수합니다(pull 없이 up, 다른 태그).
main과 서버의 불일치 기간은 "**저장소를 보고 서버를 추론할 수 없는**" 기간 — 족보의 마지막
구멍입니다.

오늘 그 구멍을 닫으면 이번 주 체크포인트의 문장이 완성됩니다:

> **커밋 푸시부터 서버 반영까지, 사람 손이 필요한 횟수: 0번.**

단, 자동화된 배포는 자동화된 사고이기도 합니다 — 사람이 지켜보지 않으므로, **배포가 스스로를
검증하고(스모크), 실패하면 스스로 물러나는(롤백)** 장치까지가 오늘의 범위입니다. Day 115
deploy.sh의 정신(검증이 파괴 앞에)이 한 단계 진화합니다.

## ③ 개념 설명

### CD의 두 수준

| | Continuous **Delivery** (전달) | Continuous **Deployment** (배포) |
|---|---|---|
| main 병합 후 | 배포 **가능** 상태까지 자동 (버튼은 사람이) | 운영 반영까지 **전자동** |
| 어울리는 곳 | 규제 산업 · 배포 창구가 정해진 팀 | 테스트 신뢰도가 높은 팀 · 잦은 배포 |

우리는 Deployment로 갑니다 — 게이트(127)와 스모크(오늘)가 사람 승인을 대신할 만큼 촘촘하다는
전제이고, 그 전제를 오늘 실험으로 시험합니다. (버튼 하나를 남기고 싶다면 GitHub environments의
승인 기능 한 줄이면 Delivery로 전환됩니다 — 구조는 동일.)

### 러너가 서버로 들어간다 — self-hosted runner

배포의 난제는 방향입니다: GitHub의 러너(클라우드)가 내 서버에 **들어와야** 하는데, 우리 서버
(WSL)는 바깥에서 접속할 주소가 없습니다. 두 경로가 있습니다:

| 경로 | 구조 | 어울리는 상황 |
|---|---|---|
| **self-hosted runner (오늘)** | 러너 프로그램을 **서버 안에** 설치 — 서버가 GitHub에 "일감 주세요"라고 **밖으로** 접속 | 공인 주소 없는 서버(WSL·사내망) · 무료 |
| SSH 배포 액션 | 클라우드 러너가 **SSH로 서버에 접속**해 명령 실행 (`appleboy/ssh-action` + secrets에 개인키·호스트) | 공인 주소 있는 클라우드 서버 |

방향만 다를 뿐 도착지는 같습니다 — "서버에서 deploy.sh 실행". 클라우드 서버가 생기면(W29)
둘째 경로로 갈아타는 데 워크플로 몇 줄이면 됩니다.

### 배포 전략 — 우리는 어디까지

| 전략 | 방식 | 순단 | 우리 과정 |
|---|---|---|---|
| **재시작 (recreate)** | 옛것 내리고 새것 올림 | 수 초 있음 | **오늘의 방식** |
| 롤링 | 여러 인스턴스를 순차 교체 | 없음 | 개념만 — nginx 뒤에 API 여러 대일 때 |
| 블루-그린 | 새 판 전체를 옆에 세우고 스위치 | 없음 | 개념만 |
| 카나리 | 소수 트래픽으로 먼저 검증 | 없음 | 개념만 — [Day 135](day-135.md)에서 재회 |

무중단 전략들이 전부 "문지기(프록시) 뒤의 일꾼을 손님 몰래 바꾼다"는 한 문장 위에 서 있다는
것 — [Day 124](day-124.md)의 그 "모름"이 이들의 지반입니다.

### 스모크 테스트 — 배포 직후의 30초 검진

CI의 테스트와 다릅니다 — **실제 운영 구성**(nginx 경유·실제 DB·실제 모델 파일)에서, 핵심
경로만 빠르게: 헬스 200 + 대표 예측 1건의 대조값. CI가 초록이어도 배포가 깨지는 병(포트 계약,
설정, 프록시)을 잡는 마지막 그물입니다 — 세 겹 그물(126)의 셋째 겹이 정식으로 이것입니다.

## ④ 단계별 실습

### Step 1. 러너 입주 (1~2교시)

GitHub 저장소 → Settings → Actions → Runners → **New self-hosted runner** (Linux x64).
화면의 명령을 서버(WSL)의 **deploy 계정**으로 실행합니다:

```bash
su - deploy
mkdir actions-runner && cd actions-runner
curl -o actions-runner-linux-x64-2.321.0.tar.gz -L https://github.com/actions/runner/releases/download/v2.321.0/actions-runner-linux-x64-2.321.0.tar.gz
tar xzf actions-runner-linux-x64-2.321.0.tar.gz
./config.sh --url https://github.com/mlops-student/mlops-mp3 --token AXXXXXXXXXXXXXXXXXXXXXXXXXXXX
```

```
$ ./config.sh --url https://github.com/mlops-student/mlops-mp3 --token AXXX...
√ Connected to GitHub
Enter the name of runner: [press Enter for DESKTOP] mp3-server
√ Runner successfully added
√ Settings Saved.
```

`./run.sh` 로 손 실행해 볼 수도 있지만 — 우리는 이미 상주의 정석을 압니다 ([Day 113](day-113.md)):

```bash
sudo ./svc.sh install deploy && sudo ./svc.sh start
```

Settings → Runners에 **mp3-server (Idle)** 이 떴으면 입주 완료. 러너는 deploy 계정으로 돌고
(최소 권한 — docker 그룹만 추가), GitHub 쪽에서 보면 "우리 저장소 전속 일꾼"이 생긴 것입니다.

### Step 2. deploy.sh v2 — 스모크와 자동 롤백 (3~4교시)

[Day 115](day-115.md)의 스크립트를 컨테이너 시대에 맞게 재작성합니다:

```bash
#!/bin/bash
# deploy.sh v2 — pull·up·스모크·롤백 (Day 129)
set -euo pipefail

APP_DIR=/opt/mlops-mp3
IMAGE=ghcr.io/mlops-student/mlops-mp3
TAG=${1:?사용법: deploy.sh <sha-태그>}
HIST=$APP_DIR/deploy_history.log
BASE=http://localhost:8080

cd "$APP_DIR"
PREV=$(tail -1 "$HIST" 2>/dev/null | awk '{print $2}' || true)

deploy() {
    sed -i "s|${IMAGE}:.*|${IMAGE}:$1|" compose.yaml
    docker compose pull -q api
    docker compose up -d
}

smoke() {
    for i in $(seq 1 15); do
        curl -sf "$BASE/health" > /dev/null && break
        sleep 2
    done
    label=$(curl -sf -F "file=@tests/data/ant_sample.jpg" "$BASE/predict" | grep -o '"label":"ants"')
    [ -n "$label" ]
}

echo "[deploy] $TAG 배포 (이전: ${PREV:-없음})"
deploy "$TAG"
if smoke; then
    echo "$(date -Is) $TAG ok" >> "$HIST"
    echo "[deploy] 성공 — 이력 기록 완료"
else
    echo "[deploy] 스모크 실패!"
    if [ -n "$PREV" ]; then
        echo "[deploy] $PREV 로 롤백"
        deploy "$PREV" && smoke && echo "$(date -Is) $PREV rollback-from-$TAG" >> "$HIST"
    fi
    exit 1          # 어느 경우든 이번 배포는 실패로 보고 (사람 호출)
fi
```

설계 요점 — ① 태그는 **인자**(latest 아님 — 무엇을 올렸는지가 이력에 남아야 롤백이 가능),
② 스모크는 **nginx 경유**(8080 — 운영 구성 통째 검증) + 대표 예측 대조, ③ 실패 시 이전 태그로
자동 롤백하되 **종료 코드는 1** — 롤백 성공은 "서비스 원상 복구"이지 "배포 성공"이 아니므로
워크플로는 빨간불로 사람을 부릅니다.

### Step 3. build.yml에 deploy job 연결 (5교시)

```yaml
  deploy:
    needs: build
    runs-on: self-hosted
    steps:
      - name: 서버 배포 (스모크·롤백 포함)
        run: /opt/mlops-mp3/deploy.sh "sha-$(echo "$GITHUB_SHA" | cut -c1-7)"
```

`needs: build` — 빌드 성공 후에만, `runs-on: self-hosted` — 우리 서버의 그 러너에서.
sha 태그를 넘기므로 **배포되는 것과 커밋의 1:1** 이 유지됩니다 (latest 배포 금지 — 어제 ⑤).

### Step 4. 전 구간 주행 (6교시)

작은 실제 변경(예: /health 응답에 `"image_tag"` 필드 — 컨테이너에 주입된 태그를 그대로 회신)
을 PR → 병합하고, 스톱워치를 켭니다:

```
14:02:11  git push (PR 병합)
14:02:14  CI: Build & Push 시작
14:03:39  build 완료 — ghcr.io/...:sha-9e21c47 push
14:03:41  deploy (self-hosted) 시작
14:04:12  deploy.sh: 스모크 통과, 이력 기록
────────────────────────────────────────
커밋 → 운영 반영: 2분 01초 · 사람 손: 0번
```

```bash
$ curl -s localhost:8080/health
{"status":"ok","model_loaded":true,"model_version":"resnet18-antbee-v1","image_tag":"sha-9e21c47","started_at":"2026-08-24T05:04:08+00:00"}
$ tail -2 /opt/mlops-mp3/deploy_history.log
2026-08-24T14:01:02+09:00 sha-b6f92d3 ok
2026-08-24T14:04:12+09:00 sha-9e21c47 ok
```

체크포인트의 답이 나왔습니다 — **0번.** 그리고 이력 파일이 "서버의 시간표"가 됐습니다.

### Step 5. 실패 리허설 — CI는 초록인데 배포가 깨지는 병 (7교시)

스모크의 존재 이유를 증명합니다. Dockerfile의 CMD 포트를 8001로 바꾸는 변경을 상상해 보세요
— CI는 **통과합니다** (TestClient는 포트를 안 탑니다). 그러나 nginx의 proxy_pass는 8000 —
배포되면 502입니다. 실제로 리허설:

```
deploy (self-hosted)                                     ✗ 1m 48s
[deploy] sha-3f07a12 배포 (이전: sha-9e21c47)
[deploy] 스모크 실패!
[deploy] sha-9e21c47 로 롤백
[deploy] 성공 — 이력 기록 완료
Error: Process completed with exit code 1.
```

서비스는 **한 번도 사람 손 없이** 이전 버전으로 복귀했고(순단 수십 초), 워크플로의 빨간불이
"3f07a12는 배포 불가능한 커밋"이라고 외치고 있습니다. revert(109) 후, 이 병을 **앞 그물로**
당기는 개선(⑥ Q3·어제 Q3의 build-check에 컨테이너 기동 테스트 추가)을 생각해 보세요.

### Step 6. 과제 — 배포 이력의 완성 (8교시)

① deploy_history.log의 형식을 확장하세요 — `시각 | 태그 | 결과(ok/rollback) | 트리거 커밋
메시지 | 소요 초`. ② "지금 운영 중인 것은?"에 답하는 원라이너를 만들고 README 운영 섹션에
추가 (`tail -1` + /health의 image_tag 대조 — 둘이 다르면?이 보너스 문제). ③ 오늘의 전 구간
주행 기록(타임라인·이력 발췌·롤백 리허설 로그)을 `docs/DEPLOY.md` 로 정리 — MP4 "배포 이력
기록" 산출물의 원형입니다. ④ 클라우드 경로 예습: appleboy/ssh-action을 쓴다면 secrets에
무엇이 들어가고(SSH_HOST·SSH_KEY…), [Day 114](day-114.md)의 어떤 규율이 그대로 적용되는지
반 페이지.

## ⑤ 자주 하는 실수

### 공개 저장소에 self-hosted runner

**증상** — 포트폴리오 공개 직후, 낯선 PR의 워크플로가 **내 서버에서** 암호화폐 채굴을 시작.
**원인** — 공개 저장소는 외부인 PR도 워크플로를 태울 수 있습니다 — self-hosted 러너는 "내
서버에서 남의 코드 실행"의 문이 될 수 있습니다.
**해결** — self-hosted 러너는 **비공개 저장소에서만** (우리 상태 유지). 공개 전환이 필요하면
러너를 떼고 SSH 경로로 전환하거나, GitHub의 러너 그룹·승인 설정으로 외부 PR 실행을 차단한 뒤
충분히 이해하고 여세요. "러너 = 그 저장소에 내준 셸"이라는 감각이 핵심입니다.

### 러너를 개인 계정·root로 돌림

**증상** — 워크플로의 run: 이 서버에서 root 권한 — 오타 한 줄의 사고 반경이 서버 전체
([Day 112](day-112.md)의 그 문제가 CI 경유로).
**원인** — svc.sh install을 기본값(현재 사용자)으로.
**해결** — 러너는 **deploy 같은 서비스 계정**으로 (오늘 Step 1). 러너 계정이 할 수 있는 일 =
워크플로가 할 수 있는 일이므로, 최소 권한 설계가 그대로 CI 보안 설계입니다.

### 스모크 없는 자동 배포

**증상** — `up -d` 가 성공했으니 초록 — 실제로는 컨테이너가 재시작 루프 중이거나 502.
새벽 배포라 아침까지 아무도 모름.
**원인** — "명령 성공"과 "서비스 정상"의 혼동 (Day 123의 시작됨≠준비됨이 배포 층위에서 재발).
**해결** — 배포의 종료 조건은 스모크 통과입니다 — 헬스 + 대표 요청 1건이 최소 단위. 자동
배포에서 스모크는 선택이 아니라 **자동화의 면허 조건**입니다.

### 롤백 대상을 latest로

**증상** — 실패해서 "롤백"한다며 latest 재pull — latest는 방금 그 실패 버전입니다. 제자리 회전.
**원인** — 가변 태그로 상태를 관리한 대가 (어제 ⑤의 실전판).
**해결** — 롤백은 **이력에 기록된 직전 sha로** (deploy.sh v2의 PREV가 그것). 이력 없는 롤백은
추측이고, 추측 롤백은 2차 사고의 지름길입니다.

### 배포 자동화 후 서버 설정 변경을 잊음

**증상** — 코드는 전자동인데 .env·compose·nginx 설정은 여전히 서버에서 손으로 — 어느 날
"설정 바꾼 사람?"에 아무도 기록이 없음.
**원인** — 게이트·이력의 바깥에 남은 마지막 수동 영역.
**해결** — 최소한의 규율부터: 서버 설정 변경도 이력 파일에 한 줄 남기기, compose·nginx 설정은
저장소가 원본(서버는 pull만). 완전한 해법(설정까지 선언·형상 관리 — GitOps)은 취업 후의 세계
지만, "**서버에서 손으로 바꾼 것은 존재하지 않았던 것으로 취급된다**"는 문화만은 지금부터
가져가세요.

## ⑥ 확인 문제

**Q1.** self-hosted runner 방식이 "서버의 방화벽에 인바운드 구멍을 하나도 안 뚫고" 배포를
성립시키는 원리를, SSH 배포 방식과 대비해 설명하세요.

<details>
<summary>답 보기</summary>

SSH 방식은 밖(클라우드 러너)에서 안(서버 22번)으로 들어오는 **인바운드** 연결이라 포트 개방·
키 관리·발신지 제한이 필요합니다. self-hosted 러너는 서버 안의 러너가 GitHub으로 **아웃바운드**
연결을 유지하며 일감을 당겨오는(polling) 구조 — 들어오는 문이 없으니 뚫을 구멍도 없습니다.
공인 주소가 없는 WSL·사내망 서버에서도 되는 이유가 정확히 이것입니다. 대가는 "저장소에 내준
셸"이라는 새 신뢰 경계 — 그래서 비공개 저장소·서비스 계정 규율이 따라붙습니다.

</details>

**Q2.** deploy.sh v2는 롤백에 성공해도 exit 1로 끝납니다. 이 설계를 "롤백까지 했으면 성공
아닌가요?"라는 반론에 맞서 옹호하세요.

<details>
<summary>답 보기</summary>

롤백 성공은 **서비스의 회복**이지 **배포의 성공**이 아닙니다. exit 0으로 끝내면 워크플로가
초록 — "sha-3f07a12가 운영에 못 올라갔다"는 사실이 아무에게도 통지되지 않고, main은 배포
불가능한 상태로 남아 다음 병합도 같은 벽에 부딪힙니다. exit 1은 사람을 부르는 신호(원인 커밋
조사·revert·그물 보강)이고, 서비스 가용성(자동 롤백)과 문제의 가시성(빨간불)을 **동시에**
확보하는 조합입니다. 자동화의 원칙: 기계는 복구까지, 판단과 수리는 사람에게 통지.

</details>

**Q3.** Step 5의 병(CMD 포트 변경)은 CI 초록·배포 실패였습니다. 이 유형을 배포 전에 잡으려면
그물을 어디에 어떻게 보강해야 할까요? 비용(실행 시간)과 함께 설계하세요.

<details>
<summary>답 보기</summary>

병의 본질은 "컨테이너·구성 계약(포트·헬스체크·프록시)"이 TestClient 테스트의 시야 밖이라는
것. 보강: PR 단계에 **컨테이너 기동 테스트** — build-check(push: false)로 이미지를 만들고,
`docker run` + 컨테이너의 8000으로 헬스·예측 1건을 확인하는 job (약 1~2분 추가). 더 넓게는
compose 전체를 러너에서 올리는 통합 테스트(docker compose up + 스모크 — 3~4분)도 가능하며,
매 PR이 부담이면 main 병합 시에만. 원칙은 "배포에서 터진 병은 한 그물 앞으로 당긴다" — 스모크
실패 사례마다 그 검사를 PR 단계로 이식하면 파이프라인이 사고를 먹고 자랍니다.

</details>
