## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- API를 **명세(계약 표)부터** 설계하고, W19의 전 기술로 혼자 구현할 수 있다.
- 멱등한 상태 변경(PATCH)과 삭제(204/404)의 설계 결정을 내리고 근거를 댈 수 있다.
- **API 설계 리뷰 기준**(일관성 · 에러 · 문서)으로 남의 API를 심사할 수 있다.
- 주간 퀴즈로 W19의 구멍을 찾는다.

## ② 왜 필요한가

이번 주 나흘은 대기질 API 하나를 함께 키웠습니다. 종합 실습은 **새 도메인에서 혼자**
반복하는 것입니다 — 할 일(Todo) API. 일부러 평범한 주제를 골랐습니다. 화려한 도메인이
아니어도 좋은 API와 나쁜 API는 명확히 갈리고, 그 차이는 전부 이번 주 배운 것
(계약 · 상태 코드 · 계층 · 테스트)에서 나오기 때문입니다.

그리고 오늘이 **모델 없는 API의 마지막 날**입니다. 다음 주 월요일, 이 자리에 모델이
들어옵니다 — 오늘 혼자 완주할 수 있어야 다음 주에 모델 쪽 문제에만 집중할 수 있습니다.

## ③ 개념 설명

### 설계는 명세 표부터 — 코드보다 먼저

| 메서드·경로 | 성공 | 실패 | 비고 |
|---|---|---|---|
| POST /todos | 201 + TodoOut | 422 (빈 제목·오타 필드) | id는 서버가 부여 |
| GET /todos?done=&limit= | 200 + 목록 | 422 (done 타입 오류) | 필터·페이징은 쿼리 |
| GET /todos/{id} | 200 | 404 | |
| PATCH /todos/{id}/done | 200 + 갱신본 | 404 | **멱등** — 두 번 눌러도 완료는 완료 |
| DELETE /todos/{id} | **204 (바디 없음)** | 404 | |

이 표가 [Day 071](../03-machine-learning/day-071.md)의 기획서, [Day 074](../03-machine-learning/day-074.md)의
테스트 목록, 그리고 /docs 문서의 원본이 됩니다. **MP3 기획서의 "API 명세" 항목이 정확히
이 표 형식**입니다 ([Day 101](day-101.md)).

### 설계 결정에는 근거를 — 오늘의 두 가지

**PATCH의 멱등성** — "이미 완료된 것을 또 완료"를 409로 거절할 수도 있지만(대기질 API의
중복 제출처럼), 완료 표시는 **여러 번 눌러도 결과가 같아야 자연스러운** 조작이라 200으로
설계했습니다. [Day 042](../02-sql-pipeline/day-042.md)의 멱등성이 API 설계 언어로 돌아온 것 —
중요한 것은 어느 쪽이든 **의도를 명세에 적는 것**입니다.

**DELETE 204** — 성공했고 돌려줄 내용이 없음. 바디 없는 상태 코드입니다.

### API 설계 리뷰 기준 — 오후 상호 리뷰의 체크리스트

| 축 | 질문 |
|---|---|
| **일관성** | 이름·복수형·응답 모양이 전 엔드포인트에서 같은 규칙인가 (todos/todo 혼용 ✗) |
| **에러** | 모든 실패가 의도된 4xx인가 · detail이 행동 가능한 정보인가 · 500이 나는 입력이 존재하는가 |
| **문서** | /docs만 보고 처음 온 사람이 쓸 수 있는가 · response_model이 선언돼 있는가 |
| 구조 | 계층이 분리됐는가 · service에 fastapi import가 없는가 ([Day 093](day-093.md)의 감사) |
| 테스트 | 상태 코드마다 테스트가 있는가 · 서버·DB 없이 도는가 |

## ④ 단계별 실습 — 할 일 API 완성

산출물: `api/todo/` (3계층 구조) + 테스트 + 완성된 /docs. 오전에 구현, 오후에 리뷰.

### Step 1. 명세 확정과 뼈대 (1교시)

③의 명세 표를 여러분의 저장소 `docs/todo_api.md` 에 옮기고, [Day 093](day-093.md)의 구조를
복제합니다: `router.py`(계약·번역) / `service.py`(규칙 — 오늘은 얇음) / `repository.py`(SQLite).
모델은 두 개:

```python
class TodoIn(BaseModel):
    model_config = {"extra": "forbid"}
    title: str = Field(min_length=1, max_length=100)     # 빈 제목 금지
    due: date | None = None

class TodoOut(BaseModel):
    id: int
    title: str
    due: date | None
    done: bool
```

### Step 2. 구현 (2~4교시)

W19의 부품 조립입니다 — 새로운 것은 없습니다. 막히면 해당 문서로:
경로·쿼리·바디([091](day-091.md)) · 검증과 4xx([092](day-092.md)) · 계층과 Depends([093](day-093.md)).
완성 후 전체 계약을 한 번에 훑는 시퀀스 (실측):

```
$ POST /todos {제출: MP3 기획서}
  201 → {"id": 1, "title": "MP3 기획서 제출", "due": "2026-08-17", "done": false}
$ POST /todos {부하 측정}
  201 → {"id": 2, "title": "부하 측정 돌리기", "due": null, "done": false}
$ GET /todos
  200 → [{"id": 1, ...}, {"id": 2, ...}]
$ PATCH /todos/1/done
  200 → {"id": 1, "title": "MP3 기획서 제출", "due": "2026-08-17", "done": true}
$ PATCH /todos/1/done (또 — 멱등)
  200 → {"id": 1, "title": "MP3 기획서 제출", "due": "2026-08-17", "done": true}
$ GET /todos?done=false
  200 → [{"id": 2, "title": "부하 측정 돌리기", "due": null, "done": false}]
$ DELETE /todos/2
  204
$ DELETE /todos/2 (또)
  404 → {"detail": "할 일이 없습니다"}
$ POST /todos {title: ""} (빈 제목)
  422 → {"detail": [{"type": "string_too_short", "loc": ["body", "title"], "msg": "String should have at least 1 character", "input": "", "ctx": {"min_length": 1}}]}
```

시퀀스 자체가 명세 표의 증명입니다: 멱등 PATCH(두 번째도 200, 같은 결과), 204의 빈 바디,
재삭제 404, 빈 제목 422까지 — **모든 행이 의도된 응답**입니다.

### Step 3. 테스트 (5~6교시)

[Day 094](day-094.md)의 형식 그대로 — FakeRepository + fixture + 상태 코드별 테스트.
최소 목록 (명세 표의 각 칸이 테스트 하나):

```
201 생성 / 422 빈 제목 / 422 오타 필드 / 200 목록 / 200 필터(done=false)
200 단건 / 404 없는 id / 200 완료 / 200 재완료(멱등!) / 204 삭제 / 404 재삭제
```

11개가 초록색이면 구현 완료입니다. **멱등 테스트**(같은 PATCH 두 번 → 둘 다 200, 상태 동일)를
빼먹지 마세요 — 오늘 설계 결정의 회귀 방지 장치입니다.

### Step 4. 상호 리뷰 (7교시)

옆 사람과 저장소를 바꿔 ③의 리뷰 기준 5축으로 심사합니다. 특히:

- **/docs만 보고** 모든 엔드포인트를 Try it out으로 사용해 보기 (문서 축)
- `500이 나는 입력 찾기` 게임 5분 — 발견하면 그 입력이 곧 상대의 버그 리포트
- service.py의 import 문 검사 — fastapi가 보이면 지적 ([Day 093](day-093.md) ⑤)

### Step 5. 커밋 (8교시)

```powershell
git add api/todo docs/todo_api.md
git commit -m "Day 095: W19 종합 — 할 일 API (명세·3계층·테스트 11개·리뷰 반영)"
```

## ⑥ 확인 문제

**Q1.** "완료 표시 PATCH는 멱등(재호출 200)"과 "리포트 중복 제출은 409"([Day 092](day-092.md)) —
같은 '중복 요청'인데 설계가 다른 이유를 조작의 성질로 설명하세요.

<details>
<summary>답 보기</summary>

완료 표시는 **상태를 특정 값으로 만드는** 조작이라 몇 번을 해도 결과가 같고(자연 멱등), 재호출을
에러로 만들면 재시도·중복 클릭마다 클라이언트가 예외 처리를 해야 해 불편만 늘어납니다. 리포트 제출은
**새 자원을 만드는** 조작이라 중복이 데이터 오염을 의미하므로 충돌(409)로 알려야 합니다.
기준은 "재호출이 해가 되는가" — 그리고 어느 쪽이든 명세에 선언하는 것이 진짜 규칙입니다.

</details>

**Q2.** 리뷰 기준의 "500이 나는 입력이 존재하는가"가 왜 최우선 심사 항목인지, 주간 체크포인트
문장과 연결해 설명하세요.

<details>
<summary>답 보기</summary>

주간 체크포인트("잘못된 입력이 500이 아니라 의도된 4xx로 나가는가")가 바로 이것입니다. 500은
"서버 잘못" 신호라 클라이언트가 대응할 수 없고, 운영자는 허위 장애 알림을 받으며, 보안상 내부 정보가
샐 수도 있습니다. 잘못된 입력의 전 경로가 4xx로 수렴한다는 것은 계약(검증·예외 번역)이 완비됐다는
가장 압축적인 증거입니다.

</details>

**Q3.** 오늘의 할 일 API에서 다음 주 추론 API로 넘어갈 때, 바뀌는 것과 바뀌지 않는 것을
구조(3계층) 기준으로 예상해 보세요.

<details>
<summary>답 보기</summary>

바뀌지 않는 것: router의 일(pydantic 계약, 4xx 번역), 테스트 형식, Depends 조립, 설정 분리.
바뀌는 것: service 자리에 **모델 추론**(predict 함수)이 들어오고, repository 자리에 **모델
로딩·보관**(시작 시 1회 로드)이 들어옵니다 — 즉 구조는 유지되고 부품만 교체됩니다.
그 부품(load_model/predict)은 이미 [Day 085](day-085.md)·[090](day-090.md)에서 만들어 뒀습니다.

</details>

## 주간 퀴즈 17 — W19 (FastAPI 기초)

<details>
<summary>1. 입력의 세 통로와 각각의 용도는?</summary>

경로(자원 식별자) · 쿼리(조회 옵션 — 필터·페이징) · 바디(생성·실행의 데이터 뭉치, POST).

</details>

<details>
<summary>2. 422와 400, 404, 409의 구분은?</summary>

422 = 요청이 계약(타입·범위·형식) 위반, 404 = 대상 자원 없음, 409 = 요청은 유효하나 상태와 충돌, 400 = 그 외 잘못된 요청.

</details>

<details>
<summary>3. /docs가 코드와 어긋날 수 없는 이유는?</summary>

사람이 쓴 문서가 아니라 코드(타입 힌트·모델·데코레이터)에서 생성된 openapi.json의 렌더링이기 때문 — 코드가 바뀌면 문서도 같이 바뀝니다.

</details>

<details>
<summary>4. model_config = {"extra": "forbid"}가 막는 사고는?</summary>

필드명 오타가 조용히 무시되는 사고 — 오타 필드를 이름까지 지목한 422로 바꿔 줍니다. 추론 API에서는 특성 누락 = 엉뚱한 예측이므로 필수.

</details>

<details>
<summary>5. response_model의 두 가지 효과는?</summary>

응답 계약 선언(내부 필드 유출의 구조적 차단)과 /docs의 정확한 응답 예시 생성.

</details>

<details>
<summary>6. 3계층 각각의 책임과 "화살표" 규칙은?</summary>

router(HTTP 번역) → service(도메인 규칙 — HTTP·SQL 모름) → repository(SQL) 한 방향 의존. 역방향 import는 순환·재사용 불능의 신호.

</details>

<details>
<summary>7. Depends의 가치가 드러나는 순간은?</summary>

테스트에서 dependency_overrides로 가짜 부품(FakeRepository)을 꽂을 때 — 조립과 사용의 분리가 교체 가능성을 만듭니다.

</details>

<details>
<summary>8. async def 안에 time.sleep/torch 추론을 넣으면 생기는 일과 안전한 기본값은?</summary>

이벤트 루프가 잠겨 서버 전체가 직렬화됩니다(실측: 동시 5요청이 1초 대신 5.1초). 블로킹 작업은 평범한 def(스레드풀행) — "모르면 def".

</details>

<details>
<summary>9. TestClient 테스트가 빠르고 독립적인 두 가지 이유는?</summary>

네트워크·프로세스 없이 앱 객체를 직접 호출, 그리고 무거운 의존성(DB)을 가짜 부품으로 교체(overrides) — 0.6초에 10개.

</details>

<details>
<summary>10. API 설계 리뷰의 3대 축은?</summary>

일관성(이름·모양의 규칙성) · 에러(전 실패가 의도된 4xx + 행동 가능한 detail) · 문서(/docs만으로 사용 가능).

</details>
