## ② 왜 필요한가

어제 파이프라인을 완성했습니다. 이제 매일 밤 데이터가 들어옵니다.
그런데 이런 것이 섞여 들어옵니다.

```json
{"stationName": "종로구", "dataTime": "2025-06-01 14:00", "pm10Value": "45"}      정상
{"stationName": "종로구", "dataTime": "2025-06-01 15:00", "pm10Value": "-"}       결측
{"stationName": "종로구", "dataTime": "2025-06-01 16:00", "pm10Value": "9999"}    센서 고장
{"stationName": "",       "dataTime": "2025-06-01 17:00", "pm10Value": "50"}      측정소명 없음
{"stationName": "종로구", "dataTime": "",                 "pm10Value": "50"}      시각 없음
```

**어제 코드는 이걸 대부분 그냥 통과시킵니다.** `9999` 는 정수라 `_to_int` 를 무사히 지나갑니다.

그리고 이런 일이 벌어집니다.

```
일평균 PM10 = (45 + 9999 + 50) / 3 = 3,364 ㎍/㎥
    →  "초미세먼지 경보 발령" 자동 알림 발송
    →  실제로는 센서 하나가 고장난 것
```

**MLOps에서 이것이 왜 특히 중요한가.**

```
잘못된 데이터  →  잘못된 모델 (학습은 정상적으로 끝남)
              →  잘못된 예측 (서비스는 정상적으로 응답함)
              →  아무도 모름  ★

Garbage In, Garbage Out. 그런데 에러는 안 납니다.
```

코드 버그는 테스트가 잡습니다. **데이터 버그는 검증이 잡습니다.**
그리고 데이터 검증이 없는 파이프라인은 **언제 틀렸는지 아무도 모릅니다.**

## ③ 개념 설명

### 데이터 품질 6차원

| 차원 | 질문 | 확인 방법 |
|---|---|---|
| **완전성** (completeness) | 있어야 할 값이 있나? | NULL 비율 · 기대 행 수 대비 |
| **유효성** (validity) | 값이 규칙에 맞나? | 타입 · 범위 · 형식 |
| **정확성** (accuracy) | 값이 사실과 맞나? | 외부 대조 (**가장 어려움**) |
| **일관성** (consistency) | 서로 모순되지 않나? | `pm25 <= pm10` · 합계 대조 |
| **유일성** (uniqueness) | 중복이 없나? | 멱등 키 기준 |
| **적시성** (timeliness) | 제때 도착했나? | 최신 데이터 시각 확인 |

> **정확성은 데이터만 봐서는 알 수 없습니다.** "PM10이 45"가 진짜인지는 현장에 가야 압니다.
> 그래서 실무에서는 **유효성·일관성·적시성**으로 정확성을 간접 추정합니다.

### 검증 규칙 7종

| 유형 | 예 | 걸리는 것 |
|---|---|---|
| **타입** | `pm10` 이 정수로 변환되나 | `"abc"` |
| **필수값** | `station_id` · `measured_at` 이 있나 | `NULL` |
| **범위** | `0 <= pm10 <= 2000` | `9999`, `-5` |
| **형식** | 이메일 · 전화번호 정규식 | `"010-1234"` |
| **참조** | `station_id` 가 실재하나 | 없는 측정소 |
| **중복** | 멱등 키 기준 유일한가 | 같은 키 2건 |
| **통계** | 평소 분포에서 벗어나나 | 갑자기 10배 |

**앞의 6개는 행 하나만 봐도 판정**할 수 있습니다. **7번째는 전체를 봐야** 합니다.

### 어디서 검증할까 — 3중 방어 ★

```
① 파이썬 (Transform)   →  행별 판정 · 사유 기록 · 격리          ← 대부분 여기
② DB 제약              →  최후의 방어선. 코드를 우회해도 막힘   (Day 038)
③ SQL 점검 쿼리        →  적재 후 통계·일관성 검사              ← 통계적 이상
```

| 층 | 잘하는 것 | 못 하는 것 |
|---|---|---|
| 파이썬 | **사유를 남기고 격리**, 유연한 규칙 | 우회 가능 (다른 스크립트가 직접 넣으면 끝) |
| DB 제약 | 절대 못 지나감 | 사유가 에러 메시지뿐, 배치가 죽음 |
| SQL 점검 | 전체 분포·시계열 이상 | 이미 들어간 뒤 |

**셋 다 필요합니다.** 하나로 충분하다고 생각하면 반드시 뚫립니다.

### 실패 처리 정책 4가지

**"불량 행을 발견했다. 그래서 어떻게 할 것인가?"** — 이것을 정하는 것이 설계입니다.

| 정책 | 동작 | 적합 |
|---|---|---|
| **① fail-fast** | 하나라도 틀리면 **배치 전체 실패** | 금융 거래·정합성이 절대적일 때 |
| **② 격리 (quarantine)** | 불량 행만 **별도 테이블로**, 나머지는 적재 | **대부분의 로그·측정 데이터** ★ |
| **③ 보정** | 규칙에 따라 값을 고쳐 적재 | 명확한 규칙이 있을 때만 |
| **④ 경고만** | 로그만 남기고 그대로 적재 | **거의 쓰지 않음** |

②를 기본으로 하되, **임계치**를 함께 둡니다.

```
불량률 < 1%    →  격리하고 계속        (평소)
불량률 1~10%   →  격리 + 경고 알림      (뭔가 이상)
불량률 > 10%   →  배치 실패            ★ 원본 형식이 바뀌었을 가능성
```

> **임계치가 없으면 "전부 불량"인 날에도 조용히 0행이 적재됩니다.**
> API 스펙이 바뀌어 모든 필드명이 달라진 날, 파이프라인은 "성공"으로 끝나고 데이터는 0행입니다.
> [Day 043](day-043.md)에서 지적한 "예외를 삼킴"과 같은 종류의 사고입니다.

### 격리 테이블

```sql
CREATE TABLE measurement_rejected (
    rejected_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    run_id      bigint      REFERENCES ingest_run(run_id),
    reason      text        NOT NULL,
    raw_record  jsonb       NOT NULL,        -- 원본을 그대로
    rejected_at timestamptz NOT NULL DEFAULT now()
);
```

| 설계 | 이유 |
|---|---|
| `raw_record jsonb` | **원본을 통째로** 남겨야 나중에 복구 가능 |
| `reason` | 무엇 때문에 걸렸는지 |
| `run_id` | 어느 실행에서 나왔는지 ([Day 043](day-043.md)) |

**격리 테이블은 쓰레기통이 아니라 대기실입니다.**
규칙이 잘못됐다면 여기서 꺼내 다시 적재합니다.

### 개인정보 — 수집하지 않는 것이 최선

| 구분 | 예 |
|---|---|
| **식별자** | 주민번호 · 이메일 · 전화번호 · 계좌번호 |
| **준식별자** | 생년월일 + 성별 + 우편번호 (**조합하면 개인 식별 가능**) |
| 민감정보 | 건강 · 종교 · 정치 성향 · 생체정보 |

> **준식별자를 조심하세요.** "생년월일 + 성별 + 우편번호" 세 개만 있으면
> 미국 인구의 87%가 유일하게 식별된다는 고전적인 연구가 있습니다.
> 이름을 지웠다고 익명이 되는 것이 아닙니다.

### 비식별화 기법

| 기법 | 예 | 되돌릴 수 있나 |
|---|---|---|
| **삭제** | 열 자체를 안 가져옴 | ❌ (**가장 안전**) |
| **마스킹** | `010-****-0001` | ❌ |
| **해시** | `sha256(값 + 솔트)` | ❌ (솔트를 모르면) |
| **일반화** | 생년월일 → 연령대, 주소 → 시·도 | ❌ |
| 가명 처리 | 실명 → `USER_0001` (매핑표 별도 보관) | ⚠️ 매핑표가 유출되면 복원 |
| 암호화 | AES | ✅ (키가 있으면) |

**해시에 솔트가 없으면 무의미합니다.**

```
sha256("010-1234-5678")  →  전화번호는 경우의 수가 10억 개
                            → 전부 해시해서 대조하면 몇 분 만에 복원 (레인보우 테이블)
sha256("010-1234-5678" + 비밀솔트)  →  솔트를 모르면 불가능
```

**솔트는 환경변수·비밀 관리 서비스에** 두고, 절대 코드나 DB에 넣지 않습니다.

### 이 과정의 원칙

| 원칙 | 실천 |
|---|---|
| **최소 수집** | 분석에 필요 없는 개인정보는 **애초에 수집하지 않는다** |
| **최소 보관** | 필요 기간이 지나면 삭제 |
| **원본과 분석본 분리** | 분석용 뷰·테이블에는 비식별 값만 |
| **MP1 데이터 선정 규칙** | **개인정보가 포함된 데이터셋은 사용 금지** ([Day 046](day-046.md)) |

## ④ 단계별 실습

### Step 1. 검증 규칙 모듈

`src/datapipe/validators.py`:

```python
"""적재 전 데이터 검증.

각 검증 함수는 (통과 여부, 사유) 를 반환합니다.
DB·네트워크에 의존하지 않으므로 단위 테스트가 쉽습니다.
"""

from __future__ import annotations

import re
from dataclasses import dataclass, field
from datetime import datetime, timedelta, timezone
from typing import Any, Callable

KST = timezone(timedelta(hours=9))

EMAIL_RE = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")
PHONE_RE = re.compile(r"^01[016789]-\d{3,4}-\d{4}$")


@dataclass
class Rule:
    """검증 규칙 하나."""
    name: str
    check: Callable[[dict], bool]
    reason: str
    severity: str = "error"          # error = 격리, warn = 통과시키되 기록


@dataclass
class ValidationResult:
    valid: list[dict] = field(default_factory=list)
    rejected: list[dict] = field(default_factory=list)   # {"record":…, "reason":…}
    warnings: list[dict] = field(default_factory=list)

    @property
    def total(self) -> int:
        return len(self.valid) + len(self.rejected)

    @property
    def reject_rate(self) -> float:
        return len(self.rejected) / self.total if self.total else 0.0


def validate(records: list[dict], rules: list[Rule]) -> ValidationResult:
    """규칙을 순서대로 적용합니다. 첫 error 에서 그 행을 격리합니다."""
    result = ValidationResult()
    for rec in records:
        failed = None
        for rule in rules:
            try:
                ok = rule.check(rec)
            except Exception:                 # 규칙 자체가 터져도 데이터 탓
                ok = False
            if ok:
                continue
            if rule.severity == "error":
                failed = rule
                break
            result.warnings.append({"record": rec, "reason": rule.reason})
        if failed:
            result.rejected.append({"record": rec, "reason": failed.reason})
        else:
            result.valid.append(rec)
    return result


# ---------- 재사용 가능한 규칙 생성기 ----------

def required(field_name: str) -> Rule:
    return Rule(
        name=f"required:{field_name}",
        check=lambda r: r.get(field_name) not in (None, "", "-"),
        reason=f"필수값 없음: {field_name}",
    )


def numeric_range(field_name: str, lo: float, hi: float, *, allow_null: bool = True) -> Rule:
    def check(r: dict) -> bool:
        v = r.get(field_name)
        if v in (None, "", "-"):
            return allow_null
        return lo <= float(v) <= hi

    return Rule(
        name=f"range:{field_name}",
        check=check,
        reason=f"범위 벗어남: {field_name} ({lo}~{hi})",
    )


def matches(field_name: str, pattern: re.Pattern, label: str) -> Rule:
    def check(r: dict) -> bool:
        v = r.get(field_name)
        return v is None or bool(pattern.match(str(v)))

    return Rule(name=f"format:{field_name}", check=check, reason=f"형식 오류: {label}")


def in_set(field_name: str, allowed: set, label: str) -> Rule:
    return Rule(
        name=f"enum:{field_name}",
        check=lambda r: r.get(field_name) in allowed,
        reason=f"허용되지 않은 값: {label}",
    )


def not_future(field_name: str, tolerance: timedelta = timedelta(hours=1)) -> Rule:
    """미래 시각을 걸러냅니다. 서버 시계 오차를 감안해 여유를 둡니다."""
    def check(r: dict) -> bool:
        v = r.get(field_name)
        if not isinstance(v, datetime):
            return True                       # 타입 검증은 다른 규칙이
        return v <= datetime.now(KST) + tolerance

    return Rule(name=f"not_future:{field_name}", check=check, reason="미래 시각")


def consistent(name: str, check: Callable[[dict], bool], reason: str) -> Rule:
    """열 사이의 일관성 검사 (예: pm25 <= pm10)."""
    return Rule(name=name, check=check, reason=reason)
```

### Step 2. 측정 데이터용 규칙 세트

`src/datapipe/rules_air.py`:

```python
"""대기질 데이터 검증 규칙.

범위 근거:
  pm10  0~2000  — 환경부 기준 '매우나쁨'이 151 이상. 2000은 황사 최악을 감안한 상한
  pm25  0~1000  — 통상 pm10 의 절반 이하
  숫자를 왜 이렇게 정했는지 반드시 기록해 두세요. 나중에 조정할 때 근거가 됩니다.
"""

from .validators import consistent, matches, not_future, numeric_range, required


def _pm25_le_pm10(r: dict) -> bool:
    """PM2.5는 PM10에 포함되므로 더 클 수 없습니다."""
    a, b = r.get("pm25Value"), r.get("pm10Value")
    if a in (None, "", "-") or b in (None, "", "-"):
        return True                              # 결측은 다른 규칙이 판정
    return float(a) <= float(b)


AIR_RULES = [
    required("stationName"),
    required("dataTime"),
    numeric_range("pm10Value", 0, 2000),
    numeric_range("pm25Value", 0, 1000),
    consistent("pm25_le_pm10", _pm25_le_pm10, "일관성 위반: pm25 > pm10"),
]
```

시험해 봅니다.

```python
>>> from datapipe.validators import validate
>>> from datapipe.rules_air import AIR_RULES
>>> records = [
...     {"stationName": "종로구", "dataTime": "2025-06-01 14:00", "pm10Value": "45",   "pm25Value": "22"},
...     {"stationName": "종로구", "dataTime": "2025-06-01 15:00", "pm10Value": "-",    "pm25Value": "25"},
...     {"stationName": "종로구", "dataTime": "2025-06-01 16:00", "pm10Value": "9999", "pm25Value": "30"},
...     {"stationName": "",       "dataTime": "2025-06-01 17:00", "pm10Value": "50",   "pm25Value": "20"},
...     {"stationName": "종로구", "dataTime": "2025-06-01 18:00", "pm10Value": "40",   "pm25Value": "60"},
... ]
>>> r = validate(records, AIR_RULES)
>>> len(r.valid), len(r.rejected)
(2, 3)
>>> for x in r.rejected:
...     print(x["reason"], "|", x["record"]["dataTime"])
...
범위 벗어남: pm10Value (0~2000) | 2025-06-01 16:00
필수값 없음: stationName | 2025-06-01 17:00
일관성 위반: pm25 > pm10 | 2025-06-01 18:00
>>> f"{r.reject_rate:.0%}"
'60%'
```

**두 번째 행(`pm10Value = "-"`)은 통과했습니다.** 결측은 불량이 아니라 **정상적인 "값 없음"** 이기 때문입니다.
`numeric_range` 의 `allow_null=True` 가 그 판단을 담고 있습니다.

**다섯 번째 행이 중요합니다.** `pm25(60) > pm10(40)` 은 **물리적으로 불가능**합니다.
값 하나만 봐서는 둘 다 정상 범위입니다. **열 사이의 관계를 봐야만** 잡히는 오류입니다.

```python
import json


def save_rejected(rejected: list[dict], *, run_id: int, source: str) -> int:
    """불량 행을 격리 테이블에 원본 그대로 저장합니다."""
    if not rejected:
        return 0
    rows = [
        (run_id, source, item["reason"], json.dumps(item["record"], ensure_ascii=False))
        for item in rejected
    ]
    with connect() as conn, conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO measurement_rejected (run_id, source, reason, raw_record) "
            "VALUES (%s, %s, %s, %s::jsonb)",
            rows,
        )
    logger.warning("격리: %d행 (run_id=%s)", len(rows), run_id)
    return len(rows)
```

> **`ensure_ascii=False`** — 한글이 `종로` 로 저장되는 것을 막습니다.
> `jsonb` 타입이라 나중에 **JSON 안의 값으로 조회**할 수 있습니다.
>
> ```sql
> SELECT raw_record->>'stationName' AS 측정소, COUNT(*)
> FROM measurement_rejected GROUP BY 1 ORDER BY 2 DESC;
> ```

### Step 4. 임계치 정책

`src/datapipe/quality.py`:

```python
"""품질 판정 정책."""

from __future__ import annotations

import logging
from dataclasses import dataclass

from .validators import ValidationResult

logger = logging.getLogger(__name__)


class QualityGateError(RuntimeError):
    """품질 기준 미달로 배치를 중단합니다."""


@dataclass(frozen=True)
class QualityPolicy:
    """불량률 임계치.

    warn_rate 0.01 / fail_rate 0.10 의 근거:
      - 평소 불량률이 0.3~0.5% 수준이므로 1%를 이상 신호로 잡음
      - 10%를 넘으면 개별 센서 문제가 아니라 원본 형식 변경일 가능성이 큼
    운영하면서 실제 분포를 보고 조정하세요.
    """
    warn_rate: float = 0.01
    fail_rate: float = 0.10
    min_rows: int = 1                 # 이보다 적으면 실패 (빈 응답 방지)


def apply_gate(result: ValidationResult, policy: QualityPolicy, *, source: str) -> None:
    rate = result.reject_rate

    if result.total < policy.min_rows:
        raise QualityGateError(
            f"[{source}] 수집 행이 너무 적습니다: {result.total}행 "
            f"(최소 {policy.min_rows}행)"
        )

    if rate >= policy.fail_rate:
        top = _top_reasons(result)
        raise QualityGateError(
            f"[{source}] 불량률 {rate:.1%} ≥ 임계치 {policy.fail_rate:.0%}. "
            f"주요 사유: {top}"
        )

    if rate >= policy.warn_rate:
        logger.warning("[%s] 불량률 %.1f%% — 주요 사유: %s",
                       source, rate * 100, _top_reasons(result))
    else:
        logger.info("[%s] 품질 정상 — 유효 %d행 · 격리 %d행 (%.2f%%)",
                    source, len(result.valid), len(result.rejected), rate * 100)


def _top_reasons(result: ValidationResult, n: int = 3) -> str:
    from collections import Counter
    counts = Counter(item["reason"] for item in result.rejected)
    return ", ".join(f"{reason}({cnt})" for reason, cnt in counts.most_common(n))
```

`stages/load_db.py` 의 `run()` 을 고칩니다.

```python
class LoadDBStage(Stage):
    name = "load_db"

    def __init__(self, policy: QualityPolicy | None = None):
        self.policy = policy or QualityPolicy()

    def run(self, records: list[dict], ctx) -> dict:
        # ① 검증
        result = validate(records, AIR_RULES)

        # ② 격리 (게이트보다 먼저 — 실패해도 증거는 남겨야 합니다)
        save_rejected(result.rejected, run_id=ctx.run_id, source=ctx.source)

        # ③ 품질 게이트
        apply_gate(result, self.policy, source=ctx.source)

        # ④ 변환 + 적재
        station_map = load_station_map()
        rows, unmapped = transform(result.valid, station_map)
        save_rejected(unmapped, run_id=ctx.run_id, source=ctx.source)

        affected = staged_upsert(
            rows, table="measurement", columns=MEASUREMENT_COLUMNS,
            conflict_keys=MEASUREMENT_KEYS, update_columns=("pm10", "pm25"),
        )
        return {
            "loaded": affected,
            "rejected": len(result.rejected) + len(unmapped),
            "reject_rate": result.reject_rate,
        }
```

**① 완전성 — 시간 구멍 찾기**

```sql
WITH expected AS (
    SELECT s.station_id, g.hour
    FROM station s
    CROSS JOIN generate_series(
```

**③ 통계적 이상 — 평소와 다른 값**

```sql
WITH baseline AS (
    SELECT station_id,
           AVG(pm10)    AS avg_pm10,
           STDDEV(pm10) AS sd_pm10
    FROM measurement
    WHERE measured_at >= now() - interval '30 days'
      AND measured_at <  now() - interval '1 day'
      AND pm10 IS NOT NULL
    GROUP BY station_id
    HAVING COUNT(*) >= 100          -- 표본이 적으면 통계가 무의미
),
recent AS (
    SELECT station_id, AVG(pm10) AS today_pm10, COUNT(*) AS n
    FROM measurement
    WHERE measured_at >= now() - interval '1 day' AND pm10 IS NOT NULL
    GROUP BY station_id
)
SELECT s.name                                        AS 측정소,
       ROUND(b.avg_pm10, 1)                          AS 평소평균,
       ROUND(r.today_pm10, 1)                        AS 오늘평균,
       ROUND((r.today_pm10 - b.avg_pm10) / NULLIF(b.sd_pm10, 0), 2) AS z점수
FROM recent r
JOIN baseline b ON r.station_id = b.station_id
JOIN station  s ON s.station_id = r.station_id
WHERE ABS(r.today_pm10 - b.avg_pm10) > 3 * b.sd_pm10
ORDER BY ABS(z점수) DESC;
```

**z점수가 ±3을 넘으면** 평소 분포에서 크게 벗어난 것입니다.
진짜 황사일 수도, 센서 고장일 수도 있습니다. **자동으로 판단하지 말고 사람에게 알립니다.**

> **`NULLIF(b.sd_pm10, 0)`** — 표준편차가 0이면(값이 전부 같으면) 0으로 나누게 됩니다.
> 센서가 고장나 같은 값만 계속 보내는 경우가 정확히 그렇습니다. **이상을 찾는 쿼리가 이상 때문에 죽지 않도록** 방어합니다.
>
> 이 z점수 계산은 **W27의 데이터 드리프트 감지**와 완전히 같은 발상입니다.
> 모델 입력 분포가 학습 때와 달라지면 성능이 조용히 떨어지는데, 그것을 이렇게 잡습니다.

| 있는 것 | 없는 것 | 결과 |
|---|---|---|
| 검증만 | 임계치 | 전부 불량인 날에도 조용히 0행 적재 |
| 임계치만 | 격리 | 실패했는데 **왜 실패했는지 알 수 없음** |

**둘 다 필요합니다.** 그리고 **격리를 게이트보다 먼저** 실행해야 증거가 남습니다.

### 격리 테이블에 원본을 안 남김

```python
save_rejected([{"reason": r["reason"]} for r in rejected])   # ❌ 사유만
```

**결과** — "8월 11일에 19건 실패"는 알지만 **무엇이 실패했는지 모릅니다.** 복구도 불가능합니다.
**해결** — `raw_record jsonb` 로 **원본을 통째로**. 용량은 걱정할 수준이 아닙니다.

### 임계치를 근거 없이 정함

```python
fail_rate: float = 0.05     # 왜 5%?
```

**해결** — 며칠 운영해 **실제 불량률 분포를 보고** 정합니다. 그리고 **근거를 주석으로** 남기세요.

```sql
SELECT rejected_at::date AS 날짜,
       COUNT(*) AS 격리건수,
       ROUND(COUNT(*) * 100.0 / 2412, 2) AS 불량률
FROM measurement_rejected
GROUP BY 1 ORDER BY 1 DESC LIMIT 14;
```

### 이름만 지우고 "익명화했다"고 함

```sql
SELECT city, grade, joined_at, 구매액 FROM ...    -- 이름 없음
```

**문제** — `(인천, 등급없음, 2024-11-12)` 조합이 유일하면 **누구인지 특정됩니다.**
외부 데이터(회원 가입 이벤트 명단 등)와 결합하면 더 쉽습니다.
**해결** — 준식별자를 일반화하고 **k-익명성을 확인**합니다.

### 솔트 없이 해시

```sql
encode(digest(phone, 'sha256'), 'hex')      -- ❌
```

**문제** — 전화번호는 경우의 수가 10억 개뿐입니다. 전부 해시해 대조하면 **몇 분 만에 복원**됩니다.
**해결** — 비밀 솔트를 붙이고, 솔트는 환경변수·비밀 관리 서비스에.

### 검증 규칙에서 예외가 나 배치가 죽음

```python
lambda r: float(r["pm10Value"]) <= 2000     # 값이 'abc' 면 ValueError
```

**해결** — `validate()` 에서 규칙 실행을 `try` 로 감싸고, **예외가 나면 그 행을 불량으로** 처리합니다.
위 `validators.py` 가 이미 그렇게 돼 있습니다. **검증기가 데이터 때문에 죽으면 안 됩니다.**

### 통계 검사에 표본 수 조건이 없음

```sql
SELECT ... WHERE ABS(오늘 - 평균) > 3 * 표준편차     -- 표본 3개짜리 측정소도 포함
```

**결과** — 새로 설치된 측정소가 매일 "이상"으로 잡혀 알림이 울립니다.
**알림이 너무 자주 울리면 사람들은 알림을 끕니다.** 그러면 진짜 이상도 놓칩니다.
**해결** — `HAVING COUNT(*) >= 100` 같은 최소 표본 조건을 겁니다.

## ⑥ 확인 문제

**1.** 아래 다섯 행 중 격리해야 할 것과 통과시켜야 할 것을 구분하고, 각각의 근거를 쓰세요.

```
① {"stationName": "종로구", "dataTime": "2025-06-01 14:00", "pm10Value": "45",   "pm25Value": "22"}
② {"stationName": "종로구", "dataTime": "2025-06-01 15:00", "pm10Value": "-",    "pm25Value": "-"}
③ {"stationName": "종로구", "dataTime": "2025-06-01 16:00", "pm10Value": "0",    "pm25Value": "0"}
④ {"stationName": "종로구", "dataTime": "2026-12-01 10:00", "pm10Value": "40",   "pm25Value": "20"}
⑤ {"stationName": "종로구", "dataTime": "2025-06-01 18:00", "pm10Value": "40",   "pm25Value": "45"}
```

<details>
<summary>답 보기</summary>

| # | 판정 | 근거 |
|---|---|---|
| ① | **통과** | 모든 규칙 만족 |
| ② | **통과** | `'-'` 는 결측. **불량이 아니라 "값 없음"** → `NULL` 로 저장. 단 결측률은 별도 감시 |
| ③ | **통과 (단, 경고)** | `0`은 유효 범위. 다만 **PM10이 정확히 0인 것은 현실에서 드묾** → `severity="warn"` 규칙으로 기록만 |
| ④ | **격리** | **미래 시각.** 오늘이 2026-08-12인데 12월 데이터. `not_future` 규칙 |
| ⑤ | **격리** | `pm25(45) > pm10(40)` — PM2.5는 PM10에 포함되므로 **물리적으로 불가능** |

**②와 ③이 판단이 갈리는 지점입니다.**

②를 격리하면 정상적인 결측이 전부 불량으로 잡혀 불량률이 폭증합니다.
③은 규칙상 유효하지만 실제로는 센서 고장(0만 계속 출력)일 수 있어, **경고로 기록하고 통과**시킨 뒤
"연속 24시간 0" 같은 **패턴을 SQL로 잡는** 것이 맞습니다.

```sql
-- 연속으로 같은 값만 보내는 측정소 (센서 고착 의심)
SELECT station_id, COUNT(DISTINCT pm10) AS 값종류수, COUNT(*) AS 측정수
FROM measurement
WHERE measured_at >= now() - interval '1 day' AND pm10 IS NOT NULL
GROUP BY station_id
HAVING COUNT(DISTINCT pm10) <= 2 AND COUNT(*) >= 20;
```

**⑤가 오늘의 핵심입니다.** 값 하나씩 보면 둘 다 정상 범위입니다.
**열 사이의 관계를 검사해야만** 잡힙니다. 도메인 지식이 있어야 만들 수 있는 규칙이고,
그래서 **데이터 엔지니어가 도메인을 알아야 합니다.**
</details>

**2.** 품질 게이트를 통과했지만 실제로는 데이터가 잘못된 경우를 두 가지 들고, 각각을 어떻게 잡을지 쓰세요.

<details>
<summary>답 보기</summary>

**행별 검증으로는 절대 못 잡는 두 가지입니다.**

**① 완전성 실패 — 데이터가 "덜" 들어옴**

```
평소: 측정소 50개 × 24시간 = 1,200행/일
오늘: 측정소 12개 × 24시간 =   288행/일   ← 288행 모두 유효. 불량률 0%
```

**게이트를 통과합니다.** 들어온 행은 전부 정상이니까요.
하지만 **측정소 38개가 통째로 빠졌습니다.**

**잡는 법** — 기대 행 수와 비교합니다.

```python
expected = len(station_map) * hours_in_window
if result.valid_count < expected * 0.8:
    raise QualityGateError(f"기대 {expected}행의 80% 미만: {result.valid_count}행")
```

또는 SQL로 (Step 7의 "시간 구멍 찾기").

**② 정확성 실패 — 값 전체가 이동함**

```
센서가 교정 오류로 모든 값에 +50을 더해 보냄
  →  45가 95로, 30이 80으로. 전부 유효 범위(0~2000) 안
  →  불량률 0%.  게이트 통과
  →  "전국 미세먼지 급증" 보고서 작성  ★
```

**잡는 법** — **분포를 비교**합니다 (Step 7의 z점수).

```sql
-- 어제 대비 평균이 통계적으로 유의하게 이동했는지
WITH b AS (SELECT AVG(pm10) m, STDDEV(pm10) s FROM measurement
           WHERE measured_at >= now() - interval '30 days'
             AND measured_at < now() - interval '1 day'),
     t AS (SELECT AVG(pm10) m FROM measurement
           WHERE measured_at >= now() - interval '1 day')
SELECT ROUND(b.m,1) AS 평소, ROUND(t.m,1) AS 오늘,
       ROUND((t.m - b.m) / NULLIF(b.s,0), 2) AS z
FROM b, t;
```

**정리 — 검증의 층위**

| 층 | 잡는 것 | 도구 |
|---|---|---|
| **행 단위** | 타입·범위·형식·일관성 | 파이썬 규칙 · DB `CHECK` |
| **배치 단위** | 행 수·불량률·결측률 | 품질 게이트 |
| **시계열 단위** | 분포 이동·구멍·지연 | SQL 점검 쿼리 |

**세 층이 다 필요합니다.** 그리고 세 번째가 가장 늦게 만들어지고, 가장 큰 사고를 막습니다.
W27의 **모델 모니터링**이 정확히 이 세 번째 층입니다.
</details>

**3.** 분석팀이 "고객 이메일이 필요하다"고 요청합니다. 어떻게 대응하겠습니까?

<details>
<summary>답 보기</summary>

**"무엇을 하려는지"를 먼저 묻습니다.** 목적에 따라 답이 완전히 달라집니다.

| 목적 | 대응 | 이메일 필요? |
|---|---|---|
| **동일인의 주문 묶기** | `customer_id` 를 쓰면 됩니다 | ❌ |
| **여러 시스템 데이터 결합** | **솔트 해시**를 양쪽에 적용해 조인 키로 | ❌ (해시로 충분) |
| **이메일 도메인별 분석** | 도메인만 추출해 제공 | ❌ |
| **마케팅 메일 발송** | 분석 시스템이 아니라 **발송 시스템**의 일 | 분리 |
| **고객 문의 응대** | 담당자가 운영 시스템에서 개별 조회 | 별도 권한 |

**대부분의 요청은 이메일 없이 해결됩니다.**

```sql
-- 도메인별 분석 — 이메일 원본 없이
CREATE VIEW v_customer_domain AS
SELECT customer_id,
       split_part(email, '@', 2) AS email_domain,
       city, grade
FROM customers;
```

```
shop=# SELECT split_part(email,'@',2) AS 도메인, COUNT(*) FROM customers GROUP BY 1;
   도메인    | count
-------------+-------
 example.com |    12
(1 row)
```

**그래도 원본이 필요하다면**

1. **목적과 보관 기간을 문서로** 받습니다 (어디에 쓰고, 언제 지울지)
2. **최소 범위만** 제공 (전체가 아니라 필요한 고객군만)
3. **접근 로그**를 남깁니다
4. **분리된 환경**에서만 조회 (다운로드 금지)
5. 기간이 끝나면 **삭제를 확인**합니다

**엔지니어로서 가져야 할 태도**

> **"요청받았으니 준다"가 아니라, "목적을 달성하는 가장 덜 위험한 방법"을 제안합니다.**

개인정보 유출 사고는 대부분 **악의가 아니라 편의** 때문에 일어납니다.
"일단 전체 다 받아서 로컬에서 보자"가 노트북 분실로 이어집니다.

**이 과정의 규칙** — MP1·최종 프로젝트에서 **개인정보가 포함된 데이터셋은 사용 금지**입니다
([Day 046](day-046.md)). 공공데이터포털의 집계 통계나 Kaggle의 익명화된 데이터를 쓰세요.
포트폴리오 저장소는 **공개**이므로, 실수로 개인정보를 커밋하면 되돌릴 수 없습니다.
</details>

## 오늘의 정리

| 개념 | 요약 |
|---|---|
| 품질 6차원 | 완전성 · 유효성 · 정확성 · 일관성 · 유일성 · 적시성 |
| 검증 7종 | 타입 · 필수값 · 범위 · 형식 · 참조 · 중복 · **통계** |
| 3중 방어 | ① 파이썬(사유·격리) ② DB 제약(우회 불가) ③ SQL 점검(분포·구멍) |
| 실패 정책 | fail-fast / **격리** / 보정 / 경고 |
| 임계치 | `warn` 1% · `fail` 10% — **근거를 기록하고 운영하며 조정** |
| 격리 테이블 | 사유 + **원본 `jsonb`** + `run_id` → 쓰레기통이 아니라 **대기실** |

| 개인정보 | |
|---|---|
| 식별자 / 준식별자 | 이메일·전화 / **생년월일+성별+지역 조합** |
| 기법 | 삭제 > 일반화 > 해시(**솔트 필수**) > 마스킹 |
| k-익명성 | 같은 속성 조합이 최소 k명 |
| 원칙 | **최소 수집 · 최소 보관 · 분석용 뷰로 분리** |

| 함정 | 방어 |
|---|---|
| 결측을 불량으로 | 결측은 통과 + 결측률 별도 감시 |
| 격리를 게이트보다 나중에 | **증거를 먼저 남긴다** |
| 행 수 검증 없음 | 유효한 288행이 통과 (평소 1,200행) |
| 솔트 없는 해시 | 몇 분 만에 복원 가능 |
| 표본 수 조건 없는 통계 검사 | 알림 피로 → 진짜 이상도 놓침 |

**오늘의 습관** — 검증 규칙을 하나 만들 때마다 **"이 규칙에 걸리는 실제 데이터"를 하나 적어 두세요.**
걸리는 데이터를 상상할 수 없는 규칙은 대개 필요 없는 규칙입니다.

**과제 — 검증 규칙 5종 추가**

1. `src/datapipe/validators.py` · `rules_*.py` 완성
   - **본인 데이터에 맞는 규칙 5종 이상** (범위 · 형식 · 일관성 · 시각 · 열거값)
   - 각 규칙에 **왜 그 값·조건인지 근거를 주석으로**
2. `src/datapipe/quality.py` — 임계치 정책 + 게이트
   - `min_rows` 를 포함해 **완전성 검사**도 넣으세요 (기대 행 수의 80% 등)
3. `sql/migrations/` — 격리 테이블 + `CHECK` 제약 (2중 방어)
4. `sql/analysis/07_quality.sql` — 품질 리포트 쿼리 3개
   - 사유별 추이 · 결측률 · **시간 구멍 찾기**
5. `tests/test_validators.py` — 규칙마다 **통과 케이스와 격리 케이스를 각각** 테스트
6. `docs/privacy.md` — 사용 데이터에 개인정보가 있는지 점검한 결과
   - 없으면 "없음"과 **그 근거**(어떤 열을 확인했는지)를 적으세요. 이것도 산출물입니다.

**5번이 중요합니다.** 검증 규칙은 **틀리기 쉽고, 틀려도 조용합니다.**
규칙을 테스트하지 않으면 "검증하고 있다는 착각"만 남습니다.
