## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 단건 `INSERT` · `executemany` · 다중 `VALUES` · `COPY` 의 성능 차이를 **측정**하고 설명할 수 있다.
- `ON CONFLICT` 로 **몇 번을 실행해도 안전한(멱등) 적재**를 구현할 수 있다.
- 스테이징 테이블 패턴으로 **대량 upsert** 를 처리할 수 있다.
- 배치 크기·인덱스·`ANALYZE` 를 조절해 적재 시간을 줄일 수 있다.

## ② 왜 필요한가

어제 만든 `INSERT` 함수로 10만 행을 넣어 봅시다.

```python
for row in rows:                          # 100,000번
    db.execute("INSERT INTO measurement ... VALUES (%s, %s, %s)", row)
```

**80초쯤 걸립니다.** 같은 데이터를 `COPY` 로 넣으면 **0.4초**입니다. **200배**입니다.

매일 밤 도는 배치라면 80초도 참을 만합니다. 그런데 실무 데이터는 이렇게 늘어납니다.

```
10만 행    →   80초       참을 만함
1000만 행  →   2시간 13분  ★ 새벽 배치가 아침까지 안 끝남
            COPY 로는 40초
```

그리고 **두 번째 문제**가 더 중요합니다.

```
어젯밤 배치가 8만 행에서 네트워크 오류로 죽었습니다. 다시 돌리면?
  → 앞의 8만 행이 또 들어갑니다.  ★ 중복
```

[Day 039](day-039.md)에서 `UNIQUE (station_id, measured_at)` 를 건 이유가 이것입니다.
하지만 제약만 있으면 **두 번째 실행이 에러로 죽습니다.**
"이미 있으면 무시하거나 갱신"하도록 만드는 것이 오늘의 `ON CONFLICT` 이고,
이것이 [Day 043](day-043.md) **멱등성**의 실체입니다.

## ③ 개념 설명

### 왜 단건 `INSERT` 가 느린가

```
파이썬                        PostgreSQL
  │  INSERT 1건 ────────────▶  │  파싱 → 계획 → 실행 → 인덱스 갱신 → WAL 기록
  │  ◀──────────── 응답        │
  │  INSERT 1건 ────────────▶  │   ... 100,000번 반복
```

| 비용 | 설명 |
|---|---|
| **왕복(round trip)** | 명령마다 네트워크를 오감. 0.1ms여도 10만 번이면 10초 |
| **파싱·계획** | 같은 SQL을 10만 번 다시 해석 |
| **트랜잭션** | 매번 커밋하면 디스크 동기화(fsync)가 10만 번 |

**이 셋을 각각 줄이는 것이 오늘의 기법**입니다.

### 적재 방법 4가지

| 방법 | 왕복 | 파싱 | 특징 |
|---|---|---|---|
| ① 단건 `INSERT` + 매번 커밋 | 10만 | 10만 | **최악** |
| ② 단건 `INSERT` + 한 번 커밋 | 10만 | 1(준비된 문장) | 커밋만 묶어도 크게 개선 |
| ③ `executemany` | 적음 | 1 | psycopg 3가 내부적으로 묶어 보냄 |
| ④ 다중 `VALUES` (1000행씩) | 100 | 100 | `ON CONFLICT` 와 함께 쓰기 좋음 |
| ⑤ **`COPY`** | 스트림 1개 | 없음 | **가장 빠름.** 단 `ON CONFLICT` 못 씀 |

```sql
-- ④ 다중 VALUES
INSERT INTO t (a, b) VALUES (1,'x'), (2,'y'), (3,'z'), ... ;

-- ⑤ COPY (SQL이 아니라 스트림 프로토콜)
COPY t (a, b) FROM STDIN;
```

**`COPY` 가 압도적인 이유** — SQL 파서를 아예 거치지 않고 **데이터를 스트림으로 밀어 넣습니다.**
PostgreSQL 백업·복원(`pg_dump`)도 내부적으로 `COPY` 를 씁니다.

### `COPY` 의 한계

| 못 하는 것 | 대안 |
|---|---|
| `ON CONFLICT` (중복 처리) | **스테이징 테이블 패턴** (아래) |
| 행별 오류 건너뛰기 | 한 행이라도 틀리면 **전체 실패** → 사전 검증 ([Day 044](day-044.md)) |
| 값 변환 | 파이썬 쪽에서 미리 변환 |

### `ON CONFLICT` — upsert

```sql
INSERT INTO measurement (station_id, measured_at, pm10)
VALUES (1, '2025-06-01 14:00+09', 45)
ON CONFLICT (station_id, measured_at) DO NOTHING;          -- ① 있으면 무시

INSERT INTO measurement (station_id, measured_at, pm10)
VALUES (1, '2025-06-01 14:00+09', 45)
ON CONFLICT (station_id, measured_at)
DO UPDATE SET pm10 = EXCLUDED.pm10,                        -- ② 있으면 갱신
              ingested_at = now();
```

| 요소 | 뜻 |
|---|---|
| `ON CONFLICT (열들)` | **어떤 `UNIQUE` 제약과 충돌했을 때**인지 지정 |
| `EXCLUDED` | **넣으려다 충돌한 새 행**을 가리키는 가상 테이블 |
| `DO NOTHING` | 건너뜀 (기존 값 유지) |
| `DO UPDATE SET ...` | 기존 행을 갱신 |

> **`ON CONFLICT` 를 쓰려면 그 열 조합에 `UNIQUE` 제약이 반드시 있어야 합니다.**
> 없으면 `there is no unique or exclusion constraint matching the ON CONFLICT specification` 에러가 납니다.
> **제약 설계가 곧 멱등성 설계**라는 [Day 039](day-039.md)의 결론이 여기서 코드가 됩니다.

### `DO NOTHING` vs `DO UPDATE` — 무엇을 고를까

| 상황 | 선택 |
|---|---|
| 과거 데이터는 절대 안 바뀐다 (측정값·거래 내역) | **`DO NOTHING`** — 빠르고 안전 |
| 원본이 정정될 수 있다 (수정 공시·재집계) | **`DO UPDATE`** |
| 최신 것만 남기고 싶다 | `DO UPDATE ... WHERE EXCLUDED.updated_at > t.updated_at` |

`DO UPDATE` 에도 조건을 걸 수 있습니다. **오래된 데이터가 최신 데이터를 덮어쓰는 사고**를 막습니다.

```sql
ON CONFLICT (station_id, measured_at) DO UPDATE
SET pm10 = EXCLUDED.pm10, ingested_at = EXCLUDED.ingested_at
WHERE measurement.ingested_at < EXCLUDED.ingested_at;      -- 더 새 것일 때만
```

### 스테이징 테이블 패턴 ★

`COPY` 의 속도와 `ON CONFLICT` 의 안전을 **둘 다** 얻는 방법입니다.

```
① 임시 테이블 생성  →  ② COPY 로 통째로 밀어넣기 (빠름)
                              ↓
                    ③ 임시 테이블에서 중복 제거
                              ↓
        ④ INSERT ... SELECT ... ON CONFLICT ... (본 테이블로)
                              ↓
                    ⑤ 임시 테이블 자동 삭제
```

```sql
CREATE TEMP TABLE measurement_stg (LIKE measurement INCLUDING DEFAULTS)
ON COMMIT DROP;

COPY measurement_stg (station_id, measured_at, pm10, pm25) FROM STDIN;

INSERT INTO measurement (station_id, measured_at, pm10, pm25)
SELECT DISTINCT ON (station_id, measured_at) station_id, measured_at, pm10, pm25
FROM measurement_stg
ORDER BY station_id, measured_at
ON CONFLICT (station_id, measured_at) DO UPDATE
SET pm10 = EXCLUDED.pm10, pm25 = EXCLUDED.pm25;
```

**`DISTINCT ON` 이 왜 필요한가** — **한 배치 안에 같은 키가 두 번 있으면 `ON CONFLICT` 가 실패합니다.**

```
ERROR:  ON CONFLICT DO UPDATE command cannot affect row a second time
HINT:  Ensure that no rows proposed for insertion within the same command
       have duplicate constrained values.
```

`ON CONFLICT` 는 **이미 테이블에 있는 행과의 충돌**만 처리합니다.
**같은 `INSERT` 안의 중복은 처리하지 못합니다.** 그래서 넣기 전에 걸러야 합니다.

`DISTINCT ON (키) ... ORDER BY 키, 우선순위열 DESC` 는 **키별로 첫 행 하나만** 남기는 PostgreSQL 문법입니다.

### 배치 크기

```
너무 작음 (10)    →  왕복이 많아 느림
너무 큼 (100만)   →  메모리 부담 · 실패 시 되돌릴 양이 큼 · 잠금 시간 김
적당 (1천~1만)    →  대개 여기
```

**정답은 측정입니다.** 다만 **"실패했을 때 몇 행을 다시 해야 하는가"** 도 함께 고려하세요.

### Step 2. 시험용 데이터 만들기

`make_data.py`:

```python
"""적재 실험용 CSV 생성 — 측정소 50개 × 2000시간 = 100,000행."""

import csv
from datetime import datetime, timedelta, timezone

KST = timezone(timedelta(hours=9))
START = datetime(2025, 1, 1, tzinfo=KST)
STATIONS = 50
HOURS = 2000


def main() -> None:
    with open("measurements.csv", "w", newline="", encoding="utf-8") as f:
        w = csv.writer(f)
        w.writerow(["station_id", "measured_at", "pm10", "pm25"])
        for h in range(HOURS):
            ts = (START + timedelta(hours=h)).isoformat()
            for sid in range(1, STATIONS + 1):
                # 값은 재현 가능하도록 규칙적으로 생성 (난수 아님)
                pm10 = 20 + (h * 7 + sid * 13) % 120
                pm25 = 10 + (h * 3 + sid * 5) % 60
                w.writerow([sid, ts, pm10, pm25])
    print(f"생성: {STATIONS * HOURS:,}행")


if __name__ == "__main__":
    main()
```

### Step 3. 방법별 성능 측정 ★

`load_bench.py`:

```python
"""적재 방법별 성능 비교."""

import csv
import io
import time
from contextlib import contextmanager

import psycopg
from dotenv import load_dotenv

from datapipe.db import get_conninfo

load_dotenv()


def read_rows() -> list[tuple]:
    with open("measurements.csv", encoding="utf-8") as f:
        r = csv.reader(f)
        next(r)                                   # 헤더 건너뛰기
        return [(int(a), b, int(c), int(d)) for a, b, c, d in r]


@contextmanager
def timer(label: str):
    t0 = time.perf_counter()
    yield
    print(f"{label:<28} {time.perf_counter() - t0:7.2f} 초")


def truncate(conn) -> None:
    with conn.cursor() as cur:
        cur.execute("TRUNCATE measurement RESTART IDENTITY")
    conn.commit()


SQL = "INSERT INTO measurement (station_id, measured_at, pm10, pm25) VALUES (%s, %s, %s, %s)"


def main() -> None:
    rows = read_rows()
    print(f"대상: {len(rows):,}행\n")

    with psycopg.connect(get_conninfo()) as conn:

        # ① 단건 INSERT + 매번 커밋 (1만 행만 — 전체는 너무 오래 걸립니다)
        truncate(conn)
        with timer("① 단건+매번커밋 (1만행)"):
            with conn.cursor() as cur:
                for row in rows[:10_000]:
                    cur.execute(SQL, row)
                    conn.commit()

        # ② 단건 INSERT + 한 번 커밋
        truncate(conn)
        with timer("② 단건+한번커밋"):
            with conn.cursor() as cur:
                for row in rows:
                    cur.execute(SQL, row)
            conn.commit()

        # ③ executemany
        truncate(conn)
        with timer("③ executemany"):
            with conn.cursor() as cur:
                cur.executemany(SQL, rows)
            conn.commit()

        # ④ 다중 VALUES (1000행씩)
        truncate(conn)
        with timer("④ 다중 VALUES (1000)"):
            with conn.cursor() as cur:
                for i in range(0, len(rows), 1000):
                    chunk = rows[i:i + 1000]
                    values = b",".join(
                        cur.mogrify("(%s,%s,%s,%s)", r) for r in chunk
                    ).decode()
                    cur.execute(
                        "INSERT INTO measurement "
                        "(station_id, measured_at, pm10, pm25) VALUES " + values
                    )
            conn.commit()

        # ⑤ COPY
        truncate(conn)
        with timer("⑤ COPY"):
            with conn.cursor() as cur:
                with cur.copy(
                    "COPY measurement (station_id, measured_at, pm10, pm25) FROM STDIN"
                ) as cp:
                    for row in rows:
                        cp.write_row(row)
            conn.commit()

        with conn.cursor() as cur:
            cur.execute("SELECT COUNT(*) FROM measurement")
            print(f"\n최종 행 수: {cur.fetchone()[0]:,}")


if __name__ == "__main__":
    main()
```

② 단건+한번커밋                 11.37 초

**①은 1만 행 기준**입니다. 10만 행으로 환산하면 **약 82초**입니다.

| 방법 | 10만 행 환산 | ① 대비 |
|---|---|---|
| ① 단건+매번커밋 | ~82 초 | 1× |
| ② 단건+한번커밋 | 11.4 초 | **7×** |
| ③ executemany | 6.8 초 | 12× |
| ④ 다중 VALUES | 2.1 초 | 39× |
| ⑤ **COPY** | **0.4 초** | **약 215×** |

> **숫자는 환경마다 다릅니다.** 중요한 것은 **순서와 대략의 배수**입니다.
> ①→② 만으로도 7배가 빨라진 것에 주목하세요. **"커밋을 묶는다"** 는 가장 싼 최적화입니다.

**커밋을 매번 하면 왜 이렇게 느린가** — 커밋마다 **디스크에 로그를 강제로 써야(fsync)** 하기 때문입니다.
디스크 동기화는 메모리 작업보다 수천 배 느립니다.

### Step 4. `COPY` 자세히 보기

`COPY` 는 두 가지 방식으로 쓸 수 있습니다.

```python
# ① 행 단위 — 파이썬 객체를 그대로 (타입 변환은 psycopg가)
with cur.copy("COPY measurement (station_id, measured_at, pm10, pm25) FROM STDIN") as cp:
    for row in rows:
        cp.write_row(row)

# ② CSV 파일을 통째로 (가장 빠름 — 파싱조차 생략)
with open("measurements.csv", "rb") as f:
    with cur.copy(
        "COPY measurement (station_id, measured_at, pm10, pm25) "
        "FROM STDIN WITH (FORMAT csv, HEADER true)"
    ) as cp:
        while chunk := f.read(64 * 1024):
            cp.write(chunk)
```

**②가 더 빠르지만, 파이썬에서 값을 검증·변환할 기회가 없습니다.**
[Day 044](day-044.md)에서 검증을 넣을 것이므로 이 과정에서는 **①을 기본**으로 씁니다.

`COPY` 는 **한 행만 틀려도 전체가 실패**합니다.

```python
>>> rows_bad = rows[:100] + [(999, "2025-01-01T00:00:00+09:00", 50, 20)]   # 999번 측정소는 없음
>>> # ... COPY 실행 ...
psycopg.errors.ForeignKeyViolation: insert or update on table "measurement"
violates foreign key constraint "measurement_station_id_fkey"
DETAIL:  Key (station_id)=(999) is not present in table "station".
CONTEXT:  COPY measurement, line 101
```

**`line 101` 이 몇 번째 줄인지 알려 줍니다.** 그리고 **앞의 100행도 들어가지 않았습니다** (원자성).

### Step 5. 멱등성 실험 — 두 번 돌리면?

`COPY` 로 넣은 상태에서 **한 번 더** 넣어 봅니다.

```python
>>> # 같은 데이터를 COPY 로 다시 적재
psycopg.errors.UniqueViolation: duplicate key value violates unique constraint
"measurement_station_id_measured_at_key"
DETAIL:  Key (station_id, measured_at)=(1, 2025-01-01 00:00:00+09) already exists.
CONTEXT:  COPY measurement, line 1
```

**`UNIQUE` 제약이 중복을 막았습니다.** 데이터는 안전하지만 **배치가 죽습니다.**

제약이 없었다면 어땠을까요? 확인해 봅니다.

```
airquality=# CREATE TABLE measurement_noconstraint (LIKE measurement EXCLUDING CONSTRAINTS
airquality(#     EXCLUDING INDEXES);
CREATE TABLE
```

### Step 6. `ON CONFLICT` 로 멱등 적재 만들기 ★

`upsert.py`:

```python
"""멱등 적재 — 몇 번을 실행해도 결과가 같습니다."""

import psycopg
from dotenv import load_dotenv

from datapipe.db import get_conninfo
from load_bench import read_rows

load_dotenv()

UPSERT_SQL = """
INSERT INTO measurement (station_id, measured_at, pm10, pm25, ingested_at)
VALUES (%s, %s, %s, %s, now())
ON CONFLICT (station_id, measured_at) DO UPDATE
SET pm10 = EXCLUDED.pm10,
    pm25 = EXCLUDED.pm25,
    ingested_at = EXCLUDED.ingested_at
"""


def upsert(rows: list[tuple], batch_size: int = 1000) -> int:
    total = 0
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            for i in range(0, len(rows), batch_size):
                chunk = rows[i:i + batch_size]
                cur.executemany(UPSERT_SQL, chunk)
                total += len(chunk)
        conn.commit()
    return total


if __name__ == "__main__":
    rows = read_rows()
    for run in (1, 2, 3):
        n = upsert(rows)
        with psycopg.connect(get_conninfo()) as conn, conn.cursor() as cur:
            cur.execute("SELECT COUNT(*) FROM measurement")
            print(f"{run}회차 적재 {n:,}행 → 테이블 총 {cur.fetchone()[0]:,}행")
```

```powershell
(venv) $ python upsert.py

2회차 적재 100,000행 → 테이블 총 100,000행
3회차 적재 100,000행 → 테이블 총 100,000행
```

**세 번 돌려도 10만 행 그대로입니다. 이것이 멱등성입니다.**

값이 바뀐 경우도 확인해 봅니다.

```
airquality=# SELECT pm10, pm25, ingested_at FROM measurement
airquality-# WHERE station_id = 1 AND measured_at = '2025-01-01 00:00+09';
 pm10 | pm25 |          ingested_at
------+------+-------------------------------
   53 |   25 | 2026-08-12 14:22:51.183492+09
(1 row)
```

`ingested_at` 이 **마지막 실행 시각**으로 갱신됐습니다. `DO UPDATE` 가 동작한 증거입니다.

> **`DO NOTHING` 이었다면** `ingested_at` 이 첫 적재 시각 그대로였을 것입니다.
> "언제 처음 봤는가"가 중요하면 `DO NOTHING`, "최신 값을 유지"가 중요하면 `DO UPDATE` 입니다.

### Step 7. 같은 배치 안의 중복 — 흔한 함정

수집한 데이터에 중복이 섞여 있으면 어떻게 될까요?

```python
>>> rows_dup = rows[:100] + rows[:5]        # 앞 5행이 중복
>>> upsert(rows_dup)
```

`executemany` 는 한 행씩 처리하므로 통과합니다. 하지만 **다중 `VALUES` 로 한 번에 넣으면** 실패합니다.

```
psycopg.errors.CardinalityViolation: ON CONFLICT DO UPDATE command cannot affect row a second time
HINT:  Ensure that no rows proposed for insertion within the same command have
       duplicate constrained values.
```

**`ON CONFLICT` 는 "이미 테이블에 있는 행"과의 충돌만 처리합니다.**
같은 `INSERT` 문 안의 중복은 처리하지 못합니다.

**해결 — 넣기 전에 파이썬에서 중복 제거**

```python
def dedupe(rows: list[tuple]) -> list[tuple]:
    """(station_id, measured_at) 기준으로 마지막 값만 남깁니다."""
    seen: dict[tuple, tuple] = {}
    for row in rows:
        seen[(row[0], row[1])] = row        # 나중 것이 앞의 것을 덮음
    return list(seen.values())
```

```python
>>> len(rows_dup), len(dedupe(rows_dup))
(105, 100)
```

[Day 007](../01-python-data/day-007.md)에서 배운 **딕셔너리로 중복 제거**가 그대로 쓰입니다.

**또는 SQL에서 `DISTINCT ON` 으로** (다음 단계의 스테이징 패턴).

### Step 8. 스테이징 테이블 패턴 — `COPY` 의 속도 + `ON CONFLICT` 의 안전 ★★

`staged_load.py`:

```python
"""스테이징 테이블을 거친 대량 upsert."""

import time

import psycopg
from dotenv import load_dotenv

from datapipe.db import get_conninfo
from load_bench import read_rows

load_dotenv()


def staged_upsert(rows: list[tuple]) -> dict:
    t0 = time.perf_counter()
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            # ① 임시 테이블 — 트랜잭션이 끝나면 자동 삭제
            cur.execute(
                """
                CREATE TEMP TABLE measurement_stg (
                    station_id  integer,
                    measured_at timestamptz,
                    pm10        integer,
                    pm25        integer
                ) ON COMMIT DROP
                """
            )

            # ② COPY 로 통째로 (제약·인덱스가 없어 매우 빠름)
            with cur.copy(
                "COPY measurement_stg (station_id, measured_at, pm10, pm25) FROM STDIN"
            ) as cp:
                for row in rows:
                    cp.write_row(row)
            cur.execute("SELECT COUNT(*) FROM measurement_stg")
            staged = cur.fetchone()[0]

            # ③ 중복 제거 + ④ 본 테이블로 upsert
            cur.execute(
                """
                INSERT INTO measurement (station_id, measured_at, pm10, pm25, ingested_at)
                SELECT DISTINCT ON (station_id, measured_at)
                       station_id, measured_at, pm10, pm25, now()
                FROM measurement_stg
                WHERE station_id IS NOT NULL AND measured_at IS NOT NULL
                ORDER BY station_id, measured_at
                ON CONFLICT (station_id, measured_at) DO UPDATE
                SET pm10 = EXCLUDED.pm10,
                    pm25 = EXCLUDED.pm25,
                    ingested_at = EXCLUDED.ingested_at
                """
            )
            affected = cur.rowcount
        conn.commit()      # ← 여기서 임시 테이블이 사라집니다

    return {
        "staged": staged,
        "affected": affected,
        "seconds": round(time.perf_counter() - t0, 2),
    }


if __name__ == "__main__":
    rows = read_rows()
    print(staged_upsert(rows))
    print(staged_upsert(rows))          # 두 번째 — 결과가 같아야 합니다
```

```powershell
(venv) $ python staged_load.py
{'staged': 100000, 'affected': 100000, 'seconds': 1.94}
{'staged': 100000, 'affected': 100000, 'seconds': 1.87}
```

```
airquality=# SELECT COUNT(*) FROM measurement;
 count
--------
 100000
(1 row)
```

| 방식 | 10만 행 | 멱등 |
|---|---|---|
| `executemany` + `ON CONFLICT` | 8.6 초 | ✅ |
| **스테이징 + `COPY` + `ON CONFLICT`** | **1.9 초** | ✅ |
| `COPY` 단독 | 0.4 초 | ❌ (두 번째 실행이 실패) |

**스테이징 패턴이 실무의 표준 답**입니다. `COPY` 만큼은 아니어도 4배 이상 빠르면서 멱등성을 지킵니다.

> **`ON COMMIT DROP`** 덕분에 임시 테이블 정리를 신경 쓰지 않아도 됩니다.
> 임시 테이블은 **세션마다 따로** 존재하므로, 여러 배치가 동시에 돌아도 서로 간섭하지 않습니다.
> `WHERE station_id IS NOT NULL` 처럼 **스테이징에서 불량 행을 거를 수 있다**는 것도 큰 장점입니다.
> [Day 044](day-044.md)에서 이 자리에 검증 로직을 넣습니다.

**대량 적재 시의 표준 절차**입니다.

```python
def bulk_load_with_index_swap(rows: list[tuple]) -> None:
    with psycopg.connect(get_conninfo()) as conn:
        with conn.cursor() as cur:
            cur.execute("DROP INDEX IF EXISTS idx_measurement_time, idx_measurement_station")
        conn.commit()

        result = staged_upsert(rows)          # 적재

        with conn.cursor() as cur:
            cur.execute("CREATE INDEX idx_measurement_time    ON measurement (measured_at)")
            cur.execute("CREATE INDEX idx_measurement_station ON measurement (station_id)")
            cur.execute("ANALYZE measurement")          # ★ 통계 갱신
        conn.commit()
    print(result)
```

> **주의** — 멱등 키 인덱스(`UNIQUE`)는 **지우면 안 됩니다.** `ON CONFLICT` 가 그것을 씁니다.
> 지워도 되는 것은 **조회 성능용 인덱스**뿐입니다.
>
> **`ANALYZE` 를 빠뜨리면** 옵티마이저가 "이 테이블은 비어 있다"고 믿고 엉뚱한 계획을 세웁니다.
> 대량 적재 후 갑자기 조회가 느려지는 사고의 단골 원인입니다 ([Day 038](day-038.md)).

### Step 10. `datapipe` 에 로더 모듈 추가

`src/datapipe/loader.py`:

```python
"""DB 적재 — 대량·멱등."""

from __future__ import annotations

import logging
from typing import Iterable, Sequence

import psycopg

from .db import connect

logger = logging.getLogger(__name__)


def copy_rows(conn: psycopg.Connection, table: str, columns: Sequence[str],
              rows: Iterable[Sequence]) -> int:
    """COPY 로 밀어 넣습니다. table·columns 는 반드시 코드에서 정한 값만 넘기세요."""
    cols = ", ".join(columns)
    n = 0
    with conn.cursor() as cur:
        with cur.copy(f"COPY {table} ({cols}) FROM STDIN") as cp:
            for row in rows:
                cp.write_row(row)
                n += 1
    return n


def staged_upsert(rows: list[Sequence], *, table: str, columns: Sequence[str],
                  conflict_keys: Sequence[str], update_columns: Sequence[str]) -> int:
    """임시 테이블을 거쳐 멱등 적재합니다. 영향받은 행 수를 반환합니다."""
    if not rows:
        logger.warning("적재할 행이 없습니다")
        return 0

    cols = ", ".join(columns)
    keys = ", ".join(conflict_keys)
    updates = ", ".join(f"{c} = EXCLUDED.{c}" for c in update_columns)
    stg = f"{table}_stg"

    with connect() as conn:
        with conn.cursor() as cur:
            cur.execute(
                f"CREATE TEMP TABLE {stg} "
                f"(LIKE {table} INCLUDING DEFAULTS EXCLUDING CONSTRAINTS EXCLUDING INDEXES) "
                f"ON COMMIT DROP"
            )
        copy_rows(conn, stg, columns, rows)
        with conn.cursor() as cur:
            cur.execute(
                f"""
                INSERT INTO {table} ({cols})
                SELECT DISTINCT ON ({keys}) {cols}
                FROM {stg}
                ORDER BY {keys}
                ON CONFLICT ({keys}) DO UPDATE SET {updates}
                """
            )
            affected = cur.rowcount

    logger.info("적재 완료: %s 테이블 %d행 (입력 %d행)", table, affected, len(rows))
    return affected
```

> **이 함수는 f-string으로 SQL을 만듭니다.** [Day 041](day-041.md)에서 금지한 그것입니다.
> **여기서는 안전합니다** — `table` · `columns` · `conflict_keys` 가 전부 **개발자가 코드에 쓴 값**이고,
> 사용자 입력이 닿지 않기 때문입니다. **행의 값(`rows`)은 `COPY` 스트림으로 따로 갑니다.**
>
> 다만 이 함수를 쓰는 사람이 실수로 사용자 입력을 `table` 에 넘길 수 있으므로,
> **docstring에 경고를 명시**하고 호출부를 리뷰해야 합니다. 더 엄격하게 하려면 `psycopg.sql.Identifier` 를 쓰세요.

사용 예 — [Day 043](day-043.md)의 ETL이 이렇게 호출합니다.

```python
from datapipe import loader

affected = loader.staged_upsert(
    rows,
    table="measurement",
    columns=("station_id", "measured_at", "pm10", "pm25"),
    conflict_keys=("station_id", "measured_at"),
    update_columns=("pm10", "pm25"),
)
```

## ⑥ 확인 문제

**1.** `COPY` 가 단건 `INSERT` 보다 200배 빠른 이유를 세 가지로 설명하세요.

<details>
<summary>답 보기</summary>

| # | 이유 | 설명 |
|---|---|---|
| 1 | **왕복 제거** | 단건은 명령마다 요청·응답을 주고받습니다. 10만 번이면 왕복만으로 수 초.<br>`COPY` 는 **연결을 스트림으로 열어 데이터를 계속 밀어 넣습니다.** |
| 2 | **파싱·계획 생략** | 단건은 SQL 파서가 매번 문장을 해석하고 실행 계획을 세웁니다.<br>`COPY` 는 **SQL 파서를 거치지 않습니다.** 전용 프로토콜로 값만 받습니다. |
| 3 | **커밋(fsync) 횟수** | 매번 커밋하면 **디스크 동기화가 10만 번**입니다. 디스크 동기화는 메모리 작업보다 수천 배 느립니다.<br>`COPY` 는 한 트랜잭션으로 끝납니다. |

**추가 요인** — `COPY` 는 WAL(트랜잭션 로그) 기록도 더 효율적으로 하고,
행 단위 트리거·규칙 검사를 배치로 처리합니다.

**측정 결과의 순서를 보면 원인이 보입니다.**

```
① 단건+매번커밋  82초  ─┐ 커밋을 묶어서 7배 개선 (원인 3 제거)
② 단건+한번커밋  11초  ─┘
③ executemany     7초  ─── 왕복을 줄여 개선 (원인 1 완화)
④ 다중 VALUES     2초  ─── 왕복·파싱을 함께 줄임 (원인 1·2 완화)
⑤ COPY          0.4초  ─── 셋 다 제거
```

**"가장 큰 개선은 ①→②"** 라는 점이 실무적으로 중요합니다.
코드를 거의 안 고치고(커밋 위치만 옮겨) 7배를 얻습니다.
</details>

**2.** 아래 코드는 매일 밤 API에서 데이터를 받아 적재합니다. 어젯밤 8만 행에서 실패했습니다. 오늘 아침 그대로 다시 실행하면 어떻게 되나요? 안전하게 만드세요.

```python
def load_daily(rows):
    with psycopg.connect(dsn) as conn:
        with conn.cursor() as cur:
            for i in range(0, len(rows), 1000):
                cur.executemany(
                    "INSERT INTO measurement (station_id, measured_at, pm10) "
                    "VALUES (%s, %s, %s)",
                    rows[i:i+1000],
                )
                conn.commit()
```

<details>
<summary>답 보기</summary>

**결과는 `UNIQUE` 제약이 있는지에 따라 갈립니다.**

| 제약 | 재실행 결과 |
|---|---|
| **있음** | 1행째부터 `UniqueViolation` → **배치가 즉시 죽음.** 데이터는 안전하지만 복구가 수작업 |
| **없음** | 앞의 8만 행이 **또 들어감** → 중복. 에러 없음. 아무도 모름 ★ |

**둘 다 나쁩니다.**

**안전하게 만들기**

```python
UPSERT = """
INSERT INTO measurement (station_id, measured_at, pm10, ingested_at)
VALUES (%s, %s, %s, now())
ON CONFLICT (station_id, measured_at) DO UPDATE
SET pm10 = EXCLUDED.pm10, ingested_at = EXCLUDED.ingested_at
"""


def load_daily(rows: list[tuple], batch_size: int = 1000) -> int:
    rows = dedupe(rows)                      # ① 배치 안 중복 제거
    total = 0
    with psycopg.connect(dsn) as conn:
        with conn.cursor() as cur:
            for i in range(0, len(rows), batch_size):
                chunk = rows[i:i + batch_size]
                try:
                    cur.executemany(UPSERT, chunk)   # ② 멱등 적재
                    conn.commit()
                    total += len(chunk)
                except psycopg.Error:
                    conn.rollback()                  # ③ 이 배치만 되돌림
                    logger.exception("배치 %d 실패 (행 %d~%d)", i // batch_size, i, i + len(chunk))
                    raise
    return total
```

**세 가지가 들어갔습니다.**

1. **`dedupe`** — 같은 배치 안 중복 제거 (`cannot affect row a second time` 방지)
2. **`ON CONFLICT DO UPDATE`** — 이미 있으면 갱신 → **몇 번을 실행해도 안전**
3. **예외 처리** — 실패한 배치를 롤백하고 **어디서 실패했는지 로그**

**전제 조건** — `UNIQUE (station_id, measured_at)` 제약이 반드시 있어야 합니다.
없으면 2번이 동작하지 않습니다.

**더 나아가면** — [Day 045](day-045.md)에서 `ingest_run` 테이블에 진행 상황을 기록해
"어디까지 처리했는지"를 남깁니다. 그러면 실패 시 **처음부터가 아니라 중단 지점부터** 재개할 수 있습니다.
단, **멱등하면 처음부터 다시 돌려도 안전**하므로, 대부분의 경우 재개 로직보다 멱등성이 더 가치 있습니다.
</details>

**3.** 스테이징 테이블 패턴이 `COPY` 단독보다 5배 느린데도 실무에서 이것을 쓰는 이유는 무엇인가요? 어떤 상황에서는 `COPY` 단독이 맞나요?

<details>
<summary>답 보기</summary>

**스테이징 패턴을 쓰는 이유 4가지**

| # | 이유 | 설명 |
|---|---|---|
| 1 | **멱등성** | `COPY` 단독은 두 번째 실행이 `UniqueViolation` 으로 죽습니다. 재시도가 불가능 |
| 2 | **검증 기회** | 임시 테이블은 제약이 없어 일단 다 받고, **SQL로 불량 행을 걸러** 본 테이블에 넣을 수 있음 |
| 3 | **부분 실패 허용** | `COPY` 는 한 행이 틀리면 전체 실패. 스테이징은 **불량 행만 격리** 가능 ([Day 044](day-044.md)) |
| 4 | **변환** | 임시 테이블에서 조인·집계·형 변환 후 적재 (예: 측정소 이름 → `station_id`) |

**5배 느려도 1.9초입니다.** 매일 밤 도는 배치에서 1.5초 차이는 의미가 없고,
**"재실행 가능"이라는 성질의 가치가 압도적으로 큽니다.**

**`COPY` 단독이 맞는 상황**

| 상황 | 이유 |
|---|---|
| **최초 적재 (빈 테이블)** | 충돌할 기존 행이 없음. 마이그레이션·초기 구축 |
| **매번 통째로 갈아 끼우는 테이블** | `TRUNCATE` → `COPY`. 스냅샷 성격의 마스터 데이터 |
| **append-only 로그 테이블** | 멱등 키 자체가 없는 이벤트 스트림 |
| **정말로 초 단위가 중요한 경우** | 수억 행 초기 이관 등 |

세 번째 패턴은 이렇게 씁니다.

```sql
BEGIN;
TRUNCATE station_master;
COPY station_master (...) FROM STDIN;
COMMIT;
```

**트랜잭션 안에 넣으면** 실패 시 옛 데이터가 그대로 남아 안전합니다.
"통째로 갈아 끼우기"도 **결과가 항상 같으므로 멱등**입니다. 방식이 다를 뿐 목표는 같습니다.

> **판단 기준** — "이 배치를 지금 다시 돌려도 되는가?"에 **"네"** 라고 답할 수 없으면 그 파이프라인은 미완성입니다.
> 방법이 `ON CONFLICT` 든 `TRUNCATE` 든 상관없습니다.
</details>

## 오늘의 정리

| 코드 | 하는 일 |
|---|---|
| `cur.executemany(sql, rows)` | 여러 행 실행 (왕복 감소) |
| `cur.mogrify(...)` + 다중 `VALUES` | 한 문장에 여러 행 |
| `with cur.copy("COPY t (...) FROM STDIN") as cp: cp.write_row(r)` | **가장 빠른 적재** |
| `ON CONFLICT (키) DO NOTHING` | 있으면 무시 |
| `ON CONFLICT (키) DO UPDATE SET c = EXCLUDED.c` | 있으면 갱신 |
| `CREATE TEMP TABLE ... ON COMMIT DROP` | 스테이징 테이블 |
| `SELECT DISTINCT ON (키) ... ORDER BY 키, ...` | 배치 안 중복 제거 |
| `ANALYZE 테이블` | **적재 후 필수** |

| 성능 순서 (10만 행) | |
|---|---|
| 단건+매번커밋 | ~82초 |
| 단건+한번커밋 | 11초 (**커밋 묶기만으로 7배**) |
| `executemany` | 7초 |
| 다중 `VALUES` | 2초 |
| 스테이징+`COPY`+`ON CONFLICT` | **1.9초 (실무 표준)** |
| `COPY` 단독 | 0.4초 (멱등 아님) |

| 원칙 | 이유 |
|---|---|
| **`UNIQUE` 없이는 멱등도 없다** | `ON CONFLICT` 의 전제 |
| **배치 안 중복은 따로 제거** | `ON CONFLICT` 는 기존 행과의 충돌만 처리 |
| **`COPY` 는 한 행만 틀려도 전체 실패** | 사전 검증 + 스테이징 |
| **적재 후 `ANALYZE`** | 통계가 낡으면 조회가 느려짐 |
| **조회용 인덱스는 적재 전에 내린다** | 멱등 키 인덱스는 **절대 내리지 말 것** |
