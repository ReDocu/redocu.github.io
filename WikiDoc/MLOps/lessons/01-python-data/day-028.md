## ② 왜 필요한가

**요즘 노트북은 CPU 코어가 8~16개입니다. 그런데 파이썬 코드는 1개만 씁니다.**

```
파일 100개 전처리
  순차 : 100 × 3초 = 300초 (5분)
  병렬(8코어) : 약 40초        ← 7.5배
```

그리고 W04의 수집기는 더 극적입니다.

```
페이지 100개 수집 (요청당 0.5초 대기)
  순차 : 50초
  동시(스레드 10개) : 5초       ← 10배
```

**두 경우의 해법이 다릅니다.** 전처리는 프로세스, 수집은 스레드입니다.
그 이유가 **GIL** 입니다.

## ③ 개념 설명

### 프로세스 vs 스레드

```
프로세스 (Process)                 스레드 (Thread)
┌─────────────────┐               ┌─────────────────┐
│ 독립된 메모리 공간  │               │  메모리 공유       │
│  ┌───┐          │               │  ┌───┬───┬───┐  │
│  │스레드│         │               │  │T1 │T2 │T3 │  │
│  └───┘          │               │  └───┴───┴───┘  │
└─────────────────┘               └─────────────────┘
```

| | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | **독립** | 공유 |
| 생성 비용 | 큼 (수십~수백 ms) | 작음 (~1 ms) |
| 데이터 전달 | 직렬화 필요 (느림) | 그냥 접근 |
| GIL 영향 | **없음** | 있음 |
| 안정성 | 하나 죽어도 나머지 생존 | 하나 죽으면 전체 위험 |
| 적합 | **CPU 작업** | **I/O 대기** |

### GIL (Global Interpreter Lock)

**파이썬 인터프리터는 한 번에 하나의 스레드만 파이썬 바이트코드를 실행합니다.**

```
스레드 4개로 계산을 시켜도

시간 →
T1: ■■□□□□■■□□□□
T2: □□■■□□□□■■□□      ← 번갈아 가며 하나씩
T3: □□□□■■□□□□■■
T4: □□□□□□■■□□□□

결과: 1개일 때와 속도가 같거나 더 느림 (전환 비용)
```

**그런데 I/O 대기 중에는 GIL을 놓습니다.**

```
네트워크 요청 (대부분 기다리는 시간)

T1: ■□□□□□□□□□■        ■ = 실제 계산, □ = 대기
T2:  ■□□□□□□□□□■
T3:   ■□□□□□□□□□■      ← 대기 중에 다른 스레드가 실행
T4:    ■□□□□□□□□□■

결과: 거의 N배 빨라짐
```

**GIL을 놓는 작업**

| 작업 | GIL 해제 |
|---|---|
| 네트워크 요청 (`requests`) | ✅ |
| 파일 읽기·쓰기 | ✅ |
| `time.sleep()` | ✅ |
| DB 쿼리 대기 | ✅ |
| **NumPy 연산 (일부)** | ✅ |
| 순수 파이썬 계산 | ❌ |

> **NumPy·Pandas의 무거운 연산은 C에서 실행되며 GIL을 놓는 경우가 많습니다.**
> 그래서 스레드로도 어느 정도 이득이 있을 수 있습니다. 반드시 측정하세요.

### CPU 바운드 vs I/O 바운드

**판단 방법: 작업 중 CPU가 바쁜가, 기다리는가?**

| 작업 | 종류 | 병렬 방식 |
|---|---|---|
| 파일 파싱·정제 | CPU | **프로세스** |
| 통계 계산 | CPU | **프로세스** |
| 이미지 변환 | CPU | **프로세스** |
| 모델 학습 | CPU/GPU | 프로세스 |
| HTTP 요청 | **I/O** | **스레드** |
| 파일 읽기·쓰기 | I/O | 스레드 |
| DB 쿼리 | I/O | 스레드 |

**애매하면 측정하세요.**

```python
import time
start_wall = time.perf_counter()
start_cpu = time.process_time()
work()
wall = time.perf_counter() - start_wall
cpu = time.process_time() - start_cpu

print(f"실제 시간 {wall:.2f}초, CPU 시간 {cpu:.2f}초")
print(f"CPU 사용률 {cpu / wall:.0%}")
# 90% 이상 → CPU 바운드
# 30% 이하 → I/O 바운드
```

### concurrent.futures

**파이썬 표준 라이브러리. 두 실행기가 같은 인터페이스를 씁니다.**

```python
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

# CPU 작업
with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(heavy_compute, items))

# I/O 작업
with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(fetch_url, urls))
```

**`map` vs `submit`**

```python
# map — 순서대로 결과가 나옴, 간단
results = list(pool.map(func, items))

# submit — 개별 제어, 완료 순서대로 처리 가능
futures = [pool.submit(func, item) for item in items]
for future in as_completed(futures):
    result = future.result()          # 예외도 여기서 발생
```

**`as_completed` 를 쓰면 먼저 끝난 것부터 처리**할 수 있어 진행 상황 표시에 좋습니다.

### 워커 수 정하기

```python
import os

cpu_count = os.cpu_count()          # 논리 코어 수

# CPU 바운드
max_workers = cpu_count             # 또는 cpu_count - 1 (다른 작업 여유)

# I/O 바운드
max_workers = min(32, cpu_count * 4)   # 대기가 많으므로 코어보다 많이
```

**I/O 바운드에서 워커를 무한정 늘리면 안 됩니다.**
- 상대 서버에 부담 ([Day 018](day-018.md))
- 파일 디스크립터 소진
- 컨텍스트 전환 비용

**측정해서 최적점을 찾으세요.**

### 병렬화의 비용

**공짜가 아닙니다.**

| 비용 | 프로세스 | 스레드 |
|---|---|---|
| 생성 | 수십~수백 ms | ~1 ms |
| 데이터 전달 | **pickle 직렬화** | 없음 |
| 결과 수집 | pickle 역직렬화 | 없음 |
| 메모리 | 프로세스마다 복사 | 공유 |

**작업이 짧으면 오버헤드가 이득보다 큽니다.**

```
작업 1개가 0.001초 × 1000개
  순차     : 1초
  프로세스  : 3초      ← 오히려 느림!
```

**기준: 작업 하나가 최소 0.1초 이상**이어야 병렬화 이득이 있습니다.
그보다 짧으면 **묶어서(chunk) 넘기세요.**

```python
pool.map(func, items, chunksize=100)      # 100개씩 묶어 전달
```

### 직렬화 제약 (프로세스만)

**프로세스에 넘기는 것은 pickle로 직렬화됩니다.**

```python
# ❌ pickle 불가
with ProcessPoolExecutor() as pool:
    pool.map(lambda x: x * 2, items)       # 람다는 pickle 안 됨

# ✅ 모듈 최상위 함수
def double(x):
    return x * 2

with ProcessPoolExecutor() as pool:
    pool.map(double, items)
```

| pickle 가능 | pickle 불가 |
|---|---|
| 모듈 최상위 함수 | **람다** |
| 클래스 인스턴스 (대부분) | 지역 함수(클로저) |
| DataFrame, ndarray | 파일 핸들 |
| dict, list, str, int | DB 연결 |
| — | 열린 소켓 |

**큰 데이터를 넘기면 직렬화 비용이 큽니다.**

```
DataFrame 100MB 를 4개 프로세스에 넘기면
  → 직렬화 100MB × 4 = 400MB 복사
  → 계산보다 전달이 더 오래 걸릴 수 있음
```

**해결: 데이터가 아니라 "파일 경로"를 넘기세요.**

```python
# ❌ 큰 DataFrame 전달
pool.map(process, [df1, df2, df3])

# ✅ 경로 전달 → 각 프로세스가 직접 읽음
pool.map(process_file, ["a.parquet", "b.parquet", "c.parquet"])
```

### `if __name__ == "__main__":` 필수

**Windows·macOS에서 프로세스를 쓸 때 반드시 필요합니다.**

```python
def work(x):
    return x * 2

if __name__ == "__main__":              # ← 없으면 무한 재귀
    with ProcessPoolExecutor() as pool:
        print(list(pool.map(work, range(10))))
```

**이유** — 자식 프로세스가 모듈을 다시 import하는데,
`if` 가 없으면 자식이 또 프로세스를 만들고, 그 자식이 또... 무한 반복됩니다.

```
RuntimeError: An attempt has been made to start a new process before the
current process has finished its bootstrapping phase.
```

**[Day 013](day-013.md)에서 배운 관용구가 여기서 필수가 됩니다.**

### 예외 처리

```python
from concurrent.futures import as_completed

futures = {pool.submit(work, item): item for item in items}

results, errors = [], []
for future in as_completed(futures):
    item = futures[future]
    try:
        results.append(future.result())      # 여기서 예외가 다시 발생
    except Exception as e:
        errors.append({"item": item, "error": str(e)})
        logger.warning("실패 %s: %s", item, e)
```

**`future.result()` 를 호출해야 예외가 드러납니다.**
호출하지 않으면 **조용히 무시**됩니다.

### 로깅과 진행 표시

**프로세스는 메모리를 공유하지 않으므로 전역 카운터가 안 됩니다.**

```python
# ❌ 프로세스에서는 동작 안 함
count = 0
def work(x):
    global count
    count += 1          # 자식 프로세스의 복사본만 증가
```

**해결 — 메인에서 완료를 세세요.**

```python
done = 0
for future in as_completed(futures):
    done += 1
    print(f"\r  {done}/{len(futures)} 완료", end="", flush=True)
```

### Step 1. GIL 확인 — CPU 작업

`gil_cpu.py` 를 만듭니다.

```python
"""CPU 작업에서 스레드가 왜 안 되는가."""

import os
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def cpu_heavy(n: int) -> int:
    """순수 파이썬 계산 — GIL 을 놓지 않습니다."""
    total = 0
    for i in range(n):
        total += i * i % 7
    return total


N = 8_000_000
TASKS = 8

print(f"CPU 코어: {os.cpu_count()}개")
print(f"작업: {TASKS}개 × {N:,}회 반복 계산\n")

# --- 순차 ---
start = time.perf_counter()
results = [cpu_heavy(N) for _ in range(TASKS)]
sequential = time.perf_counter() - start
print(f"  순차                        {sequential:>7.2f}초   (기준)")

# --- 스레드 ---
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=TASKS) as pool:
    results = list(pool.map(cpu_heavy, [N] * TASKS))
threaded = time.perf_counter() - start
print(f"  스레드 {TASKS}개                  {threaded:>7.2f}초   "
      f"{sequential / threaded:>5.2f}배")

# --- 프로세스 ---
if __name__ == "__main__":
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=TASKS) as pool:
        results = list(pool.map(cpu_heavy, [N] * TASKS))
    parallel = time.perf_counter() - start
    print(f"  프로세스 {TASKS}개                {parallel:>7.2f}초   "
          f"{sequential / parallel:>5.2f}배")

    print(f"""
  스레드는 GIL 때문에 **한 번에 하나만** 실행됩니다.
  전환 비용까지 더해져 순차보다 느릴 수도 있습니다.

  프로세스는 각자 인터프리터를 가지므로 GIL 제약이 없습니다.
  코어 수만큼 (오버헤드를 빼고) 빨라집니다.
""")

    print("=" * 62)
    print("CPU 사용률로 확인")
    print("=" * 62)

    for label, func in [
        ("순차", lambda: [cpu_heavy(N) for _ in range(4)]),
        ("스레드", lambda: list(ThreadPoolExecutor(4).map(cpu_heavy, [N] * 4))),
    ]:
        start_wall = time.perf_counter()
        start_cpu = time.process_time()
        func()
        wall = time.perf_counter() - start_wall
        cpu = time.process_time() - start_cpu
        print(f"  {label:<8} 실제 {wall:>6.2f}초  CPU {cpu:>6.2f}초  "
              f"사용률 {cpu / wall:>5.0%}")

    print("""
  CPU 사용률이 100% 근처면 CPU 바운드입니다.
  스레드로 늘려도 사용률이 100% 를 못 넘습니다 (GIL).
  프로세스는 400% (4코어) 까지 올라갑니다.
""")
```

실행 결과:

```
  스레드 8개                       8.41초    0.93배
  프로세스 8개                     1.32초    5.94배

==============================================================
```

### Step 2. I/O 작업 — 스레드가 이기는 경우

`gil_io.py` 를 만듭니다.

```python
"""I/O 작업에서는 스레드가 효과적입니다."""

import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def io_task(seconds: float) -> str:
    """I/O 대기를 흉내 냅니다. sleep 은 GIL 을 놓습니다."""
    time.sleep(seconds)
    return f"{seconds}초 완료"


DELAY = 0.5
TASKS = 20

print(f"작업: {TASKS}개 × {DELAY}초 대기 (네트워크 요청 흉내)\n")

# --- 순차 ---
start = time.perf_counter()
results = [io_task(DELAY) for _ in range(TASKS)]
sequential = time.perf_counter() - start
print(f"  순차                        {sequential:>7.2f}초   (기준)")

# --- 스레드 ---
for workers in [4, 10, 20]:
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as pool:
        results = list(pool.map(io_task, [DELAY] * TASKS))
    elapsed = time.perf_counter() - start
    print(f"  스레드 {workers:>2}개                  {elapsed:>7.2f}초   "
          f"{sequential / elapsed:>5.2f}배")

if __name__ == "__main__":
    # --- 프로세스 ---
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=10) as pool:
        results = list(pool.map(io_task, [DELAY] * TASKS))
    parallel = time.perf_counter() - start
    print(f"  프로세스 10개               {parallel:>7.2f}초   "
          f"{sequential / parallel:>5.2f}배")

    print(f"""
  I/O 대기 중에는 GIL 이 풀리므로 스레드가 효과적입니다.
  워커를 늘릴수록 빨라지지만, 상대 서버 부담과 자원 한계를 고려해야 합니다.

  프로세스도 되지만 **생성 비용이 커서 스레드보다 느립니다.**
  I/O 작업에는 스레드를 쓰세요.
""")

    print("=" * 62)
    print("CPU 사용률로 확인")
    print("=" * 62)
    start_wall = time.perf_counter()
    start_cpu = time.process_time()
    with ThreadPoolExecutor(10) as pool:
        list(pool.map(io_task, [DELAY] * 10))
    wall = time.perf_counter() - start_wall
    cpu = time.process_time() - start_cpu
```

```python
"""여러 파일을 병렬로 전처리 — CPU 바운드."""

import os
import shutil
import time
from concurrent.futures import ProcessPoolExecutor, as_completed
from pathlib import Path

import numpy as np
import pandas as pd

IN_DIR = Path("data/split")
OUT_DIR = Path("data/processed")


# ==================== 준비 ====================

def prepare_files(n_files: int = 24, rows_per_file: int = 120_000) -> list[Path]:
    """실습용 파일들을 만듭니다."""
    if IN_DIR.exists():
        shutil.rmtree(IN_DIR)
    IN_DIR.mkdir(parents=True)

    rng = np.random.default_rng(42)
    stations = [f"{n}구" for n in ["중", "종로", "용산", "성동", "광진",
                                   "동대문", "중랑", "성북", "강북", "도봉"]]
    paths = []

    for i in range(n_files):
        df = pd.DataFrame({
            "measured_at": pd.Timestamp("2026-01-01") + pd.to_timedelta(
                rng.integers(0, 365 * 24 * 60, rows_per_file), unit="m"),
            "station": rng.choice(stations, rows_per_file),
            "pm10": rng.integers(5, 200, rows_per_file),
            "pm25": rng.integers(2, 110, rows_per_file),
            "o3": rng.uniform(0.005, 0.13, rows_per_file).round(4),
            "temperature": rng.uniform(-15, 38, rows_per_file).round(1),
        })
        # 결측·이상치 심기
        idx = rng.choice(rows_per_file, size=rows_per_file // 25, replace=False)
        df.loc[idx, "pm10"] = np.nan
        idx2 = rng.choice(rows_per_file, size=20, replace=False)
        df.loc[idx2, "pm10"] = rng.integers(800, 1500, 20)

        path = IN_DIR / f"part_{i:03d}.csv"
        df.to_csv(path, index=False)
        paths.append(path)

    total_mb = sum(p.stat().st_size for p in paths) / 1024**2
    print(f"  파일 {len(paths)}개 생성 ({total_mb:,.1f} MB)")
    return paths


# ==================== 작업 함수 ====================
# ⚠ 반드시 모듈 최상위에 정의해야 pickle 됩니다 (람다·중첩 함수 불가)

def process_file(path: Path) -> dict:
    """파일 하나를 정제하고 결과를 저장합니다.

    Returns:
        처리 요약 (프로세스 간에는 작은 값만 주고받습니다)
    """
    start = time.perf_counter()

    df = pd.read_csv(path, parse_dates=["measured_at"])
    original = len(df)

    # 정제 (Day 023)
    df = df.drop_duplicates()
    df.loc[(df["pm10"] < 0) | (df["pm10"] > 600), "pm10"] = np.nan
    outliers = df["pm10"].isna().sum()
    df["pm10"] = df.groupby("station")["pm10"].transform(lambda s: s.fillna(s.median()))
    df["pm10"] = df["pm10"].fillna(df["pm10"].median())

    # 파생 (CPU 를 좀 더 쓰게)
    df["month"] = df["measured_at"].dt.month
    df["hour"] = df["measured_at"].dt.hour
    df["ratio"] = (df["pm25"] / df["pm10"].replace(0, np.nan)).round(3)
    df["station_avg"] = df.groupby("station")["pm10"].transform("mean")
    df["deviation"] = (df["pm10"] - df["station_avg"]).round(2)

    # dtype 최적화 (Day 026)
    df["station"] = df["station"].astype("category")
    df["pm10"] = df["pm10"].astype("uint16")
    df["pm25"] = df["pm25"].astype("uint8")
    df["o3"] = df["o3"].astype("float32")
    df["temperature"] = df["temperature"].astype("float32")

    # Parquet 저장 (Day 027)
    OUT_DIR.mkdir(parents=True, exist_ok=True)
    out_path = OUT_DIR / f"{path.stem}.parquet"
    df.to_parquet(out_path, index=False, compression="zstd")

    return {
        "file": path.name,
        "rows_in": original,
        "rows_out": len(df),
        "outliers": int(outliers),
        "pm10_mean": round(float(df["pm10"].mean()), 2),
        "seconds": round(time.perf_counter() - start, 2),
        "out_mb": round(out_path.stat().st_size / 1024**2, 2),
    }


def run_sequential(paths: list[Path]) -> list[dict]:
    results = []
    for i, path in enumerate(paths, start=1):
        results.append(process_file(path))
        print(f"\r  {i}/{len(paths)} 완료", end="", flush=True)
    print()
    return results


def run_parallel(paths: list[Path], workers: int) -> tuple[list[dict], list[dict]]:
    results, errors = [], []

    with ProcessPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(process_file, p): p for p in paths}

        for i, future in enumerate(as_completed(futures), start=1):
            path = futures[future]
            try:
                results.append(future.result())
            except Exception as e:
                errors.append({"file": path.name, "error": f"{type(e).__name__}: {e}"})
            print(f"\r  {i}/{len(paths)} 완료", end="", flush=True)

    print()
    return results, errors

def main() -> None:
```

```python
"""HTTP 수집 병렬화 — I/O 바운드."""

import threading
import time
from concurrent.futures import ThreadPoolExecutor, as_completed
from dataclasses import dataclass, field

import requests


@dataclass
class FetchStats:
    """스레드 안전한 통계 수집기."""
    success: int = 0
    failed: int = 0
    total_bytes: int = 0
    _lock: threading.Lock = field(default_factory=threading.Lock, repr=False)

    def record_success(self, size: int) -> None:
        with self._lock:                 # 여러 스레드가 동시에 수정하므로 락 필요
            self.success += 1
            self.total_bytes += size

    def record_failure(self) -> None:
        with self._lock:
            self.failed += 1


# 스레드마다 별도 Session — Session 은 스레드 안전이 보장되지 않습니다
_local = threading.local()


def get_session() -> requests.Session:
    if not hasattr(_local, "session"):
        _local.session = requests.Session()
        _local.session.headers.update({"User-Agent": "MLOpsStudy/1.0"})
    return _local.session


def fetch_one(url: str, stats: FetchStats, timeout: float = 10.0) -> dict:
    """URL 하나를 요청합니다."""
    start = time.perf_counter()
    try:
        r = get_session().get(url, timeout=timeout)
        r.raise_for_status()
        stats.record_success(len(r.content))
        return {
            "url": url,
            "status": r.status_code,
            "bytes": len(r.content),
            "seconds": round(time.perf_counter() - start, 3),
            "thread": threading.current_thread().name,
        }
    except requests.RequestException as e:
        stats.record_failure()
        return {"url": url, "error": f"{type(e).__name__}", "seconds": 0}


def fetch_sequential(urls: list[str]) -> tuple[list[dict], float]:
    stats = FetchStats()
    start = time.perf_counter()
    results = [fetch_one(url, stats) for url in urls]
    return results, time.perf_counter() - start


def fetch_threaded(urls: list[str], workers: int) -> tuple[list[dict], float]:
    stats = FetchStats()
    start = time.perf_counter()
    results = []

    with ThreadPoolExecutor(max_workers=workers,
                            thread_name_prefix="fetch") as pool:
        futures = [pool.submit(fetch_one, url, stats) for url in urls]
        for i, future in enumerate(as_completed(futures), start=1):
            results.append(future.result())
            print(f"\r    {i}/{len(urls)}", end="", flush=True)
    print()

    return results, time.perf_counter() - start

    print("\n" + "=" * 70)
    print("결과")
```

```python
"""병렬화가 항상 이득은 아닙니다."""

import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def tiny_work(x: int) -> int:
    """아주 짧은 작업."""
    return x * x


def medium_work(x: int) -> int:
    """중간 작업."""
    total = 0
    for i in range(100_000):
        total += i % (x + 1)
    return total


if __name__ == "__main__":
    print("=" * 70)
    print("1) 짧은 작업 — 병렬화가 손해")
    print("=" * 70)

    items = list(range(100_000))

    start = time.perf_counter()
    r1 = [tiny_work(x) for x in items]
    seq = time.perf_counter() - start
    print(f"  순차                            {seq:>7.3f}초")

    start = time.perf_counter()
    with ProcessPoolExecutor(4) as pool:
        r2 = list(pool.map(tiny_work, items))
    par = time.perf_counter() - start
    print(f"  프로세스 4개 (chunksize 기본)      {par:>7.3f}초   "
          f"{seq / par:>5.2f}배")

    start = time.perf_counter()
    with ProcessPoolExecutor(4) as pool:
        r3 = list(pool.map(tiny_work, items, chunksize=5000))
    par_chunk = time.perf_counter() - start
    print(f"  프로세스 4개 (chunksize 5000)     {par_chunk:>7.3f}초   "
          f"{seq / par_chunk:>5.2f}배")
```

### Step 6. 재사용 유틸리티

`parallel.py` 를 만듭니다. [Day 029](day-029.md)에서 씁니다.

```python
"""병렬 처리 유틸리티."""

from __future__ import annotations

import logging
import os
import time
from collections.abc import Callable, Iterable
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor, as_completed
from dataclasses import dataclass, field
from typing import Any, Literal, TypeVar

logger = logging.getLogger(__name__)

T = TypeVar("T")
R = TypeVar("R")

Mode = Literal["sequential", "thread", "process"]


@dataclass
class ParallelResult:
    """병렬 실행 결과."""
    results: list[Any] = field(default_factory=list)
    errors: list[dict] = field(default_factory=list)
    elapsed: float = 0.0
    mode: str = ""
    workers: int = 1

    @property
    def success_count(self) -> int:
        return len(self.results)

    @property
    def total(self) -> int:
        return len(self.results) + len(self.errors)

    @property
    def success_rate(self) -> float:
        return self.success_count / self.total if self.total else 0.0

    def summary(self) -> str:
        return (f"{self.mode}({self.workers}) — "
                f"성공 {self.success_count}/{self.total} "
                f"({self.success_rate:.0%}), {self.elapsed:.1f}초")


def default_workers(mode: Mode) -> int:
    """모드에 맞는 기본 워커 수."""
    cpu = os.cpu_count() or 4
    if mode == "process":
        return max(1, cpu - 1)          # 한 코어는 여유로 남김
    if mode == "thread":
        return min(16, cpu * 2)
    return 1


def run_parallel(
    func: Callable[[T], R],
    items: Iterable[T],
    mode: Mode = "process",
    workers: int | None = None,
    progress: bool = True,
    chunksize: int = 1,
    raise_on_error: bool = False,
) -> ParallelResult:
    """항목들을 병렬로 처리합니다.

    Args:
        func: 항목 하나를 처리하는 함수. **모듈 최상위에 정의**해야 합니다
              (process 모드에서 pickle 필요)
        items: 처리할 항목들
        mode: "sequential" | "thread"(I/O) | "process"(CPU)
        workers: 워커 수 (None 이면 자동)
        progress: 진행 상황 표시
        chunksize: 작업을 묶어 보낼 개수 (짧은 작업에서 유용)
        raise_on_error: True 면 첫 예외에서 중단

    Returns:
        ParallelResult
    """
    items = list(items)
    workers = workers or default_workers(mode)
    result = ParallelResult(mode=mode, workers=workers)

    if not items:
        return result

    start = time.perf_counter()

    if mode == "sequential":
        for i, item in enumerate(items, start=1):
            try:
                result.results.append(func(item))
            except Exception as e:
                if raise_on_error:
                    raise
                result.errors.append({"item": repr(item)[:80],
                                      "error": f"{type(e).__name__}: {e}"})
            if progress:
                print(f"\r  {i}/{len(items)}", end="", flush=True)
    else:
        executor_cls = ProcessPoolExecutor if mode == "process" else ThreadPoolExecutor
        with executor_cls(max_workers=workers) as pool:
            futures = {pool.submit(func, item): item for item in items}

            for i, future in enumerate(as_completed(futures), start=1):
                item = futures[future]
                try:
                    result.results.append(future.result())
                except Exception as e:
                    if raise_on_error:
                        raise
                    result.errors.append({"item": repr(item)[:80],
                                          "error": f"{type(e).__name__}: {e}"})
                    logger.warning("실패 %r: %s", item, e)
                if progress:
                    print(f"\r  {i}/{len(items)}", end="", flush=True)

    if progress:
        print()

    result.elapsed = time.perf_counter() - start
    logger.info(result.summary())
    return result


def benchmark_modes(func: Callable[[T], R], items: Iterable[T],
                    worker_options: list[int] | None = None) -> list[dict]:
    """순차·스레드·프로세스를 비교합니다."""
    items = list(items)
    cpu = os.cpu_count() or 4
    worker_options = worker_options or [2, 4, cpu]

    rows = []

    seq = run_parallel(func, items, mode="sequential", progress=False)
    baseline = seq.elapsed
    rows.append({"모드": "순차", "워커": 1, "시간": round(baseline, 2),
                 "배속": 1.0, "효율": 1.0, "실패": len(seq.errors)})

    for mode in ("thread", "process"):
        for workers in worker_options:
            r = run_parallel(func, items, mode=mode, workers=workers, progress=False)
            speedup = baseline / r.elapsed if r.elapsed else 0
            rows.append({
                "모드": mode, "워커": workers, "시간": round(r.elapsed, 2),
                "배속": round(speedup, 2), "효율": round(speedup / workers, 2),
                "실패": len(r.errors),
            })

    return rows


def guess_mode(sample_func: Callable[[], Any]) -> Mode:
    """샘플 작업을 실행해 CPU 바운드인지 I/O 바운드인지 추정합니다."""
    start_wall = time.perf_counter()
    start_cpu = time.process_time()
    sample_func()
    wall = time.perf_counter() - start_wall
    cpu = time.process_time() - start_cpu

    ratio = cpu / wall if wall else 0
    logger.info("CPU 사용률 %.0f%% (실제 %.2f초, CPU %.2f초)", ratio * 100, wall, cpu)

    if ratio > 0.7:
        return "process"
    if ratio < 0.3:
        return "thread"
    return "process"          # 애매하면 프로세스
```

## ⑥ 확인 문제

**1.** GIL이 무엇이고, 왜 CPU 작업에는 프로세스를 써야 하나요?

<details>
<summary>답 보기</summary>

**GIL(Global Interpreter Lock)은 "파이썬 바이트코드를 한 번에 하나의 스레드만 실행하게 하는 잠금"입니다.**

CPython(표준 파이썬)의 메모리 관리가 스레드 안전하지 않아서 도입됐습니다.
객체의 참조 카운트를 여러 스레드가 동시에 건드리면 메모리가 손상되기 때문입니다.

**CPU 작업에서 벌어지는 일**

```
스레드 4개로 계산

시간 →
T1: ■■□□□□■■□□□□
T2: □□■■□□□□■■□□      ■ = 실행 중, □ = GIL 대기
T3: □□□□■■□□□□■■
T4: □□□□□□■■□□□□
```

**동시에 하나만 실행되므로 총 시간이 줄지 않습니다.**
오히려 스레드 전환 비용 때문에 **순차보다 느릴 수 있습니다.**

측정 결과:

```
순차        7.84초
스레드 8개   8.41초      ← 7% 느림
프로세스 8개  1.32초      ← 5.9배 빠름
```

**프로세스가 되는 이유**

각 프로세스는 **자기만의 파이썬 인터프리터와 GIL**을 가집니다.

```
프로세스1: [인터프리터 + GIL] ■■■■■■■■
프로세스2: [인터프리터 + GIL] ■■■■■■■■     동시 실행
프로세스3: [인터프리터 + GIL] ■■■■■■■■
프로세스4: [인터프리터 + GIL] ■■■■■■■■
```

**서로 간섭하지 않으므로 코어 수만큼 빨라집니다.**

**대신 비용이 있습니다**

| 비용 | 설명 |
|---|---|
| 생성 | 수십~수백 ms (스레드는 ~1ms) |
| 메모리 | 프로세스마다 인터프리터·모듈 복사 |
| 데이터 전달 | **pickle 직렬화** 필요 |
| 공유 상태 | 불가능 (Queue·공유 메모리 필요) |

**I/O 작업은 왜 스레드가 되는가**

**I/O 대기 중에는 GIL을 놓습니다.**

```python
r = requests.get(url)      # 네트워크 대기 중 GIL 해제
time.sleep(1)              # GIL 해제
f.read()                   # 디스크 대기 중 GIL 해제
```

```
T1: ■□□□□□□□□□■        ■ = 실제 실행, □ = 대기(GIL 해제)
T2:  ■□□□□□□□□□■
T3:   ■□□□□□□□□□■      대기 시간이 겹쳐짐
T4:    ■□□□□□□□□□■
```

**측정 결과** — CPU 사용률이 0.6%였습니다. 99.4%를 기다립니다.
이 대기를 겹치는 것이 스레드의 역할입니다.

**NumPy는 예외적입니다**

NumPy·Pandas의 무거운 연산은 **C 코드에서 실행되며 GIL을 놓는 경우가 많습니다.**
그래서 스레드로도 어느 정도 이득이 있을 수 있습니다.

**하지만 반드시 측정하세요.** 연산마다 다릅니다.

**판단 절차**

```python
start_wall = time.perf_counter()
start_cpu = time.process_time()
work()
ratio = (time.process_time() - start_cpu) / (time.perf_counter() - start_wall)
```

| CPU 사용률 | 판단 | 방식 |
|---|---|---|
| > 70% | CPU 바운드 | **프로세스** |
| < 30% | I/O 바운드 | **스레드** |
| 30~70% | 혼합 | 둘 다 측정해 보기 |

**참고 — GIL의 미래**

파이썬 3.13에서 **GIL을 제거한 빌드(free-threading)** 가 실험적으로 도입됐습니다.
아직 기본이 아니고 성능·호환성 이슈가 있지만, 몇 년 뒤에는
"CPU 작업도 스레드로" 가 가능해질 수 있습니다.
</details>

**2.** 파일 100개를 병렬 처리했는데 순차보다 느립니다. 원인을 어떻게 진단하나요?

<details>
<summary>답 보기</summary>

**① 작업 하나가 너무 짧은가**

```python
import time
start = time.perf_counter()
process_one_file(paths[0])
print(f"파일 하나: {time.perf_counter() - start:.3f}초")
```

| 작업 시간 | 판단 |
|---|---|
| < 0.01초 | ❌ 병렬화 손해 (오버헤드가 더 큼) |
| 0.01 ~ 0.1초 | △ `chunksize` 로 묶으면 이득 |
| > 0.1초 | ✅ 병렬화 이득 |

**해결**

```python
pool.map(func, items, chunksize=20)      # 20개씩 묶어 전달
```

**② 데이터 전달 비용이 큰가**

```python
# ❌ DataFrame 을 넘기면 pickle 직렬화
pool.map(process, [df1, df2, ...])

# ✅ 경로를 넘기고 각자 읽게
pool.map(process_file, ["a.parquet", "b.parquet", ...])
```

**측정**

```python
import pickle
size = len(pickle.dumps(df)) / 1024**2
print(f"직렬화 크기: {size:.1f} MB")
```

수십 MB면 전달만으로 시간이 다 갑니다.

**③ 디스크 I/O가 병목인가**

```
CPU 12개로 파일 12개를 동시에 읽으면
  → HDD: 헤드가 왔다갔다 하며 오히려 느려짐
  → SSD: 어느 정도 병렬이 되지만 한계 있음
```

**진단**

```python
# 파일을 읽기만 해 보기
start = time.perf_counter()
for p in paths:
    pd.read_csv(p)
read_only = time.perf_counter() - start

# 전체 처리
start = time.perf_counter()
for p in paths:
    process_file(p)
full = time.perf_counter() - start

print(f"읽기 {read_only:.1f}초 / 전체 {full:.1f}초 "
      f"= {read_only / full:.0%}가 I/O")
```

**I/O가 70% 이상이면** 프로세스를 늘려도 소용없습니다.
Parquet으로 바꿔 읽는 양을 줄이는 것이 낫습니다 ([Day 027](day-027.md)).

**④ 메모리가 부족해 스와핑이 일어나는가**

```
프로세스 12개 × 파일당 500MB = 6GB
  → RAM 8GB 노트북에서 스와핑 시작
  → 디스크를 메모리처럼 쓰면 100배 느려짐
```

**진단** — 작업 관리자에서 메모리 사용률과 디스크 활동을 확인하세요.
**해결** — 워커 수를 줄이거나 chunk로 처리하세요.

**⑤ 워커가 너무 많은가**

측정 결과에서 효율이 떨어지는 것을 확인했습니다.

```
워커 2개  : 1.87배  효율 93%
워커 4개  : 3.38배  효율 85%
워커 8개  : 5.57배  효율 70%
워커 12개 : 6.60배  효율 55%      ← 논리 코어(하이퍼스레딩)
```

**물리 코어 수를 넘어가면 효율이 급락합니다.**

```python
import psutil
print(f"물리 코어: {psutil.cpu_count(logical=False)}")
print(f"논리 코어: {psutil.cpu_count(logical=True)}")
```

**⑥ CPU 작업인데 스레드를 썼는가**

```python
ThreadPoolExecutor    # GIL 때문에 이득 없음
ProcessPoolExecutor   # ✅
```

**진단 스크립트**

```python
def diagnose(func, items, workers=4):
    # 1) 작업 하나의 시간
    start = time.perf_counter()
    func(items[0])
    per_task = time.perf_counter() - start

    # 2) CPU 사용률
    start_wall, start_cpu = time.perf_counter(), time.process_time()
    func(items[0])
    ratio = (time.process_time() - start_cpu) / (time.perf_counter() - start_wall)

    # 3) 직렬화 크기
    import pickle
    payload_mb = len(pickle.dumps(items[0])) / 1024**2

    print(f"작업당 시간   : {per_task:.3f}초  "
          f"{'✅' if per_task > 0.1 else '⚠ 너무 짧음'}")
    print(f"CPU 사용률    : {ratio:.0%}  "
          f"→ {'프로세스' if ratio > 0.7 else '스레드'} 권장")
    print(f"전달 데이터    : {payload_mb:.2f} MB  "
          f"{'⚠ 경로 전달 권장' if payload_mb > 1 else '✅'}")
    print(f"물리 코어     : {psutil.cpu_count(logical=False)}")
```

**해결 순서**

```
1. 작업이 짧으면 → chunksize 또는 벡터 연산
2. 데이터가 크면 → 경로 전달
3. I/O 병목이면 → Parquet 전환, 컬럼 선택
4. 메모리 부족이면 → 워커 감소
5. 워커가 많으면  → 물리 코어 수로 조정
6. CPU 작업이면  → 프로세스로 변경
```

**3.** 병렬화를 시도하기 전에 확인해야 할 것들은 무엇인가요? 순서대로 답하세요.

<details>
<summary>답 보기</summary>

**병렬화는 마지막 수단입니다.** 앞에 할 것이 많습니다.

**① 측정 — 정말 느린가, 어디가 느린가**

```python
import cProfile
cProfile.run("main()", sort="cumtime")
```

또는 간단히:

```python
for name, func in steps.items():
    start = time.perf_counter()
    func()
    print(f"{name}: {time.perf_counter() - start:.2f}초")
```

**"느낌"으로 최적화하지 마세요.** 예상과 다른 곳이 병목인 경우가 많습니다.

**② 정말 최적화가 필요한가**

```
하루 한 번 도는 배치가 5분 걸린다  → 최적화 불필요
매 요청마다 도는 코드가 2초 걸린다  → 최적화 필요
```

**시간이 남으면 최적화보다 테스트·문서를 쓰는 것이 낫습니다.**

**③ 알고리즘 개선 — 가장 큰 이득**

```python
# ❌ O(n²)
for a in list_a:
    if a in list_b:          # list 의 in 은 O(n)
        ...

# ✅ O(n)
set_b = set(list_b)
for a in list_a:
    if a in set_b:           # set 의 in 은 O(1)
        ...
```

[Day 007](day-007.md)에서 봤듯이 **25,000배 차이**가 날 수 있습니다.
병렬화로는 절대 못 따라갑니다.

**④ 벡터 연산 — 수십~수백 배**

```python
# ❌ 반복문
result = [x * x for x in values]        # 0.05초

# ✅ NumPy
result = arr ** 2                        # 0.0001초  (500배)
```

**측정 결과에서 NumPy가 병렬 프로세스보다 수천 배 빨랐습니다.**

**⑤ 불필요한 작업 제거**

```python
# 필요한 컬럼만 (Day 026)
pd.read_csv(path, usecols=["a", "b"])

# 필요한 행만 — 읽고 나서 버리지 말고
pd.read_parquet(path, filters=[("year", "==", 2026)])

# 중복 계산 제거
df["mean"] = df.groupby("g")["x"].transform("mean")     # 한 번만
```

**⑥ dtype·저장 포맷 최적화 — 수 배**

```
CSV + object       : 1,018 MB, 12초
Parquet + category :    27 MB, 0.4초      ← 30배
```

[Day 026](day-026.md)·[027](day-027.md)의 내용입니다.
**코드를 거의 안 바꾸고 얻는 이득**이므로 먼저 하세요.

**⑦ 캐싱**

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def expensive(x):
    ...
```

같은 계산을 반복한다면 결과를 재사용하세요.

**⑧ 그래도 느리면 — 이제 병렬화**

**병렬화 전 체크리스트**

- [ ] 작업 하나가 **0.1초 이상**인가
- [ ] CPU 바운드인가 I/O 바운드인가 (**측정**)
- [ ] 프로세스에 넘길 데이터가 작은가 (경로 전달 가능한가)
- [ ] 작업이 **독립적**인가 (서로 결과를 참조하지 않는가)
- [ ] 함수가 **모듈 최상위**에 있는가 (pickle 가능)
- [ ] 메모리가 충분한가 (워커 × 작업당 메모리)
- [ ] I/O 병목이 아닌가 (디스크·네트워크)

**성능 개선 효과 비교**

| 방법 | 개선 폭 | 코드 복잡도 |
|---|---|---|
| 알고리즘 개선 | 10~10000배 | 중간 |
| **벡터 연산** | 50~500배 | **낮음** ⭐ |
| dtype 최적화 | 2~30배 | **매우 낮음** ⭐ |
| Parquet 전환 | 3~10배 | **매우 낮음** ⭐ |
| 캐싱 | 상황에 따라 | 낮음 |
| **병렬화** | **최대 코어 수** | **높음** ⚠ |
| 분산 처리 | 노드 수만큼 | 매우 높음 |

**병렬화의 숨은 비용**

- 디버깅이 어렵다 (어느 프로세스에서 났는지)
- 로그가 뒤섞인다
- 재현이 어렵다 (실행 순서가 매번 다름)
- 테스트가 복잡하다
- 예외 처리를 신경 써야 한다
- `if __name__ == "__main__"` 등 제약이 생긴다

**결론**

> **"측정하고, 쉬운 것부터, 병렬화는 마지막에."**

이 순서를 지키면 대부분 병렬화까지 가지 않고 끝납니다.
</details>

## 오늘의 정리

| 항목 | 내용 |
|---|---|
| GIL | 파이썬 바이트코드를 **한 번에 하나의 스레드만** 실행 |
| GIL 해제 | 네트워크·파일 I/O·`sleep`·일부 NumPy 연산 |
| 프로세스 | 메모리 독립 · GIL 없음 · 생성 비용 큼 · **CPU 작업** |
| 스레드 | 메모리 공유 · GIL 영향 · 생성 저렴 · **I/O 작업** |
| 판단법 | CPU 사용률 = `process_time / perf_counter` — >70% CPU, <30% I/O |
| 실행기 | `ProcessPoolExecutor` · `ThreadPoolExecutor` |
| 결과 수집 | `pool.map()` 순서대로 · `as_completed()` 완료순 |
| 워커 수 | CPU: 코어 수 · I/O: `min(32, 코어×4)` — **측정해서 결정** |
| 필수 | `if __name__ == "__main__":` (Windows·macOS) |
| pickle 제약 | 람다·클로저 불가 → **모듈 최상위 함수** |
| 데이터 전달 | 큰 DataFrame 대신 **경로 전달** |
| 예외 | `future.result()` 를 호출해야 드러남 |
| 스레드 공유 | `threading.Lock` · `threading.local()` |
| 손익분기점 | 작업 하나가 **0.1초 이상** |
| **순서** | 측정 → 알고리즘 → **벡터 연산** → dtype/Parquet → 병렬화 |

**과제** — [Day 026](day-026.md)–[027](day-027.md)의 처리를 병렬화하세요.
① 파일 100개를 처리하는 스크립트를 만들고 **순차·스레드·프로세스를 비교**
② 워커 수를 2·4·8·코어수로 바꿔 가며 **배속과 효율 표** 작성
③ CPU 사용률을 측정해 **CPU/I/O 바운드 판정**을 코드로 자동화
④ 큰 DataFrame 전달 vs 경로 전달의 **직렬화 비용 비교**
⑤ 일부러 실패하는 파일을 섞어 **예외가 격리되고 나머지가 계속되는지** 확인
⑥ 병렬화 전에 dtype·Parquet 최적화를 먼저 적용해 **각 단계의 개선 폭 비교표** 작성
⑦ `docs/performance.md` 에 "무엇을 왜 했고 얼마나 빨라졌는가"를 기록
