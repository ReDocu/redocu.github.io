## ③ 개념 설명

## 1부 · 12분 발표 설계

### 시간 배분

| 구간 | 시간 | 슬라이드 | 내용 |
|---|---|---|---|
| 도입 | 1분 | 2 | 문제 · 왜 흥미로운가 |
| 데이터 | 1.5분 | 2 | 출처 · 규모 · **특이점 1개** |
| 접근 | 2분 | 3 | 베이스라인 · 핵심 판단 2개 |
| **결과** | 3분 | 3 | 성능 · **구간별 차이** |
| ★ **한계** | 2.5분 | 2 | 어디서 못하는가 · 왜 |
| 배운 것 | 1.5분 | 1 | 실패에서 배운 것 |
| 마무리 | 0.5분 | 1 | 다음 단계 |
| **합계** | **12분** | **14장** | |

**슬라이드 1장당 평균 50초.** 그보다 많으면 못 넘깁니다.

### ★ 한계에 2.5분을 배정한 이유

```
성능 자랑 5분 + 한계 30초  → "숨기는 게 있나?"
성능 3분 + 한계 2.5분      → "이 사람은 자기 모델을 안다"
```

**심사자는 한계 설명의 깊이로 이해도를 판단합니다.**

### 슬라이드 원칙

| | |
|---|---|
| 한 장 = 한 메시지 | 제목이 곧 주장 |
| 글자 | 장당 40단어 이하 |
| 폰트 | 24pt 이상 |
| 표 | 5행 × 4열 이하 |
| 그래프 | **[Day 132](day-132.md)에서 만든 것 재사용** |

### ★ 제목을 주장으로 쓰세요

```
✗ "구간별 성능"
✓ "16~30% 구간은 정확, 75% 이상은 예측 불가"
```

**제목만 읽어도 발표 전체가 이해되게 만드세요.**

## 2부 · 질의응답 준비

### 반드시 나오는 질문 5가지

| # | 질문 | 준비 |
|---|---|---|
| 1 | 왜 이 모델을 골랐나요? | 종합 근거표 3줄 |
| 2 | 신경망은 써 봤나요? | 실패 기록 (MAE 8.42) |
| 3 | 데이터 누수는 없나요? | 6항목 점검 + 실측 |
| 4 | 실제로 쓸 수 있나요? | 사용 범위 · 신뢰도 |
| 5 | 더 개선한다면? | 8절 우선순위 |

### 답변 3단 구성

```
① 결론 한 문장
② 근거 (숫자)
③ 한계 인정
```

**예시**

```
Q. 성능이 좋아 보이는데 실제로 쓸 만한가요?

A. ① 일반적인 할인 구간에서는 쓸 만합니다.
   ② 전체의 44%인 16~30% 구간에서 MAE 4.2%p입니다.
   ③ 단 75% 이상 대폭 할인은 MAE 38로 예측 못 합니다.
      그래서 예측 모듈이 그 구간에 "신뢰도 낮음"을 반환합니다.
```

### ★ 모르는 것은 모른다고 하세요

```
✗ "아마 그럴 겁니다"
✓ "확인 안 해 봤습니다. 확인하려면 ~를 하면 됩니다"
```

**추측으로 답했다가 틀리면 발표 전체의 신뢰를 잃습니다.**

## 3부 · 상호 평가

### 평가 기준 6항목

| 항목 | 배점 | 무엇을 보는가 |
|---|---|---|
| 문제 정의 | 15 | 목표·성공 기준이 명확한가 |
| 방법의 타당성 | 20 | **근거를 대는가** |
| 결과의 정직성 | 20 | ★ 한계를 말하는가 |
| 재현 가능성 | 15 | 남이 돌릴 수 있는가 |
| 전달력 | 15 | 12분 안에 이해되는가 |
| 질의응답 | 15 | 근거로 답하는가 |

### 평가할 때 주의

```
✗ "잘했어요"           → 도움 안 됨
✓ "3번 슬라이드에서 왜 층화 분할을 했는지 근거가 없었습니다"
```

**구체적으로, 슬라이드 번호를 붙여서.**

## 4부 · 회고문서

### 회고 ≠ 소감문

| | 소감문 | 회고문서 |
|---|---|---|
| 내용 | "어려웠지만 보람있었다" | "Day 129에서 3시간 낭비. 원인은 ~" |
| 근거 | 느낌 | **사실·시간·숫자** |
| 용도 | 없음 | **다음 프로젝트에 적용** |

### 4개 항목 (KPT + T)

```
Keep     계속할 것
Problem  문제였던 것
Try      다음에 시도할 것
★ Time   시간을 어디에 썼는가
```

### ★ 시간 기록이 핵심입니다

```
"데이터 수집에 2일, 예상은 반나절이었다"
→ 다음 프로젝트에서 4배로 잡는다
```

**추정치가 정확해지는 유일한 방법입니다.**

## ⑥ 확인 문제 — 대단원 04 종합

<details><summary>1. 회귀 신경망의 출력층과 활성화 함수는?</summary>

`Dense(1)`, 활성화 없음(선형).
분류처럼 `softmax`/`sigmoid` 를 붙이면 출력 범위가 제한돼 학습이 안 됩니다.
[Day 106](day-106.md)

</details>

<details><summary>2. MSE와 MAE는 각각 무엇을 쫓는가?</summary>

MSE는 **평균**, MAE는 **중앙값**을 쫓습니다.
이상치가 있으면 MSE가 크게 끌려갑니다. Huber는 그 중간입니다.
[Day 106](day-106.md)

</details>

<details><summary>3. P/S 비율이란? 권장 범위는?</summary>

파라미터 수 ÷ 샘플 수. 권장 **0.3 ~ 3**.
우리 프로젝트의 (128,64) 신경망은 **9.87** 로 과다했고, 실제로 성능이 나빴습니다.
[Day 107](day-107.md) · [Day 129](day-129.md)

</details>

<details><summary>4. 진짜 베이스라인은 무엇이어야 하는가?</summary>

`DummyRegressor`(평균)가 아니라 **현실에서 실제로 쓰이는 방식**.
우리는 "가격대별 평균 할인율"(MAE 11.82)을 기준으로 삼았습니다.
평균 예측(13.84)을 이기는 것은 의미가 없습니다.
[Day 108](day-108.md) · [Day 128](day-128.md)

</details>

<details><summary>5. TargetEncoder를 Pipeline 밖에서 쓰면?</summary>

**누수**. 우리 데이터에서 검증 MAE가 7.84 → 3.61로 54% 부풀려졌고,
게임이 1개뿐인 개발사 218행에서 인코딩값-타깃 상관이 **1.0000** 이었습니다.
`cv=5` 로 Pipeline 안에 넣어야 합니다.
[Day 113](day-113.md) · [Day 128](day-128.md)

</details>

<details><summary>6. 잔차 플롯의 x축은 무엇이어야 하는가? 왜?</summary>

**예측값**. 실제값을 쓰면 잔차와 구조적으로 상관돼 항상 우하향 패턴이 나타납니다.
없는 문제가 보이고, 있는 문제가 가려집니다.
[Day 118](day-118.md) · [Day 132](day-132.md)

</details>

<details><summary>7. 예측 vs 실제 산점도의 회귀선 기울기가 0.71이면?</summary>

**평균 회귀**. 극단값을 29% 덜 반영합니다.
원인은 ① 특성 정보 부족 또는 ② 과적합.
**학습셋 기울기를 함께 보면 구분됩니다.** 학습에서도 낮으면 ①입니다.
[Day 118](day-118.md) · [Day 129](day-129.md)

</details>

<details><summary>8. 하이퍼파라미터 개선이 "의미 있다"의 기준은?</summary>

**seed 변동폭보다 커야 합니다.**
우리는 1.13%를 측정하고 그 절반(0.57%)을 기준으로 삼아,
`min_samples_leaf`·`l2_regularization`·`max_features` 3단계를 기각했습니다.
[Day 123](day-123.md) · [Day 130](day-130.md)

</details>

<details><summary>9. 테스트셋으로 후보 3개를 평가한 뒤 최고를 고르면?</summary>

**테스트셋이 검증셋이 됩니다.** 보고 성능이 낙관적으로 왜곡됩니다.
선택은 테스트를 열기 전에 확정하고 문서로 남겨야 합니다.
우리는 테스트에서 스태킹이 0.96% 좋게 나왔지만 선택을 바꾸지 않았습니다.
[Day 125](day-125.md) · [Day 131](day-131.md)

</details>

<details><summary>10. 전체 MAE 7.68 하나만 보고하면 안 되는 이유는?</summary>

구간별로 크게 다르기 때문입니다.
16~30% 구간(n=266) **4.22** vs 76~90% 구간(n=18) **38.41** — 9배 차이.
평균 하나로 뭉뚱그리면 위험한 곳에 모델을 쓰게 됩니다.
[Day 131](day-131.md)

</details>

<details><summary>11. 학습-서빙 왜곡(training-serving skew)이란? 어떻게 막는가?</summary>

학습과 서빙에서 파생 특성을 **다르게 계산**하는 것.
조용히 틀리기 때문에 가장 위험합니다.
`features.py` 하나를 양쪽에서 import하고,
원시 데이터로 재계산해 **최대 차이 < 1e-6** 을 확인합니다.
[Day 133](day-133.md)

</details>

<details><summary>12. 보고서에서 가장 중요한 절은? 왜?</summary>

**7절 한계와 실패한 시도.**
성공만 적힌 보고서는 검증되지 않은 보고서입니다.
실패 기록은 다음 사람의 시간을 아끼고, 심사자에게 "충분히 탐색했다"는 신뢰를 줍니다.
[Day 134](day-134.md)

</details>

<details><summary>13. 재현 가능성을 "확인"하는 방법은?</summary>

**실제로 처음부터 돌려 보는 것.**
seed를 고정했다고 재현되는 것이 아닙니다.
우리는 7/8을 통과했고, 실패한 항목(노트북 순서 의존)을 부록에 그대로 적었습니다.
[Day 134](day-134.md)

</details>

<details><summary>14. 이 프로젝트에서 성능 개선에 가장 크게 기여한 것은?</summary>

**특성 공학 (+11.9%p).** 튜닝(+2.8%p)의 4.3배입니다.
[Day 119](day-119.md)의 "전처리·특성이 하이퍼파라미터보다 중요하다"가 재현됐습니다.
[Day 129](day-129.md) · [Day 130](day-130.md)

</details>

<details><summary>15. 대단원 04의 한 문장은?</summary>

**"성능을 올리는 것보다 성능을 정확히 아는 것이 어렵다."**

MAE 7.68을 만드는 데 9일, 그 7.68이 어디서 4.2이고 어디서 38.4인지
아는 데 하루가 더 걸렸습니다. 그리고 그 하루가 가장 가치 있었습니다.

</details>
