## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- **명세 표의 각 칸을 테스트 하나로** 번역해, 한 줄 명령으로 전부 도는 테스트를 만들 수 있다.
- 전처리 일치를 **회귀 테스트로 고정**할 수 있다 (학습 기록 재현 테스트).
- README(실행)와 보고서(증거)를 역할에 맞게 완성할 수 있다.
- clone 리허설과 상호 리뷰로 **남의 눈**을 통과할 수 있다.

---

## ② 왜 필요한가

MP2 마무리 날([Day 074](../03-machine-learning/day-074.md))과 같은 원리입니다 — 목요일의
문서·테스트는 장식이 아니라 **어제까지 만든 것의 증거화**입니다. 다른 점 하나: API의
테스트는 ML 스크립트보다 훨씬 직접적입니다. 명세 표가 이미 있으므로 **표의 칸 수만큼
테스트를 쓰면 끝**이고, 단원 완료 조건이 그 실행 방법까지 정해 뒀습니다 —
"API 통합 테스트가 CI 없이도 **한 줄로** 실행된다."

그리고 내일 발표의 리허설이 오늘의 clone 리허설입니다. 심사위원의 첫 행동은 발표를 듣는
것이 아니라 **README대로 실행해 보는 것**입니다.

## ③ 개념 설명

### 추론 API의 테스트 3층

| 층 | 검증 대상 | 도구 | 서버 필요? |
|---|---|---|---|
| 단위 | service.predict_image — 전처리·추론 | 그냥 pytest | ❌ (HTTP 무관 — 어제 경계 설계의 보상) |
| **계약** | 명세 표의 모든 칸 (상태 코드·응답 스키마) | TestClient | ❌ (앱 객체 직접 호출) |
| 회귀 | **학습 기록 재현** (0.7214가 오늘도 나오는가) | TestClient | ❌ |

[Day 094](day-094.md)와 다른 점 하나 — 추론 API의 TestClient는 **lifespan에서 진짜 모델을
로드**합니다 (가짜 모델로 바꾸면 회귀 테스트가 무의미). 그래서 `with TestClient(app)`
블록이 필수이고, 모델 로드 시간만큼 테스트 시작이 느립니다 — 모듈 스코프 fixture로 1회만.

### 무엇을 고정하고 무엇을 고정하지 않나

[Day 074](../03-machine-learning/day-074.md)의 "성능 숫자를 테스트로 고정하지 않는다"가
여기서 정교해집니다:

| 고정 ✅ | 고정 ❌ |
|---|---|
| 특정 입력의 확신도 (0.7214 ± 0.001) — **모델 파일이 저장소에 고정돼 있으므로** 결정적 | 처리량·지연 (하드웨어 따라 다름) |
| 상태 코드·응답 필드 (계약) | 새 데이터에 대한 정확도 (그건 평가지 테스트가 아님) |

모델 파일이 바뀌면 회귀 테스트도 함께 갱신합니다 — 그 "함께 바뀜"이 바로 이 테스트의
존재 이유입니다 (모델만 바뀌고 기록이 안 바뀌는 사고를 잡음).

### 문서 3종의 역할 분담

| 문서 | 독자의 질문 | 핵심 |
|---|---|---|
| README | "어떻게 실행하나" | 복사-실행 가능한 명령 3줄 (환경 · 서버 · 테스트) |
| docs/mp3_plan.md | "무엇을 왜 만들었나" | Day 101 그대로 + 변경 이력 |
| docs/report.md | "증거는?" | 정확성 대조표 · 성능 비교표 · 로그 집계 · 한계 |

## ④ 단계별 실습

### Step 1. 테스트 작성 (1~3교시)

명세 표를 옆에 두고 칸마다 하나씩. 예시 프로젝트의 `tests/test_api.py` (핵심):

```python
# tests/test_api.py — 명세 표의 각 칸 = 테스트 하나
import io

import pytest
from fastapi.testclient import TestClient

from app.main import app

ANT = "tests/fixtures/ant.jpg"          # 검증 세트에서 고른 고정 표본 1장 (저장소에 포함)


@pytest.fixture(scope="module")
def client():
    with TestClient(app) as c:          # with 블록이 lifespan(모델 로드)을 실행한다
        yield c


def test_health_reports_model(client):
    r = client.get("/health")
    assert r.status_code == 200
    assert r.json()["model_loaded"] is True


def test_predict_ok(client):
    with open(ANT, "rb") as f:
        r = client.post("/predict", files={"file": ("ant.jpg", f, "image/jpeg")})
    body = r.json()
    assert r.status_code == 200
    assert body["label"] in ["ants", "bees"]
    assert 0.5 <= body["confidence"] <= 1.0
    assert body["model_version"] == "antbee-resnet18-d085"


def test_predict_matches_training_record(client):
    """전처리 일치의 회귀 방지: Day 085 기록(개미 0.7214)이 재현되는가."""
    with open(ANT, "rb") as f:
        r = client.post("/predict", files={"file": ("ant.jpg", f, "image/jpeg")})
    body = r.json()
    assert body["label"] == "ants"
    assert abs(body["confidence"] - 0.7214) < 0.001


def test_fake_image_415(client):
    fake = io.BytesIO("그림 아님".encode("utf-8"))
    r = client.post("/predict", files={"file": ("cat.jpg", fake, "image/jpeg")})
    assert r.status_code == 415


def test_oversize_413(client):
    big = io.BytesIO(b"\x00" * (5 * 1024 * 1024 + 1))
    r = client.post("/predict", files={"file": ("big.jpg", big, "image/jpeg")})
    assert r.status_code == 413


def test_missing_file_422(client):
    r = client.post("/predict")
    assert r.status_code == 422
```

(+ /model/info 버전 확인, 배치 = 단건 일치, 배치 17장 413 — 명세의 나머지 칸들.)

```
$ pytest -q
.......                                                                  [100%]
7 passed, 1 warning in 4.22s
```

**4.22초** — 모델 로드(~2초) 포함입니다. 서버도 브라우저도 없이, 회귀 테스트(0.7214 재현)까지
한 줄로 돕니다. 이 한 줄이 단원 완료 조건의 마지막 항목입니다.

### Step 2. README와 보고서 (4~6교시)

README — 심사위원이 실제로 타이핑할 세 덩어리만:

```markdown
# 개미/벌 분류 API (MP3)

곤충 사진을 업로드하면 개미/벌 판정을 돌려주는 추론 API.
모델: ResNet18 전이학습 (valid 정확도 0.954) · 명세: docs/mp3_plan.md

## 실행
python -m venv .venv && .venv\Scripts\activate && pip install -r requirements.txt
uvicorn app.main:app --port 8103        # → http://127.0.0.1:8103/docs 에서 시연 가능
pytest -q                                # 테스트 (모델 로드 포함 ~5초)
```

보고서(docs/report.md) — 이번 주 만든 증거들의 편집입니다:

```markdown
# MP3 결과 보고서 — 개미/벌 분류 API

## 1. 서비스와 명세        ← 기획서 요약 + 변경 이력 (배치 실패 정책 등)
## 2. 서빙 정확성
   | 입력 | 학습 기록 | API 응답 | ✅ |  ← Day 102의 대조표 (+ 배치=단건 대조)
## 3. 성능
   측정 조건 명시 · 전후 비교표 (33.4 → 46.5장/s, +39%) · 용도별 처방 두 줄
## 4. 관측
   로그 스키마 (요청/예측) · 하루 집계 예시 (p50 30.7ms · 판정 분포) · 개인정보 판단
## 5. 한계와 향후 과제
   개미/벌 외 곤충은 둘 중 하나로 강제 판정됨(다중 클래스 아님 — 소비자 주의사항) ·
   단일 워커 · 인증 없음(과정 범위 밖) · W24에서 컨테이너화 예정
```

5절의 첫 항목을 주목하세요 — 나비 사진을 보내도 이 API는 "개미 또는 벌"로 답합니다.
모델의 세계관 밖 입력을 한계로 **명시**하는 것이 모델 카드([Day 069](../03-machine-learning/day-069.md))의
"비대상" 칸이 API 문서로 넘어온 것입니다.

### Step 3. clone 리허설 (7교시)

[Day 066](../03-machine-learning/day-066.md)의 의식 그대로 — 새 폴더에 clone하고 README의
세 덩어리를 **그대로** 타이핑합니다. venv 생성 → 설치 → 서버 기동 → /docs에서 업로드 1회 →
pytest 초록. 중간에 README에 없는 지식(경로 수정, 빠진 패키지, 모델 파일 위치)이 필요했다면
그것이 버그입니다 — README를 고치고 다시.

### Step 4. 상호 리뷰 (8교시)

[Day 095](day-095.md)의 리뷰 5축에 MP3 특화 항목을 얹어 옆 사람과 교차 심사:

- /docs만 보고 업로드 시연이 되는가 · **500이 나는 입력 찾기 게임 10분** (괴상한 파일 환영: 0바이트, 1×1픽셀, 50MB, 확장자 없음, GIF, …)
- service.py에 fastapi import가 없는가 · 로그에 원본 이미지가 안 남는가
- 회귀 테스트가 있는가 (없으면 "전처리 일치를 무엇으로 보증하나요?"라고 물어보세요)

```powershell
git add tests docs README.md
git commit -m "MP3 Day4: 테스트 7종(회귀 포함) 4.2초 · README 3줄 · 보고서 — clone 리허설 통과"
```

**오늘 퇴근 체크** — □ pytest 한 줄 전부 초록 □ 회귀 테스트(기록 재현) 포함 □ clone 리허설
통과 □ 보고서에 대조표·비교표·한계 □ 리뷰 지적 반영 커밋

## ⑤ 자주 하는 실수

### 성능 숫자를 테스트로 고정

**증상** — `assert duration_ms < 50` — 심사위원의 노트북에서 빨갛게 터짐.
**원인** — 결정적인 것(계약·기록 재현)과 환경 의존적인 것(속도)의 구분 실패.
**해결** — 속도는 보고서의 숫자(측정 조건과 함께), 테스트는 계약과 재현만. [Day 074](../03-machine-learning/day-074.md)의 규칙이 API에서도 그대로입니다.

### 테스트가 대용량·외부 자원에 의존

**증상** — 테스트가 hymenoptera 전체 데이터셋이나 인터넷 다운로드를 요구 — clone한 사람은 실행 불가.
**원인** — 개발 환경의 파일 배치를 전제로 씀.
**해결** — 고정 표본 1~2장을 `tests/fixtures/`에 포함(수십 KB). 저장소만 있으면 도는 것이 테스트의 자격입니다.

### 회귀 테스트를 "대충 맞으면 통과"로 씀

**증상** — `assert body["label"] == "ants"`만 확인 — 전처리가 어긋나 0.72 → 0.55가 돼도 초록.
**원인** — 라벨은 확률이 많이 깎여도 한참 뒤에야 뒤집힙니다.
**해결** — 확신도까지 허용 오차로 고정 (`abs(c - 0.7214) < 0.001`). 조용한 열화를 잡는 것이 목적이므로 민감해야 합니다.

### README의 명령을 안 돌려 봄

**증상** — `pip install -r requirements.txt`에 python-multipart가 빠져 있음 — 심사위원의 첫 5분이 에러.
**원인** — 자기 환경에는 이미 깔려 있어 못 느낌.
**해결** — clone 리허설이 정확히 이것을 잡습니다. 새 venv에서 README만으로.

### 마지막 날 새 기능을 넣음

**증상** — 목요일 밤의 "웹 데모 페이지 금방인데?" — 금요일 아침 서버가 안 뜸.
**원인** — 마무리 날의 목적(안정화·증거화)과 반대 방향의 작업.
**해결** — 오늘 이후 코드 변경은 리뷰 지적 반영만. 아이디어는 보고서 5절 "향후 과제"로.

## ⑥ 확인 문제

**Q1.** 회귀 테스트(0.7214 재현)가 잡아 주는 사고를 구체적 시나리오 두 개로 들어 보세요.

<details>
<summary>답 보기</summary>

① 리팩터링 중 전처리 수정: 누군가 PREPROCESS의 Resize(256)를 Resize(224)로 "정리" — 라벨은
대부분 유지되지만 확률이 이동하고, 테스트가 즉시 빨간불. ② 모델 파일 교체 누락/실수: 새 체크포인트를
올리며 회귀 기준을 안 바꿨거나, 반대로 모델은 옛것인데 코드만 새것 — 기록과 응답의 불일치가 잡힘.
공통점은 둘 다 **에러 없이 조용히** 일어나는 열화라는 것 — 그래서 라벨이 아니라 확률로 고정합니다.

</details>

**Q2.** "테스트는 진짜 모델을 로드한다(가짜 금지)"가 [Day 094](day-094.md)의 "무거운 의존성은
가짜로 바꾼다(FakeRepository)"와 충돌하지 않는 이유를 설명하세요.

<details>
<summary>답 보기</summary>

가짜로 바꾸는 대상은 **검증 대상이 아닌** 무거운 의존성(DB — 우리가 검증할 것은 SQL이 아니라 API
로직)입니다. MP3에서 모델과 전처리는 부속이 아니라 **검증 대상 그 자체**(서빙 정확성)이므로 가짜로
바꾸면 테스트의 목적이 사라집니다. 기준은 "무겁냐"가 아니라 "그것이 검증 대상이냐" — 대신 비용은
모듈 스코프 fixture(로드 1회)로 관리합니다.

</details>

**Q3.** 보고서 5절에 "개미/벌 외 곤충은 둘 중 하나로 강제 판정"을 명시하는 것과, 코드에서
낮은 확신도를 거절(4xx)하는 것 — 두 접근의 차이와 올바른 조합을 쓰세요.

<details>
<summary>답 보기</summary>

문서 명시는 모델의 세계관(이진 분류)을 소비자에게 알려 **판단을 소비자에게 넘기는** 것이고, 코드 거절은
서비스가 판단을 대신하는 **제품 결정**입니다 ([Day 102](day-102.md) ⑤). 올바른 조합: 한계는 반드시
문서에 명시하고, 거절 정책을 도입하려면 명세에 선언(예: confidence < 0.6 → 200 + "uncertain": true
같은 표시)한 뒤 테스트로 고정 — 몰래 넣는 것만이 오답입니다.

</details>
