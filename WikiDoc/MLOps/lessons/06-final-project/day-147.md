## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 검증 규칙을 4개 층(형식 · 범위 · 무결성 · 신선도)으로 설계하고 코드로 강제할 수 있다.
- 현실 데이터의 사건(결측·재게시·행수 이상)을 **검증 경보 → 조사 → 규칙 갱신**의 절차로
  다룰 수 있다.
- **데이터 명세**(`docs/DATA.md`) — 하류 사용자(모델·API)를 위한 계약 — 를 쓸 수 있다.
- 학습 데이터셋의 범위와 홀드아웃 경계를 팀 합의로 확정할 수 있다.

---

## ② 왜 필요한가

"데이터 다 모았어요"는 완성이 아닙니다. 이 단원에서 **데이터 완성의 정의는 두 가지가
갖춰진 상태**입니다: ① 데이터가 지켜야 할 약속이 명세로 적혀 있고, ② 약속 위반이
사람에게 들리게(경보) 되어 있는 것.

이 정의가 필요한 이유는 나쁜 데이터의 대부분이 **조용하기** 때문입니다. 시끄러운 문제
(API 다운, 형식 오류)는 어차피 발견됩니다. 프로젝트를 갉아먹는 것은 조용한 문제입니다 —
하루 빠진 역 하나, 소리 없이 0이 된 값, 재게시로 바뀐 과거. 이런 것들은 DB에선 멀쩡해
보이고, 몇 주 뒤 모델 성능 저하나 이상한 예측으로, **원인에서 가장 먼 곳에서** 표출됩니다.
그때부터의 역추적 비용이 오늘 검증 규칙을 쓰는 비용의 수십 배입니다.

그리고 내일부터 민준(모델)이 이 데이터를 소비합니다. 명세 없는 데이터를 넘기는 것은
계약서 없는 하도급입니다 — "이 컬럼 결측 있어요?" "공휴일 표시는요?"가 전부 슬랙 질문이
되고, 답은 사람의 기억이 됩니다. 명세는 그 질문들의 소재지를 문서로 옮기는 일입니다.

---

## ③ 개념 설명

### 검증 규칙의 4개 층

| 층 | 질문 | 한산 팀 규칙 (subway_daily) |
|---|---|---|
| 형식 | 타입·필수 필드가 맞는가 | boardings/alightings는 int 변환 가능, 날짜는 YYYYMMDD |
| 범위 | 값이 상식적인가 | 0 ≤ 승하차 ≤ 500,000 · use_ymd는 미래 금지 |
| 무결성 | 행들의 관계가 맞는가 | **일 행수 = 51** · (use_ymd, station_id) 유일 · 역명은 station 마스터에 존재 |
| 신선도 | 데이터가 늦지 않은가 | max(use_ymd) ≥ 오늘−6일 — 위반 시 경보 (D-4 정상 + 여유 2일) |

층을 나누는 이유는 **위반의 대응이 다르기** 때문입니다 — 형식·범위 위반은 적재 거부
(우리 쪽 또는 원천의 버그), 무결성 위반은 적재하되 경고(부분 결측은 흔한 현실), 신선도
위반은 데이터가 아니라 **파이프라인의 문제**(수집이 안 돌고 있음)라는 신호입니다.

### 데이터 명세 — 하류를 위한 계약서

스키마(DDL)는 명세가 아닙니다 — 타입은 말해도 의미를 말하지 않기 때문입니다. 명세에
반드시 있어야 하는 것: 컬럼의 **의미와 단위** · 갱신 주기와 지연(D-4) · 결측의 의미와
빈도 · **알려진 특성**(공휴일 급감, 재게시 가능성) · 재현 절차(백필 명령).

### 현실 사건의 3유형

| 사건 | 정체 | 올바른 흡수 |
|---|---|---|
| 재게시 | 과거 날짜 데이터가 수정되어 다시 게시(reg_ymd 갱신) | upsert가 자연 흡수 — reg_ymd로 추적 가능 |
| 부분 결측 | 특정일 특정 역이 미게시 (일 행수 < 51) | 경고 + 결측 목록 기록, 이후 도착분이 채움 |
| 지연 확대 | 연휴 등으로 D-4가 D-6+ | 신선도 임계를 D-6으로 설계 + 위험 등록부 R1 |

셋 다 "버그"가 아니라 **원천의 정상 동작 범위**입니다. 우리 코드가 이를 전제하고 있는가
가 설계 품질이고, 전제의 증거가 검증 규칙과 명세입니다.

## ④ 단계별 실습

### Step 1. 백필 완료와 전수 검증 (1~2교시)

```
$ python -m src.pipeline.backfill --from 2025-05-15 --to 2026-08-13
[backfill] 456일 처리 · upsert 23,256행 · 실패 0 · API 호출 456회
$ python -m src.pipeline.validate_all
[validate] 총 48,756행 · 기간 2024-01-01 ~ 2026-08-13 (956일)
[validate] 형식 OK · 범위 OK · 유일성 OK
[validate] ⚠ 일 행수 51 미만: 2일 — 2025-02-17 (50행, 성수 결측) · 2025-09-29 (50행, 신답 결측)
[validate] 신선도 OK (max 2026-08-13, D-4)
```

**경보 두 건이 오늘의 주인공입니다.** 48,756행 중 눈으로는 절대 못 찾는 2행의 구멍을
무결성 규칙(일 행수 = 51)이 잡아냈습니다.

### Step 2. 사건 조사 — 경보에서 규칙 갱신까지 (3~4교시)

서연의 조사 기록 (이슈 #21로 등록):

```
1) 원천 재호출: 2025-02-17 응답에 실제로 성수 없음 (610행) → 우리 버그 아님, 원천 미게시
2) reg_ymd 확인: 인접일 성수 행은 정상 — 해당 일만 단발 누락
3) 하류 영향: mart 뷰에서 성수의 lag_7이 2025-02-24에 NULL → 민준과 협의: 학습 시
   해당 행 제외(연 2건 수준, 대치보다 정직)
4) 규칙 갱신: validate_all이 결측 (날짜, 역) 목록을 data_quality_log 테이블에 기록,
   동일 (날짜, 역)이 이후 도착하면 "지연 도착 회복"으로 자동 소거
```

포인트: 사건의 종착지가 수리 한 번이 아니라 **규칙의 갱신**(경보의 자동 관리)이라는 것 —
같은 사건이 다음에 오면 이제 시스템이 처리합니다.

### Step 3. 시간대 분포 적재 — #8 (5~6교시)

```
$ python -m src.pipeline.load_hourly --month 2026-07
[hourly] CardSubwayTime 2026-07 · 2호선 51역 × 20시간대 · share 합=1.0 검증 통과 · upsert 1,020행
```

share(역별 시간대 비중)의 검증 규칙은 하나면 충분합니다 — **역별 합이 1.0(±0.001)**.
비중의 정의상 성립해야 하는 성질을 검증으로 쓰는 것 — 범위 검증보다 강력한, 도메인이
공짜로 주는 불변식입니다.

### Step 4. 데이터 명세와 학습 데이터셋 확정 (7~8교시)

`docs/DATA.md` 확정 — 그리고 **홀드아웃 경계를 팀 회의로** 정합니다 (모델 담당 단독
결정이 아니라):

```
[학습 데이터셋 확정 — 팀 합의]
- 학습: 2024-01-01 ~ 2026-04-30   검증(홀드아웃): 2026-05-01 ~ 2026-07-31 (92일 × 51역 = 4,692행)
- 분리 기준: 시간 (Day 052의 원칙 — 무작위 분리는 미래 누수)
- 2026-08-01~ 은 건드리지 않음: 최종 주간의 "진짜 미래" 시연용
- 결측 2건(성수·신답)이 만드는 lag NULL 행은 학습에서 제외 (명세에 기록)
```

홀드아웃이 왜 팀 결정인가 — 이 경계가 품질 목표(MAE 20%↓) 판정의 **재판정**이기
때문입니다. 판정 기준을 판정받을 사람(모델 담당)이 혼자 정하면, 선의와 무관하게 기준의
신뢰가 흔들립니다.

**오늘 퇴근 체크** — □ 48,756행 + 전수 검증 통과(경보 2건 처리 포함) □ 검증 4층이
코드로 존재 □ hourly_share 적재·검증 □ DATA.md(알려진 특성 포함) □ 홀드아웃 팀 합의
기록

## ⑤ 자주 하는 실수

### 검증 규칙이 머리와 주석에만 있음

**증상** — "행수는 51이어야 하죠, 알죠" — 아는데 검사하는 코드가 없어 결측 2건이 무사
통과, 3주 뒤 모델 디버깅에서 발견.
**원인** — 아는 것과 강제되는 것의 혼동.
**해결** — 규칙마다 "이 규칙을 어기는 데이터를 일부러 넣으면 소리가 나는가"를 시험하세요.
소리 안 나면 그 규칙은 존재하지 않는 것입니다.

### 결측을 0이나 평균으로 조용히 채움

**증상** — 성수 2025-02-17이 0으로 채워짐 — 범위 검증(0 이상)도 통과, 모델은 "그날 성수에
아무도 안 탔다"고 학습.
**원인** — "빈 곳은 채워야 한다"는 반사 — 결측과 0은 완전히 다른 정보인데 채우는 순간
구분이 소멸합니다.
**해결** — 결측은 결측으로 남기고 **기록**하세요(data_quality_log). 채울지, 제외할지,
그대로 쓸지는 소비자(모델)가 명세를 보고 결정할 문제입니다 — 파이프라인의 일은 정직한
전달입니다.

### "명세요? DB 보면 알잖아요"

**증상** — 민준이 lag 피처를 만들다 "공휴일에 왜 급감하지? 버그인가?"로 반나절 소모 —
서연은 "그거 원래 그래요"를 알고 있었음.
**원인** — 스키마(구조)가 명세(의미·특성)를 대신한다는 착각.
**해결** — DATA.md의 "알려진 특성" 절이 바로 그 반나절의 보험입니다: 공휴일 급감 ·
D-4 지연 · 재게시 · 결측 이력. **아는 사람의 머리에서 문서로** — 이 이동이 명세 작업의
전부입니다.

### 홀드아웃을 모델 담당이 혼자 정함

**증상** — 발표 질의 "검증 구간은 왜 5~7월인가요?"에 팀원들이 서로 쳐다봄 — 기준을
정한 사람만 답할 수 있는 팀.
**원인** — 평가 설계를 모델 영역의 내부 사정으로 취급.
**해결** — 홀드아웃은 품질 목표의 재판정이므로 팀 합의 + 기록이 원칙입니다 (Step 4).
부수 효과: 합의 과정에서 "8월은 남겨서 최종 시연 때 진짜 미래로 쓰자" 같은 발표 자산이
나옵니다 — 혼자면 못 냈을 아이디어입니다.

## ⑥ 확인 문제

**Q1.** "조용한 문제는 원인에서 가장 먼 곳에서 표출된다"를 성수 결측 사례로 구체화하세요 —
검증이 없었다면 이 결측은 언제, 어떤 모습으로, 왜 그 자리에서 발견됐을까요?

<details>
<summary>답 보기</summary>

결측 자체는 무해해 보입니다(그냥 행이 하나 없음). 그러나 mart의 lag_7 계산이 그 날짜를
참조하는 순간 NULL이 생기고, NULL의 처리 방식에 따라 학습 행 소실(dropna) 또는 오염
(fillna)이 됩니다. 발견 시점은 아마 W30 후반 — 모델 성능이 미묘하게 이상하거나, 특정
역·날짜의 예측이 튀는 모습으로, 즉 "데이터 문제"가 아니라 "모델 문제"의 얼굴로 나타납니다.
그 자리에서 발견되는 이유는 그곳이 데이터가 처음으로 **사용되는**(따라서 전제가 처음
시험되는) 지점이기 때문입니다. 역추적은 모델 → 피처 → mart → raw → 원천의 5단계 — 오늘의
무결성 규칙 한 줄(일 행수=51)이 이 5단계를 0단계로 만든 것입니다.

</details>

**Q2.** 검증 4층의 위반이 각각 다른 대응(거부/경고/파이프라인 점검)을 갖는 이유를,
"위반이 가리키는 범인이 다르다"는 관점으로 정리하세요.

<details>
<summary>답 보기</summary>

형식·범위 위반의 범인은 코드(우리 파싱 버그 또는 원천의 형식 변경) — 이 데이터를 적재하면
DB의 불변식("안은 전부 검증 통과분")이 깨지므로 거부가 맞습니다. 무결성 위반(부분 결측)의
범인은 대개 원천의 정상적 흠결 — 거부하면 멀쩡한 50행까지 버리므로 적재+경고+기록이
맞습니다. 신선도 위반의 범인은 데이터가 아니라 **우리 파이프라인의 정지**(DAG 죽음, 키
만료) — 데이터 대응이 아니라 시스템 점검을 트리거해야 합니다. 대응이 범인을 향하지 않으면
경보는 소음이 되고, 소음이 된 경보는 곧 무시됩니다 — 층 구분은 경보의 신뢰를 지키는
설계입니다.

</details>

**Q3.** share 검증(역별 합=1.0)처럼 "도메인이 공짜로 주는 불변식"이 범위 검증보다 강력한
이유를 설명하고, subway_daily에서 쓸 수 있는 같은 종류의 불변식 후보를 하나 제안해 보세요.

<details>
<summary>답 보기</summary>

범위 검증(0~500,000)은 "말이 되는 값"만 거르므로 그럴듯한 오류(예: 두 배로 뻥튀기된 값)를
통과시킵니다. 불변식 검증은 데이터의 정의 자체에서 나오는 등식이라, 계산 과정 어디가
틀려도 등식이 깨져 발각됩니다 — 검출력이 값의 그럴듯함이 아니라 구조의 정합성에 걸려
있기 때문입니다. subway_daily 후보 예: "주중 승차 총량 ≫ 주말 승차 총량"(요일 구조),
"역별 승차 합 ≈ 하차 합의 장기 균형"(승차한 사람은 어디선가 내림 — 노선 단위 근사),
"어제 대비 전 역 동시 급변(±50%)은 이상"(도메인상 불가능한 동시성). 이런 규칙은 원천의
집계 방식 변경 같은 조용한 대형 사고를 잡는 몇 안 되는 그물입니다.

</details>
