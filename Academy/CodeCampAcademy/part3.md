# 제1부 · 나 혼자 MVP 만들기 (Day 17)

### 1. 솔로프리너와 규모의 장벽

- **솔로프리너(1인 기업가)** — 통계로 확인되는 흐름: 한국 1인 창조기업 **116만 곳(전체 창업의 23.7%)**, 미국 2,980만 명이 **GDP의 6.8%**. *"저비용 온라인 도구와 AI의 확산이 진입 장벽을 무너뜨렸다."*
- 예전에는 **[사람]** 기획·디자인·개발·마케팅 + **[기술]** 웹·안드로이드·iOS·결제·보안·서버·DB + **[관계]** 기업·고객·정부가 전부 필요했다. 칸마다 전문 인력 한 명 이상 = 자본 없이는 시작 불가.
- **장벽이 사라진 게 아니라 "한 사람이 감당 가능한 크기"로 줄었다.** 그래서 **각 칸이 무엇인지 아는 사람**이 이긴다.

### 2. 전체 프로세스 3축

| 축 | 내용 | 대응 도구 |
|---|---|---|
| **① 구성원 및 역할** | 기획자/PM · 디자이너 · 개발자 · 마케터 | 지라·컨플루언스 / 피그마·펜슬 / **클로드코드** / 구글애널리틱스 |
| **② 제품 구성 요소** | 웹(유저·관리자·사장님) · 앱(AOS/iOS) · 결제 · DB/배포 | 리액트 / 리액트네이티브·플러터 / 포트원·부트페이 / **Vercel·Supabase** |
| **③ 전자상거래 유형** | B2C · B2B · **B2B2C** · B2G · C2C | 쇼핑몰 / 회계 / **플랫폼** / 폐기물 / 중고거래 |

- **하이브리드 앱** — 웹 하나를 만들고 앱으로 씌운다(*"모든 회사 → 효율성과 이윤 추구 → 하나 만들어서 재사용하자!"*). 웹 기준 1200~1400px, 앱은 **태블릿 사이즈 + 양쪽 여백**.
- **결제는 붙이는 기능이 아니라 심사를 통과해야 열리는 문**이다. 상품·가격이 확정돼야 심사가 쉽고, 구독 결제는 시스템 자체가 다르다.
- **구조도의 결정적 차이** — 일반(B2C)은 화면 2종(유저·관리자), 플랫폼(B2B2C)은 3종(유저·**사장님**·관리자)이고 그래서 **"정산"** 이 생긴다. 이것이 플랫폼 수수료 BM과 직결되고, 1인 개발자에게 플랫폼이 경고되는 이유다.

> **🧩 퀴즈** — 웹을 만들고 앱으로 씌우는 방식? → **하이브리드 앱**

### 3. 비즈니스 모델 4가지

| 모델 | 무엇을 파나 | 사례 |
|---|---|---|
| **상품 판매** | 쇼핑몰·온라인 강의 | 몬스터기어, 그로스쿨 |
| **구독** | 매거진·기능 사용 | 혁신의숲(2만~30만), Supabase(Free/$25/$599) |
| **광고** | 배너 / **네이티브** | 에브리타임(배너), 네이버(콘텐츠처럼 섞인 '광고') |
| **플랫폼 수수료** | 거래 중개 | 숙소 예약·음식 배달 |

- **두 축으로 기억한다** — ①② 유저에게 **직접** 받는 돈 / ③④ **제3자**(광고주·사장님)에게서 받는 돈.
- **BM은 글이 아니라 삼각형 도식으로 확인한다.** 공급자↔플랫폼↔고객 화살표마다 "누가 무엇을 주고 무엇을 받는가"가 채워지는지 본다. **수수료가 어디서 떨어지는지가 곧 매출**이다.

> **🧩 퀴즈** — 콘텐츠 목록 안에 콘텐츠처럼 보이는 광고? → **네이티브 광고**

### 4. 스타트업 시장 유형 — 두 갈래뿐

| | **① 기존에 없던 서비스** | **② 이미 존재하는 서비스** |
|---|---|---|
| 전제 | 아이디어 O | 아이디어 X |
| 핵심 | **수요 검증** | **차별화** |

- **수요 검증의 유일한 신호**: "아이디어 좋네요!" ❌ / **"돈 내고서라도 쓸게요!"** ⭕
- 진입 절차: **카페·오픈채팅방 → 수동 판매(가격 조정 + 수요 검증) → 앱 전환.** *"앱이 없어서 안 팔리는 게 아니에요!"*
- 차별화: **품질**(불만 조사 → **불만 해결 난이도 검증** → 출시) · **가격**(경쟁사 기준). 가운데 단계가 핵심 — 고치기 쉬운 불만이면 이미 고쳐졌고, **구조적으로 못 고치는 불만이 내 자리**다.

**내 상황별 경고**

| 상황 | 판정 |
|---|---|
| 왕초보 | 플랫폼 BM 🚨 (화면 3종 + 정산) |
| 생활비가 중요 | 광고·플랫폼 BM 🚨 — 광고·플랫폼은 **시간 → 서비스**, 상품 판매·구독은 **돈 → 서비스** |
| 투자·확장이 중요 | 이미 존재하는 서비스 🚨 |
| 아이디어 없음 | 이미 존재하는 서비스 👍 |

### 5. PM-Skills와 PRD

```
유저 인터뷰 → 인터뷰 요약 → 인사이트·전략 가정 → 전략 가정 공격 → 우선순위 → 제품 브리프 → PRD
  (수동)    /summarize-meeting  (수동)     /strategy-red-team /prioritization-  (수동)   /create-prd
                                                                frameworks
```

- **수동으로 남은 단계는 전부 "판단"이고, 슬래시 명령이 맡은 것은 "정리·검증·비교"다.** 판단을 AI에 넘기지 않는 것이 이 파이프라인의 설계 의도.
- **PRD = 누가(페르소나) · 무엇을 · 왜** + 성공 검증(지표) + 최소/확장 기능.
- 실습 MVP — 누가: **서울 구로 주변, 자동차 보유한 가족 또는 커플** / 무엇: **페이지 5개**(로그인·마이·목록·등록·상세) / 왜: **반복적인 일상에서 벗어난 색다른 경험.**
- **MVP 요소 → PRD로 넘어갈 때 새로 생기는 것은 측정 방법(KR)과 제약 조건**이다. 기능 목록만으로는 성공 여부를 판단할 수 없다.

**📝 실습** — 맛집 커뮤니티 PRD 생성(`01-prd.txt` → `02-prd.md` "숨은 맛집").

# 제2부 · 디자인 시스템으로 MVP 그리기 (Day 18~22)

### 1. 디자인 툴 선택 — 시연할 것인가, 팔 것인가 (Day 18)

> 🐿️ *"페이지가 많아지니까, 기억도 안나고, 페이지마다 색상·간격·사이즈도 제각각이네…"* (30페이지)

- **프로토타입 툴의 한계는 단방향 핸드오프**다 — 최초 디자인 → 프로덕트까지는 가지만, 추가 디자인이 원본으로 **되돌아오지 않는다.** 고도화된 툴은 **핸드오프 ↔ 추가 디자인이 순환**한다.
- **프로토타입(시연 수준·페이지 적음) vs MVP(론칭 수준·페이지 많음)** — 기준은 완성도가 아니라 **목적과 페이지 수**.

| 상황 | 툴 |
|---|---|
| 프로토타입 | **클로드 디자인** (Stitch) |
| **1인 개발 MVP** | **Pencil** |
| 팀 협업 MVP 이상 | **Figma** (월 유료 구독 + 채팅창) |

- Pencil ↔ Figma는 양방향으로 갈아탈 수 있다(Pencil→Figma: 펜슬 플러그인 / Figma→Pencil: 복사·붙여넣기). **1인으로 만들고, 팀으로 확장할 때 Figma로.**

### 2. 적응형 vs 반응형, 그리고 기준 사이즈 360 (Day 18)

| | 적응형 | **반응형** |
|---|---|---|
| 정의 | 화면 크기와 **무관하게 고정** | 화면 크기에 맞게 **같이 변동** |
| 사례 | 네이버(잘림) | 야놀자(1줄→2줄 재배치) |

- **하이브리드 앱은 반응형이 전제**다. 구현은 두 가지 — **줄이기**(텍스트 2줄·이미지 찌그러짐) vs **늘이기**(여백만 변동) → **늘이기가 정답.**
- 기준 사이즈 = **[인기 있는 기기] ∩ [그중 최소 사이즈]** → **가로 360 × 세로 780(가변)**. 1위인 384×832가 아닌 이유는 **더 넓어서**(늘이기가 아니라 줄이기가 되므로), 320×694가 아닌 이유는 **큰 화면에서 여백이 폭주**하므로.
- 디자인 프로세스: 기초 = 레퍼런스 → 시스템 → 화면 / **심화 = 레퍼런스 → 메인 시안 2~3개 → 시스템 → 화면.** 가운데 단계가 있어야 **시스템을 "고른 시안"에서 뽑아낼 수 있다.**
- 시안 생성 입력 4종: **레퍼런스 · PRD · 사이즈 가이드(360×780) · 페이지 가이드(메인·상세·등록 **에러 상태**)**. 레퍼런스는 "예뻐서"가 아니라 **정보 구조가 같아서** 고르고, 등록 페이지는 **정상이 아니라 에러 상태로** 그린다.

> **🧩 퀴즈** — 화면 크기에 따라 디자인이 변하는 방식? → **반응형 디자인**

### 3. 디자인 시스템 ① — 컬러와 디자인 토큰 (Day 19)

> 🧑‍💼 *"브랜드 컬러 보라색을 조금 더 진하게 할 수 있니?"* 😨 *"지금 **70페이지**나 완성됐는걸요?"*
> **"이건 요청자의 잘못이 아니에요. 바로 지금, 디자인 시스템이 필요한 시점입니다."**

- **디자인 시스템은 "예쁘게"가 아니라 "바꿀 수 있게" 만드는 것.** 두 축: **① 파운데이션**(컬러·타이포·아이콘) **② UI 컴포넌트**(버튼·체크박스). 파운데이션이 먼저 서야 컴포넌트가 일관된다.
- **프리미티브 컬러 vs 시맨틱 컬러** — Orange=**브랜드**(강조), Sand=**중립**(Surface/Text/Card/Line), Amber=**경고**, Green=**성공**, Blue=**정보**, Red=**에러**. *"주황색을 쓴다"가 아니라 "브랜드 컬러를 쓴다"고 말해야 색이 바뀌어도 문장이 살아남는다.*
- 팔레트는 **50~950 (11단계)**, **500이 기준**. **3:1은 500부터 · 4.5:1은 600부터**(neutral-50 대비) → 왼쪽은 배경, 오른쪽은 텍스트.
- **최소명암비** — 일반 텍스트 **4.5:1**, 큰 텍스트 **3:1** (WCAG 1.4.3). **눈이 아니라 숫자로 검증**한다(Contrast Finder).

**디자인 토큰 2층 구조**

```
시맨틱 토큰      컬러-테두리-에러          컬러-텍스트-에러
                      ↑                        ↑
프리미티브 토큰   컬러-빨강-400            컬러-빨강-600
                      ↑                        ↑
HEX                #ff5155                  #ad0004
```

- 같은 "에러 빨강"도 **테두리용 400 / 텍스트용 600**으로 갈린다(텍스트는 4.5:1을 넘겨야 하므로). 이 판단을 매번 하지 않도록 **이름으로 굳혀두는 것**이 시맨틱 토큰.
- **절대 규칙: 시맨틱 토큰에 hex 직접 입력 금지, 프리미티브 참조만.** 이 두 줄이 2층 구조 전체를 지탱한다.
- **토큰을 만들었다고 적용된 게 아니다** — 컬러 팔레트 순서도는 **프리미티브 생성 → 시맨틱 생성 → 팔레트 렌더 → 기존 시안 리팩토링** 4단계다.

### 4. 파운데이션 프롬프트의 틀 — 5블록 · 3단 서식 (Day 19)

```
[헤더 한 문장]  다음 디자인시스템 가이드에 맞게 … 할 것.
  ===                                         ← 지시(위)와 명세(아래)를 가르는 선
[1] 컬러 추출        → 입력을 정한다 (화면내 디자인 시안 ← 창작 방지)
[2] 프리미티브 토큰  → 1층 (hex에 이름, "총 11개" × 6회)
[3] 시맨틱 토큰      → 2층 (hex 금지 + 프리미티브 참조)
[4] 팔레트 렌더      → 눈에 보이게 (신규 프레임 ← 기존 시안 보호)
[5] 최종 검토사항    → [  ] 체크박스로 스스로 채점
```

- 모든 블록이 **대상**(어디에) · **명칭/종류/방식**(무엇을) · **주의사항**(무엇을 하면 안 되나) 3단 서식을 쓴다. *"variables 메뉴"라고 못 박지 않으면 AI가 토큰을 캔버스에 텍스트로 적어놓고 "만들었다"고 한다.*
- **닫을 곳과 열 곳을 구분한다** — 프리미티브는 `(총 11개)`로 **닫고**, 시맨틱은 `...`로 **열어둔다**.
- **금지와 지시는 한 쌍**으로. 금지만 있으면 우회로를 찾고, 지시만 있으면 hex를 함께 적는다.
- **좋은 프롬프트는 한 번 쓰고 버리는 글이 아니라 다음 작업에 갈아끼우는 틀이다** — 같은 5블록이 타이포·아이콘에 그대로 재사용된다.

### 5. 파운데이션 ②③ — 타이포·아이콘, 그리고 첫 컴포넌트 (Day 20)

**결정적 차이: 컬러는 "값"으로 끝나지만, 타이포와 아이콘은 "컴포넌트"까지 가야 끝난다.** (글자와 아이콘은 그 자체가 화면에 놓이는 물건이므로)

| 프리미티브 | 값 |
|---|---|
| 사이즈 9단계 | `font-size-100`(12) ~ `font-size-900`(40) |
| 두께 3단계 | bold **700** · semibold **600** · regular **400** |
| 행간 2단계 | `tight` **1.2** · `normal` **1.4** |

- **구조 10종 = 프리미티브의 조합** — display-lg/md/sm(36/32/28), heading-lg/md/sm(24/20/16), body-lg/md(16/14), label-lg/md(14/12).
- **같은 크기, 다른 역할** — 16px에 `heading-sm`(semibold/tight)과 `body-lg`(regular/normal)가 함께 있다. **계층은 "크기 순서"가 아니라 "크기 × 두께 × 행간"의 조합.**
- **자간 -2%는 상대값** — 36px→-0.72, 12px→-0.24. px으로 주면 큰 글자는 티가 안 나고 작은 글자는 붙는다.
- **토큰 이름에는 값이 아니라 역할을 넣는다** — `tight`는 값이 바뀌어도 여전히 tight다. 그리고 `font-size-900`(40)은 **어느 구조에도 안 쓰인다** — 스케일은 **고를 수 있게** 만드는 것이지 전부 소비하려는 게 아니다.
- **아이콘** — 루시드 **36종 × 4사이즈(16·20·24·32) = 144개.** `20행으로 렌더 / 넘치면 기존 프레임 오른쪽 열` 규칙만으로 2열 레이아웃이 결정된다. **arrow(이동)와 chevron(펼침)은 둘 다 넣는다** — 비슷하게 생긴 것일수록 의미로 갈라 둔다.
- **첫 UI 컴포넌트: 아이콘 버튼 48×48 세 종류**(고스트·원형 브랜드·원형 뉴트럴). 안의 아이콘은 24 → **여백 12px이 곧 오터치 방지 영역**이다. 프롬프트 첫 문장이 *"디자인시스템 가이드"* → **"컴포넌트 가이드"** 로 바뀌는 것이 경계를 넘는 신호.

> **★ 오늘의 규칙 3종** ① 렌더는 **신규 프레임**, 컴포넌트 전환은 **"신규 프레임 생성하지 않음"**
> ② **안은 컴포넌트, 밖은 프레임** — 세 프롬프트에 주어만 바꿔 **3번 반복**된다(= AI가 3번 다 틀리는 지점). 바깥까지 컴포넌트면 `display-lg` 하나 쓰려 해도 10개가 딸려온다.
> ③ 개수·크기는 **반드시 숫자로**, 같은 말을 다르게 두 번(`사이즈별 1개당` + `아이콘 1개당 4개`).

### 6. UI 컴포넌트 본편 23종 (Day 21)

> "설마, 로그인 입력창·맛집 등록 입력창·닉네임 변경 입력창 각각 따로 만들었어?"
> "네, 어차피 AI가 금방 만들어 주잖아요"
> **"구현이 문제가 아니야… 수정이 문제지"** — *AI 시대 조심할 단어: "구현 됩니다"*

- 구현 비용은 AI가 0으로 만들었고, **병목은 수정 비용으로 이동**했다. 입력창을 화면마다 따로 만들면 수정 비용은 **화면 수에 비례**한다(100페이지면 100번).
- **컴포넌트 = 설정들을 적용해 포장해 놓은 부품.** 그리고 **"컴포넌트는 복사가 아닌 연결이에요"** — 연결이므로 원본 하나만 고치면 수정 비용이 **1**로 떨어진다.

| 그룹 | 정의 | 개수 |
|---|---|---|
| ① 액션 | 클릭하여 기능 실행 | 버튼 1종 |
| ② 폼 | 등록/수정 구성 요소 | **9종** |
| ③ 내비게이션 | 메뉴 정보 | 3종 |
| ④ 피드백 | 현재 상태 정보 | 3종 |
| ⑤ 기타 | 카드·모달 등 | 7종 |
| | | **23종** |

**프롬프트의 진화 — "공통조건"의 등장.** 5개 프롬프트에 **토씨 하나 다르지 않게** 반복된다. Day 19~20에서 매번 쓰던 주의사항이 **재사용 블록으로 승격**됐다 — 컴포넌트를 배우는 날, 프롬프트 자체가 컴포넌트화됐다.

```
1. 공통조건:
   - 프레임: 컴포넌트 1개당 신규 프레임 1개
   - 소스:   화면 내 디자인 시안 반영 / 컬러는 시맨틱 토큰 / 텍스트는 타이포그래피 프레임 /
            아이콘은 아이코노그래피 프레임 / 버튼 등은 이미 만들어져 있는 컴포넌트 프레임에서 선택
   - 정렬:   타입(행) * 상태(열)
   - 색상:   subtle 계열(파스텔/틴트)은 명시하지 않는 한 사용 금지
```

- **소스 4줄 = 디자인시스템의 의존성 그래프**(Day 19 컬러 → Day 20 타이포·아이콘 → 오늘의 컴포넌트). 마지막 줄이 핵심 — **컴포넌트가 컴포넌트를 참조**한다.
- **"타입(행) × 상태(열)" 매트릭스는 렌더 방식이자 QA 체크리스트**다 — 빈 칸이 곧 안 만든 상태.
- **상태 축은 그 컴포넌트가 하는 일에서 나온다** — 버튼은 `default·disabled·loading`(누르는 물건), 입력류는 `default·**focused**·disabled·**error**`(입력하는 물건). 복붙하면 안 된다.
- 세부 규칙들: loading은 **좌측 아이콘만 스피너로, 레이블 유지** / 헬퍼텍스트는 **에러시 힌트 대체**(폼 높이 널뛰기 방지) / 체크박스는 **선택 3 × 상태 3**(indeterminate 포함) / **라디오는 단독 금지, 스위치는 단독 전용** / 칩은 좌측 아이콘이 있으면 **패딩이 절반** / 바텀내비는 선택 시 **색과 형태(아웃라인↔필)를 둘 다** 바꾼다(색약 대비 이중 부호화).
- **컨트롤 vs 표시** — 체크박스·라디오·스위치의 체크는 **직접 드로잉**(컨트롤의 일부), 셀렉트아이템의 체크는 **아이콘 사용**(표시). **공통조건에 예외가 필요하면 예외를 개별조건에 명시한다.**
- **판서 ① 칩 vs 배지** — 강사가 칩 시트에 큰 빨간 X를 그었다. 갈림길은 하나 — **누르면 칩, 못 누르면 배지.**
- **판서 ② 모달 vs 바텀시트** — 중앙 확인 vs 하단 옵션, 스크림 탭이 "닫힘" vs **"선택 없이 닫힘"**.
- **산출물 보호 지시**: 아이콘버튼은 *"이미 완료된 상태이므로 **수정 금지**"* — Day 20의 "신규 프레임 생성하지 않음"이 *방금 만든 것*을 지켰다면, 이건 **지난 세션의 산출물**을 지킨다.

**마지막 파운데이션 — 스페이싱** `spacing-8/12/16/20/24/32`. 컬러·타이포·아이콘은 **컴포넌트 안**에서, 스페이싱은 **컴포넌트 사이**에서 소비된다. 그래서 순서가 *컴포넌트 → 스페이싱 → 리팩토링* — **조립 직전에 조립용 자를 만든다.**

**최종 리팩토링 3규칙**

| 시안의 디자인이… | 처리 |
|---|---|
| 컴포넌트 목록에 있음 | **컴포넌트로 대체** |
| 없음 + **타입 자체가 없음**(예: 지도 위젯) | **시안 유지** (2-1) — 억지로 끼워 맞추지 않는다 |
| 없음 + **타입은 있는데 UI가 다름** | **컴포넌트로 대체** (2-2) — **시스템이 시안을 이긴다** |

- 갭·마진은 전부 스페이싱 토큰. 그리고 **리팩토링은 끝이 아니다** — 판서에 남은 개선 3항목: ① 컬러·컴포넌트 ② 텍스트 ③ 사진.

> **🧩 퀴즈** — AI 시대에 굳이 UI 컴포넌트가 필요한가요? → **AI는 구현을 빠르게 할 뿐, 연결 구조가 없으면 AI도 100군데를 찾아 고쳐야 한다(그리고 몇 군데는 놓친다).** 산출물이 빨리 쌓이는 시대일수록 수정 가능한 구조의 가치는 커진다.

### 7. 핸드오프 — 스토리북과 SSOT (Day 22)

> 기획자: "우리 Pencil에 **디자인된 버튼**, 이거 **코드로 구현**까지 된 건가?"
> 디자이너: "내가 **파일**을 찾아볼게" — 구석의 개발자: "에휴, 매번 저렇게…"

- 이번 병목은 수정이 아니라 **추적**이다. 답이 "사람이 파일을 뒤지는 것"뿐이면 페이지가 늘수록 무너진다.
- **스토리북 = 코드로 구현된 디자인 시스템 보여주는 홈페이지.** (정의 슬라이드로 한 번, 퀴즈로 한 번 — 오늘 외울 단 하나의 정의)
- **포트가 두 얼굴**: `localhost:3000` = 하이파이(최종 결과물, 사용자가 보는 것) / `localhost:6006` = 디자인 시스템(파운데이션·컴포넌트, 만드는 사람이 보는 것). *"구현됐나?"* 의 답은 이제 파일 탐색이 아니라 **6006 접속**이다.

```
[축약]  디자인 시스템 핸드오프 ─────────────────→ 하이파이 디자인 핸드오프
[상세]  파운데이션 → UI 컴포넌트 → SSOT 규칙 생성(CLAUDE.md) → 하이파이 디자인
```

- **재료 먼저, 화면 나중** — Pencil 안의 제작 순서(토큰 → 컴포넌트 → 시안)가 코드 핸드오프에서 그대로 반복된다. 세 번째가 코드 이관이 아니라 **규칙 생성**인 것이 핵심 — 옮긴 것을 **쓰게 만드는 장치**까지가 핸드오프다.

> **★ 오늘의 판서** — `design.md` 가이드("이런식으로 해주세요") = **확률론** / 스토리북 **결과물 갖다쓰기** = **결정론.**
> 가이드는 AI에게 매번 **복사(재생성)** 를 시키고, SSOT(진실의 원천 = **"원본 갖다쓰기 규칙"**)는 **연결(재사용)** 을 시킨다. 그래서 규칙은 AI가 반드시 읽는 **CLAUDE.md**에, 전부 **강제형**("금지"·"기준")으로 들어간다.

**SSOT 규칙 6줄** — 작업 전 스토리 확인·**재사용 우선** / 컴포넌트·토큰 **위치 고정** / **하드코딩 값 금지**(Day 19 hex 금지의 코드판) / 신규는 **스토리 즉시 추가**(유령 부품 금지) / 스토리에 없는 variant·size·state **임의 생성 금지** / **불일치 시 스토리 기준**(분쟁의 승자를 미리 정한다).

**📝 실습** — 신규 페이지(로그인·마이) 프롬프트의 3요소: **소스 지정**(PRD 참고) · **산출물 보호**(기존 3장 제외) · **시스템 강제**("반드시 기존 디자인 시스템으로"). 시스템은 만들 때가 아니라 **다음 페이지를 만들 때** 이득이 실현된다.

# 제3부 · 데이터가 앉을 자리 (Day 23~25)

### 1. DB 생성 순서도 — DB가 1번이 아니라 4번인 이유 (Day 23)

```
기획/디자인 생성  →  데이터 추출  →  데이터 정규화  →  DB 생성
```

- **무엇을 저장할지는 화면이 정한다.** 화면에 없는 값은 저장할 이유가 없고, 화면에 있는데 저장 안 되는 값은 사라진다.
- **정규화 = 화면의 정보 덩어리를 테이블로 쪼개고 ID로 잇는 일.** 스프레드시트에 네 덩어리 — **장소 · 이미지 · 프로필 · [유저] — Supabase**.

```
장소.유저ID   ──→ 유저.ID
프로필.유저ID ──→ 유저.ID
이미지.장소ID ──→ 장소.ID
```

- **이미지가 별도 테이블인 이유가 표에 그대로 있다** — `IM001`과 `IM002`가 **둘 다 `PL001`**(1:N). 장소 테이블에 `이미지1·이미지2·이미지3` 컬럼을 만들면 **4장째에서 무너진다.**
- **`[유저] - Supabase`** — 계정·이메일·소셜로그인은 **Supabase 인증이 이미 관리한다.** 직접 만들면 계정이 두 군데 생긴다. 그래서 서비스가 쓰는 값(이름·프로필 이미지)만 **`profile`** 에 두고 `유저ID`로 잇는다.
- 결과물은 **3 tables** — `place`(6) · `place_image`(4) · `profile`(5), ROWS 0. **`image`가 아니라 `place_image`** — 이름 자체가 관계를 말한다.

> **정규화의 질문은 두 개다** — "이 값이 몇 번 반복되는가"(반복되면 쪼갠다), "이 값의 주인은 누구인가"(Supabase면 만들지 않는다). 앞의 것은 Day 19 디자인 토큰의 *"한 곳만 바꾸면 전부 바뀐다"* 와 정확히 같은 원리다.

### 2. 이미지 썸네일 — 느림의 정체는 용량 (Day 23)

- 느린 사이트와 빠른 사이트는 **레이아웃도 디자인 시스템도 컴포넌트도 똑같다.** 다른 건 **다운로드 용량**뿐 — 화면에 60×80으로 보이는 자리에 4000×3000 원본을 내려보내는 것이 문제다. **브라우저가 줄여 그리는 건 공짜지만, 받는 건 공짜가 아니다.**
- 썸네일은 한 벌이 아니라 **S/M/L** — 카드에 S, 그리드에 M, 상세에 L. **원본은 지우지 않는다**(재생성·다운로드용 소스).

| | **① 영구 저장 방식** | **② 온디맨드 리사이징 방식** |
|---|---|---|
| 만드는 시점 | **등록시**(업로드 직후 트리거) | **조회시**(요청받은 순간) |
| 저장 | 스토리지에 파일로 영구 | 백엔드 캐시에 임시 |
| 용량 | 원본 + S/M/L = 많음 | 원본만 = 적음 |
| 조회 부담 | 없음(스토리지 직행) | 첫 요청만(이후 캐시) |
| 규격 변경 | **전체 재생성** | 다음 요청부터 자동 |

- **캐시 없는 온디맨드는 느린 사이트로 되돌아간다** — 100명이 같은 사진을 보면 같은 계산을 100번. 첫 요청만 계산하고 이후는 캐시에서 내보낸다. **실무의 온디맨드는 온디맨드 + 캐시가 한 세트.**
- **미리 만들면 저장 공간을 쓰고, 그때그때 만들면 계산을 쓴다.**

### 3. BaaS와 비즈니스 로직 노출 — 그리고 BFF (Day 24)

> 기획자(격분): **"도대체 경쟁사가 우리의 리뷰 평가 로직을 어떻게 알아낸 거야!"**
> *리뷰 평가 로직 등 비즈니스와 관련된 로직을 **비즈니스 로직**이라고 불러요*

- 유출된 것은 **데이터가 아니라 로직**이다. DB가 털린 게 아니라 **계산 방식**이 읽혔다.
- **자산의 기준은 "여러 단계로 조합되어 있는가"** — 프로필 조회·게시글 조회(1단계)는 자산이 아니고, **이달의 우수회원**(4단계: 이번달 글 → 싫어요 0개만 → **글점수 = 조회수 × 좋아요** → 최고점 작성자)과 **추천 영화**(3단계 경로 설계)가 자산이다.
- **Supabase = 백엔드 + DB** → 백엔드 서버 자리가 빈다 → **백엔드가 없으면 로직은 사라지지 않고 브라우저로 밀려난다.**
- **실증** — F12 → Sources → "supabase" 검색이면 `.from("item").select("apple_count").eq("id", ROW_ID)` 코드와 **한글 주석**, 심지어 **`ANON_KEY`** 까지 보인다. **해킹이 아니다.**

> **프론트엔드 코드에는 비밀이 존재할 수 없다. 숨기려면 코드를 브라우저 밖으로 옮기는 수밖에 없다.** (난독화는 해결이 아니다)

| 보호책 | 구조 | 비용 |
|---|---|---|
| ① 자체 백엔드 서버 | 브라우저는 "우수회원 조회" 한 줄 보내고 "철수" 한 줄 받음 | *"이제와서 다시 백엔드 배우라고요…?"* |
| ② **BFF 패턴** | 이미 있는 프론트엔드 서버를 백엔드처럼 | 새 서버도 새 배포도 없음 |

- **프록시서버는 요청을 그대로 대신, BFF는 요청에 맞게 조립.** 서버 하나 끼웠다고 BFF가 아니다 — **거기서 조립을 해야** BFF다.
- BFF를 놓을 두 자리: **Supabase Edge Function**(150초간 실행되는 임시 백엔드) / **프론트엔드 서버(Next)** — 후자가 가장 싼 답.
- **판정법 한 줄** — Request URL이 `*.supabase.co/rest/v1/…` **(X)** vs `localhost:3000/api/*` **(O)**. 함정은 **둘 다 200 OK**라는 것 — 화면만 봐서는 구분이 안 된다.
- 썸네일도 이 구조 위에 얹힌다: *"이미지 업로드 API를 만들어줘 / 썸네일 6개 미리 저장 / **BFF에서** / s, sm, md, lg, xlg…"* — **어디서·무엇으로·몇 개**를 지정한다. ⚠️ 판서 메모 **`4.5MB / vercel`** — 업로드 요청 크기 상한, 원본 사진은 쉽게 넘는다.

### 4. BFF로 CRUD 구현, 그리고 소프트 삭제 (Day 25)

**맛집 CRUD 프롬프트 6줄 — 각 줄이 무엇을 지정하는가**

```text
SupabaseMCP를 사용해서 맛집 등록/목록조회/상세조회/수정 기능을 구현해줘.       ← 도구 + 기능(조회를 둘로 쪼갬)
이미지는 1장 이상 등록되어야하고, place-image 버킷에 uuidv4로 저장하면 돼.   ← 검증 + 저장 위치 + 파일명 규칙
스토리지 주소는 환경변수로 분리하고, 파일 경로는 place_image 테이블에 저장해줘. ← 비밀값 분리 + 저장 대상
제목은 필수 입력이어야하고, 내용은 필수 입력이면서 10글자 이상 입력해야돼.      ← 입력 검증
주소는 이번에는 구현하지 않을 것이기 때문에, 기본값으로 "등록 대기중"으로 저장.  ← 범위 제한 + 기본값
위 기능은 BFF로 구현해줘.                                                  ← 아키텍처 지정
```

- **"조회"는 한 단어지만 화면은 두 개다** — 목록조회(카드 여러 장)와 상세조회(한 건 전체)는 필요한 데이터도 응답 모양도 다르다. **애매한 한 단어를 쪼개는 것**이 이 프롬프트의 핵심.
- **안 만들 것도 명시하고 그 자리의 기본값까지 정한다**(5번 줄). 침묵하면 AI가 주소 기능까지 만들거나 `NULL`을 넣어 화면이 깨진다.
- **아키텍처는 기능 설명에 딸려 오지 않는다**(6번 줄). 빠지면 Day 24의 노출 구조로 되돌아간다.
- 검증: `POST http://localhost:3000/api/places` · **201 Created**(조회의 200과 구분).

**삭제는 두 가지**

| | 하드 삭제 + CASCADE | **소프트 삭제** |
|---|---|---|
| 부모(게시글) | 행이 사라짐 | 행 유지 + **삭제일 기록** |
| 자식(댓글) | **함께 사라짐** | **그대로 남음** |
| 복구 | 불가 | 삭제일을 NULL로 |
| 조회 | 그냥 | **`deleted_at IS NULL` 조건 필수** |

- **CASCADE**(같이 지움) ↔ **No Action**(자식이 있으면 부모 삭제 거부) — 참조 관계를 만들 때 **미리 정해야** 한다. 안 정하면 존재하지 않는 게시글의 댓글, 즉 **고아 데이터**가 생긴다.
- 실물 컬럼은 **`deleted_at timestamptz`**(날짜가 아니라 **시각**), 기본 `NULL`.
- **소프트 삭제는 연쇄 삭제 자체가 일어나지 않는다** — 지운 게 아니기 때문이다. 대신 "부모가 숨겨졌으면 자식도 숨길지"를 **조회 로직이 판단**해야 한다. 편함을 얻는 대신 조회가 복잡해진다.

> **🧩 퀴즈** — 데이터를 실제로 삭제하지 않고 삭제 날짜를 기록해 안 보여주는 방법? → **소프트 삭제**

### 5. 위치 정보 — 현대 웹/앱의 필수 기능 (Day 25)

- 요구는 사용자 쪽에서 온다 — *"앱에서 판매자 위치를 보고 싶어요."* 카카오T(경로·요금) · 당근마켓(동네 범위) · 야놀자(검색 기준) · 쿠팡이츠(배달 추적) — **네 서비스가 위치를 쓰는 방식이 전부 다르다.** "지도를 붙인다"는 한 가지 일이 아니다.
- 위치는 **두 갈래** — ① 주소/우편번호(다음 우편번호 서비스) ② 지도/위치(네이버·카카오·구글). **국내는 네이버·카카오, 해외는 구글**(국내 상호·도로명 데이터 밀도 차이).
- 지도 기능은 **셋** — **지도**(그리기) · **지오코딩**(주소→위·경도) · **리버스 지오코딩**(위·경도→주소). 사용자가 **주소를 입력**하면 지오코딩, **지도를 찍으면** 리버스 지오코딩.
- 장소 등록 플로우 화면 5장: **03 등록 에러 → 06 장소 등록(지도+핀) → 07 검색 결과 → 08 결과 없음/직접 입력 → 02 상세.** 07은 **지역 검색 API**, 06은 **지도 API**. **08(검색 결과 없음)이 별도 화면으로 설계된 것**이 눈에 띈다 — 지도에 없는 장소를 위한 탈출구이고, 그 대가("지도 위치가 표시되지 않아요")를 화면이 미리 알린다.
- **Postman으로 네이버 지역 검색 API** — `GET .../search/v1/local?query=정자동 카페&display=2&start=1&sort=comment&format=json`, 헤더 **`X-NCP-APIGW-API-KEY-ID`** / **`X-NCP-APIGW-API-KEY`** → **200 OK · 234ms**.
- 응답의 함정 둘: **`mapx`=경도, `mapy`=위도로 지도 표기(위도, 경도)와 순서가 반대**이고, **소수점 없는 정수 문자열**(`1271063141` → `127.1063`)이다. 그리고 "정자동 카페"로 검색했는데 **미용실**이 나온다 — 지역 검색은 키워드 매칭이라 **업종 필터가 필요**하다. `telephone`·`description`은 **빈 문자열일 수 있다.**

### 2. 지도 API 6종과 오늘의 판서 (Day 26)

| 기능 | 종류 | 설명 |
|---|---|---|
| **동적 지도** | **JS-API** | 줌에 따라 변하는 지도 그리기 |
| 정적 지도 | REST-API | 지도를 사진으로 캡처 |
| 내비게이션(경유지 5 / 15) | REST-API | 상품이 **한도로 나뉜다** |
| 지오코딩 | REST-API | 주소 → 위·경도 |
| **리버스 지오코딩** | REST-API | 위·경도 → 주소 |

> **★ 오늘의 판서** — **REST-API = 백엔드 / JS-API = 프론트엔드(브라우저)**, 그리고 둘 다 **"이미 만들어져있는 기능"**.
> 이 한 단어가 **누가 호출하는지 · 키를 어디 둘지 · 어떻게 보호할지**를 전부 결정한다.

- 오늘 고른 것은 **동적 지도(JS-API) + 리버스 지오코딩(REST-API)** 둘. **지오코딩만 유독 ✕** — 지역 검색이 이미 좌표를 주므로 주소→좌표가 필요 없다. **어떤 API를 쓸지는 화면 플로우가 정한다.**
- **Dynamic Map만 서비스 환경 등록을 강제한다**(Web service URL = `http://localhost:3000`). JS-API는 브라우저에서 키가 보이므로 **"숨기기" 대신 "도메인으로 묶기"** 로 보호한다. ⚠️ **배포하면 실제 도메인으로 바꿔야** 지도가 뜬다.
- 동적 지도 최소 코드는 두 줄 — `getElementById('map')` + `new naver.maps.Map(mapDiv)`. 옵션이 없으면 **서울시청 11레벨**이 기본.
- 리버스 지오코딩 요청의 **`coords`는 경도,위도 순**(지도 표기와 반대). 응답은 `area1`(도) → `area2`(시·군·구) 계층으로 **조각으로** 오므로 문자열은 직접 조립해야 하고, **`crs: ""` · `x/y = 0.0`인 area가 섞여 온다** — `0`은 "값 없음"이지 좌표가 아니다. 응답 시간도 **61ms ↔ 417ms**로 요동한다(로딩 상태 필요).

### 3. Pencil 증분 디자인과 Node ID 핸드오프 (Day 26)

- 증분 디자인 프롬프트의 5요소: **① 진입점**("게시글 등록 페이지에 버튼 하나 추가") **② 배치 순서**("위에서부터 1.검색창 2.지도 3.주소박스 4.버튼") **③ 개수**("총 2장") **④ 재사용/복사 제약** **⑤ 검토 기준**.
- 두 제약이 핵심 — **"컴포넌트는 추가하지 말고 지금 있는 컴포넌트들을 사용해줘"**(안 붙이면 디자인 시스템이 두 벌이 된다), **"이미 만들어져있는 페이지가 변경된 경우는 복사본에서"**(원본이 남아야 비교·되돌리기가 된다 — Day 25 소프트 삭제와 같은 발상).
- **만들기 → 검토 → 반영 3박자** — *"디자인 시스템(디자인토큰, 파운데이션, UI컴포넌트)을 사용해 구현한 것이 맞는지 **검토**해줘"* → *"검토된 내용들 모두 반영해줘."* Day 19~22에서 쌓은 층이 여기서 **체크리스트**가 된다.
- **핸드오프는 이름이 아니라 Node ID로 지목한다** — "장소 등록 페이지"는 캔버스에 여럿일 수 있지만 `YYQb3`는 하나뿐이다(Day 25의 "조회를 둘로 쪼갠다"와 같은 원리). 페이지 안의 한 요소면 **ID를 두 개**(페이지 + 요소). 그리고 **해상도·디자인 시스템 규칙은 `CLAUDE.md`에 두고 참조**시킨다.

### 4. DB에 자리부터 만든다 — Nullable vs Default (Day 27)

**작업 순서: ① DB 컬럼 → ② 지도 연동 → ③ 검색 연동.** 화면이 먼저 완성되면 "받아온 좌표를 어디 넣지?"에서 막힌다.

- 추가 컬럼 3개: **`name text` · `lat float8` · `lng float8`**(모두 Nullable).
- **`title`(게시글 제목)과 `name`(장소 상호)은 다른 값**이다. 좌표는 **`float8` 두 컬럼으로 분리** — 한 컬럼에 `"37.2,126.5"` 문자열로 넣으면 계산도 못 하고 순서 함정도 영원히 남는다.

**이미 데이터가 있는 테이블에 컬럼을 추가할 때** — 컬럼은 표 전체에 **세로로** 생기고, 기존 행의 빈칸을 무엇으로든 채워야 한다.

| ▶ Nullable | ▶ Default |
|---|---|
| 기존 행 전부 **NULL**("모른다") | 기존 행 전부 **0**("0에서 시작") |

- **어느 쪽이 맞느냐는 값의 의미에 달렸다.** 조회수는 "아직 0회"가 자연스럽지만, **`lat = 0`은 "적도"라는 실제 위치**다. **"모른다"와 "0"이 구별돼야 하는 값(좌표·금액·점수)은 Nullable**이 안전하다.

### 5. `NEXT_PUBLIC_` — 파일 한 줄의 접두사가 경계선 (Day 27)

| 키 | 접두사 | 누가 쓰나 | 보호 |
|---|---|---|---|
| `SUPABASE_*` · `NAVER_CLIENT_*` | **금지** | 서버(BFF) | 브라우저에 아예 안 나감 |
| `NEXT_PUBLIC_NCP_MAP_CLIENT_ID` | **필수** | 브라우저(지도 SDK) | **도메인 제한** |

- **Supabase 키에 `NEXT_PUBLIC_`을 붙이는 순간 Day 24의 노출 구조로 되돌아간다.** 반대로 지도 키에서 빼면 브라우저가 못 읽어 지도가 안 뜬다. 정답은 **"모든 키를 숨겨라"가 아니라 "키마다 보호 방식이 다르다"** 이다. Day 26의 판서(JS-API=프론트 / REST-API=백엔드)가 여기서 **`.env` 접두사**로 실현된다.
- **두 파일의 역할** — `.env.example`(빈 값 + 발급 절차 + "키 없을 때 동작"까지 적힌 **설명서**, 커밋 O) / `.env.local`(실값, 커밋 X).
- **가장 실용적인 한 문장** — *"환경변수는 시작 시점에 읽힘"*. 코드는 Turbopack이 자동 반영하지만 **키를 넣으면 dev 서버를 재시작**해야 한다. 이걸 모르면 "키를 넣었는데 왜 안 되지?"로 한참 헤맨다.
- 키가 없을 때 **깨지지 않고 내려앉는다** — 지도는 **정적 목업**, 검색은 **비활성화 + 직접 입력만**. 팀원이 키 없이도 화면을 볼 수 있다.
- ⚠️ **AI가 쓴 설정 주석도 검증 대상이다** — 처음 생성된 주석이 발급처를 `developers.naver.com`으로 잘못 적었고, **프롬프트에 독스 URL을 붙이자 `console.ncloud.com`(네이버 API 허브)으로 정정**됐다. 정답이 하나뿐인 정보는 프롬프트에 직접 넣는다.

### 6. 화면 왕복 규약과 "생각보다 내가 할 게 많네?" (Day 27)

**분기 1 — 결과가 있을 때**

```
검색 결과 선택 → [검색어 · 지번주소(address) · 경도(mapx) · 위도(mapy)]를 들고 복귀
   검색어 → 검색창 / 지번주소 → 주소 영역 / 경도·위도 → 지도 중심
   ※ mapy, mapx는 모두 lat, lng 방식으로 수정해서 사용
```

**분기 2 — 결과가 없을 때** — 직접 입력한 장소명만 검색창에, **주소·좌표는 디폴트값 유지**(없는 값을 지어내면 핀이 엉뚱한 데 꽂힌다). 그리고 *"이건 나중에 리버스 지오코딩으로 유저가 직접 지도를 움직여 선택하게 할 예정"* — **미래 계획을 미리 알려** 지금 구조를 나중에 갈아엎지 않게 한다.

- **"무엇을 들고 / 어디로 돌아가 / 어디에 넣는지" 세 가지를 다 적는다.** 하나라도 빠지면 AI가 정한다.
- 지시 한 줄이 카피 한 줄을 바꾼다 — 분기 2 때문에 화면 문구가 *"지도 위치가 표시되지 않아요"* → **"지도에 표시된 현재 위치를 그대로 사용해요"** 로 정확해졌다.

> **★ 오늘의 판서** — 20줄짜리 프롬프트 아래 붉은 글씨로 **"생각보다 내가할게 많네?"**
> 그리고 초록 주석 둘: 그 감각이 곧 **마케팅 광고**의 반대편이고, **"유튜브를 봤더니, 자고 일어나니깐 개발 끝!"** 이 성립하는 조건은 **리팩토링 과정(생략)** 또는 **복제(클론)** 이다.
> **AI 코딩에서 줄어드는 것은 구현 시간이지 설계 시간이 아니다. 프롬프트가 길어지는 것은 실패가 아니라, 원래 사람이 하던 결정이 글로 드러난 것이다.**

# 제5부 · 세상에 내보내기 (Day 28~29)

### 1. 배포는 한 동작이 아니라 파이프라인 (Day 28)

```
기능 추가 ──"빌드"→"커밋"→"푸쉬"──▶ Github ──(업로드 감지·자동 전송)──▶ Vercel
                                       └── 연결 설정(한 번만) ──┘        │
                                                                     [.env] 환경 변수 등록
```

- **요즘 프론트엔드 배포는 두 모양** — 홈페이지(Vercel만) vs **웹 서비스**(Vercel + **Supabase**, "DB 시스템 필요"). 우리는 후자.
- **빌드·커밋·푸쉬는 별개의 세 단계**이고, **연결 설정은 한 번**, 배포는 자동이다.
- **환경변수 등록이 파이프라인 바깥에 따로 그려진 이유** — `.env.local`은 커밋되지 않으므로 **코드는 자동으로 흐르고 비밀값은 흐르지 않는다.** "로컬에선 되는데 배포하면 안 되는" 사고의 1순위.

### 2. 배포 환경 4단계 vs 1인 개발의 현실 (Day 28)

교과서는 **로컬 · 개발 · 스테이징 · 프로덕션 4단계**다. 그 대가가 슬라이드에 숫자로 적혀 있다 — 도메인 **4개**, `.env` **4개**, Supabase **4개**, 이미지 스토리지 **4개**, **소셜로그인 설정 4번**, Vercel **3개** + 로컬 1대.

> 🐰 **"로컬과 프로덕션을 공유하여 시작하고, 규모가 커지면 그 때 분리해도 늦지 않아요!"**

- **환경을 나누는 것은 공짜가 아니다.** 단계 하나가 도메인·DB·스토리지·인증 설정을 통째로 하나씩 더 요구한다. 1인이면 **둘로 시작하고 사람이 늘 때 쪼갠다.** (대신 로컬 실수가 실데이터를 건드리므로 Day 25의 소프트 삭제가 더 중요해진다)
- **소셜 로그인 URL 통합** — **Site URL**은 하나·와일드카드 불가(→ 프로덕션), **Redirect URLs**는 여러 개·와일드카드 가능(→ **프로덕션 `/**` + 로컬 `/**`**). 배포하면 **인증이 먼저 깨진다.**

### 3. 푸시 전 점검 — 두 방향 검사 (Day 28)

프롬프트: *"깃 주소는 … / **환경변수 하드코딩여부 검사** / 올라가면 안될 파일들은 **.gitignore**에 / **빌드 → 커밋 → 푸쉬**."* **푸쉬가 마지막**인 것이 방어적 순서다.

- **검사는 두 겹** — ① `.env.local`의 실제 값을 저장소 전문과 교차 대조 ② 일반 시크릿 패턴(JWT `eyJ...`, `sb_secret`, AWS, PEM) 검색.
- **"API 엔드포인트 URL은 비밀이 아니다"** — 무엇이 비밀이고 무엇이 아닌지 헷갈리면 과잉 차단이 된다.
- **`.mcp.json`이 실전 사례** — 키가 아니라 `project_ref`(식별자)인데도 제외했다. 이유가 **BFF 구조상 클라이언트에 드러나지 않아야 해서**(Day 24의 원칙이 파일 하나에까지). 그리고 "다시 커밋해도 큰 문제는 없다"는 **판단의 근거와 강도**까지 함께 남겼다.
- **`.gitignore`를 쓰고 끝내지 말고 스테이징 후 실제 목록을 다시 본다.** 결과: `.env.example`만 포함, 정적 페이지 17개 생성, **221개 파일 커밋**.
- 새 환경변수 **`NCP_MAP_CLIENT_ID` / `NCP_MAP_CLIENT_SECRET`**(`/api/reverse-geocode` 전용, **`NEXT_PUBLIC_` 금지**) — 같은 애플리케이션의 Client ID인데도 변수가 갈린 이유는 **Secret이 섞이기 때문**이다.

### 4. 도메인 — 주소창 한 줄로 끝나지 않는다 (Day 28)

- **가비아**에서 `food-community.shop` 구입 — **`D-365`**, 도메인은 사는 게 아니라 **1년 단위로 빌리는 것**이다.
- **Vercel Domains**: `food-community.shop` **→ 308 →** `www.food-community.shop`(Production), 그리고 자동 부여된 `*.vercel.app`은 **REMOVED**. `www` 있는 것과 없는 것 **둘 다 등록**하되 하나는 입구(리다이렉트)로. **308은 영구 리다이렉트**이고 301과 달리 **메서드·본문을 유지**한다.
- **도메인을 바꾸면 연쇄로 고칠 곳** — Supabase **Site URL·Redirect URLs**, NCP Maps의 **Web service URL**. 옛 주소를 가리키면 로그인이나 지도가 죽는다.

### 5. 로고와 상표권 (Day 28~29)

> 😡 **"뜬금 없이 돈을 물어내라니, 이게 무슨 헛소리야! 내가 상표권을 침해했다고?!"**

| | **상표권** | **디자인권** | **저작권** |
|---|---|---|---|
| 보호 대상 | **브랜드 이름(마크)** | **시각적 디자인** | **창작물** |
| 폰트 하나에 | "철수폰트" **이름** | "철수폰트" **디자인** | "철수폰트" **파일** |
| 보호 방법 | **등록 필요 O** | **등록 필요 O** | **등록 필요 X** |
| 신청 | 지식재산처(구 특허청) | 지식재산처 | – |

- **같은 대상이 세 권리로 동시에 보호된다.** 가장 중요한 실무 차이는 **등록 필요 여부** — 저작권은 만든 순간 생기지만 **상표권·디자인권은 등록해야 생긴다.** 안 하면 남이 먼저 등록한다.
- **사업자** — 법인은 **설립등기·등기소·법인등록번호 13자리**, 개인은 **출생신고·주민센터·주민등록번호 13자리**(설립등기 = 법인의 출생신고). 그 아래 **사업자등록번호 10자리(국세청)** 는 별개이고 여러 개일 수 있다. **상표권은 법인 또는 개인 명의**로 붙는다.

**로고 제작 6단계**

```
브랜드명 확정 → 로고 디자인 학습 → 폰트 BI/CI 검색 → 로고 작업 → 로고 목업 테스트 → 유사 상표 검색
  키프리스          로고북             눈누         리크래프트     리크래프트          키프리스
```

- **시작과 끝이 모두 키프리스**다 — 이름이 통과해도 **로고 모양이 걸릴 수 있기** 때문.
- **① 브랜드명** — 검색 결과 **0건**이 목표. 원칙은 **"널리 알려진 단어 금지"**: 치킨 ✕ / **철수치킨** ○, 여의도 ✕ / **여의도곱창** ○. 일반명사·지명 단독은 식별력이 없어 상표가 안 되고, 해법은 **고유어 + 일반어 결합**.
- **③ 폰트 BI/CI** — 눈누 라이선스 요약표에서 인쇄·웹사이트·영상이 전부 허용이어도 **BI/CI 한 줄이 막힌 폰트가 많다.** 로고는 상표로 등록되어 독점권이 생기기 때문. (**BI** = Brand Identity, **CI** = Corporate Identity)
- **④ 로고 작업** — 핵심은 **`svg`**. 로고는 명함부터 간판까지 모든 크기로 쓰이므로 벡터여야 한다. 1인은 **리크래프트(svg)**, 디자이너는 png→피그마(svg). **무료 등급은 상업적 사용 ✕ / 구독제 ○** — **로고는 정의상 상업적 사용**이므로 구독이 사실상 필수. 프롬프트는 색상 코드(`#ff5722`)·그라데이션 금지·서체·**negative space**까지 디자인 언어로 정확하게.
- **⑥ 유사 상표 검색 — 이름 검색과 완전히 다른 검색이다.** KIPRIS 상세검색에서 권리구분 **상표(40)·서비스표(41)·상표/서비스표(45)** 를 함께, 유형은 **도형상표·도형복합**만, 행정상태는 **출원·공고·등록 전부**(등록 전이어도 **먼저 신청한 쪽이 우선**). 결과는 **국내 2,458건** — 이름 0건과 대비된다.

> **이름 검색 0건은 시작일 뿐이다.** 로고는 도형만으로 수천 건과 비교된다 — **"없다"를 확인하는 게 아니라 "닮은 게 있나"를 찾는 검색**이다. `(상표명 정보없음)` = 글자 없이 도형만 낸 상표라 **모양으로만** 비교되고, 같은 도형이 여러 상품분류로 반복 출원되기도 한다.

### 6. PWA — 앱스토어 없이 앱처럼 (Day 28~29)

> 남자: "안드로이드, IOS 둘 다 **심사** 올렸어?" / 여자: "이제 막 웹 배포 끝났어요. **앱 패키징**은 시간 좀 걸려요…"
> 소년: **"일단 PWA로 배포하고, 운영 하면서 패키징 하는게 낫겠네요"**

- 앱 배포의 비용은 두 겹 — **패키징(AOS·iOS 각각)** + **심사 대기**. 둘 다 개발자가 통제할 수 없는 시간이다.
- **PWA 3종** — **홈 화면 설치 · 푸시 알림 · 오프라인 모드.** 앱스토어를 거치는 이유가 대부분 이 셋인데, PWA는 **웹인 채로** 제공한다. 설치 후 달라지는 건 **껍데기뿐**(주소창이 사라지고 전체화면). 배너는 기술이 아니라 이득을 말한다 — *"주소창 없이 앱처럼 바로 열려요."*

> **🧩 퀴즈** — 앱스토어 없이 홈 화면 설치·푸시알림이 가능하게 하는 기술? → **PWA**

### 7. 로고 + PWA 배포 실전 (Day 29)

**PWA 프롬프트 해부**

```text
PWA 방식으로 배포를 업그레이드 할거야.
1. 설치: 하단에 앱아이콘 설치 유도 띠배너 만들기 ⇒ 띠배너는 컴포넌트 재사용 X
      - 안드로이드: 띠배너 클릭시 바로 설치
      - IOS: 띠배너 클릭시 바텀시트에서 설치 가이드 제공
2. 스플래시 화면: 안드로이드, IOS 호환되는 기본 방식
3. 기타(오프라인, 푸시알림 등): 제외
이 과정에서 로고(폴더에 포함된 logo.svg)를 사용해줘
로고의 사이즈, 확장자 등의 변형이 필요하면 직접 스크립트를 만들어서 편집해줘.
이 과정에서 favicon도 로고를 활용해서 만들어줘.
파비콘은 뒤에 흰색 배경이 없도록 해줘.        ← 결과를 보고 나중에 추가된 한 줄
```

- **① 범위를 먼저 자른다** — 3번 줄이 **"제외"라고 명시**되어 있다(Day 25의 "주소는 이번에 구현하지 않을 것"과 같은 기법). 침묵하면 서비스 워커·알림 권한까지 붙는다.
- **② 플랫폼 분기는 취향이 아니라 제약이다** — 안드로이드 크롬은 브라우저가 설치 프롬프트를 띄워 주지만 **iOS 사파리에는 그런 API가 없다.** 그래서 iOS는 "설치"가 아니라 **"안내"** 가 최선.
- **③ "띠배너는 컴포넌트 재사용 X"** — Day 26의 "기존 컴포넌트를 사용해줘"와 모순이 아니다. 띠배너는 **디자인 시스템 밖의 시스템 UI**다. 규칙은 "항상 재사용"이 아니라 **"무엇이 시스템 안인지 밖인지 판단"**.
- **④ 변형은 스크립트로** — 아이콘은 한 장이 아니다. 손으로 만들면 **로고를 수정할 때마다 전부 다시** 만들어야 한다.

**결과 — 로고 한 장에서 나온 것들**

| 구분 | 산출 |
|---|---|
| Android | `src/app/manifest.ts` — 브라우저가 이걸 보고 "설치 가능한 앱"으로 인식 |
| iOS | `layout.tsx`의 `apple-touch-startup-image`(manifest를 다 못 읽으므로 별도) |
| 에셋 스크립트 | `scripts/generate-pwa-assets.mjs` — **C2PA 메타데이터 제거 + 바운딩 박스 자동 계산** |
| 파비콘 | 투명 배경, 마크 중심으로 `viewBox` 축소 |
| 아이콘 | `apple-icon.png`(180px), manifest 아이콘 **4종(`any` / `maskable`)** |
| 소요 | **16분** · 에셋 **16종** |

- **`maskable`이 실무 포인트** — 안드로이드는 제조사마다 아이콘을 원형·둥근사각형으로 **잘라낸다.** 잘려도 되는 여백을 미리 넣은 버전을 안 주면 **로고가 잘려 나간다.**
- **파비콘은 투명 배경으로** — 흰 사각형이 붙으면 다크 모드 탭에서 흰 딱지가 된다. **한 줄이 늘어난 과정 자체가 교훈**이다: 만들어 보고, 결과를 보고, 한 줄을 더 적는다.

> **★ 마지막 판서 — "너 지금 어떤 브랜치에서 작업하고 있니?"**
> `git branch --show-current` → **`main`**. 저장소는 **1 Branch · 2 Commits**, 커밋 메시지가 전부 같다.
> 판서는 로컬 `.git`의 `main`에서 **`feature-board` / `feature-payment` / `feature-product`** 를 쳐서 원격 `main`으로 올리는 구조를 그린다(워크트리 `wt1~3`은 ✕ 처리).
> **작업을 시작하기 전에 브랜치를 묻는다.** `main`에서 바로 고치면 되돌릴 단위가 없고, 커밋 두 개에 한 달이 뭉친다.

- 오늘 커밋은 달라졌다 — **`2f4b2ef` "PWA 설치 배너·스플래시·파비콘 추가"**(34 files, +1,441/−192, `create mode 100644 logo.svg`). **원본 로고가 저장소에 들어간 것**이 실습 "로고 다운받기"의 최종 목적지다 — AI 도구의 약관(개인/비즈니스 사용 구분, **비활성 계정 삭제**)이 바뀌어도 원본이 남는다.
- **배포는 푸시로 끝나지 않는다** — 실제 도메인(`food-community.shop`)에서 확인했더니 안드로이드에서 배너가 안 떴다. 원인은 **하이드레이션 레이스**(설치 프롬프트 이벤트 `beforeinstallprompt`가 **React가 붙기 전에 지나가 버림**). 확인은 **Android Chrome 시크릿 탭**에서 — 한 번 닫은 배너는 다시 안 뜬다.
- 콘솔의 경고들은 출처가 `contentscript.js`였다 — **브라우저 확장이 낸 것이지 내 코드가 아니다.** 남의 오류를 내 버그로 착각하지 않는 것이 디버깅의 첫걸음.
- 에셋 **16분** + 버그 **7분** — Day 27 판서 *"자고 일어나니깐 개발 끝"* 이 아니라는 것이 로그로 증명된다.

# 닫는 글

- **제1부** AI가 규모의 장벽을 낮춰 솔로프리너가 가능해졌다. 3축(역할·제품·상거래)으로 서비스를 보고, BM은 도식으로, 시장은 수요 검증 또는 차별화로 — **"앱이 없어서 안 팔리는 게 아니다."** 수동 판매로 검증한 뒤 앱으로 전환하고, 기획은 PRD(누가·무엇을·왜 + 지표)로 확정한다.
- **제2부** 디자인 시스템은 "예쁘게"가 아니라 **"바꿀 수 있게"** 만드는 것. 360×780을 기준으로 작게 만들어 늘이고, 프리미티브 → 시맨틱 2층 토큰(**hex 금지**) 위에 타이포 10종·아이콘 144개·컴포넌트 23종을 쌓아 시안을 재조립한 뒤, 스토리북을 SSOT 삼아 코드로 넘긴다. **구현이 아니라 수정이 문제이고, 컴포넌트는 복사가 아니라 연결이며, 가이드는 확률론·원본 갖다쓰기는 결정론이다.**
- **제3부** DB는 1번이 아니라 4번 — 화면이 무엇을 저장할지 정한다. 반복되면 쪼개고(정규화), 주인이 Supabase면 만들지 않는다(유저 테이블). 속도는 디자인이 아니라 **용량** 문제(썸네일 S/M/L). 그리고 **프론트엔드 코드에는 비밀이 존재할 수 없다** — 로직을 지키려면 브라우저 밖으로 옮겨야 하고, 그 가장 싼 답이 **BFF**(프록시는 대신, BFF는 조립)다. 삭제는 지우기가 아니라 **안 보여주기**로 구현할 수 있다.
- **제4부** 화면부터 펼치고 API를 배당한다. **JS-API인지 REST-API인지**가 누가 호출하고 키를 어디 둘지를 결정하고, 그것이 `.env`의 **`NEXT_PUBLIC_` 접두사** 한 줄로 실현된다. 좌표는 순서·배율·좌표계가 API마다 다르고 `0`은 값 없음이다. 프롬프트에는 **무엇을 들고 어디로 돌아가 어디에 넣는지**까지 적는다 — **"생각보다 내가 할 게 많네?"**
- **제5부** 배포는 파이프라인이고, **코드는 자동으로 흐르지만 비밀값은 흐르지 않는다.** 환경 분리는 공짜가 아니니 1인은 로컬+프로덕션 둘로. 푸시 전에 두 방향으로 검사하고, 도메인은 인증·지도 설정까지 연쇄로 바꾸며, 이름과 로고에는 상표권이 걸린다(이름 검색 0건은 시작일 뿐). 앱 심사를 기다리며 출시를 미루지 말고 **PWA로 먼저 내보낸다** — 그리고 배포는 푸시가 아니라 **실제 기기·실제 도메인·처음 방문 상태에서의 확인**으로 끝난다.

> **한 문장 요약** — *수요를 검증한 기획을 PRD로 확정하고, 토큰 → 컴포넌트 → 스토리북으로 바꿀 수 있는 시스템을
> 세운 뒤, 정규화된 DB 위에 BFF로 로직을 감추고 외부 API를 연결해, 도메인과 로고와 PWA까지 얹어 세상에 내보내라 —
> AI가 없애준 것은 구현 시간이지 결정의 몫이 아니며, 그 결정을 글로 적어두는 사람이 혼자서도 서비스를 만든다.*
