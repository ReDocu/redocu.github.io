## 이 문서들을 읽는 법

각 일차 문서는 **6개 블록의 고정 구조**를 갖습니다. 어느 날짜를 펴도 같은 자리에 같은 종류의 내용이 있습니다.

| 블록 | 내용 | 이렇게 쓰세요 |
|---|---|---|
| ① 학습 목표 | 오늘을 마치면 할 수 있게 되는 것 | 수업 전에 읽고, 수업 후에 다시 읽어 체크 |
| ② 왜 필요한가 | 이 단계가 없으면 프로젝트가 어떻게 무너지는지 | 팀이 갈등할 때 여기로 돌아오세요 |
| ③ 개념 설명 | 오늘 단계의 원리와 판단 기준 | 표와 그림 위주. 팀 회의 전에 함께 읽기 |
| ④ 단계별 실습 | 오늘 팀이 할 일 Step 1 → N + 예시 팀의 기록 | **자기 팀의 것**을 만드는 게 실습입니다 |
| ⑤ 자주 하는 실수 | 이 단계에서 팀이 무너지는 전형적 방식 | 우리 팀 증상인지 매일 대조 |
| ⑥ 확인 문제 | 3문항, 답은 접혀 있음 | 팀 회의에서 토론 소재로 써도 좋습니다 |

**코드 블록 규칙** — 명령은 `$` 로 시작하는 줄이 입력, 그 아래가 실제 출력입니다.

> **이 단원 문서의 성격 — 예시 팀 "한산"** · 앞 단원까지는 문서의 코드를 그대로 따라 치면
> 같은 결과가 나왔습니다. 이 단원은 다릅니다 — **여러분 팀의 주제·데이터·설계는 여러분이
> 정하고, 문서는 같은 4주를 먼저 완주한 예시 팀 하나를 따라가며 보여 줍니다.**
> 예시 팀 "한산"(가상의 4인: 서연·민준·지우·하람)은 주제 후보 1번(대중교통 혼잡도 예측)을
> 선택해 기획→구현→운영→발표를 완주합니다. 문서 속 한산 팀의 코드·수치(MAE 1,183 ·
> 커밋→운영 2m40s 등)는 **재현 대상이 아니라 참조 모델**입니다 — "이 단계의 산출물은
> 대략 이런 모양·이런 수준"의 눈금으로 쓰고, 여러분 팀의 숫자로 바꿔 채우세요.

## 이 단원을 마치면

- [ ] 팀으로 **데이터 수집 → 저장 → 학습 → 서빙 → 운영 자동화**의 전체 사이클을 완성한다
- [ ] 브랜치 전략·PR 리뷰·이슈 관리로 **4주짜리 개발을 계획하고 완주**한다
- [ ] 시스템의 상태를 **실측과 문서**로 증명할 수 있다 (재현·롤백·재학습)
- [ ] 채용 담당자 앞에서 **아키텍처와 기술 선택의 이유를 설명**할 수 있는 포트폴리오를 갖는다

**단원 완료 조건 (최종 프로젝트 제출 기준)**

- [ ] 공통 필수 구성 요소 6종이 모두 동작한다 ([커리큘럼](../../curriculum/06-final-project.md) 참조)
- [ ] 팀원 전원의 유의미한 커밋·PR 이력이 있다
- [ ] 개인 포트폴리오 저장소 5종(README 통일)이 공개 상태다
- [ ] 결과 보고서에 한계와 개선 방향이 솔직하게 적혀 있다

**단원 산출물** 팀 저장소(운영 중인 서비스) + 개인 포트폴리오 5종 + 최종 발표

## 개발 환경

| 도구 | 용도 | 비고 |
|---|---|---|
| 지난 140일의 전체 스택 | Python·PostgreSQL·sklearn/부스팅·FastAPI·Docker·Actions·MLflow·Airflow | 새 도구 없음 |
| **팀별 클라우드 인스턴스 1대** | 운영 서버 (Ubuntu 22.04 · 2vCPU/4GB 급) | [Day 144](day-144.md)에 수령 · W28까지의 WSL2 "서버"가 진짜 서버로 바뀌는 것뿐, 명령은 동일 |

> **GPU 없이 완주 가능하게 주제를 고르세요.** 주제 후보 5개는 전부 CPU 학습이 가능한
> 범위입니다. GPU가 필요한 아이디어라면 [Day 141](day-141.md)의 데이터 실재 확인 단계에서
> Colab 학습 + CPU 서빙으로 감당되는지 먼저 검증해야 합니다.

## 자주 나오는 질문

| 질문 | 답 |
|---|---|
| 예시 팀(한산) 코드를 그대로 써도 되나요? | 패턴(구조·검증 방식·문서 형식)은 얼마든지. 단 **주제가 같아도 데이터 확인·설계 판단은 직접** 해야 합니다 — 심사 질의응답에서 "왜"에 답하지 못하는 코드는 본인 것이 아닙니다. |
| 팀원과 실력 차이가 커요 | 역할 분담을 "잘하는 사람이 어려운 걸"로 하지 마세요. [Day 144](day-144.md)의 분담 원칙(전원 코드 작성 + 교차 리뷰)이 기준입니다. 개인 기여도가 팀 점수의 30%를 조정합니다 — 몰아주기는 전원 손해입니다. |
| 4주 안에 못 끝낼 것 같아요 | 정상 감각입니다. 그래서 [Day 142](day-142.md)가 통째로 "자르기"입니다 — 필수 6종 관통이 화려한 미완성보다 높게 평가됩니다. |
| 모델 성능이 안 나와요 | 성능보다 **베이스라인 대비 개선 과정·원인 분석**이 배점입니다 ([Day 148](day-148.md)). 낮은 성능 + 정직한 분석 > 근거 없는 높은 숫자. |
| LLM을 쓰고 싶어요 | 사전학습 모델 추론(W18 범위) 안에서 허용. RAG·프롬프트 중심 주제는 후속 LLM 과정 캡스톤으로 — [커리큘럼 FAQ](../../curriculum/06-final-project.md) 참조. |
| 데이터 공개에 제약이 있으면? | 원본 데이터는 커밋 금지(DVC 관리)가 기본입니다. 수집 스크립트 + 재현 절차가 공개되면 저장소는 포트폴리오 역할을 합니다 ([Day 156](day-156.md)). |
