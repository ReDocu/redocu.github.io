## ① 학습 목표

이 레슨을 마치면 이렇게 할 수 있습니다.

- 리버스 프록시가 서비스 문 앞에서 맡는 **네 가지 일**을 말할 수 있다.
- nginx 설정(server·location·proxy_pass)을 읽고 써서 **nginx + API + DB 3단 구성**을 완성할 수 있다.
- 진입점을 nginx 하나로 모으고 **API의 직접 노출을 제거**할 수 있다.
- 정적 파일을 nginx가 직접 서빙하게 하고, HTTPS(TLS 종료)가 어디서 일어나야 하는지 설명할 수 있다.

---

## ② 왜 필요한가

지금 구성에서 바깥 손님은 `:8080...` 아니, `:8000` 으로 API에 **직접** 들어옵니다. 서비스가
어리면 문제없지만, 조금만 자라면 파이썬 서버 혼자 감당하기 억울한 일들이 문간에 쌓입니다:

| 문간의 일 | uvicorn 혼자 하면 | 전문가(nginx)가 하면 |
|---|---|---|
| 여러 서비스의 교통정리 | 포트를 손님이 외움 (8000, 8001, 5000…) | **한 문(80/443)** 에서 경로로 분배 |
| 대용량·불량 요청 거르기 | 파이썬까지 와서야 413 | **문 앞에서** 차단 — 앱은 구경도 안 함 |
| 정적 파일 (HTML·이미지) | 추론용 워커가 파일 서빙에 소모 | nginx의 주특기 — 초당 수만 건 |
| HTTPS (암호화) | 앱마다 인증서 관리 | 문 앞에서 **한 번만** (TLS 종료) |

그래서 실무 웹 서비스의 표준 대형은 거의 예외 없이 이렇습니다:

```
손님 ──▶ [nginx :80/443] ──▶ [API 컨테이너들 (내부)] ──▶ [DB (더 내부)]
          문지기·안내원          일꾼                       금고
```

안쪽으로 갈수록 노출이 줄어드는 **양파 구조** — DB는 Day 119부터 내부 전용이었고, 오늘 API도
문 뒤로 들어갑니다. 바깥에 남는 문은 nginx 하나. MP4의 필수 구성이자, 최종 프로젝트에서
프론트엔드(정적)와 API(동적)를 한 주소로 내보내는 뼈대입니다.

## ③ 개념 설명

### 리버스 프록시 — 방향이 반대인 대리인

프록시(proxy)는 대리인입니다. **누구의 대리인가**로 종류가 갈립니다:

| | 포워드 프록시 | **리버스 프록시** |
|---|---|---|
| 대리 대상 | **클라이언트** (회사 망의 출구 등) | **서버** (서비스의 입구) |
| 손님이 아는 것 | 목적지 서버 | 프록시뿐 — 뒤의 일꾼 수·위치는 모름 |

리버스 프록시 뒤에서는 일꾼(API 컨테이너)을 늘리든 바꾸든 재시작하든 손님이 모릅니다 —
이 "모름"이 무중단 배포·스케일링의 공간이 됩니다 (W26에서 사용).

### nginx 설정 최소 문법

```nginx
server {                                # 가상 서버 하나 (문 하나)
    listen 80;                          # 이 문의 포트

    client_max_body_size 8m;           # 업로드 상한 — 문지기의 자

    location /static/ {                 # 경로 규칙 1: 정적은 내가
        alias /usr/share/nginx/html/;
    }

    location / {                        # 경로 규칙 2: 나머지는 일꾼에게
        proxy_pass http://api:8000;     # ← 서비스 이름! (Compose 네트워크의 DNS)
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

- `proxy_pass http://api:8000` — 목적지가 **서비스 이름**입니다. Day 119~121의 이름 기반
  통신이 nginx 설정 안에서도 그대로 통합니다 (nginx도 같은 Compose 네트워크의 주민이므로).
- `proxy_set_header X-Forwarded-For ...` — 프록시를 거치면 API가 보는 발신 IP는 nginx의
  것이 됩니다. **원래 손님의 IP를 편지 겉봉에 적어 전달**하는 관례 헤더가 이것입니다
  ([Day 098](../04-deep-learning-serving/day-098.md)의 요청 로그가 의미를 유지하려면 필수).

### HTTPS는 어디서 — TLS 종료

암호화(HTTPS)는 "문에서 풀고, 안에서는 평문"이 표준입니다 — 이를 **TLS 종료(termination)**라
합니다. 인증서 관리·갱신(Let's Encrypt가 무료 표준)이 nginx 한 곳에 모이고, 내부 통신은
격리된 도커 네트워크 안이라 평문이어도 위협 모델이 다릅니다. 오늘은 개념까지 — 실제 인증서
발급은 공인 도메인이 필요해 과정 범위 밖이지만, **"443과 인증서는 nginx의 일"** 이라는 배치만
정확히 새겨 두면 실무에서 그대로 조립됩니다.

## ④ 단계별 실습

### Step 1. 3단 구성 선언 (1~2교시)

브랜치 `feature/nginx`. 프록시 설정 파일부터 — `nginx/default.conf` 에 ③의 설정을 그대로
(경로만 우리 것으로). 그리고 compose.yaml에 문지기를 추가하고 **API의 문을 닫습니다**:

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"                      # 이제 바깥 문은 여기 하나
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./static:/usr/share/nginx/html:ro
    depends_on:
      api:
        condition: service_healthy     # 어제의 healthcheck가 곧바로 재사용됨
    restart: unless-stopped

  api:
    build: .
    # ports: 제거! — 내부 전용 (nginx만 접근)
    environment:
      DATABASE_URL: postgresql+psycopg://mp3:${DB_PASSWORD:?required}@db:5432/mp3
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request,sys; r=urllib.request.urlopen('http://localhost:8000/health', timeout=2); sys.exit(0 if r.status==200 else 1)"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 30s

  db:
    # (어제와 동일 — 생략)
```

api에서 `ports:` 가 사라진 것이 오늘의 핵심 한 줄입니다 — 양파의 한 겹이 닫혔습니다.

### Step 2. 기동과 3단 검증 (3~4교시)

```bash
docker compose up -d --build
curl -s localhost:8080/health
curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8080/predict
curl -s localhost:8000/health
```

```
$ curl -s localhost:8080/health
{"status":"ok","model_loaded":true,"model_version":"resnet18-antbee-v1","started_at":"2026-08-21T04:40:18+00:00"}
$ curl -s -F "file=@tests/data/ant_sample.jpg" localhost:8080/predict
{"label":"ants","confidence":0.7214,"model_version":"resnet18-antbee-v1","elapsed_ms":31.7}
$ curl -s localhost:8000/health
curl: (7) Failed to connect to localhost port 8000 after 0 ms: Connection refused
```

8080(프록시 경유)으로는 모든 것이 되고, 8000(직접)은 **막혔습니다** — 문이 하나뿐임을 두
방향에서 확인했습니다. nginx의 접근 로그에서 손님 기록도 확인:

```bash
docker compose logs nginx | tail -2
```

```
nginx-1  | 172.19.0.1 - - [21/Aug/2026:04:41:02 +0000] "POST /predict HTTP/1.1" 200 96 "-" "curl/7.81.0" "-"
```

### Step 3. 문지기의 자 — 크기 제한이 앞당겨진다 (5교시)

[Day 100](../04-deep-learning-serving/day-100.md)의 3중 검사 중 크기 검사(413)를 nginx가
**먼저** 수행하게 됐습니다. 11MB 파일로 실험:

```bash
dd if=/dev/zero of=/tmp/big.jpg bs=1M count=11 2>/dev/null
curl -s -o /dev/null -w "%{http_code}\n" -F "file=@/tmp/big.jpg" localhost:8080/predict
curl -s -F "file=@/tmp/big.jpg" localhost:8080/predict | head -3
```

```
$ curl -s -o /dev/null -w "%{http_code}\n" -F "file=@/tmp/big.jpg" localhost:8080/predict
413
$ curl -s -F "file=@/tmp/big.jpg" localhost:8080/predict | head -3
<html>
<head><title>413 Request Entity Too Large</title></head>
<body>
```

응답이 **HTML**입니다 — API의 JSON 413이 아니라 nginx의 413. 11MB가 파이썬 근처에도 못 가고
문 앞에서 반송된 증거입니다 (앱 부하 절약). 설정값 8m는 [Day 106](day-106.md)에서 팀이 충돌
끝에 합의한 그 8MB — **한 값의 세 거처**(앱 검증 · nginx 제한 · 팀 문서)가 일치해야 한다는
과제를 ⑥에서 다룹니다.

### Step 4. 정적 파일 — 데모 페이지 (6~7교시)

발표일마다 curl로 시연하는 것도 한계 — 업로드 데모 페이지를 nginx가 직접 서빙하게 합니다.
`static/index.html`:

```html
<!doctype html>
<html lang="ko">
<meta charset="utf-8">
<title>개미/벌 분류기 — MP3</title>
<body style="font-family: sans-serif; max-width: 480px; margin: 40px auto">
  <h1>개미 🐜 / 벌 🐝 분류기</h1>
  <input type="file" id="f" accept="image/*">
  <button onclick="go()">판정</button>
  <pre id="out">이미지를 선택하세요</pre>
  <script>
    async function go() {
      const fd = new FormData();
      fd.append("file", document.getElementById("f").files[0]);
      const r = await fetch("/predict", { method: "POST", body: fd });
      document.getElementById("out").textContent = JSON.stringify(await r.json(), null, 2);
    }
  </script>
</body>
</html>
```

`docker compose restart nginx` 후 브라우저에서 `http://localhost:8080/static/` — 개미 사진을
올리면 화면에 0.7214가 뜹니다. 주소가 **하나**라는 것에 주목 — 페이지도 API도 8080이므로
fetch("/predict")에 호스트조차 필요 없습니다. 정적(nginx)과 동적(API)의 분업이 한 문 뒤에서
일어나는, 실서비스의 축소판입니다.

### Step 5. 과제 — 설정 전 지시어 주석 달기 (8교시)

`nginx/default.conf` 의 **모든 지시어**에 두 종류 주석을 달아 PR로 제출하세요:
`# 무엇: ...` 과 `# 없으면: ...` (이 지시어를 지웠을 때 벌어지는 일 — **실제로 지우고 실험한
결과**로 쓸 것). 최소 실험 3건 필수: ① proxy_set_header X-Forwarded-For 제거 → API 로그의
클라이언트 IP가 어떻게 변하나 ② client_max_body_size 제거(기본 1m) → 5MB 정상 업로드가
어떻게 되나 ③ proxy_pass의 대상을 `http://api:8000/` (끝 슬래시)로 → /predict 요청이 어디로
가나 (⑤ 첫 실수의 체험판).

## ⑤ 자주 하는 실수

### proxy_pass 끝의 슬래시 하나로 경로가 뒤바뀜

**증상** — `proxy_pass http://api:8000/;` (슬래시 추가) 후 404 폭발 — API 로그를 보면 경로가
잘려 도착.
**원인** — nginx의 오래된 함정: 끝 슬래시가 있으면 location 매칭 부분을 **잘라내고** 전달,
없으면 그대로 전달합니다. `location /` 에선 차이가 없지만 `location /api/` 등에서 정반대
결과가 납니다.
**해결** — 규칙을 하나로 통일해 기억: **"경로를 그대로 넘길 거면 슬래시 없이"** (`proxy_pass
http://api:8000;`). 라우팅이 꼬이면 nginx가 아니라 **API의 접근 로그에 찍힌 경로**부터
확인하세요 — 무엇이 도착했는지가 진실입니다.

### client_max_body_size 기본값(1MB)의 매복

**증상** — 어제까지 되던 5MB 업로드가 nginx 도입 후 413:
```
<html>...413 Request Entity Too Large...</html>
```
**원인** — nginx 기본 상한이 **1m**입니다 — 앱(8MB)보다 문지기가 먼저, 더 짜게 자릅니다.
**해결** — 앱의 계약과 **일치**시키기: `client_max_body_size 8m;`. 교훈은 일반형으로 —
프록시를 문 앞에 세우는 순간, 크기·시간(타임아웃)·헤더의 **기본값들이 새 병목**이 됩니다.
"앱 계약 ≤ 프록시 허용"을 점검표에 넣으세요.

### API의 ports를 남겨 둠 — 문 잠그고 창문 열기

**증상** — nginx로 다 정리한 것 같은데, 8000으로 직접 붙으면 여전히 응답 — 크기 제한도
로그도 우회됨.
**원인** — api 서비스의 `ports: ["8000:8000"]` 을 지우지 않음.
**해결** — 프록시 도입의 완성 조건은 **뒷문 폐쇄**입니다 (Step 2의 refused 확인이 그 검증).
"nginx의 제한이 잘 동작해요"는 뒷문이 없을 때만 의미 있는 문장입니다.

### 설정을 고쳤는데 그대로 — reload를 잊음

**증상** — default.conf 수정 후에도 옛 동작.
**원인** — nginx는 설정을 기동 시 읽습니다 (systemd의 daemon-reload와 같은 계열 —
[Day 113](day-113.md) ⑤).
**해결** — `docker compose restart nginx` (또는 무중단로는 `docker compose exec nginx nginx -s
reload`). 그 전에 `docker compose exec nginx nginx -t` 로 **문법 검사** — visudo가 sudoers를
지켜 주듯, -t가 문법 오류 반영으로 인한 문지기 사망을 막아 줍니다.

### X-Forwarded-For 없이 "모든 손님이 같은 IP"

**증상** — 접근 분석을 하려는데 API 로그의 클라이언트 IP가 전부 172.19.0.x (nginx의 내부 IP).
**원인** — 프록시가 새 연결로 전달하므로, 헤더로 옮겨 주지 않으면 원 발신자 정보가 소실.
**해결** — proxy_set_header 3종 세트를 표준 장착 (오늘 설정). 앱 쪽에서도 로그에 X-Forwarded-For
를 읽도록 한 줄 (uvicorn은 `--proxy-headers` 옵션) — 헤더는 **넣는 쪽과 읽는 쪽이 한 쌍**입니다.

## ⑥ 확인 문제

**Q1.** "양파 구조"(nginx만 노출 → API 내부 → DB 더 내부)를 보안 관점에서 정당화하되, 각 겹이
차단하는 구체적 공격·사고를 하나씩 드세요.

<details>
<summary>답 보기</summary>

nginx 겹: 대용량 요청(413)·느린 요청·비정상 프로토콜이 앱에 닿기 전에 반송 — 자원 고갈 공격의
1차 방어이고, 노출 포트가 하나라 공격면 자체가 최소화됩니다. API 겹(ports 없음): 검증·제한을
우회한 직접 호출이 불가능 — "프록시의 규칙 = 유일한 규칙"이 보장됩니다. DB 겹(가장 안쪽):
애초에 외부 스캔 대상이 아니므로 무차별 대입·유출 경로가 네트워크 층에서 차단 (Day 119 Q2).
각 겹은 "그 겹에서 가장 싸게 막을 수 있는 것"을 막는 분업입니다.

</details>

**Q2.** Step 3에서 같은 413인데 nginx는 HTML, API는 JSON으로 응답합니다. 클라이언트(예: 오늘의
데모 페이지) 입장에서 이 불일치가 일으키는 문제와 대응 방안을 쓰세요.

<details>
<summary>답 보기</summary>

데모 페이지는 `await r.json()` 을 하므로 nginx의 HTML 413에서 파싱 에러가 납니다 — 클라이언트가
"에러 응답도 JSON"이라는 API 계약을 믿었는데, 문지기의 반송은 그 계약 밖이기 때문입니다.
대응: ① 클라이언트가 상태 코드를 먼저 보고 본문 파싱은 Content-Type 확인 후 (견고한 클라이언트),
② nginx에 `error_page 413` + JSON 응답을 설정해 문지기도 계약에 맞게 말하게 하기. "경계를
넘는 순간 응답 형식의 주인이 바뀔 수 있다"는 것이 프록시 도입의 숨은 계약 변경입니다.

</details>

**Q3.** 업로드 상한 8MB가 현재 세 곳(팀 문서 · 앱 검증 · nginx)에 존재합니다. 셋이 어긋나면
어떤 증상이 나는지 조합별로 예측하고, 어긋남을 막는 실무적 장치를 제안하세요.

<details>
<summary>답 보기</summary>

nginx < 앱: 앱이 허용하는 크기가 문에서 반송 — 멀쩡한 요청의 오차단, 형식도 HTML이라 클라이언트
혼란 (오늘 ⑤의 매복). nginx > 앱: 대형 파일이 앱까지 와서야 413 — 문지기 무용지물, 부하 낭비.
문서만 다름: 팀원·클라이언트 개발자가 잘못된 기대로 구현. 장치: 상한을 **한 곳**(.env의
MAX_UPLOAD_MB)에서 선언하고 compose 치환으로 앱 환경 변수와 nginx 설정 템플릿에 함께 주입 +
경계값 테스트(8MB 통과·8MB+1 거부)를 CI에 넣어 어긋나면 빨간불이 켜지게 — "같아야 하는 값은
한 번만 적는다"입니다.

</details>
