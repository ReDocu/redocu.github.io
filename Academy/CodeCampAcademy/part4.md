# 제1부 · 살아 있는 PRD (Day 30)

### 1. 왜 업데이트인가 — 남는 건 디자인뿐, 그러나 디자인은 "왜"를 못 남긴다

> 팀장: *"저번에 회의할때, **Premium으로 구독하면 쿠폰 2개 주기로 했었나?**"*
> 팀원: *"기억이 잘 안나요. 나중에 쿠폰 주지 말자고 했던거 같은데… **PRD에 기록한 거 없어요?**"* — *"**PRD 최초에만 작성하고, 업데이트 안했을텐데…**"*

- 결정("쿠폰 2개")도 **번복**("이슈 있어 주지 말자")도 있었는데 **둘 다 어디에도 없다.** 디자인 툴은 **최종 상태만** 보여 준다 — 쿠폰 UI가 없는 게 *"처음부터 안 하기로"* 인지 *"하려다 뺐다"* 인지 구분할 수 없다.
- 판서 — **`기획(X) → 디자인(팩트) → 개발(X)`**. 디자인만 살아남는 이유는 **만들지 않으면 개발을 못 하기 때문**이고, PRD는 없어도 당장 굴러가서 제일 먼저 방치된다. 그런데 디자인은 **"무엇을"** 만 보여 주고 **"왜"** 를 못 남긴다.

> **디자인은 결과를 남기고, PRD는 이유를 남긴다. 이유가 사라진 팀은 같은 논쟁을 매번 처음부터 다시 한다.**

### 2. 최초 작성 7단계 → 업데이트 3단계, 그리고 `delta.txt`

| PRD 최초 작성 (7단계, Day 17) | PRD 업데이트 (3단계) | 도구 |
|---|---|---|
| 유저 인터뷰 → 인터뷰 요약 → 인사이트·전략 가정 → **전략 가정 공격** → 우선순위 추출 → 제품 브리프 → **PRD 생성** | ① **추가 기획 내용** | **수동작업** |
| | ② **전략 가정 공격** | **`/strategy-red-team`** |
| | ③ **PRD 생성** | **`/create-prd`** |

- **빠진 4개**(인터뷰·요약·우선순위·브리프)는 전부 "제품 전체를 처음 정의할 때" 하는 일 — **이미 한 번 했다.** 기능 하나 추가하겠다고 인터뷰를 다시 돌리지 않는다. 판서의 비유: 최초 작성은 큰 사각형(제품 전체)을 그리는 일, 업데이트는 그 안에 **상자 하나("캠핑")를 더 넣는** 일이다.
- **①만 사람이 한다** — 무엇을 만들지는 **결정이지 계산이 아니다.** AI에게 *"뭐 추가하면 좋을까?"* 를 묻는 순간 제품이 남의 것이 된다.
- ①↔②의 화살표는 **양방향**이다. 공격받으면 기획을 고치고, 고친 기획을 다시 공격한다 — **한 번 통과하는 관문이 아니라 왕복 루프.**
- 입력 파일은 **`delta.txt`** — 델타(δ)는 **변화량**. 제품 전체가 아니라 **"이번에 달라지는 부분"만** 담는다. 형식은 평범한 들여쓰기 목록이면 충분하고, **날짜 폴더로 쌓으면**(`20260813/delta.txt`) 그 자체가 기획 이력이 된다.

> **🧩 퀴즈** — 추가 기획으로 PRD를 업데이트하기 전, 기획을 공격하는 단계? → **전략 가정 공격(`/strategy-red-team`)** — 공격은 **문서에 넣기 전에** 한다.

### 3. `/strategy-red-team` — 공격의 6항목과 Kill criterion

| 항목 | 답하는 것 |
|---|---|
| **스틸맨** | 이 가정을 가장 강하게 옹호하면 어떤 논리인가 |
| **공격** | 그 논리를 어디서 깨는가 |
| **Fails if:** | **무엇이 사실이면** 이 가정이 무너지는가 |
| **이번 주 확보할 증거** | 지금 당장 찾아볼 수 있는 것 |
| **Kill criterion** | **어떤 결과가 나오면 이 기획을 죽이는가** |
| **가장 싼 테스트** | 최소 비용으로 판별하는 방법 |

- **"좋은 아이디어네요"로 끝나지 않는다.** 모든 섹션이 숫자와 기한으로 착지한다 — `전환 30% 미만`, `0/30`, `5분`, `30분`.
- **Kill criterion이 결정적이다** — 보통 기획서는 성공 조건만 쓴다. 실패 조건이 없으면 아무리 안 되어도 계속 붙잡게 된다.
- **공격이 기존 PRD 내부를 인용한다**(`PRD §6`, `KR0-2`, `Could 등급`) — AI가 살아 있는 PRD를 읽고 그 근거로 새 기획을 때린다. 방치된 PRD로는 이 공격이 성립하지 않는다.
- "가장 싼 테스트"가 실무적으로 가장 쓸모 있다 — *가짜문 실험이 결제 페이지 풀빌드보다 한 자릿수 이상 싸다.* **만들기 전에 알 수 있는 방법**을 매번 제시한다.

> **전략 가정 공격의 산출물은 "반대 의견"이 아니라 "판별 절차"다. 무엇이 사실이면 접을지, 그걸 얼마에 확인할 수 있는지까지 적혀야 쓸모가 있다.**

### 4. Change Log, 그리고 수업용과 포트폴리오용의 분리

```markdown
| 버전 | 날짜 | 변경 내용 |
| v1.0 | 2026-07-06 | 초판 — 6개 리서치 문서 종합 |
| v1.1 | 2026-08-13 | 20260813/delta.txt 반영: 구독결제·결제완료·마이페이지 추가
                     → §7.1 플로우, §7.2 MONETIZE, §7.3 결제 기술, §7.4 가정, §8, §9 갱신 |
```

- 오른쪽 칸이 핵심 — **무엇을 추가했는지 + 그래서 PRD의 어느 절이 바뀌었는지.** 기능 하나를 넣으면 **문서 여섯 군데**가 바뀐다. 손으로 하면 반드시 빠뜨리고, 그걸 `/create-prd`가 한다. 만화의 *"쿠폰 2개"* 문제가 이 표 한 줄로 해결된다 — 결정과 번복이 버전·날짜와 함께 남는다.
- ★ 판서 — *"앞으로 모든 답변은 1줄 요약으로. 자세히는 요청할 때만. **전역 메모리에 등록해줘.**"* Part 3의 `CLAUDE.md`가 프로젝트 단위 규칙이었다면 이것은 **사용자 단위 규칙**이다.
- **수업 vs 포트폴리오** — `/strategy-red-team`은 매번 다른 결과를 낸다. 수강생이 각자 돌리면 다음 수업(디자인·개발)이 성립하지 않는다. 그래서 **3단계 프로세스는 포트폴리오에 적용**하고, 수업은 **강사가 확정한 결제 기획 하나로 통일**한다. **학습용 프로세스와 진도용 결과물은 분리한다.**

# 제2부 · 결제를 그리고, 필드를 뽑고, 코드로 넘긴다 (Day 30~31)

### 1. 결제 기획 4페이지 — 배너에 새 역할을 준다 (Day 30)

| 페이지 | 내용 |
|---|---|
| **① 메인** | 상단 배너 **→ 강연/모임 결제 상품으로 활용** |
| **② 배너 상세** | 상품 이미지·설명·결제하기 → **결제 바텀시트**(참여자 수 / 최대 참여 가능 수 · 가격) |
| **③ 결제완료** | 결제 영수증 |
| **④ 마이** | **결제 내역 탭**(결제 취소) · **취소 내역 탭** |

- ①의 화살표가 이 기획의 전부다 — **이미 있는 UI에 새 역할을 준다.** 배너를 새로 만드는 게 아니다.
- 왜 모임/강연인가 — 맛집 커뮤니티는 음식을 파는 앱이 아니다. 식당 결제를 붙이면 제품 성격이 바뀌지만, **모임/강연은 커뮤니티의 연장선**이라 콘셉트를 깨지 않는다.
- 바텀시트의 **"참여자 수 / 최대 참여 가능 수"** — 결제 직전에 자리가 남았는지 보여 주는 **모임 결제 특유의 필드**다. 취소는 결제 내역 안의 상태가 아니라 **별도 탭**으로 갈랐다.

### 2. Pencil 증분 디자인 — 네 가지 지시 (Day 30)

```text
추가된 페이지를 새롭게 디자인해주고,
기존의 페이지에서 변경이 일어나는 페이지는 복사하고, 거기서 수정해줘.
디자인시스템(파운데이션, UI컴포넌트)은 새롭게 만들지 말고, 기존의 것들로만 재사용해서 만들어줘.
컴포넌트가 없는 경우에는 니가 마음대로 컴포넌트 만들지 말고 그냥 페이지에서 다이렉트로 만들어줘.
```

| # | 지시 | 의도 |
|---|---|---|
| 1 | 추가 페이지는 **신규 디자인** | 없던 화면 |
| 2 | 변경되는 기존 페이지는 **복사 후 수정** | **원본 보존** — 비교·롤백 가능 |
| 3 | 디자인 시스템은 **기존 것만 재사용** | 시스템 분열 방지 |
| 4 | 없는 컴포넌트는 **페이지에서 다이렉트로** | 3번의 **탈출구** |

- **4번이 3번을 실행 가능하게 만든다** — 금지만 있으면 AI는 막힌다. 그리고 **한 번만 쓰이는 UI는 컴포넌트가 아니다**(Day 29 "띠배너는 컴포넌트 재사용 X"와 같은 판단) — 재사용될 때 승격시키면 된다.
- 생성 후 **검토를 별도 턴으로** 돌린다 — *"지금 선택된 디자인들에 대해서 디자인시스템 반영 여부 재검토 해줘."* "지켜라"와 "지켰는지 확인해라"는 다른 작업이다.

### 3. 디자인에서 DB 필드를 뽑는다 — DB 생성 순서도 (Day 30)

```
기획/디자인 생성 → 데이터 추출 → 데이터 정규화 → DB 생성
```

- 완성된 화면(모임 상세·결제 바텀시트·결제 완료)에서 판서로 필드를 뽑는다 — **이름 · 설명 · 가격 / 최대수용인원 · 주소 · 날짜 / 상세사진 · 배너사진.** 화면에 보이는 것을 모으면 테이블 컬럼이 나온다.
- **사진이 두 개**인 것이 포인트다 — 메인 배너용과 상세페이지용은 **비율이 다르다.** 한 컬럼으로 합치면 하나가 깨진다.
- 정규화 결과는 **[상품]**과 **[결제]** 두 표 — 한 표에 넣으면 같은 상품을 여러 명이 결제할 때 상품 설명이 그 수만큼 복제된다. **`상품ID`**(FK)가 두 표를 잇고, 이미지는 파일이 아니라 **주소**로 저장한다.
- ★ 판서 — **"사장님"**: 상품은 누가 등록하나? ① 직접 DB에서 등록 ② 관리자사이트. 오늘 범위는 아니지만 *"이 데이터는 어디서 오는가"* 를 짚지 않으면 시드로만 도는 **데모**가 된다.

> **디자인을 먼저 확정하면 DB 스키마는 받아 적기가 된다. 반대로 하면 화면이 스키마에 끌려다닌다.**

### 4. Node ID 증분 핸드오프 (Day 30)

```text
PencilMCP를 사용해서 추가로 디자인된 다음의 페이지들은 모두 핸드오프해줘.
1. 메인페이지의 배너 디자인 ⇒ Node ID: A6m8j
2. 배너 상세페이지 디자인 ⇒ Node ID: t9wOu
…
5. 마이페이지 결제내역 탭 ⇒ Node ID: oS6oz (프로필 설정은 닉네임 우측 연필을 누…)
8. 마이페이지 프로필 설정 활성화 ⇒ Node ID: O0hO6i
해상도 및 디자인시스템 가이드는 CLAUDE.md에 있으니 확인하고 진행해줘.
```

- **Node ID 8개를 전부 명시** — 이름으로 부르면 AI가 아트보드를 찾다가 틀린다. ID를 주면 **탐색이 사라진다.**
- 디자인 4항목이 핸드오프 **8항목**으로 늘었다 — 마이 페이지는 **탭 세 개가 한 화면**이라 하나만 바뀌어도 나머지 탭(내가 쓴 글·프로필 설정)을 함께 넘겨야 일관된다.
- **정적 이미지로 전달되지 않는 인터랙션은 괄호 주석으로 보충**한다(*"닉네임 우측 연필을 누르면…"*). 해상도·디자인 시스템 규칙은 프롬프트가 아니라 **`CLAUDE.md`에 두고 참조**시킨다.
- AI의 작업 계획 — **파악(코드베이스·Next 문서·Supabase 스키마) → DB 스키마+시드 → BFF 라우트(events/payments) → 스토리 → 화면 구현.** 기존 제품에 얹는 작업이라 첫 항목이 "파악"이고, 순서는 Day 24~25의 BFF 패턴 그대로다.

### 5. 핸드오프 결과 점검 — 초보 디자인과 인터랙션 지시 (Day 31)

> ★ 판서 — 돌아가는 자기 화면 위에 **"초보디자인"**: **① 타이포그래피 ② 레이아웃, 간격 ③ 사진, 컨텐츠** (④는 미기재)

- **핸드오프는 끝이 아니라 시작이다.** AI가 만든 화면은 "돌아가는 상태"이지 "완성 상태"가 아니다. 셋 중 첫인상을 가장 크게 좌우하는 것이 **사진** — 해법 판서가 **`unsplash`**(무료 고화질 사진)다.
- **디자인 파일은 "상태"를 담고, 지시문은 "동작"을 담는다** — *"상세페이지 사진 스와이핑 처리해줘"*, *"핀치줌 인/아웃"*(양방향 — 확대만 되면 갇힌다). 정적 디자인에 없는 것은 반드시 말로 채운다.
- 레퍼런스(NOL) 읽는 법 — 색·사진을 지우고 구조로 환원한다: **파란 상자 = 고정(헤더·탭바), 빨간 상자 = 스크롤 영역.** 배너의 `6 / 15 +`와 ⏸ — 배너는 여러 장이 회전하고 사용자가 멈출 수 있다.
- **"카드 디자인 X"** — 목록 항목마다 테두리·그림자 카드를 두르면 **상자 안의 상자 안의 상자**가 된다. 연한 구분선이면 충분하다. Day 30의 "컴포넌트 만들지 말고 재사용"과 결이 같다 — **덜 만드는 쪽이 낫다.**

# 제3부 · 팔리게 만든다 — 카피·CTA·모바일 배너 (Day 31)

### 1. 알 수 없는 대화 — 카피와 CTA

> 마케터: *"이번에 괜찮은 **카피**가 나왔어! **모바일 배너**에 반영해줘!"* / 디자이너: *"좋은 소식이네요! **CTA**도 알려주세요!"*

| | **카피** | **CTA (Call To Action)** |
|---|---|---|
| 정의 | **마케팅 광고/홍보 문구** | **클릭 유도 버튼(문구)** |
| 예시 | *"아직도 고민 중이신가요?"* (질문형) | **[지금 바로 할인받기]** (명령형) |
| 역할 | **마음을 움직인다 — 묻는다** | **손가락을 움직인다 — 시킨다** |

- 둘은 사슬로 묶인 **한 쌍**이다 — 카피만 있으면 감탄하고 끝, CTA만 있으면 왜 눌러야 하는지 모른다. **카피라이팅**은 카피를 작성하는 **행위**(카피는 결과물).
- 협업 구조: **마케터 →(카피·CTA 딱 두 개)→ 디자이너 → 배너.** 이미지·색·배치는 전부 디자이너의 몫 — **역할 경계가 분명하다.**

> **🧩 퀴즈** — 배너 협업을 위해 마케터가 디자이너에게 전달하는 것 2가지? → **카피 · CTA**

### 2. 배너 2종과 AI 느낌 피하기

| | **① 사진** | **② 3D 일러스트 아이콘** |
|---|---|---|
| 기준 | **상품/실물 O** (예: 콜라 캔 실사) | **상품/실물 X** (예: 3D 도시락, 투명 배경) |

- 선택 기준은 딱 하나 — **팔 물건의 실물이 있는가.** 실물이 있으면 사진이 이긴다(콜라를 3D로 그리면 가짜처럼 보인다). 실물이 없으면(강연·모임·서비스) 찍을 게 없으니 3D 아이콘이 답이다. 우리 결제 상품(요리 수업·미식 모임)은 실물 X → **3D 아이콘.**
- **AI 느낌 피하기** — 🐶 *"사람 디자이너도 실존하는 상품·꽃·음식을 직접 그리지 않아요. AI도 사람 디자이너라고 생각하면, **실제 사진**을 사용함으로써 AI 느낌을 피할 수 있어요."* "AI가 그린 티가 난다"는 문제를 **"애초에 그리게 하지 말라"** 로 푼다. ①·②는 모순이 아니다 — 실존하는 것은 사진, 존재하지 않는 것만 그리게 한다.

### 3. 배너 생성 실습 — 프롬프트 5요소

디자인 순서: **투명 배경 소재 3종**(3D 도시락·초밥·케첩/마요네즈) + **빈 배경**(아이보리 질감) → 합성. 소재와 배경을 따로 두면 나중에 **한쪽만 갈아 끼울 수 있다**(시즌 배너·다른 상품 배너).

```text
모바일 배너디자인 만들어줘.
1. 사이즈: 360 * 180
2. 카피: 심심한 주말 놓치기 아까운 기회
3. CTA: 요리 수업 알아보기
4. 폰트: 프리텐다드
4. 구현:
- 배경 위에 이 아이콘들을 배치
- 아이콘들 중 절반은 배너 밖으로 나가서 잘리도록 유도
- 과하게 넓은 여백
```

- 구조가 협업 과정 그대로다 — **카피·CTA는 마케터에게 받은 것, 사이즈·폰트·구현은 디자이너가 정하는 것.** 사이즈 `360*180`은 Day 18의 기준 폭 360px에 맞춘 2:1이다.
- **"절반은 배너 밖으로 잘리도록"** — 프레임에 딱 맞으면 정물 사진, 잘려 나가면 장면의 일부처럼 보인다(공간이 이어지는 착시). **"과하게 넓은 여백"** — 그냥 "넓은"으로는 부족하다. AI도 사람처럼 여백을 채우려는 경향이 있다.
- 같은 프롬프트를 **두 모델**(ChatGPT 이미지 2.0 / 나노바나나2)에 돌린다 — 이미지 생성은 편차가 커서 여러 모델에 넣고 고르는 것이 실무다. 그리고 **모바일 배너와 데스크톱 배너는 따로 만든다** — 폭이 다르면 다시 만든다.

**마지막 갈림길 — 글자를 어디에 둘 것인가**

| | **① 배경이미지 + 코딩글자** | **② 이미지에 글자 포함**(오늘 실습) |
|---|---|---|
| 문구 수정 | 코드만 고치면 끝 | 이미지 재생성 |
| 다국어·반응형·접근성 | 텍스트 교체·줄바꿈·읽힘 | 언어 수만큼 이미지·잘림·안 읽힘 |
| 디자인 자유도·제작 | 제한적 · 두 단계 | 높음(글자·소재 겹침) · 한 번에 |

- 검증용 한 장은 ②가 빠르지만, NOL처럼 배너 15장이 도는 서비스라면 매번 이미지를 굽는 것과 배경+코드 텍스트는 **운영 비용이 완전히 다르다.**

# 제4부 · 돈의 흐름 — 정산, 결제 링크, 결제 시스템의 구조 (Day 32)

### 1. 정산 — 결제 ≠ 입금

> 사장님: *"유저들이 **결제한지가 언젠데**, 아직도 **정산이 안됐어?**"* / 직원: *"유저가 결제하면 **통장에 돈 들어오는거 아니었어요?**"*

- **돈은 사장님에게 직행하지 않고 결제사 서버에 쌓인다**(사장님 아이콘에 빨간 ✕). 취소·환불·사기 대응 때문이다 — 결제 직후 돈이 흩어지면 환불 요청 시 회수할 방법이 없다.
- **정산 = 판매금액 − 수수료의 합계를 정해진 주기에 지급하는 것.** 1,000원 − 100원 = 900원, 500원 − 50원 = 450원 → 정산 예정 금액 **1,350원.** 주기는 1일/2일/주단위/월 2회/월 1회 — 짧을수록 사장님 현금 흐름에, 길수록 결제사의 리스크 흡수에 유리한 **계약 조건**이다. **"오늘 판 돈은 오늘 못 쓴다"** — 이걸 모르고 자금 계획을 세우면 흑자 도산이 난다.
- 플랫폼이면 받은 정산금을 입점 업체에 나눠 주는 **2차 정산**이 생기고(우리 책임), 그 부담을 결제사에 넘기는 것이 **지급대행 서비스**다.

> **🧩 퀴즈** — 결제한 돈에서 수수료 차감 등을 진행해 최종적으로 받을 돈을 확정하는 일? → **정산**

### 2. 결제 프로세스 두 갈래 — "클로드가 못해주나?"

> 사장님: *"결제 시스템 아직 안됐어? **클로드가 못해주나?**"* / 직원: *"**구현이 전부가 아니에요.** 사업자 등록, 통신판매업 신고, PG 가입, 카드사 심사도…"*

- **코드는 AI가 짜 준다. 그러나 결제는 코드가 전부가 아니다** — 나머지 넷(사업자 등록 · 통신판매업 신고 · PG 가입 · 카드사 심사)은 **행정·계약·심사**다.

| | **① 결제 링크 생성** (페이앱) | **② 결제 시스템 구축** (포트원) |
|---|---|---|
| 특징 | **10분내 실 결제 연동** | 일반적인 결제 시스템 |
| 단계 | **아이디어 검증 단계** | **본격적인 판매 단계** |
| 준비물 | 사업자등록 X · 통신판매업 신고 X · 구축 X | 전부 O |
| 철학 | **"먼저 팔고, 팔리면 나중에 계약서 작성"** | 결제 → 내역 조회 → 취소/환불 3시스템 |

- ①의 구조 — 파는 데는 계약서가 필요 없고, **돈을 받는(정산) 시점에 계약서를 쓴다.** 안 팔리면 계약서 쓸 일도 없다 — **검증 비용이 0에 수렴**한다. Day 30 `/strategy-red-team`의 "가장 싼 테스트"와 같은 철학.
- ②의 각주 — 취소/환불 시스템은 **초반 생략 가능(관리자 콘솔 수동 취소).**

### 3. 결제 링크 실습 — 원페이지, 원샷 개발

```
결제 링크 생성 → 링크 복사·QR 다운로드 → 상품 사이트에 연동 → 결제 및 정산
```

- 페이앱 폼은 **딱 세 칸** — 상점명 `맛집커뮤니티` · 상품명 `주말 요리 교실` · 가격 `1000`(`;` 구분 다중 금액으로 구매자 선택형 가능, 1,000원 이상). 이것이 "10분내"의 실체다. 링크 하나(`payapp.kr/L/…`)가 결제창 전부를 대신하고 QR은 `png`/`eps`(인쇄용 벡터)로 나온다.
- 판매 사이트 프롬프트 — *"아이디어 검증을 위한 상품 판매 사이트… **디자인은 테스트 용이므로 니가 임의로** … **결제창은 팝업창으로** … 결제하기(링크) + QR결제하기."* Day 30의 디자인 시스템 강제와 정반대다 — **검증용 일회성 사이트라 규칙을 풀었다. 목적이 다르면 규칙도 다르다.** Day 31의 배너가 상품 이미지로 재사용된다.
- 결과는 **주말요리클럽 원페이지**(~~39,000원~~ → 1,000원) — ★ 판서 **"원페이지 / 원샷 개발".** 읽고 → 설득되고 → 결제까지 한 흐름. **버릴 수 있는 것은 빨리 만든다.**
- 실제 1,000원을 결제하니 관리자 화면에 — 상태 **미정산**, **정산 예정금액 956원**(수수료 44원). **정산 개념이 실물로 확인된다.** 상세 행의 [취소] 버튼이 곧 "초반 수동 취소"다.

### 4. 일반 결제의 구조 — 3층, 연동 4단계, 웹훅

- 복습 — **결제 검증·저장은 반드시 서버(BFF)에서.** 브라우저를 믿으면 안 된다(Day 24).
- **3층 구조** — **카드사**(승인: 신한·하나·국민…) ← **PG사**(카드사 묶음: 나이스페이·KG이니시스…) ← **결제솔루션**(PG 묶음: **포트원**) ← 내 서비스. 코드는 포트원 하나만 붙이고 어느 PG로 보낼지는 설정으로 갈아 끼운다.
- **연동 순서 4단계** — ① 결제 정보 → 포트원 ② 결제창에서 결제 완료 ③ 포트원이 **`결제ID(Bq2k)`** 반환 ④ 프론트엔드 서버가 **Supabase 결제 테이블에 저장.** ★ 판서 **"1주일"** — PG 계약·심사에 걸리는 시간. 코드는 하루면 붙는데 계약이 1주일이다.
- **웹훅 API** — ③이 브라우저 경유라면, 웹훅은 **포트원이 내 서버(BFF API)를 직접 호출**하는 별도의 길이다. 유저가 결제 직후 브라우저를 꺼 버리면 ③④가 유실된다 — 웹훅은 서버 대 서버로 결제 사실을 통지하는 **최후의 보루**다.
- `PortOne.requestPayment()` — **`paymentId`는 우리가 만들어 보내는 ID**이고, 같은 ID로는 최종 결제 성공이 단 한 번만 가능하다(**중복 결제 방지**). 모바일은 앱 전환·페이지 이동으로 콜백이 못 돌아올 수 있어 **`redirectUrl` 필수** — 결과는 쿼리 문자열로 온다.

### 5. 정기 결제 — 빌링키와 결제 예약

```
카드번호 → (한 번 입력) → 빌링키       /       빌링키 발급 → 결제 예약
```

- 정기 결제의 본질은 **"카드 정보를 매달 다시 묻지 않는 것"** — 카드번호를 **빌링키**(결제가 가능한 키)로 바꿔 저장하고 이후 키로만 결제한다. **카드번호는 우리 DB에 저장하지 않는다** — 남는 것은 빌링키와 표시용 마스킹(`신한` / `**23`)뿐.
- **결제하면서 다음 결제를 예약한다** — 결제 성공 시점에 **다음결제예약일 = 만료일 + 30일(UTC)** 을 다시 건다. 매달 크론잡이 아니라 **꼬리물기**가 엔진이다. UTC가 실무 포인트 — 한국 시간으로 계산하면 9시간 밀린다.
- 포트원 콘솔은 **테스트 모드**를 제공한다 — PG 계약 "1주일"을 기다리지 않고 연동 개발을 먼저 끝낼 수 있다.
- 마지막 경고 — **"빌링키는 정기 구독에만 사용 가능."** 우리 서비스에 대입하면: 프리미엄 구독은 빌링키, **모임 건별 결제는 일반 결제.**

> **🧩 퀴즈** — 카드 정보를 입력하여 받을 수 있는 결제가 가능한 키? → **빌링키** (판서: *빌링키 → "밀어서 결제하기"* — 간편결제의 원리)

# 제5부 · 고치지 않는 장부 — 결제 DB 설계와 포트원 실연동 (Day 33)

### 1. 시트가 실전 스키마가 된다

DB 생성 순서도의 **데이터 추출·정규화**가 오늘 실행된다 — 화면을 보고 스프레드시트에 적고, 정규화한 뒤 테이블을 만든다.

- **[상품]** — Day 30의 이미지 2컬럼이 **4컬럼**(큰/작은 × 배너/상세, `스토리지주소1~4`)으로 갈라졌다. 데스크톱과 모바일의 해상도가 달라 **한 이미지를 늘리는 대신 두 벌을 저장**한다. **`공개상태(Public)`** 도 새로 붙었다 — 상품을 지우는 대신 **내린다**(결제 기록이 참조하는 상품은 지우면 안 된다. Day 25 소프트 삭제의 철학).
- **[유저] — Supabase** — 인증이 이미 관리하므로 **참조만** 한다.

### 2. insert-only 원장 — 음수 행, 스냅샷, 트랜잭션키

**[결제]** 표 위에 적힌 한 줄: **`insert-only / append-only`**

| ID | 트랜잭션키 | 타입 | 금액 | 스냅샷ID |
|---|---|---|---|---|
| PAY001 | 포트원결제키값**A** | 결제완료 | 30000 | S001 |
| PAY002 | 포트원결제키값**A** | 취소완료 | **−30000** | S002 |
| PAY003 | 포트원결제키값**B** | 결제완료 | 30000 | |

- **결제 테이블은 수정·삭제하지 않는다. 오직 추가만.** 취소는 PAY001을 고치는 게 아니라 **반대 부호의 새 행**이다 — 두 행을 합산하면 0, **회계 장부 방식**이다. 돈의 기록은 "지금 상태"보다 **"무슨 일이 있었나"** 가 중요하다. 행을 고치면 분쟁 시 되짚을 역사가 없다.
- **[결제스냅샷]** — 결제 당시의 카드·영수증 + **상품 이름·내용·가격을 JSON으로 통째로 보존.** 상품은 나중에 바뀔 수 있다 — 석 달 뒤 환불 분쟁에서 [상품] 표에는 바뀐 가격이, 스냅샷에는 **결제한 그날의 가격**이 있다. [결제]는 `스냅샷ID`로 참조만 — 정규화(중복 제거)와 보존(스냅샷)을 양쪽 다 챙긴다.
- **트랜잭션키** — 결제와 그 취소는 **같은 키(A)** 로 묶이고(한 결제 건의 생애), 재결제는 **새 키(B)** 다. 이 구분이 없으면 환불 대사가 불가능하다.

> **결제 데이터는 고치지 않고 쌓는다. 취소는 음수 행, 과거는 스냅샷, 건의 정체성은 트랜잭션키 — 이 셋이면 어떤 분쟁에도 장부를 다시 그릴 수 있다.**

### 3. Supabase 6테이블, default value의 자리

- 시트의 표가 그대로 테이블이 됐다 — 신규 **`product`(11) · `payment`(8) · `payment_snapshot`(3)** + 기존 `place` · `place_image` · `profile` = **6 tables.**
- ★ 판서 — default value를 어디에 둘 것인가: **① Supabase에서**(*"당장은 이게 좋음"* — 클릭 몇 번) **② 코드로**(*"AWS 같은 데로 옮길 걸 생각하면 이게 좋음"* — DB를 옮겨도 로직이 따라간다).
- 옆 브라우저에 **"int2 범위" 검색**(smallint: −32,768~32,767) — 타입을 고르기 전에 **범위를 실제로 확인**하는 습관.
- 상품 조회 프롬프트 — **lg = 데스크톱, md = 모바일·태블릿** 두 벌, 상세 이미지는 unsplash에서. **"주소의 앞단은 환경변수, 뒷단은 DB 컬럼"** — DB에는 경로 뒷부분만 저장하고 호스트는 환경변수로 조립한다. **스토리지를 옮겨도 DB는 한 줄도 안 바뀐다.**

### 4. PortoneMCP — 요청 정보·환경변수·결제 SSOT

```
▶ 상세 과정:  결제 요청 정보 정리 → 결제 환경변수 설정 → SSOT 규칙 생성(rules/payment.md) → 웹훅 수신 및 DB 저장
```

- 설치는 공식 가이드 URL + *"이 가이드를 참고해서 포트원MCP를 설치해줘"* — 설치 방법을 외울 필요가 없다. PencilMCP · SupabaseMCP에 이은 **MCP 셋째 멤버**(16 tools).
- **포트원 SDK 놀이터**에서 코드 모양을 확정하고, 값 자리에 "무엇을 넣을지"를 한국어로 채워 넘긴다 — **리터럴이 아니라 규칙을 넘기는 프롬프트**:

```text
PortOne.requestPayment({
    paymentId: uuidv4 생성,
    orderName: DB에서 조회된 상품명 등록,
    totalAmount: DB에서 조회된 상품가격 등록,
    redirectUrl: 결제완료페이지,
    customData: { productId: 상품ID, userId: 회원ID }
});
환경변수로 분리가 필요한 부분은 .env.example에,
모든 결제 관련 규칙은 rules에 SSOT로 사용할거야.
```

- **`orderName`·`totalAmount`를 DB에서 조회**하게 한 것이 보안의 핵심 — 브라우저가 보내는 금액을 믿으면 **1원 결제 조작**이 가능하다. 가격의 출처는 언제나 서버의 `product` 테이블이다. **`customData`** 는 웹훅이 돌아왔을 때 어느 상품·어느 회원의 결제인지 되찾는 연결 고리.
- 환경변수 2분법(Day 26~27의 재확인) — `NEXT_PUBLIC_PORTONE_STORE_ID` · `CHANNEL_KEY`는 **공개 식별자**(브라우저 결제창에 어차피 쓰인다), **`PORTONE_V2_API_SECRET`은 서버 전용**(`serverEnv.ts`로만 접근 — 이게 있으면 결제 조회·취소가 가능하다).
- **`rules/payment.md`(결제 SSOT)** — *"결제와 관련된 모든 규칙은 **이 문서가 유일한 기준**이다. 결제 코드를 추가·수정하기 전에 반드시 이 문서를 따르고, **규칙이 바뀌면 이 문서를 먼저 고친다.**"* 버전(`v1.2 — 결제창 실연동, 결제 백엔드 없음`)까지 붙는다 — **아직 안 된 것까지 명시**한다. Day 22 SSOT가 결제 도메인으로, Day 30 "문서가 죽으면 기억이 사라진다"가 코드 레벨로 내려온 것이다.
- 결과 — 앱 안에서 결제창이 뜬다(테스트 모드, Day 32 결제 링크의 외부 페이지와 결정적으로 다른 지점). 콘솔에는 **결제완료 1 · 결제실패 3** — 연동은 한 번에 성공하지 않았고, **실패 이력까지 콘솔에서 전부 조회**된다. 이것이 결제 관제의 실물이다.

# 제6부 · 끝까지 책임진다 — 웹훅·내역 조회·취소 (Day 34)

### 1. 웹훅은 localhost에 오지 않는다

```
포트원 ③(결제ID: Bq2k)→ https://mysite.com (Vercel의 BFF API)   ← 도달 O
포트원 ③(결제ID: Bq2k)→ http://localhost:3000 (내 컴퓨터 BFF)   ← 도달 X
```

- **웹훅은 포트원 서버가 인터넷을 통해 호출한다.** `localhost:3000`은 내 컴퓨터 안에서만 유효한 주소라 포트원이 찾아올 수 없다. 그래서 웹훅만은 로컬에서 완결 테스트가 불가능하고, **순서도의 마지막이 반드시 "웹훅 API 배포"** 가 된다.
- ★ 판서 — 테스트의 경계선: **화면·결제까지는 로컬 OK**(브라우저 → 포트원 방향은 어디서든 된다), **웹훅부터는 프로덕션 필요**(포트원 → 우리 서버 방향은 공인 주소가 있어야 한다). **기능은 로컬에서 만들고, 웹훅 검증은 배포해서 한다.**
- 웹훅을 받는 곳은 별도 백엔드가 아니라 **프론트엔드 서버 안의 BFF API** — Day 24의 결정이 결제까지 이어진다.

### 2. 웹훅 API 구현 — 프롬프트 3원칙과 두 개의 비밀키

```text
PortoneMCP를 사용해서 BFF기반으로 결제 웹훅을 구현해줘.
1. insert-only 방식으로 결제/취소를 type 컬럼으로 구분하고 transaction_key를 그룹키로.
   transaction_key는 웹훅으로 전달받는 포트원의 payment_id를 사용해줘.
2. 중복결제를 반드시 검증해줘.
3. amount는 결제시 + 부호, 취소시 - 부호로 저장할거야.
결제 규칙 SSOT는 rules/payment.md에 있어. 이걸 먼저 확인하고 구현해줘.
다 끝나면 현재까지의 규칙도 추가하고, 200줄이 넘어가면 핵심 위주로 정리해줘.
```

- 1·2·3이 전부 **Day 33의 데이터 설계 언어**다 — 프롬프트가 설계 문서를 코드로 번역시킨다. **"중복결제 검증"** — 웹훅은 재발송될 수 있다. 같은 통지가 두 번 와도 원장에 두 줄이 생기면 안 된다.
- SSOT 운영법의 완성형 — **먼저 확인하고 구현 → 끝나면 규칙을 문서에 반영 → 200줄 넘으면 다이어트.** 문서는 읽기만 하는 게 아니라 **자라고, 다이어트도 한다.**
- AI에게 엔드포인트를 되물어(*"우리 BFF 웹훅 API 엔드포인트가 뭐야?"*) 포트원 콘솔에 등록한다 — `https://food-community.shop/api/portone/webhook` (결제모듈 **V2** · 테스트 모드).

| 새 환경변수 | 용도 |
|---|---|
| `PORTONE_WEBHOOK_SECRET` | **"이 통지가 진짜 포트원에게서 왔는가"** — 웹훅 서명 검증. 없으면 아무나 가짜 결제 통지를 쏠 수 있다 |
| `SUPABASE_SERVICE_ROLE_KEY` | **RLS를 우회하는 서버 전용 키.** 웹훅 요청에는 로그인한 사용자가 없다 — 세션 기준 RLS로는 원장을 못 쓴다. **절대 클라이언트 노출 금지**(노출되는 순간 DB 전체가 열린다) |

- **환경변수는 로컬과 Vercel 양쪽에** — 웹훅을 실제로 받는 곳은 Vercel 위의 서버다. 배포 환경에 등록하고 재배포해야 웹훅 API가 살아난다.
- 콘솔에는 **웹훅 발송 이력과 [재발송] 버튼**이 있다 — 우리 서버가 죽어서 못 받았어도 다시 쏠 수 있다. 결제 기록을 놓치지 않는 마지막 안전망. 결과: `payment`·`payment_snapshot`에 **첫 실데이터** — 이 행을 쓴 것은 사람도 결제 버튼도 아니고 **웹훅**이다.

### 3. 결제 내역 조회와 취소의 분류학

- 마이페이지 결제 내역 탭이 **진짜 원장(payment)** 과 연결됐다 — 날짜·상품명·주소는 전부 **결제스냅샷**에서 온다. 상품이 나중에 바뀌어도 이 카드에는 결제한 그날의 정보가 남는다. 통합 프롬프트의 구조 — **현재 상태 요약 → 요구(조회+취소, "다른 모든 API들과 마찬가지로 BFF를 통해서") → 예상되는 후속**(*"지금은 결제 웹훅만 만들어놨어. 따라서 결제취소 웹훅도 만들어줘야돼"*). **시스템의 빈칸을 아는 것은 설계를 아는 사람의 몫이다.**

> 👦 *"1건 결제하고 취소했는데, **결제 테이블에는 왜 2건이 들어가있지?**"* → *"그건 버그가 아니야, **insert-only (append-only) 방식**이야"* — **수정이 안 된 것이 아니라, 수정하지 않는 것이 설계다.**

| 취소의 분류 | 내용 |
|---|---|
| **일반(1회성) 결제 취소** | 우리 모임 상품 — 취소 웹훅으로 **음수 행 추가** |
| 정기 취소 ① **전체 취소** | 이번달 결제 취소(환불) **+** 다음달 예약 취소(구독 중지) |
| 정기 취소 ② **예약만 취소** | 다음달 예약만 중지 — **돈 이동 없음 → 결제 테이블에 새 행 없음** |

- **원장은 돈의 사건만 기록한다.** "다음 달부터 안 쓸게요"는 예약 상태 변경일 뿐 회계 사건이 아니다. 구독 서비스의 "해지해도 이번 달 말까지 이용 가능" 정책이 바로 ②의 구조다.
- 취소 구현 결과 — 확인 모달 → 토스트 *"결제를 취소했어요. **환불까지 3–5일** 걸릴 수 있어요."*(Day 30 디자인의 그 문구가 실제로 살아났다) → 결제 내역 0건, 취소 내역 탭으로 — 조회 화면은 원장의 `type`을 읽어 분류할 뿐이다.

> **🧩 퀴즈** — 취소 시 해당 건을 수정하지 않고 1줄 더 등록하는 로그 형태의 방식? → **insert-only (append-only)**

### 4. 취소 웹훅 — SSOT 세 줄 프롬프트, 원장의 완성

```
▶ 상세 과정:  포트원 결제 취소 연동 → 웹훅 API 구현 → 웹훅 API 배포   (환경 변수 설정 단계가 없다!)
```

- 결제 웹훅 순서도와 비교하면 **환경변수 단계가 빠졌다** — 시크릿들은 결제 웹훅 때 이미 만들었다. **인프라는 한 번 깔면 다음 기능이 공짜로 탄다.**

```text
BFF기반의 결제 취소 기능을 완성했어.
이어서 PortoneMCP를 사용해서 BFF기반으로 결제 취소 웹훅을 구현해줘.
결제 규칙 SSOT는 rules/payment.md에 있어. 이걸 먼저 확인하고 구현해줘.
```

- 결제 웹훅 프롬프트에 있던 insert-only·transaction_key·부호 규칙이 **여기엔 없다** — 이미 전부 SSOT에 들어 있다. **"SSOT를 먼저 확인하고 구현해줘" 한 줄이 규칙 열 줄을 대신한다. 문서에 투자한 것이 프롬프트 길이로 회수되는 순간이다.**
- 같은 웹훅 URL로 결제 통지도 취소 통지도 온다 — **엔드포인트는 하나, 이벤트 타입으로 분기.**

**최종 원장** — 프로덕션 `payment` 테이블:

| transaction_key | type | amount |
|---|---|---|
| `32af2cff-…` | PAYMENT | 30000 |
| `32af2cff-…` | **CANCEL** | **−30000** |

- **Day 33 시트의 PAY001/PAY002 표가 그대로 프로덕션 DB가 됐다.** 같은 그룹키, 반대 부호, 합산하면 0. `payment_snapshot`에도 결제 시점과 취소 시점의 스냅샷이 각각 남았다 — "취소 당시 상품이 어떤 상태였나"까지 보존된다.

# 닫는 글

- **제1부** PRD는 최초 작성으로 끝나지 않는다 — 디자인은 결과만 남기고 "왜"는 못 남기므로, 방치된 PRD는 팀의 기억을 통째로 지운다. 업데이트는 7단계가 아니라 **3단계**(delta → `/strategy-red-team` → `/create-prd`)면 되고, 공격의 산출물은 반대 의견이 아니라 **판별 절차**(Fails if · Kill criterion · 가장 싼 테스트)다. 결정과 번복은 Change Log에 버전·날짜와 함께 남긴다.
- **제2부** 새 기획은 **이미 있는 UI에 새 역할을 주는 것**부터 검토한다(배너 → 결제 상품). 디자인은 복사 후 수정·시스템 재사용만·없으면 페이지에서 다이렉트로, 핸드오프는 이름이 아니라 **Node ID**로. 디자인을 먼저 확정하면 DB 스키마는 받아 적기가 된다. 그리고 핸드오프는 끝이 아니다 — 타이포·간격·사진을 다시 보고, 스와이핑·핀치줌 같은 **동작은 말로 채운다.**
- **제3부** 마케터가 디자이너에게 넘기는 것은 **카피와 CTA** 딱 둘 — 카피는 묻고, CTA는 시킨다. 배너는 실물이 있으면 사진, 없으면 3D 아이콘이고, AI 느낌은 "실존하는 것을 그리게 하지 않는 것"으로 피한다. 여백은 "과하게 넓게", 소재는 프레임 밖으로 자르고, 문구가 자주 바뀔 배너라면 배경+코딩글자를 검토한다.
- **제4부** **결제 ≠ 입금** — 돈은 결제사에 모였다가 수수료를 떼고 주기적으로 온다(정산). 비즈니스 검증 전에는 시스템을 짓지 말고 **결제 링크로 먼저 판다**("먼저 팔고, 팔리면 계약서"). 본격 시스템은 카드사 ← PG ← 결제솔루션의 3층이고, 검증·저장은 BFF에서, 유실 대비는 웹훅으로, 구독은 빌링키(정기 전용)로 한다.
- **제5부** 결제 데이터는 **고치지 않고 쌓는다** — 취소는 음수 행, 과거는 스냅샷, 건의 정체성은 트랜잭션키. 금액·상품명은 브라우저가 아니라 **DB에서 조회**하고(1원 결제 조작 방지), 키는 공개 식별자와 서버 전용으로 가르고, 결제 규칙은 **`rules/payment.md`(SSOT)** 한 곳에 둔다 — 규칙이 바뀌면 문서를 먼저 고친다.
- **제6부** **웹훅은 localhost에 오지 않는다** — 화면·결제는 로컬에서, 웹훅 검증은 배포해서 한다. 서명 검증과 서비스 롤 키 없이는 원장을 지킬 수 없고, 웹훅은 재발송되므로 중복을 검증한다. 취소도 수정이 아니라 추가이며, 돈이 움직이지 않은 사건(예약만 취소)은 원장에 쓰지 않는다. 그리고 두 번째 웹훅부터는 **SSOT 한 줄이 규칙 열 줄을 대신한다.**

> **한 문장 요약** — *살아 있는 PRD에 델타를 붙여 공격으로 검증하고, 기존 UI에 새 역할을 주어 디자인·핸드오프하고,
> 카피와 CTA로 팔 준비를 한 뒤 결제 링크로 가장 싸게 검증하고, 팔리면 insert-only 원장 위에 포트원을 실연동해
> 웹훅과 취소까지 책임져라 — 결제는 코드가 전부가 아니고, 돈의 기록은 고치는 것이 아니라 쌓는 것이다.*
